00结论摘要

Bottom line

可行，且瓶颈不在我们以为的地方。探针实测：增量同步在 5000 种子规模下每轮只需约 3–5 毫秒，完全不是瓶颈；真正的压力集中在两处 —— 首轮灌入（实测 14–17 秒主循环停摆；W0 推算的 34 秒偏高）与 任务队列吞吐（实测 10.6 任务/秒，被 max_tasks_per_tick=20 卡死； 5000 种子 + 2 条规则时执行周期约 16.7 分钟）。

⚠ 这两处是两条互不相干的代码路径（W5 归因纠正了 W0 的框架性误判）： 首轮新种子在 _refresh_torrents 里逐个内联处理，不受 max_tasks_per_tick 约束；只有稳态周期任务才走 TaskQueue.run_due。 归因与改进建议见第 13 节。

三条最需要注意的实测结论：

  1. 增量 vs 全量差 62 倍。全量 sync（5000×70 字段）端到端 205–240 ms / 8.77 MB；增量（500×8 字段）3.3 ms / 107 KB。任何让 rid 语义失效的实现错误，都会把每轮成本抬两个数量级。
  2. rid 藏在 POST body 里。探针第一版只解析 query string，结果每次都收到 rid=0、服务端永远回全量 —— 这是仿真客户端必须做对的头号细节（FakeQbServer 已经合并解析 body 与 query，可复用）。
  3. 仿真端自己不能成为瓶颈。朴素全量 diff（5000×70 字段逐字段比对）每轮 22.6 ms，脏集合 O(变化数) 只要 0.34 ms，差 67 倍。仿真端必须用脏集合，否则测的是仿真器自己。

推荐路线：独立 HTTP 仿真服务（真实 qbittorrent-api 协议栈），auto-qb 以子进程方式接入、源码零改动；仅当需要 tick 内部剖面时，才临时用进程内版本做归因。测试定位为 scripts/ 下的手动工具，不进 CI。

日志按两层产出（第 07 节）：统计层 summary.json 每项自带阈值与结论、一行 verdict 定生死，供 AI 扫读判断有无问题；完整层四路流水时间戳对齐，供回溯定位。破坏性场景（第 08 节 D1–D5，删种子 / 删文件）依赖一棵真实落盘的虚拟文件树 —— 否则「文件到底删没删」永远只是记账，测不出真实行为。其中 D4 外部删文件 → 缺文件保护 是头号场景：判据是组内成员停止率 == 100%，漏停一个就是向站点上传垃圾数据。

所有产物统一落在 --root 指定的工作根下（日常 R:\auto-qb-sim，第 08 节）：文件树、配置、auto-qb 的 data_dir、两层日志按运行 ID 分目录存放，不再散落系统临时目录。因为 R 盘就是真实下载盘，删除动作必须有硬边界 —— 哨兵根判定、realpath 逃逸校验、数量上限、收尾核账四道校验（B1–B4），任一不过即拒绝执行。另有一处对初稿的修正：文件树必须全量物化，否则未物化种子会被缺文件扫描误判丢失、整组暂停，D4 的判据也就失去意义。

实测进展（W3b 已完成 / W3 进行中）：D1–D5 五个破坏性场景全部 verdict OK（数字见第 08 节），期间修掉四处「测假」—— ① torrents_removed 曾硬编码 []，外部删掉的种子 auto-qb 永远看不到、快照里全是幽灵；② 只盯写台账看不出幽灵（打标签是一次性的），必须改问 WEB /api/status 的快照数；③ 硬 kill 拿不到 state.json（Windows 上 terminate() = TerminateProcess，finally 根本不跑，须经装了 SIGBREAK 处理器的 sim_autoqb.py 启动）；④ 两相运行的相位重启间隔被算成稳态漂移。 同时 S5 挖出一个真缺陷：qB 短暂断连（10 秒）后 auto-qb 无法自愈，会永久停在断连态直到重启进程 —— 详见第 09 节，尚未修（本轮只做外部观测，未动 src/）。

01需求界定

Scope & semantics

原始需求是「独立测试 + 仿真客户端 + 5000 种子 + 每 1.5 秒活跃 10% + 主要测安全/性能」。其中「活跃 10%」有两种截然不同的读法，已在评审中确认为两种都做、可切换，因为它们测的东西互补：

节奏错位

仿真端 1.5 s 一拍，auto-qb 默认 main_tick=2s。不刻意对齐时，每轮实际看到约 667 个变化种子（500 × 2 / 1.5），而不是 500。计划里把这作为默认场景（客户端比我们快，更接近真实），另提供 --tick 1.5 对齐场景做 1:1 对照。

02形态选型 · 利弊

Two candidate forms

仿真客户端有两种做法，取舍的本质是：要不要保留真实协议栈的成本。探针已经证明这段成本恰恰是数量级差异的来源，因此不能想当然地选「跑得快的那个」。

结论

主路线选 A。用户要的是「独立测试」，而 A 才配得上「独立」二字：auto-qb 以子进程接入、源码零改动、安全断言有服务端台账作硬证据。

B 不作为交付物，只在 W5 归因阶段按需临时使用 —— 当 A 的实测发现某段耗时异常、需要拆到 _tick 内部各阶段时，才用进程内版本做一次剖面。它不该被用来产出性能数字。

复用的既有资产

不必从零写。tests/helpers.py 的 FakeQbServer 已经解决了最难的三件事：ThreadingHTTPServer + 随机回环端口的生命周期、body 与 query 参数合并解析（这正是 rid 的关键）、以及「库对读端点不区分 HTTP 方法」的分派策略。W1 的做法是把它提升为独立脚本并扩端点，而不是另起炉灶。

首轮 17 秒是唯一的结构性问题

实测与 W0 推算（约 34 s）方向一致、量级差一半 —— 差额来自：约 1/3 种子是未配置站点、会被跳过不归组；且回环比真实 qB 快（真实 qB 还要序列化 + 读盘）。因此真实 qB 装 5000 种子时只会比 17 s 更久。

性质上：这 17 秒是主循环完全停摆（不节流、不响应），期间集中打出数千次写请求。对 PT 站而言是「批量写风暴」，正是「保守默认」要防的情形。每次启动都要付一次。

好消息是稳态非常健康（2.017 s / 漂移 19 ms），即首轮是一次性成本而非持续劣化。判据因此必须把首轮与稳态分开——混在一起算平均漂移，每次跑都会假红，反而掩盖真正的稳态问题。

顺带实测到的一个真实开销

qbittorrent-api 在每次写请求前都会再查一次 app/webapiVersion（request.py:750 的版本检查，库内无缓存）—— 实测 2000 种子场景下 addTags 与 webapiVersion 命中数完全相同。写请求量因此翻倍，真实 qB 上同样发生。

叠加另一个观察：auto-qb 是逐种子打标签（5000 种子 = 5000 次 addTags），而 qB 的 addTags 支持一次传多个 hash。按组/按站点批量提交可把这一项降一到两个数量级 —— 归入 W5 归因候选，本阶段不动代码。

rid 语义（核心，不可简化）

服务端维护 last_sent_id 与一个脏集合。请求到达时：

  • rid == last_sent_id → 回增量：{rid: 新ID, full_update: false, torrents: 脏集合快照, torrents_removed: [...]}，随后清空脏集合。
  • rid != last_sent_id（含首轮 0、漏拍、重连）→ 回全量：full_update: true，并重置基线。这与真实 qB 的「自愈性」一致。
  • 参数必须合并解析 body 与 query —— 库对 sync/maindata 用 POST，rid 在 body 里。探针已实证：只解析 query 会恒得 rid=0，每轮退化全量。
  • 脏集合按 O(变化数) 聚合，绝不做 5000×70 的逐字段比对（22.6 ms vs 0.34 ms）。

四条设计约束：

  • 阈值必须有出处。安全类用硬阈值（0 次、必须相等）；性能类用基线阈值，首次实测后固化进 docs/plans/<plan>.baseline.json。
  • 未固化的阈值不算失败。基线缺失时该项 result 记 BASELINE，verdict 计算时忽略 —— 否则第一次跑必然满屏红，反而掩盖真问题。
  • verdict 规则单一：任一 FAIL → FAIL；无 FAIL 有 WARN → WARN；否则 OK。BASELINE 不参与。
  • 统计层必须能独立存在。完整层可以因体积被裁剪（见下），统计层永远完整。
为什么阈值写在 summary 里而不是留在计划文档

阈值会随代码演进漂移。写进 summary 后，每次运行的判定依据与那次运行同文件共存，三个月后回看某次 WARN 还能知道当时的标准是什么；只留数字、阈值靠文档回忆，等于没有阈值。

08破坏性场景与文件布局

Deletion scenarios & run directory

删种子与删文件是本项目最该被验证、也最容易测假的两类场景。难点在于：仿真客户端的种子是虚拟的，如果「删除」只是在内存里删个 dict，那么「有没有真的删掉文件」这个问题根本没被测到 —— 只是记账而已。

指定目录：所有测试产物落一处

新增 --root 指定唯一的工作根：虚拟文件树、临时配置、auto-qb 的 data_dir、两层日志、报告，全部落在这一棵树下，不再散落到系统临时目录。日常跑在 R 盘（与真实种子同盘，路径处理与磁盘 stat 行为都更贴近生产）：

虚拟文件树：让删除可被真实验证

仿真端在 <run>/fs/ 下建一棵真实的文件树，种子的 save_path / content_path 直接指向树内目录。torrents/delete 带 deleteFiles=true 时，仿真端真的删除对应目录。跑前跑后各做一次文件树快照，diff 就是「实际删了什么」。

为什么必须全量物化（与初稿不同）

初稿打算只物化 300 个种子。这是错的：未物化的种子 save_path 指向的路径在磁盘上并不存在，缺文件扫描会把它们全判成文件丢失 —— 结果是 4700 个种子被误打 MISSING 并整组暂停，D4 的「组内停止率 100%」彻底失去意义，首轮还会多出几千次多余的 stop 写操作。

因此改为默认全量物化：每个种子 1 个 4 KiB 占位文件，辅种群共享同一份。5000 个种子约 4300 个文件 / 约 17 MB，建树数秒。--fs-materialize 0 保留为降级开关，但仅限不开分组的场景（如 P3 纯同步压测），并在 summary 标注。

日常跑在 R 盘，而 R 盘正是真实下载盘 —— 删除场景会真删文件。这不是「小心一点」就能解决的，必须有硬校验：

现象：--abort-after 12 --abort-duration 10（第 12 秒断连，持续 10 秒后恢复）。 断连期间 writes_during_outage = 0（符合预期，没误删、没写风暴）。但恢复后再也没接上： 从断连开始到运行结束共 30 秒、约 15 个 tick，每个 tick 打一条 主循环异常: 'NoneType' object has no attribute 'torrents_info' 加完整异常栈（28 条栈）， sync 轮次从常态 ~22 掉到 5，且 sync_full_rounds 停在 1（全量自愈从未发生）。

根因（qbmanager.run 主循环）：重连只在 except APIConnectionError 分支里触发，而该分支第一步就是 self.client = None。 client 一旦为 None，下一次 api.sync_maindata() 抛的是 AttributeError 而不再是 APIConnectionError，于是落到 except Exception —— 这条分支不重连， 只打日志。死循环就此形成：

tick k   : APIConnectionError → client=None → _reconnect_due() 若未到期则不 connect()
tick k+1 : client is None → AttributeError → except Exception（只打日志，不重连）
tick k+2 … : 同上，永远停在这里 —— 只能重启进程

退避逻辑（_reconnect_due：2s → 4s → 8s → … → 30s 上限）本身是对的， 但它被放在了一个再也进不去的分支里。断连 10 秒是 PT 场景里很常见的抖动 （qB 重启 / 网络闪断），目前的后果是程序静默失去同步，必须人工重启。

附带问题：断连期间每 tick 一条 ERROR + 20 行栈，30 秒 ≈ 300 行噪音， 会淹没真正的错误；且真实原因（连接断开）被 'NoneType' has no attribute 这个二次异常掩盖，回溯时极易误判。

处置：本轮只做外部观测（未改 src/）。已立档待决， 修复方向（供参考，不在本计划范围）：把「已断连」做成显式状态位，断连期间跳过 _tick 并由独立分支按退避重连；或让 QbApi 在 _client is None 时抛 APIConnectionError 而不是 AttributeError， 保证异常类型始终能表达「连接不可用」。

为什么 S1 用 --read-only

如果只统计「auto-qb 有没有发写请求」，一旦它真的发了，测试已经对服务端状态造成了改变。--read-only 让写端点返回 403 但仍然记账 —— 既拿到「确实发了」的证据，又保证服务端状态不被污染。这与本项目既有的「测试期禁止真实系统副作用」守卫是同一思路，只是把它搬到了进程外。

先纠正一个框架性误判：首轮与稳态是两条互不相干的路径

W0 把「首轮灌入」和「任务队列吞吐」当成一件事，其实它们的代码路径完全不同：

  • 首轮新种子：在 _refresh_torrents 里对 matched_added 逐个种子内联跑 _handle_maintenance（拉 trackers）+ _apply_speed_limit + _assign_new_torrent（拉 files）+ _add_episode_tags —— 不经任务队列， 因此 max_tasks_per_tick 对它完全无效。
  • 稳态周期任务：走 TaskQueue.run_due(max_tasks=20)， 每 tick 只弹 20 个 —— 这才是 max_tasks_per_tick 真正约束的东西。

所以「首轮 14 s」与「规则周期 25 min」不是同一个瓶颈的两个表现，而是两个独立问题， 必须分别治。
