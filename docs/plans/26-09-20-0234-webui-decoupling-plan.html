主循环 × WebUI 解耦

QbManager 的主循环同时承担「调度核心域」与「Web 表现层节拍」两类职责。本计划用门面把表现层状态收进一个对象, 让主循环只剩四条对 Web 的调用 —— 行为逐条等价, 不引入新契约。

01

可行性结论

Verdict — 可行, 建议执行

耦合的性质是「状态与门控耦合」, 不是「控制流」耦合。Web 侧从不通写路径: 它只向 queue.Queue 投递命令、只读快照 —— 边界对象早就存在了, 只是边界两侧的字段被平铺在同一个 self 上。这类耦合可以整体搬移, 不需要重新设计交互协议。

三条支撑: ①主循环里 Web 相关调用点只有六处, 且全部集中在 run() 的一小段; ②19 个表现层状态字段在 __init__ 里连成一片(102 行中的约 60 行), 可整块迁入新对象; ③既有守阵直接覆盖本次改动面 —— 分层节拍、命令唤醒、视图节拍对齐三条回归用例钉的正是主循环结构, 改完它们红就是改错了。

代价是可预期的: 表现层改访问路径会触碰 mixins/web_view.py(741 行)与 web_commands.py(623 行)共 1 364 行, 以及测试里对 mgr._group_view 一类内部字段的 200 余处引用。前者是机械替换, 后者用一层薄代理过渡, 不改动任何断言语义。

为什么现在这个形状长歪了

它是两次增量改动叠出来的结果: 先是 2026-09-15 把大文件拆成 mixin, 职责搬走了但状态没跟着搬 —— mixin 方法通过 self 读写宿主字段, 于是 WebviewMixin 与 QbManager 共享同一份状态, 边界只剩一个命名约定。随后 2026-09-19 的三波「跟手性」优化往主循环里加了命令唤醒、补刷新、节拍对齐三套门控, 每套都要读 Web 活跃状态, 就地把 _web_last_seen _web_pending_ver 的判断写进了循环体。

症状是: 想理解一次 tick 做了什么, 得同时读 run()、_flush_views()、_task_line() 三处, 并在脑子里把 Web 门控的分支剔掉。

03

设计模式选型

目标是「主循环里不再出现 Web 的判断」。门面(Facade) 是唯一能做到这件事的结构: 它把状态与判据一起收走, 对外只留语义方法。配套三个: 沿用既有的 命令(Command)+ 队列; 用 空对象(Null Object) 表达「Web 未启用」以消除分支; 核心域向表现层的通知改成单向的 置脏(Observer 的极简形态), 依赖方向反转 —— 原来是 manager._group_view_dirty = True, 改后是 self.web.mark_dirty()。

被否决的方向

方案否决理由
事件总线
(EventBus / pub-sub)		 订阅回调在主循环线程同步执行, 与直接调用完全等价, 只是把调用栈换成了一层查表 —— 排查时「谁改了脏标记」从点一下变成全局搜。对「单一写线程」这条约束没有任何额外增益, 因为约束靠的是队列而不是总线。
MVC / MVP 全套 这里的视图是 JSON 快照而非控件树, Presenter 的「更新控件」语义落空。现有的「主循环生产快照 / Web 线程只读 / 按 rid 整表替换」本来就是 Passive View 的一个变体, 再套一层只会多出无意义的接口。
独立进程 / RPC 直接违反黄金法则第 5 条(单一写线程): 写操作必须留在持有锁与 state_file 的那个进程里。配置热重载路径也要跨进程同步, 收益为零。
主循环阶段管道
(Stage 注册表)		 钩子只有两个(consume_commands 与 flush_views)。为两个固定钩子建一套注册机制是过度设计, 且会让循环骨架的执行顺序不再能从上往下读出来。

表 2 · 否决清单。判据统一为: 是否消除主循环里的 Web 分支, 且不新增不可读的间接层。

06

风险与守阵

风险为什么危险守阵
四视图同轮发布被破坏 四份视图共用一个 rid, 半新半旧的组合会让前端把陈旧数组当新数据换上去(2026-09-18 实测事故) _view_lock 随状态进 runtime; ensure_group_state 的「判脏 → 重建 → 取值」全程持锁不变
自投递命令引发自激 build_search_index 若允许唤醒, 会形成「唤醒 → drain → 仍脏 → 再投递」的死循环, 打满 CPU SELF_POSTED_COMMANDS 判据随 drain 一起搬, 不得在重写中丢失; 既有用例 test_api_enqueue_wakes_main_loop 守住
Web 未启用 / dry-run 行为漂移 现在靠 _web_last_seen = 0 使活跃门控恒假; 若 runtime 改了初始化语义, 空转保护会失效 runtime 恒存在, is_active() 语义与原判据逐字等价; dry-run 与暂停路径不改
状态双份真相 代理 property 若与 runtime 字段不同步, 会出现两处值不一致 代理只做转发不存值; 新增断言钉住「代理与 runtime 同源」
跨平台差异 本次改的是纯 Python 对象布局, 但涉及线程与锁, 历史上有「Windows 全绿 / Linux 全红」先例 拍板前在 WSL 沙箱复跑一次全量(约 20 s)

实施中撞到的四个坑

  • 守阵因重构而失效: 自投递命令的静态守卫正则只认 web_commands.put(("…, 改走 web.post_command("…" 后匹配为 0, assert posted 直接失败 —— 守阵必须跟着代码走。
  • 自投递 payload 形状: 给自投递也加 _queued_ts 会破两条 payload == {} 断言; 自投递没有回执消费者, 埋点是死重量, 只 put 原样。
  • 打桩打在兼容层上会假绿: 回执顺序守阵原本 spy mgr._set_web_result, 而门面内部调自己的 set_result ⇒ spy 完全不生效。表现为断言静默失效, 不是报错。
  • __getattr__ 递归: 别名表里不含 'web', 故 self.web 未建立时访问别名直接抛 AttributeError 而非无限递归。
