00 · 目标态

三条硬指令

① 真值来源

不得从 /sync/maindata 读真值，改用 torrents/info 直查。 依据：真机实测命令后「等真值落地」耗时 1362 ms，而配置注释写明 sync_interval = 1.5 # 与 qB 自带 WebUI(1500ms)同量级 —— 两者几乎重合， 强烈提示滞后来自 sync 快照的刷新节奏，而不是 qB 处理慢。 QbApi.torrents_info 已存在（qbapi.py:306），无需新增依赖。

② 传输方式

事件驱动（推送），不依赖轮询。去掉回执轮询退避、 _pullTruthAfterCmd 的 1500 ms 拉取预算、常规 /api/state 轮询这三段 我们自己加的延迟（合计约 1.5~2 s）。通道选 SSE（FastAPI 原生、零新依赖、自带重连； websockets 当前未安装）。

③ 乐观 UI 的去留（2026-09-20 22:12 修订）

乐观 UI 保留，不取消 —— 但它当前这套模型必须简化： 现在的撤下链路有 6 处互相咬合的机制（真值快照 → 每轮比对 → 回执真值匹配 → 拉取退避预算 → 3 s 兜底回滚 → via 分档），任何一处判据写窄就出缺陷， 近几轮追到的 bug 几乎全部来自这些机制本身，而不是来自"要不要乐观"。

简化方向：撤下只认「推送来的结果」一个事件 —— 成功就采纳真值、失败/超时就回滚， 中间的轮询比对与兜底分支整体删掉（详见 §04）。

01 · 判定门槛

先量，再决定删不删

「反应速度」定义为点击 → 界面显示 qB 真值的端到端耗时。 只有这条数字落进门槛，才执行 §04 的删除。

🔴 10 ms 门槛：真机实测后已判定不可达（2026-09-20 23:15） 原先估的是「qB 单次调用 8.4ms + 直查 ≈ 10~15ms，可能差一点」。 真机实测把这个估计彻底推翻了：qB 执行只要 2.7 ms、补刷新 2.9 ms， 但真值要等 ~1258 ms 才在 qB 侧出现（走的是直查，不是快照）。

所以「撤下依据真值」的下界是 ~1.25 s，与 10 ms 差两个数量级 —— 不是"差一点"，是根本不在同一尺度。门槛问题因此升级为架构决策（D2）： 要么接受 ~1.25 s，要么让「撤下」不再等真值（回执即撤 + 真值后到再覆盖）。 不要为了让数字好看去砍正确性。

怎么量

  • 真机：F12 点一次暂停/开始，读 [perf] … 贴上 / 回执 / 撤下 三段 + 服务端 [cmd] 日志。
  • 仿真：sim_qb 目前是瞬时翻转的，测不出快照滞后 —— 必须先给它加一个模型： /sync/maindata 按 1.5 s 节奏更新快照，torrents/info 实时返回。 这样本地就能复现并验证「直查 vs 快照」的差别。
  • 直查耗时单独测：对 1 / 10 / 448 个 hash 分别测一次 torrents/info 往返， 确认批量场景是否也进门槛（见 D3）。

02 · 真值改直查

命令后直接用 torrents/info 取真值

改动点

  • WebUIRuntime._affected_truth()（web_runtime.py:367）—— 现在读 host.store.by_hash（sync 快照）。改为命令执行后直查 torrents/info，只取受影响那几个 hash 的 state。
  • 后端真值判定：_truth_landed() 的语义随之改变 —— 不再是"等快照追上来"， 而是"qB 直查回来是什么就是什么"。若直查仍显示旧值，说明qB 真的还没翻， 那时才需要等一小会儿（但不应再等 1.4 s）。
  • 回执里的 truth：来源从快照改为直查结果，语义不变（前端据此撤下）。

批量的坑（必须先测）

⚠ 448 个目标时不要用 hashes= 拼 URL 40 位 hash × 448 + 分隔符 ≈ 18 KB，超过多数服务端/代理的 URL 长度限制，会被截断或 414。 可选做法：① 不带 hashes 拉一次全量后在本地过滤（单轮成本固定，大库约几十~百 ms）； ② 分批（每批 ~50）并发/串行查； ③ 批量场景保留乐观 UI（见 D3）。

这直接决定"移除乐观 UI"能不能覆盖整剧/多选 —— 单种子几乎肯定可以， 整剧未必。建议把批量单独列为一个决策（D3）。 
// 现在（读快照 —— 可能滞后 ~1.4s）
def _affected_truth(self, cmd, args):
    for h in self._affected_hashes(cmd, args):
        rec = self._host.store.by_hash.get(h)      # ← sync 快照

03 · 事件驱动

推送替代轮询（沿用可行性报告结论）

表 2 · 事件契约与挂点
事件替代现在的什么挂点载荷
cmd轮询 /api/cmd/{id} set_result / flush_receipts{cmd_id, status, error, wait_ms, exec_ms, truth}

硬约束 主循环只往有界队列 put，绝不直接写 socket。 这是本项目的头号教训 —— 搜索索引单次 500 条文件 API 曾把主循环占满，导致命令排队数秒。 推送是加速手段，队列满了丢弃/合并即可（退化成轮询，不是错误）。

04 · 简化乐观 UI（保留，不取消）

把 6 处机制压成 1 个事件

乐观 UI 保留：点击即变这个体验要留着，大批量（整剧 448 目标）和 qB 慢/不可达时尤其需要。 要动的是它撤下那半边 —— 现在为了判断"能不能撤下"，前后接了 6 处互相咬合的机制：

表 3 · 现状：撤下链路上的 6 处机制（每处都能单独出错）
#机制它负责什么出过的 / 潜在的错
1_snapshotTruth每轮刷新的服务端原始值快照写在 reapplyPending 之后就恒真（原有守阵）
2_optimisticSettled真值快照 vs 预测值比对预测值 2 种 vs 落地态 6 种 ⇒ 永远不等 ⇒ 撤不下
3_settleFromTruth用回执里的真值就地撤下真值未落地时匹配不上，退化到拉取
4_pullTruthAfterCmd退避拉全量直到对齐1500 ms 预算被打满 ⇒ 慢
5_expirePending3 s 兜底回滚回滚到操作前的值 ⇒ 用户看到"弹回"
6via 分档 / settleMs诊断与埋点分档语义随机制变动，易失真

近几轮追到的 bug 几乎全部来自 2~5，而不是来自"要不要乐观"。 所以不取消乐观 UI，而是把 2~5 整体删掉。

简化后的模型（只有两步）

贴上

applyOptimistic 照旧：按动作改预测值并压暗（isPending 保留）。 这一步不变 —— 它简单、无分支、没出过问题。

撤下

只认一个输入：推送来的命令结果。 ok ⇒ 采纳随结果来的真值、结束压暗； error ⇒ 回滚 prev； 超时 ⇒ 回滚 prev（单一超时，不再有 3 s 兜底这种隐式分支）。
不再比对真值、不再拉全量、不再有条件回滚。

「不采纳命令前的旧值」这条红线怎么保：判据上移到服务端 —— 真值现在来自 torrents/info 直查（P1 已完成），服务端能可靠判断"命令是否已生效" （_truth_landed）；未生效就不发 ok，继续直查、生效了再推。 前端因此不需要再自己判"这个真值是不是旧的" —— 它拿到的必然是已生效的。

删除清单（前端 · shared/commands.js 为主）

  • _snapshotTruth / _optimisticSettled / reapplyPending —— 每轮比对与重贴整套去掉
  • _settleFromTruth —— 不再"判真值能不能撤下"，改为"收到结果即撤下"
  • _pullTruthAfterCmd —— 1500 ms 拉取预算与退避去掉（真值由推送送）
  • _expirePending 的 3 s 兜底 —— 改为单一超时（建议 8 s，见 D4）
  • settleVia / via 分档 —— 或保留一个单一 push 标记，不再多档
  • 后端「等真值落地再发回执」的超时照发分支 —— 改为"未生效就继续查"，不再有"发个可能旧的值"
  • 静态守阵 _scan_pending_settle 里关于 _optimisticSettled 的条目

保留

  • applyOptimistic / _optimisticPatch / resolveOptimistic —— 乐观本体
  • isPending / isGroupPending / isEpPending / isShowPending 与 CSS .is-pending —— "在飞"的视觉反馈
  • wait_ms / exec_ms 服务端埋点与 [cmd] 日志
  • /api/state 轮询 —— 作为兜底（首帧 / 断线 / SSE 不可用），间隔可放宽
  • RECEIPT_WAIT_CAP_MS 的"上限"概念 —— 但语义从"超时照发"改为"超时判定为失败/未知"
这一改的价值 保留"点击即变"的体验，同时让"预测值 2 种 vs 落地态 6 种"、"1500 ms 预算打满"、 "3 s 兜底弹回"这三类缺陷无处附着 —— 它们的载体（比对 / 预算 / 兜底）被删掉了。 同时前端从"每轮都要比一遍真值"变成"等一个事件"，大库下的每帧开销也降了。

06 · 决策点

需要你拍板的四处

表 3 · 决策点
编号问题建议
D1 「不得从 /sync/maindata 读」的范围：仅命令真值，还是连常规刷新也一并放弃增量同步？ 先只改命令真值（改动小、收益确定）。常规刷新是否也改，等 P0 确认快照确实滞后 1.4 s 再决定 —— 若属实，整个界面的数据新鲜度都被拖着，那就值得改。
D2
🔴 阻塞		 撤下要不要继续"等真值"？真机实测真值要 ~1.25 s 才出现， 所以"等真值"就等于撤下 ~1.25 s；而回执本身只要几毫秒。 建议改为"回执即撤 + 真值后到再覆盖"： 服务端不再为等真值扣留回执（现在扣到 1200 ms 上限才发，正是它把回执推到 1259 ms 的）， 改成"执行完即发回执、真值稍后作为独立 truth 事件推送"。 撤下可降到 10~20 ms，且因为从不采纳未落地的真值，不会弹回。
代价：真值到达前的 ~1.2 s 里行上显示预测值 —— 这正是乐观 UI 存在的意义。
D3 批量（整剧 448 目标）能否也移除乐观 UI？hashes= 拼 URL 会超限。 先测三档直查耗时。若批量进不了门槛，批量保留乐观 UI（单种子移除）， 并明确写进文档避免混淆。
D4 简化后"未知"这一路的单一超时取多久？ 建议 8 s：压暗已结束、真值由推送送，等待没有观感代价，放宽容错； 超时必须有明确 toast，不能静默（否则 qB 挂了用户不知道）。

07 · 风险

要小心的

  • qB 不可达时的观感退化 —— 没有乐观 UI 后，qB 慢/断连时点击会"没反应"。必须有超时与明确提示，否则比现在更难用。
  • ⚠ 前端验证要防浏览器缓存 —— agent-browser 的 Chrome 会缓存 /shared/*.js：改了前端代码后页面可能仍在跑旧包（本次实测：页面里 AQB_COMMANDS 只有 2 个键，但服务端下发的文件是新的）。 验证前端改动前先确认页面跑的是新包，或改用不依赖浏览器的方式（如独立 SSE 客户端）。
  • 批量直查的成本 —— 448 目标若走全量 torrents/info，单轮可能上百毫秒。要么分批，要么保留乐观 UI。
  • 主循环不能被推送或直查阻塞 —— 直查是在主循环线程做的，448 目标分批时要考虑协作式让出（与搜索索引同样的教训）。
  • 删除面比看起来大 —— 乐观 UI 渗透在前端方法、模板 class、CSS、静态守阵、冒烟断言、知识库多处； 建议 P3 单独一个提交，且删完必须全量测试 + 冒烟双 UI 都跑。
  • 别为了数字做激进优化 —— 若实测 20 ms 而非 10 ms，接受它，别去砍正确性换毫秒。
  • 直查只在"走 defer_receipt"的命令上生效 —— 本次改动后实测确认： bulk_torrents（整剧/整集/多选）仍走"handler 自写回执"，根本不会调用 _affected_truth，因此直查对它无效、遥测仍是 0 行。 批量要在 P2 一并处理（把它接入真值链路），否则单种子改好了而整剧没改。
  • ⚠ 发现一个既有的死测试（本次未改，待你定夺） —— tests/test_web.py 里 test_truth_hold_budget_matches_backend 同名定义了两次（约 3910 / 3933 行）：Python 后者覆盖前者， 于是第一条静态守阵实际从未被执行。这是"看着有守阵、其实没跑"的典型，建议单独入池或修。
