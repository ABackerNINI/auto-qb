activeContext 多 clone 冲突治理

冲突的根因不是 agent 手滑，而是把并行会话状态塞进了单文件这一串行媒介： 每个收尾 DoD 都必写、最热写点又集中在文件头同一段。本方案把写点按 clone 拆开、 把全局视图降级为生成物、再用只读预检兜底 —— 让冲突在结构上不可能发生，而不是更小心地合并。

01

问题定义与现场证据

2026-09-20 起工作区模式为多 clone 并行：每个 AI 实例一份完整克隆（独立 .git）， 跨 clone 同步一律走 Gitee develop，禁 rebase / 禁 stash、非快进合并遇脏工作区会连坐删除 .git/objects（三次 rebase 事故实证）。在这个约束下，git 合并冲突的处置成本被环境放大到危险级。

三个放大因素

因素现场证据（均为库内实记录）
写点重叠最热改动集中在头部同几十行 「最后更新」是滚动替换式设计：每个会话把旧状态嵌进「其前一条状态」，即每个会话都重写文件头同一段
高频 每个执行轮收尾必写（DoD 第 1 步）；仅 09-22 一天，该文件头部就滚动叠加了 5 个时段的会话状态（22:38 / 22:19 / 21:58 / 20:55 / 20:38）
反馈滞后 冲突不在写入时暴露，push 被拒才暴露；且本环境合并即高危 —— W1–W3 合并事故中，唯一冲突文件恰是 memory-bank/testing.md，提交后又有 12 条 D（scripts/ 整目录只在工作区消失）
现有防线评估 12 KB cap、流水账禁令、先同步后开工 —— 这三道防线缩小的都是爆炸半径（文件更小、冲突块更短、暴露更早）， 没有一个动到「写点重叠」这个根因。 collaboration.md 现行口径「合并冲突交用户主导解决」本质是承认冲突必然发生、 然后把处置成本转嫁给用户。
02

根因分析：写点热力清单

把收尾 DoD 与会话协议涉及的全部共享写点按热度排一遍，可以看到 activeContext 不是孤例，而是最热的一个：

写点频率改动形态撞概率现状
activeContext「最后更新」栈头部滚动替换每执行轮同段重写极高用户主导手工合并
activeContext「正在进行」每执行轮共享列表增删改高同上
testing.md 顶部基线行每次全量后同一行替换高W1–W3 事故的冲突点
progress/ 迁入完成任务时分区追加中同上
pitfalls/<类>/<主题>.md遇新坑不同文件为主低罕见
tasks/_index、pitfalls/_index生成物每次收尾整文件重写可解重跑生成器即解（已有标准做法）

最后一行给出了本项目已经验证过的出路：把「手写的源」降级为「数据」，把视图降级为生成物， 冲突的解决方式就从「人工合并两版文本」变成「任取一方、重跑脚本」。SKILL.md 反模式一节对 tasks/_index 的表述正是如此。 本方案做的事，就是把 activeContext 也搬上这条已经跑通的模式。

职责混杂是深层根因

activeContext.md 目前同时承载两种性质相反的状态：全局项目焦点（定案口径、下一步候选、待走查指针 —— 低频、共享、单调）与 会话滚动状态（最后更新、正在进行 —— 高频、按 clone 天然分区、滚动替换）。前者放单文件没问题；后者本质是 per-clone 的， 被塞进共享单文件，冲突是结构必然而非偶然。

03

解法空间：三条正交路线

冲突的本质是把「并行状态」塞进「串行媒介」。所有解法都在恢复维度匹配，方向只有三种： 写点并行化（拆文件，不同文件在 git 三方合并中天然无冲突）、 读点聚合化（生成物，冲突解法退化为重跑）、 写串行化（单写者，消灭冲突但牺牲并行）。

A按 clone 拆文件（所有权分区）推荐主案

activeContext 目录化：global.md 承载里程碑级全局焦点（低频共享），每 clone 一个会话状态文件， 各 clone 只写自己的文件。不同文件 = 三方合并结构性无冲突，与现行「先同步后开工 ff-only、提交时合流」流程完全兼容。 附带收益：单文件天然变小，12 KB cap 压力骤降。

B生成式聚合视图推荐组合件

在各 clone 状态文件之上用脚本生成 _index.md（每 clone 一行：最后更新时间 + 一句话状态）。 生成物的冲突解法 = 任取一方重跑脚本。与 A 组合时就是 A 的「别人在干嘛」读点。

C同文件分段约定次选过渡

每 clone 只写自己的 H2 段。改动最小，但同文件相邻段、段落重排仍可能撞 hunk，头部共享区照旧最热，文件膨胀压力不变。治标。

Dgit 层兜底低成本保险

① merge-tree 只读预检（配方已在 pitfalls/git/history-integration.md：git merge-tree --write-tree 退出码 0 即无冲突）， 把冲突从「push 被拒才发现」提前到「提交前就知道」；② 开 rerere.enabled 自动复用人工解法。 注意 union merge driver 不适用 —— 它只对 append-only 文件安全，对滚动替换式结构会织出两版混杂文本。

E单写者模型仅全局段可选

指定唯一 owner clone 拥有全局焦点文件，其余走 issues / 提交信息汇报。彻底消灭冲突但牺牲并行， 与「各 clone 自洽收尾」的现行 DoD 冲突。global.md 本来就低频，不值得为它上单写者。

方案冲突消除程度改造成本主要代价 / 风险
A 拆文件结构性消除中：目录 + 生成脚本 + 守卫 + 文档接线，一次到位需约定 clone-id；全局视图依赖生成物
B 生成式聚合解法退化为「重跑」低～中（可并入 A）单独用只解决「解得快」，不解决「撞不撞」
C 同文件分段降低，不消除低头部共享区仍最热；膨胀压力不变
D git 兜底不消除，提前暴露低预检后仍要走合流；rerere 只对同形冲突有效
E 单写者消除低牺牲并行，owner 成瓶颈
04

推荐方案：A + B + D

A 拆文件消灭冲突源，B 生成索引兜住「别人在干嘛」的可读性，D 做最后保险。目标结构：

memory-bank/
├─ activeContext.md          ← ≤ 1 KB 存根: 一句话 + 「已迁至」指针（照目录化五步配方）
└─ activeContext/
   ├─ _about.md              ← 三行头元数据, 目录自发现入口
   ├─ _index.md              ← 生成物: 各 clone 最后更新时间 + 一行状态
   ├─ global.md              全局焦点: 里程碑 / 定案指针 / 下一步候选 —— 低频共享
   ├─ clone-main.md          auto-qb 主 clone 的会话滚动状态
   ├─ clone-1.md
   ├─ clone-2.md             本 clone
   └─ clone-long-seeding.md

clone-id 直接沿用现有工作区目录名（auto-qb / clone1 / clone2 / long-seeding），不发明新机制； 文件名即 clone 标识，合作规则只有一条：每个 clone 永远只写自己的文件。

协议变化（开始 / 收尾两端点）

协议位置现行改为
会话开始 · 第 2 步 读 activeContext.md（最后更新、正在进行、下一步候选） 读 global.md + 自己的 clone-*.md + 扫 _index.md 知道别人进展
收尾 DoD · 第 1 步 更新「最后更新」滚动栈 +「正在进行」 只写自己的 clone-*.md（滚动栈原样迁入自己文件）；全局事项变更才动 global.md
冲突处置 用户主导手工合并（collaboration.md 现行口径） clone 文件层结构性消除；global 低频段万一相撞仍按现行约定交用户主导
与既有机制的关系 tasks/ 档案「不带时分、同天同专题必撞同路径」是故意设计的 add/add 查重信号（SKILL.md 明文）， 本方案不碰它；issues 认领状态继续以 Gitee 为单一事实源，不进 activeContext —— 拆分只治理「会话滚动状态」这一层。
05

实施计划

四个波次。W1–W3 必须连续入库（同一批提交、分笔连续推送）：拆分落地而协议未切换的中间态一旦跨过同步窗口， 另一 clone 会按旧协议继续写存根文件 —— 波次间隔要压在一个同步周期内。W4 独立可选。

W1结构拆分

建目录与文件，原位置留存根：

  • 建 memory-bank/activeContext/：_about.md（三行头）、global.md（迁入定案口径 / 下一步候选 / 待走查指针）、clone-*.md × 4（迁入各 clone 滚动状态，现存「最后更新」栈归入 clone-2.md）
  • 原 activeContext.md 替换为 ≤ 1 KB 存根（一句话 + 指针），头部引言的历史教训一段并入 _about.md（原文照搬不重写）
  • _common.py 的 CAP_POLICY 加档：per-clone 会话状态 6,000（单 clone 状态天然更小）、global 6,000
  • check_kb_structure.py 纳入新目录（含 _about.md 即自发现；volatile 角色改挂到目录内文件）
验证check_kb_structure.py 绿；cap 双检（存根 + 新文件）通过
W2聚合生成与守卫

把「别人在干嘛」做成生成物：

  • 新脚本 gen_active_index.py：扫 activeContext/clone-*.md 头部「最后更新」行 + 「正在进行」条目计数，生成 _index.md（带 --check，接进闸门）
  • tests/test_memory_bank.py 补守卫：索引 ↔ 文件双向一致、每 clone 文件存在且在 cap 内、存根存在且 ≤ 1 KB
验证uv run pytest tests -q 全量绿（守卫在列）
W3协议接线

让所有 agent 的入口指向新结构：

  • SKILL.md：会话开始第 2 步、收尾 DoD 第 1 步、反模式补「仍在旧单文件上写滚动状态」一条
  • 根 AGENTS.md：会话协议「开始 / 收尾」两处的文件引用同步（8000 字符硬顶内措辞）
  • collaboration.md「协作约定」补一行拆分口径；memory-bank/README.md 细路由更新
验证check_doc_links.py 绿 + check_context_caps.py 绿（AGENTS.md ≤ 8000）
W4预检加固可选

把 D 路线落进机检：

  • preflight.py 增 git merge-tree --write-tree 只读预判：推送前报「撞 / 不撞」，配方即 pitfalls/git/history-integration.md 既有步骤
  • 各 clone 本机开 git config rerere.enabled true（人工解法自动复用；仅保险性质）
验证preflight.py --check-started 输出新增一行，只读、不写任何 git 状态
06

风险与边界

风险 / 边界评估与对策
双 clone 协议错位窗口 W1 落地后、对方 clone 未拉取前，旧协议会往存根文件写。对策：W1–W3 连续入库压缩窗口；开工自检（--check-started + 读协议）会让对方 clone 在首个执行动作前完成切换；存根文案里写明「勿在本文件追加会话状态」
tasks/ add/add 信号被误伤 不受影响 —— 那是 tasks/ 路径层的故意设计，与 activeContext 拆分无关；计划明确不触碰
弃用 clone 的陈旧文件堆积 _index.md 展示各文件最后更新时间，一眼识别失活 clone；退役时在 global.md 标注即可，无需删档
global.md 低频段仍可能相撞 频率低一个量级（里程碑级更新）；真撞了按现行「用户主导解决」约定处置，成本可接受
生成脚本成为新单点 与 gen_tasks_index / gen_kb_index 同构（共用 _common.py），无新依赖；脚本挂 --check 进既有闸门，静默失效会被预检暴露
