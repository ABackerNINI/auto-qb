01一句话结论

修复没有白做, 但修补模式已到收益上限。六轮下来, 同一类"被重置"报告反复回来 —— 因为每一轮都是"用户报一次 → 找到一条根因 → 封一条通道", 而通道数目由模型决定, 模型不变通道就封不完。本计划不再打第7个补丁, 改为换模型: 意图与生效分轨、单一持久化漏斗、按页子树读写。预计改动集中在 app.js / columns.js 两个文件 (约 300~400 行), 模板与后端零改动。

用户原话: "column 设置丢失问题很严重, 修复了很多次, 急需重新设计, 简化模型, 从根本上杜绝"。#1~#3 证明补丁有效, #4/#7 证明补丁不完备 —— 两者合起来就是"换模型"的完整理由。

02病灶: 病在模型, 不在 bug

把六轮修复逐个回看, 所有缺陷都从同一组结构裂缝里长出来。现在的列状态是一个响应式字段 + 一个标志位 + 六个落盘点:

// 现状 (app.js + columns.js, 取证 2026-09-21)
colWidths: { page: { 列key: "120px" } }   // ← 混装: 既有用户拖出来的 px, 又有 materialize 按窗口算出的 px
colManual: { page: bool }                 // ← 标志位: 决定 materialize 能不能覆盖、save 要不要过滤
colHidden / colOrder                      // ← 这两段是真意图, 没病

// 6 个落盘点的调用顺序各有主张:
toggleColumn          : 改内存 → save → $nextTick(materialize)   // 先存后算
resetAllColumnWidths  : 改内存 → save → $nextTick(materialize)   // 先存后算
applyColOrder         : 改内存 → save → $nextTick(materialize)   // 先存后算
fitColumnsToWindow    : materialize → manual=true → save          // 先算后存 (且把窗口快照固化成偏好)
startResize (up)      : 拖拽中已改内存 → manual=true → save        // 先算后存
autoFitColumn         : 改内存 → manual=true → save               // 先算后存

裂缝一: 混装 —— 两种生命周期共用一个字段

colWidths[page] 里同时住着"用户拖出来的宽度"(意图, 该持久化) 和 "materialize 按当前窗口算出来的宽度"(派生, 不该持久化)。因为同字段, 读写两侧都必须靠 colManual 过滤, 且两侧规则必须永远成对同步 —— 6c1b7f4 的修法本质就是一对过滤 ("if (!this.colManual[page]) payload.widths = …[page] = {}" + 读侧 "if (!out.manual[page]) out.widths[page] = {}")。失败分析的教训已经写进 pitfalls: 持久化前先分清"用户偏好"与"派生快照" —— 但现状只是把教训做成了过滤器, 字段还是混的, 过滤器错一处或未来改动绕开它, 问题原样回来。

裂缝二: 散写 —— 持久化没有单一入口

6 个落盘点各自决定"何时把内存写进存储", 于是出现"先存后算/先算后存"两种顺序、3 处选错 (失败分析 04 节: 内存 12 键 / 存储 0 键的漂移就是它)。每一个新交互入口都是一次重新选对顺序的机会 —— 这类 bug 不是写错, 是结构允许写错。

裂缝三: 快照内存 —— 加载时读一次, 之后各写各的

initialColState = loadColState() 模块级只读一次, 内存从此是独立快照; 整份写回 ⇒ last-writer-wins。11382ed 用 F1(按页 RMW) + F2(storage 采纳) + F3(可见性补漏) 三层补丁压住, 但这是"在快照模型上模拟共享", 不是共享本身。

共同模式: 三个裂缝都不存在于"意图 / 生效分离 + 单一漏斗"的模型里。第 7 轮再打补丁, 大概率只是封住 #4, 然后等 #8。

03重设计: 双轨模型

核心不变量 (全计划只有这一条铁律): 存储只存用户意图 (hidden / order / w); 生效宽度永远是现算的派生值 —— 派生值没有资格落盘。

3.1 两条轨道

意图态 (唯一持久化对象)生效态 (易变, 绝不落盘)
内容colHidden[page] / colOrder[page] / colW[page] (null 或 {列key: "Npx"})colWidths[page] —— 保留现名现签名, 供 _gridTemplate / 拖拽冻结读
谁写只有用户意图动作 (显隐 / 拖序 / 拖宽 / 双击自适应 / 重置 / 适应窗口)recomputeEffective() (原 materializeColumns 改名收窄): 自动页按当前窗口现算, 固化页 = colW[page] 原样
何时写存储意图动作后立刻经漏斗落盘永不
字段关系colWidths[page] = colW[page] || recompute(当前窗口) —— 生效态由意图态 + 窗口推导, 单向

colManual 标志位删除 —— colW[page] != null 就是"固化页"的唯一判据, 少一个需要同步的状态, 也少一对读写过滤器。

3.2 存储 schema v5 (按页一棵子树)

// autoqb_cols_v5
{
  "v": 5,
  "pages": {
    "group":  { "hidden": ["uploaded"], "order": ["name", "size", …], "w": { "name": "229px" } },
    "detail": { "hidden": [], "order": [], "w": null },   // w = null ⇒ 全自动页, 存储里根本没有 px
    "torrent": { … }, "show": { … }
  }
}
  • w: null = 全自动页; w: {...} = 用户固化页 —— 与今天 manual=true 的用户可见行为完全一致 (拖一次 = 整页固化), 不改交互, 只改数据归属。
  • 按页子树 ⇒ F1 的 RMW 从"四段各按 page 合并"简化成"只写一棵子树", 采纳 (adopt) 也变成整段替换一棵已知安全的子树。
  • 旧键链: LEGACY_COLS_KEYS = ["autoqb_cols_v4", "autoqb_cols_v3"], 命中即迁移回写 v5。v2 仍刻意不迁 (索引式, 无法可靠对应, 口径不变)。

3.3 迁移 (v4 → v5, 一次性, 保偏好)

for page in [group, detail, torrent, show]:
  hidden[page] = clean(v4.hidden[page])          # 洗净规则原样保留: 非法 key 丢弃 / locked 列不收
  order[page]  = clean(v4.order[page])           # 去重 + 非法 key 丢弃
  w[page]      = v4.manual[page] ? clean(v4.widths[page]) : null
                   # manual=true 的页: 宽度是真用户偏好, 整段保留
                   # manual=false 的页: 存的是历史污染 px (6c1b7f4 前被别的窗口写入), 一律弃 —— 正是用户要的"清掉"

注: 定案口径当前是"键冻结在 v4, 无 v5 计划"。本计划正是那个 v5 计划 —— 升版依据是定案口径自己写的条件 ("旧缓存结构已无法被新 loader 正确解释才升"; 本次 widths 语义从"混装"变为"仅意图", 恰属此类), 且按口径要求同步挂迁移与守阵。见决策点 D1。

3.4 单一持久化漏斗

// 唯一写入口; 全仓对 COLS_STORE_KEY 的 setItem 只允许出现这一处 (静态守阵钉住)
persistPage(page) {
  const base = readColStateRaw() || emptyV5();      // 以存储为底 (RMW, 防"同一毫秒两边写")
  base.pages[page] = {
    hidden: this.colHidden[page] || [],
    order:  this.colOrder[page] || [],
    w:      this.colW[page] || null,                // 派生值到不了这里 —— 想写也写不进
  };
  try { localStorage.setItem(COLS_STORE_KEY, JSON.stringify(base)); } catch { /* 私隐模式: 会话内仍生效 */ }
}

// 六个意图动作统一收口: 改意图 → persistPage(page) → nextTick(recomputeEffective)
// recomputeEffective 只改 colWidths (易变), 不在持久化路径上 ⇒ "先存后算/先算后存"不再是可错的选项

3.5 隐藏列保宽 (封掉 #4)

固化页上, 拖宽 / 双击自适应改为以 colW[page] 为底 merge, 只覆盖可见列的实测值, 不再整段替换:

// startResize 起手 / autoFitColumn 落笔 (现状: widths = _renderedWidths(...)  ← 隐藏列在这里被抹)
const merged = { ...(this.colW[page] || {}), ...visibleRendered, [key]: `${w}px` };

3.6 跨标签同步 (F2/F3 保留, 且变得天然安全)

  • storage 事件 + visibilitychange 补漏两道机制原样保留 (现架构已验证有效, 不推倒)。
  • 质变在采纳的内容: 采纳的是纯意图 (hidden/order/w), 本地生效宽度自算 —— 不存在"采纳了别的窗口算出的 px"这回事, adoptColState 从"必须小心"变成"随便采"。
  • 残余窗口: 同页并发编辑仍最后写赢 (两个标签同秒改同一张表)。维持既有决策: 不做时间戳合并 —— 为一个亚秒级竞态给三段数据加"谁更新"语义, 代价远大于收益 (失败分析 09 节同口径)。

3.7 明确不动的东西

  • 两套 UI 的模板 / CSS: colWidths 消费签名不变, 零改动。
  • autoqb_timefmt_v1 独立键: 生命周期不同, 维持分离 (既有正确决策)。
  • 后端 / 列定义 / 对齐注入 / 行窗口化: 零改动。
  • origin 隔离: 客户端模型无解, 本计划只做可见化诊断 (D3), 不做服务端化 (见 05)。

04历史缺陷消除对照

历史缺陷旧模型的结构位双轨模型下为何不可能
升版本清零 (第①轮)修复动作用"换键"表达升版唯一入口 + 迁移强制挂钩 (守阵: 升版必须带迁移测试)
