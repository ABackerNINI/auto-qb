乐观 UI「撤下」修复计划

真机反馈「乐观 UI 生效，但从乐观 UI 恢复正常要 2-4 秒」。受控实测确认：贴上这一段上一次已经修好（4-7 ms），慢的是撤下这一段 —— 灰窗（is-pending）恒定挂满 3 秒，再叠加最多一个轮询周期，实测 3.8 ~ 5.2 秒。根因是设计注释里承诺的「真值一致即清」这条出口从来没有实现过，而本地桩服务在结构上根本走不到这条路径 —— 所以前三次修复都绕着它走。

⚠ 本文档已存档：诊断成立，实现被主线方案取代

本计划写于本地分支落后主线 4 个提交时。拉齐后发现 origin/develop 上已有同一问题的独立修复： 32f531d（真值匹配即清 + 回执后拉真值 + 桩服务真改状态）与 12657ee（3s 兜底超时必须回滚 op.prev，否则补丁值永久留在行上 —— 这一处是本文档 §05 方案里没有的，按本文档实现会踩）。 两者思路一致，主线的验证更完整（还含 hang 独占轮与「兜底后落回原状态」守阵），故以主线为准。

01结论先行

上一次的修复是成功的，只是它修的是另一半。a8eb6e8 把 applyOptimistic() 提到 POST 之前，受控复测「点击 → 补丁贴上」= 4~7 ms（修前是 POST 慢多少就晚多少）。用户现在报的 2-4 秒，发生在补丁已经贴上之后：行确实立刻变成暂停色，但整行被 .is-pending { opacity: .55 } 压成半透明，要等约 3-4 秒才恢复到正常观感 —— 用户说的「恢复正常状态」就是这一下。

三条根因叠加，全部落在「撤下」这一半：

  1. pending 只有一个出口：3 秒常量定时器。isPending()（app.js:2314-2322）只判 Date.now() - op.ts > 3000，从不与服务端真值比较。而设计注释（app.js:2308-2313）白纸黑字写的是「直到服务端数据与预期一致 或 3s 超时」—— 后半句实现了，前半句没有。于是真值 200 ms 就到了，灰窗照样挂 3 秒。
  2. 这个定时器只在轮询点被顺带求值。唯一会去删过期 op 的地方是 reapplyPending()，它在 refresh() 里每轮调一次（app.js:1726）。3 秒到了没人察觉，要等下一次 /api/state 回包才被发现 ⇒ 再叠加 0 ~ pollMs（1.5 / 2 / 3 s，按种子量分档）。
  3. 拿到成功回执后不主动取真值。act() / actTorrent() / 批量分支收到 ok 回执后只弹 toast，不发 refresh()；真值只能等下一个轮询周期进前端。而服务端写回执（web_commands.py:151）发生在视图重建之前（drain → 写回执 → _sync_line → rebuild_views），所以「回执到了就立刻查」还会扑空一次 —— 这个时序差必须在方案里显式处理。

实测公式：撤下耗时 = 3000 ms + 等到下一次 /api/state 的时间。800 种子（1.5 s 档）实测 3785 / 4047 / 4498 ms；3600 种子（3 s 档）实测 3898 / 4456 / 5178 ms —— 余数全部落在各自档位的 [0, pollMs] 区间内，吻合。

为什么必须先把桩服务修好

冒烟桩服务的命令泵（scripts/ui_harness.py:93）不执行命令，只写回执。本次实测直接暴露后果：探针问「服务端该种子的 kind 何时变成 paused」，15 秒内永远等不到。也就是说「真值一致即清」这条路径在任何本地测试里从未被跑到过；现在唯一能让它结束的机制就是那条 3 秒定时器。这与 pitfalls 已记录的两条坑是同一类（「桩服务是瞬时的 ⇒ 顺序型缺陷本地测不出来」、「桩对象缺 to_dict() ⇒ 整条链路从未被跑过」）。步骤 0 不改，后面每一步都无法验证。

03根因定位

根因 A · 出口只有常量定时器

app.js:2314-2322主因
代码
isPending(hash) 只做 Date.now() - op.ts > 3000 判定后 delete；全文检索 pendingOps 的写入/删除点（2315-2321 / 2343 / 2349-2361 / 2366-2368）没有任何一处比较服务端真值。
设计 vs 实现
注释 2308-2313 承诺「直到服务端数据与预期一致 或 3s 超时」；只有后半句落地。resolveOptimistic(hashes, true)（2357 行）做的只是把 op.ts 重置到回执时刻，等于把灰窗从回执起重新数 3 秒。
后果
真值无论多快到达，灰窗恒定 3 秒。真机上用户看到的就是「立刻变了，但灰很久」。

根因 B · 定时器只在轮询点求值

app.js:1726 / 2364-2370主因
代码
isPending() 的「顺带清掉已超时的」注释写在 reapplyPending() 里，而后者只在 refresh() 中被调用一次。没有独立的定时器去触发清理，也没有 watcher。
后果
3 秒到期后不立即生效，要等下一次 /api/state（1.5 / 2 / 3 s 分档）才被发现 ⇒ 撤下耗时 = 3 s + [0, pollMs]。实测余数全部落在档位区间内（见 §02）。

根因 C · 成功回执后不主动取真值，且存在时序差

app.js:2410 / 3160 / 3395 · qbmanager.py:354-380叠加
代码
三个动作入口在 resolveOptimistic(hashes, r.ok) 后只弹 toast，不 refresh()。
时序差
服务端 run() 的顺序是 _drain_web_commands() →（handler 内）_set_web_result() → _sync_line() → rebuild_views()。回执先于真值发布，所以「收到回执就 refresh()」必然存在扑空窗口，方案必须带重试或条件等待。
后果
真值进入前端的最早时刻 = 下一个轮询点 —— 与根因 B 叠加，把「等真值」和「等求值」两笔账算在同一拍上。

根因 D · 本地测试结构上测不到撤下

scripts/ui_harness.py:93-119判据缺失
代码
命令泵 docstring 自称「ok = 正常完成（乐观值被真值取代）」，但实现只有 mgr._web_results[cmd_id] = {"status": "ok", ...} —— 不执行、不改状态、不置脏；而 mgr.rebuild_views() 全程只在启动时调用过一次（ui_harness.py:174）。
后果
① 「乐观值被真值取代」从未发生，灰窗只能靠 3 s 兜底结束；② 冒烟断言只查「点击后 120 ms 内出现 pending」与「8 s 内最终归零」（500 ms 步长采样）—— 3.8 s 稳稳 PASS。这是判据缺失，不是代码缺失，也是同一现象能连报三次的直接原因。

04为什么前三次都没修好

次序提交改了什么对「撤下」的影响
110e06a8引入乐观 UI 本身（pendingOps / isPending / 3 s 兜底），解决「点了没反应」建立了灰窗机制，也一并把「只靠 3 s 定时器」写死为唯一出口
2a8eb6e8补丁提到 POST 之前；3 s 兜底改从回执起算贴上从 2012 ms → 6 ms，但撤下逻辑一行未动；「从回执起算」反而保证灰窗一定挂满 3 s
3fed62a8剧行补绑 is-pending（折叠态下也能看到在飞）同向叠加：让更多行进入同一个 3 s 灰窗，撤下耗时不变

共性：三次全部只动「贴上」那一段，没有一次量过「撤下」。而用户感知的两次抱怨恰好落在这两段上 —— 第一次是「点了才变」（贴上慢），这次是「变了但灰很久」（撤下慢）。每次都在正确的方向上前进，所以现象一次比一次轻，但因为从头到尾没有「撤下耗时」这个数字，没人发现慢的已经换了一半。

教训（待入 pitfalls）

「乐观 UI 响应快不快」是两个指标，不是一个：贴上耗时（点击 → 补丁可见）与 撤下耗时（点击 → 补丁撤下、行恢复正常）。只埋了前者（a8eb6e8 的 patchMs / postMs），于是真机第二次报「2-4 秒」时日志全绿、无从下手 —— 与当时「cmdStats 只量回执段」那次是同一个错误的重演。

05修复方案

六个步骤，按依赖顺序；步骤 0 不完成，后面每一步都无法验证。改动集中在 src/auto_qb/web_ui/static/shared/app.js 与 scripts/ui_harness.py，不动后端节拍、不动命令协议（备选方案见 §07）。

步骤 0 · 让桩服务真的能改状态（先做，否则无从验证）

  • _start_command_pump() 在写回执之外，按命令改合成种子的 state（pause → pausedUP/pausedDL；resume → uploading/downloading），然后置 mgr._group_view_dirty = True（/api/state 走 ensure_group_state，判脏即就地重建 ⇒ 下一轮请求必回传真值）。种子对象就是 store.by_hash 里的 FakeTorrent，state_enum 由 .state 动态算出 ⇒ 改字段即可，不要动 FakeClient（它只记 calls，被大量既有断言依赖）。
  • error 模式不改状态（命令没生效，就该走回滚路径）；hang 模式维持原样（验证 3 s 兜底）。
  • 新增 --state-delay-ms（默认 ~150 ms）：回执立刻写，真值延迟一会儿才生效。这条是必须的 —— 它模拟的正是服务端「回执先于真值」的真实时序（根因 C）。没有它，桩服务又是瞬时的，新引入的扑空竞态会再次变成「本地测不出来」。
  • 自检：探针脚本应能读到「服务端真值可用 ≈ 150-250 ms」而不是「15 s 未到」。

步骤 1 · 加「真值一致」判定，并把 reapplyPending 升级为 reconcilePending

在 refresh() 整表赋值之后、补丁重贴之前做判定 —— 顺序写反就全废（见下方 note）。

_truthMatches(action, kind) {          // 白名单只有 pause / resume
  if (action === "pause")  return kind === "paused";
  if (action === "resume") return kind === "downloading" || kind === "seeding" || kind === "checking";
  return false;                        // 其余动作没有 patch, 走不到这里
},
reconcilePending(fresh) {              // fresh = 本轮真正收到新数组的视图集合
  for (const h of Object.keys(this.pendingOps)) {
    const op = this.pendingOps[h];
    const seen = this._forEachRow(h, fresh, (row) => {
      if (this._truthMatches(op.action, row.kind)) op.__agree = true;
    });
    if (seen && op.__agree) { delete this.pendingOps[h]; continue; }  // 真值已到 ⇒ 交还真值
    if (Date.now() - op.ts > (op.confirmed ? 6000 : 3000)) { delete this.pendingOps[h]; continue; }
    this._forEachRow(h, fresh, (row) => Object.assign(row, op.patch));
  }
}
  • 只查本轮真正刷新的数组。P1-1 按视图回传（view=torrent 只回 torrents），其余数组里的行对象还是上一轮被补丁改过的旧对象；拿它判定会 100% 误判为「一致」。refresh() 里把本轮 state.groups / singles / torrents / shows 哪些键真的到了，收集成 fresh 传进来，_forEachRow 增加按 fresh 过滤的形参。
  • state.updated === false 那一轮不做判定，只重贴补丁（没新数据就无从比较）。
  • 不一致时保留补丁，不弹回。服务端可能在「点击 → 命令执行」之间插了一次周期性重建，那一版还没含本次命令；此时交还真值会造成「变过去 → 弹回来 → 再变过去」的抖动。保留补丁是安全的，代价只是多灰一拍。
本方案最易写错的一行

判定必须在补丁重贴之前用服务端新值做。写在 reapplyPending() 之后的话，row.kind 已经被补丁改成 paused ⇒ 永远「一致」⇒ 灰窗确实变 0 ms，但失败路径会永久留下假状态（红线）。必须配红绿双验：把判定挪到重贴之后，冒烟的 error 模式断言必须变红。

步骤 2 · 成功回执后主动追真值（消掉「等下一拍」）

async settlePending() {                 // 只在「有 pending 且已收到 ok 回执」的极短窗口内跑
  for (const gap of [0, 300, 800]) {
    if (gap) await new Promise((r) => setTimeout(r, gap));
    if (!Object.keys(this.pendingOps).length) break;      // 已收敛 ⇒ 立即停
    await this.refresh();                                 // 扑空就按退避再试一次
  }
}
  • 调用点：act() / actTorrent() / actEpisode() / 批量分支，在 resolveOptimistic(hashes, true) 之后。
  • 首查 gap=0 覆盖「真值比回执早」；300 ms 那次覆盖根因 C 的时序差；800 ms 是给大库重建的余量。条件成立即停，稳态下最多 2-3 次额外 refresh()。
  • 不会堆叠定时器：scheduleNext() 内部先 stopPolling()（app.js:1652-1656），手工调 refresh() 是安全的。
  • 成本：额外 refresh 只发生在用户显式命令之后。单轮实测 143 ms（1000 种子）/ 309 ms（3000）/ ~500 ms（5000），3 次上限在 1.1 s 内结束，属有界突发；需在 5000 种子档复测 renderMs 确认不越过既有阈值。

步骤 3 · 兜底分两档：已确认 / 未确认

  • resolveOptimistic(hashes, true) 时给 op 打 confirmed = true。
  • 未确认（命令在途 / hang / 发送失败）：维持 3 s 回落真值 —— 「失败绝不留假状态」是红线，一个字都不动。
  • 已确认但真值迟迟不一致：放宽到 6 s 硬上限。理由是我们已经知道命令执行成功，此时弹回的必然是陈旧值；6 s ≈ 至少两轮完整轮询都没对上，说明确实是「真值与预期不同」（如 resume 后落到 error），该交还真值。

步骤 4 · 补埋点 settleMs（防止第四次）

  • _newCmdStats() 记 t0；pendingOps 归零的那一刻写 cmdStats.settleMs。
  • [perf] 阈值扩一条：settleMs > 800 报警，文案写明是「撤下慢」而非「贴上慢」。呼应既有约定 —— 真机上「慢」必须能自己说话，不能只靠用户肉眼。

步骤 5 · 视觉配套（灰窗变短后才需要，先测再定）

.is-pending 现在是 opacity: .55; transition: .18s（atlas/style.css:456 / prism/css/views.css:147）。灰窗从 3-4.5 s 缩到 ~0.3 s 后，180 ms 的双向过渡会变成「闪一下」。待步骤 1-3 落地后看观感再定：倾向于把淡出拉长到 .35 s（出现快、消失慢），而不是现在就改 —— 别在时序没修好之前调视觉，那会把问题盖住。

步骤 6 · 静态守阵

tests/test_web.py 已有「从 app.js 正则抓符号做机械比对」的静态守阵族，加一条：refresh() 内不得再出现 reapplyPending（防止有人把一致性判定绕过、退回旧路径）。

红绿双验（每条必做，缺一不算完）

  1. 把「真值一致」判定去掉 ⇒ 撤下断言应 FAIL（回到 ~3.8 s）。
  2. 把判定挪到 reapplyPending() 之后 ⇒ error 模式的「不留假状态」应 FAIL（这一步专门钉住 §05 那条 note）。

明确不做（避免范围膨胀）

  • 不改后端节拍、不碰 _web_pending_ver 门控（那是 Open issue 26-09-19-2122 的另一件事）。
  • 不引入 SSE / WebSocket 推送（想法.md 里有，但是独立议题；本方案先把现有轮询路径修干净）。
  • 不改 FakeClient（牵动大量既有断言）；状态翻转只加在 harness 的命令泵里。
  • 不动「失败 / 未确认不留假状态」的 3 s 语义。

备选（只在主方案实测仍有残留时才做）：让命令回执带上该命令执行后的视图版本号（run() 在 rebuild 之后回写 _web_results[cmd_id]["rid"]），前端据此等到 state.rid ≥ 回执.rid 再判定 —— 可以消掉「不一致但确实已刷新」这一类的等待（如 resume 后落 error 能立刻交还真值）。代价是动协议，故列为备选。

落地到主线的三处增量(在 32f531d / 12657ee 之上)

  1. settleMs 埋点（_newCmdStats / _markCmdSettle）—— 点击 → 补丁撤下、行恢复正常。这是本轮最该留下来的东西：「乐观 UI 快不快」是两个指标，前三次修复 全只埋了「贴上」那一段，于是同一现象连报三次而日志全绿。调用点覆盖 pendingOps 的全部出口 （真值对齐 / 兜底回滚 / 失败回滚），缺一处就漏记。[perf] 阈值按目标数分档（单目标 800ms、 >100 目标 2500ms —— 整剧 800 个种子的补丁本身就要 ~160ms，按单目标报会变常驻噪音）； 无回执（hang）时只记不报，那时走 3s 兜底、慢是设计如此。
  2. 桩服务 --state-revert-ms 自愈回弹（_restore_state / _revert_after_consume）—— 主线让桩服务真改状态之后，长驻进程的状态会跨轮累积： 跑过一次「整剧暂停」（合成数据里一剧 = 全部种子）后，第二轮冒烟所有行都是 s-paused， 4 条「挑一个未暂停的行」的断言集体假失败。❗回弹必须是「真值被 /api/state 取走之后 再等 N ms」，不能是「生效后 N ms」的盲定时 —— 实测定时 4s 回弹把一次整组撤下拖到 4149ms （回弹跑到了前端观测之前，把真值又改回去了）。判「已被取走」用 _web_pending_ver 被清空。 回弹记的是最初值，否则 pause→resume 连续两次会把种子还原成暂停态。
  3. 静态守阵 _scan_pending_settle（tests/test_web.py）—— 钉住主线的三处易写反点：_snapshotTruth(state) 必须在 reapplyPending() 之前、判定必须走 _optimisticSettled、回执后必须调 _pullTruthAfterCmd。 红验已确认：把 _snapshotTruth 挪到 reapplyPending() 之后 ⇒ 守阵 FAIL （「快照到的是被补丁改过的行值，判定恒真 ⇒ 失败路径留假状态」）。

与计划的五处偏差(都是实施中撞出来的)

  1. 桩服务还得自愈回弹(计划没有): 命令泵真的改状态之后, 长驻桩服务的状态会跨轮累积 —— 跑过一次"整剧暂停"(合成数据里一剧 = 全部 800 个种子)后, 第二轮冒烟所有行都是 s-paused, 4 条"挑一个未暂停的行"的断言全部假失败。加了 --state-revert-ms。回弹还不能是盲定时: 定时 4s 回弹实测把一次整组撤下拖到 4149 ms(真值被回弹改回去了), 改成等真值被 /api/state 取走之后再回弹(_revert_after_consume)。
  2. 三条「pending 可见」断言改了写法: 原写法是"点一下 → 睡 120/150ms → 看有没有 is-pending"。修好撤下后窗口从常量 3s 变成变量(54 ms ~ 350 ms), 固定采样会因为它比窗口还长而假失败 —— 失败的原因恰恰是修复生效了。改为 MutationObserver 在点击之前就位、记录"是否出现过"。
  3. 批量断言改取峰值: 同理, 原来 1500 ms 后取一次瞬时值, 现在窗口 ~350 ms ⇒ 恒读到 0。改成窗口内 20 ms 步长取 pendingOps 峰值(实测峰值 60 / 目标 60)。
  4. [perf] 阈值按目标数分档: 单目标/小批量 800 ms, >100 目标 2500 ms —— 整剧 800 个种子的补丁本身就要 ~160 ms, 按单目标阈值报会变成常驻噪音, 而常驻的报警没人看。
  5. 步骤 5(视觉)未动: 实测窗口 200–350 ms, 配合 opacity .55 / transition .18s 呈一次柔和脉冲, 不闪。留给真机观感确认再定, 不在没有观感反馈时改 CSS。
