摘要

把 qB 界面拆成 9 个功能区逐项对照后, 结论分三句话:

① 主体缺一座「种子中心视图」。 现在 WEB UI 的一切以辅种分组为中心 (组 → 成员), qB 的一切以种子为中心 (平铺列表 → 详情面板)。这是结构性缺口, 也是替代 qB 的第一优先级。 好消息是第八轮的 singles 视图 + TORRENT_COLUMNS列模型已经把这条路的头开出来了。

② 数据层已经铺好路, 只差"端点 + UI"。 2026-09-15 合入的 TorrentRecord 70 字段 全量缓存 (官方注释写明"为 WebUI 后续功能供数") 覆盖了 qB 详情面板所需的绝大部分字段 (ETA/做种数/下载量/可用性/magnet_uri/infohash_v1v2/分享率限制/超级做种标志…)。 唯一没接住的是 server_state (全局统计/DHT节点/队列状态) —— apply_sync 目前把它丢掉了, 属于小改。

③ 两个真正要设计的是"人机边界", 不是"能不能做"。 一是添加种子后 auto-qb 自动化 (归组/标签/校验) 如何接管并让用户理解; 二是手动限速/龟速模式与 auto-qb 限速曲线的托管语义。其余操作 (校验/超级做种/限速/移动/改名/导出…) 全部是 qB API 直接映射, 走现成的命令队列 + 回执模式, 单项规模 XS~S。

01

对标范围与口径

对标对象是 qBittorrent 桌面 GUI (4.x/5.x, 与原生 WebUI 功能面基本一致)。按使用频率把 qB 界面拆成 9 个功能区, 用户口径为「除 qB 非常用设置外, 支持绝大部分功能」—— 因此 qB 设置对话框整体列入 P2 (只读展示 + 白名单可写, 默认不做), RSS/搜索两个大模块 按 PT 使用场景列入 P2 延后。

qB 功能区qB 里的形态WEB UI 现状判定
1. 种子列表主视图平铺全量种子, ~35 列, 状态/分类/标签/tracker 筛选侧栏, 多选批量, 右键菜单 ~25 项 分组视图 (组→成员展开) + singles 单种子视图; 13 个展示字段; 筛选/搜索/列管理齐备 P0 缺口
2. 种子详情面板General / Trackers / Peers / HTTP Sources / Content / Speed 六个 tab 无详情面板 (成员行仅展示字段; 想法.md 已有"详细信息显示所有字段"待办) P0 缺口
3. 种子操作添加/启停/删除/校验/汇报/限速/分享率限制/超级做种/移动/改名/队列/复制/导出… 仅 启停/汇报/删除 (组+单种, 带回执确认链) P0/P1 缺口
4. 添加种子文件/磁力/URL + 完整选项 (保存路径/分类/标签/启停/跳校验/顺序下载/分享率…) 无任何添加入口 (QbApi 透传已就绪) P0 缺口
5. 分类与标签管理分类 CRUD (含保存路径) / 标签增删 / 左侧树 只读透出 (筛选器 + 共同标签列); 无增删改 UI P1 缺口
6. 全局状态与统计底部状态栏 (DHT/速度/总量/龟速开关) + 统计对话框 + 全局速度图 速度/今日流量/限速对照有 (曲线数据源); DHT/累计统计无 (server_state 未捕获) P1 缺口
7. 日志WebUI Log tab (main/peers) ; GUI 消息日志 无日志页 (托盘 UI 有日志视图可参考; 自身 RotatingFileHandler 文件已在) P1 缺口
8. 搜索 tab / RSS tab搜索引擎插件 + 全网搜索; RSS 订阅 + 自动下载规则 无 (注意: 站内文件搜索是另一回事, 已有且比 qB 强) P2 延后
9. qB 设置对话框下载/连接/速度/BT/WebUI/高级 七组 preferences 无 (用户口径排除非常用设置; 且与 auto-qb 假设有冲突面) P2 / 默认不做

另有四类明确 不做: HTTP Sources tab (web seeds URL 清单, 场景极少); 「打开所在文件夹/预览」(浏览器沙箱做不到, 桌面专属); 多用户/登录体系/封禁 (单用户 Bearer token 已覆盖); 多语言 (界面为中文单一语言)。

02

现状盘点: 已覆盖与超集能力

评估"缺什么"之前先说清"有什么"。以下能力经过六轮打磨 + 重设计 + 第八轮, 均已实施并有冒烟/测试覆盖:

能力现状相对 qB
辅种分组视图组→成员展开, 状态摘要/共同标签/保存路径/大小一致性, HR 栏与筛选 (达标/未达标), singles 单种子视图 qB 没有的超集 —— 这是本项目的立身之本, 替代 qB 后仍应保留为第一视角
筛选与搜索状态 chip / 保存路径 / 标签·分类·站点多选 / H&R 筛选; 按种子名 + 文件列表内容搜索 (带限流增量索引) 文件内容搜索是 qB WebUI 没有的
列表交互列选择器/列宽拖拽记忆/排序/批量多选 (Shift 范围)/右键菜单/批量条吸顶 与 qB 相当 (列数少)
操作与回执组/单种 暂停·开始·删除 (含文件可选)·强制汇报 (tracker 确认链, 非"发了就算") 汇报确认链比 qB 原生更认真
信息栏与图表速度/今日流量/刷新间隔/限速对照卡; 历史流量双系列图 (天/月/年, Traffic Monitor dat) 历史流量 qB 原生没有

形态双 UI (星图 atlas / 棱镜 prism ×5 主题) + 共享逻辑层; rid 增量轮询退避; 移动端响应式—
推论: 替代 qB 不是推倒重来, 而是在现有骨架上加一个「种子页」一等公民 + 一批操作命令 + 三四个新端点。辅种视角与种子视角共享同一数据层与命令管线。
03

数据层与 API 现状 (可行性的地基)

3.1TorrentRecord 70 字段 —— 详情面板的数据已备齐

torrents/compat.py 字段表 = 必需 21 + 重加升格 6 + 可选扩展 43。 扩展字段按 qB 真机样例定稿, 缺失时取 qB 自身哨兵值 (-1/-2/8640000), qB 新字段自动落 _raw 不丢数据。对替代 qB 而言, 关键是以下字段已经在缓存里:

不在 70 字段内、需要额外 API 的只有四样: tracker 明细列表 (rec.trackers_info 惰性缓存已包装)、 文件列表 (rec.files 惰性缓存已包装)、peer 列表 (未包装, 需透传)、piece 状态图 (未包装, 可选)。

3.2server_state —— 唯一没接住的全局数据

qB /sync/maindata 响应除 torrents 外还带 server_state (全局累计上下行/会话统计/DHT 节点数/队列计数/平均速度/connection_status 等)。 store.apply_sync 目前只取 torrents 与 torrents_removed, server_state 被丢弃。补法: store 增加一个原子替换的只读字段, 全量/增量轮都更新 (qB 每轮都回), Web 端点透出即可 —— XS 级改动, 解锁全局状态栏与统计面板。

3.3写操作管线 —— 命令队列 + 回执已是样板

现有 WebCommandsMixin: Web 线程只投递 (cmd, payload) 到队列, 主循环单线程消费执行, 写 _web_results 回执, 前端轮询 /api/cmd/{id}。 强制汇报的「tracker 确认链」(基线 → 逐 tick 复查 → 30s 超时聚合回执) 是"长结果确认"的 现成样板 —— recheck 校验完成确认可完全复用同一模式。handlers 是一张 dict 分发表, 新命令 = 加一行注册 + 一个 _cmd_* 方法。

结论: qB WebUI API 的能力面 (qbittorrent-api 全覆盖) 与本项目的封装面之间没有断崖, 缺的方法全部是薄封装; 单位/版本坑 (qB5 transfer 端点、-1/-2 哨兵) 已在现有代码里趟过并留了注释。
04

缺口清单与可行性 (核心章节)

可行性: 高 = API/数据现成, 工作量在 UI 与接线; 中 = 无技术障碍但有设计决策或新基建; 延后 = 可行但规模大且非刚需。 规模: XS=单点小改 / S=单点功能 / M=整页或跨层 / L=整模块。以下均为本次逐文件核实的判断。

架构影响与复用模式

5.1直接复用的四套既有机制 (零新增架构)

命令队列 + 回执

所有写操作继续走 Web 线程投递 → 主循环单线程执行 → /api/cmd/{id} 轮询回执。 新命令只是 handlers 表加行。单一写线程黄金法则不破。

长结果确认链

汇报确认 (baseline→逐 tick 复查→30s 超时聚合) 是"发指令≠完成"的样板, recheck 与移动种子 (moving 状态观察) 直接套用。

rid 版本门控 + 惰性视图

平铺列表沿用 groups/singles 的同快照同版本门控; 无变化不回传不重渲染。 已在 ensure_group_state 验证的语义直接复制。

量化步长防重建风暴

新增展示字段 (尤其 ETA/速度/时间戳) 必须配套 _VIEW_QUANTUM, 否则活跃种子库每 tick 重建 —— 机制在, 纪律要跟上。

5.3双 UI 成本 —— 最大的工程学问题

逻辑层三件套共享, 但模板双份: 每个新页面 = atlas + prism 两套模板 × 各自 CSS 契约。 「种子页 + 详情面板 + 添加对话框」是本轮最大增量, 双份成本真实存在。 三个选项:

选项说明代价
甲. prism 主战场替代 qB 的新功能一律先落棱镜 (五主题/新设计语言), atlas 冻结增量只修 bugatlas 用户 (当前默认 UI) 拿不到新功能; 需要一次"默认 UI 切换"
乙. 双 UI 同步跟进每个功能两套模板都做前端工作量 ×2, 长期漂移风险

06

自动化 × 手动操作的冲突边界 (本项目特有)

auto-qb 的立身之本是自动化规则; 替代 qB 界面意味着引入大量手动操作。 两者的互踩点必须在 UI 层讲清楚, 否则用户会得出"程序坏了"的错误结论。 逐项核对自动化代码后的边界表:

手动操作会与之互踩的自动化建议策略
手动打/删标签, 建分类 auto_categories 覆盖逻辑 (hash 级记录, 同类自动设置可覆盖); delete_tags 定期清理未使用标签; remove_similar_tags; HR/集数标签模板打标 自动管理标签 (HR 语义色已有) 在 UI 标"自动"; 未使用标签清理给出规则提示; 分类编辑面板标注"auto_categories 已接管该种子的分类"
手动单种限速 tracker 级限速任务幂等覆盖 (_apply_speed_limit, 按站点配置周期执行) 受托管种子显示"站点限速托管中"徽标; 编辑入口仍开放但附说明
手动全局限速 / 龟速模式 全局限速曲线任务按时间档位覆盖全局上下行 (含 merge 取最严) 决策点 D2: 曲线启用时手动全局限速入口改为"查看 + 临时覆盖至下个档位切换", 曲线停用时恢复常规编辑
手动开始/暂停 规则动作 (start/stop)、同组下载冲突自动暂停、HR 达标暂停等状态机 手动操作保留 (自动化只管它该管的时刻); 组冲突暂停等带原因的场景在详情页显示最近一次自动操作原因 (state_file 已有轨迹可查)
手动移动种子 (set location) 组键 = (save_path, 文件路径元组); 移动成员触发重归组/离组; 缺文件扫描被触发 确认框明示"移动后该种子将离开当前辅种组"; 整组移动提供组级入口 (按组键整组改路径) 避免拆组
手动 recheck 组内校验串行化闸门 (active_check_hashes); skip/full-checking 规则流程 手动校验登记进同一闸门; 同组校验中提示"排队中"
手动删除种子 state_file 规则状态/执行记录、_pending_removed 回环保护 (已处理) 现状已正确; 删除确认框可补充"该组剩 N 个成员, 剩余是否仍构成完整辅种组"提示 (增强, 非必需)
总原则 (与黄金法则同源): 手动操作不绕过命令队列、不绕过 QbApi (快照同步会失真)、 不绕过闸门; 自动化不改写用户手动值之外的东西; UI 把"谁在管"显示出来。

风险红线与验收口径

9.1风险与红线

风险应对
视图重建成本: 平铺字段集 ~30 项, 活跃种子库速度字段每 tick 变严格配 _VIEW_QUANTUM (速度类分桶/时间类取整); 复用"Web 活跃才重建"窗口机制; 必要时平铺视图降频 (速度列单独走轻量端点)
危险写操作 (删除/移动/跳校验添加) 误触沿用第六轮确认框体系 (成员明细/勾选/汇报选项); 跳校验添加默认关闭 (保守默认原则)
上传端点安全 (multipart)Bearer 已覆盖 /api/*; 限制单文件大小与类型; 临时文件落 data_dir, 主循环线程消费后即删
qB 版本 API 差异 (4.x/5.x 端点改名)qbittorrent-api 已锁 2026.8.1; transfer 端点坑已趟; 新增封装沿用"qB5 优先 + 哨兵默认"的既有处理
双 UI 漂移D1 决策后写入红线 (atlas 冻结期内不得加功能)
自动化互踩造成"设置失效"错觉§06 边界表逐项落 UI 文案; 托管徽标优先于功能本身
per-torrent 轮询 (peers/trackers 详情) 放大请求量详情面板打开时才轮询、关闭即停; 不进主循环 tick; 沿用退避策略

9.2验收口径: 什么时候算"能替代 qB 界面"

  • 看: 种子页平铺全量种子, 列/筛选/搜索/详情 (General/Trackers/Peers/Content) 不需要 qB WebUI —— Phase 1 完成。
  • 动: 添加/启停/删除/校验/汇报/限速/分享率限制/移动/改名/导出/分类标签管理全部在 WEB UI 闭环 —— Phase 2 完成。
  • 懂: 全局统计 (会话/累计/DHT) 与 auto-qb 日志可在 WEB UI 查看; 自动托管状态 (曲线/站点限速/HR) 在界面上可辨识。
  • 留: qB 原生 WebUI 保留为逃生门 (auto-qb 端口独立, 互不侵占), 设置类非常用操作走逃生门 —— 与用户"非常用设置除外"的口径闭环。
一句话总结: 目标可行且路径清晰 —— 数据层已经铺好 (70 字段), 写管线已经验证 (命令队列+确认链), 缺口是"一个种子页 + 一批 XS/S 级命令 + 三个新端点 + 两个设计决策"。 真正要防的不是技术风险, 而是双 UI 成本与自动化互踩的体验债。
