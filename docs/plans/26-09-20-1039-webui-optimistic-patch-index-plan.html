把逐 hash 的全表扫描换成一次建成的 hash 索引

大库批量操作时，applyOptimistic 对每个目标 hash 线性扫三张全表，复杂度是 O(目标数 × 数据集规模)。3000 种子全选暂停实测补丁 1.8–2.1 秒，且同样的代价在 reapplyPending 里每轮 refresh 都要再付一次。本计划按 issue 建议的方案 A 改造：入口建一次索引，四个调用点共用。

01

结论先行

改动集中在一个文件、一个 helper：shared/commands.js 里新增一次建索引的私有方法，把四个「逐 hash 扫全表」的调用点换成按 hash 命中。行为逐条等价，不引入新契约。

预估收益（数据集 3000 / 目标 3000，本机实测）：补丁 1810 ms → 约 9.5 ms；reapplyPending 单轮 1588 ms → 约 10 ms。索引本身只要 2.1 ms。

为什么现在才动它：这条耗时长被记成「大库抖动」，是因为 [perf] 只报一个「补丁 2033ms」的数字，看不出是算法复杂度还是偶发卡顿。本次用受控探针把它定性后才认领 —— 见下节证据。

03

现状代码地图

_forEachRow(hash, fn) 遍历 torrents → singles → groups[].members 三张表，命中即回调。四个调用点全部是「外层逐 hash、内层全表扫」的嵌套结构（行号取证 2026-09-20 10:33）：

调用点行号频次代价
applyOptimistic 贴补丁172每次点击 1 次O(目标 × 数据集)
resolveOptimistic 失败回滚197每次失败 1 次O(目标 × 数据集)
_expirePending 3s 兜底回滚154每轮 refresh（仅超时项）O(超时项 × 数据集)
reapplyPending 刷新后重贴215每轮 refresh（全部 pending）O(pending × 数据集)

调用侧：act() :364 / bulkAct() :421 / actTorrent() :478，三处都是「先 applyOptimistic 再 POST」，顺序与本计划无关，不动。

必须保住的语义

  • 一个 hash 可能命中多行：平铺数组、singles、组成员里可能出现同一 hash 的多个行对象（甚至同一对象被两个数组引用）。改造后必须对每个命中行都执行回调，不能只取第一行。
  • 迭代顺序不变：torrents → singles → groups[].members。同一 hash 命中多行时，prev 快照与 pendingOps[h] 的写入以最后一次为准 —— 顺序变了结果就变了。
  • 取不到行即不做：视图缺行时（如追剧视图 payload 只回 shows）现状是扫不到就不做事。索引取不到同样不做，行为一致。
04

改造设计

新增：一次建索引

_buildRowIndex() {
  const idx = new Map();
  const push = (r) => {
    if (!r || !r.hash) return;
    let a = idx.get(r.hash);
    if (!a) idx.set(r.hash, (a = []));
    a.push(r);                      // 同一 hash 多行: 保留, 顺序即遍历顺序
  };
  for (const r of this.torrents || []) push(r);
  for (const r of this.singles || []) push(r);
  for (const g of this.groups || []) for (const m of g.members || []) push(m);
  return idx;
}

四个调用点改为「一次建索引 + 按 hash 命中」

  • applyOptimistic：入口建一次 idx，逐 h 取 idx.get(h)；原回调体（_optimisticPatch → prev 快照 → Object.assign → 写 pendingOps[h]）逐字保留。
  • resolveOptimistic 失败分支：同上，Object.assign(row, op.prev) 逐字保留。
  • _expirePending：循环外建一次索引（现在是每个超时 hash 扫一次全表）。
  • reapplyPending：循环外建一次索引 —— 收益最大的一处，单轮 1588 ms → 约 10 ms。

失效策略：一律现场建，不缓存

每轮 refresh 会整表替换行对象，索引不能跨轮缓存。实测建索引只要 2.1 ms，远低于收益，因此 W1 起一律「每次调用现场建」。跨轮缓存（按版本号 / rid 失效）不在本次计划内，理由见第 07 节。

顺带：让 [perf] 别再常驻报警

commands.js:106 的判定是 (c.patchMs || 0) > 50 —— 阈值恒定；而同文件 :54 的 settleMs 是按目标数分档的（>100 目标 → 2500 ms）。两处口径不一致，导致大库批量必报、变成没人看的噪音。改法：patchMs 沿用同一张分档表。

07

红线与不做的事

  • 不动后端：本问题纯前端，web_view.py / web_runtime.py / web_commands.py 一行不改。
  • 不动语义：_snapshotTruth、_optimisticSettled、3s 兜底、settleVia 标记、isPending 一律不动 —— 它们各自对应一条已修的 issue（2024 / 2141 / 1939）。
  • 不做跨轮缓存：整表替换下行对象 identity 会变，缓存一旦失效判断漏一处就是「补丁贴到旧行上」，比慢更危险。要做得配显式失效 + 守阵，属独立改动。
  • 不合并 pendingOps 写入：this.pendingOps[h] = ... 的 3000 次响应式写入已在 C 段 7.4 ms 内，不是瓶颈，不动。
  • 不改 reapplyPending 的调用时机：只换查找方式，不换它每轮都跑这件事。
08

备选与后续

  • 方案 B（视图层给行引用）：后端构建视图时直接出 hash → 行 的索引，前端不再扫表。改动跨前后端，收益上限更高，但风险面大得多 —— 本次不选。
  • 整组 / 整剧的批量粒度：即便查找降到 O(1)，3000 目标仍有 3000 次响应式写入与一次 bulk 命令往返。若真机仍嫌慢，下一步该看的是「大库批量是否要分片」，属另一条线。
  • 探针脚本：.workbuddy-ai/tmp/patch-probe*.cjs 目前是临时产物。若希望它成为可复用的回归工具，应搬进 scripts/ 并接进冒烟 —— 不在本次计划内，需要时另立任务。
