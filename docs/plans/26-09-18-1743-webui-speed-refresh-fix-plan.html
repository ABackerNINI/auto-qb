种子速度刷新滞后 —— 根因定位与修复计划

现象: 种子行的「下载 / 上传」速度长时间不刷新(或十几秒才跳一次), 而状态栏的速度合计看起来完全正常。 已用可复现探针定位到根因 —— 不是 qB 取数慢, 也不是前端渲染慢, 而是 后端两条视图重建路径的重建范围不一致, 共享脏标记被主循环提前消费, 导致种子页/单种子/追剧三份视图长期拿不到重建, 版本号却照常自增, 前端于是把陈旧数组当成新数据换上去。

01

结论速览

根因(主因)

后端有两条视图重建路径, 重建范围却不一致:

  • QbManager._tick(主循环) 只重建 _group_view, 却把共享的 _group_view_dirty 标记清掉;
  • WebviewMixin.ensure_group_view(Web 线程) 会重建全部四份视图 (groups/singles/shows/flat), 但它只在标记仍为真时才动手 —— 而主循环已经把它清了。

结果: 种子页(_flat_view)、未归组单种子(_singles_view)、 追剧页(_shows_view) 长期不重建, 而版本号 _group_view_ver 照常每 tick 自增 ⇒ 前端判定 updated = true, 把陈旧数组整表换上去。

为什么状态栏看起来正常

状态栏的「下载 / 上传速度合计」是 Σ groups[].dlspeed (app.js 的 totalDl/totalUl), 取的是 分组视图 —— 恰恰是主循环每 tick 都在重建的那一份, 所以它永远新鲜。 同一屏上「新鲜的速度合计」与「陈旧的种子行速度」并存, 观感就是"状态栏对、种子不对"。

次因(放大器)

前端把「视图版本没变」当成「没数据」, 触发轮询退避 2s → 5s → 10s (currentPollMs() 的 idlePolls)。而状态栏走的 /api/stats 是恒回传、不受版本门控的独立请求 —— 两条数据源在 同一轮轮询里刷新频率被彻底解耦, 进一步放大了"只有种子行慢"的观感。

先把"速度"这个数字在全链路上的出口列全。它们不是同一个数据源, 门控方式也完全不同:

展示位置 前端取数 后端来源 刷新门控

03

探针实测: 可复现的确定性结果

用仓库既有测试替身(tests/helpers.make_manager + FakeClient)搭最小复现: 两个下载中种子, 每轮 tick 前把速度改成新值, 交替执行「主循环 tick → Web 请求」。 

--- grouping.enabled=True (用户最可能的配置) ---
  seed ver=1789724721
  after tick1: ver=1789724722 dirty=False store.view_changed=False
     group_view rows=0  flat=[]  singles=[]  shows=0      ← flat/singles 从未被建起来
  web1: rid=1789724722 updated=True  flat=[]
  t2: ver=1789724723 updated=True  回传flat=[]  | store真值=[('H1', 999), ('H2', 888)]
  t3: ver=1789724724 updated=True  回传flat=[]  | store真值=[('H1', 555), ('H2', 444)]

--- grouping.enabled=False ---
  after tick1: ver=1789724721 dirty=True
  web1: rid=1789724722 updated=True  flat=[('H1', 100), ('H2', 200)]   ← Web 线程自己撞上脏窗口, 建对了
  t2: ver=1789724722 updated=False 回传flat=[]  | store真值=[('H1', 999), ('H2', 888)]
  t3: ver=1789724722 updated=False 回传flat=[]  | store真值=[('H1', 555), ('H2', 444)]

3.1两种配置都坏, 坏法不同

配置表现机制
grouping.enabled = true 版本号每轮自增 ⇒ updated=true ⇒ 前端每次都换表, 换上去的却是永不重建的 _flat_view。 种子页速度冻结 主循环消费标记 + 只重建 group view
grouping.enabled = false 标记被 consume_view_changed() 读走后丢弃(置脏语句在 if grouping.enabled 块内) ⇒ 版本号再不变化 ⇒ updated=false ⇒ 前端不换表且开始退避。 四份视图全冻结 + 轮询降到 5s/10s 脏标记被吞
注意

上表第二行说明 _flat_view 只在「Web 线程恰好自己撞上脏窗口」时才被建起来 —— 这个窗口要求 _web_last_seen 已过期(> WEB_VIEW_TTL = 10s)。 所以真机上它会偶尔跳一次再冻住, 这正好解释了用户说的"更新慢"而不是"完全不更新"。

04

根因拆解(含代码位置)

R1两条重建路径范围不一致(主因)

src/auto_qb/qbmanager.py:394-405

# 视图相关内容变化(store 视图字段/组成员)读取并复位, 供下方分组视图惰性重建判定
view_changed = self.store.consume_view_changed()
if self.config.grouping.enabled:
    if view_changed:
        self._group_view_dirty = True
    if self._group_view_dirty and (time.time() - self._web_last_seen) < WEB_VIEW_TTL:
        self._group_view = self._build_group_view()   ← 只重建这一份
        self._group_view_ver += 1
        self._group_view_dirty = False                ← 共享标记被清

src/auto_qb/mixins/web_view.py:517-529

def ensure_group_view(self):
    if self._group_view_dirty:            ← 走到这里时通常已是 False
        self._group_view = self._build_group_view()
        self._singles_view = self._build_singles_view()
        self._shows_view = self._build_shows_view()
        self._flat_view = self._build_flat_view()
        self._group_view_ver += 1
        self._group_view_dirty = False

两份代码都想表达"惰性组装", 但主循环那份少建了三份视图却照清标记, 使 Web 线程那份的兜底彻底失效。这正是 memory-bank/pitfalls.md 里"单种子视图数据面: singles 与 groups 同脏窗口同快照同版本门控" 那条约定被单方面破坏的地方 —— 约定写了, 但没有机械守卫。

R2关闭分组时脏标记被吞

consume_view_changed() 在门控外被调用(读走并复位), 而唯一的置脏语句在门控内。于是 grouping.enabled=false 时, 标记读一次就永久丢失, _group_view_dirty 再也不会变真。 这条与 R1 同源: 把"分组是否启用"错当成了"Web 视图是否需要维护" —— 两者无关(分组关闭时 _flat_view/_singles_view 恰恰是种子页的唯一数据源)。

R3前端 idle 退避与状态栏数据源解耦(放大器)

src/auto_qb/web_ui/static/shared/app.js:1493-1500, 1507-1530

currentPollMs() {
  if (this.pollFails) return Math.min(15000, this.pollSec * 1000 * 2 ** this.pollFails);
  // 无变化退避: 连续多轮无更新逐步放慢(2s→5s→10s); 一旦有更新立即回到 2s
  if (this.idlePolls >= 6) return 10000;
  if (this.idlePolls >= 2) return 5000;
  return this.pollSec * 1000;
}
  • idlePolls 只在 state.updated === false 时自增 —— 即把视图版本号当成了"数据是否新鲜"的代理。
  • 但状态栏数据来自 /api/stats(server_state), 完全不走版本门控, 每轮都刷新。
  • 两个源在同一轮轮询里刷新频率不同 ⇒ 只要视图版本安静几轮, 行数据就退到 5s/10s, 而状态栏仍在 2s 更新 —— 观感上就是"只有种子慢"。
一句话归因

主循环与 Web 线程各自维护同一份视图, 却对"重建哪些视图"没有共识; 前端又把"版本号未变"误读为"数据未变", 于是把这一处后端不一致放大成肉眼可见的 「状态栏正常 / 种子行滞后」。

06

修复计划

分三阶段: P0 修正确性(必做), P1 消除放大器(必做, 小改), P2 测试与文档收尾。 原则是收敛成唯一重建入口, 而不是在两处各打一个补丁 —— 否则下次加第五份视图还会漏。

P0后端: 视图重建收敛为唯一入口

P0-1

在 WebviewMixin 抽出 rebuild_views()

把"重建四份视图 + 自增版本号 + 清脏标记"收成一个方法, 作为唯一的重建入口。 ensure_group_view 与 _tick 都改为调用它, 从此不可能再出现"只重建一半"。

改: src/auto_qb/mixins/web_view.py · ensure_group_view 内联代码抽出

P0-2

把置脏语句移出 grouping.enabled 门控

if view_changed: self._group_view_dirty = True 必须在门控外 —— 标记是 Web 视图的共享状态, 与分组功能是否启用无关(修 R2)。 门控只保留给"要不要在主循环里花 CPU 重建"这一个决策。

改: src/auto_qb/qbmanager.py:394-405

P0-3

主循环改调 rebuild_views(), 并去掉"分组未启用就不重建"的分支

建议直接把主循环的重建分支改为 if self._group_view_dirty and web_active: self.rebuild_views() —— 去掉 grouping.enabled 前置判断。 理由: 种子页的数据源 _flat_view 与分组功能无关, 主循环仍受 WEB_VIEW_TTL(网页不开就不建)与脏标记(没变化就不建)双重节流, 惰性语义不受影响。

备选: 若担心 CPU, 保留门控 —— 但必须同时保证标记不被吞(即 P0-2), 此时分组关闭时由 Web 线程每请求重建一次(与今日行为一致)。 两者取其一, 不可都省。

性能提示

P0-3 采用"去掉门控"方案后, 主循环每 tick 会多建 _flat_view(O(N) 个 dict) 与 _shows_view(每种子一次 tvshows.parse_release)。 仅在 Web 活跃且视图有变化 时发生(活跃下载中才会每轮置脏), 但仍应在真机 1000+ 种子的库上观察一次 tick 耗时; 若明显变差, 再考虑给 shows 视图单独加节流(不建议一开始就加)。

P1前端: 拆掉与状态栏不一致的退避

P1-1

取消 idle 退避, 只保留失败退避

轮询间隔恒定 pollSec(2s); pollFails 的失败退避保留不动。 理由: 每次轮询本来就会额外打一发 /api/stats, idle 退避省下的请求极少, 却直接牺牲了行数据的新鲜度 —— 收益与代价完全不对等。

改: app.js currentPollMs() · 顺带清理 idlePolls 相关状态与 refresh() 里的自增

P1-2

(建议同批) 把 server_state 并入 /api/state

P1-1 会让请求频率稳定在 1 轮/2s, 但每轮仍是两条请求(/api/state + /api/stats)。把 store.server_state 作为 status.server 一并回传, syncStats() 即可退役, 请求数回到 1/轮, 且状态栏与行数据同源同轮 —— 从结构上消灭"两个速度来源"的错位。 /api/stats 端点保留给统计面板手动刷新用。

改: src/auto_qb/web.py api_state · app.js syncStats()/refresh()

P2验收与回归

  • 两套皮肤(星图 atlas / 棱镜 prism)各走查一次种子页与追剧页, 速度列应每 2s 连续变化。
  • 对照 /api/stats 的全局速度与种子页行速之和, 量级应吻合(允许采样时刻差)。
  • 关闭分组功能再走查一次(验证 R2 修复: 行数据仍新鲜)。
  • 关掉网页 30s 后确认主循环不再重建(验证惰性未被 P0-3 破坏)。

风险与回退

风险影响对策
主循环每 tick 多建 3 份视图 大种子库(1000+)且活跃下载时, tick 耗时上升 先在真机测 tick 耗时; 必要时退回"保留 grouping 门控 + 标记不吞"的备选方案(P0-3 备选)
P1-1 取消退避后请求变密 每轮 2 条请求; 若不做 P1-2 则翻倍 与 P1-2 同批提交, 回到 1 请求/轮
改写既有用例会"看起来删了断言" 评审误解为降低覆盖 改写时保留原用例的意图(惰性/不空转), 只把断言对象从"仅 group"换成"四份视图同建"; 并在 commit message 注明"原断言固化了缺陷"

回退成本: 全部改动集中在 web_view.py / qbmanager.py / app.js / web.py 四处, 建议分两个 commit(P0 后端 / P1 前端), 任一可独立 revert。
