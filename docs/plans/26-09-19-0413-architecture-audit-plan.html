02结论摘要

这套代码的底层是对的：/api/v2/sync/maindata 的 rid 增量同步把"每 tick 全量拉种子"这个 PT 工具最大的成本点压到了 O(变化数)； 单一时间堆统一所有任务、只有两个动词；脏标记把分组与视图从轮询改成了事件驱动。这些不该动。

出问题的是三条约定在压力下被绕过。一是"只有主循环线程写共享状态"——Web 线程实际在重建视图； 二是"所有 qB 调用走 QbApi"——Web 层直接拿裸 client；三是"视图惰性重建"——脏判定把速度类字段算进去， 使惰性在活跃种子库上退化成每 tick 全量重建。三条互相放大：重建越频繁，并发撞车与 API 风暴的概率越高。

03P0 · 必修

四条都已在源码中确认。前两条是同一条链路的两端，建议一起修（Wave 1 – 2）。

P0

「单一写线程」不变量被 Web 线程打破

A1
src/auto_qb/web.py:201,207 · src/auto_qb/mixins/web_view.py:541-542 · src/auto_qb/qbmanager.py:406-407
现象
web.py 的处理器是同步 def，FastAPI 会放进线程池；ensure_group_view() 在脏时直接调 rebuild_views()，而主循环 _tick 也调同一个方法。全项目只有 notify.py:216 与 ui.py:48 有锁，视图侧没有任何锁。
后果
_group_view_ver += 1 是读-改-写，并发下丢失更新；四份视图可与版本号错位 —— 前端按版本号判定"一致"却拿到错位的数组。这正是上一轮"速度刷新滞后"的同源根因：那次修的是重建范围不一致，并发这一半没修。
触发
浏览器打开 + 主循环同时命中脏标记。种子越活跃，撞车概率越高。
方向
Web 线程改为只读已发布的不可变快照；"强制刷新"走命令队列投递给主循环。若短期不能改架构，至少用一把锁把"重建 + 版本号 + 四视图赋值"包成原子发布。
P0

视图脏判定含速度类字段 ⇒ 打开页面即每 tick 全量重建

B1
src/auto_qb/torrents/view.py:9-20（_VIEW_FIELDS）· web_view.py:405（parse_release）· qbmanager.py:406
现象
_VIEW_FIELDS 含 dlspeed / upspeed / uploaded / progress，活跃种子几乎每轮都变 ⇒ view_dirty() 恒真 ⇒ 每 2s 重建 groups / singles / shows / flat 四份视图。其中 _build_shows_view 对每个种子跑一次 tvshows.parse_release（十余条正则，无缓存），_build_flat_view 每种子构造约 60 字段的 dict。
量级
N=2000 时约每 2s 做 8000 次 dict 构建 + 2000 次正则解析。qbmanager.py:406 的 WEB_VIEW_TTL 门控只在"网页关掉后"生效，页面开着就是全速重建。
连带
前端 /api/state 的 rid 版本门控因此基本失效——版本每轮都变，每轮都整表替换 DOM。修这条，前端那份 rid 优化才真正生效。
方向
① parse_release 按种子名加 LRU 缓存（名字不变则结果恒定）；② 速度/进度类字段拆到独立高频通道，不再触发整视图重建；③ 四份视图按类型拆分脏标记。
P0

跳检"已发出但未确认"时丢失 .torrent 备份

A2
src/auto_qb/rules/actions/skip_checking.py:176-182
现象
_backup_torrent 只在 torrents_add 抛异常时调用。若 add 成功但 _poll_until 三次（3 × 0.3s）确认不到种子，直接 return fail —— 不备份、不 restore_torrent。
后果
种子已从 qB 删除，data 字节只存在于内存随后丢弃 ⇒ 用户必须重新下载 .torrent；同时 store 无该记录，下轮 restore_torrent 不会执行，被误判为"已删除"。
触发
qB 重加快于 0.9s 时正常；大种子、磁盘忙、add 返回成功但随后被拒时命中。
方向
appeared 为假的分支同样走 _backup_torrent 再返回 fail。
P0

state.json 与配置写盘均非原子

A3
src/auto_qb/mixins/rule_engine.py:59-64（save_state）· src/auto_qb/config/writer.py:184-192
现象
两者都是 open(path, "w") 后直接 dump —— 无 tmp + os.replace。写前文件已被 truncate。config 侧有 backup_path 落到 data_dir 的 .bak 可救，state.json 没有任何备份。
后果
写盘时被杀 / 磁盘满 / 序列化异常 ⇒ 半截文件。state 损坏意味着执行历史与 skip_check_day 全丢，重启后规则重放（同一天可能对同一种子重复跳检）。
方向
抽一个 atomic_write()（tmp 同目录 → os.replace），state 与 config 共用；state 再留一份 .bak。

04P1 · 应修

性能

P1

搜索索引构建预算 500/tick，串行请求阻塞主循环

B2

配置

P1

D1

现象

P1
