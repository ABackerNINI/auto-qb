00结论摘要

可行性判定

可行，且是这三套测试资产里投入产出比最高的一项。判据有三条：①auto-qb 与 qB 的数据面是窄且封闭的 —— 只读端点 13 个、每 tick 真正的高频请求只有 sync/maindata 一次，其余按 hash 懒加载，全量抓一次即可覆盖；②语料体量实测可控（5000 种子 + 12 文件/种子 ≈ 16.2 MB 未压缩，gzip 后约 1–2 MB），远小于"复制真实下载盘"的量级；③文件树根本不用物化 —— auto-qb 碰磁盘的入口收敛在 4 个调用点，全部经 os.path.* / shutil.disk_usage，用一个按路径前缀限定的进程内 mock 层即可精确复现真机磁盘状态，且随 t_seq 变化（v2 修订，见 §07）。

关于性能分析（第 08 节的核心改动）：不用 --latency-ms 常数近似 —— 它既不是真机那种随载荷变化的延迟（全量 205 ms / 增量 3.3 ms），也还原不了"变化在一个 tick 内部怎么分布"。改为两件事：①可配置高频采样（性能分析档 --interval-ms 100，日常档 2 s），回放时按录制时间轴推进，客户端拿到的就是真机真实的变化序列；②周期性抓全量做对齐校验，但只保留首尾两份（T0 复用快照、T1 结束时抓）：中间检查点只用来定位漂移落在哪个时间窗，比完即弃 —— 既然增量流完整，中间的全量都能由 T0 ⊕ 增量流 重建。首尾闭合 T0 ⊕ stream == T1 是语料可信度的底线，也顺带探测 auto-qb 自己的快照会不会漂。真实 RTT 一并录下，回放按录制序列注入。

语料形态极简：一条原始流（首帧即 T0，末帧即 T1），外加流里没有的按 hash 元数据（files / trackers）。每帧是 qB 响应整帧原样落盘 —— 种子增量、server_state、tags/categories 本来就在同一帧里 ⇒ 不另造稀疏格式，也不另存 torrents / server_state / tags：种子状态只有一个来源。零语义转换即零失真，回放端退化成"按时间轴吐帧的播放器"。

真正的难点不在抓取，而在脱敏不能破坏分组等价类：auto-qb 的归组 key 是 (归一化 save_path, 排序后的文件相对路径集合)，且组内 {路径: 大小} 映射要逐项比对。一旦脱敏映射不是单射，或把路径长度/字符类别归一化掉，语料就会在回放时分出与真机完全不同的组 —— 那这份语料比合成数据更危险，因为它看起来是真的。所以第 05 节的等价类守恒校验是本计划的头号验收项，必须先于回放器完成。

  • P0全量抓取耗时：5000 种子 × (files + trackers) = 10 000 次请求，在真机 qB 上要多久、qB 自身是否被拖慢。
  • P0脱敏后分组守恒：抓完立刻用 auto-qb 自己的归组逻辑对算一遍，脱敏前后必须逐组一致（第 05 节）。
  • P1磁盘探测（--probe-fs）的负载与 temp path 覆盖修订：初轮 6 万次 stat、之后每个检查点增量一轮，打在真实下载盘上；若 qB 配了 temp path，按 save_path 根本探测不到（会记成 exists:false，与真机不符）。建议第一次跑用 --sample 200 --probe-fs=off，确认链路后再开。
  • P2R 盘持久性修订：R 盘是 Arsenal Image Mounter 挂载的虚拟盘（imdisk -l 报 "No virtual disks"，故非 ImDisk 内存盘），是否为镜像文件后端（持久）请你确认。若易失，语料不能只留这一份。空间口径已实测无异常，无需再测。
  • P2real 档才需要的稀疏可用性修订：仅当 --fs-mode=real 时才有意义 —— 需盘为 NTFS 且非压缩/去重卷。默认的 mock 档不受此项约束。
  • P0100 ms 采样对真机 qB 的负载：10 次/秒持续轮询，做种吞吐 / WebUI 响应是否被拖慢。判否即把 perf 档放宽到 250–500 ms —— 仍远细于 2 s 的 main_tick，性能分析所需的时间分辨率还在。
  • P1第二 sync session 拿全量会不会干扰增量流：rid=0 能否独立于正在递增的 rid 序列。若 qB 会重置共享序列，改用 torrents/info 做对齐基准（需声明字段差异白名单）。
  • P1全局限速两个来源的单位是否一致：server_state 的 dl/up_rate_limit vs 端点 transfer/uploadLimit（后者 auto-qb 也会调）。不一致则回放端要按各自口径回。

02目标与非目标

目标

  • G1 一份脚本把真机 qB 的数据面抓成可复现的语料（快照 + 时间轴录播，一次做完）：采样间隔可设置（性能分析档 100 ms），并周期性抓全量做对齐校验。
  • G2 脱敏到"可以贴进 issue 也不泄露 PT 身份"，同时保持一切会影响程序行为的形态特征。
  • G3 sim_qb.py 支持 --source=corpus:<dir>，与合成档并存；现有 sim_run.py 的判据尽量不动。
  • G4 新增"回放分组 == 真机分组"硬判据 —— 这是合成数据给不了的东西。
  • G5 用真实语料把 activeContext.md 里那 8 条"待真机走查"先过一遍，减少往返。

非目标

  • 不新增 src/ 行为v3 拍板。语料回放是黑盒测试，与现有仿真同定位。唯一例外：归组 key 公式抽成纯函数（§04 第 5 步）—— 纯抽取、零行为变更，用户已放行，且是本计划唯一一处 src/ 改动。
  • 不抓文件内容，只抓元数据 + 文件树（路径 / 大小）。
  • 不做"语料仓库化 / 多人共享" —— 语料只留本机，见第 10 节红线。
  • 不追求 100% 复现真机传输层耗时：改用录制真实 RTT、回放按录制序列注入来逼近（--latency-mode=recorded），不用常数近似；回环与真机网络的残余差异在结论里显式标注，不假装它不存在。
  • 不动 config.yml（红线）。抓取器只接受命令行凭据，或 --from-config 只读解析其 qB 段。

三个决定语料"能不能用"的行为约束

  • 归组 key（mixins/grouping.py:150）：key = (path_normalize(save_path), tuple(sorted(file_map.keys())))，其中 file_map = {path_normalize(f.name): f.size}。
    ⇒ 脱敏后 save_path 的等价类、文件相对路径集合必须逐元素一致。
  • 组内大小一致性（_size_mismatch）：比较组内各成员 {路径: 大小} 的完整映射。
    ⇒ size 必须原样保留，或者全语料用同一缩放比（同组内成员缩放一致则判定仍成立）。
  • 缺文件扫描（_check_missing_files:237-251）：对代表种逐个文件 os.path.exists + os.path.getsize != fsize。
    ⇒ 回放端必须有大小精确匹配的真实文件，不能只给元信息。

抓取流程（六步，逐步可中断可续）

  1. 握手与版本：auth/login → app/version + app/webapiVersion。版本写进 meta.json，回放时按版本裁剪字段。
  2. 全量 maindata：sync/maindata(rid=0)，拿 torrents map + server_state + categories/tags 的初值。
  3. 每 hash 的 files / trackers：受 --qps 限速（默认 20 QPS），并发上限 4。失败只记 warnings.jsonl，不中断 —— 缺一个种子的 files 只影响它的归组，不影响语料可用性。
  4. 磁盘探测（--probe-fs）：对每个种子的文件探测三件事 —— exists、size（getsize）、以及磁盘上的真实后缀（下载中的文件在 qB 里是 xxx.mkv.!qB，见下方 note）。记成 disk:{exists,size,suffix}。结果分两处写 —— ①初值进 files.json；②变化进流：每个全量检查点增量探测一次（只 stat 上一轮还存在的条目），差异作为该帧的 fs_delta。
    为什么值得：真机上本来就缺文件 / 大小对不上 / 还挂着 .!qB 的组，回放时按同一份表还原（v2 修订：由 §07 的 mock 层消费，不再物化真文件）；录制期间若真发生变化，回放端按 t_seq 施加 —— auto-qb 会在同样的时刻面对同样的磁盘状态，D4 从"人为注入"升级为"真机重演"，group_stop_rate / lag_ticks 原样可用。
    v2 修订成本要控：初轮 6 万次 stat、之后每检查点增量一轮（20 min × 每 60 s = 20 轮），打在真实下载盘上；建议首跑 --sample 200 --probe-fs=off，确认链路后再开。
  5. 真值归组：抓完立刻用 auto_qb.mixins.grouping 的同一套 key 公式算一遍真机分组，写入 groups.json。这是第 09 节 CORPUS.group_exact 的期望值，必须在脱敏前后各算一次。

⚠ 录流必须与 files/trackers 抓取并行 v2 修订 第 2 步（全量 maindata）与录流开始之间夹着第 3 步：每 hash 的 files / trackers = 10 000 次请求，按 --qps 20 算是 ≈ 8 分钟。这 8 分钟里 rid 会话不会丢数据（qB 累积变化），但首个增量帧会把这 8 分钟的全部变化压成一帧，t_seq 时间轴起点被推后 —— 原文说的"零缝隙"只在数据完整意义上成立，时间轴意义上不成立，而"变化在一个 tick 内怎么分布"恰恰是性能分析要的东西。
修法（二选一）：①并行 —— files / trackers 抓取走独立线程 + 独立 session，录流不被挡住（推荐）；②在 meta.json 记 record_start_offset_ms，回放端显式跳过这段。别让"零缝隙"变成读者以为已解决的模糊承诺。
⚠ 磁盘上不只有"存在/不存在"两态 ① 大小也是判据：缺文件检测里 os.path.getsize(full) != fsize 同样判为缺失（_check_missing_files:244）—— 部分下载、文件被替换、填充中的文件都靠大小发现。所以探测必须带 size，回放时按探测值回给 auto-qb（v2 修订：mock 层直接回表里的值，无需"建出"任何文件）。
② .!qB 后缀：qB 下载中的文件在磁盘上叫 xxx.mkv.!qB（可在设置里关掉）。缺文件检测拼的是 save_path + 逻辑文件名，所以带后缀的文件在它眼里就是"不存在" —— 这是真机的真实行为，回放必须还原，否则下载中的组会被误判成"文件齐全"。记后缀而不是记整个实际文件名：后缀不含敏感信息，且避免与脱敏后的文件名产生第二份映射。
③ 已知的边界（W0 实测 / 后续）：若 qB 配了 temp path（下载中文件另存他处），按 save_path 根本探测不到 ⇒ 这类文件应记成 exists:false, suffix:null 并记 warnings.jsonl；若要完整覆盖，需从 app/preferences 读 temp_path 一并探测。
录制期间新出现的种子：出现即 append 流里出现第 0 帧（T0）中没有的 hash ⇒ 当场抓它的 files / trackers，追加进 files.json / trackers.json，不等到结束再补 —— 事后补抓时种子可能已经变了甚至没了，还要多遍历一遍。
补抓会让这一帧变长：没关系 —— dt_ms 记的是实测间隔，回放按真实 dt_ms 推进，抖动天然被保留（这正是记实测 dt_ms 而不是假定等间隔的价值）。抓不到的记 warnings.jsonl；回放端对拿不到 files 的 hash 返回空列表 —— 与 auto-qb 行为一致（_assign_to_group 在 file_map 为空时直接 return ⇒ 不归组），不是错误路径。
真机负载 10 000 次请求打在正在做种的 qB 上不是零成本。三道闸：--qps 限速（默认 20，可按真机反应调低）、--sample N 只抓前 N 个种子（先小规模验通路）、--dry 只打印将要发的请求数与预估耗时不发请求。建议第一次跑用 --sample 200。

05脱敏与等价类守恒

严格档（唯一档位，不提供"原始"输出）：字段白名单 + 形态守恒的确定性伪名化。

为什么必须"形态守恒"

如果把种子名统一换成 torrent-0001 这样的短 ASCII 名，语料就丢掉了真机最容易出问题的那部分：长路径（>260 字符）、中文与全角字符、多层目录、扩展名多样。脱敏要去掉的是"这是哪一部资源"，不是"这个字符串有多难对付"。

形态守恒的确定性替换（shape-preserving pseudonymization）

  • 对每个字符按类别替换：CJK → CJK、拉丁字母 → 拉丁字母、数字 → 数字、标点/空格 → 同类。长度与层级结构 1:1 不变，目录分隔符原样保留。
  • 替换值由 HMAC-SHA256(salt, 原文上下文) 的字节流驱动，同一输入永远同一输出（跨种子、跨字段一致 ⇒ 同组共享路径仍然共享）。
  • 单射性是硬约束：维护全局字典，出现碰撞（两个不同原文映射到同一伪名）立即中止并报错，不允许"加序号后缀"这类会破坏等长性的兜底。
  • 盐：32 字节随机，只把前 8 位指纹写进 meta.json，盐本身不落盘 ⇒ 两份语料之间无法关联。

等价类边界：path_normalize 只统一分隔符 v2 修订

归组 key 是 (path_normalize(save_path), tuple(sorted(file_map.keys())))（grouping.py:150）。实测 utils.path_normalize 的实现是"仅把 \ 换成 / 并压缩重复斜杠" —— 不做大小写归一，且刻意保留首尾斜杠（注释写明是为了区分 c:/windows/ 与 c:/windowsg）。这三条推论必须写进脱敏实现：

  • save_path 的重映射自身也必须单射，原文只对"伪名字典"要求零碰撞是不够的。qB 单实例可有多个盘上的种子，若 R:\Download\TV 与 S:\Download\TV 都映射成 <run>/fs/Download/TV，两个不同的组会被合并 ⇒ 回放分组与真机不同。
    修法：重映射路径带"原盘符的短令牌"（如 <run>/fs/d0/…），并把 save_path 映射一并纳入单射校验。
  • 尾斜杠的有无必须 1:1 保留 —— 不能顺手 rstrip('/')。
  • 大小写形态必须 1:1 保留 —— path_normalize 不做 casefold，所以形态守恒替换不能把字母统一转小写（否则原本不同的两个 key 可能被合并）。
  • hash · infohash_v1/v2 → 40 hex 这条对 v2 是错的：v1 是 40 hex、v2 是 64 hex，形状要分别保持；magnet_uri 同步重写。

增量流必须过同一套映射

  • 流与快照共用同一份映射字典、同一把盐，字典在录制过程中只增不减（新原文追加映射，已有的一律复用）⇒ 同一个 hash 在 T0、流、T1 里始终是同一个假值。
  • 流里首次出现的新原文（新种子名、新 tracker 域名）即时纳入字典；若触发碰撞，同样中止录制 —— 中途换盐会让前后半段的映射对不上，比不录更糟。
  • 数值一律不动：流里的 size / 速度 / 累计流量 / 时间 / 限速原样透传，与快照口径一致。
  • 落盘前做一次流级自检：流中出现的每个 hash 都能在 files.json / trackers.json 里找到（新种子必须已当场 append，见第 04 节）；每个 tracker 域名都在站点映射表内。有漏即 FAIL。

头号验收：等价类守恒校验

Sanitize must preserve the partition

校验在第 04 节第 5 步做两次：脱敏前用真机数据在内存里算一次分组（不落盘，含真实种子名，比完即弃），脱敏后再算一次并落盘 groups.json。二者必须逐组逐成员一致（成员数、每组 hash 集合按映射后逐一对应）。不一致即中止抓取、不落盘 —— 与其留一份"看起来是真的"的错语料，不如没有。

回放端状态模型：流状态 vs 实况状态 —— 一并消化 issue 2145 v3 拍板

要消化的缺陷 memory-bank/issues/26-09-20-2145-test-sim-qb-maindata-snapshot-lag.html：sim_qb 缺「/sync/maindata 快照滞后」模型 —— 仿真端状态瞬时翻转，本地无法复现/验证「真值直查」的收益，掩盖一切"真值尚未落地"类缺陷。issue 提议"加 1.5 s 快照滞后模型"。

语料回放天然给了一半，但不够。流里的帧是真机响应，本身带着真机的快照节奏 —— 可回放期的写命令（auto-qb 发的 pause / tag / limit）不在录制流里（录制时没人发这些命令）。所以必须由回放端把命令效果叠加进去，而"叠在哪一层"正是滞后的来源。

定案：两层状态

层组成谁读它
流状态
snapshot view		录制流累积到当前 t_seq 的结果（原样，不改）sync/maindata（滞后地带上 overlay）

  • overlay 在命令被消费的那一刻立即进入实况状态；
  • sync/maindata 只在下一次快照刷新点才带上 overlay ⇒ 滞后 --maindata-lag-ms（默认 1500，取自 issue 的观测值）；
  • 于是「torrents/info 比 sync/maindata 新」这条真机语义可在本地复现 ⇒ 真值直查的收益可验证 ⇒ issue 2145 消化。

两条必须写明的口径

  • 滞后值是模型假设，不是实测。默认 1500 ms 来自 issue 里的观测，必须由 W0 校准：用户在自己 qB 的 WebUI 上做一次可逆操作（如暂停→恢复一个种子），同时跑抓取器，量 maindata 的反映延迟。校准不出就显式标注"假设值"，不许当成真机事实。
  • overlay 只影响"auto-qb 自己发的命令"，不回写语料。语料保持"整帧原样存"的原则不变 —— overlay 是回放期的内存态。冲突规则：overlay 与流里同一字段冲突时以 overlay 为准（真机上命令效果也会覆盖快照）；流里出现该 hash 的 torrents_removed 则清掉它的 overlay。
⚠ 与「窗口合并」的先后顺序 窗口内多帧先合并成"这一拍的状态"（见 §08），再把 overlay 按滞后规则叠上去。顺序反了会让滞后的边界落在错误的 t_seq 上 —— 实现时把这两步写成两个独立函数，别揉在一起。

08高精度时间轴录制 · 周期全量对齐

快照回答"长什么样"，录播回答"怎么变"。性能分析还要第三个答案：变化发生在哪个时刻，以及"客户端靠增量累计建起来的视图"到底跟真机对没对上。所以录播不是"按 tick 采样"，而是可配置间隔的高频采样 + 周期性全量校验 —— 这两条都是为了不再依赖 --latency-ms 那种常数近似。

采样间隔：可设置，性能分析档默认 100 ms

  • --interval-ms（默认 100）/ --interval（秒，等价写法）：两次 sync/maindata 之间的间隔。与 auto-qb 的 main_tick 无关 —— 录制端采的是 qB 侧的真实变化，客户端多久来拉一次是另一回事。
  • 100 ms 的意义：auto-qb 每 2 s 拉一次，拿到的是"这 2 s 内的累积变化"。用 2 s 采样只能得到"每 2 s 变了多少"，用 100 ms 采样则能还原出变化在这 2 s 内部怎么分布 —— 是持续小抖，还是某一瞬间的批量刷新（tracker 刷新、校验完成、一批种子同时转态）。合成数据给不出这个分布，--latency-ms 更给不出。
  • 两档预设：--profile=perf（100 ms，性能分析专用）/ --profile=normal（2000 ms，对齐 main_tick，日常回归）。
  • 代价：10 次/秒 × 20 分钟 = 12 000 次请求。增量请求本身约 3 ms，但高频轮询会持续占用 qB 的 sync controller —— 对真机做种的影响必须实测（已列入 W0）。

全量对齐：只留首与尾，中间的抓而不存

语料里只保留两份全量，而且都在流里 —— 首帧（T0）与末帧（T1）。中间那些周期性全量仍然要抓 —— 它们的用途是定位漂移发生在哪个时间窗，比对完即弃，不落盘。既然增量流是完整的，中间任意时刻的全量都能由 T0 ⊕ 增量流 重建出来，没有保存价值。

  • T0 就是流的第 0 帧：录播复用快照时的同一个 sync session 与 rid 继续递增 ⇒ 那次全量响应（full_update=true）本身就是 T0，其后各帧是紧接的增量，零缝隙。语料里不另存 torrents.json / server_state.json / tags.json / categories.json —— 种子与全局状态只有一个来源：流。
  • T1 就是流的末帧：正常录完时（全程检查点对齐）用第二 session（rid=0）抓一次全量，原样追加为流的最后一帧（标记 role:"closure"）⇒ 语料里不再有独立的 T1 文件。它格式上与"流中自然出现的 full_update=true 帧"完全一致，零转换。回放端读到它就结束回放并做闭合比对，不吐给客户端（否则客户端会按全量轮重置一次 —— 语义正确但没必要）。若第二 session 会重置共享 rid 序列，全量基准改用 torrents/info（需声明已知字段差异白名单）。
  • 首尾闭合校验（最强判据）：流首帧 ⊕ 中间全部增量帧 == 流末帧 逐字段比对（全程都在流内，没有外部文件参与）。中间检查点回答"对不对"，首尾闭合回答"整条流有没有丢帧 / 有没有累积漂移" —— 两者互补，都要有。
  • 未对齐即停止录制 —— 不留中间态：任一检查点比对未通过 ⇒ 立即停止采样，并把这份全量当场入盘。检查点本来就是抓一份全量来比对的，未通过时它已经在手里 —— 就地追加进流（role="mismatch"，附差异摘要），然后停止。不补抓 T1（闭合只对完整录完的语料有意义），也不另开目录 —— 它和 T1 是同一种帧，零转换。
    于是末帧永远是一份全量：正常收尾是 T1，异常收尾是出问题的那个检查点 —— 形态整齐，DEBUG 时直接看最后一帧就是现场。
    产物落盘但 meta.status="aborted"、meta.abort_at={t_seq, 差异摘要}，不写 groups.json（真值分组已不可信，绝不能被拿去当判据答案），退出码非 0。没有"带病继续录"这回事 —— 一段自己都说不清对不对的流，比没有流更危险。
  • 免费的全量：流里若出现自带 full_update=true 的帧（qB 主动要求重新全量同步，如 qB 重启 / 内部重置），它本身就是一份完整全量 —— 直接拿来当检查点，省掉一次额外请求。可做成"优先吃免费帧，超过 --full-every 没出现才主动抓"。
  • 比对维度：hash 集合差（missing_in_stream / extra_in_stream）、逐字段值差（按字段计数 + 前 N 条样本）、总对齐率 alignment_rate。结果不另开文件 —— 通过就只在 meta.json 累加一行统计（共 N 次 / 失败 K 次）；不通过则立即停止录制，差异摘要写进 meta.abort_at（见上一条）。
  • 这一步不只产出"语料质量报告"：auto-qb 与录制端用的是同一套"增量累计建全量"的逻辑。若增量语义里有坑（某些字段只在 full_update 里给、删除事件漏报、值被服务端覆盖），这里会先红 —— 等于提前探测 auto-qb 快照漂移这类缺陷。

  • 录制时记下每次请求的真实往返 rtt_ms（含 qB 自身处理时间）。回放时按 --latency-mode=recorded|p50|p95|const:N 注入 —— 比拍一个常数准确得多，尤其能还原"全量轮 205 ms / 增量轮 3.3 ms"这种随载荷变化的延迟曲线。
  • --latency-ms 降级为 const:N 的一种写法，只在合成档或无 RTT 录制时使用。
  • 诚实边界：这仍补不上"本地回环 vs 真机网络"的传输层差异。高频采样 + RTT 录制解决的是数据面对齐（变化的内容与节奏），这也正是性能分析里真正会误导结论的部分；传输层差异应在结论里显式标注，而不是假装不存在。
已知局限 录 20 分钟只覆盖 20 分钟里的真实变化；qB 的 tracker 周期刷新（30 min 级）大概率录不到 —— 长时间录制是时间成本，不是设计缺陷。100 ms 采样属于侵入式观测，录制期间不要同时做别的性能比对。建议第一次用 --profile=normal --minutes 10 验链路，确认有用再上 100 ms 档。
