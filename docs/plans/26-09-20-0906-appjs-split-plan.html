01可行性: 体积问题是真的, 耦合问题不是

先看这份文件的实际构成 —— 它不是一个"什么都粘在一起"的大泥球, 而是一个组件实例上平铺的几百个成员:

区段行数内容

方法之间只通过 this 互调, 没有模块级的私有状态纠缠 —— 这意味着换个文件放, 语义完全不变。真正的痛点是可读性: 找"删除流程"要在 5000 行里翻, 且任何一处改动都落在一个巨型 diff 里。

机制: 照抄仓库里已有的范式, 不引构建链

仓库里已经有跨文件拆分的前端范式 —— config_editor.js 与 config_rules.js 就是挂在 window 上的全局 mixin, 由 app.js 末尾 app.mixin(...) 注入。照抄即可:

window.AQB_COMMANDS = {          // shared/commands.js
  methods: { act() { ... }, ... },
  computed: { pendingAny() { ... }, ... },
};

// shared/app.js 末尾
app.mixin(window.AQB_COMMANDS);
app.mount("#app");

三条理由不选 ES Modules: ①需把两个 HTML 改成 type="module"; ②config_editor.js 仍是全局范式, 会两套机制并存; ③window 全局 mixin 的加载顺序语义与现状完全一致。Vue 的 mixin 合并后, 所有成员仍在同一个实例上 —— 两套模板(prism / atlas)里 v-on / 插值引用的方法名一个都不用改。

真正的风险不在拆分, 在"静默失效"

拆成多文件后会出现两类 pytest 全绿、界面局部废掉 的故障, 且控制台一条报错都没有:

① 漏挂 / 漏注入 —— 文件写了但没加 <script>, 或没写 app.mixin(), 那一整块功能凭空消失。
② 跨片段重名 —— 两个文件里出现同名成员, Vue 的合并是后者覆盖前者, 被盖掉的实现从此永不执行。

所以拆分不能单独落地, 必须与新增守阵同批提交(见 §04)。

两条必须记住的约束

  • 片段必须在 HTML 里排在 app.js 之前 —— app.js 末尾要读 window.AQB_*。
  • 列模型常量不许再搬 —— TABLE_COLUMNS / MIN_COL_PX / STATE_RANK / ROW_WIN_* 仍单点在 app.js 顶部, 片段按裸名引用(顶层 const 落在全局词法环境, 方法体运行时才求值)。搬一次就是上百处改名。

03执行方式: 机械切分, 两波验证

5000 行手改必然出错。改用一次性脚本按行区间搬运: 逐块原文拷贝, 不重新缩进、不改一行代码, 并自带三道断言 —— 成员区间首尾相接无空洞 / 每个成员有且仅有一个归属 / 搬运前后行数守恒(3722 行)。
另一个细节: 成员尾部的注释描述的是下一个成员, 脚本会在切分前把它挪到下一个成员头上, 避免注释跟着上一个文件走丢。

04守阵改动: 这是本次的真正交付之一

拆完第一次跑守阵就红了, 报的是 "app.js 找不到 _optimisticSettled 的调用点" —— 但功能没坏, 它只是随 act() 一起搬进了 commands.js。守阵本身需要跟着拆分改:

  • 第 7 / 8 / 9 项改为按"整包"扫描 —— 集成员取 hash、STATE_RANK 与后端对齐、乐观 UI 撤下三处顺序, 这三条不变量的代码现在可能分处两个文件。改成按 prism/index.html 的 <script> 加载顺序拼接 app.js + 15 个片段后扫描(顺序取自 HTML 而非文件名排序, 加片段时自动跟着走)。
  • 新增第 10 项「拆分接线」 —— ①shared/ 下每个非 vendor 的 js 必须被 HTML 引用; ②每个 window.X 必须在 app.js 里被 app.mixin()(ce-field 走 app.component, 已计入); ③跨文件 methods / computed 成员不得重名。

红验(故意注入两种缺陷, 均被精确报出):

删掉 app.mixin(window.AQB_HR);
  → shared/hr.js 定义了 window.AQB_HR 但 app.js 没有 app.mixin(片段漏注入)
