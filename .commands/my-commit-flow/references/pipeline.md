## 同步（sync.py）：判据与行为

- **判落后只用 ls-remote 现查的远端真值对比本地 HEAD** —— refs/remotes/* 的写入在本环境会被静默丢弃，
  `status -sb` 的 ahead/behind 是快照（单点: `memory-bank/pitfalls/git/refs.md`）。fetch 只为把对象拉进对象库。
- 行为表（D1 已拍板 2026-09-28：必要时用 rebase 保持提交历史线性）：

| 状态 | 动作 | 输出 |
|---|---|---|
| 齐平 / 本地领先(未推送) | 无 | `已同步 <hash>` |
| 纯落后 | `merge --ff-only <远端tip>`；**树脏交 git 裁决**（无重叠自然成功，重叠被 git 拒绝） | `同步成功 <hash>` / 失败行 |
| 分叉 + 树净 | `rebase <远端tip>`：只改写按定义未推送的独有提交，历史线性；冲突 → `--abort` 全量回滚 | `同步成功 <新hash>` / `同步失败需解决冲突 本地<x> 远端<y> …` |
| 分叉 + 树脏 | 不动 | 失败行（先提交或 stash） |

- v2 的「移出 → 快进 → 施回」配方与「已分叉替代路径」（reset --hard + format-patch 舞蹈）**已删除**：
  stash / rebase 解禁（2026-09-25）后，前者被「落后+脏 → 先提交或 stash 后重跑」取代，后者被自动 rebase 取代。
- **失败自动回滚现场**：rebase --abort / git 自回滚 —— sync 失败后仓库状态与跑之前一致。
- **staged 暴增**（staged_panic，默认 200）= 分支 ref 被别的会话回退的信号 → 拒绝继续，别用 add -A "解决"。
- sync 是幂等的：重复跑第二次必然「已同步」。

## ship.commit 编排（检查一个不删，只是不再逐项汇报）

```
内部同步(run_sync) → 闸门(run_gates) → 暂存计划(红线拦) → 逐路径 add
→ commit -F 消息文件 → ref 三处核对 → 消息文件消费即删 → 内联推送(run_push) → 提交成功 <hash>
```

- **闸门在暂存前**：fmt 类闸门会改文件，必须先跑再 add；改动清单以同步后的磁盘为准重算。
  闸门全过**静默**（v2 的「N 条全过」行、「无匹配文件跳过」WARN 都已废——无匹配是 `<each:>/<changed:>`
  的设计行为）；失败给**闸门名 + 失败输出末 20 行**。展开失败（占位符拼错）= 失败，不降级。
- **闸门只跑一次**：v2 在 commit / push 两阶段各跑一遍预检（WARN 成对出现的根源）；v3 push 内联时只做同步核对。
- **逐路径 add 的分流**（修 issue 26-09-28-0128）：工作区存在 → `git add -- <path>`；
  不存在但索引里有 → `git rm --cached -- <path>`；都不在（已暂存的删除）→ 无事可做。
- **消息文件** `<root>/.git/COMMIT_MSG_AI.txt` **消费即删**：提交落稳（ref 通过）后自动删除——
  文件存在 = 有待提交的消息；commit / ref 核对失败时**保留**（修好重跑还能用同一份）。
- **先同步后提交**：commit 内部第一步就是 run_sync —— 收尾回写件（baseline / 切片 / 各 _index）必须落在
  合并后的新基线上（2026-09-26 定稿，治「baseline 总是撞」）；v3 把"记得先同步"变成机器保证。
- 红线 / warn_lines / 批量 add 拒绝 / staged 暴增：全部保留，失败行化。

## 推送（push.py）

顺序固定：同步核对 → 推主线（`Recv failure` / `Connection was reset` 自动重试**一次**）→
ls-remote 核对远端 == 本地 → 镜像一次（**全程静默**，D2 2026-09-28 定调：允许滞后，成败都不提；
不重试 / 不换代理 / 不改走 SSH / 不回滚主线已完成的推送）。
取不到远端 ref ≠ 推送失败：如实说「无法核实」+ 给手工核对命令，别把网络抖动报成不一致。
