## v3.1 步骤行：改写留痕（2026-10-06）

v3 的结果行回答**"结果好不好"**，但一次命令内部 HEAD 会被改写多次 —— `ship.commit` 里最多三次
（提交自身 → 内部同步的 rebase → 闸门复跑改文件后 amend），`ship.push` 内还有一次同步。结果行只给终值，
前几段就成了黑箱：执行者看到 hash 与印象不符（rebase 前后必然不同）就回头查原因。这一行忧虑比噪音贵。

**补法**：结果行**逐字不动**；步骤行按发生顺序打在它**上面**，改写 HEAD 的必带 `旧hash→新hash`。
v3 的其余部分（模板 / 退出码 / 沉默即成功）一字未改。

登记纪律三条（单点在 `_pipeline.py`「步骤登记」段）：

1. **改写 HEAD 的步骤必须登记**，且带 `旧hash→新hash` —— 相邻两步首尾同值 ⇒ 任何 hash 变化都可回溯；
2. **没发生的步骤一律不登记** —— 齐平 / 本地领先（未推送）/ 闸门复跑无改动 全部静默；
   「跑了但什么都没做」本身就是噪音，登记它会退回 v2 的检查表。
3. **登记与打印分离** —— 动作内部只 `step()` 登记（按发生顺序），入口在结果行之前 `emit_steps()`
   一次吐干净。`commit.py` 的所有结果行只从 `emit()` 出，绕开它那个 hash 变化就没人解释。

| 任务 | 可能出现的步骤行 |
|---|---|
| `my-commit-flow.sync` | `同步: 远端领先 N 笔 → 快进 <旧>→<新>[ · 本地未提交改动原样保留]`<br>`同步: 远端领先 N 笔 · 重叠 N 处全在生成物 → 丢弃本地那份后快进 <旧>→<新>`<br>`同步: 远端领先 N 笔 · 本地领先 N 笔(分叉) → rebase 重放本地 N 笔 <旧>→<新>`<br>`同步: 生成物自动重跑后 amend <旧>→<新>` |
| `ship.commit` | 上列同步各类 ＋ `闸门复跑: 合流后闸门改了 N 个文件 → amend <旧>→<新>`<br>`快照: 上游改动了本包 → 本次仍按启动版本运行, 重跑以采用新版本`（非改写类：不动 HEAD，只提示重跑） |
| `ship.push` | 上列同步各类（本任务自己不产生步骤，只有内部 `run_sync` 那份） |

一次分叉提交的实际输出（步骤行在上，结果行压尾）：

```text
同步: 远端领先 1 笔 · 本地领先 1 笔(分叉) → rebase 重放本地 1 笔 aa11bb22→bb33cc44
闸门复跑: 合流后闸门改了 2 个文件 → amend bb33cc44→cc44dd55
提交成功 cc44dd55
```

- **结果行才是要贴进回复 / 档案的那个值**；步骤行是给读输出的人解释「中途 tip 到过哪」的证据。
- **顺序即发生顺序，两行首尾相接**：一次同步里可能连改两次（先 rebase 重放、再收尾重跑导致 amend），
  这两行必须按发生顺序排 —— 排反了箭头链就是倒的，等于把疑惑换了个位置。所以 `_resolve_rebase`
  只**返回事实**（`ok / 重跑处数 / landed / amended`），两行由唯一知道全局顺序的 `run_sync` 登记
  （守卫 `test_rebase_then_amend_steps_are_in_order`）。
- 失败时步骤行照旧吐在失败行**上面** —— 失败虽已自动回滚（结果行的 hash 是回滚后的 HEAD），
  把期间到过哪摆出来，才不让人怀疑回滚漏了东西。
- ⚠ **`steps` 是显式参数，不是模块级全局缓冲**：`run_sync(steps)` / `run_push(steps)` /
  `emit(steps, line)` 逐层透传，传 `None` = 不要痕迹。全局缓冲会让跨测试的残留互相污染。

## 快照自举：一次调用 = 一个版本（2026-10-07）

本包脚本与配置**住在被它自己操作的仓库里**（`<仓库根>/.commands/my-commit-flow/`），而流水线的内部同步
（`run_sync`）会把远端新版包脚本 / 配置 rebase 进工作区 —— 于是同一次调用里"提交前"与"提交后"跑的
**可能不是同一版代码 / 同一份规则**。这是**自指**缺陷：此前靠"在选定几个点上重取配置 / 热刷新模块"打补丁，
覆盖不全（入口脚本自身无法热刷新、`importlib.reload` 不重绑调用方已导入的名字、配置重取只覆盖两个点）。

**治本 = 快照语义**：入口脚本（`commit.py` / `sync.py` / `push.py` / `verify_ref.py`）启动时把**整包**复制到
**仓库之外**的临时目录，从副本重入（`scripts/_snapshot.py`）。副本不受 `git rebase` 影响 ⇒
**一次调用 = 一个版本**；中途的自我改写对本进程不可见，**新版本从下一次调用生效**。与"引擎不能中途换零件"同构。

| 环境变量（由 `_snapshot` 注入） | 值 | 作用 |
|---|---|---|
| `COMMAND_FLOW_SNAPSHOT` | `1` | 标记"已在快照里" —— 防无限重入 |
| `COMMAND_FLOW_PACK_DIR` | `<副本>` | 覆盖引擎注入的原包路径 ⇒ 配置 / 模块一律从副本读 |
| `COMMAND_FLOW_REPO_ROOT` | `<真根>` | 副本在仓库外、向上找不到 `.git`，`_ship_config.find_root()` 认它 |
| `COMMAND_FLOW_ORIGINAL_PACK` | `<原包>` | 诊断 / 排障（报错里的 `__file__` 是副本路径） |
| `COMMAND_FLOW_SNAPSHOT_KEEP` | `1` | 保留临时副本（排障 / 测试） |

- **纯信息入口不复制**：`--help` / `-h` / `--safety` / `--show-config` / `--init` 直接作用**原包** ——
  尤其 `--init` 要把配置写进真包，不能写进临时副本。
- **守卫在 `__main__` 下**（3 行）：`import` 不触发重入 ⇒ 测试 / 复用方不受影响。
- **重入用 `subprocess.call`**（非 `os.execv`）：Windows 上 exec 语义不可靠（不真正替换进程 / stdio 继承有坑）；
  多一层进程换稳定，代价可忽略。
- **开销**：整包 16 文件复制 avg ~26ms，加一次 Python 启动，单次调用约百毫秒级。
- **临时目录不泄漏**：正常路径子进程退出即删（`finally`）；崩溃 / 强杀靠启动时清扫 >1 天的旧快照。
- **闸门（外部工具）仍跟仓库走是对的**：闸门要测**被测的树**，每次都是新进程、内部一致；必须固定的只有流水线自身。

**取舍**：放弃"复跑用新规则"（那正是撕裂的来源，且永远补不全）。改为 —— rebase 后若发现**上游改动了本包**，
登记一行 `快照: 上游改动了本包 → 本次仍按启动版本运行, 重跑以采用新版本`（不静默；判据 =
`git diff --name-only <旧> HEAD -- <本包路径>`）。据此，`refresh_package_modules` / `reload_config` /
`sync._reload_cfg` 三条治标机制及其接线已**退役**（快照语义下它们不再有意义 —— 本进程跑的是副本，
本来就看不见自我改写）。完整可行性分析（含原型 10/10 实测与方案空间对比）见
`memory-bank/reports/26-10-07-0208-report-my-commit-flow-self-snapshot.html`；守阵 `scripts/test_snapshot.py`。

- **判落后只用 ls-remote 现查的远端真值对比本地 HEAD** —— refs/remotes/* 的写入在本环境会被静默丢弃，
  `status -sb` 的 ahead/behind 是快照（单点: `memory-bank/pitfalls/git/refs.md`）。fetch 只为把对象拉进对象库。
- 行为表（D1 已拍板 2026-09-28：必要时用 rebase 保持提交历史线性）：

| 状态 | 动作 | 输出 |
|---|---|---|
| 齐平 / 本地领先(未推送) | 无 | `已同步 <hash>` |
| 纯落后 | `merge --ff-only <远端tip>`；**树脏交 git 裁决**（无重叠自然成功，重叠被 git 拒绝） | `同步成功 <hash>` / `树脏挡路 …` 失败行（自带两条出路） |

| 分叉 + 树脏 | 不动 | `树脏挡路 …` 失败行（自带两条出路） |

### 生成物冲突自动化解（2026-10-03，计划 26-10-03-1544，默认开）

多 clone 并行下，两个会话收尾都会重跑索引生成器，同一批 `_index.md` 在两边各自产生新版本 ——
后同步的一方必然撞车。此前 `run_sync()` 见冲突就停，执行者被叫去手工合流（`pitfalls/git/sync-pull.md`
的「提交点撞远端前移」条目复发 7 次）。现在把「重跑即可收敛」这件事接进脚本：

- **三步不变量**：白名单（`generated_list_cmd` 的 `--list`）→ 任取一侧 + 重跑（`generated_regen_cmd`）
  → `--check` 自证。**不做文本合并、不做行级并集**。
- **敢默认开的理由**：生成器是纯函数（内容只由工作树里的手写文件决定），重跑后 `--check` 通过 =
  磁盘内容确实等于生成结果 ⇒ 证明没有手写内容被丢弃。
- **白名单唯一权威来源**是生成器自己的 `--list`（集合单点 = memory-bank skill 的 `scripts/gen_all.py`），
  sync 里不另抄一份清单 —— 列错会**静默丢内容**（多一个其实不是生成物的路径），所以这条单点是硬约束。
- **白名单 / 重跑命令取自本进程启动时那份配置**（2026-10-07 快照语义）：这一步的头一件事就是把树推到
  上游 tip，中途 rebase 可能把上游新版 `.my-commit-flow.toml` 写进工作区 —— 但**不换规则**：本进程
  跑的是仓库之外的副本，一次调用只认一个版本（换规则正是"同一次调用混两个版本"的来源）。
  判据（生成器是纯函数、重跑后自证通过 ⇒ 没丢手写内容）与配置来源无关，不因不重取而失效。
- **触发面**（只这两类；S3「分叉 + 树脏」仍直接拒，见计划 §09）：
  - 落后 + 本地脏与远端改动重叠（快进被拒）：重叠 ⊆ 白名单 → 逐路径丢弃本地那份 + 重试快进 + 重跑。
  - 分叉 + rebase 冲突：冲突 ⊆ 白名单 → 取一侧 + 重跑 + `--continue`（有界循环，上限 = 本地独有提交数 + 1）；
    收尾再自证一次，仍漂移则 `commit --amend --no-edit` 折进 tip（rebase 后的 tip 是未推送的本地提交，amend 安全）。
- **保守默认**：白名单取不到 / 重跑 rc≠0 / `--check` 红 / 循环超限 / 路径解析异常 —— 一律退回**现状失败行**，
  且仓库状态与跑之前一致（S1 走「快照 + 回滚」，S2 走 `rebase --abort` / `reset --hard`）。绝不「部分解决后硬上」。
- **输出**：化解成功仍是结果行 `同步成功 <hash> 自动重跑生成物 N 处`，常规成功行与失败行模板**逐字不变**；
  v3.1 起额外在该行**上面**登记一步改写留痕（`丢弃本地那份后快进 <旧>→<新>`，收尾若 amend 再补一行）。
- 开关与两条命令：`auto_resolve_generated` / `generated_list_cmd` / `generated_regen_cmd`（写在本包
  `.my-commit-flow.toml`；三键必须同时在 `_ship_config.KEY_DEFAULTS`，否则按「顶层未知键」STOP）。

- **树脏失败行自带两条出路**（2026-10-03 定配方；2026-10-04 更新）：① 不提交先同步 → `git stash push -u → sync → git stash pop → 测试 → ship.commit`
  （`-u` 必带：收尾产物常是未跟踪新文件，默认 stash 不收，快进仍会被它们挡住）；② 提交先行 → `commands run ship.commit`
  （先提交后同步，树净 rebase 恒可自动，与远端的冲突改在 rebase 时暴露）。只写「先提交或移出后重跑」会让执行者
  原地打转 —— 单独重跑 sync 树还是脏的；旧「先提交是死锁」的论断随 ship.commit 顺序翻转作废（2026-10-04）。
- v2 的「移出 → 快进 → 施回」配方与「已分叉替代路径」（reset --hard + format-patch 舞蹈）**已删除**：
  stash / rebase 解禁（2026-09-25）后，前者被上面的 stash 解锁配方取代，后者被自动 rebase 取代。
- **失败自动回滚现场**：rebase --abort / git 自回滚 —— sync 失败后仓库状态与跑之前一致。
- **staged 暴增**（staged_panic，默认 200）= 分支 ref 被别的会话回退的信号 → 拒绝继续，别用 add -A "解决"。
- sync 是幂等的：重复跑第二次必然「已同步」。

## ship.commit 编排（检查一个不删，只是不再逐项汇报）

**提交先行（2026-10-04 起，取代 2026-09-26 的「先同步后提交」）**：

```
闸门(run_gates) → 暂存计划(红线拦) → 逐路径 add → commit -F 消息文件 → ref 三处核对
→ 消息文件消费即删 → 内部同步(run_sync) → [rebase 真合入远端 → 闸门复跑 + amend] → 内联推送(run_push)
```

- **为什么翻转**：旧序「同步 → 闸门 → 提交」里同步发生在**树脏**时 —— 分叉 + 树脏 = rebase 拒绝 =
  stash 解锁舞蹈（`pitfalls/git/sync-pull.md` 的双向死锁家族，复发 12 次）。提交先行后树必然干净，
  分叉 rebase 恒可自动：同步失败只剩冲突与断网两类，一律自动回滚后按「推送未完成」停下要人
  （提交已落稳，别重新提交；退出码仍 0）。独立 sync 的树脏场景仍走上面两条出路。
- **回写件合流交脚本**（取代「回写必须落在合并后的新基线上」的手工纪律）：回写件直接写在本地基线上，
  与远端的合流由提交后的 rebase 完成 —— 各 `_index` 的两边撞车由生成物自动化解兜底（冲突 ⊆ 白名单 →
  取一侧 + 重跑生成器 + 自证，重跑发生在含两边新切片的树上，结果天然是并集）；手写件重叠才需要人 ——
  在 rebase 冲突里合流，不再走 stash 舞蹈。
- **闸门跑两轮的时机**：第一轮在提交前（按本地改动清单；fmt 类闸门会改文件，必须先跑再 add）；
  rebase 真合入了远端提交（HEAD 改写）→ 按**同一份清单复跑一轮** —— 合并后的树才算数（检查项一个不删；
  代价只在分叉时多付一轮）。复跑后 fmt 又改了文件 → 逐路径 add + `commit --amend --no-edit` 折进
  未推送的 tip（与 sync.py 生成物收尾同款；rebase 后 tip 未推送，amend 安全）。复跑红 → 推送未完成 +
  「修复后重跑 ship.commit（修复作为新提交入库）」。齐平（远端没动）时同步是 no-op，HEAD 不改写 → 不复跑。
- **复跑用启动版本那份规则**（2026-10-07 快照语义）：rebase 可能把远端新版 `.my-commit-flow.toml` 换进
  工作区，但本进程跑的是仓库之外的副本，**不重取配置**（重取正是撕裂的来源）。复跑只重验"合并后的树"，
  改动清单仍是本次提交的那批。合流若改动了本包 → 登记一行 `快照: 上游改动了本包 → … 重跑以采用新版本`
  （见「快照自举」节）。判据与守阵见 `memory-bank/pitfalls/git/self-rewrite-config.md`。
- **`--no-push` 不同步**：纯本地提交（离线可用），合流留给补推时的 `ship.push`（其内部 run_sync 树净同理）。
- **ref 核对在同步前（#1，快失败）**：提交的 ref 写入若被环境静默丢弃，同步会拿旧 HEAD 当真值 —— 必须先拦下；
  amend 又是一次 ref 写入，之后复核。推送侧真值仍由 run_push 的 ls-remote 兜底。
- **推送步不再需要"刷新本包模块"**（2026-10-07）：旧修法（`refresh_package_modules`）是为"延迟 import 的
  新脚本撞上进程缓存的旧依赖"补的；快照语义下本进程跑的是副本，中途 rebase 换不掉它，那一类 ImportError
  从根上不会发生（见「快照自举」节）。
- **逐路径 add 的分流**（修 issue 26-09-28-0128）：工作区存在 → `git add -- <path>`；
  不存在但索引里有 → `git rm --cached -- <path>`；都不在（已暂存的删除）→ 无事可做。
- **消息文件** `<root>/.git/COMMIT_MSG_AI.txt` **消费即删**：ref 核对通过即删（提交落稳的单点判据）——
  文件存在 = 有待提交的消息；commit 失败、或 ref 核对失败**且** HEAD 消息与文件不匹配（ref 真丢）时
  **保留**（修好重跑还能用同一份）。核对失败但 HEAD 消息与文件一致 = 提交已落稳（packed-refs 滞后类
  误报，2026-10-07 实证）→ 照常消费。入口另有一道**残留扫描**：约定文件内容 == HEAD 消息即删并拒跑
  （拦旧消息被复用 + 任何路径漏删的残骸在下一次 ship.commit 自愈；树净也拦得到，故在暂存计划之前）。
- 红线 / warn_lines / 批量 add 拒绝 / staged 暴增：全部保留，失败行化。

## 网络容错：单次超时 + 有界重试（2026-10-06）

Gitee 会**间歇性卡住**（不报错，就是不返回）。旧行为是单次超时 120s，等满才失败一次 ⇒ 提交被拆成
「提交成功(未推送) + 手工补推」两步，且是常态。现在：

- **单次超时 20s**（`GIT_TIMEOUT`；环境变量 `COMMAND_FLOW_GIT_TIMEOUT` 可覆盖）；
- **有界重试**：默认 3 次尝试（`COMMAND_FLOW_GIT_ATTEMPTS`），**全部失败才判失败**；重试间隔 1s
  （`COMMAND_FLOW_GIT_RETRY_BACKOFF`）；
- 重试层在 `_pipeline.run_git`，而 `git()` / `git_rc()` / `git_run()` **一律经它** ⇒ 所有 git 命令
  （push / pull / fetch / ls-remote / 本地查询 …）都带超时，网络子命令都带重试；
- 重试成功**完全静默**（v3 契约不变）；失败行在原因后缀 `(已重试 N 次)`，免得读的人以为命令没试过。

重试判据分三档（单点 `_pipeline._retryable`）—— **不是**「任何非 0 都重试」：

| 档 | 范围 | 判据 | 为什么 |
|---|---|---|---|
| ① 失败即重试 | 网络子命令 `push` / `fetch` / `pull` / `ls-remote` / `clone` / `remote` | 任何非 0 | 失败签名靠不住（网关 502 / 代理重置 / TLS 抖动），白名单必漏；且它们**幂等** ⇒ 重试永远安全，还能顺手救回「推成功但被判失败」 |
| ② 只给超时，不给重试 | 非幂等本地写 `commit` / `rebase` / `merge` / `reset` / `checkout` / `rm` … | — | 超时被杀 ≠ 没执行完：再跑一次轻则把 `nothing to commit` 当成失败，重则 amend 又挪一次 hash，把步骤链写坏 |
| ③ 超时或瞬时签名才重试 | 其余（只读查询 + 幂等写） | `rc == -1` 或命中 `TRANSIENT_MARKS` | `cat-file -e` / `merge-tree` 这类**非 0 就是正常答案**，盲重试会把每次查询拖成 3 倍耗时 |

- **GitHub 镜像**：`attempts=1` —— **只给超时，不给重试**（允许滞后，成败都不提；静态守卫 `MirrorNoRetryTest`）。
- **不双层重试**：`push.py` 原有的「瞬时失败重试一次」手写循环与 `sync.py` 的 `remote_sha_with_retry`
  都已**退役**（重试下沉到 git 层）—— 两层各重试 = 最多 6~9 次尝试，且「重试了几次」会拆成两处口径。
- ⚠ 子命令判据必须**吃掉 argv 开头的 `git`**（`run_git` 拿到的是完整 argv）：不吃它会把子命令读成
  `git`，三档判据全部失效、重试**静默失效**（实写时踩到过一次，由 `GitRetryTest` 两条守住）。

## 推送（push.py）

主线 = **`origin`**（存在即主线，2026-10-08 定调：主推 origin，镜像由 origin 主机决定）；
顺序固定：同步核对 → 推主线（**20s × 3 次**，见上节）→ ls-remote 核对远端 == 本地 →
镜像一次（`attempts=1`，**全程静默**，D2 2026-09-28 定调：允许滞后，成败都不提；
镜像 = 主机 ≠ 主线主机的第一个远端 —— origin 是 gitee 则推 github，反之亦然，**只配 origin 则无镜像**；
不换代理 / 不改走 SSH / 不回滚主线已完成的推送）。
解析判据单点在 `_ship_config.resolve_main_remote` / `resolve_mirror_remote`（含无 origin 仓库的旧逻辑回退）。
取不到远端 ref ≠ 推送失败：如实说「无法核实」+ 给手工核对命令，别把网络抖动报成不一致。
