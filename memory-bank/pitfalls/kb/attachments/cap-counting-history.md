## char_count 口径的复发与判据沉淀

- **复发**: 5 次(2026-09-23→09-30), 三种入口 —— ①Python `read_text()` + `write_text(..., newline="")`
  整份重写把 CRLF 拍成 LF, cap 按原始字节数 ⇒ 量到的数字**变小**, **把"超限"藏起来了**(同一份文件
  报 2529 / 实际 2595); ②Edit/Write 会话中途整份重写落成纯 LF(看到警告却当噪音放过 = 依据过期读数);
  ③新建文件 Write 落 LF / 脚本拼装替换串带裸 `\n` ⇒ MIXED。
- **判据沉淀**(每次复发都踩实过):
  - 仓库 `core.autocrlf=true`, 检出态就是 CRLF ⇒ **写完文件要确认行尾没被改**: `git status`(或
    `git diff`)出现 `LF will be replaced by CRLF` 警告 ⇒ 该文件当前**不是检出态**, 此刻量到的字符数
    不可信。该警告**一次都不能放过**, 且"行尾检查"必须在**最后一次编辑之后**(拿更早量过的读数=读了没照做)。
    归一(按扩展名分: `.md/.py/.toml` → CRLF)后重量。
  - **收尾回写也要过一次 `pitfalls/kb/_index.md`**, 尤其是"新建文件 / 追加流水 / 改生成物"三种动作 ——
    本条触发词正是收尾时才做的事, 不在开工路由视野里(5 次复发里 3 次的共同未命中原因)。
  - **自查脚本化**(比逐个 `git diff` 翻警告快, 且未跟踪新文件在 diff 里根本不出现):
    `git status --porcelain -uall` 取全部改动文件(含未跟踪), 循环断言
    `b.count(b"\n") == b.count(b"\r\n")` —— 已实测一次捕获四件, 是有效拦截。


## 索引膨胀第二实例与先行指标

- **第二实例起 (`issues/_index.md`, 2026-10-05→10-11 四轮触顶)**: Done 条目**恒增**, 摘要截断三连压
  (`gen_issues_index.SUMMARY_MAX` 40 → 24 → 12)每次只买到一轮。**决定性判据 = 「去掉摘要后条目数是否
  撑爆 cap」** —— 该索引**无摘要**时才 14,790 < cap ⇒ 是摘要顶爆的, 截断即正解, **不外迁**(外迁会打坏
  `**Refs:**` / `doc.links` 的外部引用)。未达 50% 线属 index-auto 性质(`CAP_POLICY` 注释: 一行一条已是
  最简), **不强行凑数** —— 别为达标去砍标题(那是条目的身份, 砍了检索就废)。
  **先行指标 = 无摘要口径占 cap 比**: 59% → 74% → 85% → **越过 100%**(27,336 / 25,200, 2026-10-11) ⇒
  摘要砍到 0 也超, 摘要侧出口耗尽, 后备出口换成「**视图归档**」(老条目只出索引、文件不搬)—— 判据与
  实施见 [index-archive-view.md](../index-archive-view.md)。
  ❗所以这条的收口不是"改小一个常数", 而是**盯着无摘要占比**这个先行指标 —— 它亮红(≈85% 起)就该
  准备后备出口, 别等摘要侧压无可压。


## 追加余量的五次复发

- **复发**: 5 次(2026-09-24→10-11), 两个层次 —— 前四次是追加前**没量余量**(含用 `read_text` 量得
  误判为安全的镜像形态, 与本文第一条坑同源), 拖到守卫才红; 第五次量了文件余量(余 1,005)却**没估
  要写那段的大小**(实际 ~1,270) ⇒ 超限 66 字符, 收口只能把新条迁出成独立主题
  [index-archive-view.md](../index-archive-view.md)(正是本文件记的「贴顶时新主题单独开文件」判据)。
- **判据沉淀**: ①追加前量余量**必须用 `char_count`**(`read_text` 会把 CRLF 折掉 ⇒ 误判安全);
  ②把「量余量」当成「量一段话」是错的 —— **两段数字的差**才决定能不能写: **先估篇幅再定落点**,
  余量 < 预写篇幅 ⇒ 直接开新档, 别写完再补救; ③最快拦截 = 写完立刻 `commands run kb.check`,
  别拖到 test.full。

## 切片计数: 三个入链机检面

- **处置**: ①删前逐片核「入链」, 而入链有**三个机检面**, 只看一个会漏或误伤:
  **a. `doc.links` 的相对链接** —— 用链接**解析到真实目录**判别, 别只匹配文件名: `activeContext/` 切片与
  `testing/baselines/` 基线切片**同名共存**(同事件各留一份), 纯文件名 grep 会把「链到基线切片」
  误判成「链到会话切片」而错留(2026-10-10 实测: 粗判 20 片「被基线引用」精判后只有 1 片);
  **b. 认领链 `**Refs:**` / HTML `doc-refs` 里的路径 token** —— 纯文本提及不进 `doc.links`,
  但 `kb.check` 的认领链检查要求 token 指向的件**真实存在**, 删片不同步移除 token 就红 33 处
  (同日实测); 移除 token 本身不制造单向链(双向链另一端已随文件删除);
  **c. 冻结件基线切片里的纯文本 Refs 行** —— 一次性快照不回写, 里面的路径提及指向已删文件也
  不报红, 属可接受的历史回溯锚(git 历史可追); ②删除; ③在本专题切片/基线切片里留一行处置记录
  保持可追溯; ④复跑 `kb.check`(含认领链)+ `doc.links` + test.full 收口。
