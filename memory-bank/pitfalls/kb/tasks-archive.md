# 任务档案与状态回扫

> 摘要: 任务档案 `Status` 只能取 4 个英文单词(2026-09-23 起为 `In Progress`/`Open`/`Done`/`Dropped`); 推送后要回扫"未提交"标记, 但只改自己那一轮的, 且只改**状态标记**不动**历史叙述**。
> 触发: 立档, 改 Status, 重建索引, 推送后回扫, 标记未提交, 一并回扫, 状态标记, 历史叙述

### 任务档案的 `**Status:**` 只能取 4 个英文单词

- **触发**: 新建 / 更新 `memory-bank/tasks/*.md` 的状态行。
- **判别**: 取值只允许 `In Progress` / `Open` / `Done` / `Dropped`(旧词 `Pending`/`Completed`/`Abandoned`
  已按 5 词表统一改写); 写成 `✅ 完成` 会让
  **两条守阵同时红**(状态行缺失 + 索引分区不一致), 容易误判成"索引坏了"。
  正确写法是 `Done (…中文说明…)`。
- **处置**: 改完**必须重跑** `commands run kb.index`(索引是生成物, 不手改)。
  **立档前先按 slug 查重** —— 并行分支各自立档会造成重复档案 + 重复索引条目, 而 `_indexed_sections()` 是 dict,
  同 ID 重复登记会**静默覆盖**。

### 推送之后回扫一遍"未提交 / 尚未提交"标记

- **触发**: 推送成功后收尾。
- **判别**: 上一轮写下的"未提交"标记已经失效(自己这一轮的改动已经入库)。
- **处置**: 把自己这一轮的改成**「已入库 `<sha>`」**(带提交号可核验)。
  ⚠ **只改自己这一轮的** —— 并发会话的条目同样会失效, 但按 scope-guard 不要顺手替别人改(改必然撞车)。
  基线数字同理: 改了测试就两侧都重测再落。

### 回扫只改「状态标记」, 不改「历史叙述」

- **触发**: 扩大回扫范围 —— 用户说「一并回扫」, 或想直接按全库 grep `未提交` 的结果批量替换。
- **判别**: 同一个词在两类位置上含义完全不同, **必须先分类再动手**:
  - **状态标记**(易变层对**当前**状态的声明)⇒ 失效即改: `activeContext/` 切片的标题 / 摘要 /
    状态行 / 下一步, `progress/` 的「已实现」条目, `tasks/` 的 `**Status:**` 与**子任务状态表**,
    `checklists/` 项, issue 的**结论段**。
  - **历史叙述**(记录**当时**为真)⇒ **一律不改**, 改了就是伪造历史: 带时刻的进度日志行
    (「18:5x — … 未提交」/「2026-09-15: … 未提交 git。」)、`plans/` 与 `reports/` 的快照、
    `progress/attachments/`、以及 pitfalls 自身的规则原文。
- **处置**: 2026-09-25 实测全库 grep 出 **122 行 / 60 文件**, 真正该改的只有 **26 处 / 18 文件** ——
  比例约 1/5, 按 grep 结果批量替换会改坏 4/5 的历史记录。
  跨轮次回扫**只在用户显式授权时**做(默认见上条: 只改自己这一轮的); 每处都要能当场拿出 `<sha>`,
  **拿不出就别猜** —— 宁可留原样并如实报告, 也不要在知识库里写一个错的提交号(那比过期标记更坏)。
  定 `<sha>` 的手法: `git log -S "<该轮引入的唯一符号>" --oneline`(比翻提交信息可靠)。
