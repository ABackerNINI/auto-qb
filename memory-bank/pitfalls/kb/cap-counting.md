# cap 字符数口径 / 流水轮转 / 索引膨胀源

> 摘要: 守卫的字符数比编辑器统计**每行多 1**(CRLF); cap 是**字符数**而外部常报**字节数**(中文一字 3 字节 ⇒ 可差 3 倍, 误报出根本不存在的债务); append-only 流水撞 `log` cap 的正解是**轮转**; 外迁到 `attachments/` 时随迁的相对链接要**整体上移一层**(否则 `doc.links` 坏链); 而生成式索引撞 cap 时先查**渲染口径**而不是先搬条目。
> 触发: 判断文件是否超 cap, 字符数对不上, KB 超 cap, 字节 vs 字符, 债务误报, 单位换算, baseline-history 超 cap, 追加流水, log 档, 轮转, attachments, 外迁附件坏链, 随迁链接, 相对链接上移, doc.links 坏链, tasks/_index 超 cap, 索引膨胀, 新增主题放哪个类, 类索引贴顶, 切片计数超限, SLICE_COUNT_LIMIT, 蒸馏切片

> **cap 现行数值单点** = `.agents/skills/memory-bank/scripts/_common.py` 的 `CAP_POLICY`(当前 `pitfall` / `index-auto` / `log` 均 8,000; 改 cap 只改这一处)。
> 本文出现的旧数值仅作历史现场, **别拿它们当现行依据**做落点决策。

## 两个连在一起的坑

### 量 cap 必须用 `_common.char_count()`, 不能用 `read_text()`

- **触发**: 自己数一个文件"超没超 cap", 或本地跑得绿、守卫却报超。
- **判别**: `read_bytes().decode("utf-8")`(守卫口径) 比 `read_text()`(编辑器 / 脚本常用口径)
  **每行多 1 个字符** —— 后者走 universal newlines 把 CRLF 折成 LF。实测 2026-09-23:
  `baseline-history.md` 自测 24,151、守卫报 24,466, 差值 315 = 文件行数。**卡在临界值时
  `read_text()` 会给出"没超"的假绿灯**, 于是提交被闸门拦下。
- **处置**: 量 cap 一律走 `_common.char_count()`(或等价地 `len(path.read_bytes().decode("utf-8"))`)。
- **复发记录与判据沉淀**: 见 [attachments/cap-counting-history.md](attachments/cap-counting-history.md)。

### 量 cap 的第三种形态: 拿「KB / 字节」去比「字符数」的 cap

- **触发**: 有人(用户 / 编辑器面板 / `ls -la` / 资源管理器)报「`<文件>` XX KB 超 XX KB cap」, 你准备去改它。
- **判别**: cap 的单点是**字符数**(`_common.char_count`), 而文件系统与编辑器统计面板给的是**字节数** ——
  中文 UTF-8 一个字 **3 字节** ⇒ 同一份文件按字节读能比按字符读大近 3 倍, **凭空多出一个"债务"**。
  2026-10-06 实测: 报「`pitfalls/web-ui/layout-css.md` 17.6KB 超 12KB cap」(当时档), 实际
  **17,661 字节 = 9,717 字符** < 12,000(当时角色 `pitfall`; 现行 8,000)—— **根本没超**; `doc.caps` 与
  `check_kb_structure` 也都判 PASS。与本文第一条(`read_text` 把 CRLF 折成 LF ⇒ 每行少算 1)是
  **同一族的第三种形态**: 都是"报数口径 ≠ 守卫口径"。
- **处置**: 先用守卫口径现算(`_common.char_count` / `commands run doc.caps` / `check_kb_structure`) **再决定动不动文件**;
  口径一致的误报 ⇒ **一行都不改**(范围守恒); 报数方与守卫不一致时**以守卫口径为准**, 并把这处口径差说清楚(否则下轮还会再报一次)。
- **判据(一句话)**: 看到「KB / MB」先把单位换成**字符**再比 cap —— `ls -la` 的输出**不是** cap 结论。

### append-only 流水撞 `log` cap 时按设计**轮转**, 不是删内容

- **触发**: 往 `*-history.md` 这类 append-only 流水追加条目后, 守卫报超 `log` 档(当时 24,000; 现行 8,000)。
- **判别**: 这类文件**设计上就会一直长**, cap 的语义是"涨到多少该轮转", 不是"该删"。
  2026-09-23 现场: `testing/baseline-history.md` 加一条后 24,466 —— 而它此前只剩 170 字符余量(当时档),
  也就是说**任何**一次追加都会越线。
- **处置**: 从**最老一端**(最近在上的文件 = 尾部)切到 **≤ cap**, 原样搬到 `<目录>/attachments/`,
  在原位留一行指针(2026-11-05 起, 旧 `TRIM_KEEP = 1/2` 已废止) —— `log` 是 append-only, 轮转不是删。
  - ❌ **别只搬"最老的一条"**: 条目大小不受控(可能只有几百字符), 下次追加会立刻再触顶。
    2026-09-23 首版就是这么写的 —— 而该文件触顶时只剩 170 字符余量, 等于**每次新增都要迁移一次**,
    这正是被用户当场指出并改掉的地方。
  - ✅ `attachments/` 为什么有效: `iter_topic_files()` 是**非递归 glob**, 且 `attachments` 在
    `_common.EXCLUDED_DIRS` 里 ⇒ 那里的文件既不被当主题文件、也不计入 cap 检查。
  - `check_kb_structure.py` 报这条时会把**目标字符数**直接打出来(如 "切到 ≤ 8,000 字符"), 照它切即可。
  - ⚠ 搬运用脚本按原换行风格切分**原样**写回, 别手抄 —— 手抄会引入不可见的行尾/缩进漂移。

### 外迁文档到 `attachments/` 时, 原文的相对链接要**整体上移一层**

- **触发**: 把某段原文(纪要 / 映射表 / 逐批记录)从 `<目录>/<文件>.md` 切到
  `<目录>/attachments/<文件>-<段>.md` 以消 cap 债务。
- **判别**: 原文里的相对链接是**相对原文件位置**写的 —— 外迁后位置深了一层, 原来的
  `../pitfalls/x.md` 会解析成 `<目录>/pitfalls/x.md`(不存在) ⇒ `commands run doc.links` 红,
  且**逐条报在新附件上**、不在主档上, 容易被当成"主档没问题"而漏看。
  2026-10-09 实测: 外迁 53,478 字符的 `backend-test-web-split` 实施记录, 9 条 `../` 链接全坏
  (`../pitfalls/testing/*.md` · `../archive/README.md` · `../testing/baselines/*.md`)。
- **处置**: 外迁后对**附件正文**做一次机械重写 —— 每个非绝对链接(`http(s)://` / `#锚` /
  `/` 开头之外)**统一前缀一层 `../`**; 主档侧新增的「指回附件」链接**不要**跟着改(它本来就对)。
  改完立刻 `commands run doc.links` 收口, 别留到 ship 闸门。
- **复发**: 2 —— 首次 2026-09-30(记于上方「追加余量」条目的复发 4), 本轮 2026-10-09 再踩。
  **为什么没命中**: 本轮开工**读了本文件**却只照做了"切分 + 留指针", 没把「链接位移」当**外迁动作
  的一部分**执行 —— 与复发 3/4 同因(回写动作不在开工路由视野里), 靠 `doc.links` 机检当场抓回。

### 生成式索引撞 cap: 先查**渲染口径**, 别急着搬条目

- **触发**: `tasks/_index.md`(或任何生成式索引)超 cap, 直觉反应是"把老条目外迁"。
- **判别**: 先算**每个条目占多少字符**。2026-09-23 实测 `tasks/_index.md` 12,299 字符 = header 626 +
  33 条 ×**平均 350 字符/行** —— 因为索引把 `**Summary:**` **全文**打进了一行。此时索引大小由
  「摘要写得多长」决定, 而不是由「有几个档案」决定; 靠外迁条目化解的话:
  ①可动的只有已完成档案(16 个 In Progress 是活的) ②其中 15 个有外部引用, 搬走会让
  `check_doc_links.py` 变红(除非连带改写引用) ③全搬也只够一次, 下次立刻再触顶 —— **病根没动**。
- **处置**: 改**渲染口径**(摘要截断成一行, 如 `gen_tasks_index.SUMMARY_MAX = 80`), 索引随即
  12,299 → 5,710, 同样 cap 能容纳 ~90 个档案, 且**零链接破坏、零信息丢失**(全文在档案里)。
  外迁条目只当**后备**(真到几百个档案、条目数本身撑爆 cap 时才用, 且要挑无外部引用的老档案)。
- **第二实例与先行指标**: 见 [attachments/cap-counting-history.md](attachments/cap-counting-history.md)。

### 类索引贴顶时, 新主题要落到**有余量的类**

- **触发**: 想给某个 pitfalls 类新增主题文件, 守卫却报该类 `_index.md` 超 cap(2026-09-26 实测)。
- **判别**: `web-ui/_index.md` 当时 **2,989 / 3,000**(余量 11 字符; 类索引现走 index-auto **8,000** 档,
  3,000 是翻倍前旧档), 而新主题的一行(文件名 + 摘要 +
  触发词)**最少也要 ~130 字符** ⇒ **任何**新条目都会让它越线, `test_kb_files_respect_caps` 立刻报红;
  缩摘要 / 砍触发词也补不回来(行本身的固定开销就在那)。**类索引的余量 ≠ 主题文件的余量** ——
  后者(现行 pitfall 档 8,000)常有空, 前者才是新条目的真正闸门。
- **处置**: ①新增主题前先量**目标类** `_index.md` 的余量(不是量要写的那个文件);
  ②不够就把主题落到**语义相近且有余量的类**(本例 `web-ui` → `docs`: 1,160 → 1,569),
  并在条目正文里用相对链接指回真正相关的那条(如 `../web-ui/columns-persist.md`), 检索链不断;
  ③"并入该类已有主题"能绕开索引膨胀, 但新坑的**触发词进不了索引** ⇒ 检索变弱, 优先选 ②。

### 追加内容前先看目标文件离 cap 还有多少余量

- **触发**: 往一个已有文件(pitfalls / 主题文档)追加一段。2026-09-24 实测: 给
  [testing/tmpdir.md](../testing/tmpdir.md) 补一条新坑, 写完才跑守卫, 报 `6,060 > 6,000 字符 (角色 pitfall)`
  (当时 pitfall 档 6,000; 现行 8,000 —— 判据不变, 数字别照抄)。
- **判别**: cap 只看**文件总量**, 不区分"是谁写的那段" —— 老内容占满时, 新坑写得再对也进不去。
- **处置**: ①追加前先量余量(`len(path.read_bytes().decode("utf-8"))` 与角色 cap 之差);
  ②余量不够时**先压自己那段**, 别去删别人的判据(那些正是这个文件的价值);
  ③写完立刻跑 `commands run kb.check`(含 cap 校验), 别留到全量测试才发现。
- **复发记录**: 见 [attachments/cap-counting-history.md](attachments/cap-counting-history.md)。

### 生成式跨形态视图撞 `index-auto` cap: 两个出口, 别条件反射调上限

- **触发**: 新增计划/报告/专题后 `test_doc_map_is_regenerated_and_capped` 红
  (2026-09-28 实测: 新专题入册 `_doc-map.md` 12,144 > 12,100)。
- **判别**: 先查渲染口径 —— 口径没问题就是**内容真长了**; 四轮触顶(09-27→28 三次上调
  12,000→12,200, 当时档)说明专题数在稳定增长, 调上限治标。
- **处置**: ①**优先收口生成器的固定文案**(head/包装行 —— 两轮收口共压 ~190 字符,
  12,144→12,118, 零信息损失); ②`CAP_POLICY` 上调是**最后手段**
  (动 `_common.py` 须同步 SKILL.md cap 表 + `test_skill_cap_table_matches_cap_policy` 守阵,
  且 cap 放水是单向棘轮)。
- **旧政策与复发记录**: 见 [attachments/cap-counting-history.md](attachments/cap-counting-history.md)。

### 切片计数触顶时, 可蒸馏的是「已完结波次的切片」, 不是"等 14 天"

- **触发**: 收尾跑 test.full, `test_kb_active_context_slices_are_valid` 报 `切片数 71 > 70`
  (2026-09-30 实测: 本会话新增 1 片恰好顶破; 注意 `kb.check` **不含**切片计数校验, 只有 pytest 看得见)。
- **判别**: 守卫消息给出处置动作与目标(现口径 = 蒸馏到 60<=目标<=80 保留带), 但**可能一个都没有**(当日切片全部 ≤7 天,
  无一片可"等 14 天")。此时别条件反射「抬 `SLICE_COUNT_LIMIT`」—— 那是治理政策(见
  [plans/26-09-30-2112](../../plans/26-09-30-2112-plan-memory-bank-cap-debt.html) 决策点 D2), 也不是
  「删活跃切片」(= 违规归档)。**合法对象 = 内容已被任务档案全量覆盖的完结波次切片**: 判别看该切片
  「状态」段是否已完结、其档案是否已含全文(如"已完成, 随档提交"那类); 次要对象 = 同专题重复片
  (一个专题一片是约定, 多片是违规产物, 合并即 -N)。
- **处置**: 删除前的三个入链机检面与操作顺序见 [attachments/cap-counting-history.md](attachments/cap-counting-history.md)。

- **注**: 该上限按 ~5 片/日校准, 而多 clone 并行日常态实测可达 15 片/日 ⇒ 份额会被他方会话的
  「一波次一片」风格烧光, 上限将反复触顶; 长期处置走治理议题, 各会话别自行调数。**2026-11-03
  用户定调上限 70→120、处置目标 = 一次清理蒸馏到 80 条以内**(`_common.SLICE_COUNT_LIMIT` /
  `SLICE_COUNT_TARGET` 单点); 上列 `71 > 70` 是当时阈值下的历史事故锚, 不随抬数改写。
