# cap 字符数口径 / 流水轮转 / 索引膨胀源

> 摘要: 守卫的字符数比编辑器统计**每行多 1**(CRLF); append-only 流水撞 `log` cap 的正解是**轮转**; 而生成式索引撞 cap 时先查**渲染口径**而不是先搬条目。
> 触发: 判断文件是否超 cap, 字符数对不上, baseline-history 超 cap, 追加流水, log 档, 轮转, attachments, tasks/_index 超 cap, 索引膨胀, 新增主题放哪个类, 类索引贴顶, 切片计数超限, SLICE_COUNT_LIMIT, 蒸馏切片

## 两个连在一起的坑

### 量 cap 必须用 `_common.char_count()`, 不能用 `read_text()`

- **触发**: 自己数一个文件"超没超 cap", 或本地跑得绿、守卫却报超。
- **判别**: `read_bytes().decode("utf-8")`(守卫口径) 比 `read_text()`(编辑器 / 脚本常用口径)
  **每行多 1 个字符** —— 后者走 universal newlines 把 CRLF 折成 LF。实测 2026-09-23:
  `baseline-history.md` 自测 24,151、守卫报 24,466, 差值 315 = 文件行数。**卡在临界值时
  `read_text()` 会给出"没超"的假绿灯**, 于是提交被闸门拦下。
- **处置**: 量 cap 一律走 `_common.char_count()`(或等价地 `len(path.read_bytes().decode("utf-8"))`)。
- **复发**: 1 —— 镜像形态: Python `read_text()` + `write_text(..., newline="")` ⇒ 整份文件 CRLF 变 LF,
  而 cap 按原始字节数 ⇒ 量到的数字**变小**: 同一份 `SKILL.md` 报 2529(实际检出态 2595/2600),
  切片报 5948(实际 **6040 > 6000**) —— **把"超限"藏起来了**。仓库 `core.autocrlf=true`,
  检出态就是 CRLF ⇒ **写完文件要确认行尾没被改**。
- **判据(最快)**: 改完跑 `git status`(或 `git diff`), 出现 `LF will be replaced by CRLF` 警告
  ⇒ 该文件当前**不是检出态**, 此刻量到的字符数不可信; 归一(按扩展名分: `.md/.py/.toml` → CRLF)后重量。
- **复发**: 2 —— 编辑器工具形态: 同一文件会话中途量过是 CRLF, 之后 Edit/Write 改两处时**整份重写**落成纯 LF;
  我在 `git diff` 里**看到警告却当噪音放过** —— 根因**读了没照做**(依据是更早量过的**过期读数**)。
  教训: 该警告**一次都不能放过**; "行尾检查"必须在**最后一次编辑之后**。新建文件同理(Write 落 LF),
  提交前对 `git status` 里每个改动文件重量一遍。
- **复发**: 3 —— 同一形态第三遍(新建档案+切片 = Write 落纯 LF; 脚本拼装附件时替换串带 3 个裸 `\n` ⇒ MIXED)。
  **为什么没命中**: 本轮是"改前端"任务, 开工只按动作读了 `pitfalls/web-ui/_index.md`, 没进 `kb` 类 ——
  而本条的触发词(`追加流水`/`log`/`轮转`/`attachments`)正是**收尾回写**时才做的事(不在开工路由视野里)。
  教训: **收尾回写也要过一次 `pitfalls/kb/_index.md`**, 尤其是"新建文件 / 追加流水 / 改生成物"三种动作。
  最快自查: 对 `git diff --name-only` + 新建文件逐个断言 `bytes.count(b"\n") == bytes.count(b"\r\n")`。
- **复发**: 4 —— 同一形态(新建档案+切片, Write 落纯 LF)。**为什么没命中**: 这次读了 `kb` 类, 但只在
  写完后才想起查行尾, 且方式是"翻上一轮日记"而非当**收尾动作**先做。收获是**把自查脚本化**:
  `git status --porcelain -uall` 取全部改动文件(含未跟踪), 循环断言 `b.count(b"\n") == b.count(b"\r\n")`
  —— 比逐个 `git diff` 找警告快且不会漏(未跟踪新文件在 `git diff` 里根本不出现)。
- **复发**: 5 —— 2026-09-30 新建计划 / 档案 / 切片 / 基线四件, Write 全落纯 LF(归一后复量通过)。
  **为什么没命中**: 开工按动作读了 `pitfalls/git` 与 cap 候选脚本, 但**收尾新建文件前没进 `pitfalls/kb` 类**
  —— 与复发 3 同因(回写动作不在开工路由视野里)。本轮靠收口时跑本条的自查断言(对 `git status -uall`
  每个改动文件断言 `b.count(b"\n") == b.count(b"\r\n")`)一次捕获四件, 说明该脚本化断言已是有效拦截。

### append-only 流水撞 `log` cap 时按设计**轮转**, 不是删内容

- **触发**: 往 `*-history.md` 这类 append-only 流水追加条目后, 守卫报超 `log` 档(24,000)。
- **判别**: 这类文件**设计上就会一直长**, cap 的语义是"涨到多少该轮转", 不是"该删"。
  2026-09-23 现场: `testing/baseline-history.md` 加一条后 24,466 —— 而它此前只剩 170 字符余量,
  也就是说**任何**一次追加都会越线。
- **处置**: 从**最老一端**(最近在上的文件 = 尾部)一次切到 **50%**, 原样搬到 `<目录>/attachments/`,
  在原位留一行指针。切多少由 `_common.TRIM_KEEP = 1/2` 定(2026-09-29 起, 原 `LOG_ROTATE_KEEP = 2/3`) ——
  切完让文件落回 ~50% 容量, 于是留出足够的追加余量。
  - ❌ **别只搬"最老的一条"**: 条目大小不受控(可能只有几百字符), 下次追加会立刻再触顶。
    2026-09-23 首版就是这么写的 —— 而该文件触顶时只剩 170 字符余量, 等于**每次新增都要迁移一次**,
    这正是被用户当场指出并改掉的地方。
  - ✅ `attachments/` 为什么有效: `iter_topic_files()` 是**非递归 glob**, 且 `attachments` 在
    `_common.EXCLUDED_DIRS` 里 ⇒ 那里的文件既不被当主题文件、也不计入 cap 检查。
  - `check_kb_structure.py` 报这条时会把**目标字符数**直接打出来(如 "切到 ≤ 24,000 字符"), 照它切即可。
  - ⚠ 搬运用脚本按原换行风格切分**原样**写回, 别手抄 —— 手抄会引入不可见的行尾/缩进漂移。

### 生成式索引撞 cap: 先查**渲染口径**, 别急着搬条目

- **触发**: `tasks/_index.md`(或任何生成式索引)超 cap, 直觉反应是"把老条目外迁"。
- **判别**: 先算**每个条目占多少字符**。2026-09-23 实测 `tasks/_index.md` 12,299 字符 = header 626 +
  33 条 ×**平均 350 字符/行** —— 因为索引把 `**Summary:**` **全文**打进了一行。此时索引大小由
  「摘要写得多长」决定, 而不是由「有几个档案」决定; 靠外迁条目化解的话:
  ①可动的只有已完成档案(16 个 In Progress 是活的) ②其中 15 个有外部引用, 搬走会让
  `check_doc_links.py` 变红(除非连带改写引用) ③全搬也只够一次, 下次立刻再触顶 —— **病根没动**。
- **处置**: 改**渲染口径**(摘要截断成一行, 如 `gen_tasks_index.SUMMARY_MAX = 80`), 索引随即
  12,299 → 5,710, 同样 cap 能容纳 ~90 个档案, 且**零链接破坏、零信息丢失**(全文在档案里)。
  外迁条目只当**后备**(真到几百个档案、条目数本身撑爆 cap 时才用, 且要挑无外部引用的老档案)。
- **第二实例 (`issues/_index.md`, 2026-10-05)**: 133 条 × 平均 86 字符摘要 ⇒ 26,260 撞 `index-auto`(25,200);
  加 `gen_issues_index.SUMMARY_MAX = 40` → 20,620。**决定性判据 = 「去掉摘要后条目数是否撑爆 cap」** ——
  该索引**无摘要**时才 14,790 < cap ⇒ 是摘要顶爆的, 截断即正解, **不外迁**(外迁会打坏 `**Refs:**` /
  `doc.links` 的外部引用)。未达 50% 线(12,600)属 index-auto 性质(`CAP_POLICY` 注释: 一行一条已是最简),
  **不强行凑数** —— 别为达标去砍标题(那是条目的身份, 砍了检索就废)。

### 类索引贴顶时, 新主题要落到**有余量的类**

- **触发**: 想给某个 pitfalls 类新增主题文件, 守卫却报该类 `_index.md` 超 cap(2026-09-26 实测)。
- **判别**: `web-ui/_index.md` 当时 **2,989 / 3,000**(余量 11 字符), 而新主题的一行(文件名 + 摘要 +
  触发词)**最少也要 ~130 字符** ⇒ **任何**新条目都会让它越线, `test_kb_files_respect_caps` 立刻报红;
  缩摘要 / 砍触发词也补不回来(行本身的固定开销就在那)。**类索引的余量 ≠ 主题文件的余量** ——
  后者(cap 6,000)常有空, 前者才是新条目的真正闸门。
- **处置**: ①新增主题前先量**目标类** `_index.md` 的余量(不是量要写的那个文件);
  ②不够就把主题落到**语义相近且有余量的类**(本例 `web-ui` → `docs`: 1,160 → 1,569),
  并在条目正文里用相对链接指回真正相关的那条(如 `../web-ui/columns-persist.md`), 检索链不断;
  ③"并入该类已有主题"能绕开索引膨胀, 但新坑的**触发词进不了索引** ⇒ 检索变弱, 优先选 ②。

### 追加内容前先看目标文件离 cap 还有多少余量

- **触发**: 往一个已有文件(pitfalls / 主题文档)追加一段。2026-09-24 实测: 给
  [testing/tmpdir.md](../testing/tmpdir.md) 补一条新坑, 写完才跑守卫, 报 `6,060 > 6,000 字符 (角色 pitfall)`。
- **判别**: cap 只看**文件总量**, 不区分"是谁写的那段" —— 老内容占满时, 新坑写得再对也进不去。
- **处置**: ①追加前先量余量(`len(path.read_bytes().decode("utf-8"))` 与角色 cap 之差);
  ②余量不够时**先压自己那段**, 别去删别人的判据(那些正是这个文件的价值);
  ③写完立刻跑 `commands run kb.check`(含 cap 校验), 别留到全量测试才发现。
- **复发**: 1 —— 2026-09-29 本文件追加「复发 3」前**没量余量**(用 `read_text` 量得 5,997 误判为安全,
  实际 `char_count` 6,121), 拖到 test.full 才红; 压缩叙述(判据全留)至 5,501 收口。追加前那一次量**必须用 `char_count`** —— 与本文第一条坑同源。
- **复发**: 2 —— 同日晚回写 `pitfalls/web-ui/contract-api.md` 时**又**没先量(该文件 5,601/6,000,
  余 ~400, 新条目却 674)⇒ 守卫红, 靠压自己那段收口(674→384)。**为什么没命中**: 没把它当**追加动作**走本条。
  最快拦截 = 写完立刻 `commands run kb.check`。
- **复发**: 3 —— 2026-09-29 档案追加 M1 日志**未量余量**(25,074, test.full 拦), 外迁收口;
  同轮脚本 5 文件落 LF, 归一后复量。**为什么没命中**: 追加前未过 `pitfalls/kb` 类。
- **复发**: 4 —— 2026-09-30 档案追加 M3 日志未量余量(25,574) + 归一脚本把 5 文件拍成 LF(首条镜像) +
  随迁链接未改 `../../` 坏链。外迁两条 + 归一 CRLF 收口。**为什么没命中**: 回写未过 kb 类、
  没跑 kb.check。

### 生成式跨形态视图撞 `index-auto` cap: 两个出口, 别条件反射调上限

- **触发**: 新增计划/报告/专题后 `test_doc_map_is_regenerated_and_capped` 红
  (2026-09-28 实测: 新专题入册 `_doc-map.md` 12,144 > 12,100)。
- **判别**: 先查渲染口径 —— 口径没问题就是**内容真长了**; 四轮触顶(09-27→28 三次上调
  12,000→12,200)说明专题数在稳定增长, 调上限治标。
- **处置**: ①**优先收口生成器的固定文案**(head/包装行 —— 两轮收口共压 ~190 字符,
  12,144→12,118, 零信息损失); ②`CAP_POLICY` 上调是**最后手段**
  (动 `_common.py` 须同步 SKILL.md cap 表 + `test_skill_cap_table_matches_cap_policy` 守阵,
  且 cap 放水是单向棘轮)。
- **复发**: 1–5 —— 09-27→28 连续触顶五次: 前四次按处置①压固定文案(12,226→12,194 等), 第五次
  (HR 复审报告入册 12,473) 走出口②上调 12,600 + SKILL 表同步。教训: **每次 kb.index 之后都要再跑
  一次 KB 守卫**, 别拖到 ship.commit 闸门才红(两次都是这么红的)。
- **收口(2026-09-29)**: `_doc-map.md` 退役改查询 `kb.docmap`(现算+轮转+查缺主键), 绝根。
- **注(2026-09-29 政策变更)**: 用户定调 `CAP_POLICY` 全表**翻倍** + 触顶处置统一"收缩到 50%"(`TRIM_KEEP`),
  治「触顶即返工一轮」的 token 税 —— "调上限是最后手段/单向棘轮"的旧口径自此放宽为"已按政策校准";
  但**先查渲染口径**的优先级不变, 渲染仍有病根时先修口径。
- **复发**: 6 —— 2026-09-30 新建任务档案后只重跑了 memory-bank 守卫, 没跑 test_docs_forms / kb.check,
  `**Topics:**` 跨形态主键缺失拖到 ship.commit 闸门才红。**为什么没命中**: 把「新建档案」当归档动作
  而非 KB 回写动作, 没触发「写完立刻 kb.check」—— 口径自此明确: **任何 memory-bank 文件新建/修改后,
  `kb.index` 与 KB 守卫(`kb.check` + `tests/test_docs_forms.py`)一并重跑再进 ship**。
- **复发**: 7 —— 同日再踩(危险操作层档案): 建档时漏 `**Topics:**` 行, 这次在 test.quick 里被
  test_doc_topics_complete 拦住(未拖到 ship 闸门)。**为什么没命中**: 复发 6 的收口口径是「重跑守卫」,
  本轮照做了且守卫确实拦住 —— 但**建档模板本身**没把 Topics 行当必备行带上, 仍靠守卫兜底而非建档
  时写入; 口径补全: 建档模板 = 状态行四件套 + `**Topics:** <slug>`(slug 与文件名一致)。

### 切片计数触顶时, 可蒸馏的是「已完结波次的切片」, 不是"等 14 天"

- **触发**: 收尾跑 test.full, `test_kb_active_context_slices_are_valid` 报 `切片数 71 > 70`
  (2026-09-30 实测: 本会话新增 1 片恰好顶破; 注意 `kb.check` **不含**切片计数校验, 只有 pytest 看得见)。
- **判别**: 守卫消息只说「把 14 天未动的切片蒸馏后删除」, 但**可能一个都没有**(当日切片全部 ≤7 天,
  无一片可"等 14 天")。此时别条件反射「抬 `SLICE_COUNT_LIMIT`」—— 那是治理政策(见
  [plans/26-09-30-2112](../../plans/26-09-30-2112-plan-memory-bank-cap-debt.html) 决策点 D2), 也不是
  「删活跃切片」(= 违规归档)。**合法对象 = 内容已被任务档案全量覆盖的完结波次切片**: 判别看该切片
  「状态」段是否已完结、其档案是否已含全文(如"已完成, 随档提交"那类); 次要对象 = 同专题重复片
  (一个专题一片是约定, 多片是违规产物, 合并即 -N)。
- **处置**: ①删前 `grep -rn "<切片文件名>"` 确认无入链(否则 `doc.links` 红); ②删除; ③在本专题
  新切片「状态」里留一行「前序波次切片已蒸馏 (内容全在其档案)」保持可追溯; ④复跑 test.full 收口。
- **注**: 该上限按 ~5 片/日校准, 而多 clone 并行日常态实测可达 15 片/日 ⇒ 份额会被他方会话的
  「一波次一片」风格烧光, 上限将反复触顶; 长期处置走治理议题, 各会话别自行调数。
