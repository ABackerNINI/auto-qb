# cap 字符数口径 / 流水轮转 / 索引膨胀源

> 摘要: 守卫的字符数比编辑器统计**每行多 1**(CRLF); append-only 流水撞 `log` cap 的正解是**轮转**; 而生成式索引撞 cap 时先查**渲染口径**而不是先搬条目。
> 触发: 判断文件是否超 cap, 字符数对不上, baseline-history 超 cap, 追加流水, log 档, 轮转, attachments, tasks/_index 超 cap, 索引膨胀, 新增主题放哪个类, 类索引贴顶

## 两个连在一起的坑

### 量 cap 必须用 `_common.char_count()`, 不能用 `read_text()`

- **触发**: 自己数一个文件"超没超 cap", 或本地跑得绿、守卫却报超。
- **判别**: `read_bytes().decode("utf-8")`(守卫口径) 比 `read_text()`(编辑器 / 脚本常用口径)
  **每行多 1 个字符** —— 后者走 universal newlines 把 CRLF 折成 LF。实测 2026-09-23:
  `baseline-history.md` 自测 24,151、守卫报 24,466, 差值 315 = 文件行数。**卡在临界值时
  `read_text()` 会给出"没超"的假绿灯**, 于是提交被闸门拦下。
- **处置**: 量 cap 一律走 `_common.char_count()`(或等价地 `len(path.read_bytes().decode("utf-8"))`)。
- **复发**: 1 —— 2026-09-24 撞的是**镜像形态**: 用 Python 改文件时 `read_text()`(universal newlines 折成 LF)
  + `write_text(..., newline="")` ⇒ **整份文件从 CRLF 变 LF**, 而 cap 按**原始字节**数(CRLF 每行 +1)⇒
  量到的数字**变小**: 同一个 `SKILL.md` 报 2529(实际检出态 2595/2600, 余量只剩 5),
  切片报 5948(实际 **6040 > 6000**, `kb.check` 本应判红) —— **把"超限"藏起来了**。
  仓库 `core.autocrlf=true`, 检出态就是 CRLF; 所以**写完文件要确认行尾没被改**。
- **判据(最快)**: 改完跑 `git status`(或 `git diff`), 出现 `LF will be replaced by CRLF` 警告
  ⇒ 该文件当前**不是检出态**, 此刻量到的字符数不可信; 归一(按扩展名分: `.md/.py/.toml` → CRLF)后重量。
- **复发**: 2 —— 2026-09-24 第二次撞的是**编辑器工具形态**: 同一份文件, 会话中途量过是 CRLF(89/89),
  之后又用 Edit/Write 工具改了两处, 工具**整份重写**时落成了纯 LF(0 CRLF / 89 LF);
  而我在 `git diff` 输出里**看到了那条警告却当噪音放过** —— 根因是**读了没照做**:
  本条的判据写着"改完跑 `git status` 看警告", 我照跑却把警告合理化了(依据是更早那次量过的行尾, 属**过期读数**)。
  教训: 该警告**一次都不能放过**; 且"行尾检查"必须发生在**最后一次编辑之后**(编辑会整份重写)。
  新建文件同理(Write 工具落 LF ⇒ 新切片一开始就不是检出态), 提交前对 `git status` 里**每个**改动文件重量一遍。
- **复发**: 3 —— 2026-09-24 第三次, **同一形态再来一遍**(新建档案 + 新切片 = Write 落纯 LF 146/146 与 49/49;
  另用脚本拼装外迁附件时 `str.replace()` 的替换串里带了 3 个裸 `\n` ⇒ 附件变 MIXED)。
  **为什么没命中**: 本轮是"改前端"的任务, 开工只按动作路由读了 `pitfalls/web-ui/_index.md`,
  压根没进 `kb` 类 —— 而本条住在 `kb` 类, 且它的触发词(`追加流水` / `log` 档 / `轮转` / `attachments`)
  正是我在**收尾回写**时才做的事(收尾不在开工路由的视野里)。教训: **收尾回写也要过一次
  `pitfalls/kb/_index.md`**, 尤其是"新建文件 / 追加流水 / 改生成物"这三种动作;
  另外 `git diff` 那条 `LF will be replaced by CRLF` 警告本轮**又出现了两次**(还原静态文件、拼装附件),
  两次都被当噪音放过 —— 判据没变, 只是没人执行。
  最快自查(改完**最后一次**编辑就跑): 见下方"全部改动文件一次性复核"的口径 ——
  对 `git diff --name-only` + 新建文件逐个断言 `bytes.count(b"\n") == bytes.count(b"\r\n")`。
- **复发**: 4 —— 2026-09-24 第四次, **同一形态**(新建档案 98 行 + 新切片 32 行, Write 落纯 LF)。
  **为什么没命中**: 这次读了 `kb` 类(上一轮的教训生效了), 但只在**写完之后**才想起来查行尾 ——
  而查的方式还是"翻上一轮日记里的教训", 不是把它当**收尾动作**先做。收获是**把自查脚本化**:
  `git status --porcelain -uall` 取全部改动文件(含未跟踪), 循环断言
  `b.count(b"\n") == b.count(b"\r\n")`, 一次打印所有不合格的文件 —— 比逐个 `git diff` 找警告快且不会漏
  (未跟踪的新文件在 `git diff` 里**根本不出现**, 这正是"新建文件最容易漏"的成因)。

### append-only 流水撞 `log` cap 时按设计**轮转**, 不是删内容

- **触发**: 往 `*-history.md` 这类 append-only 流水追加条目后, 守卫报超 `log` 档(24,000)。
- **判别**: 这类文件**设计上就会一直长**, cap 的语义是"涨到多少该轮转", 不是"该删"。
  2026-09-23 现场: `testing/baseline-history.md` 加一条后 24,466 —— 而它此前只剩 170 字符余量,
  也就是说**任何**一次追加都会越线。
- **处置**: 从**最老一端**(最近在上的文件 = 尾部)一次切掉约 **1/3**, 原样搬到 `<目录>/attachments/`,
  在原位留一行指针。切多少由 `_common.LOG_ROTATE_KEEP = 2/3` 定 —— 切完让文件落回 ~2/3 容量,
  于是留出足够的追加余量。
  - ❌ **别只搬"最老的一条"**: 条目大小不受控(可能只有几百字符), 下次追加会立刻再触顶。
    2026-09-23 首版就是这么写的 —— 而该文件触顶时只剩 170 字符余量, 等于**每次新增都要迁移一次**,
    这正是被用户当场指出并改掉的地方。
  - ✅ `attachments/` 为什么有效: `iter_topic_files()` 是**非递归 glob**, 且 `attachments` 在
    `_common.EXCLUDED_DIRS` 里 ⇒ 那里的文件既不被当主题文件、也不计入 cap 检查。
  - `check_kb_structure.py` 报这条时会把**目标字符数**直接打出来(如 "切到 ≤ 16,000 字符"), 照它切即可。
  - ⚠ 搬运用脚本按原换行风格切分**原样**写回, 别手抄 —— 手抄会引入不可见的行尾/缩进漂移。

### 生成式索引撞 cap: 先查**渲染口径**, 别急着搬条目

- **触发**: `tasks/_index.md`(或任何生成式索引)超 cap, 直觉反应是"把老条目外迁"。
- **判别**: 先算**每个条目占多少字符**。2026-09-23 实测 `tasks/_index.md` 12,299 字符 = header 626 +
  33 条 ×**平均 350 字符/行** —— 因为索引把 `**Summary:**` **全文**打进了一行。此时索引大小由
  「摘要写得多长」决定, 而不是由「有几个档案」决定; 靠外迁条目化解的话:
  ①可动的只有已完成档案(16 个 In Progress 是活的) ②其中 15 个有外部引用, 搬走会让
  `check_doc_links.py` 变红(除非连带改写引用) ③全搬也只够一次, 下次立刻再触顶 —— **病根没动**。
- **处置**: 改**渲染口径**(摘要截断成一行, 如 `gen_tasks_index.SUMMARY_MAX = 80`), 索引随即
  12,299 → 5,710, 同样 cap 能容纳 ~90 个档案, 且**零链接破坏、零信息丢失**(全文在档案里)。
  外迁条目只当**后备**(真到几百个档案、条目数本身撑爆 cap 时才用, 且要挑无外部引用的老档案)。

### 类索引贴顶时, 新主题要落到**有余量的类**

- **触发**: 想给某个 pitfalls 类新增主题文件, 守卫却报该类 `_index.md` 超 cap(2026-09-26 实测)。
- **判别**: `web-ui/_index.md` 当时 **2,989 / 3,000**(余量 11 字符), 而新主题的一行(文件名 + 摘要 +
  触发词)**最少也要 ~130 字符** ⇒ **任何**新条目都会让它越线, `test_kb_files_respect_caps` 立刻报红;
  缩摘要 / 砍触发词也补不回来(行本身的固定开销就在那)。**类索引的余量 ≠ 主题文件的余量** ——
  后者(cap 6,000)常有空, 前者才是新条目的真正闸门。
- **处置**: ①新增主题前先量**目标类** `_index.md` 的余量(不是量要写的那个文件);
  ②不够就把主题落到**语义相近且有余量的类**(本例 `web-ui` → `docs`: 1,160 → 1,569),
  并在条目正文里用相对链接指回真正相关的那条(如 `../web-ui/columns-persist.md`), 检索链不断;
  ③"并入该类已有主题"能绕开索引膨胀, 但新坑的**触发词进不了索引** ⇒ 检索变弱, 优先选 ②。

### 追加内容前先看目标文件离 cap 还有多少余量

- **触发**: 往一个已有文件(pitfalls / 主题文档)追加一段。2026-09-24 实测: 给
  [testing/tmpdir.md](../testing/tmpdir.md) 补一条新坑, 写完才跑守卫, 报 `6,060 > 6,000 字符 (角色 pitfall)`。
- **判别**: cap 只看**文件总量**, 不区分"是谁写的那段" —— 老内容占满时, 新坑写得再对也进不去。
- **处置**: ①追加前先量余量(`len(path.read_bytes().decode("utf-8"))` 与角色 cap 之差);
  ②余量不够时**先压自己那段**, 别去删别人的判据(那些正是这个文件的价值);
  ③写完立刻跑 `commands run kb.check`(含 cap 校验), 别留到全量测试才发现。
