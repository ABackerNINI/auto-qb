# 子代理并发派遣撞宿主并发上限

> 摘要: 同一轮并发派遣多个子代理(或后台代理未收割时再派)会被宿主并发上限拒收, 失败形态是 `user concurrency limit exceeded` —— 逐个重派即恢复, 不是派遣机制坏了
> 触发: 派子代理, 并发派遣, review 分面, user concurrency limit exceeded, 后台代理, 调研代理
**Refs:** memory-bank/tasks/26-11-04-memory-bank-code-review.md

### 同一轮并发派 ≥2 个子代理(或后台代理未完成时再派)被宿主并发上限拒收

- **触发**: 一条消息里同时派多个前台子代理(如 code-review skill 分面档的 2-3 个评审代理); 或已有后台代理在跑时再派前台代理(实证: 2 个后台调研代理在跑时派前台评审代理, 撞限; 单独重派同内容立即成功)。
- **判别**: Agent 调用直接失败, 错误串含 **`user concurrency limit exceeded`**; 同样的 prompt 稍后单独再派能正常跑 —— 这条是判别关键: 失败与 prompt 内容无关, 只与同时在飞的代理数有关。
- **处置**: 不改 prompt、不缩任务, **逐个(串行)重派**失败的代理即可; 分面评审场景按面一个一个派, 前一个交回再派下一个。规划多代理工作时把「并发上限」当既定约束: 能后台跑的先派后台, 前台关键路径上的分面代理预算为串行耗时相加。
- **复发**: +2 (2026-11-04): 本会话两次撞限(调研代理 A 与评审正确性面代理), 原因: 派遣前未把「宿主并发上限」列入多代理计划的前置约束 —— 已在 code-review skill 分面执行中按逐个重派处置。
