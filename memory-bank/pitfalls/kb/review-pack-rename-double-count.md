# review.pack 评审规模含 rename 时删+增双计是设计口径,别当缺陷修

> 摘要: 行数实算单点(`review_content.py` 全部 numstat 调用)恒钉 `--no-renames`,批内大文件移动被计成删+增双份全文 —— 这是刻意取舍(开 rename 检测会打开 0 行改名假绿漏算 + 排除面被合成路径绕开 + 相似度阈值跨 clone 漂移),不是「rename 未被检测」的 bug。
> 触发: 批内有大 HTML/大文件移动(如收尾回写挪件), pack 报出远超实质改动的规模(2026-11-17 实测: 13 行实质 + 移动 1172 行 HTML → 2357 行,另一会话误判成脚本缺陷并来复验)。

**触发**: 看 pack 评审规模远超预期、且数字呈「2×N + 实质行」形状(N = 被移动文件行数);或发现 pack 清单与规模对不上。
**判别**: ① 算指纹: 总行数 − 实质行是否 = 2×某现存文件行数; ② 读 `review_content.py` 的 `_count_numstat` docstring —— `--no-renames` 删+增双计的取舍与理由(宁可多算不漏算)是原始设计注释(引入提交 0967985a),不是回归; ③ 开 rename 检测的代价面见档案 26-11-17-test-review-pack-rename-display「思考过程与决策」。
**处置**: 实算面不动(改它 = 闸门假绿方向,禁止「顺手修」)。26-11-17 起展示面已对齐: 文件清单 name-status 同钉 `--no-renames`(旧路径以 `[已删除]` 进清单/删除专用行),另有「改名对(仅提示)」行列出旧→新与相似度码 —— 规模构成在 pack 输出里当场可对账,先对账再定性。若确要降双计成本,只能动展示/分档面,且须重走实算口径论证。
