# 评审/实现子代理在可跑长命令的派遣上挂死: 纯静态+短命令纪律防免

> 摘要: 评审/实现子代理在可跑长命令的派遣上挂死: 纯静态+短命令纪律防免
> 触发: 子代理挂死, 600s 无活动, TaskStop 拒绝, SendMessage 续跑, 纯静态评审

## 本篇只回答

本会话(26-11-08 评审流程改造)派遣子代理做评审/修复时,提示词允许跑测试套件 → 子代理在一个长/挂死命令上无输出,宿主 600s 无活动即报 `Subagent was inactive for 600000ms` 整次作废;实现者也可能在变异自证等长循环里同样卡死。防免靠派遣词纪律,不靠事后重试。

### 子代理挂死: 允许跑测试/长命令的派遣会在单条命令上无输出超时,重派还会再挂

- **触发**: 派遣提示词含「可定向跑测试/验证」且不设时长上限(如 `uv run pytest ...`、变异自证循环、任何子进程可能等输入的命令);同构任务连续重派连续挂(本会话两次评审 600s 超时 + 一次实现者 33 分钟无落盘)。
- **判别**: TaskOutput 长时间 `retrieval_status: timeout` 且 output 区始终是旧报告;`Subagent was inactive for 600000ms`;实现者卡死看盘面——目标文件 mtime 十几分钟不动即挂(先 `ls -la` 对比时间再下结论)。
- **处置**: ①重派时在提示词写死防卡死纪律——纯静态审读为主、**禁止 pytest/uv/任何测试执行**(评审)、或「任何 shell 命令预期 ≤2 分钟,验证用单测方法级(`pytest 文件::类::方法 -q -x --no-cov`)」;连续 3 次失败即停(用户口径)。②实现者卡死先看盘上落盘进度定位断点,再 SendMessage 断点续跑(消息会注入其活跃回合,连卡死进程都能救活);**TaskStop 可能被状态机矛盾拒绝**(`is not running (status: running)` 连报两次),别死磕,SendMessage 注入是更可靠的止损通道。③止损前必读盘面——变异自证类工作可能处于「钉子已拆」中间态,续跑指令必须写明「盘上已完成的不要重做」。
- **守阵**: 无机检(派遣词纪律属人治)。复发时把本档处置①的纪律文本整块复制进新派遣词;**注意 code-review skill ④ 的「三件套」模板不含此纪律**(照模板派遣恰恰会再挂), 重派评审时必须在三件套之外显式附加——若要把纪律固化进 ④ 三件套, 属规则面改动另行走流程。
