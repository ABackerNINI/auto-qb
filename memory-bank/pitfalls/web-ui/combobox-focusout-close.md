# 自绘 combobox 收层: 主判据走 @focusout, 且不能同步收(label 转发回焦会闪)

> 摘要: 自绘下拉(combobox)的收层判据若只靠 window click, 「点字段 label(for= 转发激活)」这条路径会关了又开 —— 浏览器对 label 的 mousedown 先 blur 输入框、click 默认动作再把焦点转回, click 关层 + 转发 click 重开落在同一交互里, leave 过渡被打断 = 用户看到的「下拉闪烁再次出现且未失焦」。处置 = 收层主判据改 @focusout, **且必须定时合帧**(同步收层仍会被回焦打断); 开层方法先撤销挂起的收层; 字段 label 与浮层内按钮(清空 x)一律 @click.stop + **@mousedown.prevent** —— 前者挡「window 收层 → 转发的 click 重开」, 后者根除 mousedown blur(合帧窗再大也赢不了人手按住时长 80~150ms), 缺一即**稳定**(非概率)闪烁。合成零延迟点击验证不了按住时序竞态, 走查必须 `delay>=120ms`。另: 浮层限高不能只靠 CSS max-height —— 绝对定位溢出会把滚动容器的 scrollHeight 撑大(窗口"变形"), 要在开层**与过滤词变化时**量「锚点→滚动容器可见底沿」净空(只开层量 = 删字让候选涨回全量时旧限高不更新)。**净空算式只治「下方有净空但不够」; 组合框若是表单最后一项, 净空为负、`avail>0` 门恒不生效, 治法只能是给容器预留空间(padding), 不是继续调限高值**(2026-10-19 设定位置弹窗报障, 见条目 5)。**焦点纪律按「区域」设, 不按「元素」设**: 面板内的**非交互区**(`.pop-head` 标题+计数、`.pop-empty` 空态文案)同样是焦点杀手 —— mousedown 的默认动作把焦点从输入框抢走, `@focusout` 照常触发 ⇒ 面板「点一下就消失」; 修饰符必须挂在**面板根**上(一处覆盖全部非交互子元素, 新增展示节点自动免疫), 逐个给子元素打补丁 = 新增一处即静默复发(2026-10-29 六修, 见条目 6)。**收层兜底(window click)的另一半是「落点归属」**: 按下与抬起落在不同元素时 click 的 target 是两者的**公共祖先**, 组件根不挂 `@click.stop` 就冒泡到 window 名单 = 面板点一下就关 —— 无焦点时最易踩(面板在按住期间才挂载), 皮肤差异也由此而来(2026-10-29 七修, 见条目 7)。

## 条目

- **触发**: 给"聚焦即展开"的自绘下拉补"点外即收", 或报障「触发下拉后点窗口其它位置, 下拉闪烁再次出现、输入框未失焦」「选项过长把窗口撑变形」(2026-10-03 用户报, 添加种子窗口三下拉: 保存路径/分类/标签)。
- **判别**: ①收层只有 window click(lifecycle.js)一路时, 点字段 label(`for=` 指向下拉输入框)的完整事件链是 mousedown → focusout → **click(label) → window click 收层 → focusin(~2ms 后, label 默认动作转发) → 转发 click 到输入框 → @focus/@click 重开** —— 中间"收层"与"重开"是否被 Vue 批处理取决于浏览器把 label 激活行为派发成同一任务还是相邻任务, 时序依赖 ⇒ **概率性闪烁**, 真机偶发而合成探针难复现; ②几何侧: `.pop-menu { max-height: 330px; overflow-y: auto }` 只保证菜单自身可滚 —— 菜单锚在输入行下方(`.add-pop { top: calc(100% + 4px) }`), 输入行贴近窗口底沿时整条菜单**伸出窗口外**(滚动条跟着出窗), 且绝对定位溢出会把 `.add-dialog-body`(overflow-y:auto)的 scrollHeight 撑大(实测 449→591, 窗口内容"变形")。
- **处置**: ①三输入框挂 `@focusout="addPopBlurClose"`(add_torrent.js 单点), 内部 `setTimeout(40ms)` 收三个浮层; 三个开层方法(openAddCatMenu/openAddTagMenu/openAddPathPop)**先 `_addPopBlurCancel()`** —— 焦点真离开(点空白/别的字段/Tab)下一拍收层, 焦点回来(label 转发/重新点入)则撤销, 菜单全程不闪; window click 降级为兜底不拆。守阵: `test_webui_static_dom_panel.py::test_frontend_add_combo_blur_close_and_fit`(focusout 挂点/合帧守卫/开层撤销/watcher 限高五组断言)。②限高走 `watch` 单点(开层入口四处: 开层方法/输入 @input 直开/键盘 _comboKeydown/候选异步到位, 直挂方法必漏), `_fitAddPop` 在 $nextTick 量 `body.getBoundingClientRect().bottom - row.getBoundingClientRect().bottom` 的净空扣掉面板头, 把可滚内层(`.add-pop-list` 或菜单自身)`style.maxHeight` 限进去(**限前先复位旧值**), 净空下限 120px。验证: Playwright 记录器逐帧抓 transitionrun + 三皮肤 12 项走查(点空白收层/label 点击零过渡重放/40 项菜单不出窗且 body 零新增滚动)。
- **触发**(2026-10-03 第二轮): 报障「点『分类(可空)』这个 label 的位置**稳定**复现下拉闪烁再现」「保存路径/标签/分类没有 x 清除」「选中分类后逐字删除会把窗口撑变形」。前两条同源, 且**不是**上面那条概率路径 —— 点 label 时输入框**已经聚焦**(不再 blur/回焦, 所以 @focusout 完全不参与), 真正的链条是「label 的 click 冒泡到 window ⇒ 收层名单把菜单关掉 ⇒ label 默认动作把 click 转发给 for= 的输入框 ⇒ @click/@focus 又开」= 关了又开, 且每次都这样 ⇒ **稳定**复现(与上一轮"概率发生"的区别就在这儿)。
- **判别与处置**(第二轮): ①**label 挂 `@click.stop`**(四个 combo: 添加窗口三个 + meta 对话框分类)—— 挡掉 window 收层, 只让转发给输入框的那一次 click 生效。②浮层内的按钮(新增的清空 x)同样要 `@click.stop`, 否则点 x 会把下拉一起收了(真机走查实测: 清空成功但菜单消失); 另需 `@mousedown.prevent` 保焦点(不拦则按钮抢焦点 → 输入框失焦走 focusout 收层)。③**过滤词变化必须重限高**: 开层那一刻的限高是按当时的候选量算的, 删字让候选从 1 条涨回全量时菜单没关过(开层 watcher 不触发)⇒ 旧限高不更新 = 撑变形; 三个输入值各挂 watcher(只在浮层开着时重限), meta 侧 `metaCatInput`/`metaCategories` 同族。④meta 分类下拉原本既没 @focusout 也没进 window click 名单 —— 点对话框别处下拉悬着不收, 与三下拉同族一并补齐。守阵: `test_webui_static_dom_panel.py::test_frontend_add_combo_label_clear_mask_and_refit`(label/清空钮/遮罩臂位/watcher 重限/meta 收层/CSS 成对六组断言)。验证: 三皮肤真浏览器 39/39(含"点 label 零 transitionrun"、x 清完后菜单仍在且焦点未丢、拖选抬手不关窗而点空白仍关窗、40 项候选逐字删除 body 滚动量零新增)。
- **复发: 1**(2026-10-04 第三轮, 用户报「上轮修复未成功, 点字段 label 稳定复现下拉闪烁」): 第二轮的两个判断是错的 —— ①"点 label 时输入框已聚焦不再 blur"不成立: label 的 **mousedown** 默认动作就会把已聚焦的输入框 blur 掉(探针实测 focusout related=null), 只是回焦要等 click 阶段的 label 默认动作; ②"focusout → ~2ms 后 focusin"只对零延迟合成点击成立, 真人按下到抬起隔 **80~150ms** —— 40ms 合帧定时器在**按住期间**先触发收层, 松手回焦再重开 = 每次必闪。第二轮走查 39/39 全绿的原因: Playwright 默认点击 down/up 只隔 ~2ms, 撞不上 40ms 窗 ⇒ **合成零延迟点击验证不了"按住时长敏感"的时序竞态**。处置: 四个字段 label 一律加 `@mousedown.prevent`(mousedown 不产生 blur ⇒ 收层定时器不武装, 竞态从根上消失; @click.stop 保留挡 window 收层, 两修饰符缺一即回归; mousedown.prevent 不破坏 label 的 click 转发 —— 关闭态点 label 仍聚焦+开菜单, 三皮肤实测)。守阵已补 `@mousedown.prevent` 断言。为什么没命中: 第二轮按"合成点击 2ms 回焦"的假象定了 40ms 合帧窗, 且走查用的默认零延迟点击恰好测不出人手时序。**教训: 涉焦点/按压时序的走查, click 必须 delay>=120ms 模拟人手; 对"浏览器先做什么后做什么"的断言必须先用事件埋点探针实测, 不许用想当然的事件序当设计依据。**
- **复发: 2**(2026-10-04 第四轮, 用户报 594e247f 三修后真机**仍**稳定复现「点 label 下拉闪烁」): 本轮探针把两件事拆开 —— ①探针自校验: 把四个 label 的 `@mousedown.prevent` 临时摘掉(回到第二轮状态), delay=150 稳定复现完整闪烁链(focusout@+0.2ms → 收层@+65ms → 回焦重开), 证明探针灵敏度, "当前代码干净"的阴性结果可信; ②当前代码三皮肤 × 四场景 24/24 零翻转 —— **三修本身有效, 用户侧仍闪 = 浏览器跑的还是旧模板**。为什么"修好了但没生效": SPA 的模板(fetch 注入)与 JS 都以**页面加载时刻**为准, 页签长开不刷新时服务端更新永远到不了 —— 源码修好 ≠ 用户侧生效, 修复验证必须区分这两层。处置双管: ①交付侧 = 用户整页强刷(Ctrl+F5)后再走查; ②代码侧 = 收层改 **JS 单点自洽**, 不再依赖模板与 JS 同代到达 —— `addPopBlurClose`/`metaCatBlurClose` 的 40ms 定时器收层前问 `_popBlurShouldHold(ids)`(add_torrent.js 单点, mounted 挂 mousedown capture 记录器): 焦点已回本族输入框 → 不收(转发 click 已落地); 本族 label 的 mousedown 落在 350ms 内且焦点不在输入框上 → 不收(转发 click 仍在途, 等松手回焦); 350ms 上界防旧记录误挡后续无 mousedown 的失焦(如 Tab)。模板修饰符在 = 纯 no-op(mousedown 已被 prevent, 定时器不武装); 缺位 = 独立根除闪烁 —— 任何模板/JS 代际混合(旧页签残留模板+新 JS、未来模板回归、个别浏览器 label-blur 不可防)都安全。守阵: combo 守阵第 7 组(记录器对称挂撤 + 守卫双判据 + 350ms 上界 + add/meta 两侧接线)。**教训: ①报"修复无效"时先做探针自校验(把修复摘掉看探针红不红), 再谈根因; ②SPA 行为修复尽量做到 JS 单点自洽, 依赖"模板修饰符 + JS 行为"成对到达的修法, 交付链上任何一环掉队都等于没修; ③让用户复测前必须先整页强刷, 并把这条写进修复的验收步骤。**
- **触发**(2026-10-19 第五轮, 用户报「设定位置弹窗太小, 新保存位置下拉显示不全, 需要滚动」): 设定位置对话框(move-dialog)的保存路径组合框复用了添加种子的 combobox 视觉与限高口径, 但**它是本表单的最后一项** —— 几何前提与添加窗口(路径字段在表单中段, 下方还有分类/标签字段)相反。
- **判别**: ①下拉朝下开(`.add-pop { top: calc(100% + 4px) }`), 输入行贴 `.add-dialog-body`(overflow-y:auto 滚动容器)底沿 ⇒ 整条菜单必伸出 body: 被 body 裁掉, 且绝对定位溢出把 body scrollHeight 撑大(实测 123→383 = 弹窗体内多出一条滚动条, 用户必须滚弹窗才能用下半截下拉); ②`_fitAddPop` 的净空算式量「输入行 → body 可见底沿」, 行贴底沿时净空为**负**, `avail > 0` 门恒不生效 ⇒ 前四轮修的限高兜底对这种形态完全无力; ③真浏览器实测(1440x900, 300 候选): 对话框仅 560x243, 下拉只露出约 2 项, 第 3 项起被 `.modal-actions` 与遮罩盖住(elementFromPoint 逐项落空), 且路径项 nowrap+ellipsis 在 514px 行宽下截得厉害。
- **处置**: 治法是**给容器预留空间**, 不是继续调限高值 —— ①`.modal.move-dialog` 宽度 `--modal-w-form`(560) → `--modal-w-add`(860, 与添加种子同宽, 路径项多显示); ②模板根元素挂 `:class="{ 'pop-open': movePathMenu }"`, 三皮肤 CSS 成对加 `.modal.move-dialog.pop-open .add-dialog-body { padding-bottom: 272px }`(面板头 ~46 + 列表 210 + 顶距 4 + 余量 12)——预留后净空 ≈216px > 列表 210, 限高算式自然不再触发, 下拉完整落在对话框内, 弹窗体零新增滚动; 收层(Esc/选中/失焦)时 padding 回落, 对话框缩回。矮视口 modal 自身滚动时 body 收缩、净空变小, 仍由限高兜底(与添加种子同口径)。模板只加类名绑定, 几何数字全在 CSS 单点。
- **守阵**: 静态 `test_frontend_move_dialog_combobox_wiring` 增几何断言(模板 pop-open 绑定 + 三皮肤成对的 860 宽档与 272px 预留规则); e2e 新增 `move-dialog-fit.spec.mjs`(双皮肤 @fast): 自动开层态(开对话框即聚焦输入框展开下拉, openMoveDialog → @focus 开层)量下拉底缘不超 body 客户区底沿、body/modal 零新增滚动、列表未被限高截断、前 6 项 elementFromPoint 命中自身; Esc 收层态与再点重开态各一轮。红绿双验: 临时回退任皮肤 CSS, 静态与 e2e 两侧均红。
- **教训**: ①「限高」只解决「下方有净空但不够」——组合框是表单**最后一项**时净空为负, `avail>0` 门让算式恒不生效, 此时任何限高值都无意义, 必须换解法(预留空间); 复用时不能只搬视觉与 JS 口径, 要复核**字段在表单中的位置**这个几何前提。②居中弹窗量几何必须等入场动画跑完再量: `.modal` 的 modal-in 带 `scale(.985)`, 动画进行中量宽度会少 4px(实测 856 vs 稳态 860), e2e 用 `getAnimations({subtree:true})` 的 finished 等待。③量 containment(下拉是否在容器内)不量位移 —— 居中弹窗增高时上下对半扩, 量「被推下多少」只有真实增量一半(pitfalls/web-ui/dialog-measure)。

- **触发**(2026-10-29 第六轮, 用户「缺陷一并修复」: 点面板头「选择保存位置 N」, 面板就收了): combobox 面板里除候选行/预置行之外还有**非交互区** —— `.pop-head`(标题+计数)与 `.pop-empty`(空态文案)。它们点了什么都不该发生, 但同样吃 mousedown 默认动作的 blur。
- **判别**: 前五轮修的都是面板内**可点**元素(label / 清空 x / 候选行)的焦点纪律, 非交互区没人管 —— mousedown 落在 `.pop-head` 上时焦点从输入框掉到 body, `@focusout` 照常触发, 40ms 合帧后 `_popBlurShouldHold` 判「焦点不在本族输入框、也没有本族 label 转发在途」⇒ 收层。它在事件链上与「点窗口空白」完全同形, 所以只能在模板层拦, JS 守卫分不出来。面板头紧贴输入行下沿、候选行正上方, 误触概率极高(与三修「面板被顶到光标底下」是同一片热区)。
- **处置**: 焦点纪律挂**面板根** —— `shared/tpl/combo-input.html` 的 `.pop-menu.add-pop` 加 `@mousedown.prevent`(与 `@click.stop` 并列), 一处覆盖现有全部非交互子元素, 将来往面板里加展示性节点也自动免疫; 5 个调用点(添加种子三下拉 / meta 分类 / 设定位置)零改动。与候选行自带的 `@mousedown.prevent` 不冲突(同一事件先到目标行再到根, 重复 prevent 无害), 行上那份保留。不影响滚轮与滚动条(滚动是合成器/原生滚动条行为, 不经 mousedown 默认动作)。
- **守阵**: 静态 `test_webui_static_dom_panel.py::test_frontend_add_combo_label_clear_mask_and_refit` 第 6 节 —— 面板根必须同时带 `@mousedown.prevent`(焦点纪律)与 `@click.stop`(挡 window click 收层); e2e **两条配对**: `move-dialog-fit.spec.mjs`「点面板头/空态不收起」(面板仍在 + 输入框未改写 + **随后点候选仍能回填并收起**, 防「修成冻住」), `add-options-recent-order.spec.mjs` 空态段(分类按输入过滤到 0 候选, 点 `.pop-empty` 不许收)。红验三段: ①摘掉根级修饰符 ⇒ 静态 1 红 + e2e 双皮肤红; ②把修复收窄成「只给 `.pop-head` 挂 prevent」⇒ **头点击仍绿、空态双皮肤红**; ③恢复根级 ⇒ 全绿。
- **教训**: ①「面板内点击」不是一类**元素**, 是一块**区域** —— 焦点纪律要按区域(根)设; 按元素逐个设, 就会随新增元素静默复发(与 issue 26-10-20-2230 把五处骨架收敛成单点的同一条道理)。②只覆盖一个可点位置的断言拦不住半截修法: 区域级不变量至少要两条落在**不同位置**(头 + 空态)的断言配对, 红验也要按「收窄版」跑一遍才算验过。③非交互区在真人手里不是「点了没事」, 而是「点了会消失」 —— 凡是紧贴高频操作热区(输入行下沿)的区域, 任何「点了会消失」的行为都会被放大成「面板自己弹回」。

- **触发**(2026-10-29 第七轮, 排查「无焦点点下拉即弹回」时复现到的独立缺陷): 按下在输入框、抬起落在**别处**(行内留白 / 面板 / 整行)时, 面板"点一下就关"。
- **判别**: 浏览器把 `click` 的 target 定成 mousedown 与 mouseup 两个落点的**公共祖先** —— 按在 `input`、抬到行内留白或面板里, click 的 target 就是 `.add-input-row`, 那一层没有 `@click.stop`, 事件照常冒泡到 lifecycle 的 window 收层名单 ⇒ `movePathMenu = false`。实测(prism, 无焦点): 抬到输入框下 6px → click target `div.add-input-row` → 面板关; 抬到候选行 → 同样关; 抬到上方说明文案 → target `div.add-dialog-body` → 关(这一路**应当**关, 属"点组件外")。无焦点时最易踩的原因: 面板是在**按住期间**才挂载的(`@focus` → 开层), DOM 在按下与抬起之间变化, 抬起落点被改写的机会就在那一段; 有焦点时面板早已在, 落点不变。**皮肤差异的由来**: 两皮肤输入行屏位差 2px(prism 413–445 / atlas 411–443), 而面板入场 `drop-in` 从 `translateY(-4px)` 起、面板顶 = 输入框底 +4 ⇒ 入场头 ~120ms 面板顶正好压在输入框下沿那 1–2px 上, 落点是否被改写就取决于这 2px 与点击高度的组合。
- **处置**: 组件**根**(`shared/tpl/combo-input.html` 的 `.add-input-row`)挂 `@click.stop` —— 落点在本组合框内部的一切点击(输入框 / 行内留白 / 面板 / 被改写成公共祖先的点击)都不再冒泡到 window 兜底; 收层主判据仍是 `@focusout`(点窗口别处照常收), window click 退回"真点到组件外"的兜底。**只许挂组件根**: 挂到对话框层会把"点对话框别处收层"一起废掉。
- **守阵**: 静态 `test_frontend_add_combo_label_clear_mask_and_refit` 第 7 节(输入行根必须带 `@click.stop`, 并注明只许挂组件根); e2e `move-dialog-fit.spec.mjs`「按下与抬起落在不同元素 · 面板不收起」—— 变体 A(抬到行内留白)/ 变体 B(抬到候选行)面板都必须还在且不回填, 末尾**反向守门**: 真点到组件外(上方说明文案)仍必须收层。红验: 摘掉根级 `@click.stop` ⇒ 静态 1 红 + e2e 双皮肤红(element not found); 恢复 ⇒ 全绿。
- **教训**: ①"点空白收层"这条兜底只该管**组件外**的点击; 组件内部的任何落点都归组件自己判 —— 用 `@click.stop` 划清边界, 比在 window 处理器里加特判稳。②`click` 的 target 不是"用户点的那个元素", 是 down/up 的公共祖先 —— 凡是用 window click 做兜底的地方都要想到这一条(拖选、按住期间 DOM 变化都会改写落点)。③"无焦点才复现"这类条件, 往往指向**按住期间 DOM 变化**(开层/关层/高度过渡), 而不是焦点本身。
