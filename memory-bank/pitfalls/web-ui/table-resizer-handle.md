# 列宽拖拽把手的可见线: 非整数缩放下的逐列粗细差 + 压住右对齐列文字 + 首列 hover 被盖

> 摘要: 报「各表 / 各列的列宽拖拽把手粗细不一致」(如种子页『分类』明显更细)时, 根因**不在某一列的代码** —— 三皮肤(prism/atlas/console)的 `.h-cell .resizer` 规则逐字一致, 粗细差来自**非整数缩放下的亚像素相位**: 可见线只有 2px, 而列宽由默认模板 `minmax(Npx, X.Xfr)` 分配 ⇒ 小数列宽让每列边界落在不同的子像素相位; 125% 缩放下 2px 线逐列渲染出的实芯宽度不同(实测同表内 ≈1.5 vs ≈2.3 设备像素), 哪几列细由累计列偏移(拖过的列宽 / 隐藏过的列)在**运行时**决定。实测 2px 基线 / 4px+opacity.55 / 3px 实色 / 铺满 10px 命中区 四种「细线当主视觉」方案**全都躲不开** ⇒ 根治 = 不让细线承担主视觉, 改用成熟产品(Excel / Notion / AG Grid)口径的**整列 hover 底色**。同族另两坑: 把手可见线压在列边界上会盖住右对齐列表头文字(2026-10-06 去掉 `padding-right` 后文字贴右缘, 11 个数字列实测重叠 −1px); 首列 `.h-cell:first-child` 的不透明吸左背景(特异性 0,3,1)压过 `.h-cell:hover`(0,2,1)使其永不亮。
> 等级: L0
> 触发: 把手粗细不一致, 有的细有的粗, 列宽拖拽把手, resizer, h-cell, hover 不高亮, 某些列 hover 没反应, 首列 hover, 表头悬停无底色, 把手压住文字, 把手离文字太近, 表头文字被盖, 右对齐列, 125% 缩放, 缩放后不一致, 亚像素, 整列高亮, --tbl-gap

**Refs:** memory-bank/tasks/26-10-16-webui-table-resizer-handle.md

## 条目

### 细线在非整数缩放下逐列落不同亚像素相位 ⇒ 粗细肉眼不一; 根治靠「面」不靠「线」

- **触发**: 收到「列宽拖拽把手有的粗有的细」「某列表头把手明显更细」; 或准备给表头把手调线宽 / 加透明度 / 换方案。
- **判别**: ①**先量再改** —— 隐藏表头文字(`.h-cell .h-label, .h-cell .arrow { visibility: hidden }`)后逐列截元素图取像素剖面(每设备像素列的着墨强度), 看实芯宽度(强度 > 阈值的连续列数)是否逐列一致: 100% 缩放所有列恒等(如 `409,409`), 125% 出现两档(如 `163,362,409,103` vs `307,409,265,55`)即命中。
  ②**别去源码找「某一列写死了细线」** —— 三皮肤 `.h-cell .resizer` 落点相同(命中区 10px / `::after` 2px); 逐列类名(`hc-*`)grep 零命中即证明不是列级差异。
  ③**相位 = 累计列偏移 × DPR 的小数部分** —— 同一列在不同视口宽 / 已拖列宽 / 隐藏列下相位会变, 所以「细的是哪几列」因人而异, 不是某一列的问题。
- **处置**: **让「面」承担主视觉, 细线退回纯位置指示** —— `.h-cell:hover { background: var(--surface-2) }`(与行 hover 同变量, 视觉语言一致); 2px 实色 accent 线保持原样。色块宽几十 px, 亚像素抖动占比 <1%, 粗细观感天然一致 —— 即 Excel / Notion / AG Grid 的列头 hover 同款语言。
  ⚠ **不要**指望「加粗 / 加透明度 / 铺满命中区」根治: 实测 2px 基线、4px+`opacity:.55`、3px 实色、10px 淡色底带**四种全部分两档**(3px 实色仍 `307,409,409,334` vs `155,359,409,409,181`)—— 相位由累计列偏移决定, 不随线宽 / 透明度消失。
  ⚠ 也别走 JS 逐列把把手吸附到整设备像素 —— 成本高、列宽一变又漂、易回归。
- **复发**: 0

### 把手可见线压在列边界上 ⇒ 盖住右对齐列的表头文字

- **触发**: 收到「把手离文字太近 / 盖住文字」; 或改 `.h-cell` 的 `padding-right` / 把手 `right` / `--tbl-gap`。
- **判别**: 量把手可见线左缘与表头**内容右缘**(`.h-label` / `.arrow` 的 `getBoundingClientRect().right`)之差。2026-10-06 起 `.h-cell` 去掉了 `padding-right`(彻底方案, 见 [header-cell-gutter.md](header-cell-gutter.md)), 右对齐列文字紧贴格子右缘, 而线若落列边界(R)上 ⇒ 差为 **−1px**(实测 11 个右对齐数字列全部重叠: 大小/上传/已上传/已下载…)。
- **处置**: **热区仍跨边界(抓握手感不变), 只把可见线移进 grid 列间间隙(gap)中央** —— `right: calc(-1 * var(--tbl-gap, 10px) / 2 - 3px)` + `::after { left: 6px }` ⇒ 线恒落 gap 正中, 距两侧文字各 4px。
  ⚠ **必须用 `calc` 自适应 `--tbl-gap`, 别写死 `-8px`**: 抽屉 dt11 内容表把 `--tbl-gap` 覆盖成 8px, 写死会在那里偏心。
- **复发**: 0

### 首列 hover 不亮 = `.h-cell:first-child` 的不透明背景特异性压过 `:hover`

- **触发**: 收到「首列(名称列)hover 没反应 / 不高亮」; 或给表头加整列 hover 底色。
- **判别**: 首列有 `.group-head > .h-cell:first-child { background: var(--bg) }`(特异性 0,3,1; 为吸左遮住滑入的相邻列而**必须不透明**), 它压过 `.h-cell:hover`(0,2,1) ⇒ 首列永不亮, 其它列正常 —— 极易误判成「hover 规则没写对」。该首列规则在**三皮肤各自的 `views.css`**, **不在** `components.css`。
- **处置**: **别动 `background-color`**(保住吸左遮罩), 用一层 `background-image` 叠高亮 —— `.group-head > .h-cell:first-child:hover { background-image: linear-gradient(var(--surface-2), var(--surface-2)); }`(多重背景里 image 层天然叠在 color 层之上)。
  ⚠ **`background: var(--surface-2), var(--bg)` 是非法语法**: 多层简写里**只有最外层能带颜色**, 非最外层带颜色会让**整条声明被浏览器丢弃**(静默失效、无报错)。要叠一层色请用 `background-image: linear-gradient(<color>,<color>)`, 不是 `background` 简写的多层。
  ⚠ 三皮肤同步: 改完逐一 grep 三份 `.h-cell:hover` 与首列 `:first-child:hover` 规则都在(曾漏掉 console 的整列高亮, 症状 = 该皮肤**全列** hover 都不亮)。
- **复发**: 0
