# 两套 UI 的性能差异 / 毛玻璃

> 摘要: 「星图卡、棱镜不卡」这类单边性能问题的定位路径 —— 差异只在 CSS(JS 是共享层), 且两套 CSS 里唯一有实质差异的昂贵属性是 backdrop-filter; 嵌套毛玻璃的成本与摘法。
> 触发: 卡顿, 掉帧, 不跟手, 两套 UI 性能差, 一边卡一边不卡, 毛玻璃, backdrop-filter, 弹层卡, 改 CSS 后变慢, 星图卡

### 先判「差异在哪一层」, 别去共享 JS 里找

- **触发**: 用户报「A 界面卡, B 界面不卡」。
- **判别**: 本项目 `shared/app.js` + 15 个域片段是**唯一逻辑层**(两套 UI 共用), `atlas/` 与 `prism/` 只放模板与主题 CSS ⇒
  **逻辑层的性能问题必然两套同时复现**。既然只有一套卡, 差异**一定**在 CSS 或模板 —— 去 JS 里找等于白找
  (2026-09-24 实测: 两套 index.html 的差异只有 328 行 diff, 且几乎全是注释与棱镜专属的主题切换器)。
- **处置**: **按属性统计两套 CSS**(backdrop-filter / box-shadow / gradient / animation / transition / will-change / filter),
  数量对不上的那个就是嫌疑。实测两套在 box-shadow(44:44)、transition(59:58)、animation(22:19) 上全对齐,
  只有 backdrop-filter **6:2**(各含 1 行注释)—— 一眼定位。

### 嵌套 backdrop-filter 才是真的贵, 单层不是

- **触发**: 全屏遮罩 / 吸顶条上加了 `backdrop-filter`。
- **判别**: 一块毛玻璃本身不贵; 贵在**它的 backdrop 里还有另一块毛玻璃**。星图的形态是
  `.modal-mask`(全屏 fixed + blur(3px))铺开时, 底下正压着 `.topbar` blur(12px) 与 `.status-strip` blur(10px),
  浏览器每帧要回读已合成的内容再重复模糊整个视口 —— 弹层内 `hist-draw` 描边动画还在主线程逐帧重绘, 两者叠成肉眼可见的卡顿。
  棱镜 `.modal-mask` 从没加过 backdrop-filter ⇒ **无嵌套 ⇒ 无症状**(这正是"一边卡一边不卡"的答案)。
- **处置**: 摘掉遮罩与吸顶/吸底条上的 blur; **底色改不透明**(半透明底靠模糊才有意义, 摘掉后继续半透明会让滚动内容从条下透出来,
  可读性下降)。棱镜 `--glass` 早就是不透明实色, 星图照此对齐即可, 观感差异 ≤ 2/255 通道。
  遮罩摘掉模糊后可**加深一档**(星图 .62 → .72)维持"底层内容退到后面"。
- ⚠ **只留一块**: 抽屉遮罩 `.drawer-mask` 的 blur(2px) 保留 —— 顶栏/状态条摘掉后它已是唯一毛玻璃层,
  且棱镜侧同款实测无卡顿; 单边改它会破坏"两套 UI 必须成对改"的纪律。

### 静态守阵比"肉眼走查"可靠, 也比真浏览器省钱

- **触发**: 修完想留一道防线。
- **判别**: 「两边都能跑、一边更卡」这类差异**不报错、不红测**, headless Chromium 也复现不出来
  (实测 headless 下修复前后"点击 → 弹层可见"都在 6~18ms, longtask 都是 0 —— 软件渲染拿不到真实 GPU 合成开销)。
  ⇒ **性能证据只能是结构性的**(两套 UI 达成 parity)+ 代码层面的, **不要编实测耗时差**。
- **处置**: 用**计数 + 位置**两条断言兜底(`tests/test_web.py::_scan_backdrop_filter`):
  ①五类元素(modal-mask / topbar / status-strip / statusbar / ce-actions)一律不许出现 backdrop-filter;
  ②两套 CSS 各自声明数必须相等(shared/* 不计, 它两边同担)—— 防"只在星图侧加回来"。
  ❗扫描前必须 `re.sub(r"/\*.*?\*/", "", text, flags=re.S)` 剥注释 —— 否则文件里解释这段历史的注释会被当成真实声明**误报**。
  已红验: 把 blur(10px) 加回 `.status-strip` ⇒ 两条断言同时红。
