# 列表行可见带: 「几何在视口内」≠「看得见」(上下各压一层 chrome)

> 摘要: 键盘光标滚动跟随把「目标行几何在视口内」当成「看得见」, 但列表的上下边各压着一层随正文滚动的 chrome —— 顶部是吸在顶栏下缘的吸顶列头 `.group-head`(sticky, top = `--head-h - 1px`), 底部是固定状态栏 `.statusbar`(fixed, 高 `--statusbar-h`), 面板开着时底部还多一个停靠面板。只拿顶栏高 `_headH` 当上界、`window.innerHeight` 当下界算落点, 光标行会停在 chrome 背后: 用 `Home`/`End`(或一路 ↑↓)把光标移到**首个 / 末个种子**时"只显示一半"(2026-10-09 用户报障)。**同族的第二面是"一次移动几行"**: PageUp/PageDown 按整窗高算一屏, 面板一开可见带只剩一半 ⇒ 每翻一屏**跳过一半行**。**同族的第三面是"坐标系"**: 无光标回落(`_kbViewportRow`)的渲染行扫描把**文档坐标** `vTop/vBot`(= `scrollY + 上界`)与**视口坐标** `getBoundingClientRect()` 同框比较, 仅 `scrollY=0` 成立, 滚过一屏后全判"出视口" ⇒ 退化成跳极值行(↓ 回顶 / ↑ 落底)。处置 = 上下各收一个单点 `_kbViewTop()` / `_kbViewBottom()`(只出**视口坐标**), 所有"这行看得见吗 / 这一屏有几行"的判定只走它们, 前缀和那一支按需自行加回 `scrollY`。
> 触发: 键盘移到第一个种子只显示一半, 最后一个种子只显示一半, 翻页跳行, 翻一屏跳过行, PageDown 少看几行, 无光标回落, 跳极值行, 落回列表顶, 落到列表底, 追剧页键盘, 光标行被列头盖住, 光标行被状态栏盖住, 看不见当前行, 滚动跟随落点, 可见带, 一屏行数, 吸顶列头, group-head, statusbar, _headH, innerHeight, _winViewH, _kbViewportRow, 文档坐标, 视口坐标, scrollY, 首行不可见, 末行不可见, Home, End, PageUp, PageDown, 滚动跟随算错
**Refs:** memory-bank/tasks/26-10-09-webui-kbd-scroll-band.md

## 条目

### 键盘滚动跟随: 上界漏吸顶列头 / 下界漏固定状态栏 (2026-10-09 用户报障, 已修)

- **触发**: 用户报「WEBUI 键盘移动光标到第一个种子时只显示一半, 最后一个种子同理」; 或任何改「元素是否在视口内」判定的改动。本仓库已有**同族前案**: 停靠面板吸底那次(`pitfalls/web-ui/dock-panel.md`)—— 可见下界一度只认 `window.innerHeight`, 忘了面板顶缘。本条是它的两个**未收编的兄弟**: 上界与状态栏。
- **判别**: 症状是**对称的一半**且只在键盘路径出现 —— 鼠标滚到列表顶/底, 首末行都是完整的; 只有键盘把光标移到极值时少半行。真机三步定位(1440x900 桩 300 种子, `--torrents 300`):
  ① 量三层 chrome 的矩形: 顶栏 `.sticky-head`(95px) / 吸顶列头 `.group-head`(32px, 滚动后 top=94 → bottom=126) / 状态栏 `.statusbar`(top=866, 高 34);
  ② 按 `Home` 后量光标行: 修复前 `top=103` < 列头 bottom=126 → **被列头盖 23px / 行高 71**(矮行时过半); 按 `End` 后量: `bottom=892` > 状态栏 top=866 → **被状态栏盖 26px / 行高 50**; 双皮肤同病(atlas 遮 28 / 16px);
  ③ 根因确认 = 落点算式把「在视口内」当可见: 上界 `_headH + 4`(顶栏高, 不含吸在它下缘的列头), 下界 `window.innerHeight`(不含固定状态栏)。**别被"内容区留了底部内边距"骗过** —— `calc(28px + var(--statusbar-h))` 那条内边距只在**滚到文档底**时把末行托到状态栏之上; 滚动跟随的落点是「视口底 - 8px」, 文档余量足够滚到那里, 于是末行安安静静停在状态栏背后。
- **处置**: 上下各一个单点(与仓库既有「可见性下界收单点」纪律同形), 消费点全部改走它们, 单点外零算式:
  ① 上界 `shortcuts.js::_kbViewTop()` = `_headH` + 吸顶列头高(读 `.group-head` 的 `getBoundingClientRect().height`, **不用当前 rect.bottom** —— 吸顶前后 rect 在两态间跳, 只有高度恒定; 列头不在 DOM(成员明细 `.detail-head` 是 `position: relative`)或计算样式非 sticky 时回落纯顶栏高);
  ② 下界 `_kbViewBottom()` 开头补状态栏: `.statusbar` 实测 `position: fixed` 且高 > 0 时取 `min(bot, 状态栏顶缘)`, 再走原有的停靠面板让位(两者取更紧者 —— 面板本就吸在状态栏之上, 面板开着时它更紧);
  ③ 消费点三处: `_kbScrollRowIntoView` 的**渲染行 rect 路径**与**窗口化前缀和路径**、无光标回落 `_kbViewportRow`。渲染行那个 `scrollIntoView` 禁令照旧(见 `hover-keynav-fight`)。
- **守阵**: `tests/test_web_shortcuts.py::test_kb_view_band_single_points`(静态: 两个单点在且被三处消费、上界不得再裸写 `_headH`/下界不得裸用 `innerHeight`)+ `e2e/kbd-scroll-band.spec.mjs`(真浏览器 @fast, 双皮肤: `End` 落末行不被状态栏盖 / `Home` 落首行不被列头盖, 且断言光标确实落在极值行 —— 否则"没被遮"可能只是光标没走到极值, 断言退化成恒真)。红验: 把 `shortcuts.js` 临时退回 HEAD 版, 新 e2e 双皮肤双双转红(已还原)。
- **家族关系**: 本坑与 `dock-panel.md`(下界漏面板)、`hover-keynav-fight.md`(跟随禁用 scrollIntoView)是同一族 —— **凡"这个元素看得见吗"都要问"它上面/下面压着什么"**。新增消费点时先 grep `_kbViewTop|_kbViewBottom`, 别再手写边界算式。
- **复发**: 0

### 同族第二处: 翻页的「一屏」不是整窗高 (2026-10-09 第二轮, 用户指令「修复 _kbMovePage 的问题」, 已修)

- **触发**: 用户翻页(PageUp/PageDown)发现"有行没看见就过去了"; 或任何用"视口高 / 行高"估算"一屏有几行"的写法。上面那条收的是**单行落点**, 这条收的是**一次移动几行** —— 同一个"可见带"概念的另一面。
- **判别**: 症状是**跳行**(屏幕上从未出现过的行被跨过), 与上一条的"半行被遮"不同形。真机一眼看出(桩 300 种子, 1440x900): 数屏内**实际可见行数**(矩形与 `_kbViewTop`~`_kbViewBottom` 相交的行数), 再量按一次 PageDown 光标前进几行(行号差)。修复前实测: 面板关 可见带 739px / 屏内 10~11 行 / **前进 12 行**(每屏跳 1); **面板开 可见带只剩 353px / 屏内 6 行 / 仍前进 12 行 ⇒ 每屏跳 6 行**。根因 = `per = floor(window.innerHeight / 行高)`, 而 `innerHeight` 里有一大半被顶栏、吸顶列头、状态栏、停靠面板吃掉 —— **面板一开就吃掉近一半, 越界量也翻几倍**。
- **处置**: 一屏 = **可见带 ÷ 行高**(`floor((_kbViewBottom() - _kbViewTop()) / est)`, 下限 1), `est` 沿用行窗口化那条既有链(`_rowH` 实测均值 → `ROW_WIN_EST_H` → 44)。判据写成**不跳行不变式**: 前进量 ≤ 屏内可见行数 +1(取整余量) —— 它同时兼容"行高估计偏保守"(前进少于屏内可见行 = 有重叠, 属翻页常态)。
- **守阵**: `e2e/kbd-scroll-band.spec.mjs` 第 2 条(双皮肤: Home 起算 → PageDown → 前进量 ≤ 屏内可见行数 +1, **面板关 / 面板开两档**; 面板开那档在修复前恰是越界最重的一档) + 静态 `test_kb_view_band_single_points` 扩写(一屏算式必须由可见带得出, 禁 `_winViewH` / `innerHeight`)。红验: 把 `per` 退回旧算式 → 静态红 + 双皮肤 e2e 红(报「面板关: 一屏前进 12 行 > 屏内可见 10 行 ⇒ 这一屏跳过了看不见的行」)。
- **未收**: `_kbViewportRow` 的渲染行扫描把**文档坐标** `vTop/vBot` 与**视口坐标** `rect` 直接比较(仅 scrollY=0 成立; 滚动后全行判"看不见" ⇒ 非窗口化视图上无光标回落退化成「跳极值行」)。属同族的第三个成员, 本轮按范围守恒未动, 待定夺。
- **已收**(2026-10-09 第三轮): 见下条「同族第三处: 可见性判定的坐标系混用」。

### 同族第三处: 可见性判定的**坐标系**混用 (2026-10-09 第三轮, 用户指令「修复 _kbViewportRow 的问题」, 已修)

- **触发**: 无光标回落(点过别的视图/行后按 ↑↓)在**滚动后**跳到极值行(↓ 回顶, ↑ 落底); 或任何拿几何矩形与"可见带"比较的写法 —— 先问一句"这两边是同一套坐标吗"。上两条收的是**边界值**与**一屏量**, 这条收的是**坐标系**。
- **判别**: 症状是**只在滚动后出现, 且退化成跳极值行**(不是"差几行", 是"瞬移到列表顶/底")。真机一眼看出(桩 300 种子, 1440x900, 追剧页展开一剧一集 = 39 行非窗口化视图): 滚到 `scrollY=1500` 后按 ↓, 期望落屏内首行(idx 6)实落 **row 0 且 scrollY 跳回 8**; 按 ↑ 期望落屏内末行(idx 10)实落**最末行(scrollY 冲到 2203)**。根因 = `_kbViewportRow` 渲染行扫描里 `vTop/vBot = window.scrollY + _kbViewTop() + 4`(**文档坐标**)直接与 `rect.bottom/rect.top`(**视口坐标**, `getBoundingClientRect`)**同框比较** —— 只在 `scrollY=0` 时两者相等; 一旦滚过一屏, 所有渲染行都满足 `rect.bottom <= vTop`, 全被判"出视口", `first/last` 恒为 -1 ⇒ 兜底 `delta > 0 ? 0 : rows.length - 1`(跳极值行)。
- **处置**: 两套坐标各归各的, 单点仍只出**视口坐标**、由消费方按需换算 —— 这正是 `_kbViewTop()` 注释早就写明的口径(「返回视口坐标, 消费方自行加 `window.scrollY`」), 旧码只是没照做。`vTop/vBot` 去 `scrollY`(渲染行 rect 直接比, 余量落成 `vTopM = vTop + 4` / `vBotM = vBot - 4`); 新增 `sy = window.scrollY`, **只**在窗口化前缀和那支(它的 y 是文档坐标)比较时加回。前缀和分支行为与旧码逐字等价, 只修渲染行分支。
- **守阵**: `e2e/kbd-scroll-band.spec.mjs` 第 3 条(双皮肤 @fast: 追剧页展开一剧一集 → 滚过一屏 → ↑/↓ 各测一遍, 判据 = **光标必须落在按键前就在可见带内的行上** —— 正是"视口就近行"的语义, 跳极值行必违反) + 静态 `test_kb_view_band_single_points` 扩写(`vTop`/`vBot` 必须是单点裸值、`window.scrollY` 只经 `sy` 取一次、前缀和分支必须 `sy + vTop + 4`、渲染行 rect 必须比 `vTopM/vBotM`)。红验: 退回 HEAD 版 → 静态红 + 双皮肤 e2e 双双红(报「↓ 落到了按键前看不见的行(idx=0); 按压前屏内可见行 = [31,32,33,34], scrollY 2371->8」)。
- **家族关系**: 与前两条同族, 但**病灶在坐标系而非边界算式** —— 边界单点用对了, 消费方换算错了照样废。**新写"可见性"判定时先确认: 手上的矩形是哪套坐标, 比较的另一边又是哪套。**
- **复发**: 0
