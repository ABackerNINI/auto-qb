# 「设计如此」的状态不许用 WARNING(会被 notify 推成系统通知)

> 摘要: 本仓把 WARNING 以上**推成系统通知**, 而取数/后台线程是分钟级轮询 —— 只要把「按设计在等 / 自己决定要做」的状态(未到取数时机、被自己的频控拦下、启动关闭重挂)记成 WARNING, 用户就会被弹窗淹没, 然后**开始忽略所有告警**。四条判据: ①故障才 WARNING ②同一根因只说明白一次 ③同一事件只由一个角色告警 ④持续状态不静默消失。
> 触发: 通知太多, 弹窗, 告警疲劳, WARNING, 日志刷屏, 每分钟一条, 节流, 限速, 未到可取时刻, partial, 启动日志, 后台线程日志, notify 推送, 轮询, 重复告警, 两条通知

## 现象与代价(2026-09-24 用户实报)

- 后端 HR 取数线程每 60~90s 轮询一次, 而一轮完整刷新要好几分钟 ⇒ 日志里反复出现
  `WARNING ... partial: 配额/间隔受限(间隔: 还差 104s)` 与 `INFO ... waiting: 未到可取时刻(间隔, 还差 51s)`,
  系统通知跟着每轮弹一次 —— 用户的结论是「弹 warning」+「没法知道数据到底拉到没有」。**没有一行是故障**。
- 更隐蔽的一半: 同一根因在不同轮次会返回**不同的 action**(`partial` 首页抓到了、第二页被拦; `waiting` 还没到时刻)——
  若按 action 做「状态变化就记一条」, 两者会交替互相触发, 等于每轮都记, 去重形同虚设。

## 判据与做法

- **①故障才 WARNING, 且「是不是故障」要先判**: 页面/字段/翻页异常(可能站点改版)、取数失败、
  通道静默、锁不生效 ⇒ WARNING; 未到时机、被自己的间隔/配额/时间窗/熔断拦下 ⇒ **INFO**,
  并把「非故障」写进消息文本(让读日志的人不用查代码)。
- **②去重的键要选根因, 不要选本轮返回值**: 用 `partial`/`waiting` 这类 action 当键会交替刷屏;
  归一成「被拦原因类别」(间隔 / 配额 / 时间窗 / 熔断 / 只读…)后, 一整个「等间隔」时期只说明白一次。
  倒计时数字必须一起抹掉, 否则 `还差 104s` 与 `还差 51s` 又变成两种状态(见 `worker.stable_key`)。
- **③同一事件只由一个角色告警**: 「谁产生原因谁负责报」—— 产生处(取数失败 / 存储层读坏)打 WARNING 并
  在结果对象上标 `alerted`, 状态层(worker)见到标记就只记 INFO。**实测代价**: 一次扩展取数超时被
  两处各报一次 ⇒ 用户一次收到**两条**通知(`取数失败(1 次): …` + `error: …`)。
- **④持续状态不静默消失**: 去重不能变成「永远不报」—— 同一状态按 `channel_silence_warn` 周期再提醒一次,
  被去重的轮次仍留在 DEBUG(排障要看得见每轮在等什么)。持续状态的告警(如站点文件读坏)同理:
  同一文本只报一次, 后续降 DEBUG。
- **有进展就清记忆**: 完整刷新/复用成功后忘掉节流记忆 ⇒ 下次再卡住会重新说明白。
- 结构化的 `reason_kind`(budget / parse)比在日志层正则匹配 `reason` 文本可靠 —— 分类在产生结果处做一次,
  日志、报告、后续通知都复用它。

## 两类「自己决定要发生」的消息, 同样别用 WARNING

- **生命周期**: 端点已启动 / 在线核实已启动 / 已关闭 / 热重载重挂 —— 全是程序按配置做的动作。
  用 WARNING 的后果是**每次重启先吃三条通知**(2026-09-24 用户实报的「一开就弹 warning」)。
  守阵 `tests/test_hr_runtime.py::test_start_stop_messages_are_info_not_warning`。
- **被叫停 ≠ 没通道**: 关停 / 热重挂时取数线程可能正阻塞等扩展回传, 取消后抛出的异常**必须能与
  「本实例没通道」区分**(专用子类 `HrChannelStopped`) —— 混成一个异常的直接后果是**每次关停都告警一条
  「无可用取数通道」**, 还会误推进失败计数/熔断。守阵 `test_cancelled_queue_reports_channel_unavailable`
  与 `test_cancelled_fetch_is_not_a_failure_nor_an_alert`。

## 坏文件/异常记录: 告警之外还要「留现场」

- 站点文件读坏(实测报 `Expecting value: line 1 column 1 (char 0)` = **空文件**)时, 除了告警**还要**:
  ①把坏文件挪到 `.bad-<ts>`(否则下次写盘就把它覆盖掉, 线索永远消失)②试 `.bak` 兜底 ③取证串带上
  大小与开头字节 —— 只报 JSON 的原始报错, 人看不出是「被清空了」还是「内容坏了」。
  (站点文件的 `.bak` 就是为此存在: 丢了索引 / 已取记录等于要重新烧配额抓一遍, `hr_downloaded` 没了还会重下 .torrent。)
- ❗从备份恢复后必须**重置写者心跳自检基线**: 恢复出来的 revision 必然比本进程上次写的旧, 不重置就会被
  「revision 回退 ⇒ 锁不生效」误判成只读 —— **自愈反而变砖**(守阵 `test_corrupt_file_is_quarantined_and_recovered_from_backup`)。
  同理, 恢复后的第一次写盘**不能**再复制 `.bak`, 否则好备份被坏内容盖掉(与 `state.json` 自愈同一个坑)。

## 同族旧账

- 通道无可用同样按「每站只报一次, 恢复后重置」处理(`service._warn_no_channel`), 理由完全一样。
- 反过来也别把它静音成 DEBUG: 用户就是靠这些行确认「它在动」——**降到 INFO + 去重**才是对的粒度。
