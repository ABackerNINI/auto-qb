# 写回路径与校验必须同一份数据 —— 版本章只许盖在已迁移的结构上

> 摘要: 带 schema 版本链的写回(writer)若「校验走迁移后的临时副本、落盘写原始提交树 + 新版章」,
> 磁盘会落成「新版章 + 旧版结构」: 写完的 reload 当场撞废除校验, 下次启动也进不来(2026-09-27
> config v1→v2 生产事故, WebUI 保存 500)。处置双防线(计划 26-09-27-2252): **启动物化单点**
> 把落后磁盘改写到当前版本(版本号备份先行) + **写回版本闸门**直接拒绝落后提交树(不做迁移修补)。
> 触发: schema 迁移, 版本链, 写回, writer, 盖章, schema_version, WebUI 保存, read_tree,
> 浏览器往返, 提交树, 临时副本, v1→v2, 废除, reload, 版本闸门, materialize

### 校验与落盘数据不一致 → 新版章盖在旧结构上

- **触发**: 给落盘文件引入破坏性 schema 变更(vN→vN+1, 迁移会改结构)时, 凡是「读原文 →
  浏览器/调用方往返 → 写回」的路径(`writer._prepare` / 预览)都要过一遍: **校验用的数据和
  落盘用的数据是不是同一棵树**。本项目的高危形状: 提交树来自 `read_tree`(磁盘原文)的浏览器
  往返, 在迁移物化前它始终是旧版结构; 而校验若把树 dump 到临时文件走 `load_config`, 迁移只在
  临时副本上生效 —— 校验绿 ≠ 落盘内容对。
- **判别**: 事故签名 = 保存动作后的 reload(或下次启动)报「该键已于 schema vN+1 废除 —— 存量
  配置应由迁移链自动改写」, 且磁盘文件版本章已是新版本、结构仍含旧版专有键; 加载路径(启动)
  一切正常(内存里是迁移过的)。看到「校验通过了但写完盘连自己的重载都过不去」即是本坑。另一
  伴随信号: 启动迁移日志缺失 —— `QbManager.__init__` 里 `load_config` 先于 `_setup_logging`,
  迁移 INFO 无 handler 被丢弃, 别被「没迁移」的表象骗了。
- **处置**: 双防线(计划 26-09-27-2252, 拒绝「迁移修补写回」的第二版方案): ①**启动物化** —
  `QbManager.run()` 开头调 `writer.materialize_schema_migration`: read_tree 重读磁盘 → 沿链
  迁移 → 校验复核 → `<名>.v<m>.bak` 版本号备份 → 原子写回; 磁盘恒为当前版本, 编辑器永远看到
  新结构。②**写回版本闸门** — `_reject_stale_version`: 提交树版本低于当前(含缺失)直接
  ConfigError/400 指路刷新, **不做迁移修补**(用户裁决: 静默写用户没见过的结构 = 替用户做主)。
  **已产出的坏文件**: 物化救不了(启动校验即失败), 用写盘前自动备份的 .bak(旧版形态)恢复,
  或按报错指引手工重配 —— 不为坏文件加常驻兼容层(设计红线, 见 config/migrations.py)。
