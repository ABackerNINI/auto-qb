# 分步退休配置段时直接删数据类/字段, 会打断「属于后续步骤」的消费者的测试

> 摘要: 把一个配置段的退休拆进多步计划(本仓常态)时, 若该段仍有消费者被计划排到**后续步骤**,
> 退休它的那一步不能直接删数据类/字段 —— Python 不做属性静态检查, 消费者只在运行期 AttributeError,
> 让「本步应全绿」的测试变红, 逼你越界去改后续步骤的东西。过渡做法: 数据类保留为**默认值 stub**、
> 字段留在 Config 上, 但从 schema / KNOWN 键 / loader / 校验 / 键面里全剔除; 待消费者重接那步再删 stub。
> 触发: 分步退休配置段, 删配置键, Config 字段与 KNOWN key 不一致, 运行期 AttributeError, 消费者属后续步骤, 过渡 stub, 一步一提交

### 退休配置段的步骤与 consumer 重接不同步时, 留默认值 stub 保绿

- **触发**: 多步计划里某一步「合并/退休配置段」, 而读该段的消费方(webui 路由、订阅线程、前端)
  被计划排到后续步骤; 同时本步出口判据又要求「测试全绿 + 行为等价」(本专题 S15 实证, 2026-10-17)。
- **判别**: 删掉 `Config.<段>`(或对应数据类)后, `config.<段>.<键>` 只在**运行期**抛 AttributeError ——
  import/collect 全过, 直到相关用例跑到才红, 症状像「我改的别处坏了」。只要该段仍有跨步消费者, 就是本坑。
- **处置**: 旧段对应的数据类保留为 stub(`field(default_factory=...)`, 全走默认值), `Config` 上字段保留,
  让后续步骤的消费者继续按旧属性名读(拿到默认值); 但把它从 `KNOWN_CONFIG_KEYS`、schema 组、loader、
  validation、键面基线里**全部剔除**(YAML 段交给迁移删除)。注意段认领完备守阵要求
  「每个 Config 属性都被某模块认领」⇒ 保留字段就得保留其认领者。收尾时在档案 / activeContext 写清
  「stub 保留 + 待哪一步删」, 免得后来者当死代码又删一次; 删 stub 那步必须连同消费者一起重接
  (本专题为 S16/S17)。若本步确须删干净, 先确认无跨步消费者, 否则扩范围或调步序。
