# 判据只落到一个消费侧: 配置「看着生效」实为不生效

> 摘要: 一条业务判据(排除表 / 白名单 / 开关 / 门槛)常有多个消费侧 —— 各侧若**各自实现一遍**该判据, 漏掉任一侧就会「配了不生效」, 且不报错、不告警, 只在行为上体现 (多为「频率 / 数量 / 展示」与预期不符)。
> 触发: 加/改一条作用于某类对象的判定; 给已有判据补新的消费点; 用户报「配置了没反应」。

## 条目

- **触发**: 新增或改动一条「作用于某类种子的判定」(如 HR 排除 `exclude_tags` / `exclude_categories`), 而该判定在系统里有**两个及以上**消费侧 (判定侧 / 展示侧 / 取数对账侧 / 调度侧)。2026-10-08 实报: HR 排除只在判定侧 (`record.hr_judgement` / `check_hr_condition` / `hr_managed`) 与展示侧 (`webui.views.hr_view_fields`) 生效, 取数/对账侧 (`HrRuntime._anchors` → `HrRefreshService._build_objects`) 从不读它 ⇒ 被排除种子仍进「对账对象集」⇒ 稳态条件 (对象集为空) 恒不成立 ⇒ 稳态降频 `idle_refresh_interval` (24H) 永不生效, 拉取频率停在 `refresh_interval` (5H)。
- **判别**: ①先给判据找**唯一判据单点**(本例 `TorrentRecord.hr_excluded`), 再 `grep` 它被谁调用 —— 消费点数量与「系统里事实上需要这条判据的地方」数量对不上即为缺口。②症状特征: 判据在 A 侧输出正确 (界面显示「已排除 / 不管束」), B 侧行为不变 (引擎仍为它翻页), 两侧口径相反且都「没报错」。③**看设计文档要当心**: 若设计文档复述 B 侧的判据时只枚举了部分分支 (计划 26-10-05-0555 §02 只列「终态 / 放行 / 超额」三条, 未含排除), 说明这是设计缺口而非实现漏行 —— 修的时候要连文档口径一起补。
- **处置**: 修法不是「在 B 侧再抄一遍判据」, 而是**把判据带过边界**: ①若 B 侧的数据载体 (如 `HrAnchor`) 结构里没有该属性, 先补属性 (带过边界), 由 B 侧单点消费; ②或让 A 侧构造载体时就按判据过滤 (注意副作用: 本例直接从锚点剔除会让被排除种子离开「本地命中集」, 反而触发一次多余的 `.torrent` 身份下载)。**两条都要求 B 侧仍保留该判据的另一半语义** (本例: 不进对象集, 但仍参与命中识别), 别把「不管理」误做成「不认识」。
- **守阵**: 补两侧一致性守阵 —— 判据命中的对象: ①不出现在 B 侧的产出集里; ②A 侧的既有能力 (命中识别 / 展示) 不被静默削弱; ③判据为空时行为零变化 (零静默变更)。本仓落地(计划 26-10-08-1249 方案 B): `tests/test_hr_service.py::test_build_objects_skips_hr_excluded_anchor`(①) · `::test_hr_excluded_anchor_does_not_break_idle`(①的行为面, 红验) · `::test_excluded_anchor_still_counts_as_local_hit`(②, 设计锁) · `tests/test_torrents.py::test_record_hr_anchor_carries_excluded_flag`(判据是否真的带过边界 —— **只断言「判据函数返回 True」等于没测**)。
