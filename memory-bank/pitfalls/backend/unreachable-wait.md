# 依赖不可能回传时不要等满超时 —— 白等会把「本机门没开」伪装成「远端没回应」

> 摘要: 与外部通道(浏览器扩展 / 本机端点 / 代理 / 设备)打交道时, 若「对面能不能收到」在本机
> 已有判据(端口没绑 / 监听器不在), 就不要把请求丢进队列然后等满 `request_timeout`: 白等既占着
> 站点锁与线程, 又把**本机故障**伪装成**远端超时**, 把排查方向引到完全错误的门上去。
> 触发: 等待回传, 超时, request_timeout, 白等, 端点未监听, 端口未绑定, 快速失败, fail-fast, 假线索, 排查方向, 通道不可用, listening

### 两条动作

- **触发**: 写「本机发任务 → 远端(扩展/服务/设备)拉走并回传 → 本机阻塞等」的通道代码;
  或给这类通道配 `timeout` 找"该设多大"。
- **判别**: 问一句「等待期里, 本机是否已经知道**不可能**有回传?」本仓实例(2026-09-29 实报):
  端点对象建了却从未 `start()` ⇒ 127.0.0.1 端口未绑定 ⇒ **任何扩展都取不到任务, 也没人能回传**。
  但 `ChannelFetcher` 照旧 `queue.put(...)` + `queue.wait(request_timeout)`: 每页白等 180s,
  一个站点一轮白占 3 分钟锁, 而日志只留下
  「等待浏览器扩展取数超时(180s)…(浏览器是否在运行 / 扩展是否启用 / 是否已登录站点?)」 ——
  **它把人引向浏览器**, 真实原因却在后端(端点没起来)。误判成本 = 数小时的错误排查方向。
- **处置**: ①把「对面是否可达」做成**现读回调**传进通道(`listening_fn: Callable[[], bool]`),
  `_fetch` 进门先查, 不可达**立刻**抛「通道不可用」而不是等超时 —— 本仓落到
  `HrChannelUnavailable` ⇒ service 折成 `ACTION_NO_CHANNEL` + 每站一次 WARNING, **不计失败、
  不推熔断**(环境问题不是站点问题); ②回调必须**闭包现读**而不是构造时快照: 端点对象热重载会被
  整个换掉; ③**语义优先级要排好**: 「被叫停(关停路径)」判在「不可达」之前, 否则正常关停会被
  报成「没通道」; ④错误分类要跟着改:`HrChannelUnavailable` 是 `HrFetchError` 的子类, 凡
  「不是这个种子/这份数据的问题」的让位元组都要把它列进去, 否则通道级故障会被记成
  「种子取 .torrent 失败」并进重试冷却。
- **守阵**: `tests/test_hr_fetcher_channel.py::test_endpoint_not_listening_fails_fast`(断言
  **不进队列**、**耗时 < 1s**、异常类型恰为 `HrChannelUnavailable`, 且叫停语义优先);
  `tests/test_hr_runtime.py::test_fetcher_fails_fast_when_endpoint_stops_listening`(门面接线:
  端点被收掉后取数立刻报无通道)。两例红验实测: 未修复时前者报 API 缺失、后者**白等 5s 后**才抛
  「等待浏览器扩展取数超时」。
