# 热重载 L0 级别 ≠ 「只替换 Config 对象」就生效 —— 消费方按值持配置时必须走挂载口

> 摘要: 影响分级标 L0 只保证「新配置对象已被替换」; 若消费方(服务/线程)构造时把配置**按值**拷走,
> L0 变更对它静默失效 —— 且机制注释/守阵测试还可能把错误语义钉死, 修 bug 时要先反转它们。
> 触发: 加配置键, 定热重载级别, impact, L0, 热重载, apply, 按值持有, 站点接入, 服务重建

### 「L0 即时生效」成立的前提是消费方每轮现读; 按值持有者必须每次热重载过一遍挂载口

- **触发**: 给某功能段定热重载级别(L0/L1/L2), 或给「构造时拷配置」的服务/线程加配置项 ——
  HR 取数服务(`HrRefreshService` 把 `global_conf` / `site_confs` 在 `__init__` 拷成自己的字典)、
  任何「重建廉价、无状态」的附属服务都是这一类。
- **判别**: 打开消费方构造函数看配置是**引用**还是**拷贝**(`dict(site_confs)` = 拷贝)。
  拷贝 + 调用点只挂在某个级别分支(如「只在 L1 才调 apply」)⇒ 其它级别的变更静默丢失:
  HR 实报(2026-09-29)是站点接入(标 L0)后 `/api/hr/status` 永远报「取数线程未启动」——
  启动时无站点 ⇒ worker 从未建过; 热接入是 L0 ⇒ 挂载口(`HrRuntime.apply`)根本不被调。
- **处置**: ①挂载口**每次热重载都调**, 不挂在单个级别分支里; 无变化的开销由挂载口自己
  **短路**(比对新旧配置, 相等直接 return) —— 别让调用方做裁剪, 裁剪就是漏调的温床;
  ②挂载口把运行态收敛到「enabled ⇒ 在跑」: 线程没建过(冷启动无站点)也要补启动,
  别用「原来在跑才重启」的 `running` 守卫 —— 那会把「从无到有」永久挡在门外;
  ③机制注释要写**机制真相**(谁按值持有什么、挂载口在哪), 别写「每轮现读」这种与实现相反的话;
  ④守阵测试若钉住「不得拉起」这类反语义, 修 bug 时**连测试一起反转并注明实报出处**。
- **守阵**: `test_apply_new_config_levels` 断言 L0 下 `hr.apply` 也被调; `test_hr_runtime.py`
  的 `test_apply_starts_worker_when_never_started` / `test_apply_no_change_short_circuits`
  钉「enabled 必启动」与「无变化不重启」两端。
