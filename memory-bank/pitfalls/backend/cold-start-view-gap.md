# 「结论已落盘」≠「消费方看得到」—— 把发布排在长任务之后 = 冷启动判定真空期

> 摘要: 数据/结论已经写进磁盘或内存, 但**广播/发布的时机**排在一个长达数小时的任务之后 ——
> 重启后消费方在整段任务期内读不到任何结论(本仓: 视图为空 ⇒ 判定入口返回 None ⇒ 全部回落本地)。
> 表现极具误导性: 「功能像没生效 / 怎么还是老的」, 而磁盘数据一应俱全、日志也没有任何报错。
> 触发: 重启后功能像没生效, 视图, 发布, publish, 广播, 冷启动, 判定真空期, 回落本地, 第一波, 长任务, 取数波

### 发布时机不要挂在长任务尾巴上

- **触发**: 写「后台任务产出 → 发布只读视图/缓存 → 消费方读」这类链路, 或排查「重启后一段时间内
  功能表现像没生效」的实报。
- **判别**: 问一句「从进程起来到**第一次发布**之间, 消费方看到的是什么?」本仓实例(2026-09-29 实报):
  `HrWorker.run_once()` 的发布排在**所有站点波次返回之后**, 而一波受站点最小间隔约束
  (90s/请求 + 待回填 .torrent)可跑数小时 —— 于是重启后 `view_revision` 长时间为 0,
  `judge()` 因视图为空返回 None, 四个判定消费点全部回落本地, 界面上 108 个种子的
  `hr_state` **全是空串**(「仍是本地」)。而站点文件里 194 条档位命中与 4 条放行记录都在。
- **处置**: ①把「发布既有结论」放在**任务启动之前**(本仓: `_loop` 在首轮取数前先
  `publish(build_views())`), 让「已知结论」零延迟可见 —— 与「证据无时效、只有真伪」的设计一致;
  ②顺序不能反: 发布多带「内容实质变化才抬版本」的短路, 若先跑了任务再补发**旧**快照,
  反而会把新视图盖回去; ③这条发布必须包 try/except 只记 ERROR —— 读盘失败不该打死后台线程;
  ④判据: `view_revision`/发布计数在「第一轮任务完成前」就该 > 0。
- **守阵**: `tests/test_hr_worker.py::test_start_publishes_disk_views_before_first_wave`
  (用「永远卡在取数上」的假通道把首轮钉在半路, 断言此时 `publisher.revision >= 1` 且判定侧已可用);
  红验实测未修复时正是 `assert 0 >= 1`。

## 排查这条的现场手法(可复用)

- 先看**发布计数**(本仓 `/api/hr/status` 的 `view_revision`)与消费方字段是否为空串 —— 空串往往意味着
  「判定入口返回 None」而不是「判定为无证据」, 两者的处置完全不同。
- 再看磁盘文件: 若文件里结论齐全、档位/放行记录都在, 就说明问题在**发布链路**, 不在数据。
- 最后核对时间戳的相对关系(`now` / `fetched_at` / 波次 ts / 文件 mtime): 差着十几小时又拿不准时,
  先确认「这个字段是谁写的」—— 本仓 `wave_ts` 只由 `_finish_wave` 写, `fetched_at` 也只由它写,
  两者差 12h 直接说明「那一波没跑完」。
