# 真机探针增量窗口: trigger 后重置 rid 会把窗口内事件被全量冲掉(假阴性)

> 摘要: 真机探针增量窗口: trigger 后重置 rid 会把窗口内事件被全量冲掉(假阴性)
> 触发: 真机探针, 增量窗口, rid 重置, 全量冲掉, 假阴性, sync/maindata, torrents_removed, 删后重加, 探针方法论
**Refs:** memory-bank/issues/26-10-11-2045-bug-torrents-store-removed-pop-readd.html

### 探针在 trigger 后才 `sync_maindata(rid=0)` 重拉全量, 窗口内积累的增量事件(如 torrents_removed)被全量响应冲掉, 得出「事件从未下发」的假阴性

- **触发**: 对 qB `/sync/maindata` 做行为探针(观测某操作会触发哪些增量事件)时, 把「取基线」写在 trigger 之后 —— rid=0 的响应是 full_update, 反映的是**当下**状态, 此前窗口内累积的事件全部丢失; 探针看到的不是连续客户端(产品主循环)的真实视角。
- **判别**: 探针结论形如「qB 从不下发 X 事件」, 但对照组(只触发删除不触发重加)里 X 通道明明工作; 或试验组首个响应总是 `full_update=true` / 覆盖全量字段 —— 基线取晚了。26-10-11-2045 复测 v1 就因此误得「删后重加完全合并无 removed」(该结论本身后来被 v2 证实仍成立, 但 v1 的证据链是无效的)。
- **处置**: 探针骨架固定三步: ① 先 `sync_maindata(rid=0)` 取全量基线拿增量起点 rid; ② 轮询**全程连续**(几十 ms 级), 删/重加等 trigger 作为定时事件在轮询循环内按时刻触发(`t >= t_del` 才调 delete), 不在循环外先做完; ③ 另设「只触发一半」对照组(如只删不重加)验证目标通道本身工作, 再解释试验组的「无事件」。
- **守阵**: 无机检(一次性探针脚本, 落 `tests-real/.work/` 随 clean 清掉); 纪律靠本条 —— 写探针先对照处置三步。
