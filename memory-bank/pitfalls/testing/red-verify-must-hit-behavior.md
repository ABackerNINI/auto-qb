# 红验必须命中行为/几何, 不能只命中写法

> 摘要: 红绿双验的「红」若只把实现**换个写法**(改变量名 / 挪声明位置)而不改变可观测行为或几何, 守阵会**绿着放行假修复**——因为守阵钉的是结果(对齐 ±1px / 计数相等 / 节点身份), 不是代码形态。红验设计纪律: 写守阵前先回答「这条断言在什么**行为破坏**下会红」, 然后真把那个行为改坏一次; 若守阵不红, 是守阵错了不是破坏错了。同类陷阱: 量具自身的口径错误(把原始字节数当格式化文案断言 / 对错弹层元素断言)也会造成「假红」, 修量具 ≠ 修实现, 两者要在报告里分开记。
> 触发: 红绿双验, 红验, 改坏实现, 守阵没红, 假修复, 假红, 量具写错, 守阵测什么, 行为回归用例, 几何守阵

## 真实案例(2026-10-13, 计划 26-10-13-0811)

**案例一: 红验绕过了被钉的几何(W2)**

- 被钉行为: 06 面「行 padding 与列头 padding 同源」(--tbl-pad-x 变量化)。
- 第一次红验设计: 把变体里的变量名改掉、回落字面量 8px——但列头默认值**本来就是 8px**, 几何一像素没变, 守阵 12 条全绿。
- 结论: 守阵测**几何**不测**写法**, 想红就得让几何真的分家(删 `.dt06-list` 的变量声明使行 8px/列头 14px 分家)→ 守阵精准红 2 条。
- 纪律: **红验动作必须作用在断言所量的事实上**, 不是作用在实现代码的形态上。

**案例二: 量具口径错误造成的「假红」(W5)**

- #5 速度实时: 量具首跑红, 但不是实现红——量具断言了原始字节值, 而格子显示的是 `fmtSpeedOrDash` 格式化文案; 改量具对齐口径后重测。
- #7 按钮不占列: 量具对 `col-menu` 断言, 实际弹的是 `headMenu`; 且 Escape 关抽屉(lifecycle Esc 链)把面板关了。
- 纪律: **假红要在报告里与真红分开记**; 假红修的是量具, 不许顺手"修实现"让它变绿; 真红才允许进修复流程。

**案例三: 红验全中目标断言才算数(W6)**

- 面背景量具首跑 8/8 红, 但要检查红因分布: 8 条全部红在「表头背景 == 页面底」目标断言 = 有效红; 若红在打开抽屉/元素可见这类前置步骤, 量具本身还没建立观测能力, 不能开始修复。
- 追加断言时同理: W7 补「表头零落影」断言, 先确认 8/8 红在该断言上, 再动实现。

## 落地纪律

1. 写守阵时, 在 docstring 里写明「红验动作 = 把 X 改坏 → 断言 Y 红」;
2. 红验后用 `sha256sum -c` 复核还原一致(改坏动作不许留在工作区);
3. 红因分布必须逐条核对目标断言, 前置步骤红 = 量具未就绪;
4. 假红(量具口径错)与真红(实现被钉行为破坏)分开记账, 不许混淆修复对象。
