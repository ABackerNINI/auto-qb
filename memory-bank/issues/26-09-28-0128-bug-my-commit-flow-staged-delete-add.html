01现象与发现场景

ALT-01 提交轮(plan 26-09-28-0037, commit 6c85ff4)中, 按收尾 DoD 删除了一个已跟踪文件(activeContext 切片蒸馏), 首跑 commands run ship.commit 在「暂存(逐路径)」步骤直接 RESULT: FAIL, 提交未发生。与平台/配置无关 —— 任何"本轮删除过已跟踪文件"的提交都会触发。

02证据

# 取证 2026-09-28 01:11 (ship.commit 首跑输出)
RESULT: FAIL git add 失败: memory-bank/activeContext/26-09-23-1959-memory-bank-doc-forms.md
WHY: fatal: pathspec 'memory-bank/activeContext/26-09-23-1959-memory-bank-doc-forms.md' did not match any files

# 当时 porcelain 形态(删除已随失败留在暂存区):
D  memory-bank/activeContext/26-09-23-1959-memory-bank-doc-forms.md   # 首列 D = 已暂存删除 -> 必败
 D ...                                                                # 空格 D = 未暂存删除 -> git add 正常

workaround 已验证(2026-09-28 01:30): git restore --staged <path> 退回未暂存态后重跑 ship.commit 一次通过(commit 6c85ff4, 27 文件)。

03影响面

维度结论
触发条件本轮含已跟踪文件的删除, 且删除已进暂存区(首跑失败后删除留在暂存区, 重跑继续踩) —— 必现
影响范围ship.commit / commit.py 暂存步骤; 不影响已提交内容, 只是提交被拦
严重度中 —— 每次含文件删除的提交首跑必败, 靠手工 workaround 绕过; 脚本自身无数据损坏风险

04定位锚点

  • .commands/my-commit-flow/scripts/commit.py:162-167(取证 2026-09-28 01:28)· 暂存循环 for path in to_stage: git("add", "--", path) · grep 关键词 逐路径 / git add 失败
  • to_stage 清单构建在其上游(同文件, grep to_stage) —— 疑似把 porcelain 的 D 路径也列入逐路径 add, 未区分删除形态(待查)
  • 关联坑条: memory-bank/pitfalls/git/ship-commit-staged-delete.md(触发/判别/处置三段, 含 workaround 口径)

05根因（可选）

机制已明确(非猜测): 逐路径 git add -- <path> 的 pathspec 同时匹配工作区与索引; 「已暂存删除」的路径在工作区与索引里都不复存在, 无处匹配即 fatal。未修的深层问题(待查): to_stage 清单为何把该形态路径照常下发, 以及脚本对删除路径应选用哪种登记口径。

06建议修法（可选）

  • 方向 A(小改): 暂存循环对 porcelain 首列为 D/ 的删除路径改走 git rm --cached -- <path> 口径(已暂存删除时为幂等登记), 其余路径维持 git add --。
  • 方向 B(更省): 对含删除的路径统一 git add -A -- <path>(单路径限定的 -A 不违背「禁 -A / . / *」的防误交本意 —— 那条禁令拦的是全仓通配, 不是单路径语义; 需在包 README 写清口径)。
  • 配套: 两方向都应补守阵(临时目录造已跟踪文件删除 + 断言 ship.commit 暂存步骤通过)。
