01现象与发现场景

走查于修复「WebUI 批量跳检后批量开始状态脱节」（plans/26-10-11-2040 §6.1「跳检收尾回写真值」）时：新方案要在跳检收尾把重加后的记录 apply_delta + restore_torrent 写回 store，于是顺查「写回的行会不会被下一轮同步再删掉」，发现 Store._apply 的增量分支存在顺序隐患。

机制：_apply 增量轮先把 patches 写进 by_hash（store.py:222-250），后按 changes（=removed + 本程序自身删除的 pending）逐个 by_hash.pop(h, None)（store.py:254-259）。若同一轮里某 hash 同时出现在 patches 与 removed，则 pop 在写之后执行 ⇒ 刚写进去的行被删除。

与本仓强相关：跳检的步骤就是「删除（保留文件）→ 重加」同一个 hash（ops_mod.py:447-450 的 _skip_delete → _skip_readd）。只要 qB 的增量响应把这次删除以 torrents/removed 下发在同一 rid 窗口，就会命中上述顺序。

待真机确认（本条未验证）：qB WebUI /sync/maindata 对「删后重加的同 hash」是否会同轮或在下一轮仍带 removed 该 hash。无论答案如何，「先写后 pop」的顺序本身是既存事实。

03影响面

维度结论
触发条件某 hash 在同一增量轮内同时出现在 patches 与 removed（含本程序 remove_torrent 的 pending）；跳检「删→重加」是天然制造者
影响范围① store 快照凭空丢一行 → 该行在 UI 短暂消失/抖动，直至下一全量轮重建；② 与 plans/26-10-11-2040 §6.1 直接冲突：6.1 刚把重加后的真值写回 store，可能被同轮/次轮的 pop 再抹掉；③ 若同时命中 member_to_key 归组，组视图会重算冲突
严重度待定 —— 取决于真机下发行为。若 qB 确会同轮下发 removed：中-高（与跳检收尾打架、UI 抖动）；若不会：仅潜在隐患（顺序本身仍建议防御性修正）

05根因（可选）

已确认（代码顺序）：「先写 patches、后 pop removed」使「同轮既在 patches 又在 removed」的 hash 以删除告终。
待查（真机行为）：qB 的增量 sync 是否会对「删后重加的同 hash」下发 removed（同轮或次轮）。
已排除：全量轮无此问题（full=True 走 by_hash 重建 + 未出现者即删除，不经过 pop 循环）。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

候选（真机确认后再拍板）：

  1. pop 尊重本轮 patches：for h in changes: if h not in patches: by_hash.pop(h, None)。一行改动，直接消解顺序竞争；代价：若 qB 真以「removed 优先」表达语义，则需确认不会因此留下一行幽灵记录（但 patches 由同一响应驱动，有 patch 即代表该轮它存在）。
  2. 重加路径显式清 pending：_skip_readd 成功后把该 hash 从 _pending_removed 摘除。范围更窄，但只覆盖跳检这一条制造者，其它「删后重加」路径仍裸奔。
  3. 仅文档化：确认真机不发生则记入 pitfalls/，不动代码。代价：隐患留存。

倾向方案 1（防御性、且与 §6.1 相容）；但须先完成真机确认。未拍板前保持 Open。
