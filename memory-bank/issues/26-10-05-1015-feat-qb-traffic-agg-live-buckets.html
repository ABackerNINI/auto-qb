05根因（可选）

已查明(非猜测): agg 行只在「完结层级 + flush 时点」由内存累计器封口追加(_agg_flush_series), 未完结小时/日/月的累计器(SeriesAgg.pending / day_hours / month_days)只在内存; 而 agg 段窗读侧只消费 agg.dat(S6 活尾快照只覆盖 raw 段窗的未落盘记录与开放游程, 不含聚合累计器)—— 两个面之间没有活数据桥。v3 计划 26-10-04-1957 设计期未覆盖图面尾部新鲜度(全文「实时」零命中), S6 只修了被验收报出的 raw 段窗。

06建议修法（可选）

候选 S7(方向, 未拍板未实施): 把 S6 活尾发布面扩到聚合累计器 —— LiveTail 快照增 pending_hours / day_epoch+day_hours / month_epoch+month_days 冻结副本, 端点 agg 分支现算 live hour/day/month 行(v3_hour_agg / v3_rollup_agg)并入栅格映射。要点与代价:

  • hour 行可能与 agg.dat 已封行同 epoch(重封竞态), 需要 cov 加权合并规则(day/month 无此问题: 当前日/月行必然不在 agg.dat);
  • 发布面扩大(每轮多拷贝 pending 桶), 量级仍小(常态只含当前小时);
  • grouping 端点需逐成员合流后再 Σ; 测试面 = 时钟边界族(小时界/日界/月界) + 重封竞态。

实际修法与上述建议方向一致, 但 live 行的计算面从「端点现算」改道到「写侧现算」, 完整修法与改道原因见 §07「修复后补充」。

修复后补充（2026-10-14 · S7）

① 实际修法（方向与建议一致，计算面改道：端点现算 → 写侧现算）

建议修法的三个要点全部成立并已实施，但 live 行的计算面不在端点（Web 线程），而在写侧主循环线程：

  • 发布：traffic_sample_mod.py::_pending_agg_rows(agg, now) 纯函数由累计器现算未封口部分行——开放小时行（v4_hour_agg dt 加权）+ 当日 day 行（day_hours ∪ 开放小时部分行，逐级 v4_rollup_agg）+ 当月 month 行；以冻结 AggRow 元组进 LiveTail 第 8 字段 pending_agg（缺省空 = 纯磁盘读，向后兼容既有 7 参构造）。改道原因：计算收在单一主线程，不破黄金法则 5；Web 线程只读不可变行、零现算，也不受请求频率影响。
  • 合流：traffic_grid.py::v4_agg_obs_live(rows, live_rows, grid) 按 epoch 合流——开放桶（磁盘无同行）直映；已封桶残余（flush 竞态窗 / 迟到补记产生的同 epoch 双行）走 v4_merge_agg：cov 加权 avg / max 取大 / totals 取后封行 / cov 相加截到桶宽。与写侧 _agg_merge_prev 同判据，竞态窗内不双计、不出尖峰——建议里担心的「重封竞态」由此落地。
  • month 段铺格：build_month_grid 数据面计入活尾当月行——否则当前月桶整个不在栅格，合流结果被窗外过滤丢弃（all 窗修复前连 null 都没有，比 hour/day 段更重的形态）。
  • 组端点：空态判据（「组从未产过流量」）与逐成员 obs 均计入活尾——修复前成员仅活尾（零盘）会被误判空态返回 points: []；组尾桶 = Σ 成员观测（无行成员按 0 计），组口径不变。
  • degraded 不融合：read_agg OSError 路径不融合活尾，保持 last-good / stale 兜底语义，不以空态冒充无数据。
  • 前端零改动：points 末桶出值后 uPlot 数据驱动 x 轴自然延伸到当前桶，与 raw 段活尾同形态。
