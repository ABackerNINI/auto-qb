§05根因（方案选型结论）

两条路线都能解决同一个病（重启后 ETag 重验 + 串行放大），差别在代价与副作用：构建工具链把指纹做在部署前的产物里，运行时方案把指纹做在启动时的 URL 里。对本项目的决定性事实是——81 个脚本是运行时从 JSON 清单动态拼出来的，打包器做静态依赖分析看不见它们，要上构建就必须把装载器改成走打包器 manifest（等于重写 boot.js），风险直接压在首屏链路上；而构建工具链的独有优势（CDN 兼容、按文件细粒度失效、压缩合并）在本地部署、无 CDN、病在延迟不在体积的场景里要么不成立，要么超出需求。

2026-11-20 07:25 拍板（grilling Q4-Q8 按推荐）：暂缓构建工具链，先做运行时方案（查询参数指纹 + 并发化）。构建工具链留作未来若上 TypeScript / 压缩合并 / CDN 时的演进方向，届时本 issue 是现成的调查底稿。

§06优劣势对比（本 issue 核心）

构建工具链 · 优势

  1. 正确性久经考验：内容哈希写进文件名是行业事实标准（MDN 首选），缓存边界天然精确——文件名不变永久命中，变了才失效。
  2. CDN / 老代理兼容性最好：部分中间层对带 query string 的资源缓存行为不一致（有的不缓存带 ? 的请求），文件名哈希无此问题。（本项目本地部署无 CDN，这条当前不适用。）
  3. 按文件粒度失效：改一个 JS 只有它的 URL 变，其余继续命中缓存。
  4. 顺带收益：压缩、合并、tree-shaking、sourcemap、体积监控。
  5. 产物不可变可审计：dist/ 是快照，回滚 = 切回旧产物目录。

构建工具链 · 劣势（对本项目的具体代价）

  1. 改造面伤筋动骨：81 脚本 + 28 分片 + 四套手工皮肤 + 内联 manifest + CSS/字体全要交给构建器；现有测试大量钉死精确路径，产物名一改全线飘红，等于重写测试基线。
  2. 与 boot.js 机制根本冲突：脚本路径来自运行时 JSON 清单字符串，打包器静态分析看不见，81 个脚本不会被打包/哈希；除非把 loader 改成走打包器 chunk manifest——重写 boot.js，风险压到首屏链路。
  3. 引入整套工程负担：Node 工具链、lockfile、CI 加 build 步骤、每个开发者本地要构建；本项目是 Python 为主、复制目录即部署。
  4. 运维流程变化：升级从「覆盖文件 + 重启」变成「构建 + 部署 dist + 保留旧产物供回滚」。
  5. 收益超出需求：压缩/合并/tree-shaking 是额外好处，但本病（串行 × 高 TTFB）用并发化 + 消除重验就够。

运行时方案 · 优势（为什么暂时选它）

  1. 改动面小：boot.js 两处 URL 构造 + 一个哈希函数 + 中间件分流 + HTML 令牌；测试只加两组断言，不动四皮肤手工维护模式。
  2. 零新增依赖、零构建步骤：不碰 CI、不碰开发者工作流、不碰部署方式。
  3. 不会人为失误失效：版本号来自内容哈希，忘了手动 bump 也不会读到旧缓存。
  4. 故障回退一步到位：关掉分流开关立刻回到今天的 no-cache 行为。
  5. 正好打在根因上：校验请求归零 + 并发化，才够得到 ≤1.5s 门槛。

运行时方案 · 劣势（诚实列全）

  1. query string 通用性弱于文件名哈希：CDN 场景是真缺点，本项目无 CDN，风险近似为零。
  2. 全树一个版本号，非按文件粒度：任一文件改动，所有资源 URL 一起变、缓存一起失效。换来的是版本一致性——不会出现新旧文件混用这种更隐蔽的故障。
  3. 启动时遍历静态树算哈希：几十毫秒一次性成本；要排除日志 / .pyc 之类，否则哈希抖动。
  4. 手工复刻，长期维护责任在自己：不是社区标准件，边界情况（新增资源类型、特殊路径字符）要自己兜；好在代码量小、集中在单点。
  5. 不带来压缩/合并收益：若将来请求体体积成瓶颈，仍需上构建——但那是另一个问题，不混进这次修复。

演进路径

运行时方案建立的「资源 URL 集中生成」单点是向构建工具链演进的接缝：将来真要上打包器，只需把这个单点从「启动时算哈希 + 查询参数」换成「读构建产物清单 + 文件名哈希」，不必再动装载器结构与皮肤组织方式。
