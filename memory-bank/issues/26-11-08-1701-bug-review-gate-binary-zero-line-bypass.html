复验

复验：2026-11-08（认领时点）仍复现 —— decide() 首位 count == 0 and not sensitive 短路在位，本机 git 实测 tracked 二进制替换 numstat 计 -\t-\t 0 行，带不带 trailer 都不落基比对。复验中修正一处取证（§02 哈希行过于悲观）：tracked 二进制替换在 diff 文本里除恒定 Binary files ... differ 标记行外还有 index <旧blob>..<新blob> 行，内容变更会动 batch_base_hash（实测旧/新内容异值）；untracked 二进制照旧按原文字节入哈希 —— 即基比对本身对两类二进制都有效，病灶只在短路可达性。

修复后补充

实际修法 = 建议方案 A（用户拍板，与 §06 倾向一致）：check_review_trace.py decide() 的 count==0 静默短路改为仅对无 Review: trailer 的批生效；带 trailer 的 0 行批照走全链校验（· 基 必填 + 与闸门重算的整批过滤 diff 哈希比对，不一致判红给出路）。复验到的 git 行为见上：tracked 替换（index blob 行）与 untracked 新增（原文字节）带 trailer 时都能被 D6 比对判红，一致（评审时点 pack 的基 = 提交时点重算）则放行。残余窗口（如实记录）：0 行批无 trailer 的静默通路按方案 A 有意保留 —— 二进制改动若不写 trailer 仍静默放行；本轮不为它扩机制（tracked 原位替换的哈希面已证可检，真正豁口只剩「不写 trailer」这条人为通路），是否收口留给用户决定。衍生修复：方案 A 撞出一处假红面 —— HEAD 消息（手工预览/复跑面）的 0 行批保持静默：HEAD 上的 trailer 描述的是已入库的上一批，锚点已推进到它，对空批校验历史 trailer 的行数/基是假红；提交面消息恒来自 file/default（commit.py 经 env 递入），不受影响，不开旁路。验证：review 包定向 pytest 117 passed（含新增 5 例：decide 面 2 + 端到端 3）→ test.pkg 全包 404 passed + 15 subtests → test.quick 5855 passed / 2 skipped。声明面同步三处：本脚本模块头判据 1 / decide docstring / main 注释、.commands/review/config.toml review.trace note、code-review SKILL.md 铁律「残余窗口」段（0 行二进制窗口 → 0 行无 trailer 窗口）。
