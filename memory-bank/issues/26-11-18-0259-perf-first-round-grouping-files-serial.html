§01现象与发现场景

立项分析轮(plan 26-11-18-0259 §02.2)取证撞见: auto-qb 重启后 store 为空, 首个同步必为全量轮, 全部种子走 torrents_added 相位 —— 归组一步对每个新增种子单发一次 qB files API, 主循环线程串行, 与用户报告的「重启后 WebUI 首份数据 5-15s(约 210 种子)」直接相关。与平台/配置无关, 种子量线性放大。

§03影响面

维度结论
触发条件auto-qb 进程重启(store 空)后的首个全量同步; 种子量线性放大(210 ≈ 2-6s, 千级更显著); 平台/配置无关
影响范围主循环线程整条管线时长(首轮): groups 视图首份数据、首轮任务线节拍、同步线被推迟; 与「首轮管线挡首次发布」同根(plan 26-11-18-0259 §02.2), 提前发布(S1)修掉 UI 空窗后, 本件独立决定 groups 第二跳时刻
严重度中 —— 重启后分组数据晚 2-6s(210 种子量级); 不影响稳态(增量轮 added=∅ 不触发)

§05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已知机制(非猜测, 取证见 §02): qB WebAPI files 端点单 hash 专用, 无法批量合并 → N 种子 = N 次串行往返; 且全部落在主循环线程的首轮关键路径上(与主循环 flush 的含数据代同拍串行)。已排除: 归组逻辑本身的 CPU 开销(文件映射/组键计算为内存操作, 毫秒级)。

§06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向: 把首轮 files 拉取从「单轮全量串行」改为「按预算分 tick 渐进归组」, 主循环每 tick 拉一部分(先例: SEARCH_INDEX_BUILD_BUDGET=500, webui/views_common.py), 组视图渐进落位。

  • 候选① 预算化分 tick: 每轮拉 BUDGET 条, 未完保持 dirty 下轮续 —— 代价: 归组完成时间拉长(但不再阻塞整拍); 需处理「归组进行中」的视图语义(plan 26-11-18-0259 S1 的基础视图已是 groups 空形态, 兼容)。
  • 候选② 挪工作线程: 后台线程拉 files + 结论回灌主循环(并发约束口径: 工作线程不写共享结构, 26-11-11-0039 §02) —— 代价: 状态机复杂度 + qB 并发请求面。
  • 判据: real-machine 轨道 ≈210 假种子, 重启后 groups 第二跳时刻显著缩短且主循环单拍不再被 files 拉取占满(拍时长 ≤ 500ms 线(26-11-11-0039 §01 用户口径, 非命令慢日志线 CMD_SLOW_MS=300ms)); 静态守阵钉预算常量消费位。
