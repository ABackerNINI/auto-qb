01现象与发现场景

跳检（删种重加 + seedMode=true）时若本地数据并不完整，libtorrent 仍会进入 seed mode，并立刻向 tracker 宣告 left=0（is_seed() 在 seed mode 下恒真、bytes_left() 恒 0）。此时没有任何校验发生。

一旦有 peer 请求到坏片，整片哈希失败 → 离开 seed mode → 全量重校验 → 缺口暴露 → 重新下载。这部分下载计入站点下载量，不可逆（分享率、HR、配额）。

发现场景：2026-10-22 会话核查 qb/libtorrent 跳检机制时，用户指出报告只算了 I/O 与时间成本，漏了下载量这条硬成本；据此补入调查报告 memory-bank/reports/26-10-22-0234-report-skip-check-arch.html §2.10（R2），并把"缺防线"单独立此条。

与配置相关：仅当允许跳检（web.skip_check_menu 放行或规则 checking.mode=skip-checking）且数据不完整时发生。完整数据不会触发下载。

03影响面

维度结论
触发条件允许跳检 + 数据不完整（progress 落在 (0,1)，或文件尺寸相同但内容被替换）+ 有 peer 请求到坏片。三者同时成立才触发下载。
影响范围规则源与 WEB 手动两个跳检入口都受影响；损失与种子大小成正比（按整片重下，piece 4–16 MiB 为放大单位）；直接作用于站点下载量、分享率与 HR 判定。
严重度中。数据不会外传、且最终会自愈，但下载量不可逆；残缺比例高的大种一次可损失数十 GB，且发现时点不可控（可能是配额紧张时）。

05根因（可选）

跳检的完整性判定只有"文件存在 + 尺寸不小于"，不读内容；而稀疏预分配使尺寸恰好等于完整尺寸，于是"部分下载"与"内容被替换"这两类残缺都能过闸。

引擎的惰性校验只保证不外传坏数据，并不阻止触发重新下载——这是两个不同后果，前者被解决了，后者没有。项目侧缺的正是"用少量读盘证明完整性"这一环。

已排除：① 站点侧记账异常（本次不涉及）；② 数据外传（发块前整片哈希，坏片不外发，见调查报告 §2.5）。

06建议修法（可选）

判断完整性只有两种货币：读盘（免费、慢）与下载（花钱、不可逆）。跳检的实质是"先不付读盘，赌不用付下载"。所以完全避免 = 不跳检；可行的方向是用少量读盘把赌注压小，再用限速兜底。三层可独立实施：

  1. 抽样校验（核心）：跳检前用 torrents_piece_hashes + torrents_files + piece_size 算出 piece→文件偏移映射，自读 N 片（建议 16 片）算 sha1 比对。全过则放行，有失败则转全量校验或拒绝跳检。成本 = N × piece_size 读盘，零下载量。抽样策略：优先抽每个文件的尾部片与跨文件边界的片（部分下载总是尾部缺失，命中率最高），再均匀随机补几片（防内容被替换）。
  2. 下载限速保险丝：重加时带极小的 per-torrent dlLimit（如 10 KB/s）；监控 amount_left 从 0 变正 / progress 从 1 掉下 / state 进入 checkingUP→checkingDL，命中即 pause + 告警；连续 N 小时无回退则解除限速。损失上限 = 限速 × 检测延迟。
  3. 结构性收紧：带 zSkipChecked 标签的种禁止再次跳检；按种子大小设阈值，超过阈值强制走"有参考种子"分支；参考种加时效约束（参考种自己也可能后来被改）。

代价与边界：抽样需要正确的 piece→文件偏移映射（含 pad file、多文件跨片），实现有边界复杂度；抽样挡不住零星坏片，但零星坏片的损失本身就是整片级（4–16 MiB），正好由保险丝封顶。保险丝会拖慢"确实需要补齐"的场景，需设自动解除条件。

已排除的方案（勿再试）：upload_mode 当闩——libtorrent 有该 flag，但 qB 只用于加 magnet 元数据并把它当错误态暴露（torrentimpl.cpp:1361/1380），WebUI 无端点，且 auto_managed 下 libtorrent 会自动退出该模式；seed_mode 加种后不能再置位（torrent_flags.hpp:41-42），所以无法"先普通加种校验、再切 seed mode"；也不存在"只校验不上传"的 API。
