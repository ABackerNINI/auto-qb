01现象与发现场景

发现场景: 2026-09-25 修「设置页刷新会回到种子页」(档案 tasks/26-09-25-webui-page-location-persist.md) 时顺路发现 —— 位置持久化让刷新后停在设置页了, 但页面上的未保存改动仍会被服务端树覆盖。同一轮我在 startPolling() 尾部新增了一次 cfgLoad() (设置页配置树是按需加载的, 刷新后必须补一次), 而那次调用必然重取 /api/config ⇒ 内存里的 cfg.tree 每次页面加载都被磁盘版本整体替换。

触发条件(任选其一, 共同点是"页面重载"): 按 F5 / Ctrl+R · 从地址栏重新回车 · 关标签再开 · 点浏览器后退 / 前进 · 硬刷新。

表现: 无确认框、无 toast、无日志 —— 改动直接消失, 且"有改动还没保存"的提示也一并消失 (脏标记跟着被重置), 事后看不出"刚才改过"。

平台 / 皮肤: 与平台无关(纯前端); 棱镜 /prism/ 与星图 /atlas/ 同形 —— 共用 shared/config_editor.js 的同一套 cfg* 读写。

实测复现(2026-09-25 17:0x, scripts/ui_harness.py --torrents 60 --port 8156 桩服务 + 真 chromium): 进设置页 → 把「界面 → 端口」改成 59999(走与输入框同一个 cfg* 写入面) → 按 F5。

03影响面

维度结论
触发条件设置页有任何未保存改动时, 任何页面重载动作必现(与站点数 / 种子数 / 配置内容无关); 无改动时无影响
影响范围设置页是唯一配置编辑入口(Console Hub; 经典设置页已于 2026-09-25 移除)⇒ 全部配置项都在射程内。两套 UI 同形。保存成功过的项不受影响(PUT /api/config 立即落盘)
严重度中 —— 不损坏数据、不报错(纯静默), 但手改多项后误按 F5 要全部重做; 危险档字段(qbittorrent.password / web.host / data_dir)重填成本与填错概率都高。不判"高": 只在用户主动重载时发生, 且不做任何破坏性写入

04定位锚点

写「符号名 + grep 关键词 + 当时的行号（标取证时间）」—— 代码会漂移，靠符号与 grep 重新定位，行号只是加速项。

  • shared/config_editor.js:56(取证 2026-09-25 17:02)· cfgDirty() · grep cfgDirty —— 脏判据(JSON 快照对比 cfg.baseline)
  • shared/config_editor.js:143 / :160 · cfgLoad() / cfgSetTree(tree) · grep cfgSetTree —— 加载即 cfg.tree = tree 并把 baseline 重置为服务端版本, 这是覆盖内存改动的唯一位置
  • shared/app.js:1003 · startPolling() 尾部的 cfgLoad() 调用(2026-09-25 新增) · grep page === "settings" —— 页面加载路径上"必定重取树"的那一处
  • 模板落点: prism/index.html / atlas/index.html 的 <main v-if="page==='settings'" class="ce-page hub-page">; 脏提示与保存按钮在 config_hub.js 的 hubStats(dirty: this.cfgDirty)
  • 反向证据: grep -rn "beforeunload" src/auto_qb/webui/static = 0 命中

05根因（可选）

已确认(实测, 非推断): 配置树 cfg.tree 是纯内存态, 全仓没有把它写进 localStorage / sessionStorage 的路径; 而页面加载路径必定调一次 cfgLoad() → cfgSetTree() 用服务端树整体替换内存树并把 baseline 重置为服务端版本 ⇒ 未保存改动被覆盖, 且 cfgDirty 随之回 false(连"刚才有改动"的痕迹都没了)。 全仓无 beforeunload 监听 ⇒ 无提醒。
已排除: ①不是 localStorage 被清 —— 位置(autoqb.ui.page)与列偏好提示标记刷新后都还在; ②不是保存失败 —— server === null 说明压根没发出保存请求。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  • A. beforeunload 守卫(最小): cfgDirty 为真时挂 beforeunload 并 preventDefault()。代价: 浏览器只给通用文案(无法自定义), 且不覆盖"后退"(需 pushState 兜底); 好处是判据单一、零副作用、可独立验证。
  • B. 会话内快照(体验最好): 脏时把 cfg.tree 写 sessionStorage, 启动 cfgLoad() 之后用冲突提示条问"发现未保存改动, 恢复 / 丢弃"(而不是静默采用)。 代价: 要定义"内存版 vs 磁盘版"的分叉语义(可参照列偏好的"意图 vs 派生"判据), 需新判据 + 守阵。
  • C. 只提示不恢复: 页面内常驻"有改动没保存"提示 + A 的守卫。解决"误刷新", 不解决"误刷新后重做"。

倾向: A 先落地(一行判据、独立可验证), B 视是否真丢过改动再排。⚠ 倾向只是建议, 拍板在用户。
