01现象

agg 段窗（3d/7d/30d/6mo/1y/all）的速率 lane 只按写侧记录的瞬时速率加权平均，而空闲 z 游程内部每个槽区间入账的速率恒为 0 ⟹ 低载日里游程期间真实走过的字节（seed↔seed 冗余连接的握手字节 + 模型化 IP/TCP 开销，机理见报告 26-10-15-0728 §04.5）从未以任何形式进入过任何一个 hour 行的 avg。极端情形已在 2026-10-15 取证实例上实测：某天全天 dl_max=0、而 alltime 实增数百 MB —— 图上显示约 0，字节确实走了。

这不是 bug，是口径判断题：要修就得先回答「速率图里的「速率」要不要包含非 payload 成分（握手字节 + 模型化 IP 开销）」。答了才能动手，所以本件是 question 而非 bug。

与 26-10-16-0020-bug-agg-hour-totals-frozen-run 同源同症状（都是 z 游程期间的隐形增长），但那条是归属错误（确定该修），本条是口径选择（待拍板）。

03建议（可选）

先拍板，再动手。两个互斥取向：

  • 维持现状（payload 口径）：速率图只表达 payload 速率，非 payload 成分当作本案之外的东西 —— 代价是低载日 3d+ 视图长期系统性偏低（甚至显示 0）。
  • 改成总字节口径：游程内部区间按 Δtotals / Δt 派生一个平均速率入账，图的语义变成「该时段平均每秒过了多少字节」。代价是①空闲期不再显示 0，可能被误读成「 idle 还在下载」；②与既有「基线几百 B/s 不是读数噪声」的口径笔记要一起改；③dl_max 会被派生值污染，需另行处理。

无论选哪支，都不必碰 raw 面（≤24h） —— 那里同样症状已由计划 26-10-15-0829 的 P2 摊配修好。另注：同批入池的 agg 行 totals 归属件 是确定该修的那一半，它不需要回答本条的口径问题，两条可各自独立推进。
