01现象与发现场景

怎么撞见的：排查本次「图表显示异常」时需要排除「前端渲染停摆」这一可能（用户第一张截图一度被怀疑是卡锁）。读前端取数链发现：api() → _request() → 裸 fetch()，全程无超时、无 AbortController；而流量图轮询的 loading 标志只在这一段之后（finally）复位。

现象：只要一次请求悬挂（服务端不响应 / TCP 半开 / 代理卡住），await 永不返回 → finally 不执行 → loading 恒为 true → 轮询每一拍都被守卫挡掉 → 图表永久停在旧帧，界面上没有任何错误文案或提示。此后即使后端已恢复，也必须手动刷新页面才自愈。

触发条件：任何导致单个请求不返回的情形。不需要后端崩溃 —— 网络抖动、连接被中间设备静默丢弃、代理在超时前挂住都可能命中。

03影响面

维度结论
触发条件任一次 api 请求悬挂。与后端是否健康无关 —— 只需连接层静默失效。
影响范围全部走 api() 的前端轮询（流量图三挂点、状态栏、抽屉等共用同一个 _request），不止流量图。流量图侧的具体后果：图表停在旧帧、无错误文案、无 stale 标记、换窗/换目标的轮询重排也一并失效。
严重度中。不自愈是关键 —— 用户看到的是「数据不再更新」，与「真没流量」在视觉上不可区分，且没有任何线索指向「请求卡住了」。排查成本高（本次会话中曾因此误判方向）。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（读码）：loading 是一个单向的「请求在途」标志 —— 入口无条件置 true，唯一的复位路径是 _qbLoad 的 finally，而 finally 只有在 try 块退出时才执行。裸 fetch() 没有超时，因此「永不返回」在实现上是可达状态；一旦进入该状态，复位路径不存在，轮询守卫（this[def.loading]）又把后续每一拍挡掉 ⇒ 自愈路径被自身封死。

已排除：不是 stale 守卫的问题（那是 10-12 已修的另一条）；不是后端接口挂起 —— 后端有独立的路由超时与降级返回（degraded → last-good），本条只谈前端侧的兜底缺失。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  1. 请求级超时（推荐）：_request 用 AbortController + setTimeout 给每次 fetch 一个上限（如 15s），超时抛错 —— 让 finally 有机会执行。AbortController 已在使用（10-12 卡锁修复同链）还是需引入，认领时先确认。
  2. loading 加时间戳兜底：轮询守卫改为「loading 且未超过 N 秒」才跳过，超时则强制释放并记一次前端警告。与方案 1 互补：前者治请求、后者治标志，即使有别的原因让 finally 走不到也能自愈。
  3. 暴露给用户：连续 N 拍未成功落袋时，在图面上显示「数据更新失败」提示（复用 P4 的 .qb-stale 样式与位置）。代价：新增一个 UI 状态，需与既有 stale/空态文案去重。

方案 1 + 2 是同一处改动的两面，建议一起做。
