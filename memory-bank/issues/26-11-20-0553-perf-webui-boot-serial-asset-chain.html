§01现象与发现场景

真机轨(环境1 副实例 36596)追查「重启后 WebUI 主界面 5-15s 不可见」时顺带量到: 前端启动链 boot.js 严格串行拉 28 个模板分片 + 81 个脚本 ≈ 109 个串行请求(稳态首屏框架可见约 1.4s)。用户复测反馈: 本地部署下 ctrl+F5 硬刷新仅 1-2s —— 说明这条链本身在本地不是 5-15s 卡顿的主因; 但它把单请求延迟线性放大(注入实验实测), 是一个独立的首屏性能面, 入池另案。

§03影响面

维度结论
触发条件每次页面加载(冷加载/刷新)都要走全链; 单请求延迟越高(远程/代理/磁盘慢)放大越显著
影响范围三皮肤共用 boot.js; 框架可见时间(导航栏/状态栏/vue mount 前的白屏段)
严重度低-中 —— 本地稳态约 1.4s 可接受; 用户复测硬刷新 1-2s, 非本次重启 5-15s 卡顿主因

§05根因（可选）

启动链结构: 分片逐个 fetch(等上一个 then 才发下一个) + 脚本 onload 链式逐个插, 109 个请求严格串行, 无并发无预加载; 每个请求的往返延迟累加成首屏时间。no-cache 使刷新时每个资源仍需 ETag 校验往返(304 也占一趟)。

2026-11-20 07:06 更正: 早先「非本次根因」的判断已被真机逐阶段桩推翻 —— 见 §08。当时依据「ctrl+F5 仅 1-2s」排除, 属误判: 稳态下连接复用 + 304 校验使单请求延迟低, 才显快; 重启后 109 个资源逐个回源校验(ttfb 54-166ms), 串行累加成 10.5s。本 issue 现为「重启后 5-15s 白屏」的根因, 原排除段保留作误判留痕。

§06建议修法（可选）

方向: 把 109 个串行请求改并发/打包, 砍掉线性放大。候选: ①分片 Promise.all 并发 fetch(顺序注入仍保序) —— 收益大, 代价低; ②脚本改 type=module 或并发 preload + 显式排序执行 —— 需处理当前的严格顺序依赖与 top-level const 冲突约束; ③服务端对 immutable 静态资源上长缓存 + 内容 hash 文件名, 刷新走本地缓存免 ETag 往返 —— 与升级即有新文件的机制要协调。三案不互斥, 可分期。

§08根因坐实：真机逐阶段桩（2026-11-20 07:06）

诊断分支 diag/webui-boot-probe-stub 在前端 boot 链插入计时桩(window.__AQBP.dump()), 用户真机(约 210 种子、本地部署、atlas 皮肤)重启后刷新取数。原样贴证据:

分段汇总: 28 分片串行 2,747ms(98ms/片) + 81 脚本串行 7,754ms(96ms/脚本) = 10,500ms, 占首屏 12,037ms 的 87%; HTML TTFB 894ms(7%) + head 565ms(5%) + Vue mount 69ms(1%)。对照本地无头浏览器: 分片 4ms/片、脚本 5ms/脚本, 框架可见约 0.9s —— 同一条链, 单请求延迟差约 20 倍, 被 109 次串行线性放大。

为什么 ctrl+F5 反而快: 稳态下连接复用 + ETag 校验走 304(无响应体), 单请求延迟低; 重启后缓存状态冷、109 个资源逐个回源算 ETag, 才暴露线性放大。这条曾被用来排除本 issue, 实为误判。

后端无罪: config_public_req 在 12.036s(框架可见那一刻)才首次发出, /api/state 更早不在链上 —— 「首轮数据管线挡发布」的方向彻底排除。

修法方向收敛: ttfb 高来自 static_ui.py::_static_no_cache 的 Cache-Control: no-cache 强制每次 ETag 重验 + StaticFiles 每请求 stat/读文件。治本 = 静态资源内容指纹化文件名 + immutable 长缓存(109 次校验请求归零), 配套保留 index.html/manifest 的 no-cache 以防升级后旧缓存; 治标 = 分片 Promise.all 并发 + 脚本并发预取。指纹化必须同步解决「升级后不加载旧文件」的兼容性(当初 no-cache 的立项目的)。
