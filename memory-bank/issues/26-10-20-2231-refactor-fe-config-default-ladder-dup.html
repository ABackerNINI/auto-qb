01现象

现象: "按 schema 形状给出默认值"这条阶梯有三处实现, 且互相嵌套调用 —— 改一处会影响另两处的行为边界。

  • config_editor.js::cfgDefaultForField(字段级: kind → 默认值);
  • config_rules.js::cfgPluginDefaultSpec(插件 spec 级, 内部调字段级);
  • config_rules.js::cfgPluginDefaultSection(section 级, 内部调 spec 级)。

02位置

  • src/auto_qb/webui/static/shared/config_rules.js grep cfgPluginDefault。
  • 明细台账: R20-C-05。

03建议（可选）

收敛为一条递归阶梯(defaultFor(schemaNode)), 三层只是递归深度不同。风险中 —— 三处互嵌套, 需先画清"哪层补哪个键"的边界再动。

04修复与验证（2026-10-21 认领并修）

复验(认领后第一件事, 2026-10-21 03:05): 现象仍在 —— 三处行号与入池记录一致 (config_editor.js:634-644 / config_rules.js:181-200 · 201-208), 三处各写一份「按 schema 形状造初值」的循环, 插件两份仍互嵌套; 测试侧零守阵(grep 实证)。

先画清边界再动(§03 点名的前置动作): 三处看似同构, 实则各留了刻意的分歧, 收敛时一律保留 —— ①插件 spec_kind=bool 初值 "true"(新动作默认开)而字段 kind=bool 是 "false"; ②object spec 只填必填子字段, 但它的 object 子段按全字段口径(且不再递归); ③可选段非 object 字段的历史口径是 []; ④未知 spec_kind 沿用子表单口径。 这四条正是"哪层补哪个键"的边界本身。

实际修法: 收敛成一条下降链, 三处的差异退化成 opts 开关(不再是三份代码) ——

  • config_editor.js 新增阶梯单点 cfgDefaultScalar(node, opts)(叶子 → 标量: enum→options[0] / bool→boolOn ? "true" : "false" / 其它→placeholder 或 cfgScalar(default))与 cfgDefaultForFields(fields, opts)(字段清单 → 对象; object 且 recurse 时再下一层); opts 三个开关 = requiredOnly / recurse / boolOn。可选段入口 cfgDefaultForField 退化为薄壳(非 object 仍返回 [])。
  • config_rules.js 两份手搓循环(cfgPluginDefaultSpec / cfgPluginDefaultSection)删除, 换为插件形态分派 cfgDefaultForPlugin(meta): 按 spec_kind 选 列表([]) / 子表单(必填优先 + object 子段递归) / 叶子(走 cfgDefaultScalar, bool 的分歧交给 boolOn); 单值形态取值域收成模块级 SPEC_SCALAR_KINDS(与后端 Plugin.spec_kind 对应), 不在列者沿用旧的子表单口径。
  • 结果: 新增一种 kind 的默认值规则 = 只改 cfgDefaultScalar 一处; 插件侧手搓字段循环 归零(for (const f of 计数 2 → 0), enum 首选项默认值全仓一处。

行为等价性实证(不是"看着一样", 是跑出来的): 改动前(HEAD)与改动后各跑同一批输入, 输出逐字节一致 —— ①合成 schema 电池 10 项(插件 bool/list/enum/str/object/未知形态 + 可选段两类 + 字段级三类)全等; ②真实 schema 全量对照: 从后端 schema_payload() 导出真 schema, 对全部 25 个插件 (13 条件 + 12 动作)的 spec 初值与全部 18 个 object 段的可选段初值各算一遍, 两份 JSON diff 为空。

守阵: tests/test_webui_static_dom_page.py::test_frontend_config_default_ladder_single_point —— 形态六查(三单点各定义一处 / 旧 cfgPluginDefaultSpec|Section 零残留 / 插件侧零手搓循环 / options[0] 全仓一处 / 两入口体内无循环只转调 / 恒久活性探针钉住两个入口的调用点 —— 入口被删光会让前面五查恒真) + 有 node 时真跑 11 项语义电池, 把上面四条分歧逐条钉死; 日后谁"顺手统一"了某条口径, 这里立刻红。无 node 静默跳电池(不引入 skip)。

验证(红验三类突变 + 测试数字): 三类突变全部符合预期 —— ①把 cfgDefaultScalar 的 bool 分支 改成一律 "false"(把插件/字段口径"顺手统一") ⇒ 红, 报「行为漂移: 插件 bool spec 初值 = "true"(与字段级 "false" 的分歧点)」; ②config_rules.js 里重新手搓一个字段循环 ⇒ 红, 报 「又出现了手搓的字段循环」; ③cfgToggleSection 不再调 cfgDefaultForField ⇒ 红, 报 「可选段初值入口断了」(活性探针)。三类均以精确反向编辑还原, git diff -- src/ 只剩本轮有意的收敛改动。 测试数字: 新守阵单跑 1 passed; commands run test.full 3967 passed / 10 skipped / TOTAL 99% (20467 语句 / 7012 分支, 各 93 单位缺口; 覆盖率闸 99% 照过) —— 数字誊至基线切片 memory-bank/testing/baselines/26-10-21-0323-dup-code-audit.md(最新值见 commands run kb.baseline)。

与建议(§03)的口径对齐: 建议是「一条递归 defaultFor(schemaNode), 三层只是递归深度不同」 —— 实际落地的正是这个形状(递归深度由 recurse 开关表达), 只是叶子与容器分成两个函数: 容器要遍历字段清单、叶子只认单个节点, 合成一个函数会让"只填必填""bool 开/关"这类开关挂在不适用的那一半上。 §03 点名的风险(三处互嵌套)已按它自己的要求先画边界(见上)再动。
