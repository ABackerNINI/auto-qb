01现象与发现场景

2026-11-04 05:53 与 05:57 在 Windows 本机连续跑两次 commands run test.full（仓库根全量，pytest-xdist 并行），两次都在同一条用例判红；同 HEAD 下把该用例单独跑则通过。触发场景是「全量 + 并行」：用例断言 threading.active_count() 在采样前后不变，失败值为 3 == 4（采样后 3、采样前 4），方向是「有线程减少」而非产品新增线程。

该用例本身验证的黄金法则 5（单写线程：批量落盘发生在调用钩子的线程内、模块不建线程），与产品功能无直接关联；红的是门禁稳定性。

05根因（可选）

机制确定（2026-11-04 06:32 修复时归因）：assert threading.active_count() == threads_before 量的是进程级全局快照相等，而 pytest-xdist 的每个 worker 是一个常驻进程 —— 同 worker 上其它用例（或其拆卸路径）启停的无关线程只要落在采样窗口内退出，计数就 4→3 判红。方向（减少而非新增）与「产品建线程」相反，产品侧经查只用 threading.Lock 不建线程，不变式本身成立；红的是量法：把「本模块不建线程」错量成了「全进程线程数不变」。至于具体是哪个无关线程退出，与修复无关，未追。

06建议修法（可选）

待定（以下候选均未验证）：

  • 候选 1：断言从「全局 active_count 快照相等」改为「采样前后线程集合的差集里没有本模块新建的线程」，允许无关线程自然退出；代价是用例断言实现更复杂。
  • 候选 2：为该用例加 xdist 串行/独占标记，降低同 worker 上其它用例线程启停的干扰；代价是全量耗时增加。

不建议用「失败自动重试」掩盖，重试会丢失门禁信号。

修复后补充（2026-11-04 06:32）

实际修法：走了建议修法之外的第三条路 —— 不再量任何全局快照/差集，改在 on_task_line 的同步窗口内 spy threading.Thread.start（monkeypatch 包装记录线程名），断言窗口内没有启动任何线程。三个候选的取舍：

  • 候选 1（线程集合差集）未采用：差集里出现「新线程」仍可能是同 worker 无关用例恰好在窗口内启动线程，污染面只是从「退出方向」换成「启动方向」，没根除。
  • 候选 2（xdist 独占/串行标记）未采用：治标且拖慢全量。
  • 实际采用 spy 量法：窗口是同步调用，只有被测模块自己的代码会经过 spy，对无关线程启停天然免疫；且比快照更强 —— 「窗口内建线程又 join 掉」的形态快照抓不到、spy 抓得到。

验证方式与测试数字（均为 2026-11-04 实测）：①红验 —— 向 on_task_line 临时注入 Thread(target=lambda: None).start() 突变，单跑判红且报错直指 模块新建了线程: ['mutation-probe']，还原后转绿（红绿双验齐）；②单文件 commands run test.one -- tests/test_traffic_store_codec.py 27 passed；③修复后全量 commands run test.full：5134 passed, 10 skipped in 195.00s，覆盖率 99%，门禁绿。改动仅 tests/test_traffic_store_codec.py 一处（原 197-201 行快照断言段），产品代码零改动。
