01现象与发现场景

乐观 UI 扩面分析（计划 26-10-30-0610）期间用户反馈：生产 WebUI（种子库 <100）添加种子后新种子出现「肯定长于 1 秒」。同日真机复测（qBittorrent-testing 5.2.3 @127.0.0.1:36595，auto-qb 独立配置 8 种子库）证明服务端 ~20ms 就已发布新数据；把前端 SSE 摘掉、只按 1.5s 定档轮询模拟，可见延迟立即抬到 ~1.19s，与用户观察吻合 —— SSE 失效时所有命令的反馈都退化为「等下一轮轮询」。用户拍板：暂不修，先入池。

03影响面

维度结论
触发条件SSE 通道失效（反代/远程访问缓冲、换票失败重连窗、后端重启），或页面跑旧 bundle（无 ver 处理）——SSE 断本身有断线 toast 提示，但用户未必留意
影响范围全部命令反馈与状态变化的新鲜度（不只添加种子）——ver 驱动的刷新全部退化为 basePollMs 节拍；种子库 ≤1000 时该节拍恒 1500ms
严重度低~中（可用性劣化非功能损坏；SSE 正常时无感）

04定位锚点

  • polling.js:264-270 basePollMs（取证 2026-10-30）· ≤1000 种子恒 1500ms · grep basePollMs / 1500
  • polling.js:271-279 currentPollMs · 无「无变化退避」（曾有，因状态栏与行数据新鲜度解耦被废），只剩失败退避 min(15000, base×2^pollFails)
  • polling.js:245-254 scheduleNext · 链式 setTimeout：上一拍 refresh 落定后 +1500ms，实际周期 ≈1500ms+RTT
  • polling.js:62-67 ver 事件 → 60ms 去抖 → refresh（SSE 通时唯一加速通道）；_esConnected 为断线态判据
  • runtime.py:499 consume_commands / qbmanager.py:554 · 服务端侧：RESYNC 命令后同拍补刷新+发布，与前端是否在线无关（实测证实）

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（2026-10-30 实测）：不是服务端慢、不是大库（已排除：用户库 <100 且 8 种子复测同样 ~1.2s）——是「ver 推送失效后，回执到达不触发任何刷新」的结构性缺口：回执（cmd 事件或轮询 /api/cmd）兑现 waitCmd 后，前端只等被动通道（ver 或 1.5s 节拍），断线态下没有主动补刷。补刷新+发布在回执后 ~10-20ms 完成，与服务端就绪之间只差一次主动拉取。

06建议修法（可选）

候选 A（推荐，零后端）：SSE 掉线态（_esConnected !== true）下，waitCmd 回执兑现后 ~100ms 武装一次定向 refresh()（补刷新+视图发布已完成，避开 runtime.py:539 记载的扑空窗口——实测该窗口 <10ms），把断线态反馈从 ~1.2s 压回 ~150ms。代价小、不碰乐观 UI 与服务端；注意与 26-10-21-2323「减少直查」方向一致（只是拉既有 /api/state，不新增端点）。候选 B：回执携带「补刷新已完成」标记，前端据此立即刷新——需要后端改回执，收益同 A，代价高，不推荐。候选 C：断线态把 basePollMs 降到 500ms 兜底——请求数 ×3，治标，仅作 A 的补充。
