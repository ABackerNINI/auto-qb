批量添加种子时部分新行要等下一轮同步(1.5s): 补刷新赶在 qB 把种子建进 session 之前, 与 SSE 无关

一次添加 N 个种子时, 主循环在命令后只补刷新一次(距 add 返回 0.5~0.8ms), 而 qB 的 add 是四跳异步管线: HTTP 200 只代表「已受理」, torrent 真正进 session 还要 6~40ms ⇒ 补刷新只拿到此刻已建好的那部分, 其余等下一个同步节拍(1.5s)。真机实测: N=6 有 22%、N=12 有 44% 的种子落在 ~1.53s, 其余 ~25ms; N=1 五轮全 ≤23ms 从不复现。

01现象与发现场景

用户在真实 WebUI 上一次添加多个种子时观察到: 列表里「一部分种子立刻就出来了(毫秒级), 另一部分明显要等一秒以上」, 当时的描述是「肯定长于 1 秒」。原报告(2026-10-30)把它归因为「SSE 掉线时 ver 推送失效, 前端退化为 1.5s 定档轮询」, 并用「摘掉 SSE、只按 1.5s 轮询」的对照复现出 ~1.19s。

2026-11-01 认领复验后, 原归因被推翻——三条都站不住:

  • 不是「SSE 掉线时」才发生: 下面 §02 的全部实测里 SSE 通道全程健康(ver 事件正常到达), 现象照旧复现。
  • 不是「全部种子都长于 1 秒」: 同一批里一部分 ~25ms、一部分 ~1.53s, 与用户观察一致, 原报告的「~1.19s 均值」掩盖了这个双峰。
  • 原对照测的是「单种子添加」: 单种子 5/5 轮全部 ≤23ms, 从来不输这场竞态 —— 于是「摘掉 SSE 就变 1.2s」被误读成「SSE 是原因」, 实际它只是把一个本来就不稳定的过程放大了。
真机环境(§02 全部数据): qBittorrent 5.2.3 @ 127.0.0.1:36596(空库副实例, real.guard 通过: 真实种子 0 个/全暂停), 产品用 tests-real/lib/app.py 起独立临时配置(数据目录隔离, 非仓库根 config.yml), WEB 端口 39000 段, 种子为内存现造的 L1 假种子(real-fake 标签, 无 announce, paused 添加, 全程非活跃), 每轮跑完按 hash 删除。跑完两个实例种子数均回到 0。

三点结论:

  • 回执是乐观的: success_count=N 在一个 torrent 都还没建的时候就已经写好了(§02-D: qb_add 3.5ms → success_count=6)。
  • 同一批的 N 个 add 串行: 每个都要过一次 ioThread 的文件搜索(单线程, :724-725), 第 N 个进 session 的时刻随 N 往后推 —— 这就是「批量才有、单个几乎没有」的来源。
  • 两个端点不会打架: makeMaindataSnapshot(synccontroller.cpp:552)与 infoAction(torrentscontroller.cpp:689)都遍历 session->torrents(); 而 m_torrents.insert 与 emit torrentAdded 在同一趟 readAlerts 里同步完成(WebUI 组件未 moveToThread, 与 session 同在应用主线程, 信号直连) ⇒ 任何时刻两者要么都有、要么都没有, 与 §02-E 的 34 个采样点一致。

由此也能解释 §02-A 的形态: 补刷新发出在 add 返回后 0.5~0.8ms, 但 qB 处理它要到 ~4~7ms(事件循环里排在告警批处理后面); 那几毫秒里管线只走完一部分, 于是拿到的既不是 0 也不是 N, 而是「已经建好的那几个」。N=1 时管线只有一次搜索、不与别人排队, 补刷新那一问通常赶得上(5/5 轮实测都在 13~23ms 内落地), 所以从不复现。

03影响面

维度结论
触发条件一次命令里添加多个种子(files_b64 多条 / 多条链接)。SSE 状态无关; 库大小无关(测试库 0~12 个种子); 视图无关(group/torrent 两种视图都复现)。单种子添加基本不触发(5/5 轮未复现)。
影响范围只影响「新行出现」这一类反馈 —— 添加种子是唯一没有乐观补丁也没有真值事件的命令(暂停/开始有补丁+truth, 重命名有补丁), 它的行只能从 store 同步里来。其它命令的反馈不受此影响。
严重度低~中: 可用性劣化(不是功能损坏), 但「批量加完只出来一半」会让人以为丢种子/加失败。批次越大越容易命中(N=6 → 22% 的种子, N=12 → 44%)。
SSE 掉线的叠加SSE 健康时延迟 = 1.5s + ~60ms(ver 去抖); SSE 掉线时 = 1.5s + 0~1.5s(轮询相位), 最坏 ~3s。原报告的 1.19s 就是「快照已就绪后纯等轮询」的那一段, 仍然成立, 但它只是二阶项。

05根因（可选）

已定位(2026-11-01 真机实测 + 源码坐实): 命令后的那次补刷新发得太早。它在 add 返回后 0.5~0.8ms 就发出(§02-D), 而 qB 的 add 要过四跳异步管线(§02-F): ioThread 文件搜索 → 主线程续体 → libtorrent 网络线程 → 排队告警。从 HTTP 200 到 torrent 进 session 需要 6~40ms ⇒ 补刷新只拿到「那一刻已经建好的那几个」, 剩下的不在本轮载荷里, 下一次同步要等 sync_interval(1.5s) ⇒ 这些行整体后移 1.5s。回执里的 success_count=N 是「已受理」而不是「已建好」, 所以 toast 立刻亮、列表只出一半。

链路逐段(每段都有 §02 的实测支撑):

  1. 前端 POST 一条 add(含 N 个文件) → 主循环下一拍消费; handler 调 qB 加种子, qB 立刻回执 success_count=N(耗时 3~4ms), 回执在这一步就写给前端了(toast 亮, 但列表还没变)。此刻 session 里新种子 0 个。
  2. qB 侧同时开始建: ioThread 逐个搜索未完成文件(单线程, N 个串行) → 回主线程 → async_add_torrent → 告警排队 → createTorrent 进 m_torrents 并 emit torrentAdded。整段实测 6~40ms, 尾部随 N 变长。
  3. 主循环看到「本批命令改了 qB 状态」⇒ 立刻补刷新一次(§04 第一条锚点), 距 add 返回仅 0.5~0.8ms —— 稳定落在管线中间。
  4. 这一轮 /sync/maindata 只返回此刻已建好的行(实测 0/6、3/6、5/6 都出现过), 没建好的不在 store 里 ⇒ 任何 ver 推送、任何前端刷新都拿不到(§02 B: 中间那版 ver 也是 hit=3)。
  5. 下一个同步节拍(1.5s)才补齐, 随后 ver 推送 + 60ms 去抖 ⇒ 用户看到的是 ~1.53s。

已排除的假设: 服务端算力(补刷新 3ms 内完成)、大库(测试库 0~12 个种子)、前端轮询节拍(SSE 健康时同样复现; 直接读 store 也是 1.5s)、网络(全部本机 loopback)、qB 的 sync 增量视图(§02-E/F: 两个端点同源, 同一时刻不会一多一少)。

为什么单种子几乎不触发: 单个 add 也走同一条管线, 但只占 ioThread 一次、不排队, 补刷新那一问通常赶得上(5/5 轮实测 13~23ms 落地); 批量时 N 个搜索在同一个 ioThread 上排队, 尾部被推到补刷新之后, 输的概率随 N 上升(N=6 → 22%, N=12 → 44% 的种子)。

06修法（已实施: 候选 A）

2026-11-01 09:4x 按候选 A 实施。原报告的候选 A(SSE 掉线时前端在回执后补一次 refresh)对本文现象无效 —— 那时 store 里还没有这几行, 前端刷也是扑空, 已弃用。

候选 A(推荐, 后端, 有界补同步): _cmd_add_torrents 已经拿到 qB 回执的 added_torrent_ids —— 把它交给主循环, 补刷新后核对 set(added_ids) - store.by_hash; 非空则以 ~80ms 间隔再同步, 上限 3 次 / ~500ms 即收工(仍缺就等常规节拍, 不无限重试)。实测管线时延 6~40ms; 已验过这个前提: add 返回后 sleep 80ms 再 sync, N=12 连跑 8 轮全部 12/12 命中(响应返回时刻 t+83~112ms), 预期把 1.5s 压到 ~100ms。代价: 每条 add 命令最多多 1~2 次 sync/maindata。

落地形态(与建议的差异: 追平逻辑放在 store 而不是命令 handler —— 内核不该知道 add 语义, 只认「有一批 hash 还没落地」这一个通用信号):
  • store.py expect_hashes() —— 登记期望集合(过滤已在快照里的), 置 80ms 后的到期时刻; expect_due_at() 给出下一次追平时刻(恒为未来值 + TTL 3s 兜底); _settle_expect() 在每轮 _apply 末尾结算(落地出局 / 仍有缺则排下一次 / 3 次用尽即放弃)。
  • commands.py _expect_landing() —— 把回执里的 added_torrent_ids 交给 store; 老版 qB 的纯文本回执拿不到 id, 静默跳过。
  • qbmanager.py 主循环 —— 同步后 next_sync_at = min(next_sync_at, expect_due_at()) 把同步线提前到追平时刻; 追平轮带 force=True(否则被「上一版已取走」门控挡掉); 断连分支先 clear_expect(), 免得到期时刻把 next_sync_at 钉在过去造成空转。

候选 B(后端, 定向灌入): 添加命令后用 /torrents/info?hashes=<added_ids> 把这几个 hash 直接灌进 store(store.refresh 的子集形态)。注意: 它不是"一步到位" —— §02-F 证明该端点与 sync 同源, 同样要等管线走完(实测 t+9.5ms 已完整, 但 t+6.6ms 仍是 0/6), 所以照样要配"缺就重试"的循环, 与 A 的差别只是"补齐时读哪个端点"。代价: 多一条 qB 调用 + 一条"命令注入快照"的旁路, 与"快照只由同步线写"的单一写入口径有摩擦。

候选 C(治标): 断线态或添加后临时把 sync_interval 降到 500ms —— 请求数 ×3, 只把 1.5s 变 0.5s, 且和"下界 1.5s = 服务端 sync 粒度"的既有设计相悖。不推荐。

候选 D(前端, 不推荐): 添加回执后前端本地补拉几次 /api/state —— 服务端没有的东西拉多少次都没有, 只会把"扑空"变成"多次扑空"。

另注: 若后续把添加也做成"乐观行"(先插一行 pending 新种子), 体验上能立刻消掉空窗, 但那是另一条更大的设计线(要处理 hash 未知/去重/失败回滚), 不在本条范围内。
