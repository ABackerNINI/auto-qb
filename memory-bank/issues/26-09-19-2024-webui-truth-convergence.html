01现象与发现场景

用户真机实测反馈（2026-09-19，口径补充）： 「乐观 UI 生效，但从乐观 UI 中恢复正常状态需要 2-4 秒，比如暂停种子，先乐观 UI， 然后 2-4 秒后才能看到种子正常暂停」。

即：不是「点击 → 变灰」慢（那一段上一轮已修，受控测量恒 0ms）， 而是「变灰 → 恢复正常」慢 —— 行一直挂着 is-pending 半透明 + 补丁值，要 2-4s 才落回真值。这与 26-09-19-1939 （已 Fixed，修的是「补丁被 POST 挡住」）是两段不同的链路。

触发条件：所有 pause / resume（单种子、整组、整集/整剧、批量），真机真实 qB 下必定命中。

⚠ 上一轮修复在这里有个反向效果（诚实记录）：为修「补丁被 POST 挡住」， 把 3s 兜底的 ts 改成回执到达时重置（resolveOptimistic(ok) 刷 op.ts）。在「真值匹配即清」根本没有实现的前提下，这让 pending 从「点击起 3s」变成「回执起再 3s」⇒ 真机上恢复时间反而多了约 0.3~0.5s （点击 → 回执本身的耗时）。这就是用户说「此次修复并未成功」的直接原因之一 —— 首变确实快了（0ms），但"恢复正常"变晚了。

02证据

证据 1（决定性）：pendingOps 只有「超时 / 失败」两个清除点，没有「真值匹配即清」

$ grep -n "pendingOps" src/auto_qb/web_ui/static/shared/app.js
317:  pendingOps: {},  // ...
2315:      const op = this.pendingOps[hash];
2318:        delete this.pendingOps[hash];   // ① 超时回落真值(3s)
2361:        delete this.pendingOps[h];     // ② resolveOptimistic 失败回滚

全文件只有这两个 delete。真值到了也不会清 —— 而 systemPatterns.md（乐观 UI 段）白纸黑字写着 「pendingOps[hash] = {patch, prev, ts}，真值匹配即清，3s 兜底回落」： 那是文档漂移，实际从未实现（3s 兜底变成了唯一的出口）。

证据 2：受控测量 —— 回执 7ms 就到，乐观态却 3.1~3.4s 才清除

桩服务种子数 3000 ⇒ 前端轮询间隔 basePollMs = 2000ms

整组 act()        : 补丁 12ms → 出现 pending 20ms | 回执端到端 7ms(排队 0 / 执行 1)
                    → **乐观态清除 3126ms**
单种子 actTorrent(): 补丁 14ms → 出现 pending 20ms | 回执端到端 5ms(排队 0 / 执行 1)
                    → **乐观态清除 3449ms**

命令链路本身只要 5~7ms（排队 0 / 执行 1ms），剩下的 3.1s 全是「死等 3s 兜底」。 ⚠ 桩服务的 FakeClient 不处理 pause（ui_harness.py 里 pause 只在 _STATES 常量里出现，命令泵只回 ok、不改状态） ⇒ 本地真值永远不到，走满兜底；真机上真值会到，但因为证据 1 的缺失，同样走满 3s。

证据 3：回执之后前端不立即刷新，真值要等下一轮轮询

# act() / actTorrent() / actEpisode() / bulk 四条入口, waitCmd 之后都只有
# resolveOptimistic + toast, 没有任何 refresh() 调用:
3312:        const r = await this.waitCmd(resp.cmd_id);
3313:        this.resolveOptimistic(hashes, r.ok);
3314:        if (r.ok) this.toast(`已执行: ${label}该种子`, "ok", 2500);

# 刷新只靠链式 setTimeout(scheduleNext), 间隔按种子量分档(app.js:1652-1673):
#   ≤1000 → 1500ms | 1000~3000 → 2000ms | >3000 → 3000ms

⇒ 即使补上了「真值匹配即清」，真值本身还要等 0 ~ basePollMs （>3000 种子最坏 3s）才被拉回来。

证据 4：服务端补刷新（P0-5）在回执之后才做 ⇒ 存在竞态

# mixins/web_commands.py:150-154 —— 回执先写, 补刷新在整批结束后
if cmd_id and not deferred:
    self._set_web_result(cmd_id, "ok", timing=_timing(queued_ts, start_ts))
if cmd in RESYNC_COMMANDS:
    changed = True      # 主循环据此补一次完整刷新(qbmanager.py:349 一带)

⇒ 「回执后立刻 refresh」这一步可能扑空：补刷新还没跑完，服务端 rid 未变，前端拿到旧快照。所以单做证据 3 的修复不稳，需要重试或调整服务端顺序。

03影响面与严重度

维度结论
触发频率每次 pause / resume（单种子 / 整组 / 整集·整剧 / 批量全中）
影响范围所有视图，真机真实 qB 下必中；与站点无关。库越大越明显（>3000 种子时 轮询档位 3s，叠加后更接近用户报的上限 4s）
数据风险无（命令照常执行、失败照常回滚）。但**行会持续半透明** ⇒ 用户会以为"没生效"而重复点击， 二次点击在真机上会再投一条命令（幂等但浪费）
严重度高 —— 「跟手性」三波次的交付体感就落在这一段：首变已经 0ms， 却还要半透明 3s，用户的主观评价仍然是"点了没反应完"。且它让上一轮的修复看起来"没成功"

04根因（初步）

根因明确（两条，都是代码事实，不是猜测）：

  1. 「真值匹配即清」从未实现 —— pendingOps 只有「3s 超时」与「失败回滚」 两个出口。真值到了也照旧挂满窗口，行一直半透明。这是 2-4s 的主体（3s）。
  2. 回执到达后前端不立即拉真值 —— 真值只能等下一轮 scheduleNext （≤1000 → 1.5s / 1000~3000 → 2s / >3000 → 3s）。这是 2-4s 里浮动的那一段。

叠加关系（真机估算，待实测）：端到端 ≈ 命令投递 + 主循环消费 + qB 执行 + 回执轮询 （实测本地 5~7ms，真机按长 tick 可能数百 ms~1s）+ 等下一轮轮询 0~3s + 死等 3s 兜底。

已排除：① 不是命令执行慢（受控测量排队 0ms / 执行 1ms，服务端 P0-5 补刷新已在做）； ② 不是补丁贴得晚（上一轮已修，恒 0ms）；③ 不是首变渲染慢（DOM 20ms）； ④ 不是浏览器缓存旧 app.js（web.py 有 _static_no_cache 中间件， 静态资源一律 Cache-Control: no-cache，且 <script src="/shared/app.js"> 无版本串 —— 真机若怀疑，可用新的 [perf] … 补丁 … POST … 日志格式判断新代码是否在跑）。

05建议修法

只写方案，不在本报告里实施（等被计划认领 / 用户指派）。

方案 A（推荐，先做）：实现「真值匹配即清」

在每轮 refresh() 之后（reapplyPending() 一带）逐个 pending hash 比对： 行当前值 == patch 期望值 ⇒ 立即 delete pendingOps[h]（不再贴补丁、不再半透明）。

  • 比对口径：patch 只有 kind（pause → paused；resume → seeding/downloading），相等即算匹配 —— 别追求"完全一致"，否则 resume 时 进度/速度变化会让它永远匹配不上。
  • 代价：小。风险点：resume 后真值可能经历中间态（如 checking → downloading）， 匹配判定要能容忍"中间态"，否则退化成走满 3s 兜底（比现在好，但不彻底）。
  • 这一个就够把 3s 主体砍掉 —— 真值一到就清。

方案 B：回执后立即把真值拉回来（与 A 配套，否则真值本身还要等一轮）

  • B1（前端）：waitCmd 拿到 ok 后立即 await this.refresh()； 因证据 4 的竞态（补刷新在回执之后），一次拿不到就短退避重试（如 200~300ms 一档， 总窗口 ≤1.5s），一旦 A 判定匹配即停。
  • B2（服务端，更干净）：把回执推迟到补刷新之后再写 （_drain_web_commands 内先收集、补刷新完成后统一 _set_web_result）， 语义变成「回执 ok = 快照已同步」。代价：回执端到端 + 补刷新耗时（真机可能 0.2~1s）， waitCmd 的「已执行」toast 会相应变晚 —— 需先拍板接受不接受。
  • 推荐 A + B1：不动服务端语义，端到端 ≈ 回执 + 一次 refresh（143~500ms）。

方案 C：重新审视上一轮的 ts 重置

A 落地后 3s 兜底不再是主路径（只是"真值迟迟不来"的兜底），此时「回执起算」是合理的 —— 建议保留；若 A 未做而只回滚 ts 语义，只能把 4s 拉回 3s，治不了本。

验收（修的时候一并补，否则测不到）

⚠ 现在的桩服务根本不改状态（FakeClient 收到 pause 只回 ok， ui_harness.py 里连 pause 处理都没有）⇒ 真值永远不到， 新断言只能测到"走满 3s 兜底"，跟没测一样。必须先给 FakeClient 加"pause/resume 真的改 kind"， 再断言「点击 → 乐观态清除 ≤ 1s」（并把上一轮的注入延迟手法一起用上，覆盖慢回执）。

修复后补充（2026-09-19 实施完成）

实际修法（方案 A + B，未走 B2）：B2（把回执推迟到服务端补刷新之后）会让 「已执行」提示晚 0.2~1s，属产品取舍，未拍板，故采用前端短退避重试。

  1. refresh() 拿到新数据时先 _snapshotTruth(state)：把仍 pending 的 hash 在本轮 payload 里的原始值（只拷补丁涉及的键）记进 truthSnapshot。
  2. reapplyPending() / _optimisticSettled() 改比 truthSnapshot， 对齐即 delete pendingOps[hash]；本轮 payload 没带的 hash 不算对齐 （继续贴补丁，交给 3s 兜底）。
  3. 四条 act*/bulk 的 waitCmd 之后，成功即 await this._pullTruthAfterCmd(hashes)： 立刻 refresh 一次，未对齐则退避 200→400ms 重试，总窗口 1.5s；窗口内没对上仍由 3s 兜底收尾， 「失败/未知不留永久假状态」不变。失败回执不走这条（直接回滚）。
  4. 桩服务加 _apply_truth()（pause/resume 真改 tor.state 并 rebuild_views()），且先回执、后改状态（_TRUTH_DELAY=0.12） —— 复刻真机"补刷新在回执之后"的错位，逼出退避重试路径。

中途踩到的坑（值得单列）：第一版判定写的是「行上的当前值 == 补丁值」， 被自己的补丁骗了 —— 行在上一轮已被贴过补丁，而 updated === false （rid 未变）时行对象根本没被换掉 ⇒ 首轮必"匹配"，pending 22ms 就清。 更隐蔽的是：此时「落回的是真值（s-paused）」也照样 PASS（补丁值还留在行上，看着就像真值）， 只有"设下界"能抓住它。已按此给断言加下界并做红绿双验。

验证方式与实测数字： 页面内 10ms 采样探针（.workbuddy-ai/tmp/probe-clear-cause.cjs）—— 修前：pending 13ms 出现 / 28ms 消失（假对齐）； 修后：13ms 出现 / 272ms 消失（真值 +120ms 落，退避 200ms 后第二次 refresh 对上）。 冒烟双 UI 54 项 0 失败（ok 模式，真值落回 259~267ms、组行 239~248ms、集行 316~319ms； 单 UI 各 27 项 —— 与「剧行 is-pending + 节拍对齐」两笔并发提交合流后重测）； --cmd-result error 双 UI 54 项 0 失败（失败立即回滚 21~22ms，落回原状态）。 uv run pytest tests -q --no-cov → 1054 passed（基线随新增守阵从 1053 上移）。 红绿双验：把 _optimisticSettled 临时改回"拿行上的值比" ⇒ 新断言 FAIL 22ms（低于 80ms 下界）； 还原 ⇒ PASS 263ms。
