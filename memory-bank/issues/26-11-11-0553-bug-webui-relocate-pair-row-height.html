§01现象与发现场景

用户口述(2026-11-11, 无截图): WEBUI 辅种页整组移动(设定位置 → relocate 武装时走整组迁移, 行内出现双排 A→B 保存路径)之后, 移动行行高塌陷, 导致移动行文字显示不全; 用户猜测是双排保存路径导致。

状态: 桩上无法复现, 现象未核实。2026-11-11 只读分析轮做了下面 §02 的全套实测, 双排本身稳态几何全部健康; 本件入池目的是把已排除面与真实缺口记下来, 下次用户在真机碰到时补截图/皮肤/视图信息即可直接开工, 不用重查一遍。

复发时要向用户收集的四项(缺一就很难定位): ① 截图; ② 皮肤(flux/atlas/console/prism) + 视图(组视图/种子平铺); ③ 被裁文字是组行双排路径本身还是别的列; ④ 时间点(提交弹确认框时 / 迁移进行中 / 迁移完成后)。

方法: commands run dev.harness 桩(ui_harness._inject_relocate_jobs 灌 moving/pending_finalize/failed/done 四态) + Playwright 逐变体量几何。组行双排(pair)实测:

真实 UI 流程(右键→设定位置→提交)全程零 console error。截图确认双排两行文字完整、弧形箭头正常。

结构性排除(为什么"裁切"在主表不可能发生):

  • .group-row 是 grid + align-items:center, 行轨 auto 高 = 最高格内容高 → 双排只会撑高行(flux components.css group-row 基础规则);
  • 行窗口化实测行高(_measureRowH)只喂上下占位 aq-row-pad, 从不动行元素本身; 行恒自然文档流, 无绝对定位;
  • 四皮肤 + row_lang.css + fx-mount.css 全量 grep: 无任何针对行/路径格的 height/max-height/裁切用固定 line-height; .rel-pa/.rel-pb 的 overflow:hidden 只在水平方向生效(nowrap+ellipsis)。

§05根因

待复现后定。已排除: ① 双排 A→B 渲染本身(四皮肤 × DPR × 行语言 × 窄视口实测全健康, 见 §02); ② 主表行高约束机制(不存在, 见 §02 结构性排除); ③ 浏览器缓存/磁盘侧静态资源错配(静态响应 cache-control: no-cache + etag 协商, 四皮肤 index.html 同盘同源 —— 运行中进程驻留旧构建产物不在此面, 见复发方向③); ④ 中文路径 11px/1.3 行高下的字形垂直裁切(独立样张排除)。

已证实的真实缺口(只影响占位, 不裁文字, 但最接近"行高异常"的体感): 组键含 save_path → 迁移完成(done)瞬间 save_path 变更 → 组行 data-key 换键 → _rowHs 旧键实测值成孤儿、新键无实测 → 该行在窗口前缀和按 est 兜底一拍, 占位/滚动总高短暂失真(列表跳一下)。用户若把这拍位移读成"行高塌陷", 与口述吻合, 但它解释不了"文字显示不全"。

复发时优先检查方向: ① 用户真机是否浏览器缩放/系统 DPI 组合下某种自绘(如用户字体设置)把 14.3px 行盒压破; ② 是否发生在抽屉/确认框等有确定高度约束的容器里而非主表; ③ 是否为旧构建产物残留在运行中的进程(重启核验)。

§06建议修法

待定 —— 现象未复现, 无从谈修法。若复现后确认是双排引入的回归, 修法大概率落在 row_lang.css 双排段或 _rowHs 换键失效面(换键时按 kind 主动作废旧键孤儿项); 若最终证实是占位失真的误读, 可考虑给 _measureRowH 加「键替换时沿用旧键实测值」或本轮全量重测, 消掉那一拍跳变。
