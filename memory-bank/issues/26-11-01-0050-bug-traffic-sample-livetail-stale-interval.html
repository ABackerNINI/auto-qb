01现象与发现场景

W5 轮 core/ 变异审计(traffic_sample_mod.py, R29)S4 裁决发现(变异体 _publish_live_tail__mutmut_59)。_publish_live_tail 选取 LiveTail.interval_s 的现行逻辑:

interval_s=(buf.interval_s if buf is not None and buf.interval_s else (self._effective_interval or 1))

改采样间隔时 _close_blocks_for_interval_change 对全部系列关块,_reset_block 复位缓冲 8 个字段(不含 interval_s)且 start_epoch=None —— 此刻 buf 处于「无块」态,但 interval_s 残留旧块值。从复位完成到该系列下一条记录块首重立 interval_s 之间的窗口内,若该键以开放游程/pending_agg 发布无块 LiveTail,发布的是陈旧旧块间隔而非当前生效间隔,违反 LiveTail.interval_s 契约(traffic_store.py:511「无块时取当前生效采样间隔」)与 v4_live_tail_slots docstring 的快照-落盘重算恒等承诺(该窗内开放游程随后落入新间隔块,旧值两头都违约)。

判定路径: 该变异体在 S4 全套件 verify 中 SURVIVED(差集空),但裁决认定变异方向(强制走 fallback=现行 effective)恰与契约一致 —— 变异反向暴露原码契约 bug,非测试缺口。处置按 W1 先例(taskqueue run_due_15/_run_one_3): bug 缺口非 test 缺口 —— 「无块 LiveTail interval_s == 生效间隔」的契约守阵会先红于原码,须先修 src 再补守阵。

05根因（可选）

两处不匹配的合成缺陷: ①_reset_block 复位字段清单不含 interval_s(复位后 buf.interval_s 残留旧值);②_publish_live_tail 的 buf 分支只判 buf is not None and buf.interval_s,不查 buf.start_epoch 是否开放 —— 复位窗口内 buf 是「无块」态却走了「有块」分支。已排除: 变异方向行为错(变异值恰与契约一致)。
  1. 发布点加无块守门: buf.interval_s if buf is not None and buf.start_epoch is not None and buf.interval_s else (self._effective_interval or 1);或等价地在 _reset_block 复位 interval_s(置 0 走 falsy 分支)。前者改动面更小、语义直白。
  2. 修后补契约守阵: 改间隔复位窗口内发布无块 LiveTail,断言 interval_s == 当前生效间隔 —— 该守阵连带杀 _publish_live_tail__mutmut_59,变异销账坐实(红验口径同 R25–R28)。
  3. 代价: 一行 + 一守阵;不涉落盘格式与存量数据。
