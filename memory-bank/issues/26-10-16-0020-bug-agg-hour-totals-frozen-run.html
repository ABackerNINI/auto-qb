01现象与发现场景

在计划 26-10-15-0829 的 P1（写侧 z 游程在盘上携带末端真值）收益评估中读码发现：一个跨越小时界的空闲 z 游程，其覆盖的那几小时的 agg hour 行 dl_total/up_total 全部等于游程开启时刻的冻结快照 —— 游程期间真实增长的字节既不进这些行的累计 lane、也不进它们的速率 lane（后者另见 26-10-16-0020-question-agg-rate-lane-invisible-bytes），只在游程结束后的第一段覆盖才开始体现。

2026-10-15 事故实例上的可见表现是「07:00 小时行封口时 totals 线一次 +15 MB 台阶」（见报告 26-10-15-0728 §05「agg 视图」行）。

触发条件：任一 z 游程（两侧速率读数同时为 0 的连续段）跨越小时界 / 自然日界，且游程期间 qB alltime 计数器仍在增长（细流，机理见报告 §04.5）。低载实例上是常态而非异常。

03影响面

维度结论
触发条件z 游程跨小时界 / 自然日界，且游程期间 alltime 计数器仍在增长（细流）。低载实例（多数种子已完成、靠冗余连接握手维持几百 B/s）上为常态。
影响范围全部 agg 段窗的累计（totals）lane：3d/7d/30d（hour 行）/ 6mo/1y（day 行）/ all（month 行），并逐级上卷（day 行 totals 取当日 hour 行末值）；依赖 agg 行 totals 的日对账同样受影响。不影响 rate lane，不影响 raw 段窗（1m–24h） —— 后者已由同期计划 26-10-15-0829 的 P2 修复。
严重度低。raw 面（日常主要看的面）无影响；agg 累计 lane 的绝对值与单调性在低载期失真，量级受限于封口粒度内的隐藏增长。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

机理已读码确认（未经真机复现，认领时先复跑 §04 锚点）：写侧 z 游程的 totals 快照冻结在开启时刻且游程内不刷新（刻意不为，免每样本重读），_agg_feed 把该常量按槽区间原样记账进 agg.pending，而 v4_hour_agg 取 samples[-1] 作为该小时行的 totals ⟹ 游程内部的每个小时，其「小时末应有的累计值」被写成「游程起点值」；增长只能从游程结束后第一条记录的覆盖开始体现，于是差额在下一个封口点一次性出现。

已排除：不是读侧判据问题 —— v4_agg_obs 对 agg 行是直映、不建差分链，磁盘上没有「增长发生在哪一刻」的任何信息，读侧结构上无从追溯。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

候选已在 计划 26-10-15-0829 的 P1 收益评估（2026-10-15 晚 ~ 2026-10-16 00:20）里逐个读过，结论录此以免重复劳动：

  1. 读侧修 —— 不可行。v4_agg_obs 对 agg 行直映不上差分，磁盘上没有锚点。
  2. 写侧 1A：z 行 totals 改存末端值 —— 已否决。会把 raw 面差分链的台阶从「游程末端（身后有整段等值 z 槽可供 P2 摊配）」搬到「游程首桶」，而 v4_totals_points 的摊配判据要求 run[2]（锚点之后的等值观测点表）非空，首桶触发时它必为空 ⟹ 每次空闲段开始都会产出一颗新的单桶 artifacts。治好 agg 面、弄坏 raw 面。
  3. 写侧补尾部记录（1B / 带派生速率的 1B'）（本计划原本的建议形态）—— 已否决，且它拿不到本条收益。_agg_feed 逐记录即时入账（:911），处理 z 行那一刻内部区间已经记完；事后到达的尾部记录只能写 open_credit、覆盖游程之后那一段，追溯不到游程内部。
  4. z 游程定期封口（如每整点） —— 语义与格式都不动，就能让每个小时拿到本段的真实起点，且顺带把 _V4_SEAM_LOOKBACK_S = 86400 那个「依赖 ZRUN_FLUSH_S 不变」的跨层耦合降到一个周期。用户在 2026-10-16 已否决：代价在行数（几千种子时放大），且会撕开「空闲期主文件零写入」这条不变式。仍是所有候选里改动面最小的一个，若日后重开它是首选。
  5. 挂起结算（_agg_feed 先不记游程内部区间，等末端值到达再补记）—— 未评估，成本最高。会引入新的待结算态，与现有「崩溃丢 ≤ ZRUN_FLUSH_S 纯零信息」的口径冲突（变成丢真实字节），且在线路与离线 _agg_credit_day_file 必须同步改造。

本条 2026-10-16 入池时未被认领，默认不修：raw 面（日常主用）不受影响，agg 累计 lane 的失真量级受限于封口粒度内的隐藏增长。

复验

复验：2026-10-16 15:09 仍复现（clone @ d58ad0c5）。两段证据：

  • 锚点复核：§04 五条锚点 + _agg_feed 调用点全部仍在，判据原文逐字未变；行号漂移 —— _agg_feed 的 V4ZeroRun 分支 :1034-1037 → :1055、OpenRun docstring :232-233 → :244、v4_hour_agg 取值 :803/:811-812 → :811（定义 :783）、v4_agg_obs :686 → :744/:753、_agg_credit_day_file :1383 → :1403、_agg_feed 调用点 :911 → :931。
  • 行为复验（合成几何，内存内直驱真实聚合路径，未落盘未入库）：3 小时 z 游程跨小时界，开启快照 (1,000,000 / 2,000,000)、末端实测真值 (15,999,000 / 18,000,000)。在线 _agg_feed 产出的小时行：+0 / +3600 / +7200 三行 dl_total 全部 = 1,000,000（冻结快照，cov 各 3600），而游程结束所落的 +10800 行 dl_total = 15,999,000 且 cov 仅 30 —— 增长被推到下一个小时行，与 §01/§02 描述逐条吻合。离线 _agg_credit_day_file 同几何重放：同样三行末样本 (1,000,000 / 2,000,000) —— 两路逐字同形，§04 的「离线同源」约束成立。

复验另得一条与既有裁决不同的发现：_agg_feed 对 z 记录是封口那一刻入账的，而主流封口路径（非零实测样本到达先 _seal_run 再出 r 记录）此时末端值就在调用方手里 —— 计划 §03 P1 裁决里「要落在游程内部只剩三条路」的枚举漏了这一条，形态面因此重开（详对照件 §03）。

修复后补充

实际修法（形态 D，即对照件 §04 D；本轮用户拍板）：z 行扩一对「末端快照」列（z,<run_len>,<dl_delta>,<up_delta>,<dl_end_delta>,<up_end_delta>[,<dt_ms>]，旧 4/5 列文件解析为 None → 退化冻结，向后兼容；显式退化 = 拿不到末端值时写冻结列同值），封口时把「封口时刻已知的末端观测」落盘；agg 入账（在线 _agg_feed 与离线 _agg_credit_day_file）改按两路共用纯函数 v4_z_totals_ramp 把「开启快照 → 末端快照」按槽序线性摊配进游程内各槽（n=1 / 无末端列 / 末端低于开启则恒取开启快照）。末端锚点解析单点 _resolve_run_end：调用方手上实测样本（封口路径 ①实测样本 / ②00:00 硬切 / ⑤保险闸）＞ 游程内最后一条零样本读数（OpenRun.last_* 跟踪字段，服务 ③stop / ④改间隔关块）＞ 开启快照；低于开启按开启钳制（游程内计数器重置的落差不是增长，且保证末端列 delta 非负）。raw 面零触碰：冻结列 / 差分链 / 读侧 V4Slot.obs 逐字不变（末端对只进 agg 车道）。

与建议修法的差异：与既有五条候选（读侧修 / 1A / 1B·1B' / 定期封口 / 挂起结算）均不同 —— 它是认领复验新找到的「第四条路径」的落盘化形态：末端值本就只在封口那一刻可得（传一手即可），D 再把它写进行内，使离线不需要前视／不依赖后继记录在盘上；代价是动了行格式定约（位次定在 delta 与可选尾列 dt_ms 之间按列数分支，避免可选尾列造成歧义列数）。

验证：①合成几何（3 小时 z 游程跨小时界，与复验同构）：修复后游程内小时行逐级摊配、右端小时 = 末端快照、剩余增长只余末段（消除「07:00 行 +15 MB 台阶」），覆盖与 rate lane 不变；②两路同源：同一 z 行在线 / 离线小时桶逐样本逐位一致（test_agg_z_end_anchor_two_paths_same_hours）；③封口五路径锚点来源各有用例（①⑤传样本值 / ③④跟踪值 / 重置退化）+ 格式兼容（旧 4/5 列 → None）与显式退化 roundtrip；④红绿双验 5 类突变逐类判红（关插值 5 红 / 离线不读摊配列 1 红 / 末端列写冻结值 5 红 / 路径①不传末端值 1 红 / 取整口径截断 3 红），还原后四文件 SHA256 逐位自证；⑤全量测试与覆盖率闸门见基线切片 memory-bank/testing/baselines/26-10-16-1628-qb-traffic-restart-spike-gap-agg-attribution-d.md。
