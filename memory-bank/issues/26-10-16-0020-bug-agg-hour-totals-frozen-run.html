01现象与发现场景

在计划 26-10-15-0829 的 P1（写侧 z 游程在盘上携带末端真值）收益评估中读码发现：一个跨越小时界的空闲 z 游程，其覆盖的那几小时的 agg hour 行 dl_total/up_total 全部等于游程开启时刻的冻结快照 —— 游程期间真实增长的字节既不进这些行的累计 lane、也不进它们的速率 lane（后者另见 26-10-16-0020-question-agg-rate-lane-invisible-bytes），只在游程结束后的第一段覆盖才开始体现。

2026-10-15 事故实例上的可见表现是「07:00 小时行封口时 totals 线一次 +15 MB 台阶」（见报告 26-10-15-0728 §05「agg 视图」行）。

触发条件：任一 z 游程（两侧速率读数同时为 0 的连续段）跨越小时界 / 自然日界，且游程期间 qB alltime 计数器仍在增长（细流，机理见报告 §04.5）。低载实例上是常态而非异常。

03影响面

维度结论
触发条件z 游程跨小时界 / 自然日界，且游程期间 alltime 计数器仍在增长（细流）。低载实例（多数种子已完成、靠冗余连接握手维持几百 B/s）上为常态。
影响范围全部 agg 段窗的累计（totals）lane：3d/7d/30d（hour 行）/ 6mo/1y（day 行）/ all（month 行），并逐级上卷（day 行 totals 取当日 hour 行末值）；依赖 agg 行 totals 的日对账同样受影响。不影响 rate lane，不影响 raw 段窗（1m–24h） —— 后者已由同期计划 26-10-15-0829 的 P2 修复。
严重度低。raw 面（日常主要看的面）无影响；agg 累计 lane 的绝对值与单调性在低载期失真，量级受限于封口粒度内的隐藏增长。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

机理已读码确认（未经真机复现，认领时先复跑 §04 锚点）：写侧 z 游程的 totals 快照冻结在开启时刻且游程内不刷新（刻意不为，免每样本重读），_agg_feed 把该常量按槽区间原样记账进 agg.pending，而 v4_hour_agg 取 samples[-1] 作为该小时行的 totals ⟹ 游程内部的每个小时，其「小时末应有的累计值」被写成「游程起点值」；增长只能从游程结束后第一条记录的覆盖开始体现，于是差额在下一个封口点一次性出现。

已排除：不是读侧判据问题 —— v4_agg_obs 对 agg 行是直映、不建差分链，磁盘上没有「增长发生在哪一刻」的任何信息，读侧结构上无从追溯。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

候选已在 计划 26-10-15-0829 的 P1 收益评估（2026-10-15 晚 ~ 2026-10-16 00:20）里逐个读过，结论录此以免重复劳动：

  1. 读侧修 —— 不可行。v4_agg_obs 对 agg 行直映不上差分，磁盘上没有锚点。
  2. 写侧 1A：z 行 totals 改存末端值 —— 已否决。会把 raw 面差分链的台阶从「游程末端（身后有整段等值 z 槽可供 P2 摊配）」搬到「游程首桶」，而 v4_totals_points 的摊配判据要求 run[2]（锚点之后的等值观测点表）非空，首桶触发时它必为空 ⟹ 每次空闲段开始都会产出一颗新的单桶 artifacts。治好 agg 面、弄坏 raw 面。
  3. 写侧补尾部记录（1B / 带派生速率的 1B'）（本计划原本的建议形态）—— 已否决，且它拿不到本条收益。_agg_feed 逐记录即时入账（:911），处理 z 行那一刻内部区间已经记完；事后到达的尾部记录只能写 open_credit、覆盖游程之后那一段，追溯不到游程内部。
  4. z 游程定期封口（如每整点） —— 语义与格式都不动，就能让每个小时拿到本段的真实起点，且顺带把 _V4_SEAM_LOOKBACK_S = 86400 那个「依赖 ZRUN_FLUSH_S 不变」的跨层耦合降到一个周期。用户在 2026-10-16 已否决：代价在行数（几千种子时放大），且会撕开「空闲期主文件零写入」这条不变式。仍是所有候选里改动面最小的一个，若日后重开它是首选。
  5. 挂起结算（_agg_feed 先不记游程内部区间，等末端值到达再补记）—— 未评估，成本最高。会引入新的待结算态，与现有「崩溃丢 ≤ ZRUN_FLUSH_S 纯零信息」的口径冲突（变成丢真实字节），且在线路与离线 _agg_credit_day_file 必须同步改造。
