01现象与发现场景

怎么撞见的：2026-10-18 收尾「WEBUI 选中摘要」计划(26-10-18-2013)时，按 memory-bank/testing/smoke.md 的矩阵轮纪律补跑全量 e2e 的 error 模式轮(E2E_CMD_RESULT=error commands run dev.e2e)，本轮 266 passed / 26 skipped / 4 failed，失败全部集中在 e2e/delta-sync.spec.mjs 的两条真值对齐用例(双皮肤 ×2)。

平台与配置：Windows 本机，桩服务 scripts/ui_harness.py(端口 8137，300 种子 / 150 组)。error 与 hang 两个模式均已实证(取证 2026-10-18 21:07–21:30)：error 轮 266 passed / 26 skipped / 4 failed；hang 轮 252 passed / 40 skipped / 同样 4 failed、逐字同签名(hang 下命令无回执 ⇒ 桩不改真值 ⇒ 同一 8s 轮询超时)。

03影响面

维度结论
触发条件模式矩阵 E2E_CMD_RESULT=error 或 hang 下必现(error 已实证; hang 按机理推断, 待实证)。ok 模式不触发。
影响范围仅测试面：生产代码零牵连(HEAD 同参复现同红已证)。受影响的是矩阵轮 ②/③ 的回归信号 —— 4 条存量恒红会把新增红色淹没(与 issue 26-10-08-0818 记载的「恒红使 dev.e2e 失去回归信号价值」同型)。
严重度中 —— 不阻塞生产与默认轮; 但使 error/hang 两个矩阵轮永远无法全绿, 收尾 DoD 的「六轮」实质打折。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

按 smoke.md 既定修法(模式分流)落地，两候选：

  • A(推荐)：给两条 test 补 requireMode(test, { cmdResult: 'ok' }) 门控(与 trigger-scope 主路径组同款)，error/hang 轮整组 skip 且 skip 消息带当前 env 值。代价最小、语义最诚实(这两条判的就是 ok 模式真值对齐)；代价 = error/hang 轮对增量合并的覆盖仍旧空白。
  • B：仿 multiselect-shows 的 if (CMD_RESULT === 'error') 分支，error 下改判「回滚干净」(pendingOps 归零 + 无残留 is-pending)，hang 下归入 optimistic.spec:535 已有的独占组或同样门控。覆盖更全，但要新写分支断言并红绿双验，成本高。

另已顺带确认：矩阵轮 ②(error)/③(hang)的失败集均只有这 4 条(② 266 passed/26 skipped/4 failed; ③ 252 passed/40 skipped/4 failed，逐字同签名)，无其他无门控的 ok 语义用例被带红; ④(skip-check off)/⑤(hr-scene empty)两轮 0 failed 全绿。⑥(3000 种子)轮另暴露 2 条追剧页用例的落点对冲规模失效，已单独入池 26-10-18-2226。

修复后补充

实际修法 = 建议修法 A（按 smoke.md「某种模式下恒红 ⇒ 按模式分流」的既定口径落地）： 只给这两条真值对齐用例加 requireMode(test, { cmdResult: 'ok' })（e2e/lib/mode.mjs 是本仓既有模式门控单点，optimistic / menus / trigger-scope / hr-history 均已用）， error / hang 轮整条 skip 且 skip 消息自带当前 env 值（「模式不匹配, 整组跳过 —— 当前 E2E_CMD_RESULT=error, 本组要求 ok」，防静默少跑，计划 §6 R2）。

一处与建议 A 的不同（保留覆盖）：建议 A 写的是「整组 skip」， 但原 describe(`皮肤 ${skin}(S4: 增量合并冒烟)`) 里共 4 条 test，另两条 （applyStateRows 行级语义直测 / S7 装饰记忆化）自带注入桩态、不依赖命令回执， 在三种模式下都成立。若在 describe 顶层加门控会连带把它们也 skip 掉（error/hang 轮白白少 4 条覆盖）。 故改为在两条真值对齐用例的 test 体内各加一次门控（menus.spec.mjs 有同款单条门控先例）， 同组另两条在 error/hang 轮照常真跑 —— 实测 error/hang 两轮该组均 4 skipped / 4 passed。

验证方式：三组同参 npx playwright test delta-sync（双皮肤 × 4 条 = 8 例）+ 两轮全量矩阵。

  • ① ok 轮（默认）：8 passed / 0 skipped ⇒ 无门控副作用，默认轮一条没少跑。
  • ② error 轮：单文件 4 skipped / 4 passed / 0 failed；全量 270 passed / 30 skipped / 0 failed （修复前 266 passed / 26 skipped / 4 failed ⇒ 4 条红精确转为 4 条 skip，passed +4）。
  • ③ hang 轮：单文件 4 skipped / 4 passed / 0 failed；全量 256 passed / 44 skipped / 0 failed （修复前 252 passed / 40 skipped / 4 failed，同上）。

换基线复跑：提交前远端又进 3 笔（含 app.js / columns.js / sort.js 前端改动）， 同步后在新基线上重跑三轮全量，仍全绿且无连带：ok 290 passed / 10 skipped、 error 270 passed / 30 skipped、hang 256 passed / 44 skipped（三轮均 0 failed）。

已知代价（不改）：error / hang 两轮对「增量合并链路」的覆盖仍是空白 —— 这正是建议 A 记下的代价。要补的是建议 B（error 下改判「回滚干净」、hang 下并入 optimistic.spec 的 hang 独占组），属新增断言、需另做红绿双验，不在本件范围。
