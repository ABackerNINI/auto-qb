01现象与发现场景

千级列表性能统一优化(计划 26-11-02-0351)收官后的验收轮中发现: 各视图(主表 torrent/group/member 与抽屉 content)首次访问时, 窗口化引擎走"全量渲染 → 量齐行高"的冷启动路径, 3000 行下单发约 5.4s 长任务。属已知的设计内代价(计划外缺陷记录第 5 条), 经用户确认本轮不修, 只入池并把"首访压平"另立排期。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已知机制(非猜测, 为设计取舍): 首访时没有行高实测值, 引擎选择"先全量渲染再逐行量齐"以保证占位总高与滚动位置精确; 量齐后转入窗口化稳态。故长任务只发生在首访一拍。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

候选: ①估算行高 + 渐进量齐 —— 首访直接用 ROW_WIN_EST_H 开窗, 量齐分批在滚动/空闲(idle callback)中补齐, 占位总高按估算值给并在量齐后校正(代价: 首访滚动位置可能微跳, 需要 sticky/回焦补偿; 与同轮已修的 sticky 面有交集)。②分批渲染量齐 —— 首访按块(如 300 行/帧)量齐, 视觉上渐进补齐(代价: 首访可见闪烁, 需占位骨架)。③维持现状(代价: 每次冷启动一次 5s)。判据: 3000 行首访单发 longtask 从 ~5.4s 压到 <500ms, 且占位总高/滚到底/键盘跨窗回焦三判据不回归(复用 e2e/drawer-content-perf.spec.mjs 与 perf.spec.mjs 口径)。

复验

复验：2026-11-02（认领前复测）仍复现 —— 桩 scripts/ui_harness.py --torrents 3000（端口 8337），首访点击种子视图, Playwright + CDP CPU Profile 实测单发 longtask 8432ms（起点约 2141ms, 持续到约 10573ms）；CPU 自耗 Top: getBoundingClientRect 2731.8ms（3310 次）、addEventListener 1245.4ms、removeEventListener 1190.6ms，_measureRowH 自身仅 24.5ms。量齐后 _winMeasured.torrent=true、常驻 DOM 20 行、scrollHeight=191009，窗口化稳态正常。结论: 长任务由「全量渲染 3000 行 + 逐行 gBR 量齐 + 每行监听增删」构成，与建议修法①「估算行高 + 渐进量齐」的判断一致。

修复后补充

实际修法：按建议修法①落地，不新增机制 —— ①app.js 增 ROW_WIN_EST_MIN=1000：千级以下仍走「全量渲染 → 量齐」的精确冷启动（保住百行级严格判据），达到千级首帧直接用 _rowH[kind] || ROW_WIN_EST_H[kind] 估算开窗、gap 缺失取 ROW_WIN_GAP_FALLBACK；②columns.js 的 _rowWindow 冷启动门控按上条分档，_winMeasured 语义改为「首访窗口行已实测」，缺的行随滚动/轮询渐进补齐；③未量过的行占位改取已实测行的全局均值（新增 _rowHAvgOf(kind)），替代原先的「当前窗口均值」—— 后者会让占位总高随窗口移动每帧抖动；④_measureRowH 去掉一次性 sum 累计，只逐行写 _rowHs。抽屉 content 同走该路径，千级以下行为零变化。

验证方式：①桩 scripts/ui_harness.py --torrents 3000（端口 8437）+ Playwright 首访探针（Playwright + longtask/gBR 计数）：修复前首访单发 longtask 8432ms、gBR 3310 次；修复后首访首行可见 263ms、longtask 最大 97ms、gBR 55 次。②commands run test.quick：4837 passed / 10 skipped / 0 failed（124.10s）。③e2e 默认 300 档 perf.spec.mjs：6 passed / 4 skipped / 0 failed（19.4s）；3000 档 perf.spec.mjs：10 passed / 0 failed（1.2m，含 A/B / 行窗口化 / 占位粗界 / 滚到底不塌陷 / W5 同屏交叉）；3000 档 window-invalidation.spec.mjs：6 passed（53.6s）。

与建议修法的差异：无改道。补充：千级首访的占位总高不再与全量渲染逐像素相等（估算值随滚动实测收敛；3000 行实测偏差约 13%~14%，方向取决于首屏采样到哪一档行高，如 216538 vs 190979 或 164278 vs 190979），故 e2e/perf.spec.mjs 两条绝对阈值按行数分档：千级以下保持原值（|Δ|<50px / 滚动 |Δ|<200px），千级及以上「占位总高」退为粗界守阵（0.5~1.5 倍全量，防估算 ×2 / 接近 0 的失真）、「滚到底」改为只禁塌陷（允许总高随补量增长）—— 判据语义不变（禁的是塌陷与失真），精确判据留在默认档。真正收敛到逐像素相等需把全表滚一遍（约 125 步），代价不划算，故不做。

二轮调优（2026-11-02 12:48, 用户指令）：①阈值实测定值 1000→200 —— 同一探针在 100/150/200/250/300/400/500/600/700/800 档各跑一次首访(全部 gBR≈行数确认走精确路径), longtask 随行数近线性涨: 100 行 146ms / 150 行 215ms / 200 行 334ms / 250 行 377ms / 300 行 455ms / 400 行 627ms / 500 行 733ms / 600 行 947ms / 700 行 1113ms / 800 行 1253ms, 250ms 拐点落在 150~200 之间 —— 故取 ROW_WIN_EST_MIN=200 与 ROW_WIN_MIN 合并, 「全量渲染」与「精确冷启动」两档合一; 用户举例的 400/500/512 均不满足 250ms 线(400 档 627ms 为其 2.5 倍)。副作用 = 200~999 原精确冷启动档消失(334~1521ms 降至 ~60ms), 默认 300 档 e2e 从严格口径转粗界档(设计变化的必然结果)。②空档1(反向判别力): perf.spec 新增「首访路径指纹」用例 —— addInitScript 注入 gBR 计数、点种子页签前清零, 断言首访 gBR<150(估算实测 ~55 与行数无关; 误切精确时 ≈行数: 200 档 228 / 300 档 325 / 999 档 1051; 150 居中各留 2.7×/1.5× 余量); 负向验证 = 门控临时恒 off 强制精确路径, 双皮肤指纹用例红(gbr=325/行数300), 还原回绿。③空档2(单测边界): node 探针电池加边界两断言 n=199 走 off(全量) / n=200 走估算开窗(active); 负向验证 = 门控恒 off, 恰红预期两条, 还原回绿(1 passed)。④顺带修正: 「滚到底」估算档判据原按「总高只会增长」写单向判据, 300 档首次踩进即红(22887→21591px, Δ-1296 —— 收敛方向不定), 改按比例禁塌陷(|Δ|<before×25%)。⑤验证轮: e2e 199 档 6 passed / 200 档 8 passed / 默认 300 档 8 passed(均双皮肤零 failed), test.full 4837 passed / 10 skipped / 99%(基线切片 26-11-02-1248)。
