01现象与发现场景

千级列表性能统一优化(计划 26-11-02-0351)收官后的验收轮中发现: 各视图(主表 torrent/group/member 与抽屉 content)首次访问时, 窗口化引擎走"全量渲染 → 量齐行高"的冷启动路径, 3000 行下单发约 5.4s 长任务。属已知的设计内代价(计划外缺陷记录第 5 条), 经用户确认本轮不修, 只入池并把"首访压平"另立排期。

03影响面

维度结论
触发条件视图首次访问(或行高缓存被整体作废后再次访问); 行规模越大越明显, 3000 行下约 5.4s
影响范围主表三 kind(torrent/group/member)与抽屉 content 变体的首访; 三皮肤共用引擎, 预计一致
严重度中 —— 每次会话/每次冷启动一次, 5s 级卡顿可感知; 稳态交互已优化到 0 longtask

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已知机制(非猜测, 为设计取舍): 首访时没有行高实测值, 引擎选择"先全量渲染再逐行量齐"以保证占位总高与滚动位置精确; 量齐后转入窗口化稳态。故长任务只发生在首访一拍。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

候选: ①估算行高 + 渐进量齐 —— 首访直接用 ROW_WIN_EST_H 开窗, 量齐分批在滚动/空闲(idle callback)中补齐, 占位总高按估算值给并在量齐后校正(代价: 首访滚动位置可能微跳, 需要 sticky/回焦补偿; 与同轮已修的 sticky 面有交集)。②分批渲染量齐 —— 首访按块(如 300 行/帧)量齐, 视觉上渐进补齐(代价: 首访可见闪烁, 需占位骨架)。③维持现状(代价: 每次冷启动一次 5s)。判据: 3000 行首访单发 longtask 从 ~5.4s 压到 <500ms, 且占位总高/滚到底/键盘跨窗回焦三判据不回归(复用 e2e/drawer-content-perf.spec.mjs 与 perf.spec.mjs 口径)。
