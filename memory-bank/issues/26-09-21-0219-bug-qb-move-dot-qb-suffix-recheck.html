01现象与发现场景

用户在实际运行中反馈:qBittorrent 移动已完成的种子时, 有概率把磁盘上的文件临时改名为 <原名>.!qB(qB 搬运过程中对未完成/被占用文件加的临时后缀, 搬运结束后才改回原名)。移动动作本身同时会让种子进入「重新校验」流程。

在这个窗口内, 本程序的缺文件磁盘扫描拿缓存的文件名去 os.path.exists, 磁盘上此时是 xxx.mkv.!qB, 原名的 xxx.mkv 不存在 → 判定「文件缺失」→ 整组暂停 + 打 MISSING 标签(严重时还会连锁触发重新校验动作)。文件其实存在, 只是带后缀 —— 属于误判。

触发条件(均为推测, 未复现验证): 大文件 / 跨盘移动 / Windows 文件被占用(qB 侧 rename 未完成)时概率更高; 与 grouping.check_missing_files 开启直接相关。发现方式: 用户现场反馈, 非测试复现。

补充线索: 移动后 save_path 变化与状态转移会在同一轮分别触发扫描(_handle_save_path_changes + _handle_state_transitions), 组内去重只保证同轮扫一次, 但扫描时机可能正落在 qB 改名窗口内。

03影响面

维度结论
触发条件grouping.enabled + grouping.check_missing_files 开启, 且发生种子移动(move_to 动作 / Web UI 移动 / 外部移动); 文件越大 / 跨盘 / Windows 占用时概率越高。概率性, 非必现。
影响范围被误判的整个辅种组(不只出问题那一个种子): 全组 torrents_stop 暂停 + 打 missing_tag; 后续轮次会按「已知缺文件」口径放行重下(multi-dl 拦截语义随之改变); 叠加一次无谓的重新校验(大文件 I/O 开销)。
严重度中偏高 —— 不丢数据, 但会误停健康做种并污染 MISSING 标签, 且误判状态需人工发现才能回滚。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  1. 过渡态容忍（首选方向）: 缺文件扫描命中「原路径不存在」时, 先探测 原路径 + ".!qB" 是否存在; 存在则视为「正在搬运 / 过渡态」, 本轮不判 missing(跳过或延后一轮再看), 不暂停、不打标签。代价: 真正被 qB 长期残留后缀的极少数情况会被放过一轮。
  2. 移动后冷却: 检测到 save_path 变化(移动)后, 该组在 N 轮内不做缺文件判定, 等 qB 搬运与重校验落定。代价: 需要新的按组冷却状态; 真实缺文件会晚 N 轮才报。
  3. 校验中一律不判: 把「种子处于 checking / 刚触发 recheck」直接排除出代表种与判定范围(现逻辑只排除 is_checking 的代表种, 未覆盖组内其他成员与过渡态)。代价: 覆盖不全, 建议与 1 搭配。

无论走哪条, 先补一次带 DEBUG 日志的移动复现, 确认后缀确由 qB 产生、且扫描确实落在改名窗口内 —— 没复现就修容易改错地方(checking.py 与 grouping.py 两条链路都可能踩)。
