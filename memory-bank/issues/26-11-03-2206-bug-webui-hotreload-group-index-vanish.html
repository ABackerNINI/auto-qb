01现象与发现场景

用户报告: 辅种页偶发只剩空态「暂无辅种」, 重启后端即恢复, 高度怀疑配置热重载。本轮调查在 clone1 当前 HEAD f89de69e 上完成 (2026-11-03 22:05 取证), 结论: 确为热重载导致, 但只在 L2 结构重建路径触发; 不是前端订阅断链, 也不是 transfer(转种) 状态源问题。

空态文案单点在 filters.js groupsEmptyText(): 只有辅种页的 groups 数组为空时才会显示「暂无辅种」; 未归组种子(singles)不参与该页正常行渲染(仅搜索命中时以虚拟单行兜底), 所以「groups 被清空」在页面上表现为整页空态, 而种子页仍正常。

02证据

受控实验 (in-process, 临时脚本置于 %TEMP%, 未入仓库; 用 tests/helpers 的 FakeClient + 默认装配, grouping.enabled=True): 2 个同 save_path/同文件列表的种子 → 期望 1 个辅种组。

grouping.enabled = True
==== 阶段1: 首轮全量, 存量种子归组 ====
H1 conf = <helpers.FakeTracker object ...> | torrents_files calls = 2
[首轮后] by_hash=2 groups=1 members=2 view_changed=True
==== 阶段2: 模拟 L2 热重载(rules.rebuild_runtime -> store.reset_runtime) ====
[重建后] by_hash=2 groups=0 members=0 view_changed=True
[重连后] by_hash=2 groups=0 members=0 view_changed=True
==== 阶段3: 全量轮兑现(tracker 重匹配 + 各相位广播) ====
[全量轮后] by_hash=2 groups=0 members=0 view_changed=True
分组视图行数 = 0
==== 阶段4: 模拟重启(新进程同数据首轮) ====
[重启首轮后] by_hash=2 groups=1 members=2 view_changed=True

即: L2 重建后 groups 归零; 之后即便兑现一次完整全量轮(tracker_conf 已重匹配), 仍为 0; 视图构建器 _build_group_view() 随之输出 0 行并自增版本, 前端收到的是一份合法的 full 代但 groups 为空数组(singles 仍在, 所以不是坏 payload)。新进程同数据首轮才恢复 1 组 —— 这正是「重启后端即恢复」。

已排除的假设: ①前端 SSE/轮询断链 —— _publish_locked 在重建后照常 group_view_ver += 1 并 notify("ver"), 客户端正常刷新, 只是内容为空; ②transfer 状态(TransferStatus 三态/汇总) —— 转种目标是 web.transfer.targets 配置源, 与分组索引无关; 空数据下转种汇总只是 0 计, 不产出「暂无辅种」; ③前端空 payload 解析 —— 前端在 full 代整表替换 groups, 行为符合协议。

03影响面

维度结论
触发条件保存配置且命中 RulesModule._rebuild_needed: rules_config 任意变更 · interval · delete_tags · delete_tags_if_has_no_torrents · global_speed_limit_curve · trackers 段的 domains/rules/groups 三元组变更或 tracker 增删。WebUI 设置页保存这些段即可触发; 仅改 web/notify/logging/grouping/hr 等段不触发(不调用 reset_runtime)。
影响范围辅种页(groups 视图)全空; 组级/成员级动作不可达, 含右键「转移到」的 group/member 两支。种子页与状态栏计数正常(计数走 groups 成员数 + singles, singles 未丢); 搜索命中时可用虚拟单行兜底。
严重度中高 —— 数据未丢, 但分组索引丢失后无自愈路径, 必须重启进程(或等新增种子/保存路径变化)才能恢复。

05根因（可选）

已定位(受控实验 + 代码链双向确认): L2 结构重建把分组索引当作「下轮全量 refresh 会重算」的派生缓存清空, 但全量轮只经 full_round 重匹配 tracker_conf, 归组只由 torrents_added(新种子)与 save_path 变更触发 —— 存量记录既不再算 added 也通常不改 save_path, 于是分组索引永久为空。
重启能恢复, 是因为新进程 by_hash 为空, 首轮全量所有种子都判 added → torrents_added 相位逐条归组(实验阶段4已验证)。
已排除: reset_runtime 把 by_hash 也清了、tracker_conf 未重匹配、视图未重建、前端丢数据 —— 均不是。

06建议修法（可选）

方向: 补齐「L2 重建后派生索引恢复」这一环; 只写方案, 不在本报告实施。

  1. 方案A(推荐, 与 26-10-01-2147 同款): GroupingModule 订阅 full_round, 在 tracker 重匹配之后, 对 store.by_hash 中 tracker_conf 已就位且未归组的记录重跑归组(需要 torrents_files)。为避免每轮全量重归组, 用一次性标志(如 reset_runtime 置位, 首个 full_round 消费), 并做队列查重防止与首轮 torrents_added 管线重复。代价: 重建后首个全量轮会多 N 次 files 查询, 大库需分批/限流。
  2. 方案B(语义最轻): reset_runtime 不清 groups/member_to_key, 只清 tracker_conf。分组 key 是纯函数派生(group_key_of), 同数据同 key; 但需先确认 P7 group_key_migrations 与文件列表缓存失效语义不依赖清空。
  3. 方案C(折中): 不改 reset, 在 reset_runtime 置 regroup_all_pending, 由 grouping 的 post 相位在首个全量轮一次性全量重归组。

建议先补一条守阵测试: L2 重建 + 全量轮后 store.groups 应恢复, 防止再次回归。
