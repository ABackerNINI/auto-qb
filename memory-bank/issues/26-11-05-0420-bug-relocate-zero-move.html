03影响面

维度结论
触发条件组内种子的磁盘文件名与 qB 账面名错位(如 .!qB 后缀冻结,深层嵌套);qB 部署开着 AddExtensionToIncompleteFiles;种子经转移/辅种跳检添加(seed_mode,做种不读盘,错位长期隐形)
影响范围relocate 三入口(WebUI 整组迁移/规则 move_to/CLI)与种子转移的目标侧;零搬移假成功 + 组按 save_path 分裂 + 失败静默 10 分钟;别名收尾若在错位态进行还会把 junction/账本建在错误前提上
严重度高:报成功但数据未动且无告警;带嵌套目标时即使数据正常也属语义死路(junction 自递归)

05根因（可选）

已查清(生产取证 + 源码 + 测试复现三重印证,详见报告): ① 账面名与磁盘名错位 —— 11-04 组迁移收尾的 ACT_FINALIZE 归位把 non-movers 指向新位置,missingFiles 成员的归位搬迁/重建以未完成姿态计算目标路径,把共享物理文件整体改名挂上 .!qB(实验 F2/G2 实证),mover 账面 prog=1.00 不动(其工作名仍声明名),错位冻结; ② qB 搬迁按声明名逐文件 stat,全 miss 被静默忽略并报「成功移动」(storage_utils.cpp:151); ③ auto-qb .!qB 闸门只扫内容根顶层,深层文件漏拦; ④ setLocation 为 fire-and-forget,唯一兜底是 10 分钟停滞看门狗,且失败不告警。 补充(2026-11-05 补证,设计意图经用户确认):dir_alias 收尾设计 = guardian 在 qB 关闭期间删 junction → qB 重启 → 成员 fastresume 找不到文件(missingFiles,设计预期输入)→ reconcile 的 ACT_FINALIZE(relocate_units.py:952,976-1030)setLocation 把成员指向新位置 → seed_mode 账面恢复进度,免全组重校验。libtorrent 对 ENOENT 也报 mismatching_file_size(storage_utils.cpp:460-479),故 rejected ×2 即该设计的正常触发。 缺陷 = 设计的隐含假设被打破(实验 F1/F2 分步证伪):①「进度完整保留」在重启步即失效 —— rejected 成员恢复为 missingFiles prog=0.00(账面丢失,非保留);②「磁盘无副作用」在归位步失效 —— ACT_FINALIZE 的零搬移 setLocation 触发 need_full_check 自动 recheck,1.2s 内磁盘原名文件被物理改名挂 .!qB(F2 逐步采样;E3 归因于 resume 不准确,F2 修正为归位步);③根源链:rejected re-add 时 filesearcher forceAppendExt 把工作名伪造为 name.!qB(save_path 下找不到文件)→ 归位后 recheck/状态机按伪造名把磁盘对齐 → 冻结;账面随后按 .!qB 名校验通过恢复 1.00(恰为设计禁止的读盘校验,被隐式触发);共享物理文件导致一个成员的重建污染全组(含账面从未出错的 mover)。 已排除:libtorrent/qB 拒绝嵌套目标(源码无此检查,实测真搬);空间/冲突/同机等其余闸门误判。

06建议修法（可选）

🔴 2026-11-05 用户拍板:以下建议修法整案不采纳 —— 压测(26-11-05-0546 计划 §08)证明主方向(G5 两步纯改名复位)对生产冻结形态不成立、其余各条也只是缝补;relocate 整组迁移功能待完全重构,重构时把本 issue 与压测计划作为输入(根因链 §05 / 源码机制表 / E0-E3 实测数字全部有效)。保留原文供重构参考。
  1. GATE_QB_TEMP 改为按声明文件核对:对 plan 文件逐个「声明名 或 声明名+.!qB」存在性双查(替代内容根顶层 scandir);命中 .!qB 态 → blocked。
  2. qB「成功」不可信:setLocation 下发后短窗内(如 30-60s)核对 mover 进入 moving 态或 dst 落盘,否则快败并告警,不等 10 分钟停滞。
  3. 嵌套目标闸门:target ⊆ save_path/content_root(或反向)→ 预检 blocked(dir_alias 的 junction 会自递归)。
  4. 失败反馈面:move_stalled 等失败原因显式透出到 WebUI(红字/通知),不只落 job 账。
  5. 收尾后按声明名做 file_stat 级名核对 + renameFolder 两步复位(设计约束内,实验 G5 验证通过):归位链自动触发的只是 resume 数据校验(checkingResumeData,逐文件 file_stat 名字+大小,不哈希不读内容),它不会摘 .!qB(摘除在 handleFileCompleted 逐 piece 完成事件,仅完整哈希/下载完成时发生),且会被改名欺骗通过(账面恢复但磁盘名错位冻结)。收尾修法:成员账面恢复后按声明名核对磁盘,发现 name.!qB 化 → torrents/renameFolder 两步(内容根 → 临时名 → 原名;doRenameFolder 按完成位 true 重建实际路径,逐文件摘后缀并清 renamed_files)——纯改名,不删种/不 skip_check 重加/不读盘校验,三项设计约束全守(实验 G5:两步后磁盘原名、账面 1.00 未动、嵌套搬迁恢复真搬)。勿用 torrents/recheck 兜底(force_recheck 完整哈希,清账面+全盘读,违背约束);torrents/renameFile 也不可用(按用户路径解析,目标与其自身用户路径冲突 409,实验 G4)。

修复现场(非本 issue 范围):465 文件摘 .!qB 后缀 → mover save_path 改回 待删 → recheck → 恢复做种。
