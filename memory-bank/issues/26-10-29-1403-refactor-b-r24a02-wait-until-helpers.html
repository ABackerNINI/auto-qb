01现象

「每 poll 秒判一次 pred()，到 deadline 停」这条 6 行轮询循环在三个互不相关的测试文件里各存一份，且三份在超时返回什么与轮询步长 / 默认超时上各不相同 —— 差异没有任何一处注释说明它是判据，读起来就是抄写时各按各的习惯写了一遍。

02现状取证

取证 2026-10-29 14:00，基线 1b7dd104；行号为当时值，重定位靠符号名。grep -rn "def _wait_until\|def _wait_for" tests/*.py

  • tests/test_hr_worker.py:121 _wait_until(pred, timeout=3.0)：sleep(0.02)，超时 return False（无 docstring）
  • tests/test_notify.py:66 _wait_for(cond, timeout=2.0)：sleep(0.01)，超时 return False（docstring「等待后台派发线程消费完成」）
  • tests/test_traffic_monitor_client.py:114 _wait_until(pred, timeout=3.0)：sleep(0.01)，超时 return pred()（docstring「超时返回最后一次判定」）
  • 共享层现状：tests/helpers.py 没有通用等待原语；只有领域专用的 drive_skip(mgr, timeout=5.0)（helpers.py:1227，专为 ops 在途 job 定制，语义是"推进到终态"）。helpers.py 已 1381 行。
  • 调用点规模：hr_worker 4 处断言 / notify 7 处 / monitor_client 8 处，全部形如 assert _wait_until(lambda: ...) —— 没有一处使用返回值的其他性质。

03分歧点与判定

  • 超时返回 False vs pred() —— 判 (b) 无判据漂移。差异只在"最后一个 poll 窗口内条件刚好翻转"时可见：pred() 版多判一次，方向只会更宽松（少 flake），False 版更严。没有任何断言依赖"必须更严"。
  • 轮询步长 0.01 vs 0.02 —— (b)。线程用例 20ms 一轮、通知派发 10ms 一轮，都无外部约束；这属于可参数化的口味差异，收敛时保留为参数，不强行统一值。
  • 默认超时 2.0 vs 3.0 —— (b)。收敛后仍由各调用点显式传，不被抹平。
  • 命名 _wait_until vs _wait_for —— 同义异名，合并后自然消掉。

判定：值得做。①重复真实（3 处，其中 hr_worker 与 monitor_client 逐字同构，只差两参数）；②收敛后断言一字不改、行为可保持；③等价性可机械验证。这与已 Done 的 test-shared-micro-helper-dup（8 族 24 处收口 helpers）是同一物种，落点惯例已存在。

04收敛建议与验证手段

  • tests/helpers.py 增 wait_until(pred, *, timeout=3.0, poll=0.02)：循环体取 hr_worker 版；超时分支取 monitor_client 版「再判一次」，并在 docstring 里写死理由（只为减少线程用例的 flake，不放宽任何断言语义）。
  • 三处删本地定义改 from helpers import wait_until；notify 显式 timeout=2.0, poll=0.01，monitor_client 显式 poll=0.01，hr_worker 用默认。
  • 本单不含另外 6 处内联 deadline 循环（test_hr_discovery.py:411/473/704、test_hr_runtime.py:579/616、test_tray.py:337、test_ui.py:182/187、test_web_hr.py:495）：它们等的是外部进程 / 线程起来，超时后的动作各不相同（continue / 换断言），可另起一批；混进来会把"字面拷贝合一"变成"语义归一"，风险不成比例。
