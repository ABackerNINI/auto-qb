01现象与发现场景

怎么撞见的：用户 04:45:40 的真实帧上，图右侧自 04:45:04 起是一整片无采样斜纹，界面上却没有任何接缝提示。而同实例的接口响应里明确带着 P4 新增的 meta 键（实测 server_started_at = 1792109764.897142 → 08:16:04），说明 P4 已在该实例生效 —— 提示行不是没实现，是判据没命中。

现象：P4 的「数据接缝中 · 服务于 HH:MM 重启, 之后无采样」提示行，在「重启后首采已入账、随后立即进入开放零游程」这一形态下恒不显示 —— 而这恰是 P4 自身 E2E5 人工验收想消除的误读面（「无采样区延伸到右沿」）。

触发条件：meta.server_started_at 早于「链末桶覆盖端」。因为重启后首采总落在重启后约 1s 内，而 1m 窗桶宽 = 2s，所以链末桶覆盖端（= 首采桶 t + 桶宽）必然晚于重启时刻 —— 判据左端条件恒成立为「不提示」。

02证据

贴原文（报错 / 日志 / 命令输出），不转述；附取证时间，让读者自己判断新鲜度。

判据原文（取证 2026-10-16 09:56 · clone 工作树）：

// src/auto_qb/webui/static/shared/qb_traffic_chart.js:288-304
function _qbSeamHint(points, interval, meta) {
  if (!meta || !(Number(meta.server_started_at) > 0) || !(interval > 0)) return null;
  const n = points.length;
  let last = -1;
  for (let i = n - 1; i >= 0; i--) {
    if (points[i]) { last = i; break; }
  }
  if (last < 0 || last >= n - 1) return null;  // 全 null(空态面)/链已到右沿: 无尾部未观测区
  const started = Number(meta.server_started_at);
  const chainCoverEnd = points[last].t + interval;  // 链末桶覆盖端 = 尾区起点
  const rightEdge = points[last].t + (n - last) * interval;
  if (started < chainCoverEnd || started > rightEdge) return null;   // <-- 本形态恒在此返回
  return { startedAt: started };
}

04:45:40 帧代入（1m 窗，interval = 2s）：链末非 null 桶 = 首采桶 t = 04:45:02 → chainCoverEnd = 04:45:04；started = 04:45:01；started < chainCoverEnd 成立 → 返回 null，提示不显示。

运行实例 meta 实测（取证 2026-10-16 09:47 · curl /api/traffic/qb/global?window=3h）：

{"window":"3h","interval_s":4,"source":"qb","stale":false,"server_started_at":1792109764.897142}

判据的设计意图（专题计划 P4 实施记录原文，取证同日）：

期间服务重启 <=> meta.server_started_at ∈ [链末桶覆盖端 t+interval, 右沿]
(左端含: 重启恰在尾区起点即属尾区; 链内重启 = 链已接续, 无尾区误读)

「链内重启 = 链已接续」这条前提在「重启后首采入账、随后立即进入开放零游程」时不成立：链在形式上接续了（末桶晚于重启时刻），但右侧那段仍是无采样区。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（读码 + 真实帧参数代入）：_qbSeamHint 用「链末桶覆盖端 ≤ server_started_at」来筛掉「缝在链中、链已接续」的情形，其隐含前提是「只要重启后有采样入账，链就算接续、右侧就不会再有无采样区」。该前提在本形态下失效 —— 首采（04:45:02）确实晚于重启（04:45:01），但首采桶的覆盖端（04:45:04）晚于重启时刻，判据据此认定「重启发生在链内」而返回 null，于是右侧那段真实存在的无采样区得不到提示。

已排除：不是 P4 未生效 —— 实测 meta 含 server_started_at；不是提示行模板缺失 —— P4 已把模板行落在 drawer 三挂点共用正文块。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  1. 补一路判据（推荐）：尾区存在成片 null 游程（长度 ≥ 若干桶）时直接提示，不再要求 server_started_at 精确落在尾区内。代价：要给「成片」定量，并确保不误报「当前桶尚未采完」这一正常形态（P4 判据原文特意排除了它）。
  2. 放宽左端：条件从 started >= chainCoverEnd 改为 started >= 链末观测点时刻（而非桶覆盖端）。改动一行，但要论证不会把「缝在链中且确已接续」的正常情况变成误报。
  3. 后端直接报事实：写侧已发布 LiveTail（block_open / head_pending / 开放游程，见 traffic_store.v4_live_tail_slots），可把「当前存在开放零游程」作为 meta 字段透出，前端不猜。代价：新增契约键，需同步 P4 的双向兼容守阵（旧前端忽略新键 / 新前端遇旧后端不提示）。

实修期落点（2026-10-16 认领后）：实际走 #2 的放宽方向，但左端落为「链末桶前一桶起点 t - interval」（两端含），而非 #2 字面写的「链末观测点时刻」—— 字面形式经实测帧代入仍不够：started = 04:45:01 ≥ 链末观测点 04:45:02 不成立，判据照旧返回 null。放宽量取一整个桶宽的内因：「链在重启处断」与「重启后首个观测桶即链末」在桶粒度上本就不可分（首采恒落在重启后 ≤ 一个 main_tick，桶宽即最细窗口的判据精度）；反方向（链末桶起点晚于重启 + 1 个桶宽以上 = 链确已接续）不提示。#1 未采纳 —— 「成片 null 游程 ≥ K 桶」的阈值与既有「尾区存在（≥1 桶）」在实测帧（尾区 18 桶）同真，缺的是左端不是阈值，且新增 K 常量对「链确已接续」反例也无甄别力；#3 未实施（本轮范围守恒，「开放游程为何读侧不可见」按本报告 §03/§07 认定为独立未解问题）。
