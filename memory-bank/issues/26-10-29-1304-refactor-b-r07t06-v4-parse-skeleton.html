01现象

天文件解析 parse_v4_day_text 与 agg 解析 parse_v4_agg_text 共用约 20 行逐字相同的「解析纪律骨架」（头行门闩 / data+bad 计数 / 空行注释跳 / split(",") / except (ValueError, IndexError) / 撕裂尾豁免 / key 首个消费），当前只靠两处互指注释维持同步，任一侧改纪律即静默漂移。

03分歧点与判定

  • 输入形态：同一（text: str 全文件文本）——无分歧。
  • 行型语义：完全不同（9 列聚合行 vs 块头 + r/z/n 行）—— 属正解差异，应留在回调内。
  • 纪律语义：头行门闩口径、data 分母（头行之后逐行计入，含空行/注释/坏行）、bad 计数口径、撕裂尾豁免（仅「末行之前」那一行）、key 首个消费 —— 四项逐字相同，无判据漂移，属同一事实的两份表示。

判定归 (b) 无判据漂移该合：bad_lines/data_lines 是跨文件共用口径（读盘告警按坏行占比取阈），任一侧单独改动（如只在一侧加空行计数、只在一侧放宽撕裂尾）都不报错只静默改告警/丢行统计，正是骨架该收单点的场景。

关于上一轮修复：报告标注的相关 issue 26-10-11-0207-refactor-core-traffic-parse-diff-family-dup 为 Done，但实际做法是「B 类只登记」—— 只加了互指注释（现落在 767-769 / 1471-1473，正文仍写「登记不急合」），未消解本项（依据：该 issue 状态日志 2026-10-11 16:30 Done + 任务档案 R8 节「按建议只登记」条目）。

04收敛建议与验证

  • 抽公共驱动器 _parse_v4_text(text, empty, on_line) → (key, bad, data, torn_tail)：驱动器只管 splitlines / torn / 头行门闩（不符时 bad = data = len(lines)）/ key 首个消费 / 空行注释跳 / data += 1 / except (ValueError, IndexError) 吞异常转 bad += 1 / 撕裂尾标记；on_line(parts) 返回 True 表示已消费。
  • 两侧只留行型分支（day 的块状态机与 _close，agg 的 9/8 列兜底），空结果对象由调用方传入（V4ParsedDay(...) / V4ParsedAgg(...) 的整文件坏形态）。
  • 三个易踩点：① 头行不符时 bad 含头行本身，别在驱动器里写成 len(lines) - 1；② day 侧 cur_start is None 守卫抛 ValueError 走同一吞异常路径，不能改成回调返回 False 后另行计数（否则 data 语义分叉）；③ agg 侧逐行 continue 与 fallthrough 计坏并存，回调须能区分「已消费」与「记坏」。
  • 验证手段：① 既有守阵 tests/test_traffic_store.py::test_v4_parse_bad_line_family_cursor_not_advanced（19 类坏行 + 旧头行整文件坏 + 计数字段断言）；agg 侧撕裂行纪律用例 tests/test_traffic_sample.py:1852-1875；② 新增「同纪律夹具双 parser 同判」守阵 —— 坏行族 / 头行缺失 / 无尾换行（撕裂尾）/ 空文本 四组夹具，断言两侧 bad_lines、data_lines、torn_tail 取值同判；加分静态判据（骨架行 if not s or s.startswith("#") 全仓计数 == 1）；③ 红验两向：自抄骨架回（行为不变）只静态判据红，只删一侧撕裂尾豁免只行为判据红。
