01现象与发现场景

在 issue 26-11-02-1144（RM04-05 负向对照红灯失守）定位到闸门 GATE_SPACE 有两条拒绝分支，分别对应 relocate_units.py:488 与 L490：

  • L488：target_free is None AND same_volume is not True（空间不可判定 + 跨卷）→ 在 Z:/ 不存在盘上真实命中 → 已用方案 A 补进 RM04-05 负向对照
  • L490：target_free is not None AND target_free < needed AND same_volume is not True（空间可判定且不足 + 跨卷）→ 目前 RM04-05 无覆盖此分支的红验

为什么本机做不了（取证 2026-11-02 12:05，环境2 C盘机）：disk_usage 实测仅 C:/ 存在（68.3 GB free），D:/E:/F:/G:/H:/ 全 missing。跨卷前置 same_volume=False 在 _same_volume_resolved 里要求 src 与 dst 分属不同卷；只有 C: 盘时上溯到根也在 C: 上 → same_volume=True。且闸门自身 L492 有注释"同卷 rename 不占额外空间，空间预检不适用"——同卷即跳过 L490 分支。本机根本进不了这个分支，硬做只能伪造跨卷条件（造虚拟盘/容器），与"改测试前提"不同等，应改有第二可写卷的机器执行。

为什么不移除这个分支红验：L490 是 GATE_SPACE 两条拒绝分支之一（不是冗余），且"目标卷空间不足"在跨卷迁移动作中是真实风险场景——目标盘比源盘小、用户预算错误、qB 临时落盘吃满等。缺少覆盖不等于分支没用，应在有条件的机器上补。

05交接前置（接手机器需要满足）

需要第二可写卷（Windows 上除 C: 外至少还有 D:/E:/… 任一存在且可写），让 _same_volume_resolved 能判定跨卷；同时目标卷剩余空间 小于（或可控地调到小于）RM04-05 两枚种子数据总和（约 256 KB × 2 = 512 KB，或按用例 needed 实测值）。

第二可写卷可选来源：另一块实体盘、外置 SSD、挂载虚拟盘（DiskPart vdisk attach / DISM / 亚视虚拟盘）—— 只要 os.stat(dst).st_dev != os.stat(src).st_dev 即满足跨卷条件。

环境2（C盘机）不可用：probe 实测 D:/ 不存在。

06接手判据

不改产品代码，只改 RM04-05 负向对照段（在已补的 Z:/ 不可判定红验之后新增 L490 分支红验）：

  1. 探针：os.stat(src).st_dev != os.stat(dst).st_dev（跨卷）+ shutil.disk_usage(dst_parent).free < 用例 needed 实测值（空间不足），两个前置同时成立；
  2. 真机 POST /api/torrents/{hash}/location（跨卷 + 空间不足 dst）→ 期望 status=error + reasons[].gate == "space" + 零 started 零 "迁移发起"；
  3. 主链不受影响（dst.mkdir(parents=True, exist_ok=True) 预建后空间充足 → PASS）；
  4. 同轮 RM04 套件 9 条全 PASS（原有 8 条 + 方案 A 补的 L488 红验 + 本次补的 L490 红验 → 全绿）；
  5. 不改产品代码、不改计划正文（RM04 计划已 Done，不需要翻回）。
