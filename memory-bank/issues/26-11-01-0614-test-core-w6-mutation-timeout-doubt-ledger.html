06修复后补充（修法 / 验证 / 遗留）

实际修法（与 issue 1 共用一件，不改 src/、不改池）：问题不是「16 条该不该杀」，而是 TIMEOUT 数是超时倍数的函数，而本轮的超时倍数没有随结果留痕——W5/W6 镜像里手工加的 timeout_multiplier = 2 会在每次覆盖式重写 [tool.mutmut] 时被静默抹掉，下一轮既无法判断 120s 是 mutmut 默认 15× 还是 2×，也无法与 W6 的 TIMEOUT 计数比对。故：

  • .commands/mutants/scripts/set_conf.py：timeout_multiplier 显式写入 [tool.mutmut]（默认 15.0），新增 --timeout-multiplier 按轮次覆盖；
  • .commands/mutants/scripts/mutants.py：run 校验并透传 --timeout-multiplier，结果文件头记录 target / children / timeout_multiplier / pool / 镜像 HEAD / mutmut 版本；
  • 不改主循环异常吞没：qbmanager.run 的 except Exception 是产品容错行为，改成「不吞」属产品变更，超出本 issue 范围；变异测试只记录不判定。

验证（实测）：commands run test.pkg.scoped → [ok] test.pkg.scoped (4.9s)，包内 24 passed in 3.77s（含 4 条 set_conf 渲染 + 2 条账本头断言）；mutants.py run --dry-run --timeout-multiplier 2 确认透传与 [5/6] 行含 timeout_multiplier=2；commands run kb.index → [ok] kb.index (0.6s)；形态级探针 8/8 rc=124 @120s（见 §05）。未重跑 W6 整轮。

遗留：① 16 条 TIMEOUT 本体维持「未判定」，本轮不声称杀死任何一条；② 4 条 TypeError 只有在主循环容错策略被改（或后续轮采用更短超时倍数）时才可能改判；③ §H 6 条存疑维持疑似等价，待形态变化证伪（如 rules handler 开始读 payload）再回改真洞；④ 下一轮同池复跑时按账本头的 timeout_multiplier 能否对齐，本身即是本修法的验收点。
