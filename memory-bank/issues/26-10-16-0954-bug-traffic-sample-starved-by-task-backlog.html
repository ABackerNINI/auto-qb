01现象与发现场景

怎么撞见的：分析 08:16 重启峰值时发现，新块第二条记录是 z,1,341664,6754972,54356 —— 只有 1 个零槽，却跨 54.356 秒。按写侧口径（run_len = 连续零轮次数，dt_ms = 实测跨度），这意味着采样器重启后只转了 1 轮，下一轮迟至约 54 秒后才发生。

现象：把全部天文件按「块首第二条记录是大 dt 的 z」筛，得到 7 处，全部紧接一次进程重启，静默时长（去掉 run_len 均摊后的真实停滞 D = dt − (run_len−1)×1.5s）集中在 37.2 ~ 54.7 秒，且随种子库规模增长（种子数 177→180→183）。

后果：这 54 秒的流量增长被压进一条记录，读侧按 P2 接缝摊配打成一条平线 —— 用户看到的「重启后恢复期约 1 分钟」就是从这来的。静默被伪装成了正常速率，而且无告警、无 stale 标记。

03影响面

维度结论
触发条件每一次进程重启（7/7 复现，且历史 8 次「全量轮补建」日志全部伴随）。种子库越大静默越长；本次 183 种子 ⇒ 约 54s。热重载（L2 重建）触发同一条路径，不必是崩溃重启。
影响范围qb_traffic 采样（1.5s 周期）在静默期内一次都不执行，本次约丢 36 轮；这段真实增长被写进单条记录的 dt，读侧 P2 摊配后成一条平线。raw 段窗全部受影响（平线落在重启后的窗口内），agg 段窗同样被摊配。无告警、无 stale 标记。
严重度中-高。是本轮五个问题中唯一每次重启必然复现、且会持续产出虚假平线的一条（其余四条要么是瞬态、要么只影响单点/单个桶）。

同结构任务清单（本轮排查：队列里还有谁会被同一机制饿死）

判别式很简单：任务 interval < 积压清空窗口（≈静默时长）⇒ 必然被饿死。把队列内的周期任务逐条排开：

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（日志 + 数据 + 读码三方互证）：TaskQueue 是一条严格按 next_run 升序的最小堆，没有优先级、没有按 kind 的限额、没有独立的 internal 队列，每 tick 只弹 max_tasks_per_tick = 20 个。进程启动时 full_round 补建 183 个种子级任务（每种子 1 条 maintenance + 若干规则），全部打上「重启那一刻」的时间戳，且注释明说「补建任务立即到期」。采样任务注册得更早（日志实证 05,045 注册 / 06,018 补建），所以它首轮能抢在补建批次之前执行；但跑完这一轮后 next_run 变成 now + 1.5s，从此恒晚于整批补建任务 —— 只要积压未清空，它一次都轮不到。

清空耗时 = ⌈任务数 / 20⌉ 个 tick × 1.5s。183 种子下任务数数百，算得 40~55s，与 7 处实测（37.2~54.7s）吻合；种子数从 177 涨到 183 时静默同步变长，也吻合。

已排除：①不是主循环卡死 —— 04:45/01:30 两次的「速率键已连续 3 轮未上报」在补建后 5.3s 准时出现，说明同步线按 1.5s 节拍正常运转；②不是采样器自身抛错或休眠 —— 块首那条 r 记录证明首轮正常执行；③不是文件 IO 阻塞 —— 启动恢复本身只花 0.75s。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  1. 把采样从队列拿出来（最干净）：流量采样本质是传感器，不是一个该被 max_tasks_per_tick 限流的作业 —— 挂到「时钟线」上（与同步线同款、每轮循环按节拍直采，例如 on_sync_line 一路）。代价：采样器的生命周期与模块钩子绑定，需评估与「启动恢复 / L2 重建」的时序关系。
  2. 给队列加公平性（改动小）：_pop_due 每 tick 先保证各 kind 各取一次（尤其 internal 全局任务），再按 next_run 填满剩余名额。代价：会改变既有的「严格 FIFO」语义，需要论证不会让补建任务被无限推迟（可能引入饿死的反向问题）。
  3. 治本但需评估：补建任务的 next_run 按索引均摊到未来一个 interval，不再同一毫秒全部到期 —— 保留「首轮收敛」语义。代价：external_tag_changes 的「首轮全量收敛」契约依赖「立即到期」，需一并论证（日志里那条 issue 26-10-01-2147 的 L2 重建语义也在同一面上）。

建议优先级：本条是本轮五个问题里唯一每次重启必然复现、且持续产出虚假平线的一条，建议标 P1。

实修期对建议修法 #2 的纠正（2026-10-16 认领后）：按字面「各 kind 各取一次」修不好本例 —— 采样（kind=internal，无 hash）与补建的内置 maintenance（kind=internal，带 hash）同属一个 kind，保底的那 1 个 internal 名额会被 next_run 更早的补建任务拿走，采样仍轮不到。要生效必须细化成「无 hash 的全局任务保底」（全队列仅 ≈6 条：采样/删标/限速曲线）。原文保留于此，实际走 #1。

修复后补充

实际修法（走建议修法 #1）：src/auto_qb/core/modules/traffic_sample_mod.py —— 采样从 TaskQueue 移出，改挂时钟线钩子 on_task_line（任务线节拍，每 main_tick 一次，不受 max_tasks_per_tick 约束、不参与队列排序）：

  • 钩子只做到期闸门（_next_sample_at is None or now >= _next_sample_at 才放行），采样体 handle_traffic_sample(dry_run) 收尾自持下一到期点 _next_sample_at = now + effective；
  • 删除全局任务注册 _register_task / queue_rebuilt 订阅 / TASK_NAME 常量；_apply_interval(conf, task) -> _apply_interval(conf) -> float（去掉 task.interval 回写，节拍改由 _next_sample_at 表达）；
  • 启停与热重载不再依赖队列重建相位（采样体入口现读 conf.enabled，enabled=true 即时开采）；enabled=false 仍零文件零目录零请求（黄金法则 2）；
  • 量化口径逐字不变：effective = ceil(sample_interval/main_tick)×main_tick，块头 interval_s 与读侧消费口径不受影响（坑档 pitfalls/backend/task-interval-tick-quantization.md 条目①仍成立，同文件新增条目②记本条）；
  • 为什么挂任务线而非同步线：同步线节拍可能细于 main_tick（默认 1.5s < 2s），会把采样节拍量化到 3s，与块头 interval_s 语义冲突；采样节拍的单位本就是 main_tick（配置硬校验 sample_interval >= main_tick）。

验证方式：①回归主判据 test_sample_not_starved_by_immediate_task_backlog —— 500 个立即到期任务占满队列，走真实 _task_line 入口连打 20 拍：采样 20/20 轮全采到，且积压按配额原速排水（断言 executed == 400，证明采样不再占作业配额）；②test_sample_clock_line_gate_and_hot_reload_enable（未到点不重复采 / 停用零采样 / 热重载启用不经队列重建）；③test_sample_task_registered_when_enabled 改为断言队列零任务；④红绿双验三类突变判红后字节恒等还原复绿 —— 钩子不驱动采样(4 红) / 闸门失效(1 红) / 采样注册回队列的修复前形态(1 红)。测试数字见 commands run kb.baseline（基线切片），不在此手抄。
