01现象与发现场景

用户真机观察（2026-09-20 16:44 报）：WEBUI 底部状态栏的「下载 / 上传速度」两个数字长期显示 0， 不随实际传输变化——即有种子正在下载 / 做种上传时，状态栏仍恒为 0。

发现场景：日常使用 WEBUI 时目视发现，非某次改动的回归排查。入池时只做了静态代码阅读 （取证 2026-09-20 16:45），未做真机抓包 / 未跑 WEBUI 复现，故下面的「证据」是代码事实而非运行时事实。

状态栏位置：底部 <footer class="statusbar"> 内的 .sb-speed 区， 左右各一组「箭头 + 数值 + 当前限速」，数值分别绑定 totalDl / totalUl。

03影响面

维度结论
触发条件待复验。静态看与「状态栏合计只遍历 groups」强相关：未归组种子（singles）与平铺数据源（torrents）不计入；种子全部未成组、或分组视图未回传时合计恒为 0。是否为本例主因未验证。
影响范围prism 与 atlas 两套皮肤的状态栏共用 decorate.js 的 totalDl/totalUl，两处同受影响。统计面板（statsServer.dl_info_speed）不受影响，可作为对照。与站点 / 配置开关未见关联。
严重度中。不阻断任何操作，但状态栏是全局速度的唯一常驻入口，恒 0 等于该显示功能失效，且会误导用户以为传输停了。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

✅ 已定位（2026-09-20 17:0x 复验确认，不再是假设）。

主因：P1-1「按视图回传」把 groups 从种子页响应里裁掉了 —— VIEW_ARRAYS["torrent"] = ("torrents",)（mixins/web_view.py:48）。 前端按契约「键不存在则保留原引用」赋值（app.js:883），于是 this.groups 在种子页上 一次都拿不到数据，永远停在初始 [] ⇒ totalDl/totalUl 恒 0。

次因：合计只遍历 groups，漏掉未归组种子 singles； 桩实测（50 组 + 200 未归组）显示 1,723,392 而真值 15,206,400，少算 88.7%。

已排除：① 字段契约未声明（dlspeed/upspeed 在 _REQUIRED_SNAPSHOT_FIELDS 内， 缺失会启动期 fail-fast）；② 分组视图没跟着轮询刷新；③ 快照层速度不更新 —— 三条都被桩服务实测否定：view=group 时 groups[].dlspeed 合计 = 真值 15,206,400 ≠ 0， 数据源与刷新链路都是好的，问题只出在「种子页不回这个数组」。

推论：若先开辅种页再切种子页，groups 会保留切换那一刻的旧数组 ⇒ 状态栏显示冻结值而非 0 （比 0 更隐蔽）。用户报「永远 0」说明首屏就在种子页（autoqb.ui.view 存 localStorage）。

修复计划：memory-bank/plans/26-09-20-1702-webui-statusbar-speed-fix-plan.html ；任务档案：tasks/26-09-20-webui-statusbar-speed.md。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

本节为入池时的候选清单（保留原文）。已选定 A，详细方案与实施项见 修复计划； 若用户改要「qB 全局」口径，则走候选 C，F1/F2 整体省掉。

先把口径拍板，再动手。状态栏到底该显示「本工具纳管种子的速度合计」还是「qB 全局速度」，两者在存在未纳管种子时不相等，修之前需要用户定一句。

  • 第 0 步（复验，必做）：真机开着传输时同时读 /api/state 的 groups[].dlspeed 合计、 与统计面板的 statsServer.dl_info_speed，确认是「数据源本身为 0」还是「状态栏算错」。
  • 候选 A（口径=全部种子）：状态栏改读服务端算好的 totals（在 /api/state 里直接给 totals.{dl,up}speed， 服务端 groups + singles + torrents 去重后求和）。代价：多两行后端聚合； 优点：与 web_view.py:269 注释里「派生值后端算」的既有约定一致。
  • 候选 B（口径=qB 全局）：状态栏直接用 status.server.dl_info_speed / up_info_speed， 与统计面板同源。代价：需确认 status.server 的上游刷新频率是否够（若它本身也是低频刷新，会换个地方继续不更新）。
  • 候选 C（最小改动）：只把 singles 补进 totalDl/totalUl 的 reduce。 代价：仍是前端 O(n) 遍历、仍漏 torrents 平铺源，且违反「派生值后端算」约定 —— 只适合临时止血。

⚠️ 实施中抓到的第二个缺陷（不在原计划里）

第一版把 "totals": manager.web.speed_totals 直接写进 status 字典、ensure_group_state() 仍留在 **… 展开位 —— 字典字面量先求值，于是读到的是上一轮的旧值：首次请求拿到全 0，之后每轮慢一拍。 新守阵 test_api_state_speed_totals_survives_view_scoping 第一次跑就是红的（{'dlspeed': 0} != {'dlspeed': 10000}）， 正是它把这个缺陷顶了出来。修法：先 group_state = manager.ensure_group_state(...)（它才触发视图发布）， 再拼 status 字典。
