01现象与发现场景

怎么撞见的：32f531d（真值对齐那条）提交后收尾，补验 hang 模式 —— 它是「3s 兜底」唯一还活着的使用场景（命令发出但永远拿不到回执），而那条提交正好动了 pending 的清除逻辑，不能只验 ok / error 两种模式就收工。

现象：命令永不回执时，pending（半透明）确实在 ~3s 后消失了，但行上的状态色 停在补丁值上不走 —— 点了暂停、命令根本没执行，界面却一直显示已暂停。

触发条件：①命令没有回执（qB 未启动 / 主循环长时间没消费 / 网络中断）走满 3s 兜底； ②此后服务端视图版本没有变化（不是每次 sync 都重建 —— 95fb673「上一版没被取走就不重建」之后这更常见）。两条同时满足即永久残留； 只满足 ①的话，残留会一直持续到下一次视图重建为止。

与平台/配置无关，纯前端，两个 UI（prism / atlas）共用同一份 app.js，同样命中。

02证据

代码：src/auto_qb/web_ui/static/shared/app.js 的 isPending()（约 2314-2322）—— 超时分支只做 delete，注释写的却是“下轮以服务端为准”：

isPending(hash) {
  const op = this.pendingOps[hash];
  if (!op) return false;
  if (Date.now() - op.ts > 3000) {
    delete this.pendingOps[hash];  // 超时回落真值: 不再贴补丁, 下轮以服务端为准
    return false;
  }
  return true;
},

而“下轮以服务端为准”在 rid 门控下不成立：refresh() 里 if (state.updated !== false) { …整表替换… }，服务端版本未变时数组根本不回传， 行对象不被替换 ⇒ 上一轮贴上去的 kind: "paused" 一直留在行上。

实测（桩服务 --cmd-result hang，页面内 10ms 采样，脚本 .workbuddy-ai/tmp/probe-hang-fallback.cjs）：

目标 hash: 000000000000  点击前状态色: s-downloading
 t(ms) | 行有pending | 行状态色
    13 |       true | s-paused   <= 变化      ← 乐观补丁贴上(对)
  3660 |      false | s-paused   <= 变化      ← 3s 兜底清了 pending, 但状态色仍是补丁值(错)
① pending 立即出现: 13ms
② pending 消失时刻: 3660ms
③ 最终状态色: s-paused (点击前 s-downloading)
FAIL: 兜底窗口或落回状态不对

对照：失败回滚路径（resolveOptimistic(hashes, false)）是显式 Object.assign(row, op.prev) 的，所以 error 模式一直是干净的 —— 这也解释了为什么冒烟跑了 ok / error 两轮都没碰到它，只有 hang 模式会暴露。

03影响面与严重度

维度结论
触发频率低（要命令 3s 无回执）但一触发就持续，且不留痕、不报错
影响范围所有视图（补丁贴在 torrents / singles / 组成员上，三处都残留）； prism 与 atlas 共用 app.js，同样命中；与站点/配置开关无关
数据风险不改数据（只是显示错），但会误导判断：用户看到“已暂停”就不再操作， 实际上命令从未执行；若据此去删种子/改限速，判断依据是错的
严重度中 —— 违反 systemPatterns 明写的红线 「失败/未知绝不留永久假状态」，但需 3s 无回执才触发，不丢数据

04根因（初步）

结论（已定位，非猜测）：兜底语义写错了 —— 它把“清除 pending 标记”当成了 “回到真值”。清除标记只让行不再半透明，行上的字段值仍是补丁值；真正能覆盖它的 只有“服务端回传新数组把行对象换掉”，而这被 rid 门控挡住了（服务端没变化就不回传）。

同类的另一处：失败回滚路径显式 Object.assign(row, op.prev)，所以 error 模式干净 —— 两条路径写法不一致，超时的那条漏了回滚。

已排除：①不是 reapplyPending 又贴回去（pendingOps 已删，循环直接 continue，实测 3660ms 后 class 不再变化）；②不是服务端真值被改（hang 模式桩服务永不改状态， _apply_truth 根本没跑）；③不是选择器/DOM 陈旧（探针直接读该 hash 的行 class）。

05建议修法

方向：让超时路径与失败路径写法一致 —— 超时也显式回滚到 op.prev。

方案 A（推荐）：超时显式回滚 prev

新增 _expirePending()：遍历 pendingOps，凡 now - op.ts > 3000 的 Object.assign(row, op.prev) 后 delete；在 refresh() 里先于 _snapshotTruth() / reapplyPending() 调用一次。 同时把 isPending() 改成超时只返回 false、不 delete（回滚交给上面的清扫）， 避免在渲染函数里改响应式数据（模板每帧都会调 isPending，在那儿写字段有递归更新风险）。 代价：过期条目最多多活一个轮询周期（1.5~3s），期间行不再半透明但字段仍是补丁值 ⇒ 与现状一致，不更差；回滚发生在下一次 refresh，实测约 3.6s 到位。

方案 B：超时立即在前台回滚（不等下一轮 refresh）

点命令时挂一个 setTimeout(…, 3000)，到点直接回滚 + 删条目，不等 refresh。 落地更快（3.0s 而非 3.6s），但要为每个 pending 管定时器，且要在回执/回滚时成对清理， 漏一个就会把已成功的操作回滚掉（比慢 0.6s 危险得多）。收益小、风险大，不推荐。

验收（两者都要）

把 hang 模式做成常驻冒烟而不是一次性探针 —— 现在 ok / error 两轮都碰不到这条路径， 缺陷才能躺到现在。判据：pending 立即出现 / 约 3s 后消失 / 最终状态色 == 点击前。 ⚠ hang 模式 waitCmd 超时是 40s，整轮冒烟会很久 ⇒ 建议单独起一个 --cmd-result hang 的桩服务只跑这一条断言。

实际修法：与方案 A 一致，未改道。
