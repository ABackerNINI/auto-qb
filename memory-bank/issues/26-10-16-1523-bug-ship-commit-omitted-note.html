01现象与发现场景

2026-10-16 收尾一笔仓库卫生变更时撞见: 该笔要把 .zwork/ 与 .zcode-tmp/ 补进 .gitignore 并撤出 10 个已入库的临时证据(属既有档 pitfalls/git/ship-commit-staged-delete.md 的「变体」所述形态: 忽略规则一生效, 被撤路径对 git add 不再是合法目标)。于是按那一档的处方走**子集提交**: commands run ship.commit -- .gitignore <两份记忆文件>。

脚本末行打印: …(子集提交: 另有 10 个改动未纳入(.zcode-tmp/a-04-all.png、… ) —— 确认这是有意的) —— 字面意思是「这 10 个没进本笔」。实际相反: 紧接着的 git show --stat HEAD 里 10 条 Bin … -> 0 bytes 删除项都在, 推完后远端与本地也一致(见 §02)。触发条件: 任何子集提交, 且工作区里还有**已暂存**的、未传给脚本的其他改动 —— 此时提示与「实际提交内容」恰好相反。

03影响面

维度结论
触发条件子集提交(ship.commit -- <paths>)且存在「已暂存但未传参」的其他改动时必现 —— 计数与列表都按「未传参」算, 与「是否进了本笔」无关。
影响范围只影响**提示可读性**, 提交内容与推送结果都是对的(本件实测: 删除项已落笔并推到位)。但会直接误导操作者: 以为「要再补一笔」或「撤跟踪没生效」(本轮确实为此多做了排查); 反向风险也存在 —— 即将某个**真正未暂存**的改动读成「已进提交」。
严重度低(无数据 / 正确性损失)

04定位锚点

符号名 + grep 关键词 + 当时的行号（标取证时间）—— 代码会漂移，靠符号与 grep 重新定位。

  • .commands/my-commit-flow/scripts/commit.py:245-247(取证 2026-10-16 15:23)· omitted 的计算与那行 print("…(子集提交: 另有 …") · grep 关键词 子集提交 / omitted
  • .commands/my-commit-flow/scripts/commit.py:227-237(同上)· 逐路径暂存三分支(工作区存在 -> git add; 索引有而工作区无 -> git rm --cached; 都不在 -> 跳过) —— 删除项一旦「跳过」, 它仍在索引里, 因而会随 git commit 落进同一笔。
  • 同族既有记录: memory-bank/pitfalls/git/ship-commit-staged-delete.md(「变体」节已写「那个 D 删除条目不用 add, 会随 git commit 落进同一笔」)。

05根因（可选）

机制已定位(读源 + 实测核对, 非推测): 子集模式只把**传入路径**放进 to_stage 去逐路径 git add, 而 omitted 是「相对全部改动」算出来的清单 —— 两者都不等于「提交面」: 该笔的 git commit 提交的是**整个索引**, 所以已暂存的其他改动照样落笔。提示文案「未纳入 …… 确认这是有意的」描述的是「未参与 add」, 却读起来像「未进本笔」。

已排除: ①不是 add 失败 / 被忽略路径导致的静默跳过 —— 该笔里删除项确实进了提交(§02 ②); ②不是推送环节补写 —— git show --stat HEAD 在推送前就已包含它们; ③与 --no-push / 网线无关。

06建议修法（可选）

只给方向与代价, 不在本报告里实施。

方向 A(最小, 推荐先评估): 把措辞与语义对齐 —— 打印前按索引状态把 omitted 分成两组: 「已暂存(仍会随整索引进本笔)」与「未暂存(不会进本笔)」, 各自给计数与示例; 或直接把那句改成「未参与 add(其中已暂存的仍会在本笔里)」。代价: 改一段打印逻辑, 不动提交行为。

方向 B(更彻底, 代价高): 子集模式改成**真正路径限定的提交**(git commit -- <paths> / --only), 让提示与行为天然一致。代价: 会推翻「已暂存删除项随整索引落笔」这一既有便利(该行为已被坑档与实测依赖: 忽略规则生效后没法再 git add 那条路径, 只能靠整索引带走), 改前须逐条评估影响。

取舍建议: 现状不影响正确性 —— 选 A 即可; 若维护者想要「提示=行为」的强一致, 再议 B。
