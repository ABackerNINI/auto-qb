01现象与发现场景

在做 issue 26-11-03-1120-test-webui-config-normalize-parity-gap（前后端归一缺跨语言对拍）时，通读 tests/webui_dom_page_support.py 的 cfgNormalizeRulesDraft 用例作对照, 发现其中一条断言与"归一生效"在逻辑上互斥:

["cfgNormalizeRulesDraft: 扁平 conditions 包隐式 all(叶子零触碰)",
  (ctx.cfgNormalizeRulesDraft(), J(t().legacy.conditions) === J({ all: [{ size: ">=1MiB" }, { path: ["/a"] }] }))],

该用例的 fixture（同文件 RULES.legacy）是扁平列表 conditions: [{ size: ">=1MiB" }, { path: ["/a"] }]。若 cfgNormalizeRulesDraft() 真执行了 spec.conditions = { all: spec.conditions }, 断言期望值成立、用例绿；否则期望值是 [{size:…},{path:…}]、用例红。当前该用例为绿 —— 但绿与"电池没跑"同样无法区分（扫描型/行为型守阵共同的不可判形态）。

与此并存的是同一文件里 cfgNormalizeRulesDraft 幂等那条：(ctx.cfgNormalizeRulesDraft(), ctx.cfgNormalizeRulesDraft(), true) —— 第二次返回值被忽略、恒比 true, 无论归一是否生效都绿。这两条合起来意味着：这组 DOM 电池对"归一语义"的检出能力存疑（一条可能恒绿的真常形态 + 一条恒真的假绿形态）。

观察结论
条 1 期望 {all: [...]}, 输入是扁平列表只有归一真执行才可能绿; 绿了 ≠ 电池有效(可能根本没跑到条 1, 或 t() 取到的不是被归一的那棵树)
条 5 返回值被 () 吃掉, 第三元素 true 字面量确证恒真 —— 无论归一是否幂等都绿
条 2 未调用 cfgNormalizeRulesDraft() 直接读 t().treeform.conditions若归一有副作用改了 legacy 就该失效; 现绿说明断言间存在执行顺序耦合（条 1 是否先跑、t() 是否返回同一引用）—— 待查

03影响面

维度结论
触发条件跑任何执行 tests/webui_dom_page_support.py 这组电池的测试(本机有 node 时); 与配置数据无关, 与是否 node 无关
影响范围草稿归一(D2/W3-A/W3-B)在 webui DOM 测试面的自动守阵, 即"打开即归一形"这条验收的电池担保
严重度中 —— 不影响运行行为, 但会让前置镜像与后端归一的内存漂移静默通过这段电池

06建议修法（可选）

方向: 先让这组电池"知道自己有没有跑"(活性), 再谈修断言。候选(未拍板):

  1. 红验式参差断言：条 1 改成"先断言输入是扁平列表 → 调归一 → 再断言变树形", 三步分开; 条 5 幂等改成取两次返回值做 J(a) === J(b) 深比较(而不是丢返回值恒 true), 并先用一个非幂等专桩样本证明它红。
  2. 电池结果代替置喙：_NODE_RULE_TREE_PROBE 的 ok/total 在 Python 侧只有失败才打印; 加一条"故意注入一例必红期望, 整体必须红"的活性探针(同 pitfalls/testing/guard-dead-branch.md 手法), 防整组电池因某条语句早退/正常结束而全绿。

建议修法 不改 生产代码：config_rules.js / config_editor.js 产物在 issue 26-11-03-1120-test-webui-config-normalize-parity-gap 的对拍守卫(src/tests/config_normalize_parity_support.py / test_webui_config_normalize_parity.py)中已被独立对拍; 本条只涉及 DOM 电池自身的有效性和活性。
