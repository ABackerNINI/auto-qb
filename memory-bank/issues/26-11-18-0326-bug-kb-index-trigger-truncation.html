§01现象与发现场景

2026-11-18 认领修复 issue 26-11-18-0210(sync_agent_skills 路径断言 Windows 盲区)的收尾评审中, 给 memory-bank/pitfalls/backend/platform-fs.md 新增坑档条目时按惯例把新节关键词追加进该文件三行头的「触发」行, 重跑 commands run kb.index 后发现: 追加的关键词在全部生成索引 _index*.md 里零命中 —— 触发行过长的文件, 其尾部关键词进不了生成索引。纯机械追加/前置两种写法各实测一轮, 均由只读评审子代理抓出(追加→零命中; 前置→挤出既有尾部词的零和回退), 属索引生成器层面的机制缺口, 与单条坑档的写法无关。

§03影响面

维度结论

§05根因（可选）

已查明 (2026-11-18 认领修复时): 截断单点在生成器 gen_kb_index.py 的 TRIGGER_MAX = 120(摘要 SUMMARY_MAX = 140), _clip() 超长静默截断加省略号 —— issue 实测的「整行约 239 字符截断」即触发列 120 字符截断在整行上的体现。截断本身是**有意设计**(2026-10-11 单文件时代元数据顶爆 cap 的体积手段), 但 2026-11-05 分卷机制落地后它已是冗余, 缺陷在「静默吃路由面」: 复验查明全库 120 个坑档触发行(共 370 个)**全部**超限, 尾部关键词系统性不可达。已排除: 源文件写法问题、kb.index 未重跑(入池时的两条排除维持成立)。

§06建议修法（可选）

两条候选方向（未实施）：① 生成器侧 —— 触发列超预算时不静默半词截断: 要么全量保留(与 8000 字符卷 cap 的判定联动, 超长行单独处理), 要么截断时打可见警告行提示「尾部词不可达, 请精简触发行」; ② 约定侧 —— 在 doc-forms/kb-structure 约定里明示「触发行前 ~240 字符才进索引」, 并给 kb.new pitfall/收尾 DoD 加超长提示。①治本②治标, 可并行; 取向取决于生成器截断是有意设计(压卷 cap)还是无预算意识的副作用, 认领时先读生成器定夺。

修复后补充

实际修法 (2026-11-18): 走建议①的「全量保留」支 —— gen_kb_index.py 退役行内截断(删 SUMMARY_MAX/TRIGGER_MAX/_clip), 摘要与触发词全量进索引, 体积约束回归分卷 cap 单点(INDEX_BUDGET = 8000, 生成器确定性分卷自适配)。取向判据: 截断是分卷机制(2026-11-05 B4)落地前的单文件体积手段, 落地后已冗余; 复验查明 120 个触发行全部超限, 「截断+可见警告」路线的警告对存量是每轮 120 条的恒久噪音, 「请精简」不可行 —— 全量保留后没有内容被丢, 连告警机器都不需要。建议②落为约定回写: doc-forms.md「索引与检索」明示「触发行全量进索引, 不存在暗预算」; kb.new 不加超长提示(没有上限)。
