01现象与发现场景

做「WEB UI 操作跟手性优化」的对抗性复核时（报告 docs/plans/26-09-19-1745-webui-responsiveness-review.html §05.4）量到的：服务端同步线按 sync_interval（默认 1.5s）跑，每次 _sync_line 只要视图脏且 Web 活跃就 rebuild_views()；而前端 basePollMs() 按种子量 分档取 1.5s / 2s / 3s。两条节拍各自独立定档，中间没有任何协商。

种子数 >3000 时前端 3s 才取一次 ⇒ 服务端在这 3s 里产出 2 个版本，客户端只取到最后一个， 中间那一版的重建 CPU 没有任何请求消费过。

触发条件：只要 WEB UI 开着且种子数超过分档阈值。与平台无关，默认配置即命中。

02证据

服务端节拍（默认 1.5s，固定值）：

# src/auto_qb/config/models.py:187
sync_interval: float = 1.5  # 种子状态同步间隔(秒): 只刷新快照, 不跑任务 —— 与 qB 自带 WebUI(1500ms)同量级

# src/auto_qb/qbmanager.py:518-527
def _sync_line(self, dry_run: bool, flush: bool = True) -> None:
    """同步线(sync_interval 节拍): 拉 qB 增量 -> 推进快照/事件/分组 -> 视图惰性重建
    只做状态同步、**不跑任务** —— 状态新鲜度不再被任务节拍(main_tick)拖累。
    sync_interval 取 1.5s 与 qB 自带 WebUI(1500ms)同量级: 比 qB 自身数据粒度更快没有意义。
    """
    self._refresh_torrents(dry_run)
    if flush:
        self._flush_views()

现有门控（注意它判的是「最近有没有网页连过」，不是「这一版有没有人取」）：

# src/auto_qb/qbmanager.py:515-516
if self._group_view_dirty and (time.time() - self._web_last_seen) < WEB_VIEW_TTL:
    self.rebuild_views()

03影响面与严重度

维度结论
触发频率常驻 —— WEB UI 开着即持续（不是偶发）
影响范围种子数 >3000 的库约 50% 的 rebuild 无人消费；1000~3000 约 25%；≤1000 无浪费。与视图/站点无关，只与种子量和「网页是否开着」有关
数据风险无 —— 不丢数据、不写坏状态、不影响限速；纯粹是 CPU 与电量的浪费（页不严重时甚至更省）
严重度低（复核报告 §05.4 原判「小」，本报告沿用；属优化项不是缺陷）

04根因（初步）

结论（机制明确，浪费比例是推导）：两条节拍各自独立定档 —— 服务端 sync_interval 是固定 1.5s，前端 basePollMs() 是按种子量 1.5/2/3s，两者之间没有协商或门控； 现有的 WEB_VIEW_TTL 门控只判「最近有没有网页连过」，不判「这一版有没有被取过」， 挡不住这个浪费。

已排除：① 不是前端分档算错 —— 档位由实测单轮 refresh 耗时按「主线程占用率 ≈15%」反推 （1000:143ms / 3000:353ms / 5000:~550ms，见 testing.md），分档本身有依据； ② 不是 rebuild_views() 太慢 —— 3000 种子实测约 50ms，慢不慢都改变不了「这一版没人看」； ③ 与第 1 批加的 min(sync_interval, main_tick) 钳制（qbmanager.py:345）无关 —— 那条只兜住「sync_interval 配太大导致快照新鲜度掉到心跳之下」，解决不了「重建了没人消费」。

05建议修法

两个方向互斥，且代价量级不同，需要先拍板（本报告不给结论）。

方案 A：让轮询跟上快档（降 basePollMs() 档位）

把前端在大库下的间隔从 3s 降下来，让服务端每版都有人取。代价：会放大全量回传与整树重渲染 —— 这正是当初「P1 落地后才敢降轮询」的原因，顺序错了会加剧不跟手。有 §11 的修复（服务端 189→23.5ms） 垫底后，这条路比之前安全，但仍需重新实测 A/B 决定档位。

方案 B：给快照刷新加「会有人取」的门控（推荐方向，但成本更高）

细化现有的 WEB_VIEW_TTL：不只看「有没有网页连过」，而是让 rebuild_views() 只在「这一版会被取走」时才跑（例如按客户端实际轮询档位节流，或让 /api/state 的 rid 消费情况反向驱动）。优点：不动前端轮询频率，不引入「更频繁回传」的风险。 代价：需要服务端知道客户端当前档位/上次取的版本，属于新契约，改动面大于 A。
