01现象

抽屉种子详情「四内容页签的正文宿主」在合并态已由 dtPairCols 数据驱动，但非合并态仍是 4 个硬编码 <div class="dt-host"> + 桥循环里一个页签名数组（['general','trackers','peers','content']）—— 页签清单在 DT_TAB_LABELS 之外又多存了两份。加第五个内容页签要同时改 DT_TAB_LABELS、4 个 div、1 个数组；漏改 div 的表现是「新页签钮在、正文宿主不存在」= 整幅空白且无报错。

03分歧点与判定

  • 宿主从哪来：合并态 MERGE_PAIRS → dtPairCols（有单点）↔ 非合并态模板字面量（无单点）。
  • 桥的页签清单：合并态 col.tab ↔ 非合并态内联数组字面量。
  • 是否有意分叉：无判据。两侧注释都是同一句「每页签一个 data-dt-host 宿主」（207-208），没有一处说非合并态为何必须写字面量。归类 (b)：无判据漂移，该合；不判 (c)——当前四个宿主齐全，无现网错误。

判定：值得做（refactor / light）。① 重复真实：页签清单在单点之外还有 4 个 div + 1 个数组两处字面量；② 行为可保持：改为 v-for="t in dtTabItems" 后 DOM 仍是「4 个同级 div（顺序 general/trackers/peers/content）+ 其后 4 个桥锚」，无新增 wrapper（宿主本身就是挂载目标，不是单元格，不触 grid :nth-child 边界）；③ 可验证：静态守阵改写（见上）+ 既有 e2e e2e/drawer-merge.spec.mjs / e2e/dt-table-layout-parity.spec.mjs / e2e/drawer-tables.spec.mjs（宿主挂载与表格面）可跑；④ 收益中（页签清单真正一处，加页签零漏改）＞ 风险低（纯模板结构，无数据面）。

04收敛建议与验证

非合并态两段都改吃 dtTabItems（不要再新增单点，DT_TAB_LABELS 就是它）：

  • <div v-for="t in dtTabItems" :key="'dth-' + t.v" class="dt-host" v-show="dtHostOn(t.v)" :data-dt-host="t.v"></div>
  • <template v-for="t in dtTabItems" :key="'dtb-' + t.v"><aq-dt-bridge v-if="dtBridgeOn(t.v)" :key="dtBridgeKey(t.v)" :tab="t.v"></aq-dt-bridge></template>

不要把宿主与桥合成一个 v-for（两个根节点需要 <template v-for> 包裹，桥会插到每个宿主后面 —— 兄弟序从「4 宿主 + 4 桥」变成「宿主,桥,宿主,桥」，虽无 CSS 依赖但属无谓的 DOM 变更，等价性验证成本变高）。

验证：① 静态守阵改写 test_webui_static_dom_panel.py（同函数内）：删「逐页签 count == 1」，改断言 drawer_tpl.count(':data-dt-host=') == 1 + dtTabItems 由 DT_TAB_LABELS 投影（四键）+ drawer_tpl 里再无 ['general', 'trackers' 字面量；② pytest tests/test_webui_static_dom_panel.py -k drawer_form_judge 绿；③ e2e drawer-merge.spec.mjs（合并/非合并切换后宿主可挂）与 dt-table-layout-parity.spec.mjs 绿。
