01现象与发现场景

QbApi 的部分写方法在调用 qB 之后立即改写快照，隐含「命令已生效」：删除会立刻摘记录、 打标/分类/限速/路径会立刻改字段。qB 的状态按固定节拍刷新，这些写入在生效前就把账改了。

对照（同一份门面里已有的先例）：起停四入口已按 A 系 26-10-13-0540 S1 改为纯透传 + note_own_write， 注释写明「state 是唯一由 qB 同步权威驱动的字段」—— 本件记的是这条口径尚未推广到删除与字段写。

02证据

贴原文，不转述。

A. 删除即摘记录（core/qbapi.py:153-156，取证 2026-10-21 18:26）：

def torrents_delete(self, torrent_hashes=None, delete_files=False, **kwargs):
    self._client.torrents_delete(torrent_hashes=torrent_hashes, delete_files=delete_files, **kwargs)
    for h in self._to_list(torrent_hashes):
        self.store.remove_torrent(h)

B. 打标/分类/限速/路径直接改字段：qbapi.py:59-94（torrents_add_tags / torrents_remove_tags / torrents_set_category）、:130-151（上下限 / set_location）→ store.update_torrent_fields。 这些是确定性字段（值就是我们下发的），与「运行状态」不同；争议点是它们同样在命令返回后立即写，且 set_location 会改分组键的输入（组键由 group_key_of(物理目录, 文件映射) 构造）。

C. 反例（已改对的那一半，qbapi.py:96-124）：起停纯透传，只登记 own_writes，注释原文 「!不回写快照(A 系 26-10-13-0540 S1: 删除原 _sync_paused_state 合成回写)。state 是唯一由 qB 同步权威驱动的字段」。

D. 文档仍是旧口径：memory-bank/conventions/code-style.md 原第 101 行「写后同步: 任何通过 QbApi 的写操作同步更新 store 快照」 —— 2026-10-21 18:26 已按用户判定作为档案漂移移除（代码早已改面，文档未跟）。

03影响面

维度结论
触发条件任何走 QbApi 门面的写操作；命令未生效前读取快照的消费者都会读到假账
影响范围① remove_torrent 只摘 by_hash，groups/member_to_key 不动 → 幽灵成员；② 预测 state 污染 G3/G4/G6/G7；③ 改 save_path 直接影响分组键
严重度中：与「命令后立即读状态」叠加时，会把错误的账喂给所有闸门

05根因（可选）

门面把本地账本当成「写缓存」：命令成功即改账。命令成功只说明 qB 接受了请求，不说明状态已生效； 真正的账要等 qB 上报。起停已经按这条改面（A 系 S1），删除与字段写还停在旧口径 —— 缺的不是新原则， 是把既有原则推广完。
已排除：不是字段映射错误（字段名与 qB 一致）；不是 _sync_paused_state 仍在（已于 2026-10-13 删除）。

06建议修法（可选）

重构方向：写门面只发命令、不写账；账一律由 sync 落。需要「本地立即反映」的地方，改为等待上报或在前端做乐观态（可回滚）， 不写进服务端快照。本件不单独实施。
