WEBUI 错误信息历史: 右下角 toast 退场即销毁, 错过后无处可查

WEBUI 加错误历史功能: 全局错误反馈只有右下角 toast 一条通道, 8~9 秒自动消失且不留痕迹, 刷新/重连还清空; WEBUI 又不暴露后端日志, 错过 = 无处可查。建议 toast() 单点追加会话内错误环形缓冲 + 右下角小入口弹层

01现象与发现场景

用户提问「WEBUI 有没有必要加右下角错误信息历史功能」，据此对现有错误反馈链路做了一轮只读调查（问答轮次，未动代码）。结论：有必要。

现状是：全局错误反馈只有右下角 toast 一条通道，退场即销毁、不留任何痕迹。而本工具是挂机型使用场景，用户常常几分钟才看一眼屏幕；相当一部分错误不是点按钮瞬间发生的——批量操作逐项推进时的中途失败、命令后台等待超时、删除多目标「未完全成功」这类操作后数秒才弹的结果，toast 8~9 秒后自动消失，错过之后唯一出路是去服务器翻 auto-qb-data/ 的日志文件（WEBUI 没有暴露任何日志查看端点）。轮询/推送断线这类「无人值守期异常」目前更是静默处理（只重连不提示），历史功能落地后这类事件顺带有了可追溯的落点。

03影响面

维度结论
触发条件任何 error / warn 类 toast 在展示期（8~9s）内未被用户看到即永久丢失；刷新 / 重连则连展示期都没有。挂机型 + 批量操作场景下概率高，与平台 / 配置无关。
影响范围全部 WEBUI 皮肤（atlas / console / prism 共用 shared 层）的全部错误反馈；不涉及后端与数据安全，纯前端可观测性缺口。
严重度低～中（可用性增强而非缺陷；但错过错误后排障成本高——要去服务器翻日志文件）。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

最小方案（解决大部分场景）

error / warn 类 toast 不再纯靠定时消失：改为可手动关闭，或存活期大幅拉长（如 30s + 点击才走）。零新数据结构。

完整方案（推荐）

  • 数据层：所有错误已在 toast() 单点汇合——退场时把 error / warn 条目追加进环形缓冲（上限 ~50 条，带时间戳与 kind），会话内存级，不持久化、不进后端（符合保守默认与幂等约束）。
  • 入口：右下角常驻小图标，有未读错误时显示计数徽标；点开列表弹层（复用现有 modal / drawer 体系），支持单条复制与一键清空。
  • 清空时机：auth.js 登录 / 重连清 toasts 时历史建议保留（只在内存里，无持久化代价）。

不建议

后端持久化错误历史、错误分级过滤、跨会话保留——单用户个人工具属过度设计；全程审计已有后端日志文件承担。

待拍板

历史只收 error 还是连 warn 一起收：只收 error 最克制；连 warn 收覆盖面全但噪音多（「站点已存在」这类提醒也进历史）。倾向只收 error + busy 结算出的超时 / 失败终态。
