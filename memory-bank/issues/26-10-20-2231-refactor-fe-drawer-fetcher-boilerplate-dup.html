01现象

现象: drawer_store.js 里 _fetchDrawerDetail / _fetchDrawerTrackers / _fetchDrawerFiles / _fetchDrawerPeers 四份骨架相同, 每份约 22 行:

  • 两道 stale 代际守卫(请求前后各一次) + loading 门;
  • _dtNotify 通知变体层 + _drawerDone 落定;
  • 次序有心: 先守卫再落定, 否则慢响应会覆盖新数据 —— 这个"有心"在四份里各写一遍。

02位置

  • src/auto_qb/webui/static/shared/drawer_store.js grep _fetchDrawer(取证 2026-10-20 22:30: 四个函数连续相邻)。
  • 配套单点: _drawerStale / _drawerDone / _startDrawerPoll / _stopDrawerPoll 同文件。
  • 明细台账: R21-A-01。

03建议（可选）

收敛为 1 份骨架 + 4 个差异项(端点 / 归一函数 / 目标状态键 / 空值形状)。顺带: _startDrawerPoll 缺 qb 侧已有的"悬挂兜底"(超时未回即复位 loading), 见 fe-polling-family-dup。

04修复与验证（2026-10-21 认领并修）

复验（认领后第一件事, 2026-10-21 05:34）: 现象仍在 —— 四份 fetcher 仍连续相邻 （drawer_store.js:112-197, 各 19/22/21/24 行）, 全层 this._drawerStale(hash, seq) 共 13 处（四 fetcher 各 3 路 = 12 + _drawerDone 1 处）, 与入池记录一致。

实际修法: 按 §03 落地「1 份骨架 + 4 个差异项」——

  • 唯一骨架 _fetchDrawerSource(src, silent, seq) 固定那条有心次序: hash 快照 → ① 前置门 → try{api} → ② stale 守卫 → ③ 归一 + 引用稳定合并 → 清失败标记 → catch{失败提示 / stale 守卫 / 落失败标记} → finally{stale 守卫 → 清 loading → _dtNotify → _drawerDone}。三条「颠倒即静默故障」的次序写进头注并逐条说明为什么不能动 （stale 前移 = 慢响应覆盖新目标 / 列表通知早于清门 = 空列表停「正在加载…」一拍 / 漏 _drawerDone = FX-29 遮罩挂死）。
  • 差异项表 _DT_FETCH（顶层, 全仓唯一一处）: 每源声明 url(端点) / norm(归一: 取载荷 / peers 键名适配 / 恒数组形) / key(目标状态键) / rows + pack(空值形状), 外加三条结构性差异 loadingKey(列表门抑制) / errKey(失败标记) / notifyAtLand(通知时机)。两处刻意不对称原样保留: 详情无合并(整值落袋)、 无 loading 门、无 toast、落袋即通知; 三列表源走门抑制单点、失败落标记 + 非静默 toast、 清门之后才通知。
  • 四个具名入口 _fetchDrawerDetail/Trackers/Files/Peers 退化为 单行薄壳（名字是调用点 / 守阵 / 跨模块登记认的接口, 签名与默认值一字未动）, 差异全在表里。
  • §03 顺带提到的 _startDrawerPoll 悬挂兜底本轮未做 —— 它属 fe-polling-family-dup（轮询族收敛）, 混进本轮会把「取数骨架」与「轮询退避/兜底」 两件事绑在一起, 违反范围守恒。
