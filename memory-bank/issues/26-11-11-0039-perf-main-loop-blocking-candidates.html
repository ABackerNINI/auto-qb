§01现象与发现场景

2026-11-11 00:20–00:38 的连续问答里，用户连着问了三件事：「哪些会阻塞主循环比较久（超过 500ms 就算）」→「哪些可以且值得移出主循环」→「① 已经按开工作线程开工了，之前的约束不一定正确，需要验证」。核查后发现：先前把架构口径读窄了，把「不开工作线程写共享结构」误读成「一律不开工作线程」。用户随后要求按新事实重排，并把结论聚合成一条 issue、出一张详细表，具体实施留到后续排期。

主循环是单线程：命令线、同步线、任务线、微步线在同一拍里串行跑。任何一个同步操作占住超过 500ms，WEB 点什么都要排队、快照滞后、其它模块的任务线一起停。项目自己埋了更严的阈值 CMD_SLOW_MS = 300（对每条命令打「排队 / 执行」两段耗时），超了就 WARNING，所以 500ms 这条线已经被它覆盖。

这份 issue 是什么：一份判断与留档清单，说清「哪些值得做、做出来是什么功能、有什么坑、怎么验」。它不是改造方案、不是实施计划。本件不指派、不认领、不出实施计划、不改代码；本文件本身随本批提交入库（提交的是这份文档，不是代码改动），表里的每一项实施都等后续排期。

取证边界：代码基线 2dfb6fa3（开工同步输出「已同步 2dfb6fa3」），本机三个 clone 工作树均干净。任务队列是 TaskQueue 的内存最小堆，不落 state.json，本 clone 也没有 auto-qb-data/ 运行时目录，所以「此刻运行实例里排队的具体任务实例」读不到。表里的时长来自代码里的超时常量、注释里的实测数字和真机标定，不是运行实例采样；真值要看运行实例日志（见 §06.4）。提交时基线已推进到 09d03379，期间新增了正式实施计划，见 §04 漂移标注与 §06.6。

§03影响面

维度结论
触发条件只要主循环线程上出现一个同步等待 / 大批量 I/O：转移批次验证、多成员组迁移探测、迁移确认框预检、搜索索引重建、qB 假死命中 10s 读超时、大库 state 落盘。常态就会过 500ms 的是前四类；后两类是异常态或特定规模。
影响范围全局：WEB 命令排队变长、快照滞后、14 个模块的任务线同期停滞。不是某个视图慢，是整个进程一拍不动。
严重度高（P1 项单次可占几十秒）。但本件是聚合清单、状态 Open、全部待排期，本身不代表已在修。
口径纠正（写在这里，免得以后又读错）：项目禁的不是「开工作线程」，是「工作线程写共享结构」——任务队列、state_file、store 分组索引、表现层视图。项目本来就有 uvicorn 线程、HR worker、notify daemon；traffic_store.py:524 / traffic_limits.py:256 甚至自带 threading.Lock()。「全程无锁」只对核心 store / 队列 / state 成立。关联 issue §06 也把「独立线程 + 主循环消费结论」明写成保持约束的方案。

判断公式（本表排序依据）：收益 = 卡住时长 × 触发频率；成本 = ① 是否写共享态（决定要不要拆状态机）② 是否要读一致快照（决定要不要先拷贝）③ 是否可能并发多实例 / 带长超时（单飞 + 叫停口）④ qB client 是否共享（Session 重建竞态）。合规姿势只有三种：A 后台 I/O + 结论回灌（不写共享态，最省）、B 让出 + 跨 tick 续跑（要写共享态，留主循环切微步/相位机）、C 快照输入 + 主循环原子发布（只读但要一致快照，成本最高）。

§06.2 不值得 / 不该移（留痕，免得以后重复论证）

事项为什么不动（直白说法）真要治该用什么便宜办法
state.save() 周期落盘序列化时要读 self.data，而主循环同时在改它；后台写盘可能在关停后还在跑、或存下半更新状态。退出顺序是 stop_all → state.save → 释放锁，后台化会破坏这个顺序。默认 120s 一次、通常 < 500ms。真遇到慢盘 / 超大 state 再单独量，先别动线程。
reload_config无条件广播 14 个模块 apply + L2 全量重匹配 + 队列重建，全在写共享态。HR 端点 / 发现线程重挂各有 5s stop-join 预算。5s join 属「给等待配叫停口」的治理，不是移出主循环。
四视图重建 + 同轮发布在 view_lock 里一次性替换全部视图与版本号；跨线程会让前端把陈旧数组当新数据换上。保持现状，属架构硬约束。
qB 同步线 /sync/maindata主循环必须拿到结果才能 store.apply_sync 推进状态，搬线程不解。读超时 10s（REQUESTS_TIMEOUT=(3,10)）属假死场景。超时治理 / 熔断，不在移出清单。
tracker 预取 20 条/tickTRACKER_HEALTH_BUDGET=20，注释实测约 7.5ms，占 1.5s tick 的 0.5%，根本不是阻塞源。不用动。
traffic_snapshot 全量读 dat更正前一轮的黄档判断：26-10-21 起 notify 走载荷补丁零读盘，读盘收拢在 refresh_interval 闸门（只剩 600s 定时 + 配置切源），不是高频路径。真嫌慢就上 traffic_store 现成的 mtime/size 键控缓存，比开线程便宜。
HR 取数 180s 等待跑在 HrRuntime.start() 拉起的 worker 后台线程，占的是站点锁，不占主循环（坑档记的是「白占 3 分钟锁」）。别当主循环阻塞修。
已经拆好的几处跳检微步线（budget_ms=50 / 20 步）、relocate 执行相位机（每 tick 单步）、check / check-wait 轮询子任务、traffic_sample 时钟钩子、notify daemon——都已在后台或跨 tick。不要重复立项。

§06.3 通用风险清单（任何一项开工都要逐条过）

  • 共享态写点：工作线程不得写任务队列 / state_file / store 分组索引 / 表现层视图。结论只投递意图，由主循环消费。特别注意「看起来只是删个探针」的 torrents_delete → store.remove_torrent。
  • 单飞：同类任务并发多个实例时，要防互相认领 / 重复下发（探针共用 tag 是最典型的坑）。同步执行时主循环串行天然规避，线程化后要显式补。
  • 叫停口：带超时的等待必须能在 stop 时叫停，且「被叫停」与「等超时」分开上报；否则关停白等满超时，还可能占着锁（concurrency.md 第一条，HR 有过 7 条用例各慢 10.5s 的实测教训）。
  • client 会话：主 qB 的 Client 是单例 requests.Session，主循环每 1.5s 一拍在用；SID 过期 / qB 重启时库会丢弃并重建 Session。后台线程若要发 qB 请求，先确认并发重建的竞态（transfer 目标侧因是独立 Client 而免疫）。
  • 关停顺序：stop_all → state.save → 释放 SingleInstanceLock；线程没接进 stop 就可能在锁释放后还活着，下一进程启动的残留扫描会与旧线程互删。
  • 决策链：凡「拿到结果才继续同一条链」的（_ensure_probe → _start_job），线程化仍要改挂起 / 回灌 / 续跑，别指望开线程能省掉状态机。

§06.4 怎么验（看真值，不要只靠静态推断）

  • 运行实例日志筛 [cmd] ... 排队 Xms / 执行 Yms —— 超过 300ms（CMD_SLOW_MS=300），另有 [cmd] 命令后补刷新 ...ms（resync_elapsed_ms）。排队大 = 主循环被长任务占住；执行大 = qB API 慢。
