01这个锚是干什么的

现有三条测试轨各有盲区: 单测全 Fake(不碰真 qB)、e2e/ 打桩服务(不碰真 qB)、语料回放(qb_capture → sim_qb, 只覆盖真机的数据面形态)。剩下四类东西没有任何轨覆盖: 写侧真作用(命令 / 打标 / 限速是否真落到 qB)、qB 真行为(回执、状态机、重启)、真文件系统与进程(移动、硬链接、托盘、开机自启)、观感(配色、跟手性)。存量 checklists/manual-walkthrough.md 里约 15 条"待真机走查"正是第四类 —— 挂了两个月, 因为没有排期机制。

这条锚只回答三件事: 要不要继续做、下一片做哪片、覆盖到哪了。它不记流水(流水在各片基线切片), 也不替缺陷背书(实测发现的缺陷各自入池, 下一轮再修)。

四段职责(每段只在一个工位有权威): ①排期锚=本 issue(要不要做 / 先做哪片 / 覆盖到哪) → ②规程=memory-bank/testing/real-machine.md(硬约束 / 守卫 / 切片规则 / 漂移 / 成熟度) → ③执行=.commands/real/ + tests-real/ → ④记录=testing/real-baselines/ 切片 + 本件 §07。

02为什么不进提交闸门

维度结论
环境依赖需要两个测试 qB 实例开机、种子状态可控、端口未被占。机器没开 / 实例没起就整片红 —— 这是环境, 不是代码
有副作用会真改 qB 状态、真动文件系统、真重启进程。闸门链里不能有"改了就回不去"的步骤
代价一片 ≈ 半天; 与"提交前几秒"不是同一量级, 挂上去等于每次提交都在排队
数字不可比结论依赖真实种子库与环境指纹, 换实例 / 换 profile 就不可比; 不能进基线数字的单点
断言形态断言的是外部可观测事实(qB API / 文件系统 / 进程), 失败常因环境漂移而非代码回归 —— 直接当闸门会大量假红
不走闸门 ≠ 不提交: 用例代码、规程文档、片表更新照常走 ship.commit(可复用性全靠这个); 只有"跑真机"这件事不在闸门链上。反过来, 闸门链里出现 real.* 调用一律视为缺陷。

05一轮的标准动作

排期指令形态固定:

对「<片名>」做真机实测, 先写分步实施计划,
参考 memory-bank/issues/26-10-31-0641-test-real-machine-test-standing.html
与 memory-bank/testing/real-machine.md
  1. 定片: 把片名映射到片号。映射不到 ⇒ 先按规程 §05 改片表(并入 / 开新片)并记 §08, 再开工。
  2. 漂移体检: git log <§07 记的基线 commit>..HEAD -- <本片 glob>, 按规程 §07 三分类; 结论写进计划开头。首轮写"首轮, 无漂移面"。
  3. 环境自检: real.guard(RM00 前手工核三项)。不过就不开跑 —— 不许为了跑通放宽"种子非活跃"。
  4. 写分步计划(plans/ HTML, 拍板后冻结), 必含四块: ① 用例清单(逐条 id + 当前档位 + 期望); ② 本轮哪条从 L(n) 升到 L(n+1)(规程 §08 硬要求); ③ 标 [需活跃种子] 而跳过的条目 + 解锁条件; ④ 验收判据。
  5. 执行: 逐条跑, 每条三态 —— PASS / FAIL(⇒ 按 scope-guard 入池 bug issue) / BLOCKED(环境或约束, 写明解锁条件)。当轮不修缺陷。
  6. 记录: 新建 testing/real-baselines/<stamp>-real-<片>.md(用例数 / 档位分布 / PASS-FAIL-BLOCKED / 基线 commit / 环境指纹), 再更新 §07 该行。
  7. 收尾: 用例照常 ship.commit; 缺陷已入池; 不立 task 档案(本件即档案); 改过片表则 §08 已记。
§07 不更新等于这轮没做: 基线切片是流水, §07 是刻度。只写切片不更新表, 下轮的漂移判定就没有基线 commit 可用。
