01现象与发现场景

2026-11-04 08:45 前后，本轮「Web UI 整组迁移 confirm 回路真机验收」收尾连跑 commands run test.full：三次里第二次全量红一处，红的是 tests/test_qb_capture.py::test_sanitize_all_rewrites_fs_delta_with_same_derivation； 同一工作树前后两次全量均绿，该用例单文件单跑连续 5 次全绿。该文件与本轮改动无关 （本轮零改动 tests/test_qb_capture.py 与 scripts/qb_capture*.py）。

触发条件：用例夹具用非 hex 的假 infohash "H1" 造最小 capture； Sanitizer.infohash 的派生规则是「非 hex 字符原样保留、hex 字符按随机盐重映射」。 H1 只有 2 个字符：H 恒保留，1 被替换为 "0123456789abcdef"[b % 16]；当 b % 16 == 1（约 1/16）时派生结果 恰好仍是 "H1"，用例末行 "H1" not in stream 必红。属低概率不稳定， 与平台/配置无关（并行度只影响被撞见的次数，不改变概率）。

03影响面

维度结论
触发条件跑该用例即可能触发（与并行度无关）；只要随机盐把 H1 的 1 映射回 1（约 1/16）必红，属概率性必现。
影响范围仅此一条测试；不影响产品行为与脱敏正确性（伪名化本身是生效的）。
严重度低 —— 偶发假红会干扰全量门禁判读（需要重跑才能确认绿），但不掩盖真回归。

05根因（可选）

已定位（高置信）：夹具给的 "H1" 不在合法 hash 形态内（长度与字符集都不符）， Sanitizer.infohash 对非 hex 字符原样保留；2 字符长度下约 1/16 的随机盐会把 1 映射回 1 ⇒ infohash("H1") == "H1"，被末行全串扫描断言抓住。
已排除：并行/进程间共享状态（单 worker 与单进程复现条件一致，失败只与随机盐有关）； 与本轮 confirm 回路改动无关（该文件与本轮改动零交集）。

06建议修法（可选）

方向：让夹具的假 infohash 不再可能与自身伪名相等。候选：

  • A（推荐，最小改动）：把 "H1" 换成合法 40 位 hex 假 hash。红概率从约 1/16 降到约 16^-40（实质为 0），用例其余断言不动。
  • B（更贴语义）：末行断言改判「键已换成伪 hash」，如 assert ph != "H1" 或直接比对 c.stream[0]["torrents"].keys()， 不再对整串做裸词扫描；可与 A 并用。
  • C（改产品侧）：Sanitizer.infohash 在 cand == h 时继续派生 （拒绝恒等映射）。代价最大：会改变抓取产物的确定性映射行为，需另立范围评估。 本 issue 倾向不动产品侧。
