01现象与发现场景

WEB UI 对 4 个已完成(progress=1.0)的种子做批量 recheck(走 ctx.ops 的 full-checking),提交后约 1.1 秒日志同时打出 4 条「校验成功」,而 qB 实际才开始校验——对象是 40GB 级 Blu-ray 原盘,全量哈希校验需数分钟,用户确认界面显示成功时实际仍在校验。

触发条件:提交 recheck 时种子已是完成态。qB 的 recheck 为异步应用,store 快照按约 2s 节拍刷新,轮询子任务入队即到期(next_run=now),第一跳落在「recheck 尚未生效 / 快照尚未反映」窗口内即误判。与平台、配置无关,凡已完成种子提交 full-checking 必现。

发现路径:用户贴运行日志质疑「校验成功」检测代码,按日志时间线与 ops 轮询源码对线定位(2026-10-03 会话内完成,未改码)。

03影响面

维度结论
触发条件提交 recheck 时种子已完成(progress=1.0、不在 checking);轮询第一跳(入队即到期)落在 qB 异步应用 recheck / store 快照刷新(约 2s 节拍)之前的窗口内。WEB 批量 recheck 的典型对象就是已完成种子,故高频命中。
影响范围WEB 源:日志误报 + 轮询首跳即消亡(R1 在途登记提前释放,快照跟上前约 2s 内同种子可重复提交)。规则源同路径更重:假成功会执行 on_success 把未经真实校验的种子晋升 verified_references,且 origin 以 keep_progress 续跑后续动作(auto_start 等)。
严重度中——WEB 侧主要是信息误导;规则侧属语义错误(参考种子库被污染,后续跳检会引用未经校验的"参考")。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向:给成功分支加「recheck 确实生效过」前置——要求 seen_checking 为真才判成功,否则落回现有宽限/超时逻辑继续轮询。已排除「纯调换分支顺序」:失败分支依赖 seen_checking 的语义不动。

取舍:小种子校验在两次轮询间隔内完成时永远见不到 checking,严格 seen_checking 会等满 600s 后误判「校验启动超时」。候选:①提交时记录基线(提交时 progress 是否已=1.0)区分两种情形;②歧义分支(未见 checking 但 progress 已=1.0)改发一次实时 API 复核而非干等。修时需同步复查 tests/test_checking.py 现有轮询用例对「首跳即成功」的假设(若有用例依赖该行为,属用例需随语义修正)。
