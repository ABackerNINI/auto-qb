qB 5.3 兼容: setShareLimits 必带 shareLimitsMode, facade 缺参导致 400

qB 5.3 将 torrents/setShareLimits 的 shareLimitsMode 列为必填, core/qbapi.py torrents_set_share_limits 不透传该参 -> WebUI 分享限制命令在 5.3 下整体 400; 修复与库版本解耦, 2026.8.1 上即可合入

01现象与发现场景

qBittorrent 5.2.3 → 5.3.x 升级影响分析（全源码取证, 报告见 memory-bank/reports/26-10-31-0548-report-qb-5-3-upgrade-impact.html §08/§09）发现的唯一硬破坏（🔴）：qB 5.3 的 torrents/setShareLimits 端点把 shareLimitsMode 列为必填（requireParams, 缺失 → 400）；而本项目 facade torrents_set_share_limits 不透传该参数, 库对 None 值键直接不发 → qB 5.3 下该端点请求全部 400。

与平台无关, 与库版本也无关：share_limits_mode 形参在 qbittorrent-api 2026.8.1 就已存在（首发 v2026.7.0 #614）, 两版库行为一致——不传就不发 shareLimitsMode。qB 5.2 无此必填且忽略未知参数, 因此当前生产不炸; 升 5.3 才暴露。

03影响面

维度结论
触发条件qB 升到 5.3.x 后, WebUI 使用「分享限制」命令即必现（5.2.x 下不触发）
影响范围WebUI 种子分享限制命令整体报废（4xx → error 回执, 命令分发层捕获, 不崩程序）; 规则引擎不受影响
严重度高（qB 5.3 下功能完全不可用）—— 但修复与库升级解耦, 可在当前 2026.8.1 钉版上先合入

05根因（可选）

已定位（非待查）：facade 层未把 5.3 新必填参数 shareLimitsMode 透传; 库的 None→不发键语义 + 5.3 requireParams → 400。已排除：库版本过旧（两版库行为一致, 升库不解决本问题）。

06建议修法（可选）

  • facade：torrents_set_share_limits 增加 share_limits_mode: str = "Default" 形参, 透传给库（库签名 Literal["Default","MatchAny","MatchAll"] | None）。
  • 调用点：_cmd_set_share_limits 显式传 "Default"（语义 = qB 全局默认模式 = 旧行为; 5.2 忽略未知参数, 向后兼容无副作用）。
  • 测试：补一条请求体级测试, 断言请求体含 shareLimitsMode 键; 可顺手断言 torrents/add 的 skip_checking/seedMode 双发（防库回归, 两版库都过）。
  • 顺手项：修正 qbapi.py docstring「直传 None 会以字面量 "None" 发送给 qB」的错误描述——实测 requests 对 None 值键一律丢弃, 实际语义是「不发」而不是「发错」; caller 已把 None 归一成 -2/-1, 无实际影响, 纯文档修正（取证时间 2026-10-31, 依据 P5b 实测）。
  • 时序：本修复钉死 2026.8.1 即可合入（与库版本解耦）, 先合本件 → 升库（见 chore/qbittorrentapi-bump-dual-version）→ 再升 qB 5.3, 每步独立可回滚。
