relocate 热启用缺 sweep_probe_residue: 探测残留延迟到下次重启才清

relocate_lifecycle.apply 热启用(假→真)补了 _load_jobs 但未做探测残留清理(start 启用分支非 dry-run 时有), E1 强探测中崩溃留下的探测种子经 disabled 启动→热启用路径要延迟到下次重启才清

§01现象与发现场景

B8 批(汇总件 26-11-07-0527-bug-legacy-review4-core.html 行 5/31:stop 条件持久化/热启用 load)实施后的批评审 nit3,发现于 2026-11-08:B8 给 relocate_lifecycle.apply 热启用(enabled 假→真跳变)补了 _load_jobs(与 start 启用分支同口径),但 start 启用分支在非 dry-run 时还做 sweep_probe_residue 探测残留清理,apply 热启用分支没有同款清理——两分支口径不对称。

后果:E1 强探测中崩溃(auto-qb 被杀)会在用户 qB 留下探测种子+文件(R2 纪律:启动时按 tag 清理);经「disabled 启动→热启用」路径进入的会话,这批探测残留要延迟到下次进程重启(start 再跑到启用分支)才被扫走。

§02证据

代码对照(取证 2026-11-08 16:08,行号为现取;start:34 为任务给定的对照锚):

# src/auto_qb/core/modules/relocate_lifecycle.py — start() 启用分支(:29-36),有 sweep:
29:         if getattr(self._conf, "enabled", False):
30:             alias_fs.get_capability(refresh=True)
31:             n = self._load_jobs()
32:             # E1 探测崩溃残留扫描(计划 26-11-04-0055 P2-⑥): add 之后 delete 之前被杀会在用户
33:             # qB 留探测种子+文件, 启动时按 tag 清理(R2); dry-run 不动手(真写, 与相位机同口径)
34:             swept = 0 if self._dry_run() else sweep_probe_residue(ctx)

# 同文件 apply() 热启用分支(:84-88),只补了 _load_jobs,无 sweep_probe_residue:
84:         if enabled:
85:             alias_fs.get_capability(refresh=True)

B8 修复提交 a3d67d0e(「热启用补 _load_jobs 恢复在途账」)只对齐了 job 账恢复一半,sweep 一半漏对齐。

§03影响面

维度结论
触发条件enabled=false 启动(先前会话 E1 强探测中崩溃留有探测种子)→ 配置热启用 relocate.enabled 假→真且非 dry-run;期间无进程重启
影响范围用户 qB 中残留 aqb-probe 前缀探测种子与文件(列表可见、占空间);热启用会话内无人清理,延迟到下次重启才被 start 启用分支扫走
严重度低-中——残留有界且最终会清;但热启用与 start 启用分支守卫口径不对称,属 B8 修复的对齐缺口

§05根因（可选）

非待查——根因即「热启用分支与 start 启用分支口径不对称」:B8 对齐 _load_jobs 时未同步对齐 sweep_probe_residue 一半,属修复的对齐缺口而非新缺陷。

§06建议修法（可选）

热启用且非 dry-run 时补 sweep_probe_residue(与 start 同判:非 dry-run 才动手;dry-run 保持零真写)。apply 无 ctx 时的取参方式按 _load_jobs/能力重探同款现读路径处理,认领时再定。
