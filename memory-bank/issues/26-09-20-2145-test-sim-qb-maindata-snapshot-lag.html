01现象与发现场景

在查「乐观 UI 撤下慢」时要用 sim_qb 复现「真值尚未落地」这一类缺陷，结果复现不出来：sim_qb 收到 torrents/pause / torrents/resume 后同步就把 state 改掉了（_set_state，无延迟），于是 /sync/maindata 与 torrents/info 同一时刻返回新状态。

而真机上两者不同步：真机日志显示命令执行只要 8.4 ms，但要等 6 轮（约 1362 ms）才在同步里看到新状态。因此凡是需要「真值滞后」才能暴露的缺陷，仿真端一律测不出来 —— 包括本次计划要验证的「真值改走 torrents/info 直查是否更快」。

触发条件：任何用 scripts/sim_qb.py 做端到端验证、且被测项依赖状态传播时延的场景。与平台无关。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

给 sim_qb 加一个可开关的快照滞后模型：/sync/maindata 按固定节奏（默认 1500ms，--maindata-lag-ms 可调）刷快照，而 torrents/info 实时返回。这样：

  • 方案 A（推荐）：给 SimQb 加一层"同步可见性"—— 写操作立即改 self.torrents，但 sync_maindata 只读一个按节奏刷新的快照副本。
  • 方案 B（更省事）：加 --state-delay-ms，把 _set_state 改成延后生效（临时脚本已验证可用）。缺点：它同时延迟了 torrents/info，因此区分不出"直查更快"这个关键假设 —— 只能复现滞后，不能验证方案。

只有方案 A 能验证本次计划的核心假设（直查 vs 快照谁先拿到真值）。代价：需改 sync_maindata 的数据源，约 1~2 小时，并需保证既有 sim_run 场景不受影响（默认 lag=0 时行为与现在完全一致）。
