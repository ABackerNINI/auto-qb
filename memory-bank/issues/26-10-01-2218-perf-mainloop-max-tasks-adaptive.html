01现象与发现场景

2026-09-19 做 sim-client 压测取数时发现: --ramp 渐进灌入场景(P2, 200/拍)下主循环掉拍 —— 稳态间隔 2.87 s, 超过 main_tick 2.0 s, 最大漂移 1.22 s; 灌入期每拍都在还债。

原文出处: TODO.md「## 性能发现」PERF-02(TODO L264-L272)。

2026-10-08 复测（同一 P2 场景，develop @ 0a46b58d）：掉拍大幅收敛 —— 稳态平均间隔 2.139 s（原 2.87 s）、最大漂移 0.801 s（原 1.22 s），已落进项目固化给纯主循环的稳态门限 SYNC.drift_max_s ≤ 1.0 之内；verdict OK，无 traceback / critical。详见 §02 与 §07。

同时认定原方案无效：本条原建议「给 max_tasks_per_tick 做自适应」指向的旋钮不承载这部分成本 —— 项目实测已认定灌入期每新种子的 2 次内联请求（torrents/trackers + torrents/files）跑在同步线 _refresh_torrents 里，不受 max_tasks_per_tick 约束（memory-bank/testing/sim-5000.md「关键实测数字」）。故本条口径已从「自适应任务线配额」改道为「灌入期每拍请求预算」（见 §06）。

数据取证 2026-09-19(压测观测, 未动代码); 2026-10-01 自 TODO.md 性能发现节入池; 2026-10-08 复测并重归因(未动代码)。

05根因（可选）

已排除（2026-10-08 取证）：掉拍主体不在任务队列，因此原方案「max_tasks_per_tick 自适应」不会改善它 —— memory-bank/testing/sim-5000.md「关键实测数字」原文：「首轮灌入: 5000 种子 14.4 s(回环)≈ 15 754 次请求 ≈ 0.96 ms/次 —— 每新种子约 2 次内联请求(torrents/trackers + torrents/files), 在 _refresh_torrents 里逐个内联跑, 不受 max_tasks_per_tick 约束」。任务线配额只管 run_due 的到期任务条数（速率语义 20/2s = 10 任务/s），管不到同步线上这 2N 次内联请求。

也排除了「靠同期重构被顺手修好」这一说法的确定性：分层节拍(10e06a84) / 节拍对齐(95fb6734) / 解耦(5691c6f4) 均在 2026-09-19 当天或更早，与原取证同日，无法据此断言是它们带来了这次收敛；同期还可能相关的有视图局部重聚合(S6/S9)与发布门控(客户端活跃窗口 / pending_ver)。

仍待查：复测后残留的 0.801 s 漂移具体由哪一段构成（同步线增量同步 / 逐种子内联请求 / 分组归组 / 事件分派）—— 认领后先做这段拆分，别凭猜选旋钮。

06建议修法（可选）

给 max_tasks_per_tick 做自适应（2026-10-08 改道：经查该旋钮不承载这部分成本，见 §05 已排除项。原方案列为 sim-client-5000 计划 W5 归因候选，该计划已 Done，自适应项未实施且建议不再实施）。

改道后的方向：灌入期每拍请求预算 / 限批 —— 在同步线 _refresh_torrents 的 torrents_added 相位给「本拍最多处理多少个新种子的内联取数（trackers + files）」设上限，超额留到下一拍，把每拍的 2N 次内联请求摊平。代价：新增配置键（须同步 config.validate_config 与 config/schema.py，黄金法则 4）+ 灌入期完成时间变长。

值不值得做（2026-10-08 复测后的判断，供拍板）：倾向不做 —— ①症状已收敛到稳态门限内（漂移 0.801 s < 1.0 s，稳态间隔只超 0.14 s），投入产出比低；②它换来的是"灌入完成更快"，而灌入期本来就是一次性代价（首轮 P1.first_round_s 2.174 s 远低于 22.68 s 门限）；③每加一个速率类旋钮就多一处语义耦合（见 qbmanager.py:402 关于 max_tasks_per_tick 速率语义的注释）。若拍板不做，本条走 Dropped（理由：复测已进稳态门限 + 原方案无效 + 症状为一次性代价）。若拍板做，先把 §05「仍待查」的漂移构成拆分做完再动码。

注意: max_tasks_per_tick 是内核认领段(任务线现读), 改其语义需同步 P6 段认领守阵 —— 观测基线已按灌入期口径记录(P2.drift_max_s BASELINE), 认领后先出方案再动码。
