01现象与发现场景

用户报告（2026-11-03）：网络断开后自动恢复，WebUI 顶栏「今日流量」pill 的当日累计出现量级跳变——断网前 上传 60 多 G / 下载不到 10 G，恢复后涨到 上传 300G 量级 / 下载 500G 量级。用户判定这不是真实流量（成倍到几十倍），要求只做分析与入池。

数据链路（唯一来源）：pill 只读 GTM（global-traffic-monitor）产出的 history_traffic.dat——前端 period === "day"（static/shared/dialogs.js:460、static/shared/tpl/statusbar.html:6 的 D2 注释即此约定）；auto-qb 侧 traffic_snapshot.refresh() 调 read_source_rows() → curves.aggregate(rows,"day") 发布 periods 的 day 行。GTM 的日累计由 Sampler.sample_once() 维护、Storage.record() upsert 进 dat。整条链不经过 qBittorrent 计数器。

现场与配置：Windows；GTM 数据目录由发现指针指向 D:\Projects\auto-qb\tools\global-traffic-monitor\data（另一 clone，只读取证，未改动）。该目录无 config.yml，即全走默认值：sample_interval=5s；配置层只承载 adapter_include/adapter_exclude 两个正则列表（config.py:77-78），exclude_loopback=True / exclude_down=True 是 AdapterFilter 内部默认（sampler.py:109，down 过滤无配置开关）。

可观测性缺口：GTM 只 logging.basicConfig(stream=sys.stderr)（__main__.py:211-215），而 launch.cmd:12-13 用 pythonw.exe 拉起（该文件第 10 行注释自述「pythonw 没有 stderr, 输出全部丢弃」）→ 没有落盘日志。本轮只能靠 dat 与 state.json 取证。

2.3 算术对齐（关键：差值恰好等于用户断网前读数，且两次采样差值恒定）

量state.json 值（字节，10:47）折 GiB与 day 累计的差
day_up（当日累计）361,214,484,252336.41+62.96 GiB ≈ 用户「上传 60 多 G」
last_up（最近一次合计读数）293,613,556,677273.45
day_down（当日累计）578,225,157,679538.52+9.997 GiB ≈ 用户「下载不到 10 G」
last_down（最近一次合计读数）567,490,630,570528.51

正常单调计数器若全日在同一基线上累计，应满足 day = last - base(当日首样)（day < last）。这里 day 反而比 last 大，且差额精确落在用户报告的断网前读数上 → 当日累计里混进了一笔「不属于当前基线区间」的字节，其大小恰等于恢复瞬间的合计读数（≈273.4 GiB 上传 / ≈528.5 GiB 下载）。

二次取证对照（相隔约 10 分钟）：day_up 与 last_up 同增 69,166,852 B；day_down 与 last_down 同增 37,398,242 B——差值不变。这正是「一次性错位注入 + 之后正常同步累计」的签名，排除「持续重复累加」（H4）。2026-11-02 行 62 GiB/299 GiB 也提示历史上可能已发生过同类冲高，待认领时核对。

03影响面

维度结论
触发条件默认配置下任意一次「选中网卡集合缩小后又恢复」即必现：拔网线 / 路由器断电 / 网卡禁用再启用 / Wi-Fi 掉线重连 / 睡眠唤醒。媒体级断链（拔线/链路丢失）期间网卡对象与累计计数通常保留（仅 OperStatus 变 down）；本次实测的 273 GiB 级跳变正是「计数未清零」的直接证明——若计数被清零，只会走 reset 分支、delta=0，不会虚高。冲高幅度 = 该卡生命周期累计 ÷ 当日真实流量（本例上传 ≈4.3×、下载 ≈53×，正好是用户说的「成倍到几十倍」）。每发生一次断连-恢复，当日累计再加一份同量级累计值。
影响范围 ① WebUI 顶栏「今日流量」pill（day 行）当日整体虚高，且 pill 走 traffic_snapshot.publish_source 的每日高水位钳制（traffic_snapshot_mod.py:285-290）——即便源端后来纠正，Auto-QB 侧当天也不会回退；
② GTM dat 的今日行被 upsert 成虚高值（storage.record），当日无法自愈，历史图（_history_rows）与本月/Nd 聚合（curves.aggregate，curves.py:76）长期偏大；
③ 限速曲线 speed_curve_mod.py:186 用 day/month/Nd 聚合判档 → 误触发更严格档位，直接改 qB 限速；
④ GTM 阈值通知 notifier.py:107 以 day_total_bytes 跨阈值为准 → 推送假「今日流量超阈值」事件；
⑤ 用户据此判断流量、分享率、超量/限速策略（本报告原始诉求）。
严重度高：数据正确性缺陷；默认配置必现；无可见告警（WARNING 只进 stderr，pythonw 下丢失）；当日不可自愈；会反向驱动限速与通知等自动化动作。
与「qB 重启后计数器归零」类问题（报告 26-10-15-0728）不是同一条链：那条链有一批「回落判重置 → 关块重开」的防线；本条链的防线只覆盖「合计值变小」，没覆盖「合计值变小是因为网卡被过滤掉」。

05根因（可选）

结论：命中 H2 的机制面（恢复后首包吞下缺口期的「绝对值」），但真正致命的是「合计口径的基线被过滤集收缩污染」——不是 qB 计数器、不是 state 时序、不是并发重复累加。

5.1 精确失效链（5 步，均可在 sampler.py 定位）

  1. 断网 → 该网卡 OperStatus != up → AdapterFilter 以默认 exclude_down=True 剔除它（sampler.py:338），selected 从「主卡(+虚拟卡)」缩成子集，常见情况直接变空。
  2. total_up/total_down 是过滤后多卡的合计（:339-340），因此合计值骤降；:359-360 只在「全空」时记一条 stderr WARNING。
  3. :369-378 把「合计变小」一律判成 counter_reset：delta 记 0（看起来安全）。
  4. :380-381 无条件把 _last_up/_last_down 覆盖成收缩后的子集合计（通常是 0）。代码没有区分「计数器真归零」与「这张卡只是暂时看不见」。
  5. 网卡恢复 up：Windows 在媒体断链期间保留该卡 InOctets/OutOctets；于是 total = 生命周期累计 ≫ 基线 0 → delta = 整份累计（:373）→ :382-383 一次性加进当日累计。

5.2 逐条假设裁决

假设裁决依据
H1 重连后用累计值减失效/归零的基线，把历史累计计成当日增量（qB session 归零、本地基线未同步） 证伪（结论对、主体错） 「今日流量」pill 的唯一来源是 GTM 的 dat（statusbar.html:6 的 D2 约定 + dialogs.js:460 + traffic_snapshot_mod.refresh），GTM 全程不读 qB。qB 的 alltime/session 计数器只喂 traffic_sample_mod 的图表链路，那条链对 cur < last 有「增量记 null + 关块重开」防线（traffic_sample_mod.py:24-28、489-498、646-647），不会产生一次性冲高。断网也不会让 qB 重启。真正基线失效的是 GTM 的过滤后合计基线。
H2 断连期数据缺失，恢复后把缺口整体补算到恢复那一轮 部分命中（机制命中、数值口径需修正） 代码里没有任何「补算缺口」分支，缺口期的该卡计数其实不增长（链路断了没流量）；被记入的不是缺口流量，而是整卡生命周期累计（含断网之前的历史）。sampler.py:29-31 与测试 test_sampler.py:244-254 正是把这个错误口径写成了「缺失窗流量打进首包」的预期。
H3 state 落盘/加载时序，重连时基线被重置或读回旧值 证伪 state.json 每轮由 storage.record 落盘，last_* 是采样后值；重启走 Sampler.restore/storage.recover（缺失时首样只立基线、delta 0）。数字上也自洽：last_up=273.4GiB 正是冲高后的新基线，而不是旧值或随机值。问题是写入的新基线本身是错误口径（0），不是持久化链路错。
H4 多次轮询并发/幂等失效导致重复累加 证伪 采样在单线程主循环内（__main__.py:181），进程有 SingleInstanceLock（storage.py:393-413）防双实例；HTTP 线程只读快照。day_up += delta 每轮只加一次，且 delta 语义就是「本轮增量」，不存在重复累加；本次只跳了一次（若重复会成倍叠加，见 §5.3）。

5.3 数值推演（与 §2.3 完全吻合）

设 B = 当日基线, C(t) = 网卡生命周期计数器, R(t) = 当日真实流量
正常:  day = C - B           且 day < C   (day - last = -B < 0)
本例:  day_up   - last_up   = +67,600,927,575 B  = +62.96 GiB
       day_down - last_down = +10,734,527,109 B  = + 9.997 GiB
若冲高只发生一次且把基线置 0 (B'=0):
       day = R_断网前 + C_恢复瞬间 ;  last = C_当前 = C_恢复瞬间 + R_恢复后
       day - last = R_断网前 (恒定偏移, 不随继续采样变化)
用户读数: 断网前 上传 60 多 GiB / 下载不到 10 GiB  → 与 62.96 / 9.997 GiB 吻合
冲高注入量: day - (last - R_今日) ≈ 273.4 GiB(上传) / 528.5 GiB(下载) = 恢复瞬间合计读数
放大倍数:   336.3/63 ≈ 5.3x(上传) ,  538.5/10 ≈ 54x(下载) → 用户所述「成倍到几十倍」
若发生 k 次断连-恢复: day ≈ R_今日 + k·C  （本例 k=1）

注：C 是「过滤后所有在选网卡的合计」，不等于单卡；但冲高量与它在恢复瞬间的读数同量级，故用同一符号表述。

06建议修法（可选）

只给方案，不在本报告实施。三条候选按推荐度排序。

A（推荐）逐网卡基线：把差分下沉到每一张卡，再求和

Sampler 内部改为保存 {nic_name: (last_up, last_down)}；每轮 delta = Σ max(0, cur_i - last_i)（仅对「本轮可见且上轮有记忆」的卡），随后用本轮可见卡刷新记忆。卡新出现（无记忆）只立基线、delta 0；卡消失则保留其记忆（可加 TTL），下次回来继续按真实增量算（媒体断链期间该卡计数不涨，回来时增量≈0，天然正确）。state.json 载荷升 version（存每卡基线），旧载荷降级为首样基线（delta 0，宁可少报不虚高）。

对黄金法则：幂等性——同一读数重放只产生 0 增量；状态持久化——每卡基线进 state，跨重启/跨断连连续；单一写线程——采样路径不变。爆炸半径：gtm/sampler.py + gtm/storage.py（载荷兼容）+ 测试；dat 契约与 auto-qb 侧零改动。风险：网卡被系统改名/Alias 变化时按「新卡」处理（可接受，最多少报一窗）。

B（轻量）识别「过滤集变化」，而不是只看合计涨落

记住上轮 selected 名字集合；对本轮∩上轮的卡按合计做差，对新增卡只立基线，对消失卡的合计贡献直接丢弃（不产生 delta）。本质是 A 的简化版（基线仍可只存合计 + 上轮名单），但不解决「改名/重启后每卡基线丢失」，跨重启仍退化为「首样只立基线」（安全但不精确）。爆炸半径更小：只改 sampler，state 载荷可不升版；代价：断连窗口内若有其它卡承接了真实流量，会漏计。

C（兜底保险，不单独用）单轮 delta 合理性上限

当单轮 delta 超过阈值（如 max(1 GiB, 5×近 N 轮 p95 增量)）判为异常，本轮 delta 记 0 + WARNING。缺点：魔数、会误伤真实突发（大文件/高速下载）；且已经入账的虚高不会自动回退，需要额外「当日行修正」能力（按 day - 注入量回写 dat），而 dat 是 upsert 单调累计、没有撤回语义 → 工程代价高。建议只作为 A 之上的告警保险，不作为主修法。

测试策略要点

  • 单测（新增）：单卡 down→up 且计数不涨 → delta 0（改写现有 test_down_adapter_recovering_counts_from_zero 的 1999 期望）；单卡 down→up 且计数涨 X → delta X；新卡插入/旧卡消失；全部过滤；真·计数器归零（芯片重置）；多卡混合；跨天；state 旧版载荷降级。
  • 改写：test_all_adapters_filtered_warns_and_counts_zero 的 (100,100) 期望按新口径调整。
  • 真机验证：在默认配置下禁用/拔掉主网卡 ≥1 个采样周期再恢复，断言当日增量≈恢复窗口真实增量（≈0），并核对 state 每卡基线；再跑一次真·网卡禁用-启用（计数器会清零）确认走「重置→delta 0」分支而不重复计。
  • 文档：同步改 sampler.py:29-31 的抖动说明（从「无法区分」改为「按卡差分可区分」），并把口径写回 memory-bank/。
  • 存量数据：今日与历史的虚高 dat 行需要一次性修正（可选，按 day - 注入量 人工/脚本回写；本次不实施）。
