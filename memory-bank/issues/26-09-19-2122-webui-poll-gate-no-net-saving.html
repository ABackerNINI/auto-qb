01现象与发现场景

2026-09-19 对提交 95fb673「节拍对齐: 上一版没被取走就不重建(实测省 50%)」做 code review 时撞见。 该提交把"上一版没被 /api/state 取走"做成主循环的重建门控，实测主循环重建次数确实 40 → 20； 但复核 ensure_group_state 时发现它是第二个生产者且不受门控约束——只要脏就在请求里就地重建 （web_view.py:602）。于是被门控省下的那一版，会在客户端下一次取数时原封不动地在请求路径上补回来。

触发条件：Web UI 打开 + 库处于活跃状态（每拍都有速度/进度变化 ⇒ 每拍置脏）+ 客户端节拍慢于服务端节拍（>3000 种子时为 3s 档）。 ≤1000 种子（客户端同为 1.5s）实测不受影响，与提交说法一致。

02证据

① 代码事实（两处生产者，只有一处被门控）

# src/auto_qb/qbmanager.py:526-535  —— 主循环（受门控）
web_active = (time.time() - self._web_last_seen) < WEB_VIEW_TTL
unconsumed = self._web_pending_ver is not None
if self._group_view_dirty and web_active and (force or not unconsumed):
    self.rebuild_views()

# src/auto_qb/mixins/web_view.py:601-609  —— 请求路径（**不受门控**）
with self._view_lock:
    if self._group_view_dirty:
        self._publish_views_locked()      # <= 脏就就地重建，与门控无关
    ver = self._group_view_ver
    self._web_pending_ver = None          # 本请求观察到了 ver ⇒ 清欠账

② 实测：总重建次数（3000 种子，60s 窗口，活跃库，单客户端）

计数点是 _publish_views_locked（主循环与请求路径都走它），所以这是"总账"， 不是提交里只数主循环的那个口径。

客户端节拍无门控 主循环/请求/合计有门控 主循环/请求/合计净省
1.5s（≤1000 种子档）40 / 1 / 4140 / 1 / 410%（不受影响 ✓）
3.0s（>3000 种子档，真实档位）40 / 1 / 4120 / 20 / 40≈0%
6.0s40 / 1 / 4110 / 10 / 2051%

即：提交声称的"40 → 20 省 50%"是主循环一列的数字；真实档位（3s）下总账 41 → 40， 一半只是换了执行线程。两种拍序（客户端先取 / 服务端先拍）结论一致。表中恒定多出的那 1 次是首次轮询 （__init__ 里 _group_view_dirty = True）。

③ 实测：搬到请求路径后每次请求贵了多少（3000 种子 / 400 组）

① rebuild_views()                    p50 =  50.8 ms   （group 16.7 / shows 9.8 / flat 22.0）
② ensure_group_state(不脏, rid 命中)  p50 =   0.0 ms   ← 门控前 /api/state 的典型形态
③ ensure_group_state(脏, 就地重建)    p50 =  48.8 ms   ← 门控后的典型形态
④ json.dumps(全量回包体 6.3 MiB)      p50 =  26.4 ms   （与 49d81cf 实测的 25~50 ms 同量级）

⇒ 门控给每次 /api/state 增加约 +48.7 ms；该值与序列化同量级，但远小于 49d81cf 去掉的 161 ms
  （所以是"可接受的取舍"，不是回归）

④ 复现方式（脚本未入库，正文保留可复现版本）

# 用真实 QbManager + helpers.FakeTorrent 造 3000 种子 / 400 组；包一层计数 _publish_views_locked
# 循环 40 拍（60s）：每拍 store.view_changed = True 模拟活跃库，每 N 拍调一次 ensure_group_state
def run(mgr, gate):
    for k in range(40):
        mgr.store.view_changed = True
        if k % POLL_EVERY == 0:
            st = mgr.ensure_group_state(rid); rid = st["rid"]     # 客户端取数
        if not gate:
            mgr._web_pending_ver = None                            # 模拟"没有门控"
        mgr._flush_views()                                          # 服务端一拍
# 关键前提: mgr.touch_web_client() 必须先调，否则 web_active 为假、主循环根本不重建（第一次跑就踩了）

03影响面与严重度

维度结论
触发频率常驻：只要开着 Web UI 且库在活跃做种/下载（每拍都置脏）
影响范围仅 >3000 种子的 3s 客户端档；≤1000 种子（1.5s 档）实测不受影响；单/多客户端都成立（多客户端时门控甚至不生效，因为欠账被更快的那个客户端清掉）
数据风险无。新鲜度不受损（请求侧就地重建拿到的还是最新一版，甚至更鲜）；脏标记也确实保留（用例已钉住）。纯粹是 CPU 归属与请求延迟问题。
严重度低（无正确性/数据风险）
但提交结论"省 50%"与实际不符 —— 会误导后续优化决策（以为这条已经榨干），故入池留痕。

04根因（初步）

结论（已实测，非推测）：视图版本有两个生产者 —— 主循环 _flush_views（受门控）与请求路径 ensure_group_state（不受门控，脏就建）。门控只掐掉了前者，后者立刻把产量补回来。 总产量由"消费者取数频率 + 主循环在两次取数之间能插进几拍"决定：

  • 无门控：每拍一版 ⇒ 3s 档每轮 2 版（1 版被消费、1 版白烧）；
  • 有门控：请求侧 1 版（被消费）+ 主循环在"欠账刚被清掉"的那一拍补 1 版（白烧）⇒ 同样 2 版。

只有当两拍之间能插进 ≥2 个空闲拍（客户端节拍 ≥ 服务端节拍的 4 倍，即 6s 档）时，主循环那 1 版才真的省得下来 —— 这正是表里 6s 档出现 51% 的原因。提交把"主循环 40 → 20"当成了总账，而它恰好等于 6s 档的数字。

已排除：① 门控逻辑本身没错 —— 脏标记保留、force 绕过、并发置位/清零都在锁内，用例也钉住了； ② 不是并发或锁的问题（单线程仿真同样复现）；③ 不是测量脚本没调 touch_web_client() 导致的假象（已修，见证据④）。

05建议修法

先说清楚：现门控不是 bug，不改也不会出问题。下面按"想要真省 CPU"排序。

方案 A（推荐，真能省）：主循环在 Web 是唯一消费者时不再重建 —— 全惰性

主循环只负责把 view_changed 落成 _group_view_dirty，重建全部交给请求路径。 实测（同口径）：3s 档 41 → 20（-51%）、6s 档 41 → 10（-76%）、1.5s 档 40（持平，不吃亏）。 原理：每一次取数恰好对应一版，白烧版归零。

代价：/api/state 每次都要付一次重建（3000 种子约 +50 ms），延迟从"双峰（0 / +50 ms）" 变成"稳定 +50 ms"；好处是主循环彻底不再被重建阻塞（对 P0-5 命令响应是正面），且客户端关掉标签、 只剩 TTL 内空转时不再白烧。
注意：方案 A 下 force 通路要重新定义（命令改状态后仍应立刻可查 —— 请求侧按需重建已天然满足， 但 ensure_group_view 等其它调用方要一起看）。

方案 B（零风险）：保留现门控，只把结论与文档改对

把"省 50%"改写为"主循环重建减半；总重建次数不变，一半换到请求路径执行；每轮 3s 档每次 /api/state 多付约 50 ms（3000 种子实测）"。同时在 _flush_views docstring 里写明 "新鲜度由 ensure_group_state 的脏就建兜底"这条因果（现在没写，后人容易误判成延迟被推后一拍）。

方案 C（折中）：给请求侧重建加最短间隔

例如 1s 内已重建过就直接交当前版本并保持脏（由主循环下一拍补），把请求延迟压回去； 代价是新鲜度最多差一个间隔，且要新增一个"上次重建时间"状态（记得同时进 validate_config？ 不需要 —— 它不是配置项，但要在 __init__ 里与其它视图状态并列初始化）。

顺带（独立小修，与本条同源）

ensure_group_view()（web.py:269 的 /api/groups）发布了一版却不清 _web_pending_ver，与 ensure_group_state 的"消费即清"语义不一致。当前 UI 只走 /api/state 所以不卡（靠请求侧兜底），但只打 /api/groups 的外部脚本会让欠账永远清不掉。 一行修复：在它的持锁区内同样置 None。
