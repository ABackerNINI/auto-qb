01现象与发现场景

撞见于「把『开工前先拉取远程分支』写进 AGENTS.md（用户 2026-09-19 指定），并把同一条规则同步到各 always-on 入口」这一轮工作。为确认规则不漏副本，回读 memory-bank/conventions.md 的「Git 约定」一节时，发现它仍然写着 禁止 push，而同一次会话里 AGENTS.md 要求的是 「用户说提交 = commit + 自动推送」 —— 两处口径相反，且都带有 🔴 级强调。

触发条件很普通：任何一次「用户说『提交』」的收尾都会同时命中两份文档 —— 照 AGENTS.md 做就要 push，照 conventions.md 做就必须在 commit 后停下等第二次明确指令。

本轮实际是按 AGENTS.md 的新规执行的（已 commit 并推送 Gitee + GitHub 共 4 笔：72a45f9 / 738fe0d / 67b3828 / dc9a854），即已发生的动作本身没有回滚风险，漂的是文档。

02证据

现行口径（AGENTS.md:126，2026-09-19 用户指定）原文：

AGENTS.md:126
- **用户说"提交"= commit + 自动推送** (2026-09-19 用户指定), 一次流程走完:
  1. `git push origin develop` —— 推 Gitee (稳定, 这是协作主线, 必须成功)。…

与之矛盾的旧口径（memory-bank/conventions.md），共四处：

conventions.md:8   (## 协作约定 节)
- **🔴🔴 绝对不要 push!!** (2026-09-10)： 除非用户显式要求"提交/提交并推送/发布"且明确提到 push
  或推送到远程, AI **一律不执行 `git push`**（包括任何远程 gitee/github）。…**用户说"提交"默认只指
  commit。** 违反实例: 2026-09-10 用户说"提交", AI 擅自连带 push 到 gitee(成功)与 github(网络失败),
  属于越界动作。

conventions.md:13
  - 其余纪律不变: 不主动 commit/push (见上条), "提交"仅指 commit。

conventions.md:14
- **修改完不要直接提交**： AI 完成代码/文档改动后留在工作区，由用户逐项审核，确认后再由用户或
  显式要求时再提交。AI 不主动 `git commit` / `git push`。

conventions.md:136 (## Git 约定 节)
- **🔴 绝对不要 push (2026-09-10)**： 除非用户显式单独说"push/推送/推送到远程", 否则 `git commit`
  后保持本地, **不执行任何 `git push`** (gitee/github 均不推)。commit 与 push 分离, "提交"二字不
  暗含 push。

conventions.md:140
- 用户未要求时不主动 commit/push。

最小复现：让一个会话只读 memory-bank/conventions.md（AGENTS.md 路由表与 memory-bank skill 都要求「动代码前必读」）再执行用户的一句「提交」，它会停在 commit 不推；让另一个会话只读 AGENTS.md 执行同一句话，它会连推两个远端。同一句指令两种结局。

补充事实：本轮已在 conventions.md:135 插入了「开工前先同步分支」的指针（不复述全文、明确回指 AGENTS.md 并注明该规则共 4 处入口）。正是这次插入让上面 :136 那行紧挨着新规则出现，矛盾变得显眼。

03影响面与严重度

维度结论
触发频率高 —— 每次「提交」收尾都会读到；本仓库 9 个 worktree 并行，任一会话读到旧口径就会漏推
影响范围所有 AI 会话（与平台/站点/配置无关）。表现为两种：①漏推 —— 交付口径是「看 Gitee 有没有该提交」，漏推即等于没交付；②误判进度 —— 用户以为已推，实际本地躺着，下一次会话又在落后分支上开工（与本次新加的「先拉分支」规则直接对冲）
数据风险无 —— 不涉及代码/种子/限速；纯文档口径问题（唯一实质风险是"漏推后别人在落后分支上继续改"，属流程风险不是数据破坏）
严重度中 —— 不会跑坏程序，但会稳定地让"交付"这件高频动作出错，且错误方向（少做）不易被察觉

04根因（初步）

结论：规则在两处各自演化，知识库没跟上入口文件的更新。时间线可直接对上 —— conventions.md 那几条是 2026-09-10 因「AI 擅自 push」事故写下的（文件里连违反实例都记着），而 AGENTS.md 的「提交 = commit + 推送」是 2026-09-19 用户重新指定的（同一天还要求「提交后核对 ref」等一整套流程）。用户在 09-19 改了口径，但只改了 AGENTS.md，conventions.md 这四处自 09-10 起没有再动过。

为什么没被自动纠正：AGENTS.md 的「冲突裁决」是 代码 > memory-bank > README > 想法.md，这条只对「代码事实漂移」有效；本次两边都是文档，裁决链给不出方向，谁先被读到谁生效。

已排除：①不是"两份文档指向不同远端"的问题（两边说的都是 gitee/github 全禁 vs 全推）；②不是本轮 72a45f9~dc9a854 引入的（这几笔只加了「先拉分支」，未碰 push 口径）；③不是读取顺序可自行消解的（两处都带 🔴，同级强调）。

05建议修法

方向：让「提交/push 的现行口径」单点定义在 AGENTS.md「提交 / PR」一节，知识库只留指针 + 历史沿革，不再复述规则本身（与本次「开工先拉分支」采用的做法一致 —— 那次就是只留指针）。

方案 A（推荐）：改写三处旧口径 + 保留事故上下文

把 conventions.md:8 / :136 的「绝对不要 push」改为「以 AGENTS.md『提交 / PR』为准：(2026-09-19 起) 用户说『提交』= commit + 推送 Gitee（+ 尝试一次 GitHub）；2026-09-10 之前是禁 push 口径」，并把 09-10 的越界实例保留成「历史沿革（当时口径）」小字 —— 事故教训不丢，现行口径不再有两个答案。:13 / :140 的「不主动 commit/push」同步改为「未被要求时不主动 commit；被要求提交时按 AGENTS.md 一次走完（含推送）」。:14「修改完不要直接提交」同理改为「留工作区待审，用户说提交后再按 AGENTS.md 流程走」。
代价：动 5 行，需与并发会话确认 conventions.md 无冲突；收益：唯一答案。

方案 B：只加一条覆盖声明，保留旧原文

在「协作约定」与「Git 约定」两节各加一行：「本节 push 相关条目已被 2026-09-19 用户新规取代，现行口径见 AGENTS.md『提交 / PR』」，旧条目原文一字不动。
代价：读者要读完旧条目再读到覆盖声明才知道作废，中间仍有误读窗口；收益：改动最小（+2 行）、历史记录零损失、冲突面最小。

推荐 A（本次「开工先拉分支」已经确立了「入口文件定规则、知识库只留指针」的做法，A 与之同构，不留第三次漂移的土壤；若担心并发冲突，可先做 B 过渡，后续再转 A）。
验收方式：改完后全文搜索 绝对不要 push / 不主动 commit/push，应只剩历史沿革里的引用；任选一个只读 conventions.md 的会话做一次「提交」演练，确认它推到 Gitee 而不是停在 commit。
