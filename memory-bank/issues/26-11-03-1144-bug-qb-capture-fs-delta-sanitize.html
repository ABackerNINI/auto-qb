01现象与发现场景

S4 code review 逐文件过目 scripts/qb_capture.py 时发现：开启 --probe-fs 后写进流帧的 fs_delta 没有进入 sanitize_all() 的脱敏清单；落盘的 sync-stream.jsonl.gz 里同时保留真实 infohash（delta 外层键）与真实相对文件名（内层键），而 torrents/files/disk_map 已全部换成伪名。

03影响面

维度结论
触发条件仅 --probe-fs 开启且探测到差异（文件被删/改名/出现 .!qB）时产生 fs_delta
影响范围① 脱敏红线：真实资源名与 infohash 漏入语料（与 disk_map 已修过的同类泄漏）；② 功能：回放端 _apply_fs_delta 用伪 hash 查表，真 hash 永远查不到，增量被静默丢弃 ⇒ fs mock 看不到删除/改名
严重度高（P1：脱敏红线 + 回放语义静默失真，自带 self-test 假绿）

04定位锚点

  • scripts/qb_capture.py:376-427（取证 2026-11-03 11:44）· sanitize_all · grep sanitize_all / fs_delta
  • scripts/qb_capture.py:883-904（取证 2026-11-03 11:44）· probe_fs_delta · grep setdefault("fs_delta"
  • scripts/qb_capture.py:724-744 · sanitize_stream_consistent 段 · grep stream_hashes

05根因（可选）

已定位：fs_delta 在 sanitize_all 之前写入流帧（probe_fs_delta 在录制循环里调用），而 sanitize_all 只按白名单重键身份字段，白名单漏了 fs_delta。self-test 的流级一致性判据同样只覆盖 torrents 键，未覆盖 fs_delta，因此泄漏与失配都不会被自检拦下。

06建议修法（可选）

在 sanitize_all 中把每帧 fs_delta 外层 hash 走 san.infohash、内层 rel 走 san.name(path_normalize(...))，与 files/disk_map 用同一套派生；同时在 self-test 增加 fs_delta 的「伪 hash 必须在 files_map / rel 必须在 files name 集合内」判据，避免同类漏项再次假绿。
