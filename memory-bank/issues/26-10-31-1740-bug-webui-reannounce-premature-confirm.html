01现象与发现场景

RM09 真机实测(plan plans/26-10-31-1710-plan-real-rm09.html 用例 RM09-04)发现。场景: 活跃假种子(stalledUP)的 announce 指本机死端口 http://<局域网IP>:1/announce(零外连, §2.9 口径), 经 WebUI POST /api/torrents/{hash}/reannounce 强制汇报, 轮询 /api/cmd/{cmd_id} 等回执。

计划期望 ① 落「失败: tracker 未接受汇报(not working)」(RC_FAIL); 实测首报落 ok(confirmed) —— 确认跟踪在指令登记后 ~1ms 就读到 tracker 行 updating(在途)并按「在途直证」写终态回执, 死端口 announce 稍后的真实拒绝(status 4 + msg)不再纠正已写的 ok。与冻结计划的失败判据「活跃+死端口回了成功语义」精确命中。

02证据

取证 2026-10-31 17:35(commands run real.run -- --case RM09-04 --yes):

回执: {'status': 'ok', 'error': '', 'truth': {'results': [{'hash': '5258a4bb…', 'status': 'ok', 'reason': ''}]}}
产品日志(同一秒内):

17:35:46,657  WEB UI | 强制汇报确认成功(1个种子)        ← 指令后 +1ms 即终态

对照锚点: 同种子同 tracker 在 qB 侧随后必然是 status 4(死端口 RST); 产品自己定义的回执口径是「回执语义只承诺诚实标签」(pitfalls/backend/effect-confirmation.md, _verdict_reannounce docstring 引用)。

03影响面

维度结论
触发条件强制汇报目标 tracker 行的基线 min_announce 缺失/为 0(从未成功响应过, 如不可达 tracker / 新加 tracker), 且判定轮询恰逢 updating 在途瞬态 —— 死端口/宕机 tracker 必现首报即 ok
影响范围单发 reannounce_torrent 与组 reannounce_group 的确认回执(共用 _register_reannounce_pending / check_pending); 用户对不可达站点会看到「汇报成功」假象, 后续不再重试
严重度中(误导性回执, 不损数据; 与「诚实标签」回执口径相悖)

04定位锚点

  • src/auto_qb/webui/commands.py:466-470(取证 2026-10-31 17:40)· _verdict_reannounce 分支② — updating or status == 3 时基线 min 缺失/为 0/已过期即 confirmed "announce 在途", 不等失败证据; grep 关键词 announce 在途
  • src/auto_qb/webui/commands.py:596-658· _register_reannounce_pending(min_e 缺失时 deadline=30s, 但 confirmed 在首个判定拍就终态化); grep REANNOUNCE_DEFER_EARLY

05根因（可选）

S0 探针事实「min 过期前 updating 是 ~0.9s 假瞬态」只覆盖了 min 已存在的场景, 于是分支②给 min 缺失/为 0 的行放行 updating 直证; 但「从未响应过的 tracker」第一次被强制汇报时 qB 同样先置 updating(此时 announce 是否能成完全未知), 该瞬态与真实在途不可区分 —— 首拍读到即终态 confirmed。已排除: announce 真成功(死端口 RST, qB 侧随后必为 status 4); 快照滞后用例侧事故(已修 wait_in_store_state 后仍复现)。
