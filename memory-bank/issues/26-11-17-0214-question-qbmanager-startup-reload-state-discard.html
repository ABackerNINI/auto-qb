§01现象与发现场景

relocate 重构第一批真机验收(2026-11-17, 计划 26-11-15-2340)撞见, 证据 27 件(tmp-analysis/acc-reloc-single/): relocate 启动期接管面(迁移器盖章/启动对账回写/prune 滚出)写进 state 的突变被静默丢弃 —— 真机实测 prune 滚出后三次周期刷盘仍写滚出前旧账 27 条、relocate.model_version 章永不落盘, 直到首个账面动作 _persist 才收敛。根因在内核启动序列: QbManager.run() 先跑 start_all(模块启动期写点发生), 之后 _reload_state() 把 ctx.state.data 从磁盘整体重读替换 —— start_all 阶段的全部突变被那次替换丢弃, 周期刷盘随后把磁盘旧版原样写回。与平台/配置无关, 任何模块都会踩。

relocate 侧已在 cd786499 以「接管面写穿」规避(_load_jobs 尾部内存收敛完成后立即 ctx.state.save(), 持锁已在 QbManager.__init__, 单一写线程不变; dry-run 不动手; state 替身无 save 跳过) —— 本发病点已修, 但内核级通用隐患仍在: 未来任何模块在 start_all 阶段写 state 都会重演同款丢失。

§03影响面

维度结论
触发条件任何模块在 start_all 阶段(启动序列)写 ctx.state.data 且依赖落盘 —— 写入在 :547 reload 时被整体替换丢弃
影响范围内核启动序列为通用面: 现存模块里 relocate 已中招(已写穿规避), 未来新增模块的启动期 state 写点(迁移/对账/清理类尤甚)都会静默丢失; 启动期写入的「看似已持久」与盘面真相分叉, 违反黄金法则 3(状态持久化)的直觉预期
严重度中 —— 修复方向是启动序列语义变更(reload 时点/接管协议), 动内核面需裁决; 现存唯一发病点已有规避, 短期无新增数据风险

§05根因（可选）

启动序列顺序问题: reload 的本意是「连上 qB 后以真实状态刷新基线」(字段变化基线重新挂接), 但整体替换语义把 start_all 阶段的模块启动期写点一并回退。非并发/丢锁问题(全程持锁、单一写线程); 已排除: 周期刷盘缺漏(刷盘正常工作, 写的是被替换后的旧版)、relocate 特有缺陷(任意模块同位必现)。

§06建议修法（可选）

方向待裁决(两选一或折中, 动内核启动序列):

  • reload 挪到 start_all 之前: 基线刷新不再回退启动期写点; 代价=需核实 reload 依赖的前置条件(连接成功后的哪些字段)是否在 start_all 前可得。
  • 显式接管协议: reload 改为合并语义或提供「启动期写点登记/重放」协议, 模块显式声明接管面; 代价=协议面设计 + 各模块接线。
  • 无论哪个方向: 配套坑档(启动期 state 写点被 reload 丢弃)沉淀, 现存规避先例(relocate_mod.py:667 写穿)在坑档里记为过渡形态。
