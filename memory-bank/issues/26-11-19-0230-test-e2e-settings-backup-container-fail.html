§01现象与发现场景

发现场景: 计划 26-11-18-0801 S4 批(commit ae588e66)跑全量 e2e @fast 子集取基线时,commands run test.linux-e2e(Docker testbed 容器 auto-qb-testbed)352 例中 3 失败,其中本件 2 例(prism/atlas 双皮肤各 1)为确定性红——同位置同超时,与连跑顺序无关。

失败点: e2e/settings-backup.spec.mjs 的「导入 round-trip」用例——还原导入后 reload 等「整组迁移」块 30s 超时。

§02证据

三层对照实验(取证 2026-11-19,S4 批实施期间,容器内三跑):

1) 单独跑(无新 spec、无盘面污染)        → 仍红(同位置超时)
2) HEAD 暂存 S4 批全部改动后跑           → 仍红(排除改动面)
3) 与新 spec 连跑                        → 复现同位置红(排除交互污染)

结论: 容器环境既有失败,与 S4 批改动无关(对照实验由实施子代理完成,主会话未复跑)。

另: Windows 侧同 spec 12 例中 8 红,根因是本机有真实 gtm 工具在响应——导出 bundle 的 gtm 段非 null,违反该 spec 的桩前提「gtm 不运行 → 段为 null」;属本机环境因素(装了真实 gtm 的开发机都会撞),非代码缺陷。

§03影响面

维度结论
触发条件容器内跑 settings-backup.spec.mjs「导入 round-trip」用例即必现(双皮肤);Windows 侧需本机装有真实 gtm 工具才触发另外 8 例红
影响范围仅该 spec 的导入 round-trip 断言块;不污染其它 spec(连跑对照 3 已证);不进基线口径(计划 26-11-12-0152 明示: e2e 数字不进基线、锚 Windows 侧)
严重度中——挡住该 spec 在容器环境的可信绿,妨碍以容器跑全量 e2e 判收;主线 pytest 基线不受影响
