01现象与发现场景

在 plan 26-11-03-0120（WEBUI 搜索自动更新）落地后的回归中记录（2026-11-03）。与配置无关，与「搜索结果里的种子是否已归组」相关。两个现象：

  • A 重复展示：搜索命中一个未归组种子（分组关闭 / 同 save_path 暂无第二个种子 / 文件列表不可读）→ 结果用 searchUncovered 的虚拟行兜底。随后该种子变成已归组（同 save_path 出现第二个种子），列表同屏出现真实组行 + 陈旧虚拟行，同一个种子展示两次。
  • B 删除后滞留：搜索命中后该种子被删除 / 移出命中集，虚拟行仍留在结果里，直到用户重新输入搜索词（或下一次 search_rev 变化触发静默重查）。

本报告只记录，不修；现象由用户报告 + 静态代码可证，尚未补 e2e 复现用例。

03影响面

维度结论
触发条件搜索激活（非空查询 + 非 negative_only）且命中集里有未归组种子；随后该种子被归组（同 save_path 出现第二个种子）或被删除。分组启用时更常见；与站点/皮肤无关。
影响范围三类皮肤（atlas / prism / flux）的搜索结果列表（filteredTorrents），可与分类/标签/路径/站点/HR 筛选叠加；只影响前端展示与行计数，不影响 /api/search 返回与后端数据。
严重度中：重复行会让计数与「选中/操作目标」失真；滞留行会让人对已删除种子继续操作（点下去 404/回执失败），但不崩溃、不丢数据。0 命中变体不触发。

  • src/auto_qb/webui/static/shared/filters.js:225-249（取证同上）· 符号 filteredTorrents · grep 关键词 "u-" + r.hash / virtual: true · 渲染时对 searchUncovered 无条件追加，不校验该 hash 是否已进入当前组视图。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

初步结论（静态可证，未做动态复现）：searchUncovered 是 doSearch 时刻的快照，渲染层把「真实组」与「该快照」两路无条件合并，合流时既不校验 hash 是否已在当前组视图里，也不校验 hash 是否仍在 searchHits 内 ⇒ 转归组后重复、删除后滞留。已排除：/api/search 返回重复项（后端只回种子列表，重复来自前端两路合并）。

静默重查为何只是缓解而非治本：_maybeSearchRefresh 只在 status.search_rev !== searchRevApplied 时才重跑 doSearch(true)，而 search_rev 只在 added/removed、name/category/save_path/tags 变化与 full_round 时 +1；分组归属变化不保证伴随一次 rev 变化（且 searchPending / _searchRefreshBusy / 冷却窗口会跳过本轮）。即便 rev 变化，从「组行已出现」到「下一次静默重查落袋」之间仍有一帧重复可见。真正的边界应在渲染/状态层：合并前按当前组哈希集去重，并剔除已不在 searchHits 的虚拟行。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向（只写方案，不在本报告实施）：

  • A 渲染层去重（推荐，改动最小）：filteredTorrents 注入虚拟行前，先用当前组视图的成员哈希建一个 Set（可复用已有分组索引），跳过已在组内的 r.hash；同时跳过不在 this.searchHits 内的 r（删除后残留）。代价：每次过滤多一次 O(n) 集合构建（可缓存到 group_view_ver 变化时）。
  • B 状态层重算：在轮询成功且 group_view_ver / 组索引变化时重算 searchUncovered（按当前 grouped 与最新命中集）。代价：多一次全量 filter；需与 doSearch 的 grouped 口径保持单点，避免两份计算漂移。

验收判据（认领后按此补测试）：① 未归组命中转归组后结果只有 1 行，不出现 key: "u-<hash>" 虚拟行；② 删除命中后虚拟行在一个轮询周期内消失，无需重新输入搜索词；③ 静态守阵钉住「注入虚拟行前跳过已在组 hash / 已不在命中集 hash」；④ e2e 覆盖 A/B 两场景（三皮肤至少各 1 条）；⑤ 不新增第三处 this.searchPending = true，自动更新过程不闪全列表。
