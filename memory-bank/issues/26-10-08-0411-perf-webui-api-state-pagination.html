06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  • B 按需字段（推荐先评估）：按视图再裁一层字段集（首屏只给要渲染的列），与 VIEW_ARRAYS 同路数；增量协议的桶裁剪要跟着走。代价中等。
  • C hash 引用式：组行不内嵌 members 而给 hash 引用 —— 6.3 MiB 的主体直接塌掉，顺带把组行增量粒度降到成员级。与 B 正交，但波及前端筛选器计数与列模型数据源，是独立立项级改动（已另入池 26-10-07-1420-perf-webui-group-row-hash-ref，本条与它需一起拍板先后）。
  • A 分页：/api/state 加 page/per_page 或游标，首屏分批取。代价最大 —— 前端虚拟列表、排序、筛选器计数都要能在不完整数据集上说真话（原 issue 方向③字面方案，但不一定是性价比最高的）。

排序建议：先做「全量轮成本构成实测拆分」再选 —— 主体是 members 数组走 C、主体是种子行字段走 B、只想让首屏更快走 A。
