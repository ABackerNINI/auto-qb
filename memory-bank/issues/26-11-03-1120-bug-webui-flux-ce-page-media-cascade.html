01现象与发现场景

第三次全量 code review S3 对 flux 皮肤做 CSS 全量级联扫描时发现：views.css 的 @media (max-width:900px) 块把设置页根容器 .ce-page 的内边距压到 12px 12px 24px，但 dialogs.css 在更晚的位置给同名选择器声明了 padding: 16px 12px calc(24px + var(--statusbar-h))。两者特异性同为 (0,1,0)，后加载的 dialogs 恒胜，移动端紧凑内边距从未生效。触发条件：窗口宽度 ≤ 900px 且打开设置页；四皮肤同构（prism/atlas/console 的 views/dialogs 也是同款顺序），flux 为窗口内新增皮肤。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

最小修法：把 dialogs.css 的 .ce-page 基础 padding 提到更早的层（components.css），媒体规则保留在 views.css；或把移动端覆盖挪到 dialogs.css 的媒体块内。两种都保持层级职责，不靠提权。

若确认「12px 顶距」才是目标值，也可在 dialogs.css 内加 @media (max-width:900px) 覆盖；但更推荐消除同名同属性双写，避免下次再赌加载序。四皮肤同构，修复时应一并评估是否统一。

复验

复验 2026-11-04 02:20：仍复现，且影响面修正为 flux/atlas/console 三皮肤（各自 views.css 媒体规则 vs dialogs.css 无条件规则）；prism 两条规则同在 views.css（:522 无条件 → :680 媒体），同文件内后置胜出，媒体规则生效、无须修。另核实一处 issue 未记的事实：.ce-page 唯一落点是 shared/tpl/settings.html 的 class="ce-page hub-page"，shared/console_hub.css（加载序在所有皮肤 dialogs.css 之后）的 .hub-page { padding: 0; } 同特异性恒胜，把 base 与媒体两条 padding 都压死 —— 设置页实际内边距由 .hb-wrap 承担，故本缺陷为级联卫生问题（死规则 + 赌加载序），实测渲染差异为零。

修复后补充

实际修法：采用建议修法的「dialogs.css 内加媒体覆盖」支线 —— 三皮肤（flux/atlas/console）各自把 .ce-page { padding: 12px 12px 24px; } 从 views.css 的 @media(max-width:900px) 块移除（留指路注释），挪进 dialogs.css 基础规则之后新增的同条件媒体块。同文件内媒体覆盖紧跟基础规则，不再赌跨文件加载序，也保住 views/dialogs 的层级职责，未用提权。与建议的「提到 components.css」支线相比改道原因：components.css 无 --statusbar-h 之外的骨架语义且 base 规则本就住在 dialogs.css，就近内聚改动面最小。prism 不动（序已正确）。

验证方式：grep 六文件复核规则落位（每皮肤 .ce-page padding 仅存 dialogs.css 一处 base + 一处同文件媒体覆盖）；跑 webui 静态扫描测试 test_webui_static_skins_skin.py / dom_panel_dialogs.py / dom_page_layout.py（58 passed）与 skins_table / skins_widget / dom_page_hr / dom_panel_misc（30 passed），全部通过。
