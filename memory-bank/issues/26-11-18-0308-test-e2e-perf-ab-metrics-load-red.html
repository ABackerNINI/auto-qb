§05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（双根因, 两 clone 各自独立归因后合流; 都排除负载敏感与产品回归, 是量具面）。根因 A —— A/B 段计数窗口错位（远端 30fac406 归因）: `window.__gbr` 是整页累计的 `getBoundingClientRect` 计数器; P1-3 预算 `tRows×(rounds+2)+20` 只描述 B 段（窗口化）的逐行测高, 旧代码在 A 段（关窗口全量替换）与 B 段之间从不清零, 把 A 段的行测量一起算进 B 段 —— 临时埋点实测（E2E_TORRENTS=300）: atlas A 段末 64 次 + B 段增量 75 次 = 累计 139 > 预算 130; prism 30 + 72 = 102 < 125, 恰好解释「只有 atlas 红、prism 孪生绿」。根因 B —— 背景轮询 tick 混入 + off→on 重开窗 reprobe（另一 clone W2 归因）: bench 全程页面轮询照常跑（300 档 basePollMs 1500ms 恒定间隔）, 每拍 /api/state 恒回传 status（server/routes/state.py `_status_payload` 现拼新对象, 不受 rid 门控）⇒ vm.status 赋值必触发根重渲 ⇒ 根 `updated()`（lifecycle.js）的 `_measureRowH` 对窗内每行发一次 gBCR, 每拍混入 ~tRows 次预算外 gBCR; P1-3 预算不含墙钟项, 慢机上 bench 墙钟拉长 ⇒ 落窗拍数变多 ⇒ 预算被拖穿（本机基线 82/预算 120 余量 38 恰好只容 ~2 个 tick）。轮询隔离成纯净窗口后 atlas 仍红（累计 139 > 130）—— 暴露 第二机制: off 轮收尾 rowWin false->true 重开窗那一拍对全量 DOM 上已持键的行再探一轮（_rowWindow 的 reprobe 面, 26-11-02 后引擎引入）, 实测与轮数无关、皮肤相关（prism ~24 / atlas ~54 次, 逐轮复现）; 原基线 82 是 26-11-02 前引擎的数字, 累计预算公式被引擎演化悄悄作废。已排除: 产品侧 gBR 回归（B 段增量本身在预算内）、随机 flaky（分段清零 + 隔离后定向连跑多轮全绿）。

§06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

实际修法（与建议方向不同, 故保留建议原文; 合流后机制 = 远端分段清零 + 另一 clone 的轮询隔离与 off 侧守阵）: 不改预算、不放宽阈值, 改计数口径与量具窗口。(1) `e2e/perf.spec.mjs::benchRun` 每段 bench 开始加 `window.__gbr = 0`（A/B 两段各自独立计数）, 末尾读取只含 B 段, 与公式 `tRows×(rounds+2)+20` 同口径 —— 根因 A 的修法; (2) bench 前量具窗口与背景轮询隔离（`vm.stopPolling()` + `vm.stopEvents()` + 影子化 `vm.scheduleNext`, bench 后复原）, 消除每拍 ~tRows 次预算外 gBCR 的混淆源 —— 根因 B 的修法; (3) off 侧补宽松上限断言 `OFF_GBR_CEILING = 130`, 兜「非窗口化轮次被逐行量高」的回归模式。`rounds`、预算公式、P1-2 长任务断言一律不动。代价: 零产品改动、零判据放松。
