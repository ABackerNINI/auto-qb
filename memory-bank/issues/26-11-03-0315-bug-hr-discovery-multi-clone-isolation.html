01现象与发现场景

2026-11-03 测试侧端口盘点（只读）时发现：同机多 clone 场景下，每个 clone 的 auto-qb 进程都会把 HR 通道端点注册进同一份用户级 %LOCALAPPDATA%\auto-qb-hr\instances.json；浏览器扩展探测固定发现口 18788（候选 +0/+1/+2）并取首个命中，拿到的是「全机所有实例」的 endpoint + token，无法区分实例属于哪个 clone/项目。

触发条件：同一 OS 用户下有 ≥2 个 clone 都启用 HR 通道，且浏览器装有扩展。结果：扩展的实例列表把不同项目的实例混在一起，选中后会用别家的 token 调数据口，形成跨项目混串。旧设计只覆盖「同机多实例」，未评估「多 clone / 多项目」这一维度。

03影响面

维度结论
触发条件同一 OS 用户、≥2 个 clone 启用 HR 通道、浏览器已安装扩展；注册表不隔离时必现。
影响范围扩展的实例列表与取数通道；跨项目 token/实例混用；发现口只绑回环，不对外暴露。
严重度中（仅影响多 clone 开发者机器；但会造成「以为在操作本项目实例」的语义错误）

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

先给结论：能改，但不能只改端口。固定 18788 本身不是根因；根因是「发现响应不携带归属信息 + 扩展取首个命中」。候选表扩增只解决抢口，不解决混串。

路线做法代价 / 兼容性
T1 约定主 clone（零代码）文档/协作约定：同一时间只有一个「HR 主 clone」注册发现口，其它 clone 不启用 HR 扩展通道。最低成本；靠人守，容易复发；不改变扩展行为。
T2 注册表按 clone 隔离instances.json 路径按 clone/工作区派生（如路径哈希），发现响应只含本 clone 实例；扩展侧需能显式选择目标发现地址。后端可独立落地；旧扩展仍会连到 18788 上「碰巧在跑」的那个 clone，语义仍静默错误；需扩展提供地址选择。
T3 响应携带归属 + 扩展过滤/api/hr/discover 响应增加 workspace/clone 标识（或实例分组），扩展按当前项目过滤/多地址探测。需双端同发（旧扩展+新后端、新扩展+旧后端都只能退手动）；触碰守卫测试（响应结构契约、候选表固定 3 的约束）；部署说明要覆盖。

建议：短期 T1（立刻降低混串概率），中期 T2 + T3 分阶段；T3 必须先补协议版本/兼容判据再动。用户级指针文件不可行（MV3 扩展读不到本地文件）；主实例选举复杂度和收益不匹配，暂不推荐。

本轮不修；不开工到代码级细节。
