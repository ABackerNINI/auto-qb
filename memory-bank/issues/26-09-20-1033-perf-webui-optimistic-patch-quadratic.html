01现象与发现场景

2026-09-20 复核「WEB UI 解耦」任务、重跑浏览器冒烟时撞见：3000 种子桩服务下 ok 模式每轮都打 1~2 条 [perf]，形态恒为「补丁 2s 级 / POST 稍晚于补丁 / 排队 0ms / 执行 1ms」：

[perf] 命令 4da5d00c0136d1ee(pause): 补丁 2033ms / POST 2090ms / 排队 0ms / 执行 1ms / 端到端 917ms
[perf] 命令 545a5661bd5ee75c(pause): 补丁 2407ms / POST 2475ms / 排队 0ms / 执行 1ms / 端到端 534ms
[perf] 命令 4da5d00c0136d1ee(pause): 撤下 3081ms via=pull (3000 个目标, >2500ms 属异常)

当时被记为「大库主线程抖动，未做 A/B，不入池」。本次受控实验证明不是抖动：补丁耗时按 O(目标数 × 数据集规模) 增长，与排队/执行/网络都无关（排队 0ms、执行 1ms）。触发条件就是「目标数 × 库大小」的乘积；与平台无关（纯前端同步 JS）。

03影响面

维度结论
触发条件库大（≥1000 条）+ 批量操作（全选 / 整组 / 整剧）。单目标与小库无感（毫秒级）；3000×3000 才到 2s 级。
影响范围两套 UI（prism / atlas）共用 shared/commands.js；只命中乐观白名单 pause/resume 的批量路径（act() / bulkAct() / actTorrent()）；不涉及后端与规则层。
严重度中。无数据风险（补丁是前端覆盖表，失败/超时会回滚，见 resolveOptimistic / 3s 兜底）；但点击后主线程被同步占用 1~2s，期间 UI 无响应 —— 正是「点了没反应」那一类观感问题。附带问题：patchMs 的报警阈值恒 50ms，未按目标数分档 ⇒ 大库每次批量必报，属常驻噪音（项目自己的原则：常驻的报警没人看，反而掩盖真异常）。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（有实测支撑）：applyOptimistic 对每个目标 hash 调一次 _forEachRow，后者遍历三张全表做线性查找 ⇒ 复杂度 O(目标数 × 数据集规模 × 3)。单目标时只是 3 次全表扫描（毫秒级，无感）；3000 目标 × 3000 条 ⇒ 约 2700 万次比较 + 3000 次响应式 Object.assign，实测 2146.7ms，与冒烟报的 2033/2407ms 同一量级。

已排除的假设：① 不是网络/后端 —— 探针只调纯前端同步函数、不发请求，耗时同量级；② 不是渲染/重排 —— 探针不点击、不等 rAF，测的是函数同步返回；③ 不是 4df80dc 引入 —— 该提交之前同场景实测 1693ms。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向：把「逐 hash 全表查找」换成「一次建索引、再按 hash 命中」。

  • 方案 A（推荐，改动最小）：在 applyOptimistic 入口先把三张表扫一遍建成 hash -> rows[] 映射（O(数据集)），再按目标命中 ⇒ 复杂度降为 O(目标数 + 数据集)。代价：映射要覆盖 torrents / singles / groups[].members，且必须保持「一个 hash 可能命中多行」的现有语义（当前 _forEachRow 就是这个语义）。
  • 方案 B：视图构建时直接把行引用挂到可查结构（后端 web_view.py 出 hash→行 索引），前端不再查找。代价：改动面大，跨后端视图与前端结构。
  • 方案 C（只治标，建议与 A 同时做）：把 patchMs 的 [perf] 阈值按目标数分档（与 settleMs 的 budget 同款），消除大库常驻噪音；A 落地后若仍超阈值，那时才是真异常。
