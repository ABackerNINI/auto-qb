§01现象与发现场景

relocate 恢复确认批次评审（2026-11-15）发现的保守边界：_member_stopped 对已从 qB 删除（不在 store.by_hash）的成员判「停着」（docstring 自述：宁挂账勿漏恢复，防快照空窗误关账）——该成员的 resume_pending 永不闭合，补发穷尽后账面余量永久挂账（计数告警每开账回合一笔 + webui 待恢复行/哈希行如实显示已删成员）。同面：resume_hashes 既有行为也不清理已删成员。用户删除种子是常态操作，该账无法自愈。

§02证据

# src/auto_qb/core/modules/relocate_lifecycle.py:222-232 （取证 2026-11-15）
def _member_stopped(self, h: str) -> bool:
    """成员当前是否停着(store 为 qB 镜像; 对照 qB 真实态判定, 不靠内存标记单点)

    不在客户端(已删除)也按停着算 —— 保守不闭合其账: 快照空窗误判「已删除」会把
    该成员的恢复账悄悄关掉(宁挂账勿漏恢复), 已删成员的补发是 qB 侧无害 no-op。
    """
    store = getattr(self._ctx, "store", None) if self._ctx is not None else None
    rec = getattr(store, "by_hash", {}).get(h) if store is not None else None
    if rec is None:
        return True
    return bool(getattr(getattr(rec, "state_enum", None), "is_stopped", True))

issue 评注（非源码原文）: 已删成员（rec is None）恒判「停着」→ 该成员 resume_pending 永不闭合。

§03影响面

维度结论
触发条件成员在恢复确认窗内被用户/qB 删除（store 永久不再有该 hash，非快照空窗）
影响范围穷尽后余量永久挂账 + webui 待恢复行永久显示已删哈希；无功能损失（补发对已删成员是 no-op），纯展示噪音与告警噪音
严重度低

§05根因（可选）

已有结论：保守判停着是有意设计（防快照空窗误关账，注释自述），但缺「确认已删」的第三态——现状无法区分「快照空窗」与「真被删除」，只能一律挂账。
