§01现象与发现场景

计划 26-11-15-0914 S2 批次评审（T3）发现的窄窗行为偏差，非 blocker，用户拍板入池。S2 落地的已删确认判据（604b52b3，issue 26-11-15-0345）用 _deleted_streak 记「连续不在 store 的拍数」，达 _DELETED_CONFIRM_TICKS=3 闭账。该 streak 是 (job_id, hash) 键的进程内内存态，只在「重现 store」与「闭账移除」两处清；账重开（终态重发同 (mover,src,dst) 落同 job_id，_start_job 裸赋值覆盖旧对象）时不清零——旧账积累的缺失拍数被新账继承。

§02证据

取证时间 2026-11-15（S2 批次评审）；代码位点原文：

# src/auto_qb/core/modules/relocate_lifecycle.py:324-331（取证 2026-11-15, 604b52b3 落地面）
streak = self._deleted_streak.get((job.job_id, h), 0) + 1
if streak >= _DELETED_CONFIRM_TICKS: ...闭账
else: self._deleted_streak[(job.job_id, h)] = streak
... 重现在 store: self._deleted_streak.pop((job.job_id, h), None)  # 空窗结束作废

# 清理面全查（grep "_deleted_streak" 全 src/）: 仅 init(relocate_mod.py:86)/累加与重现清(:324-331)/闭账清(:378)
# —— _start_job（relocate_exec.py:1594 self._jobs[job_id] = job, 账重开覆盖点）无对应清零

§03影响面

维度结论
触发条件窄窗叠加：旧账对某成员已积累 1-2 拍缺失（快照空窗未达 3 拍）→ 账终态闭合并重开（同 job_id）→ 新账期间该成员真被删除
影响范围仅 relocate 恢复确认账的已删闭账节奏：新账提前 1-2 拍（而非满 3 拍确认）闭账；不误删数据、不影响非 resume 面
严重度低 —— 后果有界（提前闭账前仍有 ≥1 拍缺失确认，且重启天然清零）；属确认口径的精度偏差而非功能错误

§04定位锚点

§05根因（可选）

已有结论：streak 生命周期被设计成「进程内 + 闭账时清」，但账重开是第三条生命周期边界——job 对象被 _start_job 整体替换而 streak 键含 job_id 不变，旧账积累的缺失拍数静默带入新账（与 26-11-15-0344 的 job_id 复用覆盖同族：都是「键跨生命周期复用、状态没跟着结转/清零」）。

§06建议修法（可选）

评审时给过的候选（未拍板，不在本报告里实施）：在开账点 _start_job 落账处（relocate_exec.py:1594 一带）按新 job_id 清 _deleted_streak 同键项；或在 _load_jobs 按 job 清（覆盖点更全，代价是碰启动路径）。两向都只动内存态字典，不涉 state_file。
