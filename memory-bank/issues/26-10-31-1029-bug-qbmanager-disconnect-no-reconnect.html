01现象与发现场景

RM02 真机实测(RM02-07, 计划 memory-bank/plans/26-10-31-0927-plan-real-RM02.html): 产品进程经本地 TCP 代理连 36596, 运行期把代理掐断 75s 模拟 qB 宕机, 再恢复代理。预期(A-07/D1 验证面): 断开期间连接失败 ERROR 只在状态转换记一次, 断开静默, 恢复后自动回连并打「已重新连接 qBittorrent」INFO 收尾。

实测: 掐断后第 2 个 sync 轮起, 每 ~2s(main_tick)一条 主循环异常: 'NoneType' object has no attribute 'torrents_info' ERROR(带堆栈)刷屏; 恢复代理后 60s 内无任何回连, 刷屏持续 —— 进程停在永久断连态直到重启。另有一条误导性 WARNING(见证据)。

03影响面

维度结论
触发条件运行期 qB 断连一次(API 请求失败)即进入, 与断连时长无关; 首轮失败后 1-2s 内必然到达
影响范围断开期间日志被堆栈 ERROR 淹没(告警/通知面); qB 恢复后不会自动重连, 主循环功能(同步/规则/维护)全部停摆直到进程重启 —— 与「重连退避、恢复自动接上」的设计承诺相悖
严重度高(长期运行的主循环在 qB 一次瞬时断连后永久失能)

04定位锚点

  • src/auto_qb/core/qbmanager.py:649(取证 2026-10-31 10:29)· except APIConnectionError 分支 · grep「client = None」: 置 self.client = None 后仅当 _reconnect_due 到期才调 connect(), 未到期时 client 保持 None。
  • src/auto_qb/core/qbmanager.py:573 · _sync_line/_refresh_torrents · grep「apply_sync(self.api)」: 下一轮同步线仍照常执行, QbApi._client 为 None 时 sync_maindata 抛 AttributeError。
  • src/auto_qb/torrents/store.py:19(取证同日)· _SYNC_UNAVAILABLE = (AttributeError, NotFound404Error) · grep「_SYNC_UNAVAILABLE」: AttributeError 被当作「端点不可用」降级 → 回退 api.torrents_info() 再次 AttributeError → 穿到主循环 except Exception(grep「主循环异常」)记 ERROR + 2s 退避 —— 该路径不经过 APIConnectionError 分支, connect() 永远不再被调用, 与刷屏伴生。
  • 注: 仅在「失败后 reconnect 未到期」的窗口内 client 为 None; 实测序列 = 首次失败 → connect() 一次(留 client 为新建未认证对象)→ 再失败置 None → 之后永远走 AttributeError 路径。

05根因（可选）

两条叠加: ① 断连处置把 client 置 None, 但同步线对 None client 无守卫, AttributeError 被 _SYNC_UNAVAILABLE 误分类成「qB 不支持 sync/maindata」降级路径, 最终落进通用 except Exception(ERROR 刷屏 + 退避); ② 通用 except 与 AttributeError 路径都不调用 connect(), 而 connect() 的唯一调用点在 APIConnectionError 分支内 —— 该分支要求 client 非 None 才可能再进, 断连态从此外无出口。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向: 让「断开期间」成为有出口的稳态。候选: a) 同步线/主循环在 client is None 时直接走重连判定(_reconnect_due)而非执行请求, 复用既有退避与转换节流; b) 不置 client=None, 保留未认证 client 让失败继续走 APIConnectionError 分支(最小改动, 但 AttributeError 误分类仍在, 需把 None client 从 _SYNC_UNAVAILABLE 路径排除)。代价都集中在主循环错误路径, 需补「断开→恢复」单测 + RM02-07 真机回归。
