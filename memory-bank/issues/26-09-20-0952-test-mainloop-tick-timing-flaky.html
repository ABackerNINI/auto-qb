01现象与发现场景

2026-09-20 做「app.js 按域拆分」时连跑全量测试做回归对照，同一份代码连续多次 uv run pytest tests -q，结果在 1057 passed 与「1 failed / 1056 passed」之间跳， 失败的永远是同一条：tests/test_qbmanager.py:186。

触发条件与代码无关，只与机器当时忙不忙相关：几次失败都发生在「刚跑完一次全量」或 「同时有其它进程（Playwright 冒烟 / 桩服务 / 索引生成脚本）在跑」的时候；单独重跑该文件或空闲时重跑全量， 连续 3 次均为 1057 passed。与平台相关：这是挂钟时间断言，CI（Linux）同样会受负载影响， 本机 Windows 与 WSL 沙箱都会中。

⚠ 它不是本次拆分引入的：拆分前的基线跑（同样的并发环境）也出现过一次同样的红。

02证据

断言原文（tests/test_qbmanager.py:176~186）：

        mgr.config.sync_interval = 0.05
        mgr._tick = mock.Mock(side_effect=[None, KeyboardInterrupt()])
        start = time.monotonic()
        mgr.run(dry_run=False)
        elapsed = time.monotonic() - start
        assert mgr._tick.call_count == 2
        assert elapsed >= 0.05, f"每轮循环后应阻塞到下一条时间线, 实际 {elapsed:.3f}s —— 主循环在空转"

失败原文（uv run pytest tests -q --no-cov --tb=line -rf）：

E   AssertionError: 每轮循环后应阻塞到下一条时间线, 实际 0.046s —— 主循环在空转
    assert 0.046000000002095476 >= 0.05
D:\Projects\auto-qb\tests\test_qbmanager.py:186: AssertionError

最小复现（人为制造负载即可稳定触发）：

# 空闲时: 连续 3 次全绿
uv run pytest tests -q --no-cov          # 1057 passed ×3

# 制造负载后再跑(与别的前台任务并发, 或先跑一次全量紧接着再跑一次):
python scripts/gen_tasks_index.py && uv run pytest tests -q --no-cov --tb=line -rf
#   → 1 failed, 1056 passed
#   → E  AssertionError: 每轮循环后应阻塞到下一条时间线, 实际 0.046s

差值 0.046 / 0.05 = 92%：不是主循环空转（空转会是 0.00x 量级），是 被测的 sleep 被调度器提前唤醒 / 计时粒度抖动，而断言写成"必须 ≥ 一个节拍"且零容差。

03影响面与严重度

维度结论
触发频率本机 2026-09-20 半天内至少 3 次；并发跑任务时约 1/3 概率，空闲时 0
影响范围只影响这一条用例的可信度：红的时候分不清是"真回归"还是"机器忙"。对功能、对前端、对后端行为零影响；不区分视图/站点/配置开关
数据风险无。不涉及删除/限速/状态写入，纯计时断言
严重度低（但会消耗排查成本：每次红都要花几分钟确认不是自己改坏的）

04根因（初步）

结论：断言写法问题，不是主循环 bug。证据有三：①失败值 0.046s 与阈值 0.05s 只差 4ms， 属调度抖动量级，若真是"主循环空转"应该接近 0；②assert mgr._tick.call_count == 2 这条从未失败， 说明循环确实按节拍走了两轮；③空闲时连跑 3 次全绿。

所以是"用挂钟时间做下界断言且不给容差"这一通用反模式：被测行为（阻塞满一个节拍）在数学上是 >=，但任何 OS 的 sleep 都只保证不早于，实际唤醒时刻受调度影响，测量值必然有抖动。

已排除：①主循环真的空转（call_count 断言恒过，且失败值是 92% 而非 0）；②本次 app.js 拆分引入（拆分前同样环境下已出现过）；③Windows 专属（属通用计时问题，Linux CI 同样会中）。

05建议修法

方向：把"必须 ≥ 一个节拍"改成"允许少量调度抖动的下界"，同时保留它真正要守的东西 （主循环不能空转 —— 即不能远小于一个节拍）。

方案 A（推荐）：给下界留容差，并补一条"别太快"的上界

改成 assert elapsed >= 0.05 * 0.9（或 >= 0.045）保留防空转语义；若想更严，可再加 assert elapsed < 0.05 * 4 防"睡过头"。代价：阈值变成经验值，需在注释里写清为什么是 0.9。 推荐：改动一行，语义不退化。

方案 B：不测时间，改测"睡了多久"（注入时钟替身）

把 time.sleep 换成可注入的替身，断言"传给 sleep 的参数 == 一个节拍"，与挂钟完全解耦 —— 这是同类断言最稳的写法（项目里 test_run_loop_managed_never_sleeps 已经是这个思路）。 代价：要动被测代码的注入方式或 monkeypatch，改动面比 A 大。

⚠ 无论哪个方案，都不要顺手放宽 sync_interval 的语义或改主循环节拍 —— 本条只改测试口径。
