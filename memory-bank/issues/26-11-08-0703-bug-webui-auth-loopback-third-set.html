复验

复验: 2026-11-08(认领时点)锚点仍成立 —— grep _LOOPBACK_HOSTNAMES/def is_loopback_host/def display_host 三套并存如旧(取证 43e7ee13)。一处与 issue 文本的小偏差: _is_loopback_host 实际判定用的是函数体内联三元组(仅 127.0.0.1/::1/::ffff:127.0.0.1, 不含 localhost), _LOOPBACK_HOSTNAMES 四元集只喂 Host/Origin 白名单(_allowed_hostnames) —— 消费面其实有四个语义位而非三个。消费面核查: 回环判定(内联三元组)共两个调用点且都吃 request.client.host —— ①auth.py require_token 的 skip_local_verify 免认证分支; ②routes/config.py /api/config/public 的「仅限 loopback」403 门。

修复后补充

裁决: 收敛路(issue §03 第一支)。依据三条代码事实: (a) 消费输入 request.client.host 是 TCP 对端地址, lifecycle 显式 proxy_headers=False(B-03, test_start_web_server_config_disables_proxy_headers 钉住)挡住反代头改写 —— 不可被请求头伪造; (b) 收敛扩面 = 127/8 全段(含 127.0.0.0/127.255.255.255 两端)+ "localhost" 字符串 + IPv4-mapped 各形态(含 ::ffff:7f00:2 类十六进制书写, 实测均判回环): 127/8 不可路由、只可能来自本机进程, 而 skip_local_verify 本就是对「本机连接」整体信任的显式开关(127.0.0.1 源早已免认证), 扩面不给任何攻击者新增能力; (c) config 校验(S1-5)与 hr 配对门早已按 127/8 判回环, auth 自有字面量集是漏判的孤例 —— web.host 绑 127.0.0.2 时同一地址在配置面判回环、在鉴权面不判。实施: auth.py _is_loopback_host 改为 is_loopback_host = infra.utils 单点的别名(仿 config/validation/sections.py:137 既有别名范式), 删内联三元组; _LOOPBACK_HOSTNAMES 保留(它是 Host/Origin 白名单种子集, 消费 hostname 字符串、需含 localhost 主机名, 与回环判定是不同语义位)并在注释声明与单点的关系及「为何不并 127/8」; display_host 折叠锚不动(口径差异是刻意设计, infra/utils.py 注释已声明「折成 localhost 后还连不连得上」的展示语义)。验证: test_web_auth.py 新增 test_skip_local_verify_loopback_127_subnet(web.host=127.0.0.2 场景: 无密钥/错密钥放行、/api/config/public 200、远端仍 401/403)+ 单测补 127.0.0.2/::ffff:127.0.0.1/::ffff:127.0.0.2/192.168.1.50 断言; 19 passed(test_web_auth) / 76 passed(test_utils_parse, display_host 既有口径不受扰) / 6 passed(test_webui_static_r4_poll_auth_lifecycle), 均 2026-11-08 实测。
