§01现象与发现场景

分析「将本 clone skills 移植到其它项目」的 T4 子任务报告时发现（2026-11-14）：移植项目的子代理跑了 my-commit-flow 自带测试（test_snapshot.py），在沙箱 AppImage shim 干扰下，其 cleanup 逻辑把 整个仓库（含 .git）递归删除；该代理从 ~/.zcode 会话库回放恢复了工作树文件，但 4 笔未推送提交不可恢复。

回溯本 clone 源码证实引爆点就是 test_snapshot.py 两处 addCleanup(rmtree(snap.parent))， 与 T4 报告逐行吻合 —— 缺陷在源头，移植现场只提供了触发条件（正常环境 respawn 链恒成功、stdout 恒带 PACK_DIR 行，测试恒绿；移植恰好移除了该测试默默依赖的环境假设）。P0 已在本 clone 修复（本批工作树，见 §06）； 本件同时跟踪 P1/P2 残余。触发与平台/沙箱配置相关：respawn 链任何一环失败且 stdout 缺 PACK_DIR 行即引爆。

§05根因（可选）

根因已定（P0 部分）: 三因叠加 —— 1) 环境推导路径（子进程 stdout 解析）未经锚定直接喂 rmtree； 2) Path("") 语义恒等 Path(".")（= CWD = 仓库根）；3) ignore_errors=True 把每步失败静默吞掉 （含 CWD 自身 rmdir 必败的最后一道响亮报错）。该文件已三度同族事故: 2026-10-16 并行污染（假设 gettempdir 全局独占）、 26-10-31 空壳 .git + TMPDIR 回落误判仓库根、本次 CWD 误删 —— 系统性弱点一贯: 依赖 tempfile 候选列表/TMPDIR/stdout 等环境假设而不钉不变量。P1/P2 根因同源。
