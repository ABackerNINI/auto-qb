01现象

full_checking 的 1.6 自愈（失败记录指向已完成/已删成员）在 _skip_on_group_check_failed 里直接 recheck_fails.pop(...) 清掉失败记录，但没有调用 state.save()。同一写点的 bump_recheck_fail（checking_meta.py）有即时落盘，本处漏了，导致自愈结果只留在内存。

02位置与取证

符号名 + grep 关键词优先；行号标注取证时间，代码漂移后按符号重定位。

  • src/auto_qb/rules/actions/full_checking.py:146（取证 2026-11-03 01:04）· 函数 _skip_on_group_check_failed · grep: recheck_fails / .pop( / state.save()
  • 对照写点: src/auto_qb/rules/actions/checking_meta.py:110-119 的 bump_recheck_fail，同键 recheck_fails 在变更后调用 state.save()。
  • 原始取证: 26-10-05-1036 报告批 G · G-05（P3 / R3）：“recheck_fails 的自愈清除写点不落盘”；定稿处置见 §3.2 并池备注表。
  • 纪律依据: behavior-core · state 写点即时落盘（skip_check_day / recheck_fails 为重放代价最高的键）。

03影响面

  • 丢失窗口: 自愈 pop 后到下一次周期落盘（state_save_interval 默认 120s）或优雅退出；其间崩溃/断电会丢失本次自愈。
  • 后果有界: 残留记录下次 1.6 会再次自愈，代价是一次多余 recheck，不会毒化状态。
  • 范围: 仅 rules/actions/full_checking.py 的这个自愈写点；不涉及 recheck 判定与规则调度语义。

04验收标准

  1. _skip_on_group_check_failed 删除 recheck_fails 键后调用 state.save()（或改走同等的即时落盘 helper），与 bump_recheck_fail 的写点纪律一致。
  2. 补落盘断言: 构造失败记录指向已完成/已删成员触发 1.6 自愈，断言 pop 后状态已持久化（重载 state 文件或断言 save 被调用），且不依赖周期落盘窗口。
  3. 行为不变: 自愈判定、recheck 触发与规则结果不变；规则相关定向测试全绿。

修复后补充

修法：_skip_on_group_check_failed 自愈分支在 recheck_fails.pop(h, None) 之后补 manager.ctx.state.save()，与 checking_meta.bump_recheck_fail 的写点即时落盘纪律一致 （周期落盘 state_save_interval 仍只作兜底，写点散落多文件故不做 dirty 插桩）。自愈判定、recheck 触发与规则结果不变；频率受当日失败上限约束，不引入写放大。

验证方式：新增 2 条用例 —— test_group_fail_selfheal_flushes_state（记录指向已完成成员 ⇒ pop 即落盘，save 恰调用一次且盘上无残留记录）、test_group_fail_no_selfheal_skips_save（记录仍指向 未完成成员 ⇒ 不 pop 不落盘，两路径对照）。两者直接驱动生产写点、不经跳检路径，避免跳检自身的 save_state 掩盖本处漏落盘。
