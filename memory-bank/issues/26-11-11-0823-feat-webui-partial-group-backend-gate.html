§01现象与发现场景

2026-11-11 「webui 部分组操作醒目预警」取证轮(计划 26-11-11-0820)发现: 前端三落点预警只覆盖 webui 这条路,而 /api/torrents/bulk 可被第三方脚本/旧 UI 直发,绕过全部前端确认 —— 请求 hashes 只含某辅种组的部分成员时:

  • action=delete + delete_files=true → 组内共享物理文件被删(api.torrents_delete 原样直发),同组其余成员必然缺文件;
  • action=location 且 relocate.enabled=off → 共享文件被 setLocation 搬走,同组其余成员仍指向旧路径,缺文件。

配置相关性: relocate.enabled=on 时 location 走整组迁移(_buckets 级联全组,无此洞);off 时直发才有。delete 与迁移开关无关,任何配置下都有此洞。

§03影响面

维度结论
触发条件POST /api/torrents/bulk,action=delete 且 delete_files=true(或 action=location 且 relocate.enabled=off),hashes 含某辅种组部分成员且未整组覆盖
影响范围同组未入选成员缺文件(不可逆,数据面);webui 主路径有前端预警兜着(计划 26-11-11-0820 落地后),API 直发路径完全无守卫
严重度高(数据破坏不可逆;但触发需 API 直发,webui 主路径有前端预警,非全网必现)

§05根因（可选）

已定位(非待查): bulk 通道按「平铺 hash 单次 API 调用」设计(docstring 明言 qB 端点原生接受批量),组维度只在 keys 模式级联展开,hashes 模式无部分组守卫 —— 属纵深防御缺口,不是行为 bug。

§06建议修法（可选）

在 _cmd_bulk_torrents 分派前加部分组闸: 对 delete_files=true 的 delete 与迁移关下的 location,逐 hash 查组归属,命中「部分组」(组内还有成员不在本次删除/移动集合)时:

  • 候选 A(倾向): fail-closed 硬拒 —— error 回执点名共存成员(「辅种组 X 还有 N-M 个成员未包含: 删除文件/移动会破坏它们,请改选整组」)。简单、数据安全优先;代价=既有第三方脚本若确有部分组删除意图会被拒。
  • 候选 B: confirm 二段回路(与整组迁移 confirm 同范式,confirm=true 放行)。向后兼容第三方;代价=加确认状态与回执分支。

keys 覆盖全组 / 成员全选 / 单成员组照常放行(与前端谓词 D2 同口径,守阵可对账)。实施时另行认领,与本报告状态机联动。
