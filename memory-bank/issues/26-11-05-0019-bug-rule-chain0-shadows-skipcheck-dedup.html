01现象与发现场景

发现于修复「跳检 dedup 闸门被 G3 遮蔽」（26-10-11-2045，计划 plans/26-11-04-2357 D1 拍板）时：ops 侧同构缺陷的规则侧镜像。触发条件：同一 hash 当日跳检成功过（种子必为已完成态），同日规则源再次触发跳检决策。

现象：规则源同日重跳不会走到 ops dedup 闸门（「今日已跳检过该种子(跨规则去重)」），而是在更靠前的 CheckAction 决策链 0 被以「种子非暂停中未完成状态, 无需校验」拦下。类别恰好同为 skip（无 web 批量分桶那种口径损伤），受损的是语义归因：去重的自解释文案与「统计只丢一次」的语义在规则源不可达。与平台/配置无关，纯逻辑顺序，必现。

02证据

A. 决策链 0 先于 ops 委托（rules/actions/checking.py:100-103，取证 2026-11-05 00:19）—— 链 0 判「仅暂停中未完成放行」，跳检成功后种子已完成 ⇒ 恒命中：

# 决策链 0: 只校验"暂停中未完成"的种子(跨种添加后的典型状态), 其余状态一律跳过:
# - 已完成(progress>=1, 无论状态): 已通过哈希校验, 重复 recheck/跳检无意义
if not (ctx.torrent.state_enum.is_stopped and ctx.torrent.progress < 1.0):
    return ActionResult.skip("种子非暂停中未完成状态, 无需校验")

B. dedup 单点在 ops 层（core/modules/ops_verdict.py，26-10-11-2045 修复后已排最前）—— 规则源经 skip_checking.py 一行委托进 ops，但必须先活过链 0：

# rules/actions/skip_checking.py: 委托入口
return ctx.manager.ctx.ops.skip_submit(ctx.hash, source="rule", ...)

C. 测试绕行实证（tests/test_checking_skip.py:193-196，取证 2026-11-05）—— 规则侧 dedup 用例必须手动还原 progress 才能走到去重闸门，注释明文「真机同理」：

# !保真替身下规则A跳检成功后种子已完成(progress=1) ⇒ rules 决策链 0 会先判"种子非暂停中
#   未完成", 走不到跨规则去重闸门 —— 真机同理。把进度还原为未完成以单独验证去重闸门本身
t.progress = 0.0

03影响面

维度结论
触发条件同一 hash 当日跳检成功过 → 同日规则源再触发；无配置依赖，必现
影响范围① 规则源同日重跳的拒因文案是链 0 的「非暂停中未完成」而非 dedup 的「今日已跳检过」；② 类别同为 skip，无 web 分桶式口径损伤（这是与 ops 侧 26-10-11-2045 的关键差异）；③ 保真替身下规则侧 dedup 闸门不可测（tests/test_checking_skip.py 依赖 progress 绕行）
严重度低（拦停行为正确、类别正确，仅文案归因与可测性受损）
