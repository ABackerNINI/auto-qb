01现象与发现场景

core/ 包变异测试审计 W1 轮（任务档案 26-10-08-test-mutation-audit 的 R25）坐实：_read_state_file__mutmut_3（encoding="utf-8"→None）与 _read_state_file__mutmut_6（丢 encoding 形参）两条同构变异在 origin/develop 全套件上 SURVIVED——测试宿主是 UTF-8 locale，读侧丢显式 encoding 后落到 locale 缺省仍是 utf-8，全套件分不出差异（确认型真洞，S4 判 SURVIVED 属预期）。

为何本单不是补测而是 bug 单：S5 补测尝试打桩非 UTF-8 locale 失败——CPython 3.13 的 open() 在 encoding=None 时走 C 层 locale 查询，monkeypatch locale.getencoding / getpreferredencoding 均不可达（实测打桩后仍按 UTF-8 读成）；子进程 PYTHONUTF8=0 方案依赖宿主 ANSI 代码页（cp1252 上 UTF-8 中文可能 mojibake 不报错、cp65001 宿主恒 utf-8），跨机不稳定，不硬凑假绿。

严重度高（一旦回归：生产机状态文件被误判损坏/读坏，且全套件无报警）

06建议修法（可选）

契约钉死：state 文件读写两侧都必须显式 encoding="utf-8"（不允许落到 locale 缺省）。守阵候选（按可行性排序）：

  • 静态守阵（textual guard，参照 tests 里既有源码文本守阵先例）：断言 _read_state_file 源码含 encoding="utf-8"——注意须挂 --deselect（mutmut 把变异体写进同一份文件，文本层守阵在变异轮基线即红，见 mutation-testing skill 硬约束 4）。
  • 行为守阵（若后续找到稳定打桩路径，如测试进程内以 subprocess + 受控 env 起真实 GBK locale，或 CPython 提供可注入点）：非 UTF-8 locale 下读 UTF-8 state 断言正常解析。
  • 根治面（若认领修码）：读侧 open(..., encoding="utf-8") 已是现状——本单的「修」是把守阵立起来，不是改代码。
