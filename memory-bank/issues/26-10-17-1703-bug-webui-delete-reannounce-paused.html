01现象与发现场景

2026-10-17 用户报告: 「WEBUI 删除种子时默认勾选的『删除前强制重新汇报』对暂停中的种子无效, 需要与右键『强制重新汇报』状态对齐」。当轮 grilling 八问收敛(用户答「按推荐」), 读源取证后的结论: 「无效」的真实形态不是「没汇报」而是「删不掉」——对暂停(及全部非活跃态)种子, 复选框保持默认勾选点删除时: reannounce 请求照发 → 后端命中第二道闸回 warn「种子非活跃」→ 前端 _reannounceAll 把 warn 判为不放行 → toast「汇报未确认…已保留未删除」→ 删除被整体中止。用户必须手动取消勾选, 才能删掉一个暂停种子。

触发条件: WEBUI 删除确认框(单种子 / 单组 / 批量 / 整集 / 抽屉 / 键盘删除六个入口均汇入同一条删除链 _deleteFlow)对任一非活跃态种子(pausedDL/pausedUP、stoppedDL/stoppedUP、queuedDL/queuedUP、checkingDL/checkingUP/checkingResumeData、error、missingFiles)执行删除, 且「删除前先强制重新汇报」保持默认勾选(硬编码 checked: true, 无任何状态感知)。与平台 / 配置 / 皮肤均无关(三套皮肤入口加载同一份 delete_flow.js), 纯前端编排缺陷。

03影响面

维度结论
触发条件删除确认框对任一非活跃态种子删除且 reannounce 保持默认勾选时必现——单种子全暂停最典型; 混选(1 活跃 + 1 暂停)与组目标全暂停同型。六个入口(delTorrent / delGroup / bulkDelete / delEpisode / _kbDelete / drawerDel)全部命中。
影响范围仅前端删除链(delete_flow.js), 右链四入口 / 键盘 Shift+A / 详情面板不受影响(2026-10-10 已接入两层)。症状是功能性阻断 + 错误归因: 删除被中止, 且 toast 把「种子非活跃(永远不可能有回执)」报成「汇报未确认」, 诱导用户以为 tracker 出了问题。混选时任一端非 ok 即整体中止——活跃端已投递的汇报也可能跟着白费。
严重度中(核心操作被不可能满足的前置条件阻断 + 误导性提示; 但有绕过路径——手动取消勾选, 且无数据 / 正确性损失)

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

机制已定位(读源 + grilling 取证, 非推测): 删除链是 reannounce-inactive-gate 专题「一条『不允许』必须接全部入口, 少接即形同虚设」(坑档 :15-20)所列入口清单中唯一漏接的入口。右链(右键四支 / 键盘 Shift+A / 详情面板)在 2026-10-10 已接入两层——闸门层 _guardReannounce(全非活跃拒绝 + 零请求)与投递层 reannouncePlan(混选收敛为活跃子集 + 报跳过数); 删除链两层皆无: 既不判目标活跃性, 也不把非活跃目标从投递集合中收敛掉。

次因(口径混淆): _reannounceAll 的 warn 桶把两种性质完全不同的 warn 一视同仁——「已受理·推迟中」(真 H&R 风险, plan 26-10-05-0923 v3 有意为之「warn 不放行删除」)与「非活跃·已跳过」(永久不可能有回执: libtorrent force_tracker_request 对 is_paused() 直接 return, 停止种子盲区见报告 26-10-05-0854 §附注)。后者本应算 skip, 现实是不放行, 于是「不可能的承诺挡了真实操作」。

已排除: ①后端判据 / 回执错误——commands.py 第二道闸语义正确且与右链同源, 缺陷在前端对 warn 的消费; ②「与 qB 行为差异」——qB 的 HTTP 端点侧本无门, 置灰只在 GUI(commit aa189a7), 真正的对齐基准是右链自己的两层而非 qB HTTP 端点; ③平台 / 配置 / 皮肤相关——三套皮肤入口均加载同一份 delete_flow.js, 纯前端编排。

2026-10-17 grilling 八问收敛(用户答「按推荐」)——以下为已拍板的修法方向, 认领后按此实施; 未认领前不动码。

  • D1 两层都修(对齐深度): 删除链同时镜像右链的闸门层与投递层——全非活跃时复选框禁用; 混选时复用 reannouncePlan 只投活跃子集。只修一层会留下「混选仍挡删除」的半残状态。
  • D2 全族判据: 复用既有判据(前端 reannounceBlocked / reannouncePlan, 后端 reannounce_blocked + REANNOUNCE_BLOCKED_STATES), 覆盖 paused/stopped/queued/checking/error/missingFiles 全族, 不新造「仅 paused」特例。
  • D3 全暂停时复选框形态: opt-pill 置灰禁用 + 取消勾选 + tooltip「目标均非活跃, 无法强制汇报」; 样式层真禁点击(不照搬菜单 item 的「置灰仍可点、行为层拦」——复选框点下去要有确定反馈)。
  • D4 H&R 边界: 「非活跃跳过」从 warn 降级为 skip——不挡删除; 活跃目标 tracker 拒绝 / 超时维持「不放行删除」的既有保守口径, 不借修 bug 之机放宽。
  • D5 跳过数可见: 对话框打开时 pill 上带说明(如「3 个暂停目标将跳过」)+ 汇报等待 toast 复用「跳过 N 个非活跃」——对齐坑档「跳过数要在等待态就报出来」。
  • D6 竞态两处兜底: 前端 reannouncePlan 收敛 + _reannounceAll 把非活跃类 warn(单种 REANNOUNCE_INACTIVE_SKIP / 组「均非活跃」)降级为跳过——只修前端, 「渲染到点击之间种子被暂停」的竞态窗口仍会复现本 bug。
  • D7 测试: ①静态守阵 test_frontend_reannounce_inactive_gate_wiring 扩段接线删除链 + node 电池加 probe; ②harness 命令泵(scripts/ui_harness.py:620-667)改为按 state 判活跃——暂停目标的 reannounce 回 warn 回执, 否则删除框 e2e 永远够不着 warn 路径; ③e2e 按目标 hash 断言(坑档口径: 不数条数): 全暂停 → 零 reannounce 请求且删除成功; 混选 → 只投活跃。
  • D8 流程: 本件即入池登记(已完成); 认领须用户指派, 未认领前不置 In Progress、不动码。
