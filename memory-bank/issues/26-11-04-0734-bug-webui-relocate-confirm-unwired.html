01现象与发现场景

真机（Windows）在 2026-11-04 07:17 从 WEB UI 发起一次整组迁移：选中 3 个 hash，归为 1 项。日志显示 ok 0 / confirm 1 / blocked 0，数据侧没有任何移动。用户侧观察是“点了移动、界面没有报错，但 qB 的 save_path 与磁盘都没变”。

  • 触发条件：整组迁移（同组多成员）被 evaluate_group 判为 confirm。当前执行路径中 confirm 的唯一来源是 plan() 提议「目录别名」：文件数 ≥ alias_file_threshold（默认 8）且内容根专属，或文件级链接建不出来（能力/长路径）但目录别名可建。
  • 本次具体子型未验证：是“文件数 ≥ 阈值”还是“长路径校正”，要拿预检 item 的 reasons[0].text 才能定。两者都是设计内需要显式确认的形态。
  • 平台相关性：长路径（≥ 260 字符）分支主要在 Windows 触发；但本缺陷（前端不弹确认）与平台无关，凡命中 confirm 的组都会复现。

已排除的假设

  • 不是 D 级证据/同机证明导致的 confirm：confirm 判定发生在 _ensure_probe 与 job 启动之前；同机证明相关分支只会产出 blocked 或 note，不会产出 confirm。因此 e19bace2（D 级证据容器判据修复）与本现象无因果关系。
  • 不是目标容量/冲突/未落定/未收尾/job 在途：这些条件都走 blocked 或 skip；日志里 blocked 0、幂等跳过 0。

03影响面

维度结论
触发条件整组迁移（含单种子移动）命中 plan() 的目录别名提议：文件数 ≥ alias_file_threshold（默认 8）且内容根专属，或文件级链接不可建（能力/长路径）但目录别名可建。非整组场景若仍走 set_torrent_location 也会同样命中。
影响范围WEB UI 抽屉「移动位置」与右键批量移动的整组迁移；所有命中 confirm 的组永远无法完成迁移——用户看不到确认框，也无法回传 confirm=true。目录别名路径（大文件组、长路径组）整体不可用。
严重度中。无数据损坏、无残留 job；但核心迁移功能静默失效，且前端提示「已执行」会误导用户以为成功。
用户可见后果对话框关闭 + 成功 toast + 零移动；日志只有一行 confirm 计数，无原因文本，用户无法自助判断。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已证实：后端 confirm 语义正确（目录别名必须显式确认才继续），但回执把 confirm 报成 status=ok；前端两个移动提交函数只认 r.ok，不消费 truth.summary，移动对话框也没有确认回路、未调用预检端点。两层叠加导致「confirm 被当成成功 + 无二次确认 + 无 confirm=true 重发」。
  • 已证实：_relocate_receipt 的 docstring 明确约定“confirm 给 ok + truth，由前端据 summary 开确认框”，但前端没有任何消费 truth.summary.confirm 的代码；/api/relocate/precheck 也没有调用方。
  • 已排除：同机证明/证据级别 D/B′ 不会产生 confirm（见 02「已排除的假设」），因此该缺陷与 e19bace2 修复无关。
  • 未验证：本次 confirm 的具体子型（阈值 vs 长路径）；运行实例是否已在 07:17 前重启到含 e19bace2 的版本（e19bace2 提交于 06:06:40，HEAD 04af5d4b 提交于 07:16:12，进程启动时间未取证）。版本问题不影响本缺陷的成立。
  • 未直接验证：用户浏览器确实弹了“已执行”toast（由代码路径可推得，尚未拿到前端截图/网络面板证据）。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

首选：按计划 26-10-18-1604 P5 补确认回路

  • 打开移动对话框时调用 /api/relocate/precheck（只读），把每组的形态（目录别名/逐文件链接/直搬）、目标、是否影响未来种子、拒绝原因摊开。
  • 目录别名组加显式确认（勾选/二次按钮）；确认后提交带 confirm=true，未确认不提交。
  • 回执为 confirm 时不要 toast「已执行」，改为“需确认”并保留对话框。

最低限度兜底（不做完整 P5 时）

  • _bulkEditPost / _editPost 读取 r.truth.summary.confirm：> 0 时不报成功，弹确认框（展示 results[].reasons[].text），用户确认后带 confirm: true 重投同一命令。
  • 后端契约可保持现状（ok + truth），但需在报告/约定里明确“前端必须消费 summary.confirm”；若希望更防呆，可让 confirm 回执返回专门的 needs_confirm 状态，避免任何调用方只看 ok 就误判。

守阵

  • 后端已有 tests/test_web_commands_bulk.py 的 confirm 计数用例；需补前端/契约层守阵：模拟 confirm 回执时不得弹成功、必须发出第二次带 confirm=true 的请求。

代价

首选方案涉及前端对话框 + 两个提交函数 + 一次预检调用，低-中；兜底方案只改两个提交函数，低。两者都不改后端判定语义。
