01现象与发现场景

发现场景: 2026-09-19 在给 issue 26-09-19-1939（乐观 UI 反应 2-4s） 做受控测量时撞见的 —— 测量脚本钩住 applyOptimistic 与 DOM，三条入口对照跑时发现： 整剧（show 级）暂停的补丁 0ms 就贴上了，但 DOM 里始终等不到 .is-pending。

触发条件: 追剧页右键剧行 → 「暂停整剧 / 开始整剧」。 剧行默认折叠（集行要展开才渲染），所以用户此时看不到任何即时反馈 —— 补丁贴了，但没有任何一个可见元素把它显示出来。

与 BUG-3 是同一批漏绑的第三处：BUG-3 修的是组行（辅种页）与集行（追剧页）， 剧行没人补。属计划外，本次未改。

02证据

绑定现状（prism/index.html，atlas/index.html 同构）：

# 剧行 —— 没有任何 is-pending 绑定(prism/index.html:650)
<div class="group-row show-row" data-table="show" :class="{ expanded: isShowExpanded(s.key),
     'search-hit': s.hit, selected: showSelState(s).selected, partial: showSelState(s).partial }"

# 集行 —— 绑了(prism/index.html:684, 即 BUG-3 修的那处)
<div class="group-row ep-row" data-table="show" :class="['s-' + epState(e), { ...,
     'is-pending': isEpPending(e) }]"

# 组行(辅种页) —— 绑了(prism/index.html:389, BUG-3 修的那处)
'is-pending': isGroupPending(g)

app.js 里也只有两个对应的 computed（isGroupPending 2333 / isEpPending 2340）， 没有 isShowPending。

受控测量的输出（钩住 applyOptimistic + MutationObserver 等 .is-pending）：

整剧 actEpisode() (补丁在 POST 之前): 「暂停整剧」→ 补丁 0ms / DOM is-pending 未出现

同一次测量里组行与集行都能在 4~8ms 内见到 .is-pending，只有剧行始终「未出现」。

03影响面与严重度

维度结论
触发频率中 —— 整剧暂停/开始是追剧页的高频动作（不是每次点击都发生，但一用就中）
影响范围追剧页剧级操作（暂停整剧 / 开始整剧）；剧行展开时 集行会显示 pending，所以只在折叠态（默认态）完全无反馈。与站点/配置无关
数据风险无。纯视觉标记缺失，命令照常执行、失败照常回滚
严重度中 —— 与 BUG-3 同类（定为「中」），但只在折叠态发生、且命令本身有效， 故不按「高」计；不修会让「整剧操作没反应」的观感一直留在追剧页

04根因（初步）

根因明确（不需要查）: 剧行模板漏绑 is-pending， 且 app.js 里没有对应的 computed（组行有 isGroupPending、集行有 isEpPending，剧行这一级当初就没做）。不是时序问题、不是数据问题 —— 测量已经证明补丁 0ms 贴上、命令也照常执行。

连带的一处（同构，别只修一半）: 剧行的状态色也是后端聚合标量 （与集行 e.state 同款）—— 集行当初为这个加了 epState(e) （成员在飞时按 STATE_RANK 现算，否则用后端真值）。剧行若只加 is-pending 而不处理颜色，会出现「行变灰了但颜色还是旧的」—— 与 BUG-3 修复前的集行完全是同一个形状。 两处要一起改。

05建议修法

只写方案，不在本报告里实施（计划外，等被某个计划认领）。

方案 A（推荐）: 补齐剧行的 pending 标记 + 状态色

  • app.js 加 isShowPending(s)（语义：该剧任一种子在飞；可复用 pendingAny 短路 + 收集该剧全部集成员的 hash —— 注意成员已是对象，取 hash 一律走 memberHashesOf，那条静态守阵会拦）。
  • 颜色：照 epState 的同一张表现算剧级状态（成员在飞时现算，否则用后端真值）， 别自造第二张优先级表（STATE_RANK 与后端 _SHOW_STATE_RANK 由守阵比对， 改一边必须改另一边）。
  • 模板：prism / atlas 两份的 .show-row 各加一行绑定（两处必须同步，否则双 UI 漂移）。
  • 代价：小。风险点：pendingAny 为 true 时才逐成员查，别把「逐成员」做成每帧 O(全集)。

方案 B（不推荐）: 只靠展开后的集行

剧行展开时集行确实会显示 pending。但默认折叠，用户点完整剧不会先展开 —— 等于没有反馈，不能算修。

验收（修的时候一并补）

冒烟现在只断言集行（ui_smoke.cjs “P0-3 整集乐观(集行 is-pending)”）， 需补一条剧行的：右键剧行 → 暂停整剧 → 剧行本身出现 is-pending （与集行那条同构，error 模式断言回滚）。

修复后补充

实际修法（方案 A）：app.js 新增 isShowPending(s) （isGroupPending / isEpPending 旁边）—— pendingAny 短路后 逐集复用 isEpPending(e)，命中即返回；hash 归一仍走 memberHashesOf， 不为这一层单开一套收集逻辑。prism / atlas 两份模板的 .show-row 各加一行 'is-pending': isShowPending(s)（双 UI 同步）。 冒烟补了一条剧行断言（原来只有集行那条）。

⚠ 一处与建议不同的改道（建议原文保留）：§04 说"剧行的状态色也是后端聚合标量， 要与 is-pending 一起改（照 epState 同款）"。实测不成立 —— 剧行根本不渲染状态色：.show-row 的 class 绑定里没有 s-*， 状态列渲染的是空占位 <div class="g-cat zero"></div>（实测行 class 始终为 group-row show-row，无 s- 前缀）。 ⇒ 只加 is-pending 即完整，"行变灰但颜色是旧的"这个连带问题不存在。 教训：先确认那一行到底渲染了什么，再照搬另一层的修法。

验证：单测 1054 passed / cov 92%；冒烟 50 项 0 失败 —— ok 模式（prism/atlas 剧行 is-pending 出现）与 error 模式（失败不留假状态）双双通过； 红绿双验：去掉剧行绑定后两条都 FAIL（"轮询 1.5s 内未出现"）。

两个排查期间的坑（值得记住）：
① 端口撞车：127.0.0.1:8099 当时被另一个 worktree 的桩服务占着， 我连上去的探针一直在测别人的代码（因此一度出现"atlas 通过、prism 失败"这种假象）。 判别法：起桩服务后先 curl 一眼确认它服务的就是本 worktree 的文件 （curl -s .../shared/app.js | grep -c <你的新符号>），再跑冒烟。 改用专属端口（8111 / 8112）后一切正常。
② 固定采样不可靠：整剧操作会把该剧全部成员一起补丁（桩里这一"剧"就有 1500 个种子）， applyOptimistic 逐 hash 扫表 ⇒ 成功路径 150ms 采样太早（假失败）； 失败路径因补丁贴在 POST 之前，要等回执回来才回滚 ⇒ 150ms 采样又太早（假阳性，实测 atlas 抓到过）。 故断言改成等条件成立：成功等 is-pending 出现，失败等 pendingOps 归零。
