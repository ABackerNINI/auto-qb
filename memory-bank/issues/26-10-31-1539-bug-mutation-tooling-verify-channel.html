01现象与发现场景

W2–W4 三轮 core/ 变异审计累积的 mutants 工具链坑 3 条(档案 R26/R27/W4 均「待入池」注记, 本件合并建账)。共同点: 都直接打击 mutants.verify 判定的可信度或造成误判, 与生产代码无关:

  1. mutmut 单文件轮清注册表 → 跨目标 verify 恒 APPLY_FAIL: mutants.run 每轮先 rm -rf mutants mutmut-cache.db, 该目录是 mutmut 的变异注册表, 单文件轮把其它目标的注册表一并清掉; 换目标直接 verify 时 mutmut 找不到变异体 → APPLY_FAIL。且 verify 对 APPLY_FAIL 只计数不自动续跑(收尾提示「重跑同一命令会自动重试」只提 TIMEOUT/FLAKY/UNKNOWN), 未判定会静默堆积。实证: R26(grid 16 条因注册表被清改走手工同构机械化, tmp-analysis/mut-core-w2-classify.md)。
  2. mutmut dump 伪 hunk 行号 + /mnt 空读假成功: dump 的 @@ 行号相对源码漂移, 拿它直接 git apply 大偏移搜索恒失败; 可靠做法=按 dump diff 定位唯一匹配行后整文件 post-image cp(S4 通道演进终点)。另: WSL /mnt/* 偶发空读使 GNU patch 静默 rc=0 假成功, apply 结论须以 post-image 通道复跑为准。实证: R27(档案「遗留/待入池」a/b 两条)。
  3. 全套件 flaky 集污染 verify 差集判据: relocate / web_views_reload / commands_engine wrapper / hr_discovery 绑定类用例随机红, verify 判据「新增失败 − 基线」会把这些当击杀信号。现有「复跑复现」门槛(FLAKY 判定)已挡掉误判——W4 S4 五条首轮记 FLAKY、复验全部落定未虚增假存活——但 verify 前仍须 deselect, 否则每条候选多一轮复验开销且日志噪声大。实证: R27(遗留 c)+ W4 S4(tmp-analysis/mut-core-w4-classify.md §S4)。
