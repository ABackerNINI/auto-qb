01现象与发现场景

排查「gtm 常驻进程一直在读写磁盘」时撞见：任务管理器里 pythonw.exe（PID 12016，命令行 -m gtm run --autostart）的 「I/O 其它」列数值很高，该列 tooltip 为「进程自启动以来生成的非读取/非写入 I/O 操作（例如控制功能）数」—— 是控制操作次数（累计），不是字节吞吐。

  • 进程：D:\Projects\auto-qb\tools\global-traffic-monitor\.venv 的 gtm，2026-10-19 12:21 启动，取证时已运行约 35 小时；数据目录 D:\Projects\auto-qb\tools\global-traffic-monitor\data。
  • 配置：数据目录内无 config.yml，全部走默认值 → sample_interval=5S、flush=1MiB/30S。
  • 触发：每次采样必现（默认 5 秒一轮，永不停止），与网卡数量正相关；与流量大小无关。
  • 同轮附带现象：state.json 与 history_traffic.dat 每 5 秒各被原子写一次（当前流量约 0.3 MB/s，1 MiB 落盘阈值每轮都达）。

03影响面

维度结论
触发条件每次采样必现（默认 sample_interval=5S，无 config.yml 时恒为该值）；次数与网卡数量正相关 —— 本机含 WSL / VMware / Hyper-V / 360 虚拟网卡，net_io_counters 只返回 4 个有计数的接口，但枚举过程仍遍历全部适配器。
影响范围仅 gtm 采样线程（_run_loop）。无数据落盘（读操作 0 次/秒；写 0.42 次/秒 = 设计值），无 CPU 占用（155 秒 / 35 小时 ≈ 0.1%）。影响面是可观测性噪音：任务管理器「I/O 其它」累计值巨大，容易被误读成磁盘活动（本次排查即因此走偏两轮）。
严重度低 —— 无功能、数据、寿命影响；纯内核控制调用开销 + 观感问题。若未来降低采样间隔（如 1S）则线性放大，届时会变成 CPU/内核态开销问题。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定位（有实测，非推测）：psutil 在 Windows 上枚举网卡走 IP Helper / NSI（GetIfTable2 / GetIfEntry2 → \Device\Nsi 的 IOCTL），这些控制操作按「其它 I/O」计次。复刻测得 net_io_counters(pernic=True) ≈ 100.8 次/调用、net_if_stats() ≈ 85 次/调用，一轮采样两次调用 ≈ 177 次；5 秒一轮 ≈ 35 次/秒（运行中进程实测 72 次/秒，约 2 倍差异见「证据 · 4)」待复验）。累计值随运行时长单调增长，故 35 小时后达 780 万次。

已排除：① 磁盘读写放大（读操作 0 次/秒，写 0.42 次/秒 = 设计值，与字节吞吐无关）；② 忙循环/死循环（CPU 0.1%、句柄 225 稳定）；③ 文件句柄轮询或日志刷盘（数据目录无日志文件，endpoint.json 自启动后未再写过）。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向：减少每轮的控制操作数，或降低轮次频率。三个候选，代价递增：

方案做法收益代价 / 风险
A. 调大间隔（零代码）设置页「读后写」把 sample_interval 调到 30S控制操作线性降 6 倍（约 12 次/秒）；写盘也降到约 2 次/分钟采样粒度变粗（跨天/重置判定延迟 ≤ 30s），流量曲线更粗糙；不改代码但改变用户可见行为
B. 缓存网卡状态（小改）read_stats() 结果按 N 轮（如 12 轮 = 60s）缓存，仅定期刷新 isup每轮省 85 次（约一半）网卡 up/down 变化感知延迟到 N 轮；AdapterFilter 的 down 过滤语义变为「最多陈旧 60s」，需在文档写明
C. 合并为一次枚举（大改）ctypes 直调 GetIfTable2 一次取全量（counters + OperStatus），替掉两次 psutil 调用每轮降到约 100 次以内，且不再依赖 psutil 版本实现引入平台专有代码（Windows-only 分支）；Sampler 的注入点/NicIo 协议与单测替身要重做；三平台需分别验证

倾向：先用 A 止血（用户可自助），若后续确实要更细粒度再评估 B；C 只在需要跨平台统一口径时值得做。
