01现象与发现场景

撞见场景: 用户在评审 hr-fault-domain 计划时提出部署形态 —— 「auto-qb 配置在 NAS 里, 通过 WebUI 访问, 浏览器扩展不装在 NAS 中而装在外部 PC」(2026-10-09 会话)。核实后确认: 该形态下 HR 取数功能整体不成立 —— 扩展填 127.0.0.1:8788 会解析到 PC 自己的端口, 连不到 NAS 上的后端。

触发条件: 只要「后端实例」与「装了扩展的浏览器」不在同一台机器上, 必现。与配置开关无关 —— 端点主机在两端代码里都被写死为回环, 不是配置项。

用户判定: 这是设计缺陷(而非可接受的边界), 要求未来支持「外部扩展 / 跨机」形态。本件为记录, 详细方案另立计划(专题 hr-channel-remote)。

03影响面

维度结论
触发条件后端实例与「装了扩展的浏览器」不同机 ⇒ 必现(与任何配置开关无关; 两端都在代码里写死回环)。
影响范围HR 取数的「驱动」路径整体不可用 —— 跨机形态下后端下发不了任务、取不回数据, HR 在线核实退化为「未核实」。不影响: 同机部署(现状默认形态)完全不受影响; 站点解析 / 判定 / 报告 / WebUI 均与通道主机无关。NAS 类实例的既有替代路径是 hr_check.shared_dir「只读共享数据」。
严重度中 —— 不阻塞现状部署; 但封锁了一类合理部署形态(单一 NAS 集中管理 + 外部机器提供浏览器态), 且用户明确判定为缺陷并要求支持。

05根因（可选）

这不是"待查"级的未知缺陷, 而是设计上的显式取舍 —— 只是该取舍被用户判定为不可接受。

非回归、亦非疏漏: 两端都是显式写死回环 —— 后端连 host 配置键都不给(写了报未知键), 扩展 normalize.js 直接抛错; 扩展注释里还点名了这个场景(「填别的机器(含 NAS 上的实例)连不通」)。即设计者当时主动排除了跨机形态, 并以「走只读共享数据(hr_check.shared_dir)」作为 NAS 的替代路径。

已排除: 不是网络/防火墙问题(扩展在本地校验阶段就被拦下, 根本发不出请求); 不是 token / origin 配置问题(还没走到鉴权那一步); 不是平台差异(两端注释均已确认是有意为之)。

06建议修法（可选）

方向: 让「端点主机」成为可配项, 放开扩展侧的非回环校验; 同时正面重评由此扩大的安全面。经核实, 核心安全资产在跨机后仍然成立 —— 端点 URL 白名单在下发任务时卡死(channel.UrlPolicy), 端点本身不接受任何 URL 入参 ⇒ 它不是「带登录态的任意站代理」(README §安全边界)。故攻击面扩大有限, 但仍需论证。详细设计见另立计划(专题 hr-channel-remote); 本件只记方向:

  1. 后端: 新增 hr_check.channel.host 配置键(默认 127.0.0.1 保持保守), 同步进 KNOWN_HR_CHANNEL_KEYS / schema/hr.py / validate_config; runtime 把 host 传给已有的 HrChannelServer 形参。
  2. 扩展: normalize.js 放开非回环主机(建议限定私网段 / 显式白名单, 而非任意公网); manifest.json 静态 host_permissions 之外, 需在保存时用 chrome.permissions.request 申请远端端点 origin(现仅申请站点 origin)。
  3. 传输安全: 端点现为明文 HTTP, 跨机后 token 在 LAN 上可被嗅探 —— 需拍板(TLS 自签 / 反代 / 或明确「仅受信 LAN」假设 + token 轮换)。
  4. 鉴权加固: 401 无节流(与 hr-fault-domain 计划的 P4 同源); 跨机后变成可远程触发的刷屏 / 爆破面, 需一并加节流。
  5. 文档: 扩展 README 排障表、hr-fault-domain 计划的「设计边界」段落需同步改写(该段落把此形态写成"受支持 = 不驱动扩展", 与本次口径冲突)。
