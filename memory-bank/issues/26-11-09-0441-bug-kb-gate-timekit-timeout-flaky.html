§05根因（可选）

入池时 (2026-11-09 04:41) 的候选，保留原文：待查(已排除: timekit 自身慢 —— 单跑/并发/venv python 全 4-10s; 锁 —— 脚本无锁无 stdin; WindowsApps python 存根 —— Popen 实测 4.2s)。候选: ①双层 commit.py 各起一套 gate 并发扫描 + clone2 满载 → 单脚本被拖过 60s(观测到饥饿形态支持); ②某层进程被另一层看门狗杀树波及后 0 CPU 冻结(观测到冻结形态支持); 两者可并存。方向: 认领时先复现(满载机 + 连续提交), 再定 timeout 抬升 / 去重双层 gate / 冻结进程处置。

认领轮结论 (2026-11-09 05:26)

定性（高置信）：不是 timekit 自身缺陷，也不是锁 / stdin / 扫描路径 / 快照 env 漂移，而是固定 60s 超时 × IO-CPU 密集型全库扫描 × 并发放大 × 满载机的组合。空载下 60s 有十余倍余量；本机对「并发污染下的 CPU/IO 型任务」放大特别狠（同族坑档实测过同一命令 15.94~209.77s 的漂移），余量被吃光后即判死。波动大 ⇒ 复跑可过、负载相关，与「5 投 4 超、第 5 次自过」一致。

可直接验证的事实

  • 工作量：timekit --check 对 memory-bank 全库（2838 文件 / 31.5 MB）做两轮 rglob 并逐文件 read_bytes() 读全文 + 逐行正则（check_metadata 与 check_body 各一遍）；热缓存单跑稳定 4.1~4.3s，冷缓存 / 有负载 9.6~12.6s。
  • 并发放大：A/B/A 干净对照 —— 单跑 4.32/4.32s → 4 路并发同一脚本 14.19/14.35/14.35/14.23s（3.3 倍）→ 撤掉负载 4.28/4.28s。放大来自并发争用，不是脚本自身变慢。
  • 链路结构：一次提交最多两轮闸门（提交前 + rebase 合入远端后复跑）；kb 链 9 条脚本几乎各自扫全库；真实并发上限 GATE_WORKERS = 4（档案里「9 路并发」是对照组手工实验）；timeout = 60 逐 job 独立计时、固定值、无自适应 / 无重试；失败按提交序收集取 failures[0]，故恒报第 7 条只是排序结果。
  • 失败形态：「超时 60s (进程树已杀)」来自 run_capture 的 communicate(timeout=60) 超时分支 ⇒ 子进程已启动、60s 未退出或管道 EOF 未到，不是 Popen 卡死分支。观测到的「CPU 缓慢增长 / 恒 0 CPU」= 等 IO / 等拦截 / 杀树后未收干净，不是死循环。
  • 已排除：快照 env 改变扫描范围（plain 4.16s vs snapshot-env 4.27s）、锁 / stdin、timekit 自身慢、WindowsApps python 存根（档案既有排除）；真实 run_gates 4 池跑整条 kb 链本轮 5.23s 全绿。

对入池推断的校正

  • 代码上只有快照副本层跑 main()：commit.py 的 __main__ 先 maybe_respawn 复制整包再 subprocess.call 重入，原包父层阻塞等待、不跑闸门 ⇒「双层 commit.py 各起一套 gate」与代码不符。
  • 进程观测到的两个 commit.py（不同父进程树）更可能是「连续重跑的两次 ship.commit」；两个 timekit 并存最可能是上一次超时被 taskkill /F /T 杀树后残留的冻结进程 + 本次重跑新起的进程，也不排除同机其它 clone 的提交。下次复现请采每个 timekit 的 ParentProcessId 链与创建时刻，判是否同属一个 cmd.exe 树。
  • 「9 条脚本共享 timeout = 60」是配置层表述；执行层每条 job 各 60s，且 pool.map 先按配置序提交全部 job，第 7 条 timekit 在 4 池里排到第二波才启动 —— 排队不吃自己的 60s，但排队期间其它全库扫描已把 IO/CPU 打满。

仍待证（需满载机现场，勿当结论）

  • 冻结进程的确切产生机制（杀树后管道读线程 / 孙进程残留），需进程树快照 + 创建时刻。
  • 04:41 那批是否真的触发了合流后第二轮闸门（需当时的步骤行 / 提交日志）。
  • 系统层文件拦截是否在该时段重新出现（perf-measurement.md 记为已治好，但当时负载形态异常）。

§06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

以下保留入池时的修法方向原文。2026-11-09 grilling 四问已由用户按推荐拍板（D1–D4），方案定稿见 memory-bank/plans/26-11-09-0559-plan-memory-bank-kb-gate-timekit-timeout.html：主线 = 按改动收窄 timekit / check_html + 复跑清单扩面 + 展开长度守卫，不动并发模型与 timeout；本件仍 In Progress、未实施。

  1. 分档 timeout：kb 链 60s → 180/300s，或按脚本类型分档（全库扫描类单独档）。代价：真挂住时失败反馈更慢；只挪阈值，不消除放大。
  2. 减少重复全库扫描：9 条脚本各扫一遍 → 合并成一次遍历或聚合 kb.check 单入口（覆盖面由 test_commit_gate_covers_kb_check 守阵钉住）。代价：改脚本与守阵，聚合后失败定位粒度变粗。
  3. 降并发 / 重型独占池：全库扫描类 job 不互相并发（这类 GATE_WORKERS 降为 1，或给重型 job 独占池）。代价：闸门墙钟变长但尾部更稳；与计划 26-11-01-0434 方案 B 的并发收益要重新权衡。
  4. 杀树收尸：run_capture 超时后显式关管道、join 读线程、登记残留 pid，给出可核查的清理路径。代价：Windows 管道 / 孙进程语义复杂，容易引入新的挂死形态（见 parallel-run.md）。
  5. 失败重跑入口：超时给一次自动重跑，或提供「只重跑该闸门」入口，避免整条 ship.commit 重跑又付一整套 gate。代价：与「保守默认」冲突，须显式配置且只对这类超时生效；幂等性要单独论证。
