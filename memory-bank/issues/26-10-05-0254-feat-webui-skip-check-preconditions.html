01现象与发现场景

WEBUI 的跳检(右键 / 批量)对已完成的种子也照做 —— 会被删种重加、本地统计清空; 而规则侧跳检不会, 因为规则侧的决策链第 0 条明确「只校验暂停中未完成的种子, 已完成一律跳过」。

  • 差异来源: WEB 入口绕过了规则决策链 —— webui/commands.py:355 直接调 ctx.ops.skip_check(hash, source="web"), 只过 ops 层的两道闸门(部分下载禁止 + 同日去重), 不经过 rules/actions/checking.py 的决策链 0/1/1.5/1.6。
  • 用户要求: 跳检需补前置条件, 例如「已完成的种子不能跳检」; 且具体还有哪些前置条件需专项分析(本单含一份候选清单, 见 06 节 —— 清单是待分析方向, 不等于已确认结论)。
  • 已具备: 前端 danger 确认框(drawer.js:276 skipCheckMulti)与配置开关 web.skip_check_menu 已落地, 缺的是「该不该允许」的判定。

03影响面

维度结论
触发条件WEB 右键 / 批量跳检任意种子即触发。种子已完成(progress=1)、正处于做种中、或组内有活跃下载成员时, 均不会被拦 —— 行为与规则侧口径相反。
影响范围单种跳检 commands.py:349 与批量跳检 commands.py:702 (_bulk_skip_check_via_ops) 两个入口; 规则源跳检不受影响(它先过决策链)。前端入口见 04 节。
严重度中(偏上)。跳检必然清空本地统计(上传/下载量、做种时间), 且对已完成种子零收益(哈希早已通过); 误对做种中种子执行还会短暂中断做种。数据本身不丢(文件保留), 但统计不可逆 —— 是否可接受需拍板。

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

待查。已排除: ①「ops 层漏搬闸门」—— 看起来是有意收敛: ops 只放与安全直接相关的两条(部分下载会产生垃圾数据、同日重复零收益), 而「该不该校验」属规则语义; ②「单发入口有、批量入口没有」—— 两个入口最终都汇到同一个 ops.skip_check。合理怀疑: 从 rules 迁到 ops 时只搬了闸门, 决策链 0/1 被有意留在 rules 侧, WEB 直连入口因此少了这层判定。
