§03影响面

维度结论
触发条件宿主时区含夏令时(如 America/Los_Angeles)且用例构造的日期跨 DST 切换日(美国: 3月第二个周日 / 11月第一个周日)时必现; 无 DST 时区(Asia/Shanghai / UTC)永不触发
影响范围仅测试面: tests/test_hr_ratelimit.py 中依赖 _ts() 助手与 naive 本地时间的窗口起点组用例(同文件其它组用例若同样跨切换日构造, 换 DST 宿主同形); 生产代码 window_start_on 在 DST 日的 1h 墙钟差是限速曲线域的正常语义, 非产品缺陷
严重度低 —— 不挡 Windows/CI 两侧(恒绿), 只在 DST 时区宿主(第三个开发环境类)假红且恒红(构造日期硬编码, 不修就一直红, 与当前日期无关)

§05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

用例隐含「宿主时区无夏令时」假设, 违反 file-conventions「不依赖宿主环境能力」的既有约定: _ts() 助手与实现侧 window_start_on 各自把墙钟时刻经宿主 TZ 解析成 UTC 瞬间, 在 DST 切换日两侧对同一墙钟解析出相差 3600s 的瞬间(实测 1772985600.0 vs 1772982000.0), 断言恒红。已排除: 非 master 落后(develop 上该文件 2026-11 零改动)、非并行/时序 flake(-n 0 单跑 100% 复现)、非代码回归(TZ=Asia/Shanghai 同树即绿)。

§06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

方向: 用例内固定时区, 不改生产代码。候选:
  • A(推荐): conftest 或用例级 monkeypatch os.environ["TZ"] = "Asia/Shanghai" + time.tzset()(POSIX 原语; CI 本就 UTC, 加固定后三侧语义一致), 覆盖 _ts() 与实现两侧 —— 一处固定全文件受益。代价: 需注意 Windows 上 time.tzset() 不存在, 固定手段要按平台分支或仅 POSIX 生效(Windows 侧本来就无 DST 假设问题)。
  • B: 把 _ts() 助手改为显式固定偏移(如 datetime(..., tzinfo=timezone(timedelta(hours=8))).timestamp()), 不动环境变量。代价: 只修测试侧, 实现侧仍随宿主 TZ 解析 —— 若实现内部也跨切换日解析墙钟, 两侧仍可能分裂, 需先核 window_start_on 内部实现是否同样依赖本地墙钟。

两者都属测试面小改; 认领时先复验本锚点, 按 file-conventions「平台相关测试必须固定, 不依赖运行环境」执行。
