01现象与发现场景

W1 清偿实施 issue 26-10-01-2335（HrEntry.last_seen 补写入点，提交 54db09f2）补测试时发现：测试构造放行记录时用空锚点对象绕开了「对已 verified 的 infohash 重复签发」的场景。复读 _sign_releases 函数体确认 data.verified[h] = _release_record(...) 是无条件整条赋值，对 h 已在 data.verified 的情况不查重，既有放行记录的 source / verified_ts / 锚点快照会被整条换掉 —— 与函数 docstring 自述的「放行永续有效(终态不可逆)」语义冲突。生产路径上「已 verified 的 infohash 再次进入 unmatched」是否可达未核实，故记为疑点而非定论。

02证据

# src/auto_qb/hr/service.py:1190-1210（取证 2026-10-02 05:26, 基线 54db09f2 工作树）
def _sign_releases(site: str, data: HrSiteData, lane_states, wave: _WaveContext, unmatched, now: float) -> int:
    """批量「未列出」放行签发(§3.2 行 3 / §4.2 停翻后): 覆盖范围内未命中的未对账对象。
    每个对象要过: 各档缺席证明(全深度 或 可信完成时间位置被覆盖) + 新鲜度闸门(added_on
    不晚于该档本波取数时刻)。放行永续有效(终态不可逆); 锚点快照供本机重下作废用。"""
    signed = 0
    for h, anchor in unmatched.items():
        if h in wave.hits:
            continue
        if not _absence_proven_all(lane_states, wave, anchor):
            continue
        data.verified[h] = _release_record(   # <-- 对 h 已在 data.verified 不查重, 直接整条覆写
            infohash=h,
            tid=wave.dl_by_hash.get(h, 0),
            verified_ts=now,
            source=SOURCE_NOT_LISTED,
            anchor=anchor,
        )
        signed += 1

循环守卫只有 h in wave.hits（本波命中跳过）与缺席证明两道，均不排除「h 已被前波放行」；赋值发生时旧记录的 source（可能非 NOT_LISTED）/ verified_ts / 锚点快照全部被替换。

03影响面

维度结论
触发条件unmatched（未对账对象集）里出现已在 data.verified 的 infohash 且通过缺席证明。生产可达性未核实（_build_objects 构造 unmatched 时已排除终态/已放行，则不可达；若锚点漂移/换 tid 等路径可让已 verified 的 h 回流 unmatched，则可达）。
影响范围HR 放行记录（verified 层）的 source / verified_ts / 锚点快照；若覆写发生，「本机重下作废」的锚点对照基线随之漂移，放行判定正确性受影响。
严重度中（疑点级 —— 可达性未证实；若可达则违反「终态不可逆」设计语义）。

05根因（可选）

待查 —— 先核实生产可达性：_build_objects 构造 unmatched 的排除条件（终态/已放行/超额不出对象集）是否在所有路径下都能挡住已 verified 的 infohash 回流。

06建议修法（可选）

待定。两个方向按可达性结论二选一：① 若可达 —— 签发前对 h in data.verified 跳过（或按业务语义决定保留策略：首次放行优先）；② 若不可达 —— 补一条守阵测试钉住「unmatched 不含已 verified infohash」这一前提，防止未来重构破坏该不变量。
