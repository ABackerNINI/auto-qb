怎么撞见的：2026-10-11 修 GitHub Action 全量 e2e 那 34 条文案漂移(CI 日志 R:\Download\github action报错.txt)时的副产物 —— 改完 4 个 spec 后按收尾 DoD 跑全量 e2e(等价于 CI 那条 npx playwright test)核对是否有回归，34 条文案红全部转绿，但多出这一条红：e2e/delta-sync.spec.mjs:170(皮肤 prism)的收尾断言「lastRid 置空后下一轮为全量(full=true)」在 8s 轮询窗内没取到 full=true。

平台与配置：Windows 本机(chromium headless)，桩服务单实例长驻(scripts/ui_harness.py，端口 8137，种子 300 / 组 150)，模式组合为默认 E2E_CMD_RESULT=ok / E2E_SKIP_CHECK=on / E2E_HR_SCENE=on(即 CI 的默认组合)。未在其他模式轮(error / hang / off / empty / 3000 种子)上验过。

为什么判定与本次文案改动无关：该用例所在文件在 Playwright 文件序上排在本次改动的 4 个 spec(menus / multiselect-shows / optimistic / trigger-scope)之前，且本次改动一行 delta-sync.spec.mjs 都没动(git diff --stat 可证)。

03影响面

维度结论
触发条件仅在全量 e2e 顺序下偶发(168 条跑满时出现过 1 次)；单文件隔离重跑恒绿，CI 默认轮亦通过。默认桩组合 ok / skip-check on / hr-scene on / 300 种子
影响范围只影响 delta-sync.spec.mjs:170 这一条用例的收尾断言(「lastRid 置空 ⇒ 下一轮 full=true」)；不影响 applyStateRows 前半段的 11 项行级语义断言(那部分当次全绿)，也不影响生产代码
严重度低 —— 属观测位抖动而非功能回归；但它会让「改完东西跑全量 e2e 收口」这一步出现假红，污染回归判断(本次就被迫多花一轮排查来撇清)

写「符号名 + grep 关键词 + 当时的行号（标取证时间）」—— 代码会漂移，靠符号与 grep 重新定位，行号只是加速项。

  • e2e/delta-sync.spec.mjs:94-117(取证同上)· 探针 armDeltaProbe / deltaRounds · grep window.__d —— 给 vm.applyStateRows 装记录器，每轮合并 push 进 window.__d.rounds
  • src/auto_qb/webui/static/shared/polling.js:206-232(取证同上)· 生产侧 lastRid 生命周期 · grep lastRid / rid= —— lastRid !== null 才带 rid= 查询串；收到 state.rid 回填
  • src/auto_qb/webui/static/shared/state.js:169(取证同上)· lastRid 初值 null = 强制全量
  • 候选嫌疑面(未验)：polling.js 轮询节奏与vm.refresh() 叠加时的「踢一次」纪律 —— 用例注释自承「在轮询循环里反复踢会堆叠请求链」，全量轮里前置用例留下的请求是否在飞行中未知

05根因（可选）

默认「待查」—— 不为填单做分析。有结论才写；不确定就写已排除的假设，不要把猜测写成结论。

已定案（2026-10-15，代码走读 + 确定性竞态探针双证）：断言语义与用例本身都没坏，坏在判据读的是「探针记录的最后一轮」，而轮次到达顺序在全量 e2e 顺序下不可控。链条四环：
① polling.js refresh()(static/shared/polling.js:202-268)按发送时刻读 lastRid，lastRid !== null 才带 rid=(:211)；轮询链 scheduleNext() 只在每轮 refresh 末尾续排(:106-110/:268)，手动踢一次不取消在飞请求 ⇒ 踢出的无 rid 请求与在飞的旧 rid 请求并发，落袋先后不保证。
② 服务端 runtime.py _reduce_delta(webui/runtime.py:1489-1514)：rid 缺省/0 或 rid>ver → 全量(:1509-1510)；0<rid<ver（在飞请求的 rid 被后来的 ver 超过）→ 增量载荷 full=false + updated=true ⇒ 该响应经 applyStateRows 落袋、被探针记为 full=false 轮。
③ ver 抬升来源 = 桩命令泵/回弹（scripts/ui_harness.py 的 _apply_truth/_publish_with_delta/_restore_state，真改 pause/resume 并 bump 版本）。全量 e2e 是串行（playwright.config.mjs workers:1）但共享同一长驻桩：前序用例（含本文件第 1 条的真暂停手势）的真值版本与回弹可在本用例收尾阶段附近落 ver bump ⇒ 本用例在飞的旧 rid 请求过期成增量轮；若它晚于全量轮落袋，「最后一轮」就停在 full=false。
④ 旧断言读 window.__d.rounds[length-1].full（最后一轮），只要 8s 窗内末轮是 full=false 即红。而踢出的请求不带 rid ⇒ 全量轮必然落袋 —— 末值判据把「必然发生的全量轮」与「可选的迟到增量轮」混进同一个读法。隔离重跑时窗内没有 ver bump（回弹已过窗），末值恒为 full=true ⇒ 恒绿。
探针实证（2026-10-15，一次性探针 spec，跑完已删）：等全量轮落袋后注入一次迟到增量轮 ⇒ newRounds=2 lastFull=false someFull=true，旧判据确定性假红、存在性判据不受影响。
已排除：①本次文案漂移改动 —— delta-sync.spec.mjs 一个字没改(git diff 可证)，且它在文件序上排在被改的 4 个 spec 之前；②断言语义写错 —— 同一条断言隔离重跑恒绿，且在 CI 默认轮里也通过；③applyStateRows 的行级语义坏了 —— 同一用例前半段 11 项(upsert 替换 / 追加 / removed 剔除 / 数组新实例 / 未脏行引用恒等)全绿，只有收尾「等到一次全量轮」落空。

06建议修法（可选）

方向 + 候选方案 + 各自代价；没有想法就留「待定」，只写方案，不在本报告里实施。

  1. 先定性再动手(低成本)：连续跑若干次全量 e2e 统计该用例的红率与皮肤相关性(prism 先红、atlas 绿，可能只是执行先后而非皮肤差异)。
  2. 把「等一轮全量」改成确定性等待：断言前先等 window.__d.rounds 长度自增(新的一轮已落到探针)，再读最后一轮的 full —— 现写法直接读「最后一轮」，可能读到的是注入前那一轮的历史值。
  3. 或放宽观察窗：把 8_000 往上抬。代价是全量收口变慢、且掩盖真问题，所以优先级低于方案 2

以上均为候选，未实施 —— 按 skill 口径，入池不改码。

实施说明（2026-10-15 认领后）：采纳方案 2 的强化版并说明改道原因 —— 方案 2 字面形式「先等 rounds 长度自增再读最后一轮」仍对到达顺序敏感：第一个新轮可能恰是那个迟到的增量轮(full=false)，末值照旧假红。实际落地为存在性判据：快照踢出前的轮数，轮询等待「踢出之后落过一次 full=true」—— 踢出的请求不带 rid，服务端恒回全量，该轮必然落袋；迟到增量轮落在它之前或之后都不影响判定。方案 3（抬 8_000）未采用：掩盖真问题且拖慢全量收口。方案 1 的统计被确定性探针替代（见根因段）。
