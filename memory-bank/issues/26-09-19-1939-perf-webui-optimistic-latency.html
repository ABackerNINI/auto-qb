01现象与发现场景

发现场景: 2026-09-19 用户真机走查 —— 这正是「WEB UI 操作跟手性优化」三波次 (tasks/26-09-19-webui-responsiveness.md) 里唯一剩下的待走查项。用户原话: 「目前乐观 UI 已生效, 但反应时间太长, 估计 2-4 秒左右, 远比设计的要长」。

已生效的部分: pending 半透明、状态色翻转、失败回滚都正常 —— 说明 P0-3 链路本身是通的, BUG-3(组/集行没接乐观)已在复核第 2 批修掉, 本条不是它。

设计目标(对照口径): 该任务的决策 2 写明「主观延迟的主因是 沉默 不是慢」, 因此 P0-3 乐观 UI 的定位是点击即变、不等网络(亚 100ms 级); 后端加速只负责把真值对齐压到百毫秒级。 前端埋点阈值就是按这个定的 —— waitMs > 100 或 totalMs > 400 即打 [perf](app.js:2257-2261)。真机 2~4s 是这个阈值的 5~10 倍。

触发条件: 真实 qB 数据下(大库)的种子页单种子右键、辅种页整组右键。 本地复现不出来: scripts/ui_harness.py 的 FakeClient 与 ui_smoke.cjs 里 POST 都是本地瞬时返回(冒烟断言「点击后立即可见 pending」恒绿), 所以这条缺陷在设计、实施、冒烟三道关口都没被拦住 —— 只能靠真机肉眼发现。

⚠ 口径待确认(开工第一步): 用户说的「反应时间」可能是 ① 点击 → 行变灰/变色(乐观补丁生效)、也可能是 ② 点击 → toast 出「已执行」(端到端)。 两者根因不同、修法不同(见 §04 假设表 H1/H3 vs H2/H5)。先量再改, 别凭猜测定方案。

02证据

证据 1: 4 条乐观入口里有 2 条把补丁放在 POST 之后(原文)

先贴补丁的两条(顺序正确, 与「点击即变」一致):

// app.js:2864-2870  actEpisode() 整集/整剧
this.applyOptimistic(hashes, action);      // 2865: 先贴
const resp = await this.api("/api/torrents/bulk", { method: "POST", ... });

// app.js:3089-3094  批量 act() bulk 入口
this.applyOptimistic(hashes, action);      // 3089: 先贴
const resp = await this.api("/api/torrents/bulk", { method: "POST", ... });

先发请求再贴补丁的两条(顺序错误, 恰好是种子页/辅种页最常用的两条):

// app.js:2353-2371  act() 整组(辅种页主路径)
const resp = await this.api(`/api/groups/${this.menu.key}/${action}`, { method: "POST" });   // 2358 先发
...
this.applyOptimistic(hashes, action);      // 2368 后贴 —— 「点击即变」被网络往返 gate 住
const r = await this.waitCmd(resp.cmd_id);
this.resolveOptimistic(hashes, r.ok);

// app.js:3314-3329  actTorrent() 单种子(种子页主路径)
const resp = await this.api(`/api/torrents/${this.menu.hash}/${action}`, { method: "POST" }); // 3319 先发
...
this.applyOptimistic(hashes, action);      // 3327 后贴 —— 同上
const r = await this.waitCmd(resp.cmd_id);
this.resolveOptimistic(hashes, r.ok);

只要 POST 慢, 这两条路径的「即时反馈」就整体推迟 —— 乐观的前提是不等网络。

证据 2: 命令 POST 没有超时、也没有打点(盲区)

// app.js:1324-1331  _request(): 命令投递走裸 fetch
const resp = await fetch(path, { ...options, headers });

// app.js:2243-2263  waitCmd(): 埋点只从「回执」开始算, 不覆盖「点击 → 投递」段
const start = Date.now();
...
this.cmdStats = { totalMs: Date.now() - start, waitMs: r.wait_ms, execMs: r.exec_ms, cmdId };

即: 现有 cmdStats 只量「回执段」(wait_ms/exec_ms/端到端), 「点击 → POST 返回」这一段完全没有消费者 —— 真机慢 2-4s 在日志里是看不见的, 这也是为什么只能等用户肉眼报。

证据 3: 3s pending 兜底从 POST 返回才开始计时, 慢 POST 会吃掉兜底窗口

// app.js:2280-2288  isPending(): ts 由 applyOptimistic 写入(Date.now())
if (Date.now() - op.ts > 3000) { delete this.pendingOps[hash]; return false; }

POST 若耗 2s, 贴补丁时兜底窗口只剩 1s; 而真值要等下一轮 /api/state (>3000 种子时前端 3s 才取一次, 见关联 issue webui-poll-cadence-mismatch)。 结果就是「晚了才变过去 → 1s 后弹回陈旧真值 → 下一轮才对」的抖动, 观感比单纯慢更糟。

最小复现 / 测量步骤(不改码即可量)

1) 真机 + 真实 qB(3000+ 种子), 打开种子页 / 辅种页
2) F12 → Network 面板保留日志, Performance 面板开录制
3) 右键任一行 → 暂停, 肉眼盯「行变灰(is-pending)」的时刻
4) 读三个数:
   T1 = /api/.../pause 的 Timing(TTFB / Waiting)   ← 判 H1(POST 慢)
   T2 = 控制台 [perf] 行的 排队 wait_ms            ← 判 H2(命令消费慢)
   T3 = Performance 里点击后最长的一个 Long Task   ← 判 H3(渲染慢)
5) 同时记录 toast「已执行」出现的时刻              ← 判用户指的是 ① 还是 ②(H5)
6) 对照: 在同页面点一次「整集暂停」(补丁先贴)看是否仍然慢 —— 若显著更快, H1/顺序问题基本坐实

03影响面与严重度

维度结论
触发频率每次点击(pause/resume 是日常最高频动作), 不是偶发
影响范围种子页单种子右键(actTorrent) + 辅种页整组右键(act)两条主路径; 整集/整剧(actEpisode)与批量(bulk)补丁顺序正确、不受 POST 慢影响, 但仍受 H2/H5 影响。 与站点无关, 与库大小/机器负载正相关(本地小库与 harness 复现不出)
数据风险无。乐观补丁是纯前端只读改写, 失败仍回滚(resolveOptimistic(false)); 风险只在「假状态停留过久」与「弹回抖动」造成的误判, 不写后端状态、不涉及删除/限速
严重度高 —— 乐观 UI 是三波次里收益最大的一项(决策 2 明写「主因是沉默」), 反应慢到 2-4s 等于收益归零, 用户主观仍是「点了没反应」; 而且它是本次跟手性优化的对外交付体感, 这一条不成立, 前后三波次的观感都打折

04根因（初步）

结论: 待查。但已定位到一处结构性缺陷(事实, 非猜测): act() / actTorrent() 把乐观补丁放在 await POST 之后, 与另两条入口顺序相反 —— 这两条路径的「即时反馈」必然被网络往返延迟(见 §02 证据 1)。 至于真机上这一段往返为什么会长到 2-4s, 有以下候选, 未经验证前一律按待查处理。

假设内容判据(怎么证伪/证实)
H1
(最可能)		命令 POST 往返慢。uvicorn 跑在独立线程 (web.py:1004), 但主线程长 tick(真机大库 _refresh_torrents + rebuild_views, 实测 5000 种子首轮 ~14s)期间存在 GIL 争用; 且命令端点是同步 def, 进 anyio 线程池执行, 池被并发的同步 handler(/api/state 等)占满时也要排队 DevTools 里该 POST 的 TTFB / Waiting; 与同页面「整集暂停」(补丁先贴)对比耗时
H2命令消费慢(唤醒被长 tick 吞掉)。投递即 manager.wake()(web.py:205), 主循环 _wait_next(stop_event, _wake_event, main_tick)(qbmanager.py:353)被唤醒后 drain; 若此刻正卡在长 tick 内部, 唤醒要等这一轮走完 控制台 [perf] 行的 排队 wait_ms(>100ms 即异常)
H3前端渲染慢: 每轮 refresh 整表替换 + reapplyPending (app.js:1726 / 2322); 实测 3000 种子单轮 ~353ms 主线程占用 Performance 面板点击后的 Long Task 时长; 单轮 353ms 不足以解释 2-4s, 除非用户库远大于 3000 或机器很慢 —— 需实测
H4真值对齐晚: /api/state 轮询节拍 1.5/2/3s (与关联 issue webui-poll-cadence-mismatch 同源) 看是否出现「变过去 → 弹回 → 下一轮才对」; 只影响真值, 不影响首变时刻
H5用户指的是端到端(点击 → toast「已执行」), 而非首屏变化 记录 toast 出现时刻; 若是, 本条与 H2/H4 合流, 应归到节拍那条一起拍板
已排除: ① 乐观链路本身坏了 —— 用户确认变化会来、失败能回滚; ② BUG-3(组/集行没接乐观)—— 复核第 2 批已修(组行 is-pending + 集行 epState); ③ /api/state 序列化慢 —— §11 已把服务端 189ms → 23.5ms; ④ 回执轮询曲线过慢 —— 快命令曲线已是 0 → 150 → 300 → 500 封顶(app.js:2237-2245)。

05建议修法

方向: 先把「点击即变」从网络往返里解耦(改顺序), 同时补上打点消除盲区; 服务端侧的方案等 H1 有证据再动。本报告只写方案, 不实施。

方案 A(推荐 · 小且直接): 补丁提到 POST 之前

把 act()(整组)与 actTorrent()(单种子)里的 applyOptimistic() 提到 await this.api(...) 之前, 与 actEpisode/bulk 对齐。

  • 代价: 极小(两处移动 + 调整 try/catch 边界)。
  • 必须一并处理的点: ① POST 抛错时现在补丁还没贴(天然安全), 改顺序后必须显式 resolveOptimistic(hashes, false) 回滚 —— 「失败不留假状态」是硬要求, 不能破; ② pendingOps.ts 起点提前 ⇒ 3s 兜底窗口相对变短(见 §02 证据 3), 建议兜底改为按 「POST 已返回且真值未到」判定, 或显式放宽窗口 —— 这一处需先拍板, 别顺手定; ③ 失败回滚路径已有冒烟覆盖(ui_smoke.cjs 的 --expect-cmd error), 改完必须两种模式都跑。
  • 不解决: H2/H4(真值对齐晚)与 H5(端到端慢) —— 顺序改完若用户仍报慢, 说明是后两者。

方案 B(推荐 · 与 A 并行): 补打点, 消除盲区

在 4 条入口统一埋 T0 点击 → T1 POST 返回 → T2 DOM class 变化, 复用 cmdStats, 超阈值打 [perf](与现有 waitMs/execMs 同一条日志); 冒烟脚本加「点击 → is-pending 出现」 的耗时断言。为什么必须做: 埋点没有消费者就是死字段(项目既定教训), 现在这条链路在真机上 是盲的, 不补上下次还得靠用户肉眼报。代价: 小(前端 + 冒烟)。 注意: 冒烟要造出「慢 POST」才能覆盖本问题 —— 现有 harness 的 ok/error 模式回执都是瞬时的, 需要新增一个延迟档(否则断言恒绿, 等于没测)。

方案 C(仅在 H1 被证实后): 服务端侧降 POST 成本

命令 POST 应做到「只入队 + 回 cmd_id」的最小成本(web.py _enqueue 193-206 本身已经很轻), 所以若实测 TTFB 仍是秒级, 瓶颈在调度而非 handler: 排查同步 def 端点进 anyio 线程池的排队、以及长 tick 期间的 GIL 争用; 必要时把命令端点改 async def 或单独 executor。 代价: 中~大, 且要动 web.py 的线程模型假设 —— 先拿证据再开。

方案 D(仅在 H5 被证实后): 降级并合流

若用户指的是端到端而非首屏变化, 本条归到 webui-poll-cadence-mismatch 的节拍拍板里一起处理, 本条标 Duplicate 或作为它的补充证据。

修复后补充（2026-09-19 20:0x · 方案 A + B）

① 先量（受控测量，未改码）

用 Playwright 的 page.route 给命令 POST 注入人为延迟，量「菜单项 click 事件 → applyOptimistic 贴上（钩住该方法）→ DOM 出现 .is-pending」三个时刻。 桩服务回执是瞬时的，不注入延迟就永远复现不出来 —— 这正是这条缺陷能穿过设计、实施、 冒烟三道关口的原因。

入口注入 POST 延迟 0ms注入 POST 延迟 2000ms（修前）注入 2000ms（修后）
整组 act()补丁 14ms / DOM 22ms补丁 2012ms / DOM 2018ms补丁 0ms / DOM 7ms
单种子 actTorrent()补丁 14ms / DOM 17ms补丁 2004ms / DOM 2008ms补丁 0ms / DOM 4ms
整剧 actEpisode()（对照）补丁 0ms补丁 0ms补丁 0ms

结论：POST 慢多少，反馈就晚多少（1:1 传导） —— 与实际建议 A 的判断一致； actEpisode（补丁先贴）全程不受影响，等于自带对照组。

② 实际修法（与建议一致，无改道）

  • app.js：act() 与 actTorrent() 的 applyOptimistic() 提到 POST 之前（hashes 也提前算好）， 与 actEpisode/bulk 统一；try 块内 POST 抛错时显式 resolveOptimistic(hashes, false) 回滚（补丁提前后这条路径才第一次真正存在）。
  • 3s 兜底窗口改从「回执到达」起算（resolveOptimistic(ok) 里刷 op.ts）—— 按 §04 的拍板点选了「POST 已返回且真值未到」这一档：补丁提前后若仍按点击起算，慢 POST 会在命令刚完成时就 把窗口烧光 ⇒ 弹回陈旧真值再等下一轮。无回执（hang）不刷新 ts，3s 后照旧回落真值， 「失败/未知绝不留永久假状态」这条不变。
  • 方案 B 一并做掉：新增 _newCmdStats() / _markCmdPatch() / _markCmdPost()， 把「点击 → 补丁」与「点击 → POST 返回」两段写进 cmdStats（4 条入口统一打点）， waitCmd 由替换改为合并以免冲掉，[perf] 阈值扩展为 补丁 >50 / POST >400 / 排队 >100 / 端到端 >400。真机再报慢时，日志里会自己说话。
  • 回归守阵：冒烟新增「P0-3 补丁先于 POST（注入 800ms 仍即时）」—— 人为拖慢命令 POST， 断言点击 → .is-pending < 400ms（实测 4~5ms）；error 模式加一条 「慢投递 + 失败回执后回滚干净」。

③ 验证方式与测试数字

  • 受控复测（同上表）：注入 2000ms 时 2012ms → 0ms。
  • uv run pytest tests -q --no-cov → 1053 passed（与基线一致，静态守阵未破）。
  • 冒烟双 UI：48 项 0 失败（原 46 + 新增 2 条守阵）； --expect-cmd error 模式 24 项 0 失败（回滚路径干净）。
  • 未验证项：真机 POST 为什么慢到 2-4s 仍未实测（H1 的底层成因：长 tick / GIL / 线程池）。本次修法让 UI 不再依赖 POST 快慢，但成因本身没消除 —— 建议真机复测时看新的 [perf] … POST xxxms，若 POST 持续 >400ms 再按方案 C 追。

④ 顺带发现（已另立 issue）

测量时发现：整剧（show 级）操作在剧行上没有 is-pending 绑定 —— 补丁 0ms 就贴上了，但 .show-row 不绑 pending 标记（只有集行 .ep-row 绑）， 剧行折叠时用户看不到任何即时反馈。与 BUG-3 同类，属计划外，已另立 issue 26-09-19-1959-webui-show-row-no-pending，本次未改。
