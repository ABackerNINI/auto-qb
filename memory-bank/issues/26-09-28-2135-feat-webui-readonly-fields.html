01现象与发现场景

用户提出「WEBUI 设置里有部分设置不适合修改（如 schema 版本），应可展示给用户但不支持修改」，要求排查其余同类字段。逐字段通读 config/schema/（fields/groups/hr/trackers）、config/impact.py（热重载分级）、config/writer.py（保存链路）与前端 config_editor.js 后，共定位 4 个点位：除 schema_version 外还有 data_dir / state_file / fs 段。它们有一个共同形态：后端机制实际会覆盖或丢弃用户输入，UI 却渲染成可编辑控件，且丢弃后的反馈是误导性的「已保存」口径。与平台 / 特定配置无关，任何配置下保存即现。

02证据

取证时间 2026-09-28 21:35（代码阅读取证，非运行时报错）。4 个点位的现状行为：

字段类别现状行为（保存时）
config.schema_version程序盖章 保存/预览时 _stamp_schema_version 无条件把该键盖为当前版本，手改必然被覆盖；改低则整次保存被 _reject_stale_version 拒绝，报错文案却是「页签过期请刷新」——与用户实际操作（手改版本号）对不上
config.data_dirR 级（进程身份） 保存时 _fallback_restart_fields 把该键静默回退为磁盘旧值，但 API 仍返回 restart_required 含该项，前端 toast「已保存并热重载(变更 N 项); 需重启进程才生效: config.data_dir」——用户重启后发现值根本没变
config.state_fileR 级（进程身份）同 data_dir：静默回退 + 误导 toast
config.fs 整段（含 fs.path_map）R 级 + 控件不匹配 ①整段 LEVEL_R，保存静默回退（同上）；②path_map 是 YAML 列表结构，schema 却声明为 text 控件——列表值在表单里显示为 [object Object]（cfgScalar 对列表做 String 化），编辑产出字符串必挂校验；help 文案自认「WebUI 暂不提供逐条编辑, 在 config.yml 按 YAML 列表编辑」
# writer.py: _stamp_schema_version docstring（程序盖章语义）
该键是文件格式标记, 由程序统一维护 —— WebUI 保存/预览时无条件盖章, 用户手编配置不需要写它

# writer.py: _fallback_restart_fields（R 级静默回退）
R 级字段回退为磁盘旧值: 旧值存在则覆盖, 旧值不存在则删除该键(走默认值)

# config_editor.js: cfgSave 的 toast（对被回退的 R 级变更仍报「需重启才生效」）
this.toast(`已保存并热重载(变更 ${n} 项); 需重启进程才生效: ${result.restart_required.join(", ")}`, "timeout", 9000);

排查过但不在此列：敏感字段（web.token / qbittorrent.password / trackers.*.passkey / hr_check.channel.token）已有掩码哨兵机制（展示打码、保存还原磁盘旧值），设计上可改；其余 risk="修改后需重启" 字段恰为上述 R 级三项，全部 L0/L1/L2 字段设计为热改生效；校验层 KNOWN_CONFIG_KEYS 与 schema 键面一一对应，无隐藏键。

03影响面

维度结论
触发条件在 WebUI 设置页编辑这 4 个点位任意一个并保存——必现（后端覆盖/回退是保存链路的无条件行为）
影响范围设置表单 4 个点位；R 级三项（data_dir/state_file/fs）保存后 toast 误导；schema_version 改低会以「页签过期」错误堵死整次保存
严重度中——写盘防线兜住了数据（R 级回退、版本盖章），无数据损坏；但交互误导（用户以为改成功），且 fs.path_map 控件形态本身就是坏的

05根因（可选）

代码阅读已有结论（取证 2026-09-28 21:35）：schema 的 Field 数据类没有只读概念（所有声明字段默认可编辑），前端按「schema 声明即可编辑」渲染；而后端保存链路存在两条覆盖/丢弃用户输入的路径（程序盖章、R 级回退），丢弃后仍以「已保存并热重载」口径反馈——表单元数据与写盘防线脱节。另外 PUT /api/config 是结构化树直写，表单只是前端约束，后端无字段级只读防线（当前仅 R 级回退与版本盖章两道）。

06建议修法（可选）

  1. schema：Field 加 readonly: bool = False，4 个点位打标（schema_version / data_dir / state_file / fs 段）；schema_payload() 走 dataclass 序列化自动下发，前端零成本拿到。
  2. 前端：CE_FIELD_BASE（及 config_hub.js 的 HUB_FIELD_COMPONENT 同款）对 readonly 渲染禁用控件 + 「程序维护」视觉标记；fs 段建议改只读摘要（显示已配置映射对）而非 text 框。
  3. 反馈修正：R 级回退发生时，保存结果反馈改为「该项仅在配置文件中修改，本次未写入」口径，不再说「需重启进程才生效」（回退 = 值没写进去，重启也不会生效）。
  4. 后端防线（可选加固）：R 级回退与版本盖章已实际兜住 4 个点位；可再加 readonly 键面防线（_prepare 里对 readonly 键做同款回退），防未来新增点位漏配时重演「可编辑但不生效」。注意 schema_version 比程序新时仍应放行给校验层报精确错，别在回退里误伤。
  5. 守卫：补 readonly 点位清单断言（schema 键面守卫测试已有挂点）。
