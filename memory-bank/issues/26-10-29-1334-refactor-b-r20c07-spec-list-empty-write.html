01现象

03分歧点与判定

  • 分歧 1（键集）：删空后 [] vs 键消失。前者改变全树 JSON → 脏标记认改动， 且 notify.channels 类键空表过不了后端「必须是非空列表」。
  • 分歧 2（可达性）：写 [] 的那一支目前无入口（八助手无调用者）， 与三处删键实现同时存在于同一 JS 目录，后来者抄错边后才发现「合了却没生效/脏标记消不掉」。
  • 判定：(b) 无判据漂移、且分歧侧已死。审计原记录认为「规则 conditions/actions 空表是合法形状」 （cfgRuleAdd 建 {conditions:[],actions:[]}）故需人裁定——复核结论是这条与本项无关： 那是规则集骨架的创建，不是 spec 值列表的删除；spec 列表删空按既定口径就该删键（后端走缺省）。
  • 为何仍值得做：8 个死方法约 40 行（含一条与全项目相反的空态写法 + 一条 cfgSpecPath 之外无人用的 cfgSpecSet），删除零行为影响，收益是消掉唯一的「写空表」模板。

建议：删除 config_rules.js:77-117 的八个无调用者助手（保留在用的 cfgSpecPath（:72）与 cfgSpecItems（:119）， cfgSpecPath 仍在 cfgSpecItems 内被调用）。若出于「spec 增删将来要回来」的理由保留， 则必须把 :107 改成与 cfgItemRemove 同口径的删键并加注释指向 toggleKey 的两条理由——两者选一，不要留着写空表的分支。
