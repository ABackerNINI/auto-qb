01现象与发现场景

发现场景: 2026-10-05 复析计划 26-10-05-0314(WEBUI 危险动作防护)的拍板点 D4 时, 下沉核对决策链 1.5/1.6 的实现语义, 发现失败推断(chain 1.6)按设计只查其它成员, 而失败冷却(recheck_fails)的唯一消费点在 recheck 提交前 —— 两条跳检路径(规则侧决策链 0-4 / WEB 直连 ops.skip_check)对「候选种子自身当日校验失败后再跳检」都没有任何闸门。

后果形态: 自身校验失败 = 该种子对自身 piece hash 的校验未通过(数据与种子不匹配的确证, 见 §05 语义注记) → 用户/规则此时跳检 → is_skip_checking 把全部块标有效 → progress=1 被判「已完成」→ chain 0 永不再复查, zSkipChecked 打标后仅隔离出参考链, 本体无人回头。

03影响面

维度结论
触发条件种子自身当日 recheck 失败且仍暂停未完成(失败后回落态恰好满足 chain 0); 规则侧需 without_reference 段 mode=skip-checking 且组内无可过 basic_check 的参考(自身失败的组通常正好没有 —— 同映射姊妹若曾通过, 自身不会失败); WEB 侧仅需 skip_check_menu 启用时用户点跳检(单发或批量), 无任何配置前提
影响范围全部跳检路径(rule / web 单发 / web 批量); 坏数据被标全块有效后做种外传 —— PT 站 H&R / 口碑 / 封号风险; zSkipChecked 只隔离参考链不保护本体, chain 0 保证自动化永不复查, 仅用户手动 recheck 可翻案
严重度高 —— 数据完整性工具的核心保证(未验证不发种)被既有路径绕过, 且后果对外不可逆、对用户静默

05根因（可选）

已核结论(代码核实, 非猜测): 失败推断(1.6)的设计语义是「同组他人失败可外推到自身」, 「自身失败」的防护没有任何一处承接 —— 决策链 0-4 无对应闸门, 失败冷却的唯一消费点在 recheck 路径(且仅 rule 源)。属设计时未覆盖的防护缺口, 非回归。

语义注记: recheck_fails 计数含噪声 —— 「曾见 checking 后落回未完成」(真数据证据)与「宽限耗尽未开检 / 异常」(非数据证据)都计数(full_checking.py:47-49); 假失败自愈仅清「指向已完成/已删成员」的记录。修本件时须沿用或收窄该接受面, 不要假设计数=确定坏数据。
