WEBUI 危险动作防护: 重新校验确认框 + 跳检前置条件

跳检是删种重加级危险操作。本计划把「该不该跳检」的判定下沉 ops 层单点(方向 A), WEB 与规则两来源共用一套闸门; 在此之上前端交互改为三分流预检: 点跳检 → 确认框先开但确认钮禁用 → 预检请求(ops 同谓词 dry-run) → 后端按「禁止 / 需显式强制 / 可跳检」三态返回 → 前端按态渲染详细原因与逃生通道。重新校验补齐鼠标路径确认框与键盘路径对齐。前置条件逐条核对矩阵(含三分流归类) + 每闸门一测一红验的守阵在 §03/§06。

01结论与拍板点

一句话: 跳检缺的不是确认框(两入口已有 danger 框), 是「该不该允许」的判定与判定结果的呈现 —— WEB 入口直连 ops.skip_check, 只过 ops 层两道闸门(部分下载禁止 + 同日去重), 规则侧决策链 0/1 的语义(仅暂停中未完成、组内无活跃下载)与文件前置检查都没跟上; 而且点下才知道被拒, 用户在确认时看不到自己正在赌什么。重新校验反之, 确认框只在键盘路径有, 鼠标三入口裸奔。两边合起来是同一件事: 危险动作的防护要落在单点, 判定结果要在用户确认之前摊开。

方案结论(推荐, 待拍板)

  • 跳检前置 → 方向 A + 三分流预检: 闸门全部下沉 ops._skip_gates 单点(规则侧行为零变化, 决策链 0/1/1.5/1.6 本就在更早处拒绝或等待, ops 层再加一道同谓词是纵深防御); 前端交互改为「点跳检 → 确认框先开但确认钮禁用 → 预检请求(ops 同谓词 dry-run, 非前端复制谓词) → 三态返回 → 按态渲染」。三态: case 1 禁止(跳检无意义或确定性坏数据, 无逃生)、case 2 需显式强制(不能完全确定, 给逃生通道)、case 3 可跳检。执行路径闸门原样全跑 —— 预检只前移判定呈现, 不减任何防护; case 1 硬闸在服务端, 前端绕不过。
  • force 语义: 执行请求带 force=true 时, 仅 case 2 闸门(G5 同 hash 在途 / G7 组内校验在途, D8)降为警告放行; case 1 闸门对 force 一律硬拒。force 缺省 False, 规则侧不传 —— 规则侧零变化不变式保持。
  • 新前置条件 7 条(详见 §03 矩阵, 含逐条三分流归类): 已完成禁止、活跃中禁止、组内有活跃下载成员禁止、同 hash recheck 在途禁止(可强制)、组内校验在途禁止(chain 1.5 镜像, 可强制)、组内校验失败推断禁止(chain 1.6 镜像)、前置文件检查(check_filelist)并入执行链。其中文件检查是 03:14 复验核实的缺口 —— check_filelist 全仓唯一调用点在规则侧(checking.py:121), WEB 跳检从不查文件, 缺失文件会被 is_skip_checking 标成「完整」; 组内两道是 2026-10-05 复析补入(D4 拍板翻转, 见拍板点)。
  • 重新校验 → 前端共用确认框: 抽 _recheckConfirm(what), 批量浮条/批量右键(经 bulkAct)、单选右键与抽屉(经 torrentCmd)、键盘(改调共用 helper)四处同一文案; 后端零改动。(本条不受三分流调整影响 —— recheck 无预检需求, 在途互斥后端已有。)
  • 测试盯死: 每个新闸门一条单测 + 一条红验探针(摘闸门必红); 预检三态/force 语义/只读性各一条单测; WEB 单发/批量回执文案断言; 前端对话框静态守卫; 全量基线切片。

04方案与取舍

跳检前置: 方向 A(下沉 ops 单点) vs 方向 B(WEB 入口自判)

  • 方向 A(推荐): 新闸门全部进 ops._skip_gates(G3-G6)+ 执行链并 filelist 检查。规则侧零行为变化(决策链 0/1 先于 ops 调用, 同谓词等价 no-op, 纵深防御); WEB 单发/批量同过一道闸; 拒绝文案写一次, 两来源共用。代价: _group_has_downloading 判定需上移 store(见下), 触及 grouping 模块一处委托改写。
  • 方向 B(否): WEB 入口(commands.py)前置一次等价只读判定。否决理由: ①ops_mod.py 头注明文「提交点检查与保护策略单点归本模块」, plan 26-09-30-0109 危险操作收口的既定架构; ②单发/批量两入口要写两遍; ③filelist 检查原语在 ops 模块, WEB 层调用要么跨模块拿要么复制; ④两处谓词必然漂移 —— 正是 issue §05 合理怀疑的根因模式重演。
  • 组级判定的落点: grouping_mod._group_has_downloading(members) 的数据源全是 store(by_hash + state_enum)。上移为 TorrentStore.group_has_downloading(hash)(签名收 hash, 内部取 members), grouping_mod 改委托(单一真相), ops._skip_gates 经 self._ctx.store 消费 —— 模块间不 import 的契约不破(消费的是 store 服务)。
  • filelist 检查的插入点: R2 live 复核(确认种子还在)之后、导出之前 —— live 都不在的种子不值得查文件。规则侧会双查(chain 4 一次 + ops 一次): 跳检天级低频, 一次文件列表 API + 若干 stat 可忽略, 换「执行体内不信任调用方」的单一安全真相, 值。失败语义 fail(带 check_filelist 错误描述), 不是 skip。
  • G5 的插入点: _skip_gates 内(纯内存读, 零 API 成本), 在 G3/G4 之后。文案点明后果:「跳检会删除种子, 在途校验将作废」。
  • G7/G8 的实现要点(2026-10-05 复析补): 谓词逐字镜像规则侧 —— G7 镜像 others_checking(full_checking.py:69-72), G8 镜像 _skip_on_group_check_failed 四要件(:123-153, others-only); 镜像偏差即规则侧行为变更, 「候选自身失败」缺口不并入(另立 26-10-05-0402)。原语全部已在 ops 可达: recheck_fail_count 经 checking_meta 导入(ops_mod.py:41, 依赖方向契约允许; :167 已在消费), group_sizes/member_to_key 经 self._ctx.store(与 G6 同路), active_check_hashes 已在消费(:156)。G8 自愈做只读变体(不 pop 记录); recheck_fails 含宽限耗尽/异常噪声(full_checking.py:47-49), WEB 闸门继承规则侧既有假阳性面(同日窗口+自愈条件兜底, 瞬态可重试), 不发明更锐利谓词。文案: G7(case 2, 赌注两面写清)「同组种子正在全量校验: 等其结束后再跳检, 校验通过即证明共享文件完好; 强制跳检将不经其判决断言数据有效, 若判决为失败坏数据将被永久洗白」; G8(case 1)「同组种子 X 今日校验失败且文件映射一致, 共享数据已证实有问题, 禁止跳检; 请先对该组做 full-checking」。

跳检三分流预检: 端点 / force 语义 / 对话框(2026-10-05 04:33 用户定向后新增)

  • 架构原则: 预检 = ops 同谓词 dry-run, 不是前端复制谓词。新增 ops.skip_check_precheck(hashes) -> list[verdict], 内部逐 hash 走只读变体 _skip_gates_detail(hash, tor) -> list[GateVerdict];_skip_gates(执行路径)改为从 detail 派生「取首个未过闸门」—— 谓词只写一遍, 两路径同源。GateVerdict = {gate: "G3"…/"G8"/"filelist"/"partial"/"dedup", cls: "blocked"|"force"|"ok", text: 文案}; cls 就是 §03 归类, 分流标签与谓词同点定义。⚠ _skip_gates 现有副作用(清理非当日 skip_check_day 记录, ops_mod.py:469-470)不得进入 detail 路径 —— 预检必须零写入(state 不动、无 API 写、无 pop), 否则「只是看看」会改状态。
  • 端点: POST /api/torrents/skip-check/precheck body {hashes: [...]}(单发 = 单元素数组), 挂同一 403 门控; 经 _enqueue 走主循环线程(与写命令串行化, 快照无撕裂; 复用 cmd_id + waitCmd 既有通道, 前端不新开请求机制)。批量上限沿用 bulk 语义; 每 hash: 内存闸门(瞬时)+ filelist(D9 推荐: 一次 files API + N 次 stat)。回执结构: {results: [{hash, name, cls, reasons: [GateVerdict...]}], summary: {ok, force, blocked}}。
  • force 语义(服务端裁决, 前端绕不过): 执行请求 body 增 force: true; 单发 torrent_cmds.py 解析后进 payload, 批量 commands.py 透传给 _bulk_skip_check_via_ops(force=...) 逐 hash 下发; ops.skip_check(..., force=False) 新参数缺省 False —— 规则侧不传, 零变化不变式保持。执行时闸门照常全跑: force=True 仅把 cls=="force" 的未过闸门降级为 warning 日志后放行, cls=="blocked" 照旧硬拒(即使请求带了 force)。强制动作记 INFO 日志(哪个 hash 豁越了哪个闸门), 留审计痕迹。
  • 预检-执行无信任传递: 预检结果只决定对话框渲染(哪些钮可用、显示什么原因), 不进任何白名单 —— 用户点确认/强制后, 执行路径重跑全部闸门; 预检到确认的窗口内状态变了(如组员开始下载), 执行时照样被拒, 回执文案自解释。force 同理只是「许可」不是「指令」: 预检说可强制、执行时校验恰好结束, force 无害(闸门已自然通过)。
  • 对话框状态机(S4, 两入口共用一个 builder): 抽 _skipCheckDialog(hashes) 取代 skipCheckTorrent / skipCheckMulti 里各自为政的两个 _openModal 调用。共享 modal 是数据驱动的(_modalInit + popovers.html 模板, Vue 3), 扩展三字段即得, 既有全部对话框零变化: okDisabled(确认钮禁用, :disabled 绑定, 进框时 true)、busy(「正在检查前置条件…」行)、verdict(三分流渲染区)。确认钮进框即禁用 → 预检回执 → 按态切换: 全 ok → 启用确认(文案「跳检 N 个」); 有 force → 复用既有第三钮 extraText 当强制钮(模板里第三钮本就是 danger-solid 破坏性分支, 语义严丝合缝): ok+force 混合 = 确认钮文案「跳检 N 个可跳检的」(只送 ok 子集)+ 强制钮「强制跳检全部 N+M」(送全量+force=true); force-only = 确认钮保持禁用, 只有强制钮; 有 blocked = blocked 一律不可执行, 明细区列出。预检失败 → D10 降级: 启用普通确认、不出现强制钮、body 明示降级原因。
  • 多种子展示: 复用删除确认框的 details 行式明细范式(既有 modal-details 区, 行式键值 + 单行省略 + title 全文)。三段: 计数行(可跳检 N / 需强制 M / 禁止 K)+ 按原因分组行(「禁止 · 已完成 ×3: 名A, 名B, 名C…」单行省略, 同原因聚合避免 N 行重复文案)+ 单发时退化为全量原因行。分组内名称展示上限 5 个 + 「等 X 个」(title 悬停看全量可后续增强, 不阻塞本期)。固定警示区(统计清零/数据未经哈希校验/无参考高风险/HR 在管)始终显示, 与分流结果并列不互斥。
