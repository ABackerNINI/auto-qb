WEBUI 危险动作防护: 重新校验确认框 + 跳检前置条件

跳检是删种重加级危险操作。本计划把「该不该跳检」的判定下沉 ops 层单点(方向 A), WEB 与规则两来源共用一套闸门; 重新校验补齐鼠标路径确认框与键盘路径对齐。前置条件逐条核对矩阵 + 每闸门一测一红验的守阵在 §03/§06。

01结论与拍板点

一句话: 跳检缺的不是确认框(两入口已有 danger 框), 是「该不该允许」的判定 —— WEB 入口直连 ops.skip_check, 只过 ops 层两道闸门(部分下载禁止 + 同日去重), 规则侧决策链 0/1 的语义(仅暂停中未完成、组内无活跃下载)与文件前置检查都没跟上; 重新校验反之, 确认框只在键盘路径有, 鼠标三入口裸奔。两边合起来是同一件事: 危险动作的防护要落在单点, 而不是长在某条调用链上。

方案结论(推荐, 待拍板)

  • 跳检前置 → 方向 A: 闸门全部下沉 ops._skip_gates 单点, rule / web 两来源共用。规则侧行为零变化(决策链 0/1 本就在更早处拒绝, ops 层再加一道是纵深防御); WEB 单发/批量自动获得全部闸门, webui/commands.py 预计零改动(拒绝文案经 ActionResult 自动进回执)。
  • 新前置条件 5 条(详见 §03 矩阵): 已完成禁止、活跃中禁止、组内有活跃下载成员禁止、同 hash recheck 在途禁止、前置文件检查(check_filelist)并入执行链。其中文件检查是本次复验新核实的缺口 —— check_filelist 全仓唯一调用点在规则侧(checking.py:121), WEB 跳检从不查文件, 缺失文件会被 is_skip_checking 标成「完整」。
  • 重新校验 → 前端共用确认框: 抽 _recheckConfirm(what), 批量浮条/批量右键(经 bulkAct)、单选右键与抽屉(经 torrentCmd)、键盘(改调共用 helper)四处同一文案; 后端零改动。
  • 测试盯死: 每个新闸门一条单测 + 一条红验探针(摘闸门必红); WEB 单发/批量回执文案断言; 前端确认框静态守卫(防未来重构静默摘除); 全量基线切片。

02复验结论与问题面

问题面三层

  • 判定缺口(本件主目标): ops 层 _skip_gates(ops_mod.py:452)只有部分下载禁止 + 同日去重两道; 规则侧决策链 0(仅暂停中未完成, checking.py:88)/1(组内无活跃下载, :92)/1.5/1.6 与 chain 4 文件前置检查(checking.py:121, 全仓唯一调用点)全部留在 rules 层, WEB 直连入口一个都享受不到。已完成/做种中种子被删种重加、统计清空、HR 计时倒退; 文件缺失的种子被标成「完整」。
  • 防护不对称(姊妹件): 重新校验键盘路径有确认(shortcuts.js:806 _kbAct, :814 confirmDialog, 注释自述「鼠标路径不变」), 鼠标三入口(批量右键 ctxAct→bulkAct→_actCore、单选右键/抽屉 torrentCmd、批量浮条 bulkAct)点下即执行。
  • 架构事实(决定方案走向): ops_mod.py 头注自述「recheck/跳检的 qB 交互序列、提交点检查与保护策略单点归本模块」; AppContext 无 grouping 句柄但组级判定只需 store.group_members + store.by_hash(store 是 ctx 服务, ops 本就可达); 同 hash 在途登记 ctx.task_queue.active_check_hashes() ops 已在消费(recheck 在途互斥, ops_mod.py:156)—— 方向 A 需要的原语全部在 ops 可达范围内, 不需要新增跨模块依赖。

04方案与取舍

跳检前置: 方向 A(下沉 ops 单点) vs 方向 B(WEB 入口自判)

  • 方向 A(推荐): 新闸门全部进 ops._skip_gates(G3-G6)+ 执行链并 filelist 检查。规则侧零行为变化(决策链 0/1 先于 ops 调用, 同谓词等价 no-op, 纵深防御); WEB 单发/批量同过一道闸; 拒绝文案写一次, 两来源共用。代价: _group_has_downloading 判定需上移 store(见下), 触及 grouping 模块一处委托改写。
  • 方向 B(否): WEB 入口(commands.py)前置一次等价只读判定。否决理由: ①ops_mod.py 头注明文「提交点检查与保护策略单点归本模块」, plan 26-09-30-0109 危险操作收口的既定架构; ②单发/批量两入口要写两遍; ③filelist 检查原语在 ops 模块, WEB 层调用要么跨模块拿要么复制; ④两处谓词必然漂移 —— 正是 issue §05 合理怀疑的根因模式重演。
  • 组级判定的落点: grouping_mod._group_has_downloading(members) 的数据源全是 store(by_hash + state_enum)。上移为 TorrentStore.group_has_downloading(hash)(签名收 hash, 内部取 members), grouping_mod 改委托(单一真相), ops._skip_gates 经 self._ctx.store 消费 —— 模块间不 import 的契约不破(消费的是 store 服务)。
  • filelist 检查的插入点: R2 live 复核(确认种子还在)之后、导出之前 —— live 都不在的种子不值得查文件。规则侧会双查(chain 4 一次 + ops 一次): 跳检天级低频, 一次文件列表 API + 若干 stat 可忽略, 换「执行体内不信任调用方」的单一安全真相, 值。失败语义 fail(带 check_filelist 错误描述), 不是 skip。
  • G5 的插入点: _skip_gates 内(纯内存读, 零 API 成本), 在 G3/G4 之后。文案点明后果:「跳检会删除种子, 在途校验将作废」。

重新校验确认框(前端, 共用 helper)

  • 落点: commands.js 新增 async _recheckConfirm(what)(内部 confirmDialog, 文案沿 shortcuts.js:814 逐字:「将对{what}重新校验: 全量重读磁盘并校验完整性, 大库上耗时长且不可中断。」)。
  • 接入点 3 处(覆盖全部 4 个鼠标入口): ①bulkAct 加 recheck 分支 —— 批量浮条(topbar.html:211)与批量右键(ctxAct:574 落 bulkAct)同时覆盖, ctxAct 零改动; ②drawer.js torrentCmd 加 recheck 分支 —— 单选右键(ctx-menus.html:103)与抽屉内右键同时覆盖, 只拦 action === "recheck", 其它命令通道行为不变; ③shortcuts.js _kbAct 改调共用 helper(文案零变化, 键盘行为不变)。
  • 候选 B(_actCore 加确认)否: 键盘路径会双重确认; 且 torrentCmd 不走 _actCore, 覆盖不全 —— 正是 issue §06 候选 B 自己点出的两个代价。
  • 后端零改动: ops.recheck 的 R1 在途互斥/提交点实时复核/冷却策略原样(issue 复验已核对 :329/:656 两入口)。
