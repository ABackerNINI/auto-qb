02根因

  1. 页面加载时把存储读进内存一次：app.js:273 initialColState = loadColState()，之后每个标签的内存就是一份独立快照，此后不再回读。
  2. saveColState()（columns.js:318）写的是整份 {widths, hidden, manual, order}，而不是"我刚改的那一段"。
  3. 于是 last-writer-wins：哪个标签最后动一下，整份存储就变成它的快照，先改的标签的改动被静默吞掉 —— 不报错、不提示。
  4. 次生现象：别的标签的改动不会反映到当前标签，用户以为"改了没生效"，于是再改一次 ⇒ 又是一次整份覆盖。这是它能"经常"发生的原因。
为什么"写入时按 page 合并"单独不够：用户在两个标签里调的通常就是同一个表（辅种页 group）。按 page 粒度的合并只在"改的是不同表"时才有效；同表冲突时仍然后写赢。必须让每个标签的内存态保持新鲜（F2），否则写入合并不解决主要场景。

03修法

F1 · 写入改 read-modify-write（竞态兜底）

saveColState(page)：写前用 readColStateRaw() 读回存储，以存储为底，只覆盖本次操作涉及的那个 page 的四段，其余 page 段取存储最新值；存储缺失/损坏时退化为当前的整份写。6 处调用点都能给出 page：toggleColumn / resetAllColumnWidths / fitColumnsToWindow / startResize(up) / autoFitColumn / applyColOrder。

F2 · 监听 storage 事件做跨标签同步（关键）

在 mounted() 注册 window.addEventListener("storage", e => { if (e.key !== COLS_STORE_KEY) return; adoptColState(); })。storage 事件只在其它标签触发（写入方自己不收），天然无需判"是不是我写的"。adoptColState() 重新走一遍读 + 洗净，整体替换内存四段，再 $nextTick(materializeColumns) 让宽度按新状态重算。

F3 · visibilitychange 补漏

已有监听里 !document.hidden 分支加一次 adopt：覆盖"标签被浏览器冻结 / 事件丢失 / 后台很久才切回来"。

F4 · 冒烟

scripts/ui_smoke.cjs 加一条"双标签各自改列互不吞"（复用本次复现脚本的双页流程，同 context 两个 page）。

F5 · 静态守阵（可选）

tests/test_web.py 静态扫描：columns.js 必须出现 addEventListener("storage" 与 readColStateRaw() 在 saveColState 内被调用 —— 防回潮（与既有"静态防回潮"守阵同思路）。

04候选方案与取舍

方案做法代价 / 结论
A 只做写入合并F1改一处，但同表冲突仍丢（主场景）⇒ 不单独采纳
B 只做事件同步F2+F3能解决主场景；两个标签同毫秒写仍有极小竞态 ⇒ 配 F1
C = A+B（采纳）F1+F2+F3约 40 行，无新依赖，无后端改动
D 服务端持久化列偏好存服务端用户已明确"只存浏览器"，否决
E 冲突提示弹窗检测到冲突弹确认过度设计；同步后无冲突可提示 ⇒ 不做

05影响面与风险

  • 影响面：仅前端列偏好（顺序 / 显隐 / 宽度）的读写路径；不动列模型、不动后端、不动存储结构 ⇒ COLS_STORE_KEY 不升版本（升版本 = 清空用户偏好，见 pitfalls R10-09）。
  • 重渲染抖动：adopt 后走 materializeColumns，非 manual 页会按容器宽度重算 —— 与切视图/缩放的既有行为一致，不是新抖动；manual 页不受影响。
  • 丢未落库的自适应宽度：adopt 采用存储值，会丢掉本标签"尚未保存的 materialize 结果"。这些值本就不该进存储（见 materializeColumns 的设计），可接受。
  • storage 事件只在其它标签触发：写入方自己收不到 ⇒ 无需去重，也不会自激循环。
  • 两套皮肤：atlas / prism 共用 shared/，一处改动两边生效，无需分别处理。
