01方案C 合规化裁决（与报告推荐 A 的偏离记录）

报告 §07 推荐方案 A 的第 3 条理由是「C 买错了先例……违背『状态持久化统一进 state_file』的黄金法则 3」。用户拍板 C，本节把这条张力收掉，并逐条给报告点名的 C 三项负担以机制。此节是拍板 C 的合规化论证，实施与评审以此为口径。

1.1 定性：流量历史是观测数据，不是程序状态

黄金法则 3 所指的「跨轮次状态」是参与程序逻辑与恢复的状态：任务队列结构、去重窗口（record_execution）、跳检备份、字段基线。qB 流量历史是纯展示的观测数据：

  • append-only：只追加、不参与任何决策，规则引擎不读它（报告 §2.4 非目标已锁死）；
  • 丢失无一致性后果：停机/崩溃丢一段曲线，只是图上多一处断线（§05 的 null 语义恰好如实表达），不像 state 丢窗口会破坏幂等或去重语义；
  • 体量本质是日志型：随窗口线性增长、按龄淘汰——与 logs/ 同类，与 state.json「小而关键、整体原子替换」的访问模式相反。

故归类为观测/日志数据，落 data_dir 子目录，不入 state_file。state.json 保持程序状态单点（黄金法则 3 不破），同时免掉方案 A 的隐藏代价：100 组 ≈3–4MB 观测数据进 state.json 后，每次 maybe_flush（默认 120s）都是全文件原子重写。

1.2 报告点名的 C 三项负担 → 本计划的机制

报告点名的负担（§06/§07）本计划的机制
文件数随分组线性增长单种系列不落盘（§02.2，种子数 ≫ 组数是文件数爆炸的主源头，先掐掉）；文件总数 = 1 (global) + 组数 + index.json，组数量级见报告 §4.4 估算基准（100 组）
追加写崩溃产生半行需容错读侧坏行/半行跳过（对齐 TM 解析先例 curves.py:48-73 的坏行纪律）；重写走 temp + os.replace 原子替换；损坏超阈值移 .corrupt 重建，不静默吞（§02.4）
清理/轮转逻辑自担小时封口时原地按窗裁剪（无独立清理任务）+ 冻结文件按龄淘汰（§02.5）；全部有单测钉住（P2/P3 验收）

1.3 C 相对 A 的实质收益（写进档案备查）

  • state.json 零改动：无 v4 迁移、无版本链风险；差分基线不落盘、重启重置（§03.4），首窗 null 与停机空洞语义天然一致。
  • 24h 高分辨率段跨重启存活：C 的 raw 段落盘即持久（报告方案对比表中 C「重启存活：全存活」的兑现），A 的 24h 内存环重启即丢；读侧统一从 dat 文件取数，内存环退化为差分基线 + 单种环（§03.3）。
  • 写放大更小、崩溃丢失更小：平时每采样间隔追加一行 ≈50B；A 每次 flush 全量重写 3–4MB。崩溃丢窗口：C ≤ 1 个采样行，A ≤ state_save_interval（120s）。

1.4 对报告 §9.1 的一处设计修正

报告 §9.1 说分组系列「复用 _build_group_view 的组级 sum 结果，不重算」——不成立：_build_group_view 是 web 层懒建（webui/runtime.py:635 在脏标记时才重建，不在主循环每 tick 执行），且采样器在 core 层，引用它构成 core→webui 反向依赖。修正：采样器自算组级 sum（遍历 store.groups[key] 成员，对 by_hash 的 dlspeed/upspeed/uploaded/downloaded 求和），口径逐字段对齐 views.py:424-429, 459-460（网络流量可加和的口径注释同源）。图上曲线与分组弹层瞬时值可能有 ≤1 个采样间隔的相位差，属两套独立读取，语义一致。

2.1 目录布局与命名

  • 子目录名 qb-traffic：kebab-case 对齐既有兄弟目录（skip-check-backup/hr）；qb- 前缀与 TM 口径的流量数据在目录层划界（报告 §2.2）。硬编码常量（对齐既有子目录先例，全部非配置键），建目录走 os.makedirs(..., exist_ok=True)。子目录名不做配置键——用户拍板只要求「合适的子目录」，少一个旋钮；真有需求后续加键是纯加法。
  • 创建时机：enabled 且首次采样时惰性创建（enabled=false 的安装不产生任何文件/目录，P3 验收项）。

2.2 落盘范围：单种系列不落盘（子决策，可后期推翻）

只有全局与分组两类系列落 dat 文件；单种系列只留内存环（24h @ 采样间隔，每活跃种子一 deque，删种即清——对齐 store.py:291-307 field_snapshots 删种即清先例）。理由：种子数 ≫ 组数（文件数爆炸的主源头），且报告 §9.4 本就判「单种 24h 环纯内存即满足观察需求」、单种 30 天长段口径还挂着 all-time 持久性待真机验证（§10.2）。单种图的窗口即 24h，重启即清零——UI 文案如实声明。若日后要单种落盘，加 torrents 子目录 + 配置键是纯加法，本期不做。

2.3 文件格式 v1

# auto-qb qb-traffic v1                          ← 头行：格式标识 + 版本
key,<base64url(group_key)>                      ← key 原文（base64url 编码）；global.dat 固定 key,global
raw,<epoch_s>,<dl_rate>,<up_rate>,<dl_total>,<up_total>        # 采样行，≈每采样间隔一行
hour,<hour_epoch>,<dl_avg>,<dl_max>,<up_avg>,<up_max>,<dl_total>,<up_total>   # 小时封口行
字段口径说明
raw.dl_rate / up_rate瞬时速率，bytes/s直采（server_state/record.dlspeed/组级 sum），对计数器重置免疫；不做差分
raw.dl_total / up_total累计快照，bytesPrometheus 口径：存快照、消费侧差分；速率与累计双轨互证（报告 §4.4）
hour.*_avg / *_max桶内速率均值/峰值封口时由本小时 raw 行归并；30 天视图直接消费 hour 行（720 点）
hour.*_total本小时末累计快照相邻 hour 行差分 = 小时累计增量；max(0,·) + 回落判重置（§03.4）
头行 key,组 key 原文孤儿文件自愈的数据源（§02.3 index 对账）；base64url 即 encode_group_key 的编码（infra/utils.py:1063-1069）

行格式刻意与 TM 的 history_traffic.dat（YYYY/M/D ul/dl，curves.py:48-73）同构不同义：同为行式文本、坏行跳过的容错纪律对齐，但 TM 是外部只读文件、我们是自有写路径——「半行容错是我们自己的义务」（报告 §06 的告诫，§02.4 兑现）。单文件稳定上限：raw 24h@30s = 2,880 行 ≈150KB + hour 30d = 720 行 ≈55KB ≈ 205KB/文件；100 组 + global ≈ 21MB 总量，分摊在 101 个独立小文件里。

2.4 写路径与读路径

写（仅主循环线程，黄金法则 5）

  • 平时：每次采样 open("a") 追加一行 raw + flush——崩溃丢 ≤1 行；不做常驻句柄（每小时 rewrite 需要换文件）。
  • 小时封口（每小时首个采样触发一次）：读全文件 → 追加 hour 行 → 按窗裁剪（raw 段留 raw_window、hour 段留 rollup_window）→ 写 *.tmp → os.replace 原子替换（对齐 utils.atomic_write 的 tmp+replace 纪律）。单文件 ≈205KB，每系列每小时一次，成本可忽略。
  • rewrite 崩溃窗口：os.replace 前崩溃 → 旧文件完好，丢本小时已追加的 raw 行（≤1h 数据，null 语义如实呈现）；os.replace 后崩溃 → 新文件完好。无中间态。

读（Web 线程 API，只读）

  • 半行/坏行容错：不匹配格式或字段非法的行跳过并计数（纪律对齐 curves.py:60-71）；仅尾部半行是正常崩溃残留。
  • 损坏阈值：坏行占比 > 5% 判文件损坏 → 原文移 <name>.corrupt 后按空文件重建（不静默吞数据，也不让一个坏文件常驻报错）。
  • Windows 替换竞态：reader 打开期间 os.replace 目标会失败——rewrite 侧遇 PermissionError 退避重试 ×3（每次 50ms）；读侧文件 ≤205KB 一次性快读即关，窗口极小。

2.5 index.json 与清理/淘汰

index.json：
  { "format": 1,
    "groups": {
      "3f9a1c2e4b57": { "key_b64": "…",            # base64url(group_key)，与 dat 头行同源
                        "frozen_at": null,          # 非 null = 组已解散/换键，文件冻结不再追加
                        "created_at": 1727…, "updated_at": 1727… } } }
  • 启动对账（reconcile）：扫描 qb-traffic/ 目录与 index 求差——孤儿 dat（index 无条目）从头行 key, 重建条目；失配（头行 key ≠ index 条目）以头行为准自愈；index 条目无文件则删条目。对账只读目录与头行，永不动 raw/hour 数据。
  • 冻结与淘汰：组解散 / 换 key（§04.3 默认「不保留」）→ 旧文件置 frozen_at、停止追加；采样任务每小时顺带（复用封口时机，无独立任务）检查 frozen 文件，now - updated_at > rollup_window 即删除文件 + index 条目。冻结期的旧数据仍可查询（30 天内），自然过期——这正是「不保留」选项的实现形态：不删历史，只是不再续写、按窗消亡。
  • index.json 写入：utils.atomic_write（tmp + replace），仅条目变化时写（封口/冻结/淘汰时点），非每采样。

3.4 差分与基线重置规则（沿报告 §9.2，落盘部分按 C 改）

  • 速率字段直采不差分；累计差分在消费侧（API 栅格离散时）进行：delta = max(0, cur - last)；cur < last（qB 重启会话归零 / alltime 回退 / 删种重加）⇒ 判计数器重置：该桶记 null，基线更新为 cur。
  • 基线不落盘：程序重启 → 基线为空 → 重启后首个采样只立基线不出增量（首窗 null）。这是方案 C 免掉 state v4 的关键取舍，代价 = 每次重启损失 1 个采样窗的累计增量（速率曲线不受影响——瞬时值对重启免疫），与「停机 = 断线」的拍板语义一致。
  • 显式重置：组键换手（移动目录/增删文件 ⇒ 新 key）→ 新文件新系列从零起，旧文件冻结（§02.5）；种子删除 → 该 hash 内存环清除；同 hash 重加 → all-time 归零由回落判重置兜底。

3.5 断连与空值防御

  • qB 断连退避期间（qbmanager.py:549-559）采样任务照常出队：server_state 为 stale → 该轮出 null 点（写 raw,t,,,, 空值行，读侧还原为 null）——不沿用旧值画假曲线，也不断档（恢复后曲线连续、断连段为洞）。
  • 增量轮字段缺失防御（报告 §11.2-④）：采样读 server_state 关键字段缺失/空值 → 该轮按 null 处理并 DEBUG 记录，不写 0。

04分组 key 详细对比（拍板点⑤ · 用户点名）

sha1(base64url(key))[:12] + index.json恒 12 hex 字符哈希不可逆 → 须 index 映射（头行 key, 兜底自愈）；理论碰撞（100 组下 2^48 量级，可忽略；创建时查重，碰撞则加长到 16 hex 并 WARN）采用

4.3 换 key 后旧历史展示策略（待拍板 · 默认「不保留」）

组 key 是内容指纹，「换 key = 内容集合变了」。移动目录、增删文件都会换 key——尤其前者（整库挪盘符/改目录名）会让用户直观感觉「我的组断了」。三选项：

选项做法语义正确性实现成本对 dat/index 格式影响
甲 · 不保留（报告推荐，本计划默认） 换 key 即新系列；旧文件冻结、30 天内仍可查旧 key 曲线，按窗自然消亡（§02.5）；分组弹层只挂当前 key 最严谨：旧曲线对新内容集合无语义，不硬拼；「目录挪了 = 新观察对象」自洽 0 额外：冻结+淘汰本就是清理机制的一部分 无（frozen_at 字段已预留）
乙 · 按 save_path 归并展示 分组图把同 save_path 的多代 key 按时间段拼成一条连续曲线（代间衔接点 null 断开） 稀释：增删文件导致的换 key 也被拼进「同一目录的历史」，但内容集合其实变了；hover 需标代次，否则用户误读 +0.5–1 天：查询聚合层按 save_path 归并多文件 + 时间段拼接 index 条目加 save_path + periods 元数据（v1 即预留字段位，甲乙通用）
丙 · 组别名 用户给组命名，别名做展示键，底层仍指纹键；换 key 时别名自动继承（同 save_path）或手动重绑 体验最好，但「自动继承」的判定规则本身就是乙的归并问题 +1.5–2.5 天：命名 UI + 持久化 + 绑定/继承规则；报告 §08 已判「超出本期」 index/独立别名存储 + 配置面

拍板状态与影响面：三项中甲是默认（与报告推荐一致），P1–P6 全程按甲实施；实施到 P4（分组查询端点）前用户可改判乙/丙——改判只动「分组查询聚合层 + index 元数据」（乙 +0.5–1 天，丙另计），不回改采样器与 dat 格式（P1/P2 成果全部保留）。若不另行拍板，视为维持甲。

补充说明：甲之下「挪目录断档」并非数据丢失——旧 key 文件冻结后 30 天内在分组弹层仍可查（旧 key 经 index 反查）；断的是新 key 的曲线从零起。若用户后续反馈强烈，乙是低成本升级路径（字段已预留）。

05时间栅格与 null 断线语义（拍板④落定）

5.1 栅格离散（读侧统一口径）

  • raw 行时间戳 = 采样时刻 epoch_s（不对齐栅格——qB 重连退避、主循环抖动都会让采样时刻漂移，存储层不假装均匀）。
  • API 层把 [t0, t1] 按 栅格 = 采样间隔离散：bucket = floor(t / interval) * interval；桶内多行取速率均值；空桶 = null。24h 窗 ≈2,880 桶（raw 段），30d 窗 ≈720 桶（hour 行，hour_epoch 即桶键）。
  • 累计增量（totals 段，报告响应形状的细化）：相邻桶累计快照差分，max(0,·)；cur < last 判重置 → 该桶增量 null（§03.4）。

5.2 null 的三种来源（前端统一渲染为断线）

来源机制用户看到
程序停机停机期无采样者 → 连续空桶曲线断开；文案「程序未运行期间无数据」
qB 断连采样任务照常出队但写空值行（§03.5）断线（与停机洞视觉一致，不需要区分色）
计数器重置 / 单种非活跃判重置桶 null（§03.4）；单种非活跃期不产点断线 / 单种图仅在活跃期有线段
  • uPlot 侧 spanGaps=false 纯断线；「最大跨越」参数后置（报告 §9.6 已判产品上先做纯断线够用）。
  • 与 TM 图划界：TM 图「窗口内缺失日视为 0」（curves.py:76-92）是聚合语义，不适用于时序曲线（报告 §4.5）；两图同屏/同弹层时图例与文案明确「qB 口径 · 程序运行期间」——null 洞不补 0、不回填，是拍板语义不是缺陷。
