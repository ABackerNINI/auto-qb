§01目标与设计原则

为什么现在做第二次

首次全面 review 定格在 a4d14a8d(26-10-05, 起点 test.full 2610+4 / 99%), 其 57 条发现已全部经修复计划 26-10-06-0103(六批 28 issue)处置完毕。此后 develop 前进了 620 笔提交, 214 个 src/ 文件变更、累计 +243k/−28k 行: 代码面近乎翻倍(后端 Python 33.6k→46.3k 行, 前端 JS 13.5k→26.6k 行), 且新增了三个大面 —— tools/global-traffic-monitor/ 全新子项目(22 件 10.4k 行, 与主程序跨进程通信)、qb 流量 v4/delta 与 source 集成、前端抽屉重构族(drawer_tpl 14 件等)。首次评审的结论对约半数现行代码已经失效。

目标与完成判据

  • 只读取证: 评审轮内不改一行代码、不改一份文档; 全部产出 = 发现清单 + 分级 + 处置去向。修复一律另走认领(issue → 计划 → 实施)。
  • 算成 = 九批全部走完「每文件过目 + 十一维度勾选 + 底册去重」; 汇总后每条 P0/P1 有可达性复验论证; P0/P1 全部经 create-issue 入池并互链; 终版报告 doc-status → Done。

设计原则(继承首次四条 + 本轮一条)

  • 先底册后读码: 开工先把 issues 池 Open 条目、坑档 7 类、在途计划/报告、重复代码审查 322 条发现(17 条已入池)蒸馏成一页「已知问题底册」; 每条发现先对底册去重, 不报告已知问题。
  • 分批 + 统一五步: 九批覆盖全部源码, 每批一轮会话, 统一走「读档 → 坑档对照 → 逐文件读码 → 工具提示源 → 登记去重」。
  • 证据纪律: 每条发现必须带 文件:行 + 函数名 + 行号三锚 + 可达性论证; 论证不出可达不登记为 bug。
  • 基线不变式: 评审轮零改动, 每轮 test.full 数字与起点基线(4073 passed + 2 skipped / 99%)持平; 漂移先查明再继续 —— 这是评审期间的回归哨兵。
  • 增量优先(本轮新原则): 评审深度按文件与首次基线的变更关系分层(D1 拍板), 变更/新增面吃满深度, 未变面保覆盖但降单文件工时 —— 保证「全面」的同时不重付 25 天未变代码的等深读码成本。
