§01目标与设计原则

为什么做

知识库经过 09-22 目录化(拆分+墓碑兼容层)、10-31 分级清理(L0–L3, 删除能力就位但 0 件执行)、11-05 8K 压缩(已执行完, cap 债务 45→8)三轮改造, 体量仍是 1,967 个 md / 10.1MB。三轮的共同盲区: 只治「体量与过期」, 从未裁决「哪些文件根本不该存在」。用户 26-11-08 拍板哲学: 「代码本身就是最好的文档, 仅保留大的架构设计类文档; 低价值的一律移除; 漂移靠『没有可漂移的文件』根治, 不靠流程与机检」。

设计底线/不变量

  • git 历史即冷库(D2 总闸): 工作区不留墓碑、不留无人读的清单类生成物, 该删就删; 删除不再需要逐轮授权 —— 本计划即是授权。
  • 历史件正文零改动维持(D2): tasks/plans/reports/issues 正文一行不改; 删除导致的死链不修, 兜底 = grep 文件名 + git log -- <旧路径>。唯一例外口径维持 09-23 先例: 活文件允许机械路径串修正。
  • 蒸馏三动作(11-05 B3 口径沿用): 外迁 attachments / 删死段 / 合并邻近件; 禁止压文案。
  • 冻结快照不动: testing/baselines/、real-baselines/、各 attachments 证据链、「当时现场本身就是其职责」。
  • 红线不动: config.yml、auto-qb-data/、其它 clone。
  • 不建流程(D14): 不加陈旧度机检、不加定期巡检 —— 移除本身就是治理。

痛点实测证据
墓碑/指针桩顶层 13 个 md 中 9 个是「已迁至」(8 墓碑 + activeContext.md 指针桩, 各 ≤1KB, 全部落款 09-22); 另 ~27 个活文件正文含「已迁至/已并入/已废弃」字样。体量小, 但每次跟历史引用跳进去都白走一趟。

假漂移说明生成物 _index 的「最后修改日期早」多数是假信号(确定性函数, 主题件没变它就不变); config-reference/_index 停在 10-03 属此类。真漂移判定看内容与代码矛盾(11-03 评审 S5 曾入池 6 条)。

体量分布全库 1,967 md / 10.1MB, 其中 testing/baselines/ 独占 968 件 / 2.84MB(26.7%, 冻结快照, 不动)。

检索现状: AGENTS.md 承诺「先索引、后 grep」, 但实际主消费路径是 kb.active(只回溯 11-03 蒸馏后 90 片 ≈ 5 天)+ grep; 索引层的承诺没有被执行兑现 —— 这是 D13 换轨的依据。

§03方案总览

主线

五波次串行: W1 蒸馏(先把移除层的原料提炼成终态件)→ W2 移除与更名(git rm + git mv)→ W3 机器退役(生成器/命令/守卫收缩)→ W4 口径重写(AGENTS.md / README / doc-forms / SKILL)→ W5 sweep 与清零(活文件死链 + cap 债务 + 全量验收)。W1 必须先行(W2 删的是 W1 的原料); W3/W4 都必须在 W2 之后(守卫不退役, 删完天天红)。

落点

  • 蒸馏映射: systemPatterns/ 八件(61,587B)+ rule-system/ 五件(45,331B)→ architecture/ 六包(≤8K/件, 允许合并到 4 件; 撑不过 2K 的并入 overview, D7)。productContext.md(8,901B)+ techContext.md(6,025B)→ projectbrief.md(≤8K, D8)。蒸馏物落 新名 architecture/, 不复用 systemPatterns.md 墓碑名(D1 拍板, 历史件引用死链按 D2 兜底)。
  • progress/ 全灭(D9): implemented-*×7 删(演进叙事由 tasks/plans 原始件承载); known-bugs.md 未修项逐条 kb.new issue 入池后删; roadmap.md 删(职责归 issue/plan, D1); evolution/suggestions/distilled 删。
  • 权威归位(D10): 配置键权威 = src/auto_qb/config/schema/ + validate_config(config-reference/ 删); 找代码位置 = grep/IDE(modules/ 删); 真机走查 = testing/real-machine.md 自带规程(checklists/ 删)。
  • 索引例外面(D5): pitfalls 8 个 _index 保留 —— grep 需要「已知关键词」, 「改码前扫陷阱」的本质是扫到不知道要 grep 的坑, 25 行触发词表是该动作唯一载体; 其余 12+ 个 _index 与 5 个 _archive 删。
  • 检索纪律换轨(D13): 「先索引、后 grep」→ 「kb.active(最近)→ README 极简路由 → grep 兜底」; AGENTS.md 同步行删除, README 路由表重写为十几行。

#结论
D1新计划独立成件, 不吸收 8K 压缩计划 —— 用户指正「8K 计划似乎已完成」, 实测确认(git 链 8dedcd92→fef982ee, 债务 45→8), 上一轮「整份 Open」情报过时。
D2删除总闸: git 历史即冷库, 工作区不留墓碑与无人读的清单类生成物; 推翻「引用路径永不失效」与「L3 purge 永不执行(零删除传统)」两条旧默认; 历史件正文零改动维持, 死链 grep + git log -- 路径 兜底。
D3顶层 9 个「已迁至」文件全删(8 墓碑 + activeContext.md 指针桩)+ 15 个活文件引用 sweep + STUB 守卫常量退役; 历史件死链不修。接受唯一实际退化: 历史链接从「跳墓碑再一跳」变成「grep 才能到」。
D4issues/_index.md + 5 个 _archive.md 全删; 开放池对 agent 变 write-only 接受(无主 open issue 无人看见是已知代价); 排期锚不受影响(README 直连)。
D5pitfalls 8 个 _index 唯一例外保留(触发词聚合 = 改码前扫陷阱载体, grep 替代不了「扫到不知道的坑」); 其余 _index 删; kb.index 收缩为只服务 pitfalls。
D6kb.nav 保留 —— 用户挑战后实测撤回退役: nav_data.py 自算数据(rglob 扫 meta 头), 与 _index 生态零耦合; 它是四工位档案层(~1,200 件)的人的导航入口。
D7architecture/ 分包六件起步(overview / main-loop-queue / data-state / rule-engine / hr-groups / webui), 各 ≤8K, 允许蒸馏时合并(撑不过 2K 并入 overview); 不复用 systemPatterns.md 名。
D8projectbrief.md 吸收 productContext + techContext 蒸馏物, ≤8K; 六文件 Memory Bank 惯例名仅存 projectbrief。
D9progress/ 全灭: implemented-*×7 删; known-bugs 未修项 issue 化后删; roadmap 删(职责已有 issue/plan); evolution/suggestions/distilled 删。
D10checklists/ config-reference/ modules/ archive/ 移除; 权威归位: 配置键 → schema/ + validate_config, 代码定位 → grep/IDE。
D11activeContext/ → active-context/ 更名(90 切片 git mv; kb.active/守卫/skill 内部路径同步)。
D12机器退役清单: gen_issues_index / gen_docs_index / gen_tasks_index / kb.tier / kb.docmap; test_memory_bank_*.py 与双 SKILL 收缩; kb.index、kb.nav、kb.new/status/bump/wrap/active/baseline 保留。
D13检索纪律换轨: 「kb.active(最近)→ README 极简路由 → grep 兜底」; AGENTS.md「先索引、后 grep」行删除。
D14漂移治理 = 移除, 不是流程: 不建陈旧度机检、不建巡检; conventions/(协议单点)与 pitfalls/(事故驱动)过刀保留。
