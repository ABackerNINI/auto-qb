流量启动恢复改为按需读取口径

把启动恢复的读集从「rollup_window 内全部历史天文件」收敛为「agg 水位所在日 → 今日」，已封口小时不读不重算；agg.dat 按系列照读（水位与聚合行数据）。启动死区从此与历史数据量、与保留口径彻底解耦：不打开流量图，启动不碰历史天文件；打开 24h 流量图，启动与图表读的是同一份 ≤2 天的数据。rollup_window: 1000000D 的永久保留口径不动。

§1摘要与结论

报告 26-10-12-1923 把「启动后 WEB UI 好几秒才正常」定位为启动死区：装配序最后一个模块的 TrafficSampleModule.start() 调 _recover_aggregates()，在 WEB 监听就绪与主循环第一拍之间静默地把 qb-traffic-v4/ 的全部历史天文件重读一遍并逐槽重算（实测死区 11.16s，其中恢复全量实测 7.09~7.28s，且随历史 +1.5~2.0s/天 无界增长）。

本轮用户定调给出判定基准：流量图的数据方案定调一直是「按需读取」——不打开流量图，理论上不需要读任何历史文件；打开 24h 流量图，理论上最多读 2 天数据。据此，启动恢复全量重读历史 = 该定调的实施缺口（不是配置问题，也不是「WEB UI 慢」）。

结论（一句话）：修 = 把恢复读集下界从「配置窗口 now - rollup_window」改为「agg 水位（wm_hour）所在日」，读集变为 [day(wm_hour), day(now)]——常态 1 个天文件、跨日界至多 2 个，与 24h 流量图的读侧契约同阶；agg.dat 仍按系列读（小文件，水位与聚合行）。保留口径（rollup_window: 1000000D）不动。
#项裁定
靶点启动死区 = 恢复读集无界修（报告 §7-B1 方向，按用户定调收敛为「读集下界 = agg 水位」）
保留口径rollup_window: 1000000D 永久保留不动——用户有意设定；B3（补 raw_window 删除）/ A1（调小 rollup_window）出局
次要因素搜索索引首建独占主循环（1.7~2.5s）不在本计划——与流量图按需口径无关，另立 issue（报告 §7-C1）
读侧图表raw 段窗按窗口日期集只读涉及天文件零改动——已是按需读取，本计划只让启动恢复对齐它

§2已裁定事项(本轮拍板记录)

用户本轮给出三条定调（D1–D3），加两条由报告与既有契约推出的边界裁定（D4–D5）。这些即本计划的需求边界，实施不得越界：

#决策裁定
D1按需读取是既定契约不打开流量图 ⇒ 启动不得读历史天文件；打开 24h 流量图 ⇒ 最多读 2 天数据。启动恢复必须遵守同一契约，而不是按配置保留窗全量重读。
D2保留口径不动rollup_window: 1000000D（等效永久保留）是有意设定——本场景下不应有性能问题。不改保留语义：不启用 raw_window 删除（B3）、不调小 rollup_window（A1）、不改 hour 行裁剪与系列淘汰口径。
D3启动恢复保持同步不做 B2（恢复后台化/挪出关键路径）——读集收敛后同步成本有界，不值得引入与在线记账的并发/时序契约（黄金法则 5 单写线程）。
D4agg.dat 仍按系列读恢复需要水位与聚合行数据（read_agg，实测 24 系列合计 0.021s）；agg.dat 不是历史天文件，不在「按需」排除面内。
D5正确性优先于成本agg 缺失/不可信（无 wm_hour）时退回现读法（now - rollup_window 全量兜底）并留日志——诚实兜底，不猜、不静默。

3.2 各视图读集契约（本轮一一钉死）

读侧一次请求只碰三类文件：raw 天文件（raw 段窗）、agg.dat（agg 段窗）、限速天文件（qb-traffic-v4/limits/，注解面，三作用域同源只读一次）。下表是冷读口径（首次请求或文件变更后）；重复轮询由解析缓存兜住（V4DayCache 4MB 文本预算 LRU · LimitsCache 4096 条目 LRU）。参数取生产配置 sample_interval: 1.5S（raw 桶宽 = max(1, ceil(1.5), ceil(span/2880))，只影响种子外扩的秒级量）。

  • 日期数公式：涉及本地日期数 = date(t1) - date(t0) + 1。raw 段读集区间 = [grid.t0 - grid.interval, grid.t1]（种子外扩一个桶宽，D3）；限速面读集区间 = [grid.t0 - 86400, grid.t1]（多看一天：合成首事件要窥窗口起点之前最近的事件，它可能落在前一天文件末行）。
  • 24h 恒 2/3 的原因：区间长 = 86400 + 30s > 86400 ⇒ 恒跨一个日界（2 个日期）；本地 00:00 后 30 秒内起点落到前一日、跨两个日界 ⇒ 3 个。
  • 「跨日界」何时发生：now < 本地 00:00 + 区间长。故 12h 窗在每日前 12 小时是 2 个天文件，其余时间 1 个；限速面同理（前 12 小时 3 个）。
  • agg 段与窗口长度无关：3d→all 一律 1 个 agg.dat/系列 —— 这正是 day/month 行永久保留、长窗不扫 raw 的设计意图。
  • 组作用域放大只在数据面：raw 段按成员各读窗口日期集、agg 段按成员各读 1 个 agg.dat；限速面三作用域同源共用一份（不乘 M）。
  • 唯一随窗口/历史增长的项 = 限速注解面（1 文件/天且不淘汰）：6mo/1y 上百、all 随保留无界。已由 mtime+size 缓存 + 单文件几十条兜住（不是性能问题），但它是本契约表里唯一「窗口越长读越多」的面。备选（不在本计划）：把限速事件 rollup 进 agg.dat、或给长窗按段裁剪读取范围 —— 属另一件事，需要时另立 issue。
  • 与启动恢复的关系：本计划把恢复读集收敛为「水位日 → 今日」（≤2 个天文件/系列 + 1 个 agg.dat/系列），即与 24h 视图同阶；「不打开流量图」的 0 文件契约由读侧轮询门控保证，恢复读的是写侧缺口（报告 §10）。

§4方案设计

4.1 核心改动: 读集下界 = agg 水位所在日

  • 口径：_recover_series 里把 store.series_day_dates(key, now - window) 的实参改为 v4_day_epoch(wm_hour)（wm_hour = parsed.hours[-1].epoch，即 agg 文件尾最新封口小时）。
  • 为什么是「所在日」而不是「水位时刻」：series_day_dates 按文件名日期过滤（v4_date_str_epoch(d) >= min_epoch，traffic_store.py:940）。传 day(wm_hour) 恰好把「水位当天的天文件」纳入——水位之后的 raw 就落在这一天文件里；传更细的时刻会误排掉该文件。
  • 为什么足够：小时行 h <= wm_hour 已在 agg.dat（现判据 :1183-1192 已在过滤，不重算）；需要补算的只有 h > wm_hour 的小时，而它们必然属于 day(wm_hour) 或更晚的天文件（天文件 00:00 硬切、块不跨天）。
  • fallback（D5）：wm_hour is None（agg.dat 缺失/损坏/尚无 hour 行）时，退回现口径 now - window —— 无可信水位时全量兜底是唯一诚实的做法；此路径打 INFO/WARNING（见 4.2），且属罕见路径。
  • 硬序不变：catch-up 全部 append 完成之后才 _agg_trim（:1203）——这条既有钉住不放。

4.2 埋点(报告 §7-B4): 消除静默

  • _recover_aggregates 起止各留一条 INFO：开始行（启用态、系列数）、完成行（系列数 / 读入天文件数 / 补算小时数 / 耗时）。
  • 单系列级：读集 > 2 天（水位陈旧或 fallback 全量）时留一条 INFO 说明下界来源（水位日 / fallback 窗口），便于下次这类问题 5 分钟定位。
  • 失败路径 WARNING 维持现状（OSError 不阻断其它系列）。
  • 计数（系列数/天文件数/槽数/耗时）落模块级属性，供测试断言——把「读集有界」变成可机检的事实，而非靠读日志目测。

§5边界情形与正确性论证

情形读集为什么正确
正常停机(优雅退出)水位日 → 今日，常态 1 个天文件stop() 已封口 + flush；wm_hour = 最后封口小时，其后的小时只在当天天文件里。停机数小时 → 补算等价（既有守阵 :1482 覆盖）。
崩溃(无 stop)同上，至多 2 个天文件append 成功即水位推进；崩溃窗口 ≤ flush_interval（默认 600s）的 raw 已在当天天文件，h > wm_hour 判据照常补算；撕裂尾/坏行由解析层整行跳过。缺文件断链（day_tail=None）语义不变。
停机跨多日 / 反复重启水位日 → 今日；实际存在的文件仍 ≤ 2停机期间不写新天文件；day(wm_hour) 天文件含水位后的全部 raw，today 文件（若已建）含重启后 raw。中间日期目录里没有文件，read_day 返回 None → 真空（与块间 gap 同语义）。
长停机 + hour 行已裁剪同「停机跨多日」wm_hour 是最新封口行（不是最老），裁剪只删老行，水位仍指向停机前最后封口小时；读集不因裁剪变小或变大。
agg.dat 缺失/损坏now - rollup_window（现口径）D5 兜底：无水位则不可判「哪些小时已聚合」，全量重算 + 日志；正确性不降级（该路径与现状逐字一致）。
系列目录只有 agg.dat、无天文件空读集series_day_dates 返回空 → 只重建累计器，零 raw 读（现状即如此）。
00:00 跨天覆盖结算读集含跨日界两个文件时读集是连续日期区间（水位日→今日），prev_tail 接力链不断；跨午夜至多 3 个文件的情形只在读侧图表出现（窗首外扩），恢复侧不需要外扩。
与 24h 流量图「最多 2 天」的口径差异（有意保留）：读侧图表在窗首跨本地午夜时外扩一个桶宽、至多 3 个天文件（traffic_qb.py:15-16 契约）；恢复侧读集是日期区间，跨日界时同样落在 2 个日期文件内（水位日在昨天 + 今日）。两者同阶，不是同一个数——计划不强行统一，避免为对齐数字引入窗首外扩这种读侧专用语义。

§8风险与取舍

点判断
水位可信性依赖「append 成功即推进」既有语义（agg 文件尾 = 水位，崩溃于 append 后从文件尾恢复不重 append，幂等），本计划不改。水位之后的 raw 一定在天文件里——这是补算的全部前提，已在 §5 逐情形论证。
恢复仍读 agg.dat（每系列一个）实测 24 系列合计 0.021s；agg.dat 是水位与聚合行的唯一来源，不是历史天文件。系列数增长时该项线性（小常数），与「历史天数」无关——正是要达成的解耦。
读集仍随「在途小时数」线性在途 = now - wm_hour，由 flush_interval（默认 600s）封顶 ⇒ 常态只读当天天文件的一部分。崩溃/停机越久在途越长，但读集仍 ≤ 2 个天文件（§5）。
埋点行会新增日志启动一次两条 INFO，可忽略；换来的是这类「静默死区」问题下次可 5 分钟定位（报告把「完全静默」列为最大排查障碍）。
与既有 hard-ordering 的交互只改读集下界，catch-up → append → trim 的硬序与累计器重建逻辑零改动；既有三条恢复守阵即是回归网。
跨 clone 取证数据报告数据取自另一 clone（只读）；本计划与实施只动当前 clone，跨仓库写操作绝对禁止。
