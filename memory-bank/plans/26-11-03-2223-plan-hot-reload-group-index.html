§01目标与设计原则

目标

  • 热重载命中 L2 后，辅种分组索引不再永久为空；视图在当轮刷新（最迟下一个成功同步轮）恢复为真实行数。
  • 不改变「首轮启动 / 新增种子 / save_path 变化」的既有归组语义；不新增任何配置键（因此不触碰 config.validate_config 与 config/schema.py）。
  • 用守阵测试钉死「L2 重建后不会再次永久空」，并防止后续改动顺手把索引清空或引入无谓的全量重算。

不变量与底线

  1. 分组键的输入面 = (规范化 save_path, 文件相对路径元组, 物理解析结果)；见纯函数 group_key_of（grouping_mod.py:41-49）。
  2. 单写线程：groups/group_sizes/member_to_key 只由主循环线程改；Web 线程只读已发布视图（既有约束，本计划不引入第二把锁、不新增跨线程通路）。
  3. reset_runtime 的职责边界：继续清 tracker_conf/state_snapshot/verified_references/own_writes/state_since 等真·运行态；分组索引是否属于「必须清」由本计划 §03 判定，不按名称惯性处理。
  4. 幂等：重复 L2 重建/全量轮不得产生重复成员、重复停种或重复警告。
  5. dry-run 零真实副作用：任何重归组路径不得在 dry-run 下触发 torrents_stop。
成功判据：受控实验四阶段脚本中「阶段 3（全量轮兑现）后 groups 仍为 1、队列视图行数 > 0」；新增回归/守阵测试全绿；commands run test.full 通过并重记基线切片。

§02现状与根因

触发链（代码复核）

  1. WebUI 保存配置 → QbManager.apply_new_config()（qbmanager.py:733-770）→ 每模块无条件 apply。
  2. RulesModule._rebuild_needed()（rules_mod.py:189-202）判 L2：rules_config / interval / delete_tags / delete_tags_if_has_no_torrents / global_speed_limit_curve / trackers 的 domains·rules·groups 三元组或 tracker 增删。
  3. RulesModule.rebuild_runtime()（rules_mod.py:217-233）→ store.reset_runtime()（store.py:747-770）：750-753 清 groups/group_sizes/member_to_key/group_key_migrations，765 view_changed=True；769-770 保留记录但 tracker_conf=None；尾段 reconnect() 使 rid 失效。
  4. 下一成功同步轮是全量轮：store.need_validate → 广播 full_round（qbmanager.py:922-932），tracker 模块把 tracker_conf 重匹配（tracker_mod.py:59-68）。
  5. 但归组只有两个入口：torrents_added（新纪录才判 added；全量轮只重建 by_hash，store.py:424-469 对 prev.get(h) 复用记录，不判 added）与 post 中的 save_path 变化（grouping_mod.py:269-308）。GroupingModule.subscribe（grouping_mod.py:104-108）不订阅 full_round。
  6. 结果：索引永久为空 → _build_group_view() 输出 0 行并 group_view_ver += 1、notify("ver")（runtime_views.py:377-404）→ 前端收到合法的空 groups 代 → 整页「暂无辅种」。

受控实验证据（调查会话，HEAD f89de69e）

阶段1 首轮全量:  by_hash=2 groups=1 members=2  view_changed=True  (torrents_files calls = 2)
阶段2 L2 重建:   by_hash=2 groups=0 members=0  view_changed=True
阶段2 重连后:    by_hash=2 groups=0 members=0
阶段3 全量轮:    by_hash=2 groups=0 members=0  → 分组视图行数 = 0
阶段4 模拟重启:  by_hash=2 groups=1 members=2

先例与先例更正

  • RulesModule._on_full_round（rules_mod.py:133-154）是「L2 后恢复存量种子派生态」的既有先例，但它恢复的是种子级任务，不是分组索引；两者是否该用同一手法，取决于派生数据的输入面（§03）。
  • 26-10-01-2129-bug-webui-hotreload-ext-vanish 已于 2026-10-02 置 Superseded，理由「新机制无对应路径、辅种消失未经证实」。本件受控实验证明该结论不成立：新机制的 L2 分支就是对应路径。修复落地时应在该件「状态变更日志」补一行更正，并指向本件/本计划。

关键观察（决定方案取舍）

「重建索引」不等于「向 qB 重新取证」。 TorrentRecord.files() 是持久缓存（record.py:290-296），只在本进程首次读取时请求 torrents_files；reset_runtime 不丢记录（store.py:424-425 全量轮复用 prev 记录），故 L2 后重新归组读到的仍是同一份 _files 缓存。
因此方案 A/C 的「重算」与保留索引得到完全相同的分组键；差别只在成本与副作用，不在正确性。这是本计划推荐 B 的核心依据。

§03候选方案与取舍

方案做法与改动面取舍主要风险 / 成本验证与回滚
A
订阅 full_round		 GroupingModule 订阅 full_round，reset_runtime 置一次性 pending；在该相位对所有 tracker_conf 已就位且未归组的记录重跑归组。
改动：store 新字段 + grouping 订阅/处理器 + 内核 full_round 载荷补 dry_run + 测试。		 与 rules_mod._on_full_round 同款，语义直白：「全量轮恢复派生态」。 全量归组把每个组标 dirty_groups → post 的跨组检测全量展开（grouping_mod.py:603-660，O(组×文件)）+ 每组大小一致性检查；A 的 full_round 当前无 dry_run 载荷（qbmanager.py:932），不加就会在 dry-run 下真停种；依赖「tracker 先于 grouping 装配」（当前 qbmanager.py:227 vs 245，但无测试钉住）；同轮 save_path 变化的缺文件扫描可能被「已归组」短路。 单测：files_calls 不增（缓存命中）、恢复后视图 > 0、dry-run 无 stop；回滚 = revert 单提交（无磁盘/状态迁移）。
B
保留分组索引
（推荐）		 store.reset_runtime() 不再清 groups/group_sizes/member_to_key（及 group_key_migrations，见 D2）；更新注释；新增守阵测试。改动约 4 行 + 注释 + 测试。 分组键输入（save_path / 文件表缓存 / 物理解析）都不在 L2 判据的变更面；与既有「cross_group_conflict_warned 有意不清」同一条逻辑（store.py:760-762 已写明「同数据派生同 key」）。零 API、零 syscall、零 O(N)、无 dry-run 风险、无装配序依赖；不新增跨线程状态。 把 reset_runtime「全清」语义收窄：若未来 L2 判据纳入影响分组键的配置（当前没有），B 会保留旧键 —— 用注释 + 守阵测试提示；不修复「重置前已不完整」的索引（与本次症状无关）。 单测：reset 后 groups/member_to_key/group_sizes 原样、view_changed=True、tracker_conf=None；L2 + 全量轮后视图 > 0；回滚 = revert。
C
pending + post 重建		 reset_runtime 置 regroup_pending；GroupingModule._on_post 在 _handle_save_path_changes 之后一次性消费，对未归组记录重归组。
改动：store 新字段 + grouping post 入口 + 测试；不改内核载荷。		 避开 A 的两个硬伤：post 自带 dry_run；full_round 已在同轮更早发出，不依赖模块装配序。且在 torrents_added 之后，配合「已在 member_to_key 则跳过」不会与首轮 added 管线重复；重建放在 save_path 处理之后可保住缺文件扫描触发。 与 A 相同的 O(N) 重算与 dirty_groups 全量 → 跨组全量展开（一次）；pending 生命周期需定义（启用关闭时消费还是保留，D3）；若 post 前 refresh 抛异常，pending 留到下一成功轮（可接受）；group_key_migrations/transitional_missing_skips 的注释与实现需同步。 同 A/C 单测 + dry-run 无 stop；回滚 = revert。
A vs C：C 严格优于 A（少改内核载荷、无装配序依赖）。若用户否决 B、坚持「显式重建」，选 C 而不是 A。

§04推荐方案与实施就绪（决策已定）

决策：B（保留分组索引），并用测试钉死

理由：A/C 的重算不会产生新的分组键（_files 缓存 + 记录保留，见 §02「关键观察」），却会付出一次 O(N) 键计算/目录 syscall、把全部组标脏触发跨组全量展开，并新增 pending 生命周期；A 还额外要求改内核 full_round 载荷以避免 dry-run 真停种。B 直接消除错误的前提——「分组索引必须随 L2 清空」——改动最小、风险最低，且与项目既有「纯函数派生 → 热重载可续用」的决策一致。

拍板状态：D1=B、D2=保留 group_key_migrations、D4=不并入本轮、D5=不加运行时自检、D6=允许在测试环境做一次非 dry-run 真机验证；D3 随 D1=B 关闭（仅 A/C 适用）。逐条结论见 §05/§06。

§07风险与对策（grilling 拷问记录）

按 grilling 的「设计树」逐条拷问：隐含假设 → 失败模式 → 边界条件 → 并发/单写线程 → 幂等 → fail-fast → 性能/内存 → 回退 → 「测试如何证明不会再次永久空」。每条给出处置：改方案 / 补验证 / 接受风险。

G1 · 「重建 = 从 qB 重新取证」是错的 —— A/C 没有正确性收益

拷问：reset_runtime 不丢 TorrentRecord，而 files() 是持久缓存；重算读到的是同一份文件表。那 A/C 所谓的「重建」到底改变了什么？如果什么都没变，为什么要付 O(N)？

结论：站不住。A/C 只重算同一函数、同样输入的相同结果，额外成本换不到新信息。处置：改方案 → B（并保留 A/C 作为「未来分组键输入进入 L2 变更面」时的备选）。若用户坚持「显式重建」，改选 C，并在测试里写明「重建不刷新 _files 缓存」这一事实，避免后人误以为它提供自愈。

G2 · 全量归组的副作用被低估：跨组全量展开 + 可能的整组停种

拷问：_assign_to_group 每次都会 dirty_groups.add(key)（grouping_mod.py:364），并对组内做大小一致性检查（:367-368）。一次性重归全部记录 = 把所有组标脏 → 同轮 post 的 _check_cross_group_file_conflicts 走全量展开（组×文件，:643-660）+ _check_download_conflicts。若某组原本就大小不一致（外部改文件），重归组会当场停整组。另外 A 的 full_round 无 dry_run 载荷，dry-run 下会真停。

结论：A 存在真实侧效应与 dry-run 破口；C 有侧效应但 dry-run 安全；B 全部规避。处置：D1 默认 B；若选 C，必须在实施轮补「dry-run 下断言语义（zero stop）+ 大库单轮耗时实测」；A 必须给 full_round 补 dry_run 载荷，否则不得采用。大库成本（5000+ 种子的键计算 + _physical_dir syscall）未实测 → 补验证项。

G3 · 一次性 pending 的失败模式：请求位悬挂 / 被启用开关吞掉 / 另一个永久空入口

拷问：全量轮失败（qB 断连、tracker 重匹配抛异常）时 pending 会不会丢？enabled=False 时消费是否导致「启用分组后依旧空」？这算不算把同一个 bug 换个入口留下？

结论：
① pending 不应在「轮首」清除：full_round/post 都是 refresh 尾段，异常轮根本到不了；pending 留存到下一成功轮（与 rules 的 queue_rebuilt 幂等重入同理），可接受。
② enabled=False 时建议无条件消费并记 INFO，避免标志在后续无关全量轮突然生效（D3）。
③ false→true 热重载不触发 L2，确实构成另一个「永久空」入口（D4）：不并入本轮，复验后单独入池；本轮计划只承诺修 L2 路径，测试也不应假装覆盖该入口。
处置：B 天然无 pending；若选 A/C，按上述语义补测试（失败轮后 pending 存活、启用关闭时消费、启用后不误触发）。

G4 · 装配序依赖（A）没有契约保护

拷问：A 依赖 tracker 模块先跑、把 tracker_conf 填好；当前装配序是 tracker（qbmanager.py:227）先于 grouping（:245），但这是注释约定还是可回归的契约？

结论：目前只有装配注释，无守阵测试。处置：B/C 不依赖它（C 在 post，full_round 早已发出）；若选 A，必须补「tracker 注册序号 < grouping」的守阵测试，否则未来一次装配重排就会让恢复静默失效（比原 bug 更隐蔽）。

G5 · 幂等与重复重置

拷问：apply_new_config 可能同时触发 L2 与「未认领段兜底」rebuild_runtime（qbmanager.py:750-767），reset 两次；A/C 的 pending 会不会消费两次、归组两次、停种两次？

结论：_assign_to_group 是「先 leave 再 add」的幂等实现（grouping_mod.py:360-363）；A/C 用「已在 member_to_key 则跳过」可消除重复；pending 用布尔位只会消费一次。处置：接受风险 + 补一条「连续两次 rebuild_runtime 后只重建/消费一次」的单测（A/C 才需要；B 无此状态）。

G6 · 并发与单写线程

拷问：B 让 reset_runtime 少改三个容器，会不会反而破坏「reset 后视图读到一致快照」？Web 线程读取时可能看到什么？

结论：B 减少了 reset 对共享容器的突变（更安全）；view_changed=True 仍保证下一次 flush 全量重建；tracker_conf=None 窗口在 A/B/C 都存在，而 tracker_name 对 None 返回 "Unknown"（record.py:216-227），不会让视图构建抛异常。处置：接受风险（无新增并发面）；实施轮在 dry-run 真机观察一次「保存后首帧」即可。

G7 · 性能与内存

拷问：保留索引会不会让内存长期偏高？A/C 重建期间会不会出现旧/新两份索引叠加？

结论：B 保留的是稳态本来就在内存里的结构（groups/group_sizes），无新增峰值；A/C 是原地 leave/add，不会复制整份，但会把 dirty_groups 一次性填满并在同轮触发跨组展开，峰值 CPU/syscall 更高。处置：B 接受；A/C 需补大库实测（见 G2）。

G8 · 回退路径

拷问：出问题能否一键回到旧行为？有没有磁盘/状态迁移要回滚？

结论：三个方案都是纯内存逻辑，无配置键、无 state 文件格式、无迁移脚本；回退 = revert 单个提交 + 重启（重启本来就会重建索引）。B 的最小 diff 使回退成本最低。处置：接受，无需额外回退开关。

G9 · 测试如何证明「不会再次永久空」

拷问：现有测试只断言 reset_runtime 置 view_changed（test_torrents_store.py:346-352），根本测不到「索引恢复」。新增测试怎么防止假绿？

结论：需要三层：①守阵（reset 后索引原样，防止再次 clear）；②回归（L2 重建 + 全量轮后 groups 与 _build_group_view() 非空，直接复刻受控实验阶段 3）；③成本守阵（files_calls 不增，防止未来改成 A/C 而无提示）。②必须在「未改 S1」时先红，否则证明不了修复。处置：按 S2 落地；②的失败态（阶段 3 视图 0 行）写进测试 docstring 作为反例。

G10 · fail-fast 与配置校验

拷问：方案是否引入新配置键或运行期校验分支？会不会绕过 config.validate_config 的聚合报错？

结论：三个方案都不新增配置键，不触碰 config/schema.py、validate_config 与「新配置键必须登记」守阵。处置：接受（无变更）。

G11 · save_path 同轮变化 + L2 的联合边界

拷问：若某种子在 L2 的同一轮里 save_path 变化，A/C 的重归组会不会吞掉 _handle_save_path_changes 本该触发的缺文件扫描？

结论：A 在 post 之前归组、C 若放在 save_path 处理之前，都会让后者看到「键已正确」而提前返回，丢掉扫描触发；B 保留 group_sizes/member_to_key，原有扫描路径不变。处置：B 无此问题；若选 C，必须把重建放在 _handle_save_path_changes 之后，并补一条「save_path 变化同轮仍触发扫描」的测试。
