1.2 为什么先 hr

  • 对象优先级第 2 位 —— 可行性报告 §11 按「判据密度 × 出错代价」排: ① rules/ ② hr/ ③ config/ ④ core/; infra/ 与 webui/server/ 估值最低。报告 §09 的口径是「先跑一轮拿分数, 分数最低的先补」; 本计划只盯一个包, 由用户选定 hr/(rules/ 优先级更高, 走它自己的一份计划)。
  • hr/ 出错代价是站点侧实打实的处罚 —— HR 判定错 / 做种要求漏算 / infohash 对账错, 后果是账号被站点罚分或封禁, 不是本地状态不一致。判据密度也高: 四行判定表 · 停翻三条件 · 防伪下载 · 频控 · 锁隔离 · 序列化契约。
  • hr/ 是复合体, 最难写全边界 —— 多线程(worker) + 文件锁(store) + 本地 HTTP 通道(server/channel) + JSON 持久化(model) + 站点解析(parse/adapters)。这类代码的测试最容易「偏跑通而非钉边界」, 正是变异测试的靶心。
  • 池构造成本低 —— 15 个 test_hr_*.py 已按模块整齐切分、一一对应目标文件, 不用拼池。
  • 本轮的核心产出是一个刻度, 不是一次修复 —— hr/ 目前没有实测分数; 本轮先给它一个覆盖率给不出的刻度, 用它决定后续要不要在 hr/ 上投入补测。

时长口径要留余量。 0.134s/变异 是在 rules/ 的 6 文件池上量的; 本轮 hr 池是 15 文件 / 457 test fn(config 池才 186 fn), 每条变异要跑一遍的池大 2.5 倍, 单变异成本会更高 —— 实测量级预计 17–25 min, 不是 17 min 封顶。

· 实测显著低于 ≈7,800 → 有一批声明被排除在 mutmut 范围外, 属正常, 记一笔即可;
· 实测显著高于 ≈8,000 → 先核 glob 是否多收了文件 (看 commands run mutants.status 回显的 only_mutate);
· 单轮墙时超 30 min 或 WSL 内存吃紧 → 按 §5 停手点按模块再切, 不硬撑。

S3导出 + 三分类存活变异 (人的动作)

先导出带 diff 的清单与按状态 / 按模块汇总, 再逐条判成三类之一。分类是人的动作, 不是工具输出:

commands run mutants.report -- --target '**/hr/*.py'
类判据处置
真洞变异后行为确实错了, 且没有测试抓得住→ S4 手工确认 → 入池或补测
等价变异变异后行为与原代码在所有输入上等价 (如 @dataclass(frozen=True) → False)记一笔「为什么等价」, 不追
假存活相关测试存在但不在选择池里 (换宽池就死)记一笔; 必要时加进池, 下一轮复跑

提示 —— hr 域的高频等价形态: 展示 / 事件文案字符串、日志级别、异常类型替换、lane_is_* 在有限枚举上的 <= 与 <。高频真洞形态: 停翻条件的边界(早一行 / 晚一行)、频控窗口与日额端点、排序失效判据、from_json 的缺失兜底、URL 白名单的路径前缀、锁有效性的 revision 比较。

S4手工确认 (只认这一个判据)

对每个疑似真洞, 在全套件下逐条 apply → 跑 → 还原, 看是否变红。记法 (每条一行):

字段记什么
位置文件:行 (如 resolve.py:246)
同构变异把 < 改成 <= / 删一行 / 换常量 …
全套件结果N failed, M passed —— 红 = 有测试抓得住(假存活, 只是没进池); 不红且行为错 = 真缺口
commands run mutants.verify -- --from-report <清单> [--only-status survived]

先按硬约束 10 收窄候选 —— 每条 ~15s, 若候选与 config 同量级(~270 条)则 ~68 min。优先文件按「判据密度 × 出错代价」取: service.py > resolve.py / bencode.py / ratelimit.py > channel.py / store.py; 或按变异形态(continue→break / 边界 / and-or 互换 / 语句删除)筛, 再 mutants.verify。

判据边界 (报告 §09 实测): 一个被判 SURVIVED 的变异, 拿全套件手工验证后其实可能是被杀死的(utils.py 那条 return None: 5 文件池报存活, 全套件 3 条新红)。所以「变红」不等于「真洞」, 只等于「池没选到」。

S5补测 (只对确认的真洞)

对确认的真洞加断言 —— 走正常测试流程 (改 tests/, 同步头部 docstring 的「## 测试计划」清单), 补完跑 commands run test.full。补的守阵必须红验(套上同构变异 → 目标用例变红 → 还原复绿, 源码零残留)。

若真洞指向的是代码缺陷 (而非测试缺口), 不在这里顺手改 —— 按范围守恒入池 memory-bank/issues/, 由用户决定什么时候修。

S6复跑

同目标 · 同池 再跑一轮 S2, 看存活数是否下降。换池的数字不可比 —— 池必须与首轮完全一致。

04验收 (可判定)

#判据
1基线切片字段齐全 (缺一即跨轮不可比): 目标 glob · 选择池逐个文件 · 变异总数 · 杀死 / 存活 / no tests / 超时 计数 · 杀死率 · 耗时(墙时 + CPU) · 工具名 + 版本 · --max-children · 机器(WSL 核数) · 手工确认后的真洞数 + 各 issue 链接 · 一行 **Refs:** <任务档案路径>
2三分类后的真洞全部已入池或已当场补测 (无悬空真洞)
3复跑 (同目标同池) 存活数 ≤ 首轮
4补测后 commands run test.full 全绿; 覆盖率不低于基线
5常驻锚 §07 覆盖进度总表的 hr/ 行已同步(日期 / 变异数 / 杀死率与切片逐位一致, 且挂了切片链接)
注意口径: 目标不是「分数涨」, 是「hr 包内不再有不知道为什么活着的变异」—— 每条存活都要有一个分类理由 (真洞 / 等价 / 假存活)。等价变异杀不掉是数学事实, 不追。

05风险与停手点

风险 / 现象停手点与处置
基线不绿停, 先修基线 (test.quick 过) 再跑 —— 工具会直接跳过变异
WSL 整体失去响应wsl --shutdown 救回 → 降 --max-children 重来; 核目标 glob 是否多收了文件
hr 池比 config 大 2.5x, 单轮明显超 17 min超 30 min 或内存吃紧 → 按模块再切: 先跑 service.py 单模块(池 = test_hr_service.py + test_hr_multisite.py), 再 resolve/bencode/parse, 分多轮而不是硬撑一整包
池越宽内存越紧回 §2.3 的定向 15 文件池 —— 宽池代价落在内存不在结论
no tests 整片集中若一批变异落在池没碰过的函数(如 events / model.from_json) → 先补进池再复跑, 否则那批连三分类都做不了(硬约束 9)
--deselect 表随测试拆分漂移本轮 hr 池无源码文本守卫, 预期不触发; 若基线仍报文本层守阵红, 先核 set_conf.py 的 DEFAULT_DESELECT 路径是否漂移
把存活清单当缺口单停 —— 必须先 S3 分类 + S4 手工确认; 假存活比例不小
换池后跨轮比存活数禁止 —— 池是变量, 数字不可比; 池必须写进切片
拿 mutmut 分数与 gremlins 分数横向比禁止 —— 分母不同 (前者含 no tests)
计划的边界: 本计划只写「怎么修、为什么这么修」, 不实施。执行时按 memory-bank skill 立任务档案, 轮次进档案; 计划本身拍板后冻结 (改版 = 同文件加变更记录 + 抬 doc-updated)。
