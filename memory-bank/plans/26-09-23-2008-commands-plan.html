Auto-QB · Agent 基建 · 工程方案

commands — 项目命令统一调用面

项目命令的现状不是"没有规范"，而是同一事实有多份副本、写法互不相同：以一条测试命令为例， 仓库里有 8 处副本、5 种写法，其中只有 1 种在本工具 shell 里真正生效 —— 而它恰好是"看起来最不正常"的那条。 本方案的设计初衷是三条：减少出错（把命令固定下来，不让执行者再拼）、 隐藏复杂细节（环境前缀、远端名、顺序约束都不进执行者的视野）、 降低 token 消耗（不必为了找一条命令去读整份文档）。 做法是把 skill 缩成纯引擎（零项目事实、零领域逻辑）—— 它只认识「包」与「命令」， 连"提交"这件事都不知道；包是黑盒，配置自持。 配置层只留一种形态 —— 包：每包一个 config.toml 作接口面，引擎自动扫描， 想加命令只有"放进某个包"这一条路可走。 提交流水线（my-commit-flow）就是这么活的 —— 从 skill 降为一个可整包复制的包，自己的配置原样带着走。 路由不写死在 skill 里，而是按当前任务逐级查出来（高频命令标常显直接浮出），好让每个仓库加自己的路由而不必改 skill； 并教 agent 遇到可复用的有价值命令时自动收录进包，再用一条反漂移闸门让文档里的手抄命令直接判红。

01

问题定义与现场证据

要执行一个项目动作（跑测试、同步分支、重建索引、起 WEB UI），执行者得先去某份文档里把命令抄出来。 问题是同一命令被抄进了很多份文档，且每一份的写法都不一样 —— 于是"用哪一份"变成了一个需要判断的问题， 而判断依据（哪种写法在本 shell 生效）并不写在命令旁边。

证据一：一条命令，8 处副本、5 种写法

以 uv run pytest tests -q 为例。5 种写法里有 4 种不满足项目自己的约定，而其中 POSIX 前缀那一条 是唯一看起来"正常"的 —— 它是多数人凭直觉会写出来的形式。

位置写法判定
AGENTS.mdREADME.md · memory-bank/SKILL.md · .github/copilot-instructions.md · ci.yml uv run pytest tests -q 缺 TMPDIR
memory-bank/testing/run.md TMPDIR="R:/Temp/auto-qb/tests" uv run pytest POSIX 前缀，实测 rc=1
.commit-flow.toml（闸门） set "TMPDIR=R:/Temp/auto-qb/tests" && uv run pytest tests -q --no-cov 唯一生效
pitfalls/testing/tmpdir.md TMP=H:/… TEMP=H:/… uv run pytest 第三种变量组合
.workbuddy-ai/memory/2026-09-21.md TMPDIR=D:/tmp_pytest uv run pytest 第四个目录

同样的发散还有 git 同步：AGENTS.md 写 git fetch gitee develop + merge --ff-only， memory-bank/SKILL.md 写 git fetch <主线远端> <分支>，而 my-commit-flow/SKILL.md 的「最常见组合」一节教的是 提交 → rebase → 推送 —— 与 AGENTS.md 的 rebase 禁令直接冲突。

证据二：危害已经实际发生

pitfalls/testing/tmpdir.md 里该条 复发 +1，记录的未命中原因是 "读了文件、也知道要设 TMPDIR，但只给自己手工跑的测试带了，没意识到闸门是配置里的另一条执行路径"。 处置结论是「改配置比改记忆可靠」。本方案正是把这条结论从"一个闸门"推广到"全部命令"。

现有防线评估 .commit-flow.toml 已经证明「外置配置 + 机检闸门 + 缺配置就停手」这条路走得通，且它把测试命令收口得很好 —— 但那一条只覆盖提交这一个动作。其它命令（开工同步、知识库索引、dev 服务、文档机检）至今没有归属， 仍然靠每份文档各自抄一遍。
02

初衷 · 目标 · 错误模式

三条设计初衷（约束级，不是口号）

初衷具体含义落成什么机制
减少出错 执行者不再有"写错的机会"—— 命令固定、参数固定、顺序固定 命令单点定义 + requires 检查命令 + 反漂移闸门
隐藏复杂细节 环境前缀、远端名、代理参数、顺序约束不进执行者的视野；它只管"调哪个" 细节沉到包里；run 默认不 dump 命令
降低 token 消耗 不必为了找一条命令去读整份文档；不必让命令本体在上下文里来回搬运 包式配置 + 路由生成 + 信息预算（见本节末）

目标

#目标判据
G1agent 侧只认 task idSKILL.md 里不出现任何可直接执行的命令；执行时不需要拼参数、不需要回忆前缀写法
G2命令本体单点定义改一处即全局生效；文档里只剩 commands run <task>
G3支持超出单行的复杂命令task 可指向项目自带脚本，不必把逻辑压成一行 TOML 字符串
G4my-commit-flow 降为配置它不再是 skill，而是 .commands/my-commit-flow/ 一个包；引擎里不认识"提交"
G5反漂移文档里手抄的命令被机检判红，而不是靠人记得别抄
G6降低 token 消耗执行一个动作的上下文成本从"读整份文档找命令"降到"当前层级一行 + 一次调用"；预算随层级收敛，不随命令总数增长
G7命令集能自己长大agent 遇到可复用的有价值命令时按协议自动收录，不必等人下指令（见 §06）
G8路由可随配置生长新增路由只改包 —— 查询式路由没有生成物要重跑；SKILL.md 与 skill 体积恒定，仓库特有路由不污染通用 skill（见 §05）

非目标

#非目标理由
N1不做通用任务编排 / 构建系统不重造 make / npm scripts；只收"本项目会话里反复要跑"的命令
N2不替代 CI.github/workflows/ci.yml 保留原样，它是另一条独立执行路径
N3不收一次性调试命令见 §06 收录判据：三条任一命中才收
N4不改动生产红线文件config.yml / auto-qb-data/ 仍是红线，只在新包配置里继承这条声明

初衷一：减少出错 —— 错误模式与对应防线

"减少出错"要落成具体机制，就得先列出到底会怎么错。下表每一行都是本项目已实际发生或已记录的失败形态， 第三列是本方案给出的防线 —— 注意防线不在人的记忆里，而在命令本身或机检里。

错误模式现场形态本方案的防线
抄错写法 POSIX 前缀 TMPDIR=… cmd 看起来最正常，在本 shell 实测 rc=1 命令只有一处定义，且 note 写明"为什么必须这样写"
漏环境前缀 直接 uv run pytest → 收尾抛 PermissionError … pytest-current，测试其实全过 前缀内置在 task 里，调用者看不见也不用管
顺序错 测试放在回写知识库之后 → 分不清红的是代码还是文档；格式化放在暂存之后 → index 与工作区不一致 requires 检查命令 + 流程内置在脚本里
用错远端 历史 clone 的 origin 可能是 GitHub 镜像，按名字取会推错 从 config.toml 的 main_host_mark 按 URL 特征探测，不按名字
忘同步就开工 在落后分支上改代码，提交时才撞车 sync.start 机检，落后即 STOP；结果可贴进会话回复，跳过会留可见空洞
用了不生效的写法却无人发现 无任何信号 —— 直到某次拿到假红 反漂移闸门（§07 W4）

初衷三：降低 token 消耗 —— 信息预算

省 token 不能靠"写得简洁"，要靠把信息放在正确的层级、并规定谁在什么时候才读它。 本方案给四层各定一个预算：

层放什么什么时候读预算
SKILL.md四个子命令 + 引导 + 收录协议每次加载 skill 时恒定大小，不含路由与命令
list 输出只出当前层级：包 + 常显命令，或某级的子包要执行动作时不出命令本体，也不铺平
run 输出结果摘要与关键行常规路径只走这一层不 dump 完整命令
包内文件config.toml（接口面）+ 包私有配置（如 my-commit-flow 的 .my-commit-flow.toml）引擎只读前者；后者由包脚本自读人不读 —— 排障才 show
show / note / pitfalls展开后的命令、环境陷阱判据、原理排障、自证、迁移时才读低频，可放宽
风险自适应的详略 「不 dump 命令」不能一刀切 —— 高风险动作恰恰最需要先自证。规则是： 带 requires 或标 risky = true 的 task，run 先打印将要执行的命令再执行； 其余 task 只回结果。这样"自证"的成本只花在真正需要它的地方（my-commit-flow.commit 这类）， 而高频低风险的 test.full / kb.index 不付这份钱。
03

解法空间 A–C

A单文件配置：.command-flow.toml未采用

照搬 .commit-flow.toml 的形态，一个根级 TOML 装下全部 task。优点是简单、与既有习惯一致。 缺点致命：复杂命令只能压成超长单行字符串 —— 现有那条 pytest 闸门已经是 set "…" && … 的形态， 再复杂一点（多步、带条件、要解析输出）就没法写了；也没有地方安放项目自带的包装脚本。

B独立目录：<仓库根>/.commands/采用

配置层只放包：每个包一个 config.toml 作接口面，包内其余文件（私有配置、脚本）引擎一概不读； 引擎自动扫描 .commands/*/config.toml。四条收益：①命令按包拆分，单文件不会长成几百行； ②复杂命令有正规去处，不必压成一行；③包就是复用单位，且是黑盒 —— 整包复制到别的仓库即可用，连它自己的配置一起带走；④引擎保持零项目事实、零领域逻辑，可移植。

C纯脚本化：每条命令一个脚本未采用

最灵活，但每加一条命令都要写代码：改一个超时、加一个 task，都得走"写 Python → 提交"的循环， 而 agent 无法自助。收益（灵活）远小于代价（把配置问题变成开发问题）。

取舍要点 B 与 C 的差别不是"要不要脚本"，而是脚本是常规路径还是兜底路径。B 让绝大多数 task 停留在包的声明式配置里 （改超时、加 task 都是改 TOML），只在命令确实复杂时才落到脚本 —— 这与 .commit-flow.toml 把闸门写成 声明式 [[gates]]、把真正复杂的流程（合流预判、ref 三处核对）交给脚本的做法同源。

B 里的"命令包"是关键一格：它让"成套的复杂命令"既能复用、又不落进引擎 —— my-commit-flow 的四个脚本正需要这个位置，否则就只能塞进 skill（把领域逻辑带进引擎，即 v1.0 的错误）。
04

推荐方案：纯引擎 + 配置层

三层职责

这条边界是 my-commit-flow 已经验证过的：流程（禁 add -A、ref 三处核对、推送顺序）写死在代码里， 项目事实（红线文件、闸门命令、远端名）一律外置，缺配置就停手、不猜默认值。本方案把同一套骨架从"提交"扩到"全部命令"， 并把边界推到底：引擎里连"提交"这件事都不知道 —— 它只认识「包」与「命令」；my-commit-flow 是个黑盒：自带配置、自己的脚本自己读，引擎连"它有配置"都不需要知道。

与 v1.0 的关键修正：my-commit-flow 不是"被吸收"，而是"降为一个黑盒包" v1.0 打算把 preflight/commit/verify_ref/push 迁进 skill 的 scripts/ —— 那等于把领域逻辑写进了引擎：引擎从此认识"提交"这件事，也就有了项目味、不再可移植。 修正后的归属是：它成为一份自持配置的黑盒包 .commands/my-commit-flow/ —— 原配置改名 .my-commit-flow.toml 原样搬进去，由引擎自动扫描到。 这正是"当作 commands 的配置存在"的落地方式。

目录结构

# ── 引擎：可移植。只认识「包」与「命令」—— 不认识任何领域概念 ──
.agents/skills/commands/
├── SKILL.md                    # 恒定大小：四个子命令 + 引导 + 收录协议
│                               # ⚠ 不含路由表本体、不含任何命令、不含项目事实
└── scripts/
    ├── run.py                  # dispatcher: run / list / show / add
    ├── _config.py              # 扫描包树 + 校验 + 占位符展开
    └── _tree.py                # 层级视图：按 包 → 子包 → 命令 逐级列
                                # ⚠ 引擎里 grep 不到 gate / red_line / commit / ship 任何一个词

# ── 配置层：只放包。顶级包自动扫描 = .commands/*/config.toml ──
<仓库根>/.commands/
├── test/                       # 顶级包：一个包 = 一个职责
│   └── config.toml             # [pack] + [tasks.*]（+ 可选 [packs] 注册子包）
├── kb/                         # 知识库：索引 / 会话切片
│   └── config.toml
├── dev/                        # 开发服务：WEB UI / 仿真 / 浏览器冒烟
│   └── config.toml
├── env/                        # 环境：uv sync / 自检
│   └── config.toml
├── doc/                        # 文档机检：链接 / 上下文上限
│   └── config.toml
└── my-commit-flow/             # ← 那个 skill 退场后以包形态继续存在
    ├── config.toml             # 接口面：注册子包 + 声明本包 task
    ├── .my-commit-flow.toml    # ← 原 .commit-flow.toml 原样搬入：闸门 / 红线 / 远端
    ├── README.md               # 纪律与原理（排障 / 迁移时才读）
    ├── scripts/                # preflight / commit / verify_ref / push / _ship_config
    │                           #   ← 它们自己读 .my-commit-flow.toml
    └── ship/                     # 子包：在上级 config 的 [packs] 里注册
        └── config.toml

没有 core 包 —— 一个包一个职责，拆开之后没有任何东西还需要一个"约定名的杂项包"。 也没有路由表文件 —— 路由不落盘，改为运行时逐级查询（见 §05）。

层级：子包

二级 / 多级不是靠"命令上的分组字段"，而是包本身可以嵌套 —— 包是复用单位， 那么"一组成套的包"自然就该是一个子包。

概念是什么怎么声明
顶级包一级 一级视图就是"有哪些包、各自管什么事" 不需要注册 —— .commands/*/config.toml 存在即被发现
子包二级 / 多级 包内的包，深度不限；子包自己也是完整的包（可再嵌套） 在上级 config 的 [packs.<名>] 里注册
enabled 显示 / 禁用。禁用的包不参与视图与执行，list --all 会标出它 顶级包写在自己的 [pack]；子包写在上级的注册表里
常显pin 标了 pin = true 的命令浮到父级列表，不必进入所属包就能看到 task 的 pin
为什么子包要"注册"而不是也自动扫描 ①上级对下级要有控制权（启不启用），自动扫描给不了； ②注册表本身就是"这个包由哪些子包组成"的清单，一眼可见； ③enabled 只有一处声明（子包不自己写）—— 避免两处事实源各说各话。

扫描与冲突规则

规则内容为什么这么定
顶级扫描 .commands/ 下的一级子目录，只认 <包>/config.toml 不做递归 —— 往下走必须经过上级的注册表，否则"谁控制谁"就没了
子包路径 <父包目录>/<子包名>/config.toml，名字由父的 [packs] 给 路径由注册表决定，不是靠目录名猜
包名 取目录名；[pack].name 与目录名不一致即 STOP 两处名字各写一份，迟早会漂移
包已确认 [pack].confirmed 缺失或为 false → STOP 包是复用单位，拷一个包过来往往没核对过 —— 这条挡住"照单全收"
task id 冲突 全树唯一；两个包声明同名 task → STOP，不静默覆盖 run <id> 要能全局直达，重名会让"调的是哪个"不可知
包的粒度 一个包 = 一个职责；判据是"这些命令是否总因同一个原因被一起想起" 拆得动才复用得动：整包复制 / 整包删除

一个包 = 一个黑盒

层引擎知道什么
<包>/config.toml接口面 引擎唯一读的文件：这个包叫什么、管什么事、有哪些子包、提供哪些 task
包里其它一切如 .my-commit-flow.toml / README.md 包私有 —— 引擎不读、不扫描、不知道它们存在
包脚本 引擎只知道"有个脚本要跑"，并注入 COMMAND_FLOW_PACK_DIR 告知本包目录； 脚本自己去找自己的私有配置
所以 my-commit-flow 的配置一行都不用改 它原来那份 .commit-flow.toml 改名成 .my-commit-flow.toml 原样搬进包里 —— [[gates]] / red_lines / 远端探测 / staged_panic 全留着， 它的 _ship_config.py 照旧读它。没有任何东西被"融入"引擎的配置： 引擎不解析、不校验、甚至不知道这个文件存在。

由此推出的归属调整：开工同步（sync）也归本包 —— 它是 git 协作领域的事，且 AGENTS.md 里的开工自检本来就指向 my-commit-flow 的 preflight.py --check-started。这样远端名只在一处声明，不会两边各写一份。

引擎 schema 的边界判据

判据（一句话） 引擎认识的键，必须对任何仓库、任何命令都成立。只要某个键的含义依赖"我们在做什么事" （提交 / 同步 / 测试 / 发布），它就属于包，不属于引擎。
键 / 文件含义依赖"做什么"吗归属
[pack]name / when / enabled / version / origin / scripts_dir / confirmed 否 —— 只描述包自己（when 是"这个包管什么事"，用于按任务选包） 引擎 schema
[packs.<名>]enabled 否 —— 只描述"本包由哪些子包组成、是否启用" 引擎 schema
[tasks.<id>]run / script / args / when / note / timeout / requires / risky / pin 否 —— 只描述"怎么跑一条命令"与"是否常显" 引擎 schema
[[gates]] 是 —— "提交前跑什么" my-commit-flow 包私有
red_lines / warn_lines 是 —— "不得进暂存清单" my-commit-flow 包私有
远端寻址main_candidates / main_host_mark / mirror* 是 —— "往哪推 / 从哪拉" my-commit-flow 包私有（原样留在它自己的配置里）
开工同步 sync 是 —— git 协作领域 my-commit-flow 包

引擎 schema 只有三块：[pack] / [packs.*] / [tasks.*] —— 三块都只描述"包与命令的结构"，与"做什么"无关。 占位符只剩三个通用的：<root> / <skill-dir:NAME> / <args> （"哪些文件改过"是 git 概念，由包脚本自己算）。

四个子命令

子命令作用为什么必须有
run <task> 先校验前置条件，再执行；超时按失败计。常规路径只用它 执行路径唯一，requires 不满足即 STOP；默认只回结果摘要，不 dump 命令（省 token + 隐藏细节）
list 逐级列出当前层级：一级是包与常显命令，下钻到组、再到命令；--all 才全量 agent 靠它按当前任务逐级定位；不出命令本体，也不铺平（见 §05）
show <task> 打印展开占位符后的真实命令，不执行 排障与自证用（低频）。没有它，agent 在需要核对时仍得靠猜 —— 只是把猜的对象从命令换成了 task id
add 把一条命令收录进配置（默认 dry-run，--write 才落盘） 本方案的自生长入口 —— 让命令集能自己长大，而不是等人维护（见 §06）
详略策略（省 token 与减少出错在这里折中） run 默认不打印命令，但 带 requires 或 risky = true 的 task 例外： 它先打印将要执行的命令再执行。show 与 note 的完整内容只在排障时读， 原理与陷阱判据留在 memory-bank/pitfalls/，由 note 字段指针过去 —— 与既有 pitfalls_index「把约束接到决策点上」的做法同源。
不降级原则（沿用 my-commit-flow 的既有裁决） 引擎 schema 违规（类型错 / timeout 非法）/ 占位符展不开 / requires 的命令非 0 / 包级 confirmed = false —— 一律 STOP（退出码 1）；未知顶层键是 WARN 不是 STOP（它可能正是包私有配置，见上节）， 不静默退回"只打印给人"。理由与 _ship_config.py 里写的一致：静默失效比报错坏得多 —— 报错会立刻被发现，静默失效会让人以为"该跑的跑过了"，而且 WARN 会被淹没在十几行检查表里。 代价是新增配置键必须先加进白名单，否则一写就挡住执行 —— 接受。
05

逐级路由：按任务下钻

把路由铺成一张平表，命令一多就必然臃肿 —— 而且它把"提交时才用的命令"和"改完代码就要用的命令" 混在同一张表里，不同任务适合的命令本来就不该并排。执行者要的从来不是"看完全部命令"， 而是"当前这件事该调哪个"。

所以路由不落盘、不铺平：改为运行时逐级查询，命令按任务域分隔在包里，高频的标常显。

视图（逐级）

引导（写进 SKILL.md，agent 侧唯一要看的东西）

  • 要执行动作 → list：看有哪些包、各自管什么事，以及各包的常显命令
  • 按当前任务选包 → list <包>：看这个包的本级命令与子包
  • 还没定位 → 继续下钻 list <包>/<子包>（深度不限）
  • 已经知道 id → 直接 run <id>，跳过前面所有步骤
  • 排障 / 迁移 → list --all：一次性列出全树（含被 enabled = false 禁用的，标出来）
"不臃肿"靠的是分层，不是靠写得短 一级输出里只有包与常显命令，所以命令总数从 10 条长到 200 条， 一级视图仍然是"几个包 + 几条常显"。list --all 是兜底，不是入口 —— 它存在的意义只是排障，一旦被当成常规入口，臃肿就会从那张表搬到这里。

为什么去掉路由表文件

生成的路由表（v1.5）逐级查询（本方案）
规模 必须把所有命令铺平在一份文件里 ⇒ 必然臃肿 只出当前层级 ⇒ 与命令总数无关
新鲜度 是副本，会与包脱节，需要 --check 闸门兜 实时读包，不可能过期，也不需要那条闸门
任务相关性 不同任务的命令混在一张表里，要自己筛 按任务域天然分隔（包 → 子包）
代价 多一份要维护的生成物 + 一条闸门 + 一个子命令 少一个"可 diff / 可静态引用"的视图 ⇒ 由 list --all 兜底
与 G8「路由可随配置生长」的关系 目标不变，机制换了：v1.5 靠"生成器 + 闸门"保证路由跟得上配置； 本方案把路由变成查询而非副本，于是"跟得上"不再需要机制去保证 —— 它天然成立。
06

配置的自生长：收录协议

如果只是把现有命令搬进配置，那这套东西仍是一份等人维护的清单 —— 遇到新命令照样没人收， 几周后又退回"命令散落各处"。所以 SKILL.md 里必须写清一条协议： agent 遇到可复用的有价值命令时，自己把它收录进配置。 这是本方案与"又一份命令文档"的分水岭 —— 前者会自己长大，后者只会变旧。

什么时候该收录（三条任一命中）

#判据怎么判
1 重复 同一条命令在本会话（或近几轮）出现第二次 —— 第二次出现就是"它会再出现"的最强信号
2 难拼 拼装它需要 ≥2 个环境前缀 / 参数，或得先查文档才知道怎么写 —— 查文档这一步本身就是成本
3 易错 存在"看起来正常但不生效"的写法（如 POSIX 前缀）—— 这类错误没有提示，只有假红

命令的归宿（收录前先选对包）

情况归宿放哪个包
会话固定流程的一环 / 反复要跑 写进包的 config.toml 的 [tasks.*] —— 改超时或加 task 都只是改 TOML 本仓库特有 → 按职责归到 test / kb / dev / env / doc
逻辑复杂：多步、要解析输出、要条件分支 落到该包的 scripts/，task 用 script = 指过去 同上
成套的、别的仓库也用得上 同上，但单独成包 —— 包是复用单位，整包复制即可带走 新建包（如 my-commit-flow）
只跑一次 / 纯调试 不收录 —— 直接在对话里跑。配置保持瘦，是它能被信任的前提 —

收录动作

# 默认 dry-run：只打印将要写入的 TOML 片段与落点文件，不落盘
run.py add --id test.one --pack test \
  --run  'set "TMPDIR=R:/Temp/auto-qb/tests" && uv run pytest <args> -q -n 0' \
  --when "排查单个文件（单文件用 -n 0，并行会慢在 worker 启动上）" \
  --note "必须 cmd.exe 写法 —— 本 shell 的 POSIX 前缀不生效 (rc=1)"

# 核对落点与片段无误后再落盘；落盘后自动做两件事：
#   ① show 自证展开正确  ② 它立刻出现在 list 的对应层级里（查询式, 无需重跑生成物）
run.py add ... --write

# --pin 只在"每次会话都要用"时才给（如 test.full / 开工同步）；滥用等于把平面表搬回一级
# 落盘即入库改动 ⇒ 会走提交闸门（反漂移闸门也在那里），天然有复核点

为什么 --when 与 --note 是必填

  • --when 是下次能被发现的唯一线索。缺了它，这条 task 在 list 里只剩一个 id， agent 下次遇到同样场景也认不出来 —— 等于没收录。
  • --note 是环境陷阱的判据。缺了它，下次有人（含 agent）"顺手把命令写正常点"， 就退回那个不生效的 POSIX 写法 —— §01 那 5 种写法正是这么长出来的。
两条必填字段其实是同一件事 它们把"这条命令为什么长这样"从执行者的记忆搬到了包里。 这正是 §01 那条复发坑的结论 —— 改配置比改记忆可靠。

防滥用（避免配置变成垃圾桶）

机制作用
add 默认 dry-run 落盘前先看到"写进哪个文件、写成什么样"，避免手滑污染配置
强制 --when 非空 说不出"何时用"就说明这条命令还没有场景 —— 那它不该被收
--id 已存在则拒绝覆盖 改既有命令必须走 edit，避免 agent 在不知情时改写已有语义（那是另一类出错）
配置是入库文件 收录 = 一次代码改动 ⇒ 过提交闸门 ⇒ 天然有复核点，且改动可追溯
三条判据同时是上限 收录是有判据的动作，不是"看到就收"。不满足判据的收录在复核时会被打回

风险与边界

风险成因对策
配置漂移本方案最大的失败模式 新 skill 上线后，文档里仍有人（含 agent）手抄命令 → 变成第 9 处副本 W4 的反漂移闸门；它是本方案的必要条件，不是加分项
过渡期双配置 W1–W2 期间提交闸门仍靠 .commit-flow.toml，而包内的 .my-commit-flow.toml 已就位 —— 两处可能各自演化 过渡期新包只声明不启用闸门（或干脆先不写）；W3 一次迁完并删旧文件，闸门始终只有一处生效
命令写在包外包形态的新失效模式 有人（含 agent）把命令塞进 .commands/ 顶层的散文件或别处 —— 引擎扫不到，静默失效 add 只能落到包里（--pack 不存在即拒绝），是唯一的收录入口；W4 的文档收口让手抄形态判红
层级过深 / 常显滥用 组套得太深会让人下钻到迷路；pin 滥用则等于把平面表搬回一级视图 两条纪律：组不超过两级；pin 只给"每次会话都要用"的命令 —— 由 W4 的层级完整性检查兜住
引擎被领域逻辑污染v1.0 的原错误 "顺手把 my-commit-flow 的实现放进引擎"最省事，一旦开了头，引擎就有了项目味、不再可移植。配置也是同一类越界：v1.4 曾把闸门与红线写进包的 config.toml，等于让 commands 的配置面承载 commit-flow 的领域 W5 的引擎纯净度机检：引擎目录 grep 项目词必须为空；判据写进 AGENTS.md
过度设计 把只跑一次的命令也收进来 → 配置膨胀、维护成本超过收益 收录判据（三条任一命中才收）：①同一命令在仓库出现 ≥2 处 ②带环境前缀陷阱（如 TMPDIR） ③属会话固定流程的一环
迁移期提交流程断档 W3 删旧配置时若闸门漏迁，提交前就没有机检了 删除前逐行比对两侧检查表；旧配置的 confirmed / 红线 / 闸门条数作为迁移 checklist
自生长失控配置变成垃圾桶 "自动收录"若无判据，会把一次性调试命令也收进来 → 配置膨胀、信噪比下降，最后没人愿意读 三条收录判据 + --when 必填 + --id 拒绝覆盖 + 落盘走提交复核（见 §06 防滥用）
脚本冒烟闸门误伤 新脚本若没有 --help，既有闸门会判红 W1 起所有新脚本用 argparse 提供 --help，并在 W1 的 verify 里先跑一遍
边界 本方案不引入新的 git 操作，也不放宽任何既有红线 —— 它只改变"命令从哪里取"。 requires 里的检查命令（如 git diff --quiet）是把既有纪律变成机检，不是新增约束。 跨仓库操作的红线（需显式「授权」）与提交口径（"提交" = commit + push）全部保持不变。
09

验收标准

  • A1SKILL.md 里不存在任何可直接执行的命令，也不含路由表本体 —— 只有四个子命令的用法、引导与收录协议；路由由 list 逐级提供（与 §05 一致）。
  • A2同一条命令在仓库里只有一处定义（某个包里）；grep 全仓不再出现手抄形态。
  • A3run.py show <task> 能打印展开后的真实命令，且与配置逐字一致。
  • A4包写错（未知键 / 非法超时 / 残留占位符 / 包级 confirmed = false）一律 STOP，退出码 1，不静默降级。
  • A5反漂移闸门生效：文档里手抄一条已收录命令 → 判红；改成 task id → 转绿。
  • A6my-commit-flow.* 全链路等价于原 skill：闸门条数与红线条目逐条对齐，全量测试通过。
  • A7.commit-flow.toml 删除后无悬挂引用；my-commit-flow 目录已删除，其能力以 my-commit-flow 包形态存在（含它自己那份 .my-commit-flow.toml）。
  • A8全量测试基线不退化（test.full 实测数字与 memory-bank/testing/baseline.md 对齐，无回归）。
  • A9token 预算达标：SKILL.md 有硬上限且不含任何可直接执行的命令；常规 run 不 dump 完整命令；只有带 requires / risky 的 task 才先打印命令。
  • A10收录入口安全：add 默认 dry-run；--when 为空即拒绝；--pack 指向不存在的包即拒绝；--id 已存在时拒绝覆盖；落盘后自动 show 自证。
  • A11自生长真的发生：在一次真实会话里，agent 遇到重复出现的命令时自发调用了 add，且未等人下指令 —— 这是 G7 的唯一有效判据。
  • A12细节确实被隐藏：执行 test.full / my-commit-flow.push 的全过程中，上下文里不出现 TMPDIR 前缀、远端名、代理参数等实现细节。
  • A13引擎零领域逻辑：引擎目录 grep 项目词（提交 / 测试 / 知识库 / gate / red_line / commit / ship / gitee / TMPDIR）为空；把 my-commit-flow/ 整包移走后引擎仍能 list / run 其它 task。
  • A14逐级路由可用：list 只出当前层级，能按 包 → 子包 → 命令 逐级下钻，pin 的命令浮到父级列表；新增命令只改包、无需重跑任何生成物，SKILL.md 与 skill 体积不变。
  • A15配置层只有一种形态：.commands/ 下全部条目都是包（没有生成物、没有散落文件）；包名与目录名不一致、或两个包声明同名 task，均 STOP。
  • A16引擎 schema 只有两块：[pack] / [tasks.*]；占位符只有 <root> / <skill-dir:NAME> / <args>；引擎代码与文档里不出现 gates / red_lines / main_candidates / commit / ship 等任何领域词；闸门与红线只存在于 my-commit-flow 包内的 .my-commit-flow.toml，由包脚本自读。
