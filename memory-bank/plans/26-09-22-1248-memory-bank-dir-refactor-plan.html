四个失效机制（全库通用，不止 pitfalls）

  • 体量决定了它不被读。「必读」清单里放着 60~80 KB 的文件，最优行为必然是跳过 —— 这不是纪律问题，是预算问题。
  • 检索键错位。作者按主题组织（「任务队列」「已实现」），使用者按动作检索 （我要加一列 / 我要跑测试 / 我要查一个配置键）。没有「动作 → 文件」的映射，找不到就等于不存在。
  • 主题已经串了。systemPatterns 的「任务队列」节里塞着三节 WEB UI 内容 （21,406 字符）；modules 的模块表混着前端契约 —— 说明「按主题切分」这件事本身没被执行。
  • 零机械后果。tasks/ 有 8 条守卫、issues/ 有生成器 + 闸门， 其余文档一条守卫都没有：写超了、写了没人知道、写了不照做，都没有代价。

两条反向实证

「提交后必查 ref 三处」有 verify_ref.py 兜底、「脚本改名漏改的未定义名」有 test_preflight.py 的 ast 静态检查兜底 —— 这两条此后一次都没再犯。反过来，写在文件里、 只靠人记的 git rebase 禁令在工具 shell 里出了三次事故（09-21 两次、09-22 一次）， 第三次正是照通用 skill 踩的。

所以目标不是「拆文件」本身：能变成红的，从文本搬进守阵；搬不动的， 必须在做那个动作的决策点可见。

02为什么是「分类 + 二级指针」

把 400+ KB 的知识库重新编排，至少有四种排法。逐个排除之后落在「分类 + 指针」上。

方案检索键为什么不选
保持单文件 + 顶部 TOC章节名 体量没降。TOC 只解决「跳到哪」，不解决「读得起」
按日期 / changelog 归档时间 使用者的键是「我正在做的动作」，不是「上次改动是哪天」
每节一个文件（平铺，像 issues/）文件名 / grep 几百个文件、无归类；「看一类」退化成打开 30 次；目录列表本身就不可读
分类 + 指针（本方案）动作 → 索引 → 文件 采用：目录与索引承担「按动作定位」，主题文件小到读得起，索引是生成物、可守

指针有两条硬要求（写进第 03 节规范）：

  • 索引一屏可读（≤ 3 KB）—— 会话开始读得起，才有资格叫「入口」。
  • 每条指针含触发词（「推送」「加列」「写测试」「查配置键」这类动作词）—— 能用 grep 命中，才可能在没读索引时被找到。

层级由规模决定，不强制两级。pitfalls/ 有 7 个类、250+ 条目， 所以是「L1 全库指针 → 类索引 → 主题文件」；testing/ 只有一个层次， 就是「_index.md → 主题文件」。同一个生成器两种都能出。

03统一配方：五步 + 元数据 + cap 分级

这部分是可复用的规程 —— 任何一份超标文档、包括将来新增的，都按同样五步处理。 第 05、06 节只是把它逐份实例化。

五步配方

  1. 量：按 ## / ### 切段统计字符数，对照本节的 cap 分级定目标文件数； 同时统计该文档的引用处数（决定存根的必要性）。
  2. 建：建 <文档>/ 目录；每个主题文件头部写元数据（见下）； 原句照搬，不重写内容 —— 只做三件事：按动作补 触发、长叙事压成一句「为什么」、 散落的实测数字与守阵名收进字段。
  3. 生成：跑生成器产出 _index.md（不许手写）；原文档位置留 ≤1 KB 存根 （一句话说明「已迁至 <目录>/_index.md」）。
  4. 接线：更新路由（memory-bank/README.md 细路由 + AGENTS.md 粗路由）、 改活文档里的互引、把 skill / DoD 里的路径改成新目标。
  5. 守恒核对：迁移前的条目/段落清单（md5 + 字节）与迁移后逐条比对， missing 必须为 0；守卫与闸门转绿。

主题文件的头部元数据（生成器的数据源）

# <标题>                                  ← 索引行用它
> 摘要: 一句话说清「这文件治什么病」           ← 索引行用它
> 触发: 推送, 同步, ref 核对                 ← 动作词, 供 grep 与路由

正文…（叙述型文档就是原来的段落；pitfalls 类是字段化条目: 触发 / 判别 / 处置 / 守阵 / 复发）

条目型与叙述型共用同一套元数据 —— 这是「全库一套机制」的关键：新增一个主题文件 = 写三行头 + 跑生成器， 不需要新脚本、不需要改守卫。

cap 分级（首个匹配生效，口径同 check_context_caps.py：按字符数）

角色上限理由
索引（**/_index.md）3,000 必须一屏可读；它随库增长只增行数、不增厚度
触发式条目集（pitfalls/*）6,000 读法是「扫描找一条」，比通读更贵，所以比一般主题更严
常青主题文档（叙述型）10,000 ≈4k token，一次通读可接受；systemPatterns / modules 的目标档
参考速查（config-reference / rule-system）12,000 它们是「查表」不是通读，允许更厚
易变层（activeContext.md）12,000 会话开始必读，必须硬顶住；超了就是内容该外迁的信号
任务档案（tasks/*.md）24,000 含「历史会话纪要」段 ≤8,000；超了移 tasks/attachments/
项目引导（AGENTS.md）8,000 IDE 注入硬上限 —— 仍由项目脚本管（项目专属值不进 skill）

另设下限建议 1.5 KB（只 WARN 不红）：主题文件过小会让「读三个文件」取代「读一节」， 反而更贵；命中时提示并入邻文件。

存根规则（保护历史引用）

  • 被拆的文档一律在原路径留 ≤1 KB 存根：一句话 + 指向 <目录>/_index.md。 理由见第 08 节引用面统计 —— testing.md 被引 132 处、pitfalls.md 113 处， 其中大量在历史计划 HTML、issue 报告与任务档案里，那些一行都不改。
  • 活文档指向目标文件，不指向存根（AGENTS.md / instruction / skill / 主题文档互引 / 源码注释）， 否则每次读都多一跳。
  • 存根本身也被守：≤1 KB、含「已迁至」、不含正文或条目。

07三条入口接线

拆完文件不等于会被读到。要让约束在做那个动作之前进入上下文，三个消费者各接一条线。

（a）决策点：AGENTS.md 粗路由 + README 细路由

  • AGENTS.md 只放粗路由（现 7,653/8,000 字符，余量 347，塞不下 9 个目录的路由）： 「按任务读哪份文档 → 见 memory-bank/README.md」+ 三行动作级提示 （改代码前读对应 _index.md；跑 git 前读 pitfalls/git/_index.md； 写测试前读 testing/_index.md）。同时精简「跨仓库操作」「提交 / PR」「命令」三节， 目标 ≤6,500 字符（留约 19% 余量）。
  • README.md 承担库内细路由（≤3 KB）：一张「任务 → 目录 → 入口索引」表 + 生成物说明。 守卫保证每个 _index.md 都被 README 引用（无孤儿目录）—— 新增目录忘了登记就红。
  • skill 侧不写仓库事实：走已有的配置外置路径 —— .commit-flow.toml 增 pitfalls_index = "memory-bank/pitfalls/git/_index.md"，预检在表尾打印该指针； create-issue / memory-bank skill 各指 kb/_index.md。
  • 最贵的三条在决策点内联一行结论 + 指针：rebase 禁用、非快进 + 脏 = 必炸、 判「推没推上」只看 ls-remote —— 写在 skill 的《最常见组合》与「停手点」段落里。 单点定义仍在 KB，不复制全文。

（b）入库：memory-bank skill 收尾 DoD ⑤

  • 现在：「新坑追加 pitfalls.md」→ 改成：「按动作选类，写进 pitfalls/<类>/<主题>.md（补三行头元数据）；没有合适的类先扩枚举； 然后跑 skill 的 scripts/gen_kb_index.py 重建索引」。同一规则适用于其它目录 （新增 testing/ 主题同样跑生成器）。
  • 新增闭环纪律：若这一轮踩到了已记的坑，把该条 **复发** 加一， 并在任务档案里写一句为什么没命中（路由没到 / 文件没读 / 读了没照做）。 反复重踩于是变成可排序的数字，也是「下沉为守阵」的优先级依据。
  • 拆文档也算入库动作：任何一次把内容写进 memory-bank，先看目标文件的 cap； 超了就要么拆文件、要么外迁 —— 这是「库不会重新长胖」的收口。

（c）检索：先索引，后 grep，禁止整读

memory-bank/README.md              按任务选目录
  → testing/_index.md              按动作选主题 (一句话 + 触发词)
    → testing/tmpdir.md            读一个 ≤10 KB 的文件

不确定关键词时: grep -rn "TMPDIR" memory-bank/          grep 是三条线共用的兜底

「禁止整读某个目录」不是格式洁癖，是预算纪律：目录整体仍是几十 KB 量级， 整读行为一旦回来，这次重构就白做了。

08机械后果：通用生成器 / 守卫 / 闸门

脚本落位：统一进 memory-bank skill

索引生成器与结构检查脚本不放仓库根 scripts/，统一落在 .agents/skills/memory-bank/scripts/：它们实现的是 Memory Bank 模式本身 （生成物索引、目录指针、cap 策略），不是本项目的业务脚本 —— 放 skill 才能跨 clone / 跨项目共用一份， 也避免各项目各写一版慢慢分叉。gen_tasks_index.py 同时迁入该目录。

.agents/skills/memory-bank/
├─ SKILL.md                    ← 会话协议 + 五步配方; 文档里的路径一律写 <skill-dir>/scripts/...
└─ scripts/
   ├─ _common.py               find_root() · CAP_POLICY · 首部元数据读取 (各脚本共用)
   ├─ gen_tasks_index.py       迁入 (原 scripts/gen_tasks_index.py) —— 状态分区专用
   ├─ gen_kb_index.py          新 · 通用: 任意目录 → _index.md (有子目录出类指针, 无则出文件指针)
   └─ check_kb_structure.py    新 · 通用: cap 策略 / 元数据 / 双向一致 / 无孤儿 (供守卫 import)

三条纪律（都是 KB 里已记过的坑，迁移时必须照做）：

  • 找仓库根用 find_root() 向上找 .git，不按 skill 安装深度反推 parents[n] —— create-issue/scripts/_common.py 已是这个写法，直接复用同款； 并允许 --root 覆盖。
  • skill 文档里的路径写 <skill-dir>/scripts/…，不写相对路径 —— 否则执行者会去仓库根 scripts/ 里找（已踩过）。
  • 项目专属值不进 skill：AGENTS.md 的 8000 上限仍留在项目脚本 scripts/check_context_caps.py；skill 里只放模式默认值（第 03 节的 cap 分级）， 需要按项目覆盖时用 --max-chars；将来真需要外置配置再走 .memory-bank.toml。

新增文件随 .codebuddy/skills/memory-bank 的 junction 立即生效（实测该目录是指向 .agents/skills/memory-bank 的 junction），不必重跑 sync_agent_skills.py —— 那条闸门只管 skill 的增删。新脚本还会被既有的 <each:.agents/skills/**/scripts/*.py> --help 冒烟闸门自动覆盖。

通用生成器 gen_kb_index.py

一套代码覆盖全库：给任意目录，扫其中 *.md（排除 _ 开头）读三行头元数据 → 渲染 _index.md；若目录下还有子目录，则为每个子目录渲染一行「类指针」（读其 _about.md）。pitfalls/ 的两级与 testing/ 的一级， 是同一个实现的两种输入。

# 数据源（手写的只有这些）
testing/tmpdir.md       →  # 标题 / > 摘要: ... / > 触发: ...
testing/_index.md       →  生成物: 每个主题一行指针
pitfalls/git/_about.md  →  类元数据 (一句话 + 触发条件)
pitfalls/_index.md      →  生成物: 每个类一行指针

# 用法
python <skill-dir>/scripts/gen_kb_index.py            重建全库所有 _index.md
python <skill-dir>/scripts/gen_kb_index.py --check    只比对 (闸门与守卫用)

结构检查 check_kb_structure.py + 守卫（tests/test_memory_bank.py 增 9 条）

守卫测试在进程内 import 检查器（本仓库测试禁止起子进程，sidefx.py 会记账越界）， 与 gen_tasks_index.py 现做法一致；cap 与类枚举常量单点定义在 skill 的 _common.py， 守卫 import 它，不手抄。

  1. 每个目录的 _index.md == 生成结果（全库一次校验）
  2. 索引 ↔ 目录内容双向一致：有文件没登记、登记了没文件，都红
  3. 每个主题文件含头部元数据（# 标题 + > 摘要: + > 触发:）
  4. 每个文件 ≤ 其角色的 cap（第 03 节策略表，首个匹配生效；下限 1.5 KB 只 WARN）
  5. 类名 ∈ 固定枚举；文件名匹配 ^[a-z0-9]+(-[a-z0-9]+)*\.md$
  6. 每个 _index.md 都被 memory-bank/README.md 引用（无孤儿目录）
  7. 存根（pitfalls.md / testing.md / …）≤1 KB、含「已迁至」、不含正文或条目
  8. activeContext.md ≤12 KB（易变层硬顶）
  9. pitfalls/ 条目含 触发 / 判别 / 处置 三字段（沿用既有约定）

扩类 / 扩目录规则（写进 skill）：新增一个类或目录，要同时改三处 —— 枚举（若属枚举范畴）、README.md 细路由、该目录的 _about.md / 元数据；少一处就红。

10守恒与验收

  1. 逐文档条目守恒（防迁移丢内容）：W0 清单按规范化后的行文本 md5 比对 —— missing 必须为 0；extra 允许（索引行、元数据行、分流判据不算条目）。 每份文档的核对结果（原 N 条命中多少）写进任务档案。
  2. 结构守卫全绿（9 条），且三条关键项各有一次「故意写错 ⇒ 红」红验： cap 超限 / 删主题文件 / 文件缺元数据。
  3. cap 全库达标：check_kb_structure.py 报 0 超标； 项目侧 python scripts/check_context_caps.py --strict PASS，AGENTS.md 精简后 ≤6,500 字符。
  4. 脚本落位：两个 --check 从 skill 路径跑通（--help 由既有冒烟闸门覆盖）； preflight.py --show-config 显示 <skill-dir:memory-bank> 已展开为真实命令； 活文档里旧路径 scripts/gen_tasks_index.py 残留为 0。
  5. 检索演练 ×3（改前端 / 跑测试 / 查配置键）：从 README 粗路由出发 ≤2 跳命中目标条目， 且不整读任何超过该角色 cap 的文件；实测的「跳数 / 文件数 / 读了多少字节」记进档案。 这是 G1 与 G3 的唯一有效证据。
  6. 入口链不随库体量变长：演练时额外记录入口链（AGENTS.md → README → 索引 → 文件）的 累计字节，确认在 6.5 + 3 + 3 + 10 KB 的量级。
  7. 引用完整：每个存根 1 跳到达对应 _index.md；迁移前统计的旧锚链接 （如 pitfalls.md#…）在活文档中为 0。
  8. 回归：uv run pytest tests -q 绿。基线 1152 passed + 1 skipped （2026-09-22 实测）；只动文档与守卫，数字应保持不变 —— 若因新增守卫而增加， 按纪律只改 testing/baseline.md 并把增量写进本轮结论。

11风险、取舍与验证步骤

风险与取舍

  1. 引用面很大。被拆的 8 份文档合计被引 400+ 处（testing.md 132、 pitfalls.md 113 …），其中大量在历史计划 HTML、issue 报告与任务档案里。 策略：活文档改指向目标文件，历史只靠存根。存根 ≤1 KB 且被守卫盯住， 属于低成本的兼容层，不是技术债。
  2. 多 clone 撞车。这是结构性改动（新增目录 + 大量文件搬迁）， 每波都要在一个 clone 里一次做完并尽快推送；动手前 git fetch 确认不落后。 冲突形态是 add/delete —— 处置是「以新结构为准，把对方的增量按动作归位」，不要合并旧文件。
  3. 拆分过度。主题文件过小会让「读三个文件」取代「读一节」。 故设 1.5 KB 下限建议（WARN 不红）；演练若显示要 3 跳才命中，改的是索引指针措辞， 不是再加一层。
  4. 索引自己也会漂。所有 _index.md 都是生成物，漂移由 「生成器 + --check 闸门 + 守卫」三件套按住 —— 与 tasks/_index.md 同款， 冲突处置也相同（重跑，不手改）。
  5. 「搬了家」不等于「被读到」。本方案最容易自我欺骗的一点：目录化只降低阅读成本， 真正让约束生效的是第 07 节的接线与 W8 的机检化。若只做 W2–W7 而不做接线， 一年后仍会重踩 —— 验收判据里的「检索演练」与「复发计数」就是为这条设的。
  6. 移动 gen_tasks_index.py 自身的风险面。它现在是提交闸门的一部分， 迁移必须与引用改写同一次提交落地 —— 中途失败会让闸门指向不存在的路径。 顺序：写新脚本 + 改引用 → 手动跑 skill 路径的 --check → 删旧文件 → 跑预检验证展开。 代价是其它 clone 在 pull 后旧引用立即失效，这正是要一次改全的理由。
  7. 顺带修的漂移：.github/instructions/memory-bank.instructions.md 还在教旧的 8 文件结构，并把任务命名写成 YY-MM-DD-HHMM-taskname.md （现规范是 YY-MM-DD-<slug>.md）。它是 applyTo: memory-bank/** 的规则载体 —— 不重写，新结构在编辑 memory-bank 时就不可见。列入 W8。
  8. 波次即提交边界。九波若合成一两次提交，一旦某波校对出错， 回滚会连带把已好的波一起退掉。故每波一次提交，提交信息写明该波守恒核对的实测数字。

验证步骤（可执行清单）

  1. 生成器幂等：连跑两次 gen_kb_index.py 无 diff；--check 退出码 0； gen_tasks_index.py --check 同样绿。
  2. 守卫会红（三条红验）：给某主题文件塞内容让它超 cap → 红；删一个主题文件 → 双向一致红； 去掉某文件的 > 触发: 行 → 元数据守卫红；各自复原。
  3. 存根有效：8 个存根都 ≤1 KB、含「已迁至」，点开 1 跳到达对应 _index.md； git grep -c 旧路径计数不下降。
  4. AGENTS.md 预算：check_context_caps.py --strict PASS，且余量 ≥ 1,000 字符。
  5. 细路由完整：memory-bank/README.md 覆盖全部 _index.md（无孤儿守卫绿）； 故意漏登记一个新目录 → 红。
  6. 闸门接入：单独改一个主题文件、故意不重跑生成器 → 预检该 gate STOP。
  7. 检索演练 ×3，记录跳数 / 文件数 / 字节数 / 入口链累计字节。
  8. 引用残留：迁移前统计旧锚链接处数，迁移后活文档为 0。
  9. 入库演练：临时造一条假坑与一个假主题文件，各走完 DoD ⑤（选目录 → 写三行头 → 跑生成器 → 闸门绿 → 删除）；同时给某条已有坑 复发 +1，确认 W8 候选清单能按它排序。
  10. 全量回归：uv run pytest tests -q 绿，数字与基线一致（或按第 10 节第 8 条记录增量）。
  11. 历史不回改：git diff --stat 里 memory-bank/plans/ 只有本次新增的这一份； memory-bank/tasks/ 的既有档案正文只在 W7 那波被动过，且只是纪要段外迁。

本方案不改 src/ 业务逻辑、不改业务测试；仅 3 处源码注释里的 KB 路径会随对应波次更新。 第 04 节的全库落位与第 03 节的 cap 分级确认后再开工。
