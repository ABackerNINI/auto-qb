01结论与拍板点

本计划认领 issue 26-10-03-1140(recheck 轮询首跳误判已完成种子校验成功), 但不做点状补丁: 复验确认该 bug 只是「从陈旧观测直接下确定性结论」这一类缺陷的一个切面 —— 复验同时确认了同路径的假失败缺陷与 qB 重启场景的伪证据别名(§02)。方案把 recheck 轮询的判定重构为证据门控状态机, 并与代码库里已有的四处生效确认基建(WEBUI 真值落地 / reannounce 确认 / 跳检 R2 复核 / 直查不回落红线)归一到同一模式(§04), 模式沉淀进知识库(§06 P2)。

核心结构变化一句话: 现在的成功分支是 if rec.progress >= 1.0: 成功; 改后成功是不可达的, 除非本周期内观测到过真正的全量校验态(checkingDL / checkingUP)。判定本身提为纯函数, 「无证据成功」在函数签名层面无法表达(§05 原则 3)。

拍板点

#决策推荐备选与理由
D1小种子「校验已完成但观测不到」的残余风险(§10 R1): 等满 600s 宽限判「校验启动超时」, 经 origin 重提重走决策链(冷却上限 3 次/日兜底)接受宽限后盲判成功 —— 拒绝: 假成功正是本 issue 要消灭的东西; 严格 seen_checking 的这个代价是安全方向上最便宜的
D2verdict 纯函数与证据谓词的落点rules/checking_metaops_mod 私有 —— checking_meta 是 ops 与 rules 之间的中性叶(依赖方向现成), 测试可直接导入; 决策链 1.5/1.6 将来也可同源取用
D3R1 提交点实时复核纳入本轮(P1), 复核异常时 fail-closed(拒绝提交, R2 同款)是不做 —— 则重复提交窗口仍开: 源码确证重复提交无数据风险(正在 hash 时 lt 层 no-op; 排队时重扫文件并挪到队尾), 但无效 I/O 与排队推迟真实存在, 且 R1 live 同时承担「取实时基线」职责(见 §6.2); fail-open 则把「拿不到真值」伪装成「可以动手」
D4拒绝「状态位变化」(如 uploading→stopped)作为生效证据拒绝用户在校验等待期内手动暂停种子会产生同款 delta —— 换一条路 reintroduce 假成功, 与结构化排除目标相悖
D5宽限耗尽仲裁直查(qB 是否真在校验)每次超时事件至多 1 次1 次不设上限 —— 同步线真断了时退化为周期直查(API 轰炸形状, 违反等价性红线的精神)

03根因: 判定混叠

3.1 数据流与节拍

3.2 两问混叠

轮询每跳其实在回答两个正交的问题: Q1 操作是否已生效(recheck 是否被 qB 应用并真的跑过), Q2 操作结果如何(校验通过与否)。现代码只有失败分支用 seen_checking 回答了 Q1, 成功分支直接拿 Q2 的观测(progress >= 1.0)下结论。而 Q2 的观测值在「生效前」与「生效后」是别名的: 已完成种子的生效前状态(1.0, 非 checking)与校验通过后的状态(1.0, 非 checking)完全相同 —— 仅凭一份快照, 这两个世界不可分辨。

3.3 别名清单(方案必须逐一处置)

别名不可分辨的两件事处置
A1已完成种子「recheck 未生效」vs「recheck 已跑完且通过」—— 可观测状态同为 (progress=1.0, 非 checking)成功必须以观测到校验态为前置(原则 2); 歧义落回有界等待(原则 5)
A2小种子「recheck 未生效」vs「recheck 已在采样间隔内跑完」—— 任何 ≤2s 间隔的采样都抓不到承认观测硬边界: 保守判超时 + 有界重试(D1); 辅以 progress 回落证据缩短真失败的判定(§06)
A3「全量校验进行中」vs「qB 启动期简历校验(checkingResumeData)」—— 同落 is_checking证据谓词收窄为 {checkingDL, checkingUP}, 明确排除 ResumeData(原则 2)
A4「recheck 生效导致状态位变化」vs「用户手动暂停导致状态位变化」拒绝状态位 delta 作为证据(D4)

3.4 可观测性硬边界(2026-10-04 子代理源码调研确证, qB master/5.2.4 + libtorrent 2.0.11)

对 qB 官方 WebUI 行为与 forceRecheck 全链路做了源码级调研, 结论收窄并加固了本节判断:

  • 官方 WebUI 不解决、只回避: 点击 Force Recheck 后仅有(可选)事前确认框 → POST → syncData(100) 立即刷一次增量, 之后完全交给 1.5s 周期 sync 反映状态 —— 无乐观更新、无 pending 指示、无任何事后回执。官方姿势即「不宣称结果、只反映状态」; 我们方案多出来的判定纪律, 恰是自动化工具必须下结论(晋升/auto_start)而官方 UI 不必承担的部分。
  • POST 200 只代表异步投递: WebAPI recheckAction 是同步 for 循环逐个调 TorrentImpl::forceRecheck(), 每个向 libtorrent 投递异步消息后立即返回; qB 不暂停种子, m_state 要等下一次 alert 驱动的 updateState()(qB 内部刷新节拍默认 1.5s)才翻。
  • 「排队等待校验」状态已消亡: libtorrent 2.x 删除了 queued_for_checking; 排队与正在 hash 在 lt 侧同为 checking_files, qB 一律映射成 checkingUP/checkingDL —— 排队中的种子同样产出生效证据。校验队列默认串行(lt active_checking=1, qB 可经 max_active_checking_torrents 偏好并行化), 批量 recheck 时后续种子逐个执行, 但因为等待期就显示 Checking*, 它们立即转入 WAIT_RESULT 长等待而不会误判超时。
  • 无任何持久回看信号(源码级否定): completion_on 成功不刷新(lt 只在首次完成时写 m_completed_time)、失败也不清零; seen_complete 是 swarm 侧信号与本地校验无关; qB 内部 m_unchecked 与 lt 的 torrent_checked_alert 均未暴露到 WebAPI。「校验做过」只能靠状态转移的过程观测, 不能靠任何字段回看。
  • 每次被应用的 recheck 必经 checkingResumeData → checking* 过程态: forceRecheck 把 lt 状态置为 checking_resume_data(文件预扫描), 随后进 checking_files。但 ResumeData 与 qB 启动期简历校验同名同态(别名 A3), 仍不作判定证据; 谓词维持 {checkingDL, checkingUP}。
  • sync 是电平采样不是事件缓冲: 服务端只记「变化的种子 ID」, 序列化发生在轮询时刻 —— 两次轮询之间走完全程的校验(小种子)中间态彻底丢失, 只见终态。这是别名 A2 的 qB 侧结构性根源, 轮询间隔必须远小于最小校验时长。
  • 重复提交无风险但有代价: 正在 hash 时 lt 层 no-op; 排队等待时重跑文件预扫描并挪到队尾 —— 无报错、无数据风险, 代价是无效 I/O 与排队推迟(影响 P1 动机表述, 见 §6.2)。
  • API 面其它候选逐一否定(收尾排查): /log/main 无任何校验开始/完成日志(forceRecheck 与 torrent_checked_alert 全链路 0 条 LogMsg, master/5.2.1/4.6.7 三版本逐行核验, 仅 FileErrorAlert 写文件 IO 错误) —— 日志不能当事件缓冲证据; pieceStates 唯一确定性变化是应用瞬间位图清零(可作「已应用」瞬态旁证), 但校验完成后位图回填、窗口同样受电平采样限制, 收益边际不纳入; WebAPI 2.9.3→2.15.1(qB 4.6.7→5.2.4)变更清单无任何校验相关新增。社区实践(qbit_manage fire-and-forget / cross-seed 先停后有界轮询 state)亦无更强信号; qB 官方 issue #12451/#20646 证实「校验过程不可见不可控」是公认痛点。

综合: 观测不可分辨的 corner(A1/A2)是 qB 可观测性的结构上限, 官方实现同样绕不开 —— 方案目标维持不变: 让歧义永远落到安全的一侧: 无证据不宣称成功, 有界等待 + 有界重试兜底(§05 原则 5)。2026-09-25 的「首样本竞态修复」(现 else 分支)已经为 progress<1.0 的样本确立了这个方向, 本次是把 progress=1.0 的路收进同一纪律。

04既有生效确认基建: 模式已经存在, 只缺一个执行点

复验过程中盘点全库, 发现「异步操作 → 生效确认」在代码库里已有四处成熟实现。recheck 轮询是唯一一个宣称成败结论却没有证据门控的判定点:

机制位置体现的模式要素
WEB 命令真值落地webui/runtime.py defer_receipt / flush_truths / _truth_landed / _affected_truth决定性时刻直查 qB 不回落快照(「拿快照当命令后的真值 = 读到命令前的旧值」真机实测 1362ms 滞后); 「取不到就 None, 不伪装」; 效果落地才推真值, 超时宁可让前端回滚
强制汇报确认webui check_pending + _confirm_reannounce_result提交时抓 baseline, 轮询确认效果与基线的差, deadline 判败聚合回执 —— 异步效果确认的完整范本
跳检 R2 实时复核ops_mod.skip_check + _poll_until破坏性动作动手前重拉实时状态, 拒绝发生在零副作用点; 删除/重加均轮询确认生效(qB 删除/重加同为异步)
recheck 轮询(本计划对象)ops_mod.recheck poll仅失败分支有 seen_checking 门控; 成功分支、提交点检查(R1 读快照)均无证据要求

共性提炼(即 §05 的设计原则来源): ① 基线在提交点取得; ② 生效需要正证据, 不认「没坏就是好了」; ③ 决定性时刻直查真值、不回落快照; ④ 歧义有界等待, 等不出就诚实地说「未确认」; ⑤ 拒绝尽量前移到零副作用点。

05设计原则(结构性排除, 非点状补丁)

  1. 两问解耦, 判定不可达原则。「生效确认」(Q1)是「结果判定」(Q2)的前置状态: 判定只有 WAITING / SUCCESS / FAILED / START_TIMEOUT 四个出口, 其中 SUCCESS 与 FAILED 必须经由「已观测到生效证据」这一状态转移才能到达。没有 Q1 的答案, Q2 的任何观测都只配维持 WAITING。
  2. 证据谓词单点。生效证据 = 观测到 state ∈ {checkingDL, checkingUP}(真全量校验态), 单点实现为 is_piece_checking(state), 明确排除 checkingResumeData(别名 A3)。成功证据本周期内只认它; 辅助失败证据 = progress < baseline_progress(数据缺损签名: 暂停/做种中的种子 progress 只会因校验发现坏块而回落, 别名 A4 的状态位 delta 不作为任何方向的证据)。观测到的真校验态不区分发起者 —— 语义是「该种子数据已被全量校验」, 与谁提交无关。
  3. poka-yoke: 判定提为纯函数。每跳的判定从闭包里抽成全显式入参的纯函数(落点 D2): poll_verdict(seen_checking, progress, baseline_progress, elapsed, giveup) → {WAITING, SUCCESS, FAILED, START_TIMEOUT}。「无证据成功」在签名层面不可表达 —— seen_checking=False 时函数没有任何一条路径返回 SUCCESS, 由全叉积穷举测试钉死(§09 A 组), 而不是靠 reviewer 记住规则。
  4. snapshot 与 live 的分工边界。周期观测(逐轮读 store 活记录)与决定性直查(实时 API)各管一段: 周期观测零 API 成本、覆盖可能长达数小时的校验期(等价性红线原样保留); 直查只出现在三个决定性时刻 —— 提交点取基线 + R1 复核(P1, 每次 1 次)、宽限耗尽仲裁(P0, 每事件 ≤1 次, D5)—— 都是事件驱动的一次性调用, 不是周期轮询, 不构成 API 轰炸形状。
  5. 失败安全方向(风险不对称决定保守侧)。假成功与假失败的代价不对称: 假成功污染参考种子库(后续跳检引用未经校验的「参考」)+ auto_start 未校验种子, 是语义错误; 假失败只多跑一次小校验 + 计一次当日冷却(次日自愈)。歧义永远不映射成功 —— 宁可要一个标签诚实的「启动超时」, 不要一个标签体面的假「校验成功」。

06方案

6.1 P0 — recheck 轮询重构为证据门控状态机

checking_meta.py 新增(中性叶, 不引新依赖; 落点见 D2):

PieceCheckingStates = frozenset({"checkingDL", "checkingUP"})

def is_piece_checking(state: str) -> bool:
    """是否处于真正的全量校验态(排除 qB 启动期 checkingResumeData 伪证据)"""
    return state in PieceCheckingStates

class PollVerdict(Enum):  # 轮询单跳判定: 唯一出口集, WAITING 之外都是终局
    WAITING / SUCCESS / FAILED / START_TIMEOUT

def poll_verdict(*, seen_checking, progress, baseline_progress, elapsed,
                 giveup: float = CHECK_START_GIVEUP) -> PollVerdict:
    if seen_checking:                      # 生效已确认 -> 结果判定
        return SUCCESS if progress >= 1.0 else FAILED
    if progress < baseline_progress:       # 数据缺损签名: 校验必已运行且未通过
        return FAILED
    if elapsed >= giveup:                  # 宽限耗尽仍无生效证据(仲裁直查在闭包侧)
        return START_TIMEOUT
    return WAITING                         # 歧义(含别名 A1/A2) -> 继续等

ops_mod.recheck 改造(闭包瘦身, 单一写线程模型不变):

  • 提交点捕获 baseline_progress(来源随 P1 升级为实时真值; P1 之前取 store 快照值, 语义偏保守安全)。
  • poll 每跳: 删除守卫与删除路径原样不动; is_piece_checking(rec.state) 为真 → seen_checking = True → REQUEUE(此后的等待仍是纯快照观测, 零 API); 否则调 poll_verdict 按判定分派: WAITING → REQUEUE; SUCCESS → 原 on_success / 冷却清除 / auto_start / origin keep_progress 序列; FAILED → 原失败序列; START_TIMEOUT → 走下述仲裁。
  • 宽限耗尽仲裁(唯一新增直查点): 判 START_TIMEOUT 前对 qB 做一次单 hash torrents_info —— 见真校验态 → 延长一次宽限继续快照观测(覆盖暂停旁观 / 同步线故障期间 qB 真在校验的场景), 未见或调用异常 → 判超时(原判败序列不变)。每超时事件至多仲裁 1 次(D5), 日志报真实等待时长。
  • R1 快照检查、冷却、登记/释放、pending/ok/skip/fail 返回面、WEB 回执映射全部不变。R1 登记的释放时点从「首跳误判」后移到「真判定」, 重复提交窗口随之闭合。

6.2 P1 — R1 提交点实时复核(跳检 R2 同款, 决策点 D3)

现状 R1 读快照判断「是否在校验中」, 快照 ≤1.5s 龄: qB 自家 WebUI 刚发起的校验在这个窗口内不可见, 此时提交 recheck 会造成重复提交 —— 源码确证其后果是 no-op(正在 hash)或文件重扫 + 挪队尾(排队中), 无数据风险但属无效 I/O 且推迟自身排队。升级为: 快照检查(快速拒绝路径, 不变) → 冷却(不变) → 单 hash 实时复核: 种子已不在 → skip(R2 同款文案); is_piece_checking → skip(校验进行中); 否则以实时值作 baseline_progress。复核调用异常 → fail-closed 拒绝提交(「提交前实时复核失败(未执行任何变更)」, 与 R2 文案同族)。recheck 与跳检同为动种子文件域的操作, 保护策略拉齐; 成本为每次提交 1 次 API(人工点击与规则决策链都是低频事件)。

6.3 P2 — 模式固化

  • 新坑档 pitfalls/backend/effect-confirmation.md(三行头元数据): 坑 = 「从陈旧观测直接下确定性结论」; 判据 = 异步操作宣称成败结论必须有证据门控 + 决定性时刻直查不回落快照; 引用本 issue 与四处范本位置。
  • issue 26-10-03-1140 修后补充(实际修法 / 验证方式 / 测试数字), 状态 Fixed(Done); commands run kb.index 重建索引。
  • ops_mod 模块头注释补一行「新异步操作接入 = 新 source, 判定必须走证据门控」—— 该文件已声明「新来源不开旁路」, 本次把判定纪律一并写进同一个单点。

6.4 明确不做(范围守恒)

  • WEBUI 真值落地 / reannounce 确认 / 跳检四阶段: 已是范本, 不动。
  • 决策链 1.5 组等待与 1.6 失败推断: 语义不动; 其依赖的「登记提前释放」缝隙随 P0 闭合。
  • auto_start 不加二次生效确认: start 是幂等操作且不宣称结论, 其前置(校验真成功)已由 P0 闭合。

09测试计划(盯死)
