§01目标与设计原则

目标：真机（约 210 种子、本地部署、重启后首次刷新 WebUI）框架可见——#app 的 v-cloak 卸除、导航栏/状态栏出现——从今天约 12s 降到 ≤1.5s；P1 单独上线后的中间目标 ≤3s。

不变量（改完必须仍成立）：

  1. 模板按清单顺序注入；全部成功后才放行脚本；任一失败仍走 fail() 可读占位 + 重新加载按钮（boot.js 现有契约，D8 确认不改）。
  2. 脚本执行顺序 = 清单顺序（顶层 const 与依赖顺序依赖它，不能用 type=module 改作用域）。
  3. 升级后绝不让用户拿到旧的 app.js/style.css——这是当年 no-cache 中间件要防的事，长缓存不能把它丢掉。
  4. 诊断桩只留在独立分支 diag/webui-boot-probe-stub，不进 develop；后端 API 不进首屏关键路径。
  5. 四套皮肤（atlas / prism / console / flux）装配保持一致。

§02现状与痛点

今天：boot.js:72 nextPart() 逐个 fetch 28 个模板分片（then 链串行）；boot.js:119 nextScript() 逐个插入 81 个脚本（async=false + onload 链串行）。static_ui.py:48 _static_no_cache 给所有非 API 响应加 Cache-Control: no-cache，每个资源每次都要 ETag 校验往返。

# 真机桩（2026-11-20 07:06, 约 210 种子, 本地部署, atlas）:
28 分片串行 2,747ms + 81 脚本串行 7,754ms = 10,500ms = 首屏 12,037ms 的 87%
单请求分解: connect=0  download=2-3ms  ttfb=54-166ms  -> 瓶颈在服务端每请求响应
config_public_req 出现在 12,036ms（框架可见那一刻）-> 后端 API 不在关键路径
本地同链无头浏览器: 分片 4ms/片, 脚本 5ms/片, 框架可见约 0.9s -> 单请求延迟差约 20 倍

# 批量插入保序实验 (parallel_script_probe.cjs):
8 个脚本 x 100ms -> 串行链 867ms, 批量插入 117ms, 执行序都是 0..7

§03方案总览

主线：两期，先并发化再指纹化；每期独立可上线、独立可回退（D1）。

P1 · 并发化（治标，先上）

  • 分片：Promise.all 并发 fetch 全部 28 个分片，结果按清单 index 归位后再拼接注入——顺序与「全部成功才注入」不变；每请求保留独立 10s AbortController，任一失败 fail()。
  • 脚本：用 link rel=preload as=script 并行预取全部 81 个（只用 preload，不用 fetch——P1 阶段中间件仍全量 no-cache，fetch 预取后再插 <script src> 会二次 ETag 重验，破坏「每脚本只一次网络请求」判据；preload 可被后续 script 复用缓存），全部成功后按清单顺序批量插入 async=false 脚本；任一失败在插入任何脚本之前 fail()。这样既并行掉 TTFB，又守住 D8 的 fail-fast。
  • 落点：仅 src/auto_qb/webui/static/shared/boot.js 一处，四套皮肤共用，一处改动四套受益。

P2 · 指纹化 + 长缓存（治本，达成 ≤1.5s）

  • 版本源：应用启动时计算 static/ 树的内容哈希 V（只算静态源码扩展名，排除日志 / .pyc），缓存内存（D5）。
  • HTML：四套 index.html 的 head 资源写成 ?v=__AQB_V__ 并注入 window.AQB_V；服务端替换令牌，HTML 自身保持 no-cache（D4）。
  • 装载器：boot.js 集中给分片/脚本 URL 追加 ?v=V（已有 query 则用 &v=），对应 D4 的「集中追加」。
  • 缓存分流：带当前 V 的静态响应发 public, max-age=31536000, immutable；裸路径 / 无 v / /api/* 维持 no-cache（D6）。
  • 测试：test_static_assets_disable_heuristic_cache 拆成「裸路径 → no-cache」与「带 v → immutable」两组；补哈希稳定性、令牌替换、URL 追加、四皮肤一致性。

§04实施步骤

期 / 步内容验收判据
P1-1 分片并发boot.js 分片改 Promise.all + index 归位拼接28 请求并发发起（相邻启动间隔 <5ms）；注入顺序与清单完全一致；注入一个失败分片仍进 fail()
P1-2 脚本并发并行预取 + 全部成功后按序批量插入81 请求并发且每脚本只 1 次网络请求；执行序 0..80；注入一个 404 时任何脚本执行前就 fail()
P1-3 回归四皮肤 + 210 种子 harness + 真机复测test.quick 全绿；四皮肤框架可见；真机 ≤3s
P2-1 版本源启动算静态树哈希 + HTML 令牌替换改任一静态文件后 V 变、不改 V 稳定；四套 HTML 都成功替换
P2-2 URL + 分流boot.js 追加 ?v=；中间件按 v 分流缓存头带 v 响应 immutable；裸路径 no-cache；/api 不受影响
P2-3 测试改造拆精确路径断言 + 升级演练升级前后 V 变化、旧 URL 不再被引用；test.full 全绿
P2-4 真机验收重启后刷新，外部 Playwright 探针量 v-cloak 卸除框架可见 ≤1.5s；静态重验请求为 0（HTML 除外）；页面功能与升级路径无回归

验收探针走浏览器原生 performance + 外部 DOM 轮询，不往 develop 注入任何桩（D3）。分期门槛：P2 未上线前不得把 ≤1.5s 当作已达成。

§07风险与对策

风险触发条件处置
脚本失败语义变化批量插入后某个脚本 404，后续脚本可能仍执行「并行预取全部成功后再插入」把失败挡在执行前；验收专门注入 404 验证
版本号抖动日志 / .pyc 等非静态文件混进哈希只算 static/ 下白名单扩展名；加哈希稳定性测试
query string 缓存通用性将来引入 CDN，中间层不缓存带 ? 的请求本地部署当前无此问题；真发生时转 issue 26-11-20-0726 走文件名哈希演进
全树单版本号失效面大改一个文件导致全部资源 URL 变化升级是低频事件，换来版本一致性（无新旧文件混用）；升级演练验收
并发瞬时压力109 个请求同时打到服务端本地单用户场景可接受；若出现压力，加有限并发窗口（如 12 并发）仍远快于串行
诊断桩误入 develop合并分支时带上 __AQBP 桩D3 分支隔离；验收在 develop 上 grep __AQBP 为零
