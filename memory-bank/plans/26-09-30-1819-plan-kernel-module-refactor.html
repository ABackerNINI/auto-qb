1.2四个结构性病灶

  • 共享命名空间无边界的隐式耦合 —— mixin 之间不互相 import, 却经由 self.store / self.state / self.api 互相读写 (grouping 对 store 42 次引用里混着 webui 的视图字段消费)。任何属性的语义都是「全类公约」, 改一处要靠全量测试兜底。
  • 主循环替业务模块做判断 —— _refresh_torrents 硬编码了归组/规则/维护/限速/集数五家的调用次序; _create_global_tasks 在内核里逐个点名业务任务。内核每长一个业务点, 就多一分「必须知道模块在干什么」。
  • 配置热重载的消费知识分散 —— apply_new_config 按 L0/L1/L2/R 分级分派, 每个消费方钩子挂哪一级是一个决策点。四类失效族 (过度重启 / 重启竞态 / 语义回滚 / 漏调) 已在 plan hot-reload-simplify 定性为同一根因, 其推荐方向一「统一挂载口」(组件自认领 + 每轮无条件 apply + 自判短路) 与本计划是同一件事的两个切面。
  • 外围绕过边界直写内核私有面 —— 托盘 4 处直写 manager._notify_handler (tray/app.py:405,426,456,460); start_web_server 直写 manager._web_token (webui/server/lifecycle.py:165); 路由与测试 279 处 make_manager 调用钉在 _WEB_STATE_ALIAS 兼容层 (19 字段 + 8 转发方法) 的旧名字上。
既有进展, 不是从零开始

项目已经在往这个方向走了三步: ① TaskQueue 已是通用调度器 (handler + REQUEUE/FINISHED 契约, 内核无关); ② WebUIRuntime / HrRuntime 两个门面已拆出, HrRuntime.apply 已实现「每轮必调 + 自判短路」的目标语义; ③ rules/registry.py 已有装饰器注册的条件/动作插件表。本计划是把这三个孤立的正确决策升格为统一制度。

02

这套思路的学名

「中央管理器只调度、不含业务、甚至不知道模块具体干什么」—— 这在架构模式语汇里叫微内核架构 (Microkernel Architecture), 又称插件式架构 (Plug-in pattern)。它由三件东西拼成, 各有专名:

  • 微内核 + 插件 —— 内核只提供注册表、生命周期编排与通用机制 (调度 / 事件 / 配置广播); 业务全部住进带统一契约的插件。对应本计划: QbManager = 内核, tags/grouping/rules/webui/… = 插件。
  • 控制反转 / 依赖注入 (IoC / DI), 服务定位器变体 —— 内核构造一个共享上下文 (AppContext), 模块从上下文取能力 (store/api/state…), 而不是内核把业务逐个喂给谁。「宿主不知道模块是什么」的法律保障就是依赖倒置: 模块依赖抽象契约, 不依赖内核。
  • 调停者 (Mediator) 的事件总线变体 (Pub/Sub) —— 模块之间不直接调用, 通过内核广播的领域事件 (种子增删 / 状态变化 / 刷新相位) 协作。内核做路由不做解释, 这是 Mediator 退化成 broker 的形态。

03

目标模型: 内核 / 能力服务 / 功能模块 三层

3.1分层判据

  • 内核 (kernel, 即瘦身后 QbManager) —— 只含: 主循环三条时间线 (同步线 / 任务线 / 命令线)、模块宿主 ModuleHost (注册表 + 生命周期编排)、事件总线、qB 连接管理 (重连退避)、周期落盘计时、status_snapshot。判据: 知道「何时」(节拍 / 相位 / 生命周期), 不知道「何事」(标签 / 归组 / 规则语义)。
  • 能力服务 (services, 挂在 ctx 上的单例) —— 无启用开关、无线程、无热重载语义、被多方消费的纯能力: store (种子数据层)、api (qB API 门面)、client (连接与绑定)、state (状态持久化服务, 从 rule_engine 迁出)、file_access。服务不是模块: 没有生命周期, 内核与模块都可调用。
  • 功能模块 (modules, 实现 Module 契约) —— 有启用开关、可能持有线程 / 服务器 / 队列任务、有配置认领与热重载语义的自治单元。模块之间不互相 import, 需要别人能力时经 ctx 取服务或事件协作。

04

模块契约与事件相位

4.1Module 契约

class Module(Protocol):
    name: str
    def sections(self) -> tuple[str, ...]: ...
    # 声明消费的配置顶层段; 守阵保证每段至少被一个模块认领 (hot-reload-simplify §3.3 原文采纳)

    def start(self, ctx: AppContext, dry_run: bool) -> None: ...
    # 幂等启用: 起线程 / 服务器 / 注册队列任务都在这里; 未启用 = 无操作

    def stop(self) -> None: ...
    # 幂等停用; 先叫停后 join (pitfalls/backend/concurrency.md 第 1 条)

    def apply(self, old: Config, new: Config) -> ApplyResult: ...
    # 每次热重载无条件调用; 相关段整段相等即短路返回 none
    # (统一挂载口语义; hr.apply 已是此形态, 2026-09-29 修复即样板)

    def subscribe(self, phases: PhaseRegistry) -> None: ...
    # 声明消费哪些刷新相位 (§4.2); 同相位内按装配序调用

    # 可选 loop hooks (有则被主循环按装配序调用, 无则跳过):
    #   on_command_line() -> bool    消费控制命令, 返回「本批是否改了 qB 状态」
    #   on_sync_line(force)          同步线收尾 (webui: 视图发布)
    #   on_task_line(force)          任务线收尾 (webui: 错误原因预取 / 搜索索引)
契约边界的诚实声明

内核仍然知道契约本身 (生命周期动词 / loop hooks / 相位清单) 与装配清单里的模块名 —— 这就是「仅调度」的准确含义: 内核知道每个模块「何时」被调用, 不知道任何模块「干什么」。主循环里不再出现 web / hr / rules / grouping 字样, apply_new_config 里不再出现 L1/L2 业务分支。

4.3热重载收敛 (与 hot-reload-simplify 的合并)

apply_new_config 瘦身为「替换 config 对象 + 广播 apply + 汇报动作」, 级别分派层与三张手写表退役 —— 这正是 hot-reload-simplify 方向一 W2-W4 的内容, 本计划吸收其协议并按模块边界落地:

def apply_new_config(self, config) -> dict:
    changes = diff_config_impacts(self.config, config)
    restart = [c.path for c in changes if c.level == "R"]   # R 闸留在内核
    old = self.config
    self.config = config                       # L0: 换对象, 现读键即刻生效
    actions = self.host.apply(old, config)     # 每模块无条件 apply, 自判短路
    return {"applied": True, "actions": actions, ...}

两个语义细节必须保留并写进守阵: ① webui.apply 不能完全短路 —— 视图含配置派生展示值 (HR 标签模板等), 现状是每次热重载无条件 mark_dirty, 模块化后保持「有差异即置脏、仅监听身份变化才重启服务器」; ② rules 模块的 L2 重建只重建队列与规则, 运行期内存态 (exec_history / skip_check_day) 原对象保留 (issue 26-09-21-1347 的教训)。

06

分段实施 P0–P6 (每段独立入库、全量绿、可回退)

排序原则: 风险递增, 先立契约再搬家, 已验证形态 (hr / 门面) 先行, 最大一刀 (规则 + 刷新管线) 放最后。每段验收统一为 commands run test.full 全绿 + 段内指定守阵; 每段结束新建基线切片记实测数字。

不变量与兼容策略 (全程不许破)

7.1运行时不变量 (来源: pitfalls/backend + qbmanager 回归注释)

不变量要害
单一写线程 (黄金法则 5)只有主循环线程改队列结构 / state_file / store 分组索引; 模块线程只投递意图 (命令队列模型), apply 只在主循环线程跑
_throttle 非托管必须真实睡眠2026-09-14 空转事故: stop_event 判断改写必须保语义, 回归注释随迁内核
命令线 ≠ tickwake 只 drain 命令不触发任务线, 否则速率语义 (max_tasks_per_tick) 失效 + 自投递命令自激打满 CPU
flush_truths 次序补刷新之后 / 兜底只在正常路径没跑到时补, 漏调 = 前端 waitCmd 干等 40s
_suppress_events 首轮重放保护热重载全量重建的 added 事件抑制, 收口进总线 suppress, 语义等价
重连退避 + 连接状态转换日志断开期静默不刷屏, 退避上限 30s; connect 仅启动调用一次的恢复检测路径保留
hr.judge 只读契约无状态 / 无写 / 无 API / 零等待; 判定桥经 store.hr_link 稳定引用
代表种两口径不混缺文件扫描 (is_complete or is_errored) 与跳检参考 (仅 is_complete) 判据不同, 分模块后仍各自单点
校验先登记在途再发请求ops 模块内保留顺序与返回值语义 (重复校验 / 假 pending 防线)
dry-run 只打日志不落盘模块 start(dry_run) 全量透传; 落盘 / 通知 / web 启用的 dry-run 判定口径不变

7.2测试兼容策略 (279 处 make_manager 不动)

  • 构造签名不动: QbManager(config_path, config=None, no_lock=False) 全程保持, 76 处构造点零改动。
  • 属性委托: manager.store / api / state / task_queue / web / hr / config 保持为属性 (指向 ctx 同一对象), 测试 340 处 mgr.client / 309 处 mgr.store / 134 处 mgr.config 直读不受影响。
  • 方法委托逐段保留: 被测试点名的 mixin 方法 (_load_rules / _handle_maintenance / _create_global_tasks / _match_tracker_conf / _check_download_conflicts 等) 搬家后在 manager 留单行委托 —— 这正是 _WEB_STATE_ALIAS 已经验证过的迁移惯用法。
  • 别名层处置后置: routes 与测试改新名涉及 webui 11 个路由文件 + 20 个测试文件, 独立成后续计划, 不混进本重构的任何一段。

风险与代价

风险档位对策
相位化后事件次序回归 (本重构最大风险)高相位表是现顺序的忠实编码而非重设计; 现有 1,685 条守阵整体背书 + P5 新增相位顺序断言; grouping 52 处构造点测试覆盖最敏感区
热重载行为漂移 (四失效族复发)高影子并行 (P1) + hr 已验证形态先行 (P2) + 四场景真机走查 (P6); 协议本身来自 hot-reload-simplify 已调研拍板推荐
委托层滞留成新脏面中每段委托方法带清理标注 (与 _WEB_STATE_ALIAS 同款); 别名层处置独立计划, 不烂尾在主线上
段认领遗漏 → 配置变更不生效中sections() 认领守阵 + 未认领段 WARN + 全量重建兜底 (hot-reload-simplify §3.3 原对策)
迁移动作量大导致长分支中七段各自独立入库, 每段全量绿 + 基线切片; 多 clone 协作走 Gitee develop 常规合流

8.1代价估算

以搬家为主: 新写约 250–300 行 (module.py 契约 + EventBus + ModuleHost), 搬家约 2,600 行 (mixin / state / 门面对齐), 删除约 200 行 (级别分派层 + 三张表 + 内核点名代码); 守阵新增 / 改写估 25–35 例。完成后 qbmanager.py 958 → ≈450 行, 「内核不知道业务」成为可用 grep 验证的事实 (内核文件零业务 import)。

09

决策点清单 (待拍板)

D1 · 与热重载计划的关系
本计划吸收 hot-reload-simplify 方向一 (统一挂载口) 作为模块契约的 apply 语义 —— 两案合并执行还是并行?

推荐: 拍板本计划即视为方向一拍板, 1751 号计划标 Superseded (被吸收), 其 W1-W4 波次映射进本计划 P1/P2/P5。两案分头执行会在 apply 语义上互相踩。

D2 · checking mixin 归属
39 行的 CheckingMixin (文件存在性 / 大小一致性) 并入 ops 模块还是独立成模块?

推荐: 并入 ops —— 与 recheck / 跳检同属「动种子文件」域, 消费方同为 rules 动作; 独立模块的管理成本大于体量。

D3 · tracker 匹配的形态
_match_tracker_conf 做成 ctx 服务 (rules / store 都消费) 还是模块私有方法经事件回传?

推荐: ctx.trackers 服务 —— 规则上下文 (ctx.tracker_confs) 与全量轮重匹配都要用, 服务化可避免事件回传的时序绕弯。

D4 · 别名层处置时机
_WEB_STATE_ALIAS (19 字段) + 8 兼容转发方法的清理放本计划 P6 还是另立后续计划?

推荐: 另立后续计划 —— 改动面在 webui 路由与 20 个测试文件, 与内核重构的风险正交, 混在一起会拉长每段验证面。

D5 · QbManager 命名
内核瘦身后是否更名 (AppKernel / AppHost)?

推荐: 保留 QbManager —— 构造签名与 76 处测试引用零成本; 名字语义仍成立 (它管理的对象仍是 qB 生态), 更名收益纯审美。
