流量与限速合并与流量快照解耦 (Phase 2)

两件事：① 把「流量快照」的所有权从限速曲线任务手里拿走，交给新模块 traffic_snapshot（曲线模块降为「只写 limit 段」）—— 顺带修掉「没配曲线就永远没有历史图」这个结构性死角；② 把设置页的「数据来源 / 限速曲线 / 流量图」三张卡合成一张「流量与限速」（schema 合组 + 独立组件 + 卡内三区）。设计主轴：段级契约代替整体替换，让「谁写哪一段」写进 API 而不是靠约定。

§01目标与设计原则

为什么做。Phase 1 把「数据来源」提成了一等开关，但快照的所有权还留在限速曲线任务里：曲线任务既算限速又发布历史与累计 —— 于是 没配曲线就永远没有历史图（任务根本不注册）、两条刷新路径语义不一致（事件刷新只换 periods/history，state/limit 不动）、轮询每轮背着整份 history。前端侧「来源 / 曲线 / 流量图」三张卡分散在两个模板分片里，且都挤在额度边缘，再往上加任何东西都会撞分片上限。

做到什么算成。§04 的 A1–A5、B1–B5 每条都有可验判据；判据分两类：行为等价（既有守阵全绿 + S8 新守阵回归）与三项明确改进（无曲线配置也能看历史图 / 轮询载荷不含 history / state 拆成来源态与限速态且顶层 state 为单点派生）。改进项必须能在重构前先红、重构后转绿。

设计底线 / 不变量

  • 取数唯一入口不变：谁要 dat 路径一律走 core/traffic_source/paths.dat_path(config)；traffic_source.enabled 的闸门仍在该单点与 tool_client._desired / agent.ensure_running，本计划不新增第二个取数分支。
  • 快照唯一赋值点：ctx.web.set_traffic_view（webui/runtime.py:422-429）仍是唯一实际赋值处。段级写只经 traffic_snapshot 的 publish_source / publish_limit / publish_off 三个方法，任何模块不得直改 traffic_view（测试里直接赋值的 stub 除外）。
  • 段隔离：publish_source 不得清除 limit 段（off 态除外）；publish_limit 不得动 source / periods / history 段。方法内部是「读旧快照 → 改自有键 → 一次赋值」。
  • 单一写线程：所有发布在主循环内执行（黄金法则 5）；定时任务与 refresh_traffic 命令都入队，端点/线程只投递意图。
  • 顶层 state 是派生值：由单点纯函数 derive_state(source_state, limit_state) 算出，不允许任何调用方各写各的；守阵断言「发布的 state 恒等于 derive 结果」。
  • 保守默认：新键默认 10M；不迁移、不改写用户盘上已有的曲线 interval；旧 hub.view 持久化值靠映射兜住，不清 localStorage。
  • fail-fast：新配置键必须进 validate_config 并同步 config/schema.py 镜像（配置键全量一致性守卫会查）。
  • 行为等价：UI 可见行为与今日一致，例外只有 §01 列的三项改进与 §10 记的「曲线 interval 语义收窄」一处文案级变更。

§02现状与痛点

#现象根因（落点）
1 没配限速曲线时，历史流量图永远是空的 快照唯一写者是曲线任务，而 gslc is None 时任务根本不注册（core/modules/speed_curve_mod.py:173-174）；启动期快照无 history 键（webui/runtime.py:249）
2 「刷新」有两个语义：定时整份替换 vs 事件浅拷贝覆写 _publish_traffic 整份替换（speed_curve_mod.py:402-421）；refresh_traffic_view 只覆写 periods/history/ts/date，state 与 limit 不更新（:327-335）—— 旧 stale/off 态会挂到下一次曲线任务为止
3 快照所有权错位：来源变化被迫借曲线任务的节拍 同一个方法里既算 periods/history（来源职责）又算 target/actual/reasons（曲线职责）；曲线关掉，来源侧数据立刻停更
4 轮询每轮背着整份 history 走 /api/status·/api/state 直接返回快照引用（webui/server/routes/state.py:24-31），与「历史行不进轮询响应」的设计注释相反；实际前端从不从轮询读 history（dialogs.js:908 注释：弹层走 /api/traffic/history）
5 三张卡分散在两个模板分片 来源卡 settings.html:318-418；曲线卡 settings-detail.html:1-125；流量图（qB 采样）卡在通用兜底分支 settings-detail.html:185-205，靠 hubBlocks 自动生成
6 任何合并都会撞分片额度 settings.html 418/440 行、settings-detail.html 543/560 行（tests/test_webui_static_skins.py:1750）；守卫注释已指路「下次再长应先把该卡整体重构成独立组件再谈拆分」（:1745-1748）
7 provider 条件显隐靠手写，schema 元数据形同虚设 show_if 挂在两个 object 段上（config/schema/groups.py:492、:508），但通用渲染对非叶子项恒 visible()===true（config_editor.js:1162-1168），实际靠 tmProviderItems() 手工选子树（settings.html:330）
8 「不走通用渲染」的排除是硬编码一行 config_hub.js:281 if (hubKey(it.path) === "config.hr_check.sites") continue —— 合并卡要再排除两块，会变成三处散落 if
9 首页导航与视图 key 绑死 schema 组 hubCards() 直接 schema.groups.map（config_hub.js:192）；hubNow 按 hub.view === group.key 查（:257）；hubBlocks 只取当前 view 那一组（:266）—— 不合组就得在三处写自定义合并逻辑

另有一条与本计划正交、但决定批次顺序的事实：Phase 1 的 S8（切源即刷新）尚未收口，而它改的正是快照刷新路径。先收 S8 再动所有权 —— 否则重构与新触发器一起改，出问题分不清是谁的（D4）。

§03方案总览

主线两条 + 通用层两修：① 新模块 traffic_snapshot 拥有 ts/date/source/periods/history，曲线模块经 publish_limit() 只写 limit 段；来源侧节奏由新键 traffic_source.refresh_interval 决定，与曲线 interval 解绑。② schema 三组合成一组 traffic_limit（label「流量与限速」），设置页对应视图抽成独立组件 aq-traffic-card + 独立模板分片，卡内三区（来源 / 限速曲线 / 流量图）复用既有 hub-field 与曲线编辑器。③ 通用层补两笔欠账：show_if 下移到 object/section 项、排除表从硬编码改成单点常量。

P0 — 收口 S8（前置，不属本计划重新定义）

A2 — 快照契约拆段 + 派生 state + 段级 API

# 新契约（顶层 state 为派生, 其余三段正交）
{
  "ts": 1750000000.0, "date": "2026-10-18",
  "state": "ok",                     # = derive_state(source.state, limit.state)
  "source": {"state": "ok", "reasons": []},        # ok | stale | off
  "periods": [{"period": "day", "label": "今日", "up": 0, "down": 0}, ...],
  "history": [{"date": "2026-10-18", "up": 0, "down": 0}, ...],
  "limit": {"target": {"up": 0, "down": 0}, "actual": {"up": 0, "down": 0},
            "reasons": [], "state": "ok"}          # ok | dry_run | disabled | stale
}
  • traffic_snapshot 三个方法：publish_source(rows, source_state, reasons=())（写 ts/date/source/periods/history，保留旧 limit 段）、publish_limit(target, actual, reasons, state)（只写 limit）、publish_off(reason)（source.state="off"、清 periods/history、limit.state="disabled"）。三者内部「读旧 dict → 改自有键 → 一次 set_traffic_view」。
  • derive_state(source_state, limit_state) 单点纯函数，优先级：source.state=="off" → "off"；source.state=="stale" → "stale"；limit.state=="disabled" → "disabled"；limit.state=="dry_run" → "dry_run"；否则 "ok"。该表刻意与今日语义逐格对齐（今日：来源关 → off；读档失败 → stale；曲线未启用/未配置 → disabled；试运行 → dry_run），所以前端三个消费点（顶栏 trafficOn()、弹层 historyState、限速浮层 curve_enabled）行为不变。
  • periods 由来源侧固定发布 day + month 两行，不再从曲线配置的 period 并集推导（唯一消费点是 period === "day"，dialogs.js:712）；曲线侧需要的 ND 累计继续由曲线模块自己用 curves.aggregate 算，不进快照。
  • webui/runtime.py:249 初始快照补齐 source 与 limit.state 键（{"state":"disabled","source":{"state":"off","reasons":[]},"periods":[],"history":[],"limit":{"target":{"up":None,"down":None},"actual":{"up":None,"down":None},"reasons":[],"state":"disabled"}}）。

验收：段隔离守阵 —— publish_source 后 limit 段逐键不变；publish_limit 后 history/periods/source 逐键不变；publish_off 后 periods/history 为空且 state=="off"；derive_state 表驱动 6 组合全绿；无曲线配置时 历史图有数据、顶栏 pill 仍不显示（与今日一致）；/api/speed/mode 的 curve_enabled 取值不变。
