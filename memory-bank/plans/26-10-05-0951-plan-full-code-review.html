01结论与拍板点

本任务定性为 只读取证: 评审轮内 不改一行代码、不改一份文档, 全部产出是「发现清单 + 分级 + 处置去向」。修复一律另走认领(issue → 计划 → 实施), 避免评审轮与修复轮混在一起导致范围失控。方案骨架三句话:

  • 先底册后读码 —— 评审开工先把 issues 池 38 条 Open、坑档 7 类、在途计划/报告、守阵清单蒸馏成一页「已知问题底册」, 之后每条发现先对底册去重, 不报告已知问题。
  • 分批包结构 + 统一动作序列 —— 8 个批次覆盖全部源码(前端可拆两轮), 每批一轮会话, 统一走「读档 → 坑档对照 → 逐文件读码 → 工具提示源 → 登记去重」五步, 每轮收尾走会话 DoD。
  • 证据纪律 —— 每条发现必须带 文件:行 位置 + 可达性论证; 沿用近期复验先例(如 hr verified 覆写 issue 复验判「全路径不可达」), 不可达不登记为 bug。
评审报告落在 memory-bank/reports/(审计工位), 与本计划共用专题 full-code-review; P0/P1 在 S6 一律经 create-issue 入池并互链。

04评审方法与发现登记

每批统一动作序列(五步)

开工 my-commit-flow.sync → 记本批 HEAD ↓ ① 读档 systemPatterns / modules 对应主题 + 该包 docstring 建心智模型 ② 坑档对照 pitfalls/ 相关类先过一遍(历史缺陷模式 = 免费检查清单) ③ 逐文件读码 按 LOC 降序, 每文件对照维度矩阵勾选, 全文件过目 ④ 工具提示源 ruff + bandit 限该包范围, 逐条人工复核(D3 拍板后) ⑤ 登记去重 发现表回填报告草稿 + 已知底册撞车标注 ↓ 收尾 会话 DoD: activeContext 切片 + test.full 记数字 + 报告草稿落盘
基线不变式: 评审轮不改码, 每轮 test.full 数字应与起点基线(2581+4 / 98%)持平 —— 漂移只可能来自他人提交或环境变化, 先查明再继续, 这本身就是评审期间的回归哨兵。

发现条目登记格式

字段约定
ID<批字母>-<序号>(如 A-03), 跨批不重号
维度R1–R10 之一 + 必要时补「general」
级P0 数据破坏/安全/PT 账号风险 · P1 功能错误(恒不触发/恒误报/洗白类) · P2 健壮性(边界/竞态/退避缺失) · P3 可维护性/命名/文档
位置三锚: 文件:行 + 函数/类名(行号漂移时靠函数名找)
症状一句话说清「什么条件下会出什么问题」
可达性证据调用链论证或复现路径; 论证不出可达就不登记为 bug(降 P3 备查或不记)
撞车底册 issue 编号 / 坑档 / 在途计划, 三者其一或「无」
处置建议入池(建议类型与档位) / 并入在途计划备注 / 仅记录不处置
