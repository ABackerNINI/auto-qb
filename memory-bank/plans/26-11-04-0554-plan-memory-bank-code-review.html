收口 code review 制度化实施计划

把 code review 固化为「完整任务收口」的前置动作:规程住新 skill、机械面进 review 命令包、触发挂收尾 DoD 第 0 步——设计主轴是判断与机械分离:收口判定与相关性裁决留给 agent,引文逐字校验、规模分档、基线钉死交给脚本。

§01目标与设计原则

为什么做:任务收口前没有第二双眼睛。agent 自查会顺着写代码时的思路走(新鲜眼缺失),而 LLM 评审有两个已证实的失效模式——幻觉引文(引文与源码对不上)与长上下文稀释(单代理扫大 diff 时漏检)。本任务把评审做成带固定输入、固定产出格式、固定裁决口径的流水动作,失效模式用机械手段对治。

完成判据:①收口任务在收尾 DoD 各步之前完成评审+裁决+留痕,blocker 级发现清零;②评审发现可追溯(引文过逐字校验、入池件有编号);③本任务自身首跑评审通过(dogfood)。

设计底线/不变量:

  1. 判断与机械分离:收口判定、相关性裁决、severity 定级是判断,不脚本化;引文校验、分档、基线自检是机械,不靠人眼。
  2. reviewer 只读:评审子代理禁任何 git 状态变更(单一写线程原则在评审场景的延伸)。
  3. 基线钉死:评审期间工作区状态不变;子代理开工自检锚(派遣时 HEAD)不匹配即停手。
  4. 范围守恒不被架空:「相关」写死定义(计划目标内 / 本任务改动直接引入或暴露),其余一律入池。
  5. 不加机械守卫:评审是判断性动作,硬守卫逼出走过场;先攒复发数据再议。
  6. 既有闸门不重复:红线(.my-commit-flow.toml red_lines)、新配置键同步(validate 守卫测试)已有机检,评审只查闸门外侧面;非ASCII 符号不在任何闸门内,须评审真查。

§02现状与痛点

现状:收尾 DoD 实际 7 步(.agents/skills/memory-bank/SKILL.md 「收尾 DoD」节),无评审步;评审质量全靠 agent 自觉,无固定评审包构造、无产出 schema、无裁决口径、无留痕。

痛点证据:

  • AGENTS.md 两处写「DoD 5步」(L16、L20),与 skill 实际 7 步漂移;守卫指针 tests/test_memory_bank.py 是死路径(实际四分:test_memory_bank_{cli,docs,naming,structure}.py)——顺手修,见 D10。
  • 子代理上下文自动继承 AGENTS.md 的「开工同步硬性」规则,评审子代理可能执行 my-commit-flow.sync → 快进/rebase 使评审基线漂移、引文行号全错。三层修复见 §03。
  • 调研佐证:单次评审 200–400 行可达 70–90% 缺陷检出率,超 400 行明显衰减(SmartBear/Cisco 案例,smartbear.com);业界对幻觉引文的对治是逐字引文+行号、对不上即弃(level1techs 社区流水线);Cloudflare 按风险分档定评审投入(blog.cloudflare.com/ai-code-review)。

§03方案总览

主线三层:①触发层——完整任务=命中立档阈值 4 条,review 挂任务收口那次收尾、DoD 全部步骤之前,中途「提交」不触发;②规程层——新 skill 八节承载全部语义;③机械层——.commands/review/ 包两个 task id(review.pack 评审包生成、review.check 引文校验)。

子代理 sync 风险的三层修复(排障时按层检查):

  1. 治本:AGENTS.md 同步条目加「只读评审子代理豁免」句(可写子代理不豁免)——子代理实际只看得到 AGENTS.md,豁免必须写在它读的文件里。
  2. 固化:skill ③ 评审提示模板三件套(只读契约 / 双 hash 钉死 / 开工自检),主 agent 派遣照抄不临场发挥。
  3. 兜底:开工自检把静默错位变干净中止——即使前两层失效,sync 后 hash 不匹配即停手报告,不产出行号全错的报告。
