落盘文件 schema 版本号与逐级升级链

给程序落盘的结构化数据文件引入 schema_version 字段，并建立「每个版本只写 N→N+1 迁移函数、加载时沿链逐级执行」的升级框架。覆盖 state.json、hr/<site>.json、config.yml 三类；其余落盘点逐项豁免并记录理由。

01背景与目标

现状

  • state.json（核心状态）没有任何版本字段——顶层键形状散在多个写点，读回只有 _load_state 单入口（core/mixins/rule_engine.py:70）。结构演化目前完全靠读点 .get(默认值) / 写点 setdefault 隐式兜底，破坏性变更（键改名、结构重组）无从表达。
  • hr/<site>.json 已有 SCHEMA_VERSION = 1（hr/model.py:13），但版本不符一律报错拒绝（hr/store.py:125-127）——只「挡」不「迁」。挡是对的（未来版本不猜），缺的是旧版本向前迁移的能力。
  • config.yml 无版本概念。校验入口 validate_config 只认当前键集；将来任何键级重构（改名 / 拆分 / 挪段）都只能靠「未知键报错」硬着陆，用户旧配置直接 fail。
  • 程序自身版本号与文件格式无关，且已有双源漂移（pyproject.toml 0.1.0 vs __version__ 0.2.0，见 软件版本管理方案，专题 In Progress）——文件 schema 版本必须与之解耦，独立递增。

目标（用户口径）

所有落盘的文件需要增加版本号以及升级脚本；升级脚本只考虑从低一个版本的文件升级到下一个版本，形成升级链。

方案解读（本计划的两个关键转译）

  • 「升级脚本」= 代码内置的迁移函数，随加载自动执行，不另设需人工调用的独立脚本。取舍：自动链消灭「忘跑脚本」这一类事故；迁移函数是纯函数，照样可以单测、可以单独调用，人工介入通道并不丢失。
  • 「只考虑相邻版本」= 迁移表按 from_version 索引，每个注册项恰好 +1 级；跨多级升级由执行器沿链串行完成（v1→v2→v3），任何一级都不感知更早的历史。
  • 文件 schema_version 与程序版本（__version__）完全解耦：文件结构变一次就 +1，程序发版不迁文件；反之亦然。

03升级链框架设计

新模块 src/auto_qb/infra/versioning.py（文件格式基础设施与 atomic_write / locking 同层，不依赖任何业务模块）：

CURRENT_VERSIONS = {"state": 1, "hr_site": 1, "config": 1}

# MIGRATIONS[kind][from_version] = fn(data: dict) -> dict
# 纪律: 每个注册项恰好 +1 级; 纯函数(dict→dict, 无 IO);
#       原子写 / 备份等 IO 语义一律留在调用方。
MIGRATIONS: dict[str, dict[int, Callable[[dict], dict]]] = {
    "state":    {},   # 首个破坏性结构变更出现时, 在此注册 migrate_state_1_2
    "hr_site":  {},
    "config":   {},
}

def detect_version(kind: str, data: dict) -> int:
    """schema_version 缺失 → 1(存量文件口径);
    非 int / < 1 / > CURRENT_VERSIONS[kind] → SchemaVersionError"""

def migrate(kind: str, data: dict) -> tuple[dict, str]:
    """从检测出的版本沿链逐级 apply 到 CURRENT;
    已是最新则原样返回; 返回 (数据, "v1→v3" 形式的描述供日志)"""
  • SchemaVersionError(AutoQbError)：新错误类型（infra/errors.py），复用 CLI 既有 AutoQbError 干净出口（stderr + 退出码 1）。
  • 迁移函数集中注册在 versioning.py：当前三表皆空（三文件现行结构即 v1），首批真实迁移函数出现时若数量膨胀，再拆 migrations/ 子包——先不定死。
  • 版本检测的口径：字段缺失 = v1。这意味着本次改造对存量文件零迁移成本——state.json 现行结构定义为 v1，第一次破坏性结构变更才诞生 v2 与第一个迁移函数。
为什么本次不造一个假 v2 来「演示链」：为补字段动作凭空造版本，会让所有存量文件平白走一次迁移写盘，换来的是演示价值。链式执行的正确性由单测里的临时注册验证（测试内注册假 v2/v3），不落生产。

04三类文件集成点

4.1 state.json —— 读写双单点，改动最小

位置改动
_load_state（rule_engine.py:70）读回 dict 后过 migrate("state", …)；.bak 回退分支同样过链——备份与主文件同版本，链是幂等重放，重复执行无副作用
save_state（:133）与 _write_back_recovered（:93）写前统一打 schema_version = CURRENT["state"]（收敛为一个小助手函数，两处共用）
run() 持锁后加载完成处（core/qbmanager.py:370 附近）磁盘文件版本 < CURRENT 时立即落盘一次物化 + INFO 日志「state.json 已从 vN 升级到 vM」；沿用 _cleanup_orphan_tmp 先例——持锁后才写盘
__init__ 早期加载（qbmanager.py:195）只做内存迁移，不落盘（此时尚未持锁，写盘违背单一写线程判据）

4.2 hr/<site>.json —— 把「只挡」升级为「旧迁新拒」

  • _parse（hr/store.py:125-127）：版本 < CURRENT → migrate("hr_site", raw) 后继续 from_json；版本 > CURRENT → 维持现有「不符即拒」报错（未来版本不猜的既有判例不动）。
  • _write（:224）已打版本，不动。迁移结果随下次 HrLockSession.commit 物化——revision 心跳机制天然保证写回一致。
  • 多实例共存语义：老实例读到新版本文件 → 报错拒绝（现状保持）；这正是版本字段对 HR 共享目录场景的核心价值。

4.3 config.yml —— 校验前迁移，写回时打标

  • load_config（config/loaders.py:335）：YAML 解析后读 config.schema_version（缺失=1）→ migrate("config", data) → 再进 validate_config；未来版本 → ConfigError 聚合报错风格报出（「配置 schema 版本 3 高于本程序支持的 1」）。
  • schema_version 作为新配置键走六处同步（黄金法则 4，守卫测试带路）：KNOWN_CONFIG_KEYS（validation/core.py:9）+ int ≥ 1 校验 + config/schema 包 Field（标记不可编辑，参照 R 级字段先例）+ impact 分级 + models / 文档。该键是文件格式标记而非行为配置，不进 Config dataclass——loaders 在迁移分派后即消费掉。
  • 写回侧打标：write_tree（config/writer.py，WebUI 保存）与 --export-yaml（core/exporter.py:97 export_yaml_template）写出时补 config.schema_version。
  • 运行期不主动写回 config.yml：磁盘物化发生在下一次 WebUI 保存；启动检测到旧版本时日志提示一次。用户手编配置永远不需要手写这个键。
红线：本机 config.yml 与 auto-qb-data/ 是生产文件，实施全程只改代码，不碰这两个文件本身；验证用 minimal.yml / test_yamls/ 与临时目录。

05故障语义与一致性

情形行为依据
文件无 schema_version视为 v1，正常加载存量文件口径，零迁移成本
版本 < 当前支持沿链逐级迁移，INFO 日志留痕，按 kind 各自的物化时机落盘本计划新增能力
版本 > 当前支持（文件比程序新）fail-fast 启动失败，报错说明两个版本号；不静默清空、不回退 .bak备份里也是同一个新版本，回退无意义——hr/store.py:107 既有判例；回退旧版程序读新 state 同样被拦，防静默降级写坏
版本字段非 int / < 1SchemaVersionError，与损坏文件区别对待（不算 _CORRUPT）版本问题不是内容损坏，混进三态模型会触发错误的 .bak 回退
迁移后、写回前崩溃文件保持旧版本完整内容；下次启动从旧版本重放同一条链幂等性（黄金法则 1）：链的输入是磁盘上的真实版本，重放天然幂等
dry-run 模式迁移仅内存，不落盘与现有 dry-run 落盘口径一致（qbmanager.py:450-451）
.bak 的角色不变：仍是「上次成功写盘」的副本；迁移链不依赖 .bak备份与主文件同版本，「从备份猜」没有意义（既有决策）
单一写线程（黄金法则 5）：迁移执行只出现在启动序列（主线程、持锁后物化）；运行期不重读 state 覆盖内存态——issue 26-09-21-1347 的守阵 test_apply_new_config_l2_preserves_runtime_state 会拦。写点纪律（迁移函数纯函数、无 IO）让这条约束结构性成立。
