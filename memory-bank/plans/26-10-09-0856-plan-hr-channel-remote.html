HR 取数通道「外部扩展 / 跨机」支持 分步实施计划

上游 issue 26-10-09-0855: 用户判定「扩展只能本机」为设计缺陷, 未来须支持「auto-qb 配置在 NAS 里, 通过 WebUI 访问, 浏览器扩展装在外部 PC」的形态。本计划放开两端被写死的回环边界, 并先给出零改码的即时通路(SSH 隧道) 作为现状兜底, 再设计原生支持。核心难点不在「放开校验」, 而在放开之后的安全模型 —— 传输加密、鉴权节流、来源可分辨, 三者列为本计划的拍板点与实施重点。

01拍板回执与范围

事项结论
用户诉求当前「HR 端点只听回环 + 扩展硬拒非回环」使「NAS 集中管理 + 外部机器提供浏览器态」这一类合理部署形态整体不成立; 用户判定为设计缺陷, 要求未来支持。
本计划范围① 后端端点主机成为可配项(S1/S2); ② 扩展放开非回环校验 + 补齐端点 origin 权限申请(S3); ③ 传输安全与鉴权加固(S4, 依赖拍板); ④ 与故障归属分层的衔接(来源可分辨, S5); ⑤ 测试与文档(S6)。
明确不在范围① 不改变保守默认 —— host 缺省仍是 127.0.0.1, 现有同机部署零感知(黄金法则 2); ② 不动站点 URL 白名单 / 解析 / 判定(安全资产逐字保留); ③ 不做多用户 / 多租户鉴权(超出一个自托管工具的范围); ④ 不废弃 hr_check.shared_dir「只读共享数据」路径 —— 它与本计划是并列的两条路。
Is 已修问题?否, 新特性。两端都是显式写死(后端连 host 配置键都不给、扩展 normalize.js 直接抛错), 注释里还点名了 NAS 场景 —— 是设计取舍, 不是回归。
与 hr-fault-domain 计划的关系该计划的「WebUI 活跃信号」与「设计边界」callout 建立在本形态不受支持的前提上。本计划落地后:「设计边界」应翻转为「已支持」; 而 WebUI 活跃信号不需要任何同源 / 同机判断(该计划 26-10-09-0913 版已把判据简化为「WebUI 是否活跃」), 故跨机对本计划不构成额外约束; 但通道层需新增一类「跨机网络不可达」。两份计划需同步, 见 §03.4。
先说一个能立刻用的通路: 在用户当前形态下, 一条 SSH 本地端口转发即可让现状零改码跑通 —— 见 §03.2 路径 A。本计划设计原生支持, 但不阻塞用户今天就开工。

03方案设计 (跨机形态)

3.1 目标形态与数据流

协议、端点集合、鉴权方式全都不变 —— 仍然是浏览器扩展每分钟一次 HTTP 短轮询, 仍然 token + origin 两道关。变的只有两件事: 端点绑在哪个地址、扩展认不认非回环主机。

目标形态 (跨机):

  ┌─ NAS ──────────────────────┐            ┌─ 外部 PC (日常浏览器) ─────────────┐
  │  auto-qb 主程序            │   LAN      │  WebUI (访问 NAS 的 webui)         │
  │  ├─ HR 取数线程 / 解析      │            │  扩展 hr-fetch-proxy (轮询端点)    │
  │  └─ 端点 host = LAN 地址   │ ─────────▶ │  └─ 站点请求带本机登录态, 回传页面  │
  │      (默认仍是 127.0.0.1)  │  HTTP+token │                                    │
  └────────────────────────────┘            └────────────────────────────────────┘

不变: 短轮询 60s · token 鉴权 · origin 白名单(chrome-extension://) · URL 白名单(下发时卡死)
变化: 端点 bind 地址(可配) · 扩展主机校验(放开) · 传输加密(需拍板) · 401 节流(需补)

3.2 四条达成路径 (先看清"最小代价"是哪条)

「支持外部扩展」不必等价于「改两端」。下面四条都能达成用户的目标形态, 代价差异极大:

#路径改谁攻击面 / 代价评价
A SSH 本地端口转发 (隧道) 零改码 PC 上 ssh -N -L 8788:127.0.0.1:8788 user@nas ⇒ PC 的 127.0.0.1:8788 直达 NAS 端点。扩展看到的是回环, 两端校验都自然通过; 加密由 SSH 提供。 立即可用。隧道断则通道静默(与"浏览器关着"同形, 由故障分层的通路裁决)。
B NAS 侧反代 (nginx/caddy 终止 TLS) 仅扩展 反代绑 LAN + TLS, 转发到 127.0.0.1:8788; 后端仍只听回环 ⇒ 后端攻击面零扩大。扩展需放开非回环校验 + 申请远端 origin。 推荐给「想要 TLS 又不想动后端」的用户。
C 端点直绑 LAN (本计划主角) 两端 新增 host 配置键; 端点直接暴露在 LAN 上。传输安全需自决(见 §03.3 三方案)。 原生体验; 攻击面最大, 必须有传输与鉴权加固。
D VPN 组网 (Tailscale / WireGuard) 两端(视实现) 端点绑 VPN 接口地址; 网络面由 VPN 承担加密与准入。校验放开同 C。 适合已用 VPN 的用户; 本质是 C 的加固外壳。
本计划的取舍: 把 C(直绑) 做成产品化能力(配置键 + 扩展放开 + 文档), 同时把 B(反代) 写进文档作为「后端零改动」的推荐路径, 并明确 A(隧道)是当前即可用的兜底。这样: 想要原生 → C; 想要安全省事 → B; 想今天就用 → A。

3.3 原生路径(C)的改造面

3.3.1 配置面: hr_check.channel.host

  • 默认 "127.0.0.1"(保守默认不变); 允许填具体私网地址(如 192.168.1.10)或 0.0.0.0(全部网卡)。
  • 校验联动(重要): 当 host 非回环时, 若 token 为空 ⇒ validate_config 报错 —— 绝不允许「无密钥 + 全网可达」。这是把「保守默认」升级为「安全默认」的关键一条。
  • 0.0.0.0 与具体地址的区别写进文档: 前者暴露所有网卡(含可能的上网口), 后者可精确限定。

3.3.2 扩展面

  • normalize.js: 放开非回环; 建议限定私网段(10./172.16-31./192.168.)或走显式白名单, 而非任意公网域名 —— 避免扩展被诱导连公网端点。
  • manifest.json: 静态 host_permissions 保留回环三项(同机场景零授权); 远端端点 origin 走 chrome.permissions.request 动态申请(与站点 origin 同一流程, 见 options.js:267)。
  • 协议折叠: 若采用 TLS 方案, normalize.js:43–45 不再是「一律折 http」, 而应按 https 保留 scheme(否则会握手失败)。

3.3.3 传输安全(三候选, 见 §05 D1)

方案做法代价
T1 受信 LAN + token明确假设「端点只在受信内网」; token 已具; 依赖 LAN 物理/账号信任明文 HTTP, token 在 LAN 上可嗅探(家宽/小办公室可接受, 公共网络不可)
T2 端点 TLS端点裹 ssl 自签证书MV3 的 fetch 不能忽略证书错误 ⇒ 需用户导入 CA / 企业策略; 复杂度高
T3 反代终止 TLS即路径 B: 反代对外 TLS, 后端仍回环需用户自建反代; 后端零改动零攻击面 —— 这也是为什么 B 值得单独写进文档

3.3.4 鉴权加固(与 hr-fault-domain 的 P4 同源)

  • 401 出口现为 logger.error 且无节流(server.py:212–215)。同机下这只是刷屏; 跨机后它变成可远程触发的刷屏 / 枚举面 —— 必须加节流(状态变化时报一次 + 持续期按 gap 提醒), 并把级别降为配置态档。
  • 建议同时给「被拒次数」一个简单上限(如按来源地址计数, 超阈临时静默日志) —— 具体阈值待定, 不在本计划硬编码。

3.4 与故障归属分层(hr-fault-domain)的衔接

本计划落地会让那份计划的三处口径过时, 必须同步(本计划不代改那份文件, 由实施时一并处理):

#那份计划里的原文本计划落地后须改成
C1「WebUI 活跃信号」(原 W-b「活跃必须与扩展同源 / 来源地址交集」)简化为「WebUI 是否活跃」单信号(用户口径⑤, 2026-10-09-0913): 不判断同源 / 同机, 不推断「扩展离线」, 只陈述「WebUI 有活动而扩展未在联系」。跨机形态下因此不需要来源地址比对 —— 本计划无需为它新增任何面。
C2「设计边界: NAS + 外部扩展的形态下 HR 取数整体不成立 … 属新特性, 不在本计划范围」改为: 该形态由本计划支持(hr-channel-remote, issue 26-10-09-0855); shared_dir 仍是并列的只读路径, 不再作为唯一解。
C3通道层三档: 预期离线 / 可定位故障 / 无联系跨机后新增第四类「跨机网络不可达」 —— 端点监听中、扩展在跑, 但 LAN / 隧道 / 防火墙断了。它在后端观测面上与「无人联系」同形, 故仍归「无联系」档的文案分支, 但需明确列出「查隧道 / 查 LAN / 查防火墙」。
一个必须点明的观测盲区: 路径 A(SSH 隧道)下, 隧道断与浏览器关在端点观测面上再次同形(都表现为"没人来联系")。区别只在于「是否有人在看 WebUI」—— 这由 C1 的极简判据覆盖(活跃 ⇒ 告警, 不活跃 ⇒ 静默), 不需要判来源、判同机。故 C1 是跨机形态的必要件, 而其实现成本已被压到「复用既有 is_active()」。

3.5 安全面重评(为什么放开是可接受的)

风险现状放开后缓解
端点变「带登录态的任意站代理」(SSRF)已挡: URL 由后端按配置拼出, 端点不接受 URL 入参(UrlPolicy)不变 —— 这条与 bind 地址无关资产保留
token 在 LAN 上被嗅探不适用(不出本机)明文下可被同网段读到 token§05 D1 的传输方案; 或文档明确「仅受信内网」
鉴权枚举 / 刷屏只影响本机日志可被远程触发S4 节流 + 来源计数上限
伪造任务回传已挡: 只有派发过的任务 id + 域名一致才收不变资产保留
普通网页 JS 打端点已挡: 非 chrome-extension:// origin 一律 403不变(LAN 上的浏览器页同样被 403)资产保留

结论: 放开 bind 地址不引入 SSRF 类新风险(URL 白名单在派发时卡死), 新增风险集中在「传输机密性」与「鉴权滥用」两点, 均可通过拍板方案收敛。

05拍板点

#事项建议 (待拍板)
D1 传输安全走哪条? T1 受信 LAN + token / T2 端点 TLS 自签 / T3 反代终止 TLS 推荐 T3 为首选并在文档主推, T1 作为「家宽/受信内网」的轻量默认, T2 标注为高复杂度备选。理由: T3 让后端零改动零新攻击面(TLS 由用户的反代承担), 与「后端最小暴露」的项目气质一致; T1 是零成本但明文的现实解; T2 受 MV3 证书信任限制, 用户体验差。若只选一条: T3。
D2 扩展放开到哪一档? 仅私网段 / 任意主机(加警告) / 显式白名单 推荐「回环 ∪ 私网段(10./172.16-31./192.168.)」。理由: 恰好覆盖 NAS / 局域网场景, 又不会让扩展被诱导去连任意公网端点; 需要公网时用户应走反代 + 域名, 属进阶用法, 可后续单开白名单能力。
D3 后端 host 是否允许 0.0.0.0(全网卡)? 推荐允许但文档警示: 0.0.0.0 会暴露所有网卡(可能含上网口); 引导优先填具体私网地址。校验层面两者都放行(不做过度限制), 靠「非回环必须配 token」兜底安全。
D4 多扩展拓扑: 一台后端是否接受多台机器的扩展同时连接? 推荐「协议上允许, 配置上默认单扩展」: extension_id 现可钉死一个 id; 跨机多机时需要多 id。建议先不扩 extension_id 为列表(避免过度设计), 文档说明「多机共用同一浏览器扩展 id 亦可(同一扩展装多台), 端点按 token 鉴权即可」—— 待真有需求再单开。

06验收判据

#判据怎么验
V1同机部署零回归: 不配 host 时端点仍只绑 127.0.0.1, 现有行为逐字不变单测(host 缺省) + 真机同机跑一轮
V2非回环 + 空 token ⇒ validate_config 报错S1 校验用例(安全默认)
V3跨机形态(S1–S3 后)扩展能拉到任务并回传真机: NAS 绑私网 + 外部 PC 扩展填 NAS 地址 ⇒ 一轮取数成功
V4扩展拒绝非私网主机(按 D2 结论)normalize 用例: 公网域名 ⇒ 抛错; 私网/回环 ⇒ 通过
V5401 不再每分钟刷 ERROR / 推送真机: 错 token 跑 10 分钟, 日志与通知均不增长(P4)
V6跨机形态下「有人在看 WebUI 但扩展未在联系」能被告警真机: NAS 上开 WebUI + 停用外部扩展 ⇒ 入环告警; 无人用 WebUI ⇒ 静默(判据 = WebUI 活跃, 不判来源)
V7文档齐备: README 跨机节 + 四条路径 + 排障新类; hr-fault-domain 三处口径同步人工核对 + commands run doc.links
V8全量不回归commands run test.full + kb.check; 新基线切片单点记数字

07风险与不变项

7.1 已接受的风险

#风险评估
R1明文传输下 token 可被同网段嗅探(选 T1 时)由文档明确「仅受信内网」+ 建议 T3; 用户须知情。不选 T1 则风险消失。
R2端点暴露到 LAN 后被扫描 / 探测token 鉴权 + origin 白名单仍在; URL 白名单使端点无法被用作跳板。残余面是鉴权枚举 ⇒ S4 节流覆盖。
R3隧道/反代/VPN 中断时, 通道静默与「浏览器关着」同形靠 hr-fault-domain 的「WebUI 活跃」判据区分(活跃 ⇒ 告警, 不活跃 ⇒ 静默, 不判来源); 文案需列出「查隧道 / 查网络」。
R4新增配置键触发的守卫测试(writer / schema / mutation)期望变更S1 明列须核对项; 属机械同步, 不构成设计风险。
R5扩展放开判据后, 误放行非预期主机按 D2 限定私网段; 用例覆盖公网拒绝。

7.2 不变项 (须逐条保持)

  • 默认仍回环 —— host 缺省 127.0.0.1, 同机部署用户零感知。
  • URL 白名单 / 任务绑定 / origin 白名单三道安全资产逐字不变。
  • 协议不变: 仍是 60s 短轮询 + token 鉴权; 轮询周期 < request_timeout 的硬约束不变。
  • allow_reuse_address=False 的独占端口守卫不变; 端点线程「只入队 + 置一次旗标」的单一写线程假设不变。
  • hr_check.shared_dir「只读共享数据」路径保留 —— 与本计划并列, 不替代。
