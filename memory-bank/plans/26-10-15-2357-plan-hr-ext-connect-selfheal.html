Implementation Plan · HR 扩展连接自愈

HR 扩展「连接自愈 + 手动优先 + 不静默」修改计划

用户实报: 点「立即发现」有时显示 发现未命中(未知)、点「保存发现地址与配对码」后「自测端点连通」却说 先在 1. 存入一个实例端点再自测 —— 操作逻辑混乱。经 grilling 11 问收敛, 根因不在文案, 而在连接模型: 数据端口重启即变、扩展把发现结果当一次性缓存(死端点永久堆积)、后台发现结果进不了选项页(静默)、无任何常驻可见信号。本计划把连接做成自愈且可见的自愈通道, 并确立手动条目高优先级语义。仅动扩展侧(extensions/hr-fetch-proxy/), 不碰后端与发现协议。

01拍板回执与范围

下表是 grilling 三轮的全部决策; Q1–Q7 首轮通过(Q1 经用户更正), Q8–Q11 次轮通过。任何实现细节与下表冲突, 以本表为准。

#决策结论
Q1主从关系(更正后)发现 = 自愈 / 自动补充通道(负责端口变化后的自动恢复); 手动条目 = 高优先级的用户显式指定 —— 优先使用、优先展示、不被自动覆盖或删除。零配置时由发现提供全部实例; 一旦用户手动指定, 手动条目优先。
Q2发现实例的生命周期发现实例按租约管理: 每次成功发现整批替换旧的发现集(不再"只增不减"); 失效的发现实例自动剪除。手动条目原样保留。空集例外见 §05 C1(空结果不得清空发现集)。
Q3自愈时延任一实例拉取失败即触发一次发现(沿用 60s 节流, 覆盖"1 死 1 活不算全失败"的漏网); 周期发现 10 分钟 → 2 分钟。恢复靠发现, 用户零操作。
Q4可见性(不静默)① 工具栏图标加状态徽标(连接正常 / 重连中 / 发现失败 / 未配置); ② 选项页顶部加一行"连接状态"总览(上次发现时间、命中端口、实例数、最近一次发现结果)。lastDiscoveryAt 终于有展示位。
Q5失败反馈形态每个失败码映射成中文结论 + 逐候选探测结果 + 下一步动作; 后台 .catch 的 error 也显示出来; (未知) 字面量从代码里删除。
Q6手动兜底定位手动端点区保留但折叠; 发现成功不覆盖手动条目; 发现失败态提供"改用手动指定"的跳转。
Q7改造范围本轮只动扩展侧(options.html/js、background.js、discovery.js、README.md、测试守阵)。不动后端 hr/*.py、不动发现协议常量。后端"持久化上次实绑端口"记为后续可选增强。
Q8同端点冲突合并规则手动整条胜: 保留手动的 name/token/source, 发现的同端点条目直接丢弃。发现只做"补齐手动没覆盖的端点", 不碰手动。
Q9"高优先级"的作用面a+b+c+d 全要: (a) 列表手动置顶; (b) 主实例(instances[0], 自测 / 拉站点清单用它); (c) 不可被自动覆盖/删除; (d) 轮询顺序手动在前。周期发现继续跑(只打本机 loopback, 成本可忽略)。
Q10手动条目失效处置只提示不代删: 连续拉取失败的手动条目在列表里打"疑似失效"标记 + 提示"发现到的端点已自动补入, 手动这条可能已作废, 确认后可删除"; 绝不自动删。
Q11呈现与措辞① 手动区标题由「手动端点(兜底: 发现关闭/失败时用)」改为「手动端点(优先: 你显式指定的实例, 永远优先使用)」; ② 实例列表手动置顶 + 「优先」徽标、发现条目「自动」徽标; ③ README.md 口径同步翻转; ④ 发现失败提示由"改用手动兜底"改为"改用手动指定"。视觉顺序保持"自动发现在前" —— 优先级靠列表内置顶 + 徽标 + 措辞表达, 不靠区块顺序。
明确不做范围外后端端口持久化(Q7)、后端/协议任何改动、mDNS/UDP 组播、多发现地址、自动删除手动条目、给发现端点加 token 鉴权。
与上游计划的关系: 26-10-14-1241 已 Done, 是发现机制的落地来源(S4 只做到"发现区块 + 立即发现按钮 + 实例并入", 未处理自愈与可见性)。本计划不回头改该计划, 只在它之上补齐"自愈 + 可见 + 手动优先"。S4 原文的"手动添加入口保留(兼容/兜底路径)"表述被 Q1 更正为"手动优先", 属口径演进, 不构成回归。

03目标形态与数据流

3.1 连接模型(三层)

发现地址 (稳定会合点, 默认 http://127.0.0.1:18788)
      │  探测候选表 18788/18789/18790 (并行)
      ▼
发现集 (租约)  ── 整批替换 ──▶  ┌─────────────────────────┐
      │                        │  实例清单 (唯一事实源)   │
      └── 补齐未覆盖端点 ──────▶ │  ① 手动条目 (优先)       │──▶ 轮询 / 自测 / 拉站点清单
                               │  ② 发现条目 (自动, 租约) │
手动端点(折叠) ─────────────────▶ └─────────────────────────┘
      (用户显式指定, 永不被自动覆盖/删除)
  • 发现地址是稳定会合点(发现端口默认固定 18788); 数据端口可能每次重启变化, 由发现分发。
  • 手动条目: source 非 'discovered'(或缺失)。置顶、优先、永不自动删。
  • 发现条目: source:'discovered'。每次成功发现整批替换; 失效自动剪除; 同端点让位手动。

3.2 合并规则(替代现有 mergeInstances)

mergeInstances(current, discovered):
  manual  = current 中 source !== 'discovered' 的条目          # 原样保留, 保持原顺序
  manualEp = Set(manual.map(e => e.endpoint))                  # 手动已覆盖的端点
  fresh   = discovered 中 endpoint 与 token 均非空,
                       且 endpoint ∉ manualEp 的条目           # 去重后按发现顺序
  # 空集例外(C1): discovered 为空 ⇒ fresh 为空 ⇒ 保留旧的发现集, 不清空
  if discovered.length === 0:
      out = manual ++ (current 中 source === 'discovered' 的条目)   # 不替换
  else:
      out = manual ++ fresh.map(d => ({name, endpoint, token, source:'discovered'}))
  return out
为什么不无条件整批替换: 后端重启瞬间, 注册表条目可能已过 TTL 或心跳未落 ⇒ 发现返回空集。若此时清空发现集, 扩展会自断连接(且实例为空时连"失败即发现"都不触发, 只能等周期)。故空集 = 不替换(见 §05 C1)。

3.3 连接状态机与徽标四态(Q4)

态徽标判据触发更新点
未配置(空)发现地址为空 且 实例清单为空load / instances 变更 / 保存
连接正常✓ 绿最近一轮轮询至少一个实例成功pollAll 收尾
重连中… 橙有发现地址, 但当前无成功实例(全失败 / 发现集为空 / 手动全失败)pollAll 收尾 / runDiscovery 收尾
发现失败! 红候选表全无应答(非 401/异形) 且 无任何可用实例runDiscovery 收尾

徽标文案用 chrome.action.setBadgeText, 底色用 setBadgeBackgroundColor; 图标点击(无 default_popup)经 chrome.action.onClicked 打开选项页。禁用(enabled:false)时清空徽标。

05实施期裁量点

#裁量点结论 / 处置
C1发现返回空集时是否清空发现集不清空: 保留旧的发现条目(可标"待确认"), 并继续按周期/失败重试。理由见 §3.2。此为 Q2"整批替换"的唯一例外, 防自断连接。
C2发现返回部分集(多实例死其一)是否替换替换(非空即整批替换): 死掉的实例自然被剪除, 符合 Q2 意图。
C3手动条目失效标记的阈值连续失败 ≥3 轮(约 3 分钟)才标"疑似失效", 避免瞬时抖动误报; 由 instanceHealth 的连续失败计数判定。
C4徽标"重连中"与"发现失败"的边界有候选应答但无可用实例(如配对码缺失) → "重连中"(可自愈); 候选全无应答 → "发现失败"(需人工看一眼)。
C5顶部总览是否随每次轮询刷新是(1 分钟节拍), 但"上次发现时间"只在发现后变; 总览文案同文不重排(防闪烁)。
C6手动端点区默认展开/折叠折叠; 但"发现失败"态下自动展开并高亮, 降低用户下一步的操作成本(Q6)。
C7是否给手动条目也自动发现是: 手动条目失败同样计入 failCount 触发发现(Q3 口径"任一实例")。
C8旧 instances 数据迁移不写迁移脚本: 旧条目无 source 字段 ⇒ isManualEntry 判为手动 ⇒ 自动获得"优先"语义, 行为等价于"用户显式指定", 零破坏。

#判据验证方式
