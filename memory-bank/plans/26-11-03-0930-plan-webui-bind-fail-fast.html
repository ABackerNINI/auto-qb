WebUI bind 失败改为启动期 fail-fast

把「WebUI 端口被占 → 只记一条 ERROR、进程带病继续」反转为「启动期 fail-fast：干净退出码 1 + 可操作文案 + 跨平台占用者诊断」。设计主轴：失败发生在启动期，就让它带走进程；运行期语义一行不改。

§01目标与设计原则

目标：当 web.enabled=true 且 WebUI 监听失败时，进程在启动期以退出码 1 结束，stderr 给出一条可直接照做的单行指令，日志留下含占用者与处置的结构化诊断。做到这一步即算完成；不做运行期自愈、不做 WebUI 内状态展示。

设计底线 / 不变量：

  • 只碰启动期：热重载 apply() 的重启路径行为不变；运行中 uvicorn 线程异常退出不在本计划范围。
  • 单一写线程（黄金法则 5）：状态落盘与锁释放仍只在主循环线程/run() 的 finally 执行；诊断探针不写任何业务状态。
  • 无新配置键（黄金法则 4）：不引入 web.fail_fast_on_bind 之类开关，因此 validate_config 与 config/schema 零改动。既有的 web.enabled / web.host / web.port 原样使用。
  • 诊断是旁路：探针失败、超时、命令缺失都不得改变退出码、错误类型或 stderr 主行。
  • 可操作：文案必须同时给出「改哪个键 / 怎么改 / 怎么关 / 进程会怎样」。

§02问题与取证结论

issue 标题说「静默吞掉」，复验后的准确结论是三缺一有：缺诊断、缺机器可读面、缺自愈；但人可见的失败信号其实已经存在。

维度现状（取证）结论
失败是否被记录 _run_server 捕获 BaseException 并记 ERROR（lifecycle.py:146-157）；start_web_server 再记一条「WEB UI 启动失败: host:port 无法监听」（lifecycle.py:206-208），并返回 started=False 的句柄。 不是「无日志」，是日志没有可操作性（只说「端口被占用?」）
失败态是否被消费 WebServerHandle.started 全仓零消费方；失败后 web.handle 仍非空，WebUIModule.start 的幂等闸（module.py:69-71）导致配置不变即永不重试。 无状态面、不自愈
人可见信号 控制台 StreamHandler(sys.stdout)（logging.py:101-105）；滚动日志文件默认 <data_dir>/logs/auto-qb.log（loaders.py:660）；notify handler 在 webui 之前挂载（qbmanager.py:166-168 vs L218），min_level 默认 ERROR（models.py:350），所以今天这条 ERROR 已经会推一条 toast。 已有，但信息量不足
机器可读面 容器 healthcheck 仅 GET / 布尔值（compose.yaml:25-32）；/api/status 由「起不来的那个服务」提供（routes/state.py:46-52）→ 对本次故障恒不可读；state.json 是业务态且有单一写线程约束，不适合承载运行期健康位。 容器有布尔面（unhealthy）；裸机无面
契约 RM01-06 显式断言「端口被占进程照常活」（test_rm01_startup.py:191-215）；真机基线切片把「不退出」记为 PASS（real-baselines/26-10-31-0831-real-RM01.md:25）；qbmanager 注释把 web 与 HR 的不对称写成口径（qbmanager.py:478-481）。 反转对象，见 §03
关键结构事实：失败检测同步发生在主线程——start_web_server 会等最多 WEB_START_TIMEOUT=5s 才返回（lifecycle.py:159-168、199），不是只发生在 web 线程里。因此「读结果 → 抛错 → 走 finally 释放锁」天然满足单一写线程。

§03已确认推翻的既有判断（契约反转）

被推翻的判断：「一个端口占用不该带走整个程序」。它不是一个注释，而是三处固化的事实：

  • RM01-06 的 docstring 把它写成失败判据（「进程直接退出 = 红」），断言 assert p.alive()（test_rm01_startup.py:191-215）。
  • 真机基线切片把它记为 PASS（real-baselines/26-10-31-0831-real-RM01.md:25）。
  • qbmanager.py:478-481 用注释把「web 记 ERROR 由句柄呈现 / HR 抛错穿透」的不对称写成产品口径。

谁确认：用户在 2026-11-03 的 grilling Q2 中明确回答「确认推翻」，并选择改判据（保留「先占端口再启动」的场景，把断言翻成干净退出），否掉「改场景配 web.enabled=false」与「删用例」两种更不诚实的做法。

反转后的统一口径：启动期监听了可选服务（WebUI / HR）失败 → 一律 fail-fast、干净退出码 1。HR 的既有 HrChannelBindError 行为不变，只是不再漏锁（见 §04.1）。

历史处理：旧真机基线切片是历史事实，不改写数字；RM01-06 改判据后，用新切片记录新实测（口径见 memory-bank/testing/baseline.md）。

§04代码改动面

4.1 前置：把 start_all 移入 try/finally（qbmanager.run）

现状：self.host.start_all(dry_run) 在 qbmanager.py:484，位于 L485 的 try 之外；负责 stop_all → state.save() → lock.release() 的 finally 在 L703-710。任何模块 start 抛错都会跳过 finally → 锁与 state.lock.meta.json 残留。

# qbmanager.run()：目标结构（示意）
lifecycle_ready = False
try:
    self.host.start_all(dry_run)      # ← 从 try 外移入
    lifecycle_ready = True            # ← 新增：启动期完成闸
    ...                               # 连接 / 主循环（原样）
finally:
    self.host.stop_all()
    if not dry_run and lifecycle_ready:   # ← §4.2 闸门
        self.ctx.state.save()
    if self._lock is not None:
        self._lock.release()

连带行为变更（需在提交信息与文档写明）：既有 HrChannelBindError 在启动期抛出时，现在也会走 stop_all + lock.release()，即修掉 HR fail-fast 的既有漏锁。这不是顺手改，是 A 路线「锁已释放」判据成立的必需前置（Q4b 已确认）。

注意：qbmanager.py:472 的 materialize_schema_migration 仍在 start_all 之前，磁盘版本落后时的迁移落盘不受影响。

4.2 空态 state.json 闸门

失败启动若执行 state.save()，会在 fresh 目录落一个只有 schema_version 的空态文件（state.py:179-180、227-242）。功能上无副作用（load() 对缺失/空文件都返回 {}，state.py:95-98），但会误导人、并破坏「fresh 目录不该有 state.json」类断言。

方案：用 §4.1 的 lifecycle_ready 闸门，只有 start_all 正常返回后才允许退出落盘。仍由主循环线程调用（黄金法则 5）；正常运行的非优雅终止丢失窗口语义不变（黄金法则 3）。

4.3 WebUIBindError 与抛点（R1）

错误类：定义在 lifecycle.py（就地定义，不新建模块文件，仿 QbConnectError 的做法）：

class WebUIBindError(AutoQbError):
    """启动期 WebUI 监听失败(端口被占/地址非法)。AutoQbError => CLI 干净退出: 码 1、stderr 一行、无堆栈。"""

抛点：WebUIModule.start——web.start_server() 返回后检查 web.handle 的 started：

# webui/module.py  start() 尾部（示意）
web.start_server()
handle = web.handle
if handle is not None and not handle.started:
    owner = describe_port_owner(...)          # 旁路探针，见 4.4
    logger.info(_format_bind_diagnosis(ctx.config.web, owner))   # 多行诊断块
    raise WebUIBindError(_bind_message(ctx.config.web))          # 单行，给 stderr/notify_fatal
self._subscriber.sync()
  • 为什么不在 start_web_server 内抛：该函数同时服务热重载 apply() 的重启分支（module.py:107-112），在那里抛错会把异常带进 PUT /api/config 请求，属于运行期语义变更。R1 让低层函数保持返回 handle 的原契约，test_start_web_server_reports_failure_when_port_taken 继续绿。
  • 日志分层：lifecycle 既有的那条 ERROR 保留（既有单测断言它）；模块层的多行诊断块用 INFO 记——它不是新的失败事件，而是同一故障的附加诊断，避免 handler 再推第二条 toast。前缀固定为 WEB UI 启动失败诊断，紧跟在 ERROR 之后。
  • toast 可靠性：只押 notify_fatal（notify.py:299-310，同步发送）；它由 cli.py:210 在 AutoQbError 分支调用，此时 manager 已构造、配置可读。handler 的异步队列在退出时可能丢，接受它「可能多一条、可能没有」。
  • 不改 cli.py：except AutoQbError 已覆盖新错误类，prefix 只对 ConfigError 加「配置错误:」，本错误直接输出。return 1 已是契约。

4.4 P1 跨平台占用者探针

新增 src/auto_qb/infra/port_owner.py（无外部依赖，纯标准库 + 平台命令）。返回三态，供日志选择文案：

PortOwner  = (pid: int, name: str, cmdline: str)
PortProbe  = found(owner) | absent(未找到监听者) | unavailable(原因)

def describe_port_owner(host: str, port: int, budget: float = 1.5) -> PortProbe
平台实现单步超时
Linuxss -ltnp（首选，解析 pid=）→ 失败转 lsof -nP -iTCP:<port> -sTCP:LISTEN；命令行直读 /proc/<pid>/cmdline（不再 spawn）各 0.5s
Windows一次 PowerShell（-NoProfile -NonInteractive）：Get-NetTCPConnection + Get-CimInstance Win32_Process 合并输出 pid|name|cmdline；不沿用 scripts 的两次调用1.0s
macOSlsof -nP -iTCP:<port> -sTCP:LISTEN；命令行再 ps -o command= -p <pid>各 0.5s

铁律：总预算硬上限 1.5s（失败路径在等完 5s 之后再叠加，可接受）；每步超时即杀子进程并降级；任何异常（FileNotFoundError / PermissionError / 超时 / 解析失败）只写 debug 日志；探针结果只进日志，绝不进 WebUIBindError 消息、stderr 或 notify_fatal 内容。

降级文案（显式，不静默）：found → 占用者: pid=…, 进程=…, 命令行=…；absent → 占用者: 未找到(端口可能刚被释放)；unavailable → 占用者: 未识别(本机无 ss/lsof 或查询超时)。容器（python:3.12-slim-bookworm 只装了 tzdata）里 ss 与 lsof 都没有，走 unavailable 是常态。

安全：命令行截断 160 字符、换行替换为空格；可能含凭据，只落日志文件，不写 stderr、不推 toast。

4.5 文案

stderr（单行，WebUIBindError 消息原文）：

WebUI 启动失败: 127.0.0.1:8080 无法监听 (web.enabled=true, web.host=127.0.0.1, web.port=8080); 常见原因: web.port 被占用(同机多实例默认同端口); 处置: 改 web.port 换空闲端口, 或设 web.enabled: false 关闭; auto-qb 将退出(退出码 1), 采集不会启动

日志（多行 INFO 诊断块，紧跟既有 ERROR 之后）：

WEB UI 启动失败诊断 (web.enabled=true, web.host=127.0.0.1, web.port=8080)
  - 原因: 端口无法监听 (uvicorn: [Errno 10048] ...)
  - 占用者: pid=12345, 进程=python.exe, 命令行=...
  - 处置: 改 web.port(同机多实例各配一个); 监听地址写错则改 web.host; 不需要 WebUI 则 web.enabled: false
  - 退出: 启动期 fail-fast, 退出码 1, 采集不会启动

文案里的 host/port 用配置原值（127.0.0.1），不用展示口径 localhost（display_host 只用于「已启动」那条 INFO）。原因：用户要照着改 web.host。

§05文档与运维口径

5.1 docs/deployment.md 两处

  1. healthcheck 成因（L169-170）：由两种改为三种——① web.port 改了而 compose 的 ports/healthcheck 没同步；② web.enabled: false（容器活着但 unhealthy）；③ 端口被占。第③种在 A 之后的容器表现是「进程退出 → 容器 Restarting」，不再是「unhealthy 但照跑」，必须把这两种表现分开写。
  2. 退出码表（L174-181）新增一行：WebUI 启动失败(bind 失败/端口被占) → 退出码 1 → stderr WebUI 启动失败: ... → 「按 restart 策略重启」。

5.2 compose / systemd / 多 clone（只写口径，不改代码）

  • compose 不改：restart: unless-stopped（compose.yaml:9）对任何退出码都会拉起，Docker 自带指数退避（上限 1 分钟）；端口冲突不会自愈 → 表现是永久 Restarting、每分钟一次空转，不是快速崩溃循环。当前 compose 用 8081:8080 且容器独占网络命名空间，进程内 8080 冲突是低频场景；改 restart 无法区分 bind 失败与 qB 不可达，属生产行为变更，不做。
  • systemd：仓内无 auto-qb 自己的 unit 文件（systemd 只属于 tools/global-traffic-monitor，不受影响）。文档加一句：用户自建 unit 的 Restart=on-failure 会对退出码 1 按 RestartSec 无退避循环，建议 RestartSec=30s 或配 StartLimitIntervalSec。
  • 多 clone 并行：默认 web.port=8080（models.py:307-326），A 之后第二个启用 WebUI 的实例启动即死。这是用户已接受的代价；缓解只在文档（每 clone 独立 web.port）+ 文案已点明「同机多实例默认同端口」。配置层不做端口探测（那会把纯配置校验变成网络探测，破坏黄金法则 4 的分层），也不改默认端口。

§07明确「不做」清单

  • 运行中挂掉不处理：bind 成功后 uvicorn 线程异常退出仍维持现状（记 ERROR、句柄置未就绪、不自愈），不在本计划范围。
  • /api/status catch-22 明确不做：WebUI 死了就没有可读端点；不设计「失败态写进 API」的任何方案。
  • 不新增 web.enabled=false 长活用例：认 RM02-02 等既有真机覆盖（test_rm02_loop.py:244-259，write_cfg 默认 web_enabled=False）。
  • 不改 compose（restart / ports / healthcheck 一行不动）。
  • 不建 / 不改 systemd unit 文件（仓内不存在 auto-qb 的 unit）。
  • 不新增配置键，validate_config、config/schema 不动；也不在配置校验里探端口。
  • 不改默认端口 / 不做动态端口分配（issue 原文已定）。
  • 不清理失败启动留下的 web.token：ensure_token 在等待前已落盘（runtime_stream.py:210-212），属既有幂等语义，清理会引入额外删除路径。
  • 不重建 scripts 里 Windows 两次 PowerShell 查询；只在新 src/ 模块内实现单次合并。
  • 不新增 macOS CI job；不改写历史基线切片。

§11风险与对策

风险触发条件处置
探针拖慢退出PowerShell 启动抖动 >1.0s，或 ss 卡住每步硬超时 + 总预算 1.5s；超时杀子进程并降级为 unavailable；主消息不受影响
容器无探针slim 镜像无 ss/lsof固定输出「占用者: 未识别(…无 ss/lsof…)」；不假装「没人占」
占用者误判端口刚被释放 / IPv4/IPv6 双栈差异 / 权限不足文案统一用「疑似/未识别」措辞；探针仅辅助，不参与退出判定
命令行泄密占用进程命令行含凭据截断 160 字符、换行替换；只进日志文件，不进 stderr / toast
重复通知lifecycle ERROR 的 handler toast 抢在退出前发出 + notify_fatal接受「最多两条」；可靠性押 notify_fatal；诊断块用 INFO 不再触发新 toast
启动期其他模块抛错notify/logging 等 start 失败（非本次引入）移入 try 后统一走 stop_all + 锁释放；属行为改善，写进提交信息
热重载路径回归误把抛点放进 start_web_serverR1 明确禁止；新增模块级用例 + 既有低层用例双向守
容器重启空转端口被占 + restart: unless-stopped文档写明「永久 Restarting、每分钟一次、不会自愈」；用户按文案改端口
