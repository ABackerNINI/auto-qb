code-review 跨 clone rebase 组合缺口修补

本篇只回答一个问题: 跨 clone 并行开发下, 两批各自评过、rebase 组合后的树无人评的组合缺口, 怎么在评审时点闭合、在提交时点兜底、在 trailer 留痕。

§01目标与设计原则

背景。code-review 的批次锚点法(「最近一条 Review: trailer → 工作树」)与提交管线(「提交先行 → 内部 rebase → 推送」)各自成立, 但并行 clone 交错时存在组合缺口: clone A 与 B 各评各的批, ship.commit 把 A 的提交 rebase 进 B 的历史后, 组合树没有任何 reviewer 看过; 且 6b 复跑轮的 review.trace 被 POST_MARKER 显式跳过(check_review_trace.py:267), 组合树只有 test.quick 兜底、没有评审兜底。缺口发生时无任何信号, 事后也无法审计评审是否在齐平态进行。

目标(做到什么算成)。

  1. 评审时点闭合: 评审批次的上下文保证含远端全部最新代码(齐平), B 的 reviewer 看到的周边代码就是合流后的真实周边;
  2. 提交时点可见: rebase 真合入远端提交时, 「组合树评审未覆盖」从静默变为一行可见痕迹;
  3. 事后可审计: 齐平态进 trailer, 任何一笔提交都能查出它评审时是否齐平。

设计底线(不变量)。

  • 「评审固定发生在提交之前」(skill ①)不动, 不新增提交后补评时点;
  • 锚点法「不留免评节点」不动 —— 齐平协议必须与锚点现算兼容(实测兼容, 见 §03);
  • pack 保持纯本地瞬时(零网络依赖), 机械强制落在 reviewer 开工自检这个已有停手机制上;
  • 判断与机械分离: 齐平是 agent 动作(sync), 齐平判定是脚本/自检(ls-remote + rev-list 现查)。

§02现状与痛点

现状机制(证据)

  • 批次锚点 = 最近一条 Review:/Review-Skip: 提交, 全量 log 现算、不设扫描窗口 —— check_review_trace.py:194;
  • 提交管线: 闸门 → 提交 → 内部同步(分叉自动 rebase) → 6b 复跑闸门(「合并后的树才算数」) → 推送 —— commit.py:19,416;
  • 6b 复跑轮 review.trace 经 POST_MARKER 跳过, 原因: 锚点法会把 rebase 进来的远端提交算进本批 → 假红 —— check_review_trace.py:267;
  • 远端真相机制: fetch 拉对象 + ls-remote 现查, refs/remotes/* 写入本环境静默丢弃、不可信 —— sync.py:36;
  • 开工同步硬性(任何轮次第一个动作), 但只覆盖「会话开始」一个时点。

痛点(缺口的四层)

  1. 组合缺口: B 的评审批次范围 = B 本地锚点 → B 工作树(不含 A 的改动), A 对称地同样不看 B; rebase 组合后的树无人评。语义相交(A 改接口 / B 改调用方)在文本上不相交, rebase 静默合入。
  2. 静默: 缺口发生时无任何信号 —— 6b 只跑测试, review.trace 被跳过, 输出无一行提示。
  3. 不可审计: 评审是否在齐平态进行, 提交后无从查证(trailer 无此字段)。
  4. 已知非洞(澄清): 「无 trailer 提交被 B 的 trailer 掩埋、连坐机制扫不到」不成立 —— ≥50 行无 trailer 会被提交闸门拦下(check_review_trace.py:253), 能进历史的只有 Review-Skip(可审计)与低于下限豁免(设计内)两类合法态。

窗口大小。触发条件 = A 恰在 B 的开工 sync 之后、ship.commit 之前推送 + 语义相交 + 文本不相交 + 测试盲区, 四条同时成立才真漏。概率低但非零 —— 存量评审 R2/R3 各批都是跨日推进的, 窗口真实存在。

§03方案总览

三个落点, 决策编号对应 §06。

落点 1 —— 齐平协议 + 三钉自检 (D1/D4/D5)

  • 协议面(skill ④): 派遣前主会话跑 commands run my-commit-flow.sync, 结果行贴进评审记录; sync 失败按失败行自带出路解决(树脏重叠 → stash 配方), 确实解决不了(离线)才允许声明未齐平态派遣。
  • 机械面(三钉): 派遣三件套第 2 条「双 hash 钉死」扩为三钉 —— 批次 base / 自检锚 HEAD / 远端 tip。reviewer 开工自检加一条: git ls-remote 现查远端 tip → git rev-list --count HEAD..<tip>: 落后 >0 → 停手报告(评审上下文缺远端 N 笔, 主会话 sync 后重派); 落后 =0(含本地领先, 上一批推送失败的合法态) → 放行; tip 取不到(离线) → 打「无法核实」行继续评(「无法核实 ≠ 不一致」, sync.py:78 同款哲学)。
  • 收尾复核: 主会话加同款远端核对; 发现评审期间远端推进 → 不作废已交发现(评审对象 diff 未变), 但修复/收尾前必须重新 sync; 修复增量若触发复评(>100 行), 以齐平后上下文评。
  • pack 零改动; sync.py / review_pack.py 均不动。
锚点法兼容性(方案成立的关键): sync 后锚点现算自动跳到远端最新一条 trailer —— 评审包 diff 恰好仍只含本批改动, 且以 A 的代码为上下文。齐平协议不需要改任何锚点逻辑, 这正是锚点法「从历史现算」的红利。

落点 2 —— 复跑轮评审边界提示行 (D2/D3)

  • commit.py 步骤 6 分支(rebase 真合入远端提交)加一行步骤行: 评审边界: 组合树仅过测试闸门, 评审未覆盖远端 N 笔 · 路径 <前5条> · 与本批相交 M 处。
  • 不打条件: 远端改动路径全部落在记账类/生成物(口径与 check_review_trace.py:56 的 BOOKKEEPING_PREFIXES + gen_all.py --list 同源, 抄用 + 同源注释 —— 先例 SENSITIVE_PATH_MARKERS 双处同源)。
  • 相交标注 = 远端改动路径 ∩ 本批清单(commit.py 步骤 1 现成的本地改动清单); 判「远端改动路径」用 git diff --name-only <merge-base(旧HEAD, rsha)> rsha(只取远端侧, 不含本地侧)。

落点 3 —— trailer 齐平字段 (D6)

  • skill ⑦ 格式扩为 Review: <范围> · <N> 行 · blocker <N> · 修 <N> · 入池 <N>[ · 分面][ · 齐平 <远端tip前8位>]。
  • 弱校验: check_review_trace.py 对齐平字段只查格式(· 齐平 [0-9a-f]{8}), 不强制存在、不验 hash 真值; 格式异常打一行 warn 但 rc=0 放行。v3「全过即静默」约定让步一步: 警告仅在字段被写坏时出现。
  • 齐平 hash 的值 = 派遣自检核对的远端 tip 前 8 位, 与评审记录交叉可验。

§07风险与对策

风险触发条件处置
R1 reviewer 离线 ls-remote 等待久(默认重试 3×20s)离线派遣实测 >2 分钟判据先用默认档(与 sync 判据同款); 实测成痛点再收紧 attempts=1, 记入变更记录
R2 记账类判据第三处同源漂移BOOKKEEPING_PREFIXES / 生成物清单日后改动抄用 + 同源注释(先例 SENSITIVE_PATH_MARKERS); 统一 import 单点超出本轮范围, 不顺手做
R3 评审期间远端推进收尾复核远端核对发现落后不作废发现; 修复前强制 sync; 复评轮以齐平后上下文评; 落点 2 提示行兜底
R4 齐平字段被误当强校验字段写坏 / 缺位被误拦gate 仅格式警告(rc=0); skill ⑦ 写明弱字段地位, 与「行数 ±0 强校验」区分
R5 高频推送期三钉反复停手停手 → sync → 重派循环停手原因行自带出路; 停手是未齐平的正确代价, 不设豁免通道
