02

目标与非目标

目标

  • 一条命令起服务: docker compose up -d 后, 浏览器打开 Web UI 即可完成全部配置。
  • 状态跨重启续接: stop / start (乃至宿主机重启) 后, 标签历史、规则账本、限速状态接着上次继续。
  • 优雅停机 (P3 后): docker stop 走既有优雅退出路径, 落盘后再退出, 退出码 0。
  • 构建可复现: 镜像内依赖只认 uv.lock, 不出现「锁外漂浮」的包。
  • 红线不受影响: 仓库根的 config.yml 与 auto-qb-data/ 不进镜像、不进 .dockerignore 白名单、不进 compose 示例。

非目标

  • 多副本 / 高可用 —— 单实例锁天然拒绝双开, 本方案不绕过它。
  • 镜像发布到 registry (GHCR 等) —— 列为 P4 可选项, 首期只本地构建。
  • qBittorrent 本身的容器化 —— 用户 qB 跑在哪是既有事实, 本方案只解决「连得上」。
  • 托盘 / 状态窗口 / 桌面通知等桌面能力 —— 无桌面环境, 属预期不可用。
03

决策点 D1–D7

D1 · 镜像构建方式

uv 多阶段构建

推荐: builder 层用 ghcr.io/astral-sh/uv 镜像跑 uv sync --frozen --no-dev, 运行层 python:3.12-slim 只拷 venv。备选: uv export 出 requirements.txt 再 pip 安装 —— 运行层更干净, 但多一道导出物, 漂移风险与维护成本都更高。

推荐理由: 与 CI (astral-sh/setup-uv) 和本机开发同一把锁, 复现性最强; uv 官方镜像模式成熟, 不引入新工具链。

D2 · GUI 依赖处置

第一期保留在镜像里

推荐: 不动依赖布局, 镜像照装 pystray / customtkinter / Pillow (仅托盘模式加载, 容器内永远不触发)。备选: 把三件挪进 PEP 735 依赖组或 extras, 容器不装。

备选的瘦身收益预估十几 MB 级 (P1 实测回填), 代价是动 pyproject + uv.lock + env.sync 口径 + 托盘安装说明, 还可能碰依赖锁定纪律。不值得在首期付, 列入 P4 可选。

D3 · 配置与数据面

可写的 config 目录 + named data 卷

推荐: bind mount 一个 config 目录 (放 config.yml, 可写 —— Web UI 保存与 .bak 备份都要写回) + named volume 挂 /data 作 data_dir。容器示例配置以 minimal.yml 为底, 改两处: data_dir: /data 与 web.host: 0.0.0.0。

两个必须写进部署文档的坑: ① web.host 默认 127.0.0.1 在容器里等于自断访问, 示例配置必须改 0.0.0.0, 并保留 README 的安全提示 (token 必填 / 反代 / 防火墙); ② logging.file 留空的语义是「落到默认文件路径」, 不是「关闭文件日志」。

D4 · 到 qB 的网络路径

按 qB 的实际位置分三案, 不用 host 网络模式

  • qB 在宿主机 (用户当前场景, Docker Desktop): qbittorrent.host: host.docker.internal, 开箱即用; Linux 宿主由 compose 补 extra_hosts: host.docker.internal:host-gateway。
  • qB 也进同一 compose: 直接填服务名, 走 compose 内部网络。
  • qB 在 NAS / 远程: 直接填 IP, 与容器化无关。

network_mode: host 虽然省事, 但会把 web.port 与 qB WebUI 的默认 8080 冲突暴露出来, 且失去端口映射的显式性 —— 不采用。

D5 · 优雅退出

P3 补 SIGTERM 处理 (全方案唯一代码改动)

推荐: 在入口注册 SIGTERM handler, 转入与 KeyboardInterrupt 相同的优雅关闭路径 (落盘 → 停 uvicorn → 退出码 0); compose 侧配 stop_grace_period。不做的话: docker stop 直接杀进程, 尾部最多 120s (默认周期) 的运行态丢失, 且 restart 场景每次都吃这个损失。

改动集中、风险低, 收益直接兑现黄金法则 3 (状态持久化) 的容器场景; 具体实现与测试策略见 P3。

D6 · 健康检查

用 python 内联探活, 探 web.port

slim 镜像没有 curl / wget, healthcheck 用一行 python (urllib.request.urlopen) 探 Web UI 端口。容器示例配置里 web.enabled 恒为 true, 避免健康检查探测一个不存在的端口; 具体探活路径 (根路径 307 → 默认 UI) 在 P2 实测定型。

D7 · 时区

ENV TZ + tzdata, 默认 Asia/Shanghai

slim 基础镜像需显式装 tzdata; TZ 经 compose environment 可覆盖。HR 窗口、每日曲线、日志时间戳都随宿主钟, 避免默认 UTC 的整体平移。实施时核对 state 里时间戳的语义 (epoch 与本地串的混用点), 确保换 TZ 不产生双写歧义。

compose.yaml · 样例 (实施时以实测为准)
services:
  auto-qb:
    build: .
    container_name: auto-qb
    restart: unless-stopped
    stop_grace_period: 30s          # P3 落地前此值无效果 (SIGTERM 即杀)
    environment:
      TZ: Asia/Shanghai
    ports:
      - "8081:8080"                 # 宿主 8081 → 容器 web.port (避开宿主 qB 的 8080)
    volumes:
      - ./config:/config            # config.yml 所在; 必须可写 (Web UI 保存 + .bak)
      - auto-qb-data:/data          # data_dir: 状态/锁/日志/token
    # qB 在 Linux 宿主机时需要; Docker Desktop 免:
    extra_hosts:
      - "host.docker.internal:host-gateway"
    healthcheck:                    # 探活实现 P2 实测定型
      test: ["CMD", "python", "-c", "import urllib.request as u; u.urlopen('http://127.0.0.1:8080/', timeout=3)"]
      interval: 30s
      timeout: 5s
      retries: 3
    command: ["/config/config.yml"]

volumes:
  auto-qb-data:
Dockerfile · 样例 (要点示意, 实施时以实测为准)
FROM ghcr.io/astral-sh/uv:python3.12-bookworm-slim AS builder
WORKDIR /app
COPY pyproject.toml uv.lock ./
COPY src ./src
RUN uv sync --frozen --no-dev --no-editable

FROM python:3.12-slim
RUN apt-get update \
    && apt-get install -y --no-install-recommends tzdata \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH" \
    TZ=Asia/Shanghai
ENTRYPOINT ["auto-qb"]
CMD ["/config/config.yml"]

注: --no-editable 让项目以普通 wheel 形态装入 venv (镜像内代码与 venv 不脱节); uv.lock 在 builder 层单独 COPY 以利用层缓存 —— 依赖不变时, 改源码不触发重装。 GUI 三件随锁文件装入 (D2), 不额外装任何 X / GTK 系统库 —— 它们只在托盘分支被 import。

05

分阶段实施

P1 + P2 属纯新增文件, 预估一次会话可完成; P3 是代码改动, 单独成段以便独立验证与回退; P4 全部可延后。

P1 · 镜像化

  • 产出 Dockerfile + .dockerignore, 本地 docker build。
  • 验收: 构建成功; docker run --rm <img> auto-qb --help 输出正常; 用假 qB 地址的配置启动 → 走 fail-fast 路径, stderr 报「无法连接」, 退出码 1, 无堆栈。
  • 实测记录: 镜像体积、构建耗时、GUI 三件实际占用。

P2 · 编排与文档

  • 产出 compose.yaml + docker/config.example.yml + docs/deployment.md; healthcheck 探活路径实测定型。
  • 验收: docker compose up -d 后浏览器可登录 Web UI (token 从 /data/web.token 取); docker logs 有 INFO 日志流; 在 Web UI 改一处配置 → config.yml 写回 + .bak 出现; stop / start 后状态续接 (规则历史不重置); 手动起第二个容器实例 → 被单实例锁拒绝, 提示干净。

P3 · 优雅退出 (唯一代码改动)

  • 入口注册 SIGTERM handler → 复用 KeyboardInterrupt 优雅关闭路径 (save_state → WebServerHandle.stop → 退出码 0)。改动面预估仅 cli.py / 主循环退出路径一处, 不碰任务队列结构 (单一写线程红线)。
  • 测试: 平台相关断言按守则 monkeypatch 固定 sys.platform; 容器内以真实 docker stop 实测兜底。
  • 验收: docker stop 后日志出现 Shutting down..., state.json mtime 更新, 容器退出码 0; 既有全量测试无回归。

P4 · 可选延后

  • CI 增加 docker build job (只 build 冒烟, 不推送)。
  • GHCR 镜像发布与版本 tag 策略 (与 deps-version-management 的版本管理对齐)。
  • GUI 依赖分组瘦身 (D2 备选)。
  • 非 root 运行 (PUID/PGID 或固定 uid) —— 现阶段容器内写面只有 config 与 data 两卷, root 可接受。
