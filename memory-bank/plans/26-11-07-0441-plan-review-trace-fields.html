§01目标与设计原则

背景。评审闸门 2026-11-06 落地, 2026-11-07 跑完第一笔真实大批次(630a9b9f, 1229 行 / 17 文件 / 2 次派发 / 15 条发现)。复盘发现: 闸门能证明「你报的数对得上」, 不能证明「你真的评了、真的校验了引文」。三个缺口都在同一处 —— 留痕面只记了结果数字, 没记过程事实。

目标(做到什么算成)。

  1. 超限的补救从「写一个词」变成「报一个数」: 批 > 400 行时, 闸门要求派发次数 ≥ 2; 既有 · 分面 保留为等价声明(Q2 待拍), 但不再是唯一通路。拆批仍是首要判据 —— 拆得动的批次每笔都 ≤ 400, 走不到这一步, 所以闸门见到的 400+ 就是「确实不可拆」的残余;
  2. 引文校验进闸门: review.check 从独立 task 变成必跑动作, 其结果以 · 检 P/T 进 trailer, 并与「修 + 入池」做下界一致校验;
  3. 评审自身的产物不再触发评审义务: 消掉实测中 13 笔同句 Review-Skip。

设计底线(不变量)。

  • 锚点法(「最近一条 trailer → 工作树」)、FLOOR=50、Review-Skip 豁免、· 齐平 弱字段 —— 全部不动;
  • 不新增提交后补评时点(26-11-07-0201 的既有决定), 评审仍固定在提交之前;
  • 只加字段与判据, 不追溯历史提交: 闸门只看当前批, 老 trailer 的合法性按「缺省值」兼容, 不回头判红;
  • 新流程的 findings 不入 git: 评审产物不进版本库, 避免制造新的待评面(这正是 P3 的成因); 已入库的 R4 路线产物按 D3 归记账, 不追溯搬迁;
  • 判断与机械分离: 「派几次 / 修几条」是 agent 声明, 「行数 / 下界一致 / 正则形状」是脚本机械。

§02现状与痛点

现状机制(证据)

  • 判据单点 check_review_trace.py:46-54: FLOOR=50 · CEILING=400 · 三个计数正则(blocker/修/入池), 没有派发次数, 没有校验结果;
  • > 400 行的唯一出路是 trailer 里出现「分面」二字 —— check_review_trace.py:240 的 if count > CEILING and "分面" not in line, 不验派发次数、不验是否真拆;
  • Review: 语法(SKILL.md:118)字段集 = 范围 / N 行 / blocker / 修 / 入池 / 分面 / 齐平 —— 没有任何字段承载「引文校验跑没跑」;
  • review.check 是独立 task(.commands/review/config.toml), 闸门不引用它, 也不留痕;
  • 记账类前缀只有三个(check_review_trace.py:58): tasks/ · activeContext/ · testing/baselines/。

痛点(全部来自 2026-11-07 那笔真实批次)

#痛点实测证据后果
P1词闸: > 400 行只验「分面」二字本批 1165 行 > 400, 闸门拦一次(107.5s); 补上「分面」后即过。而 SKILL.md:139 反模式恰好写着「超 400 行用分面代替拆批」是反模式闸门实际在鼓励它自己文档里的反模式; 400 行这条规则没有行为后果, 只产生文书
P2裸采信: 引文校验可跳过且无痕迹本批 15 条发现没跑 review.check就采信(findings 只在对话里, 未落盘); 闸门绿灯「只写 trailer 不真评」与「真评了但引文是幻觉」在闸门眼里完全一样; SKILL.md:138 的禁令无机械面
P3分类错位: 评审产物被算进待评面截至 4da13dd2 的近 30 笔里有 16 笔 Review-Skip, 其中 13 笔是同一句「纯盘点数据落盘, 零代码改动」(复现: git log --format=%B -30 | grep "^Review-Skip:" | sort | uniq -c); 这类提交 100% 落在 reports/attachments/legacy-review4/(目录内 11 json + 5 md)每写一份 findings 就要手写一遍豁免; 固定措辞让 Skip 退化成仪式, 也稀释了真正需要解释的 Skip
P4报数摩擦: 失败行不给整行, 且 N 会漂失败行只给「本批实算 1165 行」, N 要自己再捞。更要紧的一处: 无消息文件跑 review.trace 会退回按 HEAD 的 trailer 判 —— 上一笔是 Skip 时直接报 ok(本次实测把 233 行待评静默放行), 真实行数只能靠故意写错一次才捞到; 实算含事实性文档, 收尾回写后同一批从 1137/1811 漂到 1138/1812每次提交多一次试错(本批 1 次, 107.5s); 数字漂移逼你重算, 容易写错而被二次拦
为什么这条缺口值得修。实验(10 派发 / 56 发现)的三条结论要分开读: ① 发现数 ≈ 派发次数 × 5.6, 与批次大小无关; ② 「2 批召回 7/8, 1 批 0/8」比的是同一 diff 的切分粒度(报告 §02: 只改切分粒度), 不是同一大块派两次; ③ 幻觉率不随批次变大而上升。所以超限的首要补救仍是拆批(②直接支持它), 而「单块多派」能否换来同等召回没有实测 —— 只有 ① 支持「多派必多得」, 因此它只对「确实不可拆」的残余可接受。闸门在提交时点管不到拆批(代码已写完), 能核的只有「有没有至少多派一次」, 这就是 D1 只设派发下限的原因, 不是把多派当成拆批的等价物。

§03方案总览

四个落点 + 一组不变量, 决策编号对应 §06。

落点 1 —— · 派发 <K> 字段取代「分面」判据 (D1)

  • 语法: Review: … · 派发 <K>, 缺省 1。历史格式的 · 分面 视为 派发 ≥ 2 的等价声明 —— 老 trailer 继续合法, 不追溯。
  • 判据: count > CEILING 时要求 派发 ≥ 2(或带 分面); ≤ 400 时不校验派发。拆批仍是 skill ② 的首要判据: 拆得动的批次每笔都 ≤ 400, 走不到这条; 走到它的都是「确实不可拆」, 此时闸门能核的最小事实是「至少多派了一次」。
  • 为什么是数: 派发次数可用 git log --format=%B | grep -o "派发 [0-9]*" | sort | uniq -c 统计, 能与行数/发现数对账; 词没有这个性质。

落点 2 —— · 检 <P>/<T> 把引文校验钉进 trailer (D2)

  • 语义: T = 送检的发现数, P = 引文逐字通过数(review.check 判过的条目);
  • 校验: 字段必须存在; 0 ≤ P ≤ T; 且 P ≥ 修 + 入池 —— 约束 P 而不是 T, 否则 检 0/15 · 修 15 会合法通过。口径随之收紧: 修/入池 只数过检的发现(自发顺手修、被 REFUTE 弃掉的条目都不进这两个数);
  • 效果: 写 修 15 就必须有 P ≥ 15(真过检 15 条), 凭空编不出下界 —— 这是「只写 trailer 不真评」能加的最便宜的一道坎。

落点 3 —— 记账类前缀扩容 (D3)

  • 只加 memory-bank/reports/attachments/legacy-review4/ 一层(check_review_trace.py:58), 不做父目录通配;
  • reports/attachments/ 其余件(26-10-31-fx-research-notes.md 这类)仍是事实性文档, 照旧计行;
  • 依据: 该目录整体是 R4 存量评审的 findings / manifest / 路线小结, 是被评代码的产物, 不是被评代码。

落点 4 —— 失败行直接给整行骨架 (D4)

  • decide() 的三类失败行(超限无派发 / 缺字段 / 行数不符)尾附可粘贴骨架: Review: <范围> · <实算> 行 · blocker ? · 修 ? · 入池 ? · 检 ?/? · 派发 ?, 行数位直接用实算值;
  • 骨架里的 ? 不是数字 ⇒ 直接粘贴会被拒(检/修/入池 走原正则, 派发 也补 \d+ 形状校验, 否则 ≤400 批里未被判据覆盖的 派发 ? 会静默通过) —— 失败方向安全;
  • 无消息文件时不再假装通过: review.trace 缺消息文件时按 HEAD 的 trailer 判, 上一笔是 Review-Skip 就报 ok(本次实测把 233 行待评静默放行)。改为照算实算行数并打一行提示(「未给消息文件, 按 HEAD 判, 实算 N 行」)—— 预览与闸门不一致本身就是 P4 的一半;
不做。① 不把 · 齐平 <hex> 升级为强校验(既有决定: 弱字段, 不因齐平判红); ② 不给 派发 设上界; ③ 不做「提交后自动复评」; ④ 不把 findings 存进 git。

自举顺序(这条不写清会卡住落地)

批 A 改的是闸门自己。改完后, 批 A 的提交就按新判据受检 ⇒ 它的 trailer 必须已带 检 P/T, 而 P/T 只能来自该批的 review.check。顺序固定为: 改脚本 → 补测试 → 派评审批 A → 修复 → 跑 review.check 拿 P/T → 写 trailer(检 P/T · 派发 K) → ship.commit。批 B 同理; 批 C 是纯文档, 仍须带 检。

首个实战样本: 本计划落地后的下一笔真实功能提交即验收样本 —— 若它 > 400 行, 看闸门是否在「没报派发」时真的拦下; 若 ≤ 400 行, 看 检 缺失是否被拦。用 git log 出一行统计留档。

§05待拍板清单

  1. Q1 T ≥ 修 + 入池 这道下界收不收。收(推荐) ⇒ 代价是 修 的口径收紧为「过检的发现」, 自发顺手修不再计入; 好处是不加字段也堵住了 P2。备选: 只要求 检 存在、不做下界 —— 更宽松, 但等于没堵住「凭空写 修 15」。
  2. Q2 超限判据是否保留「分面」作为等价声明。保留(推荐) ⇒ 历史 trailer 与 skill ④ 的分面档都不用改写; 代价是同一意思两种写法。备选: 只认 派发, 分面 判红 —— 干净, 但要让 26-11-06-0759 以来的既有写法全部失效。
  3. Q3 记账类扩容的范围。只加 legacy-review4/(推荐) ⇒ 最小面、可验证。备选: 整个 reports/attachments/ 归为记账 —— 覆盖未来所有附件, 但会漏掉真实的事实性附件文档。

§07风险与对策

风险触发条件处置
自报数字仍不可验永远成立: 派发/检 都是 agent 写的只做下界一致与形状校验, 不假装能验真; skill ⑦ 顶部一句话写明「这是记账闸门, 不是质量闸门」
水派发为过闸门派两次, 第二次敷衍P ≥ 修+入池 只挡得住「派了但一条没交」的极端; 「派发多而修少」与「这批本来就干净」机械上不可区分, 所以只做事后人工看比例: git log --format=%B | grep -o "派发 [0-9]*" | sort | uniq -c, 对高派发低发现的批次抽看 findings 是否落在不同面。不假装能自动检。
兼容性老 trailer 无 检 字段落地后第一笔提交起生效(闸门只看当前批, 不追溯历史); skill ⑦ 标注生效日
骨架被直接粘贴忘记替换 ?? 不匹配数字正则 ⇒ 判红, 失败方向安全
自举卡死批 A 改完后自己的提交过不了新判据§04「自举顺序」固定六步; 真卡住时逃生 = 该笔用 Review-Skip 并在下笔补评(可见、可审计, 不进静默区)
