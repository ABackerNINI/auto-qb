分批评审: 从「收口一次评」到「一批一评 + 强制留痕」

把 code review 的评审单元从「任务」改成「批」, 并用提交闸门强制留痕。起因是实测发现一半会话根本没触发评审; 设计依据是一场对照实验(10 次派发 / 56 条发现), 它把「400 行」从容量红线改判为产出密度的经济学选择。本计划为补记——拍板发生在 grilling 的四轮对话里, 实现先于本文成文。

§01目标与背景

用户的原始问题: 「code review 环节在一半会话中没有被正确触发」。查下来不是 agent 疏忽, 是结构性逃逸:

  • 豁免判据是「立档阈值 4 条不命中」——四条全是判断题(≥5 轮 / ≥3 源文件 / ≥2 会话 / 有计划文档)。
  • 再叠加「中途提交不触发」。于是只要 agent 从不宣布「收口」, 就可以连续几天、每次改一两个文件, 全程不立档、不评审。
  • 实测: skill 2026-11-04 落地后新建 20 份档案, 8 份零提及评审(其中 4 份已 Done); 62 份切片 95 条 R 行, 只有 23 条含评审。

第二个问题在 grilling 中被挖出来: 「全部做完再评一次」对大计划结构性失效。实测 mpy 计划收口 1495 行、假钟计划收口 3357 行, 分别是 400 行容量线的 3.7 倍与 8.4 倍; 而现有「分面 2–3 子代理」只按面切, 切完每面仍约 1100 行。

§02方案的三个支点

支点一: 评审单元是「批」, 不是「任务」

批次范围 = 最近一条带 Review:(或 Review-Skip:)的提交 → 当前工作树。锚点从 git 历史现算, agent 不用填 hash。这条规则同时解决两件事: 触发不再依赖 agent 自我判定「是不是收口」; 漏评的提交会自动滚进下一批(连坐), 于是「不留免评节点」不是口号而是机制。

支点二: 触发按「累计改动面」, 不按任务类型

累计 ≥50 行(代码 + 事实性文档), 或触碰安全敏感面/红线(不论行数) → 必须评。有没有档案、是不是「小修」都不再影响判断 —— 档案是记账需要, 评审是风险需要, 两件事被绑在一起正是逃逸的根。

支点三: 提交信息 trailer 是唯一闸门键

Review: <范围> · <N> 行 · blocker <N> · 修 <N> · 入池 <N>[ · 分面]

闸门校验三件: 声明行数 == 实算(±0)、三个计数齐、超 400 行必须带 · 分面(否则应先拆批)。选提交信息而不是档案 R 行, 是因为它随提交走、跨 clone 一致、git log --grep 可统计; 档案 R 行继续写叙事, 但不当闸门键(两处必然漂移)。

§03实验结论(设计依据)

为回答「agent 一次能评多少行」, 做了对照实验: 同一份 diff 按 4 批 / 2 批 / 1 批三种粒度各评一遍, 共 10 次派发、56 条发现。三条结论(详见 报告):

  • 发现数 ≈ 派发次数 × 5.6, 与批次大小无关(26/4=6.5、8/2=4.0、5/1=5.0、12/2=6.0、5/1=5.0)。
  • 幻觉率不随批次变大而上升: 56 条全部通过引文校验, 0 条被弃, 含 1313 行单块。这条推翻了事前假设。
  • 大块不是少找几条, 是换了地方找: 有真值的 diff 上, 2 批召回已知修正点 7/8, 1 批召回 0/8。

方法论修正: 原 TIER_LIMIT = 400 注明来源是 SmartBear/Cisco 的人类注意力研究(200–400 行 / 60–90 分钟)。agent 没有这个生理约束, 把人类数字当默认值是错的。400 行保留, 但理由换成「产出密度与切分合理性的折中」。

§06未做与已知边界

  • 50 行下限未实测: 实验只覆盖 328–1313 行, 低于 50 行「不值得单独派发」仍是推断。
  • 跨块问题未测: 实验没有构造「只有看全才能发现」的缺陷, 因此「切太细会丢跨块问题」来自推理; 接缝终审(D2)是它的对冲。
