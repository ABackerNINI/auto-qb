HR 在线核实热重载后, WebUI 停留「本地·达标」

现象: 热重载开启站点 HR 在线核实后, WEB UI 一直显示「本地·达标」; 重启进程后才显示「在线·已达标」。本文给出完整判定链路取证、两层根因与分步修复计划。

结论 TL;DR

两层缺陷叠加。主因: 热重载只替换 manager.config 对象, 存量种子的 TorrentRecord.tracker_conf 仍指向旧配置的 TrackerConfig——它的 hr_check 派生视图是 None, 而重绑的两条既有路径(L2 重建判据 / full_round 补绑)都不覆盖 hr_check 类变更, 判定入口 hr_judgement() 因此永远返回 None(「站点未接入」语义), WebUI 走本地兜底显示「本地·达标」。辅因: 取数线程随后抓到数据、发布了新判定视图(revision 自增), 但 HR 判定结果不是 store 快照字段, 不会触发 WebUI 视图重建——界面挂在旧值, 只能等重启。

01

现象还原: 逐时刻链路

按用户实测时间线还原, 红点为断链时刻, 绿点为工作正常的环节。

t0 · 程序启动, 站点未接入 HR
存量种子在首次同步时绑定 TrackerConfig(其 hr_check=None); HR 运行时因无启用站点不启动。
t1 · 用户改配置热重载「开启站点 HR 在线核实」
apply_new_config 先换 manager.config(loaders 已派生填充新 trackers.X.hr_check), 再广播全部模块 apply —— 时序正确。
t1+ · 取数侧正常重建
HrRuntime.apply 现读新配置的站点表, 重建取数线程并补启端点; 随后开始轮询取数(60s 节拍), 抓到数据后写盘并发布视图。
t1+ · 判定输入陈旧 —— 根因 1
存量 rec.tracker_conf 不重绑: L2 重建判据只比较绑定三元组(domains/rules/groups), hr_check 变化不触发; full_round 只补 tracker_conf is None 的记录。hr_judgement() 读旧对象上的 hr_check=None → 返回 None → 「本地·达标」。
t1+ · WebUI 视图重建了一次
热重载时 WebUIModule.apply 有全量置脏, 视图确实重建了——但重建时判定输入还是旧对象, 重建出的就是「本地·达标」。
t2 · 取数完成, 视图已发布 —— 根因 2
判定结果变化不触发视图重建: HrViewPublisher.revision 自增没有任何消费方置脏 WebUI, 界面快照停留在 t1 时刻的内容。此刻判定输入明明已能算出「在线·XX」, 界面却看不到。
t3 · 用户重启进程
store 从零构建, 全量按新配置匹配 → tracker_conf.hr_check 就位; worker 冷启动先发布盘上既有视图(不留判定真空); WebUI 视图初始即脏。三者同时满足 → 显示「在线·已达标」。
02

根因 1(主因): 存量记录的 tracker_conf 不随热重载重绑

2.1 重绑只有两条路径, 都不覆盖 hr_check 变更

存量 TorrentRecord.tracker_conf 指向旧 Config 的 TrackerConfig 对象。配置对象按值比较(TrackerConfig 是 dataclass), 但重绑依赖以下两条链, hr_check 派生视图的从无到有在两条链上都不成立:

路径 A · L2 结构重建(不触发)

判据单点 RulesModule._rebuild_needed → _tracker_bindings_changed: 逐站点只比较 (domains, rules, groups) 三元组。rules_mod.py:124-134

开启 HR 核实只改 hr_check 派生字段, 三元组不变 → 返回 False → store.reset_runtime()(会把全部 tracker_conf 置空)不执行。store.py:438-439

路径 B · full_round 补绑(够不着)

TrackerModule._on_full_round 只对 tracker_conf is None 的记录重匹配; 存量记录绑定非 None, 永不重绑。模块 docstring 也明说「apply 无热重载动作」。tracker_mod.py:43-48, 10-11

2.2 判定入口读到旧对象, 恒走本地兜底

TorrentRecord.hr_judgement() 读的是 self.tracker_conf.hr_check: 旧对象上为 None → 命中「站点未接入」短路, 返回 None。record.py:356-358 随后 safety_display(None, satisfied=True) 落本地兜底分支 → 「本地·达标」。resolve.py:332-334 WebUI 组装层(hr_view_fields)是现算的, 没有字段缓存——它算得再勤, 输入也是旧对象。views.py:301-305

2.3 影响面不止显示

  • 取数侧对账管线同样瘫痪: HrRuntime._anchors() 也读 rec.tracker_conf.hr_check, 旧对象上为 None → 本地锚点收集为空 → 取数波次的覆盖对象集为空 → 本地种子不进对账(命中定论 / 「未列出」放行签发都不发生)。hr/runtime.py:374-377
  • hr 规则段同病: hr(required_seeding_time / condition / exclude_tags)同样挂在 TrackerConfig 上、同样不在绑定三元组内——热重载改要求做种时长也不会被存量记录感知, 只是用户尚未撞见。本修复一并覆盖。
03

根因 2(辅因): HR 判定变化不触发 WebUI 视图重建

WebUI 分组视图是惰性重建的快照, 重建判据只有两个来源: store.consume_view_changed()(种子快照字段变化)与显式 web.mark_dirty()。webui/runtime.py:337-352

HR 判定结果不属于任何快照字段: 取数线程发布新视图(HrViewPublisher.revision 自增)时, 没有任何代码路径把它翻译成一次置脏。库里已有同构先例——「错误原因」预取注释明说「原因不是快照字段, store.view_changed 覆盖不到它, 故变化时显式置 web.group_view_dirty」, 并在变化时调 mark_dirty(); HR 判定缺的正是这同一个机关。views.py:207-234

该缺陷独立于热重载存在: 运行期任何一次取数刷新改变了判定(考察中转 B 档、签发放行…), WebUI 都要等到别的原因碰巧置脏才能看到。热重载场景只是让它最先被撞见。

05

修复计划(四步)

方案取向: 让「绑定结果」在热重载时收敛到当前配置(修根因 1), 再给 HR 判定新鲜度补上置脏机关(修根因 2)。不改判定语义、不改 L2 重建判据、不动取数链路。

Step 1 · 修根因 1

TrackerModule 新增 apply: trackers 段变化时立即重绑存量记录

  • 落点: src/auto_qb/core/modules/tracker_mod.py(新增 apply(old, new) 方法; 该模块认领 trackers 段, match 知识本就在此, 现在只有恒短路的默认实现)。
  • 逻辑: old.trackers != new.trackers(整段按值比较)时, 遍历 store.by_hash 中 tracker_conf is not None 的记录执行 rec.tracker_conf = self.match(rec); 返回 ApplyResult(self.name, f"rebound {n}") 供热重载回执可见。相等即短路, 无关保存零动作。
  • 成本依据: tracker_urls() 走 trackers_info 惰性缓存, 存量记录已被全量轮拉过, 重绑是纯内存 O(N) 操作, 零 qB API 调用 record.py:254-264。
  • 防御: ctx.api.client is None(qB 断开)时跳过重绑并照常返回(留给下轮 full_round / L2 兑现), 不得在 apply 里抛异常打断热重载广播。
  • 幂等收敛: 若绑定三元组同时也变, RulesModule.rebuild_runtime 的置空 + full_round 重匹配与本重绑收敛到同一结果, 先后顺序无影响。
  • 顺带修复: hr 规则段热重载生效; HrRuntime._anchors() 的锚点收集恢复(对账管线随通)。
Step 2 · 修根因 2

WebUI 增加 HR 判定新鲜度置脏: hr.revision 变化 → mark_dirty

  • 落点: src/auto_qb/webui/runtime.py(WebUIRuntime)+ 视图宿主的取数口; 仿「错误原因」先例的形态 views.py:207-234。
  • 逻辑: rebuild_views() 重建完成时记录基线 self._hr_rev_at_build = hr.revision(hr 门面经 manager 现取, 判空防御); flush_views()(或 on_task_line 预取同段)先对比当前 hr.revision 与基线, 不等即 mark_dirty()——下一轮重建后基线自然前移, 无循环置脏。
  • 效果: 热接入后的首次取数成功 / 周期刷新 / 「立即拉取」按钮, 判定一变 UI 下一拍即刷新, 与重启后的观感一致。
  • 线程口径: 全部发生在主循环两条线上, 与 web.group_view_dirty 的既有跨线程语义一致 views.py:807-811。

单测补两个回归面, 同步测试计划清单

  • test_tracker.py: 新增用例——存量记录持旧 TrackerConfig(hr_check=None)→ 构造新旧 Config 调 TrackerModule.apply → 断言 rec.tracker_conf.hr_check 就位、回执含 rebound; 补 client=None 防御用例; 补「trackers 段相等即短路」用例。

  • 守阵确认: test_modules_p6.py 段认领不受影响(trackers 已被认领, 无新增顶层段); 检查既有热重载回执断言是否精确枚举 actions, 新增 tracker:rebound N 后同步修正 test_core_modules.py。
  • 两个测试文件头部 docstring 的「测试计划」清单按 AGENTS.md 口径同步补条目。

按用户原始场景走一遍, 再按收尾 DoD 归档

06

方案取舍(为什么不走另两条路)

备选做法不取的原因
扩大 L2 重建判据把 hr_check / hr 纳入 _tracker_bindings_changed 的比较, 让它触发全量重建会把「开一个 HR 核实」放大成重建任务队列 + qB 重连的全量重建, 代价与语义都不成比例; L2 判据是「结构语义」单点, 塞进展示/配置值比较会污染它的职责
判定端现读hr_judgement() 不读 self.tracker_conf.hr_check, 改按站点名现读 link.config.trackers[name].hr_check只修 HR 判定一个入口, 修不到 hr 规则段与 _anchors() 锚点收集(同一缺陷的另外两个面), 修完仍有三处各说各话

选定方案(立即重绑)的本质: TrackerConfig 上凡「派生/配置值」类字段的变化, 都让绑定结果一步收敛到当前配置——一处修复覆盖判定入口、规则段、锚点收集三个消费面, 且不触碰 L2 结构语义。

07

风险与兼容

  • 重绑改变 rec.tracker_conf 引用: 其余消费方(tags/分组/限速/规则)按字段读值, 除 hr/hr_check 外新旧对象字段值一致, 无行为变化; 三元组真变时 L2 重建路径保持原样。
  • 重绑耗时: 主循环线程 apply 阶段同步执行, O(N) 纯内存; 万级种子也在毫秒量级(无 API 往返)。
  • 置脏频率: hr.revision 只在取数实质变化时自增(publish 内容指纹去重), 不会周期性空转重建视图 hr/worker.py:79-98, 125-132。
  • 零静默变更闸门: 未接入 HR 的站点判定路径一字不变——重绑后 hr_check 仍为 None 的站点照旧走本地兜底。
