04

每批统一动作序列与基线不变式

统一动作序列(每批八步)

  1. 开工同步: commands run my-commit-flow.sync, 记录当批 HEAD。
  2. 读档: 逐条读批内 issue 全文(七字段) + 批表列出的坑档对照。
  3. 锚点复核: 按「文件 + 函数名 + 行号」三锚在当下 HEAD 复核, 行号漂移以函数名定位。
  4. 修复 + 守阵: 按批表修法实施; 每条配守阵测试(新增测试同步该测试文件头部 docstring 的「测试计划」清单; 新守阵登记 memory-bank/conventions/testing/guards.md)。
  5. 格式化: commands run dev.fmt -- <改过的 .py>; 改 JS 后跑 node --check(守阵 test_frontend_static_bundle_health 同源)。
  6. 批内迭代: commands run test.quick; 收尾 commands run test.full 基线对照(判据见下)。
  7. 回写: 修毕 issue doc-status → Done(带实测数字与提交指引); 涉及文档口径的条目同步回写(rule-system / contract-api 坑档 / keys.md 等); commands run kb.index 重建。
  8. 提交: 消息写 .git/COMMIT_MSG_AI.txt → commands run ship.commit(gitmoji + 中文, 数字用当批实测); 会话收尾按 memory-bank skill 五步 DoD 更新 activeContext。

基线不变式(S0 立基线, 每批收尾对照)

  • S0: 开工 sync 后跑一次 commands run test.full, 新建基线切片落 memory-bank/testing/baselines/(体例见 testing/baseline.md 口径段), 记实测 passed / skipped / 覆盖率 / 语句分支总数, 作为 S1–S6 的对照点。
  • 判据: 每批收尾 passed ≥ S0 基线 + 本批新增用例数; skipped 持平; 覆盖率维持 99% 档; 语句/分支总数按改动自然增长(改动即变, 看的是无改动域不缩)。
  • 抖动判读: 首跑若出现 ±2 级未覆盖 / ±1 partial 的小幅波动, 同 HEAD 复跑一次再判漂移(评审批 A/F1/F2 已实证该抖动形态), passed/skipped 数则必须严格持平或 +新增数。
