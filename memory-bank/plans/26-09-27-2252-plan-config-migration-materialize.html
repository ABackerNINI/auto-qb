config schema 迁移物化重构: 加载即迁移 + 版本号备份 + 立即落盘

现行口径是延迟物化——加载时迁移只在内存生效, 磁盘等下一次 WebUI 保存才改写。它与另外两个缺陷(写回侧校验/落盘数据分裂、启动期迁移日志被吞)在 2026-09-27 生产事故里合流: 保存把未迁移的 v1 树带上 v2 章直接落盘, 坏文件让 reload 与重启双双报废, 且日志全程看不到一次可信的迁移记录。本章按用户裁决重构: 加载即迁移(保留)、迁移前做带版本号的备份、迁移完成立即落盘、延迟语义全部退场。

02

目标口径(硬需求)

  • R1 加载即迁移: load_config 校验前沿链迁到当前版本 —— 现状保留, 是一切的前提(只读模式、首次物化都靠它)。
  • R2 迁移前版本号备份: 磁盘文件被迁移改写前, 先把迁移前原样备份为带版本号的文件; 与每次保存都覆盖写的 config.yml.bak 不同名, 不被其他操作覆盖。
  • R3 迁移完成立即落盘: 版本落后的磁盘文件在启动路径上立即改写为当前版本(校验通过后), 不再等 WebUI 保存。
  • R4 延迟语义退场: 「内存生效, 下次 WebUI 保存时写回」的日志语义、docstring、文档表述全部移除; 写回路径不做迁移 —— 提交树版本落后由版本闸门直接拒绝(§06, D-C 用户裁决)。
03

设计: 物化单点与挂载点

3.1 物化单点(新增, 落 writer.py —— 配置 IO 的既有归属)

def materialize_schema_migration(config_path: str, backup_dir: str) -> str:
    """磁盘版本落后时: 迁移 -> 校验 -> 版本号备份 -> 原子落盘; 返回迁移描述(无迁移 = "")"""
    tree = read_tree(config_path)                    # 磁盘原文(BaseLoader 树, 保注释的 merge 源)
    desc  = migrate_config_schema(tree, config_path) # 沿链迁移 + 框架盖章(纯内存); 空 = 已是当前版本
    if not desc:
        return ""                                    # 常态路径: 零 IO 零开销, 幂等
    _validate_tree(tree)                             # 写什么校验什么: 迁移结果复核, 不过则抛错不碰磁盘
    backup_versioned(config_path, backup_dir, from_version)   # 迁移前原样 → <名>.v<m>.bak(§04)
    _dump_roundtrip(config_path, tree)               # ruamel round-trip + atomic_write(保注释, 与保存同通道)
    return desc

要点: 物化只认磁盘真实状态(自己 read_tree 重读, 不信任启动时的内存副本 —— 两读之间文件被手改也不至于写错); 校验不过(如旧键定位不到档案)就抛 ConfigError 中止启动, 磁盘一字不动; from_version 在迁移前先 detect_version 取得, 用于备份命名。

3.2 挂载点: run() 开头, 不进 __init__

物化的三个前提只有到 run() 才同时成立: 单实例锁已持有(__init__:253, 并发写免疫)、日志已就绪(__init__:189, 物化 INFO 可见)、dry_run 已知(run 参数)。且必须先于 WebUI 对外服务 —— 物化与保存请求不存在并发窗口。

def run(self, dry_run=False):
    if not dry_run:
        desc = materialize_schema_migration(self.config_path, self.config.data_dir)
        if desc:
            logging.getLogger(__name__).info(f"配置 schema 已迁移 {desc} 并落盘(迁移前备份: {bak})")
    elif detect_version("config", read_tree(...)["config"]) < CURRENT:   # dry-run 只提示不动手
        logging.getLogger(__name__).info("磁盘配置 schema 落后, dry-run 仅内存生效不落盘")

04

备份策略

  • 命名: <data_dir>/<配置文件名>.v<m>.bak, m = 迁移前版本 —— 例: auto-qb-data/config.yml.v1.bak。名字即「这个文件是 config.yml 在 v1 时刻的原样」。
  • 不与保存备份撞名: 每次保存覆盖写的 config.yml.bak 与版本号备份互不干扰 —— 迁移备份不会被其他操作覆盖(R2)。
  • 时机与内容: 校验通过后、落盘前, 字节级拷贝当前磁盘文件(迁移前原样)。
  • 重入: 同一版本再次迁移(如用户把 v1 备份恢复回去再启)会覆盖同名备份 —— 内容仍是「迁移前原样」, 语义无损。刻意不做「已存在则跳过」: 跳过会让陈旧备份冒充本次迁移前状态。
  • 数量: 每次版本推进至多一个新名字, 文件数 = 版本跃迁次数, 天然可控。

08

上线与生产恢复

  1. 前置: 用户生产 config.yml(D:\Projects\auto-qb)已被事故写坏(v2 章 + 旧键)。本重构不自动治它——启动校验即失败, 物化根本不会执行。必须先用 <data_dir>/config.yml.bak(事故保存前的自动备份, v1 形态)覆盖回 config.yml。
  2. 同步新代码后启动: load_config 内存迁移 → run() 物化: 生成 config.yml.v1.bak + 磁盘落成干净的 v2。
  3. 此后每次版本推进自动完成「带版本号备份 → 立即落盘」; WebUI 编辑器任何时刻看到的都是当前结构; 「保存时才发现迁移问题」的形态不复存在。
  4. DoD: 实施 → test.full 全绿 + 基线切片 → 文档回写 → kb.index → 待「提交」指令。
09

风险与回滚

  • 启动期写 config.yml: 三重保险 —— 校验先行(不过不写)、版本号备份(永远可回迁移前)、atomic_write(无半截文件)。最坏情况: 从 .v<m>.bak 恢复, 与今天从 .bak 恢复同级。
  • 与保存/其它实例并发: 物化在单实例锁内且先于 WebUI 服务启动; 保存走同一 writer 通道。
  • 行为面变化: dry-run/只读模式不落盘(口径表 §3.3); 测试面变化见 §07 注意点。
  • 回滚: 单 commit revert 即回到现状; 版本号备份文件留存无害。
