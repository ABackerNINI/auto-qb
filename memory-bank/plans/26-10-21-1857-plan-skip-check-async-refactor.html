1背景与目标

用户报告（2026-10-21 17:22 / 17:32）：在 qB 里对某种子做完强制校验后，到 WebUI 对同组种子批量跳检，回执是「批量跳检未完成: 11 个失败: 同组种子正在全量校验中…」（同一段文案重复 3 次）；另一次同组 3 个目标出现「成功 1、失败 2」，失败原因相同。单发跳检同样会命中。

追查确认这不是一个闸门写错，而是执行模型的问题：批量跳检在命令 drain 内同步串行跑完 N 个 hash（每个约 6s，几乎全是 sleep 轮询），整批期间同步线停摆、快照冻结；跳检收尾又把「命令后直查到的状态」写回快照。三个环节叠加，产生误挡、自毒化与不可诊断的回执。

本计划要达到的

  • 不占主循环：任何一步只做一次 QbApi 调用（毫秒级），不再有 5s 级 sleep 轮询；
  • 响应 <1s：完成语义只依赖「命令 ack + 存在性确认」，不等运行状态；
  • 真值单源：运行状态（state / progress）只由 apply_sync 写，跳检路径一个字不写；
  • 批量与目标数解耦：11 个目标 ≈ 250ms（现状 ≈ 66s），慢的不拖快的；
  • 可诊断：失败点名 blocker（hash8 + 名字 + state），回执按原因聚合。

非目标

  • 不改 ops.recheck 的提交 + 轮询结构（它本来就是「命令 + 快照观测」的正确形态）；
  • 不改 qB 的 RefreshInterval 等参数；不改分组算法、不改 HR / relocate。

3设计公理与边界

四条公理，后面所有设计都由它们推出，不再逐条论证：

  1. A1 真值单源：运行状态（state / progress）只由 apply_sync 写；命令后不查、不推、不写。
  2. A2 门面唯一：所有 qB 访问经 QbApi（业务代码不得直连 raw client）；QbApi 是 store 的唯一维护点。
  3. A3 不占主循环：不阻塞、不 sleep、不按 tick 摊开动作；每步只做一次毫秒级调用。
  4. A4 响应 <1s：完成语义不等运行状态。

边界：存在性 ≠ 运行状态

类别例子生效方式能否当场确认
存在性（会话级）delete 后是否还在会话、add 后是否出现qB 处理请求即改 m_torrents删除：可以（m_torrents.take 同步）；新增：可以短轮询（告警泵异步，ms 级）
运行状态（节拍级）progress / checkingUP / stoppedUPqB 每 refreshInterval（1500ms）批量刷新不可以，只能等上报
由此产生的一个必须接受的窗口

跳检完成后，qB 自己在第一个上报周期内报 pausedDL / 0%，第二个周期才报 pausedUP / 100%；再经我们的 sync 落账 → WebUI 行会有 1.5~3s 的「暂停 / 0%」。这是 qB 的真值，不是假账。服务端不做任何补偿；前端可显示「跳检完成，等待客户端刷新」的纯展示临时态（不落快照）。

4执行模型：主循环微步

写必须走 QbApi，而 QbApi 改 store ⇒ 写必须在主循环线程上。那就让每一步都小到可以接受：

  • 一步 = 至多 1 次写调用 + 1 次存在性读（都是 ms 级），做完立刻让出；
  • 步间间隔 10~20ms，由主循环的等待超时纳入调度，不 sleep、不空转、不等 tick；
  • 每轮预算：50ms 或 20 次调用，先到先止；超出的下一轮优先；
  • 批量：同一次唤醒里所有到期 job 各推一步。

内核改动（唯一一处）

# core/qbmanager.py:636 现为
wait_for = max(0.0, min(next_sync_at, next_tick_at) - time.time())
# 改为: 把"下一条 job 的下一步"并入等待超时
wait_for = max(0.0, min(next_sync_at, next_tick_at, self.skip.next_run_at()) - time.time())

命令线（run_command_line）每轮调用 skip.advance_due(budget_ms=50, budget_calls=20)；job 注册表与相位推进都在 SkipCheckModule 内，内核只认识「下一条到期时间」这一个数字。

时序（11 个目标）

轮 1   delete ×11                      主循环占用 ~50ms
轮 2   确认消失 ×11 + add ×11           ~100ms
轮 3   确认出现 ×11 + 打标/开始 ×11      ~100ms
→ 整批 ~250ms 完成(现状 66s 且全阻塞); 慢的只影响自己, 不拖住整批

5相位表（单 hash）

相位本轮动作进入下一相的条件上限 / 重试失败处置
ACCEPTED判闸门（只读快照，零 API）；写 .torrent 备份（本地 IO）闸门全过—拒绝 → REJECTED（零副作用）
DELETINGapi.torrents_delete(..., keep_record=True)调用返回成功3 次（10/20/50ms）FAILED（未删除，无损失）
GONEapi.torrents_info(hash) 为空返回空5 次（10~100ms）回 DELETING 重发一次，仍不空 → FAILED
ADDINGapi.torrents_add(skip_checking=True, stopped=True, …)返回 Ok.5 次（撞「已存在」即重试）FAILED（种子已移除，备份保留）
APPEAREDapi.torrents_info(hash) 非空非空5 次FAILED
FINISH打标 + auto_start + 写 skip_check_day + 清备份打标成功或失败均继续1 次打标失败仅 warning
两条不可退让的细节

① 删除不摘记录：torrents_delete(keep_record=True) 只发命令、不动 by_hash。理由：delete+add 若落在同一上报间隔内，qB 视角里种子从未离开，增量 diff 只会给变化字段；若我们本地摘了记录，apply_sync 会拿残缺 patch 新建记录（缺 name / save_path 等必填字段）。普通删除（非跳检）行为不变。

② 备份先于删除：沿用现有语义（备份写不进去就不删除），只是把备份从「同步链的中段」提前到 ACCEPTED 相位。

6批量：N 个 job 并行推进

受理（一次命令，逐 hash O(1) 判定）

keys(组) → 展开成员 ─┐
hashes(直接选中) ────┴→ 去重(保序) → 逐 hash 判闸门(同一份快照) → 建 job
→ 立即回执 { batch_id, items:[{hash, cls, reasons}] }
  • 判定同源：整批用同一份快照判，避免「先删的成员让后面成员的判定变样」；
  • 快照龄闸：快照龄 > 1 个 sync 周期 ⇒ 整批推迟到下一轮上报后再判（不半批判定、不半批执行）；
  • 幂等：同一 hash 在 keys 展开与直接选中里重复出现只留一个；已有在途 job 的 hash 直接返回 skip。

调度

轮 = 一次主循环迭代
取所有到期 job → 按"组"归并排序(同组连续) → 依次推进一步
直到预算用完(50ms 或 20 次调用, 先到先止) → 剩下的下一轮优先

组内同轮是优先级而非硬约束：文件不动，组内拆到两轮没有物理风险；只是判定已在受理时完成，拆开不影响正确性。

窗口抑制（批量才暴露的问题）

批量的删除→重加窗口只有 ms 级，但 N 个目标让「sync 恰好插进窗口」的概率变大。插进来时 qB 会报 torrents_removed，apply_sync 会摘记录、grouping 会走「种子已删除」链路（取消归组 / 缺文件扫描 / 删除事件）。

处理：批次在途的 hash 暴露为 store.skipping_hashes；apply_sync 收到这些 hash 的 removal 时只登记内部待结算，不进 last_removed、不触发 grouping 链路；job 终态时统一结算（成功 → 忽略这次 removal；失败 → 按真删除处理，摘记录）。

失败与重试（逐 hash 独立）

每个 hash 独立重试与终态；整批不回滚——已成功的保持，失败的点名，互不影响。某个 hash 的 delete 没落地，只它自己停在该相重试，其余照常推进。

8回执与进度契约

  • 受理即回执：{batch_id, items:[{hash, name, cls, reasons}]}，前端据此渲染三分流（可跳检 / 需强制 / 禁止）；
  • 执行中：每个 hash 终态一条 SSE 事件（成功 / 失败 + 原因 + blocker）；
  • 全部终态：一条汇总（成功 X / 失败 Y / 跳过 Z，失败逐条列原因，不再 [:3] 截断、不再重复同因文案）；
  • 前端：批量跳检不再用 60s waitCmd 等整批，改为「受理回执 + 事件驱动 toast」。

9崩溃恢复与幂等

  • job 账落 state["skip_check"]["jobs"]：{hash: {phase, backup, started_at, source, origin_rule}}，由主循环单点写（黄金法则 3 / 5）；终态即清；
  • 启动对账：非终态 job 在第一轮上报后核对——qB 里没有该 hash 且有备份 ⇒ 用备份重加一次（seed_mode + stopped）；重加失败或 qB 里仍有 ⇒ 标 FAILED 并通知；
  • 幂等：同 hash 已有在途 job ⇒ 拒绝重复受理；skip_check_day 仍在终态写（跨来源同日去重语义不变）。
