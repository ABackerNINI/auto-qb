HR 扩展缺站点权限的可见化与失败分类修正

把「扩展到底能不能访问这个站」从隐性前提变成显性状态：扩展预检并逐站展示授权态，后端按 kind 把权限/网络失败归进通道层，再让这个状态一路贯穿到分类、计数、站点卡与告警。

§01目标与设计原则

要做到什么算成

  1. 缺站点权限是可观测事实，不是反推结论。扩展侧逐站可见 + 抬头可见；auto-qb 侧站点卡片「通道」一行直接说「扩展未授权该站点」，并给动作（去选项页授权哪个域名）。不再靠「三档全失败 + Failed to fetch」倒推。
  2. 网络层/权限层失败不再冒充站点结论。「浏览器到不了这个站」与「这个站改版了」必须分家：前者归通道层（不计档位失败、不推连续失效、不带 [HR 页面改版] 前缀、文案给的是环境动作）。
  3. 判据不撒谎。zero_rows 只描述「全档有效且清单为空」；一页都没取到的波不许自称「结构完好」，更不许把用户引向 --hr-confirm-empty。

不变量（违反即破坏设计）

  • 零 cookie 边界：后端仍不直连站点、不持 cookie；取数只经扩展。host_permissions 保持只回环，站点继续走 optional_host_permissions，绝不 <all_urls>。
  • 通道层 / 页面层分家的判据不变：能不能靠重试解决。HrChannelTimeout 的 docstring（fetcher.py:32）已经写明这条，本次是把它贯彻到「网络层失败」这一类，不是新造分层。
  • v3 裁决不变：不引入退避/熔断/令牌桶（ratelimit.py:13 明写「被删除的旧概念」）。
  • 零迁移：新落盘字段走「缺键回默认」，不抬 hr_site 的 schema_version（照 history 的既有范式，model.py:474）。
  • 单一写线程 / fail-fast 不变：不新增配置键；若最终必须加，必须同步 config.validate_config 与 config/schema.py（黄金法则 4）。

痛点本质

三处缺口是同一件事的三个投影：环境态被写成站点结论。fetcher.py:32 的 docstring 已经为「等超时」修过一次同类问题（「那是环境态被伪装成站点结论的量级混淆」），但当时的修法只覆盖了「通道不可用」，没覆盖「通道可用、但扩展对站点没权限/网络不通」这一类。本次把这一类补齐，并顺手把 G2/G3 这两处「判据与文案不同步」收口。

M1 · 扩展侧：预检、拒发、展示

① 预检（background.js）

  • 新增 readSiteGrants(origins)：用 chrome.permissions.getAll() 一次取全量已授予模式，再用纯函数 originGranted(origin, patterns) 做匹配。不要用 permissions.contains({origins:[a,b]}) 判多个——它只在全部都授予时返回 true，会把「部分未授权」误判成整批状态。
  • 匹配前必须归一化：授予回来的是 https://pt.btschool.club/*，目标是 https://pt.btschool.club。归一化与匹配写成纯函数，直接进守阵测试。
  • 每轮 pollInstanceOnce 开头跑一次，结果写 storage.local.sitePerms = {origin: bool, checkedAt}。徽标是同步纯函数，不能 await，只能读这份缓存（badgeStateOf 现有签名不变）。

② 拒发（runTask）

  • 取数前查缓存：未授权 → 不发请求，直接回 {id, ok:false, kind:'no-permission', error:'站点未授权(<origin>): 到扩展选项页点「申请勾选站点的权限」'}，并 pushEvent(tag:'no-permission')。
  • 归因兜底：catch 里若 msg.includes('Failed to fetch') 且预检说已授权 → kind:'network'，文案指向「浏览器网络/代理」，不要复用 explainFetchError 那份「后端没起」清单（那是拉清单的错因，不是站点取数的）。

③ 选项页（options.js）

  • 站点权限区每行右侧加状态：已授权 / 未授权（读同一份 sitePerms，进页与「重新获取站点」后各刷一次）。
  • 顶部汇总条：有未授权时给「N 个站点未授权，取数会全部失败」+ 一个「授权未授权站点」按钮；复用 options.js:496 的 chrome.permissions.request({origins})，仍是手势内第一个 await（options.js:244 的硬约束）。

④ 徽标（background.js:612-651）

BADGE.noSitePermission = { text: '!', color: '#b0453d', label: '站点未授权' }
BADGE_ICON.noSitePermission = 'icon-bad'
// 判据定序（badgeStateOf 内，自上而下第一条命中即返回）
unconfigured → noSitePermission → ok → discoveryFailed → reconnecting

noSitePermission 排在 ok 之前是必须的：实例连通正常但站点未授权时，若徽标显示「连接正常」就是在撒谎。只要存在一个已勾选站点未授权即报此态（保守，宁可报警）。

§07风险与对策

风险触发条件处置
权限匹配误判 → 假报警授予回来是 https://host/*，目标是 https://host；或用户授予的是 https://*.host/*originGranted 归一化后按「scheme+host 相等，或 pattern 为通配父域」匹配，纯函数直测；宁可漏报也不误报
徽标长期红着被误读成「后端坏了」用户一直不授权文案写「站点未授权」而非「异常」，选项页给一键授权入口；与「发现失败」的红 ! 靠悬停标题区分
历史站点文件的 zero_rows=True 残留站点长时间不再取数（refresh_interval 5H）blocking_reason 先判 channel_last_error 再判 zero_rows；下一波自然重写
