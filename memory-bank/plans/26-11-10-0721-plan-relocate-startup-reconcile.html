§01目标与设计原则

背景: 26-11-10-0230 修复(链接对象判别 → skipped)已随生产 clone 更新并重启(06:42:56,日志实证 v6→v7 迁移即新代码),但既有失败账 jr-a2ce556d0165 仍 failed、组视图仍裂——修复只改「失败当下」的判定,没有任何治愈既有伤害的路径。用户拍板: bug 修复应当自愈,至少每次重启要有重新判断当前状态的机制。

目标:

  • 启动对账机制: 终态 failed 账在每次进程启动后按物理现状(qB 现值 + 盘面)重推相位;物理已完成的翻案重入生命周期走完既有收尾链,物理未完成的保持 failed(账面=现实)。
  • 通用性: 不看 failure reason、不建白名单——对未来未知事故形态、用户在 qB 侧手工补完的迁移、旧版本遗留账,同一套逻辑生效(区别于 hotfix 形状的 reason 白名单方案)。
  • 收敛判据(Blood 组): 部署后重启 → 对账重入 → 收尾窗 → qB 退出窗改写 → 核验删链 → done + 组归一 + symlink 删净,全程零人工零搬数。

设计底线 / 不变量:

  • 账面服从现实: failed 账是「判定那一刻的结论」,不是永久事实;重推只认物理证据。
  • 保守默认: 证据不可得/矛盾一律保持 failed;重入本身不搬数据(只复用既有链);重入上限每生命周期 1 次(防跨重启 churn,A1)。
  • 幂等: 对账判据从 job 记录无态推导,零新持久状态、零新配置键(黄金法则 1/4)。
  • 单一写线程: 对账发生在主循环首轮 qB 连接后的 tick,落账走既有 _set_job 单点(黄金法则 5)。
  • 真机验证硬约束: 只碰环境1(real.*),生产 26586 零触碰(继承上轮 D5)。

§02现状与痛点

2.1 生命周期缝隙: 终态 job 是唯一「死了没人体检」的状态

  • 启动路径对终态 job 只「计数+展示」: _load_jobs 全部条目无条件入账并计数(relocate_mod.py:222/235),启动日志「恢复在途 job N 条」含终态虚高(issue 26-11-10-0327);active_jobs() 滤终态(relocate_lifecycle.py:111-113)→ 终态永不进 _advance(:287),启动对终态无任何恢复/推进。
  • 唯一「离开 failed」的路径 = 同键 re-issue 换生命周期(relocate_exec.py:1379-1412);账面本身无出口(issue 26-11-10-0326)。
  • 启动时 qB 客户端未连接(qbmanager.py:510 start_all 在先、:520-532 connect 重试循环在后)→ 任何需要 qB 事实的处置不能落在 start(),自然钩点是首轮连接成功后的 tick。
  • 非终态 job 每 tick 都被 _advance 推进、moving 相位本有恢复判据(rt["recover"],relocate_mod.py:233)——缝隙恰好只在终态。

2.2 既有机械面盘点(本机制全部复用,零新增破坏性逻辑)

恢复落点 moved 是已支持流(relocate_exec.py:93 _recover→moved、:829 rebuild→moved);_arm 入口自带陈旧终态 journal 清理(_reset_stale_terminal_journal :434-498,调用点 :509);收尾末端 _step_verify 全员核验(:941)不过走 _verify_hang 悬挂、删链门有组外依赖扫描(:945/:1000-1016);收尾窗 FINALIZE_WINDOW_PHASES={armed,rewritten}(relocate_units.py:90);第 1 层作用域登记表=活跃 job(26-10-18-1604 §3.4)→ job 非终态组即不裂;WebUI「立即收尾」按钮对窗内 job 生效(server/routes/relocate_chain.py:110-143)。

2.3 生产两笔失败账落格(2026-11-10 只读取证)

  • jr-a2ce556d0165(qb_side_check_failed, mover 35711db2): qB 现值 mover save_path=I:(=dst)、7 颗=H:(改写未做,读经 symlink)、dst 数据 5,691,143,274 字节在位(上轮 §02.2 对照组)→ 完美落在判定表「搬迁段完成、收尾断」格。
  • jr-82f6dee7620d(move_stalled): 3 颗全在 src、alias_paths 空 → 落「搬迁段未完成」格,保持 failed(现状正确,机制不改写它)。

2.4 关联件

  • issue 26-11-10-0326(终态留账无清理出口): 本机制给 failed 账一条自动出口,但 done/cancelled/真 failed 仍累积——issue 收窄保留(G5⑤)。
  • issue 26-11-10-0327(启动计数含终态): 对账日志改写同一行,本计划吸收(G5⑤)。

§03方案总览

3.1 对账判定表(G1/G2)

前置闸(A1/G3): armed_at>0 的 failed 一律保持 failed(本生命周期的自动链运行配额——常规武装或对账重入——已用掉一次),不进判定表;armed_at==0 才按下表分流。

物理现状(qB 现值 save_path 分布)推断动作
mover==dst 且 dst 内容全量在位(证据②)搬迁段完成,断在收尾(本事故形态)重入 moved,重跑后段链 → 收尾窗 → done
全员==dst(armed_at==0,如 qB 侧手工补完形态)收尾只剩核验删链同上,既有链自然收敛(建链/核验幂等)
全员==src搬迁段未完成(82f6 形态)保持 failed(账面=现实)
矛盾 / 证据不可得不可判保持 failed(保守)

混合态(mover==dst 而部分文件不在 dst)由证据②排除 → 落「保持 failed」格;判定表按证据成立性分流,不按 save_path 分布穷举。

3.2 重入资格证据(G2)

双证据同时成立才重入: ①job.mover 的 qB 现值 save_path==dst(store 快照,path_normalize 等值——与既有 _recover/_step_verify 同口径,不折叠大小写,大小写病态形态落保守保持 failed;save_path 是 qB 自己的搬迁完成记录);②dst 内容全量在位: plan.files 全量逐条本机 stat(经 map_to_container/add_long_path_prefix_for_win 单点换算),文件存在且 size 相等才算在位,缺文件或 size 不等即不在位。不能复用 B′ 抽样口径(relocate_proof.py:257-278 任一命中即 positive、缺文件 OSError 直接跳过——any-hit 语义会放走「部分在位」态,对账要的是全量真值;换算与前缀工具可复用其单点,判定逻辑另写)。①②任一不成立或取不到 → 保持 failed。

3.3 重入动线(G3)与上限(A1)

单一入口恢复到 moved: 既有后段链原样重跑——建链(幂等,缺失重建)→ 修后代码自检(skipped 不挡武装;NEGATIVE 合法再 fail)→ _arm 进窗(入口自动清旧 failed journal)→ daemon 退出窗改写 → rewritten → _step_verify 全员核验 + 删链门 → done。不为「全员已到 dst」做特殊直达分支——链上每步本就幂等且有护栏,第二套判定逻辑增加的面比省下的一两步 tick 值钱。重入上限: 每生命周期至多一次自动链运行(常规武装或对账重入共用此配额)。重入落账即置 armed_at(语义 = 重入/武装时点): 自检在 _arm 之前跑(relocate_exec.py:240 先于 :251-254),pre-arm 自检 NEGATIVE 的失败 armed_at 恒 0(_fail 的 replace 不置它,relocate_lifecycle.py:170)——若闸只认武装置位,对这类失败永不闭环,恰是 A1 要防的跨重启 churn 形态;重入置位后闸对所有失败形态闭环,之后出路=人审 re-issue。journal 陈旧锚点联动(relocate_units.py:1229 armed_at>0 时锚点取 armed_at): 重入前的旧失败 journal 仍早于锚点(照旧清理)、重入后的新 journal 晚于锚点(保留),方向正确,S2 实现期核对。attempts 是别名重建配额(建链失败 +1 / _arm 归零,:334/518),不挪用——评审轮 1 裁断: 原定 attempts≥1 闸对 qb_side_check_failed 类失败永不触发且会被 _arm 归零销毁。

3.4 触发面(G5①)

每次进程启动后首轮 qB 连接成功的 tick 对账一次(消费点与 rt["recover"] 同窗,具体落位实现期钉死);配置热启用(relocate_lifecycle.py:86-94)同口径。对账 flag 在 _load_jobs(relocate_mod.py:213-238)按 phase==failed 无态推导——零新持久状态、零新配置键。运行期新失败不重判(修后代码在失败当下已判对)。

3.5 出路面(G4)与范围(G5④)

启动对账日志一行「启动对账 N 笔: 重入 M / 保留 K」;WebUI 零新增——重入后的待收尾/核验悬挂展示既有反馈面已覆盖,「立即收尾」按钮联动零改动(G5③)。cancelled(用户意图且物理已回滚)与 done 不在对账范围。

3.6 生产恢复语义(取代上轮 runbook §4.1 的重发步骤)

机制部署后,Blood 收敛 = 生产 clone 更新 + auto-qb 重启即可: 对账自动翻案重入,余下等 qB 退出窗(16585 与 26586 两实例全部退出,判据 pitfalls/testing/relocate-window-machine-roster.md)→ 改写 → 重启 → 核验删链 → done + 组归一。若用户此前已按旧 runbook 手工重发也兼容(新生命周期走常规链,对账对其无事可做)。红线不变: 收敛前不手删 H: symlink;期间组视图表现以 job 相位为准(重入后合并为单组「待收尾」)。

§07风险与对策

风险触发条件处置
跨重启 churn: 重入后自检再次真失败,下次重启又重入判定表行 1/2 持续成立但自检持续 NEGATIVE(未知形态)A1 闸闭环: 重入落账即置 armed_at,第二次 failed 起 armed_at>0 不再自动重入,出路=人审 re-issue;单周期内 failed 仍终态,运行期零循环
误重入: 证据①过但 dst 数据残缺数据部分在位/部分滞留 src唯一防线 = 证据②全量在位: 数据不全在 dst 一律不重入。兜底不能靠 _step_verify——改写先于核验(relocate_journal.py:177 自注「真错向由主循环重启后逐成员 save_path 核验兜住」),改写后成员 save_path==dst 使 _member_at_dst(:954-957,仅核 save_path)恒过,链门可达且核验失败会 reset_rewrites 重放再改写(:980-981)——误重入的破坏面(数据困 src + 别名删净)必须在重入前排除
qB 长期不连接,对账延迟qB 停机/网络断无超时: flag 保持,首连后执行;qB 恒离线则账维持 failed(现状不变)
对账与手工 re-issue 竞态用户在对账窗口同时 WebUI 重发同键在途闸 GATE_UNFINISHED(relocate_exec.py:1274-1292): 重入后 job 非终态,再发起被 blocked;对账只在启动窗一次,单一写线程不与运行期写竞争
相对键保存形态(2336 家族)污染改写dst 与 qB CWD 同盘2336 已修 Done;生产零同盘(上轮复核);真机拓扑沿用 src=R:/dst=.work(D:)
