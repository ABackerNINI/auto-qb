与维护任务 tags 部分迁移

01

背景与需求

需求原文（2026-09-27）:

需求记录

新增任务触发时机：某字段发生变化时触发，比如 tags 变了才执行（trigger:??，语法待定）。同时维护任务部分场景可迁移——比如添加站点 tag 在种子添加时已执行，后续仅需在 tags 发生变化时重新检查。

拆成两件相互独立、但有依赖关系的事：

  • A · 新触发时机——规则可以声明「只在我关心的字段变化时执行」，替代当前唯一的替代方案「interval 周期轮询 + 条件判断」，消除无变化轮次的全量重扫。
  • B · 维护任务迁移——内置 maintenance 的站点 tags 部分（add / remove / similar）是纯幂等收敛，种子 tags 未变且 tracker 配置未变时重跑没有收益；迁移为事件驱动后，每轮每种子省掉一轮 qB API 往返。

B 复用 A 的字段变化检测底座，故实施顺序 A → B；但 B 的正确性不依赖 A 的持久化快照（见 §05）。

缺口：字段变化的「最后一公里」已铺好，但没有接上事件

  • qB 增量同步每轮已产出 delta_fields（torrents/store.py:60，apply_delta :177-193）——tags / category 的外部变化当轮可见。
  • 但 delta_fields 当轮消费即丢：_CONFLICT_FIELDS（:156，含 tags）只用于登记 dirty_groups 重算下载冲突，不触发任何事件。
  • 跨轮对比目前只有 state 一个字段（state_snapshot :72 + update_state_snapshot qbmanager.py:811-812），且仅存内存。
  • 磁盘上没有任何种子字段快照——唯一按种子持久化的 upload_snapshots 已随计划 26-09-27-1232 整体移除（infra/versioning.py:34-40，state 现为 v2）。
  • 后果：规则想知道「tags 变没变」只能 interval 轮询 + conditions 判断，每轮全量评估；断电重启后「变化过」这一事实也无处可查。

维护任务现状

  • 内置 maintenance 任务按 config.interval（默认 60S）对每个种子跑 _handle_maintenance（qbmanager.py:854-871）：站点 tags 补打 / remove_tags / remove_similar_tags / HR tag-or-category。
  • 新种子添加路径已立即跑一次 maintenance（qbmanager.py:785）——即需求里「添加站点 tag 在种子添加时已执行」的现状，且这条链路不动。

方案总览

#决策点定案理由 / 备选
D1trigger 取值名on_torrent_field_changed与 on_torrent_state_enum_changed 前缀对齐；备选 on_field_changed 更短但破坏命名族一致性
D2监听字段怎么声明新规则键 watch_fields（列表）一个规则可同时监听多字段；白名单常量 FIELD_WATCH_ALLOWED，v1 = (tags, category)
D3跨轮基线放哪state 新顶层键 field_snapshots，state v2→v3重启不风暴、停机期变化可补捕；只存被监听字段控制体积（§05）
D4程序自写是否触发不触发（self-caused 抑制）防「add_tags 自喂环」；同轮内外部变化不可区分时保守跳过（§04 细则 5）
D5维护迁移开关全局键 maintenance_tag_mode: interval | on_change默认 interval = 现状，保守默认（黄金法则 2）；HR 部分不迁移（§07）
04

触发语义设计

配置写法（回答 trigger:??）

# 规则集内（任意 *_rules 键）, 与现有规则完全同构:
add_drive_letter_tag_rules:
  site_tag_recheck:
    enabled: true
    trigger: on_torrent_field_changed
    watch_fields: [tags]      # 必填; v1 白名单: tags / category
    cooldown: 5M              # 可选, 语义与 interval 规则一致
    conditions: [ ... ]       # 语法不变, 现有 13 个条件插件原样可用
    actions: [ add_tags: ["R"] ]

全局维护迁移开关（第二阶段，§07）：

maintenance_tag_mode: on_change   # 默认 interval (现状); 顶层键

语义细则

  1. 监听白名单——watch_fields 仅在 trigger: on_torrent_field_changed 下允许出现（其它 trigger 下出现即校验报错，fail-fast）；值非空且逐项落在 FIELD_WATCH_ALLOWED = ("tags", "category")。v1 不含 state（已有专属 trigger）与 amount_left（高频变化，事件化即噪音）。
  2. 变化判定——qB 增量 delta_fields 报告字段变化，再与持久化快照对比确认净变化；tags 比较前排序，消除 qB 返回顺序噪声。
  3. 首见不触发——快照无该 hash 记录视为首见：只记基线，不分派（对齐 on_torrent_state_enum_changed 先例，tests/test_trigger_events.py:136）。
  4. 重启 / 升级语义——快照持久化后，重启后首轮对比：真实变化仍触发（受 cooldown 约束，风暴有界）；一致则静默刷新。state v2→v3 迁移后首次启动 field_snapshots 为空表 → 全部按首见处理，升级零事件风暴。
  5. 自触发抑制——本程序自身的 add_tags / remove_tags / set_category 经 update_torrent_fields（store.py:319-374）落内存快照时，同步登记「本轮 self-caused 字段变更集合」；当轮事件分派跳过这些 (hash, field)。同轮内外部变化与自写叠加无法区分时保守按自写处理（宁可漏一次、不可自喂环；漏掉的变化等下次变化自然补上）。
  6. 去重与节流——cooldown / execute_once 直接复用 exec_history（base.py:262-263 → rule_engine.py:216-224），机制零新增。
  7. 动作白名单——不需要。事件分派时种子在场、上下文完整，对齐 validation/rules.py:266 「现场完整，不设限」；仅 on_torrent_deleted 有白名单。
  8. 执行通道——与现有事件一致：即时同步分派、不进 fast 队列、不计 max_tasks_per_tick（rule_engine.py:287-349）；_create_rule_task 对非 interval 返回 None 的现有逻辑（:244-260）无需改动。
05

检测与持久化底座

state 顶层键 field_snapshots

field_snapshots:
  # <hash>: { 仅存被监听字段的当前值 }
  "abcdef1234": { "tags": ["R", "HR"], "category": "pass" }
  • 按需写入——监听字段集合 = 所有 on_torrent_field_changed 规则的 watch_fields 并集，从配置推导；没有任何此类规则时不建快照、零写入开销。
  • 更新点——_refresh_torrents 轮末，与 update_state_snapshot 并列（qbmanager.py:811-812，该处注释已写明此位置承担「上一轮快照对比」职责）。
  • 落盘复用——走既有 _maybe_flush_state 周期落盘 + 退出兜底（rule_engine.py:198-214、qbmanager.py:457/500），单写线程假设不破坏（黄金法则 5）。
  • 版本迁移——infra/versioning.py schema_version 2→3：v2→v3 仅补 field_snapshots: {} 空表（比照 v1→v2 的最小迁移风格 :34-40）。

全量 refresh 降级路径（老 qB）

旧版 qB 走 torrents_info 全量 refresh（store.py:133-143），没有 rid 增量语义。设计约束：全量路径下同样「与持久化快照对比出净变化」，禁止按「全变」处理（否则每次全量刷新都是事件风暴）。delta 语义在 M1 实施时以测试钉住。

为什么维护迁移（B）不依赖持久化快照

on_change 模式运行期消费当轮 delta_fields；停机 / 重启场景走添加路径全量收敛一次（qbmanager.py:785 现有行为），天然幂等。持久化快照只为事件规则（A）服务。

07

维护任务迁移（maintenance_tag_mode）

行为矩阵

maintenance 组成interval（默认 = 现状）on_change
站点 tags 部分（_add_tags / _remove_tags / _remove_similar_tags）每 interval 执行添加路径立即执行一次（现状 qbmanager.py:785 不变）＋ 仅当该种子当轮 tags 发生外部变化时重检；无变化跳过
HR 部分（_add_hr_tag_or_category）每 interval 执行不变，仍每 interval 执行——HR 达标状态随时间演化，tags 变化捕捉不到，迁移会产生漏判
tracker 配置变更热重载全量重建 → 首轮全量收敛，两个模式行为一致，无需特判

为什么只能「部分」迁移

  • tags 部分是「tracker 配置 → 种子 tags」的幂等收敛：输入只有 tracker 配置与种子当前 tags，两者都没变时重跑输出不变，纯属浪费——这是可迁移的判据。
  • HR 部分的输入是种子做种时间 / 分享率等随时间流逝的状态，与 tags 是否变化无关——保留周期节奏。
  • 省下的是每轮每种子一次 qB API 读写往返（add_tags 虽幂等跳过已有 tag，但读取与请求本身有成本），种子量大时收益显著。
红线

生产 config.yml 由用户自行决定是否设置 maintenance_tag_mode: on_change，AI 不改动该文件（pitfalls/ops/prod-files.md）。默认值 interval 保证升级后行为零变化（黄金法则 2 · 保守默认）。

里程碑范围可独立交付
M1 快照底座store 层 field_snapshots + 监听字段推导 + state v3 迁移 + 全量降级路径核对（§05 两处核对点在此收口）是——纯底座，无行为变化

M4 维护迁移maintenance_tag_mode 五件套 + maintenance 分支行为 + 行为矩阵对应用例是——独立开关，默认关

验收标准

  • 外部（人工 / 其它工具）改动种子 tags → 下一轮 sync 内 on_torrent_field_changed 规则触发且仅触发一次。
  • 程序自身 add_tags / set_category → 不自触发（无自喂环）。
  • 重启后无事件风暴；停机期间发生的外部变化在重启后首轮补捕（受 cooldown 约束）。
  • state v2 存量文件升级后正常加载，首轮全部按首见处理。
  • maintenance_tag_mode: on_change 时站点 tags 维护只在添加 + tags 外部变化时执行，HR 部分节奏不变；默认 interval 行为与现状逐字节等价。
  • 守卫测试覆盖全部新键；test.full 通过。

风险与边界

风险应对
老 qB 全量 refresh 路径 delta 语义与增量不同M1 以「全量 + 快照对比出净变化」为设计约束并用测试钉住（§05）
state.json 体积增长（数万种子 × tags 数组）只存被监听字段；无监听规则零写入。M1 实施时用现网规模实测评估，过大再降级为存指纹（记录为核对点，默认存值——语义最直白）
self-caused 登记漏标 → 规则自喂环抑制逻辑集中在 update_torrent_fields 单点；专项守卫测试（§08-③）钉住 add_tags 场景
同轮内外部变化与自写叠加不可区分保守按自写跳过（宁漏勿环）；漏掉的变化待下次变化自然补捕，写入 keys.md 语义说明
tags 顺序 / 大小写噪声排序后比较（qB API 返回顺序不保证）

明确不做（本期 scope 外）

  • webhook / qB 实时推送——qB Web API 无此能力，sync 增量轮询已够。
  • 监听白名单扩展到 state（已有专属 trigger）、amount_left（高频噪音）。
  • 旧值 / 变更字段暴露给 conditions / expr——按需后补，v1 不加新条件插件。
  • WEB UI 新编辑器——RULE_FIELDS / constants 驱动自动呈现，仅回归。
  • 改动生产 config.yml——红线。
