transfer_run 验证等待异步化: 目标侧整段进 daemon 线程(结果队列回灌 + 命令线尾部消费)

本篇只回答: issue 26-11-11-0039 §06.1 行 1 的「transfer_run 验证等待」如何移出主循环——目标侧整段(add→验证→pause)进 daemon 线程,源侧读/门/导出留主循环,结论经队列回灌由命令线尾部消费(删源+回执),消除转移批次期间 N×10s 量级的主循环阻塞。两段回执(即时受理+终态补发)已拍板为后续阶段,不在本计划实施。

§01目标与设计原则

为什么做

issue 0039 行 1:用户点「转移种子」后界面卡几十秒——_cmd_transfer_run(webui/commands.py:178)在主循环线程同步跑完 TransferOrchestrator.run_batch(commands.py:194 → orchestrator.py:274),其中 _verify(orchestrator.py:417-447)对目标侧每 0.5s 轮询一次 find_torrent,单种子最多等 10s(verify_timeout=10.0),批内串行 → 一批 N 个的验证等待按 N×10s 量级占住主循环。期间 WEB 点什么都要排队、快照停滞、全部模块任务线同期停。命令面 docstring 自己就把这条认成「已知形态」(commands.py:181-183「验证轮询期间主循环被占用是计划 §03 已知形态」)。

做到什么程度算成

  1. 转移批次期间主循环可感知时长只剩生产段(每种子 2 次 qB HTTP:读源+导出);慢目标/超时场景下 [cmd] ... 排队 Xms 不再被验证等待拉大(CMD_SLOW_MS=300 埋点,commands_common.py:237);
  2. 逐种子外部语义(三态结果/失败分类/回执 truth 形状/入参顺序/summary)逐字节不变,前端 transfer_flow 零改动(waitCmd 超时已随批量放大,transfer_flow.js:326);
  3. 「验证未成不删源、数据文件永不删」不变量逐条保持(orchestrator.py 模块 docstring 不变量 1/2);删源与回执只在主循环线程;
  4. 既有 transfer 测试面(test_transfer_orchestrator 43 + test_transfer_adapters 43 + test_transfer_routes 8 + web_commands 用例)语义保留,worker 侧 runner 可注入(测试内联同步执行,不真等)。

设计底线/不变量

  • worker(daemon 线程)零共享态写:不碰任务队列 / state_file / store 分组索引 / 表现层视图(黄金法则 #5);adapter(独立 Client,adapters/qb.py:156 惰性建,不复用主 qB 连接)由线程独占,不与主循环并发使用;
  • 源侧三步只在主循环:torrents_info/torrents_export 走主 qB 共享 Session(qbapi.py:481/494),torrents_delete 还写 store.remove_torrent(qbapi.py:202-240);
  • 结论只经线程安全 handoff(queue.Queue)回灌,消费(删源/回执/聚合)全在主循环;
  • 关停顺序不变:stop_all → state.save → release(qbmanager.py:756 起 finally);退出不 join worker(daemon);
  • 零新增配置键:verify_timeout=10.0/poll_interval=0.5 维持 orchestrator 构造常量(可注入,orchestrator.py:259-270),validate_config 不动(探针计划 D5 同款)。

§02现状与痛点

现状(取证 2026-11-20,基线 a14e1e20;issue 锚点行号按符号重定位)

  • 入口唯一:WEB 命令 transfer_run(routes/transfer.py:72 经 _enqueue 投递);规则/其它模块不触发,只有这一条链。
  • 执行面:命令线消费(runtime_commands.py:28 consume_commands)→ _cmd_transfer_run(commands.py:178)同步执行 run_batch(orchestrator.py:274):串行逐种子 _transfer_one——读源(torrents_info,共享 Session)→ 状态门(gate_verdict 纯函数)→ 导出(torrents_export)→ 准备(路径映射/跳检决策,纯函数)→ adapter.add_torrent(目标独立 Client)→ _verify(:417-447:find_torrent 每 0.5s,≤10s,TARGET_ERROR 早退)→ after_state=paused 时 pause_torrent → 删源(torrents_delete+store.remove_torrent)。
  • 回执面:transfer_run 在 DEFERRED_RECEIPT_COMMANDS(commands_common.py:168,handler 自写、drain 不补写),handler 结算后写 truth={results(按入参顺序), summary, target}(commands.py:198-207);等待期间前端 waitCmd 转圈,超时已随批量放大(transfer_flow.js:326 注释自认「单条最坏=export+添加+验证 10s」)。
  • 阻塞量化:验证等待是设计内长等待(每种子 0.5~10s+,N 个串行 N×10s 量级);叠加 HTTP 超时面(源侧与目标侧同 REQUESTS_TIMEOUT=(3,10))——qB 假死/目标不可达时单种子可到 10s+。issue 0039 §03 判「P1 项单次可占几十秒」。
  • 消费挂点现状:命令线每轮必跑且暂停分支也跑(qbmanager.py:596 run_command_line 在暂停判断之前),其返回值 cmd_changed_state 驱动 P0-5 立即补刷新(qbmanager.py:609-613)——drain 的删源可白享这条通路。
  • 先例面:探针异步计划 26-11-10-2350 已把同形态问题(run_probe 三段轮询占主循环)拍板成「daemon 线程 + 结果队列 + 主循环消费」,其 §07 钉过「线程与主循环共享 qB client Session」风险(独立 client 处置)——本计划目标侧 adapter 天然独立,该风险面更小。旧 transfer 计划 26-10-31-0306 D6「串行逐种子」与 orchestrator docstring「不引入线程/并发(D6)」的读法按本计划改道(反指已落 0306 变更记录)。

§03方案总览

主线

(拍板 D1-D8,见 §06)_transfer_one 拆两段——生产段留主循环(读源→门→导出→准备,产出「已结算结果」或「验证作业」),目标侧整段(add→验证→pause)进 daemon worker(单线程 FIFO,逐种子 try/except 兜底,结论沿用 TorrentTransferResult 原结构);结果经 queue.Queue 回灌,consume_commands 尾部 drain 消费:验证成功的删源、填批次槽位、批次齐了写回执。主循环空了,回执契约不变(单段终态,truth 逐字节同形),前端零改动。

落点(三个组件)

  • orchestrator 拆分(transfer/orchestrator.py):生产函数(单种子:读→门→导出→准备 → 返回已结算结果或验证作业 {source_hash, plan, keep_source, after_state, notes})与 worker 侧函数(add→verify→pause,复用既有 _transfer_one 各步与失败分类)抽出;run_batch 保留为「生产+worker 逻辑顺序执行」的参考实现(既有测试与语义锚);纯函数与可注入面(sleep/verify_timeout/poll_interval)全保留。
  • TransferVerifyCenter(webui runtime 持有):作业队列 + 结果队列 + 单 daemon worker(stop Event 驱动 Event.wait(poll_interval) 可即时醒)+ 批次聚合容器(cmd_id → 槽位数组/剩余计数,主循环单写者);批次=任务分组,多批次自然共存(D3a);worker 循环级全异常捕获→合成 UNEXPECTED 结果回灌(防「线程死→结论永不到→回执挂死」)。
  • 命令面接线(webui/commands.py + runtime_commands.py):_cmd_transfer_run 改跑生产段——全批已结算(无验证作业)→ 现场写回执(快路径,行为与今天一致);有验证作业 → 递交 center,回执延后由 drain 写。drain 在 consume_commands 尾部:收全部结果→删源(成功且非 keep_source)→填槽→批次齐写回执;删除并入 cmd_changed_state 返回值(白享 P0-5 补刷新)。

分期

S1-S6 见 §04;两段回执为后续阶段(D5b,未排期,不在本计划实施)。

§06拍板记录

D决策点结论(2026-11-20,grilling 单轮)
D1 修法选型 案甲:后台 daemon 线程跑目标侧整段 add→验证→pause(adapter 批次级创建、仅线程使用)。拒绝案乙(issue 原案 add 留主循环——worker 验证种子 1 与主循环 add 种子 2 并发共用同一 adapter Session);拒绝案丙(相位状态机跨 tick,拆 _transfer_one 黑盒)
D2 生产段归属 留主循环同步跑完一批(读源→门→导出→准备);残余占用(N×读+导出 ≈ 百毫秒级/种子)记录在案,后续真遇到再立项,本计划不摊跨 tick
D3 并发治理 (a) 不设单飞:单 worker FIFO,批次=任务分组,多批次自然共存(与今天命令串行的最终语义等价);同 hash 跨批次撞车分两形——B 生产晚于 A 删源:生产段门拦(SOURCE_READ_FAILED,诚实失败);B 生产插在 A 验证期(反序,B 先入 worker):同目标时 B 侧 add 走「目标已存在」判定的命中形则落跳过(按实测 5.2 形 409→探针兜底成立;未命中响应形如通用 Ok. 判 ADDED 时 B 走完验证落 SUCCESS,终态仍无差);异目标时两批都可验证成功,后删者的删源是静默无操作(qB 对未知 hash 回 200、store.remove_torrent pop-None,_delete_source 返 True),回执纯 SUCCESS 无注记——失真面是「无提示的成功」而非误报失败,终态无差:数据文件永不删、源只删一次;若要显式「已由其它批次转移」注记属新增逻辑(删源前 hash 存在性探查),实施时可选。该交错面纳入 S2 验收用例(按实际删源语义钉住)。拒绝显式拒绝/等位受理段(都要新状态或两段回执)
D4 关停语义 (a) 退出不 join:worker daemon,stop Event 让轮询即时醒;在途验证作废、回执不写(前端按放大后超时超时,与今天进程崩溃一致);已验证未删→丢弃删除意图+WARNING 清单(「目标已建,源未删」);验证任务/删除意图不持久化(重启不续跑)。拒绝优雅退出补执行删源(往 finally 序列塞路径)与 pending 持久化(转移验证 ≤10s/种子且用户手动发起,不值续跑状态机)
D5 回执形态 本期单段终态回执不变(truth 形状/顺序/summary 逐字节同形,前端零改动);两段回执(即时受理+终态补发)拍板为后续阶段——方向已定,前端要动,实施另行排期(用户改判:原推荐单段不动,两段降后续)
D6 消费挂点 命令线尾部(consume_commands 内 drain):每轮必跑、暂停分支也跑(用户命令尾随语义一致);删除并入 cmd_changed_state 白享 P0-5 补刷新。拒绝 on_task_line(为一条链造 module 骨架)与 qbmanager 直调(层次倒挂)
D7 调度粒度 串行 FIFO 逐种子(每种子最多等 10s,批次墙钟时间与今天一致,只是不占主循环);拒绝批内并行轮询(本计划卖点是主循环解放不是提速)
D8 文档回写 计划入库即 kb.new --refs 双向补链(issue 0039 / 计划 0306)+ issue 行 1 状态格指针 + 0306 变更记录反指(D6 线程禁令读法改道)

§07风险与对策

风险触发条件对策
worker 异常 → 结论永不到 → 批次回执挂死 线程被杀 / 解释器异常 / 单种子处理未捕获异常 worker 循环级全异常捕获 → 合成 UNEXPECTED 结果回灌(S2);批次容器记入队时刻,drain 对超龄未结算批次按 VERIFY_TIMEOUT 口径兜底结算并记 WARNING(同探针计划「超龄条目」思路,上界 = verify_timeout+裕度 × 串行深度)
adapter Session 并发使用 案乙形态残留(add 在主循环、验证在线程,同 adapter 两线程) 案甲下 add 进线程:adapter 批次级创建、仅 worker 调用;S2 隔离断言钉死(主循环不持任何目标 adapter 调用面)
验证窗口内源被用户手动删/改 验证等待期(秒级)用户删源/重命名/recheck 删源走既有 torrents_delete(_delete_source 已兜 False+注记,删不存在 hash 不翻已成功结算);门判定在生产段完成,窗口内状态变化不影响已受理种子的验证/删源语义——与今天「验证后删」窗口同形,只是窗口从毫秒级拉长到秒级
已验证未删源残留(双份做种) 验证成功后、drain 删源前进程退出(D4a) 丢弃删除意图 + WARNING 清单(hash +「目标已建,源未删,请手动处置」);重启不重放(保守默认:绝不自动删源);残留面与今天「删源失败源已保留」同族,属既有兜底语义
drain 消费中主循环异常 drain 内删源/回执写入抛异常 drain 逐结果 try/except,单条失败不影响其余;批次聚合容器是主循环单写者(黄金法则 #5),异常轮次由下轮重试同一槽位,批次计数只由主循环改
快路径回归(无验证作业批次行为漂移) 全跳过/全失败批次误走队列路径 S3 快路径判据单点(生产段无验证作业 → 现场结算回执,与今天同步路径同形);web_commands 用例钉回执时机
CMD_SLOW_MS 仍可能报 WARNING 大批次生产段 N×(读+导出) 超 300ms 残余已在 D2 记录在案;埋点照报是观测面不是缺陷,真成了痛点按 D2 单独立项
暂停模式下的删源时机 暂停期验证完成,drain 执行删源 命令线在暂停分支本就照跑(qbmanager.py:597-602 先命令后 continue),删源是用户已发起命令的尾随动作,语义一致;实施中若发现暂停期删除面需要守卫,按既有命令面口径处置并回写本件
