01结论先行

实施质量高于一般水平，架构判断经得起复核，但「证据链」比代码弱一档。P0/P1 十二项全部落地且落点与计划一致：命令唤醒只走命令线、命令后整批补一次完整刷新、按视图回传、只读端点短缓存、请求超时、行窗口化 —— 每一条的实现都能在源码里指到具体位置，注释里写清了「为什么不能那样做」（例如为什么不能只调 apply_sync、为什么自投递命令不能唤醒），这些否决理由在本次复核中全部成立。

问题集中在三处：

  1. 三层行窗口共用了一个硬编码的间距常量，而三个容器的真实 gap 各不相同（6 / 5 / 0）。实测 prism 的滚动总高比全量渲染高 2973 px（3000 行），atlas 恰好为 0 —— 也就是说这个 bug 只在棱镜一套 UI 上存在，而双 UI 的冒烟断言是「窗口化前后各测一次」，天然测不到它。
  2. P0-3 乐观 UI 只覆盖了三个入口中的一个。种子行右键 ✓；整组操作只给成员行打补丁，组行本身的状态色与 pending 标记都不变（不展开明细就看不到反馈）；整集/整剧走 actEpisode，完全没有乐观更新。而用户最初的抱怨场景正是辅种页。
  3. 计划的量化验收口径没有落成任何产物。「单目标 ≤ 400 ms」「响应体 ≤ 200 KB」「单帧 ≤ 50 ms」三条中，只有第一条能用埋点间接证实；第二条实测未达成（种子页 4.31 MiB / 轮，是目标的 22 倍），第三条没有任何数字。P0-0 埋点本身做得很干净（wait_ms/exec_ms 一路回传到前端），但前端 cmdStats 全仓只写不读，计划的「走查表」始终没产出。

安全面本轮没有引入新风险：新增端点都挂在全局鉴权依赖下，只读缓存的写入点在 _require_torrent() 校验之后（伪造 hash 无法污染缓存），断连判定被刻意提到缓存之前，请求超时把「永久挂死」变成「有界失败」。三条低危项都是工程习惯问题，不是漏洞。

维度评级判据
计划本身A−14 候选 / 3 否决全部带实测数字；附录用实测把「主循环 50 ms」方案否决得很干净。扣分在验收口径没有配交付物、以及白名单在实施中悄悄收窄后没有回写计划。
实现符合度A−12/12 项落地，落点与计划描述一致；偏差集中在 P0-3 的覆盖面（见 BUG-3）。
BUG 风险B1 个高（prism 窗口化总高 +2973 px）、2 个中、3 个低。无数据损坏类缺陷，无并发写冲突。
安全A−无新增攻击面；鉴权/校验次序正确。3 条低危工程项。
性能B+长任务与整轮 refresh 大幅下降（实测 1384 → 244 ms）；但按视图回传对种子页几乎无收益，且 sync_interval 与分档轮询不匹配造成约一半重建白烧。
测试与证据B−1049 passed / 92% 与文档一致；34 项浏览器冒烟可复跑全绿。但「写后失效」只测机制不测接线，关键性能数字不可复现。

03缺陷（BUG）

BUG-1

三层行窗口共用一个硬编码间距，与 prism 的实际 gap 不符 —— 棱镜滚动总高偏差 +2973 px

高
证据
同一进程内 A/B 实测（3000 种子 / 200 组，1440×900，桩服务）：
prism gap=5px 窗口化 167043 → 全量 164070 ⇒ Δ = +2973 px
atlas gap=6px 窗口化 167071 → 全量 167071 ⇒ Δ = 0 px
根因
app.js:170 的 const ROW_WIN_GAP = 6 注释写着「与 CSS gap: 6px 同源」，但三个行容器并不都是 6 px：atlas .group-table{gap:6px}（style.css:395）、prism .group-table{gap:5px}（views.css:106）、成员行容器 .detail 是 block 容器根本没有 flex gap（间距为 0）。_rowWindow() 的前缀和、padTop、padBottom 全部按 6 px/行累加。
影响
棱镜页的滚动条比全量渲染长 ≈1.8%（3000 行）；「滚动位置 ↔ 可见行」的映射整体偏移，中段最大约 49 行。末行仍可达、视口不出现空白（占位与滚动解释用的是同一套虚标尺，彼此自洽），因此是观感/一致性缺陷而非功能中断。但它同时说明「占位撑住总高」这一硬约束在 prism 上不成立。
为何漏网
冒烟断言 Math.abs(after - before) < 200 的 before 在 A/B 之后才读，而 A/B 结束时已把 rowWin 还原为 true —— 两次测的都是窗口化高度，不是「窗口化 vs 全量」。本次复跑输出的 167043 -> 167043px 正是这两个窗口化值。
建议
不要硬编码：首次测量时用 getComputedStyle(container).rowGap 取真实值（_measureRowH 里顺手做，一次成本），三层各存一份；或把占位改成用 margin-top/bottom 表达、让 flex gap 不参与高度公式。断言改为「窗口化高度 vs 关闭窗口后的全量高度」。
BUG-2

成员行窗口的间距假设同样错（实际 0 px），且追剧页的成员窗口是死路径

中
证据
prism/css/views.css:232 .detail { margin:…; padding:…; background:…; } 无 display:flex ⇒ 块级容器，成员行之间只有 border-bottom，行间距为 0；代码按 ROW_WIN_GAP=6 算。另：memberWin() 由 expandedGroup 驱动，而追剧页用的是 expandedShows/expandedShowEp，expandedKey 在追剧页恒为 null ⇒ memberPadTop/Bottom 在追剧页恒为 0，模板注释「集成员行同样走窗口（超 200 个版本的集才真正生效）」与事实相反。
影响
两条都属于「当前很难触发」：成员窗口需要 ≥200 个成员的组才会启用（ROW_WIN_MIN=200），触发时占位会偏大 6 px/行；追剧页则永远退化为全量渲染（正确但不省）。属潜伏缺陷 + 注释失真。
建议
与 BUG-1 一并修（间距改为实测）；成员窗口的驱动源改为「当前展开单元」而不是 expandedGroup，或明确删掉追剧页的占位与 winMembers 调用并回写注释。
BUG-3

P0-3 乐观 UI 只覆盖三个入口中的一个：整组无可见反馈、整集/整剧完全没有

中
证据
① 种子行 actTorrent()：applyOptimistic + resolveOptimistic ✓（冒烟实证「1 行半透明」「60 目标 pendingOps 60」）。
② 整组 act()：只把成员 hash 传进 applyOptimistic，而组行的状态色取自 g.status.primary（模板 :class="['s-' + g.status.primary, …]"），组行也没有 is-pending 绑定 ⇒ 不展开明细时「点击即变」不发生。 ⚠️ 本条判断已被实测推翻，见 §10.1：组行颜色本来就是变的（s-checking → s-paused，实测），真正缺的只有 is-pending 绑定。
③ 整集/整剧 actEpisode()（app.js:2770-2782）：直接投 bulk + 等回执，没有任何乐观调用。
影响
计划把 P0-3 定为「主观收益最大的一项」，而用户最初的抱怨发生在辅种页。现在整组暂停的可见反馈仍然要等回执（P0-1/P0-2 之后约几十毫秒，体感已可接受，但「感知层」的收益没有兑现）。冒烟只走了种子行路径，因此这条缺口在自动化里不可见。
建议
给组行加乐观：补丁 g.status = {primary, text} 并按成员状态重算，同时给 .group-row 绑 is-pending（键用组 key，pendingOps 需要支持组粒度）；actEpisode 复用同一套。冒烟补两条断言（整组 / 整集各一条）。
BUG-4

容器偏移是非响应式的：窗口宽度变化后的第一帧用旧偏移算窗口

低
证据
_winTop 在 created() 里是普通对象（刻意不入 data，注释解释了原因），只在 updated() 的 _ensureWinTop() 里更新；而 _rowWindow 是 computed，在渲染阶段先求值。_onWinResize() 只递增 _winResize 与 _winViewH。
影响
resize 后的第一次重算读到的是旧 _winTop，而写回新值不会触发重渲染（非响应式）⇒ 窗口切片可能偏一行左右，直到下一次轮询/滚动带来新的响应式变化才纠正。观感上是极轻微的跳动。
建议
把 _winTopSig 或一个 _winTopVer 计数放进 data，_ensureWinTop 更新后自增，让 computed 依赖它；或在 _onWinResize 里同步 $nextTick 后重算。
BUG-5

回执写入先于缓存失效序号自增（微秒级竞态，顺序反了）

低
证据
web_commands.py:138-146：先 _set_web_result(cmd_id, "ok", …)，再 self._web_write_seq += 1。前端拿到回执后会立刻重取只读端点（如改完分类重取 /api/categories），理论上存在命中旧缓存键的窗口。
影响
窗口在微秒量级，且写序号只被主循环线程写、Web 线程读，实际撞上的概率极低。但顺序在语义上应当反过来：先让缓存失效，再宣布命令成功。
建议
把 _web_write_seq += 1 提到 _set_web_result() 之前。
BUG-6

sync_interval 的帮助文案承诺了实现里不存在的钳制

低
证据
config/schema/groups.py 的 help 写「大于主循环间隔时按主循环间隔生效」，但 qbmanager.run() 是 next_sync_at = time.time() + sync_interval，没有任何 min(sync_interval, main_tick)。配 sync_interval: 5S 时同步线真的 5 s 一次，且此时任务线（2 s）不再刷新快照 —— 与文案暗示的「至少保持主循环频率」相反。
建议
二选一：在 run() 里 sync_interval = min(sync_interval, main_tick) 落实文案；或改文案为「独立节拍，可快可慢于主循环」。校验侧 positive=True 已挡住 0（不会忙等），这点是对的。

04安全审查

本轮改动引入了新的对外接口面（/api/state?view=）、新的服务端缓存、以及一条新的线程间失效信号。逐项核对结论：没有引入新漏洞，设计上还有两处刻意为之的正确取舍。

检查项结论依据
鉴权覆盖通过web.py:161 dependencies=[Depends(require_token)] 挂在 app 级；本轮新增/修改的端点（/api/state、只读缓存化的 5 个端点）全部继承，无绕过。
缓存投毒通过_cached_read() 一律在 _require_torrent(hash) 之后调用 ⇒ 不存在的 hash 先 404，不会以攻击者可控的键写入缓存；/api/categories、/api/tags 键固定。这是正确次序。
断连不被缓存掩盖通过三个直连 qB 的端点把 _require_client() 提到 _cached_read() 之前，断连仍返回 503；有单测固化。
参数注入 / 类型混淆通过新增 view 参数只用于字典查表（VIEW_ARRAYS.get(view)），未知值回落「全量」；不参与 SQL / 路径 / 命令拼接。bulk 的 keys 走既有 _group_key_param 编解码，未新增解析路径。
埋点字段污染命令参数通过_queued_ts 以下划线前缀约定隔离，drain 侧 not k.startswith("_") 剔除后才 **args；否则会被原样传给 handler 报 TypeError。这个约定有注释、有测试。
拒绝服务 / 资源耗尽改善但有残留P1-5 的 (3, 10) 超时把「qB 假死 ⇒ 主循环无限期挂起」变成有界失败，是净改善。残留：_cached_read() 在锁外调用 fn()，同键并发会重复打 qB（惊群）；且 len(_ro_cache) > 128 时整表 clear()（连新鲜项一起丢）。均为低频、有界，不构成可被放大的攻击。
XSS / 注入面通过新增的 data-hash/data-key、isHit()、占位 div 全部走 Vue 绑定与属性插值，无 v-html/innerHTML/eval 新增；无新外链资源。
密钥 / 凭证泄漏通过回执新增字段只有 wait_ms/exec_ms；无 token、无路径回显。
dev 工具暴露面低危scripts/ui_harness.py 以 skip_local_verify=True 起真实 app，且提供 --host 参数 ⇒ 传 0.0.0.0 会在局域网上暴露一个无鉴权服务（数据是合成的，风险有限）。建议硬编码 loopback 或对非 loopback 直接拒绝启动。
一处值得肯定的设计

只读缓存的失效键选择是「写序号」而不是「时间戳 + 主动失效」，这意味着缓存是按键自动换代的：任何写命令后旧键自然不再被命中，不需要在每个写路径上记得调失效函数。用「忘记调用」这一类 bug 换成了「键空间增长」，而键空间又有 128 条上限兜底 —— 取舍是对的。

05性能审查

三组实测（桩服务，3000 种子 / 200 组）：响应体构成、行窗口高度、命令端到端。前两组是本轮新增的测量，计划里没有。

5.1 按视图回传的真实收益：种子页几乎没有

计划把 P1-1 的收益写成「响应体 ≈ 1/4」，验收口径是「≤ 200 KB」。实测 /api/state 各视图字节数：

请求字节占全量说明
/api/state（不带 view）6 405 735100 %四份数组全回，≈ 6.11 MiB
?view=group（辅种页）1 746 31927 %≈ 1.67 MiB，接近计划的 1/4 ✓
?view=torrent（种子页）4 524 99271 %≈ 4.31 MiB —— 不是 1/4
?view=show（追剧页）134 8082 %≈ 132 KiB，唯一达成 ≤200 KB 的视图

原因很直接：VIEW_ARRAYS["torrent"] 要回的就是那个「每条 74 个字段 × 3000 条」的平铺数组，它本来就是全量里最大的那一份（也是 filteredTorrents 曾经复制 68 ms 的同一份）。按视图回传只切掉了「这一页用不到的另外两份」，切不掉这一页自己要用的那份。

后果是：种子页 3000 种子时前端每轮仍要收 4.31 MiB（分档后 2 s 一轮 ⇒ 峰值约 2.1 MiB/s），而 updated 在速度类字段每轮都变的情况下几乎恒为真 ⇒ 每轮都是全量替换。计划验收的「≤ 200 KB」在种子页差 22 倍，且没有任何产物给出过这个数字。

建议

真正的解药是计划里的 P2-2（按 hash 增量回传），或退一步：给平铺数组做「按可见列裁剪字段集」——种子页最多同时显示 13 列，74 个字段里大半是抽屉才要的。两者都不需要改前端渲染路径。

11.4 教训

  • 「载荷大」不等于「要裁字段」。报表 §05.1 量到 view=torrent 4.31 MiB 就推出「按可见列裁剪」，但没量三件事：字节怎么分布、客户端花在哪、服务端花在哪。量完发现三处结论都与直觉相反（裁不动 / 客户端只占 10 ms / 服务端占了 85% 且全是白跑）。
  • 框架的「方便」是有价的。FastAPI 自动做 jsonable_encoder 对普通接口是便利，对「一次回传几 MB 原生数据」的热路径就是纯税。凡是返回体超过百 KB 的端点，都该走 Response 直返（/api/torrents/{hash}/files、/api/search 等同类端点尚未改，见下）。
  • 对照实验值得花时间。第 3 步那个「5 MiB 静态文件走 uvicorn 只要 1.6 ms」的对照，一句话就把「网络/框架传输层」整片排除掉了 —— 否则很容易在错误的方向上做优化（比如加 gzip）。

后续已全部补做（同日，见 issues/26-09-19-1900-webui-hot-endpoints-jsonable-encoder，已 Fixed）： /api/search、/api/torrents/{hash} 及 /trackers、/files、 /peers 一并改为 JSONResponse 直返。/api/search 服务端 82.6 → 23.3~30.1 ms （输出字节与基线逐字节一致）；详情族在桩里 payload 太小测不出收益，改为真实数据预置。 守阵清单同步扩到 8 个端点并红绿双验。

⚠ 一条重要例外（值得单独记住）：/api/config/schema 不能这样改 —— 它的 schema_payload() 返回 dataclass 实例（Group/Field/Plugin）， 直返会抛 TypeError: Object of type Group is not JSON serializable ⇒ 500；它正是靠 jsonable_encoder 做转换的，那趟遍历对它不是白跑。判据：载荷里有非 JSON 原生类型就必须保留编码器。 已回退并在端点留注释。

10.1 修订：BUG-3 证据② 判断有误（把「没接线」误判成「机制不生效」）

用 --cmd-result hang 的桩（命令永不回执）实测：整组暂停后组行 class 由 s-checking 变为 s-paused is-pending 前的那一步 —— 即颜色本来就变，pendingOps 2 条。原因：组行状态色取自 decoratedGroups.status.primary，而它是 _aggStatus(成员 kind) 算出来的 computed；applyOptimistic 改的正是成员对象的 kind，computed 自动重算并重渲染。

真正的缺口只有一条：组行没有 is-pending 绑定（缺「在飞」的视觉标记）。证据③（整集/整剧完全没有乐观调用）实测属实：actEpisode('pause') 后 pendingOps 为 0、集行 class 不变、e.state 不变。

教训：把「机制」与「接线」分开断言。本报表只读了调用点就下了「不生效」的结论，没有真跑一次看 class —— 于是把「没绑 class」误判成「机制没工作」。同族坑已写进 memory-bank/pitfalls.md。

把追剧页当默认页的用户，刷新一次就再也看不到内容。这属功能性回归，且正好落在本报表 §05.1 判为「收益」的那次改动上 —— 报表量到了 134KB 的响应体，却没问「这份响应够不够把页面渲染出来」。同时它暴露了 ui_smoke.cjs 里一条恒真断言（epRows >= 0），所以 34 项冒烟全绿也没拦住。
修复
VIEW_ARRAYS["show"] = ("shows", "groups", "singles")（仍不回 4.5MB 的 torrents）。响应体实测 134,808 → 1,880,935 B（全量 6,405,735 / 辅种页 1,746,319 / 种子页 4,524,992）。守卫：改写 test_api_state_view_scoped_payload，新增 test_ensure_group_state_show_view_carries_member_index；冒烟新增「刷新后追剧页不空白」，并把那条恒真断言改成 > 0。
BUG-9

「复制磁力」对所有种子恒失败

中
证据
magnet_uri 只出现在种子页的平铺 SEED_ITEM（web_view.py:305），分组/未归组的成员视图（_member_view）没有该字段。而 memberByHash 先无条件注册 groups、再用 if (!map.has(hash)) 注册 singles/torrents ⇒ 平铺数组永远当不上「兜底」，索引条目恒无 magnet_uri。实测（种子页，平铺数组已加载）：flatHasMagnet=true 但 idxHasMagnet=false，copyTorrentInfo('magnet') 得到 「该种子没有 magnet 链接」。
影响
右键「复制磁力」100% 失效（与种子是否真有磁力无关），而提示文案还把人往「这个种子没磁力」上带。辅种页/追剧页同样失效 —— 因为索引优先取分组条目，与当前在哪个视图无关。
修复
点的时候按需取一次详情（复用 _editDetail，抽屉已开则连请求都不发），不给每 1.5~3s 一轮的响应体加字段（3000 种子 ≈ +0.6MB/轮）。冒烟新增断言，并刻意同时断言「索引里确实没有该字段」，否则这条断言会因为「索引恰好带 magnet」而空过。
BUG-7

同一概念两张状态优先级表：辅种页与追剧页对同一批种子显示不同颜色

低
证据
后端 _SHOW_STATE_RANK = {error:0, downloading:1, checking:2, paused:3, seeding:4, other:5}（决定追剧页集行的 e.state）；前端 decoratedGroups 用的是 ["error","checking","downloading","seeding","paused","other"]（决定辅种页组行颜色）。两处结论相反的混合态：{downloading,checking} 后端取 downloading、前端取 checking；{paused,seeding} 后端取 paused、前端取 seeding。
影响
同一批种子在辅种页是绿、在追剧页是黄，用户无法解释（只会觉得「颜色乱」）。乐观 UI 更危险：前端按自己的表算「点击后的颜色」，下一轮回执却按后端的表算真值 ⇒ 颜色弹回。本批实际未触发弹回（白名单动作后成员 kind 是齐的），但那是运气不是设计。
修复
前端抽 STATE_RANK 单点表并对齐后端顺序（语义：先报需要处理的、再报在跑的、最后报已完成的），组行与集行共用 _aggStatus。可见变化仅限上述 2 种混合态（6 组样例实测：2 组变、4 组不变）。守卫：静态守阵机械比对前后端两张表，改一边不改另一边即红。
