§ 1

背景与现状模型

现有 HR 能力是站点级静态配置: trackers.<site>.hr 一旦配置 (required_seeding_time 必填, 另有 required_share_ratio / extra_seeding_time / condition), 该站点的所有种子一律按 HR 管束。判定逻辑收口在 TorrentRecord 的两个方法上:

  • check_hr_condition() — 是否「触发」HR (下载比例 / 下载量达到 condition, 或下载满); 兼作辅种排除依据;
  • check_hr_satisfied() — 触发之后, 做种时长达标或分享率达标即视为满足。

全部消费点都经这两个方法, 共四处: maintenance 打 HR 标签/分类 (mixins/tags.py _add_hr_tag_or_category)、WEB UI 的 HR 展示字段 (mixins/web_view.py _hr_view_fields)、规则条件 hr (rules/conditions.py, modes condition-met / condition-not-met / satisfied)、表达式变量 tor.hr_condition_met / tor.hr_satisfied (rules/expr/env.py)。

问题: 部分种子 HR 站点上的两难

部分站点实行部分种子 HR 策略: 同一站点的种子只有一部分受 HR 约束, 且下载时站点不提供可机读的逐种标记, 只有「HR 种子统计页」(通常列出当前账号下受 HR 约束的种子清单)。静态模型在这种站点上只有两个坏选项:

  • 全站按 HR — 过度保护: 全部种子不辅种、全部打 HR 标签, 辅种价值被抹掉;
  • 不配 hr — 漏管: 真正触发 HR 的种子可能被规则正常删除或停做, 带来账号处分风险。

本计划的目标: 让这类站点的 HR 身份逐种子在线核实, 其余站点行为完全不变。

§ 2

可行性结论

总评 · 可行

技术路线成立: 抓取 → 下载 → 算 infohash → 对账 → 建索引, 每一步都落在项目既有架构里, 不需要引入新线程模型或新存储。

判定收口是最大的红利: 四个消费点全部经 TorrentRecord 两个方法, 只改一处收口, 上层零改动。

cookie 是最大的不确定项: 「直接复用日常浏览器 cookie」在 2026 年的 Chrome/Edge 上有硬性技术墙 (App-Bound Encryption + Chrome 136 CDP 限制, 见 §6, 均已核实), 需要分层方案与用户配合。

账号安全是最大的运营风险: 访问频度必须默认极保守 + 全可配 + 熔断, 这恰是本需求的原始诉求, 设计上优先满足 (§7)。

边界判据 — 若某个站点其实提供了逐种 HR 标记 (详情页/搜索页图标) 或 JSON 接口, 则不需要本计划的「下载种子对比」重路线, adapter 直接读更便宜的来源即可。adapter 接口按「返回 HR 种子列表」抽象, 把这条路留开 (§4), M0 调研优先确认。

§ 4

HR 名单获取 (统计页抓取)

HR 统计页是账号维度的「我的 HR」清单, 天然就是需要核实的范围, 不需要全站扫描 —— 这是整个方案成本可控的前提。页面行字段 (2026-09-22 经用户确认的常见形态):

页面字段用途
HR 编号 (种子编号, tid)站点内唯一 id: 去重、下载 URL、索引主键都落在 (站点, tid) 上; 跨站点绝不混用
种子名称展示与人工核对; 与本地种子的匹配仍以 infohash 为准 (名称不可靠)
上传量 / 下载量 / 分享率站点侧权威流量快照: 展示与交叉核对用; 决策仍以 qB 本地实时值为准
还需做种时间距要求做种时长还差多少: 进度参照 + WEB UI 展示
完成时间语义 M0 与数值格式一并确认 (达标完成或下载完成); 已完成条目保留身份记录, 不从索引删除
剩余达标时间距达标/超期的时间余量: 展示与将来规则条件的扩展点

Adapter 抽象

每站点一个 adapter, 接口统一为「给定登录态 + 分页游标, 返回结构化 HR 种子列表」: {torrent_id, name, listed_ts, hr_requirement?} + 是否还有下一页。解析实现按站点隔离:

  • 解析器选型: 首选标准库 html.parser 子类 (零新依赖, 行为可测); 仅当页面结构复杂到 stdlib 不堪用时, M0 再评估引入轻量解析器 (如 selectolax)。
  • 更便宜的来源优先: 若站点有 JSON 接口或逐种标记, adapter 换实现不换接口, 并跳过 §5 的 .torrent 下载成本。

改版防护

解析结果做最小字段校验: HTTP 200 但解析出 0 条记录、或必填字段缺失率超阈 → 判定「页面可能改版」, 该站熔断 + WARNING (自动进 notify), 绝不把空结果当真入库 (空结果的错误语义是「该账号没有 HR 种子」, 二者必须可区分)。每站点样本 HTML 脱敏后进测试 fixture, 改版即测试红。

§ 5

种子下载与 infohash 对账

下载

HR 页列出的种子按站点 torrent_url_pattern 拼下载链接 (典型如 download.php?id={id}, PT 站通常还需 passkey 参数, 属配置的一部分)。请求带 cookie 与一致的 UA (§6)。文件落 <data_dir>/hr-check/ (运行时数据目录, 已在 gitignore 范围内), 算完 infohash 即完成使命, 保留策略可配 (默认保留最近一份供排查)。

infohash 计算 — 一个必须做对的细节

v1 infohash = sha1 over info dict 的 bencode 原始字节切片, v2 = sha256 同理。实现上不能「decode 再 re-encode」—— 重编码的键序/整数表示可能与原文件不一致, 算出的 infohash 就错了。正确姿势: 自写极小 bencode 解析器时同步记录 info dict 在原文件中的字节偏移, 对原切片做哈希。解析器预计 60 行上下, 纯函数, 强测试覆盖 (往返 + 已知 infohash 向量 + 畸形输入拒绝)。替代方案是引入 bencodepy, 代价是多一个依赖, M0 拍板; 倾向自写, 符合项目零依赖风格。

与 qB 做种库对账

  • v1 种子: qB 的 hash 即 v1 infohash, TorrentStore 现有字段直接可对;
  • v2-only 种子: qB (≥ 4.4) 的 hash 字段本身即 v2 infohash, 同样直接可对;
  • hybrid 种子: 双算双配; infohash_v2 是否已在快照字段里, M0 核对 _SNAPSHOT_FIELDS, 不在则评估增量成本。

state 模型: (站点, tid) 为主键, infohash 是回填属性

种子编号 (tid) 站点内唯一, 跨站点不混用; 同一内容 (同一 infohash) 辅种到多个站点时, 各站 HR 身份彼此独立 —— 索引一律以 (站点, tid) 为主键, infohash 在下载算出后一次性回填:

hr_index[site][tid] = {              # 页面行的站点侧事实, 每次页面刷新只更新字段 (不触发下载)
  tid, name,                         # HR 编号 + 种子名称
  uploaded, downloaded, ratio,       # 站点侧流量 (观察/展示用, 决策不替代 qB 本地实时值)
  need_seed_time, done_ts, remain,   # 还需做种时间 / 完成时间 / 剩余达标时间
  infohash: "…",                     # 首次下载算出后回填, 之后不再下载
  first_seen, last_seen              # 生命周期 (配合 index_retention 淘汰)
}
hr_downloaded[site][tid] = {ts, infohash, name}   # 已下载记录: 「永不重下」的持久凭据
hr_dl_fails[site][tid] = {count, last_ts}         # 下载失败记账, 达上限后冷却

防重复下载三层: ① hr_downloaded 是廉价永久层 (每条仅 tid + infohash + ts + name) —— 页面条目后来消失、翻页遗漏、快照超期淘汰, 只要 (站点, tid) 在里面就绝不重下; ② hr_index 中已有 infohash 的条目, 刷新只更新页面字段; ③ 下载失败按 max_download_retries (默认 3) 计数, 达上限冷却, 不死循环烧配额。淘汰 (index_retention) 只作用于页面快照字段的陈旧条目, 不触碰 hr_downloaded。

判定反查: TorrentRecord 按 (站点, infohash) 查命中 —— infohash → tid 的反向映射在主循环加载 state 时于内存重建 (state 只存 tid 主键, 不存双份)。索引不只服务当前库: 已做种种子命中 → 受 HR 管束; 辅种候选命中 → 排除辅种; 未命中走 unknown_policy (§9)。

§ 6

Cookie 分层方案 (核心难点)

「复用当前浏览器的 cookie」这个诉求, 在 2026 年的 Windows / Chromium 生态里有两条已核实的技术墙:

事实 1 · App-Bound Encryption — Chrome 自 v127 (2024-08) 起在 Windows 上将 cookie 解密密钥绑定到浏览器进程 (经 IElevator COM 服务授权), 其他进程从 cookie 库里拿到的只有密文; 传统的 DPAPI 用户级解密路线自此失效, 取证工业 (ElcomSoft, 2026-01) 与攻击面研究 (SpecterOps, 2025-08) 双侧确认。现存的「绕过」手法 (进程注入 / hollowing 冒充浏览器) 属窃密木马技术, 本项目不做。[脚注 1]
事实 2 · Chrome 136 的 CDP 限制 — Chrome 136 (2025-05) 起 --remote-debugging-port 在默认 user-data-dir 上被直接忽略 (chromedriver v136 报错原文: 「DevTools remote debugging requires a non-default data directory」)。即: 经 CDP 附着日常浏览器读 cookie 的通道已死, 必须使用独立 --user-data-dir。[脚注 2]
方案原理优点缺点 / 约束结论
A 手工导入站点配置里直接填 cookie 串 (或 cookie 文件路径) 零依赖、零配合成本、最稳; M1 即可用cookie 到期需手动更新 M1 落地
B 专用 profile + CDP引导用户以独立 --user-data-dir 启动浏览器并登录 PT 站一次; auto-qb 经 DevTools 协议 (Storage.getCookies) 读取该 profile 的 cookie 一次登录长期复用; cookie 由浏览器自己解密, 是合法通道; Cloudflare 挑战可在该 profile 里人工过 需用户配合启动/登录; 是「专用浏览器」而非日常浏览器本体 (Chrome 136 限制所迫) M4 落地 (推荐目标形态)
C 浏览器扩展小扩展经 chrome.cookies API 把 PT 站 cookie 推给本地端点 真正复用日常浏览器需开发、安装、维护扩展; 授权面更大备选, 不排期
D 直读 cookie 库读 Chrome/Edge cookie 文件并解密 —Chrome/Edge 被 ABE 挡死 (事实 1), 绕过属恶意技术, 不做; Firefox 的 cookies.sqlite 为明文 SQLite, 运行中复制文件后可读 —— 若用户日常用 Firefox 可作为 B 的平替, M0 验证 否决 (Firefox 待验证)

配套细节

  • UA 一致性: 默认使用与 cookie 同源的浏览器 UA, 避免浏览器 cookie + Python 默认 UA 的指纹不一致引起站点风控注意; 可按站点配置。
  • passkey: 下载链接通常带 passkey 参数, 与 cookie 无关, 属站点配置的一部分。
  • 登录态检测与降级: 响应跳登录页 / 401 / 403 / Cloudflare 挑战页特征 → 判 cookie 失效或被挑战, 该站熔断 + WARNING 通知用户处理, 不重试轰炸。方案 B 的 profile 平时不需要打开, 仅 (重新) 登录时人工使用, 自动化运行期间全程无窗口。
§ 7

频控与配置设计

原则对齐项目黄金法则: 幂等 (配额窗口进 state_file, 重启不重置, 重放不重复下载)、保守默认 (总开关默认关, 配额默认紧)、fail-fast (所有新键进 validate_config 并同步 config/schema/, 带上下限 —— 呼应 26-09-22 刚入库的取值范围收紧案)。

配置草案

hr_check:                            # 全局 (新增顶层键, 默认整段缺省 = 功能关闭)
  enabled: false                     # 总开关, 默认关 (黄金法则 2)
  min_torrent_interval: "90S"        # 相邻两次 .torrent 下载最小间隔 (站点侧观感的核心)
  max_torrents_per_hour: 20          # 小时配额 (全站合计)
  max_torrents_per_day: 100          # 日配额 (全站合计)
  request_timeout: "20S"             # 单请求超时 (connect 5s 固定, read 用本值)
  failure_threshold: 3               # 连续失败 N 次 → 熔断
  failure_cooldown: "12H"            # 熔断冷却时长
  fetch_window: ""                   # 可选 "HH:MM-HH:MM", 仅该时段访问站点 (跨午夜, 同 notify 语义)
  unknown_policy: hr                 # 索引未覆盖的种子按 hr (保守) | not-hr
  index_retention: "30D"             # 页面快照条目保留时长 (已下载记录 hr_downloaded 不淘汰)
  max_download_retries: 3            # 单个 .torrent 下载失败重试上限, 达到后冷却 (防烧配额)

trackers:
  <site>:
    hr_check:                        # 站点级 (与既有 trackers.<site>.hr 并存)
      mode: partial                  # all = 现状全站 HR | partial = 在线核实 | off
      hr_page_url: "https://…/hr.php"
      torrent_url_pattern: "https://…/download.php?id={id}&passkey=…"
      cookie: ""                     # 方案 A; 或 cookie_file 指向文件
      user_agent: ""                 # 缺省 = 常见浏览器 UA
      refresh_interval: "12H"        # HR 页抓取周期
      max_pages_per_refresh: 5       # 单次刷新最多翻页数 (翻页本身也限频)

频控执行要点

机制设计
间隔 + 抖动min_torrent_interval 基础上 ±25% 抖动, 避免机器人式节拍; HR 页翻页共用同一间隔但可独立更慢
两级配额小时/天配额窗口记 state (hour_window / day_counts), 到顶即静默等下一窗口, 不报错
失败退避与熔断429/5xx 按 Retry-After 或指数退避; 连续失败达阈值 → 该站熔断至 failure_cooldown, 期间零请求
去重只下载「页面上有、索引里没有」的种子 id (state 去重); 页面刷新本身受 refresh_interval 限制
站点隔离频控按站点独立计数; 一个站点熔断不占用、不拖累其它站点
落盘时机频控写点与 skip_check_day 同级对待: 写点即时落盘 (重放代价最高), 其余靠周期落盘兜底
§ 8

后台执行与线程模型

硬约束 (taskqueue 既有约定): 主循环线程是唯一修改任务队列与 state_file 的线程, 全程无锁; 任何新功能必须维持这个假设。站点请求耗时不可控 (1s ~ 超时 20s), 与 2s tick 放在一起必须二选一:

方案做法评价
甲 · 主循环内联全局任务 handler 里直接发 HTTP, 单轮预算 1 个请求 + 短超时实现最简; 代价: 最坏情况该 tick 停 ~20s, 2s 节拍的系统会有可感卡顿, 同步线一起被拖住
乙 · 取数线程 + 令牌 (推荐)常驻 fetcher 线程只做 HTTP + 解析; 主循环按频控发「许可令牌」(command queue), fetcher 回吐结果 (result queue); 主循环 hr_check 任务每 tick 收结果 → 写 state → 按频控决定是否发新令牌真后台, 主循环零阻塞; 先例充分 (Web 线程 post_command / consume_commands 同款模式); fetcher 永不触碰 store / 队列 / state_file, 单一写线程假设完好

补充: 取数线程内的解析 (bencode / HTML) 同样是纯 CPU 短任务, 放线程内可让主循环完全免于站点页面大小的波动。

§ 9

判定语义收口

TorrentRecord 新增「HR 身份解析」: 站点 hr_check.mode = partial 时, 先按 infohash 查 state.hr_index[site] 决定该种子是否受 HR 管束, 再进入既有 check_hr_condition / check_hr_satisfied 逻辑; 站点 mode = all 保持现状, off 则完全不按 HR 对待。

情形判定
索引命中 (页面列出过)受 HR 管束, 参数用站点 hr 配置; 若 HR 页本身给出要求做种时长/分享率且 M0 确认可抓, 则逐种覆盖站点配置, 语义更准
索引未命中按 unknown_policy (默认 hr 保守: 宁可多保护) —— 首次成功刷新之前整站按 HR, 行为与现状「全站 HR」一致, 无回退风险
索引过期 (超 refresh_interval × 2 未刷新)视为未覆盖, 回落 unknown_policy; 恢复刷新后自动收敛
功能关闭 / 非 partial 站点完全走现状逻辑, 行为零变化

四个消费点 (打标 / 视图 / 规则条件 / 表达式) 与辅种排除全部零改动 —— 它们本来就只调 TorrentRecord 两个方法。这是本方案在现有架构里改造面最小的根本原因。另注意 check_hr_condition 现有的「下载满即触发」兜底与「downloaded=0 纯辅种不触发」边界在 partial 站点下语义不变: 索引只回答「是否受管束」, 触发时机仍由下载量决定。

查询键是(站点, infohash): 同一内容辅种到多个站点时, 各站 HR 身份彼此独立 (tid 同理不跨站混用) —— 站点维度来自种子既有的 tracker_conf 匹配, 无需新机制。页面给的进度字段 (还需做种时间 / 剩余达标时间 / 分享率) 是站点侧的定期快照, 判定仍以 qB 本地实时值为准 (与现有语义一致); 两套值天然互补 —— 本地值实时但会被重加清零, 站点值滞后但跨重加连续, 差异本身就是排查信息。

索引的反应式本性 — HR 页列出的是「当前账号已下载且受 HR 约束」的种子, 所以索引天然滞后: 刚下载的种子要等下一次页面刷新才现身。默认 unknown_policy=hr 正是为这段滞后兜底; 若用户接受把未核实种子当非 HR, 可配 not-hr, 但需自担漏管风险 (配置项描述里写明)。

§ 13

开放问题 (待拍板)

已解决 (2026-09-22 用户确认): HR 统计页行字段 = HR 编号 / 种子名称 / 上传量 / 下载量 / 分享率 / 还需做种时间 / 完成时间 / 剩余达标时间, tid 站点内唯一、跨站不混用 —— 已纳入 §4 / §5 / §9; 原开放问题「页面是否给出要求值」不再开放。

  1. 首批站点: 先接哪 1–2 个站? (决定 adapter 顺序与 fixture 来源)
  2. 频度默认值: 90S 间隔 / 每小时 20 个 / 每天 100 个的默认配额是否符合你对目标站点容忍度的判断? (只会更紧, 不会更松)
  3. unknown_policy 默认值: 未核实种子默认按 HR 保守处理 (首刷前整站按 HR, 等同现状) —— 是否接受? 若要默认 not-hr 需明确自担漏管风险。
  4. cookie 首发路径: M1 先用手工导入 (配置里填 cookie), M4 再做专用 profile + CDP 自动化 —— 分期是否可接受? 若日常浏览器是 Firefox, 可把 cookies.sqlite 路线提前验证。
  5. 进度字段的用途边界: 还需做种时间 / 剩余达标时间本期只做「展示 + 交叉核对」, 不进判定; 是否要顺带透出到 WEB UI HR 列或规则条件 (如剩余达标时间阈值)? 默认: 本期不做, 列为后续扩展。
