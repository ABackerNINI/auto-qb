§ 1

背景与现状模型

现有 HR 能力是站点级静态配置: trackers.<site>.hr 一旦配置 (required_seeding_time 必填, 另有 required_share_ratio / extra_seeding_time / condition), 该站点的所有种子一律按 HR 管束。判定逻辑收口在 TorrentRecord 的两个方法上:

  • check_hr_condition() — 是否「触发」HR (下载比例 / 下载量达到 condition, 或下载满); 兼作辅种排除依据;
  • check_hr_satisfied() — 触发之后, 做种时长达标或分享率达标即视为满足。

全部消费点都经这两个方法, 共四处: maintenance 打 HR 标签/分类 (mixins/tags.py _add_hr_tag_or_category)、WEB UI 的 HR 展示字段 (webui/views.py _hr_view_fields)、规则条件 hr (rules/conditions.py, modes condition-met / condition-not-met / satisfied)、表达式变量 tor.hr_condition_met / tor.hr_satisfied (rules/expr/env.py)。

问题: 部分种子 HR 站点上的两难

部分站点实行部分种子 HR 策略: 同一站点的种子只有一部分受 HR 约束, 且下载时站点不提供可机读的逐种标记, 只有「HR 种子统计页」(通常列出当前账号下受 HR 约束的种子清单)。静态模型在这种站点上只有两个坏选项:

  • 全站按 HR — 过度保护: 全部种子不辅种、全部打 HR 标签, 辅种价值被抹掉;
  • 不配 hr — 漏管: 真正触发 HR 的种子可能被规则正常删除或停做, 带来账号处分风险。

本计划的目标: 让这类站点的 HR 身份逐种子在线核实, 其余站点行为完全不变。

§ 2

可行性结论

总评 · 可行

技术路线成立: 取数 (浏览器扩展代取) → 解析 → 算 infohash → 对账 → 建索引, 每一步都落在项目既有架构里。取数外移之后, 后端不再发起站点请求 ⇒ 原计划的「许可令牌」机制整体作废 —— 取数线程在 v1.5 以新职责回来 (只管 hr 文件与只读视图, 见 §8)。

判定收口是最大的红利: 四个消费点全部经 TorrentRecord 两个方法; 但仍需在 record 上补一个「HR 身份」非快照字段, 且身份解析必须发生在主循环 (Web 线程也会读它, 见 §9) —— 比 v1.1 说的「只改一处收口」多一条边界约束。

cookie 风险整体移除: 手工填写 / 导入 cookie 已否决 (把维护成本转嫁给用户 = 制造新麻烦); 取数改由浏览器扩展在真实浏览器上下文完成 ⇒ cookie 不离开浏览器, 后端零 cookie 依赖 (§6)。新增的风险面是「扩展端点被伪造注入」与「扩展分发维护」, 二者都可机检/可收敛。

判定边界 (v1.4 定稿, 本计划的核心): 把「索引里有没有」升级为三态 —— 受管束 / 已核实不受管束 (安全放行) / 未核实; 并确认站点数据是权威数据: 接入 hr_check 的站点 (partial / all) 的「是否触发 / 是否达标」一律看站点侧, 本地 qB 字段降为兜底与展示 —— 否则转移种子 (A 客户端下载 → B 客户端保种, B 的 downloaded=0 被当辅种) 与多客户端场景会直接漏管。放行只发生在「一次完整成功的刷新」之后且仍在放行有效期内 (verified_ttl 默认 = 刷新周期), 新种子另由新鲜度闸门兜住 —— 首要不漏 HR, 其次让确认为非 HR 的种子真的放行 (§9)。

多实例是常态: 账号级状态 (索引 / 放行 / 已取记录 / 配额账本 / 熔断) 不进 state_file, 而是按站点分文件落在 hr 目录 (本地或共享), 由每站点一把文件锁保护 —— 持锁期间完成「读 → 判有效期 → 必要时抓 → 写 → 释放」全程, 即使代码有 bug 也不可能两个实例同时读/写/抓同一站点; 拿不到锁的实例直接等下一轮。有效期内直接复用别的实例抓到的数据, 并照样记一次配额 (§5)。

账号安全是最大的运营风险: 访问频度必须默认极保守 + 全可配 + 熔断, 这恰是本需求的原始诉求, 设计上优先满足 (§7)。

边界判据 — 若某个站点其实提供了逐种 HR 标记 (详情页/搜索页图标) 或 JSON 接口, 则不需要本计划的「下载种子对比」重路线, adapter 直接读更便宜的来源即可。adapter 接口按「返回 HR 种子列表」抽象, 把这条路留开 (§4), M0 调研优先确认。

§ 4

HR 名单获取 (统计页抓取)

HR 统计页是账号维度的「我的 HR」清单, 天然就是需要核实的范围, 不需要全站扫描 —— 这是整个方案成本可控的前提。页面行字段 (2026-09-22 经用户确认的常见形态):

页面字段用途
HR 编号 (种子编号, tid)站点内唯一 id: 去重、下载 URL、索引主键都落在 (站点, tid) 上; 跨站点绝不混用
种子名称展示与人工核对; 与本地种子的匹配仍以 infohash 为准 (名称不可靠)
上传量 / 下载量 / 分享率站点侧权威 (账号级): 展示 + 达标判定的优先来源; 本地 qB 值降为兜底与交叉核对 (站点字段缺失才回落, WebUI 标注来源) —— 见 §9
还需做种时间距要求做种时长还差多少: 进度参照 + WEB UI 展示
完成时间语义 M0 与数值格式一并确认 (达标完成或下载完成); 已完成条目保留身份记录, 不从索引删除
剩余达标时间距达标/超期的时间余量: 展示与将来规则条件的扩展点

Adapter 抽象

每站点一个 adapter, 接口统一为「给定登录态 + 分页游标, 返回结构化 HR 种子列表」: {torrent_id, name, listed_ts, hr_requirement?} + 是否还有下一页。解析实现按站点隔离:

  • 解析器选型: 标准库 html.parser 子类 (零新依赖, 行为可测) —— 已实证够用: 实验脚本已用栈式树解析 BTSchool myhr.php (含 <td class="embedded"> 包裹表的嵌套), 样张全字段解析正确; 不再考虑引入第三方解析器。
  • 更便宜的来源优先: 若站点有 JSON 接口或逐种标记, adapter 换实现不换接口, 并跳过 §5 的 .torrent 下载成本。

抓取范围 (scope) 与覆盖证明

HR 统计页按状态分档 (BTSchool 形态: ?hrtype=A 考察中 / B 已达标 / C 未达标 / D 已免罪)。只抓 A 会把「已达标」的 HR 种子当成非 HR (身份与 satisfied 标记一起丢), 属漏 HR —— 故默认抓取范围 = A + B + C (D = 明确不受管束, 可配是否抓来展示); 范围写进站点配置 hr_page_scopes, 逐 scope 分页抓完。

覆盖证明 (coverage) 是「安全放行」的唯一依据 —— 每次刷新落一条站点级元数据, 只有它成立, 本次未命中才敢判「不受管束」:

hr_refresh[site] = {
  last_success_ts,                    # 最近一次「完整成功」刷新完成时刻 (新鲜度闸门的比较基准)
  scopes_done: [A,B,C],               # 本次真正抓全的 scope 集合
  pages_fetched, reached_last_page,   # 翻页是否到底 (未到底 = 不完备 ⇒ 不产生放行)
  entry_count, missing_field_rate,    # 解析健康度 (0 条 / 缺失率超阈 = 疑似改版)
  complete: true,                     # 上述全部成立才为 true
  reason: ""                          # 不完备原因 (分页未到底 / scope 失败 / 解析可疑 / 登录失效)
}

改版防护

解析结果做最小字段校验: HTTP 200 但解析出 0 条记录、或必填字段缺失率超阈 → 判定「页面可能改版」, 该站熔断 + WARNING (自动进 notify), 绝不把空结果当真入库 (空结果的错误语义是「该账号没有 HR 种子」, 二者必须可区分)。每站点样本 HTML 脱敏后进测试 fixture, 改版即测试红。

§ 5

种子下载与 infohash 对账

取数 (由扩展代取)

HR 页列出的种子按站点 download_path 拼出相对路径 (典型 /download.php?id={id}), 由扩展在页面上下文请求 —— 登录态与 passkey 由页面自带, 后端不参与, 也不为此保留任何凭据配置 (§6)。二进制以 base64 回传, 后端只做解码 + 算 infohash, 默认不落盘; 若日后定位需要保留原始字节, 一律落 <data_dir>/hr-check/ (运行时数据区, 不进仓库)。

infohash 计算 — 一个必须做对的细节

v1 infohash = sha1 over info dict 的 bencode 原始字节切片, v2 = sha256 同理。实现上不能「decode 再 re-encode」—— 重编码的键序/整数表示可能与原文件不一致, 算出的 infohash 就错了。正确姿势: 自写极小 bencode 解析器时同步记录 info dict 在原文件中的字节偏移, 对原切片做哈希。解析器预计 60 行上下, 纯函数, 强测试覆盖 (往返 + 已知 infohash 向量 + 畸形输入拒绝)。替代方案是引入 bencodepy (代价: 多一个依赖) —— 已定自写: 实验脚本 scripts/hr_fetch_experiment.py 已带钉死向量 (§11「已完成」), 零新依赖。

与 qB 做种库对账

  • v1 种子: qB 的 hash 即 v1 infohash, TorrentStore 现有字段直接可对;
  • v2-only 种子: qB (≥ 4.4) 的 hash 字段本身即 v2 infohash, 同样直接可对;
  • hybrid 种子: 双算双配; infohash_v1 / infohash_v2 已在 torrents/compat.py 的快照扩展字段里 (可选字段, 老版 qB 可能缺失 → 缺失时回落 hash)。

state 模型: (站点, tid) 为主键, infohash 是回填属性

种子编号 (tid) 站点内唯一, 跨站点不混用; 同一内容 (同一 infohash) 辅种到多个站点时, 各站 HR 身份彼此独立 —— 索引一律以 (站点, tid) 为主键, infohash 在下载算出后一次性回填:

hr_index[site][tid] = {              # 页面行的站点侧事实, 每次刷新只更新字段 (不触发取数)
  tid, name,                         # HR 编号 + 种子名称
  lane: A|B|C|D,                     # 档位 (§4 scope): A考察中 / B已达标 / C未达标 / D已免罪
  uploaded, downloaded, ratio,       # 站点侧流量 —— 账号级权威 (§9: partial 站点判定以它为准)
  need_seed_time, done_ts, remain,   # 还需做种时间 / 完成时间 / 剩余达标时间 (账号级; 达标判定依据)
  infohash: "…",                     # 首次取数后回填, 之后不再取
  first_seen, last_seen              # 生命周期 (配合 index_retention 淘汰)
}
hr_downloaded[site][tid] = {ts, infohash, name}   # 已取记录: 「永不重取」的持久凭据
hr_dl_fails[site][tid] = {count, last_ts}         # 取数失败记账, 达上限后冷却
hr_verified[site][infohash] = {      # 已核实「不受管束」 (§9 放行层)
  tid, verified_ts, source,          # source: absent(D 档免罪) | not-listed(完整刷新未列出)
  anchor: {added_on, downloaded, completion_on, progress}   # 本实例下载锚点 (辅助: 提前作废放行)
}
hr_refresh[site] = {…}               # 覆盖证明 (§4): 产生放行结论的前提条件
# ---- 以上全部是「账号级」状态: 与实例数无关, 落在 hr 文件里由实例共享 (见本节末「共享站点数据」) ----

防重复下载三层: ① hr_downloaded 是廉价永久层 (每条仅 tid + infohash + ts + name) —— 页面条目后来消失、翻页遗漏、快照超期淘汰, 只要 (站点, tid) 在里面就绝不重下; ② hr_index 中已有 infohash 的条目, 刷新只更新页面字段; ③ 下载失败按 max_download_retries (默认 3) 计数, 达上限冷却, 不死循环烧配额。淘汰 (index_retention) 只作用于页面快照字段的陈旧条目, 不触碰 hr_downloaded。

放行的有效期 (v1.4, 修正 v1.3 的「永久粘性」): 放行不是一个状态, 而是「最近一次完整核实」的有时效结论 —— 有效期 = min(下一次成功完整刷新, verified_ts + verified_ttl), 默认 verified_ttl = refresh_interval。理由在多客户端下才成立: 账号随时可能在别的客户端下载 (本地一个信号都没有), 发现它的唯一途径就是刷新。通道正常时每轮刷新都会给放行续期、收益照旧; 只有通道长期静默才会回落保守 (已有 channel_silence_warn 告警)。

下载锚点是辅助信号, 不是放行的充分条件: 它只能提前让本实例的放行失效 (本实例二次下载 / 文件被删重下 / 删种重加), 覆盖不到别的客户端。故放行判定 = 「刷新背书 (必需) + 锚点未漂移 (本实例辅助)」。

多实例: 共享站点数据 (带锁访问 · 有效期复用)

多客户端 / 多实例是常态, 「同一账号只在一个实例启用」不现实; 而上面那些状态全部是账号级的 —— 所以它们不进 state_file, 而是落在 hr 专属文件里 (本地目录 <data_dir>/hr/, 或 shared_dir 指向的共享目录), 由实例们共享:

<shared_dir>/hr/<site>.json   # 站点数据: 一个站点一个文件 (index / verified / refresh / 配额账本 / 熔断)
<shared_dir>/hr/<site>.lock   # 每个站点文件一把锁 (filelock): 锁粒度 = 站点
文件内: { schema_version, revision, fetched_at, expires_at, writer:{instance_id, heartbeat}, 站点数据… }
  • 带锁访问 (安全的关键): 取数线程在持锁期间完成「读 → 判有效期 → 必要时抓 → 写 → 释放」全程 —— 连抓取 (分钟级) 也在锁内。这样即使代码有 bug, 也不可能出现两个实例同时读/写/抓同一个站点; 拿不到锁 ⇒ 直接等下一轮 (不排队、不重试轰炸)。锁粒度 = 站点 (一站点一锁): 抓站点 A 不阻塞站点 B, 减小数据更新延迟; 同一站点严格互斥。
  • 有效期 = 「本轮已完成」: 站点文件带 expires_at (= fetched_at + refresh_interval)。持锁实例读到仍在有效期内的数据时: 把它当作本次抓取的数据直接采用, 并照样记一次配额消耗 (按窗口键幂等) ⇒ 该窗口内不会再有第二次抓取。于是「站点访问频率」由数据有效期决定, 与「哪个实例实际抓的」无关。
  • 能力即角色 (v1.7: 推荐都启用): 抓取能力 = 「本实例所在机器上有没有装着扩展的浏览器」—— channel.enabled=true 即本实例可被抓。硬边界是端点只听 127.0.0.1, 而浏览器只能连本机的 loopback ⇒ 跨机器的实例即使配了 channel 也没有本地浏览器可驱动, 只能只读共享数据 (数据过期就保守回落未核实)。
    所以推荐: 凡是本机有浏览器的实例都启用 channel (不再「只留一台」): ① 消掉「唯一能抓的那台退出 ⇒ 抓取能力消失」的单点故障; ② 站点配在哪个实例上, 它就自己能抓 (不必把配置凑到一台); ③ 多通道不会造成双倍访问站点 —— 同站点有锁 + 有效期复用, 谁先拿到锁谁抓, 另一个读到效期内数据直接复用并记一次配额。一个浏览器服务多个实例只需在扩展里配 N 个端点 (名称 / 端口 / token, §6)。
  • 写者心跳自检: 站点文件记 writer:{instance_id, heartbeat}; 若本实例在锁内发现「自己的心跳被别人覆盖」或 revision 回退 ⇒ 判定锁在该共享目录上不生效 ⇒ 告警并退化为单实例只读 (宁可保守, 不可双写)。
  • 合并式写入 (站点内): 站点文件内的读-改-写仍在锁内完成 (只补自己新增的部分, 含「只取缺 infohash 的 tid」); 而跨站点天然无覆盖问题 —— 每个实例只写自己负责的那个站点文件。
  • shared_dir 留空 ⇒ 文件仍走 <data_dir>/hr/, 单实例行为不变 (同一套代码, 只是没人争锁)。
  • 节奏与 tick 解耦 (v1.6): HR 的粒度是小时甚至天 ⇒ 取数线程按自己的定时器 (poll_interval, 默认 1M) 醒来检查「哪个站点过期/需抓」, 不随主循环 tick 跑; 视图只在数据实质变化 (抓取成功 / 熔断进入退出 / 通道状态翻转) 时才抬 revision 并发布 ⇒ 主循环每 tick 只做一次廉价的版本比较, 版本没变就零工作。
    「是否还在有效期内」这类时间敏感判定在读取时现算 (now vs expires_at), 不需要为「时间流逝」重发布。

边界: 共享目录必须支持文件锁且各实例看到同一份文件 (本机 / 同一台 NAS 的 SMB 预期可用; NFS 部分可用; 云同步盘 (OneDrive / 坚果云) 不可用 —— 原子替换与锁都不可靠)。filelock 已是项目直接依赖, infra/locking.py::SingleInstanceLock 就是可抄的样板 (句柄随进程退出自动释放 ⇒ 进程被杀不会留下死锁)。

判定反查: TorrentRecord 按 (站点, infohash) 查三态 —— infohash → tid 的反向映射由取数线程在发布只读视图时就建好 (站点文件只存 tid 主键, 不存双份)。索引不只服务当前库: 受管束 → 打 HR 标签/分类并纳入辅种排除; 安全放行 → 不排除辅种、不打标; 未核实 → 走 unknown_policy (§9)。

§ 6

取数通道: 浏览器扩展 (否决手工 cookie)

取数是全链路里唯一必须「以你的登录态访问站点」的一步。先给结论: 通道选浏览器扩展 —— 它是唯一既能复用日常浏览器登录态、又让 cookie 明文全程不离开浏览器的方案; 后端因此彻底不需要知道 cookie, v1.1 的 cookie 配置项与 cookie 失效风险管理一并移除。

已否决 · 手工填写 / 导入 cookie (2026-09-24 用户否决) —— 把 cookie 的维护 (到期、换设备、被登出、UA 不一致触发风控) 转嫁给用户, 是「制造新的麻烦」; 且 cookie 属长期凭据, 写进 config.yml (git 跟踪文件) 等于把凭据加进仓库。同理否决「直读浏览器 cookie 库」。

下面两条技术墙是「取数通道为什么不能是后端自己发请求」的核心依据:

事实 1 · App-Bound Encryption — Chrome 自 v127 (2024-08) 起在 Windows 上将 cookie 解密密钥绑定到浏览器进程 (经 IElevator COM 服务授权), 其他进程从 cookie 库里拿到的只有密文; 传统的 DPAPI 用户级解密路线自此失效, 取证工业 (ElcomSoft, 2026-01) 与攻击面研究 (SpecterOps, 2025-08) 双侧确认。现存的「绕过」手法 (进程注入 / hollowing 冒充浏览器) 属窃密木马技术, 本项目不做。[脚注 1]
事实 2 · Chrome 136 的 CDP 限制 — Chrome 136 (2025-05) 起 --remote-debugging-port 在默认 user-data-dir 上被直接忽略 (chromedriver v136 报错原文: 「DevTools remote debugging requires a non-default data directory」)。即: 经 CDP 附着日常浏览器读 cookie 的通道已死, 必须使用独立 --user-data-dir。[脚注 2] 即 CDP 路线只能配一个专用 profile —— 需要一次人工登录 + 一个专用浏览器常驻, 相对「装一个扩展」是更重的用户侧成本 (该路线已有可运行的实验实现, 见 §11 备选通道)。
通道原理优点缺点 / 约束结论
扩展 · 哑取数器MV3 扩展在真实浏览器上下文取 HR 页 (渲染后 DOM) 与 .torrent 二进制, 回传本地端点; 扩展不调用 chrome.cookies, 不读不传 cookie 复用日常浏览器登录态; cookie 全程不出浏览器; 后端零 cookie 配置与零 cookie 失效风险; 用户无感 (取数在扩展自己的隐藏窗口里做, 不占用你的窗口) 需装一次扩展 (unpacked / 开发者模式); 浏览器需在运行; 新增本地端点 ⇒ 需鉴权与白名单 (见下「安全边界」) 主选
专用 profile + CDP以独立 --user-data-dir 启动浏览器并人工登录一次; 脚本经 DevTools 协议 (Storage.getCookies) 取 cookie 后自己发请求 无需装扩展; 已有可运行的实验实现 (scripts/hr_fetch_experiment.py --auto-cookie); CF 挑战可在该 profile 里人工过 需专用浏览器常驻 + 一次人工登录; cookie 仍会进后端进程内存 (风险仍在, 只是换了个位置) 备选通道 (接口不变: 仍是「取 HTML/二进制」)
手工导入 cookie配置里直接填 cookie 串 (或 cookie 文件路径) 实现最简维护成本转嫁用户 (到期 / 换设备 / 被登出); 凭据进 git 跟踪的配置文件 否决 (2026-09-24 用户)
直读 cookie 库读 Chrome/Edge/Firefox cookie 文件并解密 —Chrome/Edge 被 ABE 挡死 (事实 1), 绕过属恶意技术, 不做; Firefox 明文库虽可读, 但仍是「后端持有 cookie」, 与本节结论相悖 否决

扩展的两条实现路线: 解析放在哪一侧

两种选项的根本分歧不在「取什么」, 而在「解析归谁」:

  • 路线 1 · 扩展取整页 → 后端解析: 扩展把 HR 页 (渲染后 DOM 或原始 HTML) 与 .torrent 二进制原样回传, 后端做全部解析。
  • 路线 2 · 扩展现场解析 → 后端收结构化数据: 扩展在页面里直接抽字段, 只把 JSON 回传。
维度路线 1 · 后端解析 (推荐)路线 2 · 扩展内解析
扩展代码量极小 (~200 行; 只做「取页/取二进制/回传」, 与站点无关)大 (含站点解析 + 数值容错 + 字段校验; 随站点数线性增长)
站点改版的改动面只改后端 Python: 改完发版即生效, 用户无需动扩展改扩展: 用户需回 chrome://extensions 点 reload / 重装 —— 用户侧摩擦最贵
可测性高: 脱敏 HTML fixture + pytest + 现有守阵直接复用; 实验脚本的解析器可原样搬进 src/低: 解析逻辑在 JS, 项目测试体系用不上; 后端只能靠「扩展回传的样本」事后复现
多站点扩展性天然: 一个代理吃所有站点每站一份解析器
抗改版的发现能力后端可做「200 但 0 条 / 必填字段缺失率」守卫并熔断告警 (§4 已设计)同样可做, 但代码在扩展里; 后端只能被动信任
流量整页 HTML (几十~几百 KB; 可只回传表格所在容器 / gzip)最小 (结构化 JSON, 数十字节/条)
失败可见性后端拿得到原始页面 ⇒ 改版 / 登录失效 / 挑战页一眼可辨后端只收到「空或畸形 JSON」, 排障靠猜
infohash 计算后端纯函数 + 钉死向量 (已在实验脚本验证)若也下沉到扩展 ⇒ 核心算法离开测试面 (WebCrypto 的 SHA-1 支持还不确定), 不推荐
结论 · 路线 1

判据一句话: 最需要频繁修改、最需要自动化验证的那部分 (解析) 必须留在能用 pytest 守住的一侧; 扩展只做它不可替代的事 —— 在真实浏览器上下文里取数。

补一条必要的坦白: 若扩展上商店, 商店版可自动更新, 路线 2 的「用户侧重装」摩擦会被削弱 —— 但「审核/发版周期远慢于改后端」与「解析脱离 pytest/fixture 体系」两条仍在, 结论不变。反过来, 路线 1 的扩展几乎不需要改, 这也意味着上不上商店对本方案几乎不影响。

推荐形态: 哑取数器 + 后端解析

取样上下文取「隐藏窗口里的标签页 DOM 快照」而非 service worker 裸 fetch: 前者天然带完整登录态、能过 Cloudflare 挑战、拿的是渲染后 DOM, 且用户无感 (既不是用户窗口的活动标签, 也不会把窗口抬到前台)。二者都属路线 1 —— 解析仍然后端做。

通道模型 = 拉取式 (扩展按需拉任务, 而非后端主动下发): 扩展定时 (chrome.alarms, 每 1 分钟, v2.6 定版) 问本地端点要任务 → 后端按频控返回「当前可取的清单」(URL + 期望间隔) → 扩展逐个取、回传 → 后端只入队, 主循环消费。好处: 频控单一权威在后端; 熔断时扩展直接拿到空清单; 「浏览器没开」变成可告警的通道静默状态, 而不是后端空转。
❗时序硬约束 (v2.6 实报收口): 轮询周期必须小于后端 channel.request_timeout 的等待窗口 —— 任务只有在窗口内等到下一次轮询才会被取走。v2.6 前按「建议 5 分钟」轮询、后端只等 180s, 每条任务约四成概率直接超时(实测日志:「取 .torrent 失败: 等待浏览器扩展取数超时(180s)」); 空轮询只打本机 loopback 一次 GET, 成本可忽略, 也不会碰到站点。

职责三分: 后端 = 决策 + 唯一写者 (频控 / 索引 / state); 扩展 = 哑取数器 (无策略、无解析、不碰 cookie API); 解析 = 后端纯函数 (钉死向量 + fixture 可测)。

安全边界 (替代原 cookie 风险)

  • 端点鉴权: 仅监听 127.0.0.1, 必须带 token (留空则随机生成并持久化到 data_dir/hr.token, 同 web.token 口径); 无 token → 401 且不写任何 state —— 否则任意网页 JS 都能向 localhost POST 伪造 HR 数据, 进而影响删除/保护决策。
  • CORS 白名单 (纵深防御, 非唯一防线): 优先只放行固定扩展 id (chrome-extension://<id>) —— manifest 写 key 可把 id 固定下来 (unpacked 与打包版一致); 若某形态下 id 定不住, 兜底是放行 chrome-extension://* 但强制 token —— 真正的鉴权是 token, origin 白名单只是第二道。
  • SSRF 白名单: 只接受配置里声明的站点域名与受限路径 ⇒ 端点不会变成「带登录态的任意站代理」。
  • 不可信输入: 收到的 HTML/二进制只解析、不执行、默认不落盘 (调试开关另论)。
  • 凭据面归零: 后端既不接收 cookie, 也不接收 passkey —— 「日志里出现 cookie/passkey」这条风险源整体消失 (本方案的直接收益)。

分发形态与授权代价 (能力与形态无关)

结论先说: 扩展的能力与分发形态无关 —— unpacked (开发者模式加载) / 打包成 .crx 自行安装 / 上架商店, 用的是同一套 manifest 与 API (host_permissions / alarms / scripting / tabs), 区别只在怎么装、怎么更新。两个直接推论:

  • 不需要专用浏览器: 扩展就跑在你日常用的 Chrome/Edge 里 —— 这正是选它的原因; 「专用浏览器」只是 CDP 备选通道的代价 (见上对比表)。
  • 形态只影响两件事: ① 更新方式 (商店/打包版可自动更新; unpacked 需手动 reload) ② 装载摩擦 (unpacked 免上架, 但浏览器启动时对开发者模式扩展有提示、可关; 商店版需开发者账号与审核流程 —— 本期不做, 要用时以官方页面要求为准)。

host_permissions 只列目标站点 + http://127.0.0.1/*, 不给 <all_urls>。推论: 「装一次扩展」是本方案唯一的一次性用户成本, 与打包形态无关; 换来的是「不要专用浏览器、不导出 cookie、不要人工登录」。

待真机验证 (不臆断, 进 M0)

  • 后台标签页是否被站点的「在线时长 / 浏览统计」识别 (低频 + 仅在需要取数时开, 观察即可)。
  • 目标站 download.php 在页面上下文 fetch 是否直接返回二进制 (attachment 头不影响 fetch; 需确认站点不校验 Referer/XHR 头)。
  • passkey 是否已出现在页面上下文 (若在, 由扩展从页面链接/JS 变量取, 不进配置)。
  • Cloudflare 挑战在后台标签页里是否需人工过。
  • 目标站 HR 页的 scope 全集与各档语义 (哪些档算受管束; 例: BTSchool 的 A/B/C 受管、D 不受管), 以及分页到底的判据。
  • 扩展形态与 id 固定: 确认 unpacked 与打包版 ID 一致 (预期同一套 API, 只需验证 key 写法)。

配套细节

  • UA 一致性: 无需配置 —— 请求由浏览器自己发, UA 与登录态天然同源 (v1.1 的 user_agent 配置项随之删除)。
  • passkey: 不再进配置 (见上); 由扩展在页面上下文补齐下载参数。
  • 登录态检测与降级: 后端拿到的页面命中登录页 / 401 / 403 / Cloudflare 挑战页特征 → 该站熔断 + WARNING 通知用户处理, 不重试轰炸; 通道连续静默 (浏览器长期未开) 同样告警。
  • 多实例下的归属 (v1.7): 扩展开在哪个浏览器, 就服务于哪些实例 —— 扩展侧配实例端点列表 ([{name, endpoint, token}]), chrome.alarms 逐个拉任务 ⇒ 一个浏览器可同时服务同机的多个实例 (各自不同端口 + 各自 token); 而跨机器的实例没有本地浏览器可连 (端点只听 loopback) ⇒ 那台只能只读共享数据。
    推荐每台有浏览器的实例都启用 channel: 多通道不会双倍访问站点 (同站点靠锁 + 有效期复用), 却消掉了「只有一台能抓」的单点故障; 扩展向未启用通道的实例拉清单会拿到 401 / 空, 属正常路径, 不重试。
§ 7

频控与配置设计

原则对齐项目黄金法则: 幂等 (配额窗口进 state_file, 重启不重置, 重放不重复下载)、保守默认 (总开关默认关, 配额默认紧)、fail-fast (所有新键进 validate_config 并同步 config/schema/, 带上下限 —— 呼应 26-09-22 刚入库的取值范围收紧案)。

§ 9

判定语义收口

站点配了 hr_check 段 (mode: all | partial) 时, 先按 (站点, infohash) 解析出三态之一 —— 受管束 / 已核实不受管束 / 未核实 —— 再进入既有 check_hr_condition / check_hr_satisfied 逻辑; off 则完全不按 HR 对待。站点侧数据是权威 (v1.4): 「是否触发 / 是否达标」一律看站点侧, 本地 qB 字段只作降级与展示; 三态数据由取数线程发布的只读视图提供 (§8)。

「纯辅种不触发」是已知缺口, v1.5 全面修掉 —— 现有 check_hr_condition 用本地 downloaded 近似账号级义务, 于是把两类东西混为一谈:
① 真辅种 (从未下载过该 tid) → 站点侧确实无 HR 义务 ⇒ 现状「不触发」结论是对的, 但那只是碰巧对; 现在由「清单未命中 ⇒ 安全放行」给出有依据的同一结论;
② 转移 / 重加 / 换客户端后的保种副本 (本地 downloaded=0, 但账号欠着 HR) → 现状「不触发」= 漏管。
⇒ 结论: 非 partial 站点也纳入该体系 —— mode: all 的语义从「全站按 HR + 本地下载量触发」升级为「站点侧驱动 + 未核实默认受管束」; 与 partial 的唯一差别只剩未核实的默认值。前提是该站有可抓的 HR 统计页; 没有的站点只能留在未接入状态 (配 hr 段但不配 hr_check, 保持现状)。
零静默变更: 只有显式配了 hr_check 段的站点才走新语义; 且不要全局改掉 check_hr_condition 的 downloaded 判断 (未接入的站点会静默改行为)。
为什么本地字段不可信 (v1.4 的核心修正) —— PT 里转移种子是常态: A 客户端下载 → 文件搬给 B 客户端保种。
此时 B 的 downloaded = 0 ⇒ 现有 check_hr_condition 的「纯辅种不触发」判定把它当辅种 ⇒ 不打 HR 标签、不纳入保护、规则条件也不命中, 而账号在站点侧确实欠着这个 tid 的 HR —— 直接漏管。
多客户端同理: 本地字段只描述「我管的这一个客户端」, 而 HR 是账号级义务。所以: 站点数据是权威数据, 本地值降级为兜底路径与展示。

三态的定义 (本次收口的边界)

态成立条件后果
受管束 hr该 (站点, infohash) 出现在抓取范围内的清单里 (A 考察中 / B 已达标 / C 未达标); mode: all 站点上未核实也默认受管束这本身就是「触发」 (不再看本地 downloaded): 未达标 ⇒ 打 HR 标签/分类 + 纳入辅种排除; B 档 ⇒ 落 satisfied 分支。本地 downloaded=0 的转移副本同样受管束

「未核实」的四类边界 (穷举)

  1. 从未成功刷新: 站点启用后首刷未完成 (功能刚打开 / 登录态未就绪 / 通道还没跑起来)。
  2. 刷新不完备: 覆盖证明不成立 —— 分页没抓到底 (max_pages_per_refresh 截断)、任一 scope 抓取失败、解析校验未过 (0 条 / 字段缺失率超阈)、登录失效或被挑战。
  3. 新鲜度闸门 (本地近似): 本实例种子的 added_on 晚于 hr_refresh[site].last_success_ts ⇒ 不可能出现在那次清单里, 无从核实 ⇒ 恒按受管束 (不受 unknown_policy 影响)。它只覆盖本实例新增的种子; 别的客户端新下载的种子在本地要么不存在 (无关)、要么 added_on 很老 (闸门不介入) —— 后者只能靠刷新 + verified_ttl 兜。
  4. 身份缺位: 该 tid 的 infohash 还没回填 (取 .torrent 失败 / 冷却中), 或站点维度不可得 (tracker 未匹配上任何配置)。
两个方向上的取舍 (v1.4 修订)

不漏 HR (首要) —— 四重保证: ① unknown_policy 默认 hr; ② 新鲜度闸门 (本实例新种子恒受管束); ③ 不完备刷新不产生新放行; ④ 放行有效期 = 刷新背书 (verified_ttl 默认 = refresh_interval) —— ④ 专门覆盖「账号在别的客户端下载」这条本地看不见的路径。

安全放行 (次要, 但正是做这个功能的目的) —— 放行只由「完整核实过、且不在清单里」产生, 而不是「没看见就放行」; 通道正常时每轮刷新自动续期, 收益不减; 只有通道静默到超期才回落保守。

诚实说明代价: ① unknown_policy=not-hr 等于自愿放弃第①重保证 (②③④仍生效); ② verified_ttl 调大于 refresh_interval 等于自愿放大「别的客户端下载」的漏管窗口 —— 两项都要写进配置项文案。
反过来, 站点侧驱动的达标判定会晚 ≤ 一个刷新周期生效 (站点值滞后): 表现为「已达标仍多挂一会儿 HR 标签」, 属保守方向。

身份判定的落点 (v1.4 定稿) — 判定不能去查 manager.state: TorrentRecord 是纯快照 dataclass, 且 _hr_view_fields 也在 Web 线程被调用 (详情路由 webui/server/routes/torrent_detail.py), 反向依赖 state 会违反「Web 线程不得触碰 store / 队列 / state_file」。
做法: 取数线程把三态做成不可变快照对象并整体替换引用 (项目先例: 搜索索引整体替换引用, Web 线程并发只读安全), record 持有该视图的稳定引用, 读取时现算「三态 + 锚点校验」。
为什么不用 v1.2 设想的「主循环预取写字段 + 置脏」: 锚点漂移 (本实例二次下载 / 转移) 不会置脏, 那种写法要么漏更新、要么得每 tick 全量扫; 现算则零延迟、零置脏, 且天然只读不可变数据。
配置期硬约束 — check_hr_condition() 第一行是 if not self.tracker_conf.hr: return False, 而站点没写 hr 段时 tracker_conf.hr 恒为 None (全局 hr 段只是站点段的字段兜底, 不会凭空生成站点 hr)。故必须在 validate_config 里 fail-fast: 站点配了 hr_check 且 mode != off (partial / all) ⇒ 该站 hr 段必填 (required_seeding_time); 否则整站保护静默失效, 且没有任何报错。
