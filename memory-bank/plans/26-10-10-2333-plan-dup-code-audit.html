01背景与目标

1.1 为什么单独做一轮「重复代码」审查

仓库已有多轮通用 Code Review 与变异测试审计, 但没有一次专门盯「重复 / 同一事实多份表示」。重复代码的问题不在当下会不会出错, 而在后续每一次改动要记住几个地方 —— 它是维护成本与一致性的放大器: 改 A 忘了改 B, 就产生漂移。这正是本次审查的靶心。

已知的零散证据说明这个问题真实存在, 只欠一次系统排查: 详情面板 15 变体骨架重复 (issue 26-10-07-0845)、HrRefreshService._prune_index 与模块级同名函数同体重复 (issue 26-10-02-0441)、颜色令牌族「各套 UI 各声明一处, 改值必须全处同改」(conventions/webui.md 明文纪律) —— 这类「必须记住的成对约束」越多, 维护点越多。

1.2 目标与非目标

项内容
要产出每轮一份重复发现清单 (位置 · 类别 · 分歧点 · 建议收敛形态); 全局一份重构候选排序表
要减少「一个事实的 N 个表示处」数量; 后续改动的跨文件记忆点
非目标不改代码 · 不查缺陷/安全 · 不做性能优化 · 不评价圈复杂度 · 不追求「零重复」
判定原则宁少勿滥 —— 表面相似不算重复 (见 §02 D 类); 不制造过度抽象

1.3 与既有制品的关系

  • 全项目 Code Review (26-10-05-0951 / 报告 26-10-05-1036): 查的是缺陷、安全、边界; 本次查的是结构重复 —— 不同视角, 取并集不重叠。
  • 变异测试审计 (专题 mutation-audit): 管「测试够不够硬」; 本次管「代码要不要合并」, 互不替代。
  • 前端拆分 / 抽屉去重: 已有局部结论的地方只引用不重查, 本次做全仓统账。

02重复口径 (分类词)

每条发现必须落进下面四类之一。分类决定「建议动作」, 也决定这条要不要入池。这是本计划唯一的判定词表, 各轮不得自造。

类名称判据建议动作
A真重复
可提取		 逐字或近逐字重复, 语义完全相同; 典型为样板 (boilerplate)、复制粘贴 提取函数 / 基类 / 装饰器; 收益高、风险低
B分歧重复
已各自演化		 同源但已长出差异, 直接合并会改行为 先钉差异点与回归保护, 再合; 本轮只登记不建议立即合
C同一事实多表示
单点违反		 同一个键面 / 令牌 / 口径 / 枚举 / 文案, 在多处以不同形式存在 收敛为单点 + 派生/生成; 维护成本最高, 优先
D表面相似
不动		 形状像但语义无关, 或为可读性刻意重复 记录后明确判定不动, 防止后续误合并

明确不算重复 (不记或记 D):

  • ≤3 行的惯用式 (如 if x is None: return None);
  • 语义无关的同形结构 (两个不同领域的同名小函数);
  • 测试里刻意的显式重复 (为了让用例自洽可读);
  • 为性能/线程安全刻意内联而不抽公共函数的代码 (需在注释里说明, 否则按 A 记)。

2.1 每条发现的记录字段

位置 (文件:行) · 类别 A/B/C/D · 重复对象 (哪些点) · 分歧点 · 维护风险 · 建议收敛形态 · 预估收益/风险。

03方法与工具

3.1 两段式: 机器提名 → 人工判定

机器负责穷举候选 (它不认识语义), 人负责定性 (机器不懂哪些是刻意重复)。禁止只凭工具报告下结论, 也禁止只凭肉眼漫读 —— 两者都漏。

  1. 提名: 跑重复检测工具拿基线候选; 叠加「结构线索」grep 补齐语义重复 (工具只看字面, 抓不到改写过的同一逻辑)。
  2. 判定: 逐候选打开两侧源码核对, 按 §02 四分类定性, 记分歧点。

3.2 工具 (临时环境, 不改依赖)

Python 侧走 uv run --with 临时环境, 不写进 pyproject; 前端侧用 npx。命令只作参考, 具体参数每轮按噪声调。

# Python: pylint R0801 duplicate-code (逐文件对提名) uv run --with pylint pylint --disable=all --enable=duplicate-code --min-similarity-lines=8 src/auto_qb # 全仓多语言 (python / js / css / html): jscpd (需 Node) npx --yes jscpd -f python,javascript,css,html --min-lines 10 --min-tokens 70 src tests

3.3 结构线索 (grep, 补语义重复)

同一逻辑被改写后工具抓不到, 用「这是同一件事的固有特征」去搜 —— 命中的多个实现点往往就是 C 类。

  • 同一动作的多个实现: os.replace / 临时文件+改名 (原子写)、json.loads+兜底、time.time() 取时钟。
  • 同一契约的多个方向: from_json / to_json、from_dict / to_dict、parse_* / format_*。
  • 同一键面/令牌的多次声明: 配置键名常量、CSS --token、枚举值、中文文案。

05每轮微步骤 (S1–S6)

每一轮都按同一套六步走, 保证可重复、可中断、可交接。执行时另立任务档案, 每轮的 S5/S6 结果回写档案与 activeContext。

S1圈定

列本轮文件清单 + 行数 + 目标符号清单 (预判的重点函数/类), 写进档案; 确认基线 hash。

S2提名 (机器)

跑 §3.2 工具收候选; 叠加 §3.3 结构线索 grep。只收候选, 不下结论; 噪声阈值本轮记下, 供下轮调参。

S3精读 (只读)

逐候选打开两侧源码核对 (禁止只读工具报告); 补齐工具抓不到的语义重复 (改写过的同一逻辑)。

S4判定与记录

按 §02 四分类定性, 填 §2.1 七字段; 对 B 类必须写清分歧点 (这是后续能否安全合并的关键); 对 D 类写一句「为何不动」。

S5归档

本轮发现追加进滚动报告; 可动项按 create-issue skill 入池 (type=refactor) 并在文件里写一句结论 (重复对象 + 建议收敛形态); 回写任务档案与 activeContext 切片。

S6止损

到量即停 (见 §07 上限), 不做任何修复; 向用户报本轮分类计数与待办下一轮。

07停手点与风险

7.1 硬停手点

  • 只审查、不改码 —— 任何发现都不得在本轮顺手重构 (scope-guard; 黄金法则 6)。
  • 单轮上限: 源码 ≤ 4000 行 / 提名组 ≤ 30 —— 到量即停, 余下拆到下一轮。
  • 一轮一面: 不跨轮混读; 每轮结束回写档案, 用户可暂停 / 调整下一轮顺序。
  • B 类只登记: 近似含分歧的重复, 一律不在本轮给「直接合并」结论。

7.2 风险

风险对策
误判 → 过度抽象严守 D 类: 表面相似不动; 每轮 S4 反问「合并后语义会更清楚吗」
工具噪声淹没结论先调 --min-similarity-lines / --min-tokens 到噪声可接受; 工具只提名
大文件读取成本按符号清单局部读, 不整读 (检索纪律); 轮 13/10/22 尤其注意
C 类跨文件难穷举靠 §3.3 结构线索 + 轮 25 统一收口, 不在单轮强求
审查轮与重构轮混淆本计划恒为纯审查; 任何改动需另立 refactor 任务并单独拍板
