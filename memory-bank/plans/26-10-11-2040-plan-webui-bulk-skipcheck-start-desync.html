1摘要与落点总览

报告把症状拆成三条独立缺陷叠加 + 一条加固项：① 跳检收尾不回写快照（必要）；② 批量命令没有真值出口（必要）；③ 前端预测/回滚/收敛三个单点各自是陷阱（必要）；④ _sync_paused_state 用陈旧完成位反推 state（加固）。

方案与之一一对应，六处后端改动 + 三处前端改动，另加三条测试改动（含两条机械守阵）：

2验收判据

每条都可机检（前四条由上表 T2/T3 两条守阵 + 既有用例钉住）：

  1. 跳检成功后，store 里该种子的 state/progress 等于 qB 实时值，不再停留于「跳检前的暂停 0%」；
  2. 批量 pause/resume 走完 consume_commands 后，web.truth_pending 里有该 cmd_id（真值出口存在），且回执由 drain 写；
  3. 前端 _expirePending 的回滚目标读 truthSnapshot，拿不到才退回 op.prev；
  4. 前端 _optimisticSettled 对 resume/pause 用「已离开命令前状态」判据（kind != "paused" / kind == "paused"），与服务端 _truth_landed 逐字同谓词；
  5. 全量测试通过；新增两条守阵在位（删掉任一条的实现即红）。

症状级验收（真机）：多选一批暂停未完成的辅种 → 批量跳检 → 立即批量开始，行状态应直接稳定在「做种」，不再出现「下载 → 已停止」。

36.1 跳检收尾回写真值 止血

改法

ops_mod._skip_readd 在 store.restore_torrent(tor) 之前，对刚确认出现的种子做一次 torrents_info(hash) 直查，把返回的实时字段 apply_delta 到 tor 上，再放回 store；字段有变时置 store.view_changed。

try:
    live = self._ctx.api.torrents_info(torrent_hashes=hash)
except Exception as e:
    logger.warning(f"跳检收尾回写真值失败(跳检本身已成功, 下轮 sync 校准): {e}")
    live = []
if live and tor.apply_delta(live[0]):
    self._ctx.store.view_changed = True
self._ctx.store.restore_torrent(tor)

为什么这么修

  • 跳检是不可逆操作刚生效的决定性时刻，本仓既有纪律要求此时直查真值（pitfalls/backend/effect-confirmation.md），而不是回落到快照；
  • 复用 apply_delta（增量字段写入单点）与 R2 已用的 torrents_info 读法，不新造字段映射；
  • 失败 fail-closed 但不改变跳检结论：种子确已在 qB，字段下轮 sync 也能跟上，只记 warning。这与「复核失败就放弃」的 R2 语义不同 —— 那时还没动手，这时已经动手了。

代价

每次跳检多一次 torrents_info 往返。跳检是天级低频操作（skip_check_day 去重），该代价可忽略。

46.2 批量真值出口：按 action 分流归属 止血

目标：让 bulk_torrents 的 pause/resume 走回与单种完全相同的真值通路。下游 _truth_landed（已按 action 分流）与 _affected_hashes（已展开 keys）无需改动 —— 它们本就是为批量写好的，只是可达性被名单归属切断。

四处落点

#改动
P2抽单点 is_deferred_receipt(cmd, args)：bulk_torrents 且 action in {pause, resume} → False（放行到 drain 的 defer_receipt），其余按 DEFERRED_RECEIPT_COMMANDS 判。
P3加 CMD_ID_COMMANDS = DEFERRED_RECEIPT_COMMANDS | {"bulk_torrents"} —— cmd_id 的传递与「谁写回执」是两件事：pause/resume 回执由 drain 写，但它「部分 hash 缺失」时的 error 回执仍由 handler 写，故 handler 必须拿到 cmd_id。
P4drain 用 P2 的单点判定；并在写回执前加 cmd_id not in self.results 守卫，防 handler 已写的 error 被 drain 的 ok 覆盖。
P5_cmd_bulk_torrents 的 pause/resume 成功分支不再自写 _set_web_result（错误分支照旧）。
P3 是实施期发现的坑：只做 P2/P4/P5 时，pause/resume 会落进 not deferred 分支 ⇒ drain 不传 cmd_id ⇒ handler 写不出 error 回执 ⇒ 反被 drain 的 ok 覆盖。先跑测试才暴露（4 条用例同时红）。修法就是把「传不传 cmd_id」的判据从 deferred 拆出来。

为什么不能一刀切

不能把 bulk_torrents 整条移出 DEFERRED_RECEIPT_COMMANDS：同一个 handler 还扛着 recheck / skip_check / add_torrents，它们的聚合回执（带 results/summary 与跳过/失败计数）必须自写，裸 ok 会盖掉数据位 —— 而本次症状的起点正是 skip_check。

也不在 handler 内自调 self.web.defer_receipt：handler 拿不到 drain 拆出的 timing（wait_ms/exec_ms），自调会丢埋点。判定放回 drain，回执 / 计时 / 真值登记三件事仍归同一单点。

56.3 前端：回滚不打旧值 + 收敛同谓词 止血

三处小改，独立成立：

#改动理由
F1_expirePending 回滚目标：有本轮服务端快照就用它，没有才退回 op.prev。prev 的「最后已知真值」语义只在真值事件刷新过时才成立；批量路径没有真值事件 ⇒ 裸用 prev = 打回点击那一刻的旧状态，这正是本 bug 的直接成因。
F2_snapshotTruth 里顺手 op.prev = { ...op.prev, ...v }。把「prev = 最后已知真值」这条语义在前端本地补上（onTruthEvent 已在真值到达时这么刷）。快照若仍是命令前的值，刷了等于没刷，无害。
F3_optimisticSettled 按 op.action 判：resume kind != "paused" / pause kind == "paused"。resume 的落地态有 downloading/seeding/checking 等多种，前端预测只猜得出两种；要求「服务端 kind 严格等于预测值」会让预测偏一格的动作永远收敛不了 —— 服务端 _truth_landed 早就是宽谓词，两端必须同源。
调用顺序已核实：polling.refresh 里 applyStateRows → _snapshotTruth → _expirePending → reapplyPending —— F1 依赖的 truthSnapshot 在 _expirePending 之前就已就绪。

66.4 加固与机械守阵 加固

P6 · 完成位联合判据

_sync_paused_state 原先只看 state_enum.is_complete（state 后缀 UP）。一份陈旧的 pausedDL 记录会把「已完成」写成 stalledDL。改为 is_complete or progress >= 1.0。

刻意不并 amount_left == 0：TorrentRecord.amount_left 的 slot 默认值就是 0，未同步的记录会被误判成「已完成」（假阳性）。progress 默认 0.0，无此问题。

T1 · 替身保真

FakeClient.torrents_add 在 is_skip_checking=True 时把新种子造成 progress=1.0（qB 跳过校验 = 全部块视为有效）。原替身恒 progress=0.0，使「跳检后快照仍说 0%」这条脱节在单测里天然不可见。

连锁（已按保真处理，非回退）：替身保真后，「跳检成功 ⇒ 种子已完成」变成事实 ⇒ 第二次跳检会先被 G3「种子已完成」/ 规则侧决策链 0 拦下，走不到 dedup（跨规则同日去重）闸门。真机同理。
处理：test_ops_skip_check_day_shared_across_sources 与 test_checking_skip_dedup_across_rules 在第二次跳检前把进度还原为「未完成」，以单独验证去重闸门本身（并注明原因）。
dedup 闸门被 G3 遮蔽属闸门顺序问题，超出本方案范围 —— 另立 issue 处置，本方案不动闸门顺序。

T2 / T3 · 两条机械守阵

  • T2（后端）：按前端乐观白名单遍历，断言每个动作都「不在延迟回执族 + 走完 drain 后登记待推真值 + 回执由 drain 写」；反向断言非乐观动作保持延迟回执族。新增乐观动作时必须同步 —— 这就是「白名单加了新动作、真值出口没跟上」的机械守卫。
  • T3（前端静态）：读 commands.js 源码断言 F1/F2/F3 三条写法在位（回滚读 truthSnapshot、op.prev 保鲜、_optimisticSettled 的 action 分支）。任一处被改回旧写法即红。

7被否的替代方案

方案否决理由
把批量拆成 N 次单种调用复用单种机制的实质是共用真值通路，不是共用调用次数 —— bulk 与单种底层是同一个 QbApi.torrents_resume。拆开会带来 N 次命令队列往返 + N 次主循环 tick，无任何额外正确性。
bulk_torrents 整条移出延迟回执族会害了 recheck / skip_check / add_torrents 的聚合回执（见 §4）。
handler 内自调 defer_receipt丢 drain 的 timing 埋点；判定与消费会被拆成两份（见 §4）。
兜底回滚只删 pendingOps 不回值rid 门控下服务端版本未变时不回传数组、行对象不被替换 ⇒ 上一轮贴的假值会一直留在行上（_expirePending 注释里记着的 hang 实测）。必须显式回一个值。
把 dedup 闸门提到 G3 之前闸门顺序是设计决策，超出本方案范围（应另立 issue 讨论）；本方案只保证修复不改变既有闸门语义。
