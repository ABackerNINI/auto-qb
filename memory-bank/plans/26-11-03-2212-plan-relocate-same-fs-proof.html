整组迁移同盘证明误拒：根因与修复计划

把「3 成员组跨盘移动必失败」拆成可判定的因果链：真正拦人的不是链接能力，而是用 qB 默认保存路径的剩余空间去证明「同一块盘」的代理判据。本计划只做分析与规划，不改 src/。

§01目标与设计原则

目标：让「qB 与 auto-qb 同机、但 qB 默认保存路径不在这两块盘上」的多成员组能完成跨卷迁移；同时保证真正的远程 / 跨 OS 容器场景仍被拒绝，且拒绝时一条消息就能说清是哪一种情况、差多少。

不变量（本轮不动）

  • 单成员组继续走 FORM_DIRECT：qB 自己搬字节，不建链接，不受本闸门影响。
  • 多成员组仍必须建链接；链接必须 qB 可读，这是安全底线，不能为了通过而取消。
  • 保守默认：新的「同机共享」声明默认关闭；CI / 单机用户不配置时行为不变。
  • 不引入 auto-qb 自己复制数据的新形态；字节搬运仍由 qB 完成。
  • 新增配置键必须同步 config.validate_config 与 config/schema.py（黄金法则 4）。

做到什么程度算成

  • 现场同类 3 成员组在 auto 或显式声明后可完成；拒绝时消息包含实测数字与唯一归因。
  • 远程 qB / 跨 OS 容器仍 100% 拒绝；无法判定时仍 fail-fast。
  • 单测覆盖判据分支；真机在环境 1 用伪造种子完成跨卷正反例。

2.2 为什么 3 成员组必失败、单成员组为何可过

  1. 组里有 3 个种子 ⇒ multi=True（units.py:420）。多成员组不能由 qB 一次性搬：只能让一个 mover 搬字节，其余成员靠 src 上的链接指向 dst 继续做种（exec.py:171-203）。所以必须证明 qB 能读到本机在 src / dst 上看到的文件系统。
  2. 当前「同盘证明」拿 server_state.free_space_on_disk 与本机 src / dst 的剩余空间比。问题是：qB 的这个字段报的是它默认保存路径那块卷，不是本次迁移的源卷或目标卷（代码注释自述，relocate_plan.py:256-259；RM04 真机基线实测同口径）。
  3. 因此只要 qB 默认保存路径落在第三块盘（既不是 src 也不是 dst），两侧比较都不吻合 ⇒ proved=False ⇒ GATE_SAME_FS 硬拦。同一台机器上也会误拒，这是假阴性。
  4. 单成员组走 FORM_DIRECT（units.py:31、184、454）：qB 自己搬，没有链接，也就不需要「qB 看得见」的证明，所以它「能过」不是因为盘证明通过了，而是这个闸门根本不适用。不能拿「单成员能搬」推断盘没问题。
  5. remote=not proved（plan.py:265）还会把同一个假阴性传染给平台能力判定（alias_fs.py:656-659），即使链接能力完全可用也会被记为「远程 qB 无共享文件系统」。

§06grilling：批判性压测

G1 · 剩余空间比对是否本身就是错判据？

质疑：它比较的是「qB 默认保存路径卷」与「本次 src/dst」，不是同一个对象；同容量两块盘剩余相近时会假阳性，默认路径在第三块盘时又假阴性。这不是身份证明，是相关性猜测。

证据：plan.py:256-259 注释自述字段语义；tolerance = max(1GiB, local_free × 2%)（units.py:713）；现有单测只覆盖「值相等 / 差数量级」，未覆盖「两块 20TB 盘剩余都在 2% 带内」（tests/test_relocate_units.py:519-525）。

结论：是错判据，不能作为 auto 的唯一放行依据。需用户拍板 → D2 / D3

G2 · 硬链接跨卷必然失败，是否被误当成盘错位？

质疑：是不是产品在跨卷时尝试硬链接、失败后误报成「盘不一致」？

证据：file_alias_kind 在 same_volume=False 时直接返回 symlink，硬链接只作为同卷首选（alias_fs.py:131-148）。跨卷 rename 也不会被尝试：qB 自己搬字节，剩下的靠链接。用户看到的是 GATE_SAME_FS 的文案，不是链接创建错误。

结论：不是。硬链接跨卷失败不是本次根因；但在同机 + 无 symlink 权限时，真正的拦人点会是 GATE_PLATFORM，而它可能被第一条 reason 盖住。与 G6 联动

G3 · 单成员组可迁移，是否只是因为不需要链接？

质疑：「单成员能搬」是否证明盘其实是好的？

证据：单成员走 FORM_DIRECT（units.py:31、184、454），证明失败时只进 notes（units.py:500-503），因此它根本不经过同盘证明与链接能力。它的成功只说明 qB 能自己搬，不能说明 qB 与本机共享文件系统。

结论：是。不能用单成员成功反推盘没问题；反过来，多成员失败也不能说明盘真的错位。已验证

G4 · qB 容器路径 vs 本机路径，是否应由用户显式声明？

质疑：fs.path_map 只告诉 auto-qb 自己怎么读盘，不告诉 qB 怎么读；让用户声明「共享同一文件系统」是否把安全责任外推？

证据：file_access.py:5、301、312-325：path_map 是 syscall 边界翻译，命中失败就 raise；它没有任何 qB 侧语义。平台探测能识别跨 OS 容器（alias_fs.py:660-664），但识别不了「同 OS 容器只挂载了部分卷」。

结论：需要显式声明，但必须默认关、需确认、可审计，并配合移动后校验。否则无解。需用户拍板 → D1 / D3

G5 · 降级复制是否会破坏做种连续性 / 进度？

质疑：复制 + 替换看起来能绕开链接，为什么不直接做？

证据：复制期间组内成员必须暂停；复制完成前 dst 占双倍空间；之后只能靠 qB 重校验把进度拉回；若 qB 真远程，本机连 dst 都写不到。它把故障窗口从「一次预检」放大到「整段复制时间」。

结论：会。本轮拒绝；如未来做，必须是显式慢速选项，不能成为自动降级。需用户拍板 → D6

G6 · 报错文案是否在掩盖真实原因？

质疑：一句话同时指控「远程 qB」「容器路径错位」「本机源卷」，却不给任何数字，用户无法判断。

证据：文案在 units.py:496-497；WebUI 只取第一条 reason（commands_torrents.py:403-411）；GATE_SAME_FS 在 GATE_PLATFORM 之前（units.py:495 vs 505），所以平台失败也会被这条盖住。更糟的是 remote=not proved 会把假阴性写成「远程 qB」。

结论：是。P1 + P2 是所有方案的前置，否则无法验证修复是否真的命中。已验证

G7 · 若 qB 默认卷是第三块盘，auto 是否永远误拒？

质疑：同机三块盘（默认 D:、源 E:、目标 F:）在今天的 auto 下是否无解？

证据：proved 只与 src/dst 比较（plan.py:260）；两侧都不吻合 ⇒ false ⇒ 多成员硬拦。没有其他同机证据入口。

结论：是，今天无解。这正是现场最可能的形态之一，也是 A3 存在的理由。需用户拍板 → D1

G8 · 2% / 1GiB 容差是否会把不同盘判成同盘？

质疑：两台同型号 20TB 盘、剩余都在 10TB 左右时，2% 带 = 200GB，足以让不同盘落进带内。

证据：units.py:713；注释称「真不同盘通常差数量级」，但同构车队不成立。假阳性会让 qB 读不到链接却照样放行。

结论：会。容差只能用于「同机抖动」，不能用于「跨盘身份」；这也支持 G1 的结论。需用户拍板 → D2

G9 · 放宽闸门后，如何独立验证 qB 真能读链接？

质疑：assume_shared 只是用户声明，产品没有 qB 侧的读验证；如果声明错了，链接建好但 qB 读不到，做种会静默坏掉。

证据：_build_links 只验证本进程建链成功（exec.py:192-203）；reconcile 只看 qB 的搬迁相位（exec.py:365-411），没有「qB 读到文件」的探针。qB 侧唯一的间接反馈是 progress / state 变化，且要等它自己重校验或读写。

结论：当前没有独立验证。必须在计划里定义：声明开启后，移动完成时对非 mover 成员做一次 progress/state 采样，发现 progress 掉到 0 或 error 就告警并给出回滚动作；或者把该风险写进用户确认文案。选哪种需用户拍板 → D1。

G10 · 诊断信息是否过度暴露？

质疑：打印 qB 默认路径 / 盘符 / 剩余空间是否泄露隐私？

证据：这些数据只进本机 WebUI 与 localhost API 的响应；现有日志已含 save_path。

结论：可接受。只需确保诊断不把 token / qB 凭据带出；free_space_on_disk 等字段与既有日志同级。低风险

G11 · 是否应先拿到现场事实，再决定修哪一层？

质疑：现在直接排期 P3 可能修错层（如果用户其实是真远程/跨 OS 容器）。

证据：2.4 的三类候选在文案上完全同形；本机只能证明「-1 分支存在」，不能证明用户属于哪类。

结论：是的。P1 既是修复也是取证；D7 的事实最好在 P3 编码前补齐。需用户拍板 → D7
