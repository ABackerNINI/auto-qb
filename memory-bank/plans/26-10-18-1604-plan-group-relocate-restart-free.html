§01目标与设计原则

为什么做：qB 的 setLocation 在「目标已含同名数据」时会走 need_full_check ⇒ force_recheck（storage_utils.cpp:123-127 → torrent.cpp:9381），进度清零 + 全量校验。辅种组 N 个成员共享同一份物理文件，第 2..N 个成员搬到同一目标必然中招 —— 这正是「整组迁移」在 qB 侧没有解的原因。

做到什么程度算成：

  1. 三种现实情形（独占内容根 / 组共享子目录 / 单文件或平铺布局）各有明确且自解释的行为，不存在「点了没反应」或「悄悄换了一种语义」。
  2. 开关关闭时，三个入口的调用序列与今天逐字节相同（守阵测试钉住）。
  3. 开关开启时，迁移后组不裂、进度与统计不清零、qB 侧零校验；不可别名时明确拒绝并给出路。
  4. 多平台是能力矩阵，不是平台白名单：Windows / macOS / Linux 宿主与 Linux 容器都在支持面内（见 §3.3）；只有「物理上无法建出 qB 能读的链接」的组合才拒绝，且文案必须说明为什么不可能。
  5. 迁移只影响被点名的种子，不影响未来：默认走逐文件链接，未来存进同一目录的新种子照常落原盘；只有用户显式确认「这个目录以后也不会再放别的」时才用目录别名（§3.2）。且任何落进别名目录的新种子都必须被告知并二次确认（§3.6.1）—— 盘类型不同（HDD 不适合乱序下载），静默把下载改到另一块盘是不可接受的。
  6. 真机单种子端到端跑通「迁移 → 别名 → 收尾(重启)」，并验证失败路径只做零成本动作、撤销搬回前先显示成本。

不变量（违反即视为实现错误）：

  • 不自行搬字节：所有数据移动都由 qB 的 setLocation 完成。auto-qb 只建/删别名、对账、轮询。
  • 删别名只在「qB 确认不在运行」时：qB 可能持有打开的文件句柄，运行中删链接不会关句柄，它会按旧句柄继续报做种（假种）。三证齐全（进程不存在 + 端口连不上 + 稳定窗口）才动手。
  • 单一写者：state.json 只由主循环线程写；guardian 只写自己的 journal 文件，auto-qb 读后合并。两个进程永不写同一份文件。
  • 保守默认：开关默认关；所有不可判定（能力探测失败、路径不可判定、容器 OS 不一致）一律拒绝而非猜测。
  • 失败不自动搬数据：搬迁失败时 auto-qb 只做零成本的动作（删已建链接、落账、告知），绝不自动把数据搬回 —— 搬回是又一次全量复制，成本可能比失败本身还高，且用户未必想回滚。回滚/撤销只作为用户显式选项出现，并先显示成本（数据量、目标卷、预计耗时）。
  • 别名是「作用域」不是「快照」：别名存在期间新加入同物理目录的种子自动落进同一作用域，收尾集合按作用域动态计算，不是创建时那份固定 hash 列表。
  • 默认不动目录结构：只有文件数达到阈值且目录专属、用户确认时，才把整个目录变成链接；「整目录（save_path 级）别名」不提供。

§02现状与痛点

2.1 三个入口，一个收口

入口位置现状
WebUI 单个webui/commands.py::_cmd_set_torrent_location直接 api.torrents_set_location([hash], location)
WebUI 批量/组级commands.py::_BULK_ACTIONS["location"]同上，一次传全部 hashes
规则 move_torules/actions/transfer.py::MoveToAction.execute同上，单 hash

三处都直接打 qB，没有任何前置闸门：不检查是否已完成、是否暂停、目标是否已有数据、空间是否够。目标已有数据时就是全量校验。

2.2 组键含 save_path ⇒ 裂组

group_key_of(save_path, file_map) 的第一元是词法 save_path。只要有一个成员被搬走（save_path 变 T），它就与其余成员（save_path 仍 S）分属两个组；而跨组文件交叉检测会对 save_path 做 realpath_lexical，把两组认成「不同组指向同一物理文件」，一旦任一侧有下载方就警告 + 暂停。所以「qB 搬第一个」必须配组判定改造，否则界面与告警都会裂。

2.3 搬迁窗口会误触缺文件联动

我们主动暂停组内种子会命中 grouping 的「上传转暂停」状态转移 ⇒ 缺文件扫描 ⇒ 此刻文件正在被 qB 搬走 ⇒ 误判缺失 ⇒ 整组暂停 + 打 MISSING 标签。必须引入 relocating 登记（形态同 store.own_write_pending）让扫描与跳检闸门跳过。

3.1 谁搬、有没有别名、组裂不裂

3.2 别名形态：先看文件数，再看目录

旧方案「父目录独占 ⇒ 整目录别名」被否掉了：一个通用目录今天只有一个种子，不代表明天也只放这一个 —— 整目录别名会把以后所有存进该目录的种子静默重定向到新盘，爆炸半径远超「迁移这一个种子」的授权范围。同一部剧的分集种子共用一个子目录是常态，更不能让「迁第 1 集」变成「以后每一集都落新盘」。

改为按组内文件数分流的纯函数 relocate_units.plan(save_path, files, threshold, hard_max)。注意 F 是「一个组（同内容）的文件数」，不是整个多选集合的并集 —— 一次多选里若含多个组，必须先按组拆开逐组处理：单成员组直接搬（不建链接），多成员组搬一个 + 建链接（详见 §3.2.1）。

条件形态未来种子影响成本
F < threshold（默认 8）逐文件链接：S 侧按原目录结构重建真实目录树，每个文件一条链接指向 T 对应路径零影响 —— 新种子按自己的名字落原盘真实目录F 条链接（1~7 条，可忽略）
F ≥ threshold 且内容根是独立子目录，且该目录恰好只含本组文件（无杂项、无组外种子）目录别名（junction / dir symlink），必须显式确认「该目录以后新增的种子也会落到新位置」存进同目录的新种子会落 T1 条链接
F ≥ threshold 但内容根 = save_path 本身（平铺 / NoSubfolder）逐文件链接（整目录别名不提供）零影响F 条链接
F ≥ threshold 但目录不专属（有组外种子的文件 / 有杂项）逐文件链接（只链本组自己的文件，不动别人的）零影响F 条链接
F > hard_max_links（默认 2000）且不能用目录别名拒绝—避免链接爆炸

阈值只对多成员组生效：单成员组（只有 1 个种子引用这些文件）根本不需要别名 —— qB 搬完 save_path 就是 T，没有第二个种子还指着 S。所以「F ≥ 阈值」永远不该让单成员组去建链接或目录别名。

目录别名的额外前提（硬条件）：qB 只搬 mover 自己那个种子的文件，所以只有当「该组的文件集 == 整个内容根的全部内容」时，mover 搬完目录才会空、链接才建得出来。若目录里还有别的种子的文件（分集场景），mover 搬完目录仍在 ⇒ 目录别名不可用，只能逐文件链接。这条比阈值更硬：阈值决定「愿不愿意用目录别名」，这条决定「能不能用」。

为什么是文件数而不是目录独占：文件数近似「这个目录是不是一个独立发布包」—— 单集/单部电影 1~3 个文件，季包 10~30 个。少量文件走链接，既没有未来种子的重定向，也不需要判断目录归谁；文件多的包通常独占目录，才值得把目录整体链走，且仍然要用户点头。

链接能力阶梯：目录别名 = Windows junction（免权限）→ POSIX os.symlink（免权限）→ Windows 目录 symlink（开发者模式或 UAC helper）；逐文件链接 = POSIX os.symlink → Windows 同卷 os.link 硬链接（免权限）→ Windows 跨卷 os.symlink（开发者模式或 UAC helper）。每一档都不可用 ⇒ 拒绝，文案给出路（提权运行 / 换同卷目标）。

能力校正（先于阈值生效）：形态定下来后先做可建性检查 —— Windows 上目标链接路径 ≥260 字符（MAX_PATH）时文件级 os.symlink 建不出来（实测 259 可、260 起一律 WinError 1314，带 \\?\ 前缀同样失败；ctypes 直调 CreateSymbolicLinkW 返回成功但链接不可见，不可依赖）。注意 1314 有二义性：长路径与「权限不足」都报同一个 WinError 1314，所以判定顺序必须是先按路径长度分类（≥260 ⇒ 长路径判定），再按错误码分类（<260 且 1314/EPERM ⇒ 需提权）。此时若内容根是目录且其路径 <260，改为提议目录别名（同样要确认「以后新增也落新位置」）；否则拒绝并说明。长路径绝不静默降级成「不建链接」 —— 那等于把种子留在「qB 指向 S、数据在 T」的裸奔状态。

删除语义差异（要写进文档）：文件链接下「删除种子并删除文件」只删链接，数据留在 T（变成孤儿，需要清理入口）；目录别名下会真删 T 里的数据。两种形态的用户预期不同，回执与文档都要说清。

3.2.1 多选集合先按组拆开

  • 一次批量移动可能含多个组（内容不同）：按组 key 拆开，逐组处理，回执按组汇总。
  • 单成员组：qB 直接搬（目标无同名文件 ⇒ 零校验），save_path 变 T，不建链接。
  • 多成员组：搬 mover（目标空 ⇒ 零校验）→ 给其余成员建链接（形态按 §3.2 分流）→ 武装收尾。
  • 为什么不能把整个集合当一次搬：qB 一次只搬一个种子的 storage。把不同组的文件塞进同一个别名单元，既因为「目录没空」建不出目录别名，又会把没参与搬的文件卷进作用域。
  • 因此 F 与形态判定都在「组」这一层做；集合层只负责拆组、排序、汇总回执。测试里的 S14b 就是这条：多选 {组①, C} 时必须拆成「组① 走链接 + C 直接搬」两件事。

3.3 平台支持面：多平台是能力矩阵，不是白名单

环境组合目录别名文件别名结论
Windows 宿主 + 本地 NTFS 卷junction（免权限）同卷硬链接（免权限）/ 跨卷 symlink（开发者模式或 UAC）支持
Windows 宿主 + 目标为 UNC / 网络盘junction 不可用（reparse 点不能指向 UNC）⇒ 退 symlink（需权限）symlink（需权限）支持（可能要一次提权）
Linux 宿主symlink（免权限）symlink / 同卷硬链接支持
macOS 宿主symlink（免权限）symlink支持
Linux 容器 + Linux 宿主（bind mount）容器内 os.symlink 落到宿主文件系统，同内核同左支持
Linux 容器 + Windows 宿主（Docker Desktop / WSL2）只能建 WSL 的 LX 重解析点，Windows 侧读不了（实测 Errno 22）同左拒绝
远程 qB（无共享文件系统）本机建不出 qB 能读的链接同左仅「独占情形」可用（qB 自己搬，不需要别名）

所以闸门判的是能力组合（能否在 qB 看得见的那块盘上建出 qB 能读的链接），不是「什么平台」。支持面覆盖 Windows / macOS / Linux 宿主与 Linux 容器；只有两类被拒，且都是物理不可能而非实现偷懒：跨 OS 的容器组合（LX 重解析点 Windows 不认）、远程 qB 无共享盘。这两类拒绝文案必须写清「为什么不可能」，并给出替代（独占情形照常可用 / 用 qB 自带移动并接受一次校验）。

平台细节清单：Windows 长路径走 \\?\ 前缀（junction 与 symlink 创建都要）；Unicode 路径（测试种子的韩文名 + 括号）经 UTF-8 JSON 传给 UAC helper，不走命令行参数；POSIX 大小写敏感、Windows 不敏感 ⇒ 组键解析后仍需 normcase 兜底；删除链接一律用非递归 API（os.rmdir/os.unlink/[IO.Directory]::Delete(p,$false)），禁止递归删除跟随链接。

3.4 组判定改造：作用域登记表，不是 realpath

文件级别名不会让目录本身变成链接（S/Name 仍是真实目录，只有里面的文件是链接），所以 realpath(S) 解析不出物理位置 —— 靠 realpath 合并组在文件级别名下失效。改用作用域登记表（数据源就是活跃 job，不另建一套状态）。下面只画第 1 层，完整三层见 §3.4.1：

resolver(save_path, files):          # 第 1 层: 自有 job 登记表(零 syscall)
    if save_path == job.src and 内容根落在 job.scope 内:  return job.dst
    else:                                              return save_path   # 与今天逐字节一致
  • dst 与原目录结构镜像（S/Name/x ⇒ T/Name/x），所以 key[0]=dst 与相对路径拼出来就是真实物理路径 —— 下游 _cross_physical_key 不用改。
  • 两个消费点共用同一 resolver：_assign_to_group / _handle_save_path_changes，以及跨组文件交叉检测的目录解析。单点定义，防漂移。
  • 建链后强制 regroup(scope 内 hashes)；新成员进 scope 时同一 resolver 自动并组（不需要重新武装）。
  • 作用域按「save_path == src 且内容根落在 scope 内」判定，不按 hash 列表 —— 这样迁移后新加的同内容辅种自动并入，收尾集合也随之扩大。
  • 第三方链接的处置：目录级（junction / dir symlink）经 realpath 解析后并组；文件级与硬链接只识别、不并组、拒迁 —— 见 §3.4.1。

3.4.1 与第三方链接工具兼容（自动辅种 / 媒体库整理）

环境里常见的自动辅种与整理工具（IYUU、MoviePilot、nas-tools 一类）会「删掉重复数据、在原位留 junction/symlink」，或把媒体文件硬链接进媒体库。这些链接不是本功能建的，但必须被识别，否则组会裂、迁移会搬错东西。改为三层物理位置解析，按成本从低到高：

层识别对象做法成本结论
1本功能自己的别名活跃 job 的 (src, dst, scope) 登记表O(1)，零 syscall并组（§3.4 主路径）
2第三方目录级 junction / symlinkrealpath_lexical(save_path)，不同则用解析结果当 key[0]；若 save_path 本身未变，再试内容根（save_path/首段）每组 1~2 次 syscall（只在重归组/脏组轮）并组（实测 Windows os.path.realpath 能解析 junction）
3第三方文件级 symlink（媒体库整理）用代表文件 realpath 探测；命中则把组标记为「第三方链接」每组 1 次 syscall识别但不并组：目标目录结构任意（媒体库会改名/分层），key[0] + 相对路径 表达不了；界面标「第三方链接」，迁移闸门拒绝
—硬链接st_nlink > 1（Windows 实测可读，同一 st_ino）每组 1 次 stat不并组（硬链接是「同一份数据的第二个名字」，不是跨种子的同一路径）；迁移闸门拒绝，可显式 force

为什么硬链接不并组：并组的前提是「两个种子指向同一组物理路径」，硬链接是同一 inode 的多个名字，要合并得建 inode 索引（每次同步全量 stat），成本与收益不成比例；而它的真实语义是「同一份数据的副本名」，与辅种组要解决的事不同。

为什么文件级第三方链接只识别不并组：这类链接的目标通常是媒体库路径（/media/剧名/Season 1/S01E01.mkv），与原 save_path + 相对路径 没有对应关系，现有组键形态（key[0] 当目录前缀）无法表达。要做就得把 store.groups 的键换成「物理文件集合」，牵动分组、跨组检测、视图三处 —— 不在本轮范围，作为已知限制记在 §07；是否入池 issues/ 待用户确认。

对迁移闸门的影响：第 3 层与硬链接都拒绝迁移，理由写进回执 —— 文件级链接下 qB 搬的是链接本身（数据留在原地，种子反而指向一个悬空链接）；硬链接下 qB 会复制出一份新数据并让去重失效。

3.5 C 的两本账：alias_removed 到底怎么标

为什么需要两本账：state.json 只能由主循环线程写（黄金法则 5）。guardian 是独立进程、要在 auto-qb 不在时也能记录「我删了别名」，所以它只写自己的 journal 文件；auto-qb 读 journal 合并进 state。两个进程永不写同一份文件，也就不需要跨进程锁。

账本位置唯一写者内容
state（权威，给界面与决策）state.json → relocate.jobs.<job_id>auto-qb 主循环hashes / mover / src / dst / alias_kind(file|dir) / alias_paths[] / scope / phase / reason / armed_at / updated_at / resume_hashes / attempts / last_error
journal（guardian 自述）<data_dir>/relocate/<job_id>.jsonguardianphase / ts / pid / qb_down_evidence{proc_absent, port_refused, stable_secs} / checks{file_count, total_size, sample_ok}

相位机（主干单向推进；旁支只做零成本动作，失败不搬数据）：

moving ──► moved ──► armed ──► removing ──► removed ──► finalizing ──► done
  • moving：qB 正在搬（mover 已下发 setLocation）；watching 是它的长耗时变体 —— 仍在搬、dst 仍在长，只降频轮询 + 提示，不判失败。
  • moved：qB 搬完且 dst 校验通过，准备建链接。
  • removed(reason=alias_partial)：链接建不全 ⇒ 删掉已建的 k-1 条 ⇒ 直接进 removed，与正常收尾路径合流。
  • failed(reason=move_stalled | verify_mismatch | alias_unreadable | torrent_gone)：现场保留，不搬数据，等用户选择。
  • cancelled：用户显式撤销并已完成搬回（唯一会移动数据的旁支，需成本确认）。

为什么要先写 removing 意图再删：删除是唯一「删完就观测不到」的动作。journal 里先落一条 removing（tmp + fsync + os.replace 原子写），再删链接（文件级是 N 条 unlink，目录级是 1 条 rmdir），再落 removed。崩溃后「journal 说 removing + 现场探测链接是否存在」两者组合，就能唯一确定崩在删除的哪一侧：

  • journal=removing 且链接在 ⇒ 还没删成 ⇒ 重删（幂等，逐条跳过已消失的）。
  • journal=removing 且链接不在 ⇒ 已删但没来得及落 removed ⇒ 按 removed 处理。

对账表（auto-qb 启动时 + 每 tick 对非终态 job 逐条跑；「qB 在?」= 端口连得上）：

journal链接在?qB 在?种子态处置
armed是任意正常guardian 心跳过期(>60s) ⇒ 重拉；否则等
removing是否—guardian 重删；guardian 不在 ⇒ 只重拉，auto-qb 绝不代删
removing是是正常qB 回来了 ⇒ 撤销意图写回 armed + 重拉 guardian
removing / removed否是正常（save_path==src）修复：重建链接 + 回 armed（说明删的时候 qB 其实在跑）
removing / removed否是missingFilesfinalizing：setLocation(dst) → 轮询 progress==1 && save_path==dst → done

关键简化：不需要检测「qB 重启」。收尾的充分条件是证据而非事件：qB 在线 + 种子 state==missingFiles + save_path==src + 链接不在。qB 是否重启过、重启了几次都不影响判定。

执行期崩溃恢复（phase ∈ {moving, moved}，guardian 尚未武装，journal 可能不存在 —— 只按 qB 现场判）：

  • 种子 state==moving ⇒ 继续轮询（qB 自己会把活干完），不重新下发 setLocation（会排队/覆盖）。
  • save_path==dst 且 dst 校验通过 ⇒ 补做 moved 之后的步骤（建链接 → 重归组 → 武装 C）。
  • save_path==src 且已不在 moving、dst 无数据 ⇒ failed(move_stalled)；dst 有部分数据 ⇒ 同样 failed，现场保留。

收尾集合按作用域动态计算（不是创建时那份固定 hash 列表）：members = {创建时的 hashes} ∪ {当前 save_path == src、且内容根落在 scope 内的所有种子}；mover（已在 dst）跳过。别名期间新加的同内容辅种自动落进这个集合，收尾时一并 setLocation，不会出现「收尾后新成员留在原地、链接没了 ⇒ 缺文件」的坑。

3.5.1 失败处置：如实告知，不自动搬回

「回滚」在这里从来不是零成本的：数据已经在 T，搬回就是第二次全量复制（几十 GB 到几 TB、几十分钟到几小时），而且用户可能只是想修一下权限再重试。所以自动动作只做零成本的事，搬数据一律交给用户决定。

失败点现场状态自动动作（零成本）用户选项
qB 搬迁停滞（dst 长时间不增长 + qB 已不在 moving）数据部分在 T、部分在 S落 failed(reason=move_stalled)；不碰数据；回执给出「已搬 X / 共 Y」①重试（继续等 qB）②检查 qB 日志 ③撤销（搬回，见成本提示）
qB 搬迁耗时过长（超过 move_warn_after，但仍在 moving 且 dst 在增长）qB 正常在搬不判失败：转 watching，降频轮询（30s），界面显示「搬运中（已超预期时间）」无（自动继续；只有停滞才判失败）
链接建到一半失败（第 k 条 EPERM / UAC 被拒）数据在 T；mover 在 T；其余成员指向空 S删掉已建的 k-1 条链接（让 S 侧状态一致）→ removed(reason=alias_partial) → 走收尾路径①重试建链接（数据不用再搬，修好权限即可）②等下次 qB 重启自动收尾 ③撤销（搬回，显示成本）
校验不齐（dst 文件数/大小不符）数据可能不完整落 failed(reason=verify_mismatch)；不建链接、不删数据①重新校验 ②查看 dst 现场 ③撤销（搬回）
穿透校验失败（链接在但读不到）链接已建落 failed(reason=alias_unreadable)；保留现场（不删链接，便于排查）①重试 ②撤销
qB 搬迁期间种子被删 / 用户改路径—落 failed(reason=torrent_gone)；不碰数据人工处理

撤销的成本提示：点「撤销迁移」先弹一行事实 ——「将把 X GB 从 T 搬回 S（qB 执行，预计 Y 分钟），期间该组不可用」，确认后才发 setLocation(mover, src)。不确认就不动。

为什么链接失败不搬回：链接失败通常是权限问题（UAC 被拒 / 未以管理员运行），修好之后重试是零数据移动的；搬回则要再复制一遍全部数据，而且搬回后再修好权限重来，等于白搬两趟。把「失败」降级成「收尾路径」（等 qB 重启 + setLocation）同样是零数据移动 —— 代价只是该组在下次 qB 重启前不可用，比搬两趟便宜得多。

撤销（cancel）与回滚：界面提供「撤销迁移」= 删链接 + setLocation(mover, src) 把数据搬回（目标为空 ⇒ 零校验）→ phase=cancelled。这是「用户手动删了链接、又不想被对账重建」的唯一出口：对账只在 job 未撤销时重建链接，撤销走完整回滚，不会留半截状态。撤销必须先显示成本并经确认，不自动触发。

guardian 先于 qB 退出：别名保留 ⇒ qB 下次起来照常工作（不会进 missingFiles）⇒ 收尾窗口错过。处置：① auto-qb 启动与每次 arm 时巡检 guardian 心跳，死了就重拉；② qB 重连时若 job 仍 armed 且链接仍在 ⇒ 记一次「窗口错过」并提示「等待下次 qB 退出」，不强行收尾；③ auto-qb 也不在时，下次启动照样巡检。代价是收尾可能无限期推迟，但 A 的别名态本身稳定，不影响做种。

  2. 暂停：暂停集合内运行中的成员，记录 resume_hashes；等快照回流（复用 own_write_pending 的等待语义）。
  3. 搬：对 mover 调 torrents_set_location(mover, dst)，每 tick 轮询 save_path/state。判失败只看停滞（dst 不增长且 qB 不在 moving 超过 move_stall_timeout）；超过 move_warn_after 只提示不判失败。进度用 dst 体积采样（每 5s，失败静默）。
  4. 校验：dst 侧文件数与总大小对齐（verify=sample 时抽样 SHA1）；不齐 ⇒ failed(verify_mismatch)，不搬回。
  5. 建链接：按 plan() 的形态建（逐文件：先重建目录树再逐条链接；目录别名：一条 junction/symlink）。逐条落账（alias_paths 追加式写入 state），中途失败 ⇒ 删已建链接 → removed(reason=alias_partial) 走收尾路径，不搬回。
  6. 穿透校验：经 src 路径逐文件 stat，大小一致。
  7. 重归组 + 落账：regroup(scope) → 写 job（phase=armed）→ 拉起 guardian。
  8. 恢复：按 resume_hashes 恢复运行态；回执写「已迁移 N 个 / 文件链接 M 条 / 待收尾」。

8.4 判定口径

  • 零校验：qB 日志无 checkingUP/checkingDL；progress 无中间爬升（C 收尾允许 1 秒级 checkingResumeData 瞬态）。
  • 未被重加：added_on 不变（重加会变），日志无 delete/add 事件。
  • 无感知：迁移窗口内 qB 文件日志零新增行（建链接与搬数据期间）。
  • 数据无损：每个文件跨盘往返后 SHA1 与基线一致。
  • 组不裂：同组成员组 key 相同；跨组交叉检测无告警。
  • 证据：每步落 {API 快照, 链接状态(lstat/LinkType/Target), 日志增量, SHA1} 四元组，存 tmp-analysis/relocate-e2e/（不入库），P7 报告只引用关键数字。

可以 Mock，但只能 Mock「能力探测里的尝试创建」这一个单点，不能 Mock 分支本身，也不在生产代码里留测试开关（配置键/环境变量一律不加）。
