§01目标与设计原则

背景

增量同步一期(plan 26-10-07-0414)落地后稳态轮询走 delta 载荷(1.8 KB 级), 但两笔遗留仍在: ①组行内嵌完整 members 明细数组(3000 种子全量回包 6.3 MiB 的主体), 任意成员速度抖动脏整条组行, 组视图增量粒度天然停在「组行」; ②全量轮(首屏 / 多标签冷启动 / rid 滑窗 / 防御降级)仍回整表, HTTP 93.8 ms@3000、前端整表替换 562-816 ms@3000, 原方向③(分页/按需字段)未实施。两件都要动响应体形状, 10-08 收口档案已建议一起排; 本计划联合认领。

目标

  • G1 组行 members 改 hash 引用式: 组行只带聚合字段 + hash 数组, 明细由前端经既有 memberByHash() 基建从 torrents ∪ singles 拼装 —— 全量回包的 members 重复份额塌掉(6.3 MiB 口径的主体)。
  • G2 组视图增量粒度实质下降(C1 口径): 成员抖动轮的组行 upsert 从「整行 × 全成员明细」缩为「聚合字段 + hash 列表」—— 粗估 100 成员组 ≈40 KB → ≈5 KB(约 8 倍), 精确数字 S0 实测。
  • G3 协议偏移自愈: 前端轮询比对 app version, 变更即 location.reload() —— 「升级后旧标签页静默渲染破损」变「自愈」。
  • G4 全量轮成本构成实测拆分(issue 2 §05 预置的第一步), 数字出来后 B/A 只按实测裁决, 不凭猜立项。

设计不变量

  • R8 整行替换不破(C1 口径): 组行 delta upsert 仍是完整行对象(聚合 + hash 列表), 不做字段级 patch / 部分合并。
  • 增量安全网全数保留: full 语义常驻回退、_reduce_delta 三判据(窗外 / 窗内含 full 代 / 缺行防御)、镜子测试与「S6 局部重算 == 全量重跑」单测, 全部只改形状不改语义。
  • 兼容口径换轨: 全量分支响应体形状演进, 不再承诺「与历史响应逐字节等价」(那是 S3 增量协商的独立提交兼容闸, 本计划是响应体二次演进, 两码事)。兼容保障 = 同仓同进程发布(静态 UI 由同一服务端出)+ 静态 no-cache+ETag 重校验(static_ui.py:49-58)+ G3 version-reload 自愈。
  • 前端机制不动, 只换数据源: 乐观补丁链 / WeakMap 记忆化指纹 / 筛选器族逻辑不改写; 52 处 g.members 消费位(全树 grep 口径, 见 §02; 立项复验口径 60 处经 S2 实查重锚, 见 §10 R1)零 diff 为前端主验收标准(§04 S2)。
  • 范围守恒: C2 / B / A 全部是实测触发的条件项, 不预设不顺手做; shows 视图已是 hash 引用式, 本计划不再动它的行协议。

§03方案总览

主线: C 先行(hash 引用式, = issue 26-10-07-1420 本体)

面改法依据
后端组行_build_group_row 的 "members" 从 _member_view 明细数组改 hash 字符串数组; 聚合字段(dlspeed 求和等)全部保留 —— 组行仍是完整行对象shows 先例 views_episodes.py:32

version-reload(D3)前端每轮比对 status payload 既有 version 字段(_status_payload 已回传), 变更即 location.reload()十行级改动; 根治未来一切协议偏移的静默破损

载荷数学(诚实预期, S0 实测为准)

  • 确定性收缩: 四数组全量响应(view 缺省 / shows 视图)的 members 重复份额塌掉; 抖动轮 delta 收缩约一个量级(≈40 KB → ≈5 KB@100 成员组, 粗估 ≈8 倍)。
  • 可能持平: view=group 单独看, 分组成员明细从「内嵌在 groups」改为「一次计入 torrents」(SEED_ITEM 行比 _member_view 行略重), 加上 hash 列表, 未必变小 —— 本计划对 view=group 体积不预写承诺, 收益主张押在全局去重与 delta 粒度上。若 S0 实测字段冗余仍占大头 → B(按需字段)裁决点(§05 G1)。
