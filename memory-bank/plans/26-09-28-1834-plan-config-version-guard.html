01问题与缺口

事故形态: agent 修改 config 字段, 没抬版本、没写迁移

2026-09-28 用户定调: 上一个 agent 修改了 config 中的字段而没有走现有的版本升级流程。排查确认这不是单点失误——现有体系里不存在能在开发期发现这件事的检查。改键（删键 / 改名）只要把 schema 和 validation 两边同步改掉，全部测试照样绿；后果落在用户侧：存量 config.yml 里的旧键成为孤儿键，要么被静默丢弃（配置语义丢失），要么由废除校验报废（启动进不去）。

02现有防线为何拦不住

防线它拦什么为何拦不住本事故
版本链框架
infra/versioning.py		已登记版本的旧文件沿链升级; 未来版本拒绝前提是「改键的人记得抬 CURRENT_VERSIONS + 注册迁移」——不抬号, 框架根本不知道发生过变更
写回版本闸门
writer._reject_stale_version		WebUI 提交低于当前版本的树 → 400版本号没变时, 旧结构树带着当前版本章往返, 闸门看不见差异
启动物化
materialize_schema_migration		磁盘落后结构改写到当前版本同上——没有登记的版本差, 就没有迁移可做
schema 互检
test_config_schema.py		schema Field 树 ↔ validation KNOWN_*_KEYS 两边一致两边一起改（改名/删除同步落地）互检恒绿——它守「每一键可图形化」, 不守「键面没变」

缺口本质: 四道防线都在「版本差」存在之后才工作, 而制造版本差的第一步（抬号 + 写迁移）没有守卫。运行时补不了这道岗——必须在开发期立冻结参照物。

03方案: 键面基线（核心层）

第三份冻结副本 + 生成器 + 分流报错 + 显式再生命令

新增守卫测试 tests/test_config_key_surface.py, 三条用例:

  • 键面比对 — 生成器从 schema.config_fields() 递归展开 + validation 常量补动态段（口径见 §4）, 产出全量键路径集合; 与基线文件 tests/fixtures/config_key_surface.txt（含 version: 行记录基线时的 config 版本）比对。不一致即红, 报错按 §5 分流。
  • 迁移链完整性（静态化） — MIGRATIONS["config"] 的键集合必须恰好是 1..CURRENT_VERSIONS["config"]-1。这条目前只在运行时 migrate() 里兜底（缺项 fail-fast）, 提前到测试期: 抬了号忘写迁移, 不用等人跑主程序。
  • keys.md 同步钩 — 基线键面每个叶键（路径末段, 词边界匹配）必须在 memory-bank/config-reference/keys.md 的反引号 span 内有出处。改键忘回写文档当场红。
为什么是「第三份冻结副本」

schema 与 validation 互检是两边对表, 基线独立于两者——这正是它能在两边一起改时报警的原因。基线是生成物（生成器单点在测试模块里, 再生脚本只是调用方）, 头部注明口径, 禁止手改; 「更新基线」因此成为一个显式动作而非顺手改文件。

守卫不自动裁决破坏 / 非破坏

机器判不了「这次改动语义上算不算破坏」。守卫的裁决方式是把键面差异完整摆出来 + 报错文案分流路由: 消失键 → 指向抬版本 + 迁移注册 + 回归测试（参照 test_hr_config.py 兼容锚写法）; 纯新增 → 指向重生成基线（commands run test.keys-update）。文案同时指路 versioning.py 口径段、计划 26-09-26-0506 与 pitfalls/backend/schema-stamp-writeback.md。

04键面口径与边界

段派生源路径形态
顶层键validation.KNOWN_CONFIG_KEYS（剔除 schema_version——版本章本身不入面）<key>
具名子树schema Field 树递归（web / log / notify / grouping / hr / hr_check.channel / add_episode_tags / fs / qbittorrent …）hr_check.channel.port 等
站点段（动态）schema.TRACKER_FIELDStrackers.*.<key>, 子段 trackers.*.hr.<key>
HR 站点接入（动态）schema.HR_CHECK_SITES_FIELDShr_check.sites.*.<key>
规则集（动态）schema.RULE_FIELDS + plugin_table() 全部插件 spec<任意>_rules.*.<key>, 插件 <任意>_rules.*.conditions.<名>…
路径映射条目validation.KNOWN_PATH_MAP_ENTRY_KEYSfs.path_map.*.from / .to
  • 动态段归一: 站点名 / 规则集名 / 规则名 / 档案 id / 映射条目一律通配, 键面只含「结构」, 不含用户起的名词。
  • 边界一（v1 不入面）: 限速曲线段内部键（traffic_source / curves / 阶梯点）目前是 validation/curves.py 的内联字面量, 无常量可派生——提常量属对生产校验器的计划外改动, v1 不做; 后续要纳入, 先把字面量提成常量再进生成器。
  • 边界二（永远不入面）: 默认值 / 帮助文案 / UI 元数据（tone / label 等）。改默认不改结构, 非「旧数据读不读得懂」问题——versioning.py 口径本就刻意不为补字段造版本。
  • 边界三（拦不住, 靠评审）: 键不变、语义改义。守卫看的是结构键面, 语义变更没有结构信号。

05判定与分流

现场状态判定报错指路的处置
键面 = 基线, 版本 = 基线版本过—
键面有消失键, 版本未动红 — 破坏性变更(删/改名)未走流程抬 CURRENT_VERSIONS["config"] → config/migrations.py 注册迁移(import 即注册) → 补迁移回归测试 → 重生成基线
键面只有新增键, 版本未动红 — 键面漂移未确认非破坏(补字段), 直接 commands run test.keys-update 重生成基线 + 回写 keys.md
版本已抬, 键面 ≠ 基线红 — 基线待重生成列出增删清单供复核; 迁移链完整性断言已静态兜住「抬号忘迁移」
