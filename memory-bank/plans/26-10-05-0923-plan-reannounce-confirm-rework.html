强制汇报确认机制重构: epoch 前跳证据门控

现判定把 qB 5.2 的 next_announce(epoch 绝对时间)当倒计时用, 成功判据方向反了恒不触发, 用户看到的「经常无法识别」是结构性误报。本计划按调研报告的候选设计落地: 主判据改为 epoch 前跳, 停止种子直判, 「未确认」与「失败」分列, 推迟路径早回执 + 后台日志核实, 旧版 qB 回退证据门控 —— 把确认机制从「大概率误报失败」修成「每一条回执都有正证据或诚实标签」。

01结论与拍板点

本计划认领调研报告(26-10-05-0854)的后续落地。报告已从 qB 5.2.3 / libtorrent RC_2_0 源码级确证: 现四判据里三条正向判据在「已 working + 立即成功」这一最常见场景下全部落空, 30s 窗口走完恒误报「确认超时」; 唯一持久的正向信号是 torrents/trackers 的 next_announce epoch 前跳(WebAPI 2.13.0 / qB 5.2.0 起, qbittorrent-api 2026.8.1 零成本可用)。修复不引入新配置键、不动规则侧, 全部改动收敛在 webui 确认链路三处文件 + 测试。

拍板点(实施前逐项确认)

#决策推荐备选与理由
D1推迟路径(min_interval 未过期, 汇报被 libtorrent 推迟到 min_announce 才发)怎么处置 早回执 + 后台日志核实 检出即对该种子写「已受理(推迟至 HH:MM)」结论并移出回执跟踪, 后续由轻量后台结构在预计发送时刻后核实一次、只落日志; 用户不必盯最长 10 分钟的 busy toast, 回执语义诚实。备选 A: 干等 —— item 截止期延到 min_e+15s(上限 600s), 前端 waitCmd 40s 上限同步放宽, 换取回执里直接写「确认成功」; 代价是组操作时用户可能干等数分钟。备选 C: 维持 30s 超时报「未确认」, 最省但推迟场景永远拿不到确认证据。
D2主判据 TOL 与「成功」语义 TOL = 3.0s; 语义取 (b) 窗口内 tracker 收到新鲜汇报即成功 跳幅 = 响应时刻 − 上次响应时刻, 「投递后立刻汇报」场景跳幅可能只有几秒, TOL 不能大(报告 §7); 语义 (b) 与辅种目的等价, 且确认窗口(≤30s)远小于私站周期 interval, 窗口内前跳几乎必为本指令所触发。备选: 语义 (a) 收窄「前跳时刻距指令时刻 < 一个 tick」—— 留作真机探针发现周期 announce 干扰时的加固项, 不预先实现。
D35.2 前后版本闸门 字段存在性探测(基线读时判), 不调 app_web_api_version qB < 5.2 的 trackers 行根本没有 next_announce 键, 基线读一次即可判 epoch / legacy 模式, 零额外 API。备选: 主动探测 WebAPI 版本 —— 多一次调用且要处理探测失败, 无收益。
D4「未确认」第三态的回执形态 回执状态保持二值(ok/error), 未确认/已受理走 error + 文案前缀约定 前端 _pollCmd 只认 status === "ok" || "error" 为终结(commands.js:131), 加第三态会挂死 waitCmd 直到超时; 前缀分流只改 reannounce 聚合分支一处。备选: 新增 warn 状态 —— 需同步改前端终结条件、SSE 事件路径与静态守阵, 改动面大且无机器可读收益的场景。
D5规则侧 rules/actions/transfer.py 的 ReannounceAction 是否本轮接入确认 非目标 报告 §7 顺带记录的缺口(只有 600s 限频、无结果确认)真实存在, 但其调用环境(规则线程、无 cmd_id 回执通道)与 webui 不同, 接入要做日志面回执, 独立成轮。判定函数本轮保持纯函数落在 webui/commands.py, 将来复用时再上提中性叶。

02依据与根因(引用报告)

根因取证、libtorrent 源码机制、信号盘点与兼容性结论的单点在调研报告(§2 观察解码 / §3 现状失效 / §4 信号盘点 / §5 机制 / §6 兼容性), 本节只留与本计划直接相关的最小引用, 不复写。

现判据(commands.py:228 _confirm_reannounce_result)qB 5.2 epoch 语义下的实际本计划的处置
status == 3 → 成功updating 窗口 ≈0.5s, 2s tick 命中率 ≈25%, 多数错过保留为判据 ②, 撞见即收(直接证据)
na < b_na − 60 → 成功na 是 epoch 秒, 成功时前跳(变大), 本式恒假 —— 失效根因方向反转: next > b_next + TOL 为主判据 ③
status 2←非2 → 成功对已 working 的种子 2→2 无变化, 辅种常态不触发降级进 legacy 回退分支(qB<5.2 无 epoch 字段时的正向判据)
status==4 ∧ msg → 失败可靠(持久否定信号)保留为判据 ④
30s 未出结论 → 失败推迟路径必超时; 停止种子白等 30s改为「未确认」独立标签; 停止种子直判; 推迟路径走 D1
关键机制事实(报告 §4.1/§5): next_announce/min_announce 是 Unix epoch 秒(qB 源码 toSecondsSinceEpoch); 未联系过的 tracker 时间点未设(libtorrent time_point32::min()), 序列化值待真机探针确认 —— 消费时把判据 ③ 的判定域限定在基线 status ≥ 2 的行即可规避; 虚拟行(DHT/PeX/LSD)照旧排除。

03目标行为设计

3.1 新判定(五分支, epoch 模式)

#条件(逐 tracker, 任一命中即结论)结论说明
①种子 stopped(store 快照 state_enum.is_stopped)未确认qB 对停止种子静默 no-op(torrent.cpp L3900), 立即出结论免白等 30s; 在 check_pending 侧判, 不进纯函数
②updating 或 status==3已确认announce 在途直证, 撞见即收(~0.5s 窗口, 命中是加强证据)
③next > b_next + TOL(限基线 status ≥ 2 且 b_next 非空的行)已确认主判据; TOL=3.0s(D2); min 同向前跳可记入 reason 作佐证, 不作必要条件
④status==4 且 msg 非空失败tracker 拒绝, 唯一可靠否定信号; msg 空的 status 4 不判败(歧义保守落「未确认」)
⑤窗口走完仍无 ①–④未确认不与「失败」混淆; 回执 error + 前缀「未确认」(D4)

3.2 legacy 模式(qB < 5.2, 基线行无 next_announce 键)

判据集 = ② updating + ③′ status 2←非2 + ④ status4+msg; 成功难证、失败可证, 超时一律落「未确认(旧版 qB 无 epoch 字段, 仅未观测到拒绝)」—— 与 pitfalls/backend/effect-confirmation.md 的证据门控口径一致, 回执语义只承诺诚实标签。

3.3 窗口与推迟早回执(D1 推荐项的时序)

投递 reannounce → 基线读(逐 real tracker: status/updating/next/min + epoch 模式判定) │ ├─ 停止种子──────────────→ item 立即结论 「未确认: 种子已停止」(不再轮询) │ ├─ epoch 且 min_e − t0 > 25s ──→ item 立即结论 「已受理: 最小间隔未过期, 推迟至 HH:MM」 │ └→ 移入 reannounce_background(min_e 后每 tick 核实一次, 出 ②③④ 结论只落 INFO/WARNING 日志) │ └─ 立即路径 ──→ item deadline = t0 + max(30s, min_e − t0 + 15s, 上限 600s) └→ 每 tick(2s)轮询 trackers → ②③④ → 全部 item 出结论后聚合回执: 全确认 → ok;否则 error「成功 X / 失败 Y / 未确认 Z: <前 3 条原因>」

基线形状变更: {url: (status, next_announce)} → {url: {status, updating, next, min}} + item 级 epoch / deadline / t0 字段; 截止期从 entry 级单一下沉到 item 级(组内混合推迟/立即种子时各自算账)。

3.4 回执文案契约(前缀单点)

结论回执 statuserror 文案前缀(前端分流依据)
已确认ok—(聚合全 ok 时无 error)
失败(tracker 拒绝)error失败: tracker 未接受汇报(not working): <msg>
已受理·推迟error已受理: 最小间隔未过期, 推迟至 HH:MM(后台继续核实, 结果见日志)
未确认·停止error未确认: 种子已停止, qB 静默忽略强制汇报
未确认·超时error未确认: 30s 内未观测到 epoch 前跳/在途/拒绝证据

前缀常量(RC_FAIL_PREFIX / RC_DEFERRED_PREFIX / RC_UNCONFIRMED_PREFIX)定义在 webui/commands.py 单点, 前端按前缀分流展示; 改前缀必须同步 commands.js 聚合分支(测试钉住)。

06风险与回滚

#风险缓解
R1qB 自身周期 announce 到期同样前跳 epoch, 被算作本指令成功语义取 (b)(D2)下两者效果等价(辅种目的); 确认窗口 ≤30s ≪ 私站周期, 误纳面极小; 真机探针若见干扰 → 启用「前跳时刻距指令 < 一 tick」收窄(报告 §5 预案)
R2TOL=3s 偏小: 上次汇报极新鲜时跳幅 < 3s 漏判 → 落「未确认」漏判方向是诚实标签而非假失败; S0 探针实测跳幅后可收紧/放宽; ② updating 与后台核实作二次机会
R3未联系 tracker 的 epoch 极值造成假前跳判据 ③ 判定域锁基线 status≥2; S0 探针证实序列化值后可再加 b_next > 0 类守卫
R4回执前缀文案被两侧各自改动而漂移前缀常量后端单点 + 契约测试钉住(§05); 前端只在 reannounce 聚合分支一处消费
R5后台核实结构泄漏(种子被删/qB 断连)item 上限 500 丢最旧; 断连 tick 跳过照旧; 结论或 deadline 必移除
回滚改动收敛在三个文件 + 测试, 判定单点为纯函数 —— revert 单个提交即回旧判据; 无状态迁移、无配置键、无 qB 写行为变化(reannounce 指令本身照发), 回滚零残留

07非目标

  • 规则侧 ReannounceAction 接入确认(D5): 报告 §7 已记录缺口, 独立成轮; 判定函数届时再上提中性叶。
  • 确认窗口/TOL 配置键化: 常量足够, 免 validate_config / schema 面扩大。
  • endpoints[] 明细判定: 顶层 next/min 已取各 endpoint 最早值(qB torrentimpl.cpp L264-267), 够用。
  • HR 详情页 / exporter 的 trackers 展示(views.py:188 / exporter.py:32): 只读消费不受影响, 不动。
  • GUI 侧「0 抖动」观感: qB 自家显示行为, 不在本项目范围。
