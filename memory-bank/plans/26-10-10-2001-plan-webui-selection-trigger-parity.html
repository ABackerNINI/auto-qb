01

术语与现状取证

本轮讨论的对象是「选中」与「触发」之间的关系。先把四个词钉死，后面全篇按这套用；它们与现有代码里的字段一一对应，不是新概念：

  • 选中（selection） —— 用户显式圈进来的对象，权威只有两个字段：selGroups（组 key 数组）与 selMembers（成员 hash 数组），派生集合是 selHashSet。普通单击不构成选中（2026-09-17 口径）。
  • 锚点（anchor） —— 动作被触发时指针所落的那一行对象：右键点的那行、或按钮在 DOM 上绑定的那个对象。
  • 光标（cursor） —— 键盘焦点行 kbCursor。它是 focus 语义，不等于选中（2026-09-30 方案 B 已明确）。
  • 触发（trigger） —— 一次会改变远端状态的用户输入：右键菜单项、面板按钮、快捷键、对话框提交。每次触发都必须先解析出「作用目标」才能投递。

用户的疑问可以精确表述为：一次触发解析出的目标，是否总是「用户以为的那个」？当三类输入（鼠标锚点 / 键盘光标 / 选中集合）同时存在时，谁优先？现状没有一个统一答案。

前端已经有一批质量不错的断言，但它们钉的是「单点还在不在」与「某几条链的端到端」：

  • tests/test_web_shortcuts.py::test_sel_visual_parity_and_site_cell —— 钉选中态视觉三皮肤同形。

  • e2e/multiselect-shows.spec.mjs —— CTX-03：选中行右键升级批量菜单 / 未选中行仍是单目标 / 批量暂停合单为一条 bulk。

02

问题陈述:偏差从哪来

先明确前提：本轮没有发现既有 BUG（用户已确认）。下面列的不是待修缺陷，而是「契约没被定义、因此也没有被检查」的空白区 —— 现在的行为大多是某次修复留下的合理选择，但它是局部合理，没有全局口径。

2.1用户列的场景，逐条落到现状

场景现状行为（走哪个解析器）判定
选中 A → 触发 A（右键 A 自己那行） V1 判「等同」→ 单目标菜单；动作走 R4/R3 → 动 A 符合直觉
选中 A → 右键 A 之外的 B 行 V1 判「不等同」→ 批量菜单；动作走 R1 → 动整个 A 文案说「批量…」是对的，但用户手指在 B 上；锚点被静默忽略
选中 A → 键盘光标移到 B → 按动作键 R5：有选中 → 走 R1 → 动整个 A，光标 B 被忽略 与右键路径优先级相反：右键锚点优先，键盘选中优先
无选中 → 光标在 C → 按动作键 R5：无选中 → 用光标 → 动 C 符合
无选中 → 右键 C V1 返回 false → 单目标菜单；动作走 R4 → 动 C 符合
选中 A → 按「全选」 _kbSelectAll 按视图覆盖三视图各自全量，并回扫联动 符合
选中 A（多选）→ 右键 A 内某行 → 想点「详细信息」 菜单已是批量变体，而批量变体里没有「详细信息」（依赖逐目标现值） 「菜单里没这个选项」—— 与坑档 ctx-menu-branch-parity 同族

2.2四个结构性机制

上面那些「不符合直觉」不是四个独立的疏忽，而是四个机制各出一份力：

M1 · 两套判定并行

变体判定 ≠ 目标解析

菜单长什么样，由 V1（_ctxMulti + _ctxScopeKey 的等同性比较）决定；动作作用在谁身上，由 R1/R3/R4 决定。两套逻辑谁也不知道对方在想什么，各自演化。

M2 · 优先级相反

鼠标锚点优先，键盘选中优先

鼠标路径以「被点的那行」为锚定变体；键盘路径以「选中集合非空」为唯一判据。同一屏、同一选中集合，两种输入得到不同目标，且都不提示。

M3 · 借道菜单状态

键盘把解析结果塞回 menu.hash

_kbEditAct / _kbTorrentCmd / _kbTorrentToggle（shortcuts.js:1164/1175/1184）先解析出 hash，再写进 this.menu.hash，然后调菜单绑定方法（E4/E5）。键盘目标解析与菜单状态因此耦合。

M4 · 两套「选中展开」

R1 与 R2 结果不等价

批量动作取 R1（组 key 优先覆盖成员，一个组算 1 个目标）；导出取 R2（全量展开为 hash）。同一选中集合在两条路径上「N 个目标」的含义不同，文案却共用同一个模板。

为什么这类问题值得专门治：它属于「静默改变作用对象」—— 最坏的情况不是按钮按不动，而是按钮动了你不知道的东西。批量删除、整组跳检这类高危动作都挂在这条链上，一次口径漂移的代价是一组种子。
03

一致性契约 C1–C5

先把「作用域」分成三态，契约才有主语：

  • SEL 集合 —— 目标 = 选中集合的展开闭包。
  • ANC 锚点 —— 目标 = 被触发行/对象的展开闭包。
  • CUR 光标 —— 目标 = 键盘光标行的展开闭包。
C1

解析单点

任一次触发必须解析出一个 ScopeDescriptor，由唯一函数产出。任何触发点不得自行拆解选中集合（R1–R7 全部退役为它的内部分支）。

C2

变体派生

菜单/对话框的 UI 变体（multi / group / member / episode / show）由 descriptor 派生，不得再用第二个 token 并行判定 —— V1 并入单点。

C3

文案同源

toast 与确认框里的目标形态（「该种子」/「整组」/「N 个目标」）由 descriptor 派生，不与实际载荷各写一套。

C4

出口唯一

所有动作投递经统一出口；出口内部做一次「descriptor ↔ 实际载荷」一致性自检。调用方拿不到自己拼目标的接口。

C5 · 本轮要拍板的核心口径

仅当选中集合为空时，锚点与光标才有资格当目标。

选中非空时，锚点只能用于改变选中（选中 / 取消 / 扩段），不能静默改变作用对象 —— 除非该触发点在登记表里显式声明 scope: 'anchor' 且可被守阵查到。

这条把「选中 A 右键 B」从现在的隐式批量化改成明确的二选一：要么菜单上写清「将作用于已选 N 项」，要么以 B 为目标并保留「仅 B」的项集。无论选哪边，用户都能从界面上读出来 —— 而不是靠猜。

C5 的两种可行口径（待拍板项 ①）
口径甲（提示型）：保持现在「升级为批量」的行为，但菜单顶部加一行不可点的说明 —— 「已选 N 项 · 本次将作用于全部选中」。改动最小，用户至少不会以为在操作 B。
口径乙（锚点型）：右键哪行就以哪行为目标（变体随锚点走），选中集合只在键盘路径与批量按钮上生效。更符合「我点哪个就改哪个」的肌肉记忆，但要重排 V1 与 R4 的关系。
建议口径甲：它不动已拍板过的 CTX-03 语义（选中 N 行右键 = 对全部生效），只补一个可见性缺口，风险最低。
04

路线对比与选型

路线做法代价新增功能还要加检查吗
A · 只加检查 补一批静态守阵 + 一个 e2e 矩阵，覆盖用户列的四种场景。 低 要 —— 每加一个触发点得人肉补一条。做一次，然后重新腐化。
B · 单点收敛 + 声明式登记
(选)		 descriptor 单点 + 出口收敛 + TRIGGER_REGISTRY；三类检查读同一张表。 中（S3 有行为不变式约束） 不要 —— 走出口自动被检查；不走出口守阵当场红。
C · 后端兜底校验 后端对 bulk 载荷按目标形态二次校验。 高 不适用 —— 载荷里没有「用户以为在操作谁」这个信息，后端无从判断。

选 B。理由直接来自用户那句「后续添加的功能可以自动停靠，而不是添加新的检查」：A 路线本质上就是「添加新的检查」，它治的是这一轮，下一轮加个「批量改分类」按钮又回到原点。B 路线把检查从「逐条枚举」换成「结构性必过」。

同时 B 允许分期：S1/S2 是纯增量、零行为改动（只登记与断言），可以先落地；真正碰行为的只有 S3 与 C5 那一条口径选择。任何时候停下来，已落地的部分都独立有效。

05

技术方案

5.1单点：_scopeResolve() 产出 descriptor

放在 selection.js，与既有的 _selAnchor() / _selSetAnchor() 同族 —— 选中相关的一切单点都在这个文件里，不新开文件。签名与返回形状：

字段含义
scope'sel' / 'anchor' / 'cursor' / 'panel'（抽屉内命令，目标 = 面板当前 hash）
keys组 key 数组。与现在 R1 同口径：真实组的成员 hash 被它覆盖。
hashes未被 keys 覆盖的成员 hash 数组。
closurehash 全集（= 现在 R2）。导出等「逐目标」动作读它，M4 的两套展开在这里合成一个 descriptor 的两个字段，不再各取所需。
anchor{kind, id}，记录锚点行；无锚点时为 null。
variant'multi' | 'group' | 'member' | 'episode' | 'show'。由 {scope, anchor, closure} 派生，V1 的等同性判断迁入此处。
countText「该种子」/「整组」/「N 个目标」——C3 的文案单点。

closure.length 成为「N 个目标」里 N 的唯一来源，两类展开的歧义随之消失。

5.2出口收敛：E1–E7 → 三个

新出口吸收签名约束
_dispatchAction(action, scope, opts) E1 _actCore（乐观补丁 / 回执 / toast / 三桶分流全部保留） 只收 descriptor，不收裸 keys/hashes
_dispatchDelete(scope, opts) E2 _deleteFlow 同上
_dispatchEdit(action, scope, payload) E3 _metaBulk · E5 _editPost · E6 _bulkEditPost · E7 _skipExec 同上；payload 只装业务字段（限速值 / 目标路径 / 标签）
保留的两个豁免：① torrentCmd（E4）的单种子分支 —— 抽屉内命令的目标是「面板当前 hash」，属 scope: 'panel'，在登记表里可查，不走 descriptor；② add_torrent.js 的添加种子，scope: 'none'。两个都进守阵白名单，白名单本身就是「已审计过」的记号。

收敛之后调用方无法自己拼目标 —— 这是 poka-yoke（防呆）手法：不是「请不要自己拼」，而是「没有接口让你自己拼」。

5.3触发点登记表 TRIGGER_REGISTRY

新增 shared/triggers.js，纯数据 + 纯函数（无 DOM、无 this），挂在 window.AQB_TRIGGERS 上由 app.js 注入。它有两个消费者：pytest 守阵（静态读）与 e2e（生成用例）。

字段含义
id唯一标识，如 ctx.multi.act / kbd.act / panel.cmd
ui'ctx-menu' | 'kbd' | 'drawer' | 'button' | 'dialog'
variant仅 ctx-menu 有；与模板四支一一对应
scope声明的作用域（C5 的显式豁免也写在这里）
entry所在函数名 —— 守阵「直投递白名单」按它比对源码
dispatch走哪个出口（action / delete / edit / panel）

5.4三张网

(a) 静态守阵 —— tests/test_webui_trigger_registry.py（新增）

断言防的是
G1 直投递白名单：shared/*.js 里每个写端点调用点（/api/torrents/… · /api/groups/… · /api/torrents/bulk）所在函数名，必须属于 TRIGGER_DEFS.entry 或豁免白名单。表外即红。 新功能绕过出口直接投递（这是「自动停靠」的强制网）
G2 目标解析不外包：三个 _dispatch* 出口之外，不得出现对 selGroups/selMembers 的直接展开（[...this.selMembers]、.selGroups.map( 等），selection.js 自身与登记为 scope:'sel' 的白名单除外。 M1/M4：有人又写第三套展开
G3 变体 ↔ 模板支：ctx-menus.html 的 v-if / v-else-if / v-else 支数 == 登记表中 ui:'ctx-menu' 去重后的 variant 数。 坑档 ctx-menu-branch-parity：加了一支忘了另一支
G4 动作族奇偶：四支都必须有基线四族(开始/暂停/汇报/删除)，multi/member/group 还必须各有扩展六族(重新校验/跳检/限速/移动/标签分类/导出)。按「动作族」而非「逐项集合」比对 —— 各支项集本就按形态允许不同(整集支没有限速/移动)，逐项比对会恒红；归族后正好覆盖 2026-10-09「单组右键菜单缺选项」那类回归。 「同一批动作在两条路径上项集不一致」
G5 单点唯一性：ScopeDescriptor 对象字面量在 shared/ 里只允许出现在 selection.js::_scopeResolve。 descriptor 被影子实现

(b) 运行时审计 —— shared/scope_audit.js（新增）

  • 开关：window.__AQB_AUDIT_SCOPE__。e2e 用 Playwright 的注入脚本打开；生产默认关（保守默认，不污染用户 console）。
  • 动作：三个 _dispatch* 出口各调一次 _auditScope(scope, payload)，比对 scope.keys/hashes/closure 与最终下发载荷；不一致、或 descriptor 缺失/字段越界 → 记进有界环 scopeAudit（上限 50 条）并按签名去重 console.warn 一次。
  • 不改行为：只记账，与既有 cmdStats 同范式（埋点必须有消费者）。
  • 消费者：e2e 每次交互后断言环为空；排障时可从控制台读环。

(c) 真浏览器矩阵 —— e2e/trigger-scope.spec.mjs（新增）

维度 = 视图（种子 / 辅种 / 追剧） × 选中态（无 / 单种子 / 单组 / 组+成员 / 半选 / 多选） × 触发点（右键各支 / 键盘动作 / 抽屉按钮 / 对话框提交） × 期望作用域。每个用例断言三层：

  • 下发载荷：拦截网络，比对 keys/hashes 与期望闭包（不借道 vm 注入，沿用 e2e 既有 D4 守则：有真实 UI 路径就不走 vm）。
  • 审计环为空：scopeAudit 无记录。
  • 文案：toast / 确认框含期望的 countText。

用例清单从 TRIGGER_DEFS 生成 —— 新增登记项自动出现在矩阵里，这是「自动停靠」的第三张网。按既有门禁口径拆两档：核心组合进 @fast（每次改前端跑），全量组合进全量轮。

5.5三张网怎么咬合

新功能长什么样谁接住它

口径与结构

  • 出口收敛为 3 个，调用方接口不再接受裸 keys/hashes；_kbEditAct 不再写 menu.hash。S3

用户列的四类场景（e2e 必测）

  • 选中 A → 触发 A：单目标菜单，载荷 == A 的展开闭包，文案含正确 countText。
  • 选中 A → 触发 B：按 C5 拍板口径，界面明示作用对象；载荷与界面文案一致（不许「说 B 动 A」）。
  • 无选中 → 触发 C：右键与键盘两条路径都以 C 为目标，载荷 == C 的展开闭包。
  • 选中 A → 触发全部：键盘动作 / 批量按钮的载荷 == 选中集合闭包，且组不重复展开（M4 去重）。
  • 补充：半选（组选择派生命中）时右键该行 → 仍视为「在选中集合里」，不退回单目标菜单。
  • 补充：三视图（种子 / 辅种 / 追剧）下同场景结论一致；跨视图切换后选中集合的展开仍正确。

三张网自身的有效性（红验）

  • G1：手工加一个绕开出口的直投递 → 守阵红。
  • G3/G4：手工删掉单组菜单一个动作项 → 守阵红。
  • 审计环：手工构造一次 descriptor 与载荷不一致 → 环里出现记录。
  • 矩阵自增长：在登记表加一条 entry → 无需写新用例即被覆盖（或明确报「未覆盖」）。

不回归

  • test.full 全绿，实测数字写进 testing/baselines/ 新切片（本文件只引用不抄）。
  • dev.e2e 全量在 S3 前后逐位一致。行为不变式
  • 三皮肤（atlas / console / prism）菜单、选中视觉、面板行为零变化。
  • 高危动作（批量删除 / 整组跳检 / 重新校验）的确认框文案与取消零副作用语义不变。
