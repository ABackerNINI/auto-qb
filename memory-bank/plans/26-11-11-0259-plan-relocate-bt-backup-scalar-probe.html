§01目标与设计原则

1.1 背景与动机

计划 26-11-05-0808 S1 把 bt_backup 做成顶层多实例表(键 = qB 连接身份 host:port, 值 = BT_backup 目录)。但唯一查表口 bt_backup_path_of(config/models.py:649)只按当前 qbittorrent 段身份查——表里的第二个条目永远无人消费; webui 因此要渲染键值表编辑器、校验器要逐键验端口, 全部服务于一个不存在的第二维度。本机生产 config.yml 与示例 minimal.yml 实测均无此键(grep 零命中) → 改形状零存量负担。

1.2 目标与「算成」标准

  • G1 配置形状: 顶层 bt_backup 表退役; fastresume 收尾依赖收编为 relocate.bt_backup: "<路径>" 标量, 留空 = 未启用(现状语义原样保留)。
  • G2 升级: schema_version v7→v8, 迁移链一次性搬运旧键; 不做长期双形状兼容读法。
  • G3 自动探测: 设置页「自动探测」按钮为唯一入口——后端候选扫描(多平台 × 多安装模式, qB 源码取证背书)+ hash 自证; 单一命中回填草稿, 用户确认保存才落明路径(审计轨迹)。
  • G4 运行时零探测: relocate_plan/relocate_exec 等运行面只读键, 无任何隐式探测(D3 读法2)。
  • G5 验收: 全量测试绿 + 真机按钮命中本机 %LOCALAPPDATA%\qBittorrent\BT_backup 并走通一次整组迁移 fastresume 收尾。

1.3 设计底线 / 不变量

  • 显式 > 推断: relocate.bt_backup 非空 = 完全跳过探测; 手动键是探测猜不中形态(自定义 profile、远程 qB)的唯一兜底。
  • 保守默认: 歧义 / 未命中 / SQLite 存储模式一律不猜不写, 只展示证据(D5)。
  • 只读探测: 探测零写盘、零 state、零缓存(黄金法则 1/3/5); 运行面单一写线程不受影响。
  • fail-fast: schema 校验聚合不变(黄金法则 4); 新键进 relocate 段校验并同步 schema/groups.py(守卫测试会查)。
  • 范围守恒: 取证中发现的超范围风险(SQLite 运行时防护等)只记 §07 开放项, 不顺手修(黄金法则 6)。

2.2 qB/libtorrent 源码机制表(2026-11-11 取证, qB v5.3.0 dev 8182ae07 / libtorrent 2.1.2.0)

  • 构造唯一: src/base/bittorrent/sessionimpl.cpp:1476,1482 = specialFolderLocation(SpecialFolder::Data) / "BT_backup"; 全库 grep 证实无任何 ini 键可改道(TorrentBackupDirectory 是 .torrent 另存备份功能, 与此无关)。WebAPI 全部 controller 无路径端点。
  • Data 目录解析(profile_p.cpp:87-109): Windows/macOS = Qt AppLocalDataLocation(+后缀); Linux = $XDG_DATA_HOME|~/.local/share, 带 legacy 回退 .../data/qBittorrent[_<name>](≤4.2.x 布局, 4.3.0 起 1c7bfcac4 改)。
  • Windows: %LOCALAPPDATA%\qBittorrent[_<name>]\BT_backup, 无 data\ 中间层(4.0.0 起未变; 与本机实测吻合——我方早先「带 data 层」的假设被源码证伪)。
  • 便携(application.cpp:333-335): exe 目录下存在 profile/ 且未给 --profile → BT_backup = <exeDir>/profile/qBittorrent[_<name>]/data/BT_backup(profile_p.cpp:130-139 CustomProfile 布局)。
  • 自定义: --profile <dir>(cmdoptions.cpp:320)或环境变量 QBT_PROFILE(:435-436) → <dir>/qBittorrent[_<name>]/data/BT_backup;<dir> 任意 → 外部不可静态探测, 手动键兜底。
  • --configuration(cmdoptions.cpp:321): 各路径追加 _<name> 后缀; 后缀可从配置目录枚举佐证(win %APPDATA%\qBittorrent*, linux ~/.config/qBittorrent*, mac ~/Library/Preferences/qBittorrent_*.ini)。
  • 文件命名(bencoderesumedatastorage.cpp:123,434-445,483; infohash.cpp:83-90): ^40hex\.fastresume$ + 伴生 <id>.torrent(v1-only 种子也有); <id> = TorrentID = libtorrent get_best(): 有 v2 取 sha256 前 20 字节 hex(4.5.0 起 7a539d989), 否则 v1 sha1; 4.4.x hybrid 用 v1。queue 文件(每行一个 40hex)是强结构标记。
  • SQLite 模式(sessionimpl.cpp:627 默认 Legacy): ResumeDataStorageType=SQLite 时 torrents.db 在 Data 根(:1464), BT_backup 只剩迁移残留 → fastresume 改写对它无效; WebAPI 可读 resume_data_storage_type(appcontroller.cpp:400)。

§03方案总览

3.1 主线

三层, 运行面零逻辑变化: ①配置面——顶层表退役, relocate.bt_backup 标量(D1), bt_backup_path_of 改纯读键(签名不变, 两个消费方零改); ②探测后端——新纯函数模块 src/auto_qb/infra/bt_backup_probe.py(候选推导 / 资格判定 / 自证 / 裁决, import 纪律落在 infra 白名单内, qB 事实由调用方以原语传入), routes/relocate_chain.py 新端点包装; ③编辑器——表编辑器重写为单路径输入 + 探测按钮(D3 读法2: 按钮是探测唯一入口)。

3.2 探测裁决口径(verdict 五态)

verdict判定前端行为
hit候选恰一个合格(含 ^40hex\.fastresume$ 或 queue); qB 在线时 hash 交集 ≥1 即加分自证, 离线标注「未自证」回填草稿 + 展示证据; 用户保存才落盘
ambiguous多个候选合格且 hash 自证不能消歧(多候选 hash 命中, 或全靠结构自证)只列全部候选明细; 配置一字不动(D5 拒不猜测)
miss零合格候选列已扫描候选 + 提示写手动键
unusable-sqliteqB prefs resume_data_storage_type=SQLite → BT_backup 非主存储, fastresume 改写无效(取证 §2.2 末条)标「不可用」+ 指向 qB 设置; 不回填
manual-setrelocate.bt_backup 已非空(显式 > 推断)提示「已手动配置, 按钮仅供核对」

判定顺序(短路, 防态重叠吞警示): unusable-sqlite 先于 manual-set —— 已手动配置但后端非 Legacy 时仍须示警「不可用」, 不被「仅供核对」吞掉; 其余按命中裁决。

hash 自证: qB /torrents/info 的 infohash_v1/v2 按 get_best() 规则算 TorrentID(v1 与 v2 截断双算, 兜 4.4.x hybrid v1 命名差异, R2), 与候选目录 ^40hex\.fastresume$ 文件名求交。

3.3 迁移口径(v7→v8)

_migrate_config_7_8: 旧顶层 bt_backup 表恰一条非空条目 → 搬成 relocate.bt_backup + note(经 migrate_with_notes WARNING 单点); 多于一条或全空 → 删键 + note 提示重配(不猜, D7); 旧键缺失 → 仅抬版本号。无兼容读法(D2): 校验器/加载器只认新形状, 旧形状只存在于迁移入口。
