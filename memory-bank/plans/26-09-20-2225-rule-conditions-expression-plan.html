把规则条件换成表达式

让 conditions 从「16 个固定插件 + 隐式 AND」变成一行可自由组合的表达式：种子任意字段 + 额外值（当前时间、指定盘剩余空间…），支持算术、比较、逻辑、括号、成员与正则匹配。旧条件一律保留，生产配置零改动。

2026-09-20 auto-qb · src/auto_qb/rules/ 基线 1062 passed（Windows，开工前复测） v2 · 五条口径已拍板 状态：计划 · 未动代码

00 / TL;DR一句话结论

新增一个条件插件 expr（单值字符串），自研 tokenizer + Pratt 解析器 + AST 解释器，配置加载期解析并做静态检查（fail-fast，报错聚合），运行期按已编译 AST 求值。五条已拍板的口径：

  1. 并存 —— 旧 16 个条件一个不删，生产 config.yml 不动；退役与否留到以后单独一轮。
  2. 作用域前缀 —— 标识符一律 tor.* / tracker.* / sys.*，后续可加 group.*（辅种组）而不动语法。
  3. 额外值按数据源可用性启用 —— 没数据源就禁用该名字（配置期判得出的配置期拒绝，运行期不可得的运行期报错），绝不返回假 0。
  4. 出错即停规则 —— 求值出错 = 不匹配 + 中断后续规则（比"只跳过本条"更保守，见 05）。
  5. 一层一个运算符，没有例外 —— 同一括号内出现第二个运算符（含 not、含同种连续）即报错，优先级意图一律用括号写明（见 03）。
# 以前：三条条件只能 AND，写不出「剩余空间相对种子大小」这类判断
conditions:
  - seedtime: ">=3D"
  - upload_ratio: ">1.5"

# 以后：一条写完（一层只能放一个运算符，多的用括号分层）
conditions:
  - expr: '((tor.seeding_time >= 3D) and (tor.ratio > 1.5)) and (freespace(tor.save_path) < 100GiB)'
  - expr: '(tor.is_complete and tor.is_uploading) or (tor.hr_satisfied)'
  - expr: '((sys.dow <= 5) and ((sys.time_of_day >= 22:30) or (sys.time_of_day <= 7:00)))'
  - expr: '("HR" in tor.tags) and (not (tor.category ~ "regex:^z"))'
  - expr: '(sys.dl_speed > 5MiB/s) and (tor.size > 50GiB)'   # 全局速度：数据源可用才启用

01 /现状现在是什么，为什么不够

条件在 src/auto_qb/rules/conditions.py（294 行 / 16 个插件），每个插件是「一个字段 + 一个比较表达式」，规则层把所有条件做 AND（Rule.matches，base.py:170）。字段面是手工挑选的 16 个，而 TorrentRecord 上其实缓存了 qB 的 70 个快照字段（torrents/compat.py:_SNAPSHOT_FIELDS）—— 绝大部分规则用不到。

三个真实瓶颈：

  • 写不出复合条件。「磁盘剩余 < 100GiB 且 今日上传 > 20GiB」里，前者是额外值、后者是种子增量，现有条件各自独立、只能 AND，无法参与运算 —— 想要「剩余空间 / 种子大小 > 2」这种比例判断无处下笔。
  • 字段是白名单。想按 availability / num_seeds / last_activity / eta 判断，得先写一个新条件插件 + 校验 + schema + 前端元数据（4 处接线），而它们的数据早就在记录对象上。
  • 组间/组内的或-与是特例语法。tags 用逗号、state 用 &、列表是或 —— 三套写法各记一遍，还没有取反（想法.md 与 activeContext 的「规则系统：条件取反」长期挂在这里）。
顺带解决：条件取反（not）不再需要单独设计；date_time 的「每月几号 + 星期几 + 时段」三件套可以拆成普通比较；freespace 从「一条条件只能查一个路径」变成「路径可来自种子自身」。

02 /范围目标与非目标

要做

  • 表达式语法：算术 + - * / %、比较 > < >= <= == !=、逻辑 and / or / not、括号 ()、成员 in、模式 ~
  • 作用域前缀 tor.*（种子）/ tracker.*（站点配置）/ sys.*（环境与全局）+ 白名单函数
  • 字面量带单位：100GiB / 24H / 1MiB/s / 22:30
  • 配置期解析 + 静态检查（含一层一个运算符与名字可用性），报错与既有 ConfigError 聚合输出一致
  • 出错即停规则的语义改造（Rule.process 一处）
  • schema / 配置编辑器 / 知识库接线；16 个旧条件的等价表达式对照与守阵测试

不做（本轮）

  • 不删旧条件、不改 config.yml、不做自动迁移（红线文件，迁移另开一轮）
  • 表达式里不放动作、不放副作用 —— 求值必须是纯读取，保证幂等（黄金法则 1）
  • 不引入第三方表达式库，不用 eval / ast 执行
  • 本轮不做 group.*（辅种组维度）—— 前缀体系已为它留好位置，语义另开一轮
  • 不做变量赋值 / 自定义函数 / 跨种子引用 —— 语法留口子，语义不做
  • 不重构 actions（本轮只动 conditions）

03 /语法语法设计

自研 tokenizer + Pratt 递归下降解析器（约 300 行，零新增依赖）。选它不是因为自研好玩，而是两件通用库给不了的事：配置期静态检查（标识符必须落在白名单，拼写错误在启动时报而不是运行时静默不匹配）和受控取值面（只能读种子字段与白名单函数，绝不碰到任意属性/方法）。

优先级（低 → 高）

or     := and  ( "or"  and )*                    短路
and    := not  ( "and" not )*                    短路
not    := "not" not | compare
compare:= add  ( CMP add )?        CMP = > < >= <= == != =   不可链式: a < b < c 报错
add    := mul  ( ("+"|"-") mul )*
mul    := unary( ("*"|"/"|"%") unary )*
unary  := ("-"|"+") unary | post
post   := prim ( "in" prim | "~" prim )?
prim   := NUM | SIZE | TIME | SPEED | HHMM | BOOL | STR
        | IDENT | IDENT "(" args ")" | "(" or ")"

命名空间（作用域前缀）

标识符一律带前缀，没有裸名。前缀即作用域，后续加维度（group.*）不用动语法，也不用担心和种子字段撞名。

前缀作用域例
tor.*当前种子：70 个快照字段 + 派生值tor.size · tor.ratio · tor.tags · tor.is_complete · tor.upload_today
tracker.*种子匹配到的站点配置tracker.name · tracker.groups
sys.*环境与全局（与种子无关）sys.now · sys.time_of_day · sys.dow · sys.torrent_count · sys.dl_speed
group.*本轮不做 辅种组维度group.member_count（前缀已占位）
（无前缀）白名单函数，参数显式传freespace(path) · raw("field") · file_count()

字面量

写法类型解析注
100 / 1.5int / float字面裸数字无单位

运算符

运算符语义要点
+ - * / %数值算术仅数值；除零 → 运行期 ExprError；% 取模
> < >= <=数值/字符串有序比较两侧同类型；类型不同 → 报错
== !=相等（= 视作 ==）跨类型 → 报错（不静默 False）
and / or / not布尔逻辑短路；操作数必须是 bool，非 bool 报错
in成员"HR" in tags、"国内" in tracker_groups、state in ["uploading","forcedUP"]
~模式匹配复用 utils.MatchPattern：name ~ "regex:1080p"、category ~ "regex:^HR:ignore_case"；无前缀 = 精确全等
()分组任意嵌套；括号组对所在层是不透明黑盒（见下节）

一层一个运算符（防优先级误用 · 没有例外）

优先级不靠记、靠括号写：每个括号层级内最多出现一个运算符。not、<、and、+、%、in、~ 统统是运算符，一律占一层 —— 不分种类、不设例外。于是同一个括号里根本不存在“谁先算”的问题，优先级误用在语法层面被消除。

  • 一层一个：出现第二个就报错。连续同种也算第二个 —— tor.a and tor.b and tor.c 要写成 (tor.a and tor.b) and tor.c。
  • not 同样占一层：not tor.is_complete and tor.is_uploading ✗ → (not tor.is_complete) and (tor.is_uploading)（消除辖域歧义）。
  • 一元负号也算：-tor.size > 0 ✗ → (-tor.size) > 0；数字字面量里的 -5 不算运算符。
  • 括号组对其所在层是不透明黑盒：(tor.a + tor.b) > tor.c 的外层只有 >，合法。
  • 函数参数各自独立成层：min(tor.a + tor.b, tor.c * 2) 内部各算一层。
写法判定改成
tor.a and tor.b or tor.c✗ 该层 2 个运算符(tor.a and tor.b) or tor.c
tor.a and tor.b and tor.c✗ 该层 2 个运算符（同种也拒）(tor.a and tor.b) and tor.c
tor.ratio > 1.5 and tor.seeding_time > 3D✗ 该层 2 个运算符(tor.ratio > 1.5) and (tor.seeding_time > 3D)
tor.uploaded / tor.size > 1.5✗ 该层 2 个运算符(tor.uploaded / tor.size) > 1.5
tor.a + tor.b - tor.c✗ 该层 2 个运算符(tor.a + tor.b) - tor.c
not tor.is_complete and tor.is_uploading✗ 该层 2 个运算符(not tor.is_complete) and (tor.is_uploading)
tor.seeding_time >= 3D✓ 该层 1 个—
(tor.a and tor.b) or (tor.c and tor.d)✓ 外层 1 个、内层各 1 个—
freespace(tor.save_path) < 200GiB✓ 函数调用是 primary—
报错要能照着改：规则 x.条件[0]: 同一括号内只能有一个运算符（当前 2 个：and、and）—— 请加括号分组，如 (tor.a and tor.b) and tor.c。
判定退化为「每层运算符计数 > 1 即报错」，不需要策略表（原定的 _MIX_POLICY 五种分组取消，expr/policy.py 不再存在）。
代价与出口：表达式会变成“括号套括号”。若本意是「同种连续可以、只有异种才要括号」，把判定从「计数 > 1」改成「出现多种」即可 —— 一行的事；当前按「没有例外」取最严写法。
YAML 引号（必须写进文档）：表达式里出现 *（别名）、&（锚点）、#（注释）、{}[]（流集合）、: （键值分隔）在 YAML 里都有语义 —— 表达式一律用单引号或块标量包裹：- expr: >- 换行写，或 - expr: 'a * b > 100'。% 只在行首有语义，> 只在行首有语义（折叠），但别赌。

示例

# 磁盘快满时，优先砍掉大种子（比较与逻辑各自括号；函数调用是 primary）
- expr: '(freespace(tor.save_path) < 200GiB) and (tor.size > 50GiB)'

# 上传够了就停：分享率达标 或 做种够久
- expr: '(tor.ratio >= 2.0) or ((tor.seeding_time >= 7D) and (tor.uploaded > tor.size))'

# 闲置种子：3 天没动静且没人在下载（idle 是派生值, 省掉一个减法）
- expr: '((tor.idle > 3D) and (tor.num_leechs == 0)) and (not tor.is_checking)'

# 只在工作日夜间、且不在 HR 考核中的种子上跑
- expr: '((sys.dow <= 5) and ((sys.time_of_day >= 23:00) or (sys.time_of_day <= 7:00))) and (not tor.hr_condition_met)'

# 现算分享率（一层一个运算符 -> 括号）
- expr: '((tor.uploaded / tor.size) > 1.5) and (tor.seeding_time > 3D)'

# 70 个字段之外的新字段（qB 新版前向兼容）也能读
- expr: 'raw("some_new_field") > 0'

04 /取值面字段 · 派生 · 额外值 · 函数

取值面是唯一的新事实源，落在 rules/expr/env.py 一张表里：名字（含前缀）→ 取值器（属性直取 / 计算 / 全局 / 函数调用）+ 静态类型 + 是否昂贵 + 可用性判定器。schema 暴露、前端提示、文档生成都从这张表派生，不各写一份。

A. tor.* —— 种子字段（70 个快照字段）

即 TorrentRecord 的快照字段，与 qB TorrentDictionary 同名，加前缀使用：tor.hash tor.name tor.size tor.total_size tor.tags tor.category tor.state tor.downloaded tor.uploaded tor.dlspeed tor.upspeed tor.seeding_time tor.ratio tor.amount_left tor.completed tor.progress tor.dl_limit tor.up_limit tor.added_on tor.save_path tor.content_path … 直至 tor.has_tracker_error 共 70 个。编译期按 _SNAPSHOT_FIELDS 校验，拼错在启动时报错。
⚠ tor.tags 取的是集合（tags_set）：in 直接可用，~ 对集合的语义是「任一元素命中」；原始逗号串另给 tor.tags_raw。

B. tor.* —— 派生值（数据已在种子上，但要算一下）

名字类型语义
tor.is_downloading / is_uploading / is_complete / is_checking / is_stopped / is_paused / is_erroredboolstate_enum 的类别属性（与 qB 官方语义一致，取代 state 条件）
tor.progress_pctfloatprogress * 100
tor.tags_countint标签个数
tor.hr_condition_met / tor.hr_satisfiedbool取代 hr 条件三 mode；无 HR 配置 = false（有定义的缺省，不报错）
tor.upload_today / upload_week / upload_monthint取代三条增量条件（manager.upload_delta，自然日 / ISO 周 / 自然月）

C. tracker.* —— 站点配置

指的是哪个 tracker？ 一个种子在 qB 里可以有多个 tracker URL（外加 DHT / PeX / LSD 这些虚拟条目），但本程序的数据模型里，一个种子只绑定一个站点配置 TorrentRecord.tracker_conf：主循环 _refresh_torrents（qbmanager.py:684）把种子的 tracker URL 列表交给 _match_tracker_conf，按 hostname 精确匹配 config.trackers，命中多个配置时取第一个并打 ERROR 日志，一个都没命中则为 None。tracker.* 说的就是它 —— 与旧 trackers 条件同源同口径。

名字类型语义
tracker.namestr主站点配置名；未匹配站点 = "Unknown"（合法值，不是错误）
tracker.groupslist[str]主站点声明的分组；未匹配站点 = 空列表（沿用「无 tracker_conf 恒不匹配」，不报错）
tracker.namesset[str]需 tracker 缓存 该种子所有 tracker URL 各自命中的站点配置名集合 —— 给“一个种子挂了多个站”的用法；无命中 = 空集
tracker.urlstrqB 报告的主 tracker URL（= tor.tracker）；无 = 空串
用哪个？绝大多数种子只挂一个站 —— 用 tracker.name / tracker.groups。只有「一拖多站」的种子才需要 tracker.names（此时 tracker.name 只是被选中的那一个，选谁取决于 config.trackers 的顺序，本身就不稳定 —— 这种种子在现有模型里已经会被 _match_tracker_conf 打 ERROR 日志）。

E. 函数（白名单，参数受控，无前缀）

标注 昂贵 的取值都有 I/O 或 API 开销，必须走第 07 节的缓存，且靠 and/or 短路避免无谓调用。

名字可用性：三态 + 门控（单点判定）

  1. 恒定可用 —— 配置期只校验名字存在：tor.*、tracker.*、sys 的时间与计数、全部函数。
  2. 配置期门控（禁用） —— 值依赖某项配置才存在：当前只有 sys.upload_today / sys.download_today / sys.upload_month（依赖 global_speed_limit_curve.traffic_source）。没配 = 名字禁用，用了就在 load_config 报「该值无数据源」，不是等到运行时才炸。
  3. 运行期不可用（报错） —— 数据源当时拿不到：server_state 为 None / 键缺失、磁盘不可读、raw() 字段不存在、除零、类型不符 → 抛 ExprError → 按 05 的「出错即停规则」处理。
绝不降级成假值。sys.dl_speed 拿不到就是报错停规则，不返回 0 —— 返回 0 会让「全局速度低于阈值」这类条件在数据源失效时静默成真，进而批量触发限速/停止动作（这正是「保守默认」要挡的那类事故）。
反过来，「值不存在」≠「求值出错」：未匹配站点的 tracker.name = "Unknown"、无 HR 配置时 tor.hr_condition_met = false —— 这些是有定义的缺省（与旧条件同语义），正常参与求值，不报错、不停规则。

05 /语义类型与求值

  • 类型：int / float / bool / str / list / None。算术只对数值；and/or/not 只接受 bool（避免 size and ratio 这类歧义，报错比猜好）。
  • 哨兵不翻译：qB 的 -1（从未/未设）、-2（用全局默认）、8640000（无 ETA）原样透传。要判“从未传输”就写 last_activity == -1 —— 自动翻译成 0 会让“从未”和“刚刚”混为一谈。
  • 缺失值：字段缺失/不可得 → 抛 ExprError，不返回 None 参与比较。
  • 出错即停规则（已拍板）：求值抛 ExprError → Rule.process 的条件分支（base.py:196 的 try/except）改为返回 (False, True) = 不匹配 + 中断后续规则；日志 ERROR 级（规则名 + 表达式 + 种子 + 原因）。故障优先于 stop_following_rules_if：即使该规则配了 never，出错也停 —— 判据都不可信的时候，让后面的规则继续对这个种子做动作才是真风险。
  • 日志节流：同一规则同一类错误 5 分钟内只报一次（其后转 DEBUG 并计数），避免「每 tick × 每种子」刷屏；换原因或恢复后重新报。（与连接异常日志节流同一套路。）
  • 影响面：改的是 Rule.process 里条件异常的那一处分支，旧 16 个条件同样适用（它们抛异常时也停后续规则）—— 比现状更保守，方向一致。绝不让主循环崩，也绝不静默为真。
  • 纯函数 / 幂等：求值只读，不改任何状态；同一 tick 内同一表达式对同一种子结果稳定（缓存保证，见 07）。

静态检查（配置期能查出来的，别留到运行时）

  • 未知标识符（前缀写错 / 字段拼错）/ 未知函数 / 参数个数不符
  • 一层一个运算符违例（第 03 节），报错直接给出改写后的写法
  • 名字可用性：被数据源门控禁用的名字（如未配 traffic_source 时用了 sys.upload_today）
  • 字面量参与的不可能类型：tor.size > "abc"、"a" + 1
  • 比较链 a < b < c、括号不配对、单位非法（10GB）
  • 错误聚合进既有 errors 列表（与 _validate_plugin_entry 同风格），一次性报全，不做“遇到第一个就 raise”

07 /性能热路径与缓存

条件在每 tick 对「每个种子 × 每条命中规则」求值（interval: 0S 的规则就是每轮全跑），5000 种子 × 数十规则时是几万次/轮。三条硬约束：

  • 编译一次：解析与标识符解析全在构造期完成，AST 节点直接持有取值器对象，运行期不做字符串查表、不重新解析。
  • 必须短路：and/or 在解释器里显式短路 —— 否则 seeding_time > 3D and freespace("R:/") < 100GiB 会给每个种子都来一次磁盘系统调用。
  • 昂贵值按次缓存：RuleContext 加惰性 expr_cache: dict（field(default_factory=dict)），键 = 函数名+参数 / 昂贵字段名，生命周期 = 一次 process()。同一次规则执行里 freespace(save_path) 出现三次只查一次。不做 manager 级跨规则缓存 —— 跨规则共享要引入失效时机问题，违反「单一写线程」的简洁假设；真有需要再单开一轮。

实测（2026-09-21，uv run python scripts/bench_expr.py）

环境 Python 3.13.14 / Windows 11；合成种子（真 TorrentRecord）+ FakeClient，不连真实 qB。freespace 已打桩（否则测到的是磁盘）。

结论：单次 µs 级、编译可忽略；真正要多想的是一轮总量 —— 但上面是最坏情况（所有规则都 interval: 0S，每轮全跑）。常规配置下只有到期规则才求值，量级完全可接受。

基准跑出来的真问题（比数字重要）：freespace 打桩调用 **1.4 万 / 3.1 万次**，几乎等于含该档的求值次数 —— 因为生产每条规则新建 ctx，第 07 节的按次缓存只对同一条规则内多次出现有效，跨规则不复用。于是 freespace() 落在 interval: 0S 的规则里 = 每轮每种子一次磁盘调用（几千种子 = 每轮几千次系统调用）。
对策：① 文档写明「含 freespace / file_count / 全局计数的规则必须配 interval」；② 未来可选 manager 级 tick 缓存（需设计失效时机，本轮不做，避免引入第二个缓存生命周期）。

10 /风险已知坑与待拍板

已知坑

  • YAML 引号是头号踩坑点（第 03 节注）。文档与 schema 的 help 都要写，placeholder 直接给带引号的示例。
  • 静态检查别过度：只查字面量与已知类型能判定的冲突，字段值类型（如 tracker 是 str 还是空）运行期才能定，误报会让用户改不动配置。
  • raw() 是逃生舱也是漏洞：编译期不校验名字，运行期缺失报错 —— 必须在文档里写明“仅用于 qB 新字段，稳定字段请用正式名”。
  • 昂贵函数在 interval=0S 的规则上是地雷：file_count() 每轮每种子一次 API。文档标注 + 考虑在静态检查里对“未配 interval 却用了昂贵函数”给 WARNING（不是错误）。
  • 断点续跑不受影响：process() 只在 fresh 时评估条件（base.py:191），表达式求值纯读取，不干扰 resume_index 语义。
  • 括号会明显变多：一层一个运算符的代价是 ((a > b) and (c > d)) and (e > f) 这种嵌套成为常态，连 a and b and c 都要拆。换来的是「读配置的人完全不用想优先级、写的人也无处写错」。判定只有一处（计数 > 1），要放宽成「同种连续放行」是一行改动。
  • 前缀让表达式变长：tor.seeding_time 比 seeding_time 长 4 个字符，但换来了 group.* / tracker.* 的可扩展性，也让「这个值从哪来」一眼可见 —— 值得。

已拍板（2026-09-20，不再回退）

  1. 并存 —— 新增 expr，旧 16 个条件保留，生产 config.yml 不动。
  2. 前缀 —— tor.* / tracker.* / sys.*，group.* 留位后续做。
  3. 额外值按数据源启用 —— 没数据源 = 名字禁用（配置期可判即拒绝）；运行期不可得 = 报错，绝不返回假 0。
  4. 出错即停规则 —— (False, True)，故障优先于 stop_following_rules_if。
  5. 一层一个运算符，没有例外 —— not / < / and / + / % 一律占一层，同层出现第二个（同种连续也算）即报错；判定 = 「每层运算符计数 > 1」，无策略表。
第 4 条的代价要写进文档：一条规则的条件出错，该种子这一轮后续规则全停。这是刻意的保守取向（判据不可信时不许后面的规则继续动作），但它意味着「某条规则写错」的爆炸半径是整条规则链 —— 所以日志必须 ERROR 级 + 节流后仍可见，且文档里写明“条件报错会让后续规则一起停”。

11 /延伸动作要不要也进这套体系

问题原形：if (tor.size >= 10GiB) { tor.stop() } —— 把动作也写成表达式体系里的东西。结论：能，但要分三档，代价差一个量级。共同点是「条件那一半」完全复用本计划的 expr 内核（一层一个运算符照样生效）；分歧在动作那一半要吃下多少语义。

档内容写法例代价建议
L1动作参数表达式化add_tags: ["= tor.name + '-HR'"]小 —— 复用 expr 内核，纯求值、无副作用顺手做
L2动作区支持 if / elseif (tor.size >= 10GiB) { stop() }中 —— 语句层语法 + 断点路径化 + 校验 + UI 卡片多一层单开一轮
L3动作全面脚本化tor.size >= 10GiB ? tor.stop() : add_tags(["x"])大 —— UI 从卡片变文本框、四态结果塞进表达式、断点语义重做不建议

为什么不建议 L3（四个硬点）

  1. 动作返回的不是 bool。动作结果是四态 success / skipped / failed / pending（base.py 的 ActionResult）；failed 要 break、pending 要断点 —— 这是顺序控制流，不是布尔逻辑。表达式体系里没有它的位置，if (tor.stop()) 这句话本身就问不出来。
  2. 断点是扁平索引。现在 task.resume_index = i + 1（base.py:224）就是「第几个动作」。动作一旦嵌套进 if/else，断点得变成节点路径，续跑时还要保证 if 条件不重估（与现状「续跑跳过条件评估」同口径）。可做，但等于重做断点契约 —— 风险正好压在最复杂那条路径上（full-checking pending 续跑）。
  3. 副作用必须关进笼子。求值必须纯读取（幂等，黄金法则 1）。tor.stop() 一旦可以出现在条件位置就是灾难，得靠语法位置硬性禁止：动作只允许出现在动作区。
  4. UI 会掉一半。现在动作是可视化卡片，每个插件有自己的 spec 表单（checking 还是多层子表单，config_rules.js 按 schema 渲染）。脚本化 = 只能给一个文本框，图形化配置编辑器这个方向基本作废。

如果做 L2，具体怎么落地

  • 语句层：动作区是语句列表，语句 = 动作项 ｜ if (expr) { 语句列表 } ｜ if (expr) { … } else { … }。条件就是本计划的 expr。
  • 动作形态建议保持不变（- stop: true 这种单键字典项），if 只是把它包起来。这样 object 型 spec（checking / move_to / add_category）不用去设计关键字参数语法，改动面最小。
  • 前缀：tor.stop() 里的 tor. = 作用对象，与取值面的前缀语义一致（将来 group.stop() 同理）。若采用上一条「列表项」形态则不需要前缀 —— 列表项天然作用于当前种子。
  • 断点：resume_index 从 int 改路径（如 (2, "then", 1)），续跑按路径跳到该语句；if 条件在续跑时不重估（路径已含分支选择）。
  • 伪动作：ignore_next_action_error 在 AST 下改为语句级属性，或继续保留为伪语句（语义不变）。
  • 校验与 UI：_validate_plugin_entry 扩展为「语句校验」；schema 的动作卡片要能嵌一层 if 容器。
建议：本轮（W1–W4）只做条件表达式，可选顺手带上 L1 动作参数。L2 单开一轮，且严格限在「if/else 包住现有列表项」—— 那样断点改造是唯一的大头，动作本身的 spec 形态一个都不用动。

候选 · 不进本轮 L1（动作参数表达式）明细

与条件表达式安全边界一致：都是纯读取、都能在配置期静态检查、都不产生副作用。这是它可行的核心理由。三种形态，代价从小到大：

  • L1-a 内插 —— 扩展现有 utils.replace_vars（今天只有 ${required_seeding_time}，且只吃 tracker_conf，拿不到种子）到 tor.* / tracker.*。约十几行，是 L1 的既有雏形。
  • L1-b 整值 —— 参数以 = 开头则整串按 expr 求值，结果按目标类型校验。例 upload_speed_limit: "= tor.size / (24 * 3600)"。
  • L1-c 显式键 —— {expr: "..."}，无歧义但啰嗦，不推荐。

两个必须先定口径的坑（与条件那一边不同）：

  1. 求值时机 → 幂等。条件在 matches() 里求值、断点续跑时跳过（base.py:191 的 fresh 判定）；动作参数在 execute() 内、每次执行都算，含续跑那一次。参数里若用了 sys.now，首次与续跑会算出不同值 —— 要么把首次结果随断点持久化，要么禁止动作参数用时变值。
  2. 出错语义。条件出错 = 停规则（已拍板）；动作参数算不出来 → 建议动作 fail（走 ignore_error / break 语义），绝不静默回落成空串或默认值（回落会让“移动到空路径”这类事真的发生）。

成本结构与条件相反：条件是「内核为主、接线是常数」；L1 复用同一套内核，成本几乎全在接线 —— 12 个动作 spec 形态各异（bool / list / object / speed / str），object 型（add_category / move_to / checking）还要逐字段开口。校验侧另需新增「参数期望类型」元数据，UI 才知道哪个框能填表达式。

排序（与 python 插件的关系）：条件表达式 → 用一阵 → 再决定做 L1 还是直接支持 python 插件。插件一旦落地，「按种子大小算限速」这类需求会被更通用的方式吃掉，L1 的全量接线可能白做。所以 L1 只做 L1-a + 1~2 个高频字段的整值表达式，12 个动作全接一遍等真实需求。
