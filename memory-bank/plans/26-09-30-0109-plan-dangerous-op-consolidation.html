01 / BACKGROUND

背景与现状

1.1线程模型要点：单一写线程 + 唯一命令消费点 = 天然串行器

本仓库的核心线程契约是单一写线程：所有对 qB 的写操作、任务队列结构与 state_file 的修改都只发生在主循环线程（taskqueue.py:4、webui/runtime.py:21-26）；WEB 线程只读快照 + 投递命令。主循环内三条时间线：同步线（1.5s，只刷快照，qbmanager.py:619）、任务线（2s，跑任务，qbmanager.py:632）、命令线（主循环每轮顶部 drain，qbmanager.py:422-423）。

命令线由 wake_event 驱动：WEB 提交即唤醒主循环（runtime.py:529），消费延迟 ≈ 0（qbmanager.py:100-124 _wait_next），且改状态的命令当轮强制补刷新把真值推进快照（P0-5，qbmanager.py:435）。两条关键推论：

推论一（串行器）：命令消费点全仓唯一（qbmanager.py:423）。凡「一次阻塞跑完」的执行体——跳检全程约 6s（_poll_until 内是 time.sleep，skip_checking.py:21）——执行期间不会有任何其它写操作插入。危险操作的互斥，一半由这个架构事实免费提供。推论二（及时性现状）：WEB 操作今天就是近零延迟执行的；任何新机制若把执行推迟到周期性节拍上，都是回退。

1.2实证冲突点（现状即已存在，非未来 hypothetical）

#冲突机理与后果
C1 WEB 校验 × 规则校验
commands.py:304-307		 WEB recheck_torrent 只判「hash 在快照中」，不查规则侧在途登记 _active_checks（taskqueue.py:141）、不查失败冷却 RECHECK_FAIL_LIMIT（full_checking.py:34-52）。规则校验进行中用户再发 recheck → qB 重启校验 → 规则轮询子任务看到进度回落，可能触发 CHECK_START_GIVEUP（600s 宽限）误判失败、污染当日失败计数。反向：WEB 校验不登记，规则决策链 1.5「组内校验串行化」（active_check_hashes()）看不见它。
C2 WEB 删除 × 跳检的陈旧快照竞态
skip_checking.py:39-215		 ⚠ v2 机理修正：跳检执行体一次阻塞跑完（1.1 推论一），窗口期 WEB 命令不可能插入执行——v1 把机理写成「窗口期插入致重加确认失败」是错的。真实竞态在边界：跳检任务按上一轮快照创建，闸门（skip_checking.py:124-152）读陈旧记录；WEB 删除在循环顶部先执行、qB 端尚未生效时，跳检继续走 导出→备份→删除（空操作）→确认消失→重加——把用户刚删的种子复活；删除已生效则导出失败、干净放弃（噪声失败）。
C3 WEB 汇报 × 规则限频
transfer.py:34-45		 规则侧 reannounce 按种子计 state["reannounce_ts"] 强制 600s 最小间隔；WEB 侧 reannounce_torrent 独立计数、不走这套限频。用户 WEB 点一次 + 规则窗口外触发一次 → 同一种子短时间内连续两次 announce，只能靠 qB/tracker 端 min-interval 兜底。
C4 WEB 移动/批量无在途感知
commands.py:354-361		 set_torrent_location 与 bulk_torrents 对移动/删除/校验无冷却、无限频、无在途互斥。规则 MoveToAction（transfer.py:10-23）不判 save_path 是否已在目标，仅靠规则级 execute_once/cooldown 兜底。v2 处置：接受现状（§3.5）。

1.3现有防护盘点：规则侧完整，WEB 侧只有一条守阵

规则侧防护链相当完整：决策链闸门（仅暂停中未完成种子、组内整组判定）、_active_checks 在途去重（taskqueue.py:141）、决策链 1.5 组内校验串行化、RECHECK_FAIL_LIMIT 3 次/日失败冷却、skip_check_day 跨规则同日去重、reannounce 600s 限频。WEB 侧只有一条「hash 在快照中」守阵。统一的方向不是新基建，而是把 WEB 提交点接到规则侧已有的登记 / 限频 / 去重上——这正是 §03 的全部内容。

02 / REJECTED

否决记录：全局操作队列模式（v1 → v2）

v1（同日 01:09 版）设计了「六队列（skip_check/recheck/delete/move/add/reannounce）+ 全局执行槽 max_running + 跨队列 hash 锁 + 失败 halted + 持久化恢复 + 延迟回执 + 队列面板」的完整基建，分 M1–M4 四期。经评审否决，本版替代；v1 的五个决策点（D1 max_running / D2 删除重启挂起 / D3 延迟回执 / D4 enabled / D5 priority）随之全部废止。否决原因：

#原因一句话机理
1执行槽的保护是虚的重 I/O 都发生在槽让出之后（recheck/skip_check 的 inflight、move 的 qB 异步搬移），槽实际串行化的只是毫秒级 API 提交；反而引入跨队列队头阻塞——两个卡死的 qB 调用占满槽，六个队列全部停摆。
2泵挂任务线造成延迟回退WEB 提交本可 wake 即时消费（runtime.py:529 → qbmanager.py:422），挂 2s 任务线后最坏等 2s+——仓库已有的唤醒机制被绕开（1.1 推论二）。
3move 的「短操作」分类站不住setLocation 毫秒返回、真搬移在 qB 后台异步；按「API 返回即终态」，队列内串行挡不住 qB 端并发搬移——声称要防的资源冲击照样发生。
4bulk 多 hash 粒度无解hash 锁全有或全无 → 凑不齐全部空闲即永久推迟（饥饿）；失败 / halted / 回执都要为多 hash 额外定义一套粒度。
5用户操作排队是自造问题直接执行下，「用户操作优先于规则」（v1 D5）这个问题根本不存在；排队才制造出饥饿与优先级需求。
6复杂度与收益不匹配六队列 + 持久化恢复 + 延迟回执 + 面板 ≈ 300–400 行新模块 + 四期；而四个实证冲突用三处提交点检查 + 一处闸门复核即可覆盖（§03）。
7队列的前提不成立「让出执行槽」暗示长操作非阻塞化；当前模型下阻塞执行体 + 单一写线程本身就是串行器（1.1 推论一）——队列是在给已有的性质再买一遍。

从 v1 保留的资产：C1–C4 取证与冲突清单（C2 机理已修正，见 §1.2）、操作危险度盘点（谁该被管：跳检 / 校验 / 删除 / 移动 / 添加 / 汇报）、「业务幂等闸门留在提交侧」的职责划分。

03 / DESIGN

设计方案：三处提交点检查 + 一处闸门复核

3.1核心原则：不建新基建，只补提交点动作

  1. 在途可见：长操作把「我在途」写进已有登记（_active_checks 先例）；短操作提交点只读查询，拒已在途、不挡其它。
  2. 动手前复核：长操作从「快照时代的决定」到真正动手之间，用实时状态复核一次——快照龄内的外部变化（用户删除等）在此被拦截。
  3. 计数共享：有速率语义的操作（reannounce），两来源读写同一份计数，而不是各记各的。

3.2R1 — WEB recheck 接入校验在途体系（修 C1，双向）

P1 最小版（提交点只读检查）：recheck_torrent handler 提交前加判——hash ∈ _active_checks 或快照 state 属 checking 类 → 回执「校验进行中」拒绝，qB 不重启校验。C1 的 WEB→规则半边当期闭合，全部代价是一次集合查询。

P2 全收编（D1-A）：WEB recheck handler 改调 full_checking 的提交路径（提交 recheck + check 轮询子任务 + _active_checks 登记 + 失败冷却），source 标记 web。免费获得：规则决策链 1.5 经 active_check_hashes() 看见 WEB 校验（反向闭合）；3 次/日失败冷却统一计数；校验完成后轮询 FINISHED 释放在途登记（taskqueue.py kind=="check" 既有语义）。唯一适配点：check 轮询子任务的 origin 重入队语义（full_checking.py:176）对 web 来源退化为「无 origin，FINISHED 即消亡」。

3.3R2 — 跳检闸门后、动手前的实时复核（修 C2）

位置：前置闸门 _skip_gates 通过后、导出之前（skip_checking 阶段 1 与 2 之间）。动作：torrents_info(hash) 重拉一次实时状态；种子已不在 → ActionResult.skip("种子已被移除(可能被用户删除), 放弃跳检")——发生在备份与删除之前，零副作用，无孤儿备份。

效果：消灭「按陈旧快照执行」这个主要形态；竞态窗口从快照龄（≤2s）压缩到「复核→删除」的毫秒级缝隙（qB 删除生效延迟），且残余方向安全（最坏导出失败、干净放弃）。跳检是天级低频操作，多一次 API 调用成本可忽略。

3.4R3 — WEB reannounce 对齐 600s 限频（修 C3）

WEB handler 提交点查 state["reannounce_ts"]：窗口内 → 回执「N 秒前刚汇报过，稍后再试」拒绝；执行成功后写同一份计数。两来源共享一个窗口，不再依赖 tracker min-interval 兜底。

3.5C4 — 接受现状（记为已知限制）

move 幂等可逆、规则侧已有 execute_once/cooldown、WEB 移动是用户显式动作且即时回执——维持现状。若未来实证冲击（做种速度下滑 / 移动堆积），再单独立项「moving 态 inflight 感知」：判定材料现成（record.py:231 state_enum，版本无关的状态类别判定）。本计划不预支。

3.6WEBUI 右键「跳检」（需求场景落地）

WEB 命令表加一项 → handler 包装现有 _execute_skip_checking 执行体（source=web）。天然性质，无需新机制：命令在主循环线程执行 → 与规则跳检天然串行（线程即队列）；skip_check_day 跨来源去重免费；阻塞 ~6s 期间其它 WEB 命令排队等待——与规则跳检执行时的现状一致。前端：右键菜单项 + 危险确认框（跳检清空本地统计，须显式确认）。前置依赖：R2 先落地（实时复核同样保护 WEB 触发的跳检）。

3.7可选：在途操作只读视图（D2）

GET /api/inflight 只读端点：列 _active_checks（+ 若实现，跳检窗口标记）。这是 v1「队列面板」的降级替代。倾向：不做——校验在途在种子列表 checking 态已可见，跳检窗口 6s 且天级低频；等真实需要再立项。

3.8红线（随本计划入档）

阻塞执行体 + 单一写线程是当前安全模型的一半。跳检窗口的互斥 = 主循环被阻塞（1.1 推论一）。任何把长操作改成非阻塞 / 分阶段 / 独立线程的优化，必须同步把「在途标记」升级为提交点强制检查的互斥层，否则 C1/C2 类竞态以新形态回归。新来源（HR 联动 / 外部 API / 定时任务）接入一律走同一套提交点检查，不开旁路。

3.9非目标（明确排除）

  • 不建队列模块 / 执行槽 / 延迟回执改造 / 操作优先级——v1 基建全部不做（§02）。
  • 零新增配置键（validate_config 与 schema.py 无改动）、零新增线程、零 state_file schema 变更。
  • 不改规则决策链业务语义（哪些种子该跳检 / 校验的判定逻辑不动）；delete/move/add 的规则侧行为不变。

05 / TESTING

测试 · 成本 · 回滚

5.1测试计划（新增用例同步进各测试文件头「测试计划」清单）

  • test_skip_checking 扩展：闸门复核——任务运行前种子已消失 → skip、无副作用、无孤儿备份；正常跳检路径回归对照。
  • test_full_checking 扩展（P2）：web 来源提交 → 登记 / 冷却计数 / 轮询 FINISHED 消亡、无 origin 副作用。
  • WEBUI commands 测试扩展：recheck 拒绝路径（在途时）；reannounce 600s 拒绝路径 + 执行后写同一份计数。
  • 回归：现有 test_skip_checking / test_full_checking 全绿 + commands run test.quick。

5.2成本与风险

项评估
代码量预计 ≤ 150 行含测试；全部落在现有 handler / 闸门 / 动作文件。无新模块、无配置键、无持久化变更、无迁移。
行为变化仅两处显式收紧：WEB recheck 会被「校验进行中」拒绝；WEB reannounce 受 600s 窗口约束。均为冲突修复的本意。
残余风险R2 复核后到删除之间的毫秒级缝隙（qB 删除生效延迟）依旧存在，方向安全（最坏导出失败干净放弃）；如未来要彻底闭合，在重加前再查一次即可，不预支。
回滚每 R 独立 commit；无状态迁移，revert 即回到现状。
