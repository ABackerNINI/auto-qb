01 / BACKGROUND

背景与现状

1.1线程模型要点：单一写线程 + 唯一命令消费点 = 天然串行器

本仓库的核心线程契约是单一写线程：所有对 qB 的写操作、任务队列结构与 state_file 的修改都只发生在主循环线程（taskqueue.py:4、webui/runtime.py:21-26）；WEB 线程只读快照 + 投递命令。主循环内三条时间线：同步线（1.5s，只刷快照，qbmanager.py:619）、任务线（2s，跑任务，qbmanager.py:632）、命令线（主循环每轮顶部 drain，qbmanager.py:422-423）。

命令线由 wake_event 驱动：WEB 提交即唤醒主循环（runtime.py:529），消费延迟 ≈ 0（qbmanager.py:100-124 _wait_next），且改状态的命令当轮强制补刷新把真值推进快照（P0-5，qbmanager.py:435）。两条关键推论：

推论一（串行器）：命令消费点全仓唯一（qbmanager.py:423）。凡「一次阻塞跑完」的执行体——跳检全程约 6s（_poll_until 内是 time.sleep，skip_checking.py:21）——执行期间不会有任何其它写操作插入。危险操作的互斥，一半由这个架构事实免费提供。推论二（及时性现状）：WEB 操作今天就是近零延迟执行的；任何新机制若把执行推迟到周期性节拍上，都是回退。

1.2实证冲突点（现状即已存在，非未来 hypothetical）

#冲突机理与后果
C1 WEB 校验 × 规则校验
commands.py:304-307		 WEB recheck_torrent 只判「hash 在快照中」，不查规则侧在途登记 _active_checks（taskqueue.py:141）、不查失败冷却 RECHECK_FAIL_LIMIT（full_checking.py:34-52）。规则校验进行中用户再发 recheck → qB 重启校验 → 规则轮询子任务看到进度回落，可能触发 CHECK_START_GIVEUP（600s 宽限）误判失败、污染当日失败计数。反向：WEB 校验不登记，规则决策链 1.5「组内校验串行化」（active_check_hashes()）看不见它。⚠ v3 补充取证：bulk_torrents action=recheck（commands.py:458-459）同样直调 API——C1 的第二入口，P1 必须同查，否则批量路径留旁路。
C2 WEB 删除 × 跳检的陈旧快照竞态
skip_checking.py:39-215		 ⚠ v2 机理修正（沿用）：跳检执行体一次阻塞跑完（1.1 推论一），窗口期 WEB 命令不可能插入执行——v1 把机理写成「窗口期插入致重加确认失败」是错的。真实竞态在边界：跳检任务按上一轮快照创建，闸门（skip_checking.py:124-152）读陈旧记录；WEB 删除在循环顶部先执行、qB 端尚未生效时，跳检继续走 导出→备份→删除（空操作）→确认消失→重加——把用户刚删的种子复活；删除已生效则导出失败、干净放弃（噪声失败）。
C3 WEB 汇报 × 规则限频
transfer.py:33-45		 规则侧 reannounce 按种子计 state["reannounce_ts"] 强制 600s 最小间隔；WEB 侧 reannounce_torrent 独立计数、不走这套限频。用户 WEB 点一次 + 规则窗口外触发一次 → 同一种子短时间内两次 announce，由 qB/tracker 端 min-interval 兜底。v3 处置：降级「已知无害现状」，与 C4 同口径——600s 是防自动化连发（规则每 2s tick）的自限频，不适用于人手点击；对 WEB 设限产生「按钮为什么不生效」困惑（否决理由见 §02.2）。
C4 WEB 移动/批量无在途感知
commands.py:354-361		 set_torrent_location 与 bulk_torrents 对移动/删除/校验无冷却、无限频、无在途互斥。规则 MoveToAction（transfer.py:10-23）不判 save_path 是否已在目标，仅靠规则级 execute_once/cooldown 兜底。v3 处置：接受现状（§3.9），与 C3 同口径。

1.3现有防护盘点：规则侧完整、WEB 侧一条守阵，且执行体与保护长在规则 mixin 里

规则侧防护链相当完整：决策链闸门（仅暂停中未完成种子、组内整组判定）、_active_checks 在途去重（taskqueue.py:141-144）、决策链 1.5 组内校验串行化、RECHECK_FAIL_LIMIT 3 次/日失败冷却、skip_check_day 跨规则同日去重、reannounce 600s 限频。WEB 侧只有一条「hash 在快照中」守阵。

但 recheck / skip_check 的执行体与这些保护是长在一起的：_execute_full_checking / _execute_skip_checking 是 CheckAction 的 mixin 方法（checking.py:18、full_checking.py:55、skip_checking.py:36），参数是规则侧 RuleContext，保护状态（在途登记 / recheck_fails / skip_check_day）散在动作实现与 state 键里。v2 的结论「把 WEB 提交点接到规则侧已有体系上」意味着 WEB 伪造 RuleContext、适配 origin 重入队语义、读写规则私有 state 键——依赖方向做反，改一处动两处（§02.2）。v3 的结论：执行体与保护抽成独立层，两个来源都依赖它。抽的不是新基建——执行体今天已经存在，只是长在规则 mixin 里。

02 / REJECTED

演进与否决记录

2.1v1 → v2：全局操作队列模式否决（26-09-30 01:09 版）

v1（同日 01:09 版）设计了「六队列（skip_check/recheck/delete/move/add/reannounce）+ 全局执行槽 max_running + 跨队列 hash 锁 + 失败 halted + 持久化恢复 + 延迟回执 + 队列面板」的完整基建，分 M1–M4 四期。经评审否决，由 v2 替代并保留至今；v1 的五个决策点（D1 max_running / D2 删除重启挂起 / D3 延迟回执 / D4 enabled / D5 priority）随之全部废止。否决原因：

#原因一句话机理
1执行槽的保护是虚的重 I/O 都发生在槽让出之后（recheck/skip_check 的 inflight、move 的 qB 异步搬移），槽实际串行化的只是毫秒级 API 提交；反而引入跨队列队头阻塞——两个卡死的 qB 调用占满槽，六个队列全部停摆。
2泵挂任务线造成延迟回退WEB 提交本可 wake 即时消费（runtime.py:529 → qbmanager.py:422），挂 2s 任务线后最坏等 2s+——仓库已有的唤醒机制被绕开（1.1 推论二）。
3move 的「短操作」分类站不住setLocation 毫秒返回、真搬移在 qB 后台异步；按「API 返回即终态」，队列内串行挡不住 qB 端并发搬移——声称要防的资源冲击照样发生。
4bulk 多 hash 粒度无解hash 锁全有或全无 → 凑不齐全部空闲即永久推迟（饥饿）；失败 / halted / 回执都要为多 hash 额外定义一套粒度。
5用户操作排队是自造问题直接执行下，「用户操作优先于规则」（v1 D5）这个问题根本不存在；排队才制造出饥饿与优先级需求。
6复杂度与收益不匹配六队列 + 持久化恢复 + 延迟回执 + 面板 ≈ 300–400 行新模块 + 四期；而实证冲突用提交点检查 + 闸门复核即可覆盖（§03）。
7队列的前提不成立「让出执行槽」暗示长操作非阻塞化；当前模型下阻塞执行体 + 单一写线程本身就是串行器（1.1 推论一）——队列是在给已有的性质再买一遍。

2.2v2 → v3：收编方向废弃（26-09-30 用户评审，两条修订）

v2 的「提交点检查」骨架保留（R2 实时复核 / R1 提交点拒绝），但其中两处经评审否决：

(a) R3 废止——WEB reannounce 600s 对齐整条删除，C3 降级无害现状

  • WEB 汇报是用户的显式选择，频率天然有界。规则侧 600s 的存在理由是防自动化连发——规则每 2s tick，没有自限频会对同一种子无限连发 announce，那才会被封号；把自动化限频套到人手上，拒绝回执就是「按钮为什么不生效」。
  • 危害 ≈ 0：reannounce 只是一次 announce 请求，qB/tracker 端 min-interval 本来就在兜底。对比之下 C4（move，有真实 I/O）都接受现状，危害更小的 C3 却要修——v2 口径不一致。
  • 共享计数半边（WEB 写 reannounce_ts 压制规则）纯耦合无收益：用户刚汇报过，tracker 状态新鲜，规则触发条件多半不会马上再触发；若 tracker 真有问题，压掉规则的自动重试反而有害。
  • 处置：R3 整条删除；C3 与 C4 同口径记「已知无害现状」（D3）。WEB reannounce 的行为、回执与 tracker 确认跟踪（REANNOUNCE_CONFIRM_TIMEOUT）完全不变。

(b) D1-A「全收编」废弃——P2 由收编改为操作层抽取（§3.4）

  • v2 让 WEB recheck 改调 full_checking 提交路径，是把依赖方向做反（web → rules 内部）：WEB 需伪造 RuleContext、适配 origin 重入队语义（full_checking.py:88/:176）；full_checking 为规则语义重构，WEB 随之断；WEB 有新诉求，得进规则模块里改——正是「改一处就要改另一处」。
  • 附带行为有害：WEB 校验计入 3 次/日失败冷却 = 同款「为什么不生效」——手动排障第 4 次 recheck 被当日冷却挡住。
  • 右键跳检同理：包装 _execute_skip_checking(ctx, segment, has_reference) 要带规则侧概念——has_reference=False 会把「无参考跳检(高风险)」的规则告警语义泄漏进 WEB。
  • 处置：v2 的 P2 由「收编」改为「操作层抽取」（§3.4，v3 期名 P2'）；D1 决策点改写（§06），保护策略按来源区分（§3.5）。

从 v2 保留的资产：R2 跳检实时复核、R1-P1 提交点只读检查（补 bulk 第二入口）、C1–C4 取证（含 C2 机理修正）、线程模型分析（1.1）、红线（§3.8）。从 v1 保留的资产：操作危险度盘点（谁该被管：跳检 / 校验 / 删除 / 移动 / 添加 / 汇报）、「业务幂等闸门留在提交侧」的职责划分。

03 / DESIGN

设计方案：独立操作层

3.1核心原则

  1. 依赖方向 rules → ops ← web：操作的 qB 交互序列、在途登记、保护策略单点归 ops 层；规则只保留决策（哪些种子何时该跳检/校验）与断点续跑，WEB 只保留入口与回执。修正 v2「WEB 接到规则侧体系」的反向依赖（§02.2）。
  2. 保护策略按来源区分：防「自动化频率失控」的保护（冷却、600s）只作用 source=rule；防「真实冲突」的保护（在途互斥、R2 复核、同日去重）作用所有来源。R3 的错误不是共享状态本身，而是把自动化限频套到人手上（§02.2）。
  3. 不建新基建，只换模块边界：ops 是同步阻塞函数，两个调用方都在主循环线程（WEB 命令线 drain + 规则任务线），单一写线程约束原样成立——执行模型与今天完全相同。§02.1 否决 v1 的七条理由没有一条适用于纯抽取。
判据：何时可以对 WEB 源「说不」。被拒时用户能否从界面自行看出原因。checking 态在种子列表可见 → R1 的「校验进行中」拒绝可自解释，保留；600s 窗口不可见 → reannounce 拒绝不可解释，不对 WEB 源设限。这条判据同时约束未来新增的任何 WEB 侧限制。

3.2R1 — WEB recheck 提交点拒绝（P1，修 C1 的 WEB→规则半边）

P1 最小版（提交点只读检查）：recheck_torrent handler 提交前加判——hash ∈ _active_checks 或快照 state 属 checking 类 → 回执「校验进行中」拒绝，qB 不重启校验。单发路径的全部代价是一次集合查询；bulk 路径另加在途过滤与聚合回执（下条）。

⚠ 必须覆盖第二条入口：bulk_torrents action=recheck（commands.py:458-459）同样直调 API——在途 hash 过滤，聚合回执带「N 个校验进行中已跳过」；漏掉它，批量路径就是 C1 的旁路。

P2' 后该检查迁入 ops_recheck 提交点（handler 守阵退化为回执映射），避免两处实现。WEB 源不受 3 次/日 冷却（D1）；WEB recheck 的 auto_start 恒 False（与 qB 自家 WebUI 行为一致，开始与否用户自己控制）。

3.3R2 — 跳检闸门后、动手前的实时复核（P1，修 C2）

位置：前置闸门 _skip_gates 通过后、导出之前（skip_checking 阶段 1 与 2 之间）。动作：torrents_info(hash) 重拉一次实时状态；种子已不在 → ActionResult.skip("种子已被移除(可能被用户删除), 放弃跳检")——发生在备份与删除之前，零副作用，无孤儿备份。

效果：消灭「按陈旧快照执行」这个主要形态；竞态窗口从快照龄（≤2s）压缩到「复核→删除」的毫秒级缝隙（qB 删除生效延迟），且残余方向安全（最坏导出失败、干净放弃）。跳检是天级低频操作，多一次 API 调用成本可忽略。本项纯规则内部补强，与抽取正交——P2' 搬家时随代码迁入 ops_skip_check，两来源同时受保护。

3.4P2' — 操作层抽取：rules → ops ← web（替代 v2 的 D1-A 收编）

形态：src/auto_qb/core/mixins/ops.py 新增 OpsMixin，组合进 QbManager（qbmanager.py:127-136 既有 mixin 序列追加，与 CheckingMixin / RuleEngineMixin 同模式）。选 manager 侧而非独立对象的理由：ops 依赖的三样东西（manager.api / task_queue / state）本来就挂在 manager 上，且 WEB 命令处理器的 self 就是 manager——调用零转换。两方法签名中 torrent 均为可选：None 时 ops 内部经 store 取活记录；规则侧 ctx.torrent 本就是实时 store 优先的 property，显式传参与缺省取值等价。

  • ops_recheck(hash, source, torrent=None, auto_start=False, on_success=None)：从 _execute_full_checking 搬「登记 check 轮询子任务 + 提交 recheck + 轮询」主干（full_checking.py:58-176）。规则侧差异全部收进参数：on_success 回调承载 origin 重入队（keep_progress）与晋升；source=rule 时失败冷却生效（_bump_recheck_fail），source=web 时冷却跳过、on_success=None（FINISHED 即消亡——full_checking.py:88「外部入口 origin=None」的退化路径已存在，抽取只是把这条内部路径转正为公开接口）。
  • ops_skip_check(hash, source, torrent=None, auto_start=False)：四阶段整体搬（skip_checking.py:39-121，含 _skip_gates / 备份 / 清理）；R2 复核落在阶段 1 与 2 之间，两来源同时受保护。has_reference「无参考高风险」告警是规则侧语义：随迁并按 source——web 不产生该告警（前端危险确认框已承担风险告知）。安全闸门（部分下载禁止跳检）全来源生效。
  • _active_checks 留在 TaskQueue：kind=="check" 的登记/释放与队列生命周期耦合（入队登记 taskqueue.py:141-144，FINISHED 释放 :181），挪出去要重新发明；ops 经 add_task 登记，决策链 1.5 经 active_check_hashes() 的查询照旧。这是抽取里唯一不追求「彻底」的地方。
  • CheckAction 变薄：_execute_full_checking / _execute_skip_checking 改为一行委托（ctx 字段 → ops 参数），决策链 0–4（checking.py:75-126）不动。
  • WEB handler 变薄：_cmd_recheck_torrent / bulk recheck 改调 ops（P1 的守阵迁入 ops 提交点，handler 只做回执映射）；右键跳检 handler 即 self.ops_skip_check(hash, source="web")。边界：webui 模块不得 import rules.*，加静态守阵测试钉住（v2 的收编方案做不到这一点——它要求 WEB 调进规则模块内部）。
  • 等价性红线：poll 闭包捕获的 ctx.torrent 依赖 store 原地更新的活记录语义——搬家时必须原样保留（不得改为每次 store.get 重查），由现有 test_full_checking 行为断言钉住。

3.5保护策略按来源区分（行为口径单点 · 生效范围 D1 待拍板）

保护防什么rule 源web 源理由

3 次/日校验失败冷却（recheck_fails）自动化 recheck 死循环（损坏文件）生效不生效手动排障不受限——限制它就是「为什么不生效」；且 WEB 源失败本就由人当场看见
reannounce 600s 限频（reannounce_ts）自动化连发 announce（封号风险）生效不生效人手点击频率有界；不可见窗口的拒绝 = 困惑 → C3 接受现状

3.6WEBUI 右键「跳检」（需求场景落地，依赖 P1 + P2'）

WEB 命令表加一项 → handler 调 self.ops_skip_check(hash, source="web")。天然性质，无需新机制：命令在主循环线程执行 → 与规则跳检天然串行（线程即队列）；skip_check_day 跨来源去重共享（拒绝文案「今日已跳检过」自解释）；阻塞 ~6s 期间其它 WEB 命令排队等待——与规则跳检执行时的现状一致。前端：右键菜单项 + 危险确认框（跳检清空本地统计，须显式确认）。前置依赖：R2（P1）先落地（实时复核同样保护 WEB 触发的跳检）+ ops 抽取（P2'）——v2 的方案（包装规则 mixin）因依赖方向反了而废弃（§02.2）。

3.7可选：在途操作只读视图（D2）

GET /api/inflight 只读端点：列 _active_checks（+ 若实现，跳检窗口标记）。这是 v1「队列面板」的降级替代。倾向：不做——校验在途在种子列表 checking 态已可见，跳检窗口 6s 且天级低频；等真实需要再立项。

3.8红线（随本计划入档）

阻塞执行体 + 单一写线程是当前安全模型的一半。跳检窗口的互斥 = 主循环被阻塞（1.1 推论一）。任何把长操作改成非阻塞 / 分阶段 / 独立线程的优化，必须同步把「在途标记」升级为提交点强制检查的互斥层，否则 C1/C2 类竞态以新形态回归。ops 层是这条红线的执行载体：新来源（HR 联动 / 外部 API / 定时任务）接入 = 新增一个 source 调 ops，不复制操作语义、不开旁路；ops 方法必须留在主循环线程调用。

3.9非目标（明确排除）

  • 不建队列模块 / 执行槽 / 延迟回执改造 / 操作优先级——v1 基建全部不做（§02.1）。
  • 不抽 reannounce / move / delete：单来源 + C3/C4 接受现状（D3/D4）；未来出现第三来源再扩 ops。
  • 零新增配置键（validate_config 与 schema.py 无改动）、零新增线程、零 state_file schema 变更。
  • 不改规则决策链业务语义（哪些种子该跳检 / 校验的判定逻辑不动）；delete/move/add/reannounce 的规则侧行为不变。
