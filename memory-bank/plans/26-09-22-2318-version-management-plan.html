01背景与结论

前提核实（2026-09-22 23:10 实测）：git 仓库健在——develop @ d4dea8b 与 gitee/develop 齐平（preflight.py --check-started PASS；本轮内自 49eacb8 快进合流主线 9 提交，含 src 布局归拢）、工作区干净、双远端齐全（gitee 主 + github 镜像）、多 clone 协作模式 2026-09-20 已定案运行。因此「没有版本管理」在本项目语境下的准确含义是 想法.md L281 待办「版本管理」所指的软件版本号与发布管理，不是版本控制工具本身。

核心结论：推荐组合 = 0.x 语义化版本（0.2.0 → 0.3.0 功能批次 / 0.2.1 修复）+ __init__.py 单源（pyproject 走 hatchling regex 动态接线，消灭双源）+ 手工三步发版（bump → commit → tag + 双远端 push，判定只看 ls-remote）+ Keep a Changelog（条目按既有 gitmoji 提交归类）+ 立即打 v0.2.0 基线 tag。三个待拍板决策点见 §09；阶段 0 全程不涉码。

版本号权威出处src/auto_qb/__init__.py 单源显示路径（托盘 / WEB UI）零改动，运行时零新增依赖，构建元数据自动跟随
发版动作手工三步 + ls-remote 判定与既有提交推送纪律同构，零新依赖；脚本化留作演进
变更记录Keep a Changelog + gitmoji 映射不改提交规范的前提下，把已有 gitmoji 历史低成本转成用户可读的变更记录

03目标与约束

  1. 单点事实源：版本号只允许一个权威出处——与 config/schema 单点、testing.md 基线单点同款项目哲学；双源漂移已经实际发生过（§2.2），不再是理论风险。
  2. 兼容 gitmoji + 中文提交规范：任何自动化不得以改成 conventional commits 为前提。
  3. 兼容双远端纪律：Gitee 为主线、判定只看 ls-remote；GitHub 镜像允许滞后，失败只报告一次不重试。
  4. 兼容工具 shell git 禁令：发版流程禁用 merge / rebase / stash；每一步都能被 ls-remote / show-ref 当场核验（本 shell 有 ref 静默丢弃先例）。
  5. 多 clone 感知：git fetch <remote> <分支> 不带 tag，四个 clone 的 tag 同步需要显式 fetch --tags 约定。
  6. 阶段语义：Beta + README 🚧 alpha 功能——版本号要能表达「不稳定但可用」，且给未来 1.0 留出里程碑语义。
  7. 最小改动：不引入构建期 git 依赖（无 tag 时构建失败的面）、不新增常驻工具、不改运行时代码路径。

04版本号方案对比

方案形态示例变更时机优点缺点判定
A. 0.x 语义化 0.2.0 → 0.3.0（功能批次）/ 0.2.1（修复） 人为判定 0.x = 「不稳定但可用」是社区惯例，与 Beta 自述一致；兼容 SemVer 工具链与依赖判断；单人可判 需要记得 bump——靠发版流程（§06）兜住 ★ 推荐
B. 正式 SemVer（1.x 起步） 1.0.0 同上 兼容承诺明确，用户可放心自动升级 Beta 期破坏性变更频繁会持续刷大版本；1.0 语义被透支 1.0 留作里程碑
C. CalVer 2026.9.0 日期驱动 新旧一目了然；零决策成本 对「能不能安全升级」零表达；单人工具的发布间隔不规律，日期语义弱 备选（保留）
D. 短哈希滚动 0.2.0+49eacb8 每次构建 零维护；溯源精确到提交 无里程碑语义、不可比较、不能当对外版本 仅作本地构建后缀

推荐 A，并为 1.0 设可判定的触发条件（三条全中再提 1.0）：① README 🚧 项清空；② 生产连续 2–4 周无数据风险事故；③ 配置 schema 冻结走完一个周期。在此之前 minor = 功能批次、patch = 修复，破坏性变更也走 minor（0.x 语义允许）。

05版本号载体对比

方案机制优点缺点判定
V1. pyproject 静态 + 运行时读元数据 版本写 pyproject；代码 importlib.metadata.version("auto-qb") 惯例位置；打包元数据单源 运行时依赖「项目已安装」；直接 python src/auto-qb.py 场景要兜底；包初始化次序曾有坑（web/common.py:31 注释实证） 可行
V2. __init__ 单源 + hatchling 动态 pyproject 声明 dynamic = ["version"]，构建时用 regex 从 src/auto_qb/__init__.py 提取 显示路径零改动（ui.py / web 照旧 import）；运行时零新增依赖；bump = 改一行；构建元数据自动一致，双源结构性消失 pyproject 不再静态可读版本（构建时推导）；接线后需 uv sync 刷新 uv.lock 内记录 ★ 推荐
V3. tag 驱动（setuptools-scm / hatch-vcs） 构建期从 git tag 推导，开发构建自动 .devN 零手改；溯源最精确 构建期需要 git 仓库与 tag 纪律；无 tag 构建即失败；与本 shell 的 git 怪癖叠加后排查链最长 未来选项
V4. 双写（现状） pyproject 与 __init__ 各写一份 — 漂移已实证：0.1.0 vs 0.2.0；违反单点事实源 ✗ 否决

5.1 V2 接线示意（阶段 1 实施，本方案不动代码）

[project]
name = "auto-qb"
dynamic = ["version"]              # 移除静态 version = "0.1.0"
...
[tool.hatch.version]
source = "regex"
path = "src/auto_qb/__init__.py"   # __version__ = "0.2.0" 成为唯一权威出处

配套守阵（阶段 1 一并落）：测试断言 auto_qb.__version__ 匹配 SemVer 正则（^\d+\.\d+\.\d+$）；可选加一条 uv.lock 内记录与 __version__ 一致性校验。

06发版流程与 CHANGELOG

6.1 发版流程对比

方案流程与既有约束的咬合判定
T1. 手工三步 ① bump __version__ + 写 CHANGELOG 段 → ② gitmoji commit → ③ tag + 双远端 push + ls-remote 核对 与现有「提交即推送、判定只看 ls-remote」纪律完全同构；零新依赖 ★ 起步推荐
T2. release 脚本 scripts/release.py：前置校验（工作区净 / 测试绿 / 与远端齐平）→ bump → changelog 草稿 → tag → push + 核对 把 T1 的四条纪律固化成机检，防呆 演进方向（阶段 2）
T3. 自动定版（python-semantic-release 等） 解析 conventional commits 自动决定版本号 要求改提交格式，与 gitmoji + 中文提交规范冲突 ✗ 否决
T4. git-cliff 配套 git log → CHANGELOG 草稿；regex 自定义解析器可按 gitmoji 归类（git-cliff.org，2026-09-22 检索确认在维护） 不要求改提交规范，只消费既有历史；多一个 CLI 工具 可选（阶段 2）

6.2 T1 的发版三步（命令级）

# ① bump：src/auto_qb/__init__.py 的 __version__ 改一行 + CHANGELOG.md 补本版段
# ② commit（gitmoji 规范），随主提交走 my-commit-flow 预检
git tag -a v0.3.0 -m "auto-qb v0.3.0"
git tag -l v0* ; git show-ref --tags          # 本 shell ref 写入有静默丢弃先例, 当场核对
# ③ 推送与判定
git push gitee develop v0.3.0                 # 显式 ref, 与分支推送同纪律
git ls-remote --tags gitee                    # 「推没推上」只看这里
git push github develop v0.3.0                # 镜像; 失败只报告一次, 不重试

6.3 CHANGELOG 规范

  • 格式：Keep a Changelog；文件 CHANGELOG.md；顶部 ## [Unreleased] 滚动段，发版时改名 ## [X.Y.Z] - 日期。
  • 分类沿用既有 gitmoji 提交映射（内容引用，不是装饰）：
提交里的 gitmojiCHANGELOG 段默认
✨Added（新功能）入册
🐛Fixed（修复）入册
⚡️Changed（性能 / 行为变化）入册
♻️并入 Changed（仅当有可感知行为差异）默认省略
📝 ✅ 🔧 🎨 💚 等文档 / 测试 / 内部杂务默认不入册

草稿低成本取法：git log v上一版..HEAD --oneline 按 emoji 归类后再人工润色；历史无 tag 区间用提交哈希区间代替。

07落地路线（三阶段）

阶段 0 —— 不涉码，拍板后即可做

  1. 建 CHANGELOG.md：Unreleased 空段 + [0.2.0] - 2026-09-22 一句基线说明（「首个版本基线；此前为开发期，历史见 git log」）。
  2. 打基线 tag：git tag -a v0.2.0 @ 49eacb8（当前工作区净且与远端齐平，是干净基线点）；打完 show-ref --tags 当场核对。
  3. 推送与判定：git push gitee develop v0.2.0 → git ls-remote --tags gitee 核对；github 镜像尝试一次，失败只报告一次。
  4. 约定回写：发版三步 + fetch --tags 多 clone 约定写入 conventions/collaboration.md（AGENTS.md 只留指针，注意 8000 字符上限）。

阶段 1 —— 涉码，单独立项走认领流程

  1. pyproject 改 dynamic = ["version"] + [tool.hatch.version] regex 接线（§5.1）；接线后 uv sync 刷新 uv.lock。
  2. 版本守阵：SemVer 正则断言 + （可选）lock 一致性校验；守阵先红验后合入。
  3. cli.py 增加 --version 输出（importlib.metadata 优先、__version__ 兜底）。

阶段 2 —— 按需演进（不排期）

  1. scripts/release.py：前置校验 + bump + 草稿 + tag + push 一条龙。
  2. git-cliff 半自动 changelog；Gitee / GitHub Release 页面发布。

阶段划分的意义：阶段 0 四步只动文档与 git ref，无回归面，拍板即做；阶段 1 触碰打包配置与 CLI，按仓库惯例走 issue 认领 + 红绿验证；阶段 2 纯增益，等发版频率上来再投入。

08风险与对策

风险判据对策
tag 推了本地、没推上远端ls-remote --tags gitee 为空push 一律显式 ref + 推后必核（与分支推送同一判定口径）
版本号双源再次漂移守阵红（正则 / 一致性）阶段 1 的 V2 单源让漂移结构性消失；接线前的过渡期靠发版三步纪律
其它 clone 看不到新 tag别的 clone git tag -l 查无git fetch gitee --tags 显式同步约定，写入 collaboration.md（fetch <remote> <分支> 不带 tag）
0.x 被当稳定版误用—CHANGELOG 首行写明 0.x 语义；classifiers Beta 不动；1.0 判据明确（§04）
github 镜像 tag 滞后github ls-remote 失败 / 落后沿用「GitHub 允许滞后」既有口径；失败只报告一次
bump 被忘记、Unreleased 长期空Unreleased 段跨越多个功能批次功能批次合流的收尾检查里加一句「需要 bump / 发版吗」；阶段 2 脚本化后由机检兜底

09待拍板决策点

#决策选项推荐与理由
① 基线 tag 时机 a. 现在打 v0.2.0；b. 等阶段 1 接线后一起 a——当前工作区净且与远端齐平，是干净的基线点；tag 只标 ref，不受后续接线影响
② 版本号权威出处 a. V2 __init__ 单源（hatch regex）；b. V1 pyproject 静态 + importlib a——显示路径零改动、运行时零依赖、双源结构性消失；V1 在直接脚本运行与包初始化次序上有已知坑
③ CHANGELOG 档位 a. 手工（git log 草稿 + 归类）；b. git-cliff 半自动 a 起步——单人项目发版频率低，手工成本可控；b 留作阶段 2
拍板后动作：三项确认 → 阶段 0 四步（不涉码，随下一笔「提交」走 my-commit-flow）→ 阶段 1 入池 issue 认领实施。本文档全程未改任何代码与生产文件。
