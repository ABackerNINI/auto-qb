01背景与结论

前提（v1 已核实）：git 版本控制本体健在，空白在软件版本号与发布管理层。v2 复核确认空白仍在且已产生实际代价：双源矛盾持续（pyproject 0.1.0 vs __version__ 0.2.0，issue 26-09-21-1408 认领中）；v0.2.0 tag 之后 develop 积压 1720 提交（269 ✨ / 354 🐛）零 bump——v1 §08 预警的「bump 被忘记」风险已大规模兑现，这是机械化诉求的直接实证。

核心结论（v2）：0.x 语义化版本 + __init__.py 单源（hatchling regex 接线，清偿双源 issue）+ 机械化发版管线（触发词「发版」→ 本地全测门 → gitmoji 决策器算号 → bump-my-version 改文件 → 🔖 发版提交 → ff-only 合并 master → GitHub CI 全绿 → tag 锚 master → wheel 构建 + gitee Release 页）+ Keep a Changelog（gitmoji 映射）+ hash 尾双路径（源码运行时派生 / wheel 构建期注入）。三层载体：release skill（规程+脚本本体）+ .commands 薄引用（机械面）+ conventions 口径文档。16 项拍板见 §09。
层拍板一句话理由
版本号格式0.x 语义化Beta 阶段惯例，破坏性升 minor，1.0 留里程碑（三判据）
版本号权威出处__init__.py 单源显示路径零改动，双源结构性消失；构建后端已是 hatchling，接线约 3 行
hash 尾双路径全自动提交无法含自身 hash（鸡生蛋），业内解法=取数时刻后移：运行时/构建期派生
bump 决策机器提案 + agent 改判gitmoji 决策表（semantic-release 语义移植）出提案，agent 可改判但留痕，永不跨 major
发版执行agent 全程 + 触发词「发版」进显式触发词清单，执行零人工；平时不自主发版（请求边界不破）
分支模型develop 工作线 / master 发布线用户拍板双分支；tag/Release 页锚 master，ff-only 线性合并，多 clone 纪律不变
发布形态wheel + gitee Release 页Python 业内标准形态；exe 留阶段 2 单独立项

03目标与约束

  1. 单点事实源：版本号唯一权威出处；双源漂移已实证（§2.1）。
  2. 兼容 gitmoji + 中文提交规范：任何自动化不得以改提交格式为前提（否决 semantic-release/PSR/Release Please 的默认形态；其决策表语义照搬）。
  3. 兼容双远端纪律：gitee 主线判定看 ls-remote；github 镜像允许滞后、失败报告一次不重试——唯一例外：发版轮 github 推送必须成功且非静默（CI 门的依赖，§09-12）。
  4. 全程 agent 执行 + 触发词：执行零人工；发起留触发词「发版」，与「提交/入库/推上去」同列显式清单，平时不自主发版（请求边界黄金规则不破）。
  5. 大版本人工：major 永不由机器/管线跨越，三判据全中人工拍板 + --major 旗标放行。
  6. 双分支模型：develop=工作主线（多 clone 同步/提交/判定纪律全不变），master=发布线（仅发版时 --ff-only 前进）；分叉/冲突停手要人。
  7. CI 全绿门：tag 前必须 GitHub CI（master run）全绿；本地前置全测门（test.full + dev.e2e + real.suite，变异测试不进门）。
  8. 幂等重入：管线每步独立 rc、可重入，已完成步校验后跳过（黄金法则 1）。
  9. skill 通用性：脚本本体零项目事实（分支/远端/路径全走参数与配置），移植改动面 = bump-my-version 配置 + commands 包 config + 口径文档三处。
  10. 最小依赖：uv 生态纯 Python（bump-my-version）；git-cliff（Rust 二进制）留阶段 2 评估。

04版本号方案与 hash 尾

4.1 格式：0.x 语义化（拍板维持）

变更动作示例
功能批次（✨ 存在）minor +10.2.0 → 0.3.0
仅修复/性能（🐛/⚡️）patch +10.3.0 → 0.3.1
破坏性变更minor +1 + CHANGELOG「Breaking」加粗警示（0.x 语义）0.3.1 → 0.4.0
里程碑（三判据全中）major +1，人工拍板 + --major 旗标0.x → 1.0.0

1.0 三判据：① README 🚧 项清空；② 生产连续 2–4 周无数据风险事故；③ 配置 schema 冻结走完一个周期。版本号是兼容性契约不是进度条——补发 1720 提交仍按 delta 算 0.3.0，积压量由 CHANGELOG 承载。

4.2 hash 尾双路径（拍板）

结构性事实：提交内容无法包含该提交自身的 hash（鸡生蛋），「存储式」0.2.0+hash 只能是上一个发布提交的号且 uv.lock 每次提交漂移——直接排除。业内解法（setuptools-scm / hatch-vcs / git describe）一致：hash 不存储，取数时刻后移。

运行形态hash 来源显示
源码运行（日常多 clone）显示层运行时 git rev-parse --short HEAD（+--dirty 标脏）；git 不可用退纯版本0.3.0+49eacb8，逐时刻精确到 clone 的树
发布件（wheel）hatchling build hook 构建期注入包元数据装到别处经 importlib.metadata 显示 0.3.0+49eacb8

存储 __version__ 恒为纯 SemVer（守阵正则 ^\d+\.\d+\.\d+$ 不放宽）；tag 名恒 v0.3.0 不带 hash（带 hash 破坏 ls-remote 判定与 fetch --tags 约定）；溯源链 = tag 锚发布点 + 显示层 hash 定位树。备选 hatch-vcs 全盘接管已否决（推翻 bump-my-version 拍板、dev 显示噪、构建期 git 依赖）。

06机械化发版执行

6.1 三层载体与通用性契约

层载体装什么项目专属度
规程面.agents/skills/release/（SKILL.md + scripts/）执行规程（顺序/判断点/停手规则/降级路径/留痕要求）+ 脚本本体（决策器 / merge / tag / page）低——脚本零项目事实，分支/远端/路径全走参数与配置
机械面.commands/release/ 包 task id 族管线每步一条命令，薄引用 skill 脚本（先例：kb.bump → memory-bank/scripts/bump_doc.py）高——项目事实集中在包 config
口径面memory-bank/conventions/release.md（新）版本语义/触发词/major 判据/双分支模型/hash 口径高——项目口径单点；AGENTS.md 只留指针（8K 上限）
通用性契约（用户拍板）：脚本本体放 skill 根 /scripts/，commands 只引用；移植到另一项目的改动面 = bump-my-version 配置 + commands 包 config + 口径文档三处，SKILL.md 与脚本零改动。决策表（gitmoji 标准）与 Keep a Changelog 规范本身就是通用的。

6.2 发版管线（八步，触发词起跑）

develop（工作主线：多 clone 同步/提交/判定纪律全不变）
  │ ① 触发词「发版」→ my-commit-flow.sync（同步，硬步骤）
  │ ② 本地全测门：test.full + dev.e2e + real.suite(real.guard 前置)
  │    + test.linux（视平台改动）；mutants.status 核验（不进门）
  │ ③ release.bump：gitmoji 决策器按决策表算提案（v0.2.0..HEAD）
  │    → agent 改判窗（改判必留痕）→ bump-my-version 改 __version__
  │    单行 + CHANGELOG 草稿（只改文件，不自动 commit/tag）
  │ ④ 🔖 发版提交（bump+CHANGELOG 同笔）走 ship.commit 闸门 → gitee develop
  │ ⑤ release.merge：--ff-only develop→master → push gitee master
  │    （master 分叉/冲突 → 停手要人）
  │ ⑥ push github（发版轮必须成功、非静默——唯一镜像例外）
  │    → gh 等 master run 全绿（ci.yml + playwright.yml）
  │    （红 → 停在 tag 前，修复后重走，已完成的步校验跳过）
  │ ⑦ release.tag：tag v0.3.0 锚 master 发版提交 → 显式 ref 推
  │    gitee+github → ls-remote --tags 核验
  │ ⑧ release.page：hatchling 构建 wheel（build hook 注 hash 尾）
  │    → gitee Release 页（notes=CHANGELOG 该版段；token 未配降级过渡）
  │    → github 镜像 Release 尝试一次不重试
  ▼
master（发布线：仅发版时前进，tag/Release 页全锚这里）
提交里的 gitmojibump 提案CHANGELOG 段
✨minorAdded
🐛patchFixed
⚡️patchChanged
♻️无（可感知行为差异时 agent 并入 Changed）默认省略
📝 ✅ 🔧 🎨 💚 🗑️ 等无默认不入册

分工规则（拍板）：机器出提案，agent 可改判（如琐屑 ✨ 降 patch）但必须留痕——CHANGELOG 注记 + commit body 一句原因；机器提案与最终号的差异全程可审计。幂等重入：tag 已存在则校验指向而非重建，Release 页已建则更新，重跑不重复（黄金法则 1）。

6.3 CHANGELOG 规范

  • 格式：Keep a Changelog；CHANGELOG.md 顶部 ## [Unreleased] 滚动段，发版时改名 ## [X.Y.Z] - 日期；草稿由决策器按上表自动生成，agent 精修。
  • 全程 agent 执行形态下无人审门（拍板；tag 可回滚兜底）；历史无 tag 区间用提交哈希区间代替。

08风险与对策

风险判据对策
master↔develop 关系未知（远端拒连未核）实施首步 ls-remote 核验分叉（master 含 develop 没有的提交）→ 停手要人，不自动 merge/rewind（§09-10）
gitee Release API token 未配步骤 ⑧ 调 API 失败降级过渡：「tag + CHANGELOG 即发布口径」，当轮报告；token 配好后补建页面
gh CLI 认证未核步骤 ⑥ 查 run 失败API 轮询兜底（公开仓 60 req/h）或停手报告；不静默跳过 CI 门
CI 双跑冗余（同 SHA 在 develop+master 各触发）—门只看 master run（语义直白），develop run 作早期信号，不等两遍
镜像滞后与 CI 门冲突发版轮 github 推送失败发版轮例外：必须成功、非静默（唯一镜像例外）；普通推送纪律不变
bump 遗忘（v1 主风险）—结构性消失：触发词+机器提案+决策器维护 Unreleased 段
uv.lock 漂移lock 内版本变动hash 不进存储版本（双路径口径）；单源接线后 uv sync 一次到位
wheel 构建从未执行过hatch build 失败阶段 1 步骤 6 先构建冒烟，再入管线
0.x 被当稳定版误用—CHANGELOG 首行写明 0.x 语义；classifiers Beta 不动；1.0 三判据（§04）
