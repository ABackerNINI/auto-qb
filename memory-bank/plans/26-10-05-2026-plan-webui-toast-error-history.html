03方案与取舍(完整方案 × 收 error 口径)

数据层: 收集判定口径

来源kind收?例
直接发出的错误error收「批量跳检未完成: …」「打开目标文件夹失败: …」
sticky 等待结算的失败 / 超时终态error / timeout收「强制汇报超时」「导出: 成功 2 / 失败 1」「批量删除未完全成功」
未完全成功回执timeout收「已保存并热重载; X 为程序托管字段, 本次未写入」(config_editor.js:204)
后端自治错误(经 /api/errlog 合并)WARNING→warn · ERROR+→error收「强制汇报回执: …」/「状态落盘失败」等 102 处调用点 —— 自治失败主体在 warning 级, 只收 ERROR+ 会漏掉大头
提醒类warn不收「站点已存在」类 —— 用户本轮拍板「收 error」, 与 issue §06「只收 error 最克制」一致
成功 / 进行中 / 常驻等待ok / info / busy不收成功回执瞬时语义即可; busy 未结算无终态可收

口径实现为单点常量 ERR_HISTORY_KINDS = { error: 1, timeout: 1 } —— timeout 在本库的实际语义是「超时/未完全成功终态」而非纯超时, 属 issue §06 倾向句里「busy 结算出的超时/失败终态」的覆盖面; 若拍板要严格到字面 error-only, 删掉 timeout: 1 一个键即可(守阵按 KINDS 判, 不与具体键集耦合)。

  • 收集时机 = 发出即收, 结算即更: issue 原建议「退场时追加」, 但 auth.js:68 的 this.toasts = [] 绕过 _dropToast —— 挂退场会漏掉重连前最后一批错误(恰恰是挂机型最需要追溯的一批)。发出即收对齐「模拟重连清 toast 不清历史」的演示语义。
  • 不持久化: 前端 toast 收集会话内存级、刷新即失; 后端环独立于页面生命周期(刷新 / 重开不丢, 进程重启清零 —— 重启本身是日志可查的大事件)。两者都零落盘: 不进 state_file、无 localStorage / sessionStorage 写(守阵钉死防漂移)。全程审计仍由日志文件 + /api/log 弹窗承担。
  • 清空时机: 登录 / 重连路径不动(auth.js 零改动), 历史跨重连存活; 唯一清除路径 = 面板「一键清空」(低风险动作, 不加确认框)。清空只清本地视图: 后端环条目在刷新后随 boot 合并回来(内存语义, 不加删除端点 —— 保守默认)。

后端错误环与增量端点(26-10-05 复审增补, 修「浏览器关闭期」盲区)

  • 收集: auto_qb logger 单挂一个 handler(tray/app.py:43 UiLogHandler 同款范式), 收 WARNING+, 环为 deque(maxlen=200) + lock, 每条 {seq, ts, level, msg}(msg 截断 500 字符、多行合一); emit 全程 try/except 静默 —— 收集器永不干扰业务日志。挂接在 WebUIRuntime.start_server()(幂等, 已挂不重挂); 环本体与 seq 计数器是 WebUIRuntime 字段: 日志线程经 lock 写, Web 线程经端点只读(与 results / 订阅队列同款单写纪律)。
  • 端点: GET /api/errlog?after=<seq> 落 server/routes/system.py(与 /api/log、/api/cmd 同属「系统诊断路由」); 鉴权由 factory 全局 dependencies 单点覆盖, 零新增。返回 {items, last}: 只回 seq > after 的条目; 客户端发现 last 小于已持游标即判定后端重启过 → 清游标重拉全量。
  • 前端合并: bootstrap 成功 + 本机免鉴权两条路径(lifecycle.js mounted 范式)各拉一次 after=0 全量入 _errHistory(source='backend', 不计未读); 之后 setInterval 60s 补拉增量(source='backend', 计未读); 定时器 unmounted 撤除(lifecycle.js:132 时钟先例)。按 seq 去重, 刷新重拉不产生重复条目。
  • 黄金法则对照: 零新配置键(cap / 间隔写常量, 要调档改一行) · 无跨轮状态(环纯内存, state_file 不涉) · 单写线程(handler lock 内追加, Web 端点只读) · 保守默认(boot 前条目不计未读、无删除端点、不主动打扰) · 幂等(纯追加 + after 游标, 重复拉取不重复入列)。

入口与面板

  • 入口 = 常驻图标钮 + 未读徽标(面板关闭期每条 +1, 打开即清零; 无未读时静默 —— 保守默认, 不打扰)。
  • 面板 = 列表弹层: 时间(HH:MM:SS) + kind 色点 + 文本 + 行内复制(copyText(text, '错误详情')); 头部「N 条 · 清空」; 空态「暂无错误记录」。
  • 关闭交互 = Esc + 点击面板外; 面板是非模态浮层, 不上遮罩不拦滚动(避开 modal-mask-click-self-drag 一族问题)。
  • z-index 取紧邻 toast-wrap(120)之上的一档, 实施时核 components.css 现行层级表后定值。

不做清单(26-10-05 复审拆分重写: 三个被拒项成本不同, 分别裁决)

  • 后端持久化错误历史 / 跨会话保留 —— 落盘方案引入 state_file 写路径与容量治理; 内存环重启清零可接受(重启本身是日志可查的大事件)。维持不做。
  • 通用日志查看器 —— 无需列入不做: 已存在(/api/log + FE-2C 日志弹窗 + 设置页运行日志块, 见 §02)。后端环是结构化错误事件面(增量游标 / 等级预滤), 与它互补不重复。
  • 错误分级过滤 UI —— 环收 WARNING+ 即分级本身; cap 200 的条目量撑不起筛选控件, 维持不做。
  • 前端 toast 的 warn 收集 —— 拍板收 error(见口径表); 后端侧 WARNING 级收进环(自治失败主体在 warning 级, 见口径表后端行)。
  • 新配置键(容量 / 间隔写常量; 要调档改一行)。

05分步实施(每步一笔提交, 拍板后执行)

S1 · 数据层与收集钩子

  • shared/state.js: data 新增 _errHistory / _errSeq / _errUnread / errPanelOpen(§03 结构; 条目带 source: 'toast' | 'backend')。
  • shared/ui_feedback.js: 常量 ERR_HISTORY_CAP = 50 + ERR_HISTORY_KINDS; 原语 _recordErrorToast(id, kind, text)(upsert by id + cap 裁剪 + 未读记账)与 _clearErrorHistory(); 钩子两处 —— toast() emit 时 kind ∈ KINDS 即收, _finishToast() 结算时 kind ∈ KINDS 即 upsert(覆盖 sticky busy → 超时/失败链)。
  • auth.js 零改动(历史跨重连存活的既定设计)。
  • 验收(Node 探针驱动生产原语, 同 20:07 轮验证范式): ①error emit 即入历史(source='toast'); ②sticky busy 结算 timeout 入历史且 upsert 无重复; ③第 51 条挤掉最旧; ④面板关闭期未读 +1、打开清零; ⑤清空后全归零; ⑥登录/重连清 toasts 后历史原样。

S2 · 后端错误环与只读端点

  • 验收(pytest, 独立文件 tests/test_webui_backend_errlog.py): ①DEBUG/INFO 不入环; ②第 201 条挤掉最旧; ③after 增量与 last 正确; ④msg 超长截断; ⑤无 token 请求 401(沿 routes 既有测试范式)。

S3 · 前端 boot 合并与补拉
