重启后 WebUI 首份数据 5-15s(首轮管线挡发布): 提前发布方案

本篇只回答: 重启后 WebUI 首份数据 5-15s 怎么修 —— 根因是重启后首个含落库数据的视图代要等首轮数据管线整条跑完才发布(请求触发的提前发布只能拿到落库前的空代), 修法是「启动首轮 apply_sync 落库后立即发布基础视图」; 归组 files 串行与挂载点探测两个管线重活不入本计划(已入池两条 issue 独立排期)。

§01目标与设计原则

背景: 用户报告 auto-qb 重启 + WebUI 刷新后主界面 5-15s 才出现(约 210 种子)。此前 26-11-02 修过一次(issue 26-11-02-0902, 首访行高量齐 8.4s→97ms), 但那是前端渲染段; 本次 5-15s 在后端首轮数据管线, 不在那次修复面内。渲染面已排除: 210 行 ≥ ROW_WIN_EST_MIN=200 走估算开窗, 105 组精确路径实测百毫秒级。

North Star(D1/D9 拍板): real-machine 轨道环境(D10: 不取生产数字)以 ≈210 假种子受控重启, flat / singles / shows 首份数据出现 ≤ 2s 硬判据; groups 页第二跳时刻记录数字、不设硬判据 —— 物理上限: 归组必须 ≥210 次 files API 单发(torrents_files 单 hash 端点, qB WebAPI 无批量), ②的提速由 issue 承接, 本计划不背。

设计底线 / 不变量:

  • 单一写线程不破 —— 提前发布仍在主循环线程内同一拍, 不引入新线程; 不引入第二把锁(仍只有 view_lock)。
  • 「四视图同轮发布」铁律不破 —— 提前发布只是多落一代(四份视图 + 版本号整体替换), 临时代里 groups 为空是内容问题不是结构问题。
  • 不挂配置开关(D11): 本行为不写 qB / 不动种子, 不属「高风险动作」, 回退 = 单点 revert。
  • 黄金法则 1/2/4/5 照常(幂等 / 保守默认 / fail-fast / 单写线程)。

§02现状与痛点

02.1 排除面(本地桩实测, 取证 2026-11-18, 桩 = 真 create_app + 210 合成种子 + FakeClient)

环节实测结论
/api/state 冷(含首次发布 + 471KB 载荷)52ms不是瓶颈
页面骨架 + 28 分片串行 + 81 脚本串行(全 ETag 协商, boot.js 串行链)≈0.4s不是瓶颈
CLI 导入 / 渲染面(210 行估算开窗 / 105 组精确路径)368ms / 百毫秒级不是瓶颈

前端唯一放行闸 = bootstrap 的首个 /api/state 成功(auth.js:173/:188, bootstrapping 遮罩, lifecycle.js:322 免鉴权判定); 服务端该端点是纯内存读 + 惰性发布, 不会自己慢 5-15s。慢的是数据什么时候有。

02.2 根因链(取证 2026-11-18, 行号为当时)

  1. store 不持久化种子记录(state.json 只存规则执行史/基线) → 重启后 store 空, 首个同步必为全量轮, 210 个种子全部走 added 相位。
  2. _sync_line(qbmanager.py:842)里 _refresh_torrents(:939)整条管线跑完才有 on_sync_line → flush_views(:851→:853) —— 主循环 flush 的含落库数据代被挡在整条管线之后(首请求抢先时 ensure_state 已先行发布空代, 见第 3 点)。管线内重活: apply_sync 全量 maindata(:956) → 全量轮 path_map_selfcheck 挂载点探测(:966) + full_round tracker 重匹配(:970) → torrents_added 归组每种子一次 files 单发(grouping_mod.py:401, 210 次往返 ≈2-6s) → post 冲突检查。
  3. 管线窗口期: group_view_dirty 初始 True(runtime.py:112; runtime_views.py:406 是落代后的复位), rid 以进程启动时间播种(runtime.py:105, 恒非 0)。用户刷新后首个请求的 ensure_state(runtime_views.py:616, 脏即发布 :636-637)早于 apply_sync 到达 → 立即发布一个空代(rid=启动时间戳, 0 行)并把 dirty 压住; dirty 保持 False 直到管线跑完 flush_views 消费 view_changed, 期间轮询命中「零回传」(rid==ver 不回数组) → 界面壳先出、列表空。
  4. 管线结束 → flush_views 发布含落库数据的一代 → SSE ver 推送 / 下一拍轮询 → 数据落位。5-15s ≈ 首轮管线时长(空窗主体 = 首请求早于 apply_sync + 管线期间无新发布代), 波动来自 files 往返 × qB 负载/磁盘。

§03方案总览

主线(D3): 启动首轮在 _refresh_torrents 的 apply_sync 落库后、need_validate 分支之前, 先走一次既有发布单点(flush_views → _publish_locked)发布基础视图: flat 全量; singles 为全量种子的超集(_build_singles_view 语义 = 不在任何组的种子, 归组前全体都算未归组), 第二跳收缩; shows 按名称解析可给; groups 为空(组键依赖文件列表, 归组尚不可得)。管线照常继续, 结束时 on_sync_line 正常第二次发布(归组/HR 派生字段补齐; tracker 错误原因晚一代 —— 取数器挂在任务线 module.on_task_line, 任务线一代补齐)。前端两跳落位: 种子/剧集列表 1-2s 秒出, 分组随管线补齐。

触发面(D4): 仅启动首轮; 其它全量轮(reset_runtime / qB 重启补 / 热重载 L2)行为不变 —— 它们已有「发布→管线重跑→再发布」的自然节奏。判据 = 「apply_sync 落库后, 此前发布的最后一代尚不含落库数据」(以落库前 store.rounds_applied == 0 判定, 不依赖种子数) —— 用户首请求抢先触发过空代发布的竞态下不失效(见 §07 R3)。

代价面(D6, 用户已接受): 视图多落一代(rid+1, delta 客户端多吃一代); 基础视图缺 HR 派生字段(tracker 匹配后第二跳补齐)/tracker 错误原因(晚一代 —— 取数器在任务线, 任务线一代补齐); 基础代 singles 为全量超集、第二跳收缩(观感两跳, 语义自愈); 无配置开关(D11)。

分期: S0 取证 → S1 提前发布 → S2 守阵 → S3 真机验收(见 §04)。

范围外(D5): ②首轮归组 files 逐种子单发预算化、③path_map_selfcheck/冲突检查挪出关键路径 —— 不入主修, 已入池: 26-11-18-0259-perf-first-round-grouping-files-serial · 26-11-18-0259-perf-first-round-pathmap-selfcheck-critical-path(Open 待排期, S0 数字喂基线)。
