2.3 根因

历史成因（issue §05 已排除「U2 新造缺陷」）

P3-4 件套（报告 26-10-07-0542）只盘点了抽屉变体的模拟控件，主视图引擎表头当时不在盘点面。D3 把排序表头并进引擎后，变体侧件套随载体退役、引擎侧缺口因此全域暴露。守阵 test_drawer_tpl_a11y_and_fetch_error_states 头注（tests/test_webui_static_dom_panel.py 1705-1708）自述「引擎级表头 a11y 补课属引擎全域议题，已入 issue 池另议」—— 该面确为已记未做。

2.4 为什么 issue 建议的 A / B 都不够彻底

两者有一个共同硬伤：aria-sort 挂错宿主等于没加。按 WAI-ARIA，aria-sort 只对 role="columnheader"（或 rowheader）生效 —— 挂到 role="button" 上读屏直接忽略，而这条正是 issue 摘要里「读屏不知排序态」那半个 bug。

方案键盘可达读屏报排序态列头语义件套单点改动面
A 最小件套(role=button+tabindex+aria-sort)是否·宿主非法降级为按钮两处手写小
B 原生化(<button> 载体)是否·宿主非法降级为按钮两处手写大(CSS+事件冲突)
C 语义彻底(本计划)是是保留组件内单点中

B 的额外代价：.h-cell 内嵌 .resizer（绝对定位 span）+ @mousedown 拖拽排序 + @contextmenu 右键菜单，整格改 <button> 会与这三者冲突，三皮肤 CSS 与 e2e 手势（column-prefs / drawer-* 多处 .h-cell .resizer）全要重核 —— 成本最大、收益不比 A 多。

03 方案 C 详设

3.1 语义载体：role="columnheader" + aria-sort

grid 模式的 .h-cell 从「裸 div」升级为 role="columnheader"：这是 aria-sort 的合法宿主，也是「列头」语义的正确载体（不是按钮）。thead 模式的 <th> 本身隐含 columnheader，aria-sort 直接合法、零语义补丁 —— 这是 C 相比 A/B 真正闭环的地方。

aria-sort 取值规则（与现有箭头渲染判据同源，保证任一时刻二者一致）：

aria-sort = (col.sortable && sortKey === col.key)
              ? (sortDir === 1 ? "ascending" : "descending")
              : null   // 未命中列不输出属性(Vue 对 null 不渲染), 与 arrow 的 v-if 判据同源

三态排序的第一击是降序（setSort 首次点击 dir = -1），即首击后该列 aria-sort="descending"，与箭头指向一致。

3.2 键盘可达（与既有 P3-4 件套同构）

  • .h-cell.sortable 加 tabindex="0"，@keydown.enter.prevent / @keydown.space.prevent → 走与 click 同一个激活单点。
  • thead 的 <th>（仅 .sortable）同样 tabindex="0" + keydown 转发。
  • 不新造机制：这与项目 P3-4 件套（抽屉变体折叠组头 / msg 展开行）同一套语言。转发前排除原生交互元素的口径沿用 closest("button, input, select, textarea, a[href], summary") —— 本处 .h-cell 内只有非交互 span（label/arrow/resizer），实际不会双重触发，但保留口径一致以便未来扩展。
  • 可访问名：.h-cell 子树文本即列名（.h-label，arrow 为空 span），role=columnheader 的 name 计算自然取到列名，无需额外 aria-label。

3.3 件套单点：表壳组件内两方法

把 grid / thead 两处共同的属性产出与激活收进 AQ_TABLE_COMPONENT（shared/table.js），模板只调用 —— 未来新增任何表头模式只扩展这一处，不再各写一份：

// AQ_TABLE_COMPONENT.methods（新增）
headAriaSort(col) {                       // 属性产出单点(grid / thead 共用)
  if (!col.sortable || this.sortKey !== col.key) return null;
  return this.sortDir === 1 ? "ascending" : "descending";
},
headActivate(col) {                       // 激活单点: click 与 keydown 同路
  if (!col.sortable) return;
  if (this.mode === "thead") this.$emit("sort", col.key);      // 借壳模式: 排序归调用方
  else this.$root.setSort(col.key, this.tableId);              // grid: 直连引擎排序单点
},

模板接线（两份分支同一调用）：@click="headActivate(col)" + @keydown.enter.prevent="headActivate(col)" + @keydown.space.prevent="headActivate(col)" + :aria-sort="headAriaSort(col)"。

连带收益与同轮守阵改版

grid 分支原本的 @click="col.sortable && $root.setSort(col.key, tableId)" 收进 headActivate 后，模板里不再出现 $root.setSort(col.key, tableId) 字面串 —— 守阵 test_frontend_table_registry_single_point 中「表壳列头把 tableId 当 scope」那条 pin（tests/test_webui_static_skins.py ≈812）会转红，须同轮改版为「表壳走 headActivate 单点 + setSort 在组件内」。这是设计内的守阵迁移，不是回归。

3.4 表头容器与外层语义

  • grid 的 .group-head 加 role="row"（表头是「一行列头」），其子 .col-drop-line（重排指示线 span）加 role="presentation"，避免污染 row 的内容模型。
  • 外层是否再补 role="table/grid 与表体行 role —— 属 §06 拍板点 P1，默认不做（值格全量补 role 的代价见 §1.2）。诚实标注：缺祖先表格语义时，部分读屏对 aria-sort 的播报可能不完整 —— 这是本轮明确接受的收益边界，P1 若拍板做全套可补齐。

3.5 焦点可见（三皮肤 CSS）

键盘能聚焦但看不见焦点等于没做。三皮肤各加一条（atlas/console/prism）：

.h-cell.sortable:focus-visible { outline: 2px solid var(--accent); outline-offset: -2px; }

outline-offset: -2px 内缩，避让列间 10px gap 里相邻列 outline 互相挤压，也与项目既有 .opt-pill / .pop-item 的 -2px 先例一致。.h-cell 已 overflow: visible（为 resizer 伸出格子），outline 不会被裁。

05 风险与红线

#风险处置
R1aria-sort 与箭头判据漂移（两处各算，某刻不一致）单一 headAriaSort(col) 产出，与 arrow 的 v-if="sortKey === col.key" 同源；守阵断言二者同条件
R2tabindex="0" 让表头进 Tab 序，主视图多列表格 Tab 序变长列头逐列 Tab 是标准表格可访问性做法；项目 roving 先例是针对行（大列表）的。本轮不做 roving（列数有限），列作 P4 观察项
R3Enter/Space 与 click 双重触发.h-cell 内无可聚焦原生交互元素，本无双重触发；保留 closest 排除口径以防未来在格内加原生控件
R4role="row" 加在 .group-head 而表体无 row 语义 → 语义半套与 P1 联动；默认只补表头侧，读屏对列头的识别已显著改善，值格语义列 P1
R5新增属性破坏既有「DOM 等价」类断言已核对：现存断言（test_frontend_table_shell_single_point ③ 与全部 e2e）对 .h-cell 都是类选择器 + 存在性断言，加属性不破；唯一要改的是 W1 里那条 setSort 字面串 pin（见 §3.3）
R6三皮肤 CSS 特异性 / 遗漏某皮肤W2 三皮肤成对改 + 手验截图；.h-cell.sortable 三皮肤同名类成对是既有纪律
红线（触碰即停手重议）
  • 不改 sort.js 的排序状态机与比较器（本计划只接线，不改语义）。
  • 不改列宽 grid 契约 / colAlignCss / 列偏好持久化；不升 COLS_STORE_KEY。
  • 不改 .h-cell 的既有类名与事件骨架（@mousedown 拖拽 / @contextmenu 右键原样），只加属性与 keydown。
  • 不为通过守阵而在行渲染器值格上批量加 role（那是 P1，另议）。

06 拍板点

#决策选项推荐
P1 是否补全表体 ARIA 表格语义（祖先 role=table/grid + 表体行 role=row + 值格 role=gridcell） ① 不做（另立议题）② 只补到表头侧（本计划默认）③ 全套 ②。③ 需触及行渲染器 100+ 分支、破坏 DOM 等价验收口径，收益与代价不成比例
P2 resizer 键鼠等价 + 列菜单键盘入口 ① 不做（另立）② 本轮一并 ①。二者都需新交互设计，超出本 issue「表头 a11y」范围
P3 thead 模式（HR 详情表）是否同轮 ① 同轮 ② 另立 ①。同一组件同一份模板，<th> 隐含 columnheader，成本极低、覆盖才完整
P4 表头是否走 roving tabindex（整表头一个 tab stop + 左右键移动） ① 逐列 tabindex=0（本计划默认）② roving ①。列数有限，逐列 Tab 是表格可访问性标准做法；roving 是行级（大列表）方案
