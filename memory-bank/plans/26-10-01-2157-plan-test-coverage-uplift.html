§3

阶段计划 P0–P2 与防回沉 P3

排序原则: 先清「没测过」(A 类), 再扫「测不全」(B 类), 最后攻「难测」(C 类)。每阶段是一个可独立提交、可独立验收的闭环; 预估单位均按 §1 换算, 完成时以 test.full 实测为准, 不达标的差额在下一阶段任务表里滚动补齐。

P3

防回沉机制 — 与 P0 同步落地, 之后常态化

持续 · 无单位指标
#机制说明
M1pytest.ini 加 --cov-fail-under 阈值随阶段抬: 92 (P0 后) → 94 (P1 后) → 95 (P2 后)。阈值恒低于当期实测 1 个点, 给并行分支 partial ±1 的口径波动留余量。test.quick 走 --no-cov 不受影响, 提交闸门速度不变 — 有意设计, 不要改 quick。
M2每阶段收尾记基线切片按 memory-bank/testing/baseline.md 口径: 一条基线一个切片, 覆盖率 TOTAL + passed + 耗时区间; Windows 与 Linux 两侧都重测再落数字。
M3红验纪律 (每阶段抽 ≥10%)新测试抽样做变异红验: 临时注入缺陷确认测试能红。夹具必须让目标分支真正抵达 — 防「覆盖率涨了但测的是另一条路」的假绿 (pitfalls/testing/unreached-branch-guard.md)。
M4增量不欠账本计划执行期间及之后, 新功能 / 新模块一律带测试落地 (现有惯例); 缺口只减不增, 否则 M1 阈值会直接拦住。

§5

机制建设 — 让覆盖率不再回落

历史规律: 覆盖率这类「没人拦就缓慢回落」的指标, 靠自觉守不住。P3-M1 的 --cov-fail-under 是本计划的机制抓手, 落地要点:

  • 生效面: pytest.ini 的 addopts 全局生效, test.full 必查; test.quick 的 --no-cov 有意豁免 — 提交闸门保持约 7s 速度, 覆盖率检查由 test.full 与基线切片承担。
  • 阈值节奏: 永远 = 当期实测 − 1 个点。抬阈值是阶段验收动作的一部分, 与基线切片同一轮落地, 不单独提前。
  • 豁免治理: 全仓 pragma 豁免当前仅 2 处 / 52 排除行。P2 新增的 tray 豁免逐块注明理由后, 该数字进入基线切片的记录面 — 豁免行数只减不增。
  • 与 issue 清偿路线图的关系: 本计划与 Issue 全量清偿路线图 并行不冲突 — 测试补齐不改产品代码, 不会动到 issue 认领链; 若某条 issue 的修复顺带覆盖了本计划的目标行, 在该阶段任务表标注「由 issue X 顺带清偿」即可, 不重复补。
§6

范围外 · 变更记录

6.1 明确范围外 (本计划不做)

  • 前端静态 JS: 不在 --cov=src 覆盖面内, 前端质量由 ui_harness 冒烟承担。
  • .commands 包脚本测试: 47 条已有独立通道 test.pkg, 与 src 覆盖率口径无关。
  • tray widget 主体的架构级可测化: 属抽取重构, P2 达成后另立项。
  • 97% 以上: 剩余 ~700 单位集中在 GUI 主体与深层长尾, 96% 后边际成本陡增, 是否继续届时另行决策。
  • 性能基线: L9 性能守阵有独立基线切片 (26-10-01-2125), 本计划只动覆盖率口径。
