reannounce 确认跟踪改消解等待模型:废除在途直证,成功凭 working/前跳正证据

把 reannounce 确认跟踪的「在途即成功」改为消解等待模型：updating 一律不构成成功证据，成功凭 working 转换 / epoch 前跳正证据，失败凭 status 4/5/6 + msg；可达 tracker 的回执时延 = 真实 RTT + ≤1 tick，零固定宽限。

§01目标与设计原则

背景：issue 26-10-31-1740（RM09-04 真机实测：死端口 tracker 强制汇报在指令后 +1ms 即落 confirmed(ok)）。根因是 _verdict_reannounce 分支②把 updating 当成功直证——而源码事实表明 updating 在请求发出前置位（libtorrent torrent.cpp:3571），此时成败完全未知，「在途」与「即将失败」在该观测上不可分辨，正是 pitfalls/backend/effect-confirmation.md 三问①的假成功面。

完成判据：① min 缺失/从未联系行不再在途即 ok；② 可达 tracker 的 ok 回执无固定延迟（RTT+≤1 tick）；③ 拒绝证据（status 4/5/6+msg）及时落 rejected；④ 真机 RM09-04 转绿；⑤ 判定矩阵单测钉死。

设计底线/不变量：回执三桶语义只承诺诚实标签（ok/error/warn）；歧义保守落 pending；失败判据④逐行先于成功判据（防失败退避前跳被误判成功，libtorrent announce_entry::failed() 同样会前跳 next）；判定保持纯函数；等待期零 API 红线不变（照旧读 torrents_trackers 快照）；投递收敛、D1 推迟早回执、item 级 deadline 语义（REANNOUNCE_* 常量组）全部不动。

§02现状与痛点

现状（行号取证 2026-10-31）：src/auto_qb/webui/commands.py:466-470 分支②——epoch 行 updating or status==3 且基线 min 缺失/为 0/已过期 → confirmed「announce 在途」；runtime.py:588 check_pending 在指令 drain 后同 tick 跑首拍 → +1ms 终态。legacy 行（qB<5.2，无 epoch 字段）有无守卫的②同病。从未联系行无任何成功出口（主判据③判定域限基线 status≥2）。

源码事实（2026-10-31 调查）：

  • updating 在请求发出前置位、成功（torrent.cpp:3860-3867 verified=true, updating=false, fails=0 → Working）或失败（announce_entry.cpp:97 failed()）时清除——它对成败零信息量；
  • min_announce/next_announce 在发送时即赋值 now（torrent.cpp:3572-3573），成功才覆写为 now+interval；min「从无到有」不是成功信号；
  • 失败立即置 not-working（4/5/6，RST 即时不等超时/重试），且 failed() 按退避改写 next（首重试 ~17s）——next 前跳不是成功的排他信号；
  • qB 5.x 枚举已扩 NotContacted=1, Working=2, NotWorking=4, TrackerError=5, Unreachable=6（trackerentrystatus.h:40-47），现行④只认 4 会漏判 5/6。

issue §6 建议修法（固定宽限拍 ~2s）被否决的两个独立理由：①慢 announce 在宽限结束时仍在途，②照样假 ok——只修复快失败竞态；②固定 2s 代价造成不跟手（用户明确否决）。

§03方案总览

主线（落点单点：commands.py::_verdict_reannounce 纯函数 + runtime.py 超时文案）：废除②全域（epoch 与 legacy、min 缺失/为 0/已过期一概不再给 updating 任何确认效力，updating/status==3 恒 pending），新增③″与扩④：

序判据（逐行先到先得，④' 最先）结论
④'（扩）status in {4,5,6} 且 msg 非空rejected（RC_FAIL_PREFIX+msg）；msg 空仍保守 pending
③″（新，epoch）status==2 且 b_status 非 None 且 b_status != 2confirmed（「tracker 状态转为 working」）；失败路径产不出 2，强正证据
③（不变）b_next 非空 且 b_status>=2 且 na > b_next+tolconfirmed（「epoch 前跳」，reason 可带 min 同前跳佐证）
其余含 updating/status==3、无变化的 4/5/6 空 msg 行等pending（""）

legacy 行：④' 同扩；③′（status 2←基线非 2，形状与③″一致，两模式可共用同一实现）保持；无守卫②废除 → updating 落 pending；仍无前跳判据。runtime.py:616 超时 warn 尾巴去「在途」：改「未观测到 working 转换/前跳/拒绝证据」。「announce 在途」文案与语义全量退役。

回执时延口径（拍板 D4）：ok = 真实 RTT + ≤1 tick（qB 不带 high_priority，发送经定时器 ≤~1s）；rejected = 失败证据落地（死端口 RST 即时）+ ≤1 tick；窗口内无可分辨证据 → deadline 落 warn「未确认」。第一版不新增专用快拍。

§07风险与对策

  • R1 枚举落地差异：qB 5.x 真机对死端口回 4 还是 5/6 与调查口径可能有出入（RM09-04 既有证据是 4）。处置：真机断言以实测为准；④' 域含 4/5/6，实际返回哪个都命中，差异无害。
  • R2 黑洞 tracker：DROP 型（无 RST）靠 tracker_completion_timeout 才报错，30s 窗口内可能无任何消解。处置：落 warn「未确认」诚实标签，接受；真机观测真实站点表现后再议。
  • R2' 行为变化感知：min 已过期的曾成功行 ok 回执从 +1ms 变 RTT+≤1 tick。处置：D2 已接受；换的是不再假 ok。
  • R3 既有断言修改：min_window_guard 等用例断言随语义翻转。处置：属语义变更重写而非弱化，docstring 记 D2 依据；不删任何用例。
  • R4 基线竞态：基线在 API 调用后即刻读取，libtorrent 异步处理理论上可能已生效。处置：现状既有风险面不变（基线读取时序本轮不动）；消解判据均要求终态（2/4/5/6），瞬态误读概率极低。
