§01目标与设计原则

背景: issue 26-11-18-2350 —— S0 真机取证轮 run2 停机 38.75s(6 样本 1 例, rc=0 优雅收尾齐全); 2026-11-19 静态排查已闭合排除面并把停滞窗口修正为「信号触发 ~12.4s → KeyboardInterrupt 浮出 50.995s」(主线程 ~38.4s 零 eval-loop checkpoint, 判定依据见 issue §05)。

目标: 复发时一拍判定剩余假设 H1/H2(§02), 并拿到挂点栈; 批量采样给出复发率下界。算成 = 判别证据落盘 + 判定结论回写 issue。

设计底线/不变量: ①零 src/ 产品改动 —— 观测面全在 tests-real 测量工具层; ②停机语义不变 —— 零 taskkill, 优雅停口径 real-machine.md §2.6; ③measure.json 既有键只增不改 —— S0/S3 已入库的基线数字口径不受扰动。

§02现状与痛点

静态排查结论(2026-11-19, 排除面全量单点在 issue 26-11-18-2350 §05, 此处摘六项): 排除面 —— stdout/stderr 直写文件句柄(无管道背压)、qB API 有界 (3,10)s 且失败必落日志、GTM 工具面全 urlopen(timeout) 有界、flush_truths/_publish 无阻塞面、210 种子管线(含 re 段)在 ~09.584(gen2 完成点)完成, 早于 touch(~12.4)、纯 Python 主循环(sync_interval 1.5s + ≤0.5s 分段等待)处处是 checkpoint。剩余假设:

#假设形态
H1整机/进程级冻结(磁盘停顿/AV/系统暂停)全线程一起冻, 进程内证据完全不可见, 恢复后优雅收尾 —— 与 1/6 形态吻合(奥卡姆)
H2主线程单个不可中断 C 调用具体嫌疑: requests timeout=(3,10) 是 connect/字节间读超时非总时长, qB 忙时涓流响应可静默存活任意久
H3其他线程持 GIL 的 C 调用拖住全场无持有者候选, 存疑

痛点: 现有观测面在停机窗口是盲的 —— 驱动 graceful_stop touch 后纯 popen.wait(40)(run_s0_boot.py:225, 取证 2026-11-19), 驱动轮询在测量结束即停, 进程内无栈留存; 38s 窗口内零证据(issue §04)。S0/S3 六样本只有 1 例复发, 单轮复验大概率不命中。

§03方案总览

主线: 把两条正交证据面伸进停机窗口, 复发即判定 —— ①驱动在 stop 等待期继续轮询 WEB(判 H1 全进程冻 vs H2 仅主线程); ②runner 内 faulthandler 看门狗(38s 未退自动落全线程栈 = 挂点直读)。辅线: 批量采样 ≥20 轮给复发率(D4)。落点: 单文件 tests-real/tools/run_s0_boot.py(graceful_stop + 内嵌 RUNNER 模板), 判别字段进 measure.json stop 子树(D2)。
