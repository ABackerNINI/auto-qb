01现状与实测证据

现行约定 (.agents/skills/memory-bank/SKILL.md §任务档案规范): 路径 TASKnnn-<slug>.md, 编号连续不复用(全局单调序号); _index.md 手工维护四个状态分区, 每档案一行; 5 个静态守卫负责索引↔文件双向一致、slug 唯一、命名与必备章节、状态分区一致、分区齐全。

规模: 9 个 worktree(auto-qb 主线 + backend / frontend / autoclaw / trae / zcode / other 六个 agent 分支 + .worktrees/be / .worktrees/fe), 每个都持有完整的 memory-bank/tasks/ 副本。

02根因

用「全局单调序号」当主键, 而发号这一步在 worktree 之间无法协调。
  1. 撞号 — 发号需要"读全库最大号 +1", 而 worktree 之间看不到彼此未提交的写入 ⇒ 两个 worktree 同时算出 TASK017。
  2. 同题异号 — 检索键是编号而不是专题, 立档第一步是"取号"而不是"查专题有没有档案" ⇒ 同一件事在两条分支上各建一档, 合并后变成两份。
  3. _index.md 是冲突热点 — 所有 worktree 都要往同一文件同一分区追加, 文本冲突必然发生, 且解决它是语义活(不是重跑就能恢复)。
  4. 编号伪装成顺序信息 — TASK016 > TASK002 在主线上暗示"更新", 在并行分支里没有意义, 反而误导检索。
但要注意第 4 条的反面: 序号序虽然不可靠, 它确实提供了"目录里按顺序排"的浏览体验。纯 slug 方案一旦去掉序号, ls 变成字母序, 时间信息就彻底丢失 —— 这是本方案必须补上的东西, 见 §4。

04修订: 为什么从纯 slug 改成「日期 + slug」

修订记录初版推荐方案 E(纯 <slug>.md)。复盘后改推荐 I。触发点是一句反驳: 多 worktree 撞任务是极少数, 关心时间顺序才是日常。这个判断成立 —— 17 个档案里真正的重复只有 1~2 次, 而"看新旧、按时间找回去"每天都在发生。

原方案的设计错误

把防极小概率事件(同专题重复)的成本, 转嫁给了每天都发生的操作(看新旧、按时间检索)。这是本末倒置。

正确的分工应该是:

  • 高频需求 → 编码进主键(命名) — 时间序 ⇒ 日期前缀
  • 低频风险 → 交给守卫(事后检测) — 同专题重复 ⇒ 按 slug 查重, 撞了立刻报错要求裁决

为什么不直接用 F(与 plans 完全统一的时间戳)

AGENTS.md:15 规定计划文档命名为 26-09-17-0906-improve-webui-plan。判据是: 主键必须等于「决定这个东西唯一性的是什么」。

计划文档 memory-bank/plans/任务档案 memory-bank/tasks/
是什么一次决策的产物, 写完不再改一条持续演进的功能线
版本语义round9 / round10 是两份不同计划, 都要留同一专题只有一份, 跨会话追加
唯一性由产出时刻专题

所以 task 不该用"到分钟"的时间戳:

  1. 每次续作都算出新文件名, 永远"看起来是新的" ⇒ 同专题在并行分支必然两份。比序号更糟 —— 序号至少能在同一分支看到"已有 016"而避免新建。
  2. 现有 slug 唯一性守卫会彻底失效: 重复档案的文件名不再相同(26-09-18-0203-x.md vs 26-09-18-1408-x.md), 同 slug 检查抓不到。TASK014/015 那次事故, 恰恰是靠"两个文件名同 slug"才被发现。
  3. 引用要背时间戳, 对话里没法口述。

方案 I 如何两头都要

日期到天、不到分, 后面接 slug:

26-09-18-webui-error-reason.md
→
26-09-18-webui-error-reason.md
  • 时间序 — 字典序即时间序, ls 一眼看新旧。
  • 与 plans 同源 — 同为"日期开头、slug 收尾"; 区别只在 plan 精确到分(一天可能多份), task 只到天(一天一个专题只应一份)。AGENTS.md 无需改动。
  • slug 仍在文件名里 — 检索、补全、口述都还在(ls *error-reason*)。
  • 同专题重复 — 同一天 ⇒ 同路径, 命中即追加或显式 add/add 冲突; 跨天 ⇒ 两份但排序相邻, 由守卫报错要求裁决。
task 不带 HHMM 是特性, 不是缺陷。plan 带分钟是因为一天产出多份计划是合法的; task 同日同专题本来就是异常, 让它必然撞到同一路径, 重复才能当场暴露, 而不是静默变成两份。

05目标方案设计

5.1 命名

  • 路径 memory-bank/tasks/YY-MM-DD-<slug>.md; 日期取档案 Added: / Started: 字段(创建日), 不是修改日。
  • 不带 HHMM(理由见 §4)。同一天同专题 ⇒ 同路径 ⇒ 冲突显式化。
  • slug 组成为 <领域>-<专题>, 领域用固定枚举(不够用先扩枚举): webui / backend / rule / memory-bank / docs / test / deps / config。
  • slug 禁止出现: 轮次(round9 / r10 / 第十轮)、日期(已在前缀)、会话序号、编号、分支名。轮次属于档案内"子任务状态表"的一行, 不属于文件名。
  • 保留 **Legacy-ID:** TASKnnn, _index.md 附「旧号 → 新名」映射, 让历史文档里的 TASKnnn 仍可解析(否则要改 ~80 处引用)。

5.2 索引生成化

  • _index.md 从"人人手改的源文件"降级为生成物: scripts/gen_tasks_index.py 扫描 **Status:** + **Summary:** + 首行标题, 按四状态分区输出。
  • 分区内按 **Updated:** 倒序 —— 活跃度信号来自更新时间, 不来自文件名日期。这一点很关键: 老但仍在进行的任务, 不能因为创建日早而沉底。
  • 档案头部新增 **Summary:** 一行(索引摘要的数据源)。
  • 收益: 索引冲突的解决方式从"人工读懂两版再合并"变成"任一方重跑一次脚本"。
  • 守卫随之改语义: 从"索引↔文件双向一致"变为"索引 == 生成结果"。

5.3 档案头部字段(目标形态)

# 26-09-18-webui-error-reason — WEB UI 错误种子显示具体原因

**Status:** In Progress
**Added:** 2026-09-18
**Updated:** 2026-09-18
**Summary:** 一句话, 供 _index.md 生成
**Owner:** 分支 / 会话归属 (合并时判定谁的版本更新)
**Plan doc:** memory-bank/plans/26-09-18-1743-webui-speed-refresh-fix-plan.html
**Legacy-ID:** TASK015

**Plan doc:** 是 plan 与 task 的天然连接点 —— plan 带分钟时间戳、task 用日期 + slug, 靠字段互指, 不靠文件名耦合。(TASK017 已在用这个字段, 验证可行。)

5.4 立档流程(worktree 版)

  1. 定名: 取当天日期 + 专题 slug(不是取号)。
  2. 查重(必做, 两处): 本 worktree ls memory-bank/tasks/ 且 跨 worktree ls ../auto-qb-*/memory-bank/tasks/ 与 .worktrees/*/memory-bank/tasks/; 按 slug 部分比对(忽略日期前缀), 命中 → 追加不新建。
  3. 写档案: 补齐 Summary / Status / Updated, 追加进度日志与子任务状态表。
  4. python scripts/gen_tasks_index.py 重建索引(不要手改 _index.md)。
  5. uv run pytest tests -q(守卫兜底)。

5.5 守卫测试调整(tests/test_memory_bank.py)

  • FILE_RE: ^\d{2}-\d{2}-\d{2}-[a-z0-9]+(-[a-z0-9]+)*\.md$。
  • 新增 test_slug_unique_ignoring_date: 去掉日期前缀后 slug 必须唯一 —— 这是方案 I 的核心保护, 跨天同专题的两份会在此报错。
  • 新增 test_index_is_regenerated: 跑生成器后与磁盘 _index.md 逐字节一致。
  • 新增 test_slug_has_no_volatile_token: slug 不得含 round\d / r\d{1,2} / TASK\d 等易变 token。
  • 双向一致 / 状态分区: 主键由 TASK\d{3} 换成文件名。
  • 兼容期: 新旧两种命名都接受, 旧名归一后再比对; 阶段 4 删除兼容分支。

验收(DoD)

  1. 任意两个 worktree 同时为同一专题立档, 合并后该专题只有一个文件, 或显式 add/add 冲突 —— 而非两份并存。
  2. 任意两个 worktree 同时为不同专题立档, 合并后 _index.md 只需重跑生成器即可一致。
  3. tests/test_memory_bank.py 全绿(含 3 个新守卫), 基线数字只改 memory-bank/testing.md。
  4. ls memory-bank/tasks/ 的输出即为时间序。
  5. 全仓 TASKnnn 旧引用均可通过「旧号 → 新名」映射解析。

08风险与回滚

风险应对
迁移期间某 worktree 仍用旧命名新建档案兼容期守卫双正则接受两种命名; 阶段 4 前不收紧

git mv 后历史追溯断裂用 git mv(不是删除 + 新增); 档案内保留 Legacy-ID
两份 SKILL.md 改一处漏一处阶段 4 收敛为单一载体(软链或同步脚本)
阶段 3 专题合并丢内容默认不做; 或只做机械拼接(原文进「历史会话纪要」段), 不人工裁剪

回滚: 阶段 1~2 均为纯文件操作 + 测试改动, git revert 单次提交即可回到旧命名; 兼容期设计保证回滚后旧档案仍被守卫接受。
