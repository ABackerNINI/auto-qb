01

结论与范围界定

用户的一句话决定了本计划的全部走向：「问题太多，其中很多问题是修复过几次的，删除后重构。」

「修复过几次」是这份计划唯一的、也是最硬的证据。一个缺陷能被修好两次以上，说明修的是表象而不是产生它的机制：每修一次，代码就多一层针对性补丁，下一次复发就换一副面孔。继续沿这条路走，第八次修复依然会成功，第九次症状依然会回来。

本计划的立场

下文出现的具体代码位置，是基于现状实现地图的结构性推断，用来定位「该删哪里」和「为什么删」，不是待修清单。每个推断在对应波次开工的头十分钟内做一次实证复核（见 §07 各波的「首日复核」）。即便复核后发现某处推断不成立，表格重写这件事也不变 —— 依据是每个表格面都各自重复了一遍本该共享的几何与列逻辑。

02

八个症状，三个根因簇

八个症状看上去互不相关（表头底色、多余的横条、内容挤成一堆、对齐不一致、数值不动、多一个箭头、按钮成列、勾选跳动）。按「由哪一种机制产生」重新分组，落到三个簇里 —— 每簇一个结构性根因，每簇一次修复，而不是八次。

#症状（用户原话）根因簇机制
1表头 IP/地址下方有异色背景A · B 表头落在一个自带底色的宿体里，而列宽与对齐规则是按列序号（:nth-child(n)）注入的 —— 选择器依赖 DOM 层级与列序号，任一侧不同步，底色或边线就落到相邻列上。
2上传/下载速度列下方有异常横条A 网格轨道数与单元格数不一致时，溢出单元格被塞进隐式行 / 隐式列，视觉上就是一条没有内容的横带。那条横带不是装饰，是多出来的格子。
3上次更新后多列内容挤在一起A 与上一条同根。容器只声明了 N 条轨道，行里却输出 N+k 个值格 —— 多出来的挤进最后一条轨道。两条症状是同一个错判的两个方向。
4进度表头对齐方式未与主表统一A 对齐有两个出口：注入式 CSS 规则与行内类名。一个出口更新了、另一个没有，表头与数据行就各走一路。
5上传/下载速度不实时更新B · C 更新是「重建驱动」而非「值驱动」：轮询回来后可能被某个脏比较挡住，或重建压根没发生 —— 值更新走了一条要过闸门的路径。
6密度雷达「占用」表头前多一个箭头A 列名这一纯文案字段里混入了方向符号（label: "↑ 占用"），而排序态会在命中列再画一个箭头 —— 两个来源叠加。已确证：该列的 label 字符串里写死了 ↑。
7内容表按钮被当作单独的列A 勾选框 / 折叠钮 / 动作钮没有登记为列，却在行里占了一个格子 —— 不进网格声明，却占网格位置，于是「自成列」。这正是上一条里那个 k 的主要来源。
8点击勾选，元素变化导致跳动B · C 勾选改变的是行内 UI 态，而 UI 态不在驱动渲染的数据里 → 结果成了「通知一声、整段重渲染」而不是就地更新；重渲染期间行数与子节点数变化 → 行位偏移。
簇 A
各算各的
一张表的「几列、多宽、怎么对齐、渲染什么」落在互不相识的几处：列描述符、可见列派生、按序号注入的对齐样式、按列键查表的单元格分支链，没有任何一处做一致性校验。
簇 B
两条通道
表格区一半由变体的字符串模板产出，另一半被传送进前者的空位，中间靠一个代数计数器协调挂载时序。表头与表身的祖先节点因此不由同一套样式作用域管理。
簇 C
重建当更新
速度、进度、勾选这类高频小变量走「通知 → 重装配 → 重新渲染」，与低频结构更新抢同一扇门；任何防抖、脏比较、可见性门都会顺手把它们一起挡掉。
变体保留之后，诊断还成立吗

成立。三个簇都不在「版式」上，而在「表格」上：簇 A 的重复实现出现在每个变体的表格区里；簇 B 的双通道只在含表格的那 8 个变体上存在；簇 C 影响所有含高频列的表格 —— 包括变体内的表格（例如 09 的占用条、07 的速度卡）。保留变体不改变诊断。

03

为什么补丁路线走到头

把「表格」这一层的复杂度按来源拆开：几乎全部来自「同一件事被做了 11 遍」 —— 而不是来自 11 张表彼此真有 11 种需求。

叠层现状它带来什么
表格面的手写几何（网格 / 表头 / 列宽）每面一份同一套轨道口径被重复实现；改一处，其余十处不知道
行与单元格的渲染实现每面一份同一语义的列（如下载速度）在多个变体里各有一份实现
列字符集多套并存同一列在多处登记：取值、宽度、可见性各在一处
连接层（传送 + 代数 + 空位锚）一整套四条时序路径（初开 / 切页签 / 换目标 / 合并列）各有兜底，且处处依赖挂载顺序
注入式对齐样式一份单例按列序号生成规则 —— 列集一变即失配

这些叠层每一个都有过正当的出现理由，但它们的笛卡尔积就是当前的实际复杂度。八个症状只是这个笛卡尔积的回声 —— 叠层数乘上状态组合数，表现就是无穷无尽的。

判断

在这种结构上做任何「针对性修复」都只是局部最优：它治好了 A × B × C 里的一个格子，别的格子照样出错，而且修复本身又给结构加厚一层。既然 「变体数量」不能动（用户已拍板），那就只能动「每个变体里表格部分的重复度」 —— 把 11 份各自实现，换成 11 份各自声明。

一句话概括这个转向：变体保留观感，表格交出主权。

与上一轮的关系

上一轮 抽屉表格统一重写（状态 Done）做的是把每个变体的表格体迁到公共表引擎上。那一轮成功了 —— 但它保留了「每变体一套表格体实现 + 传送甬道 + 每表一套派生」这层结构，只是让大家共用一套工具。八个症状正是从这层结构里长出来的，所以那一轮结束之后它们还在。本轮要动的是表格体本身：不再让每个变体各实现一遍。

04

新内核：一处算，多处分用

目标一句：不管变体有多少，任何一个表格面的几何与渲染，只有一个地方算出来。

列池 + 子集：变体的差异变成数据

变体之间的差异，绝大多数不是「某个列的渲染逻辑不同」，而是「要哪几列、什么顺序、宽一点还是窄一点、排序列是哪个」。这些全部是数据，应当从代码里拿出来 —— 列在一个共享列池里定义一次，变体只声明自己要哪几列。

// ① 列池：一个列的完整定义，全仓库只此一处（含渲染器键、默认宽、对齐、可否参与排序）
COL_POOL.upspeed = { label: "上传速度", width: "minmax(96px, 1fr)", align: "right", cell: "speed", live: true }

// ② 变体 09「密度雷达」：只声明取哪几列 + 改个列名 + 排序默认值
SURFACES.dt09 = {
  host: "09 密度雷达",
  rows: "dtPeers09", rowKey: "addr",
  cols: [ "addr", "client", "flags", "progress",
          { key: "upspeed", label: "占用" },          // ← 列名不带方向符号
          "dlspeed", "uploaded", "downloaded", "relevance" ],
  sort: { defKey: "upspeed", defDir: -1 },
  affix: { tail: "rowActions" },
}

五条铁律

L1 · 几何只有一个出口

由上面这份声明，一个函数同时产出三样东西：网格轨道串、每列的对齐、每个单元格的渲染器。表头行与数据行读的是同一个返回值，物理上不可能出现两个答案。按序号拼接的 :nth-child 对齐样式整套退役 —— 对齐随列对象一起输出，不再事后注入。

L2 · 单元格必须在注册表里，否则当场报错

单元格渲染器按名字登记（文字 / 数值 / 速度 / 进度 / 条长 / 徽章 / 树缩进 / 按钮 ……）。查不到名字不是「渲染空白」，而是在页面上输出一条看得见的错误条并报错。（症状 7 的终局：没登记过的格子，现在没法存在。）

L3 · 表头文案就是文案

任何列名里出现方向符号（↑ ↓ ⇅ ▸ 等）即为错误 —— 方向由排序态单点渲染，这是唯一出口。守卫极廉价：一条正则，谁也绕不过去。（症状 6 的出处。）

L4 · 交互件不进列网格

勾选框、折叠钮、行动作按钮走垫片轨道（affix.lead / affix.tail）：它们有自己独立的轨道位，不参与可见列集合，也不参与拖宽 / 隐藏 / 排序。既不能被隐藏（隐藏了就没法勾选），也永远不会「莫名其妙占了一列」。（症状 7。）

L5 · 更新是写字段，不是重建

行对象在其生命周期内引用稳定；轮询到来时是写字段，不是换数组。高频列（速度 / 进度）标 live，走独立轻量通路，不必排队过结构更新那扇门。（症状 5、8。）

四种「不太像表格」的表格，怎么用同一份声明表达

关键在于：一种形态都不需要特殊分支。

  • 卡片栅格（04）：声明一列、占满宽度，渲染器输出整块卡片；列头无意义时按声明隐藏。
  • 健康分组（05）/ 五区分组（08）：行来源自带分段，每组分用同一份列声明；组头与分组折叠留在外壳（那是版式）。
  • 树（10 / 11）：树缩进是一个单元格渲染器；树的层级次序由行来源决定，不需要为它单开一列。
  • 条长列（09 占用 / 各处进度）：仍是同一个列，只是换用一个条长渲染器 —— 几何与对齐完全一致。

渲染即自查

有了 L1，就可以在开发态做一次硬一致性校验 —— 每次渲染都验一遍：

// 三处计数必须相等；不等就在页面上说出来，而不是让用户猜
assertLayout(surfaceEl, cols) {
  tracks = computedStyle(surfaceEl).gridTemplateColumns.split(" ").length
  heads  = surfaceEl.querySelectorAll(":scope > .head > .cell").length
  cells  = firstRow.children.length
  if (new Set([tracks, heads, cells]).size !== 1) → 可见错误条 + console.error
}

症状 2 与 3 从「肉眼看见的横条 / 挤压」，变成「一进场就报错」。这是本计划里最便宜、也最值钱的一处设计：让不一致无法被忽略，而不是努力让它不发生。

06

已定与待拍板决策

项问题结论
D1模板变体怎么处理？已拍板（2026-10-13）：15 个变体全部保留。本轮只重写其中的表格体。据此本计划已重写删除清单与波次。
D2内容树的树结构还留吗？推荐 A：留树，树缩进是单元格渲染器（不是列），勾选走垫片轨道；「树 + 详情」的版式完全不动。
选项 B：树改平表 —— 更省事，但丢掉目录语义。
D3要不要继续复用现有列交互引擎？推荐 A：复用「持久化 + 拖宽 + 拖序 + 隐藏」的行为实现，不复用它对详情表的派生逻辑。表格自己算几何（L1），行为仍调引擎单点。
选项 B：详情表完全自治 —— 独立性最高，但会与主列表形成偏好双轨。
D4旧的列偏好数据怎么办？推荐 A：新表用新 id，旧偏好自然隔离，不迁移、不清理。依据：历史上「升存储版本」曾把用户手调过的宽 / 隐 / 序清零。
选项 B：写一次性迁移 —— 收益低、风险高。
D5表格面多，一次改完风险大 —— 顺序？推荐 A：先用最接近标准网格的两张（06 / 09）跑通内核，再推到分段与卡片形态（08 / 04 / 05），最后做树（10 / 11）。理由：内核先在简单形态上被验证，复杂形态只是同一份声明的另一种取值。
选项 B：按页签整页推进 —— 一次覆盖一个页签，切换成本高。
D6表格到底由谁渲染？推荐：外壳提供容器位置，表格由内核在该位置内完成渲染 —— 单通道。理由：症状 1 / 8 与「卡死」的结构来源正是「两条通道拼一块画布」，只换一侧的工具不改变这一点。
备选：保留传送方案、仅替换表格组件 —— 迁移最省，但双通道的结构性问题会被保留。
D7变体之间要共享列吗？推荐 A：共享列池 + 变体声明子集。同一列的定义只有一处，改一次、十一处同时生效 —— 这是簇 A 的直接解药。
选项 B：每变体各自一份列 —— 现状的延续，改动最小但问题依旧。
07

分波实施

八波。前几波在同一个分支上完成、不合主干 —— 中间态的表格区损坏是可接受的代价，但不允许被别人看见。每个表格面的改造各自独立成提交，便于单独回滚。

W0 · 划界与冻结先做

  • 首日复核：确认 §01 的 11 张表格面清单，逐份标出「哪些节点属于表格区、哪些属于外壳」，写成一张对照表 —— 这是本轮唯一必须落到纸面的东西。
  • 确认哪些地方引用了即将删除的共享件（尤其主列表与设置页），把共有路径摘干净。
  • 验收：对照表评审通过；应用可起；test.quick 无新增红。

W1 · 内核落地

  • 列池 + 渲染器注册表 + 「声明 → 轨道 / 对齐 / 单元格」的单一产出函数。
  • 垫片轨道（L4）、列名守卫（L3）、一致性断言（L1）。
  • 停手点：内核先不接真实数据，用一张硬编码五列的演示面通过全部断言。

W2 · 打通两张症状 1/2/3/4/5/6 的验收波

  • 接 06（Tracker 增强表格）与 09（密度雷达）—— 都是标准网格形态，且 09 自带症状 6。
  • 改这两个文件时只动表格区的节点；外壳部分保留到不改一个字符。
  • 验收：肉眼八项逐条过；几何断言全绿；外壳 DOM 与改前逐节点等价。

W3 · 分段与卡片形态

  • 08（五区分组）、04（卡片栅格）、05（健康分组）—— 用它们证明「分段 / 单列卡片」只是同一份声明的不同取值，不需要任何特殊分支。

W4 · 树形态症状 7/8 的验收波

  • 10（树 + 详情）、11（树表批量）：树缩进是单元格渲染器，勾选是垫片，且勾选态进驱动数据（不再是「通知一声」）。
  • 停手点：八个含表格的变体全部接通，此时第一版可以并回主干。

W5 · 经典三张与数据通路统一

  • 经典三表接入同一份内核（W0 复核确认其存在后再做）。
  • 三个数据源收敛到同一套「引用稳定 + 写字段」更新协议；轮询周期与暂停策略单点。

W6 · 表格样式单点化

  • 表格自身的样式（列头、行、网格、垫片）抽到共享层；变体自己的版式与配色继续留在变体里。
  • 密度三档：紧凑 / 标准 / 宽松，由单一令牌控制行高与内边距 —— 各变体保留自己的默认值。

W7 · 守阵、清理、回写

  • 八条症状各一条回归用例（见 §08），每条都做红绿双验：故意把实现改坏 → 必须红；还原 → 必须绿。
  • 变体观感回归：八个表格面各做一次改造前后对照，确认外壳与观感未被改动。
  • 静态守阵：健康检查 + 列名正则 + 「列池与各面声明同步」扫描。
  • 回写：把这一轮学到的机制性教训按动作归类写进坑档（不按波次排）。
08

验收：几何断言 + 变体观感回归

这八个症状有一个共同点：肉眼可见、工具不可见。所以过去每一轮的验收都退化成「改完发截图给用户看」，所有争议都在最后一步爆发。本轮的验收原则：看代码不算验收，看截图不算验收，量出来才算。

第一部分在真浏览器里量真实 DOM，覆盖全部 11 个表格面（每种形态至少抽一张）：

#断言量什么
1表头单行、无错位底色表头容器高度等于单行行高；各列头的 getBoundingClientRect().top 全部相等；表头背景与面板背景一致。
2无溢出横带每行的直接子格数 == 网格轨道数 == 表头列数（三者必须相等；这一条同时是症状 3 的断言）。
3列不错位第 n 个数据格的左边界 == 第 n 个列头的左边界（容差 0.5px 内），对所有列成立。
4对齐统一同一列的表头与数据格 text-align 计算值相同；与主列表同名列的取值一致。
5速度实时注入两次相邻轮询响应后 500ms 内速度格文本变化，且行 DOM 节点身份不变（同一节点，不是重建）。
6不多箭头任一时刻每个列头内部的方向图标数量 ≤ 1；且所有列名文本不含方向符（静态扫描 + 运行时计数各一次）。
7按钮不占列隐藏全部可选列后，行仍保留垫片，且网格轨道数 == 可见列数 + 垫片数；动作按钮不可被右键隐藏。
8勾选不跳动勾选前后：行容器 top 偏移为 0、行数不变、行高不变；连续勾选十行，累计偏移为 0。
+一致性 fail-fast人为在一份声明里多加一个值格 → 立刻呈现可见错误条（而不是静默错位）。
+性能三百行连续十拍轮询，每拍主线程无超过 50ms 的长任务；切换种子时无「先塌一条再撑开」的形态。

第二部分：变体必须还是原来那个变体

这是本轮相对初版新增的一项硬验收 —— 既然变体保留，就不能「表格治好了、版式却变样了」：

  • 外壳等价：八个含表格的变体，其非表格区在改造前后逐节点对照，只允许表格容器内部不同。
  • 无表格变体零改动：01 / 02 / 03 / 12 / 13 / 14 / 15 七个文件，git diff 必须为空 —— 写成自动化断言钉住。
  • 逐面推进：每个表格面一个提交；任一面验收不过，只回滚那一个提交。
为什么把 UI 症状写成量具

因为肉眼验收的争议只能在最后一步爆发，且无法复述。翻译成数字之后，问题可以被精确指代：「第几条、哪个值没达标」，而不是「我看着还是不太对」。

09

风险与回滚

风险等级处置
动 8 个文件，一次做错就是 8 份返工高一个表格面一个提交；W2 先用两张跑通内核再铺开；任一面不过只回滚那一笔。
表格改好、变体观感被改坏高W0 的划界对照表 + W7 的外壳 DOM 等价断言；非表格节点不进改动面。
误伤无表格的 7 个变体或主列表中W0 首日复核跑一遍引用扫描；「七个文件零 diff」写成自动化断言。
表格区与外壳两侧不同源中D6 拍板为单通道；容器之内一律由内核产出。
列偏好丢失低新表用新 id，隔离而非迁移（D4=A）；不升存储版本。
三皮肤观感分叉低W6 抽共享样式，但只抽表格自身的样式，变体版式留在原地。
中间期表格区不可用中全程在分支上，主干始终可用。

回滚单位是「一个表格面一个提交」，不是半个文件。划界对照表（W0）是判断「改动有没有越界」的唯一依据。

范围之外

  • 7 个无表格的变体：01 / 02 / 03（常规页）、12（空间树图）、13 / 14 / 15（流量图）—— 一行不改。
  • 每个变体的非表格内容：版式、配色、KPI、摘要、工具条、详情区。
  • 主列表四张表（辅种 / 明细 / 种子页 / 追剧）：不动。
  • 设置页 HR 三张表：不动。若新内核在 W2 得到验证，可作为后续候选。
  • 流量页图表：不动。
  • 后端接口与字段：不改；新增字段的需求另行入池。
范围守恒

执行途中若撞见不属于表格体的缺陷（相邻模块的历史债务、文案不一致、陈旧 TODO）：一律不修、不顺手改，按项目纪律入池，并在本文「范围之外」留下条目，由用户决定是否排期。
