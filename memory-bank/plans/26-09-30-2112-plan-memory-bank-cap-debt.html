背景与根因

用户命题：cap 守卫在任务后期触发，此时改字数要带着满载的会话历史反复返工，token 成本巨大 —— 应改为「只提示 WARNING、不当场修改」，知识库清理另开会话。

触发面已到「每次编辑必触」
实测（commands run doc.caps，2026-09-30）：AGENTS.md 7,975 / 8,000 字符，余量 25；任一此刻发生的 AGENTS.md 编辑都会被闸门拦下。其余三份同类文件的余量都很充足（commands SKILL 2,702/5,200 · memory-bank SKILL 6,347/15,000 · 包 README 1,789/6,000）—— 疼痛是 AGENTS.md 一处的结构性余量不足。
现行处置要求「提交前砍掉一半」
2026-09-29 定调：触顶一律「精简/外迁到上限的 50%」。对 KB 主题文件这是机械外迁（切到同目录 attachments/、原位留指针）；对 AGENTS.md 却等于砍 3,975 字符的入口文档手术，且必须保住「常驻可见」的硬约束语义（黄金法则 / 红线 / git 硬约束）。同一句口径套在两类完全不同的操作上，是这次返工税的直接来源。
债务记了，但清偿时机永远不对
切片 memory-bank/activeContext/26-09-27-1812-commit-msg-consume-delete.md 待办①写着「AGENTS.md 削薄……下次收尾时顺手做」，记于 09-27；到 09-30 实测仍是 7,975 —— 因为「收尾」恰好是全流程最贵的时刻（满载历史 + 已有多轮返工）。记账点与执行时机错配，所以债务不是没记，是记了也还不上。
拦截面有四处，其中两处不在提交闸门里
只改提交闸门不足以解决 —— 测试侧会用同一次提交在 test.full 上再拦一次。

分析结论 · 合理，但要补三件事

方向成立：cap 是文档维护问题，却被接成了提交前置条件 —— 守卫在最贵的时刻（会话尾部）索要最贵的工作（入口文档重构），还常常拦住与文档无关的提交。

补强一：债务可见性必须是派生的，且必须在提交那一刻把话交到用户手里 —— agent 开不了新会话，所以「会话开始跑 doc.caps、在该会话首件清理」并不省成本（改动历史照样累积进同一场会话），只是把返工挪了个位置。可行路径只有一条：提交时脚本现算并 WARN → agent 把「文档数字已超标」转告用户 → 由用户自行新开会话清理。

补强二：AGENTS.md 必须单列 —— 它是硬规定（用户 2026-09-30 拍板）：不能超、不套 50% 收缩口径、不进债务体系；超限仍按硬闸门 STOP，与主题文件完全分开处理。

补强三：测试侧的尺寸断言必须一起降级 —— 只改闸门的话，test.full 仍会红，降级不生效。

02

目标与非目标

2.1目标

  • G1 不阻塞：字符 cap 不再阻塞任何提交与收尾 —— 超限只是 WARN。
  • G2 必然可见且可转告：债务在提交时以派生方式（现算）输出，且警告文案自带「提醒用户另开新会话清理」的处置指令；清理由用户新开一个会话执行，收口可机检。
  • G3 AGENTS.md 硬规定不动摇：超 8,000 且本次改动命中 → 仍 STOP（不进债务通道、不套 50% 收缩口径）。
  • G4 守卫不回退：结构类守卫（命名 / 双向一致 / 状态词 / 坏链 / 存根合法 / 条目三字段）一条不放松。

2.2非目标

  • 不抬 cap 数值 —— 2026-09-29 已全表 ×2；AGENTS.md 的 8,000 不可抬（抬了守卫就是假的，尾部照旧被截断）。
  • 不改 KB 主题文件的 50% 外迁口径 —— 机械外迁仍是对的做法，本计划只把它从「提交前必做」挪到「清理会话做」。
  • 不做自动清理 / 自动改写文档 —— 路由手术需要判断，脚本只负责发现与收口校验。
  • 不在闸门里引入任何写文件副作用 —— 债务记录由收尾流程写进切片待办，不靠检查脚本动文件。
03

方案设计

一条严重度政策（预算型 → 债务 / 结构型 → 保持红 / AGENTS.md → 硬规定）+ 一条派生可见通道（doc.caps 单一入口）+ 一份清理会话规程。

3.1一类 cap，两种性质

判别标准：违反之后是「读起来更贵」还是「事实源 / 跨会话连续性被破坏」。前者是预算，降级为债务；后者是结构，保持红。

性质条目降级后的行为
硬规定 · 不降级 agents 角色 = AGENTS.md（全库唯一） 不能超：超 8,000 且本次改动命中 → STOP；不套 50% 收缩、不进债务清单（用户 2026-09-30 拍板）
预算型 · 债务 其余角色 cap 尺寸项（index / index-auto / pitfall / evergreen / reference / log / task / volatile / slice / baseline-slice）· 两份 SKILL.md 与包内阅读预算 · 切片条数阈值 WARN，提交不拦；提交时必现并由 agent 转告用户；用户另开会话清理、--strict 收口
结构型 · 保持红 存根 ≤2 KB（守「内容确已外迁」，防两处权威）· 三行头元数据 · 类名与文件名 · 索引双向一致与生成物自洽 · 状态词 · 相对链接 · 条目三字段 · 切片命名定宽 照旧判红 —— 它们守的不是尺寸
本来就只有 WARN 下限 CAP_MIN_WARN（过小提示） 不动

3.2债务的可见性通道：提交时派生输出 + 转告用户

  • 派生：债务清单每次由脚本从真实文件尺寸现算，不设手写债务表 —— 手记会陈旧、会漏、会与事实分叉，而尺寸不会。
  • 单一入口：doc.caps 扩为三组输出（IDE 注入上限 / 阅读预算 / 知识库角色 cap）。KB 组直接调用 skill 的 check_kb_structure.check_caps（进程内 import，先例：tests/test_memory_bank.py）—— 严重度判定与遍历逻辑都留在源码单点，不在两处各写一份。AGENTS.md 不在债务清单里：它以「硬规定」行单独打印（超限即拦、也不累计进债务数）—— 它不常改，一旦改了就该顺手改到合规，而不是挂账。
  • 触发点 = 提交时（ship.commit 的闸门输出）：那一刻 agent 必读输出、用户就在会话另一端，信息一步到位。不挂会话开始协议 —— agent 无法自开新会话，在会话里清理与在任务末尾清理没有区别（历史照样累积），挂上去只把返工换个位置。
  • 警告文案自带处置指令：输出直接写「本会话不修；请在回复中提醒用户：文档数字已超标，需另开新会话清理」—— 读到输出的人（agent）不必先查规则就知道该做什么，也把「转告」变成提交后回复的固定动作。
  • 接线：提交闸门保留现行 [[gates]] 条目（信息出现在提交流水里，只是不再能拦）；doc.caps 的 run 补 <args> 占位符（今天传 --strict 会被引擎拒绝，实测），清理会话用它收口。

cap 债务 1 项 —— 请在回复中提醒用户: 文档数字已超标, 需另开新会话清理
  → 提交照常: 债务不拦提交; AGENTS.md 除外 —— 它超限即拦
  → 清理会话收口: commands run doc.caps -- --strict (债务非空即 rc=1)

--strict 是留给清理会话的收口开关：平时谁都不会被它拦住，清理会话用它做「债务清零」的机检结论。

3.3AGENTS.md：硬规定，不进债务体系（2026-09-30 用户拍板）

AGENTS.md 的 8,000 与其他 cap 性质不同：越过它发生的是 IDE 注入截断（slice(0, 8000)，尾部对模型真不可见），不是「读起来贵一点」。用户定调三条：

  • 不能超 —— 超 8,000 且本次改动命中 → 仍 STOP，照旧拦提交（硬闸门不降级）。
  • 不套 50% 收缩动作 —— 它是常驻注入的入口文档，内容「外迁」= 硬约束降为按需读，是设计回退；削薄只需回到 ≤ 8,000，并按需留出能容纳一次常规追加的余量，不预设 50% / 90% 之类的比例。
  • 不进债务体系 —— 它不常改：一旦改了就该顺手改到合规，而不是挂账等下一次会话；doc.caps 里它单列「硬规定」行，不累计进债务数。

唯一保留的宽松处：判据仍是「本次改动命中才拦」—— 避免一个陈旧超限的 AGENTS.md 去拦无关提交（那种情况只报告，不拦）。

3.4目标值口径修正：AGENTS.md 不设比例，KB 角色维持 50%

2026-09-29 的「全表 50%」把两类操作混同了。修正为按性质分档（AGENTS.md 已由用户定调为硬规定，不设比例）：

角色清理目标理由
KB 角色（主题 / 切片 / 流水 / 档案 …） cap × 50%（TRIM_KEEP 不变） 机械外迁到 attachments/，一次留足半桶便宜且无风险
agents（AGENTS.md） 不设比例 —— 回到 ≤ 8,000 即可 硬规定 + 不常改：内容「外迁」= 硬约束降为按需读（设计回退），所以不套 50%；也不入债务清单，超限走硬闸门

3.5清理会话规程：由「用户」开启，agent 只负责转告

  1. 谁开：用户 —— agent 无法新建会话，这是整条链的硬边界。agent 的职责止于「在提交后的回复里转告超标事实 + 建议另开会话清理」，不在本会话动文档。
  2. 触发：提交时输出出现债务行 → agent 转告 → 用户择机新开一个会话专门清债。
  3. 清理会话的起手：跑 commands run doc.caps 拿当前债务清单（不需要谁转抄，脚本现算），按清单逐项外迁 / 精简。
  4. 范围：清空全部债务行（KB 角色按 50% 外迁）。AGENTS.md 不在债务清单里 —— 它若超限由硬闸门拦下，同一次会话内就地削薄回 ≤ 8,000（路由手术：细节下沉 memory-bank/README.md / conventions/ / pitfalls/，原位留指针）。
  5. 收口：commands run doc.caps -- --strict 绿 = 债务清零的机检结论。
  6. 升级条款：若债务的成因是机制本身（如余量结构性不足、口径不可执行），清理会话就地升级为设计任务 —— 本计划即首例（AGENTS.md 余量 25 逼出的入口文档削薄 + 「50% 对入口文档不可执行」的口径修正）。

3.6债务的记录点

  • 发现由派生通道负责：doc.caps 在每次提交时现算输出，任何时候也可手工跑它拿全量清单 —— 债务清单不落盘、不手抄，故永不陈旧。
  • 转告由收尾动作负责：agent 在提交后的回复里把债务事实告诉用户（警告文案自带该指令，见 §3.2）。
  • 背景（可选、一行）由收尾 DoD 负责：顺手在 activeContext 切片待办记一行（文件 / 当前值 / 上限 / 目标值 + 成因），好让用户开清理会话时接手有上下文。手写侧只承载判断，不承担发现职责。
  • 两者刻意分开：手写的一侧只承载判断，不承担发现职责。

07

边界与风险

风险 1（最大）：warn 了但没人清（或 agent 不转告）
缓解：提交时派生输出（现算，不依赖记忆）+ 警告文案自带「提醒用户另开新会话清理」的指令 + 收尾 DoD 把「转告」列为固定动作。代价：债务到期日取决于用户何时开清理会话 —— 这一族只有阅读预算与加载 token 成本、无截断，晚几天无实质危害。AGENTS.md 不在此风险内 —— 它保持硬拦，不带债过夜。
风险 2：「守卫不靠自觉」原则被削弱
本计划换掉的是不可便宜强制的不变量（文件永远小），换成可强制的不变量（债务必然可见 + 可机检收口）；AGENTS.md 的硬拦不动，恰好是这个「可强制」体系不必覆盖的那一类。守卫的牙齿从「拦提交」移到「现身 + 收口」，不是放弃纪律。
风险 3：尺寸失控无人知
由 doc.caps 在每次提交时承担（任何时候也可手工跑它拿全量债务清单）；输出保留「本次改动命中」标记，让人区分「刚加的债」与「存量债」。
风险 4：--strict 被误挂回闸门
会在闸门 note 里钉死「闸门只用默认模式」；--strict 只许出现在清理会话的收口命令里。
风险 5：AGENTS.md 削薄把硬约束下沉过头
由 AC-8 的「必须仍在 AGENTS.md」清单钉住；下沉只针对解释性细节，纪律条目留原位留指针。
明确的非目标边界

不做自动清理；不再抬 cap 数值；不改结构守卫；不给闸门加写文件副作用。任何超出这四条的动作都需要新计划。
