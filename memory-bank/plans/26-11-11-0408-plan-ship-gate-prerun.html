提交闸门预跑 ship.gate: pack 前置单独跑

本篇只回答: 怎么把提交闸门做成可单独跑的 ship.gate, 并接进评审批次的 pack 前置, 让小失误在评审派发之前暴露 —— 不回答: 闸门清单本身的重构、绿结果缓存去重(第一版明确不做)。

§01目标与设计原则

为什么做: 当前小失误只在 ship.commit 闸门一刻暴露 —— 典型浪费回路: 小失误 → review → 提交被拦 → 修改 → 重 review → 再提交。多花的正是评审派发(批 ≤400 行一次派遣)。

做到什么程度算成: 改完代码/文档后、评审派发前, 可用 commands run ship.gate 把「commit 将要跑的同一套闸门」原样预演一遍; 评审批次的 pack 前置固定接线这一步; commit 闸门照旧全跑兜底。

收益锚定(关键事实): 评审基哈希排除生成物与记账类(code-review skill ③) —— 生成物类闸门红(如索引没重跑)修完不触发重评。重评浪费只发生在闸门逼改可评内容时(fmt 改格式 / test 红改代码 / 措辞改文字 / AGENTS.md 超限)。预跑的目标因此锚定一句话: review 评到的树已经是闸门绿的。

设计不变量:

  • 闸门清单单点不动: .my-commit-flow.toml 的 [[gates]] 仍是唯一清单, 预跑照搬全部 auto = true 闸门, 不另抄一份;
  • commit 双跑保留(黄金法则 1 幂等): 预跑绿后 commit 再跑一遍, 不做缓存去重;
  • 快照语义照搬(_snapshot.maybe_respawn, 一次调用 = 一个版本);
  • v3 输出契约: 成功一行(要贴进评审记录), 失败一行 + 明细块。

§02现状与痛点

  • 闸门引擎早已在 _pipeline.py(gates_for / run_gates / 占位符展开, 两阶段并发执行), commit.py:519 只是调用方 —— 「拎出来」实现上是加一个入口脚本, 不是重写。
  • 闸门 11 条三类: 代码面(dev.fmt / test.quick / test.pkg.scoped)、KB 与文档面(索引 / 措辞 / 模板 / 状态漂移 / 坏链 / HTML v.Nu 等约 9 条命令)、提交语义面(review.trace / skill 链接同步 / context caps)。
  • 成本实测: test.full 全量 185s(基线切片 26-11-11-0314), test.quick 更短 —— 双跑多花约 2-3 分钟, 相对一次评审派发是小头。
  • dev.fmt 是真动作(会真格式化文件) → 预跑必须在 pack(基哈希)之前, 否则评审包基线失真。
  • review.trace 读提交消息: commit.py:515 经 COMMIT_FLOW_MSG_FILE 递下去, check_review_trace.py:168 消费; 预跑时评审尚未发生、消息通常还没写, 照跑必红。
  • 闸门键白名单 GATE_KEYS(_ship_config.py:89): 未知键一律 STOP(config_problems) —— 新键必须先扩白名单, 否则一写就挡提交。

§03方案总览

主线

新增 ship.gate(my-commit-flow/ship 子包, 入口 scripts/gate.py), 与 sync/push 并列; 行为表:

输入态行为
树净一行「树净, 无闸门可跑 —— 提交闸门照旧在 ship.commit 兜底」, rc 0
树脏changed = staged + unstaged 中工作区仍存在的路径; gates_for 命中 → run_gates(并发池 / 分片 / 聚合语义照搬, 一字不改)
红线 / warn 命中只打 WARN: 信息行(拦截语义属于 commit 的暂存计划, 预跑不拦)
review.trace仅当消息文件(.git/COMMIT_MSG_AI.txt)存在才跑(提前发现忘写 trailer), 且照 commit 同款设 COMMIT_FLOW_MSG_FILE; 不存在 → 打「略过」行(评审批次 pack 前评审尚未发生, 跑了必红)。实现: 新增闸门级键 when_message = true, 预跑侧过滤, commit 侧不受影响
skill 链接同步幂等动作, 照跑
失败全量列出未过闸门(逐条: 闸门名 + rc + 耗时 + $命令 + 输出末 20 行) —— 预跑是诊断面, 一次看全、一轮修完; 结果行「闸门预跑失败: N 条未过 —— 修完重跑 ship.gate; 绿了再 pack/评审」, rc 1
成功一行「闸门全绿: 命中 G 条, 执行 C 条命令, 总耗时 Xs(略过 M 条)」→ 贴进评审记录

接线(单点)

  • code-review skill ③ pack 前置加一步: sync 之后、pack 之前跑 ship.gate, 结果行贴进评审记录; 红 → 修 → 重跑绿才 pack; 凡 pack 必前置 —— 复评轮与接缝终审不豁免(D9); 非评审提交(纯生成物/记账)可选不预跑, commit 闸门兜底(D7)。
  • AGENTS.md 一字不动(D8): 收尾节已指向 code-review skill, skill 内部接线自动被引用到, 8000 字符预算不花。
  • 配置三处: ship/config.toml 注册 task(when/note 写语义与例外); .my-commit-flow.toml review.trace 加 when_message; _ship_config.py 扩 GATE_KEYS + bool 校验(缺了就是 STOP, 挡自己提交)。

§07风险与对策

#风险触发条件处置
R1agent 忘跑预跑(文档接线无机检, 与「该跑的没跑 = 静默红」同款失效模式)观察到预跑执行率低 / commit 被拦的回路仍频繁出现再议机检(pack 输出提示 / gate 状态文件), 当前靠 skill 文字 + D9 措辞钉死
R2评审循环 K 轮 = 预跑 K+1 次, 测试面时长累积评审循环频繁(实测发现数 ≈ 派发次数 × 5.6, 循环常见)当前接受(D9); 痛了再议「复评轮轻量子集」—— 但那会重新引入「哪些闸门能省」的裁量面, 不轻动
R3预跑 fmt 与用户编辑并发改文件预跑跑 test.quick 时用户同时改代码概率低; commit 闸门照旧兜底, 不专门处理
R4review.trace 预跑分支依赖消息文件提前写好, 实际很少触发消息在评审后才写(现状惯例)略过行如实显示不静默; 行为表注明「仅消息文件存在才跑」
