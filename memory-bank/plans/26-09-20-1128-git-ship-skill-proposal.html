01为什么：这次又飘了

今天这次提交（create-issue 类型化改造，3 个提交 `4c0d945` / `4c26c60` / `9af3e52`）虽然落地了，但对了一遍项目规则，漏了四处：

规则（出处）本次实际后果
只暂存本次范围，逐路径 `git add`，不用 `add -A`（AGENTS.md 提交节）两次 `git add -A`幸好当时没有别人的在途改动；按 pitfalls 那条「2133 个 staged」的事故，`add -A` 正是把他人改动混进提交的动作
push 前先 fetch 看一眼（本次新入 pitfalls）直接 push被拒 —— 远端另有 5 个提交，临时 rebase 救场
Gitee 推完再尝试一次 GitHub 直连，失败只报一次（AGENTS.md）没推 GitHub镜像滞后（允许，但规则要求"尝试一次"）
提交后查幽灵 diff / 暂存清单逐项对账 / 改过的 py 过 yapf（AGENTS.md）三项都没做本次恰好没触发；下次可能把"已提交"误判成"没提交上"
提交后 ref 三处核对 · 高风险前备份 `.git` · 提交前跑全量测试三项都做了—
根因不是"不知道规则"，而是规则没有被摆在执行路径上：它们分散在三份文档里，执行时靠记忆想起，而提交是高频动作 —— 漏一条只是时间问题。历史代价已经付过两次：2026-09-19 非快进合并丢 318 个对象 + 全部 reflog；同期分支 ref 被别的会话回退，冒出 2133 个 staged。

02目标与非目标

目标

  • **一次"提交"指令 = 同一条流水线**：不管哪个 agent、哪个 worktree，步骤与判据一致。
  • **能机检的都机检**：远端是不是 Gitee、有没有落后、工作区脏不脏、暂存清单有没有红线文件、ref 三处是否一致 —— 这些不该靠肉眼。
  • **必须人判的写成停手点**：合并/变基、混入他人改动、ref 异常、GitHub 直连失败 —— 到点停下并报告，不自己发挥。
  • **规则单点定义**：口径留在 AGENTS.md，步骤留在 skill，事故判据留在 pitfalls，互相只留指针。

非目标

  • 不改协作口径（Gitee 为主线、GitHub 镜像允许滞后、用户说"提交"= commit + push）。
  • 不替代 scope-guard（该不该改）与 create-issue（要不要入池）—— 它们管的是改动内容，本 skill 管的是改动落地。
  • 不自动写提交信息：动机与取舍要人/Agent 写，脚本只校验格式（中文首行 + 空行 + 细节、规模数字是否可疑）。

03skill 形态与档位

位置：`.agents/skills/<name>/`（与 scope-guard、create-issue 同层，自动被 `.codebuddy/skills/` 符号链接）。建议名 git-ship（备选：`commit-flow` / `submit-flow`）。`user-invocable: true`。description 沿用项目写法：

name: git-ship
description: '提交推送流水线(用户说"提交"= commit + push): 认远端 → 同步 → 闸门 → 逐路径暂存
  → 写提交信息 → 提交并核对 ref 三处 → 推 Gitee 并核对 → 尝试一次 GitHub 直连 → 查幽灵 diff。
  USE FOR: 用户说"提交"/"推送"/"推上去"/"commit"; 收尾阶段要把改动落到主线时。
  DO NOT USE FOR: 判断改不改(见 scope-guard)、要不要入池(见 create-issue)、纯答疑。
  红线: 脏工作区不做非快进合并; 暂存清单里不得出现 config.yml / 想法.md / auto-qb-data/。'

自动化档位（三选一，见第 09 节）

档做法适用
A 纯规范只有 SKILL.md 步骤清单 + 判据，命令由 agent 手敲最快落地，但仍靠自觉（本次偏差多数会复现）
B 规范 + 只读预检（推荐）加 `preflight.py` / `verify_ref.py` / `verify_push.py`，**只读不写 git 状态**，输出检查表与退出码把"忘了看"变成"脚本报出来"，同时不触碰红线（脚本本身不合并、不 stash、不 push）
C 半自动脚本直接执行 fetch / rebase / commit / push，遇红线自动停手省事，但脚本要处理 rebase 冲突与 ref 回退，**正是本环境最容易炸的地方**，暂不推荐

04流水线七步

步做什么判据 / 不通过怎么办
S0 认远端`git remote -v` + `git rev-parse --abbrev-ref @{u}`上游必须指向 gitee.com；不是就改用 `gitee` 远端名或改上游（**分支名必须写**，`git pull <remote>` 不带分支名只 fetch 不合并）
S1 同步`git fetch <remote> develop` → `git log --oneline develop..<remote>/develop`落后就先 rebase；**工作区必须干净才 rebase**（脏 + 非快进合并 = 必炸）。脏 → 先按 S3 提交或把改动移出。**push 之前再 fetch 一次**（本次踩的坑）
S2 闸门按改动面选：Python → `yapf -i` + `uv run pytest tests -q`；动了生成器 → 对应 `--check`；涉及平台行为/副作用记账器 → WSL 复现红了就停，不提交
S3 暂存逐路径 `git add <文件>`，**禁 `git add -A`**；清单逐项对账出现 `config.yml` / `auto-qb-data/` / `想法.md`（用户的）→ 剔出并告知
S4 信息中文首行 + 空行 + 细节（动机/取舍/影响面/实测数字）数字必须**提交那一刻实测**（`git show HEAD^:<f> | wc -l`），不沿用会话中途量的旧值
S5 提交 + 核 ref`git commit` 后核对 `HEAD` == `refs/heads/<branch>` == loose/packed-refs不一致 → 按 pitfalls 处置（format-patch 留底 + 建锚点 ref），**不要用 `add -A` 去"解决"突然冒出的成百上千 staged** —— 那是别人的在途改动
S6 推送`git push origin develop` → 核对远端 ref == 本地 → 再尝试一次 GitHub 直连（`-c http.https://github.com.proxy=`）Gitee 必须成功；GitHub 直连失败**只如实报一次**，不重试、不换代理、不改走 SSH
S7 收尾幽灵 diff 检查（`git status --short` 看两列：` M` = 已提交但工作区又脏）→ 有则补一次"格式化，无行为变化"提交；回写 activeContext / progress / pitfalls；报告提交号权威判据：`git log --oneline -1 -- <文件>` 有记录 **且** `git diff --quiet -- <文件>` 退出码 0
高风险动作前（rebase / 批量提交 / 修 ref）先整份备份 `.git`：`cp -a .git <备份路径>`；本仓 9 个 worktree 共享同一对象库，出事波及全部。

05脚本设计（B 档，只读）

脚本职责输出 / 退出码
`scripts/preflight.py`S0–S3 的机检：远端与上游是不是 Gitee、落后几个提交、工作区脏不脏、分支名、暂存清单里有没有红线文件、改动面命中哪些闸门（py / 生成器 / 平台）检查表（PASS/STOP 逐项）；有 STOP → 退出码 1
`scripts/verify_ref.py`S5 的三处 ref 一致性；额外提示"staged 数量异常激增"（ref 被回退的判别信号）一致 → 0；不一致 → 打印修复命令（`git update-ref` / format-patch 留底）→ 2
`scripts/verify_push.py`S6 后：`git ls-remote <remote> develop` == `HEAD`；`git status -sb` 无 ahead；可选执行一次 GitHub 直连（`--mirror`）一致 → 0；镜像失败单独报一次，不影响退出码
（不提供）**不**自动 commit / rebase / push / stash红线区，交给执行者按 SKILL.md 判据手动跑

三个脚本共用一份配置（远端名、分支、红线文件清单、闸门映射），放在 `scripts/_ship_config.py`，与 create-issue 的 `_common.py` 同思路；换项目只改配置。

07落地步骤

  1. 建 `.agents/skills/<name>/SKILL.md`（七步 + 停手点 + 反模式）
  2. 建 `scripts/_ship_config.py` + 三个只读脚本（先 `preflight.py`，其余两个跟着）
  3. 在本仓库实跑一遍：用一次真实改动走完整条流水线，核对每步输出是否符合预期
  4. 回写 AGENTS.md（加指针两处）、memory-bank/README.md（加路由一行）、memory-bank skill（同步步骤改指针）
  5. pitfalls 补一条：本次"push 前没再 fetch"已在册；再加"add -A 混入他人改动"的判别信号
  6. 提交 —— **用新 skill 提交它自己**（dogfooding），流程有洞当场发现

08验收：四个场景演练

场景期望
远端已落后（造 5 个远端提交，本地不 fetch）`preflight.py` 报 STOP：落后 N 个提交，先 rebase —— 不再等到 push 被拒才发现
暂存清单含 `想法.md` / `config.yml``preflight.py` 报 STOP 并点名文件；执行者剔出后再继续
工作区脏 + 需要 rebaseskill 明确要求先归零（提交或移出），**不直接 rebase**
提交后 ref 不一致（手工把分支 ref 改回上一个）`verify_ref.py` 退出码 2 并给出修复命令；不出现"看着提交成功其实没落"的情况

回归判据：走完一次真实提交后，AGENTS.md 里的每一条提交纪律都能对上一条已执行动作（可用检查表逐项打勾）。
