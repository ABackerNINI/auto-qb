01一句话背景与非目标

背景(报告 §00/§04, 源报告 memory-bank/reports/26-10-07-0204-report-webui-delta-sync-feasibility.html): /api/state 已实现 qB rid 语义的「跳过」半套(版本一致零回传, runtime.py:828), 摄入侧 store.apply_sync(store.py:112-158)今天就在跑同款协议的完整客户端, 每 1.5s 一轮的逐种子变化字段集(delta_fields)已算出、只是在视图层门口被塌缩成布尔。本计划把缺的「变化时回增量」半套补上: qB 启发的窗口式自研协议 —— deque 时间线只存键、值回放时从当前已发布视图现取(不照抄 qB 的单 accepted 点 + 值驻留缓冲, 见 R1/R3)。主要工程量与风险集中在服务端增量聚合正确性(恰是 issue 2 根因栏挂着的「dirty 集合 × 剧键派生」待查)。

非目标(报告「收益不覆盖的面」+ 02 笔记盘点明确不做的):

  1. 不改善 qB → auto-qb 摄入链(那条链已是增量, store.apply_sync)。
  2. 不动 /api/torrents/{hash} 详情、流量图、错误历史等端点。
  3. 不减少每轮请求数(SSE ver 每版必推, 轮数不变; 降的是每轮成本)。
  4. 不取消 issue 1 的「每版必须建一次」下界(复验报告 §04③), 增量是对该下界降价, 不是取消。
  5. 静态做种库不是收益目标(rid 跳过已覆盖, 增量收益趋零; 收益主体是活跃传输库)。
  6. 组行改 hash 引用式(响应体二次演进)单独立项, 一期不做(P-02, 见 §04)。
  7. pending_ver 门控一期不动(P-03), S10 再裁决。
  8. hr_view_fields 取值路径不动(02 笔记 2.5.3: 不构成新缺口; 仅镜子测试覆盖 HR revision 波次的 full 降级路径)。
  9. 不做字段级 patch 协议(设计规则 R8; 除非 P-02 二期演进再评估)。
  10. 不照搬 qB 的「全量值快照 + 待确认值缓冲」内存模型与等值 ack 清缓冲协议(自创窗口只存键; 窗口滑出清理由 deque maxlen 兜底, 见 R1/R3)。

02全局设计规则(从 01 笔记避坑清单逐条提炼)

每条一句话, 全计划(服务端/前端/测试/文档)不得违背:

  • R1 时间线只存键不存值, 值回放时从当前已发布视图现取, 内存 O(代数×脏行键) 与库大小无关 —— 这是「qB 启发的自创改进: deque 窗口只存键」, 全计划文档禁写「qB 同款」(01 笔记五.3, 最重要的一处修订)。
  • R2 时间线全局一份、每客户端只持自己的 rid; 禁止 per-session 状态 —— 窗口式天然容纳多标签页/多客户端, 免 qB 单 accepted 点互踩退化全量(避坑#2)。
  • R3 ver 沿用 group_view_ver 单调代次(runtime.py:789, 重启用时间播种 runtime.py:137-138 不回落); 窗口命中判据 =「客户端 rid ≥ 时间线最旧代次且窗口内无 full 代」; 不模仿 qB 的 %1000000 回绕与等值 ack, rid 比较用数值区间不用等值(避坑#3); 文档表述统一「本仓 ver 单调; qB 为循环」, 不写「单调递增是 qB 语义」。
  • R4 时间线每代键集并集合并、键级幂等, 禁止整代/整行覆盖(避坑#1 #24845→#24875 的键级等价物); 门控跳过的轮次其增量键集累积进下一代, 不丢。
  • R5 时间线每代 upsert/removed 先双向交叉抵消再追加(upsert -= removed; removed -= upsert); 跨代归约时 removed 让位于后续 upsert(避坑#7)。
  • R6 全量分支与增量共用同一合并函数: 全量=清空重放(语义等价于对每行 upsert + 清空 removed), 选中/展开/多选/乐观值保留路径复用现有机制(避坑#5 + qB client.js「clear 后重放再恢复选中」模式)。
  • R7 前端出错路径(请求失败/超时)禁止手动清四数组与 lastRid, 只退避; 重置责任在服务端(full 标志 + ver 播种)(避坑#5)。
  • R8 增量一律行级 upsert 整行替换, 不做字段级 patch; 行内字段集由 _member_view/_seed_view(views.py:353/:500)固定结构产出, 无「字段消失」形态(避坑#6)。
  • R9 抖动字段防线: 凡新增进视图的派生时间/速度类字段必须先过 _VIEW_QUANTUM 量化口径(torrents/view.py:83-88, view_field_value :90-100 是重建判定与展示共用的单点取整入口)或加滞后阈值, 否则 dirty 集永不清空、增量退化全量(避坑#4; dlspeed/upspeed 不量化属活跃库真脏, 是预期)。
  • R10 full 响应不含 delta/removed 键; 触发面 = 窗口滑出 / rid>ver / 窗口内任一代标 full / 进程重启 —— 与 qB 的 lastSentID/acceptedID 等值判定式不同, 维护者勿拿 qB 源码硬对(出入2/出入4)。
  • R11 无法归约为行级脏的源(HR revision、配置热重载、shows_pending 归位、跨组交叉标记、行键不可推导)一律本代标 full, 保守正确优先(降级阶梯; 避坑#7)。
  • R12 时间线写入只在主循环线程(flush_views/_publish_locked 持 view_lock 临界区), Web 线程只在 ensure_state 持同一把 view_lock 读 —— 与 group_view 读写模式同构, 不引入新锁(黄金法则 5; qB 同为主线程事件循环串行, 01 笔记 1.7)。

镜子测试总纲: 01 笔记要求的「连续两拍未确认」等用例全部落在 S5 的 M1..M9 清单(M1 即避坑#1 的回归用例), S6/S9 扩 M10..M12; 镜子不变量 =「从 rid0 逐轮吃 delta 合并」≡「每轮全量快照」。

S1store 侧 added/removed 持久化(02 笔记 2.5.1 缺口落位)

目标让 flush_views 能从 store 拿到「本轮新增/删除种子清单」—— 报告 S-1 脏行推导的数据源补全(报告原话「从 store 排空 delta_fields + added/removed」, 但 store 现状 added/removed 只是 _apply 的返回值 store.py:202-203/:264, 不持久化)。
前置依赖S0。
改动文件与插入点src/auto_qb/torrents/store.py —— _apply(:185-264)的属性赋回区(:259-261 delta_fields/state_changed/field_changed 同款先例); 零变化早退段(:194-199); reset_sync(:172-180)清空区。src/auto_qb/core/qbmanager.py:778 的解构消费保持不动。
做法要点选型, 起草人建议: 属性快照式, 不选「qbmanager 转投 WebUIRuntime」——
  • _apply 在赋回 delta_fields 的同一处, 把局部 added(:202-203)与 removed 清单赋回为 self.last_added / self.last_removed(命名对齐 delta_fields 先例; 消费方 flush_views 只读不排空, 下轮 _apply 直接覆盖, 天然「最近一轮」语义)。
  • 赋值点必须放在零变化早退(:194-199)之前的公共路径, 保证零变化轮属性为空、不留上一轮残值(否则镜子测试 M4 的抵消前提被污染)。
  • reset_sync(:172-180)同步清空两个新属性(重连/热重载不残留旧清单, 对齐「重置责任在服务端」先例)。
  • 取舍理由: 转投方案需要 qbmanager 持 web 引用跨对象搬运, 加一条隐式耦合; 属性式改动集中 store 单文件, 单一写线程语义不变(主循环线程写, flush_views 同在主循环线程读, 黄金法则 5 无新压力)。
验收 DoD每轮 _apply 后 last_added/last_removed 与返回值一致; 零变化轮为空; reset_sync 后为空; qbmanager.py:778/:789(search_index/事件分派)下游零感知。

  • runtime.py _publish_locked(:775-799): 在 group_view_ver += 1(:789)的同一 view_lock 临界区内把 _delta_pending 折叠成本代条目追加进时间线并清空累积器。

做法要点
  • 条目数据结构(起草人建议: 轻量 dict, 与 runtime 现风格一致): {"ver": int, "full": bool, "upsert": {"torrent": set, "group": set, "show": set}, "removed": {"torrent": set, "group": set, "show": set}}; S2 期 show 桶恒空。
  • 推导时序(R4/R12): flush_views 每拍(无论门控是否放行)先排空 store 增量 → 映射行键 → 并入 _delta_pending; 门控放行 → _publish_locked 落代时一次性并入时间线。这样「上一版没被取走不重建」(:506-507)原样保留, 增量下门控的成本只是一次键集追加(P-03 的前提)。
  • 组行 removed 键推导: 排空顺序先查 member_to_key 后消费 removed 清单; hash 查不到键 → 该组行键不可归约 → 本代 full(R11 保守)。
  • 归组变化: views.py:489-493 的交叉标记路径本就显式置脏, 接成「本代 full」旗标 —— 不试图归约旧组键(R11)。
  • 降级源的三处具体接线(起草人建议): ① mark_dirty()(runtime.py:298)加可选参数 full=True, WebUIRuntime 记 _pending_full_reason 集合, module.py:57 的调用处传真; ② HR(:500-502)与 shows_pending(:842-844)在 flush_views 判定点直接置 reason; ③ 交叉标记在 _build_group_view 构建期发现, 经 WebUIRuntime 属性旗标回传 _publish_locked 消费。
  • 交叉抵消(R5): 每代落代前分视图 upsert -= removed; removed -= upsert。

06实施纪律(分步派工)

  • 本计划未来由分步派工执行, 每步 = 一个独立工作单元: 开工 commands run my-commit-flow.sync(结果行「已同步 <hash>」贴进回复)→ 重核该步行号锚(HEAD 若前进, 见 §00 口径)→ 步内实现 + 自验 → commands run test.quick(关键步 S0/S4/S9/S10 跑 commands run test.full 并新建基线切片)→ 独立提交。防止长会话返工: 不跨步携带未验证状态。

  • 进度留痕: 每步完成后把步号 + 一行要点记进 activeContext 切片; 全部步完成走 memory-bank skill 收尾 DoD 5 步。
  • 提交信息: gitmoji + 中文口径(首行 <gitmoji> <一句话>, 动机/取舍/影响面/实测数字), 引用本计划步号(如「S3: ...」)。
  • 渲染与入库: 本稿经确认后渲染单文件 HTML 入 memory-bank/plans/ + commands run kb.index; 渲染本身不做内容决策。
