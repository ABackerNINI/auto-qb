日志等级整改：真正危险的情况归 ERROR，桌面通知默认只推 ERROR

现状是「WARNING 即通知」——设计内动作、用户操作审计、可自愈降级全部直推桌面弹窗，真危险被淹没。本计划做三件事：① 把数据丢失 / 写盘失败 / 任务停摆 / 认证失败等真正危险的情况升为 ERROR；② 桌面通知默认阈值从 WARNING 提到 ERROR；③ WARNING 收窄为纯排障等级。附全量调用点处置表（88 处 WARNING + 16 处 ERROR 逐条定级）。

01

背景与根因

通知链路 100% 依赖日志等级：NotifyHandler（src/auto_qb/infra/notify.py:202）挂在 auto_qb logger 上拦截日志，min_level 及以上的记录自动派发桌面通知（urgent 判据 = levelno >= ERROR，notify.py:242）。生产 config.yml 的 notify.min_level 当前为 WARNING，且模型默认值也是 WARNING（config/models.py:216）——即每一条 WARNING 都弹窗。

全仓盘点：WARNING 88 处（src 86 + scripts 2）、ERROR 16 处、CRITICAL 0 处。其中约 23 处 WARNING 是「设计如此」的信息性 / 审计消息（删除种子审计、配置变更告知、限速覆盖等），与可自愈降级、重试中、真危险混在同一等级里，通知降噪无从下手。根因是等级语义过宽（现行约定「WARNING = 回退 / 风险 / 数据异常」），本次一并收窄。

口径冲突声明：本计划改写 memory-bank/conventions/code-style.md:67 的既有等级语义，并在收尾回写该文档与 pitfalls/ops/alert-levels.md——先改约定再动代码，避免守阵与文档各说各话。
02

新等级语义口径

整改后四级各自只有一个问句能回答「该不该用」：

表 0 · 等级语义（旧 → 新）
等级旧口径新口径默认进桌面通知
DEBUG例行检查 + skipped不变——例行细节、逐种子排障轨迹否
INFO动作成功 / 状态变化扩：+ 用户操作审计、生命周期告知（启动 / 停止 / 配置变更）否
WARNING回退 / 风险 / 数据异常收窄为纯排障：可自愈降级、重试中、保护性动作、性能细节——「值得在日志里看，不值得弹窗」否
ERROR未预期异常（exc_info）扩为真正危险：数据丢失 / 状态写盘失败 / 任务停摆需人工 / 认证失败 / 未预期异常是（urgent）
CRITICAL校验允许，全仓未用不启用（无调用点，不加戏）—

判别口诀：弹窗测试——「这条出现时，用户是否需要立刻放下手头的事？」是 → ERROR；「只是排查问题时想 grep 到」→ WARNING；「事后审计想留痕」→ INFO。
