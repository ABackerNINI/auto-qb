**/config/*.py 这一条已实测 (fnmatch, 2026-10-08): 同时命中顶层与 schema/ / validation/ 两个子包, 且不误伤 src/auto_qb/webui/server/routes/config.py。不要写 **/config/**/*.py —— 它要求 config/ 下必须有子目录, 会漏掉顶层的 loaders.py / writer.py 等 8 个文件。

工具约束说明: mutmut 的 source_paths 必须是整个 src(写单文件会因包内相对 import 失败), 目标靠 only_mutate 收窄。所以「目标 = 整个 src」是工具要求, 不是我们变异了全 src; 实际参与变异的只有 glob 命中的 config 包。

1.2 为什么先 config

  • 对象优先级第 3 位 —— 可行性报告 §11 按「判据密度 × 出错代价」排: ① rules/ ② hr/ ③ config/ ④ core/; infra/ 与 webui/server/ 估值最低。
  • config 是 fail-fast 校验层 —— 出错代价是「坏配置在启动期被静默接受, 或正确配置被误拒」; 判据密度高 (边界 / 枚举 / 交叉校验 / 迁移改写)。
  • 本轮的核心产出是一个刻度, 不是一次修复 —— 报告 §09 实测到「优先级最高的包分数反而最差」(rules/ 55.5% vs infra/utils 72.5%, 覆盖率却是同一个 98%)。config 目前没有实测分数; 本轮先给它一个覆盖率给不出的刻度, 用它决定后续要不要在 config 上投入补测, 而不是凭直觉。

2.2 变异数与单轮时长 (两个口径)

口径依据变异数单轮时长
报告 §08 包级锚点 1.00 变异/行 × 4,993 行 (全行计) ≈ 5,000 ≈ 11 min
本计划精化 (推荐读数) 剔除 1,151 行纯数据表后 ≈ 3,842 行 (函数体面) ≈ 3,800 ≈ 8.5 min

单价 = 0.134s / 变异, 取自报告 §08 的包级实测锚点 (rules/ 3,270 变异 / 7m31s, WSL 8 核 · --max-children 4)。两台口径的差别只在分子: 报告 §08 按「全行 × 1.00」估, 而 mutmut v3 只变异函数体(模块级常量与数据声明不在范围内, 报告 §03) —— schema 四表 1,151 行恰好是零函数的数据声明, 应在估算里扣掉。

精化是「预期上界下调」, 不是「估算缩小」。 首轮一律以实测变异数为准并原样记进切片:

· 实测显著低于 ≈3,800 → 说明还有一批声明被排除在 mutmut 范围外, 属正常, 记一笔即可;
· 实测显著高于 ≈5,000 → 要复核 glob 是否漏收/多收了文件 (先看 commands run mutants.status 回显的 only_mutate)。

合计186—
  • 为什么不用全 tests/: 实测全 tests 池会把 WSL 打挂 (报告 §07 对照四); 而宽池的代价落在内存不在结论 —— rules/ 宽池 vs 定向池杀死率只差 1 个点 (对照五)。
  • 池是「存活数的函数」: 这 6 个文件就是本轮的选择池变量, 必须原样写进切片; 换池后跨轮数字不可比 (报告 §09 · 坑档 mutation-pool-artifact.md)。
  • config 域无「读源码文本做断言」的守阵: 池内 6 个文件均不读 src/ 文本 (键面守卫读的是 tests/fixtures/ 与 memory-bank 文档)。因此 set_conf.py 的两条默认 --deselect 与本轮无关 —— 保留即可, 无副作用。

03执行步骤 S1–S7

命令一律走 task id (命令本体与陷阱内建在 mutants 包里, 不手拼裸命令)。用法细节用 commands run show mutants.run 取。

S1环境就绪

建 / 刷新 WSL 镜像仓 + uv sync + 装 mutmut 3.8.0。幂等; 首次或镜像落后时跑。后续 S2 会自动确保, 这条只在想单独预热时用。

commands run mutants.setup

门槛: 本机需装 WSL(Ubuntu-26.04)。没有 WSL 时改走 S2′ 的 Windows 兜底 (§下)。

S2首轮 (主力 · mutmut / WSL)

对 config 包跑一轮, 池 = §2.3 的 6 个文件。记下变异数 / 杀死率 / 耗时 / 工具版本 / 选择池。

commands run mutants.run -- --target '**/config/*.py' --pool tests/test_config.py tests/test_config_writer.py tests/test_hr_config.py tests/test_config_schema.py tests/test_impact.py tests/test_config_key_surface.py

存活清单 (可能数百行) 落 R:/Temp/auto-qb/mutants/<stamp>-*-results.txt, 终端只回显头部 30 行 —— 读全文按需 grep, 别整读。

入场条件 (硬): 基线必须全绿 —— 先跑 commands run test.quick。工具硬要求「基线全绿才开始变异」, 不绿会一行报错直接跳过。不绿先修, 别跑变异。

S2′ Windows 兜底 (可选, 不想开 WSL 时) —— 用第二工具交叉验证, 或作为无 WSL 时的替代:

commands run mutants.gremlins -- --target src/auto_qb/config/validation/core.py --pool tests/test_config.py

gremlins 是单文件目标, 需按文件拆多次; 算子面比 mutmut 窄 (无字符串/语句删除), 且因做覆盖率过滤而没有 no tests 分类 —— 两者分母不同, 分数只能各自纵向比, 不横向混。

S3三分类存活变异 (人的动作)

逐条读存活清单, 判成三类之一。分类是人的动作, 不是工具输出:

类判据处置
真洞变异后行为确实错了, 且没有测试抓得住→ S4 手工确认 → 入池或补测
等价变异变异后行为与原代码在所有输入上等价 (如 @dataclass(frozen=True) → False)记一笔「为什么等价」, 不追
假存活相关测试存在但不在选择池里 (换宽池就死)记一笔; 必要时加进池, 下一轮复跑

提示: config 域的高频等价形态 —— 校验消息文案 / 边界 <= 与 < 在离散整数域上的某些形态 / 异常类型替换; 高频真洞形态 —— 数值区间端点 (min/max 边界位移)、时间区间端点、迁移里「删/留」的分支。

S4手工确认 (只认这一个判据)

对每个疑似真洞, 在全套件下手工造一个同构变异 (直接改源码), 看是否变红。记法 (每条一行):

字段记什么
位置文件:行 (如 validation/core.py:117)
同构变异把 < 改成 <= / 删一行 / 换常量 …
全套件结果N failed, M passed —— 红 = 有测试抓得住(假存活, 只是没进池); 不红且行为错 = 真缺口

判据边界 (报告 §09 实测): 一个被判 SURVIVED 的变异, 拿全套件手工验证后其实是被杀死的 (utils.py 那条 return None 变异: 5 文件池报存活, 全套件 3 条新红)。所以「变红」不等于「真洞」, 只等于「池没选到」。

S5补测 (只对确认的真洞)

对确认的真洞加断言 —— 走正常测试流程 (改 tests/, 同步头部 docstring 的「## 测试计划」清单), 补完跑 commands run test.full。

若真洞指向的是代码缺陷 (而非测试缺口), 不在这里顺手改 —— 按范围守恒入池 memory-bank/issues/, 由用户决定什么时候修。

S6复跑

同目标 · 同池 再跑一轮 S2, 看存活数是否下降。换池的数字不可比 —— 池必须与首轮完全一致。

commands run mutants.run -- --target '**/config/*.py' --pool tests/test_config.py tests/test_config_writer.py tests/test_hr_config.py tests/test_config_schema.py tests/test_impact.py tests/test_config_key_surface.py

S7记录

  • 新建基线切片 memory-bank/testing/baselines/YY-MM-DD-HHMM-mutants-config.md (体例见 testing/baseline.md), 字段见 §4。
  • 任务档案追加一行轮次 (执行时另立 tasks/ 档案; 常驻锚 issue 不动 —— 除非要改覆盖范围)。
  • 真洞各自入池: 每条一个独立的 test / bug issue (有位置、有复现)。

04验收 (可判定)

#判据
1基线切片字段齐全 (缺一即跨轮不可比): 目标 glob · 选择池逐个文件 · 变异总数 · 杀死 / 存活 / no tests / 超时 计数 · 杀死率 · 耗时(墙时 + CPU) · 工具名 + 版本 · --max-children · 机器(WSL 核数) · 手工确认后的真洞数 + 各 issue 链接 · 一行 **Refs:** <任务档案路径>
2三分类后的真洞全部已入池或已当场补测 (无悬空真洞)
3复跑 (同目标同池) 存活数 ≤ 首轮
4补测后 commands run test.full 全绿; 覆盖率不低于基线
注意口径: 目标不是「分数涨」, 是「config 包内不再有不知道为什么活着的变异」—— 每条存活都要有一个分类理由 (真洞 / 等价 / 假存活)。等价变异杀不掉是数学事实, 不追。

05风险与停手点

风险 / 现象停手点与处置
基线不绿停, 先修基线 (test.quick 过) 再跑 —— 工具会直接跳过变异
WSL 整体失去响应wsl --shutdown 救回 → 降 --children 重来; 核目标 glob 是否多收了文件
池越宽内存越紧回 §2.3 的定向 6 文件池 —— 宽池代价落在内存不在结论
--deselect 表随测试拆分漂移本轮 config 池无源码文本守卫, 预期不触发; 若基线仍报文本层守阵红, 先核 set_conf.py 的 DEFAULT_DESELECT 路径是否漂移 (test_web 拆分已发生过一次)
把存活清单当缺口单停 —— 必须先 S3 分类 + S4 手工确认; 假存活比例不小
换池后跨轮比存活数禁止 —— 池是变量, 数字不可比; 池必须写进切片
拿 mutmut 分数与 gremlins 分数横向比禁止 —— 分母不同 (前者含 no tests)
计划的边界: 本计划只写「怎么修、为什么这么修」, 不实施。执行时按 memory-bank skill 立任务档案, 轮次进档案; 计划本身拍板后冻结 (改版 = 同文件加变更记录 + 抬 doc-updated)。
