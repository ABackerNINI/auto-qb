提交信息自动审查: ship.commit 内联三态机检(BOM/乱码/骨架/残留)

在 ship.commit 的 git commit -F 之前内联一道提交消息机检:三态(硬拦 / 自动修 / 警告)覆盖编码损伤、gitmoji 骨架、正文标签结构与 AI 写作残骸;检查器独立纯函数模块,逃生走配置白名单,正文零代改。

§01目标与设计原则

为什么做:AGENTS.md 对提交消息有成文口径(首行 <gitmoji> <中文一句话概述> + 空行 + 动机/取舍/影响面/实测),但这条口径只有 agent 纪律在守,没有任何机检消费——消息文件写坏了(BOM、GBK、全英文、丢骨架)会原样落进历史。检测点选在 ship.commit 内联(不做成 [[gates]] 闸门):消息不是「改动文件」,闸门的 <changed:> 语义接不上它;且检查必须在 git commit -F 之前,闸门复跑阶段的 amend --no-edit 复用的已审消息无需再查。

做到什么程度算成:①目录内十类硬拦条目全部能在提交前拦下并给出条目 id + 原文引用;②骨架位自动修(BOM / gitmoji 承接空格 / 首行后空行)修后留痕、正常落库;③全绿零修正时输出完全静默(包哲学「沉默即成功」);④逃生白名单 msg_check_allow 生效且未知 id 触发配置 STOP;⑤test.pkg.scoped 全绿。

设计底线 / 不变量:

  • 正文零代改(拍板 D4):自动修只发生在骨架位——文件头 BOM、gitmoji 承接空隙、首行后空行;正文与首行中后部的任何字符都不代改,最多警告。
  • 修正必留痕:脚本改写了 agent 写的消息文件,每处修正打印一行;绝对静默只属于「零修正的绿」。
  • fail-fast:白名单里的未知 id = 配置错误 STOP(与未知顶层键同级),不做静默忽略。
  • 检查器纯函数:核心逻辑进独立模块 msg_check.py,输入文本输出报告,不碰 git、不碰全局状态——commit.py 只做文件读写与输出接线,快照语义下天然无副作用。

§02现状与痛点

commit.py 今天对消息只有两道检查:存在性(commit.py:279)与残留扫描(内容 == HEAD 消息即拒跑,commit.py:257-263);消息内容本身零审查。四条实测证据(2026-11-06,临时仓库真跑 git commit -F):

  • BOM 不被 git 剥离:EF BB BF 原样进入 %B——Windows 上 PowerShell > 重定向写 UTF-16LE、cmd echo 写 GBK,字节直落历史;
  • CRLF / 行尾空白会被 cleanup=whitespace 自动剥离——这两条不需要查(拒收存档的依据);
  • # 开头行在 -F 下原样保留(注释剥离只发生在编辑器流程)——粘贴编辑器模板会污染消息;
  • 反引号是既有用法:近 200 笔语料 21 行含反引号,-F 路径无 bash 替换风险——拿它当事故信号会批量误伤(拒收存档的依据)。

历史事故单点 memory-bank/pitfalls/git/message.md 记录的「反引号被 bash 当命令替换」「-F - heredoc 吞 push」均发生在手拼命令路径;本计划把「消息质量」这一层也接到机检上,补齐 ship.commit 唯一没有机检消费的成文口径。

§03方案总览

主线:新增 .commands/my-commit-flow/scripts/msg_check.py(纯函数 + 文件层入口),commit.py 在 msg_file.exists() 之后、闸门之前调用;新配置键 msg_check_allow 进 KEY_DEFAULTS,白名单校验挂 config_problems STOP 级。

条目理由

逃生与接线(拍板 D5/D6)

  • 逃生白名单:msg_check_allow = ["b4", …](KEY_DEFAULTS 兜底 [])只放行硬拦档——警告无 suppress 需求、自动修不会误伤;未知 id 在 config_problems 报 STOP。失败行自带出路:「误报逃生: .my-commit-flow.toml 加 msg_check_allow」——与包内「失败行给下一步」风格一致,不留后门旗标。
  • 检查顺序:读文件(strict UTF-8;a2)→ 空判(d7)→ A1 → B3 → C1 → 硬拦清单 → 警告清单(全部基于修后文本判定,顺序即修先于检)。
  • 输出契约:修正行/警告行/违规明细 print 在上,失败走 emit() 单点一行「提交失败: 提交信息机检 N 项未过 —— 重写消息文件后重跑」;消息文件保留(与 git commit 失败同款:修好重跑还能用同一份,但用修后文本)。
  • 不做独立命令入口;显式 --message-file 同受检同自动修;amend --no-edit 不复检。

§07风险与对策

风险触发条件对策
检查器误伤合法消息语料冒出撞签名的形态(如正文合法引用 TODO 已降警告;c2 口径遇「一句话裸正文」)失败行引原文可判 + 白名单按 id 放行;误报属检查器缺陷,修完随本次提交入库
VS16 / 多码点 emoji 拆分误判🗑️/♻️/⚡️ 等带 VS16 的 gitmoji 被当非标准集比对前统一去 VS16 归一;语料高频 emoji 逐个进单测
自动修写回与残留扫描相互作用BOM 版消息恰与 HEAD 消息「相等」Python str.strip() 不剥 U+FEFF,残留扫描(先跑)不会误判;review 在其后,写回的是修后文本,自愈语义不变
快照语义下的文件写回包脚本跑在仓库外副本,消息文件路径解析错位msg_check 只收 Path;路径由 commit.py 的 root 解析(与既有 msg_file 同一来源),无新增路径逻辑
GBK 控制台打印 emoji 崩(历史事故)失败行/修正行含 emoji 或中文commit.py 入口已 reconfigure utf-8(pitfalls/git/message.md 处置),新打印全部走该入口之后
