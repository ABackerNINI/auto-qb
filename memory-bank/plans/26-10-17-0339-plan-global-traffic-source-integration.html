R1 的起因:原设计让 auto-qb 在拉起时条件计算 --autostart true|false(provider = 工具来源且用户未关过 ⇒ 真)。「把该旗标固化进启动器以解耦 CLI 形态」这一改法会与 D13 冲突 —— 它的取值是可变的,而 false 那一支正是「用户显式关过 ⇒ 不被装回」的防复活闸,固化成常量等于把闸门焊死。故改判为:启动器只携带"顺带注册"这一个恒定意图,是否真注册由工具侧 config autostart 裁决 —— 判断权下放给状态的持有者,auto-qb 侧既不持有也不计算该状态。
R2 的起因(真机事故):26-10-17 14:00 的 v4→v5 迁移把 provider 推到 global_traffic_monitor,但旧段里根本没有 data_dir 可迁 —— 于是配置里该键为空、active_dat_path() 返回空串,曲线日志刷 读取流量数据失败(): No such file or directory: '',顶栏与历史图全空;而状态区显示的是指针里的真实数据目录,看上去「工具已就绪」。根因不是迁移漏搬一个键,而是同一件事有两个来源:数据目录本来就是工具的事实(它自己报在发现指针里),配置再存一份只会漂移。故 R2 删掉这个键,取数路径只认指针。

02拍板结论(grilling 收敛)

以下 19 条为五轮 grilling 与 R1 改版的全部决策(D19 为 26-10-17-0429 增补),实施不得再自行变更;确需变更按「同文件内变更记录 + 抬 doc-updated」处理。

#决策
D1单一来源开关:新建顶层 traffic_source 段,provider: traffic_monitor | global_traffic_monitor;严格单选互斥(两来源参数可并存,但只有一个生效);不静默回退。
D2配置落点:traffic_source.traffic_monitor.dat_path 与 traffic_source.global_traffic_monitor.{tool_dir,tool_exe,notify_cooldown_s}(不含 autostart,也不含 data_dir —— 见 D20) —— 自启状态与裁决都在工具侧,见 D13/D19);顶层 global_traffic_monitor 段退休;global_speed_limit_curve 只留 curves/interval/enabled。工具自身参数(采样间隔/通知阈值/适配器过滤)不进 auto-qb 配置,仍经控制面读写、默认即用、高级项折叠。
D3迁移走配置升级路线:用既有迁移链新增 MIGRATIONS["config"][4](v4→v5) —— 旧段下移 + 删四键 + dat_path 迁移 + provider 推导;逐键 note → WARNING;沿用启动物化单点的原子写回 + 备份。
D4工具进程形态不削减:独立进程 + 开机自启 + 多 auto-qb 共享服务;自启绝对支持,不可移除。
D5auto-qb 的角色:只做「探测 → 缺席时一次性引导拉起 → 之后走控制面订阅」;不是守护者,不管工具死活、不接管其生命周期。
D6发现机制:指针文件 endpoint.json 落在用户级平台目录(Windows %LOCALAPPDATA%\global-traffic-monitor\ / macOS ~/Library/Application Support/global-traffic-monitor/ / Linux ~/.local/share/global-traffic-monitor/),与 --data-dir 解耦、只此一处;控制面 bind 成功后原子写;优雅退出删;字段见 §05。不含密钥本体(只给 token_path)。
D7就绪判据只认探活:用指针里的 host/port 发 GET /status(带 token),200 才算在跑;残留指针文件不算就绪、不阻止拉起;pid 仅作展示。
D8单实例锁锚在指针旁(用户级目录),而非 data_dir ⇒ 整机一个工具、指针无并发写;锁必须在绑端口/采样之前 acquire,抢输的进程 fail-fast 且不占端口。
D9随机端口:工具 http_port 默认 0(内核分配),校验放开 0;指针记真实绑定端口;新增 global-traffic-monitor endpoint 子命令打印当前端点;自启项不烧端口(只写 data_dir)。
D10拉起解析顺序:①tool_exe 非空 → 直接执行该可执行文件(显式覆盖 / 编译态逃生门);②否则 tool_dir(空 = 仓库内相对路径 <repo>/tools/global-traffic-monitor)→ 执行目录内的 D19 启动器;③启动器与 tool_exe 都找不到 → UI 报「未安装」+ 文件选择器引导写 tool_exe。auto-qb 不拼 uv、不认识入口名与子命令 —— 这些全部沉进工具侧启动器(D19)。
D11双模目录定位契约:resolve_tool_root() = getattr(sys,"frozen",False) ? Path(sys.executable).parent : 由 __file__ 推导的安装目录。源码位置定位不了编译后的 exe(onefile 的 __file__ 指向 sys._MEIPASS 临时解包目录),故必须双模。
D12数据默认落点:<工具安装目录>/data(不是 shell 的 PWD —— 自启时 Windows 的 cwd 常为 %Windir%\system32);--data-dir/GTM_DATA_DIR 仍可覆盖但指针不随之移动;旧用户目录数据在「目标空」时一次性自动搬迁(幂等);D19 启动器不传 --data-dir —— 落点全由工具自解析(PWD 在被拉起/自启时不可信)。
D13自启触发与裁决:auto-qb 拉起工具时不传任何自启参数 —— 自启意图只有一个恒定值,写死在工具侧启动器里(D19);是否真注册由工具自己裁决:工具 config autostart(默认 true)被用户显式改为 false ⇒ 本次注册 no-op,不会被自动装回;设置页开关变更走 POST /autostart(install/uninstall,幂等)并回写该 config;auto-qb 不保留 autostart 配置键,UI 开关状态读指针 autostart_registered(§05)。
D14多实例竞争:探测失败才拉起;拉起后短等待探活;失败按固定退避 30s 重试;探活成功但 pid 非我所起 ⇒ 别的实例已拉起,直接订阅、不重复拉;不做实例间通信。
D15设置页合并:两处并成一张卡「全局流量来源」 —— 顶部 provider 单选,选中谁展开谁,底部工具状态区 + 「立即拉起/重试」+「打开工具设置」;限速曲线卡删掉来源字段。
D16改名只限用户可见面:CLI 命令 global-traffic-monitor、env GLOBAL_TRAFFIC_MONITOR_DATA_DIR、配置键全称、UI 文案、指针/锁/用户级目录名;Python 包 gtm、import、内部注释、内部文档继续用 gtm。
D17键面清理:删 tool_url/tool_token_path/subscribe/autostart;工具子块只留 D2 列的三键(tool_dir/tool_exe/notify_cooldown_s)。
D18非目标:qb_traffic 不进 provider 菜单;auto-qb 不守护工具;不改工具落盘格式与采样语义;不要求用户配置端口/密钥。
D20取数路径只认工具指针(R2):删配置键 traffic_source.global_traffic_monitor.data_dir 与设置页对应字段;取数路径由运行期单点 core/traffic_source/paths.py::dat_path(config) 解析 —— provider=traffic_monitor 读配置的 dat_path,provider=global_traffic_monitor 读发现指针的 data_dir + 契约文件名 history_traffic.dat(只读指针、不探活;指针缺失 = 无数据源,不回退 TM 文件)。指针是用户级/整机一份,故多 clone 自动一致;工具换数据目录零配置。active_dat_path() 随之退休,不许再有第二个入口。启动期不再校验工具来源的路径(_expr_gate 对 gtm 恒放行),缺路径由状态区与运行期日志承担。
D19启动器契约(工具侧拥有「怎么起」):工具根目录(resolve_tool_root(),D11)预置平台启动器 —— Windows launch.cmd / POSIX launch.sh;编译态同一条路径(启动器内容退化为调用同目录的可执行文件)。内容由工具自己维护:优先用工具自带 venv 解释器(装依赖时已建),缺失才兜底 uv run --project <本目录>;恒定携带自启意图常量(D13);不传 --data-dir(D12)。auto-qb 侧只做「resolve_tool_root() → 找启动器 → Windows cmd.exe /c / POSIX /bin/sh <脚本> detached 执行」——不认识 uv、不认识入口名与子命令;工具升级换命令形态只改启动器内容,auto-qb 零改动。tool_exe 显式覆盖仍在(先于启动器,逃生门);就绪判据仍是探活(D7),不看启动器退出码(detached 拿不到)。

03总体架构

三层事实:工具写指针 → auto-qb 读指针探活 → 缺席则引导拉起。指针是发现层的唯一事实源,数据目录只影响「数据放哪」,不影响「怎么找到工具」。

09风险与对策

风险对策
用户级指针目录被别的用户/权限挡指针目录按用户隔离(多用户各自一套)属预期;写入失败只告警,回退「直接探默认端口」并提示
仓库内 data/ 被 git 误纳S14 强制补 gitignore + S18 验收项;已有 git 纪律守卫兜底
uv 不在 PATH(部署机)启动器内部优先工具自带 venv 解释器(装依赖时已建),uv 只作兜底;auto-qb 侧不拼 uv —— 最坏情况也只剩 UI 引导写 tool_exe(D10 ①)
部署机挡启动器 / 无执行权限Windows 经 cmd.exe /c、POSIX 经 /bin/sh <脚本> 调用(不依赖 exec 位与 noexec 挂载);失败落「拉起失败」态 + 退避重试,不阻塞主流程
编译版首次冷启动不知 exe 在哪默认仓库相对路径;找不到时设置页文件选择器(D10 ③),状态区区分「编译版/源码版」
探活超时被误判为「未运行」首次引导 120s 容忍 uv 装依赖;超时只 WARNING + 退避重试,不阻塞主流程、不改来源
迁移把生产 config 改坏沿用既有「备份 + 原子写回」机制;config.yml 属生产红线文件,迁移由程序自身在启动物化单点完成,不由 agent 手改
