§01目标与设计原则

为什么做

memory-bank 已积累 1,093 个主题 md、约 421 万字符。按 2026-11-05 新口径, 四类高周转文档(log / evergreen / pitfall / index-auto)的历史 cap(48K / 20K / 12K / 25.2K)过大, 单个文档动辄上万字符, 与"先索引后细读、禁止整读"的检索纪律冲突; 过期信息(失效路径、被代码推翻的结论、历史状态残留)没有固定清理动作, 只能靠人临场判断。

同时, 旧的"触顶后压到 50%"策略把成本推给写作时的返工, 并未阻止回涨。本轮要同时解决两件事: 一次性把存量水位降到 8,000, 以及把防回涨前移到模板、条款与守卫。

做到什么程度算完成

  • cap 单点: _common.CAP_POLICY 中 log / evergreen / pitfall / index-auto / task = 8,000; 存量 task 由 CAP_TASK_FREEZE 整类豁免; 其余承载 cap 的文档只留指针。
  • 四类清零: commands run doc.caps 对四类不再报债务; 新 task 不再出现 > 8,000 的债务行。
  • 过期信息: 每件生活文档的失效路径与过期标记有明确处置(删除 / 改写 / 改状态), 不留"（已废弃）"段落。
  • 防回涨: 写前判定、超限固定动作、陈旧度提示、规则强度分级四项落成条款与机械守卫, 且守卫测试为绿。
  • 不动清单: 存量 tasks、生成物、第三方 skill、生产配置与运行时数据零改动。

执行顺序与理由

  1. B0 先行: 先把"写前判定 + 超限固定动作 + 陈旧度提示 + 规则强度"落成条款与守卫, 否则 B1–B4 清完还会按旧习惯涨回去。研究结论与原计划一致: 防回涨必须前移。
  2. B1 次之: 只做"单点已存在、删副本改指针"的活, 低风险、可机械验收; 它同时给后续批次腾出索引与入口的阅读预算。
  3. B2 再次: 过期信息先删, 能直接减少 B3 要处理的正文; 顺序反过来会把死段也认真蒸馏一遍, 纯浪费。
  4. B3 / B4 最后: 需要逐件人工判断(蒸馏、拆分、生成器改造), 风险最高; 放在前面两项之后, 复测数字才干净。
  5. B5 全程生效: 存量 task 不动是约束, 新 task 8K 是守卫, 不占执行窗口。

§06豁免机制: 整类豁免与个案豁免

现有机制(实测结论)

doc.caps / check_kb_structure.py 没有逐文件白名单。现有三类豁免都写在代码里, 靠常量与判据表达:

形态现有先例表达方式谁能改
按角色CAP_POLICY角色 → cap; 同一角色的所有文件适用同一上限用户定调, agent 改常量
整类日期冻结check_doc_templates.FREEZE_DATE · check_wording.FROZEN_TEST_NUM_COUNT常量 + 文件名日期/命中数判据; 存量不回头改, 只拦新增用户定调, agent 改常量
缩小扫描面check_caps(only=...)只用于提交闸门"本轮改动文件", 不是豁免; 不能拿来规避债务脚本内部

整类豁免: 存量 tasks

项定义
表达_common.CAP_TASK_FREEZE = "26-11-05"; _is_stock_task(path) 按文件名前缀 YY-MM-DD- 判断, 小于冻结日即跳过 cap 检查
范围仅 task 角色; 只豁免"存量", 不豁免新建。冻结日之后的 task 仍按 8,000 判
文档内如何写无需逐件写理由 —— 理由属于整类口径, 单点写在 SKILL.md「2026-11-05 重定调」段: 存量 task 只在排障时读, 改造收益低
由谁审用户。冻结日是用户定调的一部分, agent 不得自行改日期或扩大范围
退出条件用户显式改 CAP_TASK_FREEZE, 或存量 task 全部归档后自然消失; 本计划不设退出动作
验收commands run doc.caps 无 task 债务行; 新建 task 超限仍报债务

个案豁免: 默认不做

原则上不豁免。确实需要时, 必须同时满足三条, 缺一不可:

  1. 文档内写明理由: 在文档三行头之后加一行
    > 豁免: <为什么不能删/外迁> (审: 用户, YYYY-MM-DD)
    HTML 制品写在 doc-addendum 或正文首段; 理由必须指向具体约束(如"这是真机证据快照, 删段会破坏证据链"), 不能写"暂时保留"。
  2. 登记在案: 在 _common.py 增加 CAP_INDIVIDUAL_EXEMPT: dict[str, str](仓库根相对路径 → 理由摘要), 守卫校验"路径在表内 且 文档含匹配的豁免行"; 不登记 = doc.caps 照常报债务, 豁免不生效。
  3. 用户逐件确认: agent 只能在计划 §09 提出候选与理由; 用户说"批准"后才写进常量。agent 不得自批, 也不得用"整类"话术绕开逐件确认。

期限条目必须带复审日期; 到期自动失效(守卫按日期判), 需重新申请

§07引导 agent 写清晰简洁有效的文档

定位: 这一章解决"防回涨", 不是"事后压缩"

现有机制(四工位、单一权威、角色 cap、机检、索引生成)已接近成熟。缺的四件事全部属于写前与写中, 不是清债:

  1. 写前判定: 这篇文档只回答什么问题、属于哪种形态。
  2. 超限固定动作: 触顶后外迁 / 删死段 / 合并邻近件, 而不是压文案。

模板骨架(只写结构, 不新建模板文件)

  • plan: 只回答: 怎么修? → Context(现场与约束) → Decision(批次与动作) → Consequences(减量/风险/回滚)。批次表跟在 Decision 后。
  • task: 状态行(Status/Added/Updated/Summary) → 原始请求 → 思考过程与决策 → 实现计划 → 子任务状态表 → 进度日志。
  • pitfall: 三行头(标题/摘要/触发) → 触发 → 判别 → 处置 → 守阵/复发 → Refs。
  • report: 现场 → 证据链 → 结论 → 影响面; 不写修复步骤。
  • progress: 现行结论 → 已完结轮次指针 → 未决项链接; 流水在 attachments/。
  • index / about: 标题 → 摘要 → 触发 → 每条一行(链接 + 一句话)。
