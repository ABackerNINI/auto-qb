01

问题：每次同步都要人肉解冲突

多 clone 并行下，两个会话都会在收尾阶段重跑索引生成器，于是同一批 _index.md 在两边各自产生新版本。后同步的那一方必然撞车，而 my-commit-flow.sync 现在的行为是见冲突就停，于是执行者被叫去手工合流。

失败点只有两处，都在 .commands/my-commit-flow/scripts/sync.py，而且都不区分冲突落在手写源文件还是生成物：

位置触发条件现在的结果
sync.py:93-98 落后（ahead == 0）+ 本地脏改动与远端新提交重叠，git merge --ff-only 被拒 失败行「本地改动与远端新提交重叠」—— 这就是日常说的「快进失败」
sync.py:104-108 已分叉 + git rebase 过程中出现任何冲突 rebase --abort 全量回滚 → 失败行「需解决冲突」

证据

  • pitfalls/git/sync-pull.md 的「提交点撞远端前移」条目复发已 7 次（1 + 计划 26-10-01-2216 阶段1/阶段2 两度 + 2026-10-01/02 四次）。
  • 其中 2026-10-01 一条明确记录：「ship.commit 首跑失败（重叠文件为生成物 plans/_index.md）」；另一条记录 tasks/_index.md 自动合并无冲突。
  • 同一份陷阱文件里已经写明「旧做法『git checkout -- 掉生成物索引再 sync』只对可重跑的生成物安全」—— 也就是正确处置早就知道，只是没接线到脚本里。

杠杆：一个单点，三条入口

run_sync() 是 sync / commit / push 三条入口共用的唯一函数：sync.py 的 my-commit-flow.sync 任务、commit.py:136 的「内部同步」、push.py:44 的推送前同步，全部调它。改一处，三处受益，不存在「改了 sync 但 commit 还是老行为」的分叉。

02

目标与不变量

目标

  1. 生成物冲突零人工冲突或重叠若全部落在可重跑的生成物上，同步自行化解并给出成功行。
  2. 手写冲突零变化只要有一个手写文件参与冲突，行为与今天逐字一致 —— 该失败就失败，绝不猜。
  3. 不新增第二处集合定义「哪些文件是生成物」只能有一处声明，闸门、重建入口、sync 白名单都从它取。

不变量（改动不得破坏）

  • 失败后仓库状态与跑之前一致 —— 沿用现有纪律「写状态的命令必须比只读的更干净地失败」。任何异常路径都要 rebase --abort / 不做半截丢弃。
  • 输出契约仍是一行 —— 成功一行、失败一行（原因 + 下一步）。失败行模板逐字不变，调用方不用改。
  • 保守默认 —— 白名单取不到、重建命令缺失、自证失败、循环超限，一律退回今天的失败行，绝不「部分解决后硬上」。
  • 判据纪律不变 —— 判落后仍只认 ls-remote 现查的远端真值，不读 refs/remotes/* 快照（见 pitfalls/git/refs.md）。

为什么重跑必然收敛：四个生成器都是纯函数

输出只由工作树里的手写文件决定 —— 主题 .md 的三行头元数据（# 标题 / > 摘要: / > 触发:）、档案的 **Status:** 等字段、HTML 制品的 doc-* meta。不读 git、不读时间戳、不读环境。因此「任取一侧 + 重跑生成器」必然得到唯一正确内容，不需要任何文本合并。

单点定义：新增 gen_all.py

新增 .agents/skills/memory-bank/scripts/gen_all.py，作为生成物集合的唯一声明处：

调用行为谁用
gen_all.py依次跑四个生成器（等价于现在 kb.index 做的事）重建入口 / sync 的重跑
gen_all.py --list打印它负责的全部路径，一行一个sync 的白名单来源
gen_all.py --check全部校验，漂移即 rc=1 并逐条报路径自证闸门 / kb.check

随后把 .commands/kb/config.toml 的 kb.index / kb.check 改为调它（各从 4 条命令收成 1 条），集合从此只有一处。这是本方案唯一的「顺手重构」，理由是：若 sync 自己再抄一份清单，就是第 N+1 处副本，而「哪份才生效」不写在清单旁边 —— 这正是 scripts/check_command_drift.py 那条闸门要防的东西。

04

机制设计

三步不变量：白名单 → 重跑 → 自证

  1. 白名单只有「能被生成器重跑出来」的路径才允许自动解决。来源是生成器自己声明的 --list，不是手抄常量 —— 新增索引目录自动进入白名单，不需要改 sync。
  2. 重跑冲突解决只做机械动作（任取一侧），内容一律由生成器重写。不做文本合并，不做行级并集。
  3. 自证重跑后必须让生成器自己的 --check 通过。通过 = 文件内容确实等于生成结果 ⇒ 证明没有手写内容被丢弃；过不了就回滚 + 失败。这是敢默认打开的全部理由

S1 · 落后 + 本地脏与远端改动重叠（快进被拒）

  1. 算重叠集：git diff --name-only HEAD <远端 tip> ∩ 本地脏文件（staged + unstaged，用现成的 changed_files()）。
  2. 重叠集 ⊆ 白名单 → 逐路径 git checkout HEAD -- <path>（丢弃本地那一份生成物，索引与工作树一起回 HEAD），重试 merge --ff-only，然后重跑生成器。
  3. 重叠集含任何非白名单路径 → 现状失败行，一字不改。

只处理「被修改」的路径。本地若把某个生成物删掉或改名了，属于异常状态，直接走失败支，不猜意图。

S2 · 分叉 + rebase 冲突

把单次 git rebase 换成有界循环：

  1. rebase 停下后取冲突集：git diff --name-only --diff-filter=U。
  2. 非空且 ⊆ 白名单 → 逐路径 git checkout --ours -- <path>（rebase 里 --ours 是上游侧；取哪侧无所谓，内容马上被重写）→ 重跑生成器 → --check → git add → git rebase --continue（带 GIT_EDITOR=true，防挂编辑器）。
  3. 出现任何非白名单冲突 → rebase --abort → 现状失败行。
  4. 循环上限 = 本地独有提交数 + 1，超限即 abort（防死循环）。

收尾再自证一次。多提交重放时，中间那次重跑是基于「部分重放」的树。所以 rebase 完成后要再跑一次生成器 + --check；若仍有漂移，git commit --amend --no-edit 把最终结果折进 tip —— rebase 之后的 tip 是未推送的本地提交，amend 是安全的本地操作。

新配置键

写在 .commands/my-commit-flow/.my-commit-flow.toml。三个键必须同时加进 _ship_config.py 的 KEY_DEFAULTS，否则 config_problems() 会按「顶层未知键」直接 STOP —— 这是 load_config() 的白名单过滤机制，属于既有 fail-fast 约束。

键默认含义
auto_resolve_generatedtrue总开关。false = 完全回到今天的行为（一个冲突都不碰）
generated_list_cmdpython <skill-dir:memory-bank>/scripts/gen_all.py --list白名单来源
generated_regen_cmdpython <skill-dir:memory-bank>/scripts/gen_all.py重跑命令（自证 = 同一命令加 --check）

两条命令走现成的 <skill-dir:NAME> 占位符机制（_pipeline.expand_run），与闸门用的是同一套解析，不新造一套。

保守默认：下列任一情况即退回现状失败行

  • 白名单取不到（命令缺失 / 非 0 退出 / 输出为空）
  • 重跑命令执行失败
  • 重跑后 --check 仍报漂移（= 白名单里有东西其实不是生成物）
  • rebase 循环超限，或 --continue 报「nothing to commit」等异常状态
  • 路径解析异常（删除 / 改名 / 非 ASCII 转义）

#场景断言

5白名单取不到 / 重跑 rc≠0 / --check 红失败；仓库状态与跑之前一致（三种子情形各一条）
6幂等化解成功后重跑 sync → 已同步

夹具不依赖真实 memory-bank。用一个「假生成器」小脚本（写固定内容）+ 一个临时清单文件充当白名单与重建命令，配置指向它们即可 —— 这样测试与库内容解耦，也不受索引真实漂移影响。

取舍记录

以下四条都认真考虑过并否掉，记下来是为了避免以后重新踩一遍：

方案为什么不用
git rebase -X theirs / -X ours 策略作用于所有文件，会静默把手写冲突也取一侧。这是最坏的一类失败 —— 不报错、内容错、还能提交。
.gitattributes 的 merge=union 行级并集会让 _index.md 留下重复行与半行，闸门照样红 —— 只是把「冲突」换成了「坏内容」，问题没解决，还更难查。
自定义 merge driver 要在每个 clone 的 .git/config 里注册（不可提交），漏配的 clone 行为不同 —— 与「多 clone 并行」的现状直接相冲；且 driver 拿不到完整工作树，无法重跑生成器。
冲突时任取一侧直接 add 省掉第三步自证 = 完全相信白名单。白名单一旦写错就静默丢内容，且要到很久以后才发现。第 3 步的成本只是一次 --check，换掉这个风险很值。

09

边界：本期不做

  • S3（分叉 + 树脏）不动。现在直接拒。丢弃工作区未提交的改动，风险比丢弃已提交内容高一档，且「未跟踪新文件」还要 stash -u 才收得走。留作第二期，机制可复用。
  • 手写文件的冲突永远人工。不做语义合并、不做行级启发式。
  • 不碰未跟踪文件、不碰白名单外的任何路径。
  • 不改判落后 / 判齐平的判据（仍只认 ls-remote 真值）。
  • 不为「消掉一次失败」加手工预检 —— 沿用现有处置纪律：复踩代价 ≈ 一次重跑，不值得加前置检查。
