HR 三参数解耦:
拉取间隔 · 复用窗 · 立即拉取

现状三个参数互相掣肘的根因只有一个:复用窗的时长直接借用了「对账波周期」这个配置值, 而插件的「立即拉取一次」在设计上就只是排空后端任务队列 —— 它从来不能触发取数。 本计划把三者拆成正交参数:节奏归拉取间隔,新鲜度归可配置的复用窗(默认 2 小时), 人工意志归立即拉取(压过前两道闸,但账号安全频控照常)。

§1

现状诊断:三个参数在代码里的真实关系

逐条给代码事实。结论:「对账波周期」和「复用窗」在实现上是同一个数,而「立即拉取」根本不在同一条链路上。

参数代码事实用户感受
复用窗 唯一写入点 service.py:1031 —— data.expires_at = now + site_conf.refresh_interval if any_ok else 0.0;唯一消费点 service.py:448 —— 窗内直接 ACTION_REUSED 返回,不取数。展示在 status.py:272(「复用窗至 MM-DD HH:MM:SS」)。 时长不可配置;实际长度 = 对账波周期(默认 12H)—— 太长,数据最长陈旧 12 小时;「太长失去意义」。
对账波周期 refresh_interval(schema/hr.py:81,站点级,默认 12H)。名义是「在线对账多久跑一波」,但全链路没有第二个节奏闸门:ratelimit.next_allowed_at(ratelimit.py:97)只算 min_interval(90s)/ 日额 / Retry-After / 时间窗。所以它唯一的实际作用就是充当复用窗时长。 字面难懂;且「对账波周期仍要看复用窗」—— 因为两者就是同一个变量,不是谁看谁,是同一体。
立即拉取一次 options.html:163 按钮 → options.js:494 poll() → background.js:289 {type:'poll-now'} → pollAll('手动(选项页)') → GET /api/hr/tasks → queue.take_batch()(server.py:222)。队列内容由后端取数线程决定(worker.py 60s 节拍 → service.refresh_site → 被复用窗挡住)。 点击时若处于复用窗内,队列恒空 → 「无任务」。按钮从设计上就只是「排空队列」,不是「触发取数」。
§2

目标行为:三个正交参数

新参数配置键默认语义闸门位置
拉取间隔 hr_check.sites.<id>.refresh_interval
(键不变,展示名与 help 重写)		 12H 波次硬节奏:下次拉取 = 上次健康波 + 本值。失败波不推进基准 → 失败的档位仍按「下一轮重试」(与现状一致)。 service._refresh_locked
新增
数据复用窗 hr_check.reuse_window
(新全局键)		 2H 波后数据新鲜窗:窗内本实例/其它实例直接复用不取数(多实例去重 + 新鲜度展示)。生效值 = min(本值, 拉取间隔)。 service.py:448 既有分支,时长换源
立即拉取 非配置 —— 人工动作 — 跳过「复用窗 + 拉取间隔」两道闸立即开波;保留 min_interval / 日额 / Retry-After / 时间窗(账号安全线,详见 §3.2 决策)。 插件按钮 + WebUI 按钮 + --hr-once
关键正确性

解耦的同一时刻必须新增「拉取间隔」闸门。现状里防止按 90s 间隔连波取数的唯一机制就是复用窗 (expires_at);若只把复用窗缩到 2H 而不加节奏闸门,取数频率会从「12 小时一波」变成「约 2 小时一波」 —— 站点访问量放大 6 倍,直接踩访问安全线。这是本计划唯一的行为风险点,已作为独立改动项(§3.2-B)与测试项(§6)钉死。

决策 · 为什么基准是 healthy_ts 而不是 fetched_at

fetched_at 随失败波也会前进;若以它为节奏基准,「全档失败 → expires_at=0 → 下一轮(60s)重试」的现行失败处置 (service.py:1029 注释、§5.2「档位截断 + 周期自然重试」)会被拖慢成一个拉取间隔。 wave.healthy_ts(上次健康波)不随失败波前进,节奏语义与现状完全一致;部分失败的波两者都推进, 失败档位仍等下一波 —— 与 schema help「按本周期自然重试」的承诺一致。

决策 · force 保留哪些频控:min_interval(最多再等 90~112s,锁内等待已有 PROD_REQUEST_WAIT_MAX 上限)/ 日额 / Retry-After(站点明确指令)/ 时间窗(用户自设)一律照常 —— 「立即拉取」压过的是本程序的调度意志,不该压过账号安全线与站点指令。等待原因照常出现在状态与日志里,可解释。

§4

兼容与迁移

场景处理
旧站点文件里的 expires_at(= 旧 12H 窗)不迁移。下次成功波按新公式(min(2H, 12H))自动重算;期间旧窗最多再生效一次,无判定影响(证据无时效)。
用户生产 config.yml零改动(红线)。新键缺省即默认 2H;「对账波周期」只是展示名,键名 refresh_interval 不变,配置文件无需任何编辑。
旧后端 + 新插件POST /api/hr/refresh 得 404 → 插件降级为纯排空 + 日志提示升级,不报错。
新后端 + 旧插件旧 poll-now 消息保留,行为不变;新端点只是没人调。
多实例共享目录force 旗标是实例内内存态,不落共享文件;共享文件的 healthy_ts 已天然去重,A 实例刚跑完健康波,B 实例不会因 force 重复跑(force 只跳自己实例的两道闸,min_interval 仍在,且 healthy_ts 已推进 → 即便晚到一轮也只是 REUSED)。极端并发由站点文件锁兜底。
§5

明确不做的事(范围守卫)

  • 不改 min_interval / 日额 / Retry-After / 时间窗的任何语义 —— 立即拉取不越过账号安全线。
  • 不做站点级复用窗(全局一键);不做「复用窗 > 拉取间隔」的报错 —— clamp 静默收敛,help 说明。
  • 不改插件侧硬上限(site-caps)与取数线程 60s 轮询节奏 —— force 用 wake() 即时唤醒,不需要加密轮询。
  • 不动 WaveCoverage / 判定 / 签发逻辑 —— 本计划只动「什么时候取数」的调度层,不动「取到后怎么判」。
  • 计划外发现的问题一律入池 memory-bank/issues/,不顺手修。
