§ 02 / 定性

问题定性:为什么难维护

① 2,600 行文件里找不到「改哪儿」

一个页面区的模板(如设置页二级页、追剧视图)平均只占根模板的 200–500 行,但每次定位都要在整个文件里上下文扫描;行号级 code review 与冲突合并都随文件体积平方级恶化。

② 双份同构副本 ⇒ 成对改纪律靠人肉

atlas 与 prism 的模板语义同构,差异只在皮肤类名与少量结构。坑库(web-ui/template-render.md)为此立了「两套 UI 必须成对改」纪律与计数守阵 —— 纪律本身说明结构有缺陷:同一份语义模板存两份,漏改靠守阵兜底而不是结构上不可能。

③ 静态守阵绑死了文件位置

test_web.py 约 10 处断言直接读取 index.html 全文(按钮体系用量、tpl-hub-field 存在性、挂件类名、页面位置持久化接线等)。这些守阵保证了质量,但也意味着任何拆分都必须连着守阵一起动,否则闸门红或守阵失效。

§ 03 / 约束

约束与既有资产

硬约束

  • 零构建链:Vue 3 CDN 本地托管,无打包器;StaticFiles(html=True) 目录即 URL,index.html 必须仍是唯一入口。
  • <script type="text/x-template"> 不支持 src:浏览器不会为带 src 的 script 填充 innerHTML —— 模板分片不能直接改成 src 引用。
  • 模板内有 3 处 JS 模板字符串(反引号 + ${},atlas / prism 各 3–4 处,如 :title="`按${l10nGroup}展示`")⇒ 分片若放进 JS 反引号字符串,这些位置必须转义,是持续性的新坑源头。此路不通,机制选型据此定案(§5)。
  • 静态资源已有 no-cache(middleware),分片文件不会被启发式缓存咬到。

可直接复用的既有资产

  • app.js 片段拆分先例:test_web.py:653–709 的 _js_fragments() 按 prism/index.html 的 script 加载顺序枚举片段,并断言「每个片段文件都被 script 引用,漏挂 = 整块功能静默消失」—— 拆分 + 加载顺序守阵的模式已验证过一轮。
  • UI 冒烟工装(pitfalls/testing/ui-preview-harness.md):无头 Edge + 包装 createApp 捕获 window.__VM,可对拆分前后做渲染快照对比(等价性验证的机器兜底)。
  • 双向 class 覆盖检查与挂件类名守阵(_scan_page_class_wiring):拆分后跑同一套,只是扫描目标从 index.html 变为「分片聚合结果」。
  • prism 的 CSS 分层结构(tokens / themes / base / components / views):atlas/style.css 拆分照此对齐,不另发明。
§ 04 / 范围

目标与非目标

目标

  • 两套 index.html 瘦身为 ≤ 200 行的 shell(入口 + 有序资源清单),模板按页面区拆成分片文件,单分片 ≤ 400 行。
  • 拆分过程每一步有守阵与渲染快照兜底,任何时刻可回滚到上一波次。
  • atlas/style.css 对齐 prism 分层;app.js 按域再拆一轮。
  • 产出一份数据支撑的「双模板差异清单」,为是否进一步收敛(可选波次 W3)提供拍板依据。

非目标

  • 不引入构建链(不引入 Vite / 打包器 / node 依赖)。
  • 不改任何运行时行为:DOM 结构、类名、交互、URL 全部不变(守阵与快照按「拆分前后等价」验收)。
  • 不动共享 JS 的 18 个健康粒度文件;不动后端;不做视觉改版。
  • 双模板收敛(W3)只评估不默认实施 —— 见 §6 波次说明。
§ 05 / 设计

拆分设计

机制:分片 HTML + 启动胶水注入(定案)

模板分片以纯 HTML 片段文件落盘(atlas/tpl/*.html、prism/tpl/*.html),由一段小胶水在 createApp 之前 fetch 注入:

  1. index.html 变 shell:<div id="app" v-cloak> 置空,顶部保留图标 sprite,底部是有序的胶水与逻辑 script 清单。
  2. 新增 shared/boot.js(两套共用,约 60 行):按 shell 内声明的分片清单顺序 fetch,拼装进 #app,同时把 x-template 分片注入为对应 script 节点;全部成功后才放行 app.js 的 createApp(时序由 boot 统一收口,失败显示错误占位并停止 —— 与现有「配置加载失败 + 重试」同风格)。
  3. v-cloak 语义保留:注入完成前 #app 为空,天然无闪烁;对比现状(整段模板在 HTML 里靠 v-cloak 藏)反而是改善。

为什么不是 JS 模板字符串:模板内已有 3 处反引号 + ${}(§3),放 JS 字符串必须转义,且以后每次写模板都要记得 —— 转义错误是静默的(template-render 坑库整篇都在讲这类静默失效)。纯 HTML 分片零转义负担、编辑器高亮、diff 干净。

为什么不是后端聚合端点:会让「目录即 URL、静态零逻辑」的部署模型多一个动态路由;且 boot.js 方案在 stub 冒烟工装下同样工作(注入点适配一次即可,坑条目已知)。

分片边界(两套 UI 同一套清单)

§ 06 / 波次

波次计划

每波独立可提交、可回滚;波内先两套 UI 成对改,再跑守阵 + 冒烟。工作量以「轮」计(一轮 ≈ 一个专注会话)。

W0机检先行:守阵迁移方案 + 等价性基线0.5 轮

盘点 test_web.py 全部读取 index.html / style.css 的断言(已知约 10 处:按钮体系、tpl-hub-field、挂件类名、页面位置、键盘接线等),逐条给出「读聚合结果」的迁移写法;_scan_page_class_wiring 与 bt 计数守阵改为扫「shell + 分片聚合」。搭无头 harness 拆分前基线:两套 UI 各页 DOM 结构快照 + 关键交互(data-drv 标记)留档。

验收:守阵迁移方案成清单;快照基线可复现;不改动任何产品文件。
W1根模板分片(最大收益波)2 轮

实现 boot.js + shell 改造;按 §5 边界把两套根模板拆进 tpl/*.html(顺序:dialogs → shows → torrents → groups → settings → topbar,由小到大练手);新增守阵:①分片清单完整性(清单里每个分片存在且被 boot 引用,漏挂 = 红,仿 _js_fragments);②双 UI 分片计数断言;③聚合后的既有内容断言全部通过。

验收:两套 index.html ≤ 200 行;守阵全绿;harness 快照与 W0 基线 DOM 等价;无控制台错误。
W2样式与 app.js 续拆1 轮

atlas/style.css 按 prism 分层结构拆(base / components / views / tokens 留根),link 顺序即加载顺序、挂守阵;app.js 按域再拆(轮询 / 启动引导 / 视图切换 / 状态聚合),沿用既有片段加载顺序守阵。

验收:单 CSS 文件 ≤ 700 行;app.js ≤ 500 行;守阵全绿;快照等价。
W3双模板收敛评估(可选,默认只出报告)0.5–2 轮

以 W1 的分片为单位做两套模板的逐片 diff,产出「语义差异清单」(差异 = 皮肤类名 / 结构分叉 / 逻辑分叉三类)。若皮肤类名占比 > 90%,后续可评估「单一语义模板 + 皮肤差异表」把成对改纪律在结构上消掉 —— 这是治本,但风险最高,本计划只交付评估报告,是否实施另行拍板。

验收:差异清单数据完整、可判定;不实施时不改任何产品文件。
W4收口0.5 轮

test.full 落新基线切片;回写 memory-bank(progress / core-domain 模块表 / template-render 坑条目补「拆分后守阵口径」);真机冒烟;提交推送。

验收:闸门全绿;文档与代码事实一致;基线数字入库。

合计 4.5–6 轮(不含 W3 若实施)。每波提交独立,gitmoji 用 ♻️(无行为变化的重构);任一波次守阵红且当日修不掉 → 整体回滚该波,不留半拆状态。

§ 07 / 风险

风险与对策

风险等级对策

§ 08 / 验收

验收标准

  • 体量:两套 index.html 各 ≤ 200 行;模板分片单文件 ≤ 400 行;atlas 样式单文件 ≤ 700 行;app.js ≤ 500 行。
  • 等价:harness DOM 快照与 W0 基线结构等价;真机冒烟(双 UI、五主题)无控制台错误。
  • 守阵:test.full 全绿且守阵数量不减(迁移 ≠ 删除);新增 ①分片清单完整性 ②双 UI 分片计数 两条守阵。
  • 可维护性硬指标:此后改任一页面区,只碰对应分片 + shared 逻辑层;成对改纪律的执行成本下降(改模板时在两套同名分片间跳转,而非两份 2,600 行文件)。
  • 知识库:基线切片、progress 条目、坑条目(boot 时序 / 分片边界判定,若踩到)随 W4 入库。
