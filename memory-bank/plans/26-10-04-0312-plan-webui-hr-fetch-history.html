§01

原始请求与目标

原始请求（2026-10-04）：「WEBUI HR在线核实需要添加拉取历史详情表, 什么时间拉取了什么站点, 解析结果等, 参照插件的表格, 且需更详细. 先写一个分步实施计划」。

目标

  • 每次真实取数（波次）之后时间轴可回溯：时间、站点、触发方式（自动 / 立即拉取 / 人工对账）、结果终态、失败原因。
  • 解析结果可见：本波抓了几页、多少行，各档位（A/B/C）各自的页数 / 行数 / 截断原因，行内展开看档位明细。
  • 产出可见：回填了多少条 .torrent（成功 / 失败）、签发了多少条放行。
  • 数据持久化（重启不丢）、多实例共享（跟随现有站点分文件机制）、容量有界（环形 + 按龄修剪）。
  • 前端遵守现有口径：只在用户显式动作时拉数（不轮询）、人话由后端算好、三皮肤样式成对。

非目标

  • 不改判定、不改取数调度与频控语义 —— 历史记录是纯旁观留痕，写失败也不影响取数（见 §07）。
  • 不读扩展侧数据：chrome.storage 的 events 环是扩展私有的，WebUI 读不到；本表全部由后端自己记录（也只有后端能带上解析 / 放行语义）。
  • 不做分页：环形 + limit 已够用；不进 /api/state 轮询载荷。
  • 不新增配置键（容量 / 保留期用常量，见拍板项⑤）。
§02

现状与差距

2.1 数据流现状：只有「最新快照」，没有历史

取数链路：HrWorker(60s 自唤醒) → HrRefreshService.refresh_site → 站点锁 → 调度闸（复用窗 / 拉取间隔 / 频控）→ _do_wave → _run_pages（A/B/C 轮流翻页，经通道向浏览器扩展取 myhr.php 各页）→ adapter.parse_page 解析 + 校验 → 行处理 / 回填 / 放行 → session.commit 原子写 <hr 目录>/<site>.json。

站点文件（HrSiteData，model.py:459）只存当前态：index（清单现状）、wave.lanes（每档最近一波的状态，wave_ts 每波重算不跨波继承）、verified / downloaded（累计账本，无时间轴）、rate（频控账本）。历史只散落在：日志文本、.bak（上一版快照，仅一版）、扩展侧 events 环（WebUI 读不到）。「上周三夜里那波为什么失败」现在无从回答 —— 这是本计划要补的洞。

2.2 参照件：扩展选项页的两张表extensions/hr-fetch-proxy/options.html:141-154

「插件」= 浏览器扩展 hr-fetch-proxy。它的选项页有两张表，数据源是 chrome.storage.local 的 events 事件环（容量 50，字段 {t, host, kind, ok, status, ms, bytes, tag, note}，background.js:225）：

扩展侧表格列粒度
站点现状表站点 / 最近活动 / 最近动作·结果 / 用量(本时·本日 访问·下种) / 状态站点 × 当前
最近取数明细表时间 / 站点 / 类型 / 结果 / 耗时 / 大小单次 HTTP 请求（页面 / 种子）

WebUI 侧「站点现状」维度已被 /api/hr/status + 表② 覆盖，不重复；要搬的是取数明细表的时间轴维度，并把粒度从「单请求」升到「波次」（解析结果、档位覆盖、回填、放行只在波次粒度上才有意义），即用户说的「参照插件的表格，且需更详细」。

新增 HrHistoryEvent dataclass（与既有 HrVerified / HrLaneState 同款 to_json/from_json 序列化范式），HrSiteData 增一字段 history: List[HrHistoryEvent]（缺省空表，from_json 缺键容忍）：

字段几乎全部来自现成的 HrRefreshResult（service.py:191-211）与 lane_states，记录器只做搬运，不新算业务语义。

3.2 存储与写盘纪律

  • 存哪：内嵌 HrSiteData.history，随站点文件走 —— 天然获得既有锁、原子写、.bak、多实例共享（详见拍板项①）。
  • 容量：HISTORY_CAP = 200 条 / 站点，HISTORY_MAX_AGE = 14 天；追加时先修剪再截断。常量放 service.py 常量区（§6「程序能定的绝不配置」口径，拍板项⑤）。体积上界 ≈ 200 × 400B ≈ 80KB / 站点（S1 实测回填，超预期砍 100）。
  • 版本链：不抬 hr_site 版本。补字段属非破坏性变更，versioning.py:16-18 明示「刻意不为补字段造版本」；from_json 缺键回空表，存量文件零迁移零写盘。
  • 写盘纪律（硬不变量）：60s poll 被调度闸跳过（reused / waiting）时不记事件、不写盘 —— 否则每分钟一次全文件重写。写盘只发生在：真实波次（本来就有逐页 commit）、用户触发的 defer、对账动作（本来就写）。S2 用测试钉死这条。
  • 多实例：追加发生在站点锁内的读-改-写会话里，与既有字段同语义，不新增竞态面。已知限制：新旧版本程序混跑时，旧程序写盘会丢掉不认识的 history 字段（丢事件不损业务字段，升级窗口期短暂存在，见 §07）。

3.3 记录写入点src/auto_qb/hr/service.py · report.py

service 新增一个小记录器 _append_history(session, *, kind, trigger, result, lanes, notes)（修剪 + 截断 + append，不做 IO），写盘点三处：

事件写入点持久化说明
wave _do_wave 全部终态：正常路径在 _finish_wave 收尾处；异常路径在 HrChannelQuota / HrChannelUnavailable / HrLoginExpired / Retry-After 各 except 分支 return 前 正常路径随既有 commit；异常路径补一次 _persist_step(session) trigger 按 force 参数区分 auto / manual；HrChannelStopped（停机 / 热重挂让位）不记 —— 瞬态内部事件，重挂期间会刷屏
defer _refresh_locked 各闸 return 前（拉取间隔 / min_interval / 日额 / Retry-After / 时间窗 / dry-run），仅 force=True 显式 commit（用户点击级频次，可接受） 自动 poll 的 waiting 不记（写盘纪律）；复用窗被 force 跳过，天然不产生 defer
confirm_empty report.py run_hr_confirm_empty（:169）锁内写戳处 随既有 commit trigger='confirm'；对账是「零行波能不能放行」的关键前置，入时间轴

锁忙（HrLockBusy）与「站点未启用 / hr_check 关闭」不入历史：前者是本实例没挤进锁（别的实例会有自己的记录），后者没有发生任何取数。

3.4 只读口径与 APIsrc/auto_qb/hr/status.py · webui/server/routes/hr.py

  • 口径单点：status.py 新增 history_rows(datas: Mapping[str, HrSiteData], limit, now) —— 合并各站历史、按 ts 降序、截 limit，并算好人话字段（ts_text / elapsed_text / result_text / kind_text / trigger_text / 各档 lane_text）。遵守「行字段人话全由后端算好，前端不重算」的既有约定（表① 同款）。
  • 结果徽章映射（result_text / 色档）：refreshed→完成(ok) · partial→部分·截断(warn) · waiting→拦下·未到时刻(dim) · no-channel→通道不可用(err) · error→失败(err) · skipped-locked→锁忙(dim) · confirm_empty→对账(blue)。
  • 端点：GET /api/hr/history?limit=300&site=<可选>，加在 routes/hr.py 的 build_router（hr builder 已在 ROUTE_BUILDERS 注册，无需动路由表）。校验与 /api/hr/sites/{site}/entries（:151）同款：未启用 400；取数线程未启动 409；读站点文件走 store(site).read_unlocked() 无锁只读先例。响应：{enabled, rows[], read_errors{site: err}, now}；rows[i] 即 §3.1 字段的人话版。读坏文件不抛，read_errors 带出（表① 同款）。

#决策点推荐备选与不推荐理由
①存储位置 A 内嵌 HrSiteData.history 环 —— 零新锁、零新版本注册、随既有原子写 / .bak / 多实例共享 B 独立 <site>.history.json：要第二把锁、新版本链注册、双写点，隔离收益撑不起复杂度
②UI 形态 A 表③ = <details> 折叠段，放全屏弹层站点列表之后（表② 同范式，默认收起、展开才拉数） B 弹层页签化（种子明细 / 拉取历史两个 tab）：要动 26-10-02-1936 刚收口的全屏弹层结构，收益只是少点一次展开
③记录粒度 A 波次级一行 + 行内展开各档明细（时间轴可读性优先） B 每页一条平铺：单波 3-6 行 → 一天几十行，刷屏且丢「波」这个语义单元
④defer 事件（立即拉取被账号安全线拦下要不要留痕） A 记录 —— 用户点过按钮却没拉成，事后「为什么没拉」可考；用户触发级频次，无写放大 B 不记：省一类事件，但 G3 的排障诉求落空
⑤容量与保留 A 200 条 / 站点 + 14 天修剪，常量不入配置（§6 口径；80KB 上界） B 进配置：要 validate_config + schema + 文档全链路，为两个不会有人改的数字不值
