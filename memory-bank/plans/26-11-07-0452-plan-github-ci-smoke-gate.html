GitHub CI WEB UI smoke 门禁改造: 超时根因、分片接线与 push 节流全量轮

本篇只回答一件事: 怎么让 GitHub 上的 WEB UI smoke (chromium) 从「每次跑满 40 分钟被强杀」变成「日常门禁 10 分钟内出真结论 + 低频全量轮兜底」, 且不靠调大超时、不靠少跑用例、不掩盖既有红。

§01目标与设计原则

目标

  • 日常 push / PR 的浏览器门禁在 10-12 分钟内给出可信红绿, 不再被 job 级 timeout 强杀。
  • 全量 450 例改为低频自动触发(push 节流), 保留按需手动入口, 覆盖不缩水。
  • 超时/取消时留下可排障的证据(report + trace), 而不是像现在这样一条不留。

设计底线(违反即推翻方案)

  1. 不靠放宽预算: 不把 timeout-minutes 当解法; 改造后按实测 ×2 收紧为护栏。
  2. 不靠少跑用例: 日常门禁跑 @fast 是仓库既定口径(playwright.config.mjs 文件头已写明), 不是为绕超时临时缩水; 全量轮覆盖 430 + 20 = 450 例, 一个不少。
  3. 不掩盖既有红: 不加 continue-on-error、不 test.skip、不用 --grep 排除; 失败清单机读展示并链已入池 issue, run 结论保持真实红。
  4. 不改产品代码: 只动 .github/workflows/playwright.yml; 不动 src/、config.yml、auto-qb-data/。
  5. 不改默认分支: 保持 master 为默认分支, 通过一次性快进让它不再陈旧, 而不是切换默认分支。

不变量

  • @fast 282 例(分片口径) + CPU 敏感量具 20 例 = 日常门禁覆盖面。
  • 全量 430 例(分片口径) + 20 例补跑 = 450 例, 与改造前一致。
  • 工作区多 clone 并行、reuseExistingServer: false、桩服务 --port 0 由 OS 分配 —— 这些既有设计一律不动。

§02现状与痛点

根因: 40 分钟预算对 48 分钟的实际需求

.github/workflows/playwright.yml:15 是 job 级 timeout-minutes: 40; 第 59 行是裸 npx playwright test, 即以 workers: 1(playwright.config.mjs:47)串行跑全量。GitHub 侧实测:

# run 42261344757 (head_sha cabad24b, 2026-11-06 17:24 -> 18:04 UTC)
Running 450 tests using 1 worker
  ✓  374  ...  18:04:38Z   # 跑到第 374 例
##[error]The operation was canceled.   # 18:04:41Z, 恰好 40m14s

按 374 例 / 39m41s 折算约 6.4s/例, 450 例需 ≈48 分钟 —— 40 分钟预算结构性不够, 不是偶发。

不是偶发, 是慢性失守

指标实测值(2026-11-07 取证)
该 workflow 近 100 次运行结论93 cancelled / 7 failure / 0 success
最后一次 success2026-10-30 20:29 -> 20:44 UTC(15m45s)
11-06 单日 push 次数77 次, 每次 push 都起一个 40 分钟 job
近 20 笔提交中触及前端白名单的0 / 20(全是 memory-bank 文档)
取消时 artifact 是否留存否 —— if: ${{ !cancelled() }} 在取消时直接跳过上传

三个叠加缺陷

  1. 预算算错: 上一轮把 20m 抬到 40m 的依据是「本机 440 例 21.9m + retry 余量」(88c1d3f5), 但 CI 比本机慢约 2.6 倍, 外推不成立。
  2. 触发面过宽: on.push 无 paths 过滤, 纯文档提交也跑浏览器套件 —— 这是 93 次 cancelled 的主要来源。
  3. 证据不留: 取消即跳过 artifact, 且没有 test-results/(trace)上传, 排障只能靠猜。

既有能力已就绪但没接线

f8043824 已落地 shard 多进程隔离桩并实测 690s -> 366s -> 263s(shard=1/2/3, 2.62x 提速), 同时提供 e2e/shard-run.mjs 与 e2e/perf-serial.mjs 两个入口。但 CI 第 59 行仍是裸 npx playwright test —— 能力在仓库里, 只是没接。这是本方案成本低的根本原因。

§03方案总览

结构: 一个文件、三类 job

只改 .github/workflows/playwright.yml。不新建 workflow 文件 —— 因为 workflow_dispatch 的注册与 inputs 校验读的是默认分支上的版本, 新建文件在 develop 上会 404; 并进已有文件可完全绕开这个约束。

job触发条件内容timeout
gateevent != workflow_dispatch只读 run 历史 + compare API 算白名单行数, 输出两个布尔; 达标则 gh workflow run 触发全量轮5m
smokeneeds.gate.outputs.run_fast == 'true'@fast 282 例分 3 片矩阵, 每片独立 webServer25m
perf-serial同 smokeCPU 敏感量具 20 例串行补跑(与分片并行)25m
aggregatealways()汇总各分片结论, 占住固定 check 名 WEB UI smoke (chromium)5m
fullevent == workflow_dispatch全量 430 例分 5 片矩阵30m
full-perfevent == workflow_dispatchCPU 敏感量具 20 例串行补跑(与 5 片并行)30m

六个 job 而非五个: full 的分片矩阵与量具补跑必须拆开 —— 量具在并发下数字会漂, 且 5 片的 --total 口径已把量具 spec 排除, 混在一个 job 里会让补跑被矩阵展开成 5 份。

触发与节流

on:
  push:
    branches: [develop, master, main]
  pull_request:
    branches: [develop, master, main]
  workflow_dispatch:
    inputs:
      scope:
        type: choice
        options: [full]
        default: full

run-name: ${{ github.event_name == 'workflow_dispatch' && 'full-smoke' || 'daily' }} / ${{ github.ref_name }}

节流判定放在 gate job 内(不是 workflow 级 paths), 因为 workflow 级过滤会让纯文档 push 连判定都不启动, 时间阈值永远没机会生效。

判定项取值数据来源
距上次全量轮时间≥ 1 天最近一次 event=workflow_dispatch 且 displayTitle 以 full-smoke 开头的 completed run 的 created_at
白名单累计改动行数≥ 1000 行gh api repos/{repo}/compare/{锚点sha}...{head} 的 files[].changes, 按白名单路径过滤求和
组合关系OR任一达标即跑; 时间维度兜住低流速期, 行数维度让代码密集期提前触发

白名单路径(与 on.push.paths 同一份, 单点写在 env): src/auto_qb/webui/、e2e/、scripts/ui_harness.py、playwright.config.mjs、package.json、package-lock.json、uv.lock、pyproject.toml、.github/workflows/。

锚点为什么必须纯净

若 full 也响应 push, 「判定为不跑」的那次同样会留下一条 completed run, 下次查「最近一次」就会错误刷新锚点, 时间阈值永远达不到。因此 full 只由 workflow_dispatch 触发, 并用 event + run-name 双重校验。锚点取实际跑的 github.sha, 不是触发它的那个 commit(dispatch 只能指定分支, 会有一两笔偏差)。

证据留存与失败呈现

  • upload-artifact 改 always(), 纳入 playwright-report/ + test-results/(trace), 按分片编号命名。
  • 全量轮加 --reporter=json(叠加在 list 之上, 不改现有 reporter 配置), 由 summary 步骤把失败用例名写进 $GITHUB_STEP_SUMMARY 并链 issue 26-11-07-0326。
  • 不据此改 run 结论: 红就是红; 「无新增失败」由人对比 issue 里的既有红清单判定, 不建第二份机读基线。

权限

仓库默认 workflow 权限是 read。仅 gate job 提权到 actions: write(为 gh workflow run), 其余 job 保持只读。gate 调 API 失败(限流/网络)时 fail-open: 跑一次全量轮并打 warning, 不静默跳过。

master 处理

workflow_dispatch 的注册与 inputs 校验读默认分支版本; 当前 master 落后 develop 312 笔且是旧版 workflow。改造提交推 develop 后, 一次性把 master 快进到 develop(Gitee 与 GitHub 各一次, 按既有推送顺序核 ref)。快进是纯 fast-forward: 两个远端 master 都是 develop 的祖先, 无分叉。
