01结论先行

核心判断

可行，但不能「拉取即全脱」。程序里确实没有功能依赖 passkey 这个值本身 —— 但有两处依赖「完整 URL」：它们要的不是密钥，而是唯一标识，passkey 只是恰好长在 URL 上。所以正确形态不是「删掉原文」，而是「原文不再外发、也不再常驻」—— 只留脱敏值, 原文在写路径上当场取用即弃（单轨）。

两个容易漏的细节

  • 虚拟条目不能进脱敏器。qB 会在列表里塞 ** [DHT] ** / ** [PeX] ** / ** [LSD] **（旧版可能是裸 [DHT] 形态）。前端 drawerTrackerVirtual()（webui/static/shared/drawer.js:589）与后端过滤（webui/views.py:36 · webui/commands.py:165）都按字符串前缀识别它们。实测 sanitize_tracker_url() 会把裸 [DHT] 小写成 [dht]（** [DHT] ** 因为 ** 前缀仍在而侥幸存活）—— 一旦裸形态出现，虚拟条目会被当成真实 tracker，前端还会给它画出编辑 / 删除按钮。⇒ 虚拟条目原样透传。
  • 同 host 的多条 tracker 脱敏后同值。实测 https://pt.example.com/announce?passkey=A 与 https://pt.example.com/announce.php?authkey=x 都变成 https://pt.example.com。这不是缺陷（脱敏的定义就是如此），但它意味着脱敏值不能当唯一标识 —— 写路径的定位与汇报基线的 key 都不能建立在它上面。

03核验「没有功能依赖 passkey」

用户的前提是「当前程序似乎没有什么功能依赖 passkey，所以应该没问题」。逐点核下来的结论是：这个判断方向正确，但需要精确一层。

没有任何代码去读 passkey= 这个参数值 —— 这点确认无误。但有两个地方依赖完整 URL 字符串，而完整 URL 里含 passkey。它们依赖的不是密钥，是唯一标识：qB 的 torrents_edit_tracker / torrents_remove_trackers 只接受 original_url 来定位某一条 tracker，没有别的定位方式（不支持按索引）。

这句话决定了方案形态

既然要的是「标识」而不是「密钥」，就不该把原文删掉，而该让原文留在进程内当标识、但不再越过任何边界。谁越界（日志、API 响应、前端 DOM、通知）谁就只能拿到脱敏值。这是下面方案 B 的由来。

复核补充（2026-09-22）：这两处里只有写路径需要「重新设计标识」。另一处 —— 汇报确认基线 —— 虽然同样拿完整 URL 当 key，但它压根没有越界（活在 reannounce_pending 里，不落盘、不进响应体）。对它的正确处置是「继续用原文」，而不是原计划建议的「换成脱敏值当 key」；理由见 §04 末。

顺带发现：日志不是唯一的泄露面

上一轮修的是日志。但 /api/torrents/{hash}/trackers 目前是 qB 透传——完整 announce URL 原样发给浏览器，前端详情面板会把它渲染出来，编辑弹窗还会预填进输入框。它不在 /api/log 里，所以上一轮的守阵扫不到它。本次必须一并收口，否则"堵住日志"只是堵住了两个洞里比较显眼的那个。

04三个方案与取舍

A · 拉取即脱敏，不留原文不可行

torrents_trackers() 返回的条目里 url 直接是脱敏值，进程内不保留原文。最干净 —— 但 qB 的移除只接受 original_url，没有原文就没法定位任何一条 tracker。结果是要么砍掉移除功能，要么退化成「整颗种子删了重加」—— 都不可接受。

代价：连「删掉其中一条 tracker」都做不到。不推荐。

B · 单轨：只留脱敏值，原文当场取用即弃推荐

条目只带 url（mask 脱敏），不再常驻 raw_url。规则：任何越过边界的动作一律只许读 url —— 日志、API 响应、前端状态、通知、导出。

url 的形态 = 保形状 + 值全 hash（2026-09-23 用户提出并拍板，取代「只留主地址」）：保留 scheme / host / path 与参数名，把 query 里每一个值（以及 path 末段这类可能藏凭据的位置）替换成各自的哈希 —— https://site/announce?passkey=9f2c…&uid=3a1b…。相较「只留主地址」：唯一性天然保持（同站的不同 announce 端点仍可区分）、诊断信息更全（端点与参数名都在）、依旧不含明文。⚠ 铁律是不按参数名挑 —— 只 hash 名为 passkey 的参数就等于退回黑名单思路，authkey / token / uid / secret 会原样留下。哈希必须确定性、不得加盐（加盐则每次拉取值都变，唯一性与基线差分一起失效）；长度取完整 sha256 或至少 16 位。

写路径（只剩删除）＝「当场重取 + 用完即弃」（2026-09-23 用户提出，取代序号 + 指纹）：前端只传 hash + 待删除的 mask URL；后端在执行那一刻当场重新拉一份完整列表，逐条 mask 后与传来的值比对，命中就取出那一条的原文去调 qB，原文随局部变量立即丢弃。命中 0 条（列表已变 / 那条已被删）或命中多条 ⇒ 直接回 error 回执「未找到该 tracker, 请刷新后重试」，绝不猜。

这一版比「序号 + 指纹」更省，原因很直接：mask 保住了唯一性 ⇒ 脱敏值本身就是可用的内容标识，于是序号、指纹、映射表全都不必要了；而且内容标识天然不惧列表重排 —— 怕重排的恰恰是位置标识。

原文的暴露窗口因此从「整个进程生命周期」缩到「一次删除调用的毫秒级」：它只出现在该次调用的局部变量里，不进缓存、不落盘、不越界。代价是每次删除多读一次 tracker 列表（一条 API 调用，可忽略）。

代价：写路径是行为变更（见 §06）；前端编辑入口删除、移除改成传 hash + mask URL。收益：下游再怎么疏忽也带不走凭据，且原文不再常驻内存。

C · 保持原文，只在出口逐个加守阵治标

不改数据流，给每个出口（日志、/api/trackers、通知、导出）逐个加脱敏与守阵测试。

代价：正是用户担心的那种「以后很可能在其它地方疏忽」——每加一个出口就要记得补一次，漏一次就是一个洞。可作为 B 落地前的临时止血，不作终态。

推荐 B，但要接受它的边界

B 堵住的是「越界泄露」——日志落盘、API 响应、浏览器 DOM、系统通知，全堵住。两处边界要明说：① 原文在「删除那一刻」仍要短暂进内存（qB 的 original_url 绕不开）—— 崩溃转储 / 诊断打包 / --dry-run 的完整 dump 若恰好落在那个毫秒级窗口仍可能带出；只是窗口从「整个进程生命周期」缩到「一次调用」。要彻底归零只能连移除功能一起砍（回到方案 A）。② /api/torrents/{hash}/export（webui/server/routes/torrent_detail.py:158）是原始 .torrent 字节透传，文件里的 announce 自带凭据 —— 它是用户主动下载自己的种子（qB 原生亦然），本次不堵，要堵只能连导出功能一起砍。这两条是必须明说的取舍，不是漏考虑。

为什么汇报基线不改标识（本次复核的修正点）

原计划把基线列为「必须改 key」，复核后撤回这个判定。先看它到底是什么（基树 4c8b90e 实测）：

  1. 下发 reannounce 之后立刻抓一份快照 {hash: {完整URL: (status, next_announce)}}（排除虚拟条目），存进 reannounce_pending[cmd_id].items[hash].baseline（webui/commands.py:153 建 · :255 登记）。
  2. 之后每个 tick 重读 tracker 列表，用同一个 URL 字符串回快照取值做差分（_confirm_reannounce_result，webui/commands.py:172 · 调用点 webui/runtime.py:269）：status==3 (updating) / next_announce 比基线提前 60 以上 / status 由非 working 变 2 / status==4 且带 msg ⇒ 失败。最长等 30s（REANNOUNCE_CONFIRM_TIMEOUT），全部种子出结论后聚合写回执。

三点事实决定了处置：

  • 它不越界。基线只活在内存里 —— 不进日志、不进响应体、不落盘（失败回执里只有 err 文本，没有 URL）。它不是泄露面，所以不存在「为了脱敏而改造」的理由。
  • 它要的是「跨读取稳定的身份」。同一条 tracker 要在两次读取之间对上号，URL 是 qB 给出的唯一标识 —— 现有实现一律按 URL 匹配，等于已经承认了这点。改用序号的前提是「列表顺序跨读取稳定」，而这个前提没有任何契约保证（qB 未承诺），收益还是零（它本来就在进程内）。
  • 拿脱敏值当 key 是自伤。同 host 的不同 path / 凭据会合并成一条 ⇒ 静默漏掉一条 tracker，正是原计划想防的那种误判，而改法本身制造了它。
结论

基线维持「进程内原文作 key」不变：字段改写落地后它改读 raw_url，判据、超时、聚合逻辑一行不改；另加一条守阵防止后人把它切到 url（脱敏值）。

05推荐方案：落地波次

W1
源头归一化（不改任何行为）

在 qbapi.torrents_trackers() 里对每条补一个脱敏字段，保留原文不下线。纯增量，此波结束后所有行为不变 —— 可以先单独验证不回归。脱敏函数按「保形状 + 值全 hash」实现（见 §04）：复用已有的 utils.sanitize_tracker_url() 改成 mask 形态，或在其旁新增 mask_tracker_url() 并让日志路径继续走「只留主地址」（日志不需要 path 与参数名，两者不冲突）。

⚠ 读取不是单一入口，5 处必须逐点覆盖：core/qbapi.py:322（Facade）+ 4 处直读原始 client 绕过 Facade 的点（见 §02 直读点表）—— webui/commands.py:161（汇报基线）、webui/runtime.py:269（每 tick 复核）、webui/server/routes/torrent_detail.py:37（详情 API）、webui/views.py:119（错误原因）。只改 Facade 会漏掉后四处；要么逐点归一化，要么把这四处收敛回 Facade（后者更彻底，但改动面更大，按波次取舍）。两层缓存（记录惰性槽 + 详情 API 的 _cached_read）也要走同一份归一化，别出现「有的缓存脱敏、有的没脱」。

W2
收口外发面：详情 API 与前端展示

/api/torrents/{hash}/trackers 只返回脱敏值（raw_url 不进响应体）。前端详情面板照常显示域名与状态 —— 排查需要的「哪个站、什么状态」信息一点没少。这一步单独就能堵掉当前那个裸奔的洞，是收益最大、风险最小的一波，即使后续波次暂缓也建议先做。

W3
写路径收窄：只留添加 / 删除，编辑下线

编辑功能整个下线（2026-09-23 用户口径：改 tracker 在 PT 领域很少发生）：

  • 前端删掉 trackerEdit（webui/static/shared/drawer.js:209）与「编辑」入口；改 passkey 的操作退化为「移除旧的 + 添加新的」两步，功能等价。
  • 后端移除 /api/torrents/{hash}/trackers/edit 端点（webui/server/routes/torrent_cmds.py:105）、_cmd_edit_tracker 与命令表里的 edit_tracker；一并清掉引用它的测试与文档。
  • 连带效果：原「弹窗预填原文」这个最敏感的点自动消失（没有编辑就无所谓预填），决策点 1 的代价随之变小。

删除改为「传 hash + mask URL，当场重取、用完即弃」：前端 trackerRemove（drawer.js:225）提交 hash + 待删的 mask URL（确认框只显示 masked URL —— 看得出哪个站、哪个端点，看不到凭据）；后端当场重新拉取完整列表，逐条 mask 比对，命中即取该条原文调 qB，原文随局部变量立即丢弃；命中 0 条或多条 ⇒ error 回执「未找到该 tracker，请刷新后重试」。添加（trackerAdd）不受影响 —— 值是用户自己粘贴的。命令载荷形态会变，新旧前端不做兼容（同仓发布，无跨版本包袱）。

W4
守阵与红验
  • 端到端守阵：真调 /api/torrents/{hash}/trackers，断言响应体含 masked URL（站点与端点都在）、不含任何明文值：用一条已知 passkey 构造种子，断言它的原值不出现在响应里（不写死参数名 —— 私站参数名是任意的）。
  • 写路径守阵：构造「同 host 两条 tracker」的种子（mask 后仍可区分），传 mask URL 跑删除，断言命中的是正确那一条；再补一条「传一条已不存在的 mask URL ⇒ 回 error 且不调 qB」（专防 W3 的当场比对逻辑回归）。
  • 编辑已下线守阵：断言 edit_tracker 不在命令表、trackers/edit 路由不存在、前端无「编辑」入口 —— 防有人把它加回来时忘了接脱敏。
  • 静态守阵：扫前端与后端，凡把 tracker 条目原样塞进日志 / 响应 / DOM 的位置都点名 —— 下次有人加新出口时这条会红。
  • 红验：把归一化临时打回「原样透传」，守阵必须立刻红（上一轮就是这么验的，有效）。

06风险与代价

风险说明处置
改 passkey 从一步变两步 编辑入口下线，改 passkey 要「移除旧的 + 添加新的」两步完成 用户已认可（PT 场景改 tracker 很少发生）。多数客户端本就不帮你显示密钥片段
原文在删除那一刻短暂进内存 要填 qB 的 original_url，这一步绕不开；窗口已从整个进程生命周期缩到一次调用 明说并接受；若要归零则必须连移除一起砍（方案 A）
提交前列表发生变化（那条已被删 / 已改） 前端拿到列表后、提交前，列表可能已被别的写操作改变 后端当场重取列表、按 mask 比对；命中 0 条或多条直接报 error 回执不猜 —— 内容标识天然不怕重排
两层缓存不一致 record 惰性槽与 web _cached_read 若各自归一化，可能出现一处脱敏一处没有 归一化单点放在 QbApi，两个缓存都只存它吐出的结果
同 host 多 tracker 撞 key 汇报确认会静默漏掉一条，误判成功 / 失败 W4 解决；守阵专门构造该场景防回归
与远端重构撞车 知识库目录化重构刚收尾（W8 已落），文档类改动仍可能冲突 开工前快进同步；本计划涉及的是 src/ 与前端，冲突面小

07决策点（需拍板）

1 · 前端不再显示完整 URL —— 已拍板（2026-09-22）

而后 2026-09-23 又定了「编辑入口整个下线」，于是最敏感的「弹窗预填原文」问题自动消失；剩下的只有删除确认框，显示 masked URL 即可（看得出是哪个站、哪个端点，看不到凭据）。

2 · 进程内是否保留原文 —— 已解决：不留常驻原文（2026-09-23 用户方案）

删除不再依赖常驻原文：前端传 hash + mask URL，后端当场重取、用完即弃（见 §04）。原文只在一次调用里存在，不进缓存、不落盘。剩下的唯一窗口是「调 qB 那一瞬间」，绕不开。

3 · 脱敏形态 = mask（保形状 + 值全 hash）—— 已拍板（2026-09-23）

保留 scheme / host / path 与参数名，query 里所有值一律 hash。它不只是「更好看的脱敏」—— 保住唯一性是 W3 那套方案的前提（脱敏值要直接当内容标识用）。铁律照旧：不按参数名挑，query 里所有值一律 hash；hash 确定性、不加盐，长度 ≥16 位。

4 · 排期：是否先做 W1 + W2 止血？

W2（收口详情 API）堵的是当前唯一外发原文的口子，零行为风险。W3 是本次唯一的行为变更（编辑下线 + 删除改传 hash + mask URL），可以单独一批。

建议

先批 W1 + W2：不碰写路径、不改操作习惯，就能把当前裸奔的洞堵上，风险最低。W3（含编辑下线）单独一批，做完再补守阵。

08验收标准

  • 全量 uv run pytest tests -q 不退化，新增守阵 ≥ 3 条（端到端 / 写路径 / 静态扫描）。
  • 每条新守阵都过红验：打回旧实现必须立刻红。
  • 抓包级验收：调 /api/torrents/{hash}/trackers，响应体里 grep 不到 passkey= 一类凭据参数（同样不写死参数名）。
