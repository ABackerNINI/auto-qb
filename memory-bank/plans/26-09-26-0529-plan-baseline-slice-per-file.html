§00

前案否决记录

v1 计划是「baseline.md 单文件保留、人手只留最近 3 组、挤出的迁 history」。三处不成立：

  1. 热写点单点没消除 —— 全体 clone 收尾仍写 baseline.md 同一段，多 clone 合并撞车面不减反保；
  2. 窗口靠人手维护 —— 「保留 3 组」是纪律不是机制，漏迁一次窗口就漂；
  3. 时序藏在文件内部 —— 第几组、谁比谁新，靠读正文才知道，脚本与守卫都无法判定。

用户定案改为文件系统承载时序与窗口：时间戳文件名自带顺序，「最近 3 条」由脚本截取，写入方永远只新建自己的文件 —— 撞车面从「同一段」缩到「零」。

§01

定案与依据

三条用户定案（2026-09-26）：① 每个文件一条基线；② 由脚本列出最近 3 条；③ 不需要 _index.md。 改造方法的母本是 activeContext 目录化 —— 其四条约定与机制文件逐条映射：

activeContext 侧（已运行）基线侧对应（本计划落地）
切片命名 YY-MM-DD-HHMM-<slug>.md，定宽前缀保证字典序 == 时间序同款命名，复用 _common.py::SLICE_FILE_RE，不新造正则
切片三行头元数据（# 标题 / > 摘要: / > 最后活动:）同构三行头，排序键换 > 基线时间:（缺失回退文件名前缀）
gen_active_recent.py 只打印不写文件，「ls 本身就是索引」gen_baseline_recent.py 同构，差异是默认截取最近 3 条（见 §02）
不设目录索引，防「缓存文件过期比没有更危险」同样不设 _index.md，且把「不许补 _index」写进口径段防手贱

窗口语义：为什么这里可以截断而 activeContext 不行

gen_active_recent.py 的设计约束 2 明确「不做取最近 N 条截断」，理由是切片是活的专题（创建早但仍在推进，截断会漏）。基线条目相反：不可变的一次性快照，写完不改，最新一条恒为事实源 —— 截断语义成立，且这正是用户定案。脚本给 --all / -n N 供排障全量，默认 3。

同日多条的时序回填（迁移期真实工程点）

存量条目多数只有日期没有时分。约定：排序正确性靠切片头「基线时间」字段，不靠文件名；文件名前缀只是回退与人类检索。迁移时从可考来源回填时分 —— 事件对应在办切片的取切片时间戳（如 1641 合流重测 ← 26-09-26-1700-webui-torrent-meta-edit），对应任务档案的取档案时点；不可考的写 00:00 并在摘要注明「当日序位第 N」。脚本排序 = 基线时间字段为主键、文件名为次级稳定键。

风险与边界

  • gen_docs_index / gen_doc_map 对新子目录的遍历行为未实测 —— 第 1 步做完就跑 kb.check 验证；若把切片扫进 docs 索引或报未知目录，把 testing/baselines/ 登记进对应豁免表（与 activeContext 同待遇）。
  • 存量子条目的时分回填要对档案核对，回填错只影响同日排序，不影响数字正确性；摘要注明序位兜底。
  • cap 4000 可能需要一两次校准 —— 以存量最长条目 ~0.9k 计，4 倍余量；真超了说明该把明细下沉档案，不是调 cap。
  • 范围外不动：attachments/ 冷库、config.yml / auto-qb-data 红线、my-commit-flow 闸门逻辑（已核实其 baseline 引用只在注释文案，不解析结构）、test_rule_engine.py 的无关同名。
  • 附带收益：全体 clone 收尾从「同写 baseline.md 一段」变「各写各的新文件」，多 clone 合并撞车面归零 —— 这正是 v1 三缺陷的总解。
