§01目标与极简原则

1.1 要解决的问题

已完成种子（progress≈1、amount_left=0）本不该再产生下载。一旦出现下载证据，说明本地数据/resume 声明与实际不一致，而损失直接计入 PT 下载量且不可逆。出错概率本来就小，所以保险丝的定位是低成本兜底，不是一套监控系统。

1.2 极简原则（本轮新增，优先于一切「更周全」的设计）

  • S1 单一判据：只看「持续下载证据」。不区分文件大小、不区分缺口比例、不做累计预算。
  • S2 单一升级动作：证据成立就暂停。不做 L0–L3 梯度，不做「只告警」档位。
  • S3 零副作用：数据完整时不做第二次 qB 写；稳态零请求。
  • S4 批量也暂停：批量触发大概率是磁盘/系统级问题，此时停种就是正确动作，不降级为只告警；只处理日志风暴。
  • S5 可撤销：放行是显式动作；放行后在「重新完成」之前不再重新武装。

1.3 不变量（违反即实现错误）

  1. 只写两件事：该种子的单种下载限速、该种子的 pause/resume。绝不动全局限速、上传限速、分享率、tracker 配置。
  2. 哨兵必须 > 0 且为奇数 KiB/s。qB 会把 0 归一成「不限速」（§02）；奇数 KiB 复用仓库既有「用户手动限速」约定（utils.py:793-798），让规则/tracker 自动限速主动跳过。校验器直接拒绝 0/偶数。
  3. 只对 dl_limit == 0 的种子写。这既是幂等（重复武装不产生第二刀），也是不覆盖用户已有意图的结构性保证——不用额外配置键。
  4. 无定时解除：恢复只有三种来源——显式放行、种子删除、放行后重新完成。
  5. 放行必须 CAS：当前限速仍等于哨兵值才恢复 pre_limit；否则视为第三方已接管，什么都不写。
  6. 幂等 + dry-run 只读：重复武装/触发/放行、进程重启都不产生第二次副作用；--dry-run 不写 qB、不落状态。

§03极简方案

3.1 三个状态

      （完成 & dl_limit==0 & 无条目）
                 │ 写哨兵
                 ▼
              [armed] ──连续 N 拍 dlspeed > 0──▶ [triggered]（pause）
                 ▲                                    │
                 │                                    │ 显式放行（CAS 恢复限速）
                 │                                    ▼
                 │ 重新完成 & dlspeed==0          [released]
                 └────────────────────────────────────┘
状态由什么事件进入这一状态下做什么
armed种子完成且 dl_limit==0哨兵已在；每拍看 dlspeed 累计连击数
triggered连击数达到 confirm_ticks已暂停；每拍确认仍在暂停（被外部启动则再暂停一次）
released显式放行（或外部把限速改走）不再干预；等「重新完成且 dlspeed==0」回到 armed

三点刻意简化：

  • 没有 monitor_only 状态：dl_limit!=0 的种子不建条目，只在触发时建一条 triggered。判定是「值是否为 0」的无状态分支，不需要记「我打算不写它」。
  • 没有 released_external：外部改走限速与用户放行的后续行为完全一样（都不再干预），合并进 released。
  • 没有 gc：种子消失就是删条目，不是状态。

3.2 武装：每拍扫一遍，写入只发生在「第一次」

  • 主循环每拍本来就会遍历完整快照，不需要额外的定时器或 sweep：对满足完成谓词的种子，若 dl_limit==0 且无条目 → 写哨兵并建 armed。
  • 批量写：setDownloadLimit 的 hashes 用 | 合并，每批 100（常量，不做配置键）。
  • 完成谓词：progress ≥ 0.999 && amount_left == 0 且 state 不在 checking* / moving / allocating / metaDL / forcedMetaDL。不要求 dlspeed==0——已在异常下载的种子也要被纳管。
  • 跳检路径仍在 torrents/add 里直接带 download_limit=fence，消除「add 成功→首拍武装」的不限速窗口。

3.3 触发判据：连续 N 拍 dlspeed > 0

两个候选里选「持续」，不选「累计字节」：

候选实现代价可解释性结论
连续 N 拍 dlspeed > 0一个整数连击计数；无基线、无字节运算「完成种子的持续下载」本身就是异常采用
自武装起累计 downloaded 增量 > 固定阈值要记基线 + 处理重启/计数器回绕 + 每次比较阈值天然要选一个「字节数」，等于变相按大小分级不采用

量级依据（这不是大小分级）：哨兵把速度压到 13 KiB/s，因此「发现前最多损失多少」只由检测窗口决定——confirm_ticks=3 × 同步拍间隔（约 5–10 s）≈ 15–30 s，对应 ≈0.2–0.4 MB。也就是说阈值不是「容忍多少数据」，而是「容忍多长的证据延迟」；文件多大都无关紧要。

为什么不需要额外的速度下限：qB 的 dlspeed 是整数 B/s，真实下载必然 > 0；连击要求已经把单拍抖动过滤掉。也不需要「>2×fence 的超速单独判据」——超速和普通下载的处置完全一样（都是暂停），多一条判据不改变动作。

3.4 动作集合：三个写动作 + 一个标记

动作触发时机说明
写哨兵 setDownloadLimit(fence)种子首次完成只对 dl_limit==0；奇数 KiB
torrents_pause连击数达标唯一升级动作；note_own_write 让规则延后一拍
恢复 pre_limit显式放行且 CAS 成立通常恢复为 0（不限速），不 resume（由用户决定是否启动）
加 / 删标记标签进入 triggered / 离开 triggered固定 zFusePaused；只随状态迁移写，详见 §3.8

没有告警档、没有限速降档、没有全局动作。日志只承担可观测性：L1 级一行 WARNING（hash/name/证据/已下载量），批量时见 §3.5。

3.5 批量场景：全停 + 聚合日志（不引入保护逻辑）

  • 动作不降级：同一拍内有多少条就暂停多少条。批量触发大概率是磁盘/权限/系统级问题，停种正是正确处置。
  • 日志聚合：每拍最多一条汇总行——fuse: paused 12 torrents (batch) first=abc123,def456,ghi789；单条明细降到 DEBUG。这不叫保护逻辑，只是输出格式。
  • 通知聚合：每拍一条，内容同上；不按种子各发一条。
  • 恢复：提供 fuse release --all（一次性放行全部 triggered，内部按批 CAS）；这是运维命令，不是自动保护。

3.6 用户主动补齐：最简放行

  • 唯一入口：WebUI 列表/详情的「解除保险丝」按钮，或命令 fuse release <hash>。放行 = CAS（当前仍为 fence）→ 恢复 pre_limit → 状态 released；不自动 resume（用户自己点启动，避免我们在错误的语义上替他做决定）。
  • 不会立刻被重新武装：released 期间不做任何写；只有「该种子重新完成（amount_left==0）且 dlspeed==0」才回到 armed。因此一次放行足够完成整个补齐过程；补完自动重新武装，不需要冷却参数。
  • 不猜意图：外部 qB 的 resume、规则 start 都不算放行（否则一次误点即失守）。想补齐就用本 UI 的按钮——这是刻意的取舍（见 §04 Q3）。

3.7 状态与自愈

state.data["download_fuse"] = {
  "entries": {
    "<hash>": {
      "status": "armed|triggered|released",
      "fence": 13312,        // 写入时的哨兵值（配置改了也按旧值 CAS）
      "pre_limit": 0,        // 首次武装前的值
      "streak": 0            // 连续 dlspeed>0 拍数
    }
  }
}
  • 写盘点：武装一批一次、触发、放行、重新武装。都不是每拍。
  • 体积：约 80 B/条；2000 个完成种子 ≈0.16 MB。
  • 自愈（state 丢失/损坏）：条目缺失但该种子「已完成 + dl_limit 恰等于配置的 download_limit」→ 按证据重建：带 zFusePaused 标签且已暂停 ⇒ triggered；否则 armed。两种都不写 qB，日志标注 adopt；由 fuse release --all 兜底。
  • 外部改限速：armed 条目发现 dl_limit != fence → 转 released，不写回。

3.8 触发标记：一个 qB 标签（默认名固定）

结论：triggered 的种子加 zFusePaused 标签——默认值 zFusePaused、可由配置键 download_fuse.fuse_tag 覆盖（保留名，默认值即约定）；进入 triggered 时加，放行时删；只在状态迁移时写，不做每拍对齐。标签同时出现在 qB 原生列表与自家 WebUI（标签 chip / 搜索行天然可见），前端零改动。

载体对比：为什么不是分类 / comment / 只在我们 UI 标

载体利弊结论
qB 标签qB 原生列表可见，正是用户痛点所在；自家 WebUI 的标签 chip/搜索自动可见；集合语义天然幂等；定义随首个 add 自动创建规则引擎可见（有规避路径，见下）；每个触发种子多一次 resume 写采用
qB 分类qB 列表同样显眼单值：会覆盖用户分类，并影响保存路径/分组/规则；写一次就破坏现状否
comment规则不可见（record.comment 未进条件/表达式，仅展示）覆盖站点/用户备注；要恢复就得把原文存进 state（长度不可控）；列表默认看不到，只在详情抽屉；还需新增 API 方法否
只在自家 WebUI 标零 qB 写、零规则冲突qB 原生里仍是「莫名暂停」，与用户原始诉求相反；后端加字段 + 前端加 chip 一样要改仅作兜底

命名、创建与生命周期

  • 名字默认 zFusePaused，配置键 fuse_tag：实现的落点是可配置键（默认值即保留名），文档 / 用户排除规则 / WebUI 识别都以配置值为准；默认值不许改的理由仍在——z 前缀是规避规则泛匹配的约定。qB 只裁剪首尾空白、含逗号即非法、区分大小写（tag.cpp:37-62）；默认名不含逗号与空白。
  • 谁创建：首次加标签时 qB session 自动建定义（m_session->addTag），无需额外 create 调用。
  • 加：仅 armed → triggered 迁移时，与 pause 同拍、按批一次请求。删：显式放行离开 triggered 时，与恢复限速同一批。删种：标签随种子消失，定义可能余留到 qB / 清理任务处理，无害。
  • 幂等：qB 侧 TagSet 集合 + hasTag 提前返回，重复加无副作用；我们侧调用前先读快照 tags_set，已存在则不发请求。
  • 不每拍对齐：标签若被规则/清理/用户移除，只记一条日志，不自动重加——否则会和清理任务互删成环；triggered 仍由 state + 暂停事实保证。

关键冲突：规则引擎会不会吃掉或误触发

链路源码事实结论 / 规避
规则按标签匹配TagsCondition 支持精确、regex:、:ignore_case（conditions.py:49-72）标签对规则可见：用户若写泛匹配（如 regex:z.*）会命中。规避 = 固定 z 前缀 + 文档声明为保留名、不鼓励泛匹配。
标签变更触发 on_torrent_field_changedwatch_fields 可含 tags（store.py:627-632）；但 QbApi 写 tags 会登记 self_caused_fields 期望值，下轮上报值一致即按自写消费（store.py:648-663 / 788-819）不自触发：前提是所有标签写都走 QbApi facade，绝不直接用 raw client。
规则 / 维护 remove_tagsbasic.py:44-58、maintenance_mod.py:181-194 用 match_tag_patterns（含 regex）泛正则可能误删：标记丢失，保险丝状态不受影响；不自动重加。文档要求排除 zFusePaused。
全局标签清理delete_tags / delete_tags_if_has_no_torrents 对全部定义做 regex 匹配并整标签删除（maintenance_mod.py:345-371）同上：用户配 regex: 通配时标记会被清掉；建议收窄清理正则，或接受标记消失。
HR 排除 / 站点 remove_tags / remove_similar_tagshr.exclude_tags（record.py:318-331）、maintenance_mod.py:215-230只有用户显式把本标签写进排除/删除规则才生效；remove_similar_tags 只比对站点 tags，天然安全。
WebUI 标签候选auto_managed_tag_rules 只从配置派生（utils.py:687-726；torrent_detail.py:131-142）本标签不在配置 → 会出现在「添加标签」候选里（轻微噪声），无功能影响。

取舍：不在规则引擎里给保险丝开特例（例如让 TagsCondition 跳过本标签）——那会改变全局规则语义，爆炸半径远大于「标记可能被清掉」。选择保留名 + 文档 + 不重加。

同名冲突与多实例

  • 用户已有同名标签：固定保留名；启动时若定义已存在记一条 WARNING（一次性，读 store 标签缓存，不发额外请求），行为上复用同一标签。残余影响：用户曾把该标签用在别的种子，我们在「该种子被触发并放行」时会移除它——文档写明这是保留名。
  • 同一 qB 多实例：标签共享；A 放行会摘掉 B 仍触发的种子的标记。多实例共用一个 qB 时，保险丝只应在一个实例启用（写入文档与残余风险）。多 qB 各自独立，无影响。

成本（Else 源码）

只有真实变更才写：addTag 走 deferredRequestResumeData()（合并到同一事件循环，每种子最多一次 save），而 stop() 本身也触发一次 resume 写（torrentimpl.cpp:2014-2022、890-910、965-1008）——标签只让每个 triggered 种子多一次同量级写，不改变数量级。批量 N 个：1 次 HTTP + N 次 resume 写；标签不影响队列/状态，也不会让种子起跑。

adopt 顺带变准（不增加配置）

state 丢失后：完成 + dl_limit==fence + 暂停且带标签 → 直接重建 triggered（零 qB 写）；只有 fence 没标签 → armed。标签因此兼作「触发过的持久证据」。

若不想引入标签：唯一零冲突的替代是「只在自家 WebUI 标」（后端把状态作行字段、前端加 chip），代价是要改 WebUI，且在 qB 原生里仍看不出原因——与你的原始诉求相反。因此推荐标签；它的全部复杂度就是一条 add/remove + 一条保留名约定。

§04极简版 grilling：简化后会咬人的地方

#风险会不会真咬是否加复杂度
Q1「连续 dlspeed>0」挡不住慢速大额下载不会更糟：慢速同样满足 >0，反而更早被暂停；且哨兵已把速度压到 13KiB/s，慢速大额本来就走不完。不加
Q2暂停落在 checking 上不中止校验真咬一小口：校验会延后到恢复之后，但不会丢数据、不会误判。用户看到「暂停 + 校验中」即可。不加（只记一行日志）
Q3用户连续小量补齐被反复暂停不会：released 在重新完成前不重新武装，一次放行覆盖整个补齐过程。真正的体验代价是「不能在 qB 里直接 resume，要来本 UI 点一下」。不加
Q4批量暂停把做种面整体打停会，但这正是用户要求的语义（磁盘级问题就该停）。恢复靠 release --all。不加（拒绝对 mass guard）
Q5adopt 误判：用户恰好手设 13KiB概率低但非零；后果只是多一条被我们盯着的条目，行为与用户手动限速一致（不写、可暂停）。不加
Q6每拍全量扫描的开销不会：遍历的是已在快照里的记录，零 HTTP；写入只发生在状态迁移时。不加
Q7state 丢失后残留 13KiB 限速完成态不下载 ⇒ 当期危害≈0；adopt 重建；真正影响是「将来补齐被拖慢」。不加
Q8「我经常要补齐，每次都点按钮烦」会咬，但这是少数场景；本轮先不加白名单（两个键 + 一条判断），等真出现频次再说。先不加（记为后续候选）

§05配置：四个键

键类型默认校验说明
enabledboolfalse—总开关；默认关（保守默认，等价今天行为）
download_limitspeed13KiB/s>0、整 KiB、KiB 数为奇数、≤1024KiB哨兵值；0/偶数直接报错
confirm_ticksint31..20连续多少拍 dlspeed>0 才暂停
fuse_tagstrzFusePaused非空字符串触发标记名；默认值即保留名，改值需同步排除规则与文档

去掉的键与理由

去掉理由
scope只有一种作用域（全部已完成）。留一个键只会让「默认到底覆盖什么」重新变成问题。
fill_bytes / large_bytes / large_ratio用户明确否掉按大小分级；动作已经是「暂停」，分级不改变结果。
overspeed_factor超速与普通下载的处置相同（暂停），多一条判据不改变动作。
budget_window_hours没有累计阈值就没有预算；released 语义已天然挡住「反复小量」。
mass_trigger_count / mass_guard_global_limit用户否掉批量降级。日志聚合是输出格式，不是策略，不需要键。
sweep_minutes / arm_batch每拍扫描本就有；批大小 100 作为常量足够。
respect_existing_limit变成无需配置的结构性行为：只对 dl_limit==0 写（同时是幂等基础）。
settle_ticks / rearm_cooldown / fill_grace重新武装的条件简化成「重新完成且 dlspeed==0」，不需要时间参数。
exempt_tags / exempt_categories白名单是「高频补齐」的优化；先用显式放行覆盖，真有频次再加（§04 Q8）。
trust_priority_fill / trust_runtime_recheck / trust_external_resume不再自动猜意图；补齐只认显式放行。这是简化后的明确取舍，不是遗漏。

§06决策清单

#决策推荐备选 / 备注
D01总开关默认关（enabled=false）默认开：首日全量写盘风险大
D02作用域全部已完成种子，无配置键仅跳检：省不了代码，只少覆盖
D03哨兵值13KiB/s 奇数，可配取全局 5%：随曲线漂移、有偶数风险
D04触发判据连续 confirm_ticks（默认 3）拍 dlspeed>0累计字节阈值：要基线与字节算术，且天然是大小分级
D05升级动作唯一动作：暂停L0–L3 梯度：已否
D06批量全停；只聚合日志/通知降级为只告警：已否
D07已有非零限速不写、只监控（无配置键）一律接管：会抹掉用户预置值
D08放行显式 release（CAS 恢复，不 auto resume）；released 到重新完成才再武装自动识别补齐：复杂度不成比例
D09state 自愈adopt（值恰等于 fence 且完成）+ release --all不 adopt：残留限速无人认领
D10触发标记载体qB 标签，默认 zFusePaused、配置键 fuse_tag：qB 原生可见、我们 UI 自动可见、集合幂等、qB 自建定义仅自家 WebUI：qB 原生仍无解释；comment：覆盖用户备注且需存原文
D11标签写入策略只在状态迁移时加/删；不每拍对齐；全部走 QbApi（自写抑制防规则自触发）每拍 ensure：会与用户清理任务互删成环；规则引擎开特例：改全局语义

§07分步实施（每阶段可独立验收、可回滚）

四个阶段各自是一个「能单独收尾」的最小闭环：任一阶段结束都可以停手，后续不做也不会留下半成品。每阶段收尾都要跑 commands run test.full，并按仓库口径记基线切片。

阶段改动范围（文件）退出条件 / 验收判据回滚
S1 配置面
无行为		config/models.py（download_fuse: enabled/download_limit/confirm_ticks/fuse_tag）、config/loaders.py、config/validation/core.py、config/schema.py、配置单测默认 enabled=false；0/偶数/越界聚合报错且含键名；默认配置下全量测试与 test_actions_skip.py:122 不变；dev.run --dry-run 能打印配置且零 qB 写删键即回滚；不产生 state、不写 qB
S2 状态机 + 哨兵 + 暂停
核心		新模块 core/modules/fuse_mod.py（三态 / 每拍扫 / 批 100 / CAS 恢复 / 无标签版 adopt）、state 的 download_fuse、聚合日志、fuse release <hash> 入口单测：武装写、N 拍触发、恒 0 不误伤、批量全停 + 单条汇总、CAS 失败不写、dry-run 零写、state 丢失 adopt、重复执行幂等；真机隔离实例：3 个完成种子得到 13KiB，制造缺片（删一个 piece/文件后强制校验）→ 连续 3 拍 dlspeed>0 → pauseenabled=false 即停；fuse release --all 清残留限速；state 字段留存无副作用
S3 标签标记 + adopt 增强fuse_mod.py：进入 triggered 批量加标签、放行删标签、adopt 以标签判 triggered；标签名走配置键 download_fuse.fuse_tag（默认 zFusePaused）；启动一次性 WARNING（定义已存在）；released 残留标签不重加、不自动重试摘除（放行时删一次，删失败就留着，等下一次显式放行/人工处理）单测：加标签一次 / 第二拍零调用、放行删、批量一请求、标签被外部删除不重加、dry-run 零写、adopt 命中标签 → triggered；真机：qB 列表与自家 WebUI 都能看到该标签；规则日志无 on_torrent_field_changed 自触发回滚 S3 代码即可；已打标签用 fuse release --all 摘除
S4 隔离实例端到端 + 回写测试补全、README / 知识库回写、验收剧本；实测发现 CLI 放行缺快照同步，最小修复 cli.py（fuse_release 先 store.apply_sync 再走 CAS）完整剧本：武装 → 触发（标签 + 暂停）→ 放行 → 重新完成再武装；批量 10 个；state 清空重启（adopt 只覆盖已完成种子）；enabled=false 与 dry-run 全程零写；test.full 全绿并记基线关 enabled 回退；文档变更可单独回退

阶段间不留半成品：S1 只有配置没有行为（等价现状）；S2 有行为但没有标记（可用但可读性差）；S3 才补标记。任何一段停下都能上线，因为默认关闭 + 显式放行始终成立。

§08待拍板

  1. P1 默认是否开：推荐保持 false，先手工跑一轮观察再开。
  2. P2 confirm_ticks=3：按约 5–10s 一拍，即 15–30s 证据窗口；如果你希望「更快拦」可设 2。
  3. P3 放行后不 auto resume：推荐维持；若你希望「点一下就继续下载」，加一个 resume=true 参数即可（不加配置键）。
  4. P4 白名单：本轮不加（§04 Q8）；若你有固定的「经常补齐」标签/分类，这里需要你确认再补。
  5. P5 标签名 zFusePaused：推荐就用它（z 前缀沿用程序标签约定）；若你想要更直白的中文/其它名字，现在改成本最低——之后改会连带文档与可能的排除规则。

§09残余风险（选择接受）

风险影响为什么接受
R1 暂停落在校验中会延后校验补齐/自检变慢不丢数据、不误判；加「等校验结束再暂停」要多一个状态判定
R2 批量暂停打停做种面短时无上传、队列位变手排批量触发≈磁盘级问题，停种是用户认可的正确动作
R3 adopt 误判（用户恰设 13KiB）多盯一个种子行为与用户手动限速一致；日志可见；可一键清
R4 外部 resume 不算放行用户要多点一次按钮否则误点即失守；这是刻意的安全侧重
R5 state 丢失残留限速未来补齐被拖慢完成态不下载，当期危害≈0；adopt 重建
R6 无白名单，高频补齐需重复点体验成本先观察频次；真高频再加两个键
R7 哨兵被规则/tracker 当「手动限速」跳过规则限速不生效于这些种子这正是设计意图（防止规则覆盖保险丝）
R8 用户规则/清理正则泛匹配清掉标签标记消失，qB 里又看不出原因保险丝状态不受影响；保留名 + 文档；不自动重加（避免互删成环）
R9 同一 qB 多实例共享标签A 放行会摘掉 B 仍触发种子的标记多实例共用 qB 时只在一个实例启用保险丝（文档写明）
R10 标签多一次 resume 写每个 triggered 种子多一次 save；批量 N 次与 pause() 自身的 resume 写同量级，不改变数量级

§10验收（逐条可测）

  1. 武装：启用后，3 个完成种子（dl_limit=0）首拍后各有一次批量写、dl_limit==13KiB；dl_limit=2MiB 的完成种子没有条目也不被写。
  2. 触发：伪造连续 3 拍 dlspeed=5KiB/s → 一次 pause、状态 triggered、日志含 hash/证据；第 1–2 拍不动作。
  3. 零误伤：完成种子 dlspeed 恒 0 跨 100 拍，无 pause 调用。
  4. 放行：CAS 成立 → 恢复 pre_limit；当前值被外部改成 3MiB → 不写；放行后未完成期间不再武装；重新完成后回到 armed 并重写哨兵。
  5. 批量：同拍 10 个触发 → 10 次 pause、日志恰好 1 条汇总、通知 1 条；release --all 后全部恢复。
  6. 自愈：清空 state 重启 → fence 值的完成种子按证据重建（无标签 armed / 带标签且暂停 triggered）且零 qB 写；release --all 全部转 released 并恢复限速。
  7. dry-run：所有 fuse 方法零 qB 调用、不落状态。
  8. 回归：test_actions_skip.py:122（默认配置下 add 仍为 2001KiB）保持通过，证明默认关闭不改变现状。
  9. 标记：触发后 zFusePaused 出现（与 pause 同拍、批量一次请求）；同一触发状态第二拍不再发标签请求；放行后标签消失。
  10. 规则不被打扰：标签写入后的下一轮没有 field_changed(tags) 事件（self_caused 已消费）；只有用户规则在正常节奏按 tags 命中时才可能动作。
  11. adopt 带标签：清空 state 重启，带标签且暂停的种子重建为 triggered（零 qB 写）；同 fence 无标签的重建为 armed。
  12. 标签被外部删除：不自动重加、不产生写循环；released 条目残留标签不重加、不自动重试摘除——放行时删一次，删失败就保留，等下一次显式放行或人工处理。

真机验证只用隔离 qB 实例（独立端口 + 独立数据目录 + minimal.yml），绝不碰生产 config.yml 与 auto-qb-data/。

10.1 S4 真机验收记录（26-11-03，副实例 56590，qB v5.2.3）

  1. 11 个本地假种子（主 8MiB + 批量 10×2MiB）首拍武装为 dl_limit=13312B/s；
  2. 主种子暂停 → 前 2MiB 写零 → recheck 落账后再 resume（校验中 resume 会被 qB 忽略）→ web seed 真下载，条目 reason=连续 3 拍 dlspeed>0，pause + zFusePaused；
  3. CLI --fuse-release <hash>：限速归 0、摘标签、状态 released（修好 CLI 快照同步后才生效）；
  4. 复原文件 + recheck → 重新完成 → 回 armed 并重写 13312B/s；
  5. 批量 10 个同拍触发 → 单条汇总日志 paused 10 torrents (batch)，10/10 pause + 标签；
  6. 批量复原为完成态 → 清空 state 的 download_fuse 域 → 重启 adopt 11 条（10 triggered + 1 armed），零 qB 写；
  7. --fuse-release-all 后 enabled=false 与 --dry-run 各 3 拍，标签/限速/日志全部零变化。

adopt 只覆盖「已完成」种子：未完成的 triggered 条目在 state 丢失后无法凭 fence 值重建，需人工 / 下次放行兜底——这是当前实现的已知边界。
