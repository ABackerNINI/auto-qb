01拍板回执与范围

事项结论
用户拍板 · 安全传输HTTP(T1 受信 LAN + token)是唯一实现形态 —— 大部分部署在局域网内, 明文可接受; T2(端点自签 TLS)不实现(MV3 证书信任难题); T3(反代终止 TLS)不实现, 仅在文档中给出配置路径, 非局域网用户自行搭建。
用户拍板 · 路线路线 A(发现端口 + 随机数据端口 + token 自动分发)叠加跨机路径 C(端点直绑)之上, 同一计划一次落地。路线 B(native messaging + 命名管道)缓行, 不并入(联合分析 26-10-14-1135 §03: 结构上到不了 NAS, 且打破「协议不变」不变项)。
派生口径 · 端口语义port 默认 0(交 OS 随机); 显式非零 = 完全旧行为(存量零感知)。discovery_port 默认 18788(用户现产端口转正为发现端口); 置 0 = 关闭发现(退手动配置)。
派生口径 · 配对码新键 pairing: auto|on|off, 默认 auto: host 非回环时强制(发现端点免 token, 非回环可达时它是 LAN 上的 token 分发器, 必须有一道人工关口); 同机默认关(残留风险已论证, 见 1110 报告 §09)。on = 同机也强制; off = 永不(校验会挡: 非回环 + off + 空 token ⇒ 报错)。
派生口径 · 扩展放开主机判据 = 回环 ∪ 私网段(10. / 172.16–31. / 192.168.)(原计划 D2 结论); https scheme 保留不折(反代用户需要, 后端本身仍只讲 http); 0.0.0.0 允许 + 文档警示(D3); 多 PC 部署协议层允许, 文档推荐打包扩展固定 id(D4, 理由见 §07 R8)。
用户拍板 · R2 缓解升级(26-10-15 补写)发现端口被占的缓解从「日志 + 退手动」升级为零人工三件套: ① 候选表先绑先得 + 扩展并行探测; ② 绑定失败后台退避重试、占用者退出自动接管(翻转 R6); ③ 校验期对落入 OS 临时端口段的 discovery_port 告警。详 §04 S1/S2/S4、§05 C7/C8、§06 V11/V12、§07 R2/R6。mDNS/SSDP/UDP 组播一族维持 1110 报告 §6.2 否决(扩展无 UDP/组播/mDNS 能力)。
明确不做advertise 对外声明端点覆盖键(隧道/反代用户保持显式端口即旧行为, 不受随机化影响); WebSocket 推送(路线 C); native messaging(路线 B); 多租户; shared_dir 只读路径的替代(它与本计划并列, 不替代)。
Is 已修问题?否, 新特性。两端写死是设计取舍(注释点名过 NAS 场景), 不是回归。
与三份前件的关系: 原跨机计划 26-10-09-0856 已转 Superseded(范围被本计划吸收, 其 S1–S6 目标逐一落入本计划 S1–S7); 可行性报告 26-10-14-1110 是路线 A/B 的事实背景(其 §10 六项决策由本表收敛); 联合分析 26-10-14-1135 是「计划适配哪条路线」的判断来源。三份均为冻结快照, 不回头改; 决策权威在本计划 §01。
一处必须知道的冲突: 用户当前 config.yml 显式写着 port: 18788(数据端口)。升级后 discovery_port 默认也是 18788 ⇒ 两端口相同, 启动即报错。S1 的校验会给出可操作文案, §08 有该用户的具体迁移步骤。这不是设计瑕疵, 是「现产端口转正」的必然摩擦, 用校验 + 迁移文档消解。

03目标形态与数据流

3.1 两种部署, 同一套机制

同机(默认形态, 用户零配置):

  扩展(选项页/后台)                auto-qb 后端(单机)
  ── GET /api/hr/discover ───────▶ 发现端点(18788 起连号 3 候选先绑先得, 免配置, 默认只绑回环)
  ◀── { 实例清单: 端点(随机端口) + token } ──
  ── GET /api/hr/tasks ──────────▶ 数据端点(OS 随机端口, 60s 短轮询)
      (token + origin 两道关, 协议逐字不变)

跨机(NAS + 外部 PC, 计划目标形态):

  外部 PC 扩展                    NAS 上的 auto-qb
  ── GET http://<nas-ip>:18788/api/hr/discover ──▶ 发现端点(host=私网地址)
  ◀── { 端点 http://<nas-ip>:<随机> + token } ──(非回环 ⇒ 先过配对码)
  ── GET http://<nas-ip>:<随机>/api/hr/tasks ─────▶ 数据端点(同一套轮询)

非局域网用户(文档路径, 不实现): 自行反代终止 TLS, 后端仍只听回环或私网;
  扩展填反代地址(https 保留, normalize 不再折 http)。

3.2 变化与不变

变化(本计划引入)不变(逐字保留)
· host 可配(端点绑哪个地址; 发现/数据两端同值)
· port 可随机(0); 显式值 = 旧行为
· 新发现端点 GET /api/hr/discover(18788 起连号 3 候选先绑先得, origin + 配对门)
· 多实例注册表(本机 app-data, 心跳 + TTL 聚合)
· 配对码(非回环强制; <data_dir>/hr.pairing 0600)
· 扩展主机判据放开(回环 ∪ 私网段) + https 保留 + 发现/配对 UI 		· 60s 短轮询 + token 鉴权(发现端点除外, 它发 token)
· origin 白名单(chrome-extension://)
· URL 白名单 / 任务绑定(SSRF 防线)
· request_timeout 硬约束(轮询周期 < 超时窗)
· allow_reuse_address=False 独占端口守卫
· hr.token 文件 = 信任锚(人可打开核对)
· shared_dir 只读路径并列保留
为什么发现端点可以免 token: 它本身就是发 token 的(先有鸡还是先有蛋)。它的两道关是: ① Origin 钉死(chrome-extension://, 配了 extension_id 则只认那一个 —— 与数据端点第二道防线同一机制); ② 配对码(仅非回环可达时强制)。同机场景下残留风险(本机恶意进程抢占发现端口钓鱼)已由 1110 报告 §09 论证为可接受增量, 用户可选 pairing: on 自行硬化。

07风险与不变项

7.1 已接受的风险

#风险评估与缓解
R1port 默认 8788→0 的翻转, 对「旧扩展 + 未显式配端口」存量表现为扩展突然连不上三重可观测兜底: 启动日志打实绑端口 / status() 带端点 / fault-domain「WebUI 活跃而扩展未联系」告警(不静默); README 迁移节写明。受影响面 = 只升后端不升扩展且从未配 port 的用户。
R2发现端口被普通应用误占零人工三件套(26-10-15 补写): ① 候选表轮换 —— 后端 discovery_port 起连号 3 个先绑先得, 扩展并行探测同表(S2/S4); ② 绑定失败后台退避重试, 占用者退出自动接管(S2, 翻转 R6); ③ 校验期对落入 OS 临时端口段(Windows 49152–65535 / Linux 32768–60999)的 discovery_port 告警(S1 ⑥)。默认 18788 已在临时段之外, 最常见的「临时端口随机撞上」形态天然免疫; Windows 特有形态是 Hyper-V/WSL2 动态排除段(无监听者也绑不上、随重启漂移), 候选轮换对其免疫, 排障查 netsh interface ipv4 show excludedportrange protocol=tcp(S7 文档)。仍全占 ⇒ 明确日志 + 数据端点照常 + 扩展退手动; discovery_port 可改可关(0)。mDNS/SSDP/UDP 组播一族维持 1110 §6.2 否决(扩展无 UDP/组播/mDNS 能力); 不杀占用进程、不抢绑(SO_REUSEADDR 双绑语义未定义 / SO_REUSEPORT 分流)。
R3配对码暴力枚举(6 位, 10⁶ 空间)失败节流 + 每来源计数上限(§05 C3); 文档写明「LAN 受信」前提; 同机默认不开配对(不需要)。
R4明文 HTTP 下 token 可被同网段嗅探(T1 已知)用户已拍板接受; 文档显式标注「仅受信内网」+ 非局域网走反代路径; 配对码只治「未授权拉取」不治「链路嗅探」(1110 报告 §05.1 精度说明)。
R5注册表文件竞态 / 损坏 / 被放云同步盘原子替换 + 读容忍(坏文件当空); 文档钉「不得放云同步盘」; 单实例场景自述不依赖文件。
R6发现端口归属者退出后, 其他实例不接管S2 后台重试接管已翻转此限制: 占用者退出 ⇒ 重试线程自动绑定(接管延迟 ≤ 重试间隔, §05 C8); 单实例(主流)重启无感。
R7新增配置键触发守卫测试(writer / schema / mutation)期望变更S1 明列须核对项; 机械同步, 不构成设计风险。
R8未打包安装的扩展 id 随安装路径变化 ⇒ 跨机多 PC 时两台 id 不同, 钉单 extension_id 会挡住第二台文档推荐多 PC 场景打包扩展(固定 key)或留空 extension_id(发现端点靠配对码把关); 单 PC 场景无感。

7.2 不变项(须逐条保持)

  • 默认仍回环 —— host 缺省 127.0.0.1, 发现与数据两端同值; 同机部署零感知。
  • URL 白名单 / 任务绑定 / origin 白名单三道安全资产逐字不变。
  • 协议不变: 60s 短轮询 + token 鉴权; 「轮询周期 < request_timeout」硬约束不变。
  • allow_reuse_address=False 独占端口守卫 + 免 FQDN 绑定口径不变; 端点线程「只入队 + 置一次性旗标」单一写线程假设不变。
  • hr.token 文件仍是信任锚(自动生成 0600, 人可打开核对); shared_dir 只读路径保留, 与本计划并列不替代。
  • 路由「纯逻辑可单测」结构不变(route() 直接钉鉴权与白名单的方式延续到发现端点)。

08迁移与兼容

8.1 三种组合

组合行为处置
旧扩展 + 新后端显式 port ⇒ 完全旧行为(零感知); 未显式配 port ⇒ 数据端口转随机, 旧扩展还在打 8788 ⇒ 连不上可观测兜底(日志/status/fault-domain 告警); 解法二选一: 升级扩展(自动发现)或把原端口显式写回 port
新扩展 + 旧后端发现探测无响应 ⇒ 退手动配置(选项页手填端点 + token), 路径与今天完全相同不做断崖; background 发现失败有明确日志
新扩展 + 新后端同机零配置; 跨机只填 NAS 发现地址(+ 首次配对码)目标形态
