§01目标与设计原则

1.1 目标与完成判据

  • 只审计 src/auto_qb/webui/server/auth.py: 它是 Web UI 的鉴权与跨站防护单点, 出错代价高于普通 IO 胶水层; 不跑 webui/server/ 整包。
  • 首轮后每条 survived 都必须落进「真洞 / 等价变异 / 假存活」之一并给一句理由; no tests 视为函数面缺口, 先补池或补用例, 不拿残缺数字收尾。
  • 确认的真洞各自入池或当场补断言; 新守阵必须做同构变异红验, 再按同目标、同池复跑。
  • 复跑存活数不高于首轮; 新增存活必须解释。最终出一条基线切片、追加任务档案轮次, 并更新常驻锚 §07。

1.2 设计不变量

  • 目标永远只有一个模块; 池只取直接相关的两个测试文件, 禁止退化成全 tests/。
  • 命令一律走 .commands/mutants/ 包 task id; forkserver、-n 0 --no-cov、文本层守阵 deselect 由包脚本内建。
  • 基线不绿不开跑; TIMEOUT / UNKNOWN / APPLY_FAIL / FLAKY / SUSPICIOUS / SEGFAULT 是未判定, 既不算杀死也不算存活。
  • 量化只认 mutants.run 同池复跑; 手搓变异只用于形态复验和新守阵红验。
  • 立项阶段未改 src/ 或 tests/、未执行变异测试; D1–D3 已于 2026-11-27 拍板, 计划转入 In Progress, 后续按 §04 分批实施。

§02现状与痛点

2.1 当前规模与风险面

2.2 为什么要做

  • 立项时常驻锚 §07 把 infra/ 与 webui/server/ 合并在「待做」行; S1 已拆成两个父包待做行, 并新增 webui/server/auth.py 待做行, 尚无变异刻度。
  • 覆盖率不能证明鉴权守阵的强弱: 一个 and/or、边界端口、票据路径集合或 fail-closed 分支被改错, 现有状态码断言可能仍绿。
  • 计划盘点时该目标的容器镜像仓尚未建立; S1 用 mutants.setup 建立本轮镜像, 不能把历史 versioning.py 结果当本轮基线。

§03方案总览

3.1 范围与显式排除

  • 目标: src/auto_qb/webui/server/auth.py。
  • 定向池: tests/unit/test_web_auth.py + tests/unit/test_web_traffic_stream.py。
  • 排除: webui/server/ 其余模块(含 routes/config.py 的公开端点路由门)、infra/(含 utils_parse.py 的 127/8 判据实现)、JS 前端、真实 qB 行为、生产配置与运行时数据; 计划外发现只记录, 不顺手修。

3.2 函数面核对

目标函数池内直接守阵结论
_host_header_partstest_auth_host_origin_parsing_helpers已覆盖
_allowed_hostnames / _hostname_allowed / _origin_allowedhelper 单测 + Host 白名单 + 写方法 Origin 用例已覆盖; S1 补 HTTP 80 / HTTPS 443 默认端口与 Host 无端口矩阵
_log_reject跨站拒绝用例的 caplog 断言已覆盖
_reject_cross_siteHost、Origin、全部写端点、凭证绕过、默认关闭用例已覆盖; S1 补票据凭证 × 外部 Host/Origin 组合
make_require_token / require_tokentest_web_auth.py 全部鉴权用例 + test_traffic_stream_ticket_discipline已覆盖; 两张 SSE 路径都在池内; S1 核 compare_digest 调用守阵

3.3 开跑前安全矩阵核验

  • 只在既有两文件内补用例: HTTP 默认 80 / HTTPS 默认 443、Host 无端口、显式端口不一致的正负矩阵。
  • 补 valid/invalid ticket、外部 Host/Origin、两张 SSE 路径与集合外路径的组合, 钉住 presented 的 or qticket 与票据消费语义。
  • 用确定性 spy 断言 ASCII 与非 ASCII token 都调用 secrets.compare_digest 且两侧为 UTF-8 bytes; 把 compare_digest 换成 == 纳入红验。
  • 补完先跑定向池与 test.quick; 若必须新增第三个池文件才能覆盖, 停手改计划并另立轮次, 不混入本轮同池对比。

3.4 三分类与确认策略

本轮是两文件窄池, 适合用 mutants.verify 捞「相关测试不在池里」的假存活; 但不对全部存活无差别开跑。候选文件纳入安全高相关项、所有无法判等价的行为改变项, 以及 timeout / suspicious / segfault / no tests 等非 killed 项; 安全高相关只决定优先顺序。读 diff 只能筛可证明全输入等价的明显项并记录理由, 其余必须 verify, 或在全套件上做同构手工确认后再分类。

4.1 验收(可判定)

  • 每条存活变异都有分类与理由; 每条真洞都有 issue 或已补断言, 且新守阵红验通过。
  • no tests 已清零或有明确函数面缺口处置; TIMEOUT / UNKNOWN / APPLY_FAIL / FLAKY / SUSPICIOUS / SEGFAULT 未被计入存活, 且逐条复跑或明确记为工具盲区。
  • 同池复跑完成, 存活数不升; 基线切片、任务档案、常驻锚三处指针闭环。
  • 未修改生产配置、运行时数据或计划外模块; 未把单模块结果外推成整包结论。

§07风险与对策

风险触发条件处置
基线不绿test.quick 或 mutmut 自带基线失败停手先修基线; 不带病开跑, 不用 verify 的差集口径掩盖计划内红测
同目标镜像互冲另一会话同时跑同 target, mutants/ 的 meta 被删或串目标停跑; 专用 --mirror + children 2; 已损坏轮次不作数
安全变异被误应用候选 diff 看起来像鉴权绕过或跨站放行只在容器镜像仓 apply/还原; 不碰运行中的生产实例; 先读 diff 再 verify
超时或 flaky出现 TIMEOUT / UNKNOWN / APPLY_FAIL / FLAKY / SUSPICIOUS / SEGFAULT记未判定并复跑同一条; 仍不稳定就记工具盲区, 不伪报杀死或存活
函数面遗漏报告出现 no tests只在既有两文件内补对应用例; 若必须新增池文件, 停手改计划并另立轮次基线, 不与首轮直接比较
文本层守阵污染基线阶段读源码文本的守阵先红依赖包脚本默认 deselect; 若仍红, 按坑档修正守阵表, 不手工绕过
复跑冲掉新测试新增测试只在工作树, 默认 run 刷新镜像先同步测试进镜像, 再 --no-refresh; 镜像内确认测试文件已更新
红验假红假绿锚点重复、替换未落地或还原不完整锚点 count == 1; 字节级比对替换前后; 原字节恢复并确认 src/ 无差异后才跑 test.full
范围漂移发现 auth.py 之外的相关缺陷不顺手修; 按范围守卫记录, 是否入池另行授权
