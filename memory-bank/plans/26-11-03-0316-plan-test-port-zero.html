§01目标与设计原则

目标

  1. 测试/开发轨的所有监听端口改为 0：由 OS 分配，脚本自己拿到实绑端口并在进程间传递，退出时按实绑端口回收。
  2. 同机多 clone 可以同时跑 commands run dev.e2e，互不抢口、互不误杀、互不复用陈旧桩。
  3. 不需要人工分配端口表，也不需要在启动前先查 netstat 选口。
  4. 失败必须响亮可诊断：拿不到端口、捕获不到端口、绑定失败都要给出「哪一步 / 期望什么 / 下一步做什么」。

设计原则（不变量）

  • 只动测试/开发侧：src/auto_qb/ 生产代码与 config.yml 一律不改；测试桩仍走真实 create_app + 真实 QbManager。
  • web.port 不纳入治理：它是用户配置、保持固定（浏览器 localStorage 按 origin 隔离）；本计划不引入端口分配表、不改成动态。
  • HR 发现口 18788 不在本计划内：只留 issue，改动另案；scripts/hr_ext_stub.py 的发现口保持现状，数据口已是 0。
  • 不复用外部服务：reuseExistingServer: false 保持。动态端口从机制上消除了「撞到别 clone 残留桩 → 验错对象」的假信心；该开关作为纵深防御保留。
  • 端口只由脚本传递：不落盘端口文件（避免残留/竞态），走 Playwright 官方 webServer.wait 捕获 stdout 命名组 → process.env。
  • 不保留固定口覆盖：不再读取 E2E_PORT（或任何旧的固定口覆盖变量）；环境中若出现，脚本直接报错并说明原因。真遇到排障场景再另议，不预先留逃生口。

§03方案总览

主线：webServer.wait 命名捕获组

Playwright 1.63 支持「不预先知道端口」的 webServer：wait.stdout 正则里的命名捕获组会写入 process.env（键名转大写）。官方示例见 node_modules/playwright/types/test.d.ts:1023-1046；实现证据 node_modules/playwright/lib/runner/index.js:921-931（process.env[key.toUpperCase()] = value），以及 :1004-1012（url 与 port 只能给一个；只给 wait 时走 stdio 等待）。webServer setup 在测试文件加载之前执行，因此 spec 运行时读 env 是安全的。

// e2e/harness.mjs —— 单一捕获契约
export const WAIT_STDOUT = /\[harness\] http:\/\/127\.0\.0\.1:(?<ui_harness_port>\d+)\//;
export function baseUrl() {
  const p = process.env.UI_HARNESS_PORT;
  if (!p) throw new Error('[e2e] UI_HARNESS_PORT 未注入: webServer.wait 没捕获到桩端口');
  return `http://127.0.0.1:${p}`;
}
// 启动前: 若检测到 E2E_PORT, 打印说明并退出非零 (不提供覆盖)
export const HARNESS_CMD = `uv run python scripts/ui_harness.py --torrents ${TORRENTS} --port 0 ...`;

数据流：

  1. ui_harness.py --port 0 先 bind 一个 socket（bind((host, 0))）拿到实端口，再把这个 socket 交给 uvicorn 启动（uvicorn.Server(...).run(sockets=[sock])）—— 取号与监听使用同一个 socket，没有 TOCTOU 窗口。
  2. 启动成功前打印一行 [harness] http://127.0.0.1:<实端口>/atlas/ ...（保持 flush=True）。
  3. Playwright 用 WAIT_STDOUT 捕获 ui_harness_port → 写入 UI_HARNESS_PORT。
  4. spec 侧调 baseUrl()；global-teardown.mjs 读同一个 env 做收尾。
为什么不用外层预取号（方案 A）：配置加载阶段先 bind(0) 拿号再传给 harness，取号与 uvicorn 真正绑定之间存在竞态（另一 clone/进程可抢走），且 Playwright 仍需要静态 url。
为什么不用 globalSetup 自起桩（方案 C）：要自己管生命周期、失败清理与 Windows 进程树，等于重写 webServer+global-teardown 已有能力；收益不抵复杂度。

§04实施步骤

S1 · ui_harness.py 预绑 socket + 打印实绑端口

文件：scripts/ui_harness.py

  • :964 --port 默认改 0，help 写明「0 = OS 分配」。
  • 新增取号逻辑：sock = socket.socket(); sock.setsockopt(SO_REUSEADDR? 不用); sock.bind((args.host, args.port))；actual = sock.getsockname()[1]。非回环检查保持在 bind 之前。
  • 把 args.port 的使用点统一替换为 actual：WebConfig.port（:983-990）、_materialize_config（:998）、打印（:1067-1071）。
  • 启动改为 uvicorn.Config(app, host=args.host, port=actual, log_level="warning") + uvicorn.Server(cfg).run(sockets=[sock])；绑定失败在预绑阶段就抛，打印端口与原因并返回非零。
  • 打印行必须包含 http://127.0.0.1:<actual>/ 且 flush=True（这是捕获契约）。

验收：uv run python scripts/ui_harness.py --torrents 1 打印非零端口且 curl 该地址 200；同时起两个实例得到不同端口；--port 8099 显式指定仍可用。

S4 · dev_webui.py 顺延链替换为 0

  • 删除 --web-port 的 8177 默认值与 _pick_web_port（:97-107）的 +1…+20 顺延分支；默认值改为 0。
  • 0 就地 bind((host, 0)) 取号后立即 close（必要时回绑自验一次）拿到具体口，再写 config.yml（产品校验要求 1–65535）；显式传具体口时保留该值。不 import 任何 free-port helper。
  • 冲突按正常错误处理：清晰报错（端口 + 原因）并退出非零；不做顺延、不静默退回。

验收：不带参数启动即 0，落盘为具体非 0 口并能打开页面；显式具体口被占时报错退出；代码中不存在 8177 默认与 range(want + 1。

代价说明：默认 0 会让每次启动的 origin 变化，localStorage 状态不跨次保留；这是测试/开发工具的既定取舍。只有专门测 localStorage 本身的场景才可能需要固定 origin，那种情况另行说明。

取证（2026-11-03，grep -rn "free_port\("）：改 0 之后仍需「取具体端口号」的调用点共 47 处（tests-real 28、tests/ 18、dev_webui.py 1），远超「≤3 且一两行」的内联条件。D3 已定案为保持现状 + 补自验：不新建共享核心、不逐点内联（后者会把 bind(0) 复制 47 份，违反单点纪律）。

§08验收标准

  1. 多 clone 并行：两个 clone 同时执行 commands run dev.e2e，两边都通过，且各自 UI_HARNESS_PORT 不同；无 8137/8099 冲突。
  2. 无固定口残留：e2e/、scripts/ui_harness.py、scripts/e2e_selfcheck.py、scripts/dev_webui.py 中不存在作为默认监听口的 8137/8099/8177；不存在 E2E_PORT 覆盖路径，设置该变量即报错。
  3. 收尾正确：e2e 结束后命令退出、无残留 ui_harness；teardown 只处理本次捕获端口，不误杀同机其它 clone 的进程。
  4. 失败可诊断：wait 超时错误能看出「跑了什么命令、等什么正则」；baseUrl() 缺 env 有明确消息；ui_harness 绑定失败打印端口/原因/rc≠0。

  6. 手工桩可用：commands run dev.harness 打印实绑 URL，可直接打开；--port N 仍可指定。
  7. dev_webui：不带参数默认即 0，落盘为具体非 0 口；具体口冲突按正常错误处理；无 8177 默认、无 +1…+20 顺延。
  8. 回归：实施轮跑 commands run test.quick（必要时 test.full），结果与基线切片对比无新增失败。
