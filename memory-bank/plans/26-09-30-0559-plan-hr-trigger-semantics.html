Delivery Plan · auto-qb · HR 在线核实

HR 触发语义重构:
移除「本地不触发」· 全量纳入管理

「未核实(本地不触发)」这个状态的根因,是拿本机下载量当有没有 HR 义务的判据 —— 但转移种子在本机 downloaded 恒为 0,这在 PT 圈是常态,不代表无义务;更拧巴的是,做种已满的种子 也因为「达标 ⇒ 不触发」的短路落进同一个桶。本计划把「触发」降级为纯展示辅助(只用来区分 「本机下载的」与「疑似辅种」),后端管理(打标 / 管束)全量纳入配置了 HR 的站点的所有种子; 做种早已超额的老种直接跳过不打标。

§1

现状诊断:「未核实」桶里装的都是谁

「未核实(本地不触发)」由 resolve.safety_display 派生:站点侧无个体证据(判定落「无站点证据」身份) 且 check_hr_condition() 为 False。而 check_hr_condition 在无站点证据时是「先问达标、再问本地下载触发」的混合体 (torrents/record.py 的 check_hr_condition / check_hr_satisfied),于是三种互不相干的人落进了同一个桶:

桶里的人怎么进来的实际语义
转移种 / 纯辅种(downloaded=0 或部分下载) 本地下载条件不满足 → 「未触发」;站点侧从未把它列进任何清单(没下载过的种子不会进考察名单)→ 无证据。 两头都没话说。不代表无义务 —— 转移种子在原机可能正在考察期。
做种已满的种子(含超额线 3× 老种) 无站点证据路径下「达标 ⇒ check_hr_condition 返回 False ⇒ 未触发」—— 达标反而显示「未核实」。 义务早已了结,却挂着「未核实」的灰档 —— 最误导的一格。超额老种被取数侧排除在对账对象集外(hr/service.py 的对象集现算),永远拿不到放行记录,只能常驻此桶。
刚加的新种(新鲜度闸门内) 种子 added_on 晚于该档本波取数时刻 → 本波缺席证明不成立 → 无证据(hr/service.py 的缺席证明)。 过渡态,下一健康波自愈。桶是稳态的,这批人不是。

四个消费点全部走 check_hr_condition / check_hr_satisfied 单点(HR 打标 core/mixins/tags.py、 规则条件 rules/conditions.py、表达式 rules/expr/env.py、WebUI webui/views.py), 所以语义必须在判定层一次改对,而不是在消费点各自打补丁。

§2

术语约定与目标模型

本文与后续实现一律用业务词称呼站点侧结论;代码标识符(函数 / 常量名)保留原名。

业务词含义
考察中站点在线清单命中、义务进行中 —— 站点绝对权威,管束。
毕业达标站点确认达标并移出清单 —— 终态放行。
未达标终态考核期结束仍未达标,结论已定 —— 终态放行(删除安全档是独立红档,不是管束)。
免罪站点豁免 —— 终态放行。
放行记录「覆盖范围内未列出 / 免罪」在案的永续本地记录 —— 放行。
无站点证据站点侧对这颗种子没有任何个体记录 —— 交由本地判据兜底。
未接入站点未配置在线核实(或全站型不取数),判定桥返回空 —— 走本地判据。
本地触发本机下载条件满足(下载比例 / 下载量达线,或下载量覆盖全种)。
疑似辅种本地未触发 —— 转移种 / 纯辅种常态,downloaded 丢失不代表无义务。
超额本机做种时长 ≥ 3× 该站点做种要求基准(与取数侧对象集排除线同源)。

目标模型三句话

  • 「触发」降级为展示辅助:check_hr_condition 只回答「本机下载条件满足吗」,唯一消费点是前端在未达标种子里区分「本机下载」与「疑似辅种」。管理语义不再消费它。
  • 后端全量纳入:配置了 HR 的站点,所有种子(含 downloaded=0)要么「义务已了」(check_hr_satisfied)要么「需管束」(打 HR 标签)。不再有「不触发 ⇒ 不管理」的早退。
  • 超额老种跳过打标:站点侧未命中考察中时,做种 ≥ 3× 基准的种子不打任何标签 —— 义务早已了结,打卡无信息量。

目标状态矩阵

站点侧本地状态展示(删除安全档)打标管束
考察中任何(含超额)在线·考察中(danger 橙)HR 标签管(站点权威)
毕业达标任何在线·已达标(safe 绿)不打放
未达标终态任何在线·未达标·终态(failed 红)不打放(终态)
免罪 / 放行记录任何在线·已核实(safe 绿)不打放
无证据 / 未接入做种 ≥ 3× 基准(超额)本地·达标(safe 绿)跳过,不打放
无证据 / 未接入做种满 req+extra本地·达标(safe 绿)达标标签放
无证据 / 未接入未满 + 本地触发本地·未达标(danger 橙)HR 标签管
无证据 / 未接入未满 + 未触发本地·未达标(疑似辅种)(warning 黄)HR 标签管
RATIONALE

「疑似辅种」给 warning 而非 danger(2026-09-30 用户拍板):它可能有义务也可能早已在原机完成,本机无法分辨 —— 黄色警示「注意」比红色「删了吃 H&R」诚实。删除流程的「不能删」点名集合只含 danger(delete_flow.js 的 HR_NO_DELETE),warning 天然不拦删除,行为与语义一致,该文件只需同步注释。

§3

判定层变更(record.py 三方法)

check_hr_condition → 纯本地触发判据(展示辅助)

方法体简化为:配置了 hr 且未命中排除表时,返回纯本地下载触发判据(现 _local_hr_triggered 原样保留)。 四行判定表的混合短路逻辑(考察中恒 True / 放行恒 False / 无证据先问达标)全部删除。docstring 明确: 管理语义(打标 / 规则 / 表达式)不得再消费本方法。

check_hr_satisfied → 义务已了的单点

唯一实质变更:删掉「本地未触发 ⇒ 未达标」的前置(check_hr_satisfied 尾部对 _local_hr_triggered 的门)。 无站点证据 / 未接入路径的达标判据变为:

seeding_ok = seeding_time >= (required_seeding_time + extra_seeding_time)
ratio_ok  = required_share_ratio > 0 and ratio >= required_share_ratio
satisfied = seeding_ok or ratio_ok   # ratio 通道保留(独立功能, 不搭车移除)

站点侧结论分支全部不变:考察中恒未达标(义务在);毕业达标 / 免罪恒达标;未达标终态恒未达标; 放行记录(站点没给达标结论)维持「本地判据说了算」—— 本就无触发门,不动。 原方法尾部为修递归而写的注释与防递归结构随前置删除一并简化(check_hr_condition 不再调用 check_hr_satisfied,递归风险源消失)。

新增 hr_managed →「需管束」单点

打标分流、规则、表达式共用的管理语义。放行类结论即使本地未做够也不许管束,所以不能写成 not check_hr_satisfied() —— 必须显式先排除放行:

def hr_managed(self) -> bool:
    # 需按 HR 管束: 考察中, 或 (无站点证据/未接入 且 未达标)
    if not self.tracker_conf.hr or self.hr_excluded(): return False
    judged = self.hr_judgement()
    if judged is None:   return not self.check_hr_satisfied()   # 未接入
    if 考察中:           return True
    if 放行(终态/记录):  return False
    return not self.check_hr_satisfied()                       # 无站点证据
§4

打标层变更(tags.py)

_add_hr_tag_or_category 的门禁从「check_hr_condition 不过就早退」改为放行短路 + 超额跳过 + satisfied 分流:

if hr is None or rec.hr_excluded(): return False
judged = rec.hr_judgement()
if judged is not None and 放行(judged):
    return False                 # 毕业/终态/免罪/放行记录: 不打标(维持现状)
if rec.seeding_time >= 3 * 基准(rec) and not (judged is not None and 考察中(judged)):
    return False                 # 超额老种跳过; 被动命中考察中仍打 HR 标签(站点权威)
if rec.check_hr_satisfied():
    打达标标签/分类               # 含转移种做种满 —— 义务已了
else:
    打 HR 标签/分类               # 含疑似辅种未满 —— 全量纳入(2026-09-30 拍板)

超额基准的配置源(拍板点 3 的落地)

两个配置各自独立:hr.required_seeding_time(本地要求,int 秒)与 hr_check.required_seeding_time(在线核实的站点档案预设,float 秒,由 config/site_presets.py 填充)。 取数侧对象集排除线用的是后者。打标跳过与取数侧同源:

  • 已接入站点(hr_check 存在且启用):基准 = hr_check.required_seeding_time —— 与取数侧同源,同一颗种子不出现「取数跳过但打标不跳」的劈叉;
  • 未接入站点(hr_check 为空):基准 = hr.required_seeding_time;
  • 基准 ≤ 0 时跳过线不生效(与取数侧 required_seeding_time > 0 前提一致)。

实现时抽一个小函数(如 _seed_exempt_baseline(rec))承载上述分支,禁止两处各写一份判据。

明确不变项(防实现走样)

  • 站点权威不动:考察中管束(含超额种子被动命中仍管束)、终态放行、放行记录永续 —— 判定收口(26-09-28-1932)的既有原则原样保留,本计划不碰 hr/resolve.py 的身份判定与 hr/service.py 的取数 / 签发链路。
  • 排除表优先级不动:命中排除表恒不纳入(打标 / 规则 / 表达式 / 展示全空),排除短路保留在所有入口顶部。
  • 取数侧对象集与新鲜度闸门不动:超额排除、缺席证明、放行签发 —— 「疑似辅种 warning 是过渡态」靠的就是这条链路把它们收编成「在线·已核实」。
  • 零配置变更:不新增 / 修改任何配置键,validate_config 与 config/schema.py 无需触碰。
  • 打标是加法:已在种子上的历史标签不回撤(与排除表既有口径一致);旧「未核实」种子在下一轮维护时按新语义重新分流。

§9

风险与迁移影响

风险评估与对策
标签铺面 配置了 HR 的站点全部种子进入打标分流(未满 → HR 标签,满 → 达标标签,超额跳过)。纯辅种大户的标签量会显著上升 —— 用户已拍板接受(2026-09-30),这是「全量纳入」的直接体现。
规则语义漂移 tor.hr_condition_met 与规则 condition-met 含义变化。存量规则/表达式无法静态识别,落地后交付「迁移提示」:旧「本机下载判别」用途改用 tor.hr_local_triggered。
疑似辅种 warning 的持续时长 已接入站点:过渡态 —— 转移种在对账对象集内,健康波签发「未列出」放行后转「在线·已核实」。未接入站点:无站点证据可救,warning 持续到本机做种满 req+extra —— 保守代价,已拍板。
未达标管束的误伤面 部分下载未达线的种子从「不管」变「管束打标」(做种满即自动放行,不会永久管束)。方向保守,漏管代价大于误管。
前端旧 token 残留 浏览器缓存的旧页面可能短暂收到 warning 而无对应样式 —— 映射表缺项时无类名(灰底),可接受;不强推缓存失效。
