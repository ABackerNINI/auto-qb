WEBUI 主表横向滚动条隐藏与底部紧凑指示条

把横向滚动条从表格容器里彻底拿掉，换成一个只在「伸手够底部」时才淡入、且只占 160px 宽的悬浮指示条 —— 少种子时横在屏幕中部的那条粗线消失，横向滚动的可达性不降。

doc-added 26-11-01-0553 · doc-updated 26-11-01-0633 · doc-status Done · 载体 单文件 HTML(dark)
来源 用户报障「只有几个种子时横向滚动条出现在中间，很显眼也很丑」→ 一轮 grilling（6 轮问答、11 项拍板，见 §06）

§01目标与设计原则

要解决的问题

主表（种子 / 辅种 / 追剧）列宽超出视口时，横向滚动条画在 .group-table 容器的底边上；而该容器的高度等于内容高度 ⇒ 只有几个种子时，这条 10px 粗的横线横在视口正中，读作一条与内容毫无关系的噪声带。用户原话：「在只有几个种子时横向滚动条出现在中间很显眼也很丑」。

设计主轴

不在「把原生条调得好看一点」上做文章，而是把横条从容器里拿走：原生条彻底隐藏，另给一个悬浮在状态栏上缘的紧凑指示条，只在指针伸到内容区底缘时淡入。判断依据是 §02 的几何推导 —— 原生条在长列表下也藏在整页最底部，本来就不是一个可用控件，为它保留条件分支等于给一个死控件付监听器与列宽抖动的代价。

不变量（违反即方案作废）

  1. 表格几何链路不动：.layout / .torrents-dock / .group-table 三者的高度关系保持现状 —— 行窗口（columns.js 的 _winViewH）、吸底面板、吸顶表头的前提全挂在这条链上。任何「撑高容器把条推走」的做法都在动这条链，故否。
  2. 只动 .group-table 的横条：页面竖滚动条、.status-strip 窄屏横条、.drawer-body 等一律不碰。
  3. 可达性不降：Shift+滚轮 / 触控板双指 / 触摸屏横滚保持原样，并新增一个「热区召唤 + 可拖」的入口（今天纯鼠标用户没有拖拽入口）。
  4. 单点：隐藏规则一处（shared/hscroll.css）、横滚同步一处（syncHeadScroll）、指示条逻辑一处（columns.js）。不许在别处再写第二份。
  5. 保守默认：不给任何「可横滚」提示（无右缘渐隐、无一次性引导），常态下指示条完全不可见。

算成什么样

  • 少种子 + 列溢出时，视口中部没有任何滚动条痕迹，且 offsetHeight - clientHeight === 0（无条槽）。
  • 指针伸到内容区底部 24px 带内，出现一条 3px 胶囊；拖动它，表格真的横滚，表头 --head-pin-x 与 .is-hscrolled 首列提示同步跟随。
  • 三皮肤（prism / atlas / console）行为一致，静态守阵与 e2e 双绿。

§02现状与痛点

几何：横条为什么会在屏幕中部

环节事实出处
横条挂在谁身上.group-table { overflow-x: auto }，原生横条画在容器底边prism css/views.css:149 · atlas css/components.css:211 · console css/components.css:199
容器高度由谁定.torrents-dock 是 flex column，.group-table 是 flex: 1 1 auto —— 但没有自由空间可占prism css/dialogs.css:404-405 · atlas css/dialogs.css:16-17 · console css/dialogs.css:10-11
自由空间去哪了.layout { align-items: start } ⇒ .content 不被拉伸，高度 = 内容高度prism css/views.css:48-50 · atlas/console css/components.css:143-145
条的尺寸与配色*::-webkit-scrollbar { height: 10px }，thumb 取 --border-strongprism css/base.css:14-19 · atlas style.css:166-171 · console style.css:147-152
三个滚动容器三主表共用 .group-table，各自接 @scroll="syncHeadScroll($event, '<page>')"shared/tpl/groups.html:18 · torrents.html:4 · shows.html:5

把前四行连起来：容器高 = 内容高 ⇒ 横条永远画在「最后一行下方」。于是同一条控件在两种场景下表现完全不同：

  • 只有几个种子：容器底边就在视口上半部 ⇒ 横条横在屏幕中部，与内容无关，最刺眼（本次报障场景）。
  • 种子很多：容器底边 = 整页最底部 ⇒ 横条要滚到列表末尾才看得见，实际上不是可用控件。
这条推导是「彻底隐藏」而非「条件隐藏 / 撑高推走」的根据：长列表下它本来就没用，保留条件分支只是为一个几乎不出现的控件付监听器与 10px 列宽抖动的代价。

今天能怎么横滚

  • Shift+滚轮 / 触控板双指 / 触摸屏 —— 浏览器原生，无需接线。
  • 拖拽 —— 全仓没有实现：scrollLeft 只有读取（columns.js:61-71 的 syncHeadScroll），唯一写入是 drawer_templates.js:185 的程序化跳转。
  • Shift 键本身已被区间选择占用（selection.js 六处 shiftKey 判断）⇒ 不能拿它当「显示指示条」的修饰键。

同款缺陷的旁支

.group-table 不止主表：抽屉表引擎 shared/tpl/xtpl.html:359 也挂它，同样吃 overflow-x: auto，抽屉里也会出现「条贴在最后一行下方」的同款观感。本方案把隐藏规则覆盖到所有 .group-table（一个选择器），但指示条只给主表三视图（见 D4 / R5）。

§03方案总览

两半：A 隐藏（纯 CSS，覆盖所有 .group-table）+ B 替代（底部紧凑指示条，只给主表三视图）。A 单独成立（隐藏本身就是用户要的），B 是为补回「拖拽」这个唯一会丢的能力。

A · 隐藏原生横条（新文件 shared/hscroll.css）

/* 三皮肤共用, link 排在皮肤 views.css 之后(级联序同 row_lang.css)
.group-table { scrollbar-width: none; }             /* Firefox */
.group-table::-webkit-scrollbar { display: none; }  /* Chromium / WebKit */

为什么放共享层而不是三份 views.css：三皮肤 index.html 的 /shared/*.css 链接集逐字相同（守阵 test_frontend_template_split_wiring 钉清单一致），新增共享文件仍是三份 HTML 各加一行，但规则本体只有一份，不会像三份 views.css 那样日后各自漂移。shared/row_lang.css 就是现成先例（结构/行为类规则放共享层，link 排在皮肤 views.css 之后靠级联序赢）。

为什么要 display: none 而不只写 scrollbar-width：全局 *::-webkit-scrollbar { height: 10px } 仍在，Chromium 系靠后者决定是否绘制；元素级 .group-table::-webkit-scrollbar 特异性 (0,1,1) 压过 *::-webkit-scrollbar (0,0,1)，不依赖书写顺序。

隐藏后 .group-table 不再产生纵向溢出（容器高度由内容驱动，结构性无竖向滚动），所以整条隐藏不会误伤竖条。

B · 底部紧凑指示条

参数取值理由
横向位置left: 50%; transform: translateX(-50%)居中对称，位置不暗示任何内容几何；右对齐会撞状态栏右侧的速度/限速区，左对齐易被读成行内进度条
轨道宽width: min(160px, 42vw)1440 宽下约占 11%，「精致小巧」的量级；小屏由 42vw 兜底不撑破
纵向位置bottom: calc(var(--statusbar-h) + 6px)贴内容区底缘、不压状态栏的 1px 分界线；高度走令牌不写死 34px
高度 / 圆角静息 3px → hover·拖拽 4px；border-radius: 999px细到几乎不占视觉重量；交互时给一点物理反馈
配色底 --border-strong；hover·拖拽 --fg-dim与原生 thumb 同源令牌；令牌名集三皮肤相等（守阵 test_frontend_skin_css_token_parity），共享层可安全引用
滑块宽max(32px, 轨道宽 × clientWidth / scrollWidth)32px 是「抓得住」的下限
滑块位移(scrollLeft / (scrollWidth - clientWidth)) × (轨道宽 - 滑块宽)标准映射，两端严格对齐
触发带clientY ≥ innerHeight - 状态栏高 - 24内容区最底部 24px，不含状态栏（状态栏是常用控件区，不该召唤滚动条）
淡入 / 淡出150ms / 200ms，无停留定时器掠过时淡入没走完就离开，观感几乎不可见；不加定时器是给一个已经很低的风险付复杂度
交互拖动改 scrollLeft；点轨道跳转；拖动期间不淡出；user-select: none既然替代原生条，就得承担原生条的交互；否则用户本能去拖却拖不动
z-index25低于状态栏 30、列拖虚影 120；高于行
覆盖范围仅当前可见主表（三视图 v-if 互斥，同时最多一个）抽屉面不配指示条，见 R5

§04实施步骤

#内容验收判据
S1 新建 shared/hscroll.css：两条隐藏声明 + 指示条样式（.hscroll-pill / .hscroll-pill.on / .hscroll-pill.drag）。样式只用令牌，不写死颜色；不出现 emoji / 图形符号。 文件存在；含 scrollbar-width: none 与 ::-webkit-scrollbar + display: none；指示条规则齐全
S2 三皮肤 index.html 各加 <link rel="stylesheet" href="/shared/hscroll.css">，位置紧随 /shared/row_lang.css 之后（prism 约 :21 / atlas :14 / console :17）。 三份 /shared/*.css 链接集仍逐字相同；test_frontend_template_split_wiring 绿
S3 columns.js 接线：①惰性创建单例 .hscroll-pill 挂 body；②syncHeadScroll 尾部调 _hscrollSync(ev.target) 更新几何；③document 上挂一个 mousemove，只做一次 clientY 比较、状态变化才切 class；④pointerdown/move/up 实现拖动与点轨道跳转；⑤ResizeObserver（照 columns.js:186-206 的 _headObs 范式）+ 列应用路径触发重算（可见列/列宽变化时 scrollWidth 会变而 ResizeObserver 观察不到）。 热区外指示条 opacity: 0 且 pointer-events: none；热区内淡入；拖动后 scrollLeft 变化且表头 --head-pin-x 同步；无横滚余量时不出现
S4 静态守阵：tests/test_webui_static_skins.py 新增一条，钉三皮肤 HTML 都挂了 hscroll.css、该文件含两条隐藏声明、columns.js 里 _hscrollSync 接线锚点在位、syncHeadScroll 仍带 is-hscrolled 打标（既有守阵不回归）。 新测试红绿双验：删掉任一皮肤 link 即红、删掉 display: none 即红
S5 e2e（桩服务 + 真浏览器）：窄窗触发列溢出后断言 —— ①offsetHeight - clientHeight === 0（无条槽）；②scrollWidth > clientWidth（仍可横滚）；③鼠标移入内容区底部 24px 带后胶囊 opacity 非 0；④拖动后 scrollLeft 变化且表头 --head-pin-x 同值。 4 条全绿；宽窗（无溢出）时胶囊永不出现
S6 回写：memory-bank/conventions/webui.md 或 pitfalls/web-ui/ 记一条「.group-table 横条几何 + 隐藏口径」；计划状态 Open → In Progress → Done；按收尾 DoD 跑 commands run test.full 并新建基线切片。 commands run kb.docmap --check 绿；基线切片记实测数字

§07风险与对策

#风险 / 触发条件处置
R1热区 mousemove 落在热路径上（每次移动都触发）处理体只做一次 clientY 比较、不读布局属性；状态不变不写 DOM（class 切换才是唯一副作用）
R2拖动改 scrollLeft 后表头不同步程序化改 scrollLeft 同样会触发 scroll 事件 ⇒ syncHeadScroll 照常跑；S5 ④ 用真浏览器钉死（不能只信推断）
R3160px 轨道映射到数千 px 内容，拖动精度粗（1px ≈ N px）接受：这是「粗调 + 可达」的控件，精调走 Shift+滚轮；点轨道跳转覆盖大跨度移动
R4隐藏原生条后 clientWidth 多出 10px，列宽/溢出判定变化隐藏是静态生效（不做运行时切换）⇒ 无跳动；列宽由列模型重算，不缓存旧值。S5 宽窗用例确认「不溢出时不出条」
R5抽屉变体面隐藏了原生条却没有指示条 ⇒ 该处横滚无可见入口抽屉列集窄、横滚罕见；若用户报障，按 D4 扩展指示条到抽屉面（届时需处理多实例同屏），本轮不赌
R6三份 index.html 的 link/manifest 漂移守阵 test_frontend_template_split_wiring 已钉清单一致；本次新增 link 必须三份同轮加，S4 再补一条显式钉 hscroll.css
R7状态栏高度变化（--statusbar-h 非 34px）导致指示条压线或悬空bottom 与热区判定都读令牌/实测高度，不写死 34
R8与吸顶表头（z-index 5）、列拖虚影（120）、状态栏（30）层级打架25 已排在状态栏之下、虚影之上；若与抽屉/弹层冲突，弹层均高于 30，不受影响
R9热区与「点击最后一行下缘」重叠，误召3px 细线 + 150ms 淡入 ⇒ 掠过几乎不可见；指示条仅在可见时 pointer-events: auto，不拦行点击
R10触屏设备无 hover 语义，热区无从触发热区监听只在 pointer: fine 下挂；触摸横滚本就原生可用，不退化
