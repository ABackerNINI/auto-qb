01

背景与拍板反转

本件是详情面板重构的一个被划出范围的备选案，现在被单独认领。

详情面板重构计划 memory-bank/plans/26-10-06-0838-plan-webui-detail-panel-redesign.html §06 拍板点 P-02 原文（取证 2026-10-07 01:49）:

P-02 | 06 的逐 tracker 汇报倒计时数据缺 per-tracker 口径
     | 推荐: 以 detail.reannounce_in 全局值近似展示, 行内标「全局」; 不加端点
     | 备选: 省略倒计时列(信息增量少一块); 或后端加端点(超范围)

当时拍板（2026-10-06）取推荐案: 06 变体每行「下次汇报」列显示同一个 detail.reannounce_in 全局值并标「全局」，微条比例 = reannounce_in / reannounce； 「后端加端点」被划出本次重构范围。本件即该备选案，2026-10-09 用户显式指派认领。

触发条件: 用户在 06 变体看某行 tracker 的汇报倒计时时，多 tracker 种子上全局值与各 tracker 真值偏差可见（纯增强，无缺陷面）。严重度: 低（信息精度增强）。

本计划的产出目标

把 06 变体的逐行汇报倒计时从「全局近似」换成真 per-tracker 口径（各 tracker 自己的 next_announce），去掉行内「全局」标，并为不暴露该字段的低版本 qB 保留可判定的降级口径。 范围以 §02 取证结论为准。

03

方案设计

数据来源 / 时钟口径 / 微条比例 / 刷新粒度 / 降级 —— 各维度先给判据，具体取舍见 §04。

3.1 数据来源与逐行判定 next_announce

每行 tracker 用行级 t.next_announce（epoch 秒）算剩余: remaining = next_announce - now；格式化沿用现有 ctx.fmtDuration。逐行判定:

  • 真口径行（含 next_announce 键，qB 5.2+）: 显示该行自己的剩余时间，去掉「全局」标。
  • 虚拟行（DHT/PeX/LSD）与未启用行: 恒「—」（不变）。
  • 更新中行（status=3）: 沿用「正在汇报」（此时 qB 把 next_announce 置为 now，剩余≈0，不必特判也可，但保持现状语义更稳）。
  • legacy 行（不含该键，qB < 5.2）: 回退 §3.5 降级口径。

版本探测逐行按键存在性判，与后端 _trackers_baseline 的 epoch_mode 同一判据 —— 不得凭 qB 版本号或「秒/毫秒」式臆测。

3.2 时钟口径 epoch − now

next_announce 是 qB 主机的 epoch 绝对秒；前端相减用本机 epoch （Date.now()/1000，或既有响应式 this.nowSec，format.js:64/lifecycle.js:174， 每 30s 一跳）。单机 / 局域网场景浏览器与 qB 时钟通常已由系统 NTP 对齐，偏差可忽略。 若要求更强健（跨机、时钟漂移），可选后端随响应下发 server epoch 供前端算偏移（P-02）。

硬约束（不得回潮）: next_announce 是 epoch 绝对时间，不是倒计时 —— 必须先减 now 再格式化。把它直接当剩余秒数是 commands.py 已记录的事故根因 （_verdict_reannounce docstring: 「不得把 epoch 当倒计时用」）。

3.3 微条比例 分母不可得

qB 只给 next_announce / min_announce，不给 per-tracker 的 announce interval； 故「剩余 / 周期」的真 per-tracker 分母不存在。当前全局近似用的分母是种子级 detail.reannounce （反映的是当前活跃 tracker 的周期），用它当所有行的分母只有活跃行近似正确。取舍见 P-03。

3.4 刷新粒度 5s vs 1s

现状是 5s 轮询刷新（显示粒度 = 轮询粒度，非逐秒）。设计稿 resources/detail-panel-templates/06-trackers-table-collapsed.html 标注「倒计时微条(逐秒走)」， 但那是演示稿的模拟。若要逐秒走需加本地 1s ticker（变体已有 destroy() 钩子，重构计划亦记 「定时器(如 06 倒计时)必清」）。取舍见 P-04。

3.5 降级 qB < 5.2

低版本 qB 无 next_announce：保留现状路径作为 fallback 分支 —— 逐行同一全局值 + 「全局」标 + 种子级微条。即「现状代码」不退场，只是不再是 qB 5.2+ 下的默认分支。取舍见 P-05。

04

拍板点清单

每点给推荐案与备选；拍板后 doc-status 转 In Progress 并开工。

编号问题推荐案备选
P-01 后端是否改动 推荐 纯前端 —— 数据已在既有透传里，后端零改动（零新增 qB 调用，天然满足「5s 轮询负载不得加频」）。 后端加派生相对字段 next_announce_in（须处理 2s 读缓存与「相对值过期」的矛盾: 缓存命中时相对值已陈旧，需绕过缓存或改下发 server epoch）。
P-02 时钟口径 推荐 前端用本机 epoch 与 qB epoch 相减（单机/局域网已对齐，零协议改动）。 后端随响应下发 server epoch，前端算一次偏移再倒计时（更强健，但改响应形状）。
P-03 微条比例（per-tracker interval 不可得） 推荐 per-tracker 模式去掉微条（分母不存在，不造假数据）—— 与文件头「不造 per-tracker 假数据」原则一致。 A: 用种子级 detail.reannounce 作分母近似 + tooltip 明标「比例以种子级周期为分母」；B: 仅当该种子只有一个 real tracker 时显示微条。
P-04 刷新粒度 推荐 沿用 5s 轮询粒度（与现状一致，零新增负载，无定时器）。 本地 1s ticker 逐秒走（更贴设计稿；须在 destroy() 清定时器并加守阵）。
P-05 低版本（qB < 5.2）回退 推荐 保留全局近似（现状即 fallback，行为可预期、信息不丢）。 直接隐藏该列（更「干净」但信息更少，且与设计稿版式不符）。

若全取推荐案: 后端零改动；前端把 nextHtml 改为读行级 next_announce、 去「全局」标、去微条，保留 legacy 分支；工作量落在 S1 + S3。

06

验收与守阵

全部可判定，不靠人眼「看起来对」。

  • ✓ 多 tracker 种子: 各行「下次汇报」互不相同，且与 qB GUI「下一个 announce」逐行一致（真机抽查，容差 = 轮询粒度）。
  • ✓ 行内不再出现「全局」标（qB 5.2+ 路径）；legacy 路径仍带「全局」标（P-05 推荐案）。
  • ✓ 虚拟行 / 未启用行「—」；更新中行「正在汇报」；空态 / 失败态行为不变。
  • ✓ 无新增 qB 调用（5s 轮询次数不变；P-01 推荐案下天然成立）。
  • ✓ 换种子 / 关面板无残留定时器（若 P-04 取 1s ticker）。
  • ✓ test.full 全绿，基线切片记实测数字。
07

风险与坑

按动作选类，指向 memory-bank/pitfalls/ 相关主题。

风险判据 / 处置
epoch 当倒计时用next_announce 是 epoch 绝对秒 —— 必须先减 now。事故根因见 commands.py::_verdict_reannounce docstring（「不得回潮」）。
时钟偏差跨机 / 未 NTP 对齐时本机 epoch 与 qB epoch 有偏差 → 倒计时整体偏移。单机/局域网可接受；否则走 P-02 备选。
2s 读缓存/trackers 走 RoCache（TTL 2s）。epoch 值缓存安全（绝对时间不因缓存而错）；但若改后端下发相对值，缓存会让相对值陈旧 —— 这是推荐 P-01「纯前端」的关键理由。
变体 sig 跳过重建render() 靠序列化 sig 跳过重建；换真口径后 sig 必须含逐行 next_announce，否则倒计时不刷新（坑档 pitfalls/web-ui/template-render.md 的 _dtNotify 变体通知族）。
定时器残留若 P-04 取 1s ticker，destroy() 必须清（重构计划 :234 已记「定时器(如 06 倒计时)必清」）。
版本判定靠猜不得凭版本号判字段有无 —— 按「行含 next_announce 键」逐行判（与后端 epoch_mode 同判据）。
桩保真桩（FakeClient.torrents_trackers / ui_harness）默认返回不含 next_announce，e2e 若不补会走 legacy 分支 → 假绿。S3 必须补桩。
