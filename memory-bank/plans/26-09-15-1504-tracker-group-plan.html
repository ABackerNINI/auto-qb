01

需求与边界

需求原文 (想法.md 待办): 「支持给 tracker 分组, 规则筛选器可以按分组过滤」。拆开是两件事: 站点配置能声明分组; 规则条件能按分组匹配种子。

名词澄清 —— 两种"分组"

本任务的分组是站点层概念: 给 tracker 配置归类, 纯配置维度, 不写种子、不加标签。与 grouping 段的「辅种种子分组」(相同文件列表的种子归组, 种子层) 完全无关。这也正是它和站点 tags 的区别 —— tags 会写入 qB 种子, 分组只活在配置里, 供规则筛选与后续视图使用。

本期不做

  • 条件取反 (!) —— 独立待办, 将来统一解决; tracker_group 只做正匹配
  • 辅种管理页按组筛选 —— 列为阶段 3 可选项, 待确认 (D4)
  • 分组到种子的任何写操作 —— 分组不落种子
  • exporter 模板 —— 导出的是未配置站点骨架, 无分组概念
02

配置形态 (推荐方案 B)

推荐在站点段直接声明分组 (D1 详见 03 节)。形态如下:

# config.trackers 每个站点新增可选键 groups (字符串列表)
trackers:
  HDSky:
    domains: [hdsky.et]
    groups: [国内, 影视]
  MTeam:
    domains: [kp.m-team.cc]
    groups: [国内]
  BTN:
    domains: [broadcasthe.net]
    groups: [国外, 影视]

# 规则条件: 种子的 tracker 所属组 任一命中 即匹配
example_rules.by_group:
  conditions:
    tracker_group: [国内]        # 或关系; 同 trackers/category, 支持 regex: 与 :ignore_case
    state: [is_complete]
  actions:
    add_tags: [done]

语义要点

  • groups 缺省 = 未分组, 不匹配 tracker_group 条件, 其余一切行为不变 (完全向后兼容)
  • 一个站点可属多个组; 组名是自由文本 (建议 2-6 字), 不需要预先定义
  • 分组是声明不是引用 —— 没有"组定义段", 因此不存在引用悬空类错误
  • 条件与站点名无关: 改站点配置名不影响分组; 换站点域名也不影响
03

设计决策

D1组定义放哪 —— 站点字段 (推荐) vs 顶层组段

维度方案 B · 站点字段 groups 推荐方案 A · 顶层段 tracker_groups
形态 每个站点自带 groups: [国内] tracker_groups: {国内: [HDSky]}, 组名 → 站点名列表
错误面 组名即声明, 不存在引用悬空; 条件里组名拼错不可静态校验 (与 tags/trackers 条件一致) 组内站点名引用可 fail-fast 校验 (唯一硬优势); 条件里组名拼错同样不可校验
Web UI 成本 TRACKER_FIELDS 加一个 str_list 字段, 现有站点编辑器自动渲染, 前端零改动 需新做「动态字典 → 站点多选」编辑器 (index.html + config_editor.js + style.css)
后端负载 集中在既有扩展点: load_tracker_config 一行 _get、KNOWN_TRACKER_KEYS +1、schema Field +1 新顶层段: 根级键 +1、独立校验函数、加载回填、schema 专段登记
组一览 YAML 层无集中视图; 阶段 2 可做反向聚合 (按组列出站点) YAML 层天然集中一览
站点改名 组随站点走, 无需同步 需同步改组段 (有校验兜底)

推荐 B。决定性理由: A 的校验优势面对的是 B 根本不存在的错误面; 而两方案共同的盲区 (条件里组名拼错) 都查不出来。B 的改动面、UI 成本、语义直给性全面占优, 且阶段 1 即端到端可用。

D2条件命名 —— tracker_group

推荐 tracker_group (单数): 与 category 同为「属性匹配」风格, spec 列表为或关系; 站点字段名 groups, 条件名 tracker_group, 在规则 YAML 里读作「tracker 分组 ∈ […]」。备选 tracker_groups (与 trackers 复数对仗), 语义无差, 二选一即可。

D3匹配语义边界

  • 正匹配 only, 无「不属于某组」语法 —— 取反归入条件取反待办统一解决
  • 组名匹配走 utils.match_value, 与全项目一致, regex: / :ignore_case 免费获得
  • 种子无 tracker_conf (未匹配任何站点配置) → 条件恒 False, 与 trackers 条件同构
  • 条件内多个组名为或关系; 组内成员无「与」需求 (站点可属多组已覆盖)

D4交付分期

阶段 1 后端端到端 (YAML 直改即可用, 设置页借 str_list 自动渲染也能编辑保存); 阶段 2 设置页增强 (可选); 阶段 3 辅种管理页按组筛选 (可选, 待确认)。

05

校验与 fail-fast

全部进 validate_config 聚合报错, 每条带配置路径, 风格与既有站点段校验一致:

  • groups 若配置: 必须为列表 —— config.trackers.X.groups: 必须是列表
  • 每项须非空字符串 (BaseLoader 下 key: 留空得空串, 视为手滑, 报错)
  • 组名不做存在性/唯一性校验 —— 自由声明语义, 组名没有单一来源
  • 条件 spec: tracker_group 经 _validate_pattern_list_spec, regex: 主体须可编译
  • schema 登记 Field + Plugin 后, test_config_schema.py 守卫自动核对键集合与插件表 (漏登记直接红)
注意: 黄金法则「新配置键必须加入 validate_config 并同步 config/schema.py」—— 本任务两个面 (站点字段 + 条件插件) 都有对应守卫, 守卫测试是最后防线。

08

风险与核实点

  • 热重载级别 (首要核实, S0) —— TRACKER_FIELD_LEVELS 里 groups 列 L0 (与 tags 同, 运行时动态读) 还是 L2 (绑定固化), 取决于 TorrentRecord.tracker_conf 在热重载后的重绑定机制。拿不准列 L2: 保守正确, 代价仅是改组后重建任务队列 + 全量重匹配 tracker, 可接受。
  • 双"分组"心智 —— 站点分组 (本任务) vs 辅种种子分组 (grouping 段)。文档与 UI 文案统一用「站点分组」字样, 帮助文本里点名区别。
  • 组名拼错静默失效 —— 条件里组名拼错不可静态校验 (与 tags/trackers 条件一致的盲区); 靠阶段 2 下拉候选缓解, 帮助文本提示。
  • BaseLoader 字符串语义 —— groups 列表项全为字符串, 与既有 str_list 处理一致, 无数字/布尔歧义; 空串校验挡手滑。
