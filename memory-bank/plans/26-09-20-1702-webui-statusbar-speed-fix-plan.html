WEBUI 状态栏速度恒为 0
修复计划

状态栏的上传/下载速度不是没算，是算错了地方：它在前端对 groups 求和，而「按视图回传」在种子页根本不回 groups。 本计划把合计搬回服务端并恒回传，让状态栏不再依赖任何一个视图的数组是否回传。

01

结论先行

主因（恒为 0）：状态栏数值 = 前端 totalDl / totalUl，两者都是对 this.groups 求和 （shared/decorate.js:136-141）。而 P1-1「按视图回传」把 groups 从种子页的响应里裁掉了 —— VIEW_ARRAYS["torrent"] = ("torrents",)。种子页上 groups 键一次都不会出现， 前端按「键不存在则保留原引用」赋值，于是它永远停在初始值 [] ⇒ 合计恒为 0。

次因（严重偏低）：合计只遍历 groups，漏掉未归组种子 singles。 同一文件里的 totalTorrents() 却写了 groups + singles + torrents 三份兜底 —— 两者口径不对称。 桩服务实测（50 组 + 200 未归组）：显示 1.64 MiB/s，真值 14.5 MiB/s，少算 88.7%。

修法：服务端在 /api/state 的 status 块里恒回传 totals = {dlspeed, upspeed} （对全量种子求和），与 traffic / server 同口径 —— 不参与视图分片、不参与 rid 门控； 前端 totalDl / totalUl 改读 status.totals。一次修掉主因与次因。

为什么不是"补回 groups"

把 groups 加进 VIEW_ARRAYS["torrent"] 能修好状态栏，但会直接废掉 P1-1 的成果： 种子页响应体从 4.52MB 回到 6.41MB（3000 种子实测），且现有守阵 test_api_state_view_scoped_payload 明确断言 "groups" not in t。 状态栏要的只是两个数字，不该为它回传一整张表。

02

复验：怎么证实的

静态阅读只能给出假设，所以起真 create_app + 合成种子的桩服务直接量。 （取证 2026-09-20 17:0x，合成种子自带非零 dlspeed/upspeed）

# 起桩: 300 种子 / 150 组
uv run python scripts/ui_harness.py --torrents 300 --port 8177

# A) 辅种页
curl -s "http://127.0.0.1:8177/api/state?view=group"
keys: ['groups', 'rid', 'singles', 'status', 'updated']
groups: 150  singles: 0
totalDl(前端口径) = 15206400
totalUl(前端口径) = 45926400

# B) 种子页 —— 同一份数据的同一个进程
curl -s "http://127.0.0.1:8177/api/state?view=torrent"
keys: ['rid', 'status', 'torrents', 'updated']
groups present? False | torrents: 300
全量真值 dlspeed 合计 = 15206400
全量真值 upspeed 合计 = 45926400
status.server 含 dl_info_speed? False   # 桩里 server_state = null

响应里根本没有 groups 键，而真值是 15,206,400 —— 前端在种子页上能算出来的只有 0。复现成立。

# 次因: 50 组 + 200 未归组
uv run python scripts/ui_harness.py --torrents 300 --groups 50 --port 8178
curl -s "http://127.0.0.1:8178/api/state?view=group"
groups: 50  singles: 200
前端口径(仅 groups) dl/ul = 1723392 / 5068800
全量真值(groups+singles) dl/ul = 15206400 / 45926400   # 少算 88.7% / 89.0%

补充一条推论：若用户是先开辅种页再切种子页，groups 会保留切换那一刻的旧数组 —— 此时状态栏不是 0，而是冻结的旧值（比 0 更隐蔽）。用户报「永远 0」说明首屏就在种子页 （autoqb.ui.view 落在 localStorage 里，下次打开直接进种子页）。

03

根因链路

1 主循环重建四视图并发布web_runtime._publish_locked · group_view / singles_view / flat_view / shows_view 四份都在
2 前端带 view 参数轮询app.js:866 · viewMode=torrents ⇒ view=torrent view=torrent
3 按视图裁剪：种子页只回 torrentsweb_view.VIEW_ARRAYS["torrent"] = ("torrents",) groups 被裁掉
4 前端「键不存在则保留原引用」app.js:883 · if (state.groups !== undefined) groups 停在 []
5 状态栏对 groups 求和decorate.js:136-141 · totalDl / totalUl 0 B/s

第 4 步本身不是缺陷 —— 「不抹空没回的视图」是 P1-1 的正确契约（否则切回别的视图要等一轮全量）。 缺陷出在第 5 步：状态栏是一个跨视图的常驻显示，却去依赖一个按视图裁剪的数组。 这与 2026-09-19 修掉的 BUG-8（追剧页因成员索引被裁而永久空白）是同一类错误，只是换了个消费者。

04

候选修法与取舍

三个候选
候选做法代价结论
A 服务端算 totals /api/state 的 status 块加 totals（全量种子求和），前端改读它 每次视图重建多一趟 O(n)（5000 种子约 1–2 ms，1.5s 一次） 推荐
B 前端兜底求和 groups.length ? groups+singles : torrents 求和 违反「派生值后端算」约定；且 groups 非空但陈旧时显示错值而非 0 否决
C 读 qB 全局 状态栏直接用 status.server.dl_info_speed 口径变成「qB 全局」（含未纳管种子），与现有 title「全部组合计」不同；桩实测 server_state = null，真机才有值 备选

候选 C 的真实风险

status.server 来自 qB sync 的 server_state，不是本工具自己算的。 桩服务里它是 null（FakeClient 不提供），意味着走 C 的守阵在 CI 里测不出真值，只能测「不报错」。 而 A 的数据源是本工具的 store，合成种子可断言、可复现。故默认走 A。

F5

守阵：三条，各防一种失效

P0
  • 端点守阵（tests/test_web.py）：view=torrent 与 rid 命中（updated=false）两种情况下，status.totals 都必须在，且等于全量合计（含未归组）—— 防主因与次因复现。
  • 静态防回潮：decorate.js 的速度求和不得再出现 this.groups.reduce —— 防有人把 F4 改回去。
  • 浏览器冒烟（scripts/ui_smoke.cjs）：切到种子页后断言 vm.totalDl === status.totals.dlspeed 且 > 0 —— 唯一能防「pytest 全绿但界面废掉」的一道。

冒烟断言刻意写成「等于服务端真值」而不是「不为 0」：切视图前若已取到过 groups，旧实现也会显示一个非零的冻结值，只断言非 0 会漏。

回归风险与红线

风险登记
风险判据处置
每轮多一趟 O(n) 求和 5000 种子约 1–2 ms，视图重建 1.5s 一次 可接受；若实测超预期，改从已构建的 flat_view 求和（省一趟遍历，代价是耦合 SEED_ITEM 契约）

待拍板

口径：本工具纳管的全部种子 vs qB 全局

本计划默认走 A（本工具纳管的全部种子，含未归组） —— 与状态栏现有 title「全部组下载/上传速度合计」语义最接近， 且数据源可测。

如果你想要的是 qB 全局口径（等于 qB 原生状态栏，包含本工具不管理的种子），那应该走候选 C， F1/F2 可以整个省掉，只改 F4 一行。说一声即可，其余部分不变。

另：修完之后建议顺手确认 /api/state 在种子页下还有没有别的「跨视图消费者」被裁掉的阵列 饿到（本轮不动，只记录）—— 这是 VIEW_ARRAYS 裁剪机制第二次暴露同类问题了。
