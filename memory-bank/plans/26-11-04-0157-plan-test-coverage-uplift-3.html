§01目标与设计原则

1.1 背景与前两轮的关系

第二轮收口时(2026-10-21):TOTAL 99.41%、缺口 162 单位、门槛 --cov-fail-under=99(win)转绿、watchlist 清零,残留硬骨头(真机探测 / GUI / 低频错误路径 / 路由竞态)逐条列名留第三轮。两周后的今天(2026-11-04 实测):TOTAL 仍显示 99%(win 门槛通过,exit 0),但缺口绝对量回涨到 319 单位(167 miss + 152 partial),覆盖分母 27,683 → 31,281(+3,598)。发生了什么:

  • 旧残留基本清偿:第二轮列名的残留大头被后续重构连清带补——relocate_mod 29 → 8(26-11-02-2342 大文件拆成 relocate_exec/plan/units 三叶后补测)、webui/runtime 25 → 21(拆 4 个 runtime_* 叶)、views 8 → 1、ops_mod 7 → 4、traffic_grid 8 → 7。
  • 新欠账约 +157 单位进场:规则引擎重设计(26-11-01-0106)带进 rules/base.py 35 + config/validation/rules.py 22;下载熔断(26-11-03-0456)带进 fuse_mod.py 33 + cli 放行入口 16;种子转移(26-10-31-0306)带进 transfer/orchestrator.py 10;追剧视图、ops 拆分叶等零散进账。新面出生覆盖率约 95.6%(+3,598 单位里 157 未覆盖)。
  • M4「增量不欠账」的口径盲区:覆盖率守在 99% 没人红,欠账绝对量没人看——门槛是比例指标,分母一涨,同样的 99% 背后多藏了 157 个未覆盖单位。这是第三轮机制段要堵的洞。

1.2 目标(做到什么程度算成)

  • 缺口收敛:319 → ≤100 单位(TOTAL ≈ 99.7%±0.2),残留逐条列名(预计为真机探测 / GUI / 防御支)。
  • 阈值阶梯:win 99 → 99.3(P1 后)→ 99.5(P2 后);其他平台 98.5 → 98.8 → 99.0(单点 tests/conftest.py::COVERAGE_FLOOR_*)。
  • watchlist 清回零:行覆盖 <95% 单文件从回沉的 7 个清回 0(§2.5)。
  • 机制 M8:基线切片新增「缺口净额 vs 上一条切片」栏,新欠账当轮点名(M1–M7 继承不动)。

2.5 watchlist 回沉——机制为什么没拦住

第二轮 M5(watchlist:行覆盖 <95% 单文件每轮切片点名)在收口时清零,但两周后回到 7 个:fuse_mod 90% / webui/commands.py 90% / cli.py 90% / ops_jobs 90% / runtime_common 93% / views_episodes 94% / rules/base 94%——其中 6 个是这段时间新出生或拆分出的文件。M5 只「点名」不「拦截」,新模块进场时没人看它一眼。第三轮处置:P0/P1 任务表把 7 项全部纳入核销范围,P2 目标清回零;机制段 M8 把「缺口净额」钉进基线切片,让新欠账在收尾轮必然被看见(§03)。

§03方案总览

排序原则沿用前两轮:先清「没测过」(A 类),再扫「测不全」(B 类),外部依赖型(C 类)用回环 stub 与 monkeypatch 收敛,长尾收口并逐条列名残留。每阶段是可独立提交、可独立验收的闭环;预估单位按 §2.1 换算,完成时以 test.full 实测为准,不达标的差额滚动进下一阶段任务表。三阶段预估合计 +256±35,与「319 − 100 = 219」的终点需求之间留了新码继续进场的稀释余量。
