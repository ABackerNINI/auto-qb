§01目标与设计原则

1.1 目标与边界

  • 目标 glob: **/core/**/*.py —— 命中 32 个 .py(根 14 + modules/ 13 + traffic_source/ 3 + 3 个 __init__), 合计 14,710 行(入轮 14,644 行, 3 个 __init__ 共 66 行不设轮)。
  • 目标不是涨分: 是「包内不再有不知道为什么活着的变异」—— 每条存活变异落进三分类之一(真洞 / 等价变异 / 假存活)并各有处置; 等价变异杀不掉是数学事实, 不追 100%(引可行性报告 §11)。
  • 显式排除: hr/(已有七模块轮)、webui/、infra/、JS 前端(无单元层, 前提不成立, 锚 §03); 需真实 qB 在场的真机行为验证(变异审计只在桩面跑)。

1.2 为什么 core 是下一个

  • 锚 §03 优先级表里 config/ 已清(R13, 90.02%)、hr/ 已做余量(R22 后六条 test issue 全清)、rules/ 已清(R23); core/ 是剩下的唯一大件, 锚里只有一行「主循环 / 限速」, 没有刻度。
  • core/ 是五条黄金法则里四条的主要落点: 幂等性(taskqueue.py 去重)、保守默认(限速面的跳检/强制汇报开关)、状态持久化(state.py state_file)、单一写线程(taskqueue.py 队列结构)—— 出错代价在全部包里最高。
  • 覆盖率量不出强弱: 同为 98% 分支覆盖, 实测变异分数 rules/ 55.5% vs infra/utils.py 72.5%(报告 §01)。core/ 的 98% 覆盖不构成「够硬」的证据。

1.3 设计不变量(违反即白跑)

  • 按模块切轮, 永不一把跑整包(实测全量在 37% / 74% 两处打挂 WSL); 每轮估变异 ≤ ~2,500。
  • 池 = 定向的几个测试文件, 不用全 tests/; 每轮开跑前核「池覆盖目标函数面」(硬约束 9)。
  • 全程走 .commands/mutants/ 包的 task id, 计划与文档不抄命令本体(doc.drift 判红)。
  • process_isolation=forkserver、-n 0 --no-cov、--max-children 4、文本层守阵 --deselect —— 均已内建在包脚本, 正常路径不手工拼。
  • 基线不绿不开跑(test.quick 先过); 基线越红 verify 判据越弱。
  • 量化只认 mutants.run 同目标同池复跑; 手搓变异只做形态复验与红验, 不进存活计数。

§03方案总览

3.1 主线

不做整包首轮(与 config/hr 不同的开局): core 行数是 hr 的 1.83 倍, 按 hr 校准的单轮长尾, 整包 ≥ 2.5h, 必撞 mutants.run 的 timeout 且 no tests 面会在报告里糊成一团。改为 9 轮模块轮, 每轮独立走完整 round protocol(skill 的 S1–S9), 每轮出一条自己的基线切片; 轮与轮之间没有依赖, 可穿插在任意会话执行。计划里轮次用 W1–W9 占位, 真实 R 号开工时先 fetch 远端任务档案再取(多 clone 并行撞号先例: hr 轮与 config 轮都曾用 R11)。

3.3 测算口径

  • 变异密度 0.84–1.23/行(报告 §08 实测区间), 中值取 1.0; 不剔除「纯数据声明」行去精化。
  • 墙时不用 config 单价外推: hr 实测大包 ≈0.7s/变异且极不均匀(mutmut 按估计快的先跑, 前 85% 用 60 min, 余 15% 长尾再花 36 min); 排期按「每 1,000 变异 ≥12 min + 2x 余量」。
  • S4 全套件 verify 单价 ≈15s/条(config 窄池实测); 池宽的轮(W6)直接读 diff, 不走全量 verify。

§04实施步骤

4.1 每轮标准步(一轮一收口, 不跨轮攒)

步动作验收判据
S0 入场commands run test.quick 确认基线绿; git fetch 看远端任务档案轮次号, 取本轮真实 R 号(计划占位 W# → 实际 R#)基线绿; R 号与远端档案不撞
S1 定池commands run mutants.setup(首次/镜像落后); 按 §03 表定池, 并核函数面: 对照目标文件的 def/class 清单与池测试的引用 —— 缺口按 W1/W6/W7 的预案先扩池或补用例目标公开函数在池内都有对应用例; 核对结论写进切片
S2 跑轮commands run mutants.run -- --target '<本轮glob>' --pool <池文件...>; 有并行会话时加专用镜像 --mirror ~/auto-qb-mut-core + --children 3记录变异数 / 杀死率 / 耗时 / 工具版本 / 选择池(逐文件)
S3 导出+三分类commands run mutants.report -- --target '<本轮glob>' 拿带 diff 的清单; 逐条判 真洞 / 等价变异 / 假存活(人的动作, 不是工具输出)每条存活变异有分类与一句理由; 不拿纯 id 清单分类

S5 补测确认的真洞各自入池(test 缺口 / bug, 填 doc-refs)或当场补断言; 守阵给「正向 + 反向对照」两种输入, 补完红验(同构变异→目标用例红→还原复绿, 锚点 count != 1 报 ANCHOR-MISS 停手), 再 commands run test.full红验全红(守阵不空转); src 零残留
S6 复跑同目标同池再跑; 带新守阵先 cp 进镜像 + --no-refresh(否则被 git checkout -f 冲掉)复跑存活 ≤ 首轮; 新增存活单独点出
S7 记录commands run kb.new baseline 立切片(字段: 目标/池/计数/杀死率/耗时/工具版本/children/机器; 首轮与复跑各一行; 真洞数+issue 链接; **Refs:** 指向任务档案); 任务档案追加轮次行切片字段齐; N passed 只出现在切片里
S8 更锚改常驻锚 §07 覆盖进度总表 core/ 行: 日期 / 变异数 / 杀死率 / 轮次 / 状态 / 切片链接(首跑插行, 状态 待做 → 已做(余量在池))日期与切片一致, 数字与切片逐位一致

4.2 分期

  • 第一批(W1–W3): 状态队列 / 限速 / 判定内核 —— 黄金法则落点与出错代价最高的三块, 共 ≈2,490 变异。
  • 第二批(W4–W7): 流量面(存储 / 采样 / 快照来源)与编排客户端, 共 ≈6,260 变异; 其中 W6 是唯一宽池轮, S4 玩法切换。
  • 第三批(W8–W9): 搬移面与 modules 余量, 共 ≈5,895 变异; 体量最大但出错代价相对低, 排最后。
  • 批与批之间可以停: 每轮都有独立切片, 中断不留半成品; 恢复时 commands run mutants.status 回看镜像。

4.3 验收(可判定)

  • 每轮基线切片字段齐(skill「记录口径」必填清单), 首轮与复跑各一行。
  • 确认的真洞 100% 已入池或已补测(带红验); 等价变异 / 假存活各有一句理由。
  • 同池复跑存活数 ≤ 首轮; 任何「新增存活」有解释。
  • 常驻锚 §07 的 core/ 行与最近切片逐位一致(skill 硬约束 12, 没更视为该轮未收尾)。
  • W1/W6/W7 三个函数面风险区(state.py / qbapi.py / reader.py)各有明确结论: 盖住了, 或 no tests 面已入池 issue。
  • 整包收口后: core/ 状态从 待做 翻 已做, 锚 §03 优先级行补 ✔ 与刻度。
