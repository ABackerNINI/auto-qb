WEBUI 抽屉跨周期让位误补偿与下降抖动修复计划

本篇只回答：在不改动「最小滚动 / 非对称 / 可见下界单点」这套原设计的前提下，怎么修掉抽屉「开 → 关 → 再开」后本不该让位的选中行仍被抬起，以及收起动画期的可见抖动。

§01目标与设计原则

做到什么算成：用户复现路径的第二步（关闭后再选中「附近不会被覆盖的种子」并打开抽屉）中，window.scrollY 与选中行 rect.bottom 全程零位移；收起动画 160ms 内背景列表不出现逐帧来回位移。两个症状都归零，且既有让位语义、判据、位移公式、三发挂点、下界单点一字不改。

复现路径（用户原话）：先在种子列表最下方选中一个种子 → 触发抽屉上升（种子跟着上升，正常）→ 关闭抽屉 → 选中附近不会被覆盖的种子 → 再触发抽屉（此时种子仍上升，不正常）；另外下降过程中有不正常抖动。

硬约束：用户 2026-11-12 指令「机制尽量尊重原设计」。下面不变量全部来自明文，不来自推测。

口径差异如实注明（D4 / D10）

  • 「非对称还原」「不做对称还原」「不主动复位 scrollY」「除非是列表最后几个种子，抽屉下降时列表保持不动」——全库未找到逐字明文；可定位到的最接近表述是「中间行不扰滚动(scrollY 不变)」「几何也不动」「先问要不要动几何，能撑住的就撑住」，以及代码事实：让位仅在打开路径调用、无成对 close 复位。故按本次新拍板记录，不冒充历史设计。
  • 档案里「文档变矮 → 滚动钳制」记作「钳回 0 / 整页跳顶」（列表被筛空、文档塌到视口高时，pitfalls/web-ui/search-pending-collapse.md:27、tasks/26-10-07-webui-drawer-search-jump.md:17），与用户「只影响文档底部」措辞不同。二者不是同一现象，实施轮回写时不得混成一条。
  • 对照分界：pitfalls/web-ui/frame-swap-scroll-reset.md:13 的 H.withScroll 成对恢复是抽屉内部表格体滚动容器，与主列表文档滚动两套口径，不能据它推出主列表也该对称还原。

§02现状与痛点

取证基线 HEAD 59113c69（会话开工同步值），全部为只读静态阅读结论，未在真机/浏览器复现。

面代码事实
组件抽屉不是浮层，是 app 级 position: sticky 吸底停靠面板 shared/tpl/dock.html:10；<transition :duration="220"> 四钩子 shared/tpl/drawer.html:16-19；可见性单点 shared/drawer.js:87-91
开合动画JS rAF 对 .drawer-dock 的 height / marginTop 插值，非纯 CSS：enter shared/drawer_general.js:251-292、leave :302-338、stop :239-250；_drawerFinalTop :236-237
让位单点shortcuts_engine.js:331-345 _kbRevealRow：判据 rect.bottom > vBot - 4 → window.scrollBy(0, rect.bottom - vBot + 8)；下界 _kbViewBottom() :228-259，动画期优先读登记值 _drawerAnimTop - 8（:249-250）
三发挂点drawer_general.js:69（开场）、:300（after-enter）、drawer_store.js:398（集合落定兑现挂单）

W1 根因：动画期瞬态登记量泄漏成跨周期状态

  • closeDrawer()（drawer_general.js:79-102）不清 _drawerAnimTop，反在 :88 写入落定顶缘；清零只挂 drawerAfterLeaveHook :339-350，而它带 if (this.drawer.open) return;（:340）——收场被快速重开打断时跳过清零。
  • drawerEnterHook 的 reduced-motion / 无 dock 早退（:255）在登记赋值前 return，不清旧值；h0=0 早退（:263）的前一行 :262 已写 _drawerAnimTop = h0 ? _drawerFinalTop(dock) : 0，该分支已清零、不需补清场（评审更正）；_kbViewBottom :249-250 在面板仍于 DOM 时直接返回旧登记值且不清零。
  • _drawerSwitchEnd()（drawer_store.js:417-422）只清 _drawerWait / _drawerSoftSwitch / _busyArmTimer / drawer.switching，不含 _drawerAnimTop、_drawerAnimDock、_drawerOpenReveal 与 dock 内联 height/marginTop。
  • 后果：旧顶缘偏小 → vBot 偏小 → 对本不该让位的行 rect.bottom > vBot - 4 也成立 → window.scrollBy 把整页连同选中种子抬起。window.scrollY 全程无还原，但那是原设计（§01），不是本 bug 的修复靶点。

W2 根因：收场高度逐帧传导给文档高

  • drawerLeaveHook :327-329 每帧写三处内联样式（el.style.height / dock.style.height / dock.style.marginTop）；dock 是流内 sticky 元素，dock.style.height 从 h0 → 0 令文档逐帧变矮，浏览器逐帧钳制 scrollY → 背景列表逐帧回弹。
  • 与 dock-panel.md:118「滚动钳制（属预期）」的区别：预期是结果变短后的一次性钳制，缺陷是动画期逐帧反复。W2 只治后者。
  • 抽屉开合链无 transitionend 监听、无 scroll 驱动的让位重算；after 钩子由 :duration="220" 定时器触发。三发让位分散在 nextTick / after-enter / 数据落定三个拍。

覆盖空白与坑档复发

e2e/drawer-dock-stability.spec.mjs 只测单次打开后搜索/筛选时面板 top 稳定（不关不重开）；全库零用例覆盖「开 → 关 → 再开」或「不会被覆盖的行不该上升」。静态守阵 tests/test_web_shortcuts_drawer.py::test_drawer_open_reveal_row / ::test_drawer_transition_dock_anim 只钉「调用存在」——dock-panel.md:55-57 已记复发 1：「守阵只断言『调用了让位』，探不到『调用存在但几何/时机错』……静态守阵全绿而真机必红」。本次是该坑同族机理的触发面从「文档底首次打开」扩展到「开 → 关 → 再开」周期残留，复发 +1 与补明文列入 S6（本轮不动坑档，D10）。

§03方案总览

一个计划、两个工作包（D5），各自独立红绿双验；判据、位移公式、三发挂点、_kbViewBottom() 单点口径零改动（D3/D7）。

包靶点改法明确不做
W1_drawerAnimTop 生命周期（D7）最小改动（D8）：在 openTorrentDrawer 周期起拍作废旧登记 + 补齐 drawerEnterHook / drawerAfterLeaveHook 各早退分支的清场，使旧顶缘不可能流到下一周期不引入代际状态机、不改 _kbViewBottom() 读取口径、不加 scrollY 快照、不动三发挂点
