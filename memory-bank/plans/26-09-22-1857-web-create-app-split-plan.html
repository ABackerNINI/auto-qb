01一句话结论

create_app 926 行的问题不是"行数多", 而是鉴权、路由、缓存、装配、静态挂载五类职责共用一个闭包作用域: 任何 Web 改动都在这一个作用域里叠加, 安全审查面 = 整个函数。本计划把它拆成 web/ 包(15 个文件, 沿用项目 2026-09-15 config.py→config/、torrents.py→torrents/ 两次单文件转包的成熟先例), create_app 收成只做"建 app + 挂依赖 + include 路由 + 挂静态"的组装壳(预估 ~80 行)。

三条硬边界: ① 纯移动不改行为 —— 57 个 API 端点 + 3 个重定向 + 1 个中间件的语义、鉴权、日志命名空间全部原样; ② tests/test_web.py 115 条用例零改动全绿; ③ 不顺手修任何安全项 —— 三条安全 issue(S1-01/S1-02/S1-05)在拆分完成后各自变成局部改动, 这是本重构的直接收益, 不是本次范围。

外部消费面已核实仅 3 处(qbmanager.py 两处函数内导入 / tests / scripts/ui_harness.py), 经 __init__.py 门面全量 re-export 后调用方零改动。

3.1 路由挂接模式

每个 routes 模块暴露 build_router(ctx: WebContext) -> APIRouter; factory 按固定顺序 app.include_router(...)。鉴权不落到任何 router 上 —— 仍由 factory 里 FastAPI(dependencies=[Depends(require_token)]) 单点全局生效, 与现状逐字等价, 杜绝"某个 router 忘挂依赖"这类漂移。端点函数体逐字平移, 仅两处机械改写: @app.get(...) → @router.get(...)、闭包变量 manager/_cached_read/_enqueue → ctx.manager/ctx.cached_read/ctx.enqueue。

04关键设计决策

#决策理由 / 不变量
K1web.py → web/ 包, __init__ 门面全量 re-export项目已有两次同类转换先例; from auto_qb.web import X 与 from .web import X 对包同样成立, qbmanager/tests/ui_harness 零改动
K2鉴权 = auth.make_require_token(manager) 闭包工厂_local_skip_logged("只记一次")天然 per-app 实例, 与现状等价; 测试对同一 mgr 多次 create_app 的语义不变
K3日志命名空间钉死 "auto_qb.web"web/ 下所有子模块显式 logging.getLogger("auto_qb.web"), 不用 __name__(否则变 auto_qb.web.auth, caplog 按 r.name == "auto_qb.web" 过滤的 3 条测试必红)。拆分后如需分模块定级, 再单独立项
K4RO 缓存 = context.RoCache 实例, factory 每 app new 一份缓存键含 manager._web_write_seq(写失效)的语义逐字保留; 保持 getattr 兜底(stub manager 可能没有该属性)
K5路由注册顺序 = 现源码顺序, 金清单守阵钉死今日无同形路径冲突(/api/torrents/bulk、/add 与 /{hash} 靠方法区分), 但顺序保持是零成本保险
K6static_ui.mount_static_ui(app) 在 factory 最后调用app.mount("/") 必须在全部 /api 路由之后; no-cache 中间件注册次序随迁, 非 /api 语义不变

05方案取舍

取舍点选定放弃项与原因
文件组织web/ 包 + 门面web.py 留单文件 + web_*.py 兄弟模块 —— 顶层命名空间被 15 个文件污染, 且无先例; 一把梭大爆炸无中间可验点
routes 组织routes/ 子包包内平铺 15 文件 —— 基础件(auth/context/common/lifecycle)与端点混在一层, 找东西靠命名约定; 子包一眼分层
路由形态build_router(ctx) -> APIRouterregister_routes(app, ctx) 直接装饰 —— 少一层但丢 router 分组; app.state + 模块级 router —— 隐式全局, 与本项目显式传依赖风格相悖, 且 stub manager 场景更脆
与安全修复的先后先拆后修先修后拆 = 在 926 行函数里继续叠三层刀(CSRF 中间件/SSE ticket/日志脱敏), 拆分 diff 与修复 diff 互相污染。拆完的落点: S1-01 CSRF → auth.py; S1-02 SSE token → auth.py+routes/events.py; S1-05 passkey 脱敏 → routes/system.py(api_log)
波次粒度6 波, 每波可独立提交/回退一次 PR 全量平移 —— 1,100+ 行 diff 没人能审; 单端点逐个搬 —— 57 次提交噪音
