提交闸门按改动收窄优化

提交闸门固定开销按「本次改动」收窄：drift 全库扫描改查改动的 md、十条 KB 校验并行跑、caps 债务计算面按改动收窄、test.pkg 按改动包收窄；test.quick 经拍板本轮不动。设计主轴：拦截面不弱化，改动清单一律复用预检 <changed:GLOB> 展开这一单点，闸门脚本不自查 git。

§01目标与设计原则

背景。提交闸门是 ship.commit 的前置机检（11 条，定义在 .commands/my-commit-flow/.my-commit-flow.toml）。2026-11-01 逐条实测（本机单次热跑）发现固定开销集中在四处：check_command_drift 每次提交全库扫 md（6.1s，match 为空串）；memory-bank 十连检改任何 KB 文件就串行跑十条全库校验（合计 6.2s）；test.pkg 改任一包就整跑 154 个真实 git 子进程用例（约 73s）；test.quick 改 src/tests 就全套跑（约 27s）。典型墙钟：纯代码提交约 35s（其中 drift 的 6s 与代码毫无关系），KB 提交的文档机检约 13.5s。

目标：不弱化拦截面的前提下降固定开销——纯代码提交不再为 drift 付 6s；KB 提交的十连检关键路径从串行 6.2s 压到并行后约 3.5s；改单包时 test.pkg 只跑该包。算成的标准：S1–S3 各自验收判据全绿，且复测数字回写本计划。

设计底线（不变量）：

  • 改动清单单点 = 预检 changed_files()（staged+unstaged）。方案 A/C 一律经 <changed:GLOB> 展开消费，闸门脚本不自查 git —— ship.commit 在 rebase 后会用同一份 present 清单复跑闸门，脚本自查 git 在复跑阶段语义就错了（树已净，status 查不到本次改动）。
  • 守阵不动：tests/test_memory_bank.py::test_commit_gate_covers_kb_check 用正则在闸门配置里逐字找 <脚本> --check —— 十连检的 run 清单一条不能删、不能合，并行化只能落在引擎层。
  • 沉默即成功契约：全过静默、失败才说话；失败行 (note, cmd, rc, secs, tail) 结构与「取第一条失败」语义保持，失败顺序 = 配置序（确定性）。
  • 保守回退：展开失败按既有语义 STOP 不降级；改动面判定拿不准时宁可全量跑。

§02现状与痛点

机制现状。_pipeline.py::run_gates 是双层串行 for（闸门逐条 × run 逐条，run_capture 阻塞等完）；<changed:GLOB>/<each:GLOB> 已有改动级展开，无匹配即整条静默跳过；hit() 按路径前缀/子串判触发。11 条闸门逐条盘点：

实测口径：python 直跑各脚本 --check（本机 2026-11-01 单次热跑，含解释器启动）；test.pkg / test.quick 引 .commands/test/config.toml 注记的 2026-10-08 实测值（-n 8）。数字用于量级判断，验收时以同口径复测为准。

复测（2026-11-01 实施后，同一口径经 run_gates 真跑）：drift 纯代码改动三条 run 全跳 = 0.00s（原每次提交 6.1s）、改 md 单条 0.28s、改注册表全量单条 6.39s；caps 改 KB 单条 0.36s（原全量 0.57s）、改 AGENTS.md 单条 0.07s；十连检并行 ran=11 耗时 4.25s（关键路径 timekit ≈3.6s；S2 验收线 ≤4.0s 按 10 条口径订立，实施时上游已加至 11 条 —— 收益 6.2s→4.25s，落在并行化理论下限附近）；test.pkg 纯代码改动两条 run 全跳 = 0.00s。回归面：test.pkg 与 test.quick 全绿（总数只写一处，见 commands run kb.baseline）。

痛点一：drift 与本次改动无关地全量跑。手抄漂移只有两个引入途径：(a) 本次改动的 md；(b) 命令注册表 / 骨架提取逻辑变化（.commands/**/config.toml、引擎 .agents/skills/commands/scripts/）使旧副本在新判据下漂移。(a) 只需扫改动文件，(b) 才需要全量——现状两者不分，一律全量。

痛点二：十连检串行。十条互相独立的校验逐条跑：timekit 3.5s（mb.rglob 两遍全库）/ gen_doc_map 1.0s（919 份文档）/ 其余 8 条合计约 1.7s。串行合计 6.2s，并行后关键路径 = timekit 约 3.5s。

痛点三：test.pkg 不分包。154 个用例是真实 git 子进程场景（init/push/rebase，IO 密集），改 .commands/kb/ 单包脚本时引擎与其它包未动，仍整跑约 73s。

§03方案总览

方案 A（P0）：check_command_drift 按改动收窄

落点：scripts/check_command_drift.py 加两种模式 + 闸门 run 由一条拆三条（match 保持空串，触发命中后由展开自选）：

# .my-commit-flow.toml —— check_command_drift 闸门的 run 由一条拆三条
run = ["python scripts/check_command_drift.py --files <changed:*.md>",                                # (1) 只扫本次改动的 md
       "python scripts/check_command_drift.py --full <changed:.commands/**/config.toml>",            # (2) 注册表变了 → 全量
       "python scripts/check_command_drift.py --full <changed:.agents/skills/commands/scripts/*.py>"] # (3) 骨架提取逻辑变了 → 全量

展开语义现成：任一 run 的 <changed:GLOB> 无匹配即整条静默跳过 —— 纯代码提交三条全跳（省 6.1s）；改 md 只扫改动文件；改注册表/引擎脚本才全量。--files 模式对传入文件仍逐个过 SCAN_GLOBS 归属与 EXEMPT 豁免再逐行比对骨架；无参直跑维持现状全量（兼容既有调用与手工）。

为什么改脚本不改 match：md 散布在根部/memory-bank/.agents/.commands 多处，用 match 复刻 SCAN_GLOBS 就是第二处演化点；脚本内收窄让 SCAN_GLOBS 保持单点。

方案 B（P0）：十连检并行化（引擎层）

落点：_pipeline.py::run_gates —— 命中闸门展开后的命令扁平清单按配置序提交线程池（池上限见 D2），每条命令保留自己的 note/timeout；失败全量收集、按提交序排序（确定性），调用方仍取第一条。run 清单零改动，守阵原样。run_capture 的看门狗/杀树/超时语义原样沿用（线程只等 subprocess，Windows 下安全）。收益：十连检 6.2s → 约 3.5s；冒烟闸门的 <each:--help> 逐脚本启动同样吃到并行。

明确不做：把十条 run 合并进一个 wrapper 脚本并发跑 —— 守阵逐字匹配 <脚本> --check，合并即把防静默红设计架空（§01 底线 2）。

方案 C（P1）：test.pkg 按包收窄

落点：test 包新增 script 型 task test.pkg.scoped（wrapper python 脚本内置 TMPDIR 设置，不走 cmd.exe 引号配方；--full 时转调 run.py run test.pkg，配方单点不复制）。闸门一条 run 换两条：

run = ["python <skill-dir:commands>/scripts/run.py run test.pkg.scoped -- <changed:.commands/**>",                       # 包文件改动 → 收窄到受影响包
       "python <skill-dir:commands>/scripts/run.py run test.pkg.scoped --full -- <changed:.agents/skills/commands/**>"]  # 引擎改动 → 整跑

归并规则（默认拍板 D4）：改动文件按 .commands/<包>/ 前缀归并出受影响包集合，只收这些包的测试目录；受影响包 ≥2 或命中引擎 → 直接整跑。两条 run 都命中时 scoped + full 各跑一次（full 已覆盖，scoped 白跑一趟，罕见、接受）。

方案 D（P1）：check_context_caps 按改动收窄（2026-11-01 用户拍板纳入）

落点：scripts/check_context_caps.py 加 --files 模式 + KB 角色 cap 的单点 check_kb_structure.check_caps 加可选 only 参数（默认 None = 行为不变）+ 闸门 run 一拆三条（match 不变）：

run = ["python scripts/check_context_caps.py --files <changed:AGENTS.md>",          # (1) AGENTS.md 改了 → 硬规定
       "python scripts/check_context_caps.py --files <changed:.agents/skills/**>",  # (2) skill 改了 → SKILL/阅读预算 cap
       "python scripts/check_context_caps.py --files <changed:memory-bank/**>"]     # (3) KB 改了 → KB 角色 cap

语义：硬规定不变——AGENTS.md 超限且改动命中仍 STOP（展开传来的就是改动文件，与现状 rel in changed 等价）；债务计算面收窄到改动文件。代价（D5 拍板接受）：未改动文件的存量债务不再每次提交重复提醒，可见性收敛到「该文件被改时 + 清理会话 doc.caps --strict」——与方案 A 同一档「落后到下一次提交」模式。无参直跑维持现状全量（doc.caps 与手工兼容）。

不做清单

  • test.quick 改动级选测 —— D1 拍板暂不动（§06）。
  • check_doc_links 收窄 —— 收益约 0.5s，且会漏「指向改动路径的他件」（改名坏链落在别的文件里），搁置。
  • sync_agent_skills —— 同步非检查，设计上靠每次提交兜住拉取来的改动，收窄即失效。

实施顺序 A → B → C：A 最独立先行；B 动引擎、C 动 test 包与闸门配置，各自独立成提交。
