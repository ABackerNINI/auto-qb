§01目标与设计原则

背景

curves 列表(多条 period 曲线: DAY / ND / MONTH)的顺序今天完全随写入序, 校验层只拒重复 period、无任何排序规则(validation/curves.py:55-61)。真实实例已出现乱序展示(Q4 场景确认); UI 新增 period 是尾部追加(config_editor_curve.js:53-58), 加 7D 会落到 MONTH 之后即乱。动机 = Web UI 展示顺序(D2); 入口 = UI 为主、手改/复制粘贴 config.yml 为辅(D3)。

目标(做到什么算成)

  • 编辑器打开即有序(GET 面排序); 新增/改值即时归位(前端两触发点); 乱序磁盘经一次 UI 保存收敛为规范序(被动)。
  • 限速语义与阈值校验零变化; 全量测试绿。

设计底线 / 不变量

  • 幂等(黄金法则 1): 排序键唯一(重复 period 已被校验拒绝)+ 稳定排序, 重入无漂移; month 不按当月实际天数参与比较(D5, 否则 28-31 天波动导致重排翻转)。
  • 保守默认(黄金法则 2): 数据可疑不动手 —— GET 树任一 period 解析失败即整段放弃排序(D8); 不加启动迁移主动改生产文件(D7)。
  • fail-fast 不放松(黄金法则 4): 阈值「严格递增」硬报错保持(validation/curves.py:86-91), 自动排序仅针对无语义的列表序(D1/D6)。
  • 单点: 排序键 helper Python 单点(core/curves.py 挂 normalize_period 旁); JS 复刻一份并注释互指(D4/D12)。
  • 范围守恒(黄金法则 6): 阈值面 UI 加点乱序的改善不在本计划, 需要则另行入池(D6)。

§02现状与痛点

关键事实(决定落点)

  • UI 渲染的是磁盘原始树, 不是解析模型: GET /api/config → read_tree(PyYAML BaseLoader, 保磁盘顺序, routes/config.py:129-136); 编辑器工作对象 = 该树(config_editor.js:177)。没有任何写回路径序列化解析模型 → 仅 loader 排序到不了 UI, 解决不了动机。
  • 运行时与顺序无关: 多曲线同方向取 min 合并(core/curves.py:107-117); 列表序只影响 period_stats 日志行序与展示。运行时排序纯规范面。
  • writer 列表 = 整体替换语义(writer.py:868): 提交列表与磁盘不同 → 整体重建(列表项内注释丢失一次); 相同 → skip, 字节稳定(writer.py:863-867)。UI 保存提交的是前端树(PUT routes/config.py:138-170), 保存后重拉(config_editor.js:216-217)。
  • period 归一化: normalize_period(core/curves.py:33-43) → "day" / "month" / "{N}D"; 别名 DAY/1D/D → day。重复 period 在校验层按归一化值拒绝(validation/curves.py:55-61)。
  • loader 先验证再解析(loaders.py:444-490, 排序自然槽位 = 循环结束后构造 GlobalSpeedLimitCurve 前); GET 面则是磁盘原始树, 可能遇到运行中手改的非法 period。
  • 阈值点乱序 = 硬报错(validation/curves.py:86-91); UI 图表对阈值显示副本已排序(config_editor_curve.js:162)。

痛点

  • 乱序实例 UI 展示无序(用户实证, Q4)。
  • UI 新增 period 尾部追加, 添加即乱。
  • 复制粘贴他实例配置(任意序)后 UI 展示随粘贴序。

§03方案总览

排序键(D5)

归一化 period → 序: day=(0,) < {N}D=(1,N) 按 N 数值(2D < 10D) < month=(2,) 恒最后。别名归一化后判键。

三层落点(D4)

层位置作用
GET 路由routes/config.py GET /api/config 返回前, 对树内 curves 数组排序编辑器打开即有序(动机主面)
loaderloaders.py 构造 GlobalSpeedLimitCurve 前排序运行时模型有序(period_stats 日志序); diff 基线两侧一致, 消灭首次保存 phantom diff
前端config_editor_curve.js + traffic-card.html新增定位插入(D9) + 改值提交重排(D10)

前端两触发点(D9/D10)

  • 新增(cfgCurveAddPeriod): 按天数定位插入(默认 1D→day→插最前), 展开态 cfg.openCurves 按实际插入下标记录(现 [list.length-1] 需改)。
  • 改值(period 输入框): @input 逐键写树照旧; @change(失焦/回车)提交时整段重排, openCurves 按条目身份跟随搬移(模式参照 cfgCurveRemovePeriod:65-70)。逐键重排有数据错写风险: v-for 是下标 key(traffic-card.html:169), 重排后焦点所在行数据换条, 继续键入写错条目 —— 故重排只挂提交时机(D10)。
  • JS 解析失败: 与 GET 面同策略 —— 任一 period 解析不了整段放弃(不重排, 新增退回尾部追加)(D8/D11)。

落盘收敛(D7)

被动: 不加启动迁移。乱序磁盘在下次 UI 保存时经整体替换语义自然重排为规范序; 不保存则磁盘保持原序(UI/运行时已有序)。乱序实例曲线段列表项内注释在该次保存丢失一次(当前 config.yml:131-189 已升序, 走 skip 路径无损)。
