1背景与目标

2026-10-21 复盘 A 系计划（26-10-13-0540：删合成回写 + 局部 deferral）是否遗漏了后来入池的三条 post-command-state-writes issue，结论是：

  • 一处真遗漏：跳检收尾的直查回写（_skip_readd 的 apply_delta(live)）违反该计划的不变量，但 §6 清单与静态守阵只覆盖 qbapi.py / store.py，漏网两天 —— 已于 2026-10-21 S2（c48ba02e）修复。
  • 一处判断分歧：写命令后的补刷新。计划 §5 判定「读到节流缓存不是缺陷，是 A 系特性」，但没考虑它把下次同步推后一个周期。
  • 一处明文非目标：tags / category 的写后同步（计划 §11 明确不改）。
  • 一处机检缺口：验收口径写「全库」而守阵只扫两个文件。

本计划处理复盘后仍然成立的四件事，一一对应四条 issue：

  • 删除「提交前直查运行状态」这条通道（含跳检与 recheck 两处），重复提交保护回到「在途登记 + 快照」。
  • 把「哪些字段可写后同步、哪些必须等上报」写成单点口径，并修掉唯一有真实副作用的一处（save_path）。
  • 守阵扫描面覆盖 src/auto_qb/**，让「全库」成为机检事实。

4设计

4.1 补刷新不推后计时

现状（qbmanager.py 主循环）：只要本批命令改了 qB 状态，sync_due 立刻为真，跑一次补刷新，并无条件把 next_sync_at 推到 now + sync_interval。若这次补刷新读到的是同一份节流缓存，就等于白刷一次、还把校正推迟了一个周期。

sync_due_by_time = now >= next_sync_at
sync_due = sync_due_by_time or (cmd_changed_state and not dry_run)
... 跑 _tick / _sync_line ...
# 只有「按时到的」或「这次真的拿到了变化」才重设节拍
if sync_due_by_time or self._sync_moved():
    next_sync_at = time.time() + sync_interval
# 否则: 保持原 next_sync_at 不变 —— 白刷一次, 不惩罚下一次校正

判据 _sync_moved()：本轮 store.delta_fields / last_added / last_removed 任一非空。它只是「qB 缓存是否前进」的代理，不是真值判断 —— 与 A 系「快照 = 同步结果」的口径一致。

边界

① rid 失效触发的全量轮一定带 patches，_sync_moved() 为真 ⇒ 照常重设（与今天一致）。② 空库/静止种子库的补刷新会一直保持原节拍，不会出现"每轮都补刷"的放大。③ 不动 next_tick_at（任务线节拍与命令无关）。

4.2 移除提交前复核

删掉 ops_mod._live_recheck 与它的两处调用。两处的替代如下：

位置今天改后
recheck 提交前直查一次；live 显示在校验则拒绝重复提交不再直查。重复提交保护 = active_check_hashes（在途）+ 快照 is_piece_checking
recheck 进度基线baseline_progress = live[0].progressbaseline_progress = tor.progress（快照）
跳检入口直查确认"种子还在"，不在则干净放弃不再直查。种子已不在时，相位机在「导出 .torrent」失败，文案改为「导出 .torrent 失败(种子可能已不在客户端)」，并由失败路径撤掉残留记录
失败路径的存在性探测_skip_fail 里查一次保留 —— 它不参与放行/拒绝，只决定"清备份还是留恢复凭据"
语义变化（写进提交信息）

「种子已不在客户端」不再在提交前被识别：跳检会先失败在导出步（结果从 skip 变 fail，文案带"可能已不在客户端"）；recheck 的"进度回落"基线从 live 改快照，回落判据的灵敏度略微下降（基线最多旧 1.5s），但判据方向不变。

4.3 写后同步的字段边界

判据只有一条：这个值的事实来源是谁。我们下发的值可以回写（最坏是命令失败、下轮上报纠正）；qB 自己算的值不能回写（写的是预测）。

写方法写后对快照的动作事实来源结论
add_tags / remove_tags / delete_tags改 tags / 全库摘标签我们保留
set_category改 category我们保留
set_upload_limit / set_download_limit改 up_limit / dl_limit我们保留
set_location改 save_path我们改为等上报（分组键输入，搬家是异步的）
rename不写，等同步我们保持（D4）
start / stop / pause / resume只登记 own_writesqB保持（A 系已删净）
recheck / reannounce / force_start / super_seeding / share_limits / auto_management / 队列与文件优先级 / rename_file / rename_folder纯透传qB保持
add_trackers / remove_trackers只失效该种子 tracker 缓存—保留（缓存不是值）
create_tags / edit_category / remove_categories只失效全局定义缓存—保留
torrents_delete摘记录 + _pending_removed 兜底我们（确定动作）保留（D5）
torrents_add纯透传，靠同步入表—保持（"等上报"的样板）
set_global_speed_limits / set_alt_speed_limits不动种子快照我们保持

code-style.md 补一条口径（替换已删除的「写后同步」条）：

写后同步只对「值来自我们」的字段成立: tags / category / up_limit / dl_limit。
运行状态(state / progress / 速率 / seeding_time / ratio)只等 qB 上报, 一律不写。
save_path 例外 —— 它也是我们的值, 但它是分组键的输入而 qB 搬家是异步的, 同样等上报。

4.4 守阵扩容

test_no_synthetic_state_write_site 的扫描面从两个文件扩到 src/auto_qb/**/*.py，并把「正则」换成「AST」—— 正则会把 docstring 里的 source.state="stale" 当成写点（实测 traffic_source/reader.py 就有一例假阳性），也会漏掉多目标/换行的赋值。

判据四条（前三条形似原三条，第四条是这次补的）：

  1. .state = ...（属性赋值）；
  2. setattr(obj, "state", ...)（间接赋值）；
  3. update_torrent_fields(..., state=...)（形参已删，残留即回写通道复活）；
  4. apply_delta(...) 的调用点白名单 —— 只允许出现在 torrents/store.py（同步应用点）与 torrents/record.py（记录类自身）。这条是为历史漏网形态补的：tor.apply_delta(live[0]) 绕过前三条，只有按调用点才拦得住。

白名单（每条必须带理由，理由为空或文件不存在即红）：

文件为什么允许 .state =
core/qbmanager.pyctx.state / self.state —— 状态服务句柄，不是种子记录（2 处）
core/taskqueue.pyTask.state —— 任务状态机（PENDING/RUNNING，6 处）
文件为什么允许调用 apply_delta
torrents/store.py同步应用点（_apply）
torrents/record.py记录类自身（定义 + from_torrent）

实测（AST 扫描，2026-10-21 23:29）：全仓 .state = 命中 8 处，全部落在上述两个白名单文件，无种子记录命中；apply_delta 调用点只有 store.py / record.py 两处。traffic_source/reader.py 的正则命中是 docstring 假阳性，AST 下不存在。

8风险与回退

风险说明 / 处置
跳检"种子已不在"的提示变差从"干净放弃(skip)"变成"导出失败(fail) + 可能已不在客户端"；批量回执里仍按原因聚合，可读性不降
recheck 重复提交变多qB 侧幂等；仅"qB 自家界面刚发起的校验"会多提交一次，日志多一行
补刷新计时判据的代理性_sync_moved() 是代理不是真值：静止种子库的补刷新不会重设节拍（正合期望）；活跃库会重设（与今天一致）
save_path 显示延迟移动后 1.5s 才在 UI 反映；搬迁中的分组判定仍由 relocating_hashes 负责，两条线不打架
回退四期各自独立可 revert：S1 只影响守阵；S2 只影响 save_path；S3 恢复直查；S4 恢复旧计时
