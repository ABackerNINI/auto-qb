§01目标与设计原则

目标 — 移植单位是「轨道」而非单个 skill(收编报告 §2.6-1 实证: T4/T5 的一半移植工作量在 PORTING 没写的地方, 即 skill 目录之外)。改造后的成态判据: 最小移植 = 拷目录 + 填 ≤10 个配置键 + 0 行代码 diff; 且移植到「正在开发中的项目」时, 对存量代码的评审(review.lane)开箱可用。

六条设计原则(改造判据, 源报告 §3):

  1. 配置/数据与代码分离 — 项目词汇(领域枚举)、项目路径(sibling 工作区)、排除表、闸门清单、批次矩阵一律外置; 代码读配置, 无配置回落通用默认。判定法: 换项目不该需要改任何 .py。
  2. fail-closed 守卫必须显式 opt-in — 默认检查链只允许「对新空库恒绿」的成员; 要求「某文件必须存在」的守卫属项目层, 进可选清单(PORTING 标注勿默认移植)。
  3. 环境中立默认值 — 出厂 python3 而非 uv run(脚本纯 stdlib; uv 是项目偏好属配置层); 单远端假设; 无远端是合法稳态(本地分支/离线 bootstrap)。
  4. 测试卫生 — 清理路径先校验后删(非空+不在 cwd/仓库根下); sys.executable 派生子进程防解释器失真; 平台断言一律 os.name 条件化。
  5. 协议与演进史分离 — SKILL.md 是协议, 历史进 references; 本轮只摘要置记, 演进史批量下沉缓行(D14, 实施开工轮入池跟踪)。
  6. 可移植性声明 — 每 skill 一份移植帮助文档(依赖面清单: 需要项目提供哪些数据件/配置键/可选守卫), 双场景指导(新项目绿地 / 开发中途存量, 重点存量)。

配置落点口径(D12/D19/D20): skill 面 = <skill>/config/project.toml(统一名, 项目绑定面单点) + 帮助文档 <skill>/references/PORTING.md; 包面 = 包根先例(.my-commit-flow.toml / 新增 lane.toml); sync 脚本例外 = .agents/skills/.config/sync.toml(点前缀, 避免被 skill 遍历误收)。配置缺失回落语义(D13): 校验类缺失 → 跳过对应校验 + 必打一条提示(禁止静默降级); 运行必需数据(如 lane 批次矩阵)缺失 → 引导性报错。

不变量: ①本项目(auto-qb)行为零变化 — 每批含回归验证; ②对照组(commands/create-issue/scope-guard)零改动; ③第三方 skill 本体一律不碰, 半自制件不改本体、仅按 S8 新增 PORTING 文档(与 D2/D17 口径对齐); ④跨仓红线零消耗 — 验收场地只用仓内沙箱(D5)。
