00审查结论

总判

可以进入 W0，但必须先修 2 处 P0、改正 6 处事实错误。计划的骨架（语料=一条原始流 / 首帧 T0 / 末帧 T1 / 脱敏守恒为头号验收 / 未对齐即停）是这三套测试资产里最扎实的一份设计，不需要推翻。问题集中在「最后一公里」的实现细节：稀疏文件的创建序列、以及头号判据的参考时刻 —— 都不是"再想想"，而是不写死就会出错。

两处 P0（不修则 W1 之后必返工）

  • P0-1 稀疏文件的创建序列写错了。计划写「每文件 2 次系统调用（setflag + truncate）」，但 truncate 会让稀疏标志失效，实占整个逻辑大小。我按这句话的字面意思在 R 盘上跑，第一个 4 GiB 文件就实占 4 GiB，第二个文件直接 ERROR_DISK_FULL。正确的写法（FSCTL_SET_SPARSE + SetEndOfFile）实占 0 字节、0.23 ms/文件 —— 比计划声称的"128 KiB"还好，但必须写死。
  • P0-2 头号判据 CORPUS.group_exact 没定义「在哪个时刻比」。groups.json 按计划是「抓完立刻算」⇒ 对应 T1 终态；而回放从 T0 开始，且回放期 auto-qb 会因缺文件/大小不符暂停整组、按规则删除种子、新种子中途出现 —— 分组是动态的。参考时刻不钉死，这条判据要么空转、要么假红。

03P0 阻断项

P0-1稀疏文件的创建序列写错了，字面实现会写满磁盘

计划 §07 方案 A 写「每文件 2 次系统调用（setflag + truncate）」，并在 §00 报「2 GiB 文件实际占 128 KiB」。这两句都靠不住：fsutil 不是系统调用而是进程派生；更要命的是 truncate 会把刚设好的稀疏标志作废 —— NTFS 必须让新扩展出来的区域"读到 0"，在非稀疏语义下就是实打实分配簇。

我在 D 盘（NTFS，225 GB 空闲）用 100 文件 × 64 MiB 逻辑做了四种写法对照：

创建写法实占每文件判定
CreateFileW → DeviceIoControl(FSCTL_SET_SPARSE) → SetFilePointerEx + SetEndOfFile0.0 MiB0.23 ms✅ 唯一正确；仅 MFT 开销（205 B/文件）
标记稀疏 + os.truncate 计划原文6400 MiB—❌ 满额分配，稀疏标志失效
朴素 seek+write6400 MiB0.72 ms❌ 满额分配
fsutil file createnew 256 MiB → sparse setflag先占 166 MB—❌ setflag 不回收已分配的簇

在 R 盘上的实证后果：按计划字面写法跑，第一个 4 GiB 文件实占 4 GiB，第二个文件抛 OSError: 112（ERROR_DISK_FULL），磁盘当场写满。这不是理论风险，是我刚刚亲手复现并清理掉的现场。

修法：在 §07 方案 A 里把创建序列写成不可含糊的四步，并注明"禁止用 os.truncate / open(...,'wb') 扩展"：

h = CreateFileW(path, GENERIC_WRITE, 0, None, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, None)
DeviceIoControl(h, FSCTL_SET_SPARSE, None, 0, None, 0, byref(n), None)   # 必须先标记
SetFilePointerEx(h, size, byref(pos), FILE_BEGIN); SetEndOfFile(h)      # 再置 EOF
CloseHandle(h)

按此实现，6 万文件 ≈ 14 s、占用 ≈ 12 MB（远优于计划所称的 128 KiB × 6 万 ≈ 7.9 GB —— 那个数字恰好超过 R 盘全部可用空间）。顺带：方案 A 的"回退到 B"也应改成先在建树前探测（试建一个稀疏文件并校验分配量），而不是"第一个文件失败即降级"—— 中途切换会留下半稀疏半实占的混合树。

更正原 P0-2「R 盘空间 API 互相矛盾」不成立 —— 已下调为 P2-6

本报告初版把「shutil.disk_usage("R:/").free = 0 而 Get-PSDrive/df 报 7.3 GB」判为三套 API 互相矛盾，并据此把 R 盘列为 P0。这个结论是错的，错在测量时序。

  • 7.2–7.3 GB 是我写入之前测的（Get-PSDrive 7,735,275,520 B、df 7.3 G）—— 是当时的真值；
  • 0 是我用 4 GiB 满额文件把盘写满之后测的 —— 那一刻盘确实是满的，读数同样正确；
  • 同刻复核（2026-09-21 03:0x）：shutil.disk_usage('R:/').free = GetDiskFreeSpaceExW = df = 18,474,057,728，三口径逐字节相同。不存在矛盾。

把两个不同时刻的读数当成同一时刻的对照，是我的方法错误，与计划无关。更要紧的是：计划原文从未对 R 盘的空间 API 做过任何断言，这条"缺陷"完全是我引入的。R 盘相关的内容已改写为 §05 的 P2-6，只保留经得起复核的部分。

P0-2头号判据 CORPUS.group_exact 缺少参考时刻

计划把"脱敏前后分组逐组一致"定为头号验收项，判据本身是对的。但 groups.json 按 §04 第 5 步是「抓完立刻用同一套 key 公式算一遍」⇒ 对应 T1 终态。而回放从 T0 开始，回放期间分组是会变的：

  • _check_size_consistency 在归组时若发现组内 {路径: 大小} 不一致 ⇒ 暂停整组；
  • _check_missing_files 发现缺文件 ⇒ 整组暂停 + MISSING 标签；
  • 规则动作可能删除种子 ⇒ _leave_group 拆组；
  • 流里中途新出现的种子 ⇒ 新组产生（计划 §04 已明确"出现即 append"）。

于是"回放期 auto-qb 分出的组 == groups.json"这句话，在 t=0 与 t=末尾会得到两个不同答案。不钉死时刻，这条判据不是空转就是假红 —— 而它恰恰是计划自称"合成数据给不了的东西"。

修法：在 §09 明确"group_exact 在首帧应用后、任何写动作发生前求值"（此时与 T0 快照同构，语义最干净）；若确实想验终态，就同时产出 groups_t0.json / groups_t1.json 两份，各在对应时刻比一次。另外：groups.json 若按"抓完算"则含录制期新出现的种子，而 T0 时刻它们还不存在 —— 这一点必须与上面的选择自洽。

04P1 实质缺陷

P1-1「pieceHashes 不抓、现场合成」会让严格模式判据恒假

计划 §03 把 torrents/export / torrents/pieceHashes 判为「不抓（有 hash 可现场合成）」。但 rules/actions/checking.py:145-154 的严格模式是把候选与目标的 piece hash 列表逐项比对：

target = ctx.api.torrents_piece_hashes(ctx.hash)
...
if ctx.api.torrents_piece_hashes(cand.hash) == target:   # 要求两个列表完全相同

真实世界里辅种组成员的 piece hash 必须相同（同文件、同大小、同分块）。若按 hash 各自随机合成，同组成员会互不相等 ⇒ 严格模式判据恒假，比不测更糟（会给出"没有候选通过"的错误结论）。

另外 sim_qb.py 的路由表里根本没有这两个端点（只有 sync/maindata / torrents/info|files|trackers|tags|categories / transfer/* / app/* / auth/login），落到 unknown endpoint: … 404。所以这不是"抓不抓"的问题，而是回放外壳缺两个端点。

修法：piece hash 由 （排序后的「相对路径 + 大小」集合） 确定性派生 —— 同组成员天然共享同一列表，与真机语义一致；export 可返回一个最小合法 bencode。并把"端点覆盖"写进 W3 的验收判据。

P1-2回放端"合并窗口内多帧"的语义未定义

计划 §08 说回放时"把游标推进到当前回放时刻，把这段时间内落过的采样帧合并成一次增量响应"。100 ms 采样 + 2 s 的 main_tick ⇒ 一次响应要合并约 20 帧。窗口内若同一 hash 先出现后删除（或先改再改回），朴素合并会把它当成"存在"；torrents_removed 也需要按序净额化（先删后加 ⇒ 净额是"加"）。

这正是 auto-qb store 自己的语义，必须对齐 —— 否则 D 系列（删除/重复投递/幂等）判据会因合并错误而假红或假绿，且很难归因（看起来像 auto-qb 的 bug）。

修法：在 §08 补一小节"窗口合并规则"，逐类字段写明合并方式（torrents 逐 hash 后写覆盖；*_removed 与 torrents 的净额判定；server_state 仍是 merge）。并给一条守阵：构造"窗口内先增后删"的语料片段，断言回放端不吐该 hash。

P1-3脱敏的等价类风险不止在「名字字典」

计划把单射性校验挂在"伪名字典"上（§05 硬约束）。但归组 key 的第一半是 save_path，而它的处置是「盘符与根目录重映射」—— 这条映射自身也必须单射，计划没要求：

  • 跨盘并组：qB 单实例可有多个盘上的种子。若 R:\Download\TV 与 S:\Download\TV 都映射成 <run>/fs/Download/TV，两组会被合并 ⇒ 回放分组与真机不同。
  • 尾斜杠：utils.path_normalize 的实现是"仅统一分隔符 + 压缩重复斜杠"，刻意保留首尾斜杠（注释里写明是为了区分 c:/windows/ 与 c:/windowsg）。所以重映射必须原样保留尾斜杠的有无，不能顺手 rstrip('/')。
  • 大小写：path_normalize 不做大小写归一 ⇒ 形态守恒替换必须保留大小写分布，不能统一转小写。
  • hash · infohash_v1/v2 → 40 hex：v1 是 40 hex、v2 是 64 hex，一条"40 hex"规则会把 v2 的形状改掉。计划已提 magnet_uri 要同步重写，但 v2 的长度要单独处理。

修法：把 save_path 映射一并纳入单射校验；重映射路径带"原盘符的短令牌"（如 <run>/fs/d0/…）；在 §05 显式声明"尾斜杠与大小写形态 1:1 保留"。这些正是 path_normalize 的等价类边界，值得逐条写死。

P1-4「不碰 src/」与「用 auto-qb 自己的归组公式算真值」互相打架

计划 §04 第 5 步要求抓取端"用 auto_qb.mixins.grouping 的同一套 key 公式算一遍真机分组"，§11 又写"只动 scripts/ 与 docs/，不碰 src/"。这两条同时成立不了：

  • _assign_to_group 是 mixin 方法，签名是 (self, torrent, file_map, dry_run)，依赖 self.store.groups / group_sizes / member_to_key / dirty_groups —— 脱离 manager + store 实例调不起来；
  • 要"调起来"，得在抓取器里拼一个假的 store/manager，成本高且脆弱；
  • 要"复制公式"，就引入了漂移风险 —— 而这恰恰是整份计划最想消灭的东西（"期望值来自真机原始数据"）。

更要命的是：如果抓取端复制了一份公式、而它与 grouping.py:150 悄悄漂移，CORPUS.group_exact 就会拿"错误的期望"去判"正确的实现"，结果是稳定假红或（更糟）稳定假绿。

修法（三选一，需你拍板）：①把 key 公式抽成 src/auto_qb/utils.py 或 grouping.py 里的纯函数（group_key_of(save_path, file_map)），抓取端 import 它 —— 代价是动了 src/，需要你放行（属"范围守恒"例外）；②在 scripts 里复制公式，但必须配守阵：同一份合成输入同时喂给复制体与原公式，断言输出相等（这样漂移会立刻变红）；③抓取端不自己算，改为让 auto-qb 自己产出期望（例如用一次 dry-run 回放，导出它的分组）。

我倾向 ①：抽纯函数是零行为变更的重构，且一次性消灭漂移面；但按本项目的范围纪律，这需要你明确点头。

05P2 需补齐

P2-1「零缝隙」在时间轴意义上不成立

计划说 T0 复用快照的同一 session，"其后各帧是紧接的增量，零缝隙"。但 §04 的流程里，第 2 步（全量 maindata）与开始录流之间还夹着第 3 步：每 hash 的 files / trackers = 10 000 次请求。按 --qps 20 算是 ≈ 8 分钟。

这 8 分钟里 rid 会话不会丢数据（qB 会累积变化），所以"数据完整"意义上成立；但第一个增量帧会把这 8 分钟的全部变化压成一帧，t_seq 时间轴的起点被推后 8 分钟，"变化在 tick 内怎么分布"这件事在最关键的第一段上是失真的。

修法：要么把 files/trackers 抓取与录流并行（独立线程 + 独立 session），要么在 meta.json 记 record_start_offset_ms 并在回放端显式跳过这段。别让"零缝隙"变成读者以为已经解决了的模糊承诺。

P2-2采集期磁盘探测的成本与权限没进风险表

§10 风险表只写了「真机抓取拖慢正在做种的 qB」（HTTP 侧），没写文件系统探测。而 --probe-fs 的代价不小：初轮 6 万次 stat，之后每个检查点增量一轮（20 分钟 × 每 60 s = 20 轮）。更别说：

  • 计划自己把 temp path（下载中文件另存他处）列为"已知边界"—— 这类文件按 save_path 探测不到，会记成 exists:false，与真机语义不符；
  • 目标盘若是网络盘 / 90% 满的虚拟盘（正是本机 R 盘的情形），stat 延迟会显著放大；
  • 探测读的是真实下载盘，属于侵入式观测，风险等级应与"100 ms 采样"同级。

修法：把「磁盘探测负载 + temp path 覆盖」升为 W0 必测项，并给 --probe-fs 加 --probe-sample 限流与"只探存在项"的默认。

P2-3config.yml 口径自相矛盾，凭据泄漏面没封

§10 风险行写「抓取器不得读取/写入 config.yml（红线文件）」，紧接着同一句又给「或 --from-config 只读解析」。两句话互斥。项目红线原文是"禁止改动/提交"，读是允许的，所以正确的表述应该是"不修改、不提交；允许只读解析"。

同时有一个没被点到的泄漏面：config.yml 里存着 qB 密码。抓取器若把"使用的配置来源"或凭据写进 meta.json，语料就带上了凭据。计划说了"盐不落盘"，但没说凭据。

修法：改正 §10 措辞；在 §05 字段分档里加一条「凭据绝不进入语料 / meta.json / warnings.jsonl」，并让 --self-test 扫一遍语料目录做凭据串匹配。

P2-4语料档会继承现有 HTTP 外壳的端点盲区

计划说"HTTP 外壳、rid 语义、写端点记账、B1–B4、emit_config、self_test 全部可原样复用" —— 这话对，但也意味着语料档覆盖不到 sim 未实现的端点。除了 P1-1 的两个，还有：

  • sync/torrentPeers —— sim 没有这个路由（会 404），而 web.py:747 的 WEB 详情抽屉会调它；计划 §03 把它列进"抓（可 --skip-peers）"，但没提回放端要补实现；
  • WRITE_ENDPOINTS 只有 24 个，而 qbapi.py 门面有 51 个方法 —— 差额里的写端点会 404。

所以"合成数据从未覆盖的路径会被语料覆盖"这句承诺，需要加上边界：覆盖范围 = 现有外壳已实现的端点集。W3 验收应加一条"逐端点清单核对：语料档覆盖的端点 ⊇ 语料里出现过的端点"。

P2-5W6「闭环 8 条走查」是过度承诺

计划 G5 与 W6 承诺"用真实语料回放，把 activeContext.md 里那 8 条待真机走查先过一遍，减少往返"。两个问题：

  • 实际是 约 15 条，不是 8 条；
  • 更关键的是构成：绝大多数是前端观感项 —— 右键菜单响应、3000+ 种子滚动流畅度、追剧页三级右键、状态栏双色图标是否分得清、五主题下配色是否协调、列设置多标签页互不覆盖、今日流量目视…… 这些要的是"人在浏览器里看"，回放 qB 数据面根本测不到。

真正与数据面相关、可能被语料回放覆盖的只有少数几条（如「TASK015 错误种子原因 —— 错误态状态列是否显示 tracker 原文」「视图重建范围收口 —— 速度是否随轮询刷新」）。

修法：W6 收窄为"数据面相关的 N 条"并逐条列出，其余明确标注"仍需真机目视"。否则这条验收会把"没闭环"记成"闭环了"，比不写更危险。

P2-6语料落 R 盘：可用空间与持久性都没评估（原 P0-2 的更正版）

计划 §10 与 §12 推荐语料落 R:/auto-qb-sim/corpus/<日期-标签>/。这块盘经得起复核的事实是：

剩下两个真问题（都不是"不能用"，而是"没写"）：

  • 可用空间没进流程。R 盘同时是 qB 的真实下载盘（qBittorrent 正在运行），可用空间在 7–18 GB 之间波动。正确实现下物化树只占 ~12 MB、语料 ~50 MB，完全放得下；但计划没有任何"落盘前查一下可用空间"的步骤 —— 一旦实现退回满额分配（见 P0-1），就会直接撞上"下载盘写满"。加一条建树前的可用空间预检即可（这条建议仍然成立，只是理由变了）。

审查要对称。下面这些设计我认为不需要改，而且明显优于替代方案：

  • 等价类守恒作为头号验收、且是阻断式的（不一致即不落盘）—— 判断准确。合成数据永远给不了这个。

  • 中间检查点"抓而不存" —— 由"增量流完整 ⇒ 中间全量可重建"推出的结论成立，省掉 160 MB 落盘。
