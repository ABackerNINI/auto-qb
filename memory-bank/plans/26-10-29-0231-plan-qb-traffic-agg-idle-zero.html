§01目标与设计原则

目标

  • 做到：agg 段窗（3d/7d/30d 的 hour 桶、6mo/1y 的 day 桶、all 的 month 桶）里，凡是「采样在跑且速率确实为 0」的小时，图上出 0 值点；hover 出 0 桶状态行，不是「无采样」。
  • 做到：跨天（00:00 硬切）后新一天的整段空闲，不再出现「从 00:00 一直到现在的整片斜纹」。
  • 不做：不改前端（`qb_traffic_chart.js` / `drawer.html` 的 null 与 0 本就分开渲染）、不加配置键、不改落盘格式、不动 raw 段（1m–24h）语义。

设计底线 / 不变量

  1. 合成行 = 封口行的前缀：同一时间区间必须用封口路径的同一套纯函数（`_agg_credit_hours` / `v4_z_totals_ramp` / `v4_hour_agg` / `v4_rollup_agg`）算出来。这样落盘后读侧 `v4_merge_agg` 合流不会出现第二口径（项目已有 R07/R10「同源双实现」旧账，不再加一份）。
  2. totals 单调不回退：合成行的 `dl_total/up_total` 取游程末端锚点（= `_resolve_run_end` 用的同一个值），保证 `v4_merge_agg`「totals 取后封行」时拿到的是更晚的快照。
  3. 归因诚实：z 游程 = 已知 0（可画 0）；n 游程 = 断连未知（必须留 null）。合成末端取 `run.last_seen`，不推到 now —— 采样停摆时不能凭空造覆盖。
  4. 覆盖不双计：合成区间从 `open_credit` 槽位起算，与磁盘已封区间天然互斥；合流后 cov 截到桶宽 3600。
  5. 单写线程不变式不动（黄金法则 5）：合成只在主线程 `_publish_live_tail` 内读内存累计器，产出不可变 tuple 后整体替换引用。

三个关键证据

  1. 空闲期确实一条 hour 行都不产（子代理实测，26-10-29）：空闲 09:00:30 → 10:00:00，agg.dat 不存在、pending = {}、OpenRun(kind='z', samples=120)。
  2. 跨天是「昨天补上、今天全空」的分水岭：00:00 硬切把前一日整段空闲封口补记成行（实测 23:00 行在跨天后落盘，dl_avg=0, cov_s=3570）—— 所以昨天以前的 0 线是对的；同时新开一个 z 游程并一直不封口，新的一天从 00:00 起整段 null，直到出现第一个非零样本。这正是「特别是跨天后」的机制解释。
  3. raw 段没有这个病：v4_live_tail_slots（traffic_store.py:513）会把开放游程按未来封口形态合成 z 槽（obs = (0,0,快照)）⇒ 24h 视图有 0 线。agg 段缺的就是这条同款路径 —— 这是「只有 3 天及以上才犯」的直接原因。

影响面

  • 三个作用域全中：global / group（成员逐个合成）/ torrent（单种空闲即整段 null）。
  • 6mo/1y 的当日行同款：`_pending_agg_rows` 的 day 行由 hour_partials 逐级 rollup，hour 缺段 ⇒ 当日行 cov 偏小；all 的当月行再往上一级同样。
  • 窗口内累计（`qbCurSummary`）不受影响：null 桶本就不计。

§03方案总览

主线（D1 拍板：写侧活尾合成）

在 _pending_agg_rows 的入口把「未结算 credit + 开放游程」合成进 agg.pending 的副本，其余逻辑（逐桶 v4_hour_agg → day/month 逐级 rollup）一行不改。合成段本身复用封口路径的两个既有纯函数，不新增任何聚合语义。

载体边界（别与方案③混读）：合成出来的是内存 AggRow 元组，只挂进活尾快照 LiveTail.pending_agg 供 Web 读侧按请求消费 —— 不进 agg.dat、不写天文件、不切记录，每轮采样末尾整体重建替换（不累积），进程一重启就没了。磁盘上仍然只有封口行（00:00 硬切 / 非零样本 / stop() 产出），封口路径 _agg_flush_series → _agg_append 读的仍是 agg.pending 本体（合成只进副本，故零影响）。所以「空闲 8 小时出 8 条 hour 部分行」描述的是读侧这一刻能拿到的行，不是落盘了 8 条；写放大为 0，落盘格式与文件布局不变。方案③（按小时 _seal_run 落盘）换来的「重启不丢」被明确放弃，代价记在 §05 观察项。

合成口径（伪代码，落实时按此实现）

# 新增：纯切段（与 _agg_credit_hours 的切段规则同源，单测可直接喂）
def _hour_spans(start, end) -> list[tuple[float, float]]: ...

# 新增：未结算 credit + 开放游程 -> hour 桶样本（每段恰 1 条，O(小时数) 不是 O(槽数)；不接收 now）
def _open_run_hour_samples(agg, run) -> dict[int, list]:
    out = {}
    credit = agg.open_credit                      # (槽位, dl_rate, up_rate, dl_total, up_total)
    if credit is None:
        return out                                # null 期后无观测：不猜
    if run is None:
        return out                                # 无开放游程 = 无「仍在采样」证据，不把信用推到 now（R1 修订）
    # (1) credit 段 [上一记录末槽, 游程首槽) 按上一记录速率 —— 与 _agg_feed 结算口径逐字一致
    _agg_credit_hours(out, credit[0], run.start, *credit[1:])
    if run.kind != "z":
        return out                                # n 游程：断连不可归因，之后留 null（D3）
    # (2) 游程内速率恒 0，totals 按末端锚点逐段摊配（与封口时 v4_z_totals_ramp 同源）
    spans = _hour_spans(run.start, run.last_seen)          # 末端 = last_seen，不推 now（D2）
    ramp = v4_z_totals_ramp(run.dl_total, run.up_total,
                            run.last_dl_total, run.last_up_total, max(len(spans), 2))
    if len(spans) == 1:
        ramp = ramp[-1:]                          # 单段 = 整条游程：取末端锚点（R1 修订）
    for (s, e), (dl_t, up_t) in zip(spans, ramp):
        _agg_credit_hours(out, s, e, 0, 0, dl_t, up_t)
    return out

# 改：入口合流副本（agg.pending 本体不动，封口路径零影响）
def _pending_agg_rows(agg, run, now):
    merged = {h: list(v) for h, v in agg.pending.items()}
    for h, samples in _open_run_hour_samples(agg, run, now).items():
        merged.setdefault(h, []).extend(samples)          # 同桶相加，cov 由 v4_hour_agg 截到 3600
    ... # 其余逐桶 v4_hour_agg / day / month rollup 原样不动
为什么不是另两条路（D1 的取舍记录）：
② 读侧合成（给 LiveTail 加 credit 字段、在 traffic_grid 里按请求算）：读侧要复刻 credit 切段 + totals 摊配，等于把封口口径写第二遍 —— 正是 R07/R10 那类旧账。
③ 按小时封口落盘（_advance_run 跨小时界就 _seal_run）：磁盘数据确实更完备（能扛重启），但每个有空闲游程的系列每天 z 记录从 1 条变 24 条（24× 写放大），raw 段记录数跟着涨；收益只是「重启后那段不丢」，不值得在这一轮付。
