HR 排除功能: 按标签/分类把种子排除出 HR 体系

给 HR 管理加一个用户显式的退出通道: 命中配置的标签/分类格式的种子, 不再打 HR 标签/分类、不参与站点侧在线核实判定、规则条件一律按「未触发」——一个配置键, 四个消费点全部生效(判定单点)。全局与站点两级配置, 列表取并集, 排除态在 WebUI 可见。

状态 Open 日期 2026-09-28 范围 config / torrents / webui / tests 判定单点 torrents/record.py

01背景与问题

HR 体系当前有四个消费点, 全部经由 TorrentRecord 的三个判定入口(check_hr_condition / check_hr_satisfied / hr_judgement, 单点语义):

消费点位置消费入口
HR 标签/分类维护core/mixins/tags.py:147,153 _add_hr_tag_or_categorycheck_hr_condition + check_hr_satisfied
规则 hr 条件rules/conditions.py:159-164同上
表达式 tor.hr_condition_met / tor.hr_satisfiedrules/expr/env.py:303-304同上
WebUI HR 列 / 站点侧字段webui/views.py:284-286三者 + hr_judgement 直调

问题: 只要站点配了 hr 段, 该站种子一律纳入 HR 管理, 没有任何用户侧退出通道。实际使用中存在「这几个种子我不想让程序按 HR 管」的需求(例如用户手动标记过的种子、站点已免罪但程序侧没有证据的种子), 目前只能整站关掉 hr 段 —— 粒度是站点级, 不是种子级。

02目标与非目标

目标

  • 可配置的种子级排除: 按标签与分类两种维度, 复用全项目统一的匹配语法(regex: 前缀 / :ignore_case 后缀, 单点 utils.MatchPattern)。
  • 两级配置: 全局 hr 段 + 站点 trackers.<站点>.hr 段, 列表取并集。
  • 排除语义贯穿全体系: 判定单点改一处, 四个消费点自动生效, 不在消费点散落分支。
  • WebUI 可见: 排除态在 HR 列有明确显示, 不与「未触发」混淆。
  • 零静默变更: 不配排除键 = 现状逐字节一致(延续 HR 在线核实的零静默变更闸门传统)。

非目标

  • 不回撤已打的 HR 标签/分类(只停管, 不清洗)。
  • 不省站点侧取数配额: HR 清单是账号级全量, 翻页与 .torrent 回填照旧; 排除只省本地判定。
  • 不新增排除事件/告警(排除判定每种子每轮都在发生, 只有 DEBUG 级日志)。
  • 不做「排除但站点侧仍显示」的混合态。

03语义定义

排除 = 该种子从 HR 体系整体退出, 且优先级最高:

维度排除后的行为
打标/分类触发与达标两个分支都不进 —— _add_hr_tag_or_category 经 check_hr_condition 早退, 不再写任何标签/分类
在线核实hr_judgement() 返回 None —— 站点已接入也不判定; WebUI 站点侧字段(hr_site_*)留空
规则条件hr 条件按「未触发」(condition-not-met 匹配); tor.hr_satisfied 为 False
优先级排除 > mode=all > unknown_policy > 新鲜度闸门 —— 用户显式排除压过一切保守管束, 与既有「豁免压过清单」先例(completed_age_limit / 豁免 A / 豁免 B)同构
生效时机判定时现算(读 tracker_conf.hr 排除表 + 种子当前 tags/category): 在 qB 里加/删排除标签, 下一轮维护即生效或恢复管束, 无需重启
存量标记已打的 HR 标签/分类残留不动, 程序不再触碰; 需要清理由用户手动(与达标流「只加不摘」的既有口径一致)
排除 = 自愿放弃管束。被排除的种子若实际仍在站点考核期, 程序不会替用户盯它 —— 与超龄豁免/豁免 A/B 同一性质的漏管风险, help 文案必须写明。

04配置设计

键与语法

全局 hr 段与站点 trackers.<站点>.hr 段各加两个键(格式列表, 复用 remove_tags 的 pattern_list 语义):

hr:
  add_tag: "!!HR${required_seeding_time}!!"
  exclude_tags: ["noHR", "regex:^skip.?hr:ignore_case"]   # 命中任一标签格式的种子 => 排除出 HR 体系
  exclude_categories: ["free"]                            # 命中分类格式的种子同样排除

trackers:
  某站点:
    hr:
      required_seeding_time: 3D
      exclude_tags: ["site-nohr"]    # 站点段: 在全局之上追加, 与全局取并集

合并语义: 并集, 不是覆盖

  • 最终排除表 = 全局列表 ∪ 站点列表(去重保序), 在 load_tracker_hr 合并进站点 HRRule —— 下游只读合并结果。
  • 理由: 输出设置(add_tag 等)是标量, 「站点覆盖全局」成立; 排除是列表且语义是收窄管束面 —— 站点段只应允许「在全局之上再加排除」。若做覆盖, 「站点段写了排除就静默丢了全局排除」是不可预期的陷阱。
  • 排除键只允许收窄、不允许「反排除」(不做 ! 取反语法) —— 保持匹配语义与 match_tag_patterns 完全一致, 不发明新语法。

匹配口径

  • 标签: 对种子 tags_set 逐个 utils.match_tag_patterns(精确或 regex: 正则, :ignore_case 后缀忽略大小写)。
  • 分类: 对 category 单串同款匹配(一个种子只有一个分类)。
  • 默认大小写敏感; 空列表/缺省 = 无排除 = 现状。

判定单点: torrents/record.py

def _hr_excluded(self) -> bool:
    # """HR 排除(计划 26-09-28-1805): 命中 hr.exclude_tags/exclude_categories 的种子
    #  不纳入 HR 体系 —— 判定时现算, 加/删排除标签下一轮即生效; 空表零成本。"""
    hr = self.tracker_conf.hr
    if hr is None or (not hr.exclude_tags and not hr.exclude_categories):
        return False
    if hr.exclude_tags and any(match_tag_patterns(t, hr.exclude_tags) for t in self.tags_set):
        return True
    return bool(hr.exclude_categories) and match_tag_patterns(self.category, hr.exclude_categories)

# 三个判定入口顶部各一行短路:
def check_hr_condition(self):  # → if self._hr_excluded(): return False
def check_hr_satisfied(self):  # → if self._hr_excluded(): return False (显式, 不依赖传递)
def hr_judgement(self):        # → if self._hr_excluded(): return None (覆盖 views.py 直调点)
为什么 hr_judgement 也要短路: webui/views.py:286 直调它取站点侧字段, 只改两个 check_hr_* 会出现「触发=否 但 站点档位照显」的自相矛盾展示; 三入口一起短路后, 排除种子在 WebUI 呈现与「站点未接入」同构的干净空态。

09取数侧为什么零改动(论证)

  • HR 清单是账号级全量: 取数线程按站点页翻页取行, .torrent 回填按「清单行缺 infohash」驱动(service._fill_infohashes) —— 本地排除无法映射回 tid(要先有 infohash 才知道是哪个种子, 鸡生蛋), 本来就不存在可省的配额。
  • 排除种子的 infohash 仍在站点索引里, 但判定侧(hr_judgement)不再消费 —— 纯本地计算, 无配额含义。
  • 锚点供给(qbmanager._hr_anchors)保持全量: 锚点是失效信号不是管理动作, 不区分排除与否可保持「放行作废」语义零变化; 用户日后删掉排除标签恢复管束时, 判定链路即刻完整(放行记录、对账撤销全部照旧)。

10不做的事

  • 不回撤已打的 HR 标签/分类, 不清洗 auto_categories 存量(需要回撤是另一个显式需求, 单独立项)。
  • 不做排除事件/告警、不做排除统计报表。
  • 不做「反排除」(! 取反)语法与站点覆盖全局的合并语义。
  • 不把排除标签纳入 /api/tags 的 exclude_auto 程序自动维护标签过滤 —— 排除标签是用户手动维护的, 本来就该出现在候选里。
