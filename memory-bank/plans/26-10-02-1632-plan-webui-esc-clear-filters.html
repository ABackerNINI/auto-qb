01

结论与拍板建议

判定

ESC 绑「清除全部筛选」不会造成混乱 —— 条件有三: ① 触发点走 lifecycle.js Esc 退栈链的终端兜底(排在全部 16 层浮层 pop 与清选择/收展开兜底之后); ② 新分支带门条件(数据页 / 非输入态 / 无 hrPop 卡 / 面筛有值); ③ 触发时 toast 点名, 不静默。三条在 §05 改动清单里全部落死。

反过来, 若按 issue §03 的字面建议「把 ESC 设为 clear-filters 的默认绑定」走引擎键表, 会造成真混乱(双触发 / 面板改键语义崩坏 / 守阵倒退), 该路线在 §04 明确否决。

拍板建议: 采纳方案 A(退栈链终端兜底)。按键表侧 clear-filters 保持空位不变 —— 用户仍可在面板给它自定义别的键, 与 ESC 兜底双路径并存、互不冲突。前案 26-09-28-0354 §08 C5「Esc 是唯一固定键」的设计决策原样保留。

02

现状事实 (代码调研, 2026-10-02 @ develop c02e9e14)

  1. ESC 是唯一固定键: shortcuts.js 注册表条目 clear-esc(def "Escape", fixed: true, run: null, 语义「清除选择 / 逐层退栈」), 实现归 lifecycle.js 既有退栈链(FIX-07); 引擎入口 _kbOnKeyDown 第一行 if (e.key === "Escape") return;, 且引擎监听注册序排在退栈链之后(双保险)。文件头注 L11-13 与注册表注释两处写明此设计(前案 §08 C5)。守阵 test_web_shortcuts.py:221(注册序)与 :228(引擎对 Escape 早退)是断言级约束。
  2. 退栈链形状(lifecycle.js:48-73): 一条 else-if 链, 一次按键只走一个分支 —— 16 层浮层 pop(确认框 → 添加种子 → 统计 → 限速 → 管理 → 标签编辑 → 文件优先级 → 抽屉 → 历史 → 表头菜单 → 列选择器 → 界面切换 → 搜索浮卡 → 快捷键帮助 → 筛选器下拉 → 右键菜单) + 4 个兜底(清选择 → 收组展开 → 收集展开 → 收剧展开)。链 handler 无 stopPropagation, 也不检查输入态(见事实 10 的既有 quirk)。
  3. clear-filters 是空位动作: shortcuts.js:292 def ""(默认不绑定, 可自定义), scope list, run → vm.clearFilters()。
  4. clearFilters() 的字段清单(filters.js:76-86): 清 kindFilter / pathFilter / tagFilter / categoryFilter / siteFilter / hrFilter / hrSrcFilter 七项面筛 + filterMenu + expandedKey; 不清 searchQuery(搜索词归 clearSearch(), 单独一条)。
  5. filtersActive 含搜索词(filters.js:113): 七项面筛之外还算 searchQuery.trim() —— 它是顶栏按钮的启用条件, 不能直接拿来做「clearFilters 会改变状态」的门(只设了搜索词时它为真, 而 clearFilters 空转)。
  6. 顶栏按钮(topbar.html:274-277): 「清除筛选」常驻占位, :disabled="!filtersActive" —— 面筛是否激活有现成的可视指示。
  7. 用户无法把任何动作绑到 ESC: 录制器捕获段按 Esc 即取消录制(shortcuts.js _kbOnRecordKey), fixed 条目不进冲突检测 —— ESC 在面板体系里完全不可触碰。
  8. hrPop 悬停卡(hr.js:61,173-175): HR 在线核实悬停卡有自己的 document 级 Esc handler(无条件 hrPopHideNow()), 它不在退栈链与 escBusy 名单里。
  9. escBusy(dialogs.js:485): 与退栈链同一名单(含兜底段), 是 config_hub「Esc 返回设置首页」的守门。若新兜底能在设置页触发, 就必须同步进 escBusy —— 方案 A 用 page 门把这个场景整个挡掉, escBusy 零改动。
  10. 既有 quirk(本计划不修): 链 handler 无输入态门 —— 焦点在搜索框里按 ESC, 现在也会清选择/收展开。另: 设置页按 ESC 会隐式触发这些兜底(列表态不可见但仍在)。新分支自带输入态与 page 门, 比同链兄弟分支更严; 既有分支不回改(范围守恒)。
  11. page 取值: 数据三视图 page === "groups"(view.js:78-82 goView 落点), 设置页 page === "settings"; viewMode ∈ {groups, torrents, shows}。引擎 _kbRows() 同款判据。
03

混乱性分析: 五个向量 × 两条路线

「混乱」拆成五个可判定的向量, 逐一看两条实现路线下的表现:

混乱向量路线 B · 引擎键表 (def = "Escape")路线 A · 退栈链终端兜底 (推荐)
① 双触发
一次按键干两件事		 真实存在: 链 handler 不 stopPropagation, 引擎若也接 Escape, 同一次按键「关浮层 + 清筛选」并发, 浮层开着筛选就被清了。 不存在: else-if 链一次只走一个分支; 引擎对 Escape 依旧早退, 触发路径单点在链上。
② 面板 / 录制器语义
改键体系是否自洽		 崩坏: clear-esc(fixed)与 clear-filters 同显 Esc 两个条目; 录制器按 Esc = 取消, 用户永远录不进也改不掉; fixed 不进冲突检测, 改键出现死区。 无感: 键表零改动, clear-filters 仍显示空位可自定义; 面板/帮助浮层只改 clear-esc 的 label 文案。
③ 与浮层关闭语义冲突
ESC = 关浮层的反射		 取决于引擎侧的浮层屏蔽 —— _kbOverlayBusy 名单与链/escBusy 名单必须三处同步, 漏一处就是「关浮层顺手清筛选」。 结构上免疫: 新分支排在 16 层 pop 之后, 只要任何浮层开着就轮不到它; 筛选器下拉先收、面筛后清, 语义连续。
④ 反射连按误清
连按 ESC 退层时顺手清掉辛苦搭的筛选		 同样存在, 且引擎路线没有「一层一层退」的减速带。 可控: 链本身就是减速带 —— 连按时先清选择、再收展开, 面筛排最末; 触发即 toast 点名; 面筛是纯前端视图态, 无后端命令、无落盘、顶栏按钮一键可见, 非破坏性。
⑤ 输入态 / 非数据页误触 引擎有 inInput / scope 五值屏蔽, 本向量无差异。 门条件挡死: 数据页(page === "groups") + 非输入态 + authOk 四重门; 设置页 / 登录遮罩期 / 搜索框内按 ESC 都到不了这个分支。

心智模型: 为什么「清筛选」放兜底最末是自洽的

退栈链的隐喻是 LIFO: 最后建立的状态最先退。链已经把「清选择 / 收展开」设为兜底 —— 即项目早已接受「ESC 可以逐层退掉列表视图态」; 面筛与展开同属「数据可见范围的收窄态」(clearFilters() 本身就复位 expandedKey, 两者本就是同族操作), 排在兜底最末 = 视为退栈深度最深的一层, 不引入新的心智负担。而「筛选 → 选择 → 浮层」的使用顺序与退栈顺序互为逆序, 与既有四层兜底的次序感一致。

什么情况才算「会造成混乱」而没有被化解: 一次按键干两件事(①)、键表自相矛盾(②)、浮层开着清筛选(③)。三条在路线 A 下结构性不存在; ④⑤属「误触成本」而非「混乱」, 已由减速带 + 门 + toast 压到与既有兜底同级。

04

方案决策

方案 A · 退栈链终端兜底 (推荐, 本计划主体)

在 lifecycle.js 退栈链最末(收剧展开之后)加一个分支, 门条件四件套 + toast。键表、面板、录制器、冲突检测、后端 /api/keys 全部零改动; 尊重前案 §08 C5「Esc 是唯一固定键」; diff 最小。

方案 B · 引擎键表 (否决)

把 clear-filters 的 def 改为 "Escape" 并让引擎接 Escape。四条否决理由: ① 与退栈链双触发(§03-①); ② fixed 语义与冲突检测崩坏(§03-②); ③ 守阵 test_web_shortcuts.py:228「引擎必须对 Escape 早退」要改 —— 那是前案 §08 C5 的设计决策, 等于倒退; ④ 帮助浮层出现两个 Esc 条目, 面板语义混乱。

方案 C · 给 clear-filters 配其它默认键 (不采, 不答本题)

例如默认绑 Ctrl+Shift+X。超出本题(issue 只问 ESC); 空位维持, 用户想要键位可自行在面板录制。

5.1 filters.js — 新增 computed facetsActive

放在 filtersActive 旁。不含 searchQuery —— 语义是「clearFilters() 会改变状态」, 与 clearFilters 字段清单同源; 未来加面筛字段时两处同步(注释写明)。

/* 面筛(不含搜索词)是否有值: Esc 退栈链「清筛选」兜底的门 —— 与 clearFilters 字段清单
 * 同源, 新增面筛字段时两处同步; 搜索词不算(归 clearSearch, Esc 兜底不动它) */
facetsActive() {
  return !!(this.kindFilter || this.pathFilter.length || this.tagFilter.length ||
    this.categoryFilter.length || this.siteFilter.length || this.hrFilter.length || this.hrSrcFilter.length);
},

5.2 lifecycle.js — 退栈链终端兜底

handler 顶部(Escape 早退之后)算一次输入态判定(与引擎 _kbOnKeyDown 同式, 仅新分支消费, 不改既有分支行为); 兜底最末(收剧展开之后)加分支:

document.addEventListener("keydown", (e) => {
  if (e.key !== "Escape") return;
  const inInput = !!(e.target && e.target.closest &&
    e.target.closest("input, textarea, select, [contenteditable]"));  // 仅清筛选兜底消费
  ...
  else if (this.expandedShows.length) this.expandedShows = [];  // 兜底: 收起追剧剧展开
  // 兜底最深一档: 清全部面筛(26-10-01-2108 拍板) —— 仅数据页 + 非输入态 + 无 hrPop 卡;
  // 搜索词不清(归 clearSearch); 触发即 toast 点名, 不静默。门条件缺一不可:
  // page 挡设置页(escBusy 无需同步), inInput 挡搜索框, hrPop 让"收卡"独占该次按键
  else if (this.authOk && this.page === "groups" && !this.hrPop.open && !inInput && this.facetsActive) {
    this.clearFilters();
    this.toast("已清除全部筛选(搜索词保留)", "ok", 2500);
  }
});

同时更新链顶注释(L48 附近): …→ 清选择/收展开兜底 后补 → 清筛选兜底(仅数据页+非输入态, 26-10-01-2108)。

07

风险与不做的事

风险与既有化解

  • 反射连按误清: 链位减速带 + toast 点名已缓解; 若真机走查后仍嫌误触率高, 后续可在面板加「Esc 兜底范围」开关 —— 不在本轮。
  • IME 组合期: 组合期 keydown 的 e.key 多为 "Process", 不命中链; 焦点在输入框时另有 inInput 门。链 handler 现无 isComposing 门是既有形状, 新分支不单独加(与同链兄弟一致), 真机走查覆盖中文输入法场景。
  • 预鉴权: 新分支带 authOk, 比同链兄弟分支更严; 不回改既有分支。

明确不做(范围守恒, 撞见即入池不修)

  • 不修「搜索框内按 ESC 也清选择/收展开」的既有 quirk(链 handler 无输入态门的另一面)。
  • 不动 escBusy(新分支被 page 门挡在设置页场景外, hub 守门无需同步)。
  • 不给 clear-filters 配其它默认键、不动 KB_BLACKLIST、不动录制器与冲突检测。
  • 不做「Esc 兜底开关」配置项(避免新增配置键与面板面)。
