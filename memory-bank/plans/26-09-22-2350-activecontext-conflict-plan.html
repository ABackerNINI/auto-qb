activeContext 多 clone 冲突治理

冲突的根因不是 agent 手滑，而是把并行会话状态塞进了单文件这一串行媒介： 每个收尾 DoD 都必写、最热写点又集中在文件头同一段。本方案把「每会话重写头部同一段」改成 「新增 / 更新自己的时间戳切片」，把长青职能交还各自的真实归属，再用只读预检兜底 —— 让冲突在结构上不可能发生，而不是更小心地合并。

01

问题定义与现场证据

2026-09-20 起工作区模式为多 clone 并行：每个 AI 实例一份完整克隆（独立 .git）， 跨 clone 同步一律走 Gitee develop，禁 rebase / 禁 stash、非快进合并遇脏工作区会连坐删除 .git/objects（三次 rebase 事故实证）。在这个约束下，git 合并冲突的处置成本被环境放大到危险级。

三个放大因素

因素现场证据（均为库内实记录）
写点重叠最热改动集中在头部同几十行 「最后更新」是滚动替换式设计：每个会话把旧状态嵌进「其前一条状态」，即每个会话都重写文件头同一段
高频 每个执行轮收尾必写（DoD 第 1 步）；仅 09-22 一天，该文件头部就滚动叠加了 5 个时段的会话状态（22:38 / 22:19 / 21:58 / 20:55 / 20:38）
反馈滞后 冲突不在写入时暴露，push 被拒才暴露；且本环境合并即高危 —— W1–W3 合并事故中，唯一冲突文件恰是 memory-bank/testing.md，提交后又有 12 条 D（scripts/ 整目录只在工作区消失）
现有防线评估 12 KB cap、流水账禁令、先同步后开工 —— 这三道防线缩小的都是爆炸半径（文件更小、冲突块更短、暴露更早）， 没有一个动到「写点重叠」这个根因。 collaboration.md 现行口径「合并冲突交用户主导解决」本质是承认冲突必然发生、 然后把处置成本转嫁给用户。
02

根因分析：写点热力清单

把收尾 DoD 与会话协议涉及的全部共享写点按热度排一遍，可以看到 activeContext 不是孤例，而是最热的一个：

写点频率改动形态撞概率现状
activeContext「最后更新」栈头部滚动替换每执行轮同段重写极高用户主导手工合并
activeContext「正在进行」每执行轮共享列表增删改高同上
testing.md 顶部基线行每次全量后同一行替换高W1–W3 事故的冲突点
progress/ 迁入完成任务时分区追加中同上
pitfalls/<类>/<主题>.md遇新坑不同文件为主低罕见
tasks/_index、pitfalls/_index生成物每次收尾整文件重写可解重跑生成器即解（已有标准做法）

最后一行给出了本项目已经验证过的出路：把「手写的源」降级为「数据」，把视图降级为生成物， 冲突的解决方式就从「人工合并两版文本」变成「任取一方、重跑脚本」。SKILL.md 反模式一节对 tasks/_index 的表述正是如此。 本方案做的事，就是把 activeContext 也搬上这条已经跑通的模式。

职责混杂是深层根因

activeContext.md 目前同时承载两种性质相反的状态：全局项目焦点（定案口径、下一步候选、待走查指针 —— 低频、共享、单调）与 会话滚动状态（最后更新、正在进行 —— 高频、按 clone 天然分区、滚动替换）。前者放单文件没问题；后者本质是 per-clone 的， 被塞进共享单文件，冲突是结构必然而非偶然。

03

解法空间：三条正交路线

冲突的本质是把「并行状态」塞进「串行媒介」。所有解法都在恢复维度匹配，方向只有三种： 写点并行化（拆文件，不同文件在 git 三方合并中天然无冲突）、 读点聚合化（生成物，冲突解法退化为重跑）、 写串行化（单写者，消灭冲突但牺牲并行）。

A按 clone 拆文件（所有权分区）推荐主案

activeContext 目录化：global.md 承载里程碑级全局焦点（低频共享），每 clone 一个会话状态文件， 各 clone 只写自己的文件。不同文件 = 三方合并结构性无冲突，与现行「先同步后开工 ff-only、提交时合流」流程完全兼容。 附带收益：单文件天然变小，12 KB cap 压力骤降。

B生成式聚合视图推荐组合件

在各 clone 状态文件之上用脚本生成 _index.md（每 clone 一行：最后更新时间 + 一句话状态）。 生成物的冲突解法 = 任取一方重跑脚本。与 A 组合时就是 A 的「别人在干嘛」读点。

C同文件分段约定次选过渡

每 clone 只写自己的 H2 段。改动最小，但同文件相邻段、段落重排仍可能撞 hunk，头部共享区照旧最热，文件膨胀压力不变。治标。

Dgit 层兜底低成本保险

① merge-tree 只读预检（配方已在 pitfalls/git/history-integration.md：git merge-tree --write-tree 退出码 0 即无冲突）， 把冲突从「push 被拒才发现」提前到「提交前就知道」；② 开 rerere.enabled 自动复用人工解法。 注意 union merge driver 不适用 —— 它只对 append-only 文件安全，对滚动替换式结构会织出两版混杂文本。

E单写者模型仅全局段可选

指定唯一 owner clone 拥有全局焦点文件，其余走 issues / 提交信息汇报。彻底消灭冲突但牺牲并行， 与「各 clone 自洽收尾」的现行 DoD 冲突。global.md 本来就低频，不值得为它上单写者。

方案冲突消除程度改造成本主要代价 / 风险
A 拆文件（按 clone）结构性消除中：目录 + 生成脚本 + 守卫 + 文档接线，一次到位需约定 clone-id；全局视图依赖生成物
A′ 时间戳切片（本计划采用）结构性消除，且写形态从「重写头部」变「追加切片」中：目录 + 阅读脚本 + 守卫 + 文档接线文件数无界，靠归档阈值收口；命名须定宽前缀
B 生成式聚合解法退化为「重跑」低～中（可并入 A）单独用只解决「解得快」，不解决「撞不撞」
C 同文件分段降低，不消除低头部共享区仍最热；膨胀压力不变
D git 兜底不消除，提前暴露低预检后仍要走合流；rerere 只对同形冲突有效
E 单写者消除低牺牲并行，owner 成瓶颈
04

推荐方案：A′ 时间戳切片 + D

A′ 把「每会话重写头部同一段」改成「新增 / 更新自己的切片」，D 做只读预检兜底。 v1.1 相对初稿（A + B + D）有三处修订，均于 2026-09-23 与用户确议： 取消 global.md、取消 _index.md、取消「取最近 N 条」截断。目标结构：

memory-bank/
├─ activeContext.md          ← ≤ 1 KB 存根: 一句话 + 「已迁至」指针（照目录化五步配方）
└─ activeContext/
   ├─ _about.md              ← 三行头元数据, 目录自发现入口
   ├─ 26-09-23-0034-partial-hr-verify.md      会话切片: 创建时间 + 专题 slug
   ├─ 26-09-22-2350-activecontext-conflict.md
   └─ 26-09-22-2038-qb-move-dot-qb.md

三处修订（为什么不按初稿做）

  • 不要 global.md —— 「定案口径 / 下一步候选 / 待走查 / 历史归档」四段长青内容 各自都有真实归属（根 AGENTS.md · conventions/collaboration.md · pitfalls/web-ui/* · 想法.md + progress/roadmap.md · checklists/manual-walkthrough.md · tasks/ 档案纪要段），留在这里只是副本 —— 双份必然漂移。 实测该文件 13,070 字节里长青段占 3,516 字节（27%）。 ⇒ 剥掉后 activeContext 只剩「会话滚动状态」一种性质，不需要任何共享层。
  • 不要 _index.md —— 时间戳文件名自带时间与主题，ls 本身就是索引。 ⚠ 代价：本目录不能放 _about.md 之外的自发现标记 —— 一旦 gen_kb_index.py 把它识别成索引目录，就会自动生成一个随切片数增长的 _index.md，终将撞 3,000 字符的 index 档。 故 W2 必须把 activeContext 加进 _common.EXCLUDED_DIRS。
  • 不要「取最近 N 条」 —— 条数不是稳定的时间尺度：活跃期一天十条会把半天挤出去， 安静期三条可能跨一个月；更糟的是截断会漏掉「创建早但仍在推进」的切片。 ⇒ 改为全量按「最后活动」倒序输出 + 陈旧标记，目录规模靠归档阈值控制（建议 14 天）。
  • 也不产出任何缓存文件（没有 _recent.md）—— 缓存会过期： 一个看着可读、实际是上次运行快照的文件，比「没跑脚本」更危险。阅读脚本直接打印到 stdout。

切片命名：定宽时间前缀 + 专题 slug

YY-MM-DD-HHMM-<slug>.md。前缀定宽才能保证字典序 == 时间序（26-9-3-34 立刻乱序）。 不带 clone 标记：同分钟同名 add/add 概率极低，撞了改个 slug 重来；「我上次做到哪」靠 slug 复用检索 —— 这给出的是专题维度的时间线，比 clone 维度分区信息价值更高。

协议变化（开始 / 收尾两端点）

协议位置现行改为
会话开始 · 第 2 步 读 activeContext.md（最后更新、正在进行、下一步候选） 跑 gen_active_recent.py 看切片摘要（全量倒序 + 陈旧标记）；「下一步」改看 想法.md + progress/roadmap.md，定案口径改看根 AGENTS.md / conventions/
收尾 DoD · 第 1 步 更新「最后更新」滚动栈 +「正在进行」 写 / 更新自己的切片 —— 同一专题沿用同一 slug，只刷新「最后活动」；换专题才新建文件
「我上次做到哪」 （不成问题：单文件里就是最新状态） 按 slug 复用检索 —— 同专题的切片自然串成时间线，不需要 clone 标记
冲突处置 用户主导手工合并（collaboration.md 现行口径） 切片层结构性消除（不同文件 = 三方合并无冲突）；仅≤1 KB 存根与 _about.md 是低频共享点
与既有机制的关系 tasks/ 档案「不带时分、同天同专题必撞同路径」是故意设计的 add/add 查重信号（SKILL.md 明文）， 而切片故意带时分以避撞名 —— 两者命名意图相反，所以必须分目录， 也别把 SKILL.md 那条「不要用精确到分的时间戳」的反模式套到切片上（该条已就地限定为只针对 tasks/ 档案主键）。 issues 认领状态继续以 Gitee 为单一事实源，不进 activeContext —— 切片只承载「会话滚动状态」这一层。

06

风险与边界

风险 / 边界评估与对策
双 clone 协议错位窗口 W1 落地后、对方 clone 未拉取前，旧协议会往存根文件写。对策：W1–W3 连续入库压缩窗口；开工自检（--check-started + 读协议）会让对方 clone 在首个执行动作前完成切换；存根文案里写明「勿在本文件追加会话状态」
tasks/ add/add 信号被误伤 不受影响 —— 那是 tasks/ 路径层的故意设计，与 activeContext 拆分无关；计划明确不触碰
切片数量无界增长 初稿是 4+N 个（有界），切片方案不再有界。对策：归档阈值 14 天 —— 切片 14 天未动且已完成 → 蒸馏进 progress/ 或任务档案后删除；阅读脚本每次输出「M 个待归档」，把收口这件事摆到眼前
长青内容剥离后无处可寻 「下一步」/ 定案口径不再出现在 activeContext。对策：README 细路由拆行显式指向 想法.md + progress/roadmap.md 与根 AGENTS.md；阅读脚本输出末尾固定附一行去处提示
阅读脚本「没跑」是静默失效 与生成物不同：生成物失效是「过期」（--check 抓得住），脚本失效是「没跑」（无人知晓）。 对策：写进会话开始第 2 步（不是可选项）；--check 挂闸门兜住命名 / cap； 最后兜底是文件名本身 —— 时间戳 + slug，ls 即索引
