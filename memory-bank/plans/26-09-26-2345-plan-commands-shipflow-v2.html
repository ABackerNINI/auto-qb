让命令自己出示证据

commands 引擎 × my-commit-flow v2 —— 输出契约 · 零参数 · 一次调用走完提交与推送

这套命令系统的根本目的从来不是「把命令收进包里」，而是减少手写命令的出错面、压低每轮会话的 token 消耗。 现状离这个目的差一层：调用方（AI 会话）要替脚本抄写它自己一查就知道的事实（改动文件清单），要替脚本复述它自己已经做过的核对（push 后查远端）， 出错时还要去读脚本源码才能理解退出码的含义。本方案用一层输出契约把这三件事全部反转回脚本侧。

01

诊断 — 痛点逐条对应到机制根源

四个痛点不是四个独立 bug，而是同一条根因的四个切面：脚本知道的事，被要求由调用方转述；脚本做过的核对，被要求由调用方重做。下面逐条定位到文件与行号。

痛点 ① 改动文件一多就要一一传参多次出错

  • commit.py:46 — paths 是必传参数（nargs="+"），而权威的改动清单 changed_files() 就在同包 preflight.py:218 里，脚本自己一查就有，却要 AI 先跑 git status 抄一遍再拼进命令行。
  • _config.py:395 — 引擎参数链是 " ".join(extra) → args.split()：路径先被拼成字符串再按空格拆开，含空格的路径必碎；_quote 加引号发生在 split 之后，顺序倒了，救不回来。
  • commit.py:47 — --message-file 必传但路径无约定：写到仓内有红线误伤风险，写到系统临时目录则随平台漂移，「提交消息文件不存在」（commit.py:65）这类错就是这么来的。
  • 漏传比错传更隐蔽：某个文件忘了写进参数，它就静默不进本次提交——没有任何告警，产生「提交不完整」这类事后很难追认的事故。

痛点 ② push 之后还要手动检查本该脚本直接做

push.py:161-169 其实已经做了远端核对（ls-remote 现查、本地远端 SHA 比对、瞬时失败重试一次），问题出在核对结果的可见性没有契约保障：

  • 证据行 本地 <sha> → 一致 后面还跟着镜像段的两行输出——它恰好卡在引擎摘要「末 3 行」（run.py:28 SUMMARY_LINES = 3）的保留线边缘，靠行数运气存活。镜像输出多一行，证据就被挤掉。
  • 摘要的异常行正则（run.py:32 _ANOMALY）只认 [WARN]/[STOP]/[FAIL]/FAILED/ERROR/Traceback——不认 PASS，也不认任何成功证据。协议只保护失败，不保护成功。
  • AGENTS.md:91 第⑤步「查幽灵 diff」在 references/pipeline.md 里没有定义、没有机检承载——一个只存在于引导文档里的口头规程，每轮会话由 AI 自行发挥实现，实现方式就是再跑一遍手动核对。
  • pitfalls/git/push.md 的口径「判推没推上的唯一依据是 ls-remote，不是 push 的输出」写于脚本吸收核对之前，没有随实现更新——AI 被这条旧规则训练成连脚本自己的核对也不信任。
  • 远端真值取不到时（push.py:165，rc=6）脚本主动要求「请手工确认」——这合理，但它是目前唯一被显式定义的核对出口。

痛点 ③ 出错要深挖命令是怎么写的rc 语义被压扁

  • 引擎把一切非零退出码压成一行 [FAIL] task rc!=0（run.py:69）。而脚本各自的退出码语义是精心设计的：push.py 的 1/5/6（落后/推送失败/核对不到）、commit.py 的 1/4/5、verify_ref.py 的 2/3——全部在传递中丢失，语义只活在 docstring 里。「想知道 rc=4 是什么意思」的唯一办法是去读脚本源码。
  • 脚本内部其实写了大量高质量指引（preflight.py 的「同步路径」配方、verify_ref.py:34 的 FIX_HINT），但格式不统一、不保证出现在输出末尾，可能被失败摘要的 40 行截断线（run.py:30）吃掉中段。
  • 引擎自己的三类失败——requires 前置不满足、占位符展不开、超时——都只报现象不给下一步；超时甚至不说是哪条命令超的时。

痛点 ④ 其它命令的共性问题同根

  • 成功时的结论可见性靠「末 3 行」猜：pytest 的末行恰好是 N passed 所以 test.* 运气好；检查表类输出结论在中段就只能靠异常行正则捞——捞到的也只是带 [WARN] 的首行，多行详情仍被截。
  • risky 任务的「自证」每次全量打印展开命令（run.py:50-53）——每轮提交固定多花一份 token 重复已知信息。
  • 引擎本体零测试覆盖：test.pkg 只收集 .commands/**，而 run.py / _config.py 在 .agents/ 下——改动引擎没有任何机检兜底，这也是「其它命令也出现很多问题」改一次坏一次的结构性原因。

02

设计原则

五条原则，后面每一层设计都能回指到其中一条；实现评审时拿它们当判据。

  1. 能推导的不传参 —— 改动清单、分支、远端、消息路径，这些仓库状态脚本一查就有；凡是让调用方手抄的参数，都是一次出错机会。
  2. 证据自持 —— 每条命令的结论必须自带证据行（sha / 数字 / 比对结果），且引擎以协议保证证据行永不被摘要截掉——不靠行数运气。
  3. 失败可导航 —— 失败输出必须是「现象 + 根因 + 可直接执行的下一步」，下一步本身就是一条命令或 task id，而不是一段描述。
  4. 编排进脚本，判断留给人 —— 固定顺序的步骤串（预检→暂存→提交→核 ref→推→核远端→镜像）塌缩成一次调用；该停的 STOP 点一个不少。
  5. 每个机制配守阵 —— 没有测试锚定的约定必然回退；引擎本体顺带补齐测试收集面。

04

L1 输出契约 — RESULT 协议

整套 v2 的单点发明。script 型 task（commit / push / preflight / verify_ref 及未来一切包脚本）的输出末尾必须以协议行收尾；引擎则承诺协议行与异常行同权，永不被摘要截掉。至此「命令正常时反馈简单直接、出错时指引下一步」不再是各脚本的自觉，而是引擎强制。

RESULT 协议 · 规范
RESULT: OK <一句话结论，含关键 sha / 数字> EVIDENCE: (可选) 证据行，≤3 行：比对结果 / 计数 / 耗时 RESULT: FAIL <语义化失败名> | RESULT: STOP <同> | RESULT: PARTIAL <前段成功后段失败> WHY: (FAIL/STOP/PARTIAL 必填) 根因，一句人话 NEXT: (FAIL/STOP/PARTIAL 必填) 可直接执行的一条命令或 task id；确无则写「无——报告用户」

四态语义：OK 全部完成；PARTIAL 前段成功后段失败（如已提交未推送——重推即可，不重提交）；FAIL 动作失败；STOP 前置拦截未执行。PARTIAL 是新增的关键状态——它让「提交已落、推送没走」这类中间态不再需要人肉分辨。

适用面只限 script 型 task：run 型任务（pytest 等）末行本就是结论，不强加。引擎对没有协议行的输出退回现有摘要行为，不报错——协议是渐进采纳的，不会因旧脚本炸掉。

引擎侧改动

  • _digest（run.py:213）：新增正则 ^(RESULT|WHY|NEXT|EVIDENCE):，命中行与异常行同权保留——成功证据不再依赖「恰好落在末 3 行」。
  • cmd_run 失败路径（run.py:69）：[FAIL] task rc!=0 改为 [FAIL] task (<耗时>)——文本输出不再出现裸 rc 数字。退出码只走进程通道（wrapper / CI 可编程消费），语义只走 RESULT / WHY / NEXT 文本通道（脚本承载，引擎不翻译、不二写 rc 表）。裸数字除了诱导调用方去查码表——恰是本方案要消灭的「深挖命令怎么写」——没有信息量。

效果对照（示意，ship.push 成功路径）

L2 零参数化 — ship.commit 不再收路径

paths 从必传变缺省全量

commit.py 的 paths 改为可选（nargs="*"）。缺省时脚本自己调 changed_files() 取全量改动（与预检同一权威单点），红线 / 高危三道闸（BULK 拒绝、red_lines STOP、warn_lines 警告）原样保留，暂存清单显式打印后再动 git add。传路径仍合法——语义变为「子集提交」，且脚本补一行「未纳入 N 个文件」提示，治「漏传静默不提交」。

人因论证：抄对 N 个路径的出错率远高于核对 N 行打印出来的清单——把「审清单」从命令行参数侧挪到输出侧，正是这套系统该做的事。

消息文件路径约定单点

--message-file 缺省指向 .git/COMMIT_MSG_AI.txt：.git 内文件永不入库（不触红线）、多 clone 天然隔离（各自写各自的 .git）、路径跨平台恒定。调用方只剩「写消息文件 → 跑一条命令」两个动作，路径不再有自由度。

引擎参数链修复

_extra（run.py:161）不再 join 成字符串：script 型 task 的额外参数以 argv 列表直达（调用方 shell 层已处理过引号，引擎不拆不拼）；run 型任务的 <args> 文本替换保持现状，但拼回命令串时对每个含空格的元素统一 _quote。commands.cmd wrapper 的引号透传行为在实施时一并核对（cmd.exe 的 %* 引号半残是已知坑）。

调用形态对照

# 步骤 1: 把提交消息写进约定路径 (Write 工具一步) .git/COMMIT_MSG_AI.txt ← 新约定：.git 内，永不入库 # 步骤 2: commands run ship.commit ← 零参数：全量改动 + 缺省消息路径

L3 编排合一 — 提交即推送

ship.commit 在 ref 三处核对通过后，同进程续跑 push 全流程（含推送前 --no-auto 预检、远端核对、一次镜像尝试），--no-push 才停在提交。这不是新发明——commit.py 已经 import verify_ref 续跑，把 push.main 加进同一条链即可。

收益是把口径与实现finally对齐：AGENTS.md 早就定义「用户说提交 = commit + push 一次走完」，但实现层是两个 task，靠 AI 记得接着跑第二步、记得跑完再核对。固定顺序的步骤串交给脚本，STOP 点一个不少（落后照旧拦、闸门照旧红），判断全部保留在人（AI）这一侧。

# v2：3 步，⑤ 由 RESULT 行取代 ① my-commit-flow.sync → ② 收尾回写 → ③ ship.commit(提交+核 ref+推送+核远端+镜像, 一次调用)

L4 错误导航 — 每个失败都有下一步

原则 3 的落地：失败输出的三行结构（RESULT / WHY / NEXT）由脚本产出，引擎负责两件它擅长的事——保证这三行不被截掉（L1 已定），以及给自己的三类失败补上 NEXT。退出码维持脚本现状、只走进程通道；文本输出不出现裸 rc——语义只由 RESULT / WHY / NEXT 承载，引擎不做 rc 翻译表（那是配置二写）。

触发NEXT 行内容承载者
落后 / 分叉主线fetch + merge --ff-only 配方，或树脏时的「移出→快进→施回」五步（现成的 sync_recipe 挪进 NEXT 行）preflight.py（已有，改格式）
闸门红修复后 commands run my-commit-flow.preflightpreflight.py
ref 三处不一致FIX_HINT 收进 NEXT（内容现成，改格式）verify_ref.py（已有）
主线推送失败commands run ship.push（补推）commit.py / push.py
消息文件缺失写 .git/COMMIT_MSG_AI.txt 后重跑commit.py
引擎前置不满足 / 占位符展不开 / 参数不接show <task> 或对应修复动作run.py（引擎补默认 NEXT）
超时指名超时的那条命令（多命令 task 时逐条计时已有，差在输出）run.py / preflight.py

自证压缩（token 项）

risky 任务的「将要执行」从全量打印改为首条 + (共 N 条, 全量: show <id>)——自证的价值在「知道将要跑什么」，不在每次复述全部展开串。

取舍与风险

  • 缺省全量 vs 逐路径纪律：逐路径的本意是防误交红线、防混入不相干改动。三道闸原样保留 + 暂存清单显式打印，且子集传参仍可用——纪律的意图全保留，被替换掉的只是「手抄路径」这个最易错的实现载体。
  • RESULT 协议是新约定：只约束 script 型 task；run 型不强加；无协议行时引擎退回现有行为——渐进采纳，不产生一次性大爆炸迁移。
  • .git/COMMIT_MSG_AI.txt：git clean 不清 .git 内文件、会跨提交残留——残留无害（下次提交直接覆盖），体积可忽略。
  • ship.push 保留为独立 task：合一后它仍是补推 / rc=6 重验的入口，不是被删除，只是不再是常规路径的必经步。
  • 引擎行为变更波及既有用例：test_preflight.py 现有 47 条中若有锚定旧参数行为的，随 P2 同步修正——已在守阵清单内，不是范围外改动。
  • rc 语义不进引擎、也不进文本：退出码维持现状（0-6），只走进程通道供 wrapper / CI 可编程消费；文本通道只出 RESULT / WHY / NEXT。没有裸数字，调用方就没有「rc=5 是什么意思」的查询钩子——省 token，也少一条误入歧途的路。
  • 调用面 hook 闸门（原 L5/P4 案）已评审否决（2026-09-27）：PreToolUse 拦裸命令只覆盖 ZCode 单工具（跨工具无效），且命令写出后拦截徒增一轮重写往返——对策为写前引导口径（AGENTS.md 命令节缺省动作 + SKILL.md 缺省规则与触发描述）；若未来重提机检，先解决「写前引导」而非「执行前拦截」。
