WEBUI 搜索结果随新增种子自动更新

给搜索结果加一个“数据版本号”，让前端在下一次 /api/state 轮询内静默重算当前查询，并用一条 3 秒的“结果已更新（+N 个种子）”短提示告诉用户结果在增长 —— 搜索语义仍由服务端单点裁决，前端不新增任何文本匹配。

§01目标与设计原则

要解决的问题

搜索进行中或搜索完成后，如果有新种子进入且其名称/文件命中当前搜索词，结果列表不会自动变化，必须重新敲一次搜索才能看到。用户视其为缺陷，而不是“已知取舍”。

设计主轴

“版本号驱动的一次性快照刷新”：后端只在搜索相关数据变化时自增一个轻量标量，前端发现自己的结果版本落后，就重新调用同一个 /api/search。不做增量补入、不做服务端活跃查询、不加 SSE 新事件。

不变量（违反即方案作废）

  • 搜索语义单点：所有文本匹配、负词、文件行语义仍只在服务端 views.py::search_torrents；前端不得新增任何匹配函数（现有守阵继续生效）。
  • 单一写线程：search_rev 只由主循环写，Web 线程只读；不引入绕开主循环的并发写。整数自增在 GIL 下原子，跨线程读取安全。
  • 状态不落盘：搜索词本来就不持久化（state.js:229），本方案不新增 state_file 字段、不新增配置键。
  • 幂等：每次刷新整集替换 searchHits 与 searchUncovered，重复触发不产生重复行。
  • 保守默认：只在前台、搜索态、版本变化、冷却窗口之外触发；后台标签不拉数。
  • 三皮肤一致：UI 提示落在共享模板 shared/tpl/topbar.html，复用既有 .strip-note 视觉，不做三套皮肤各自的复制件。

算成什么样

  • 搜索“尼古”得到 5 个结果；新增一颗名称含“尼古”的种子后，不碰搜索框，在 1 次轮询 + 1s 冷却内变为 6 个结果。
  • 结果增长时，顶部筛选说明条出现 结果已更新（+1 个种子），3 秒后消失；连续新增合并计数，不闪烁。
  • 0 命中 → 有命中的场景同样可见：空态消失、行出现、顶部提示出现。
  • 删除/改名/标签变化不会把列表打回全量，也不会让 searchPending 语义塌陷。

§02现状与痛点

症状与复现步骤

  1. 打开任意一套皮肤（/atlas/、/prism/、/flux/），在右上角搜索框输入“尼古”，等待结果稳定（例如 5 个）。
  2. 通过 qB API 或测试桩新增一颗名称含“尼古”的种子；保持当前页面与搜索框不动。
  3. 等待至少两个 /api/state 轮询周期（1.5–3s/次）。结果仍是 5 个。
  4. 重新敲一次回车或改一个字再改回来 —— 结果立刻变 6 个。说明后端能查到，前端没有再次取。

“搜索进行中”变体：若新增发生在文件索引构建期间，已有的 1s building 轮询可能碰巧带入新种子；一旦 building=false，同样的新增就不会再被看到。

根因链路（带证据）

  1. 后端没有结果缓存：/api/search 每请求重算，候选行即时从 store.by_hash 取，文件行才取自缓存索引 search_index（src/auto_qb/webui/views.py:1119-1160）。因此“重新搜索就能看到”排除了后端固化结果。
  2. 前端是一次性快照：searchHits = new Set(results.map(...))、searchUncovered = results.filter(...) 只在 doSearch() 落袋时写入（src/auto_qb/webui/static/shared/view.js:41-48）。
  3. 唯一自动重查条件过窄：只有响应里 building=true 时才有 1s 重查（view.js:51-55）。索引完成后新增的种子没有第二次查询。
  4. 轮询链路不重跑搜索：SSE ver 只触发 refresh()（polling.js:62-67）；refresh() 更新 groups/torrents 与 status，但从不调用 doSearch（polling.js:345-380）。新种子进了组列表，却不在 searchHits 里，被命中门挡掉（filters.js:213-224、filters.js:260-268）。
  5. 主循环没有“结果需刷新”的信号：新增/删除时只做 self.web.mark_search_index_dirty()（src/auto_qb/core/qbmanager.py:914-917；runtime.py:464-466），该信号只影响文件索引，不影响前端结果版本。
  6. 增量同步本身不是瓶颈：新种子会在下一个同步轮进入 store，名字行无需索引即可命中（views.py:1119-1130）。缺的是“前端知道该重查”的触发。

相邻缺陷（不在本计划范围）：searchUncovered 是搜索时刻快照，未归组命中之后被归组时会出现“真实行 + 陈旧虚拟行”的重复；删除后虚拟行也会滞留到下轮搜索（filters.js:225-249）。本方案的静默重查会缩短其暴露窗口，但不作为本次修复目标。

方案候选与被否理由

方案做法结论
A · 版本号 + 静默重查（采纳） 主循环在搜索相关数据变化时自增 search_rev；随 /api/state 恒回传；/api/search 响应带回结果对应版本；前端发现落后就重调。 复杂度可控；结果与“此刻重新搜索”严格一致；无长驻状态；服务端字段是加法，可独立回滚。
B · 仅前端固定轮询 搜索态下每 1–3s 盲调 /api/search，后端零改动。 O(N) 全扫与全量响应持续发生；3000+ 库、宽查询时 CPU/带宽不可接受；与 building 轮询叠加更容易互相踩。
C · 服务端活跃查询 + 增量推送 客户端注册查询，主循环只对新增种子做匹配并推送 hash 增量。 引入跨请求生命周期/多标签/清理/TTL/并发；文件行语义与负词仍要回退全量；增量与全量易漂移，测试成本高。
D · 只提示、不自动刷新 显示“结果有更新，点击刷新”。 不满足用户“自动更新”的核心诉求，只能作为性能兜底。
E · 前端本地重算命中 新种子到达后前端自行匹配。 直接违反“唯一文本匹配点”不变量；三页/负词/文件行语义会分叉；现有静态守阵会拦。

§03方案总览

主线

服务端只增加两个标量：search_rev（当前数据版本）与响应里的 rev（该次结果对应的版本）。前端只增加一个判断：status.search_rev !== searchRevApplied 时静默重查。UI 提示由共享 topbar 模板承接。

# 服务端语义
added/removed ────────────────┐
name/category/save_path/tags 变化 ─┼─→ search_rev += 1
full_round(重连/tracker 重匹配) ────────────┘

GET /api/state  → status.search_rev（恒回传标量）
GET /api/search → { results, uncovered, building, negative_only, rev }

# 前端语义
refresh() 落 groups/status
  └─ status.search_rev !== searchRevApplied && 搜索态 && 前台 && 冷却已过
       └─ doSearch(quiet=true)  // 不置 searchPending，不触发 pending 塌列表
            ├─ 成功: 整集替换 hits/uncovered，写回 rev；新增命中 > 0 时亮提示 3s
            └─ 失败: 保留旧结果，等下一次轮询重试

触发面与定值

项定值说明
服务端触发字段{"name","category","save_path","tags"}与 _instant_rows 的候选来源对齐；速度/进度/大小等变化不触发。tracker 不列入：快照字段表 compat._SNAPSHOT_FIELD_SET 无此字段，tracker_name 由 tracker_conf 派生、只在全量轮重匹配时变化 —— 已由 full_round 触发覆盖（R1 修正）。
增删触发added or removed每 tick 最多自增 1 次（按批合并，不按种子数）。
全量轮触发full_round 一次覆盖 tracker 配置重匹配导致的 tracker_name 变化；重连时多一次刷新可接受。
索引构建不额外触发静默重查若见 building=true，由前端独立定时器续查；无需服务端再发信号。
前端冷却SEARCH_REFRESH_MIN_MS = 2000P0 实测 3000 库宽查询 p95 150.1ms、响应 3.48MB，超闸门（p95>50ms 且响应>500KB）⇒ 按判据取 2000ms（见 §08）。
提示时长SEARCH_REFRESH_HINT_MS = 3000每次更新重置计时；查询变更/清空/切页立即清掉。
版本初值int(time.time()*1000)服务重启后旧页面版本几乎必然不等，触发一次自愈刷新。

UI 提示：让用户知道结果在增长

位置：共享模板 shared/tpl/topbar.html 的筛选说明条内，紧跟结果计数之后、· 索引构建中… 之前（topbar.html:203-215）。该条只在 filtersActive 时出现，搜索态必然满足。

实现：新增一个无 CSS 的钩子类 search-refresh-note（沿用 .sel-summary 的“仅作 e2e 选择器、无样式”先例，topbar.html:199-200），视觉完全继承父级 .strip-note，因此三套皮肤零复制、零新增配色。

文案：结果已更新（+N 个种子）。全角括号；title 写“本次自动刷新新增 N 个命中种子（按 hash 去重）”；role="status" + aria-live="polite" 让读屏可用。

搜索“尼古” → 6 个种子(仅命中成员高亮) 结果已更新（+1 个种子）

示意：提示不新增图标、不使用 toast，不占独立行。

计数口径：N = |newHits \ hintBaseHits|，按 hash 去重，统计“种子数”而非组数/集数，避免组视图与种子视图口径漂移。提示窗口内连续刷新以窗口起点的 hits 为基线累加；窗口结束（3s 无新更新）清空基线。仅 N > 0 时显示；删除、改名、仅内容变化不显示 (+N)，避免噪声。

出现/消失：静默重查落袋且 N > 0 时立即出现；SEARCH_REFRESH_HINT_MS=3000 后消失；期间再有新增则更新数字并重置计时。查询变更/清空/切换视图/手动搜索立即清掉。

0 命中 → 有命中：不额外做居中横幅。空态 aq-empty 消失的同时，顶部提示照常出现；因为搜索态下说明条始终可见，用户能从“空态消失 + 顶部 +N”同时看到变化。

§04实施步骤

阶段内容验收判据
P0 · 实测与定值 用 scripts/ui_harness.py --torrents 3000 起桩，对当前版本测量 /api/search：窄词与宽词各 20 次，记录 p50/p95 与响应字节数。按 §08 闸门确认 SEARCH_REFRESH_MIN_MS 取 1000 还是上调。 测量脚本输出可复现；本计划 §08 回填实测数字后，冷却常量才冻结。
P1 · 服务端信号 S1–S4；补后端单测（触发面、状态回传、响应版本、结果增长）。 commands run test.quick 绿；新增用例覆盖“仅速度变化不触发”。
P2 · 前端刷新与提示 F1–F4；补静态守阵；手工三皮肤走查。 “恰两处 pending”守阵仍绿；0 命中→有命中不闪全量；提示 3s 消失、连续更新合并计数。
P3 · e2e 与真机 在 scripts/ui_harness.py 增加仅测试用的“新增种子”命令；新增 e2e/search-auto-refresh.spec.mjs；三皮肤跑通；真机 qB 加种验证。 不碰搜索框 5s 内结果增长；提示出现并消失；控制台无错误；主循环日志无命令积压。
P4 · 收尾 回写 memory-bank/ 与基线（若跑了 test.full）；用户另行授权后提交。 DoD 完成；本文件 §08 数字与代码一致。

实施注意

  • P0 未完成前，1000ms 是暂定值，不得把它写成“性能已验证”的结论。
  • F2 的 quiet 路径必须复用同一落袋逻辑；不要复制第三份 hits/uncovered 赋值，避免三处漂移。
  • full_round 触发若发现配置热重载重匹配 tracker 但不走 full round，需在配置应用处补一次 note_search_data_changed()；实施时按实际调用链确认。
  • 索引构建续查使用独立定时器，不要复用输入防抖的 searchTimer，避免取消用户正在输入的去抖。
  • 提示文案只出现在共享 topbar；禁止在 atlas/、prism/、flux/ 各自复制一份。

§07风险与对策

风险触发条件处置
宽查询重算成本高查询命中数千、/api/search p95 超闸门上调冷却到 2000ms，或追加轻量/hash-only 刷新模式；实测前不宣称达标。
规则引擎高频改标签每 tick 都有 tags 变化，rev 持续增长冷却兜底；若仍抖动，缩短触发面为增删即时 + 字段变化更长冷却（常量单点）。
滚动位置被插入行推动新命中按 added_on 降序插在顶部quiet 不置 pending、不重建列表；实测有跳动再保存/恢复 scrollTop，不在首版预防性加代码。
陈旧虚拟行重复命中之后才被归组（不伴随 rev 变化）本方案不修；静默重查缩短窗口。若仍高频，另立 issue 跟踪 searchUncovered 一致性。
服务重启版本重置Web 服务重启但页面未关search_rev 初值取启动时刻，旧页面版本几乎必然不等，触发一次自愈刷新。
多标签放大请求同一浏览器开多个主视图标签后台标签跳过；前台每标签每 rev 变化最多一次，可接受。后续再考虑共享 Worker。
e2e 桩与生产漂移测试桩自己复刻置脏/自增副作用优先改 FakeClient 快照后调用与主循环同一同步入口；若只能显式三连调用，注释标明仅测试并加断言防漂移。
守阵误伤新增 quiet 分支改变 pending 次数或落袋顺序保持 searchPending = true 恰两处；新增断言只钉 rev/提示/模板钩子，不改既有语义断言。
配置热重载 tracker 不触发重匹配 tracker_name 但不走 full round实施时核调用链；缺则补一次自增，属于 S2 验收项。

回滚

  • 前端回滚：删除 F3 的 rev 判断块，即回到“一次性快照”行为；F4 模板提示不再亮。
  • 服务端回滚：S1–S4 都是加法字段/只读标量，无迁移、无配置；旧客户端会忽略新字段，可独立发版。
  • 顺序：先发服务端（无行为变化），再发前端；不需要 feature flag。
