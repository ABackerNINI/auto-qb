让运行期状态活过一次崩溃

现状是 save_state() 只有优雅退出这一条路可达：taskkill /F、原生崩溃、OOM、 断电、关机、直接关掉控制台窗口，都会丢掉整个运行期的规则执行历史与各类去重记录。 本方案把丢失窗口压缩到一个可配置的常量（默认 120 秒）：主循环周期性落盘为主， 两个重放代价最高的键即时落盘为辅。生产实测 state.json 仅 37.5 KB， 周期落盘的写放大在 120s 档约 54 MB/天 —— 当年「仅退出时落盘」要规避的写放大，在今天这个体量下已经不成立。

01问题与代码事实

issue 26-09-21-1347-bug-backend-state-save-only-on-exit（Open）的结论在当前 HEAD （4c8b90e，2026-09-22 复核）仍然成立。全库落盘点只有两类：

落盘点位置（@ 4c8b90e）可达条件
退出落盘 qbmanager.py:450（run() 的 finally） 仅 Python 异常语义展开时：Ctrl+C（KeyboardInterrupt）、托盘/命令的 stop_event。 Windows 上 CTRL_CLOSE_EVENT / 关机 / taskkill /F 不产生 Python 异常， finally 永不执行
跳检备份即时落盘 skip_checking.py:252（_clear_backup）/ :277（_backup_torrent） 仅跳检备份路径 —— 崩溃安全专项里唯一开过的口子（备份凭据不能只活在内存）

退出路径枚举（递归 grep atexit|import signal|SIGINT|SIGTERM|SetConsoleCtrlHandler）为 零命中 —— 进程没有注册任何 OS 信号处理器，所以非优雅终止没有任何兜底。

丢失的是什么

state.json 的全部键。按重放代价排序：

state 键用途（去重依据）丢失后重放代价
skip_check_day同日跳检去重（跨规则）最实在：同日可重复跳检，PT 本地统计再丢一次
exec_historyexecute_once / cooldown 去重规则动作重放；动作普遍先查状态再写，多为幂等 API 重复调用

skip_check_backup跳检恢复凭据该键已有即时落盘（上表），不受影响

已经排除与已经修掉的

  • 原子写缺陷——不成立。utils.atomic_write（tmp + fsync + os.replace + .bak）保证文件要么全旧要么全新，本 issue 只丢「新变更」，文件本身无损坏风险。
  • 损坏恢复管线——姊妹 issue state-load-corrupt-silent-reset 已于 2026-09-22 修复入库（e11df80）：损坏回退 .bak、自愈写回、孤儿 tmp 清理。本方案叠加在其上：周期落盘让 .bak 与自愈的「新鲜度」从「上次优雅退出」变成「最多 N 秒前」。
  • filelock 死锁残留——不成立，句柄随进程死亡由 OS 释放。
这是知情取舍的推翻，不是修疏忽：pitfalls/backend/behavior-core.md 明文记载 「state_file 仅退出时落盘 = 已知取舍，需要更稳的持久化要先推翻这条设计」。本计划就是那次推翻， 由 issue 发起；落地时黄金法则 3 与相关知识库条目要同步改口径（见 §08）。

02目标与非目标

目标

  • 非优雅终止时，state 丢失窗口 ≤ state_save_interval（默认 120s；计入主循环节拍，实际 ≤ interval + 1 个 tick）。
  • 重放代价最高的 skip_check_day 窗口 → 0（跳检完成标记即时落盘）。
  • 零新线程、零新锁：flush 只发生在主循环线程，单一写线程约束原样保持。
  • dry-run 不产生任何磁盘写入（与现有退出路径 if not dry_run 口径一致）。

非目标

  • 不追求零丢失——断电瞬间最后 ≤ interval 的变更仍会丢；这是「缩小窗口」不是「消除窗口」。
  • 不修托盘 join 超时（26-09-21-1347-bug-tray-join-timeout-abandons-save，Open）——但本方案让它从「丢全部」降级为「丢 ≤ interval」，两个 issue 是缓解关系不是依赖关系。
  • 不修热重载 L2 回滚（26-09-21-1347-bug-backend-hot-reload-l2-state-rollback，Open）——同理，L2 分支重读磁盘的回滚半径从「整个运行期」缩到 ≤ interval。
  • 不做 exec_history 剪枝——该键目前无界增长（生产 37.5 KB 尚无压力），另行观察，不入本计划。

03方案：周期落盘为主 + 关键键即时为辅

A · 主循环周期落盘（候选 A，主机制）

在 run() 主循环的正常路径（暂停分支之后、flush_truths() 一带）加一个到期检查。 主循环节拍是 sync 线 1.5s / tick 线 2s，循环永远不会睡过 2s，所以到期后 ≤ 1 个 tick 内必然执行：

# qbmanager.py · run() 主循环内（正常路径，暂停分支不经过这里 —— 暂停期无状态变更）
self.web.flush_truths()
if not dry_run:
    self._maybe_flush_state(time.time())

# mixins/rule_engine.py · RuleEngineMixin 新增
def _maybe_flush_state(self, now: float) -> None:
    """周期落盘：间隔由 state_save_interval 控制（0 = 关闭，回到仅退出落盘的旧行为）。

    仅主循环线程调用（单一写线程约束不变）；save_state 自带原子写与 OSError 兜底。
    """
    interval = self.config.state_save_interval
    if interval <= 0:
        return
    if now >= self._next_state_flush_at:
        self.save_state()
        self._next_state_flush_at = now + interval
  • 计时器在 run() 里 self.state = self._load_state() 之后初始化为 time.time() + interval —— 启动时刚从磁盘加载过，立刻 flush 是无意义的重写。
  • 间隔每轮从 self.config 现读，与 main_tick 同口径，热重载 L0 即时生效。
  • 不引入 dirty 标记：state 是普通 dict，写点散在 ~10 处（见 §04），逐点插桩必漏； 周期兜底对「未来新增的写点」也自动生效。

B · 关键键即时落盘（候选 B，辅助）

两个重放代价最实在的键，在写点就地落盘。两处变更频率天然低（跳检是小时~天级事件； recheck 失败有 3 次/日/种上限），且 skip_checking 里已有两处即时落盘先例，口径一致：

写点位置（@ 4c8b90e）改法
skip_check_day skip_checking.py:207（_skip_readd 尾部，跳检完成标记） 标记写完后 ctx.manager.save_state()。注意 _clear_backup 的落盘在 meta 为空时提前返回不会执行，所以这里要显式落，不能指望顺带
recheck_fails full_checking.py:_bump_recheck_fail（函数尾部） 累加后 manager.save_state()。放在函数内单点覆盖全部调用方； 频率上界 = 3 次/日/种

exec_history（record_execution）不即时落盘：它在规则命中时逐条写， 初轮可能一秒几十条，即时落盘会把写放大放大几个量级；其重放代价多为幂等调用，交给周期落盘即可。

04否决的备选

备选否决理由
全部 ~12 个 state 写点插 dirty 标记 写点散在 rule_engine / tags / basic / full_checking / skip_checking / transfer / speed_curve 七个文件； 未来每个新写点都必须记得插桩 —— 与「.bak 写出去没人读」是同一类漏接形态（刚修完的 issue 就是前车）。 周期兜底不需要任何插桩
state 换成代理 dict，赋值自动置脏 嵌套结构（exec_history / upload_snapshots.baseline）的深层变异拦截要做到可靠， 复杂度远超收益；还改动了 self.state 的类型契约
OS 信号处理器 + atexit（CTRL_CLOSE_EVENT / SIGTERM） 覆盖不了真正的威胁面：taskkill /F、OOM、断电根本不给清理窗口；Windows 关控制台的 CTRL_CLOSE_EVENT 不进入 Python 异常语义。能给的几秒清理窗只救得到其中一种情况， 复杂度却进入信号处理这一高风险领域 —— 不值得
每 tick（2s）无条件落盘 43,200 次/天，fsync 开销无意义；状态变更频率本来就是小时~天级

05配置键规格：state_save_interval

新键 state_save_interval（状态周期落盘间隔），默认 120s，0 = 关闭 （回到「仅优雅退出落盘」的旧行为，作为逃生口）。按黄金法则 4，新键必须走完全部注册点：

注册点内容
config/models.pystate_save_interval: float = 120.0 字段 + 缺省注释（挂在 main_tick / sync_interval 旁）
config/loaders.py_get(cfg, "state_save_interval", d.state_save_interval, parse_time)（口径见拍板点 ②）
config/schema/groups.pyField 登记（与 main_tick 同组），WebUI 设置页可见可编辑
config/validation/core.py加入已知键列表 + 校验规则：数值合法、≥ 0（负数聚合报错；0 合法=关闭）
config/impact.py"state_save_interval": LEVEL_L0 —— 主循环每轮现读，热重载即时生效，无需重启
⚠ 实现时须确认 _try_time 的 positive=False 分支是否放行 0 （现有调用全是 positive=True 的「>0」语义，main_tick 用它防 0 忙循环）。 若不放行，补一个「≥0 且 0=关闭」的分支 —— fail-fast 口径：负数/非数报错，0 放行。

06写放大量化

生产实测（主 clone auto-qb-data/，2026-09-22）：state.json = 37,545 B， .bak 同尺寸。每次 flush 的磁盘写入 ≈ 2 × 文件尺寸（临时文件写 + .bak 复制），约 75 KB。 当年「仅退出时落盘」规避的写放大，按这个体量折算：

间隔落盘次数/天写入量/天（含 .bak）断电丢失窗口
60s1,440≈ 108 MB≤ 1 min
120s（建议默认）720≈ 54 MB≤ 2 min
300s288≈ 22 MB≤ 5 min

即便是 5000 种子 × 多规则的大库，exec_history 撑到 1 MB 量级，120s 档也在 1.5 GB/天以内， SSD 无感；真担心还有两道闸：调大 interval，或 0 直接关回旧行为。主要成本是 fsync， 频率已压到「分钟级一次小文件」，不再有优化价值。

09风险与拍板点

风险与缓解

风险评估
写放大实测 37.5 KB，120s 档 ≈ 54 MB/天 —— 可忽略；interval 可调 + 0 关闭双兜底
flush 瞬间恰逢崩溃原子写 + .bak + 孤儿 tmp 清理均已就位（e11df80），最坏丢这一次 flush 本身
与热重载 L2 的交互L2 重读磁盘的回滚半径反而从「整个运行期」缩到 ≤ interval；无新增风险

单一写线程钩子只在主循环线程；两个即时落盘点都在既有主线程动作路径内（与先例同径）
