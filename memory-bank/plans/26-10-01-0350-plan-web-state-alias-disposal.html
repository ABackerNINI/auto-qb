01现状与问题定性

内核化重构 P0–P6 已把全部业务迁出 core/qbmanager.py;为了让 76 处构造点 / 279 处 make_manager 测试 / 路由零改动,每段迁移都在 manager 上留了旧名兼容层。它们是当时验证过的迁移惯用法(plan §7.2),但按设计就是待清理的过渡层 —— 现在重构已收官,这层成了内核上唯一一块「知道所有模块内部方法名」的脏面。

1.2 三个结构性问题

脏面集中在宿主 —— 81 个成员让 qbmanager.py 行数停在 1092(plan §8 估的 ≤450 目标被兼容层盖住,P5 档案已注记「该目标随 D4 清理才可达」);「内核不知道模块内部方法名」的可验证事实被这层打破,任何模块改名都要回头改 manager。

dunder 转发遮蔽拼写错误 —— __getattr__ 对 20 个别名之外的未知属性抛 AttributeError,但别名内的旧名永远「存在」:新代码误写旧名不会在定义处报错,只在运行期转发,IDE 与静态检查全部失明。

双名并存是持续税 —— 每个被兼容的名字都有两份文档语义(旧名注释 vs 模块 docstring),memory-bank 的模块文档必须同时维护两套指称。

02处置原则

  • 逐名分诊, 不一刀切 —— 81 + 20 个名字逐个归三类:①纯转发 → 调用方改新名后删除;②内核自有方法(如 _refresh_torrents/_tick/_throttle 等「何时」域方法, 形似旧名实非委托)→ 保留并从清单里摘出;③测试专用 seam → 评估改经 host.get("…") / ctx 取用后删除。分诊结果落一份清单文件进本计划附件(tasks 档案引用), 作为 W1 的施工图。
  • 先改调用方, 后删名字; 每波独立入库全量绿 —— 与内核化重构同款节奏:删名字的提交里不允许同时有行为变更。
  • 行为零变化 —— 本计划只做改名/删转发, 不改任何语义;唯一「行为」变化是旧名真正消失时的 AttributeError(由全量测试兜底)。
  • 属性委托(config/store/api/state/web/task_queue)最后处置 —— 它们的消费面最大(测试上千处直读), 且 76 处构造签名不动是全程不变量;是否值得清(收益 vs 727 处测试点改动)单独拍板, 允许「永久保留属性面」的结论。
