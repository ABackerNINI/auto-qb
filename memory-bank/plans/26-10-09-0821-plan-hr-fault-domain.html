HR 故障归属分层拆分 分步实施计划

用户实报: 关闭浏览器一晚, WebUI 错误历史里出现 4 条 [HR 页面改版] 页面取数失败(等待浏览器扩展取数超时 180s) 与 2 条 [HR 通道静默]。用户口径五条: ①「连不上浏览器」这类只打后端 log, 不发到前端错误历史; ②「等扩展超时」与「页面改版」两件不同量级的错误混为一谈, 必须绝对禁止; ③「浏览器离线」与「扩展离线」必须分清 —— 故「通道/环境层」不设单一静默桶, 须按可分辨证据再分档(§03.6); ④「扩展只能本机」是设计缺陷, 未来须支持跨机(NAS + 外部扩展)(issue 26-10-09-0855 / 计划 26-10-09-0856); ⑤「WebUI 在线而扩展不在线」发 WebUI 警告、不静默, 且无需判断同机 / 同源 —— 判据极简化为「WebUI 是否活跃」(§03.6.1)。本计划不给出口打标记(那是补丁 —— 把出口的意志写进产生点), 而是把已存在的归属层 (fault domain) 骨架补齐、并让「层」贯穿到出口。

01拍板回执与范围

事项结论
用户诉求① 通道/环境类事件只进后端 log, 不进前端错误历史; ② 通道层与站点层的混淆绝对禁止(不是"少报几条", 是分类模型问题)。
本计划范围把「等扩展超时」补进已有的异常归属分层(S1) → 按层分派、消掉三处污染(S2) → 事件文案分层(S3) → 出口声明式收层 + 补「被拒接触」状态面(S4) → WebUI 存活证据面(S4b, 改动面扩到 webui/) → 守阵(S5) → 文档与收尾(S6)。
明确不在范围① 不动 hr_check.allow_window 等运维侧缓解(那是绕开, 不是修复); ② 不为「通道离线」新增前端替代可见性(如状态栏离线角标) —— 见 §05 D2; ③ 不动判定侧对 verified/index 的任何语义。
Is 已修问题?否。异常家族本来就分了层(见 §03.1), 「超时」是漏建模, 属设计缺口而非回归。
用户追加口径 (本轮)「浏览器离线」与「扩展离线」必须分清。二者在端点观测面上同形(都表现为「没人来联系」), 根因与动作却相反: 前者是正常作息(应静默), 后者是配置/启用故障(必须告警)。因此「通道/环境层」不得整层静音 —— 那会把「用户以为在跑、其实扩展早已停用」一起吞掉, 是比原问题更危险的新混淆。
用户口径 ④ (26-10-09-0856)「扩展只能本机」是设计缺陷, 未来须支持跨机(NAS + 外部扩展)。→ 入池 issue 26-10-09-0855, 另立计划 26-10-09-0856(专题 hr-channel-remote)。对本计划的影响: 原「设计边界」callout 定性翻转(见 §03.6.1)。
用户口径 ⑤ (26-10-09-0913)「WebUI 在线而扩展不在线」适合发 WebUI 警告, 不静默; 无需判断是否同机 / 同源。→ 判据极简化: 只看「WebUI 是否活跃」(W-a/W-b/W-c 全部撤销, S4b 退化为直接复用既有 is_active()); 出口改为「活跃 ⇒ 入环告警 / 不活跃 ⇒ 静默」(§03.6.1 / D2 ③ / D4)。
本计划拒绝的一条路线: 给这类记录挂 extra={"web_silent": True} 让前端跳过。它把「前端」这个词写进了 HR 业务代码 —— 产生点要知道出口的存在, 这是耦合; 而且它只让前端看不见, 下面三处污染一点没动(见 §03.3)。用户判定为「补丁」, 采纳。

03方案设计 (归属分层)

3.1 分层骨架本来就存在 —— 这不是「缺一层」

项目已确立判据, 写在异常家族的 docstring 里: 「与 HrChannelStopped / HrChannelQuota 同一套判据: 能不能靠重试解决」(hr/fetcher.py:52–64)。即异常即分类已经是本项目的范式, 通道层与账号层都已建模:

HrFetchError                    # 基类: 通用取数失败(计失败)
├─ HrChannelUnavailable         # 通道/环境层: 没有可用通道
│   ├─ HrChannelStopped         #   叫停(程序自己的决定, 非事件)
│   └─ HrChannelQuota           #   扩展侧硬上限(后端频控失效信号)
└─ HrLoginExpired               # 账号层: 需人到场登录

  (裸 HrFetchError)  # !「等扩展超时」没有自己的类型, fetcher.py:154

洞口的位置恰好最致命: 唯一漏建模的那一支, 正落在最吵的路径上 —— 它掉进基类, 于是在 service 里被当作「页面取数失败」处理, 套上 EVENT_PARSE 的 [HR 页面改版] 前缀, 最后进前端错误环。

3.2 归属层模型 (本计划的正式口径)

通道/环境层不能是单一桶(用户口径③)。它内部至少有三档, 判据是后端能观测到什么证据 —— 而不是猜根因:

层 / 子类成员判据 (后端可观测量)出口
通道 · 预期离线浏览器按作息关闭无联系 且 WebUI 不活跃(可再叠加 allow_window 之外)仅后端 log(降到 DEBUG/INFO) —— 这就是「用户睡觉去了」
通道 · 可定位故障扩展在敲门但 token / origin 不对被拒接触计数 > 0(有人来敲)后端 log + 告警且能指名根因(「扩展在联系, 检查 token」)
通道 · 无联系浏览器未运行 / 扩展未启用 / 未安装 / 等回传超时端点在监听 且 无任何接触(成功与被拒都没有)后端 log; 若 WebUI 活跃 ⇒ 发 WebUI 警告(不静默), 否则归「预期离线」静默(§03.6.1 / §05 D2)
账号层登录失效页面是登录页后端 log + 弹窗(每站一次)
站点 / 内容层改版 · 字段 · 排序 · 计数 · 守恒 · 零行页面结构 / 字段 / 排序 / 防伪判据后端 log + 前端错误历史

层内判据沿用既有那条: 能不能靠重试解决。超时的解是「等通道恢复」—— 与 HrChannelUnavailable 同解, 故归通道层。

3.3 量级混淆的真实代价 (为什么必须禁止, 而不只是"标签难看")

前端错误历史只是其中一面。下面三处都在前端之外, 只滤前端等于「把报警器的线剪了, 报警原因还在烧」:

#污染位置后果
P1写进 wave.notesservice.py:684、733「页面取数失败: 等待浏览器扩展取数超时」进站点文件, 报告与 WebUI 的 notes 都读它 —— 环境噪音进了持久证据链
P2推进档位失败计数service.py:685 → 1495–1498浏览器连关几晚可能攒到 LANE_FAIL_ALERT_STREAK=3, 把环境问题升级成 ERROR「疑似改版, 建议走查」 —— 环境态被误判成站点结论
P3action 语义被改写service.py:666–686落 ACTION_ERROR 而非 ACTION_NO_CHANNEL —— 「通道不可用」在状态机里被伪装成「站点故障」
P4鉴权失败按 ERROR 无节流server.py:212–215扩展 token 配错时, 扩展每 60s 敲一次 ⇒ 每分钟一条 ERROR ⇒ 进前端错误历史 + 触发系统通知(默认 min_level=ERROR)。一个持续配置态被按最高级别刷屏 —— 与本计划主题同源(瞬态/配置态被当成最高量级故障)

3.4 为什么「出口打标记」是补丁, 而「分层 + 出口声明」不是

做法语义耦合方向
extra={"web_silent": True}「前端别收我」产生点必须知道前端存在 —— 出口的意志泄漏进业务代码
hr_domain="channel"「我属于通道层」产生点只描述归属; 出口自己声明「我收哪一层」 —— 两者靠「层」这个共享词汇解耦

区别的实质: 前者要在每个调用点记得加标记(漏一处就漂移); 后者由单点按事件对象附加层信息, 调用点只有一个动作 —— 「选哪一个事件」。要让「通道层事件贴上站点层标签」这件事在代码上不可表达, 而不是靠约定去拦。

3.6 可分辨边界: 后端能分清什么, 分不清什么

「浏览器离线」与「扩展离线」是否要分清? 先得承认后端观测面的极限 —— 否则只是把猜测包装成结论, 那正是本计划要消灭的那类错误。而本轮结论(口径⑤)是: 不必强行分清 —— 我们不推断「是什么离线」, 只问「有没有人在用」(§03.6.1), 该问句由既有信号直接回答。

后端能观测不可观测
① 端点是否在监听(ChannelStatus.listening) · ② 最近一次成功联系(last_contact_ts) · ③ 曾联系过的扩展 origin(extensions_seen) · ④ 被拒的敲门(401/403, 当前只进日志、未入状态)浏览器进程是否存在 —— 后端不能主动连浏览器, 浏览器也不会通知它
原则性不可分辨: 浏览器关闭 → 扩展的 chrome.alarms 不触发(仅在浏览器运行时走) → 无任何请求; 扩展被停用 / 卸载 → 同样无任何请求。两者在观测面上逐字同形。任何声称能自动区分它们的判据都是在猜。能做的是把不可分辨的格子缩到最小, 并如实说明。

但不可分辨的格子可以靠第二条独立观测线缩小 —— WebUI 的存活证据(§03.6.1)。

3.6.1 WebUI 存活证据: 第二条独立观测线

WebUI 与 HR 端点是同一个 auto-qb 进程。所以「WebUI 有活跃」= 有人在照看这个实例(不论从哪台机器、哪个浏览器访问)。本轮口径(用户指令): 不判断是否同机 / 同源 —— 判据只问「WebUI 是否活跃」这一件事; 「WebUI 在线而扩展不在线」这个状态本身就值得警告, 无需再推断「扩展离线」这种更强的结论。

观测组合可下的结论
端点有成功联系(last_contact_ts 新鲜)通道健康。
WebUI 活跃 + 端点无任何联系发 WebUI 警告, 不静默 —— 有人在用 WebUI, 但扩展未在联系(浏览器可能已关 / 扩展被停用 / 卸载 / SW 崩溃 / 跨机网络断)。这正是 401 抓不到的那一类。
端点有 401 / 403 敲门扩展在跑但配置错(浏览器也在跑) —— 问题在 token / origin。
WebUI 不活跃 + 无任何敲门「浏览器未运行 或 WebUI 未开 或 扩展未启用」—— 归预期离线(§03.2 第 1 行), 仅后端 log。
端点未在监听本实例自身问题(HrChannelUnavailable 既有分支, 与扩展无关)。
曾经联系过, 之后中断配置曾经成功 ⇒ 排查重心从「配对是否对」转向「浏览器是否被关 / 扩展是否被停用」。

两条线互补: 401/403 覆盖「扩展在跑、配置错」, WebUI 活跃覆盖「有人在用、但扩展根本没在联系」。分子落在哪个格子, 取决于拿到哪条证据。

判据的极简形态 (本轮用户指令 —— 撤销 W-a / W-b / W-c)
不引入同源 / 同机判断。曾考虑过 W-b「活跃必须与扩展同源 —— 来源地址交集」与 W-c「WebUI 与扩展同浏览器」, 现一并撤销: ① 它们要求新增「带来源的活跃面」, 改动面从 hr/ 扩到 webui/, 成本高; ② 更关键 —— 它们推断的结论(「扩展离线」)比我们需要的更强。我们只需知道「有人在看 WebUI, 而扩展没在联系」, 这由既有信号直接给出。
既有信号已够: WebUIRuntime.last_seen + is_active()(webui/runtime.py:176、367–373, 窗口 WEB_VIEW_TTL = 10.0)本来就存在, 且由 SSE keepalive 每 5s 自动刷新(routes/events.py:61, 另有 20+ API 路由也 touch)。故 S4b 退化为「直接复用」, 不再新增任何面。

残余代价 (明示): 不判断来源 ⇒ 若你从手机 / 另一台机器长期开着 WebUI, 而装了扩展的那台机器浏览器关了, 也会触发该警告 —— 但它是警告而非误判: 「扩展确实没在联系」这一事实成立, 只是它未必意味着故障。这是买「判据极简 + 不误静默」付的价格, 用户已确认接受。

同时把被拒的敲门记进端点状态面(S4) —— 于是「扩展配错」从「日志里的一行」变成「状态上的一个事实」, _check_channel_silence 才有资格在文案里区分这些情形。

⚠ 口径更新 (26-10-09-0856): 原「设计边界」已被判定为设计缺陷 —— 此前本计划把「HR 取数要求扩展与 auto-qb 同机」记作正当的设计边界(「NAS 实例应不装扩展、走只读共享数据」); 用户判定其不可接受, 要求未来支持「NAS + 外部扩展」形态, 已入池 issue 26-10-09-0855 并另立计划 26-10-09-0856(专题 hr-channel-remote)。技术事实不变(两端确实都写死回环), 变的是结论的定性: 从「受支持 = 不驱动扩展」改为「该形态应当被支持」。

#事项建议 (待拍板)
D1 HrChannelTimeout 的归位: 继承 HrChannelUnavailable(并入「无通道」出口), 还是与它平级、单列一个通道层分支? 推荐继承 HrChannelUnavailable。按既有判据「能不能靠重试解决」, 超时的解是等通道恢复, 与「无通道」同解; 且可直接复用 _warn_no_channel 的每站一次 + 恢复即重置节流, 比现在「每 6h 一条」更安静。代价: action 由 ERROR 变 NO_CHANNEL, 需确认下游消费面(报告 / HR 面板)对 ACTION_NO_CHANNEL 的展示无回归。
D2 静音的范围: 「通道/环境层」三档里, 哪些不上前端? 本轮按档定(其中 ③ 已由用户拍板): ① 预期离线(无联系 + WebUI 不活跃) ⇒ 静默(只后端 log), 这正是你要的; ② 可定位故障(有被拒敲门) ⇒ 必须上前端 —— 它是真问题, 静音等于把「扩展早已配错」藏起来, 是最危险的一种静默; ③ 无联系 ⇒ WebUI 活跃则发 WebUI 警告 / 入环(不静默), WebUI 不活跃则静默(本轮用户口径⑤, 见 §03.6.1)。
D3 通道层文案是新增独立标签 [HR 通道不可用], 还是并入既有 [HR 通道静默] 一族? 推荐新增独立标签(EVENT_CHANNEL): 「静默」是端点级、按时间判定(6h); 「超时」是单次取数失败 —— 两者归同一层但不同事件, 合并会让「grep 锚点」失去区分度。
D4 是否采信 WebUI 证据? — 本轮已闭环 已拍板(用户口径⑤): 采信「WebUI 是否活跃」这一极简信号; 结论只说「WebUI 有活动而扩展未在联系」, 不推断「扩展离线」, 也不判断同源 / 同机(W-a/W-b/W-c 全部撤销, S4b 退化为直接复用既有 is_active())。收益: 把「扩展被停用 / 卸载 / 跨机断」从不可分辨提升为可提醒; 代价: 远端 WebUI 活跃也会触发(已接受, 见 §03.6.1 残余代价)。

7.1 已接受的风险

#风险评估
R1通道层静音后, 「HR 保护实际没在跑」这件事在前端不可见接受(用户明确要「不发到前端」)。替代可见性 = HR 面板的通道最近联系时间; 建议另立离线角标计划(§05 D2)。
R2浏览器开着但扩展偶发卡顿导致的超时, 也从「计失败」变为「通道层让位」按判据这是正确归位: 它同样靠「等下一次轮询」解决(轮询周期 60s < 窗口 180s)。代价是这类瞬态不再进档位失败统计 —— 这是买「不混淆」付的价格。
R3S2 的 except 落点若与预期不符(继承链 + 顺序), 可能被更宽的 except HrFetchError 先接住本步唯一需红验处: 临时移除新分支应能观察到 P1/P2 复现。
R4「无联系」档在 WebUI 不活跃时被静默 ⇒ 「浏览器没开 / 扩展被停用」在前端不可见已按本轮口径收敛: WebUI 活跃时会提醒(D2 ③); 仅当 WebUI 也不活跃时才静默 —— 那正是「没人在用」, 静默是正确行为。后端原则分不开「浏览器关」与「扩展停用」(§03.6), 故文案只陈述「未在联系」而不点名根因。
R5远端 WebUI 活跃(手机 / 另一台机器)也会触发该告警接受(用户裁量): 已不判断来源(W-b 撤销)。影响是「你从手机看 WebUI 而 PC 浏览器关了」也会收到告警 —— 但结论「扩展未在联系」为真, 属提醒而非误判, 且比「误静默」安全。文案不点名根因, 只陈述事实。
