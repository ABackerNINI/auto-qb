§01目标与设计原则

原始请求。「kb.nav 关联文档交互展示优化: 当前台账页中只能看到文档的认领链/反向引用/同专题件等, 且无法跳转查看这些文档的关联, 只能自己查找。初步想法是增加跳转功能, 增加关联文档拓扑图展示方式, grilling」。后续两条修正:「Q4 A/C 先各做一个简单的演示」(先看真实数据原型再定布局)、「C 能否增加限制在当前正在查看的文档与其所有关联文档上, 全库能力也保留。Q7 拆」。

目标(做到什么算成)。

  1. 关联可下钻: 从一件出发, 点它的关联件不再甩去原文丢上下文, 而是在抽屉内切件(带返回栈), 原文降级为次级按钮;
  2. 关系可看: 三个不同问题各有自己的视图 —— 「这一件连着谁」(局部环) / 「这件事散在哪几个族」(关联泳道) / 「全库谁孤立、哪个专题是巨团」(全库团级图);
  3. 每条边都可解释: 页面上的每条引用要么能点开, 要么标出为什么不可点(库外件 / 归档回退 / 仓库根 / 真失效), 不再出现笼统的「(未入库)」。

设计底线(不变量)。

  • 不动数据源口径: gen_doc_map.collect() 是 kb.docmap / kb.check / 索引生成的共同单点, 解析只加在导航层 nav_data, 不扩扫描面、不改「台账件」定义;
  • 壳即全部: 单文件、零 CDN、离线可开(file://); tests/test_kb_nav_shell.py 禁一切 http(s):// 外链, 所以图形不准引任何库, 手写 SVG;
  • 守卫口径对齐: 归档回退只在 memory-bank/testing/baselines/ 前缀的 ref 上生效(与 check_claim_chain 同款闸门), 否则台账件被删而同名切片还在时, 真死链会被说成可点;
  • 红线不进导航: config.yml / auto-qb-data/ / .git / .env 及一切 .. 穿越路径一律判死, 不给可点链接;
  • 跨轮次的 UI 取舍不留在组件闭包: 档位必须能在轮询重挂后存活。

§02现状与痛点

事实先于方案(原型实测)

抽屉里的关联件其实一直有 href(nav_page.html 的 <a class="rel" href="/memory-bank/…">), 真正点不动的是 1812 条 ref 里的 579 条:

情况条数现状
目标文件存在, 但不在 collect() 扫描面(pitfalls/ testing/ progress/ activeContext/ conventions/)324渲染成灰字「(未入库)」, 无 href
声明路径失效, 实际躺在 testing/baselines/attachments/(按 basename 可找回)253同上
文件在仓库根下(resources/*.html), 导航页静态路由不代理2同上
真失效0——

痛点四条

  1. 守卫绿 ≠ 页面可点: gen_doc_map 给 kb.check 做了归档回退, 所以认领链守卫是绿的; 但 nav_data.collect() 与前端 byLink 都没有这条回退 —— 页面说死链, 守卫说没事。
  2. 能点 ≠ 能看关联: target="_blank" 直接甩到原文, 跳出去就丢了台账上下文, 回不到「这件的上下游」。用户感受到的「只能自己查找」本质是没有下钻, 不是没有链接。
  3. 全库一键铺平没有可读性: 第一版把 774 个「形态 × 专题」团全部铺开, 其中 676 个只有一件 —— 画出来是一面对称的方块墙, 结构信息归零。这是「族泳道 + 专题聚簇」直接实现的实测反例。
  4. 静态导出的链接前缀写死: STATIC_LINK_PREFIX = "../../memory-bank/" 只有输出到仓库根下两级才碰巧对, --gen-static out/ 或绝对路径导出会让所有链接算到仓库外。

§03方案总览

四个落点, 决策编号对应 §06。

落点 1 —— 认领链五态解析 (D2)

  • nav_data.collect() 之后做加法 enrich: 每条 ref 解析成 {t, st, raw}, st ∈ ok / ext / repo / basename / dead —— ok 落在台账四类件(可下钻)、ext 库内但不在扫描面(可打开)、repo 仓库根下(存在但导航页不代理, 只标示)、basename 归档回退命中、dead 真失效;
  • 判据对齐 check_claim_chain: ref 是仓库根相对; 归档回退只对 memory-bank/testing/baselines/ 开头生效; _inside() 做 resolve 后围栏, _denied() 按真实落点拒红线;
  • 顶层新增 data.ext: 库外件的反向边(只扫「已被台账件引用到的」库外件, 有界), 否则坑档/基线的「谁认领我」永远看不见。

落点 2 —— 三档关系图 (D1/D3/D5)

  • 局部环(抽屉内嵌, compact): 本件居中, 环深 = 跳数; 边三态 —— 双向闭环实线 / 单向虚线带箭头 / 库外或失效点线。抽屉 380px 下折叠到 18 个节点(缩半径 0.74), 其余给「另 N 个已折叠」提示;
  • 关联泳道(全屏): 只画本件 + 它全部一度关联所在的团, 按族分层; 这里保留单件专题 —— 用户要的就是「本件 + 全部关联」, 折进碎片等于没画;
  • 全库团级图(全屏): 只画成员 ≥ 2 的 98 个团 + 每族一个「碎片」节点(承接 676 个单件), 碎片链默认不画(它承接数百条 ref, 画出来是假枢纽), 保留节点角标计数。

落点 3 —— 组件拆文件 + 静态前缀现算 (D7)

  • nav_graph.js(577 行)承载图组件, 只暴露 window.MBGraph, 零依赖零请求;
  • 服务模式走 GET /nav_graph.js 路由; --gen-static 时内联回单文件, 静态件仍 file:// 可开;
  • 链接前缀按 out_dir 相对仓库根 relpath 现算, 跨盘(D:\ 导出到 C:\ 仓库)退 file: 绝对前缀。

落点 4 —— 壳接线与档位存活 (D4)

  • 抽屉内嵌图(#dGraph) + 全屏层(#gStage 三档); 节点点击走 openRowDetail 抽屉内下钻, Ctrl/中键仍开新标签, Esc 逐级退(全屏层排在遮罩之前);
  • 档位 {scope, steps, showFrag} 提到壳侧会话态 S.graph: 抽屉每 30s 轮询都会 destroy() + 重挂组件, 状态留闭包必被洗回默认; applyData 后用新数据重挂全屏层并保留 center(先判中心件还在库)。

§05待拍板清单

本计划无待拍板 —— Q1–Q7 已在 grilling 全部拍定(§06)。遗留项如下, 均不阻塞:

  1. 全库图的规模上限未实测: 当前 1138 件 / 98 团画得动; 件数翻倍后碎片节点会重新变成"墙", 需要在真到那一步前重估是否改分层聚合;
  2. 非四类件的反向引用只做一度: data.ext 只收「被台账件引用到的」库外件, 二度以上不追 —— 有界性是刻意的, 但用户在坑档页面上仍看不到完整上下游;
  3. nav_server 无鉴权: 只绑回环 + 只读 memory-bank, 但静态路由之外的路径面每次加新端点都要重判一次(本次新增 /nav_graph.js 已核)。
