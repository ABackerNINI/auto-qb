kb 闸门 timekit 超时治理：按改动收窄全库扫描

本篇只回答「怎么修」：把 kb 闸门里两条全库扫描型脚本按本次改动清单收窄，同时补齐「复跑阶段远端合入文件」与「命令行长度」两个正确性前置漏洞；不动并发模型、不改 timeout、不聚合 wrapper。根因与现场证据的权威在 issue 26-11-09-0441 §05 与任务档案，本篇只引用不重写。方案经 2026-11-09 grilling 四问拍板（D1–D4，§06），本轮只定稿、不实施。

§01目标与设计原则

背景。ship.commit 的 kb 闸门（.commands/my-commit-flow/.my-commit-flow.toml，9 条脚本、逐 job 固定 timeout = 60）在 2026-11-09 04:41 满载机上连续 4 次把 timekit.py --check 判成 60s 超时，第 5 次复跑自过。认领轮（05:26）把根因收敛为固定 60s 超时 × IO-CPU 密集型全库扫描 × 并发放大 × 满载机：空载单跑 4.1~4.3s 有十余倍余量，4 路并发把同一脚本放大到 14.2~14.4s（3.3 倍），冷缓存 / 有负载单跑 9.6~12.6s，余量被吃光即判死；真实 run_gates 4 池跑整链本轮 5.23s 全绿，60s 判死未复现，不能判已消失。

目标：把 kb 链两条全库扫描型脚本从「每次提交扫全库」改成「只扫本次改动」——timekit 4.23s → 约 0.4s、check_html 1.69s → 改动级——使 3.3 倍并发放大后仍只有约 1.6s，从工作量侧消掉根因，而不是挪阈值或降并发。算成的标准 = §04 的 S1–S5 验收判据全绿，且复测数字回写本计划。

设计底线（不变量）：

  • 改动清单单点：一律复用预检 changed_files() 与 <changed:GLOB> 展开，闸门脚本不自查 git —— 复跑阶段树已净，自查 git 语义就错。承袭 26-11-01-0434 §01 底线 1。
  • 守阵逐字匹配：tests/test_memory_bank_docs.py::test_commit_gate_covers_kb_check 用正则在闸门配置里找 <脚本>.py --check。每条 run 必须保留该前缀，增量参数只加在后面；kb.check 的 run 列表一条不动，它是全量兜底入口。
  • 无参即全量：timekit / check_html 不带 --files / 显式 paths 时行为逐字不变，kb.check 与手工全量调用不受影响；全量覆盖仍由它兜住。
  • 不动并发模型与 timeout：GATE_WORKERS = 4（26-11-01-0434 D2，_pipeline.py:489）与 timeout = 60 原样；收益只来自减工作量。
  • 保守回退：展开失败按既有语义 STOP 不降级；改动面判定拿不准时宁可全量跑。

§02现状与痛点

逐条实测与适配性裁定（2026-11-09 05:5x 本机热缓存，python 直跑各脚本 --check 单次，含解释器启动；数字用于量级判断，验收以同口径复测为准）：

#脚本耗时裁定依据
1gen_kb_index0.11s不收窄build_all 重算全库生成物再逐字比对；生成物常不在改动清单里，收窄就漏「索引没重生成」——正是它要拦的
2gen_doc_map0.81s不收窄认领链双向校验，目标常是未改动文件；还有「没有任何件声明引用 → 判红」的全量兜底
3gen_baseline_recent0.09s不收窄（不值）单文件属性，但要动守阵，收益不足 0.1s
4check_wording0.35s不收窄族 B 是存量冻结数目制（len(num_hits) > FROZEN_TEST_NUM_COUNT），增量会让「新增手抄」判据恒失效
5check_mutation_anchor0.11s不收窄锚文件本身通常未改动（改的是任务档案），收窄 = 守卫无对象
6check_doc_templates0.13s不收窄（不值）本就是「新增面」语义，但动守阵不抵风险
7timekit4.23s收窄文件名 / 元数据 / 正文三层全是单文件属性，不依赖其它文件
8check_status_drift0.38s不收窄（不值）状态一致性属单文件属性，合计收益小
9check_html1.69s收窄L1+L2 结构检查是单文件属性；collect_files() 已支持显式文件参数（注释即写「闸门 <changed:> 形态」），闸门也已有 --vnu --strict <changed:**/*.html> 增量行

合计 7.90s；7 + 9 占 5.92s（75%）。其余 7 条要么语义上必须全量，要么合计不足 0.6s。

工作量证据。timekit --check 对 memory-bank 全库（2838 文件 / 31.5 MB）做 check_filenames 的目录扫描（约 0.39s 固定成本）+ check_metadata 与 check_body 各一次 mb.rglob("*") 并逐文件读全文 + 逐行正则。单次 rglob 仅 0.03s、_read 占 10%，瓶颈是正文行正则。模拟把扫描面换成 k 个文件：k=1 → 0.36s、k=100 → 0.45s（4.23 → 约 0.4s）。顺手的算法优化（两轮 rglob 合一、每文件读一次、无数字行预筛可跳 53.1%）合计仅 -0.8s，只作附带项、不作主线。

放大与排除项。A/B/A 干净对照：单跑 4.32/4.32s → 4 路并发同一脚本 14.19~14.35s → 撤负载 4.28/4.28s；同族坑档 perf-measurement.md 记过同一命令 15.94~209.77s 漂移、parallel-run.md 记过高负载下 CreateProcess / communicate 挂死。快照 env 对照（plain 4.16s / snapshot-env 4.27s / plain 4.12s）已排除「扫描路径被快照环境改变」。本机同族形态见 issue §05。

纯增量必须先补的三个洞：

  1. 远端合入漏检：commit.py:587 复跑闸门用的是同一份 present 清单（:579 注释「改动清单也不变」）。远端 rebase 合入的 KB 文件不产生本地 diff ⇒ 纯增量会让「合流后第二轮闸门」对这批文件形同虚设。.my-commit-flow.toml:173-174 的 sync_agent_skills 闸门注释也记过同款形态（从远端 pull 进来的 skill 改动在本地不产生 diff，按路径匹配永远命中不了）。
  2. 命令行长度：<changed:> 经 run_gates 走 shell=True（cmd.exe 8191 上限），平均相对路径 69 字符 ⇒ 100 个改动文件约 6856 字符，大批量 KB 提交会截断。
  3. 守阵硬约束：见 §01 底线 2，run 前缀不能改。

§03方案总览

主线 A（D1）：增量减工作量 + 扩清单补漏 + 长度守卫。减到约 0.5s 后即便 3.3 倍并发放大也只有约 1.6s，根因被消掉；不动并发模型、不改 timeout、不推翻上游 D2。

期步内容定位
P0S1–S3timekit --files / check_html 显式 paths / 守阵钉收益主体（-90%），零正确性风险
P1S4复跑清单扩面 + 展开字符上限守卫P0 的正确性前置：与 P0 同批验收，不得拆开发布（见 §07 R5）
P2条件分支分档 timeout（60 → 180/300）；重型 job 独占池仅 S5 实测仍触发超时 / 尾部不稳时启用；独占池须用户再拍板（§07 R4）

「合并扫描 / 聚合 kb.check」否决理由：与计划 26-11-01-0434 方案 B 拍板的「明确不做 wrapper（守阵逐字匹配 <脚本> --check）」直接冲突，且聚合后失败定位粒度变粗。

明确不做：9 条全收（4 条全量语义硬冲突、3 条合计不足 0.6s，D2）；改 GATE_WORKERS / 改 timeout（D1）；杀树收尸、失败重跑（D3 独立立项），缓存层（§03 判复杂度过高，排除）；本轮实施 S1–S5（D4 只出方案）。
