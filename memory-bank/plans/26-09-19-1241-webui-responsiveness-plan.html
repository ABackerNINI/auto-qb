01

结论先行

「不跟手」不是一个性能问题，而是四段延迟叠加的结果：点击之后界面什么都不做（没有即时反馈）， 命令还要等主循环的下一个 2 秒节拍才被消费，回执又固定先睡 500 ms 才第一次查， 最后行状态要等下一轮同步 + 下一轮轮询才变。四段叠加，用户感知就是「点了没反应，过几秒突然一起变」。

好消息是：这四段都不需要动架构就能砍掉。主循环加一个唤醒事件（命令一到立即消费）、 回执改成首查不等、前端做乐观 UI、批量动作合单 —— 这四项做完，主观延迟从「秒级」降到「百毫秒级」， 且全部保持「写操作只在主循环线程」的既有约束。

剩下的一类（大库下每次渲染整树重算、每 2 秒全量回传四视图）属于规模问题： 种子量上去之后，单次点击的渲染成本与每轮响应体同步膨胀。这部分放进 P1，用「按视图回传 + 行窗口化 + 去布局抖动」解决。

下一节（02）把本轮讨论过的 14 个候选方案按「感知 / 命令 / 真实状态 / 规模」四层摊开横向对比， 含 3 个被否决方案与各自的否决判据 —— 想直接看权衡去那里。

先说清一件事

视图重建本身不是瓶颈。TASK017 实测过：200 / 1000 / 3000 个种子重建四视图耗时 4.97 / 25.22 / 79.36 ms，占 2 秒 tick 预算 0.25% / 1.26% / 3.97%。 真正的开销在传输与渲染侧：每轮把四份视图全量序列化回传，前端整表替换后整棵 Vue 树重渲染。

04

四类根因

A · 命令要等主循环节拍（P0）

所有写操作必须落在主循环线程（项目黄金法则「单一写线程」），这个约束是对的、不动。 但现在的等待方式太粗：主循环 _throttle() 无条件睡满 main_tick （qbmanager.py:60–75），命令在队列里躺到下一轮才被 _drain_web_commands() 取走。 队列是现成的唤醒源，却没有用起来。

B · 回执首查固定 500 ms，且全程无即时反馈（P0）

waitCmd()（app.js:2007）第一次轮询前先睡 500 ms —— 哪怕命令 20 ms 就执行完了也要等满。 同时整个交互路径上没有乐观更新、没有 pending 态、没有禁用双击：用户在等待期唯一能看到的就是「什么都没发生」， 于是重复点击，把 N 条命令灌进同一个队列。

C · 每 2 秒全量回传 + 全树重渲染（P1）

/api/state 一旦版本变化，就把 groups / singles / shows / torrents 四份视图全量回传（web_view.py:567），而前端一次只用其中一份。 前端拿到新数组后整表替换（app.js:1508–1524），触发整棵 Vue 树重渲染 —— 这是单个巨型 Vue 实例， 任何响应式变化（点一行、开个菜单、敲一个搜索字符）都会重跑整棵树。 种子页无虚拟化（prism/index.html:544 v-for="m in filteredTorrents"）， 3000 个种子就是一个屏幕里几万个 vnode 与 DOM 节点。 叠加 updated() 钩子每次渲染后都做一次 getBoundingClientRect()（app.js:1136 → 3975）， 强制同步布局。

D · 批量动作 N 条命令 × N 次 qB 调用，串行阻塞主循环（P0）

bulkAct()（app.js:2703）对 pause / resume / recheck 是逐目标 POST 并各自等回执， 而后端已有单命令批量端点 /api/torrents/bulk（web.py:521）与 _cmd_bulk_torrents（一次 qB 调用 + 聚合回执）却没被用上。 后果是双向放大：前端 100 个目标 = 100 次 POST + 100 条 500 ms 轮询；后端 100 条命令在同一个 drain 里 串行各发一次 qB HTTP 请求，主循环被占满，连状态刷新都停摆 —— 这正是「点批量之后整个界面卡住」的成因。

P0-0

埋点量化

P0

在改任何代码之前，先把「慢在哪一段」变成数字。否则每改一项都无法证明它生效。

改什么
后端 _web_results 增加 queued_ts / start_ts / done_ts，/api/cmd/{id} 一并回传耗时分解；前端 waitCmd 记录「投递 → 回执」耗时，refresh() 用 performance.now() 包住赋值 + $nextTick，超 50 ms 打 warning。
交付

风险
极低。仅新增字段，前端不消费即无影响。
P0-1

命令即时唤醒主循环

P0

设计已修订（v2） —— 唤醒只触发「消费命令」，不触发 tick。 初版设想是「投递即 wake，主循环提前跑下一轮」，但那会让 main_tick 不再是 tick 频率的唯一决定者， 连带把 max_tasks_per_tick 与两个每 tick 预算一起放大（详见下一节）。v2 把两者解耦：

结构
循环拆成两条独立时间线 —— 命令线：任何时刻被唤醒即 _drain_web_commands()（+ 汇报确认检查，自带 ≥1 s 间隔）； tick 线：next_tick_at 到点才跑 _tick()（含 run_due），跑完推到 now + main_tick。等待 = wake.wait(剩余时间)。
收益
链路第 02 段 0–2 s → 近乎 0，而 _tick 频率严格不变（仍每 main_tick 一次）。
取舍
停止信号：托管模式下 stop_event 与 wake 是两个事件。方案 —— ui.py 在 stop_event.set() 后一并调 manager.wake()（一处改动）；若不接受，退化为 wake 等待 + 每轮循环顶部已有 stop 检查，最坏延迟 1 个 tick。
验收
① 投递命令后 200 ms 内 _web_results 出现回执；② 命令风暴下 tick 次数不增加（连投 100 条命令，2 s 窗口内 _tick 仍只跑 1 次）；③ 无命令时等待仍睡满 main_tick（防忙等回归）。

为什么不能「投递即跑下一轮 tick」

max_tasks_per_tick 的字面语义是每次 run_due 最多弹 N 个（taskqueue.py:184 _pop_due）—— 唤醒后每次仍 ≤ N，字面不失效。但它实际承载的是速率语义：默认 max_tasks_per_tick=20 × main_tick=2s ⇒ 吞吐上限 10 任务/秒。tick 频率一旦由命令决定，这个上限就失效了。

更严重的是自投递命令会形成自激循环：_build_shows_view（web_view.py:513）与 search_torrents（:699） 在索引脏时会自己投递 build_search_index，而该命令单轮可拉 SEARCH_INDEX_BUILD_BUDGET=500 条文件 API。 「投递即唤醒」⇒ 唤醒 → drain(500 次 API) → tick → 重建视图 → 又投递 → 立刻再唤醒 …… 直到索引建完为止， 中间没有 main_tick 兜底 —— 这不是变慢，是打满 CPU 并把 qB 冲垮。

同层受影响的还有两个每 tick 预算：_refresh_torrents（每 tick 一次 qB sync）与 refresh_error_reasons（Web 活跃时每 tick 5 次 tracker 请求）。tick 变密 ⇒ qB 请求变密。

因此 P0-1 加三道保险：① 唤醒只走命令线（tick 线不动）；② 命令白名单 —— build_search_index 这类自投递命令不唤醒；③ 汇报确认检查自带最小间隔，不随唤醒频率放大。

P0-2

回执首查不等 500 ms

P0

waitCmd 改成先查后退避：0 ms 首查 → 150 → 300 → 500 ms 封顶； 强制汇报（reannounce，确认窗口 30 s）另走宽松曲线（500 ms → 1 s 封顶），避免刷请求。

收益
第 04 段稳定 −500 ms；单次快命令（pause/resume）端到端可压到百毫秒级。
风险
请求数略增（仅在命令在途的极短窗口内），可接受。
P0-3

乐观 UI：点击即变

P0

新增 applyOptimistic(targets, patch)：按动作白名单（暂停 / 开始 / 删除 / 限速 / 分享率 / 超级做种 / 强制开始 / 队列调整 / 移动 / 重命名）在本地把目标行立刻改成预期状态，并打 pending 标记（半透明 + 细微动效）； 回执 ok 清除 pending，error 回滚原值并弹错误 toast；下一轮轮询以服务端数据为准覆盖。

收益
把「沉默的几秒」变成「立刻有反馈」。这是主观跟手性收益最大的一项。
取舍
只对结果可预测的动作做乐观（白名单）；强制汇报、重新校验、添加种子这类「结果在远端」的动作不做，改由「等待中」常驻 toast 承担（现有 reannounce 已是这样）。
风险
状态抖动（乐观值被服务端下一轮覆盖时闪一下）。缓解：pending 期间不再被轮询覆盖同一字段，超时 3 s 未确认则回落真值。
验收
断网 / qB 未启动时点暂停：应在回执失败后回滚并报错，不允许留假状态；双 UI（prism / atlas）各走查一遍。
P0-4

批量动作合单

P0

bulkAct 的 pause / resume / recheck 改为一次 POST /api/torrents/bulk （传 keys + hashes + action），等一个聚合回执； 后端 _cmd_bulk_torrents 已有展开组键、去重、缺失计数与单条 qB 调用。删除动作已走这条链，口径对齐。

收益
100 个目标：前端 100 次 POST + 100 条轮询 → 1 次；后端 100 次 qB 调用（串行阻塞主循环）→ 1 次。顺带消除「批量后界面卡住」。
风险
失败文案口径变化（部分成功也报 error 并带缺失计数，前端沿用现有汇总文案）。
P0-5

命令执行后立即同步一次

P0

这是「把主循环提到 50 ms」想买的东西的便宜买法：命令在主循环线程执行完（qB 已改状态）后， 立刻补一次刷新，让真实状态在几十毫秒内进入快照，而不必等下一轮 tick。成本按操作次数计费，不是按时间计费。

红线
必须调完整的 _refresh_torrents()，绝不能只调 store.apply_sync()。 apply_sync 只更新 by_hash + server_state（store.py:81）， 分组索引 / 任务 / 事件 / 搜索索引一概不碰 —— 单调用它会留下"已进快照但未处理"的半刷新态： 新增种子不建任务不归组、删除种子的 on_torrent_deleted 不触发且 store.groups 残留 hash、 状态快照不推进导致事件时机错位。而 _refresh_torrents 本来就每轮都跑，转换与事件由快照 diff 消费一次，天然幂等。
触发点
_drain_web_commands() 整批结束后补一次，不是每条命令后各补一次 —— 否则 N 条命令 = N × 14.5 ms（3000 种子）。
门控
仅当本批含"改 qB 状态"的命令（白名单；reload_config / build_search_index 不触发）； 程序暂停时不补（drain 在 pause 检查之前，但"暂停 = 完全旁观"的语义要保持）；dry_run 不补。
实测
单次 _refresh_torrents()：200 / 1000 / 3000 种子 = 0.87 / 4.86 / 14.52 ms（纯 CPU，不含 qB 往返）。
收益
把链路第 05 段（等下轮 sync）从 0–2 s 压到 ≈ 一次刷新的耗时。
备选 B
不补刷新，改为「把下一轮 tick 拉前」（在 P0-1 v2 的分层结构里改 next_tick_at）。代码更少、完全复用既有 tick 路径， 但需加最小间隔下限（如 ≥ main_tick/2），否则连续点击会把 tick 频率顶上去。
注意
端到端仍受前端轮询 pollSec=2s 限制 —— 真实状态进 store 快了，用户看到仍 ≤2 s。 因此本项与 P0-3 乐观 UI 配套：感知靠乐观 UI，真实值靠本项在下一次轮询时对齐。彻底去掉这 2 s 要走 P2-3（SSE 推送）。
验收
红绿用例：同一状态下连跑两次 _refresh_torrents()，断言 ①状态变化事件只触发一次 ②下载冲突告警不重复 ③缺文件扫描不重复 ④on_torrent_deleted 不重放 ⑤热重载后的事件抑制窗口不被误消耗。

P1

P1-5

qB 客户端加请求超时

P1

_new_client()（qbclient.py:44）未设任何超时：qB 假死时，主循环的命令执行或 Web 线程的抽屉请求会无限期挂起， 表现为「点一下之后整个界面再也不动」。加 REQUESTS_ARGS={'timeout': (3, 10)}（连接 / 读）。

收益
把最坏情形从「永久假死」变成「超时报错 + 走既有重连退避」。
风险
读超时可能截断超大响应（如几千文件的 /files）。取宽松读超时，并保持现有重试与重连逻辑；先在 3000 种子量级实测一次。

红线与不做

  • 不在 Web 线程写状态。 命令仍然只投递、由主循环线程执行（黄金法则「单一写线程」）。P0-1 只是让主循环早点醒来，不是让它旁路。
  • 不把节流改成忙等。 _throttle 必须保持真实阻塞；新增一条防回归用例。
  • 唤醒不得改变 tick 频率。 main_tick 是 tick 的唯一节拍源：命令只提前"被消费"，不提前"跑一轮任务"。 由此 max_tasks_per_tick 的吞吐上限（N / main_tick 每秒）与两个每 tick 预算（一次 qB sync、5 次 tracker 请求）保持原样。
  • 不动生产文件：config.yml、auto-qb-data/。若本计划引入新配置键（如 web.poll_sec），必须同时进 validate_config 与 config/schema.py（守卫测试会查）。
  • 双 UI 同步：prism 与 atlas 两套模板/CSS 一并改，不落下一套（历史教训：星图漏改导致观感回退）。
  • 不靠缩短 main_tick 换响应。 轮询频率与响应延迟是两件事：命令侧用 wake 事件（≈0 ms、零成本）， 状态侧用「命令后单次同步」（按次计费）。把主循环提到 50 ms 是 40× 成本换 0 收益（收益被前端 2 s 轮询截断），见附录 A1。
  • 不预先做 P2-3 推送化。 轮询在 P0/P1 之后已足够跟手；推送化涉及鉴权、重连、与主循环的耦合，单列一期评估。
  • 提交纪律：日常在 develop，以 Gitee 的 origin/develop 为准；GitHub 只作镜像，直连失败不重试。
A1

附录 · 方案 B「主循环 50 ms」可行性评估

提议：主循环改成 50 ms，任务仍按 main_tick=2s（= 50 ms × 40）触发，种子状态刷新提到 50 ms。 结论：不可行 —— 成本 40×，收益被前端 2 s 轮询截断为 0。下面是实测与逐条判据。

实测：单轮各项成本（Fake 替身，纯 CPU，不含 qB 网络往返 ⇒ 下界）

三条硬否决

  • ① 3000 种子下单轮 61.4 ms > 50 ms 预算 —— 循环永远追不上节拍，_throttle 的剩余时间恒为 0， 退化成无间隔连续跑。这形成正反馈：负载越高 → 单轮越慢 → 越没有休眠 → CPU 100%。当前的 2 s 节拍正是这条正反馈的隔离带。
  • ② 空闲成本 ×40 —— 现在空闲（无浏览器）时每 2 s 才 14.5 ms ≈ 0.7% 核；50 ms 后是 29% 核，且永久。 这是"没人操作时也在烧"的开销，与长驻托盘进程的定位冲突。
  • ③ 每 tick 预算同步放大 40× —— qB sync 0.5 → 20 次/秒；refresh_error_reasons 2.5 → 100 次 tracker/秒； _build_search_index 250 → 10000 次文件 API/秒；run_due 若每次仍弹 20 个 ⇒ 任务吞吐 10 → 400 个/秒， max_tasks_per_tick 的限流作用被完全架空（这一点与 P0-1 v1 是同一类问题，只是倍数从"不定"变成"恒定 40×"）。

收益侧：买到的东西相对现方案为 0

  • 命令延迟：50 ms 轮询换来 ≤50 ms；而 P0-1 v2 的 wake 事件是 ≈0 ms 且零成本。相对收益 = 0。
  • 状态可见延迟：后端刷新再快也救不了 —— 前端 pollSec=2s 是端到端的下限。 要让前端也 50 ms，就得每轮回传 MB 级响应体 × 20/s，传输与渲染（P1 要解决的正是这个）先崩。 也就是说：50 ms 循环把瓶颈从"后端节拍"搬到"前端轮询"，端到端延迟不变。

真正的诉求与更便宜的买法

想要的是「操作之后立刻看到真实状态」。按时间提频是最贵的买法；按事件触发是最便宜的： 命令执行完补一次完整刷新（P0-5，单次 14.5 ms @3000，按操作次数计费；注意不能只调 apply_sync）， 感知层交给乐观 UI（P0-3）， 彻底去掉前端那 2 s 下限则走 SSE 推送（P2-3）。三者相加的成本远低于把整个循环提频 40 倍。

附录 · 分层节拍「刷新 50 ms / 视图 1 s / 任务 2 s」可行性评估

结论：技术可行（与 A1 那版 50 ms 全量不同 —— 那版是物理上跑不动，这版跑得动）， 但需要补三个门控，且有两处收益打折。若要做，建议把 50 ms 放宽到 250–500 ms，并挂在「Web 活跃」门控上。

为什么这版跑得动（与 A1 的关键差别）

A1 的 50 ms 是「整轮 tick 50 ms」⇒ 单轮 = 刷新 14.52 + 重建 46.91 = 61.43 ms > 50 ms 预算（3000 种子）， 直接退化成无间隔连续跑。本版把重建降到 1 Hz 后，单轮只剩刷新 14.52 ms，占 50 ms 预算的 29% —— 节拍站得住了。

两处收益打折

  • 重建 1 s vs 前端轮询 2 s —— 一半的重建没人来取。要么前端 pollSec 一起降到 1 s（响应体频率翻倍， 正是 P1 要治的问题），要么重建保持 2 s。建议：先对齐 2 s，等 P1-1（按视图回传，响应体 ≈1/4）落地后两边一起降。
  • 状态 50 ms 新鲜度用户看不到 —— 端到端仍被前端 pollSec=2s 封顶。50 ms 档唯一落到用户身上的收益是 「命令执行后 ≤50 ms 被感知」，而这件事 P0-1 的 wake 事件用 ≈0 成本就能做到（且是 ≈0 ms 而非 ≤50 ms）。

两个隐藏成本（不在我们的 CPU 预算里）

  • 打在 qB 进程上：sync/maindata 20 次/秒，qB 的 synccontroller 每请求要做 O(N) diff 构造响应 （N = 种子数）⇒ 3000 种子 ≈ 6 万次字段比较/秒，消耗的是 qB 的 CPU，还会拖慢 qB 自带 WebUI。 qB 官方 WebUI 默认 1500 ms 一轮；20/s 属极激进。建议快档取 250–500 ms（2–4 Hz）起步。
  • GIL 争用：主循环 33.7% + Web 线程每轮重建 47 ms + MB 级 JSON 序列化，三层都持 GIL ⇒ 可能出现「后台更快了、前台更卡了」的反直觉结果。需真机对比 Web 请求 P95 才能定论。

建议的落地形态：做成「Web 活跃快档」

分层节拍本身是对的架构（P0-1 v2 的 D 方案就是这个形状），问题只在档位取值。别把它设成常态， 而是挂到已有的 Web 活跃门控上（_web_last_seen / WEB_VIEW_TTL=10s）： 浏览器开着 ⇒ 同步走快档；关掉网页 ⇒ 自动回落到 main_tick。这样 29% 核只发生在用户正在看的时候， 空闲成本回到 0.7%。

  • 新增配置键 web.fast_sync_ms（默认 0 = 关闭，跟随 main_tick）；取值建议 250–500， 不提供 50（qB 侧成本与收益不成比例）。新键必须进 validate_config 与 config/schema.py。

  • 先做 P0-1/B + P0-5/E（成本 1%，拿走 ≈0 ms 命令延迟）；快档作为 P1 末的可选增强， 真机对比「qB 侧 CPU + Web 请求 P95」后再决定是否默认开启。

附录 · 「刷新 1 s / WEB UI 1.5 s / 任务 2 s」可行性评估

结论：后端侧完全可行且几乎免费（3000 种子合计 ≈4.6% 核，只比现状多 1.5 个点）； 唯一风险在前端侧 —— WEB UI 从 2 s 提到 1.5 s 会把「每轮全量回传 + 整树重渲染」的频率提高 33%， 而那正是「不跟手」的主因。所以这项必须与 P1 的降本配套，否则大库下会越改越卡。

一个可以省掉的节拍：视图重建不需要自己的定时器

现有实现里 ensure_group_state() 已经是「请求驱动 + 脏门控」：Web 请求到达时，脏才重建，不脏直接返回当前引用。 也就是说 视图重建频率天然 = 前端轮询频率，且只在真有变化时发生。给它单独配一个节拍（1 s / 1.5 s）反而是多余的， 还会在"前端没来取"时白建。

故本节把「WEB UI 1.5 s」理解为前端 pollSec = 1.5 s，视图重建自动跟随 —— 后端不需要第三个节拍。

取值建议：让两个节拍成整数倍

刷新 1 s 与轮询 1.5 s 不构成错误（前端拿到的永远是最新快照），只是有 1/3 的刷新没人取 —— 成本 1.45% @3000 可忽略， 但更整齐的取法是：

  • 方案 i（推荐）：刷新 1.5 s / 轮询 1.5 s —— 与 qB 自己的节奏对齐，一次刷新配一次拉取，零浪费。
  • 方案 ii：刷新 1 s / 轮询 2 s —— 两次刷新配一次拉取，前端拿到的一定是"最新那一版"，后端成本仍只有 1.45%。
  • 你提的 1 s / 1.5 s：可行，只是不整齐；若不在意那 1.45%，也能用。

落地清单

  • 新增配置键 sync_interval（默认 1 s，或按上面方案取 1.5 s）；必须进 validate_config 与 config/schema.py（守卫测试会查）。 main_tick 语义收窄为「任务节拍 + 兜底节流」。
  • 门控不变：_build_search_index 与 refresh_error_reasons 跟 main_tick（2 s）， 不跟随 1 s 快档（否则 500 条文件 API/轮、5 次 tracker/轮的预算被翻倍）。
  • 前端 pollSec（app.js 现为硬编码 2）改为可配：默认仍 2 s，P0-0 测出单次渲染耗时、 且 P1-1/P1-2 落地后再按种子量放宽到 1.5 s（建议阈值 ≤1000 种子用 1.5 s，大库保持 2 s）。
  • 顺序：P0（wake + 首查 + 乐观 UI + 批量合单 + 补刷新）→ P0-0 埋点 → P1-1 / P1-2 → 最后才动 pollSec。 反过来先降 pollSec 会在大库上把症状放大。
