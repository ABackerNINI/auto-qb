§01目标与设计原则

背景: 0808 计划交付的 recycle daemon(src/auto_qb/tools/recycle_daemon.py)进窗判据里, 进程证是全机口径——进程名册(tasklist//proc/ps)只出映像名, 分不出实例; 名册见任一 qB 进程即判「进程在」。同机多实例形态(P7 真机实测: 日常库在跑、目标测试库已死待收尾)下, daemon 永等不到窗口, 直至全部实例退场。该取舍已显式声明并挂账为 issue 26-11-07-0528(N1 优先的显式取舍, 单实例零影响)。

目标一句: 给 daemon 补一条实例级证据链(owner 死证 + 新面孔无害化 + 端口拒连), 让 P7 形态下「目标实例死亡」即可开窗收尾, 单实例部署窗口开启不晚于现状, N1 铁律不放一条口子。

做到什么程度算成: §04 三波判据全绿; P7 形态真机验证(目标死 + 日常活, 窗口开启并完成改写); 单实例回归等价; issue 0528 收口 + pitfalls P7 专档立档。

设计底线/不变量:

  • N1 铁律不动摇: 任何进窗与逐成员落盘都要求「目标 profile 的 qB 进程不存在」的证据; 证据链每一档都必须严于或等于现状某条已在跑的路径(现状名册探测失败时已允许端口单证进窗——本方案的证据严格强于它)。
  • 竞争面精确定义: N1 的竞争 = 同 profile 实例对同一 BT_backup 目录 fastresume 的运行期重写。不同 profile 实例不加载这些文件, 不构成竞争。全机口径的病根 = 把非竞争者(其它实例)也当竞争者挡窗。
  • 保守退化(黄金法则 2): 观测记录缺失或观测通道故障 → 原样退回全机口径(现状判据), 告警留痕不静默; 弱证据配 30s 稳定期, 强证据(进程级)才配立即进窗。
  • 默认开、零配置键(拍板 D5): 无 validate_config 触碰, 行为随代码走。
  • 账本契约不碰: journal/daemon.json 语义不变, 绝不碰 state.json(D13); 观测状态走独立 obs 文件。
  • 零新依赖: 不引 psutil, 观测通道与现有名册同款手搓子进程/proc 风格。

§02现状与痛点

  • 现状判据: 进窗 = 三证——进程不在(证一, _proc_absent recycle_daemon.py:114) + 端口拒连(证二, _port_refused :55) + 稳定 30s(证三, STABLE_WINDOW :142, run :410-414 down_since 计时); 逐成员落盘前瞬时复验证一+证二(:337)。证一内部: 名册可用时「名册无 qB AND 端口拒连」合取; 名册见任一 qB ⇒ 一票否决。
  • 痛点(P7): 进程名册只有映像名, 跨平台尽力而为, 分不出实例。目标实例已死、同机另一实例在跑 ⇒ 名册永远见 qB ⇒ 证一永不成立 ⇒ 收尾改写无限期延迟。issue 0528 以「显式取舍」记录, 未来增强方向挂账「需比映像名更强的实例身份证据——设计题」。
  • issue 原候选思路的洞(本次推演结论):
    • 朴素端口归属记录(趁端口可达记下 owner pid, pid 死即进窗): 堵不住「目标重启、新身已创建但 WebUI 端口未绑」的尾部间隙——彼时 owner 死证为真、端口证为真, 但同 profile 新实例的 BT 引擎已在运行, 落盘即 N1 破。(注: 新身完全未创建的死亡间隙落盘是安全的——写时无 qB 在运行, 新身起来读到的就是改写件, 走 N4 别名加载自洽; 危险的只是「已创建未绑端口」的尾部。)
    • WebUI 身份凭据: 实例活着才可验, 死后死无对证——issue 判须与落盘侧证据组合(独立不充分)。
  • 现状已有降级路径: 名册探测命令异常 ⇒ 空名册 ⇒ 退端口单证 + warning(:137)。这条路径的证据强度弱于本方案的实例级证据——这是 D5「默认开」的正当性锚点之一。
  • daemon 形态: 主循环自动重拉(relocate_exec.py:19 _DAEMON_MODULE 声明拉起目标, _spawn_daemon(:1683)detached, ACT_ENSURE_DAEMON), CLI 仅 --data-dir/--host/--port/--stable/--poll/..., 无配置键; 常驻形态(grilling 拍板 D3)。

§03方案总览

主线(拍板 D1/D2): 实例级证据链 = owner 死证 + 新面孔无害化 + 端口拒连, 证据成立即立即进窗; 观测由 daemon 自维护并持久化, 缺失即退回现状。三层证据链:

层触发条件进窗判据稳定期
L1 实例级(新增) owner 观测记录有效 且 观测通道健康 owner 已死(pid 消失 / pid 在但 create_time 不匹配 / pid 在但映像非 qB) AND 端口拒连 AND 无未决新面孔 无(立即, 拍板 D2)
L2 全机口径(现状保留) 无 owner 记录 / 观测通道故障 全机名册无 qB AND 端口拒连(现 _proc_absent 原样) 30s(保留, 弱证据配稳定期)
L3 端口单证(现状降级, 不动) L2 名册探测也失败 端口拒连单证 + warning 留痕 30s(保留)

§03.1 观测面(每 poll, pending 非空时维护)

  • O1 owner 归属: 端口可达(create_connection 成功)时, 从 LISTENING 表归属该端点的 owner pid, 交叉校验映像名含 qbittorrent(非 qB 服务占端口 ⇒ 不记录, 保守), 再取 create_time 统一换算为 epoch 秒, 记 {pid, ct, ts} 持久化。Windows: netstat -ano -p tcp 解析 LISTENING 行(按本地端口匹配, 0.0.0.0 通配监听同算); create_time 用 PowerShell Get-Process 的 StartTime.ToFileTimeUtc()(单次调用批量取全机 qB 进程)。Linux: /proc/net/tcp{,6}(st==0A)端口→inode → /proc/<pid>/fd/socket:[inode] 归属; create_time = /proc/stat btime + /proc/<pid>/stat starttime/HZ。
  • O2 全机 qB 身份枚举: 每 poll 枚举全机 qB 进程的 (pid, create_time) 集合(Windows 用同一 PowerShell 调用顺带取映像名; Linux 扫 /proc/*/comm + stat)。它驱动新面孔状态机。
  • 通道纪律: 解析失败/超时(10s)⇒ 本拍观测不可用 ⇒ 走 L2/L3, warning 节流留痕(60s 一次, 不刷屏)。解析器不硬赌输出格式——解析不出就退, 宁可保守。

§03.2 新面孔状态机(堵「同 profile 新实例已创建未绑端口」尾部)

owner 死后出现的 qB 进程分不清「目标 profile 新身」还是「别的实例新身」; 但它们有一个硬差异——目标 profile 的实例终将监听我们的 host:port, 别的不会。状态机按此收敛:

观测到的 qB 进程(非 owner)判定对窗口的作用
ct < owner.ts_last_seen零赌注吸收: 它在 owner 存活期间创建。若同 profile, 与 owner 双开被单实例锁/WebUI 端口冲突排挤——该论证以单实例锁开启为前提, 用户关锁双开属 §07 R4 原理性残余, 不在本行覆盖域无害, 永不挡
ct ≥ ts_last_seen 且监听我们端口就是 owner(复活或换身)⇒ owner 记录更新端口证自然失败, 挡(正确: 目标活着)
ct ≥ ts_last_seen, 监听集稳定 NEW_FACE_SETTLE=30s 且不含我们端口吸收(写进 obs 文件 absorbed 清单)——WebUI 绑定是启动早期动作, 30s 不绑即非目标 profile(有界赌注, 见 §07 R3/R4)吸收后无害; 场景 Y(日常实例重启)代价约 33s
ct ≥ ts_last_seen, 未 settle未决——可能是目标新身(已创建未绑端口)挡, 直到绑定我们端口(转 owner)或被吸收或消失

settle 计时(first_seen/监听集指纹)只在内存, daemon 重启即重置(settle 重算, 代价 30s); absorbed 清单持久化, 重启后继续有效。absorbed 成员从名册消失即移出(死进程无威胁, 文件不膨胀)。

§03.3 L1 进窗判据(精确语义)

进窗(L1) ⇔
  1. owner 记录存在, 且 owner 已死:
       pid 无进程  OR  pid 在但 create_time != 记录值  OR  pid 在但映像名非 qbittorrent
     (后两条 = PID 复用防御: 被别的程序/别的 qB 实例复用都判「原实例已死」)
  2. 端口拒连(_port_refused 原样)
  3. 新面孔状态机: 无未决成员(§03.2)
  4. 1+2+3 同时成立 ⇒ 立即进窗, 无 down_since 计时(拍板 D2)

逐成员落盘前瞬时复验 = 1+2+3 全套现读现判(升级现状的两证复验;
这是「立即进窗」安全性的必要条件——复验粒度必须与进窗判据同级)
场景 X 论证(目标重启, 拍板 D2 的安全性根基): owner 死、新身完全未起时落盘——写时无任何 qB 进程运行, N1 字面(运行期零写入)与深层(与 qB 秒级重写竞争)均不触发; 新身起来读到的是改写后 fastresume, 走 N4 别名加载, journal 已逐成员记账, 主循环重启后 save_path 核验兜底(S4), 全链自洽。新身已创建未绑端口的尾部由状态机未决态挡住。比现状(30s 稳定期)窗口更早开, 但每一拍的安全前提不弱于现状。

§03.4 观测持久化(obs 文件)

  • 路径: <data_dir>/relocate/obs-<instance_key>.json(与 spec/journal/daemon.json 同目录同家族); helper 进 relocate_journal.py(read/write, 原子写, 对齐 daemon-state helper 风格)。
  • schema: {schema_version: 1, host, port, owner: {pid, ct, ts} | null, absorbed: [{pid, ct, ts}], ts}。
  • 写时机: 状态变更即写(owner 换身/吸收/清出), 频率低; daemon 重启后 owner/absorbed 恢复——覆盖「daemon 停机期间目标死亡」的判定(记录仍是有效的死证)。
  • daemon.json 不动(watcher 归属与心跳语义不混); state.json 不碰(D13 契约不变)。

被否决的备选: 人工放行标记文件(每窗人工介入, 常驻形态下摩擦大)、profile 指纹(读目标 qBittorrent.ini 与进程对照——依赖 qB 内部布局与 cmdline 可见性, 脆)、psutil(新依赖, 违背零依赖风格)。远程端点 host 分类——事实裁决不修(拍板 D4, 同机判定是迁移链硬闸, 远程端点走不到收尾)。

§06拍板记录

#拍板内容与理由
D1实装实例级证据链三档(实装/人工放行/维持现状)中拍板实装: P7 是真机常态形态(日常库+测试库同机), 常驻 daemon 下每窗都撞, 长期摩擦大。
D2进程级证据成立即立即进窗用户裁决原文方向:「既然有进程级观测, 连续 30s 稳定就降级——如果进程表面确实退出了, 就立即收尾」。落地为: L1 无稳定期; 30s 保留给 L2/L3 弱证据路径(弱证据配稳定期); 逐成员复验升级为全套 L1 证据(安全性必要条件, §03.3); 场景 X 论证见 §03.3 callout。
D3按 daemon 常驻形态设计主循环 ACT_ENSURE_DAEMON 自动重拉、daemon 长期在跑; 观测文件持久化, 冷启动无记录仅发生在首次部署/清数据(一次性, 走 L2 等目标下次上线即解锁)。
D4远程端点 host 分类不修(非目标)第二轮 grilling 提出「非本机端点被本地名册误挡」; 用户反问后事实核查: 迁移链有硬性同机判定(relocate_plan.py:557 _same_fs_proof, D 级路径证据/E1 强探测/assume_shared 三选一), 远程 qB 走不到收尾——误挡仅在 assume_shared 越权形态理论上可及, 被产品判据刻意排除。按范围守恒不扩代码面, 方案仅留非目标声明。
D5默认开, 零配置键L1 每一档都严于现状某条已在跑的路径(名册故障时现状已允许端口单证); 真要钉回旧行为, git 回滚比配置旋钮诚实。不触发黄金法则 4(validate_config 无新键)。

grilling 轮次: 第一轮 Q1(目标档位)/Q2(证据链主形态, 含朴素 pid 方案尾部洞的推演)/Q3(部署形态); 第二轮 Q4(伴生缺陷范围)/Q5(配置开关); 第三轮 Q4 事实翻案(同机判定硬闸)后共识确认。

§07风险与对策

#风险定性对策
R1观测通道开销/挂起: 每 poll 由 1 个子进程(tasklist)增至 3 个左右(netstat + PowerShell + 名册), PowerShell 约 100-500ms低——常驻 daemon、poll 5s、判据路径本就轻全部子进程 10s 超时; 失败即退 L2/L3 保守判据; 通道失败告警节流 60s。
R2netstat/PowerShell 输出解析脆(语言版本/格式漂移)低解析器不硬赌: 解析不出=观测不可用=退回 L2, 不产生假证据; W1 在本机实测中英文输出; LISTENING 状态字各语言版一致的假设在 W1 验证, 不成立则换通道再评。
R3settle 30s 是有界赌注: 若目标新身 WebUI 绑定 > 30s, 会被误吸收进窗低——qB WebUI 监听绑定在启动早期(秒级), 30s 为 10 倍量级余量常量独立(NEW_FACE_SETTLE)可调; 常量数值与依据写进代码注释与 pitfalls 专档; 误吸收前提(目标待收尾期间重启且绑定超 30s)本身罕见。
R4配置漂移残余: 用户改目标 profile 的 WebUI 端口且不同步 config——新身永不绑我们端口, settle 后被吸收, 暴露。同 profile 异常双开(用户关单实例锁)同属此类「外部不可区分」残余极低——需「改端口/双开」与「该实例有待收尾 journal」双重巧合无零赌注堵法(外部观测原理上分不出), 诚实定性为方案边界: pitfalls P7 专档写明「改 WebUI 端口须同步 config.yml 与 bt_backup 表」警示; 不为极低概率复杂化判据。
