02证据与根因

2.1代码自相矛盾: 文档串承诺「保留执行历史」, 问题行把它清掉

apply_new_config 自己的 docstring(qbmanager.py:472)写着 L2 「重建任务队列与规则 + 全部记录重匹配 tracker(保留 store 记录/分组/执行历史)」。执行历史 exec_history 就存在 self.state 里 —— 而 503 行恰恰用磁盘旧版整体替换了 self.state。docstring 是对的, 代码违反了它: 这一行是语义 bug, 不是有意设计。

2.2磁盘 state 不可能比内存新: 重读没有任何正向价值

全库 save_state() 落盘点只有三处(qbmanager.py:449-450 主循环退出 finally 且 not dry_run 才落; skip_checking.py:252 / 277 跳检「删除→重加」路径落): 平时 state 不落盘 ⇒ 磁盘上的 state.json 永远停在「上次优雅退出」的版本。且 state_file/​data_dir 是 R 级(热重载拒绝应用, impact.py), 配置热重载不可能合法地更新磁盘 state —— 运行期这次重读只能拿旧数据覆盖新数据, 没有任何正向收益。

2.4根因

根因即 qbmanager.py:503 这一行本身: 它是从 run() 启动路径(qbmanager.py:334)照搬来的「启动时从磁盘加载」语义, 被误复制进了运行期的 L2 热重载分支。与「state 平时不落盘、仅退出落盘」组合后, 语义变成「回滚到上次退出版本」。已排除: L0/L1 分支不触碰 state; 热重载路径上没有任何先行 save_state; 磁盘 state 在运行期不可能因合法途径变新(见 2.2)。

03修法

三步: 守阵先红验(F2) → 删一行(F1) → 文档回写与收尾(F3)。顺序刻意把测试放在修码前 —— 红验输出就是本 issue 的验收凭据(issue §06 的约定)。

F1删除问题行

qbmanager.py:503 的 self.state = self._load_state() 整行删除。L2 重建只需要任务队列与规则; state 与配置变更无关, 内存态原样保留即正确语义。同时核对 L2 分支留有的日志文案与 docstring 是否需要微调(docstring 472 行本就承诺「保留执行历史」, 删行后承诺兑现, 不需要改)。

F2守阵测试: L2 热重载保留运行期状态

放 tests/test_web.py、紧邻既有 test_apply_new_config_levels(约 3410 行), 复用同一套替身模式(make_manager + monkeypatch diff_config_impacts + mock _load_rules/_create_global_tasks/connect):

  1. 构造 manager 后, 直接往 mgr.state 注入运行期条目(exec_history / skip_check_day / recheck_fails 各一条), 并保留注入前 dict 引用 state_before;
  2. 向磁盘 state_file 手工写入一份内容不同的旧版 state.json(如 {"stale": true})—— 模拟「上次退出」的版本;
  3. 以一条 L2 变更触发 apply_new_config;
  4. 断言 mgr.state is state_before(对象未被替换)且注入的三组运行期条目原样还在。

红验: 在 F1 之前跑, 现行代码会把 mgr.state 替换成磁盘旧版 ⇒ 断言必红, 输出留痕; 转绿: F1 之后同测试通过。用「对象同一性 + 内容保留」双断言, 不 monkeypatch _load_state 本身(避免把测试耦合在实现符号上)。

04候选方案与取舍

候选做法结论
A · 删行
(issue 推荐, 本计划采纳)		 删除 qbmanager.py:503, L2 不再触碰 state 采纳 语义正确(与「重启进程」行为一致: 历史跨重启保留, 热重载理应同样保留); 改动最小; 无副作用。黄金法则「保守默认」也支持: 重置运行期状态属于高风险动作, 不该是隐式默认。
B · 先存再读 L2 分支改为 save_state() 后再 _load_state() 不采纳 net 效果等于把内存 dict 经 JSON 往返一趟再原样读回 —— 纯粹的磁盘空转, 还多出一个写盘窗口; 且它修不好语义: 「重读」这个动作本身没有正向价值(2.2)。
C · 合并保留 重读磁盘后与内存态 deep-merge 不采纳 为不存在的需求引入 merge 策略(键冲突取谁? 删除的键要不要复活?), 复杂度与风险全无回报。

与姊妹 issue 的关系: 26-09-21-1347-bug-backend-state-save-only-on-exit(运行期完全不落盘)是独立问题 —— 即使将来加了周期性落盘, 本条的「重读=回滚」语义错误依然成立, 候选 A 不受其修法影响; 两案互不阻塞, 本计划不扩scope 去顺手修它(scope-guard)。

05影响与风险

正面影响
  • Web UI 改规则/interval/曲线/tracker domains 等保存后, 跳检去重、校验冷却、执行历史、上传基线不再丢失
  • dry-run 模式同样受益: 退出时不落盘(449 行), 磁盘版更陈旧, 现行 L2 回滚在 dry-run 下更严重
  • 热重载路径不再可能触发 _load_state 的损坏恢复分支(告警 + .bak 自愈写回), 减少运行期噪音
风险与对策
  • 有人依赖重置吗? 分析: exec_history 键为 rule_name:hash, 改规则条件不会(也不应)清历史 —— 与进程重启语义一致(重启后历史同样保留); 未发现任何依赖重置的调用方。若未来确需「改规则即重跑」, 应做成显式配置项, 不靠隐式回滚
  • state dict 换成原地保留, 是否有组件持有旧引用? grep 全库: 所有访问都经 self.state/manager.state 属性现读, 无缓存引用, 删行后该疑虑(换对象导致旧引用悬挂)直接消失
  • 改动面极小(一行 + 一测 + 文档), 无并发/时序敏感点; L2 其余重建步骤不动
