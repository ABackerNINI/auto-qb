01 · Scope

需求拆解

把需求逐条翻译成技术口径,后面的章节都围绕这四行展开:

需求原话技术口径
按同一部剧组织分组(如何判定同一部剧需要调研和头脑风暴) 聚合键 = 规范化剧名;判定规则见 03 —— 这是本功能唯一有真正难度的点
分组中按第几季第几集排序 剧内二级结构:季升序 → 集升序;集键支持三种形态:整数集数 / 日期(综艺日播) / 整季范围
多站点辅种不分开显示,类似辅种视图 展示行 = 集:同一集的多份种子(同一辅种组的各站点副本、不同编码的独立种子)聚合为一行,行内以站点徽章区分;辅种组内成员文件列表相同,天然解析出同剧同季同集,自动归并,无需显式关联
先计划 本文档即产出:不改任何代码,输出方案、调研结论与待拍板决策点

术语

  • 辅种组:现有 grouping 的分组,键 = (规范化 save_path, 排序文件路径元组),即"文件列表相同的种子集合"。
  • 版本:本文档定义的中间层 —— 同一集的一份内容实体 = 一个辅种组,或一个未归组的独立种子。
  • 集行:追剧视图的展示行 = 同一 (剧, 季, 集) 下全部版本的聚合。

03 · Brainstorm

同剧判定:调研与头脑风暴

这是整个功能的核心难题。Sonarr 这类媒体管理器的思路是"解析发布名 → 与库内已登记剧集(TVDB 数据)匹配",它有一个权威答案可对;而 auto-qb 面对的是没有任何外部真值的种子集合 —— 问题本质是无监督聚类:只靠种子自身携带的信息,把"同一部剧"聚到一起。所以重点不是找一个标准答案,而是设计一套可解释、可纠偏的启发式规则。

3.1 可用信息源

信息源质量成本判定
种子名 name高(信息密度最大,噪声也大)零(全种子必有) 主信号 —— 发布名天然携带 剧/季/集/制作参数,业界(scene/P2P)命名惯例成熟
文件列表 files高(文件名与 Season 目录结构可靠)中(依赖搜索索引缓存,首建有延迟) 兜底信号 —— 名称无标记时(季包/合集)从文件名与目录提取
保存路径 save_path不稳定(媒体库惯例组织时极准,手动管理时无结构)零 辅助信号 —— 不进聚合键,可用于"疑似同剧"提示(后续迭代)
分类/标签不可依赖(用户可能没设;auto-qb 的 zE 集数标签只有集数)零 不作为主信号;P2 可考虑从标签读取集数
外部数据库(TMDB/TVDB)权威(规范 ID,可解跨语言剧名/绝对编号/同名剧)高(网络 + 密钥 + 限流) P2 opt-in,首版不做

3.2 命名田野:要覆盖的格式家族

PT/scene 生态的发布名是一套事实标准的方言体系。解析器必须先见过这些长相才谈得上规则:

家族样例解析要点
西方 scene/P2PShow.Name.S01E05.2160p.WEB-DL.DDP5.1.HDR.x265-GROUP标记前段 = 剧名;S/E 明确;尾部噪音 token 剥离
季包Show.Name.S01.Complete.1080p.BluRay / …Complete.Season.1有 S 无 E → 整季节点,集范围由文件列表兜底
多集包Show.Name.S01E01-E05区间展开或范围行(见 3.5 决策)
中文命名【剧名】第1-5集 4K 中字 / 剧名 第一季全集 / 剧名.S01E05.国语中字第x集 / 第x季 模式;书名号、全角字符清洗
动画字幕组[SubGroup] Show Name - 05 [1080p] / [SubGroup][Show Name][05][v2]破折号/中括号内的 bare number;绝对编号(无季标记)
日播/综艺Show.Name.2026.09.15.1080p.WEB.h264日期即"集键",排序按日期
变体与身份差分Show Name (US) / (2019) / Re:Zero / Shōgun / Show Name 2年份、国家、续作数字是剧的身份差分,归一化时保留(见 3.4)

3.3 候选方案对比

方案思路优点缺点结论
A手写名称解析器(正则模式表 + 剧名归一化) 零依赖;全种子覆盖;规则可解释、可测试、可持续调优;与 episodes.py 同族 边缘格式长尾需要持续养规则;绝对编号跨季等硬限制 主方案(推荐)
B引入 guessit(4.4.0,活跃维护,2026-07 仍在发版) 现成的专业解析,英文生态覆盖广 +3 依赖(rebulk / babelfish / python-dateutil);行为黑盒难微调;中文 PT 命名并非其强项;本项目依赖策略是 == 锁死 备选 —— 不引入;若后续边缘格式失控再评估
C文件列表解析(复用 extract_episodes_from_files + Season 目录) 文件名/目录结构比发布名规整 依赖索引缓存(首建延迟);文件 API 不可用时失效;单独使用覆盖不全 兜底层(与 A 组合)
Dsave_path / category 参与聚合键 用户按媒体库惯例组织时近乎免费命中 组织方式因人而异,进键会在辅种场景(路径是分组键一部分)产生歧义 只做校验/提示,不进键
ETMDB 匹配出规范剧 ID 终极解:跨语言剧名、绝对编号跨季、同名重制全部可解 网络依赖 + 密钥配置 + 限流;违背"本地优先"默认假设 P2 opt-in
F人工纠偏(合并/拆分,持久化) 唯一能兜住所有误判的手段 需要状态持久化设计(state_file 单写线程约束)+ UI 投入 P2 —— 第一版先验证自动聚类质量

3.4 推荐方案:分层解析管线

A 为主 + C 兜底,每个种子解析出 (剧键, 季, 集键) 三元组;解析不出完整三元组的进"未识别"桶:

剧名归一化规则(草案)

  1. 结构清洗:分隔符 . _ - → 空格;全角 → 半角;折叠连续空白;去书名号/引号/首尾标点;lowercase。
  2. 噪音 token 剥离:分辨率(2160p/4k/1080p…)、来源(WEB-DL/BluRay/BDRip/HDTV…)、编码(x264/x265/HEVC/AV1…)、音频(DDP5.1/AAC/FLAC…)、发布组尾段(-GROUP)、字幕说明(中字/简繁/内嵌)。词表集中在一个常量里,便于增补。
  3. 身份差分保留(关键取舍):年份 (2019)、国家 (US)、续作数字 Show Name 2 不清洗、参与聚合键。宁可偶尔把同一部剧拆成两行等人工纠偏,也不能把《 ipAddress 之战 1994》和重制版合并 —— 误合并比误拆分难发现得多。
  4. 季标记识别只认显式形式:S01 / S1 / Season 1 / 第一季 / 第1季 / 2nd Season;纯数字尾缀保守保留在剧名里(可能本身就是剧名的一部分)。
  5. 简繁转换不做(依赖转换表过重,PT 场景同剧通常同简繁;列为开放问题)。

3.5 关键边界决策

边界推荐理由与替代
动画绝对编号(Show - 05 无季)归 S01,文档写明跨季限制追剧场景"全部在 S01"最直观;绝对编号 → 真实季映射无名称真值可依,属 TMDB(P2)要解的问题。替代:独立"剧场版/特别篇"桶 —— 增加心智负担,不做
季包(S01 整包)不展开:该季下挂一行"整季范围行"(E01–E25,文件解析出范围)展开成 25 行每行都引用同一个 hash,重复且误导;范围行一眼看出"这是一整包"。替代:展开 —— 行数膨胀,不做
日播/综艺(日期命名)日期型集键,排序按日期综艺是追剧高频场景,丢进未识别会显得"这视图不好使";集键设计成 (类型, 值) 二元组即可统一排序
完全无标记(电影等)进"未识别"折叠区,参与搜索隐藏会让用户"找不到自己的种子";折叠区不影响追剧主视图。替代:直接隐藏 —— 否
同辅种组解析结果冲突(理论不该发生)多数结果为准,记 warning 日志组内文件列表相同 → 解析必然一致;不一致说明解析器有 bug,暴露而不是掩盖
04 · Data Model

数据模型与聚合设计

排序规则

  • 剧:默认按剧内最新 added_on 降序(最近有动静的剧在前,与现有分组视图"新补的辅种最先看到"的哲学一致);列头可切剧名排序(locale 排序)。
  • 季:升序。
  • 集:集键统一为 (类型, 值) —— 整数集数按数值升序,日期按日期,范围行按起点;同集多版本不排序(并列)。

缺集提示(gap)

对整数型集数做连续性检查:[E01, E02, E04] → 季头徽章提示 缺 E03。这是"追剧"语义的灵魂之一(一眼看出还差哪集才齐),实现只是一次遍历,建议第一版就带 —— 但仅做季头徽章级展示,不插虚位 DOM 行,控制渲染复杂度。

05 · Backend

后端设计

新模块 tvshows.py(纯逻辑)

  • 位置 src/auto_qb/tvshows.py,与 episodes.py 同族(领域逻辑独立模块,零/轻项目内依赖,便于单测)。
  • 导出:parse_release(name) → ParsedRelease(剧名原文/规范化剧名/季/集键/置信分类)、normalize_title(s)、episodes_from_files(files)、噪音词表与模式表常量。
  • 集数模式表继承 episodes.py 的"插入即扩展"设计;新增季标记与日期模式。

视图组装 mixins/web_view.py

  • _build_shows_view() → List[dict]:数据源是全量 store.by_hash,不依赖辅种分组是否启用 —— 追剧语义是"这部剧我有哪些集",未归组种子同样要进视图(这与 singles 视图互补:singles 是"未归组",shows 是"全部种子换一种组织方式")。
  • 挂在现有脏窗口:ensure_group_view 同一 _group_view_dirty 触发、同一 _group_view_ver 版本号下三视图一起重建;ensure_group_state 回传 state["shows"](与 groups/singles 同 rid 门控,版本一致时不回传)。
  • 响应体积控制:shows 节点不带成员明细字段,只带 members=[hash,…] + 聚合字段;前端用 hash 从现有 groups/singles 数据建立 byHash 索引取明细(R08 已有完全相同的合并先例,app.js:1469)。
  • 性能:每次重建 O(N) 正则解析,千级种子为毫秒级;per-hash 解析缓存(以 name 为键)预留不实现,实测后再说 —— 与 SEARCH_INDEX_BUILD_BUDGET 的"先简单"精神一致。

文件兜底的接线点(唯一需要动重建逻辑的地方)

现有重建由 _VIEW_FIELDS 字段变化驱动,而"搜索索引建成一批"不会触发任何字段变化。因此:

  • shows 视图存在"名称无标记待兜底"种子且索引 dirty 时,复用现有 build_search_index 命令(幂等,已有限流)。
  • _build_search_index 每轮完成时,若存在待兜底种子 → 置 _group_view_dirty = True,下一轮视图重建自动归位。改动约两行,配合测试锁死。

不碰的东西

  • 零新配置键 —— 视图切换是纯前端行为,不动 models/loaders/validation/schema(与 R08 单种子视图同策略)。
  • web.py 零新端点 —— state 承载回传;控制命令完全复用现有 pause/resume/reannounce/delete。
  • qB API 零新增调用 —— 文件列表走搜索索引缓存。
06 · Frontend

前端设计(atlas)

视图开关第三态

  • viewMode: groups | torrents | shows;顶栏开关加第三枚按钮"追剧"(atlas/index.html:132 处插入)。
  • localStorage autoqb.ui.view 兼容:缺省仍是 groups;新值 "shows" 进白名单。

渲染结构

  • 剧行(默认折叠):展开箭头 / 剧名 / 季数·集数 / 聚合状态 / 最新动静时间。
  • 展开后:季子标题条(含缺集徽章)→ 集行平铺;集行 = 集号(含范围行样式)/ 聚合状态 / 进度 / 大小 / 版本数·站点徽章 / 速度 / HR。
  • 底部"未识别"折叠区,命名过野的种子在此,按名称排序,参与搜索。

列模型与交互

  • SHOW_COLUMNS 进 TABLE_COLUMNS 新 page "show" —— 列宽按列 key 记忆,存储结构向后兼容(R08 torrent page 同款先例)。
  • 集行右键 = 整集操作:对该集全部成员执行现有命令(暂停/恢复/汇报/删除),复用 R08 的批量目标拆解语义(_resolveTargets 拆 hash);剧行初版只读。
  • 点开集行 → 复用现有成员明细表(DETAIL_COLUMNS),明细数据从 byHash 索引取。
  • 筛选/搜索全复用:集行 members 与分组成员同构,kindFilter/tag/category/site/hr/路径六套筛选"任一成员命中保留整集"语义不变;搜索命中(剧名/种子名/文件名)保留对应剧集并高亮。
  • 统计条改为"N 部剧 · M 集";状态分布条聚合逻辑复用。

prism(棱镜)

本计划不触碰 prism 文件(与 R08 同红线),移植作为后续独立任务 —— 共享逻辑层的解析成果(后端 shows 数据)届时直接可复用,prism 侧只差模板与样式。
