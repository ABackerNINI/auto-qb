§01目标与设计原则

做到什么算成

  1. 站点健康可见：种子页 / 辅种页 / 追剧页任一行的站点 chip 上，能直接看出「该站点没在配置里」或「该站点 tracker 报错」，不必开抽屉。
  2. 汇报结果可定位：多目标强制汇报部分失败时，能精确指出哪几个失败（行内图标），聚合 toast 仍保留作总览。
  3. 取数单点：所有判定在后端算完，前端不按 state 猜原因 —— 沿用 error_reason 已确立的口径（views.py:181 注释「前端只展示这里的字符串」）。

不变量（设计底线，实施时不得让步）

  • 不新增列、不改列宽：站点 chip 已是 inline-flex; gap:4px（三皮肤各自的 .site-chip 规则），图标塞进现有 gap，不触发列宽重排。
  • 不动 error_reason 语义：状态列文案逐字不变，只给已有 i-warn 图标加动画。
  • 主循环仍是唯一写者：取数在主循环内按预算轮转，不引入新线程（除非 S0 标定触发 R2）。
  • 保守默认：新增常量先给保守值，S0 真机标定后再定死；不新增配置键（预算/TTL/阈值全走模块常量），避免 schema 面积扩张。
  • 三皮肤同步：任何新样式必须 atlas / console / prism 三份齐备，由静态守阵机械比对。

位置即语义：左槽说「这个站点现在不好」，右槽说「你刚才让我做的事结果如何」。两槽可同时存在（一次失败的汇报很可能同时点亮 tracker 报错），互不覆盖。同一时刻每个槽最多一个图标 —— 多类命中按左槽优先级 no_site_conf > tracker_error（缺配置更根本：配置缺失时连报错文本都不可信）。

3.2 判定与取数（后端单点）

报错口径：status ∈ {4 not working, 5 tracker error, 6 unreachable} 且 msg 非空，跳过虚拟条目（DHT/PeX/LSD，已有 VIRTUAL_TRACKER_PREFIXES）。取第一条命中的 msg 作为展示文本。

去抖状态机（新字段落在 TorrentRecord，紧邻 tracker_error_msg）：

观测条件动作
无报错—清 health_msg 与 suspect_since（恢复即灭）
有报错，首次suspect_since == 0置 suspect_since = now，不亮；调度器给它 30s 复查
有报错，已满窗now - suspect_since >= 30写 health_msg（亮），此后按 60s 复查等待恢复
有报错，未满窗—不动，等下次复查
为什么不是「连续 2 次观测」：常规轮转 TTL 是 600s，一个种子两次观测间隔就是 20 分钟，「连续 2 次」等于没有去抖。故去抖按墙钟算（首次疑似 → 30s 后复查确认），复查频率靠调度器给疑似种子短 TTL 实现，而不是靠轮转自然覆盖。

取数调度（改造 views.py::refresh_error_reasons 为统一的 tracker 健康取数器）：

常量值含义
TRACKER_HEALTH_BUDGET20 / 轮每 tick 最多发起的 /trackers 请求数（现状 5，tick 2s）
TRACKER_HEALTH_TTL600s常规全库轮转周期（5000 种子 × 2s / 20 ≈ 500s 扫完一轮）
TRACKER_SUSPECT_TTL30s疑似（首次观测到报错、未确认）复查间隔
TRACKER_LIT_TTL60s已亮（确认报错）的恢复检测间隔
ERROR_REASON_TTL300s（保留）error 态种子展示原因的重取间隔，行为不变

扫描范围：活跃态（seeding / downloading / checking）+ error 态；paused / other 跳过（暂停种子不会汇报，报错文本无意义）。预算分配顺序：疑似 → 已亮 → error 态 → 全库游标。前三类数量有界（通常几十个），余下预算推进游标。

统一取数，不双份开销：现有 tracker_error_msg（error 态展示用）与新 health_msg 由同一次 /trackers 调用产出。改造后 ERROR_REASON_BUDGET 退役，views.py 只剩一个取数入口、两个消费方 —— 否则 error 态种子会被两套机制各查一次。

3.3 回执契约（逐目标结果）

runtime.check_pending 聚合时把已有的 items 直接带出，不改任何判定逻辑：

# runtime.py::check_pending 聚合段（现状只拼 msg）
msg = f"成功 {ok_n}, 失败 {err_n}, 未确认 {warn_n}"
# 新增: 逐 hash 结果随 truth 出通道（cmd 端点已支持 truth）
truth = {"results": [
    {"hash": h, "status": it["status"], "reason": it["reason"]}
    for h, it in entry["items"].items()
]}
self.set_result(cmd_id, status, msg, truth=truth)

前端 _actCore 把 job 从「纯 URL」改成「URL + 目标标识」，组级 job 的结果按 truth.results 展开到成员 hash；truth 缺失（旧版后端 / 等待超时）时该批目标统一落 warn（时钟图标），不谎称成功。

§07风险与对策

编号风险触发条件处置
R1去抖与 TTL 自相矛盾：常规 TTL 600s 下「连续两次观测」= 20 分钟，去抖形同虚设照字面实现 D3 而不看调度已内置解法：疑似种子走 30s 短 TTL 复查（D3 推论）。实施时不得把去抖写成「两次轮转观测」
R25000 库把 tick 拖慢：20 次/轮 × 单次耗时超预算S0 实测单次 > 5ms，或每轮占用 > tick 的 5%先降预算（20 → 10，TTL 同比放大）；仍不够则评估独立轮询线程（有 notify / hr 先例，但引入第二个写者）——须单独立档，不在本件内做
R3组行图标永远陈旧：decorate.js 的装饰记忆化指纹只含 kind/size/category/site/tags，新字段不进指纹则命中旧缓存只改模板不改指纹S3 明确要求同步改 _decoFpBuild / _decoFpHit，并加一条「改 site_alert 后组行装饰必变」的单测
R4图标状态随视图重建丢失：把结果写在行对象上，服务端每次发布都是新 dict实现时图省事挂在 row 上命令结果必须存 state.js 的 hash 键 map（alertIcons），与行对象解耦
R5两槽打架：一次失败汇报同时点亮 tracker 报错，图标互相覆盖两槽共用同一位置位置即语义（左持久 / 右临时），DOM 顺序固定，测试断言两图标可同时存在
R6qB 请求量上升：5000 库从 2.5 次/秒升到 10 次/秒全库轮转上线预算硬上限 + 只查活跃态 + 断连整轮跳过；S0 标定后若 qB 侧有压力，先放 TTL 再谈线程化
R7报错文本过长/含特殊字符：站点自定义文案可能几百字符直接塞 titlesite_alert_msg 后端截断到 200 字符；前端只做纯文本绑定，不拼 HTML
R8三皮肤漂移：只改了 atlasCSS 各写一遍静态守阵机械比对三份样式 key 集合相等（沿用 test_webui_static_skins.py 既有手法）
