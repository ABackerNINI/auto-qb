2.2 拆分条件核查 (结论: 干净)

04分步实施 S0–S8

总原则: 纯机械迁移——不动任何断言 / 夹具 / 逻辑, diff 审查口径是「行只在文件间移动」。每批一个 commit, 批内先红验后迁移后验证; 批间独立可停, 任何一批后中止仓库都处于全绿状态。

批通用门 (每批相同, 下文不再重复): my-commit-flow.sync → 工具跑批 → 校验器 4 条全绿 → test.one 新文件 → test.quick 全绿 → (批 2/4/5 后加跑 test.full) → 用户显式「提交」→ ship.commit (commit 信息 gitmoji + 中文, 数字用当批实测)。

05拆分机制与机检

5.1 为什么用脚本而不是手搬

14,367 行手工搬移必然产生漏迁 / 重迁 / 夹具落错文件, 且测试照样全绿——这正是 bulk-rename 坑档记过的「静默漏迁, 全绿假象」。脚本化后「漏迁」从靠人眼变成靠校验器, 每批迁移的机械面零判断。

5.2 校验器 4 条 (内建于脚本, 每批必跑)

#校验钉住的失败形态
①函数名集合恒等: 拆前 AST 清单 == 拆后 15 文件清单并集, 按名 diff 为空漏迁 / 丢函数
②总数恒等: 拆后函数计数 == 323, 且每名恰出现一次重迁 (同名两处)
③docstring 计划反幽灵 + 条目守恒: 每文件清单条目必须指向本文件存在的函数; 15 文件条目总数 == 306计划清单漂移 (26-10-05-0945 切片的教训)
④可收集: 全部新文件 py_compile 通过 + pytest --collect-only 计数恒等import 裁剪错 / 常量落错文件

5.3 红验 3 条 (S2 一次性做, 先红后修)

  • 映射表故意划走 1 个函数不迁 → 校验 ① 必须红;
  • 映射表把同一函数指给两个文件 → 校验 ② / no_duplicate 守卫必须红;
  • 某文件 docstring 一条计划行的函数名改成不存在的 → 校验 ③ (反幽灵) 必须红; 整行删掉 → 条目总数 306 恒等必须红。

红验与被测失败形态必须同构 (assertions 坑档纪律): 只验「整批漏迁」等于没验过。

06风险与对冲

风险对冲
隐藏的测试间耦合被拆分显形 (共享全局状态 / 顺序依赖), 换文件分组后 flakyxdist -n 4 本就打散执行顺序, 分组变化不改变并行语义; 若显形, 属既有缺陷——当批最小修复并入档案, 修复面超出即入池 issue, 不顺手扩修 (范围守恒)。
docstring 测试计划漂移校验 ③ 机检 + 拆分本身把 300 余行大清单缩成单文件尺度, 漂移面变小。
机械迁移漏迁 / 重迁且全绿假象校验 ①② + 红验 3 条 + no_duplicate 守卫三重兜底。
静态守阵的路径常量 / 白名单常量落错文件S1「定义→使用」矩阵先裁决归属; 校验 ④ 的 --collect-only 在导入期即暴露 NameError。
覆盖率口径漂移 (并行与串行差 1, 坑档在案)全程沿用 -n 4 口径对比基线, 不跨口径比较; 单文件验证用 test.one (自带 --no-cov)。
实施跨会话, 其他会话同批改 test_web.py 撞车每批开工先 sync; 批粒度小且每批独立 commit, 冲突面收敛在单批内。
「顺手修」蠕变 (迁移中看到相邻缺陷想改)纯移动纪律 + diff 审查口径「行只在文件间移动」; 相邻缺陷一律入池 issues/。
