§01目标与设计原则

定片(规程 §06 步骤 1)

片号 RM04 = 辅种与分组(锚件 §03), glob 6 条(见 §02 glob 自检), 验证面: 归组 key / 跨组文件冲突 / 缺失文件标记 / 跨盘移动 / journal 恢复。上一轮: 2026-10-31 首轮 8/8 全绿(计划 plans/26-10-31-1042-plan-real-rm04.html, 切片 testing/real-baselines/26-10-31-1219-real-RM04.md, 基线 bb02248b)。

本轮要做成三件事

  1. 全量复测: 8 条既有用例在 qbittorrent-api 2026.8.1 → 2026.10.1 升版 + torrents 快照新字段(share_limits_mode)下回归(库变属基建变, 不是纯重构, 按漂移纪律一律重跑)。
  2. fbaf0446 记入 RM04 漂移面的两个新真机面: facade share_limits_mode 与跳检重加回传 —— 在 5.2.3 上把「可触发面」真机验掉(新增 RM04-09), 5.3 服务端语义预登记 BLOCKED + 解锁条件(§04 ③)。
  3. 环境2 前提差异落成用例改造点: R: 盘缺席 ⇒ RM04-05/06/07 的 RAM=R:/qbt-fake 落点失效; D: 为空光驱 ⇒ 本机唯一可写卷 C: ⇒ RM04-05「真跨卷」判据不可达, 按同卷口径重写(§04 ①)。

做到什么程度算成

官方 real.suite --slice RM04 一轮: 复测 8 条 + 新增 1 条全 PASS(预登记 BLOCKED 之外零 FAIL); 红验全数见红; 基线重立 commit 落切片; 锚件 §07 RM04 行同步更新; 收尾核净(§04 ④)。

设计底线 / 不变量

  • 产品 src/ 零改动 —— 只动用例代码(tests-real/rm04_relocate/)与必要的用例侧基建; 缺陷当轮不修, 一律入池。
  • 同一件事不测三遍(锚件 §08 拍板口径): checking 跳检/全量决策链与执行体引用 RM03-15..17; guardian「qB 退出删链接」路径引用 RM10-05/06/07; 转移面(path_map/api_key/409 查重)引用 2026-11-01 转移真机再验收 R3 —— 一律只记账引用, 不复测。
  • 零外连红线: 假种子 announce 用本机死端口 http://<本机IP>:1/announce; 绝不碰主实例真实种子(环境2 主实例本就 0 枚)。
  • 任何文件不得出现 token; 允许开启/重启两个测试 qB(56589/56590), 绝不动其它 qB。

5.3.x 面可触发范围结论(按代码实况核实, 2026-11-01)

fbaf0446 的设计目标即「同一份代码双服 5.2.3/5.3.x, 不引入版本号分支」—— 产品代码里没有任何版本分支: facade(qbapi.py:197)恒发 share_limits_mode="Default"; 跳检重加(ops_mod._skip_add_call)恒透传快照值, 而 5.2.3 快照无该字段恒 None ⇒ 库对 None 值键不发, wire 与升版前完全一致。⇒ 在本机 5.2.3 上:

  • 可真机触发: ① facade 调用链端到端(_cmd_set_share_limits → facade → qB)带新参后 5.2.3 照常生效(= RM04-09); ② 跳检重加主链在新库(2026.10.1)上不回归(= 复测 + RM03-15..17 引用); ③ 快照层新字段采集不炸(compat 加法式字段, 随全量复测)。
  • 不可真机触发(BLOCKED): 5.3 服务端语义 —— torrents/setShareLimits 缺 shareLimitsMode 回 400、重加后 MatchAny/MatchAll 保持不被重置为 Default、share_limits_mode 作为 torrent 字段出现在 5.3 快照里。解锁条件 = 任一环境部署 qB 5.3.x 测试实例(feat issue 26-10-31-0711 族 P4「真机确认」原口径就等 stable 发布, 与本轮一致, 不另立条件)。
