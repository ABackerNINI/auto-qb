热重载机制简化: 统一挂载口 vs 保存即重启

配置热重载机制四类失效反复复发, 根因是「谁需要知道配置变了」这一知识分散在中央分级表、分派分支、消费方钩子、测试守阵四处, 各自演化各自腐烂。本文对比两条彻底简化路线 —— 方向一「统一挂载口」(Spring RefreshScope 同族) 与方向二「保存即重启进程」(nginx / uvicorn 同族), 附成熟方案调研、对比矩阵与推荐路线, 供拍板。

01背景与问题定性

现有机制 (config/impact.py + qbmanager.apply_new_config + HrRuntime.apply + webui/server/lifecycle.py, 核心约 800 行): WebUI 保存 → 写盘 YAML → 命令队列投 reload_config → 主循环线程 diff 新旧配置, 每项变更按 L0(换对象即生效) / L1(轻量重挂) / L2(结构重建) / R(拒绝, 须重启进程) 分级应用。分级靠三张手写表 (SECTION_LEVELS / TRACKER_FIELD_LEVELS / HR_CHECK_FIELD_LEVELS), 未列出键默认 L2。

问题定性
四族 bug 是同一根因的四种表现: 配置消费知识没有单点。L0 的成立前提「消费方每轮现读」是散落在几十个类里的实现细节, 中央表把它们编码成静态分类后必然腐化 —— 2026-09-29 实报时 impact.py 注释写「取数线程每轮现读」, 与实现 (HrRefreshService.__init__ 按值拷贝) 完全相反; 旧守阵还把反语义钉死。任何简化必须让这个知识回到单点。

02成熟方案调研

2.1 进程级重启 —— 工业界的默认答案

Unix 守护进程四十年的惯例是 SIGHUP → 重读配置; nginx 把它做成教科书: master 收 HUP 后先校验新配置语法(不合法则旧配置继续跑, 什么都不变), 再用新配置起新 worker, 旧 worker 停止接新连接、排空在途请求后退出 —— 监听 socket 由 master 持有, 全程不关, 所以零宕机。uvicorn 的 --reload 更简单粗暴: 文件变了就 kill 进程重新 spawn (开发场景)。systemd / supervisor / docker 的 restart 策略则是「外部监督者拉起」的通用形态。这一族全部映射到本仓的方向二。

2.2 组件级刷新 —— Spring 已证明的另一条路

Spring Cloud 的 @RefreshScope 是「不重启进程、按组件重建」的旗舰实现: /actuator/refresh 事件触发 RefreshScope.refreshAll(), 只销毁标注了刷新作用域的 bean 缓存, 下次访问时用新 Environment 惰性重建; @ConfigurationProperties bean 由 rebinder 单独重绑。机制核心与方向一同构: 「刷新事件广播 → 组件自判重建 → 惰性/短路兜底」。同族还有各守护进程的 rehash 惯例。

2.3 Python 生态的边界 —— 没有现成库

Python 侧的配置库只解决「设置对象」不解决「消费方」: dynaconf 的 settings.reload() 只刷新设置对象本身; watchdog / watchfiles 只探测文件变更; HMR 类库 (promplate/hmr 等) 是开发期模块热替换, 不是生产配置面。2026-01 还有人写「生产 Python 系统自建 config hot-reload」的指南 (OneUptime blog), 佐证消费方重建这一段生态里没有可引用的现成品。

调研结论
两条路线在工业界都是成熟模式、无现成库: 方向二的对应物 (nginx / uvicorn / supervisor) 成熟到无聊, 方向一的对应物 (@RefreshScope) 证明该模式可长期演进。能抄的是模式 (nginx 的「先验证后切换」、RefreshScope 的「销毁缓存 + 惰性重建」), 不是代码 —— 「消费方重建」这部分纪律注定是本仓自有代码。两个方向的真正差别, 是把这部分纪律做多小。

03方向一 · 统一挂载口

把 2026-09-29 修复中 HR 已被迫走通的模式 (每次热重载都调 + 组件内部自判短路) 升格为唯一模式, 删掉级别分派层。

3.1 协议

class ConfigConsumer(Protocol):
    def sections(self) -> tuple[str, ...]:
        """声明消费哪些顶层段 (守阵: 配置里每个段至少被一个组件认领)"""
    def apply(self, old: Config, new: Config) -> ApplyResult:
        """每次热重载无条件调用; 内部做整段相等比较, 相等即短路 return"""
# ApplyResult = (组件名, 动作: none | remount | rebind | rebuild, 摘要)

编排退化为一行循环: diff 只剩两个职责 —— 生成用户可读的变更报告 + 把守 R 级闸门 (state_file / data_dir / fs 变更不进组件循环, 维持「须重启进程」提示); 其余全交给组件。主循环节拍现读键 (main_tick / sync_interval / state_save_interval 等) 不属于任何组件, 天然零动作。

3.3 四条设计规则

  1. 整段相等, 不做逐字段白名单 —— dataclass == 自动覆盖段内新增键, 「新键忘登记」从「静默失效 / 全量重建」变成「被认领组件自动看到」;
  2. 比较与状态同居组件侧 —— 消费知识单点化, 中央表不再编码实现细节;
  3. 认领守阵 —— 配置每个段至少被一个组件 sections() 认领, 未认领段的变更落 WARN 日志 + 全量重建兜底 (保守性可解释);
  4. 从无到有收敛 enabled ⇒ 在跑 —— 坑档既有结论, 端点与线程一体适用, 不再靠守卫放行。

3.5 代价与风险

核心改动估 300-400 行 (其中相当部分是「搬家」而非新写), 守阵改写估 15-20 例。风险两条: ①段认领遗漏 → 变更不生效, 对策是认领守阵 + 未认领段全量重建兜底; ②receipt 形态变化的前端适配 (改动集中在 config_hub 一处)。

04方向二 · 保存即重启

任何配置保存 → 写盘 → 主循环收到 reload_config 后不再 apply, 而是走优雅停机 → 外部拉起。热重载机制 (分级表 / 分派 / 组件钩子, 约 800 行 + 三个测试文件的相关守阵) 整体退役, 模型退化为「冷启动唯一路径」。

4.1 流程

PUT /api/config (写盘, 校验不变)
  -> 主循环 consume reload_config
       -> save_state()            # 优雅退出落盘, 丢失窗口 = 0
       -> 停 hr / web / notify    # 复用现有 stop 纪律
       -> 退出 (退出码 0)
  -> 外部拉起 (见 4.2 宿主形态)
  -> 前端轮询 /api/state 直到服务回来, 自动恢复

可行性支撑: 周期落盘 (commit ffb74409, state_save_interval) 已把非优雅终止的丢失窗口压到 ≤ 间隔, 优雅路径丢失为 0; 单一写线程保证停机时刻无写在途。

4.2 宿主形态 —— 方向二的真正成本在这里

宿主拉起方式评估
docker / composerestart 策略 + 退出码契约 (qbmanager.py:350 既有)零新增, 最顺
宿主直跑 CLI进程退出即停用户手动重跑, 或外层脚本循环 —— 谁来保证外层活着?
托盘 (Windows 桌面, 主场景)托盘与主程序同进程 (tray/app.py 直接持 QbManager)进程退出 = 托盘一起消失, 桌面无人拉起 —— 必须补 launcher 外壳 (批处理循环 / 计划任务) 或 os.execv 自我替换; Windows 下 execv 的控制台与 stdio 继承有历史坑, 需真机验证

4.3 体验与变体

每次保存断连约 3-5 秒 (进程重启 + 连接重建), 调参期连续保存时明显; web.port 变更时旧页面永远连不回, 只能人工换地址 (docker 端口映射固定则无此题)。变体「方向二′」: 保留 L0 现读 (节拍类零成本), 仅 L1/L2 变更重启 —— 但这意味着级别表留下了一半, 简化不彻底, 只作为体验折中候选。

4.4 代价与风险

净删约 500 行 (删 800 增 ~250: 停机序列 ~100 + 前端重连 ~80 + 桌面拉起 ~50-100, 均为估算), 测试侧热重载守阵大半退役。新故障面一条:拉起链 —— launcher 挂了 = 程序失踪, 且三种宿主形态都要验证。换来的是机制彻底不存在, 四族 bug 连根拔。

06推荐与实施路线

推荐方向一, 四条理由:

  1. 保存体验零回退 —— 本工具是常驻自动化 + WebUI 调参场景, 保存即断连伤调参效率;
  2. 已被半验证 —— hr.apply 2026-09-29 修复后就是目标形态, 且再未复发, 方向一是把既成事实升格为制度, 不是赌新设计;
  3. bug 族结构性消灭 —— 漏调/从无到有族的老家 (分派分支) 被删除, 而不只是修补;
  4. 留退路 —— 组件协议与方向二不冲突, 若落地后同族 bug 再犯, 随时可切换方向二作为终局解 (届时唯一要补的工程是桌面拉起)。

实施按 §3.4 五波走, 每波独立入库: W1 影子并行 (行为等价) → W2/W3 逐组件迁移 (每波删一个分支) → W4 表退役 → W5 回写与基线。拍板后本件冻结, 执行滚动进 tasks/ 档案。
