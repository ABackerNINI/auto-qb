qB 移动已完成种子误判缺文件
—— .!qB 过渡态容忍修复计划

qBittorrent 移动已完成种子时偶发把磁盘文件临时改名为 <原名>.!qB，缺文件磁盘扫描在这个改名窗口内拿原名做存在性判定，把过渡态读成永久缺失，导致整组误暂停并打 MISSING 标签。本计划在扫描汇聚点加过渡态容忍，并用连续次数上限兜住残留场景。

01背景与结论

现象（来自 issue 26-09-21-0219，用户 2026-09-21 现场口述）：qB 移动已完成的种子时，有概率把磁盘文件临时改名为 原名.!qB；移动伴随重新校验。窗口期内本程序的缺文件磁盘扫描用缓存的文件名拼原路径做 os.path.exists，原名不存在 → 判「文件缺失」→ 整组 torrents_stop 暂停 + MISSING 标签。文件其实存在，只是带后缀 —— 误判。

后果：误停健康做种的整个辅种组；MISSING 标签污染后续 multi-dl/mixed 冲突语义（带标完成成员不再计入「已完成」，放行重下），需人工发现才能回滚；另叠加一次无谓重校验的大文件 I/O。

核心结论：在三类触发源的唯一汇聚点 _check_missing_files 做「过渡态容忍」—— 原路径不存在时先探测同名 .!qB 孪生文件，存在则本轮整轮放弃判定（不暂停、不打标）；同时记录每组连续命中次数，连续 3 次未消除按真实缺失处理，兜住 qB 残留后缀的极少数场景。不加新配置键；check_filelist 只加诊断日志不改行为。

前提事实：issue 标注「未复现 = 未证实」，后缀成因是假设。本方案对「成因」保持中立 —— 只对「原名缺失且 .!qB 孪生存在」这一可观测状态做容忍，无论后缀由 qB 哪个内部机制产生都覆盖。取证要求保留在 §07。

02误判链路（已按 676f761 逐环核实）

步骤发生什么代码事实（取证 2026-09-22 20:38）
① 移动发起move_to 规则或 Web UI 移动对话框 → qB torrents_set_location；qB 侧搬运伴随重新校验（issue 记录的现场行为）MoveToAction.execute（rules/actions/transfer.py），本程序只发 API，不动
② qB 改名窗口磁盘文件短暂呈 原名.!qBqB 内部行为，成因未证实（issue §05 维持假设定性）
③ 同轮触发扫描save_path 变化或进入 errored 触发缺文件扫描_handle_save_path_changes / _handle_state_transitions（mixins/grouping.py），事件驱动
④ 误判第一现场原名 os.path.exists 为 False → 判缺失_check_missing_files（mixins/grouping.py），用缓存 sizes[rep.hash] 拼路径
⑤ 连锁污染整组暂停 + MISSING 标签torrents_stop + _add_tags；标签改变 _check_download_conflicts 的 mixed 语义

为什么单点修在 _check_missing_files

  • 唯一汇聚点：删除事件 / save_path 变化 / 状态转移三类触发源最终都进这一个函数 —— 一处覆盖全部链路，不用分别打补丁。
  • 代表种筛选恰好放进窗口：2026-09-12 放宽后 errored 成员可当代表种（_valid_for_representative = complete/errored 且非 checking），而「重校验发现文件缺失 → errored」正是误判主触发 —— 代表种的 save_path 与缓存映射在窗口内都指向被改名的物理目录。
  • 扫描是事件驱动的：轮内去重靠 _missing_scanned_keys（qbmanager.py:218 定义、:663 每轮清空）。「本轮跳过」的实际语义是「跳过这次触发事件」，下一个事件到来才再判 —— 这直接决定 §03 必须配「连续次数上限」。
  • checking 链路危害有限：check_filelist 被 CheckAction 决策链 4 用作跳检前置检查，失败走 ActionResult.skip、并不发送 recheck；torrents_recheck 只在前置检查通过后才发送（rules/actions/checking.py + full_checking.py）。所以该链路最坏后果是「跳检白跳一次」，不值得改行为，加日志即可。

03方案设计

3.1 修改点总览

#位置改动行为变化
1src/auto_qb/utils.py新增纯函数 has_qb_incomplete_twin(path) 与单点常量 QB_INCOMPLETE_SUFFIX = ".!qB"无（新函数）
2mixins/grouping.py · _check_missing_files原路径不存在时先探测孪生；命中 → 记 warning，本轮整轮放弃判定，组计数 +1误判窗口内不再整组误停
3torrents.py · TorrentStore新增会话级内存计数 transitional_missing_skips: Dict[str, int]（组 key → 连续次数），不落盘无（新字段）
4mixins/grouping.py · 同函数连续 ≥ TRANSITIONAL_SKIP_LIMIT = 3 次未消除 → 按真实缺失走原暂停+MISSING 分支；判定正常结束则清零该组计数残留后缀不被无限放过
5mixins/checking.py · check_filelist缺失且孪生存在时，错误文案追加「（疑似 qB .!qB 过渡态）」仅日志文案，返回语义不变

3.2 _check_missing_files 改造（示意）

missing = False
transitional = False
for fname, fsize in sizes.get(rep.hash, {}).items():
    full_path = utils.add_long_path_prefix_for_win(
        os.path.normpath(os.path.join(rep.save_path, fname)))
    if not os.path.exists(full_path):
        if utils.has_qb_incomplete_twin(full_path):   # 原名缺失时才探测, 健康路径零新增 stat
            transitional = True                        # 改名窗口: 整轮放弃, 单文件结论不可靠
            break
        logger.warning(f"辅种组 | 文件缺失: '{full_path}'")
        missing = True
        break
    ...                                                # 大小不一致 / OSError 分支不动
if transitional:
    n = self.store.transitional_missing_skips.get(key, 0) + 1
    self.store.transitional_missing_skips[key] = n
    if n < TRANSITIONAL_SKIP_LIMIT:
        logger.warning(f"辅种组 | 疑似 qB 搬运过渡态(.!qB), 本轮不判缺文件"
                       f"(第{n}次): 代表种 {rep.log_repr}")
        return                                         # 不暂停、不打标
    logger.warning(f"辅种组 | 过渡态(.!qB)连续 {n} 次未消除, 按真实缺失处理")
    missing = True                                     # 落入下方原有整组暂停 + MISSING 分支
else:
    self.store.transitional_missing_skips.pop(key, None)  # 正常判定(含真实缺失): 清零重计
if missing:
    ...                                                # 原有逻辑一字不动

3.3 语义细节

  • 整轮放弃，不是单文件 continue：目录正处于改名窗口，部分文件在、部分带后缀，任何部分结论都不可靠；放弃整轮等下一个事件是最稳语义。
  • 大小不一致 / OSError 分支不动：.!qB 问题的表象是「原名不存在」；原名存在但大小不符是另一种真实异常，与窗口无关，保持原判定。
  • 计数放 store、不落盘：软信号，重启归零的丢失方向是「更早恢复判定」—— 保守方向，可接受；沿用 verified_references 仅内存的先例，docstring 写明取舍。注意它与 _missing_scanned_keys（轮清）不同，跨轮存活，不能在 qbmanager.py:663 的轮清点清空。
  • LIMIT = 3 的依据：三个触发源在移动场景常同轮命中同一组（轮内去重后只扫一次），连续 3 次独立事件都撞上窗口，大概率是残留而非窗口。常量不进配置 —— 触发条件本身已足够窄（原名缺失 且 孪生存在），默认开启符合最小惊讶；真需要开关再走 validate_config + schema.py 同步流程（黄金法则 4 的联动成本现在不必付）。
  • 后缀单点定义：.!qB 字符串只在 utils.py 出现一次，grouping 与 checking 共用，避免散落副本悄悄分叉。

04落选方案与备选

维度本计划：过渡态容忍 + 连续上限落选：移动后按组冷却 N 轮（issue 建议修法 2）
修复面单点改在扫描汇聚处，三类触发链路一次覆盖需在 save_path 变化路径上新增按组冷却状态并逐处接入
状态需求会话级内存计数，不落盘跨轮状态 → 按黄金法则 3 应进 state_file，新增持久化键
真实缺文件延迟仅窗口内推迟；无孪生即正常判定移动后固定晚报 N 轮
时序假设无（只看可观测状态）N 的取值本质是对 qB 窗口时长的猜测
升级条件——现场数据显示 .!qB 窗口远超 3 次事件间隔时，再升级为冷却案（届时本计划档案保留备选地位）

issue 建议修法 3（「校验中一律不判」）已被现有代码部分覆盖：代表种筛选排除 is_checking，MOVING 状态天然不在 complete/errored 集合内（docstring 已注明）。剩余缺口正是「checking 结束后的 errored 窗口」，由本计划主体覆盖，无需重复改 _valid_for_representative。

06风险与边界

风险判据兜底
qB 长期残留 .!qB，组被永久放过同组连续 ≥3 次过渡态命中上限触发后按真实缺失暂停+打标（T2 守住）
真缺失恰逢窗口被推迟窗口通常短于事件间隔下一个事件再判；连续上限保证不会无限推迟
共享物理文件的组：一成员移动，全组判定被推迟一轮轮内去重已保证同组单次扫描事件驱动下轮再扫，无放大
代码漂移导致锚点失准行号只是加速项一律按符号 + grep 重新定位（本计划行号取证 2026-09-22 20:38）

明确不做

  • 不动 MoveToAction，不做移动后主动等待 —— qB 侧行为本程序控制不了，时序等待是猜测。
  • 不采用冷却案（§04 备选地位，升级条件已写明）。
  • 不加新配置键（理由见 §3.3）。
  • 不动 _valid_for_representative（MOVING 已天然排除）。
  • 不碰红线文件：config.yml / auto-qb-data/ / 想法.md。
  • 不做 Web UI 改动 —— Web UI 移动走同一条 qB API，容忍逻辑在后端扫描处，天然覆盖。
