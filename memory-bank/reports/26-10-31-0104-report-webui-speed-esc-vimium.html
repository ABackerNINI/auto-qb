WEBUI 限速浮层 Esc 需按三次: Vimium C 扩展吞键取证

「限速浮层要按三次 Esc」不是页面代码缺陷: 前两次 Esc 的 keydown 被 Edge 扩展 Vimium C 在扩展层整个吞掉(事件未到达页面), 第三次才放行 —— 页面侧退栈链第一次收到 Esc 就正确关窗(真机诊断日志实证)。

doc-added 26-10-31-0104 · doc-updated 26-10-31-0104 · doc-status Done · 载体 单文件 HTML(dark)
来源 用户真机实测(uv run auto-qb, Edge, 三皮肤)报障「点击右下角限速显示弹出的速度限制窗口需按三次 Esc 才能退出」; 本轮在桩服务 + Playwright 上穷尽复现未果后, 转真机 Console 诊断定位到扩展吞键。

§01结论

根因: Vimium C 扩展拦截, 不在 auto-qb 代码。Vimium C 的 content script 在 document_start 注册 keydown 监听, 注册序恒先于页面脚本; 它处理 Esc 时对事件 stopPropagation, 页面(含 window capture 档)完全收不到。用户在扩展设置中禁止捕获 Esc 后现象消失 —— 反向实证。

页面代码无罪的判据:Esc 退栈链(lifecycle.js:101)是无条件冒泡监听, 不查 isComposing/defaultPrevented —— 事件只要到达 document 必动作; speedOpen 排链上第 4 档(仅次确认框/添加对话框/统计面板), closeSpeedDialog() 一次置 false。真机诊断第三次 Esc 的日志: capture 档 {kc:27, composing:false, prevented:false, target:'BODY'} → bubble-doc → 400ms 后 pop:false, 即一次按键一次关窗, 行为完全正确。

我方代码缓解评估(均已否决, 2026-10-31 终态)

  • keyup 兜底档 —— 已证伪: 设计是在退栈链同点加 keyup 监听, keydown 未到达而 keyup 到达时兜底执行一次退栈动作(一次物理按键只走两条路径之一)。前提是「扩展只吞 keydown、放行 keyup」; 真机验证(用户实测, Vimium 捕获 Esc 开启): 限速浮层前两次 Esc 的 keyup logger 同样零输出 —— Vimium C 对 keydown 与 keyup 一并吞掉, 该前提不成立, 方案作废。keydown/keyup 两通道皆断后, 页面侧不存在任何可感知该按键的事件(Esc 不触发 keypress), 且扩展 content script 注册序恒先于页面脚本, capture 档也抢不到 —— 代码侧无可行缓解。
  • 不建议为此动退栈链顺序、给浮层加遮罩或改交互 —— 链本身在各浏览器上的行为已证正确, 改它对 Vimium 用户无益、对其他用户是纯回归风险。
  • 正解(用户侧配置, 已验证有效): Vimium C 扩展设置中把本站加入排除列表或禁止捕获 Esc; 报障现象即消失。

§03方法与局限

方法:①scripts/ui_harness.py(真 create_app + FakeClient, 端口 8099)+ Playwright Chromium 逐序列探针(脚本在系统 Temp, 未入库); ②CDP Input.imeSetComposition 模拟 IME; ③追加安装 playwright Firefox 155 排引擎变量; ④真机侧由用户执行 Console 诊断 snippet(capture + bubble 双档 logger + 浮层/焦点状态快照)。.

局限:①桩侧始终无法复现「三次」—— 吞键者只存在于用户浏览器扩展环境, 本地无 Vimium C 实例, 关键判定依赖用户真机的 Console 诊断与 keyup 验证; ②「Vimium C 是否吞 keyup」起初未测(报告中曾列为 keyup 兜底方案的前提), 后经用户真机实测证伪(keyup 同被吞), 方案随之作废 —— 本条为快照内的事实修正, 见 §01 终态; ③Edge 与探针 Chromium 同内核, 引擎差异未覆盖 Safari 类(项目不面向)。
