01 / 结论

结论: 方案成立, 是当前唯一能同时救回 A 类能力并打通 Windows 宿主的路径; 但有 1 个必须处理的坑和 2 条安全红线

✅ 成立。「包装层 + 只读挂载 + 路径映射」能救回 §11 矩阵里全部 A 类(宿主路径不可见)只读触点: 缺文件扫描、跳检前置检查、规则 exists() / disk_*()、freespace 条件、目录浏览。其中「缺文件扫描」是唯一会写坏 qB 的一条, 救回它的安全收益最大。

✅ 推翻一条旧结论。§11.5 写的「Windows 宿主无解」只在「同路径挂载」方案下成立。引入映射层后, Windows 宿主有解: -v D:\Downloads:/mnt/downloads + 映射 D:/Downloads → /mnt/downloads。这是本方案相对 §11.5 的核心增量。

❌ 救不回的维持原判: 打开文件夹(缺 xdg-open + 无文件管理器, B/C 类)、桌面通知、托盘、时区/网络身份(D 类)与映射层无关, 处置不变。

⚠️ 两个必须写进设计的前提: ①包装层必须做到「逻辑路径进、逻辑路径出」——映射只发生在 syscall 边界, 否则组 key / 规则匹配 / 回传 qB 的路径全部错位(§04); ②映射 miss 时「宁可报不可判定, 不可判缺失」——映射配错不能复刻「误暂停整组」事故(§05)。

「/mnt/?」的回答: 挂载点叫什么不重要(映射表消化任意前缀), 建议固定约定如 /mnt/downloads; 若宿主是 Linux 且能同路径挂载, §11.5 的零代码方案仍然更优, 映射层是给 Windows 宿主与异路径部署的通用解(§06)。

02 / 前提验证

「下载目录目前只读、其它操作都走 qB」—— 前提成立

对 src/ 全量检索确认, 程序对下载目录(qB 报回的 save_path / content_path 派生路径)的全部本地访问只有 4 类, 读为主, 唯一的写是 WebUI 新建文件夹:

04 / 关键设计坑

双路径空间: 状态与接口必须永远存"逻辑路径", 映射只准发生在 syscall 边界

引入映射后系统里同时存在两个空间: 逻辑空间(qB 报回的宿主路径, 如 D:/Downloads/x)与容器空间(挂载点路径, 如 /mnt/downloads/x)。全库检索确认, 逻辑空间路径被以下消费方以字符串形态使用, 一旦被映射污染即出错:

  • 分组 key: store.groups 的 key 首元 = path_normalize(save_path)(fs.py:82, grouping 归组) —— 映射污染会导致同盘异名两套组、触发器全部失配;
  • 回传 qB 的动作: set_location(qbapi.py:152)、edit_category(qbapi.py:292)、重加种 save_path(qbapi Facade 写方法同步 store)—— qB 认的是宿主路径;
  • 跳检备份元数据(skip_checking.py:277-281): state.skip_check_backup[hash].save_path 记录宿主路径供人工恢复, 必须保持可读的宿主语义;
  • 规则路径匹配 / freespace 配置: conditions.py 的 path 是用户写的宿主路径(R:\), 规则匹配是纯字符串比较;
  • /api/paths 与 /api/open-path 的对外契约: 前端拿到/回传的都是逻辑路径。

因此包装层的 API 契约必须是「逻辑路径进 → 内部映射 → syscall → 结果翻译回逻辑空间再返回」。这不是可选优化, 是硬约束。

fs.py 里已经埋着一个具体的坑

/api/fs/dirs 的白名单判定 _within_roots(fs.py:94-101)拿 os.scandir 返回的 entry.path 与宿主路径 roots 比较(fs.py:134)。若包装层只映射"进"不映射"出", entry.path 是容器空间 /mnt/downloads/..., 与逻辑空间 roots D:/Downloads/... 永远撞不上 ⇒ 所有子目录被白名单过滤 ⇒ 目录树恒空 —— 与 fs.py:53-58 已记录的"前缀差异导致子目录全部被过滤"是同一失效机制。同理 os.path.realpath(fs.py:61,127)在逻辑空间路径上做不了(路径不存在), 符号链接逃逸防护退化为 normcase + normpath 词法比较(与 fs.py:57-59 既有已知限制同口径, 可接受但必须写明)。

Windows 映射的三个细节

  • 大小写不敏感: 前缀匹配须 casefold(nomcase 语义), 否则 d:/downloads vs D:/Downloads 配不上;
  • 分隔符: 映射在 path_normalize(折叠 \→/)之后做即可统一两种写法;
  • \\?\ 长路径前缀: 现在 add_long_path_prefix_for_win 散在 grouping.py:250 / checking.py:25 / fs.py 等调用点, 容器(Linux)里它是空操作。包装化时应把"加前缀"收进包装层单点, 调用点只交逻辑路径 —— 调用点反而变简单。
05 / 安全红线

映射 miss 必须 fail-safe: 「宁可报不可判定, 不可判缺失」

事故链重演风险: 缺文件扫描的逻辑是 exists == False ⇒ 判缺失 ⇒ 暂停整组 + MISSING 标签(真实写 qB, §11.3)。若用户映射表配错(前缀大小写/盘符/尾斜杠不匹配), exists 会再次恒 False —— 方案自身复刻它要修的事故, 且这次用户以为已经修好了, 更难排查。

红线: 包装层对任何无法映射到容器空间的路径, 不得返回"不存在", 必须向上返回「不可判定」。具体语义: check_filelist 返回"路径不可判定(未命中映射)"而非"文件缺失"; 缺文件扫描遇到不可判定跳过该组并 WARNING(不暂停、不打标); exists() 表达式抛 ExprError(显式报错优于静默 False, 与 disk_* 现状口径一致)。

配套的启动期自检

  • 启动时校验每条映射的目标(容器侧挂载点)isdir 存在, 不存在则 WARNING 提示"检查 compose volumes"(进 §13 排障表);
  • 校验映射源与现存种子的 save_path 前缀命中率, 零命中则 WARNING —— 提示映射表可能写错;
  • Docker 环境检测建议显式配置键(如 fs.path_map 映射表, 空 = 功能关, 保守默认), 不建议 /.dockerenv 自动探测 —— 自动探测命中即改变核心行为, 违反黄金法则 2; 新键必须进 validate_config + config/schema.py(黄金法则 4)。

open_path 的处置: 不是修好, 是优雅降级

现在 /api/open-path 的失败是两层根因叠加(未挂载 404 → 挂载后 xdg-open 缺失 500, 实测见 pitfall 文件)。docker 包装层接手 open_path 后应直接返回"容器环境不支持"(501 + toast 引导用「复制路径」), 把两层根因收敛成一句话 —— 这是包装层顺手能拿掉的排障负担。

06 / 挂载策略

只读挂载覆盖全部读触点; 挂载点选 /mnt/ 还是哪里, 由映射表消化

部署形态挂载方式映射表说明
Linux 宿主, 可控挂载点-v /volume1/downloads:/volume1/downloads:ro空(同路径直通)§11.5 零代码方案, 仍是最优选; 映射层不启用
Windows 宿主(Docker Desktop / WSL2)-v D:\Downloads:/mnt/downloads:roD:/Downloads → /mnt/downloads推翻 §11.5 "Windows 无解"旧结论; drvfs 挂载的 disk_usage 数值需实测
qB 也在容器里(NAS 常见)两个容器挂同一 volume, 各自路径可不同qB 内路径 → 本容器挂载点同路径能对齐则退化到第一行
  • 挂载点命名(/mnt/?): 无功能性差别 —— 映射表消费任意前缀。建议固定约定(如 /mnt/downloads)并写进 compose 示例, 减少示例配置的组合爆炸;
  • :ro vs :rw: 只读覆盖全部读触点(§02); 唯一写「新建文件夹」需要 :rw。建议默认 :ro(保守默认黄金法则), docker 包装层对 mkdir 直接语义化拒绝(403「容器只读挂载不支持新建」), 不让 OS 抛 EROFS 变 400 乱码; 用户确需新建再换 :rw, 无需改代码;
  • :ro 的额外收益: 从文件系统层杜绝 auto-qb 误写下载数据(与"所有写操作都通过 qB"的设计互为保险);
  • qB 侧不变: qB 继续按宿主(或自己的容器)视角写数据, auto-qb 的 :ro 挂载对它零影响 —— 两进程共享同一物理目录, 只是一个只读视角。

08 / 遗留与边界

本方案不背的包(维持原处置)与待实测项

  • B/C/D 类 17 项(通知、托盘、时区、网络身份等)与本方案无关, 维持 deployment.md §11.4 配置口径;
  • Windows 宿主 drvfs 挂载的 disk_usage 数值正确性与 getsize 在 9p/drvfs 上的性能 —— 代码级可判定, 数值/性能需真机实测(实施轮第一件事);
  • 同实例双跑: 宿主实例与容器实例共用 data_dir 时锁互挡不住(msvcrt ↔ fcntl, §11.2 #16)—— 与本方案正交, 维持警示;
  • 映射配置错误的过渡期风险: 上线映射功能本身不引入新事故面(默认空表 = 现状), 但开启后配错的 fail-safe 靠 §05 红线兜底 —— 该语义必须先于功能落地, 不能后补;
