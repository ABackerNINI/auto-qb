1摘要

现象（用户报）
批量跳检成功后，接着「批量开始」：UI 先显示下载，过几秒变成已停止/暂停；而此时 qB 里那批种子状态已经翻成做种。UI 与 qB 脱节。
机制（一句话）
这是三条独立缺陷叠加的结果：① 跳检收尾不把重加后的状态回写快照（快照里那批种子仍是「跳检前的暂停 0%」）；② 批量开始的乐观补丁按陈旧的行进度预测成「下载」，而 qB 真值是「做种」；③ 批量命令永远收不到服务端真值事件（bulk_torrents 被整体列入延迟回执族、drain 不给它登记真值 —— 而真值通路其实早已为 bulk 备好，只差归属，见 §4.3），于是乐观值既不收敛、也等不到真值来纠正 —— 8 秒后兜底回滚，回滚目标却是点击那一刻的旧值（暂停），于是一屏假状态被钉在行上，直到服务端下一次把该行标记为脏。
结论（可修，改动都在既有单点上）
  1. 必要 跳检重加成功后，用一次单 hash 直查真值把 state/progress 等字段回写记录（对齐本仓既有纪律：决定性时刻直查真值，坑档 pitfalls/backend/effect-confirmation.md）。
  2. 必要 让 bulk_torrents 的 pause/resume 也登记真值（defer_receipt）—— 后端 _truth_landed / _affected_hashes 里 bulk 分支早已写好、且是按 action 正确分流的实现，与单种走同一条真值通路；它一步走不到只因 bulk_torrents 被整体列进 DEFERRED_RECEIPT_COMMANDS（该 handler 是 8 种 action 的大杂烩，回执只能一刀切，见 §4.3）。修法是按 action 分流归属，不是拆成 N 次单种调用。
  3. 必要 前端回滚目标不得是「点击时刻的旧值」：兜底回滚前先看服务端快照，服务端已不再处于命令前状态就别打回旧值；同时把「已收敛」判据放宽为「服务端已离开命令前状态」（与服务端 _truth_landed 同谓词）。
  4. 加固 _sync_paused_state 的完成位不要只看 state_enum.is_complete，联合 progress/amount_left；替身 FakeClient.torrents_add 补上 skip_checking → 已完成 的真实语义（当前替身把重加结果造成 progress=0，这条链路在单测里天然不可见，见 §5）。
影响面（为什么单组/单种子操作看不到）
单组开始走 /api/groups/{key}/resume → 命令 resume_group，单种子开始走 /api/torrents/{hash}/resume → resume_torrent：两者都不是延迟回执族，drain 会给它们 defer_receipt，因此有 truth 事件 → op.prev 被真值刷新 → 即使预测错了，回滚也不会打回旧值。只有多选（批量）路径（/api/torrents/bulk → bulk_torrents）缺失这一环。

2口径对照：症状里的三个词分别指什么

先钉住术语，避免把「用户口语」和「代码状态词」混起来读。

症状原话对应代码界面取值来源
UI 显示「下载」kind = "downloading"，行状态列文案「下载」（decorate.js:139-141）后端 state_kind()（webui/views.py:149-166）按记录 state_enum 分类；前端乐观补丁也会直接写 row.kind
UI 显示「已停止」kind = "paused"，我们 UI 的文案是「暂停」；qB 5.x 的中文界面把 stopped* 家族译作「已停止」（qB GUI 译名存在 decorate.js:64-71 的触发表里）同上。「已停止」是用户口语，代码里就是 paused 这一档（= 停止/暂停轴）
qB 里「做种」stalledUP / uploading → kind = "seeding"qB 实时状态（torrents/info）

所以真正的不一致是：UI 行上是 paused，qB 实时是 seeding。中间那 8 秒的「下载」既不是真值也不是旧值，是乐观预测（外加服务端快照在同时段也说错话，见 §4.2）。

3取证：探针实测 + 逐帧链路

3.1 进程内探针实测（最关键的一条证据）

用项目自带替身（tests/helpers.py 的 FakeClient / FakeTorrent）构造「暂停未完成」种子，直接调真 OpsModule.skip_check，再把 qB 侧真值改成跳检重加的真实结果（is_skip_checking=True ⇒ 全部块视为有效 ⇒ 完成），随后调真 QbApi.torrents_resume，最后跑一轮增量同步：

=== 跳检前 ===
[before]              store: state='pausedDL'  progress=0.0 kind='paused'      | qB(live): state='pausedDL'  progress=0.0
skip_check -> ActionResult(success, skip-checking 跳检完成)
[after-skip]          store: state='pausedDL'  progress=0.0 kind='paused'      | qB(live): state='pausedUP'  progress=0.0
--- 把 qB 真值设为 stoppedUP / progress=1（跳检重加的真实结果）---
[snapshot-still-stale] store: state='pausedDL' progress=0.0 kind='paused'      | qB(live): state='stoppedUP'  progress=1.0
--- 批量开始（已知快照完成位为假）---
[after-resume]        store: state='stalledDL' progress=0.0 kind='downloading' | qB(live): state='stoppedUP'  progress=1.0
--- 下一轮 sync 之后 ---
[after-sync]          store: state='stoppedUP' progress=1.0 kind='paused'      | qB(live): state='stoppedUP'  progress=1.0

三条硬结论（探针直接打出，不靠推理）：

  1. skip_check 全程没有回写被重加种子自身的快照字段 —— 跳检「完成」之后，快照里那批种子仍是跳检前的 pausedDL / 0%（第 3、4 行）。
  2. 在这份陈旧快照上执行「开始」，服务端快照自己也会说错话：_sync_paused_state 按陈旧的完成位推出 stalledDL（kind=downloading），而 qB 明明是完成+在跑（第 5 行）。这是 UI 上「下载」的第二个来源（第一个是前端乐观补丁）。
  3. 只有等下一轮 apply_sync 才对齐（第 6 行）—— 也就是说「快照对齐窗口」在跳检收尾后必然存在，窗口内系统对这批种子的认知整体是错的。

链路自证
第 4 帧的「陈旧行」是必要条件：只要预测值恰等于最终真值（例如行进度已是 100% ⇒ 预测 seeding），第 7~8 帧都不会发生。第 7、8 帧则是放大器：一旦预测错，批量路径必然走满 8 秒并回滚到旧值 —— 这个失配是确定性的，不是抖动。

4逐层根因（4 条，按「是否必要」排序）

4.1 必要 跳检收尾不回写快照 —— 快照的「跳检结果」全靠下一轮 sync 兜

定位：core/modules/ops_mod.py:749-801（_skip_readd）·core/qbapi.py:177-178（torrents_add 透传）·torrents/store.py:562-574（remove_torrent / restore_torrent）

证据：重加走的是 QbApi.torrents_add，它刻意透传（注释原文「写操作: 无快照变化(下轮 refresh 校准)」）；收尾则是 store.restore_torrent(tor)，把删除前捕获的那条记录对象原样放回 by_hash。于是重加带来的真实变化（skip_checking ⇒ 全部块视为有效 ⇒ progress=1、本地统计清零、状态进 stoppedUP）一个字段都没进快照。探针第 3 行实测：跳检「成功」返回后 store.state='pausedDL' / progress=0.0。

为什么这是缺陷而不是「可接受滞后」：① 同一条链上的标签写了快照（torrents_add_tags ⇒ update_torrent_fields），只有 state/progress 没写 —— 快照变成「半新半旧」；② 系统随后会拿这份错快照做判定（G5/G7 的 is_checking、分组冲突 _CONFLICT_FIELDS、乃至这里 _sync_paused_state 的完成位），不只是显示问题；③ 本仓既有坑档已把这条纪律写死：memory-bank/pitfalls/backend/effect-confirmation.md 明确要求「决定性时刻直查真值，不回落快照」，而跳检收尾恰恰是「不可逆操作刚生效」的决定性时刻。

触发窗口有多大：至少「跳检命令结束 → 补刷新 apply_sync 落地 → 前端取到新视图」这三段之和；若用户在同一条命令批次内点击（批量跳检还在跑时就点了批量开始，两条命令会被 drain 的 while True 一次性取走、补刷新在两条之后才跑），窗口可横跨整个跳检执行期。

4.2 加固 _sync_paused_state 用「快照的完成位」反推 state —— 陈旧时把已完成写成 stalledDL

定位：core/qbapi.py:96-119（torrents_pause/torrents_start/torrents_resume 共用）

证据：实现是 complete = state_enum.is_complete，然后 want = "stalledUP" if complete else "stalledDL"。探针第 5 行：快照陈旧（记录还是 pausedDL）时，「开始」把这批种子写成 stalledDL，而 qB 是 stoppedUP（完成）。is_complete 由 state 后缀 UP 判定（torrents/record.py:231-238 转 state_enum），陈旧记录的后缀是 DL ⇒ 判假。

为什么算加固而非主因：它只在「快照陈旧」时才出错，而 4.1 修好后这个前提基本消失。但它同时把「UI 显示下载」这件事从前端单点扩散到服务端快照（前端即使不打补丁，读到的也是 downloading），并且是 pause/resume 两个轴共用的单点，值得顺手收紧判据（例如联合 progress >= 1.0 或 amount_left == 0）。

4.3 必要 批量命令没有「真值出口」—— 可达性被 DEFERRED_RECEIPT_COMMANDS 的名单归属切断

定位：webui/runtime.py:431-495（drain）·webui/runtime.py:966-982（defer_receipt）·webui/commands.py:142-152（DEFERRED_RECEIPT_COMMANDS）

证据链（三条，缺一不可）：

  1. drain 只在 cmd_id and not deferred 且 cmd in RESYNC_COMMANDS 时调 defer_receipt（runtime.py:463-469）；
  2. bulk_torrents 在 DEFERRED_RECEIPT_COMMANDS 里（commands.py:146，它由 handler 自写回执）⇒ 永远不调 defer_receipt ⇒ truth_pending 里从来没有它；
  3. flush_truths 只遍历 truth_pending（runtime.py:895-897）⇒ 批量命令永远不会推 truth 事件。

被锁住的支路（冒烟枪）：_truth_landed 里专门写了 bulk 的判据 —— act = args.get("action") if cmd == "bulk_torrents" else ...（runtime.py:995），_affected_hashes 也专门展开了 bulk 的 hashes+keys（runtime.py:1013-1017）。这套机制是为批量写的，却永远收不到批量命令。而前端 resolveOptimistic 在成功时明确设 hold=true 并注释「值覆盖等到真值事件到达」—— 前端假设每个乐观动作都会有真值事件，批量路径没有兑现这个契约。同一处的测试也印证了口径：tests/test_web_commands.py:628-632 只对「延迟回执族之外」的命令断言真值登记。

影响：批量 开始/暂停 的「值覆盖」只剩两个出口 —— ① _optimisticSettled（要求服务端 kind 等于预测值，预测一旦错就恒假）；② 8 秒 _expirePending 回滚。出口 ② 的回滚目标 op.prev 只被 onTruthEvent 刷新过（全仓就 commands.js:240 一处写它）—— 批量没有真值事件 ⇒ prev 永久停在点击那一刻的旧值 ⇒ 回滚必然打回「暂停」。这就是「与 qB 脱节」的直接成因。

口径修正（26-10-11-2028）：那两条支路不是死代码，是被「名单归属」锁住的活代码
复读 runtime.py:995 与 :1013-1017 会看到：_truth_landed 里的 act = args.get("action") if cmd == "bulk_torrents" else ... 就是按批量 action 正确分流的判据，_affected_hashes 也已把批量 hashes 加 keys 组展开写全。这两处直查 qB torrents/info（_affected_truth），与单种 resume_torrent 走的是同一条 defer_receipt → flush_truths → truth 事件 通路 —— 也就是说，「单种机制」里那套真值通路，服务端早就为 bulk 铺好了。
它们一步都走不到，只因为一处归属判定：commands.py:146 把 bulk_torrents 整体列入 DEFERRED_RECEIPT_COMMANDS ⇒ runtime.py:453 deferred=True ⇒ runtime.py:463 if cmd_id and not deferred: 整段跳过 ⇒ 回执全交 handler 自写、truth_pending 里从来没有它。故原稿「死支路」措辞不准确，应为「可达性被名单归属切断」。

4.3.1 为什么不干脆「走单种机制」（把批量拆成 N 次单种调用）？

因为「复用单种机制」的实质是共用同一条真值通路，不是复用调用次数 —— bulk 与单种底层调的本来就是同一个 QbApi.torrents_resume，差别只在传一个 hash 还是一次传全列表（qB 端点原生收列表，一次调用即设计意图）。拆成 N 次单种命令的代价是 N 次命令队列往返 + N 次主循环 tick，批量上百个种子必然拖长且中途抖动，却没换来任何额外正确性。所以正确做法是按 action 分流归属（见 §6.2），让 pause/resume 走回 drain 的 defer_receipt。

为什么当初会一刀切：_cmd_bulk_torrents 一个 handler 扛 8 种 action，其中 recheck / skip_check / add_torrents 必须自写聚合回执（带 results/summary、跳过与失败计数 —— drain 的裸 ok 会把这些数据位覆盖掉）。一个命令名对「是否延迟回执」只能做整体归属，于是 pause/resume 被连带牺牲。

4.3.2 接回单种通路是不是就万事大吉了？不是

接回后能消掉「过几秒变已停止」（§4.4 的 8 秒兜底回滚不再打回旧值），但不会让 4.1/4.2 消失：它们是让快照本身带错值的独立第一因。真值通路保证的是「最终显示对」，保证不了「全程不抖」—— 快照陈旧仍会让本轮 /sync/maindata 带 stalledDL（靠 qB 下一轮自愈），truth 8 秒超时不推时仍会回滚。4.3 走回单种通路 = 症状消失的必要条件之一；4.1 + 4.2 才让它全程不抖。

4.4 必要 预测只看 row.progress + 兜底回滚回「旧值」：两个单点各自都是陷阱

定位：static/shared/commands.js:289-293（预测）·275-288（兜底回滚）·385-392（收敛判据）

  • 预测：if (action === "resume") return { kind: row && row.progress >= 1 ? "seeding" : "downloading" }; —— 判据只有进度，且读的是行上的值。行数据一旦滞后于 qB（跳检刚完成就是这种时刻），预测必然错。注意：即使把判据改成联合 state（stoppedUP 也代表已完成），也救不了「行本身陈旧」—— 陈旧行的 state/progress 同时是旧的，所以真正的修法是「不确定就别预测」或「让收敛判据不依赖预测是否命中」。
  • 兜底回滚：_expirePending 的注释写着「回滚用的是 op.prev（贴补丁那一刻的行值 = 最近一次已知的服务端真值）」—— 这个等号只在有真值事件刷新过 prev 时成立；批量路径下 prev 永远是「命令前的值」，回滚 = 把行改成命令前的假状态。这与同文件 226-228 行自己写的红线（「兜底回滚必须回最后已知真值：回命令前的旧值等于把一个已暂停的种子显示成做种」）正好相反 —— 只是当初的语境默认了真值事件存在。
  • 收敛判据：_optimisticSettled 要求「服务端 kind 严格等于 补丁 kind」。服务端侧的 _truth_landed 用的是更宽的谓词（resume: kind != "paused" 即算落地）。两侧谓词不对称：服务端认为已落地，前端却认为未收敛，于是补丁继续挂着。

5为什么测试与守阵没拦住

面现状结论

6修复建议（按最小改动集）

四条相互独立、可分别落地；1+2+3 是「先止血」，4 是「防同类」。改动点全部落在既有单点上，不新增旁路。

6.1 改 跳检收尾回写真值（后端）

位置：ops_mod.py::_skip_readd 成功分支（_poll_until 确认种子已出现之后、restore_torrent 前后）。做法：复用既有单点 _live_recheck（ops_mod.py:531-548，内部就是一次 torrents_info(hash) 直查），把返回的实时字段 apply_delta() 到恢复的记录上，再放回 store —— 一行 live 查询换「快照不再撒谎」，且天然符合坑档 effect-confirmation 的「决定性时刻直查真值」。失败时 fail-closed 记 warning 即可（种子已确实回到 qB，字段下轮 sync 也能跟上，不改变跳检成败结论）。

6.2 改 给批量 pause/resume 补上真值（后端，按 action 分流归属）

目标：让 bulk_torrents 的 pause/resume 走回与单种完全相同的真值通路；下游 _truth_landed（:995 已按 action 分流）与 _affected_hashes（:1013-1017 已展开 keys）无需改动。

关键：不能把 bulk_torrents 从 DEFERRED_RECEIPT_COMMANDS 整条删掉 —— 那会害了同 handler 的 recheck / skip_check / add_torrents（它们的聚合回执必须自写，且本次症状的起点正是 skip_check）。要做的是按 action 分流归属，共四处落点：

#位置改动
1webui/commands.py抽单点 _is_deferred_receipt(cmd, args)：cmd == "bulk_torrents" and args.get("action") in ("pause", "resume") → 返回 False（放行到 drain 的 defer_receipt）；其余照旧按 DEFERRED_RECEIPT_COMMANDS 判。
2webui/runtime.py:453deferred = _is_deferred_receipt(cmd, args) —— 让 drain 用同一个判定（判定与消费同源，避免两处各写一份）。
3webui/commands.py:931-946pause/resume 的成功分支不再自写 _set_web_result(cmd_id, "ok")，回执交给 drain 的 defer_receipt（否则双写）；错误分支（部分 hash 缺失）照旧自写。
4webui/runtime.py:463defer_receipt 前加守卫 cmd_id not in self.results —— 否则 pause/resume 遇「部分 hash 缺失」时，handler 已写的 error 会被 drain 的 ok 覆盖。

为什么不走「handler 内自调 self.web.defer_receipt」：handler 侧拿不到 drain 拆出的 timing（wait_ms/exec_ms），自调会把埋点丢掉；把判定放回 drain，回执 / 计时 / 真值登记三件事仍归同一个单点。

范围：严格对齐乐观白名单 {pause, resume}；其它批量动作（跳检 / 限速 / 移动 / 标签）不做乐观，不需要真值出口。bulk_torrents 本就在 RESYNC_COMMANDS（commands.py:130），补刷新照旧触发，无需改动。

6.3 改 前端：回滚不许打回旧值 + 收敛判据与服务端同谓词（前端）

位置：static/shared/commands.js。两条小改，独立成立：

  1. 回滚前先看服务端（_expirePending，:275-288）：若 truthSnapshot 里该 hash 的 kind 已不是 op.prev.kind，说明服务端早已翻篇 —— 此时rollback 应恢复服务端现值（或无操作、直接删 pendingOps 让行落回服务端值），而不是把 op.prev 写回行上。
  2. 让 prev 保鲜（可选但更彻底）：每轮 _snapshotTruth 之后，用快照值刷新仍 pending 的 op.prev（它就代表「最后已知服务端真值」），语义与 onTruthEvent 里 op.prev = {...op.prev, kind: t.kind} 完全一致 —— 把批量路径缺的那一环在前端本地补上。
  3. 收敛判据放宽（_optimisticSettled，:385-392）：把「服务端 kind === 补丁 kind」改成「服务端已离开命令前状态」（resume: ≠ paused；pause: == paused），与服务端 _truth_landed 同谓词，两端不再各说各话。

6.4 加固 单点收紧与守阵补齐

  • QbApi._sync_paused_state（qbapi.py:96-119）：完成位判据联合 progress >= 1.0 / amount_left == 0，别让一份陈旧快照把「已完成」写成 stalledDL。
  • tests/helpers.py::FakeClient.torrents_add：is_skip_checking=True 时按真实语义造成「已完成」（progress=1.0 / amount_left=0），让 4.1 那条脱节在单测里可被断言。
  • 新增两条机械守卫：① 按前端乐观白名单遍历，断言对应的批量/单发命令都能登记真值（防「白名单加了新动作、真值出口没跟上」）；② 断言渲染前行的 kind 不可能停留在「服务端已离开的状态」（即 §6.3-1 的回归用例）。
  • 文档口径：把「批量命令自写回执 ⇒ 无真值事件」这条隐含前提写进 conventions/webui-*.md 或坑档（现在只散落在 commands.py 两处注释里，读代码不看注释极易再踩）。

7验证方法与待真机确认项

7.1 复现 & 验证（真机）

  1. 造一批「暂停未完成」的辅种（0%），多选 → 批量跳检 → 等 toast 出现后立即点「批量开始」；观察行状态是否出现「下载 → 暂停」而 qB 已做种。
  2. 抓后端日志三处：WEB UI | 批量 skip_check/跳检完成（跳检收尾）· [cmd] bulk_torrents: 排队 Xms / 执行 Yms（补刷新耗时）· 若出现 [cmd] 真值超时(>8000ms)未落地, 放弃推送，说明走到的是单发路径（批量路径按现设计不会有这一行 —— 这本身就是 §4.3 的旁证）。
  3. 窗口期直接读写两侧对照：接口 GET /api/torrents/{hash}（我们快照）vs qB /api/v2/torrents/info?hashes=…（真值），对齐 §3.1 的那张表。
  4. 前端侧：浏览器控制台在行状态不动的 8 秒里看 [perf] 命令 … 那行、以及 pendingOps/truthSnapshot 是否如 §4.3 描述（pendingOps 非空且 truthSnapshot.kind=seeding）。
  5. 止血验证：对同样操作改用单选一个组的「开始」——应观察不到该失配（因为它有真值事件），可反向确认根因定位。

7.2 待真机确认（本报告未能证实，按假设处理）

H1 · 增量同步同轮同时上报「删除 + 重加」的隐患
store._apply（store.py:251-259）在增量轮的执行序是「先把 patches 写进 by_hash，后对 torrents_removed 里的 hash 做 by_hash.pop」。若真机 qB 在跳检那一轮把同一 hash 同时列进 torrents（重加）和 torrents_removed（删除），记录会被 pop 掉 ⇒ 该行从视图消失（与本次症状不同，但同属「快照与 qB 脱节」家族）。需要真机抓一次 /sync/maindata 响应确认；若成立，修法是把 pop 收窄为「仅对本轮 patches 里没有的 hash 执行」。
H2 · 跳检重加后 qB 的即时状态串
qB/Web API 版本的差异会决定重加后是 stoppedUP 还是短暂 checkingUP/stalledUP（skip_checking 的 seed-mode 语义）。本报告按「完成 + 停止」建模（与 qB 选项文案一致）；若真机是别的组合，§3 链路里 kind 的取值会变，但失配的机制与 4.1~4.4 的定责不变。
