Feasibility Report

HR 取数通道「去端口配置 + 后端主动注册」可行性分析

用户提案: 扩展侧是被动连接, 能否去掉后端端口配置、改为随机端口, 由后端主动联系扩展完成注册, 甚至扩展也不需要固定端口、由后端主动探测。本报告只做可行性与路线判断, 不含实施设计; 事实取证截至 de83fbe8。

01 / 结论速览

字面方案不可行, 底层目标可以达成

提案包含三个诉求, 可行性各不相同。核心事实: Chrome 扩展没有监听端口的 API, 后端永远无法向扩展主动建链或「探测」扩展 —— 连接只能由扩展侧发起。因此「后端主动探测扩展」在纯扩展形态下不可行; 但「用户零配置 + 后端主动派发」在 native messaging(原生消息) 形态下可以完整达成。

诉求结论达成形态
去掉后端端口配置, 改为随机端口 可行 端口传 0 由 OS 分配; 寻址改由「发现端口」或「命名管道」补上, 用户不再接触端口。
后端主动联系扩展注册 部分可行 HTTP 路线做不到(扩展不能被连); native messaging 路线在通道接通后可由后端主动推送任务、主动维护注册态。
扩展也不需要固定端口, 由后端主动探测 字面不可行 扩展无监听套接字, 无可探测。两端皆无端口的形态只有 native messaging: 桥进程由浏览器拉起, 与后端走命名管道, 全程零端口。
顺带收益 附带成立 「同机多实例端口必须各不相同、被占即启动报错」这条约束随随机端口/管道命名一起消失。
推荐: 以路线 A(发现端口 + 临时数据端口 + token 自动分发)先落地 —— 用户侧配置归零、改动面最小、安全模型与现状对齐; 若同时想消灭轮询时延、让后端真正主动派发, 再评估路线 B(native messaging 桥 + 命名管道)。两条路线都保留旧式固定端口配置作为兼容回退, 不搞断崖式切换。
02 / 现状事实

当前连接模型与用户配置面

先校正一处表述: 现状并非「扩展被动连接」——连接由扩展主动发起(MV3 service worker 每 60 秒轮询一次), 后端是被动监听方; 「被动」的是任务流(扩展只在后端派发了任务时才动作)。用户诉求的实质是把用户侧那两道手工配置(端口 + token)消掉, 并让后端能主动找到扩展。

2.1 拓扑与协议(代码事实)

项事实
端点hr/server.py 的 HrChannelServer: 标准库 ThreadingHTTPServer 绑 127.0.0.1:<port>; allow_reuse_address=False(Windows 上抢绑检测, 端口被占 ⇒ 启动 fail-fast)
四个 APIGET /api/hr/tasks(拉任务清单) · POST /api/hr/result(回传) · GET /api/hr/sites(选项页授权清单) · POST /api/hr/refresh(立即拉取)
鉴权X-Hr-Token 常数时间比较(token 留空则自动生成并持久化到 <data_dir>/hr.token, 0600); Origin 白名单只放行 chrome-extension://(配了 channel.extension_id 则钉死单个 id, 属第二道防线)
其它边界UrlPolicy 在下发时卡死域名+路径(SSRF); 单请求体上限 12MiB; 无 Origin 放行(真鉴权是 token)
取数模型取数线程把任务入队后阻塞等待回传(上限 request_timeout, 默认 180s); 扩展 60s 内轮询取走。硬约束: 轮询周期必须小于 request_timeout(v2.6 前 5 分钟轮询导致约四成任务直接超时, 2026-09-25 实报后定为 1 分钟)
多实例同机多实例必须各配不同 hr_check.channel.port(被占即启动报错); 扩展选项页持实例列表, 逐实例各配一份端点+token

2.2 用户侧配置面(即要被消掉的「一道配置」)

  1. 从后端启动日志抄端口(HR 取数通道端点已启动: http://127.0.0.1:<端口>);
  2. 打开 <data_dir>/hr.token 复制密钥;
  3. 在扩展选项页「① 连接本机端点」填 127.0.0.1:<端口> + token, 点「存入实例列表」——多实例重复三遍。

此外站点授权(选项页 ②)是从后端 /api/hr/sites 自动拉的, 已属零配置, 不在本次范围。

2.3 可复用的既有资产

  • SSE 推送先例: WebUI 已有 GET /api/events(FastAPI/Starlette 原生), 证明「后端推送」在本仓有成熟形态; 但 HR 端点是标准库 http.server, 不共享该设施。
  • 手写 WebSocket 先例: scripts/hr_fetch_experiment.py(CDP 实验)有零依赖的手写帧/mask/ping-pong 客户端。
  • CDP 路线已否决(2026-09-23~24): 后端驱动专用浏览器 profile 抓 cookie 的方案因「专用 profile 没有用户日常登录态」被否, 才选了扩展路线 —— 本次任何方案都不得退回该形态。
  • 扩展 manifest 已放行任意回环端口: host_permissions 含 http://127.0.0.1/*, 探测任意端口无需改 manifest。
03 / 技术边界

为什么「后端主动探测扩展」字面不可行

事实 1: Chrome 扩展(MV3)没有监听 TCP 端口的 API。历史上 chrome.sockets.tcpServer 属于已废弃的 Chrome Apps 平台, MV3 扩展只能当客户端。扩展没有「端口」可被固定, 也没有「端口」可被探测。
事实 2: 因此后端永远无法向扩展主动建链。后端 → 扩展只有一条路: 在扩展先拨号打开的通道上推送。可选通道仅三种: native messaging(stdio, 由浏览器拉起宿主)、WebSocket、SSE。
事实 3: native messaging 的宿主进程只能由浏览器启动并走 stdio, 后端也不能反向连浏览器。即便路线 B, 「后端主动」的准确含义也是: 传输层首次接通由扩展侧触发(浏览器启动时一次), 此后后端随时可主动推送, 无需轮询。

推论: 提案第三句(后端主动探测扩展)不可行; 第二句(后端主动联系扩展注册)只有路线 B 能达成其精神; 第一句(去端口、随机化)两条路线都能达成, 且都必须补一个寻址机制来替代「用户抄端口」——要么是固定但免配置的发现端口(路线 A), 要么是命名管道(路线 B)。

04 / 路线 A

发现端口 + 临时数据端口 + token 自动分发(推荐先行)

保留现有轮询模型与全部安全边界, 只把「寻址」从用户手工搬运改为扩展自动发现。用户侧配置归零, 选项页降级为高级/手动模式。

4.1 后端设计

  • 数据端口随机化: hr_check.channel.port 语义改为 0(默认)= 交 OS 分配; 显式非零值 = 旧式固定端口(完全兼容现有安装)。
  • 发现端点: 新增 GET /api/hr/discover, 监听在一个固定但永不需要用户配置的发现端口(建议默认 18788, 冷门口径; 可被配置覆盖)。免 token(它本身就是发 token 的), 靠 Origin 钉死(chrome-extension://<extension_id>)鉴权——与现状第二道防线同一机制; 普通网页 JS 打进来只有 403。
  • 多实例聚合: 每个 daemon 启动时把 {id, name, endpoint, token, 心跳时间戳} 写进本机注册表文件(建议 %LOCALAPPDATA%\auto-qb-hr\instances.json, 文件锁 + 临时文件原子替换); 发现端口「先绑先得」的归属者每次请求时读注册表、按心跳 TTL 过滤后聚包返回。多实例不再需要端口互斥。
  • 启动日志照旧打印实际端点(随机端口), 供人核对; 另打一行发现端口。

4.2 扩展设计

  • 启动时 / 全部实例连不上时 / 每 N 分钟, 探测一次发现端口; 命中则把实例清单(含 token)落 chrome.storage.local, 后续轮询完全走现状逻辑。
  • 选项页: 「自动发现的实例」只读展示 + 「重新发现」按钮; 保留手动添加作为回退(发现失败 = 今天的体验, 不更差)。
  • 发现响应里带 poll_hint 与实例声明的 extension_id, 不一致时选项页亮警告(与现状 403 排障口径一致)。

4.3 安全论证与残留风险

现状信任根 = hr.token 文件(0600, 只有 daemon 能写)经用户手工粘贴进入扩展。路线 A 的信任根 = 发现端口归属 + Origin 钉死, 是一次可感知的削弱: 同机恶意进程可抢占发现端口、伪装 daemon 钓鱼扩展, 收割带登录态的页面/种子字节(扩展只校验「任务是后端派发的」这一形式, URL 白名单在真后端侧, 伪装者不在其约束内)。

  • 量级论证: 该威胁模型(同用户恶意进程)下现状也已失守——未打包扩展就是磁盘明文文件, 同用户进程可直接改 background.js; App-Bound Encryption 保护的 cookie 库不被直接读, 但改扩展文件等价。故增量风险小, 不建议为此付出结构性成本。
  • 可选硬化: 一次性配对码——daemon 在日志/WebUI 亮 6 位码, 用户选项页输入一次, 之后发现响应须带配对密钥的 HMAC 才被采信。一步手工换回完整信任根, 按需开启(保守默认关)。
  • 可用性风险: 发现端口被普通应用误占 ⇒ 扩展发现失败, 退手动配置(不静默、有日志)。注册表文件按项目既有口径不得放云同步盘。
改动面: 后端 hr/server.py(发现端点 + port 0) · hr/runtime.py(注册表写入) · config/schema/hr.py + validate_config(port 语义) · WebUI 设置页(端口项渲染「自动/固定」) · 扩展 background.js(发现探测) · options.js(实例展示) · 测试面 tests/test_extension_proxy.py 与端点单测。轮询语义、任务协议、安全边界全部不变。
05 / 路线 B

native messaging 桥 + 命名管道(完整形态, 零端口)

唯一能同时兑现「零端口 + 后端主动派发」的路线。扩展不再轮询, 后端不再有 TCP 监听面。

5.1 构成

  • 扩展侧: 用一个离屏文档(offscreen document)持有 chrome.runtime.connectNative 长连接(MV3 service worker 随时被回收, 长连接必须挂在离屏文档上; 该 API 自 Chrome 116 起可用, 与 manifest 的 minimum_chrome_version 一致); service worker 只做消息路由。协议 = Chrome 原生消息格式(4 字节长度前缀 + UTF-8 JSON 行), 任务/结果契约与现状 JSON 完全一致, 零协议迁移成本。
  • 桥进程: 由浏览器按 native messaging 清单拉起(stdio), 只做「stdio ⇄ 命名管道」透传, 不解析业务; 连接目标 = \\.\pipe\auto-qb-hr-<实例标识>(Windows; 类 Unix 用 unix socket)。可用标准库 ctypes 实现, 不必引入新依赖。
  • 后端侧: 以命名管道服务器替代 ThreadingHTTPServer; 管道名含实例标识(由 data_dir派生), 多实例天然互斥, 无端口概念; 桥一连上即完成注册, 之后后端随时主动推送任务, 轮询、request_timeout、「轮询周期 < 超时窗」这条硬约束一并消失, 任务时延从「最多 60s」降到亚秒级。
  • 信任链: native messaging 清单的 allowed_origins 钉死扩展 id(浏览器强制执行) + 命名管道 ACL(仅限本用户会话) + 管道上仍校验 hr.token。不比现状弱, 且没有可抢占的「发现端口」。

5.2 成本(这是它最大的问题)

  • 一次性主机注册: 每个浏览器要写自己的注册表项(Chrome: HKCU\Software\Google\Chrome\NativeMessagingHosts\…; Edge 另一键)。可做成 auto-qb --install-native-host 一键脚本(顺带按本机探测到的 chrome/edge 分别注册), 但这是新增的一个安装步骤, 与「减少配置」的初衷部分相悖——只是从「每次改端口都手工搬」变成「一次性装桥」。
  • 新组件: 桥进程的构建/分发/路径漂移(venv 迁移后清单里的绝对路径失效, 需重跑注册); 桥成为新的本地进程面(须最小化: 只透传)。
  • 扩展传输层重写: 轮询、实例列表、自测连通、降噪逻辑全部改写; 旧后端(无管道)时期降级 = 现状手动流程。
  • 仅覆盖 Chromium 系桌面浏览器(与现状扩展的 Chrome/Edge 定位一致, 不算新增损失)。
06 / 路线 C 与已否决项

中间态与被淘汰的思路

6.1 路线 C: 发现 + WebSocket 推送(中间态)

用路线 A 的发现机制寻址, 之后扩展开 WebSocket 长连接, 后端主动推送。可获得「亚秒级派发」而不引入 native messaging; 但要在标准库 http.server 上手写 WebSocket 服务端(帧/mask/ping-pong/分片, 仓内只有客户端先例), 或引入 websockets 新依赖(本仓此前刻意回避)。工作量大于 A、小于 B; 只有「不想上 native messaging、又想要推送」时才值得考虑。不推荐 SSE: EventSource 不能带自定义头, token 只能进 query string, 会泄进访问日志。

6.2 已评估并否决

思路否决理由
全端口段扫描(6.5 万端口)随机端口落在临时段(~2.8 万个), 扩展侧扫描量不可接受; 且扫描与真实使用之间存在端口复用竞态, 误连普通应用
注册小端口块(如 100 个)让扩展扫块比全段扫描可行, 但块大小 × 扫描成本 × 竞态窗口三者拉扯; 仍保留 polling 与 token 搬运问题, 不如发现端口干净
mDNS / Bonjour 广播Chrome 扩展无 ServiceDiscovery API, 扩展侧无法参与
chrome.storage.managed 经策略注入需管理员级 GPO 部署 StorageManagedSchema, 家用场景过重; 且 daemon 以普通用户运行, 写不了 HKLM
扩展直读 file:// 端点文件需用户手动开「允许访问文件网址」开关; data_dir 路径对扩展不可知; MV3 SW 对 file:// 支持不稳
后端 CDP 驱动浏览器2026-09-24 已否决: 专用 profile 无用户日常登录态, Chrome 136+ 禁默认目录调试端口

08 / 兼容与迁移

不做断崖式切换

  • 旧扩展 + 新后端(路线 A/B): port 显式配置即完全旧行为; 选项页手动加实例照旧可用。存量安装零感知。
  • 新扩展 + 旧后端: 发现无果(旧后端无发现端点) ⇒ 退手动配置, 即今天的流程; 日志给一句「未发现本机实例, 请手动配置」。
  • 配置语义: hr_check.channel.port 默认 0(自动); validate_config 与 schema 同步放开 0 值; WebUI 设置页端口项渲染为「自动(推荐)/ 固定端口(高级)」。
  • token 口径不变: 仍自动生成到 <data_dir>/hr.token(0600); 路线 A 由发现响应携带, 路线 B 在管道握手时校验——文件始终是信任锚, 人也能打开核对。
  • 文档同步: extensions/hr-fetch-proxy/README.md 的配置章节、docs/

10 / 待拍板事项

实施前需要用户决策的问题

  1. 路线选择: A(零配置, 保留轮询) / B(零端口+主动派发, 多一次性安装) / C(中间态)?
  2. 发现端口默认值(仅路线 A/C): 建议 18788(现产端口转正为发现端口, 数据端口让位给随机); 是否认可?
  3. 配对码硬化(路线 A): 接受文档化残留风险(推荐, 威胁模型增量小), 还是要一次性配对码?
  4. 多实例注册表落点(路线 A): %LOCALAPPDATA%\auto-qb-hr\(单用户场景)是否覆盖你的实际部署(所有实例同用户运行)?
