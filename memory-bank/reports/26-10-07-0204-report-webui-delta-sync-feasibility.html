01任务与判定速览

输入材料: 复验报告 26-10-07-0054(两条 perf issue 重构后仍成立)与两条 issue 原文(26-09-19-2122 节拍门控双生产者 / 26-09-21-1408 四视图全量重建)。本轮为只读取证 + 可行性分析, 不改代码、不出实施计划(计划另走 plans/)。代码事实全部在本会话逐文件核对(2026-10-07 @ b736f1a3), 在账数字标注原取证时间。

判定: 可行, 且地基比预期厚 —— ①当前 /api/state 已经是 qB rid 语义的「跳过」半套(版本一致零回传, runtime.py:811-840), 缺的只是「变化时回增量」半套; ②auto-qb 的摄入侧(qB → store)今天就在跑同款协议的客户端(store.apply_sync, store.py:112-158, 含 full_update 兜底 / rid 失效归零 / 逐种子变化字段集), 协议形态在仓内有已验证先例; ③每 1.5s 一轮的逐种子变化字段集(delta_fields, store.py:259)已经算出来了, 只是进视图层时被塌缩成一个布尔(consume_view_changed, store.py:266-270)后丢弃。主要工程量与主要风险都集中在同一处: 服务端增量聚合的正确性(恰是 issue 2 根因栏挂着的「dirty 集合 × 剧键派生」待查)。
问题一句话答案
能不能做?能。协议、降级路径、单写线程约束都有现成落位; 无架构性障碍。
收益多大?集中在「大库 + 有活跃子集」: 传输与前端每轮成本从 O(全库) 降到 O(脏行); 静态库收益趋零(现在的 rid 跳过已覆盖)。服务端重建成本同比例受益(若配套增量重建)。
成本多大?中型工程: 服务端时间线 + 增量聚合 + 前端合并。正确性论证与测试是主体, 传输协议本身很薄。
和 issue 1/2 什么关系?增量传输是 issue 2「增量聚合」的传输侧配套, 两者共享同一套脏集合推导; 与 issue 1 的方案 A/B/C 正交可叠加, 且不受方案 A「SSE 下收益蒸发」结论影响(它降的是每轮成本, 不是轮数)。

03qB rid 语义与一个关键事实

qB 的 /api/v2/sync/maindata 做了什么

  • 客户端持 rid(单调递增代次)轮询; 服务端 full_update=true 表示「你落后到只能拿全量」(首轮 / rid 失效); 否则返回增量: 只含变化种子的变化字段字典 + torrents_removed 删除清单。
  • 服务端维护「代次 → 该代内哪些种子哪些字段变了」的时间线(键集合, 不存值快照 —— 值在回增量时从当前状态现取); 客户端 rid 落在时间窗之外就重给全量。
  • 客户端按 hash 把增量逐字段合并进持久化的行对象, 删除行走 removed 清单。

关键事实: 摄入侧已经有一个该协议的完整客户端

TorrentStore.apply_sync(store.py:112-158)每 1.5s 就是按这套语义消费 qB: rid 传递、full_update 检测、降级兜底(端点不可用回退全量 torrents_info)、未知异常 rid 归零强制全量、torrents_removed 对齐删除。更关键的是 _apply(store.py:185-264)在增量轮里已经逐种子算出了变化字段集:

delta_fields: Dict[str, FrozenSet[str]]   # {hash: 本轮变化的字段集}   (store.py:205, 259)
added / changes                            # 新增/删除 hash 清单        (store.py:202-203, 261)
state_changed / field_changed              # 状态变化 / 监听字段变化    (store.py:206-207, 260)

这些信息支撑了规则引擎、冲突检测(dirty_groups, store.py:229-232)、外部变化登记等下游; 但流到 Web 视图层时, flush_views 只调 consume_view_changed() 读一个全局布尔(store.py:266-270) —— 「哪些种子、哪些字段变了」在视图层门口被扔掉了。这正是 qB rid 式方案在 auto-qb 的落点: 把这份已在生产的信息接住, 而不是从零造增量机制。

仓内另有两个增量读端点的先例: 错误历史 err_log_since(seq)(runtime.py:243-251, 游标式增量拉取)与搜索索引的增量维护(runtime 按 hash 建增量、限流续建)。前端对增量语义并不陌生(rid、seq 都在用)。

04方案映射: /api/state 升级成 maindata 语义

保持端点 URL 与「status 恒回传」口径不变, 把「未命中 → 全量数组」扩成「未命中 → 时间窗内回增量, 窗外回全量」:

GET /api/state?rid=4183&view=group
→ {
    "rid": 4187, "updated": true,
    "status": {…与今日完全一致: connected/paused/traffic/server/totals…},
    "full": true,                        // rid 失效/重启/全局置脏源触发 → 与今日同形的全量
    "groups": [ …全量数组… ], "singles": [ … ]
  }
  // 或 rid 在时间窗内:
  → {
    "rid": 4187, "updated": true, "full": false,
    "status": {…},
    "delta": {
      "groups":  {"upsert": [<脏组整行, 服务端重聚合后>], "removed": ["<组key>"]},
      "singles": {"upsert": [<脏成员行>], "removed": ["<hash>"]},
      "torrents": {"upsert": […], "removed": […]},   // 只在 view=torrent / 无 view 时回
      "shows":   {"upsert": [<剧级 patch>], "removed": ["<剧key>"]}
    }
  }

服务端新增件(全部收在 WebUIRuntime, 单写线程不破)

  • 脏行推导: flush_views 在消费 consume_view_changed 的同一拍, 从 store 排空 delta_fields + added/removed, 映射到各视图的行键 —— flat/singles 行 = hash 本身; 组行 = member_to_key(store 现成映射, store.py:208); 剧行 = parse_release(rec.name)(该推导本来就是增量聚合要付的成本, 见 §08 S3)。推导全程主循环线程、_publish_locked 同一 view_lock 临界区 —— 黄金法则 5(单一写线程)与「四视图同轮发布」硬约束(runtime.py 模块 docstring)原样保持。
  • 增量时间线: deque(maxlen≈40)(≈60s 的 tick 量), 每代存「视图 → 行键 upsert/removed 集合」—— 只存键不存值(qB 同款): 回增量时从当前已发布视图现取行内容, 时间线内存 O(代数 × 脏行键数), 与库大小无关。
  • 降级阶梯(与 qB full_update 同构): 触发任一「无法归约为行级脏」的源 → 本代标记 full, 客户端重置本地状态整体替换。这类源今天就有明确清单: HR 判定 revision 变化(runtime.py:500-502)、配置热重载(webui/module.py:60-63 显式 mark_dirty)、shows_pending 文件兑底归位(runtime.py:842-844)、跨组交叉标记增删(views.py:489-493, 可精确到组键)、进程重启(版本号播种重启不回落, runtime.py:137-138)。
  • 缓存兼容: 时间线只存键意味着「值从当前视图现取」, 客户端拿到的永远是最新值 —— 中间代次被跳过(慢消费/多客户端不同 rid)也不会吃到中间态, 语义与 qB 一致。

前端新增件

  • 合并: refresh() 对 delta 分支按 key/hash 做「按行替换 + removed 删除」; 四个数组本身仍是整体引用替换(Vue 层数据流不变), 但未脏行的对象引用原样保留 —— 这是增量重建的天然副产品(§05④)。
  • 装饰记忆化: decoratedGroups(decorate.js:115)加一层按行对象身份的 WeakMap 缓存 —— 引用没变的行直接复用已装饰结果, 重算面 = 脏行。乐观值补丁(reapplyPending)、多选交集修正、memberByHash 都已按 hash/key 键控(polling.js:169-182, decorate.js:148-154), 与增量天然兼容, 零改动。
  • 切视图强制全量、SSE 断线退轮询兜底、失败退避 —— 语义全部不变(协议升级对「兜底路径」是透明的: 轮询同一端点, rid 窗内拿增量, 窗外拿全量)。
一个必须当面说的粒度事实: 组行内嵌完整成员数组(members: members_view, views.py:494-495; 6.3 MiB 的主体就是它) —— 任意一个成员的速度抖动都会脏整条组行(含全部成员)。组视图的增量粒度天然是「组行」而非「成员」; 追剧视图已是 hash 引用式(members 只放 hash, views.py:645-647)不受此限。要不要把组行也改成 hash 引用式(成员数据由前端从 torrents 平铺数组解析)是响应体契约的二次演进, 单列为拍板点 D2(§08), 不阻塞一期。

05收益分析(分层 + 工作负载相关性)

先立诚实前提: 以下「增量后的数字」均为按在账成本口径的结构性推演, 非实测; 在账数字仅 ①-⑤ 各段现状。收益与工作负载强相关, 分两种典型库讨论。

段现状(活跃库)增量后受益条件
① 服务端重建 每版 O(全库): 全库 by_hash 遍历 + 逐种子 parse_release + 三层聚合(~50.8ms@3000, 40 版/60s) 每版 O(脏行): 只重聚合脏组/剧的成员(成员数远小于全库) 需配套增量重建(§08 S2/S3); 只做传输(S1)则此段不变
③ 传输+序列化 每版当前视图全量数组(≈1/4 × 6.3 MiB; json.dumps 26.4ms; 63ms 序列化+网络+解析@3000) O(脏行): 脏组行/成员行 + status。传输量 ≈ (脏行数/全库行数) × 现量 活跃库: 脏行 ≈ 传输中的种子数(速度/进度每拍变); 5000 种子库 100 个活跃 ⇒ 约 2% 现量
④+⑤ 前端 每版全量赋值 + decoratedGroups 全量重算 + 全行 vdom diff(396~501ms@5000, 10-17% 主线程) O(脏行): 只有脏行进 vdom diff(keyed), 装饰复用未脏行 依赖服务端保留未脏行对象引用(增量重建天然满足; S1 期可用「全量重建但按 hash 摘行」近似, 引用稳定性弱一档)

工作负载相关性(收益的边界)

  • 静态做种库(辅种场景的常态): 现方案 rid 命中零回传, 每轮成本已趋零 → 增量方案在这里几乎不增加任何收益。这不是浪费 —— 它只是不动这块。
  • 活跃传输库: 下载/上传中的种子每拍速度必变(dlspeed/upspeed 不在量化表内), 每版都全量 → 增量后每轮只传/只算/只渲染活跃子集。这是收益主体。
  • 命令突发: 批量改标签/分类/限速会瞬时置脏大面, 增量把「一次突发 = 一批脏行」的传导成本从全库压到突发面 —— 用户可感知的「点了之后卡一下」的来源之一。
  • 轮数不变: SSE ver 每版必推、客户端每版必拉(复验报告 §04 的结论)在增量方案下原样成立 —— 它不减少轮次, 降的是每轮成本。40 版/60s 的节拍保留, 但每版从「全库一遍」变「脏行一遍」。

一个当前方案结构上拿不到的收益: 引用稳定

全量重建每版产生全新行对象, 前端即使内容没变也要付出: 全量赋值、decoratedGroups 全量 map、全部已渲染行的 vdom diff。增量重建天然保留未脏行引用, 上面三笔按「脏行占比」等比例消失 —— 这是「全量重建 + 前端记忆化」组合做不到的(引用每版全换, 记忆化必失效)。

收益不覆盖的面(说清楚它不是什么)

  • 不改善 qB → auto-qb 摄入(那条链已是增量); 不影响 /api/torrents/{hash} 详情、流量图、错误历史等端点; 不减少每轮请求数(仍 1 条/轮)。
  • issue 1 的「每版必须建一次」下界(复验报告 §04③)原样成立 —— 增量方案是对该下界降价, 不是取消。

件量级说明

正确性边界清单(issue 2 待查的细化 —— 本轮只列论证项, 不下结论)

  • 成员迁移: name/save_path 变化会移动成员的剧键/组键 —— 必须从旧键行移除、进新键行; store 有组侧 member_to_key 现映射, 剧侧需要等价的「上一版键」记忆或从旧快照反查。
  • 季级聚合: gaps(缺集)与整包覆盖标记是季级派生(views.py:741-752) —— 任一集变化, 该 (剧, 季) 的 covered 集与 gaps 要整季重算(集行本身便宜, 可接受)。
  • 剧名频次: 展示名 = titles 频次最大(views.py:705-708) —— 同剧任一成员标题变化影响剧名, 需重扫该剧成员的标题(局部)。
  • 状态归并: 集行 state = 成员 kinds 按 rank 取 min —— 集行重算本来就局部, 无跨行传播。
  • HR 派生字段: hr revision 变化使全库 HR 展示字段可能变化(hr_view_fields 读判定视图) —— 无法归约成行级脏, 走 full 降级(波次频率低, 可接受; 这正是「降级阶梯」存在的理由)。

风险与对策

风险对策
增量链路出「拼不全/拼错行」的陈旧视图缺陷(2026-09-18 四视图漏建事故同型)镜子测试兜底: 任意操作序列下「从 rid0 逐轮吃 delta 合并」≡「每轮全量快照」—— store.apply_sync 的测试范式(tests 里 FakeTorrent 增量序列)直接镜像; 不变量不成立即红。另保留 full 语义为默认回退(开关或异常路径), 可随时退回现行为。

多客户端/慢客户端语义时间线服务所有客户端独立 rid; 窗外一律 full —— qB 已验证的同构语义, 无需自创。
与门控(pending_ver)的相互作用一期保留门控不动(行为保守); 增量下「未被消费的版本」成本变成一次便宜的键集追加, 门控的剩余价值与去留在 S4 单独裁决(拍板点 D3)。
JSONResponse 契约(delta 载荷必须 JSON 原生类型, state.py:84-86 fail-fast 注释)行内容直接取自现有视图 dict(已是 JSON 原生), 无新增类型面。
复杂度税: 全仓多了一条「键集时间线」状态收在 WebUIRuntime 单点(与 pending_ver/search_index/err_ring 并列), 文档进 web-runtime.md; 这是本方案最大的隐性成本, 列入 D4 让用户权衡。

若立项, 按依赖与收益密度分四步, 每步独立交付、可回退(full 语义全程保留为回退路径):

步内容交付即可兑现的收益依赖

S2 组/单种子增量重聚合(按脏组键局部重跑, 保留未脏行引用) 服务端重建降 O(脏行); 前端引用稳定兑现 S1 的时间线与协议
S3 追剧增量重聚合 issue 2 的最大单点(_build_shows_view 全库 parse_release)落地 S2; 并需先完成 §06 正确性边界论证 —— 建议与 issue 2 认领并轨做, 一份论证喂两处

  • D1 协议形状: 推荐「同一端点加 delta/full 字段」(前端单请求轮询契约不变); 备选「新端点 /api/state/delta」(老客户端零感知, 但前端要双请求切换)。
  • D2 组行成员粒度: 一期接受「组行级增量」(内嵌成员随组行整行走); 是否演进成 hash 引用式(响应体契约二次变更, 波及筛选器/列模型数据源)单独立项评估。
  • D3 门控去留: 增量下 pending_ver 的保护对象从「重建成本」缩水成「键集追加成本」, 建议一期不动、S4 裁决。
  • D4 范围: 是否接受「时间线状态」进 WebUIRuntime 的复杂度税; 以及 S1 是否先只覆盖种子页(最小可见收益)。
  • D5 开关: delta 语义默认开(镜像测试过关后)还是配置开关灰度 —— 倾向默认开 + full 回退路径常在, 不新增配置键(黄金法则 4 口径: 若加开关必须进 validate_config 与 config/schema.py)。

09结论与建议

  1. 可行性: 成立。无架构障碍; 单写线程/四视图同轮/SSE 兜底三条硬约束都有干净落位; 仓内摄入侧(store.apply_sync)与两个增量读端点(err_log_since/搜索索引)构成完整先例组。
  2. 收益定位(诚实口径): 集中在「大库 + 活跃子集 + 命令突发」; 静态库已被现有 rid 跳过覆盖, 增量方案对其近乎零增量。四段成本(服务端重建/传输/前端赋值/渲染)中, 传输与前端两段只靠 S1 就兑现, 服务端两段依赖 S2/S3。
  3. 成本定位: 协议与时间线是薄件; 主体工程量与风险都在增量聚合正确性(§06 清单)与镜子测试 —— 而这恰好就是 issue 2 根因栏挂着的同一笔「待查」, 建议把本方案 S3 与 issue 2 的认领并轨, 一份正确性论证同时服务两处。
  4. 与既有方案的关系: 方案 B + 顺带小修 + 指纹注释修正(合计文档/一行级)独立且便宜, 不必等增量; 方案 A 在 SSE 世界性价比低(复验报告已裁定), 增量协议部分吸收其动机(让主循环的重建变便宜)而不需要动重建归属。
  5. 下一步: 本报告为证据快照, 不自动转实施。若决定立项: 从 S1 出实施计划(plans/, 带 §08 拍板点); 若暂不立项: issue 2 认领时把本报告 §06 的正确性边界清单作为其「增量聚合论证」的输入清单, 两份档案互为引用。
