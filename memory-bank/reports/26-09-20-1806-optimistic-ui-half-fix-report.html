乐观 UI 的「撤下」修复只覆盖了一半入口

上一笔 4df80dc 把「回执改到补刷新之后写、并带上真值」落到了 pause_torrent / resume_torrent / pause_group / resume_group 四条命令上。而 bulk_torrents 因为被列在 DEFERRED_RECEIPT_COMMANDS 里、回执由 handler 自己在补刷新之前立即写， 整条新链路被完整绕过 —— 它带的三类入口恰好是目标数最多的那三类：多选批量、整集、整剧。 更麻烦的是它连 wait_ms / exec_ms 都没有，导致 [perf] 一行都不打：这一半的问题在控制台里是静默的。

这条日志把结论改了 「一半」的分界不在端点，而在两个条件：
① 真值在 RECEIPT_WAIT_CAP_MS 内落地　② 落地后的真值符合该动作的撤下判据
两个条件任一不满足 ⇒ via=pull ⇒ 额外约 1.5 s 拉取，撤下推到约 3 s。
⚠ 一个我差点写错的推论（用户纠正后补测） 我一度据此推出「暂停已经好了、开始还没好」—— 理由是 pause 的预测值恒为 paused、qB 暂停又几乎立刻生效。这个推论只在仿真里成立，真机不成立：

上面那 1362 ms 大概率不是 resume 特有的，而是 qB 状态传播到 /sync/maindata 的固有延迟 （日志形态很典型：HTTP 立刻返回 200、执行 0.0 ms，但状态要过 6 轮才在同步里出现）。 这个延迟对 pause 一样存在 ⇒ 旧上限 1200 ms 对暂停同样不够用 ⇒ 暂停一样会踩到超时照发。

用 sim_qb 加 1.4 s 传播延迟补测（修复后的代码）：
操作行的状态时间线[perf]
暂停1ms s-seeding → 9ms s-paused+灰 → 1956ms s-paused未打印（轮询早于回执到达）

两者都不再弹回，但耗时被 qB 的传播延迟（1.4 s）钉住 —— 这部分不是我们代码能省的。 所以真机上「暂停 / 开始都要 1.5~2 s」是预期内的，而您报的 2~4 s 应该是 「传播延迟 + 旧上限不够导致的额外拉取 + 兜底回滚」三层叠出来的。

01 · 结论

「一半」的边界画在 bulk_torrents 上

乐观 UI 有两条撤下路径：① 回执自带真值 → 前端就地撤下（via=truth，与库大小解耦）； ② 回执没真值 → 前端退回 _pullTruthAfterCmd() 反复拉全量 /api/state 等真值落地 （via=pull，代价随库大小线性上升）。修复把六类用户入口里的三类搬到了 ①， 另外三类仍留在 ②。

端点修好的一半 · 回执带真值

  • 辅种页 · 整组右键 暂停 / 开始
  • 种子行右键 暂停 / 开始
  • 详情抽屉 头部动作（复用单种子链路）
  • 共 4 条后端命令：pause/resume_torrent、pause/resume_group
  • ⚠ 只是端点修好 —— 观感还要看 §00 的两个条件

没修的一半 · 恒为 via=pull

  • 多选 · 批量按钮 暂停 / 开始
  • 追剧页 · 整集右键 暂停 / 开始
  • 追剧页 · 整剧右键 暂停 / 开始
  • 共 1 条后端命令：bulk_torrents（整剧动辄上百个目标）
  • 回执连 truth 都没有，无条件退化到拉取路径

按端点划分只是第一层。还有一条贯穿两层的判据（§00）：真值是否 ① 在 1200 ms 内落地 且 ② 等于预测值。两个条件任一不满足，哪怕是修好的端点也会 退化为 via=pull。真机实测 resume 两个都不满足 ⇒ 撤下 3026 ms。

判定依据一行代码 —— DEFERRED_RECEIPT_COMMANDS 与 RESYNC_COMMANDS 的交集里， 只有 bulk_torrents 与 add_torrents 既「改种子状态」又「回执由 handler 自己写」， 因此永远进不了 defer_receipt()。

                                       "bulk_torrents", "add_torrents"})

// src/auto_qb/web_runtime.py:163-171  —— 进不了这个分支就永远没有 truth
if cmd_id and not deferred:
    if cmd in RESYNC_COMMANDS:
        self.defer_receipt(cmd_id, cmd, args, timing)   # ← bulk 走不到这里
    else:
        self.set_result(cmd_id, "ok", timing=timing)

06 · 证据四

为什么本地 1058 单测 + 54 项冒烟全绿也测不到

两道防线都绕开了这条链路，所以这个缺口不是「没测出」，而是「压根没被测到」。

07 · 次级发现

三个连带问题

  1. 批量操作的遥测是静默的 _markCmdSettle() 在 cmdStats.totalMs == null 时直接 return， 而 bulk 回执不带 wait_ms ⇒ totalMs 恒为 null ⇒ 一行 [perf] 都不打。 浏览器实测已证实。这意味着「批量操作慢」既修不了也报不出来 —— 与当初 issue 26-09-19-1939 的教训（埋点没有消费者就是死字段）是同一类问题，只是这次连埋点都没写进去。
  2. 回执仍在补刷新之前写 _cmd_bulk_torrents() 在 fn(self.api, known, delete_files) 之后立刻 _set_web_result(cmd_id, "ok")，而补刷新（P0-5）要等本轮主循环稍后才跑。 前端拿到回执后第一次 refresh() 必然扑空，只能靠 200/400 ms 退避重试。 这正是 4df80dc 在单种子/整组上修掉的那个时序，bulk 上原封不动。
  3. 有弹回风险：1500 ms 预算 + 3 s 兜底回滚 _pullTruthAfterCmd() 预算 1500 ms，退避 0 → 200 → 400 ms。大库单轮 /api/state 实测 143 ms（1000 种子）/ 353 ms（3000）/ ~550 ms（5000）—— 按这个节奏，3000 种子库的预算只够跑满 2 轮（见表 5 推算）。 若真值在这个预算内没对上，pendingOps 会一直挂到 _expirePending() 的 3 s 兜底，而兜底是回滚到 op.prev（操作前的值）。 用户看到的就是「点了开始 → 乐观下载 → 3 秒后弹回已暂停 → 下一轮才变回来」， 与当初 4df80dc 要修的弹回是同一个观感，只是成因不同（这次不是采纳旧真值，是兜底回滚）。
  4. 预测值只有 2 种，落地态有 6 种 —— 「开始」的弹回机制还在 这条与 bulk 缺口互相独立，且对所有页（含种子页右键）都生效。 _optimisticPatch("resume") 只能猜两种： progress ≥ 1 ? seeding : downloading。而服务端 _state_kind() 会归出六种：
    qB 落地态kind能匹配「开始」的预测值吗
    downloading / stalledDL / queuedDL / forcedDL / metaDLdownloading能
    uploading / stalledUP / queuedUP / forcedUPseeding能
    checkingDL / checkingUP / checkingResumeDatachecking不能
    missingFileserror不能
    allocating / moving / unknownother不能
    落在后三行的任意一种，真值就永远匹配不上预测值 ⇒ via=stale ⇒ 1500 ms 拉取预算打满 ⇒ 挂到 3 s 兜底 ⇒ 回滚到 op.prev（已暂停） ⇒ 下一轮才显示真值。 qB 恢复种子时常常先跑一遍 resume-data 校验（checkingResumeData）， 所以这不是边缘情况。

    已复现（sim_qb + 真 auto-qb 子进程 + 真浏览器）

    用 scripts/sim_qb.py 起真 HTTP 仿真 qB，跑真 auto-qb 子进程， agent-browser 上去点；运行时给 SimQb.apply_write 打补丁 （不改仓库源码），让 torrents/resume 落到 checkingResumeData。 同一个种子先「暂停」再「开始」，两次对比：

    3382 ms 那一步就是「弹回已暂停」 —— 真值是 checking（已核对 /api/state），预测值是 seeding，永远匹配不上 ⇒ via=pull ⇒ 1500 ms 预算打满 ⇒ _expirePending() 的 3 s 兜底 回滚到 op.prev ⇒ 行变回「已暂停」，要等下一轮轮询才显示真值。 16 ms vs 3379 ms —— 同一个种子、同一套代码，只差「暂停」和「开始」两个字。

    复现脚本（临时，未入库）：sim_probe.py 起仿真端并打补丁 + scripts/sim_autoqb.py 拉真子进程；仿真端工作根需先放哨兵 .auto-qb-sim-root，否则 prepare_root 的 B1 校验直接拒绝。

    反向不对称：暂停的预测值恒为 paused，而 pause 后 qB 几乎必然落到 pausedDL/pausedUP/stoppedDL ⇒ 稳。所以现象是「暂停已经好了，开始还没好」。

08 · 已排除

查过但排除的假设

  • 「贴上」慢 —— 浏览器实测 patchMs 0~11 ms， 4df80dc 未回归。a8eb6e8 的修复仍有效。
  • 整组 / 单种子撤下慢 —— via=truth，撤下 − 回执 = 17 ms，正常。
  • 追剧页「按视图回传」导致真值快照为空 —— 查过 VIEW_ARRAYS["show"] 是 ("shows", "groups", "singles")，_snapshotTruth() 扫的 singles / groups 都在里面，快照不会空。排除。
  • reannounce / delete / recheck 没接乐观 —— _optimisticPatch() 白名单只有 pause/resume，其余由「等待中」toast 承担，是设计如此，不是缺陷。
  • （原列为已排除，经复核后撤销 —— 见 07 第 4 条） resume 的预测值猜错。 初判「正常情况能匹配上、仅低频」是错的：checkingDL / checkingResumeData / missingFiles 都是 resume 后的常见落地态， 而它们对应的 kind 与预测值永远不可能相等。

09 · 修法方向

建议（只给方向，本轮不改代码）

  1. 让 bulk 走同一条回执链路 _cmd_bulk_torrents() 的成功分支不要再 _set_web_result(cmd_id, "ok")， 改为 self.web.defer_receipt(cmd_id, "bulk_torrents", args, timing)， 由 flush_receipts() 在补刷新之后统一写并附真值。 ⚠ 前置：bulk_torrents 现在在 DEFERRED_RECEIPT_COMMANDS 里， 而 consume_commands() 的判据是 if cmd_id and not deferred —— 必须先把 bulk 从该集合移除（或另立一个"延后但不自行写回执"的集合），否则改了也不生效。
  2. 保留 bulk 的部分成功语义 bulk 现在会在「有 hash 缺失 / 组不存在」时写 error 回执。改链路时要保证这条 error 路径仍然立即写（它不涉及真值，不能跟成功路径一起被扣住等补刷新）。
  3. 补上 wait_ms / exec_ms 顺手让 bulk 回执带上 timing，[perf] 才能开口说话； 否则修完也还是没有回归判据。
  4. 把 RECEIPT_WAIT_CAP_MS 抬到真机实测之上（或改成自适应） 真机实测 resume 的真值落地耗时 1362 ms > 上限 1200 ms（§00）， 于是回执是踩着超时照发的 —— 服务端那段"等真值落地"白等了 6 轮， 最后还是把可能是旧值的真值发了出去。上限按 1200 ms 拍脑袋定的，真机不够用。 建议抬到 2000 ms（仍远小于前端 waitCmd 的 40 s 干等）， 或按「上一轮补刷新耗时」自适应；同时把 TRUTH_RETRY_S 从 0.2 s 收紧到 ~0.1 s，让 6 轮 ~215 ms/轮的粒度变细。
  5. 把「开始」的预测值从"猜种类"改成"退出暂停态即可" 现判据要求真值等于预测值才撤下，对 resume 太苛刻。更贴切的语义是： 「只要真值不再是 paused，命令就生效了」—— 即撤下条件按动作分档， pause 要求 kind == "paused"，resume 只要求 kind != "paused" （checking / error / other 都算已生效，直接撤下并让真值显示出来）。 这样既不会采纳命令前的旧值（4df80dc 那条红线保住了）， 也不会把「成功但落地态不是我猜的那种」误判成"还没落地"。
  6. 补守卫测试 把 test_receipt_waits_for_truth_to_land 扩到 bulk_torrents （hashes 模式 + keys 模式），并加一条静态守阵钉住 「RESYNC_COMMANDS 与 DEFERRED_RECEIPT_COMMANDS 的交集必须为空」 —— 这类"某条命令悄悄滑出新机制"的回归，靠人肉 review 抓不住。
  7. 修桩服务的保真度 scripts/ui_harness.py 的命令泵改成走真实 consume_commands() + flush_receipts()，否则浏览器冒烟永远只能测到 pull 路径， 下次再出同类缺口还是测不出来。

11 · 已修复与验证（2026-09-20 20:50）

改了三处，sim_qb 实测对比

改动清单

  1. bulk 接进真值链路（mixins/web_commands.py + web_runtime.py） 把「回执由 handler 自己写」的 DEFERRED_RECEIPT_COMMANDS 拆成两个语义清晰的集合： HANDLER_RECEIPT_COMMANDS（reannounce / add，结果不依赖补刷新） 与 CMD_ID_RECEIPT_COMMANDS（= 前者 ∪ bulk_torrents，只决定要不要把 cmd_id 传给 handler）。 _cmd_bulk_torrents 的成功分支不再写 ok，交给 drain 侧 defer_receipt；失败（缺失计数 / 未知动作 / 空列表）仍由 handler 立即写 error —— 这条不能动，它不依赖补刷新。
  2. 撤下判据按动作分档（shared/commands.js） 新增 _truthMatches(op, t) 并让 _settleFromTruth 与 _optimisticSettled 都走它：pause 要求真值是暂停态， resume 只要求"不再是暂停态"。不再要求真值等于预测值 —— 否则落地态是 checking / error / other 时永远撤不下。
    「不采纳命令前的旧值」这条红线没破：真值仍是 paused 时不撤下。
  3. 真值等待上限 1200 → 2000 ms 真机实测 resume 的真值落地是 1362 ms，原上限不够用 ⇒ 回执踩着超时照发。 前端 TRUTH_HOLD_BUDGET_MS 同步抬高（两边有静态守阵钉住，不会漂移）。
