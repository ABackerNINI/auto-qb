01 · Problem

现象与问题

用户原始问题: 流量图太陡, 调研 qB 和成熟解决方案, 是采用移动平均还是平均上传/下载数据而不是实时速度? 比如 t0→t1 上传了 10MiB, 这段时间的平均上传速度可以算出来, 就不需要保存瞬时速度了。

问题拆成三层: ①现象 —— qB 流量图在 1m-24h 窗上曲线剧烈跳变, 相邻采样点大幅上下; ②口径选择 —— 修「陡」是靠对瞬时序列做移动平均(SMA/EMA), 还是换掉口径本身、用区间累计字节差分出的平均速度? ③存储连带 —— 如果区间平均可算, 瞬时速度这个字段还有没有保存的必要?

本轮调研按四阶段展开: 本仓库现状梳理 → qBittorrent/libtorrent 上游机制 → 业界成熟做法网络调研 → 方案对比与推荐。各阶段原始笔记见 07 节附录。

「陡」的直接成因(代码事实判定)

直接成因 = 「瞬时值直采入图 + 桶宽=采样间隔(无聚合) + 前端无平滑」三者叠加。qB 端瞬时速度本身在 1.5s sync 粒度上逐拍抖动, 30s 抽样点之间无相关性平滑 → 相邻点大幅跳变; 活尾合流(traffic_qb.py:19-22)让图尾实时跟随采样节拍, 使抖动无衰减地进图(放大器, 非成因)。

差分基数已完全现成

qB 总量字段已被读取并按采样节拍落盘: 全局 alltime_dl / alltime_ul 与 dl_info_data / up_info_data(traffic_sample_mod.py:175), 单种 record.downloaded / uploaded(:178); 每条 r 行携带 totals 快照(:626)。读侧差分也已实现: series_totals_points / v4_totals_points 相邻桶快照差分产 totals 数组(core/traffic_grid.py:198-216, 435-452), 前端 qbCurSummary 已用它求窗口累计(qb_traffic_chart.js:456-463)。即「把速率曲线换成计数器差分」所需的全部原料(字段、存储、差分函数、前端消费)都已存在, 只是速率 points 通道仍走瞬时直采。既有报告 26-10-05-1946 qb-traffic-v4-delta(块头基线 + delta 行编码)是本报告存储事实的直接前件。

qB 侧无二次平滑: WebUI 速度 = 各单种 5 秒 EMA 之和

src/base/bittorrent/sessionimpl.cpp:6656-6669 (qB @ 8182ae071)
// Use the sum of per-torrent payload rates instead of session-level
// instantaneous rate calculation. Per-torrent rates are smoothed by

for (const TorrentImpl *torrent : asConst(m_torrents))

TorrentImpl 直接透传 libtorrent torrent_status.download_payload_rate / upload_payload_rate(torrentimpl.cpp:1579-1590), qB 侧无任何二次平滑。qB 自己另算了一套 session 级字节差分速率(calcRate, 见下), 但 WebUI 的 dl_info_speed 不用它。

libtorrent: 每秒采样的指数滑动平均(EMA, α = 1/5)

src/stat.cpp:15-21 second_tick (lt @ 53acefea9; 机制单点 stat.hpp/stat.cpp)
// should be called once every second  (stat.hpp:53)
void stat_channel::second_tick(int tick_interval_ms) {
    std::int64_t sample = std::int64_t(m_counter) * 1000 / tick_interval_ms;
    m_5_sec_average = std::int32_t(std::int64_t(m_5_sec_average) * 4 / 5 + sample / 5);
    m_counter = 0;
}

每秒把该秒累计字节按实际 elapsed 换算成 B/s 的 sample, 再做 new = old×4/5 + sample/5 —— 官方所称 "5 sec average"(stat.hpp:84), 采样周期 1s, 等效矩形窗约 4-5 秒, 最近样本占主导。peer / torrent / session 三级同一个类同一公式(peer_connection.cpp:1130-1141; torrent.cpp:10894-10917, 12585-12587; session_impl.cpp:3748-3793); 速率值每秒才前进一次, 快于 1Hz 的轮询拿到的是量化值。qB 的 RefreshInterval 默认 1500ms(sessionimpl.cpp:575), 与 auto-qb 的 sync_interval 默认 1.5s 同源。

累计字节数: counter 差分原料在 qB 侧完全现成

  • 会话级 dl_info_data / up_info_data(重启清零); alltime_dl / alltime_ul 经 fastresume 持久化(AlltimeDL/AlltimeUL 键, sessionimpl.cpp:6625-6626, 6959-6973) —— 跨 qB 重启单调, 适合差分; 单种 downloaded = all_time_download(torrentimpl.cpp:1393-1396)。
  • 字节差分平均的内部先例: sessionimpl.cpp:6578-6586 calcRate lambda —— (current - previous) × 1s / interval, 对 session_stats 单调计数器按两次 alert 的真实时间差差分; WebUI properties 的 dl_speed_avg / up_speed_avg = 累计字节 / 活跃秒数(torrentscontroller.cpp:844-845)。
  • qB GUI 自带流量图(SpeedPlotView): 数据源为每个刷新 tick 的瞬时速率, 前端 Averager 分桶窗口平均(speedplotview.h:102-139): 5min/1s · 30min/6s · 6h/36s · 12h/72s · 24h/144s —— 时段越长桶越宽, 图上每点 = 窗口内样本的 SMA。WebUI 没有速度图(上游 issue #20868), 本工具正是在补这个缺口。

借鉴判断: WebUI 的 dl_info_speed 是「各单种 5s EMA(payload 口径, 1Hz)之和」, 陡峭是口径本身; 用「累计字节差分 / 轮询间隔」自算区间平均完全可行, 且是 qB 自家验证过的路子(calcRate / dl_speed_avg 同构)。

04 · Industry

业界实践

核心问题: 业界画流量/速率图, 通行口径是「瞬时速度」还是「累计计数器差分的区间平均」? 有共识, 且是后者。

监控/计量系统: counter 差分是教科书口径

  • MRTG/RRDtool(CACTI 同模型): 轮询 SNMP 单调计数器, 每次 update 做「当前 counter 减上一值, 除以流逝时间 = bytes/s」(rrdtutorial / 镜像)。数据源类型 rrdcreate: COUNTER(含 32/64 位回绕自动补偿)、DERIVE(允许负 delta, 配 min:0 用于会重置的计数器)、ABSOLUTE(读即清零型); "the rrd *always* stores rates" —— 归档里存的从头就是速率。
  • Prometheus: 官方 rate() 文档 原文 "rate/delta/increase should only be used with counters"; "Breaks in monotonicity (such as counter resets due to target restarts) are automatically adjusted for" —— 重置自动调整 + 窗口首末斜率外推。社区共识: 存算好的速率 = 把派生量固定在单一窗口, 事后无法按别的窗口重聚合, 还丢失 counter 重置感知(来源: Asserts、MetricFire、Last9)。
  • Netdata: 反其道提高采集分辨率(每秒全量、宣称 sub-2s 延迟, 架构页), 网络吞吐来自 /proc 计数器按每秒增量入库; 展示层 "Smooth" 开关只改渲染不改口径。反例佐证: 平均窗口过宽会抹掉 microburst(pfSense 用户帖「峰值只显示 ~6 mbps」)。
  • vnstat: 以约 5s UpdateInterval 轮询接口字节计数器, 按 5 分钟(SaveInterval)聚合入库, 最细粒度 5 分钟、保留 48 小时 —— 图上每点都是一个 5 分钟区间的平均速率; 吞吐超 MaxBandwidth 的读数视为无效丢弃(issue #234)。
  • Grafana: $__rate_interval 官方设计目标 = "guarantees a range window large enough to capture at least four samples"; 经典画法 rate(node_network_receive_bytes_total[5m]) 即 counter 的 5 分钟窗口差分, "smoothing out momentary spikes"; 窗口经验: rate() 至少窗口内 2 个点, 建议 ≥ 2× 抓取间隔(MetricFire、hoelz.ro)。

操作系统级网速图

Windows 任务管理器网络图约每秒刷新、60s 滚动窗, 画的是 Bytes Sent/Received/sec —— 源为 WMI/PDH PERF_COUNTER_BULK_COUNT(64 位差分速率计数: 两采样点间 Δbytes/Δt; 判据: WMI 计数器类型文档、SO 对照讨论)。macOS 活动监视器默认每 5s 刷新(Apple 支持), 平滑方式查不到公开资料。共同点: 图上每点都是采样间隔内的平均吞吐(源是 OS 计数器差分), 无再平滑。

下载工具横向(源码为证)

  • qBittorrent GUI 速度图(master @ blob 6fb78c95, GitHub contents API): 喂进去的是每次刷新的瞬时速度(1Hz×5s EWMA), 图上每点 = Averager 窗口内样本的 SMA(1s→144s 分桶)。
  • Deluge Stats 插件(ianmartin/Deluge-stats-plugin, stats/core.py @ blob d1e9776): 每 1s 采瞬时速率存 1s 数组, 逐级 SMA 桶平均 (5,1,5)→(30,5,6)→(300,30,10) —— RRD「AVERAGE 合并 + 多分辨率归档」的手写翻版。
  • Transmission / aria2 / Motrix: 无内置速度历史曲线(Transmission web UI 文档仅速度列), 无口径可考。
  • qB web UI 本身无速度图(issue #20868), 没有「qB web 端先例」可直接抄。
  • 横向小结: 两个有真实实现的(qB GUI、Deluge 插件)都是「采样即时速度 + 时间桶 SMA」; 没有任何一家从瞬时速度直接进图 —— 差异只在桶宽。

SMA vs EMA: 没有共识, 只有场景分工

SMA 等权更平滑、滞后更多; EMA s(t)=α·x(t)+(1-α)·s(t-1) 更跟手更抖(公式与取舍多来源一致, 见 StockCharts ChartSchool); α 与窗口等效关系 α ≈ 2/(N+1), 即 N ≈ 2/α − 1(Quant StackExchange、Investopedia)。窗口长度无权威标准, 但监控界锚点互相吻合: Prometheus 需窗口内 ≥2 点、Grafana 保证 ≥4 样本、MetricFire 建议 ≥2× 采样间隔 —— 「窗口至少覆盖 2~5 个采样间隔」是实际共识区间。EMA 的经典先例是控制反馈而非画图(TCP RTT 估计, RFC 6298); 画图场景下监控生态实际采用时间桶平均(SMA)占绝对多数(RRD CF=AVERAGE、qB Averager、Deluge 多级桶、Grafana rate 窗口), 未见任何主流监控图以 EMA 为落盘口径 —— EMA 的优势场景是要省内存的流式单点平滑(O(1) 状态)。

counter 回绕/重置的通行处理

①负 delta 一律不画原值: 丢弃该点(RRD DERIVE + min:0、Graphite nonNegativeDerivative() / perSecond(), Graphite 文档)或 clamp 到 0; ②有界回绕(32/64 位)按 max+1 补偿(RRD COUNTER、Graphite maxValue 参数); ③Prometheus 的「按重置后增量计」是折中: 重置点产生一次偏低的速率而非洞。对「qB 重启后 total 清零」: Δbytes 为负 → 丢弃该点或按 0 计, 与业界完全一致; qB 的 total 字节计数是 64 位, 无回绕之忧。

逐维度论证要点

  • B 把每点变成真实的 30s 区间平均: 相邻点共享单调 counter 链(本桶增量 + 上桶增量 = 两桶总增量), 序列在数学上是实际传输字节的一个划分 —— 采样噪声不是被平均掉, 而是结构上不存在了。这正是 Windows 任务管理器/vnstat 曲线「平但有真实起伏」的来源。
  • C 是在坏数据上化妆: 对 5s-EWMA 快照再开窗, 平滑的是采样伪影而不是传输过程; 业界窗口经验(≥3~5 个采样间隔)意味着 90~150s 滞后, 比 B 的 30s 更钝; 1m 窗只有 2 个桶, SMA 根本开不了窗 —— C 在最小的窗上直接失效。
  • D 的正确形态 = 先落 B: 业界的展示层平滑(RRD AVERAGE、qB Averager、Deluge 多级桶)是建在区间平均之上的进一步加宽, 不是对瞬时口径的修补。B 落地后 30s 真平均的曲线大概率已达到 vnstat 级观感, D 有可能根本不需要(Netdata 反例: 过度平均抹掉 microburst)。
  • 1m 窗特别说明: 30s 采样下 1m 窗 = 2 个桶, 这是采样密度问题不是口径问题, 四个方案都救不了; 若在意 1m/5m 窗分辨率, 正确杠杆是既有键 qb_traffic.sample_interval(models.py:311, 下限 main_tick 上限 600s), 与本次口径改造正交。
  • 附带收益: B 落地后「速率 × 桶宽 = 累计增量」逐点成立, 前端 qbCurSummary 的窗口累计与曲线视觉严格一致(现在两者可以打架: 瞬时均值 ≠ 实际字节)。
06 · Recommendation

结论与建议

对用户原始问题的正面回答: 不采用移动平均 —— 采用用户提议的口径 B: 区间平均速率(t0→t1 传了 10MiB, 平均速度 = 10MiB ÷ (t1−t0)), 纯读侧实现, 一步落地。它是业界标准口径(RRDtool/Prometheus/vnstat/Windows 性能计数器), 是 qB 自家验证过的路子(calcRate / dl_speed_avg 同构), 且把采样噪声结构性消除而非化妆。瞬时速度仍继续保存(现状不变), 但图的速率通道不再用它 —— 它继续作为 agg 层 dl_max 峰值的聚合源与原始信号留存。

为什么是 B 而不是 C(移动平均)

「陡」的结构性成因是口径错误(把 gauge 当速率用), 移动平均只治放大器。B 使相邻点共享单调 counter 链, 序列成为实际传输字节的一个划分, 噪声结构上不存在; C 在 5s-EWMA 快照上开窗, 平滑的是采样伪影, 且 1m/5m 小窗上直接失效(桶数不够开窗)。业界没有「SMA 优于 EMA」的画图共识, 但有明确分工: 历史曲线用时间桶 SMA, EMA 只用于省内存的流式平滑 —— 而两者的共同前提都是先有正确的口径底座。

纯读侧实现路径要点(建议形态, 文件级)

  1. core/traffic_grid.py(核心): 新增桶点级变换(如 v4_rate_from_totals(points)) —— 复用 v4_totals_points 的全套边界规则(重置→null / 基线缺失→null / null 点断链 / z 桶 delta=0 续链), 输出把 V4PointEntry.dl_rate/up_rate 替换为 delta / w(w = 该点覆盖宽); totals 原样保留。约 30 行 + 单测。
  2. 窗首种子: 调用侧把 t0 外扩一个桶宽取前驱桶点作链种子(不外发该点); 数据几乎总在同份当天 .dat, 零额外文件读取。1m 窗必带, 否则半图空。
  3. v4_grid_obs 一处小豁免: 种子缺失时窗首桶点 rate=None 但 totals 有效, 现行实现会整点跳过导致 totals 链级联断 —— 需允许「rate null 但 totals 参与」(rate 权重记 0)。两行级改动。
  4. 注入点选桶点级(v4_grid_obs 之前)而非 obs 级: 宽桶(采样抖动/暂停恢复产生的 w>interval)的区间平均按真实覆盖秒分摊, 字节守恒; obs 级差分会把宽桶增量整段落进首个覆盖桶出假尖峰。
  5. webui/server/traffic_qb.py(接线, 约 3-5 行): raw 段窗三处(global :192 / 单种 :250-254 / 组 :232-234)在 v4_series_points 与 v4_grid_obs 之间插入变换; agg 段窗(3d+)速率通道不动(dl_avg 已是真均值)。
  6. 零改动面: 采样器 / 存储格式 / 前端逻辑 / 配置键(零新键)。口径修复不做成可选项 —— 保留 A 作为「另一个模式」= 双口径长期维护 + 双倍测试面, 业界无此先例。
  7. 测试: tests/test_traffic_grid.py 增变换函数用例(窗首种子/无种子、重置 null、z 链、真空断链、宽桶分摊字节守恒、组求和); tests/test_webui_delta*.py 一族补接线用例; 各文件头部 docstring「## 测试计划」同步。

边界处理

边界归宿
首样本(启动后无上次 counter)窗首外扩一桶取种子(1m 窗必带); 程序刚启动、窗口早于首个采样时窗首 null 是真值(无前驱字节可差分), 与 totals 通道现行语义一致。对 ≥5m 窗是 1/N 缺口(24h 窗 1/2880), 视觉无感。
qB 重启全局 totals = alltime_dl/ul、单种 = all_time_download, 均经 qB fastresume 持久化 → qB 重启通常不产生 counter 重置, 差分无缝; fastresume 丢失才回落。
counter 回退写侧: 计数器回落强制关块重立基线(traffic_sample_mod.py:759-763); 读侧: cur<last → null(traffic_grid.py:435-452)。两套独立判定已在生产路径, B 直接继承。
断连 / 离线n 游程断链→null(已实现); 离线期 qB 自行传输的字节不会被错误归到恢复后首桶(断链正是防这个); auto-qb 重启跨块 gap 由既有覆盖结算裁决, 连续则差分跨块成立。
旧数据兼容无风险 —— .dat 行型不动, 读侧差分只消费盘上已有的 totals 列; 全部历史 v4 数据即刻按新口径出图(口径变更的预期效果, 非兼容性问题)。
agg 层口径残差raw=Δ/w vs agg=dt 加权均值, 差异 ≤ 上游 5s-EWMA 滞后量级(可忽略); 严格统一(Δ/cov_s)可选, 需把 cov_s 接进 obs(现被 v4_agg_obs 丢弃), 不阻塞。

「是否还需要保存瞬时速度」

需要, 保存现状完全不变 —— 变的只是上图口径。三个理由: ①图的速率通道改走差分通道后, r 行 rate 列(瞬时直采值)继续落盘, 是 agg 层 dl_max(峰值)的聚合源 —— 换成区间平均会让「真峰值信息永久丢失」; ②原始信号留存(Prometheus 社区共识: 速率是派生量, 丢掉原始数据就丢掉可修正性), 供未来分析; ③读侧方案的全部价值就在于写侧零改动 —— 瞬时值照存、差分在读侧现算, 两者不冲突。用户提议「平均速度可算出, 就不需要保存瞬时速度了」在本项目语境下的准确回答是: 不需要保存瞬时速度「上图」, 但需要继续保存瞬时速度「落盘」 —— 且差分所需的 totals 也已在按同一节拍保存, 无新增存储。

D 的后续位

展示层平滑(B 底座之上的可选加宽, 如 qb_traffic.chart_smooth + 窗口)建议待 B 落地看实际观感再议 —— 业界形态是「B 是底座, 展示层平滑是可选加宽」; 若日后引入, 按黄金法则4 需四处同步登记(config/models.py QbTrafficConfig 字段、config/validation/sections.py KNOWN_QB_TRAFFIC_KEYS 白名单(:635 未知键直接报错)、config/schema/groups.py Field、守卫测试)。
