「禁止带 IYUU辅种 分类的种子开始下载」— 现行规则系统可行性实验

问题来自 想法.md L298「实验规则是否支持: 禁止带"IYUU辅种"分类的种子开始下载」。实验分两步: 配置期校验候选规则 spec 是否合法, 行为级用内存 Fake(qB 桩)跑 Rule.process 观测各状态下的实际动作。结论: 条件侧完全支持, 动作侧只有 stop —— 可以表达「永远不处于下载方向状态」的持续压制, 但不是「禁止开始下载」的预防保证。

1 · 结论

Verdict

  • 条件侧: 完全支持 —— category: ["IYUU辅种"](精确匹配, 支持 regex: / :ignore_case)或 expr: 'tor.category == "IYUU辅种"' 都能选中目标集合。
  • 动作侧: 只有 stop(暂停) —— 12 个动作里没有任何「禁止下载」类开关; qB WebAPI 也没有这个开关。语义只能写成「发现它处于下载方向状态就立刻暂停」= 持续压制(reactive), 不是预防(preventive)。
  • 有一条不可消除的竞态窗口 —— 种子由 IYUU 等外部工具直接加入 qB, 本程序只能在同步节拍上事后发现(sync_interval 默认 1.5s / 主 tick 2.0s), 窗口内 qB 已经开始下载。所以能保证「长期不处于下载状态」, 不能保证「一字节都不下载」。
  • 条件必须带状态限定 —— 只按分类写会误伤做种(实测 uploading / stalledUP 被暂停); 加 state: ["is_downloading"] 后只落在下载方向状态, 但该状态集含 checkingDL / metaDL ⇒ 会连带挡住校验与拉元数据(见 §6.3)。

2 · 实验方法

2.1 配置期: spec 合法性(fail-fast)

把候选规则集塞进一份完整配置字典, 直接调 auto_qb.config.validation.validate_config(data), 看错误列表。结论: 三种写法(纯 category / category + state / expr)全部通过; 同时实测到两条取值约束:

  • 规则里显式写 interval: 0S 被拒 —— "必须为正时间: 0S"(config/validation/rules.py:102-104)。想「每 tick 跑」必须省略 interval(缺省 0S 才归一化为每 tick)。
  • state 条件只接受 is_* 类别名 —— 写 downloading 报 "非法状态属性 'downloading'"(config/validation/rules.py:136-149)。

2.2 行为级: 内存 Fake 跑真 Rule.process

用仓库自带测试替身(tests/helpers.py 的 FakeConfig / FakeTracker / FakeTorrent / FakeClient / make_ctx + QbManager(config=cfg, no_lock=True))装配 manager, 让规则经真实绑定链(tracker rules: ["@规则集"])加载, 然后对同一批状态逐个执行 Rule.process(ctx), 观测 client.calls 里有没有 stop。全程不写仓库文件、不连真实 qB。

关键 harness 片段(其余为配置装配):

cfg = FakeConfig(); cfg.trackers = {"HHan": FakeTracker("HHan", rules=["@iyuu_guard_rules"], hr=_hr_rule())}
cfg.rules_config = RULES
mgr = QbManager("", config=cfg, no_lock=True); mgr._load_rules(); mgr.client = client
tor = FakeTorrent(hash="H1", category="IYUU辅种", state="stalledDL")
make_ctx(mgr, tor, client)                      # 副作用: 完成 tracker_conf 匹配
for rule in mgr._rules_for_torrent(tor):        # 真实绑定链取的规则列表
    client.calls.clear(); rule.process(make_ctx(mgr, tor, client))
    print(rule.name, ("stop", None) in client.calls)

替身语义说明: FakeClient.torrents_stop 会把种子状态改写为 pausedDL(tests/helpers.py:288)—— 与 qB 实际语义一致。因此「同一状态连跑两轮」时第二轮会走 stop 动作的「已停止 → skip」分支, 这是正确行为而非漏判; 本报告 §4 用「每轮前把状态重置回下载方向」模拟「又被重新开始」。

4 · 去重与触发语义

「禁止开始下载」是个不变量, 要求每次被重新开始都能再次按下。实测两种去重配置(每轮前把状态重置回 stalledDL, 模拟外部/用户又把它 resume):

配置第 1 轮第 2 轮第 3 轮
execute_once: never(缺省)暂停暂停暂停
execute_once: once暂停漏过漏过

⇒ 这条规则不能配 execute_once: once/daily(跑过一次后 exec_history 就去重掉, 之后被重新开始也不再拦)。stop 动作在已停止时返回 skip("已停止") 天然幂等, 每 tick 跑无副作用(rules/actions/basic.py:121-131)。

触发路径的先后

  • trigger: on_torrent_added —— 在同步线 _refresh_torrents 内同步即时分派(core/qbmanager.py:779), 早于本程序自有动作; 只对「匹配到 tracker 配置」的新增种子触发。
  • trigger: interval(缺省) —— 种子级任务「加入队列即立即到期, 下一 tick 执行」(core/qbmanager.py:824), 且此后每 tick 重入队 ⇒ 兜底压制(也覆盖程序启动时已存在的种子、以及热重载首轮被抑制的事件)。
  • 两者叠加 = 「发现即按 + 持续按」, 是本次推荐形态。单用事件触发则之后被 resume 无人管; 单用 interval 则首次压制晚一个任务线节拍。

5 · 可用写法

config:
    iyuu_guard_rules:
        block_on_add:                  # 新增种子被发现时立即压制
            enabled: true
            trigger: on_torrent_added
            conditions:
                - category: ["IYUU辅种"]
                - state: ["is_downloading"]
            actions:
                - stop: true
            stop_following_rules_if: never
        keep_stopped:                  # 兜底: 每 tick 压制, 防被重新开始
            enabled: true
            # trigger 缺省 = interval; interval 缺省 = 0S(每 tick) —— 显式写 0S 会被校验拒绝
            execute_once: never        # 不能配 once/daily
            conditions:
                - category: ["IYUU辅种"]
                - state: ["is_downloading"]
            actions:
                - stop: true
            stop_following_rules_if: never
    trackers:
        <每个相关站点>:
            rules:
                - "@iyuu_guard_rules"  # 绑定: 规则只对引用它的站点种子生效
                # ...原有引用照旧

等价单条写法(实测行为一致, 少一条规则): - expr: '(tor.category == "IYUU辅种") and (tor.is_downloading)'。注意 YAML 里含 * / & / # / {} / : 的表达式必须加引号。

规则可在 WEB UI 的配置编辑器里加(规则编辑 + 表达式试算), 也可直接写 YAML; 改动后 validate_config 会 fail-fast 拦住非法名/非法状态属性。

6 · 前提与副作用

6.1 竞态窗口: 「压制」不是「预防」

IYUU 把种子直接加进 qB, 本程序只能在同步线上看到它(sync_interval 默认 1.5s, config/models.py:267; 主 tick 2.0s, :266)。窗口内 qB 按自己的策略开始下载 —— seedbox 带宽下 1~2 秒可能就是数 MB~数十 MB。要「零字节」只能在加入端解决(IYUU/添加方配「添加时暂停」), 规则系统管不到添加动作。

6.2 绑定前提: 规则只对配置过的站点生效

规则经 tracker.rules: ["@规则集"] 引用绑定(core/mixins/rule_engine.py:248-274), 未匹配 tracker 配置的种子不建任务、事件也不分派, 只留一条 WARNING(core/qbmanager.py:774)。IYUU辅种 分类里若混有未配置站点的种子, 规则对它们完全无效 —— 要全覆盖, 得在每一个相关站点上引用这条规则集。

6.3 副作用: is_downloading 含校验与元数据阶段

按 §3 的推荐条件, 该分类的种子在 checkingDL(新加种子重新校验)与 metaDL(拉元数据)阶段也会被按下暂停。如果这个分类的种子本来是「数据已完整、只等校验完做种」的辅种, 规则会把校验一并挡住, 它就永远进不了做种。现有动作集没有「只禁下载、允许校验/做种」的粒度; 只能靠 expr 排除(如再加 and (not tor.is_checking))自己取舍 —— 代价是校验期间的下载也不再被拦。

6.4 与跳检动作的 auto_start 会互相拉扯

checking 动作的 skip_checking.auto_start 段在跳检完成后会 torrents_start(rules/actions/skip_checking.py:115-120)。同一种子上同时挂跳检规则与本压制规则, 两者会来回拉扯(跳检 start ↔ 本规则 stop)。别在同一批种子上同时配这两者。

6.5 限速动作不能当「禁止」用

download_speed_limit 只能把速度压低: qB 限速语义里 0 = 不限速, 而设成奇数 KiB/s(如 1KiB/s = 1024B/s)会被项目自己的「单数值保护」视为用户手动设置而不再覆盖(infra/utils.py:479-484)。无论哪种都不等于「不下载」。

7 · 真正闭环的缺口

  • qB 层唯一能表达「不下载」的手段是文件优先级 0(逐文件; 把种子全部文件置 0)。本仓库 WEB UI 已有手动入口(_cmd_set_file_priority, webui/commands.py:424; 前端抽屉 0=跳过), 但规则动作集里没有对应动作 —— 这是「现行规则系统不支持」的准确边界: 能力在 qB 侧存在, 未规则化。
  • 加入端暂停是唯一能做到「连一字节都不下」的路径(qB torrents_add(is_stopped=True) 一类的添加参数), 但施加点在 IYUU/添加方, 不在本程序。
  • 若目标其实是「缺数据时不要下载」, 更贴合现成能力的是 checking 跳检(数据完整才跳检, 部分下载被前置闸门拒绝) —— 但语义不同: 跳检要删除重加、需参考种子、且默认可能 auto_start。

要不要补一个「整种子文件优先级置 0」的动作插件属于改代码的决定, 本报告不落方案; 「现行系统能不能接近表达」的答案已在 §1/§3/§5 给出。

8 · 附注: 实验期间发现的口径不一致(计划外, 未修)

现象: 规则 spec 的已知键是 {enabled, trigger, interval, execute_once, cooldown, conditions, actions, stop_following_rules_if}(config/validation/rules.py:11-12), 写 log_level 会被判未知键 —— 实测 config.sample_rules.rule: 未知键 ['log_level'], 可用键: [...]。而 test_yamls/test_actions/ 下五个样例配置都写着 log_level: info(test_stop.yml / test_start.yml / test_up_dl_limit.yml / 两个 checking 样例), 且 AGENTS.md 与 config-reference/keys.md:93 都把 test_yamls/ 当作可运行示例指引。

影响判定: 这些 YAML 若真的走 dev.run 会在 load_config 的校验阶段直接失败。属计划外文档/样例漂移, 按范围守恒本轮一行未改, 仅在此留证(是否入池由用户定)。
