01方法与执行过程

按用户指令采用「三路调查 Agent + 监督者」分工：监督者只做结构分析、派单、复核与汇总，不参与细节调查；三个 Agent 分别负责 安全与可靠性（凭据 / 注入 / Web 鉴权 / 线程安全 / 状态持久化）、性能与资源（主循环节拍 / 增量同步 / 视图重建 / 内存驻留）、架构与质量（分层耦合 / 测试 / 文档一致性 / 可观测性）。

执行实况需要如实记录：本次 8 次子代理派发（安全 ×3、架构 ×3、性能 ×2）无一完整跑完，全部毁于模型服务基础设施故障（长会话 5–14 分钟后「lost context」或秒级请求失败，无一次与任务内容相关）。有效的 salvage 有三份：安全 Agent 的「先写盘后补内容」策略留下近 10KB 半成品报告（5 个检查点完成 4.5 个）；架构 Agent 的首轮运行留下实测数字（pytest 基线、函数规模、注解覆盖率）与一份 20KB import 依赖图；性能 Agent 两次均在产出前夭折。最终交付 = 半成品 + 监督者逐条交叉复核（每条发现核到 文件:行号）+ 监督者定向补证三项（passkey 泄露线索、yaml/notify 注入面、Facade 渗漏）。

置信口径：所有发现均给 文件:行号 证据；性能数字凡标「项目实测」者来自项目知识库（memory-bank/activeContext.md）既有测量、本次未独立复测；凡标「推演」者为代码阅读推断。监督者补证或推翻原结论之处在对应条目注明。

02安全与可靠性

S1-01P2skip_local_verify 开启后缺 Origin/Host 校验 → 本机跨站 CSRF / DNS rebinding置信度 中高
web.py:125-145（本机放行分支）· web.py:1033-1043（middleware 仅加 Cache-Control）· config/models.py:119（默认 False）

开关打开时 loopback 连接完全免 token，且不校验 Origin/Referer/Host。用户浏览器里任意网页可对 http://127.0.0.1:port/api/* 发跨站简单请求——不触发预检，删除 / 暂停 / 改限速等写动作照常入队执行（攻击者读不到响应）。无 Host 校验同时意味着 DNS rebinding 可让攻击页面同源读全量数据。

# web.py:134-138
if manager.config.web.skip_local_verify and _is_loopback_host(request.client.host ...):
    ...  # 全文件无 Origin/Referer/Host 校验；无 CORS 中间件、无 CSRF token

修复建议：开启该开关时校验 Host ∈ {127.0.0.1, localhost, 配置 host}（直接废掉 DNS rebinding），写端点再校验 Origin 为空或同源。

S1-05P2tracker URL（含 passkey）全文写入日志，且可经 /api/log 读回置信度 高 · 监督者补证确认
mixins/web_commands.py:381、:389（URL 全文入日志）· web.py:893-894（/api/log）· web.py:78（自认知晓密钥份量的注释）

Web UI 编辑 / 移除 tracker 时把完整 URL 写进 INFO 日志。私站 announce URL 普遍内嵌 passkey（…/announce.php?passkey=…），于是密钥落入轮转日志文件（含 5 份备份）——同机其它进程、日志备份、云同步都是泄露面；/api/log 的消费者虽已持 token（边际风险有限），但日志落盘这件事本身构成泄露面。调查 Agent 中断前抓到该线索，由监督者补证坐实并修正其摘要中「未发现泄露证据」的中间结论。

# web_commands.py:381
logger.info(f"WEB UI | 种子 {hash[:8]} 编辑 tracker: {orig_url} -> {new_url}")
# web_commands.py:389
logger.info(f"WEB UI | 种子 {hash[:8]} 移除 tracker: {url}")

修复建议：日志输出前对 URL 做 query 脱敏（剥 passkey/token/uuid 类参数，保留 path），单点包一个 sanitize_tracker_url() 即可覆盖两处。

S3-01P2state.json 仅在退出时落盘——硬杀 / 断电丢全部去重历史置信度 高
qbmanager.py:443-450（run() 的 finally，全仓唯一常规调用点）· rules/actions/skip_checking.py:238（跳检例外）

save_state() 只挂在主循环 finally：正常退出 / Ctrl+C 能落盘，但 taskkill /F、断电、原生崩溃时 finally 不执行——自上次退出以来所有 record_execution 去重记录丢失，重启后「每天一次 / 每小时一次」窗口失忆，通知与动作类规则重放一遍。跳检去重已单独即时落盘，兜住了最疼的场景。注意：这与黄金法则 3「程序退出时才落盘」的声明一致，属声明的固有丢失面，不是实现违背。

修复建议：周期性节流落盘（如每 5 分钟或每次 record_execution 后 debounce），复用现成 atomic_write，成本可控。

S1-02P3SSE 用 ?token= 查询串兜底鉴权，密钥可进中间层日志置信度 高
web.py:147-154

EventSource 发不出 Authorization 头，密钥允许走 URL 查询串。泄露面在反向代理 / 隧道场景的访问日志（本项目自身 uvicorn 已压到 warning、无 access log）；浏览器历史基本不涉及（EventSource 不是导航）。比较用 secrets.compare_digest，无时序侧信道。代码注释已自知该取舍。

修复建议：远程访问场景可改一次性短时 ticket（POST 换 ticket → EventSource 带 ticket），或前端改 fetch + ReadableStream 消费 SSE。

S1-03P3/api/config/public 免鉴权暴露「是否处于免鉴权模式」置信度 高
web.py:126-128（显式放行）· web.py:172-175

登录前可探测本实例是否处于 skip_local_verify 模式——本身不含机密，但等于向潜在攻击者广播「CSRF 面（S1-01）是否开着」。可接受；若收紧，对该端点限 loopback 即可。

S1-04P3反代部署在本机时，XFF 头可致本机免鉴权误判置信度 低
web.py:84-89（_is_loopback_host）· web.py:1106-1110（uvicorn.Config 未显式关 proxy_headers）

uvicorn 默认 proxy_headers=True 且信任来自 127.0.0.1 的 X-Forwarded-For。若用户把 auto-qb 反代部署在本机（nginx 监听 loopback 转发外部流量），外部请求经代理到达时 XFF 被采信，request.client.host 可能变为攻击者指定的 127.0.0.1 → 命中本机免鉴权。直接连接（无反代）不受影响：非本机源不采信 XFF，套接字地址不可伪造。

修复建议：uvicorn.Config 显式 proxy_headers=False（项目自身直连监听，无需反代头），或在文档警告反代场景必须关 skip_local_verify。

S3-03P3results / truth_pending 的跨线程安全依赖「单写者 + GIL」隐式约定置信度 中
web_runtime.py:103（view_lock）· :126-155（SSE 订阅）· :514-604（命令与视图）

核查结论：四视图 + 版本号在同一临界区发布与读取，无撕裂读；SSE 订阅队列独立小锁、无锁序倒置；commands 为线程安全队列。但 results / truth_pending / write_seq 是主循环单写者、Web 线程无锁读——依赖 CPython GIL 的字典读原子性，实践安全但属隐式约定（换解释器或将来出现第二个写者就露馅）。潜在争用：Web 线程持 view_lock 重建全视图时会堵住主循环 publish——是性能争用不是死锁，且有节拍对齐缓解。

修复建议：在读路径显式注释「单写者 + GIL」假设，防将来被无意破坏。

03性能与资源

执行口径：本维度由监督者结构性补位（性能 Agent 两次派发均毁于基础设施故障）。以下基于代码结构验证 + 项目知识库既有实测（已标注来源），未做独立压测；推演项已标注。

P-F1P2大库下四视图全量重建是单轮成本大头，追剧视图最重置信度 高（有项目实测）
mixins/web_view.py:412 _build_shows_view（140 行全量聚合）· web_runtime.py _publish_locked（唯一重建入口）

四个视图构建器均为全量重建（按 by_hash 重新聚合），有 rid 门控与活跃窗口门控，但一旦脏了就是整棵重建。项目实测（memory-bank/activeContext.md，2026-09-19，本次未复测）：单轮视图回传 1000 / 3000 / 5000 种子 = 143 / 353 / ~550ms；前端大库渲染占主线程 10–17%。已有缓解：轮询按种子量分档（≤1000 → 1.5s / >3000 → 3s）、行窗口化、视图分片回传。剩余痛点集中在追剧视图的全量聚合与浏览器主线程渲染。

优化建议：追剧视图改增量（只重算 dirty 剧 / 季键），成本中等；前端虚拟滚动已在（ROW_WIN_*），下一步是避免每轮 decoratedGroups 全量重算。

P-F2P3真值直查按 50 hash 分批，大库批量命令的 qB 侧等待是物理下界置信度 高（项目实测）
web_runtime.py:59 TRUTH_QUERY_CHUNK=50 · :473-475（分批 torrents_info）

批量 448 个 hash ≈ 9 次 torrents_info 往返。项目实测（2026-09-20/21）：qB 自身状态翻转要 1.3–1.6s（直查也绕不开），服务端链路已压到 21ms、端到端撤下 2947→85ms（via=receipt）。结论：WebUI 命令链路已无自加延迟，剩余延迟是 qB 的——这条记录在案，防止将来误判回归方向。

P-F3P3SSE 事件队列有界（200）满则丢，依赖轮询兜底置信度 高
web_runtime.py EVENT_QUEUE_MAX=200 · put_nowait 满则丢

推送风暴（如批量命令 + ver 事件并发）时事件会被静默丢弃；设计上前端轮询与 SSE 赛跑、断线回退轮询，所以丢失不致卡死，但表现为「该推送的更新迟一拍」。可接受；若要收紧，丢弃时计数并周期性记一条 DEBUG 即可观测。

04架构与质量

A-F1P1create_app 单函数 926 行——全项目最大函数坐在最高危文件里置信度 高（AST 实测）
web.py:121 create_app（926 行）· 次大：qbmanager.run 154 行 · web_view._build_shows_view 140 行 · 全库 ≥80 行函数共 9 个

鉴权依赖、全部 API 端点、静态挂载、中间件、uvicorn 启停全部内联在一个工厂函数里。web.py 同时是本项目唯一对外暴露面（web.py 1,143 行，占 src 约 8%）：安全关键逻辑与业务端点纠缠，diff 审查困难，合并冲突高频——它与 S1-01/S1-02/S1-05 三个发现全部发生在同一个文件里并非巧合。

修复建议：按域拆 Router（torrents / groups / config / fs / events / auth），create_app 收成 <150 行的组装壳；鉴权依赖与安全头中间件独立成模块。这是本报告唯一 P1。

A-F5P2表现层经 self._host 回调核心域私有方法，无 Protocol 约束置信度 高
web_runtime.py:317 self._host._build_search_index() · :479 self._host._state_kind() · :312 refresh_error_reasons()

2026-09-20 的解耦把表现层状态迁入 WebUIRuntime 门面，方向正确；但门面仍直接调用宿主 QbManager 的私有方法，接口面靠约定不靠类型。表现为：宿主重命名私有方法时门面静默炸（无静态检查），依赖方向声明（表现层 → 核心域单向）只对了一半。

修复建议：定义一个 HostCapabilities Protocol（写能力 / 视图构建器 / wake），宿主显式实现，门面只认 Protocol——迁移成本低，收益是类型检查与边界文档二合一。

A-F2P2版本号双源且互相矛盾：__version__ 0.2.0 vs pyproject 0.1.0置信度 高（监督者实读确认）
src/auto_qb/__init__.py（__version__ = "0.2.0"）· pyproject.toml（version = "0.1.0"）

Web UI 顶栏透出的版本号来自 __init__.__version__（web.py _app_version），打包元数据来自 pyproject——两者已差一个 minor。将来做发布 / issue 定位时会出现「用户报的版本对不上任何 tag」。

修复建议：pyproject 单源 + __init__ 动态读取（importlib.metadata），或 hatchling 钩子注入，二选一，删掉手写双份。

A-F4P2CI 只跑 ubuntu——主力部署平台 Windows 不在矩阵里置信度 高
.github/workflows/ci.yml（runs-on: ubuntu-latest，python 3.12/3.13，coverage 上传）

项目的 pitfalls 里明确记载过「Windows 全绿 / Linux 全红」的平台差异史（路径分隔符、编码、文件锁行为），而用户实际生产环境是 Windows 桌面（托盘 / 注册表自启 / WinRT 通知全是 Windows 专属路径）。CI 的 ubuntu-only 矩阵拦不住 Windows 回归，这些代码路径只有手动跑测试时才被执行。

修复建议：matrix 加 windows-latest（tests 全绿是常态，24 秒的套件在 Windows 上也就 1–2 分钟）；托盘 / 通知相关测试若依赖 GUI 可标记 skip 条件。
