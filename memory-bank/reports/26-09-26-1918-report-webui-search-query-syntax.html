WEBUI 搜索强化 — 查询语法调研

起因:「恶女 10」搜不到单文件发布物 [虽然我不是完美恶女～雏宫蝶鼠替换传～].Futsutsuka…S01E10…mkv(根因已定位:整句连续子串匹配,不分词)。本报告调研主流成熟搜索产品的查询语法,提炼公共核心,并给出适配本项目的推荐设计——目标能力示例:-DV 排除、多词 AND、短语匹配。

1 · 现状口径与问题

搜索实现在 src/auto_qb/webui/views.py 的 search_torrents()(L672–731),匹配口径:

  • 查询 q 与种子名/文件名各自经 _search_norm()(L35)归一——正则 [\W_]+ 把点/下划线/连字符/全角标点等非文字字符折叠为单空格、转小写;CJK 保留
  • 把整个查询当一段连续子串在归一后的种子名(L714)与文件名列表(L723)里找;文件列表依赖 _search_index 缓存(预算限流构建,building 时前端 1s 重查)

实测归一(2026-09-26 本会话复现):文件名归一后为 虽然我不是完美恶女 雏宫蝶鼠替换传 futsutsuka … den 2026 s01e10 1080p …,查询「恶女 10」要求两词连续出现——「恶女」后跟「雏宫蝶鼠替换传」,「10」在远处的 s01e10 里,两词不连续 ⇒ 整句必不命中。逐词都能中(恶女 ✓ 10 ✓),拆词 AND 即整体命中。种子名(单文件发布与文件名同构)同理。

问题定性:这是「整句连续子串」口径的固有边界,不是回归。docstring(L675)与行内注释(L712)写明的示例场景("cat and" 命中 "The.Cat.and…")也是连续同序场景。多词查询只有「在某个名字/文件名里连续且同序」才能命中——这同时挡住了两类高频需求:非连续多词(「恶女 10」)与排除词(「-DV」,现状会把 -dv 归一成 dv 当正词搜)。

2 · 调研范围与方法

目标形态是单框交互式搜索(一个输入框 + 即时结果),因此调研对象限定「用户直输查询语法」的成熟方案,按家族分六系(§3)。方法:官方文档核实 + 公认口径整理——本轮经网络核实的三条高不确定性事实(PG websearch_to_tsquery 的隐式算子与宽容性、Typesense 的 - 排除、Meilisearch 的负词)均以官方文档/权威转述为准并在 §来源 列出;其余为各产品长期稳定、广为引用的语法口径,标注「公认」。域内先例(qB / Sonarr / Radarr)单独一系。

3.1 逐系要点

A · 通用 web 搜索(用户基数最大,迁移成本最低)

  • Google:空格分词隐式 AND;-term 排除;"exact phrase";OR(大写)。+term 强制包含已于 2013 年弃用(公认)。
  • GitHub / Gmail:同上,并扩展 key:value 限定符(language:python、from:、label:)与布尔关键字。这是「限定符」功能的来源(第二梯队,见 F5)。

B · 检索引擎经典(Lucene/Elasticsearch)

  • 经典 query_string(Lucene QueryParser 血统):+term 必须 / -term 禁止 / AND OR NOT / "短语" / field: / * 通配 / ~ 模糊 / ^ 提权 / () 分组——能力最全,但解析严格,非法输入抛异常,官方都不建议直接暴露给用户。
  • Elasticsearch 为用户直输专门设计了 simple_query_string:只保留 + / - / |(OR)/ "短语" / * 前缀,从不抛异常,语法错误的部分降级为字面量(官方表述 "never throw an exception")。这个产品的存在本身就是一条设计结论:面向人的解析器必须宽容。

C · 数据库 FTS

  • PostgreSQL websearch_to_tsquery(11+):Google 式——未引号词隐式 AND、or 关键字、-word 排除、"fat cat" 短语;对任何输入永不抛错(已核实,官方文档「Controlling Text Search」);不支持前缀通配 :*。定位即「把用户搜索框输入安全转成查询」。
  • SQLite FTS5:隐式 AND,OR/NOT,"短语",列过滤 col:,前缀 term*,NEAR()。关键教训在分词器:默认 unicode61 对 CJK 不分词(整段成一个 token),要子串检索得上 trigram(3.34+)且查询须 ≥3 字符——成熟方案在 CJK 上都要额外 machinery,见 F4。

D · 嵌入式/托管专用引擎

  • Typesense:官方 Search API 文档——「排除词在词前加 - 算子」,例 electric car -tesla(已核实)。
  • Meilisearch:负词(negative keywords),Homer -Simpson 排除含 Simpson 的文档(已核实)。
  • Whoosh(Python 纯库):默认 qparser 即支持 +term / -term / AND / OR / NOT / field: / "短语" / *。若要「现成解析器」它是零服务化依赖的候选,但为 50 行内的语法引入一个依赖不值得(见 §6)。

E · 桌面文件搜索

  • Everything(voidtools):-term 排除、"…" 短语、通配符、case:/content: 等修饰符。它就是「在海量文件名里搜」的产品,口径与 A 系完全一致——侧面印证文件名场景不需要比 websearch 更复杂的语法。

F · PT/媒体自动化域内先例

  • qBittorrent RSS 自动下载规则:每条规则两个正则框——必须包含(Must Contain)与必须不包含(Must Not Contain),外加剧集过滤器。用户手工档时的表达方式。
  • Sonarr / Radarr:release profiles 用 must contain / must not contain 关键词列表。
  • 共同点:排除是该领域的刚需,且以「正/负两个列表」的形态出现。交互式单框里对应的自然演化就是 -term。Jackett/Prowlarr 只透传各站点自身搜索框,无统一语法,不列为参照。

4 · 公共性提炼(5 条事实)

#事实证据面
F1-term 排除是跨家族的压倒性惯例。六系中五系(A/B/C/D/E)原样支持,写法一致:词首 -。Google/GitHub/Gmail · Lucene/ES(simple_query_string)· PG websearch · Meilisearch/Typesense/Whoosh · Everything
F2现代单框搜索的公共核心恰好是三件套:空格分词隐式 AND + -term 排除 + "短语"。+ 显式与已近废弃(Google 弃用,Lucene 系保留),OR 与括号是可选增强层,限定符是第二梯队。A/C/D/E 系逐项吻合;B 系的 simple_query_string 子集亦然
F3面向用户的解析器必须宽容、永不报错。ES 专门做 simple_query_string 替代 query_string 面向用户;PG websearch_to_tsquery 官方定位即「web 搜索式、对任意输入不抛错」;搜索框报错是反模式——语法错误的部分按字面降级。ES 官方设计动机;PG 官方文档
F4成熟方案全都是词元(token)匹配,没有一家用裸子串;CJK 依赖分词器/trigram 额外 machinery。但本项目规模(数千种子、内存索引、无排序相关性需求)下,「归一 + 子串」等价于 CJK 词元匹配的务实近似——scene 命名的分隔符折叠(_search_norm)已经把两侧统一到同一空间。应保留子串语义,不为 CJK 引入分词。FTS5 unicode61 的 CJK 缺陷与 trigram 的 ≥3 字符限制;PG/ES 均需 CJK 分词器配置
F5限定符(key:value)是交互搜索的成熟第二梯队,且本项目结果项字段已齐(site/tag/category/kind/state),后加不动匹配核心。首期不做(保守默认)。GitHub/Gmail/Everything/Lucene;本结果项 _view() 字段对齐检查

5 · 推荐设计

推荐:websearch 核心三件套 + 行级匹配语义

采纳 F2 的公共核心(词 AND / - 排除 / "短语")按 F3 做宽容解析,匹配语义用行级(定义见下),完全复用 _search_norm 归一与 files_q 索引缓存。纯后端小改、零依赖、零配置、零状态变化;顺带修复「恶女 10」失配。

5.1 语法层(宽容解析)

词        空格分隔;隐式 AND;每个词归一后在候选行内做子串匹配   → 恶女 10
排除词    词首单个 -(后随非空白)→ 该词不得出现在候选行内      → -DV
短语      "…" 内整段归一后作连续子串(可含空格/分隔符)          → "s01e10" · "web dl"
排除短语  -"…"                                                   → -"H264 AAC"
宽容规则  孤立 - 忽略;未闭合引号收至行尾;其余字符原样进词;永不报错   → F3

词法判定全部在原始查询上进行(先按空白切 token 再逐个归一),与归一化互不干扰:-DV 在切词阶段即识别为负词;而 web-dl 不以 - 开头,是正词,归一后为 web dl——与现状口径一致,无歧义。scene 命名里真实的连字符经归一折叠为空格,不会再被误判为排除符。

5.2 语义层:行级匹配(推荐)vs 种子级

定义候选行 = 归一种子名,或归一文件名之一(files_q 既有缓存)。则:

行通过 ⇔ 该行含全部正词/正短语,且不含任何负词/负短语
种子命中 ⇔ 存在至少一行通过
方案规则优点缺点
行级(推荐)如上——所有词约束在同一行内求值可预测(「某条名字/文件名整体匹配查询」);与单文件 scene 命名现实一致;前端 placeholder「搜索种子名或文件名…」承诺的就是这个模型;负词语义自然(含 -DV 的行作废);顺带修复「恶女 10」失配季度包/合集包依赖「单行含全部词」:若包名不含集数、文件名不含剧名,正词可能跨行分布而漏配(见下表第三行)
种子级正词在 名字∪全部文件 任意命中即可(词间 AND、位置无关);负词在 名字∪全部文件 任一出现即整种子排除召回更高(合集包靠跨行 AND 命中);实现同样简单跨文件连词不可预测(foo bar 可能因两个不相干文件各含一词而命中);负词整种子误杀——合集包只要任一文件带 DV 就整包消失,即使它同时含用户想要的非 DV 集

两方案都能修复原失配,行为差异集中在多文件合集包。以 恶女 10 -DV 为例:

种子形态行级(推荐)种子级
单文件 DV 发布(名字/文件都带 DV)不命中 ✓(用户意图:排除)不命中 ✓
季度包,含 E10 非 DV 行与若干 DV 行命中(E10 非 DV 行通过)——「包里有你要的那集」不命中(DV 行触发整包排除)——即使包里有非 DV 的 E10
季度包,包名含剧名不含集数,文件名只含集数可能漏配(正词跨行)命中(跨行 AND)

拍板点:行级胜在可预测与负词合理性;种子级胜在合集包召回。推荐行级——搜索框的可预测性优先(「你搜的就是某条名字或文件名」),合集包场景用户可改用 恶女 或 恶女 s01 之类的宽查询。若实施后反馈合集包漏配频发,再把「种子级跨行 AND」作为可选放宽项评估,不动语法层。

5.3 行为示例与兼容性

查询行为
恶女 10行级 AND——本例命中 E10 单文件发布,原失配修复
恶女 10 -DV同上,且含 dv 的行作废(单文件 DV 发布被排除)
恶女 "s01e10" -UBWEB短语与排除词并用
-DV仅负词,无正判据 ⇒ 返回空并前端提示(与 Google 一致:「只说不要什么」无从起搜)
web-dl / WEB-DL正词 web dl,行为与现状一致(大小写、分隔符归一不变)
"cat and"连续短语,现状已命中的场景不变
cat and(两词)现状:仅连续同序命中;新:行内 AND(「The.Cat.and…」仍中,另可命中 cat … and … 非连续行)

兼容性:新语义是旧语义的严格超集——单词查询行为不变;多词连续同序不变(连续 ⇒ 行内 AND);多词非连续从「恒不命中」变「可命中」。无配置迁移、无状态升级、无回归面。

5.4 性能与实现要点

  • 复杂度不变:每候选行做 (正词数+负词数) 次子串 in 判断,O(行数×词数)。数千种子 × 文件列表(files_q 已缓存归一,构建期预算限流的机制原样保留)在主循环与 web 线程均无感。无需预建分词/倒排索引——词数是用户输入量级(个位数),倒排在这个规模只有负收益。
  • 解析器为纯函数(建议 _parse_query(q) -> (positive: list[str], negative: list[str]),词已在函数内归一),匹配段只读解析结果,便于单测与将来加限定符。
  • building 兜底不变:文件索引脏/缺失时 building=True + 前端 1s 重查的既有机制原样复用,负词作用于已缓存行,行为与现状同构。
  • 前端只动文案:placeholder 提示升级(如 搜索种子名或文件名… 支持 空格=且、-排除、"短语"),atlas / prism 两主题成对;strip-note「搜索"…"」照旧展示原文,不需改。

8 · 结论

调研覆盖六系成熟方案,公共核心高度收敛:空格分词隐式 AND + -term 排除 + "短语",宽容解析永不报错——这正是用户诉求(「-DV 排除」)所在的语法家族,且是 Google/GitHub/PG/Meilisearch/Typesense/Everything 等跨行业的一致惯例,用户零学习成本。域内先例(qB RSS「必须不包含」、Sonarr/Radarr must-not-contain)进一步印证排除是 PT 场景第一刚需。

推荐按 §5 设计实施:websearch 三件套语法 + 行级匹配语义,严格超集无回归 单文件 ~60 行 零依赖零配置,顺带修复「恶女 10」失配。唯一待拍板点是行级 vs 种子级(§5.2),已给推荐与理由。拍板后可直接进入计划文档(plans/)。
