2 · 发现清单 (本轮未改代码, 处置建议见各条)

P2 F1 · 早停② 的 P 机检「空真」+ B/C 档语义假设未验证 ⇒ C 档存在误放行链

证据: service.py:477 period_ok = True 起始; :561-572 只有 remain_seconds > 0 的行参与 P 反算 (已到期行被站点截 0, 不参与); :622 早停②闸门是 if period_ok and zero_remain_streak >= 5 and parsed.has_next —— 整页 remain 全为 0 时 period_values 为空, 机检从未运行却被当作通过。对比轮尾 meta: service.py:828 period_consistent = bool(period_values) and period_ok (空 = False) —— 判定侧豁免 A 因此被正确禁用, 取数侧早停②却没有同等闸门, 两道机检口径不一致。

触发链 (需要两个未验证的站点形态假设同时成立):

  1. 计划注释自己写明「已到期行 remain 被站点截 0」(service.py:557) —— 若 C 档(未达标)行的「剩余达标时间」恰以可解析的 0 展示 (考核期已过 = remain 归零, 语义上自洽);
  2. C 档第 1 页 ≥5 行且还有第 2 页 (has_next) ⇒ 早停②在第 1 页即触发, got_all_pages 保持 True ⇒ C 档「覆盖证明成立」;
  3. complete=True 后, C 第 2 页起的种子不在索引里 ⇒ 判定侧反应式路径 (resolve.py:260-273) 按「完整刷新未列出」放行 ⇒ 用户删除 ⇒ H&R 惩罚。C = 未达标 = 站点明确终态「不能删」, 这是漏管方向的失效。

缓解因素: B 档同形态误停翻无害 (B=已达标=本就可删, 两条路径殊途同归「安全」); A 档才是早停②的设计目标场景; C 行 remain 也可能是空白/文本 (不可解析 → None, == 0 不成立 → 不触发)。但注意另一种形态也不安全: remain 列若为空白, 它是必填字段 (REQUIRED_KEYS = name/need_seed/remain, adapters/nexusphp.py:57) ⇒ S2 零容忍中止, 连续 3 轮 ⇒ suspended 误停站。即 C 档 remain 只有「可解析的非零值」这一种形态是全安全的 —— 而这恰是 M0/真机走查尚未覆盖的假设。

建议: ① 早停②闸门加 period_values 非空前置 (与 meta 的 period_consistent 口径对齐, 约一行改动); ② 或把早停②限定在 A 档生效; ③ M0 前置实测补第④项「B/C 档 remain 列展示形态」。方向: 建议入池 issue 或并入下轮计划, 由用户拍板。

P3 F2 · 跨页 S1 校验对「轮内清单顶端插入」零容忍 ⇒ 活跃账号可能误停站

证据: parse.py:329-330 desc 方向的跨页判据是 max(cur) > min(prev) 即违反; service.py:538-546 一处即 _SignalAbort ⇒ 本轮失败 + 计入熔断失败; 连续 3 轮 (SUSPEND_ROUNDS) ⇒ 12H 熔断 + suspended 人工恢复 (service.py:674-681)。

触发链: 轮内相邻两页请求间隔 90~113s, 一轮 9 页约 15 分钟。若其间该站有 ≥2 个新种子完成下载、进入清单顶端 (按完成时间倒序), 则下一页首行会比上一页末行「新」(max(cur) > min(prev)) ⇒ 判「跨页乱序」。清单是活的: 活跃账号 15 分钟内进来 2 个新完成并不罕见 —— 这与「页面改版」是两种机制, 但共享同一个零容忍处置。

影响: 数据安全方向无损 (fail-safe: 本轮不放行); 代价是可用性 —— 单次发生浪费当轮剩余预算, 连续 3 轮各遇一次 ⇒ 停站等人工 (--hr-resume)。

建议: 给跨页判据加边界容差 (如改比 min(cur) > max(prev) 的方向性反转, 或忽略 cur 页首 k 行), 或把跨页证据降级为告警、不参与停站计数。❗这与用户 2026-09-26「哪怕 1 处即中止」的定稿存在张力 —— 该定稿针对页面真改版, 轮内自然插入是否纳入零容忍值得单独拍板, 故只报告不改。

P3 F3 · parse_missing_rate_max 已被 S2 零容忍架空 (死配置 + 文档漂移)

证据: service.py:551-553 S2 对任何缺失率 > 0 立即中止 (M5.2 定稿, 无阈值); 该中止发生在 :806 if max_missing > parse_missing_rate_max 之前 —— 能走到 806 的轮必然 max_missing == 0, 该分支不可达; complete 条件里的缺失率项 (:780) 恒真。而配置键仍在 schema/validate 里, keys.md:30 仍写旧语义「超过则判『页面可能改版』不产生放行」。

影响: 无行为风险 (S2 比旧阈值更严); 但配置面有一把「假的锁」—— 用户调它以为在调阈值, 实际无效。

建议: keys.md 与 schema 帮助文案改注「已被 S2 零容忍取代, 仅展示用途」, 或走配置键废弃流程移除。

P4 F4 · 注释漂移 ×2 + 死变量 ×1 (无行为影响)

  • 旧公式注释: hr/status.py:143 与 :190 的 docstring/注释仍写勘误前公式「P ≈ done + remain − now」—— 实现是正确的 (status.py:202-203 与 service 同步用了 (now − done) + remain), 但注释与三份制品同源的笔误仍会误导后来人 (读注释对不出实现)。
  • 死变量: service.py:486,596 covered_local_any 置 True 后无任何消费点 —— 早停③的证据经 notes 落进 refresh.reason 不丢失, 变量本身是死代码; 可清理或接进 --hr-status 观测行。

已核实无误的关键防护 (抽查清单)

  • Retry-After 封顶: 站点/扩展回传的 Retry-After 以本站 failure_cooldown 封顶 (ratelimit.py:164-181) —— 畸形值不能把熔断推到天荒地老;
  • 只读口径不落盘: 失败计数/熔断在 dry-run 与 --hr-once 下同样不写盘 (service.py:734-740 注释 + 分支), 走查不会污染正式实例的取数节奏;
  • 幂等窗口键 + 跨重启令牌桶: 小时/天窗口键比较 (ratelimit.py:95-111), split 令牌按 refill_ts + 速率 现算 (:294-312), 重启不重置;
  • 预算消耗在请求前: 取数失败也计配额 (保守方向); mark 在 legacy 于请求后记账、split 由 split_try_consume 在消费时推进 —— 两模型语义各自自洽;
  • 登录退避与熔断解耦: 退避期零请求、不计失败、登录恢复即清零, 且不动 fetched_at (登录失效不产生新的放行背书)。

维度机制与证据
存储自愈链原子替换写 (临时文件 + os.replace) + 每次写留 .bak + 坏文件挪 .bad-<ts> 留证再试备份恢复 (顺序不能反, store.py:252-294); 主文件坏时不盖备份 (:235-247); 取证串区分「空文件」与「写坏内容」(:152-166); schema 版本沿迁移链, 未来版本不猜
多实例一致性账号级状态不进 state_file, 落 <shared_dir|data_dir>/hr/<site>.json 由实例共享; 每站一把 filelock, 全程在锁内读-判-抓-写, 拿不到锁等下轮不排队 (lock_timeout=0); 写者心跳自检: revision 回退/心跳被覆盖 ⇒ 锁不生效 ⇒ 退化只读防双写 (store.py:215-233); 恢复后重置自检基线防「自愈变砖」(:196-204)
崩溃恢复每抓一页/每取一个 .torrent 增量落盘 (service.py:582-584, _persist_step) —— Ctrl+C/断电最多丢当前页; hr_downloaded 永久层防重复下载烧配额
停机路径stop 先 cancel_all 叫停取数通道再 join (worker.py:186-210) + 锁内频控睡眠可中断 (1s 切片查停止位, runtime.py:249-263) —— 关停不等 180s 回传超时/睡完间隔; 被打断折 HrChannelStopped 不计失败
失败遏制单站点异常不外抛 (service.py:278-282); 单轮异常不打死取数线程 (worker.py:244-245); 端点线程单请求异常回 500 不退出
告警纪律三档分级: 节流态 (间隔/配额/时间窗) 只 INFO 且按根因去重; 页面/字段/翻页问题与取数失败 WARNING; 通道静默周期提醒 —— 同一状态不逐轮刷屏, 系统通知不被淹没 (worker.py:42-74, 292-339; 各 _warn_* 均有单次/节流口径)

结论: 稳定性设计在「防双写 / 防丢数据 / 防卡死 / 防告警疲劳」四个方向都有实打实的机制与守阵; F1/F2 是保守方向内部的两处「过严可能反噬可用性」与「闸门口径不一致」, 不动摇整体结构。

5.3 默认配置下的访问节奏 (回答「多久访问一次 / 每次多少页」)

前提: hr_check.enabled=true、站点 mode=partial、channel.enabled=true, 其余全部默认值 (legacy 配额模型, 12H 刷新周期):

  • 稳态节奏: 数据完整有效期 = refresh_interval = 12 小时 —— 每 12H 才有一个抓取轮; 完整刷新后整段静默, 与实例数无关 (站点访问频率由数据有效期决定, 谁抓的都一样)。
  • 一个抓取轮抓多少: 档位顺序 A(考察中)→B(已达标)→C(未达标), 上轮未完成的档位优先起翻 (预算轮转); 每档最多 5 页 (max_pages_per_refresh), 单轮总量硬顶 9 页 (max_pages_per_round)。每页行数由站点页面自然行数决定 (不在配置面)。翻页终止 = 「下一页」链接与 maxpage/currentpage 脚本标记的并集; 另有三路早停 (整页超龄 / 连续 5 行已到期段 / 本地种子全覆盖)。
  • 请求间隔: 相邻请求 ≥ 90s + 0~25% 只向上抖动 (90~113s) ⇒ 一轮 9 页约 12~17 分钟, 全程持该站点锁。
  • 配额硬顶: legacy 合并账本 = 12 次/小时、60 次/天 (页面与 .torrent 下载同一个账本!) —— 90s 间隔理论上允许 40 次/时, 实际先撞 12/时; 隐含效果是「每小时窗口最多 9 页 + 3 个下载」。
  • 不完备轮的自愈节奏: 预算截断/改版可疑 ⇒ 数据有效期降为 120s ⇒ 60s 节拍下先插一个「复用轮」只补 .torrent 下载, 再进下一个抓取轮。一个 15 页的清单 (3 档 × 5 页) 典型 2~3 个抓取轮 (~1~2 小时) 收敛到 complete; 之后回到 12H 静默。
  • 单请求上限: 等扩展回传最多 180s (request_timeout); 频控等待单次 >300s 或单轮累计 >900s 即放弃剩余请求 (不持锁干等)。
  • split 站点 (站点显式 quota_model: split 才生效): 页面桶 40/时 · burst 10 · 400/天 · 间隔 90s, 下载桶 20/时 · burst 5 · 200/天 · 间隔 90s; 页面只在新轮、下载只在复用轮 —— 治「下载被页面挤占」的 legacy 痛点, 但默认不开 (40/时比 12/时松, 激活门保守)。
  • 扩展侧节奏: 扩展每 1 分钟拉一次任务清单 (DEFAULT_POLL_HINT=60, 必须小于 180s 回传窗口, v2.6 定版)。

5.7 观测与恢复口子

  • --hr-status: 全量现状 —— 运行时自检 (端点/token 来源/锁) + 每站配额两组 (页面/下载) + 观测面四行 (排序 ✓/✗/未判定 · 考核期 P 分布 · 骤降观测 · 档位计数上轮→本轮) + 清单明细表 (档位/量/名称/infohash) + suspended 恢复指引;
  • --hr-once: 真机只读走查 —— 真发请求出报告, 不写盘不联动 qB (熔断/配额也不落盘), 单次等待上限 600s;
