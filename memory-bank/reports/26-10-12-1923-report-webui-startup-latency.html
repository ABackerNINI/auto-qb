1摘要

现象（用户报）
启动 auto-qb 后，WEB UI 要好几秒才「正常」（能看种子、能搜）；以前在 2 秒之内。
结论（一句话）
不是 WEB UI 慢 —— 服务本身 0.07s 就绪、HTTP 响应毫秒级（实测）。真正的问题是主循环开始工作之前的「启动死区」：装配序最后一个模块 TrafficSampleModule.start() 里的 _recover_aggregates()，每一次启动都把 qb-traffic-v4/ 的全部历史天文件重读一遍并逐槽重算。它完全静默（无一行日志）、又恰好卡在「WEB 已监听」与「主循环第一拍」之间 —— 这段时间里 store 是空的，所以界面开着却没有数据。耗时随历史数据无界增长：实测 +1.5~2.0s/天。
实测数字（19:11:01 那次启动）
启动死区 = 11.16s（19:11:01.360 → 19:11:12.385，中间零日志）。其中 _recover_aggregates 全量实测 = 7.09 / 7.28 / 7.09s（在真实数据的只读副本上跑真实函数，3 次）。

三条独立事实，合起来就是用户看到的「好几秒」

#事实证据时长
① traffic-v4 启动恢复重读全部历史（主因） 85 次启动趋势单调增长，与 v4 数据积累起点（10-06）严格对齐；真实数据实测 7.09~7.28s ≈ 7~11s
② 首次全量同步被死区挡在后面 ⇒ 界面空表 死区结束才 加载规则(12.385)，检测到新增种子 165 个 在 12.623 累计到 12.6s
③ 搜索索引首建：165 个种子一次拉 165 次 /torrents/files，独占主循环 SEARCH_INDEX_BUILD_BUDGET = 500 > 165 ⇒ 一轮拉完；日志 13.425 → 15.079 ≈ 1.7~2.5s

⇒ 用户体感的「完全正常」= 进程起算 ≈14s（init→搜索索引已构建 = 13.93s）。而 09-29~10-06 期间同一指标是 3~6s。

4根因：启动死区 = traffic-v4 全历史重读

4.1 代码链（静默、且在关键路径上）

ModuleHost.start_all(dry_run)                       # module.py:347  按装配序调各模块 start
  └─ TrafficSampleModule.start(ctx, dry_run)        # traffic_sample_mod.py:371  ★装配序最后一位
       └─ if not dry_run: _recover_aggregates()     # traffic_sample_mod.py:377 / :1124
            └─ for key in store.series_keys()       # traffic_store.py:915  global + 每个有数据的种子
                 └─ _recover_series(key, store, now, conf.rollup_window)   # :1158
                      ├─ store.read_agg(key)        # 读 agg.dat
                      └─ for date in store.series_day_dates(key, now - window):   # :1176  ★窗口 = rollup_window
                           ├─ store.read_day(key, date)          # :944  读 + 解析整个天文件
                           └─ _agg_credit_day_file(...)          # :1206 ★把游程展开成槽, 逐槽 Python 循环入账
两个致命属性叠在一起
① 静默：_recover_aggregates / _recover_series / _agg_credit_day_file 全程只在失败时打 WARNING，正常路径一行 INFO 都没有。所以日志上就是一个 11s 的洞 —— 这是本次排查最大的障碍（见 §7 建议 B4）。
② 位置：它在 connect() 之前、主循环第一拍之前。这段时间 store 里一个种子都没有 ⇒ WEB UI 虽然能响应，但拿不到任何数据。

4.2 为什么会「无界」增长：rollup_window 三义合一 + raw_window 零消费方

rollup_window 在本仓是一个键三个含义（config/models.py:309）：

  1. hour 行保留窗；
  2. 系列淘汰龄；
  3. catch-up 补算窗口（= 天文件存活期） ← 启动恢复读多少文件由它决定。

用户把它设成了 1000000D（≈ 2740 年，等效「永久保留」）⇒ 补算窗口覆盖全部历史，一个天文件都不会被跳过。

并且：天文件目前没有任何删除点
raw_window 在配置里声明、在校验里检查、在文档里写着「raw 段 = 按天整文件存删」，但代码里零消费方（全仓仅注释提及：traffic_store.py:66 / :817 / :1105、traffic_sample_mod.py:104）。
天文件唯一的删除路径是 evict_expired_series()（traffic_store.py:973）—— 整系列按 rollup_window 淘汰。
⇒ 结论：只要一个系列还在产数据，它的天文件就永远不删。所以即使把 rollup_window 调回默认 30D，稳态仍是 30 × 25 ≈ 750 个天文件 ≈ 50s 启动。这不是「配置没调好」，是恢复策略本身与保留口径不匹配。

5次要因素（同一「不正常」窗口内的另两项）

5.1 首次全量同步被死区推迟（12.62s）

主循环的 next_sync_at = 0.0，本意是「起来就同步」。但这一拍必须等 start_all → connect → _reload_state → load_rules 全部走完（qbmanager.py:462 / 472 / 485 / 491）。死区把它们整体推后 ⇒ 165 个种子直到 12.62s 才进快照。

5.2 搜索索引首建独占主循环（1.7~2.5s）

SEARCH_INDEX_BUILD_BUDGET = 500（webui/views.py:31）＞ 165 个种子 ⇒ 首轮一次拉完 165 次 /torrents/files，全部在主循环线程内（views.py:856）。索引只存内存（web.search_index），每次重启都要重建。

  • 日志证据：13.425（限速曲线任务）→ 15.079（搜索索引已构建）= 1.65s，基本就是这 165 次 API。
  • 这一项不随历史增长（受种子数封顶），所以它不是本次回归的主因，但它把「完全正常」又推后了近 2s。

    ts, msg = m.group(1) + "." + m.group(2), m.group(3)

        if cur: rows.append(cur)

    if "WEB UI 已启动" in msg and "web" not in cur: cur["web"] = ts
    if "加载规则" in msg and "rules" not in cur: cur["rules"] = ts
if cur: rows.append(cur)
t = lambda s: datetime.strptime(s, "%Y-%m-%d %H:%M:%S.%f")
for r in rows:
    if "web" in r and "rules" in r:
        print(r["start"], f'{(t(r["rules"]) - t(r["web"])).total_seconds():6.2f}s')

10附：为什么启动恢复必须读 raw（不是「打开才读」）

本节为 2026-10-12 20:17 追加：讨论中提出「流量图定调一直是按需读取，为什么不打开就完全不用读」，这里把 §7-B1 的口径说全 —— 恢复读的不是图表数据，而是写侧聚合链的缺口。

问题答案
「按需读取」管的是谁？ 管图表读侧：打开页签才拉取，只读窗口涉及的天文件（24h ≤2 天，见 webui/server/traffic_qb.py → V4DayCache.read_window），前端关闭后无任何请求路径。这一层已经是按需，本报告与修复都不动它。
启动恢复读的是什么？ 写侧（采样器）聚合链的缺口：当前小时累计器与当日/当月累计器只存在于内存（_agg_states），进程一停就没了；上次停机时尚未封口的那几个小时的 raw 只落在天文件里 —— 它是唯一幸存来源。恢复 = 用这段 raw 把缺的 hour 行补出来。
不补会怎样？ 那几小时永不封口 ⇒ hour 行永久缺失 ⇒ day/month 行（只从 hour 行逐级派生，不从 raw 直聚）永久偏小；且 3d/6mo/1y/all 窗口只读 agg.dat，缺口在图上永远看不到补。时间上也等不起：重启后第一次 flush（默认 600s 内必到）就会把残缺累计器封成行，错误当场固化 —— 等不到你打开图表。
为什么不让「打开图表」触发它？ 图表读侧是只读契约（读 raw 窗口 + agg.dat，零写入）。让它去补封口 hour 行 = 读路径写盘 ⇒ 破坏「单一写线程」（黄金法则 5）与读侧契约；而且不打开就永不补 ⇒ 不是「暂时看不到」，是永久丢数据。
那「按需」定调被破坏了吗？ 没有 —— §7-B1 把恢复读集收敛为 [agg 水位所在日, 今日]（常态 1 个、跨日界至多 2 个天文件），与 24h 图表同阶、读同一批文件；差别只在触发时机：写侧因「重启后要接着聚合」而读（且只读在途那一段），UI 因「你打开」而读。这正是本报告要修的那一刀。
若要「重启零 raw 读」，只有两条取舍路（都不免费）
  • 在途累计器落盘（每次 flush 快照进 state.json）：重启不读 raw，代价是每 flush 写放大 + 与 raw 双份记账；
  • 接受空洞：在途小时永不封口，hour/day/month 永久缺这一段 —— 主动丢掉本来可恢复的数据（与既有「崩溃窗口 ≤ flush_interval 丢样本」不是一回事）。
当前设计取「raw 单一事实源 + 重启补读有界」；取舍与实施见计划 26-10-12-2010。
对 §7 建议的影响
不改变方向，只把 B1 的口径说全：不是「不读」，而是「只读在途那一段」。B4 埋点照旧（把「读了多少」变成可见事实，而不是又一个静默洞）。
