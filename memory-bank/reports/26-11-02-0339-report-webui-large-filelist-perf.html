WebUI 单种子千级文件列表性能调研

结论先行: 千级文件列表卡顿的根因不在数据线(后端已短缓存 + JSONResponse 短路), 而在前端抽屉 content 页签全量渲染 + 全量重算 —— 主表早有 P1-2 行窗口化, 抽屉三表全部 window: null; 且每次点选/重拉都整棵树重派生、千行行对象全新、千个行组件全量 re-render。推荐路线 = 记忆化止血 + 把主表窗口化机制推广进抽屉引擎。

doc-added 26-11-02-0339 · doc-updated 26-11-02-0339 · doc-status Done · 载体 单文件 HTML(dark)
来源 用户报障: 单种子约 1000+ 文件的详情文件列表操作卡顿, 需要性能优化; 主表性能问题一并取证。本轮为纯调研(只取证不改码), 证据为 2026-11-02 本地 clone 代码走读(HEAD fe211faf)。

§01结论

前端技术栈事实: Vue 3 全局构建(shared/vendor/vue.global.prod.js, Options API + x-template 字符串模板), 无构建步骤、无打包器, 三皮肤(prism/atlas/console/flux)共享同一套 shared/ 模块; 表格行由自研「引擎行容器」(group-table + .group-row grid)渲染。这个事实直接决定方案取舍: 任何需要打包器/JSX 的方案都不适配; 凡能与「引擎行容器 + Teleport 桥 + 列偏好双轨」共存的方案才是候选。

卡顿根因(按影响排序, 详见 §03): ① 抽屉 content 行全量渲染无窗口化(主表已有); ② 每次 reactive tick 全量重派生(O(F·D) 建树/聚合)并产出全新行对象 → 千个行组件全量 re-render; ③ 交互粒度 = 整列表(点一次勾选 = 全表重算重渲); ④ JSON.stringify(files) 全量序列化做变更比对; ⑤ 优先级提交后整列表(千文件 payload)静默重拉再全渲一遍。

推荐路线(详见 §05): 分三阶段 —— P1 低风险止血(行对象记忆化 + content-visibility); P2 主修(把主表 _rowWindow 窗口化参数化推广到抽屉引擎表); P3 数据与交互面(乐观优先级 + payload 裁剪, 按 perf-cadence 四步量法先测后裁)。不建议引入 AG Grid/整套第三方表格或上构建步骤。

§02证据快照 · 现状取证(代码事实)

2.1 前端架构与两条渲染线

  • 主表线(种子/分组/追剧): 数据走 /api/state 单请求轮询, rid 门控 + view 裁剪 + delta 增量协商(server/routes/state.py:47-60 端点注; shared/polling.js:347-354 前端带 rid= 与 delta=1)——版本未变时响应体趋近于零, 数组不回传、不触发整表替换。渲染层有 P1-2 行窗口化(shared/columns.js:515 起一整节; 常量 ROW_WIN_MIN=200 / ROW_WIN_OVERSCAN=10 在 shared/app.js:648-652), 模板经 <aq-row-pad> 上下占位消费切片(shared/tpl/torrents.html:7,19、groups.html:22,48)。逐行实测行高(columns.js:567-612 _measureRowH), 前缀和 + 二分求可见窗(columns.js:620-660 _rowWindow)。主表的数据与渲染两条线均已优化到位。
  • 抽屉详情线(本次病灶): 详情面板四页签(general/content/trackers/peers)各有变体注册表; content 页签无 classic 档、缺省落首个注册变体 10「树 + 详情」(shared/drawer_templates.js TPL_REG.defaultSel; manifest 装载序 10<11<12)。content 页签无轮询(变体 11 头注自述, drawer_tpl/11-content-treegrid-batch-low.js:364), 文件列表按需拉取。

2.2 数据线: 文件列表端点(健康, 但全量)

  • 端点 GET /api/torrents/{hash}/files(src/auto_qb/webui/server/routes/torrent_detail.py:58-64): 一次返回 client.torrents_files(hash) 全量数组, 无分页、无字段裁剪; JSONResponse 包裹(跳过 jsonable_encoder 收税, 与 pitfalls/web-ui/perf-cadence 判据一致) + _cached_read("files:{hash}") 只读短缓存。qB WebAPI 的 files 元素本就只有约 7 字段(name/size/progress/priority/is_seed/piece_range/availability), 裁剪空间有限。
  • 前端取数: shared/drawer_store.js:95-104(files 源配置) — 拉全量、整数组替换 drawer.files(引用换新)。拉取时机 = 打开 content 页签 / 换种子 / 合并双列补给(drawer_store.js:141,296,312,328) / 优先级提交后 silent 重拉(shared/drawer.js:565)。无 SSE、无轮询, 数据线本身不是卡顿首恶。

2.3 渲染线: content 文件列表(全量 + 全量重算)

  • 窗口化缺席: 抽屉全部表注册条目 window: null —— drawerContentV10/V11 在 shared/app.js:602-615, peers/tracker 五条同; 而主表三条是 window: "torrent"/"group"/"member"(app.js:445 注)。即 P1-2 行窗口化只覆盖主视图, 千级文件行在抽屉里全量进 DOM。
  • 桥渲染链全量: 变体外壳只画锚(data-dt-anchor-slot), 行经 <aq-dt-bridge> 组件 Teleport 进锚(shared/tpl/drawer.html:208,221), 桥模板对 $root.dtBridgeSegs(tab) 的全部行做 v-for, 每行一个行渲染器组件(shared/tpl/xtpl.html:333-366, <component :is="'aq-'+model+'-cells'" :p="r">)。1000 文件 + 目录行 ≈ 千级行 × 每行 8~11 个元素(勾选框/折叠钮/名/徽章/大小/进度条/可用性)≈ 万级常驻 DOM 节点 + 千级行组件实例(规模为按分片模板的估算)。
  • 每次求值全量重建派生: 变体 10 的 rowsFn 每次求值都调核心 buildFileTree 重建整棵树(drawer_tpl/10-content-tree-detail-tall.js:232-247 → shared/drawer_templates.js:469-496, 无缓存); 变体 11 的 rowsFn → derive 每次做 O(文件数×目录深度) 的路径前缀归并聚合(drawer_tpl/11-content-treegrid-batch-low.js:153-196, 逐祖先 segs.slice(0,i).join("/") 拼串)。树扁平化单点 drawerFileRows() 是 method 不是 computed(shared/drawer.js:1451), 无 Vue 缓存, 每次调用重走。
  • 行对象全新 → 千组件全量 re-render: rowsFn 每次产出全新行对象数组(rowOf/dirRowOf/fileRowOf 均新建字面量, dt10:198-227、dt11:224-289), 桥 v-for 按 key diff 时每一行的 prop 对象引用都变了 → 1000 个 aq-dt11-cells 全部重渲。变体 11 的目录行装配还是 O(目录数×文件数): 每目录行 subtreeFiles 全表 filter(startsWith), 且 chkStateOf(paths) 在同一行对象里算两遍(dt11:244 ckState 与 :253 _cls)。
  • 变更比对用全量序列化: 变体 render 通知(换页签回来/数据落袋/补拉)每次先 JSON.stringify(files) 拼签名比对跳过重建(dt11:360、dt10:316) —— 千文件时每拍白付一次 ~105 字节级的字符串化。
  • 交互粒度 = 整列表: 勾选/折叠/筛选/徽章点击都改 reactive ui 态(dt11:49, Vue.reactive, W5 改造)→ dtTplRows 重求 → derive + 全行重装配 + 全表 keyed patch。W5(计划 26-10-13-0811 L5)已把「整表 DOM 全换」降为 keyed 写补丁(dt11 头注 44-48 行自述: 旧结构「每次点选行 DOM 全换 → 勾选跳动 + 大树点选卡死, 用户 2026-10-13 症状 7/8」), 但复杂度仍是 O(文件数)/交互 —— 本次报障是同一症状在更大文件数下的延续。
  • 优先级提交链放大: 点一次徽章 = setFilePriority POST(drawer.js:950-959)→ 成功回执后 silent 全量重拉 files(drawer.js:565)→ 整数组替换 → 派生重建 + 千行全渲, 一轮全价。

2.4 主表现状(顺带取证)

  • 主表数据/渲染两线已优化: rid+delta 增量轮询、view 裁剪、行窗口化、JSONResponse 短路(见 §2.1-2.2 与 pitfalls/web-ui/perf-cadence)。
  • 残留已知面全部已入池且有结论, 不在本轮展开: 5000 种子冷启动/降级轮仍回整表全量(issues/26-10-08-0411-perf-webui-api-state-pagination.html)、组视图增量粒度可降到成员级(26-10-07-1420)、SSE/补刷新延迟(26-10-30-0626)。前端残余开销为 _measureRowH 全量轮的逐行 getBoundingClientRect 与每帧 O(n) 前缀和, 量级小(代码自注 ≈0.03ms)。
  • 判断: 用户感知的「主表卡」若发生在几千种子库, 属上述已入池议题的延伸; 若与本次同场景(打开千文件种子详情时主表连带卡), 则更可能是抽屉全量渲染拖累同一页面主线程 —— 与 §03 R1/R2 同源。

§03根因分析(按影响排序)

#根因机制与证据影响面
R1抽屉行全量渲染, 无窗口化DRAWER_TABLE_DEFS 全部 window: null(app.js:602-615); 桥 v-for 全量(xtpl.html:353-365)。主表 _rowWindow 机制现成(columns.js:620-660)但只接主视图。万级常驻 DOM + 千组件实例 → 首渲/滚动/任何 patch 的基数都被放大; 是「千级文件」场景的第一要素。
R2每次 reactive tick 全量重派生 + 全新行对象rowsFn 每次重建树/聚合(dt10:232-247; dt11:153-196; 树单点 drawer_templates.js:469 无缓存); 行对象全新 → 千行组件全量 re-render; drawerFileRows 是 method(drawer.js:1451)。把「数据没变」也变成全价; 任何一处 reactive 依赖翻动(文件数组引用/勾选/折叠)都付千行 patch。
R3交互粒度 = 整列表点选/折叠/徽章 → reactive ui → dtTplRows 重求 + 全表 patch(dt11:44-48 头注自认「大树点选卡死」前史); 目录行装配 O(D×F)(dt11:224-255 subtreeFiles + chkStateOf 双算)。单次点击的卡顿感直接来源; W5 已降一档(换代→keyed patch), 千级规模下仍不够。
R4sig 比对 = 全量 JSON.stringifydt11:360 / dt10:316, 每次变体 render 通知序列化整份 files。每拍 O(payload) 字符串化; 不是首恶但在千文件下白付, 且随文件数线性恶化。
R5优先级提交后整列表重拉重渲POST 成功 → _fetchDrawerFiles(true)(drawer.js:565)→ 整数组替换 → 全价一轮。乐观补丁机制(applyOptimistic 族)未覆盖 files 列表(对齐 pitfalls/web-ui/webui-optimistic-rollback-symmetry 的「覆盖面」概念)。把一次小交互(改一个文件的优先级)放大成网络往返 + 千行重渲。
R6数据线全量无裁剪(次要)torrent_detail.py:58-64 全量返回, 无分页; qB files 字段本就 ~7 个, 裁剪空间有限。payload 一次性传输(非轮询), 网络占比待测 —— 按 perf-cadence「载荷大不等于要裁字段」四步量法先量再动。
与 pitfalls 判据对齐说明: ① 本报告的「前后端契约」结论与 pitfalls/web-ui/contract-api.md 一致 —— content 文件列表是按需拉取、无 rid 门控, 不存在「轮询全量 payload」问题; ② R2/R3 与 pitfalls/web-ui/frame-swap-scroll-reset.md 的「整帧换/replaceChildren」史一脉相承, 现行 withScroll/anchFill 保锚机制在窗口化改造时必须继续保活; ③ 主表窗口化已踩平的坑(逐行实测行高、gap 实测、sticky 内缩补偿 pitfalls/web-ui/sticky-scrollpad-inset.md)在抽屉推广时全部适用。

§05推荐路线(给计划阶段的输入)

总路线: 记忆化止血 → 窗口化主修 → 数据面收尾, 三阶段相互独立、可分批交付; 全程不引入构建步骤、不换框架、不动引擎对外契约。

P1 · 低风险止血(建议先做, 收益/风险比最高)

  • 行对象记忆化(R2/R3): 变体 10/11 的 derive/rowsFn 按 path 记忆化行对象 —— 未变文件(引用/字段哈希相等)复用旧对象, 让桥 v-for 里 999/1000 行组件因 prop 引用相等而跳渲; 目录行聚合失效按子树脏标记传播。顺手消掉 dt11:244/:253 的 chkStateOf 双算与 subtreeFiles 每目录全表 filter(改前缀计数)。
  • sig 廉价化(R4): 全量 JSON.stringify(files) 换「长度 + 抽样字段 + 版本号」指纹(数据落袋时后端/取数层本可带单调版本), 或只在 files 引用未变时直接跳过。
  • content-visibility(R1 渲染税): dt10/11 行容器加 content-visibility:auto; contain-intrinsic-size: auto 27px;(按各自 min-height 定值), 与 P2 不冲突; 需实测 sticky 表头/键盘回焦/锚保活(H.anchFill/withScroll)不受影响。

P2 · 主修: 窗口化推广进抽屉引擎

  • 把 columns.js 的 _rowWindow/_measureRowH/_winGapFor 参数化: 滚动源(window.scrollY → 容器 scrollTop)与视口矩形(面板内滚动)抽成 kind 配置; DRAWER_TABLE_DEFS.drawerContentV10/V11 的 window: null 改挂新 kind。
  • 树语义天然兼容: 窗口化的输入就是 rowsFn 输出的已扁平化可见行(折叠/筛选已在 rowsFn 完成), 窗口化不碰树; 折叠/展开引起行数突变时走既有的「全量重测一轮」路径(_winMeasured 失效机制现成)。
  • 成对处理(坑档已踩平): 行高逐行实测 + gap 实测(_winGapOf 已实测不硬编码); sticky 表头/吸底条的 padding 内缩补偿(dt11 现有 -14px/-20px 注释口径); 键盘跨窗移动焦点走主表 W2 前缀和先例(shortcuts.js _kbScrollRowIntoView 同法); 滚动位自保 withScroll 继续生效。

P3 · 数据与交互面(可选, 按实测决定)

  • 乐观优先级(R5): 提交后不整表重拉, 直接按 indices 写 drawer.files[i].priority 并复用行级补丁; 失败/超时回滚必须与贴补丁走同一单点且覆盖面对称(对齐 webui-optimistic-rollback-symmetry; 现有 applyOptimistic 族可扩 files 覆盖面)。
  • payload 实测后再裁(R6): 按 perf-cadence「载荷大不等于要裁字段」四步量法(字节构成/客户端拆分/网络对照/端点内耗时)实测千文件 payload 各环占比, 有数据再决定裁 is_seed/piece_range 等非渲染字段或做 range 懒取; 无实测数字不动端点。

明确不做

  • 不引入 AG Grid/整套第三方表格(推翻三皮肤与列偏好双轨, 违和成本远超收益); 不上构建步骤/不换框架; 不给 content 列表上 SSE(无轮询可替)。
