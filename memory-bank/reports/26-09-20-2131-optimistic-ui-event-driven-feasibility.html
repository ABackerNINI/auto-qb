撤下改为事件驱动：可行性报告

目标由「让撤下变快」修正为：让真值更快到 + 撤下依据真值 + 事件驱动，不依赖轮询。 本报告先把真值从 qB 到「行恢复正常」的整条链路拆成可计时的段，分清哪些是我们自己加的延迟（可省） 与哪些是外部系统的下界（省不掉），再给事件驱动的方案设计与风险。 结论先说：方向可行，但「10 ms」能否达成取决于一个必须先做的判定实验。

01 · 结论摘要

可行，但有一个前置未知

可行 · 明确可省

我们自己加在链路上的延迟合计 约 1.5~2 s：回执轮询退避（0/150/300/500 ms 粒度）、 _pullTruthAfterCmd 的 1500 ms 拉取预算、常规 /api/state 轮询 （1.5 / 2 / 3 s 分档）。事件驱动可以把这三段整体去掉，只留一次推送。

待定 · 决定 10 ms 能否达成

qB 那一侧还有 ~1.36 s。但这个数到底是「qB 内部真的慢」还是「我们从 /sync/maindata 快照读、快照 1.5 s 才更新一次」——现在无法区分。 两者的应对完全不同（见 E1）。

硬约束 · 与目标冲突处

「撤下依据真值」与「10 ms」在 resume 上互斥：真值本身要 1.36 s 才到， 依据真值撤下就不可能 10 ms。除非 E1 证实那是快照滞后（可绕开）， 否则 10 ms 只能对 pause 成立，resume 的下界就是 qB。

一句话：先把 E1 做了（半天量级），再决定要不要投入事件驱动改造。 若 E1 证实是快照滞后，那么「直查 + 推送」两条加起来就能把撤下压到几十毫秒，10 ms 目标可望可即； 若 E1 证实是 qB 内部慢，事件驱动仍然值得做（能省掉我们自己的 1.5~2 s）， 但必须接受 resume 的下界 ~1.4 s。

03 · 关键未知

判定实验 E1：1362 ms 到底卡在哪一侧

这是整份报告唯一必须先把答案拿到手的问题，因为两条分支的应对完全不同：

分支 A：是快照滞后

若 torrents/info 明显早于 /sync/maindata 翻状态 ⇒ 那 1362 ms 是我们从快照读的代价（快照按 qB 的节奏更新，而 sync_interval = 1.5 # 与 qB 自带 WebUI(1500ms)同量级 —— 实测 1362 ms 几乎正好是这个节奏，这是很强的一条旁证）。

应对：真值改走 torrents/info 直查（QbApi.torrents_info 已存在，qbapi.py:306），只查命令影响的那几个种子 ⇒ 真值到达压到几十毫秒， 10 ms 目标可望可即。

分支 B：是 qB 内部慢

若两者同一刻翻 ⇒ 1362 ms 就是 qB 自己处理 resume 的时间（做 resume-data 校验、 连 tracker 等），我们改不到。

应对：事件驱动仍然值得做（能省掉我们自己的 1.5~2 s），但必须接受 resume 的下界 ≈ 1.4 s；「撤下 10 ms」只能对 pause 成立（pause 的 qB 翻转待实测）。

怎么做（约半天）

在仿真端或真机上，resume 一个种子后同时以 ~50 ms 间隔轮询 /api/v2/torrents/info?hashes=X 与 /api/v2/sync/maindata， 记录两者各自的 state 翻转时刻，比较先后。

注意：sim_qb 是瞬时翻转的，测不出这个差异，必须在真机做 （或先给仿真端加一个"maindata 快照按 1.5 s 更新、info 实时"的模型）。

04 · 方案设计

事件驱动：推什么、挂在哪、前端怎么改

推什么（三类事件，全部小载荷）

表 2 · 事件契约
事件替代现在的什么载荷
cmd 前端轮询 /api/cmd/{id} {cmd_id, status, error, wait_ms, exec_ms, truth}
truth _pullTruthAfterCmd 反复拉全量 {hashes:[...], truth:{hash:{kind}}}
ver 常规 /api/state 轮询的触发信号 {ver}

关键决策：只推「信号」和「命令影响到的那几个种子的真值」，绝不推全量状态。 3000 种子库一轮全量是 63 ms 的序列化 + 网络 + JSON.parse，频繁推会把主线程打满 —— 那正好是这个项目踩过的坑（搜索索引 500 次文件 API 阻塞主循环）。

挂在哪（后端）

  • WebUIRuntime.set_result() / flush_receipts() → 推 cmd（含 truth）。这正是现在写回执的地方，改成"写完顺便推"即可。
  • WebUIRuntime._publish_locked() → 推 ver。它是唯一的视图发布入口（web_runtime.py:439），主循环侧、持 view_lock，语义上就是"产生了一版新状态"。
  • 主循环 → Web 线程必须非阻塞：主循环只往一个线程安全队列 put 事件，由 SSE 的生成器（跑在 Web 线程）取出发送。主循环绝不能直接写 socket —— 这条是硬约束，否则大库下命令会被推送拖住。

前端怎么改

  • waitCmd 从「退避轮询 /api/cmd/{id}」改为订阅 cmd 事件（保留轮询作为断线兜底）。直接省掉 0/150/300/500 ms 的粒度。
  • 撤下判定保持「依据真值」，但真值来源从"拉全量"改为"cmd/truth 事件里的真值"。
  • refresh() 的链式 setTimeout 改为由 ver 事件驱动；保留一个放宽后的兜底轮询（断线、重连、首帧仍需要）。
  • 现有 rid 门控语义要跟着改：pending_ver 现在是"这一版还没被 /api/state 取走"，推送场景下应改为"这一版已推送/已消费"。
// 后端：Web 线程侧的 SSE 生成器（示意，非最终代码）
async def events(request):
    q = runtime.subscribe()                 # 拿到一个订阅队列
    try:
        while True:
            ev = await q.get()              # 主循环只 put，不碰 socket
            yield {"event": ev.type, "data": json.dumps(ev.payload)}
    finally:
        runtime.unsubscribe(q)

// 主循环侧：非阻塞地“喊一声”
self.web.notify("cmd", {"cmd_id": ..., "status": "ok", "truth": truth})

05 · 通道选型

SSE 优于 WebSocket

表 3 · 通道对比（按本项目现状）
维度SSE（StreamingResponse）WebSocket
新依赖无（FastAPI / Starlette 原生）需要 websockets（当前未安装，已实测）
方向服务端 → 客户端（正是本需求）双向（用不上）
断线重连EventSource 自带重连需自己实现
鉴权不能带 header → 需 query token / cookie握手时可带 header
与现有 HTTP 中间件同一套路由/中间件/鉴权需单独处理
单测ASGI test client 可直接读流需 WS 测试客户端
建议 选 SSE。本需求是单向推送，SSE 零新依赖、自带重连、能复用现有鉴权与中间件， 单测也最好写。WebSocket 多出来的双向能力用不上，却要多装一个依赖并单独处理鉴权。

⚠ 两个 SSE 的实际坑：① 反代缓冲 —— 若前端经过 nginx 之类，需要关掉响应缓冲 （X-Accel-Buffering: no）；② EventSource 不能带 Authorization 头 —— 需要走 query token 或 cookie；本机 skip_local_verify 场景无碍，远程部署要单独设计。

07 · 风险与对策

改这个要小心什么

  1. 主循环绝不能被推送阻塞 这是本项目的头号教训（搜索索引 500 次文件 API 曾把主循环占满，导致命令排队数秒）。 对策：主循环只 put 到有界队列；队列满则丢弃/合并（推送是加速手段，丢了只是退化成轮询，不是错误）。
  2. 大库下的事件风暴 _publish_locked() 每轮同步都会自增版本号；3000 种子库下这很频繁。 对策：ver 事件做合并窗口（~100~200 ms 内的多次只推一次），并且只推版本号不推数据。
  3. 推送不能取代兜底 断线、重连、首帧、qB 断连期间都必须还能工作。对策：保留 /api/state 轮询作为兜底 （间隔可放宽），SSE 断开时自动退回；恢复后拉一次全量对齐。
  4. rid / pending_ver 语义要改 现在它是"这一版还没被 /api/state 取走"，用来做节拍对齐（防止主循环空转生产）。 推送场景下消费方变了，必须同步改，否则要么主循环被误判为"没人消费"而停摆，要么失去背压。
  5. 「撤下依据真值」的判据会被放大 一旦真值来得快，_optimisticSettled 的"真值 == 预测值"严格相等就会立刻变成瓶颈 —— resume 的预测值只有 downloading/seeding 两种，而落地态有 6 种 （checking*→checking、missingFiles→error、allocating/moving/unknown→other 永远不等）。这一条必须在同一批改动里解决，否则真值越快、卡在判据上的比例越高。
  6. 可测性 浏览器端已验证 agent-browser 可用（0.27.0 / Chrome 153 / Windows）， 可以做端到端冒烟；SSE 单测可用 ASGI test client 直接读流，不需要新工具。

08 · 分阶段

建议的推进顺序

  • P0 · 做 E1（约半天，阻塞后续） —— 判定 1362 ms 是快照滞后还是 qB 内部慢。 这一分支决定「10 ms」是不是一个可达目标，也决定 P1 要不要做。先做这个，别先写代码。
  • P1 · 真值改直查（仅当 E1 = A） —— 命令执行后对受影响的少数种子走 torrents/info 直查，绕过 sync 快照节奏。改动面小（_affected_truth 附近），收益最大。
  • P2 · 回执改推送 —— set_result/flush_receipts 处推 cmd 事件， 前端 waitCmd 改订阅。省掉回执轮询的 0/150/300/500 ms 粒度。
  • P3 · 视图版本改推送 —— _publish_locked 推 ver，前端轮询放宽为兜底。省掉 1.5/2/3 s。
  • P4 · 收尾 —— 删除过渡机制（_pullTruthAfterCmd 退避预算、 RECEIPT_WAIT_CAP_MS 扣留等），避免留下死字段；同步知识库与守阵测试。
  • 贯穿 · 撤下判据 —— 「真值 == 预测值」改成分动作判据（pause 要求暂停态； resume 只要求不再是暂停态），与 P1/P2 同期做，否则会成为新的瓶颈。

09 · 未覆盖

本报告没有回答的

  • E1 的答案 —— 这是刻意留下的前置未知，需要真机实验。
  • pause 的 qB 翻转时间 —— 没有真机的暂停日志，无法判断 pause 是否也有 1.4 s 量级的下界。
  • 远程部署 / 反代下的 SSE —— 只考虑了本机与直连；反向代理的缓冲与超时需另外设计。
  • 多实例 / 多用户 —— 当前是单实例锁（state.lock），推送的订阅管理按单实例设计。
  • SSE 与 skip_local_verify 的交互 —— 远程开启鉴权后，EventSource 无法带 header， 需要 query token 或 cookie 方案，本报告只标注了风险没给设计。
