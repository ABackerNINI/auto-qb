1摘要

问题
全部 12 个带遮罩的模态弹窗上滚动滚轮都会连带滚动背后的页面（种子列表所在），三皮肤（atlas / console / prism）无一例外；全库当前没有任何滚动链阻断手段。
机制（一句话）
前端是「整页滚动模型」—— 全站唯一的纵向滚动容器是 document（种子列表的行直接铺在文档流里）；弹窗虽是 position: fixed，但仍是 #app 的 DOM 后代，滚轮按 DOM 祖先链向上找最近可滚祖先，而弹窗层自身（.modal-mask / .modal）没有设置 overflow、不是滚动容器 —— 于是有内滚区的弹窗「滚到边界后」连锁到 document，无内滚区的弹窗「第一个滚轮事件」直达 document。
推荐方案（一句话）
主改动走 CSS：三皮肤共享壳 .modal-mask 加 overflow: hidden; overscroll-behavior: contain;（MDN 官方背书的「遮罩截断滚动链」用法，零布局位移、天然不伤无遮罩浮层），8 类弹窗内滚区顺手补 overscroll-behavior: contain，HR 全屏的专属遮罩 .hr-full-mask 单独补同一组规则；再在 JS 层加一个特征检测门控（CSS.supports('overscroll-behavior','contain') 为 false 才激活）的 wheel / touchmove 拦截，兜底老 Safari / iOS < 16。不选锁 document 派：本方案不存在滚动条位移问题，无需补偿，也无需动 12 个弹窗的开关逻辑。
需要拍板的分叉（详见 §5.4）
  1. JS 兜底是否本期一并做 —— 推荐做（约 40 行 vanilla，仅老 Safari / iOS < 16 生效，现代浏览器零开销）；也可拆第二期。
  2. 遮罩 overflow 用 hidden 还是 overflow-y: auto 变体 —— 推荐 hidden 起步 + 给 6 号通用壳补 max-height 作可选加固；auto 变体可兼防超高弹窗，但会引入 flex 居中溢出顶端不可达的边角问题。
  3. 无遮罩浮层（含「列」窗口）确认不改 —— 推荐维持用户假设：不改（裁决与理由见 §6.3）。

3机制诊断

3.1 主页面滚动结构（三皮肤一致：整页滚动模型）

  • 垂直滚动由 document 承担：html, body 只有 margin / preset，无 height / overflow 约束（atlas/style.css:141-142 · console/style.css:136-137 · prism/css/base.css:6-7）；全库 grep 无任何 html/body { overflow }。atlas/css/dialogs.css:10 注释自证：「整页滚动模型下 flex:1 不改变现状」。
  • 骨架：#app → .sticky-head（service-banner + header.topbar；sticky: position: sticky; top: 0; z-index: 30，console components.css:40 / prism:33，atlas 等价规则）+ .layout（grid，padding 含状态栏让位，atlas components.css:142-143）→ main.content（overflow-x: clip 只裁横向，atlas components.css:151 · console:144 · prism views.css:53）→ 视图内容。
  • 种子列表滚动容器：.group-table 只有 overflow-x: auto（仅横向），纵向不滚（atlas components.css:209 · console components.css:195 · prism views.css:140）；行直接铺在文档流里，纵向滚动 = document 滚动。分组 / 种子 / 追剧三个视图同构（groups.html:30 @scroll="syncGroupHeadScroll" 只同步横向列头）。种子视图额外挂 .torrents-dock flex column（atlas dialogs.css:11-13）与虚拟滚动 padding 行（torrents.html:22,98 row-pad，按文档滚动位置补偿）。

3.2 滚动容器链（按 DOM / 滚动规范推演）

document (html)  ←  【唯一的纵向滚动容器 = 种子列表所在】
└─ body
   └─ #app
      ├─ .sticky-head / .layout > .content > .group-table(仅横向滚) / 视图…
      └─ .modal-mask  (position: fixed; inset: 0; overflow: 未设 → 不是滚动容器)
         └─ .modal    (overflow: 未设; 仅 .add-dialog 变体有 max-height)
            └─ .add-dialog-body 等 (overflow-y: auto → 弹窗内自滚区)

关键事实链：

  1. 弹窗是背景滚动容器的 DOM 后代：所有 modal-mask 都由 boot.js 注入 #app（boot.js:67，atlas/index.html:132-146）。虽然 position: fixed 使其脱离布局流，但 wheel 事件的滚动链按 DOM 祖先链向上找「最近可滚祖先」，fixed 定位只改包含块、不改滚动链。
  2. 弹窗层自身不可滚：.modal-mask 与 .modal 均未设 overflow（atlas components.css:546-549），溢出可见 → 不是链上的滚动容器。
  3. 没有中间滚动容器兜底：modal-mask 是 .content / .group-table 的兄弟节点而非后代，链上从弹窗到 document 之间没有任何 overflow: auto 的元素 —— 弹窗内滚区滚尽后，下一站直接是 document。
  4. document 一滚，种子列表就滚：因为列表纵向滚动就是文档滚动（3.1 节），弹窗遮罩后面整个页面（含吸顶表头之下的全部行）跟着位移。

4.1 流派 A：CSS overscroll-behavior（contain / none）

  • [规范语义] 作用对象：CSS Overscroll Behavior L1 明确 "Applies to: scroll container elements"（https://drafts.csswg.org/css-overscroll-1/）；MDN 侧注："this property applies only to scroll containers… setting this property on an iframe has no effect"（https://developer.mozilla.org/en-US/docs/Web/CSS/overscroll-behavior）。Inherited: no —— 对非滚动容器设置无效。
  • [规范语义] contain："no scroll chaining occurs on neighboring scrolling areas; the underlying elements will not scroll"（MDN）；规范："the element must not perform non-local boundary default actions"。none：在 contain 之上再禁掉本元素自己的边界默认行为（回弹 / 下拉刷新等）。
  • [规范语义] 关键条款（直接命中本项目「遮罩无内滚」形态）：规范 "If a scroll container has no potential to scroll… the element is always considered to be at the scroll boundary"；MDN 展开原文："A scroll container that has no scrollable overflow, such as an element with overflow: hidden, is always considered to be at its scroll boundary. So setting a non-default overscroll-behavior such as contain or none on it will prevent scroll chaining to ancestor scroll containers. This can be used to prevent background scrolling while a dialog or overlay is open."（MDN overscroll-behavior 页，2026 年现行版）—— 这是「遮罩 + overflow:hidden + contain」组合的官方明文背书。
  • [本项目适配] 对两种形态的适用性：① 有内滚区弹窗：内滚区加 contain 即可止住「到边界后连锁」（MDN 官方示例场景），但滚轮落在标题 / 按钮 / 遮罩空白时链不经过内滚区，单独用①挡不住全部穿透；② 无内滚区弹窗：.modal-mask 加 overflow: hidden 使其成为滚动容器 + contain/none，遮罩覆盖整个视口、滚轮目标必然在遮罩子树内 → 理论全覆盖。变体：.modal-mask { overflow-y: auto; overscroll-behavior: contain; }，遮罩自身成为真正的滚动容器，兼带「超高弹窗可在遮罩内滚动」的能力。浏览器差异：Chromium 旧版对 hidden 组合的处理未证实（未检索到权威 bug 单）；caniuse 将所有厂商标为 partial support。
  • [主流实践] 兼容线（https://caniuse.com/mdn-css_properties_overscroll-behavior，2026-10 查询）：Chrome 63+（63–143 partial，144+ full）、Edge 18+、Firefox 59+（partial，150+ full）、Safari 16.0+（partial）、iOS Safari 16.0+（partial）、Chrome Android 154 full。结论：Safari / iOS 支持线是 16（2022-09），更老的 iOS 需 JS 兜底；caniuse 全线标 partial（≈96% 全局覆盖：71.84% full + 24.19% partial）。
  • [本项目适配] 对无遮罩浮层是否误伤：两种形态都只写在 .modal-mask / 内滚区上，.col-menu 等无遮罩浮层不含这些类 → 不误伤。

4.2 流派 C：锁 document（Bootstrap / element-plus / Vuetify / antd 路）

  • Bootstrap 5 [主流实践]：开弹窗时 body 加 .modal-open（CSS overflow: hidden），JS 端 Scrollbar.hide()（https://github.com/twbs/bootstrap/blob/main/js/src/util/scrollbar.js，经 jsdelivr 5.3.3 核实）：element.style.overflow = 'hidden'；滚动条消失补偿 padding-right += width（宽度实测 Math.abs(window.innerWidth - document.documentElement.clientWidth)）；额外补偿 .fixed-top, .fixed-bottom, .is-fixed, .sticky-top 的 padding-right（sticky-top 还加负 margin-right），且只补实际伸进滚动条区的元素。文档：https://getbootstrap.com/docs/5.3/components/modal/。现代替代：scrollbar-gutter: stable（https://developer.mozilla.org/en-US/docs/Web/CSS/scrollbar-gutter："the gutter will be present if overflow is auto, scroll, or hidden even if the box is not overflowing"，classic scrollbars 下；Baseline 2024，2024-12 起 all evergreen；通常口径 Chrome 94+ / Firefox 97+ / Safari 18.2+，后两个版本号未证实）。
  • element-plus [主流实践]：packages/hooks/use-lockscreen/index.ts（https://github.com/element-plus/element-plus/blob/dev/packages/hooks/use-lockscreen/index.ts，经 jsdelivr 核实）：弹窗打开 → body 加类 el-popup-parent--hidden；补偿用 width 而非 padding：document.body.style.width = calc(100% - ${scrollBarWidth}px)；清理延迟 200ms（源码注释：兼容 jsdom 场景），onScopeDispose 兜底；无引用计数 —— 每个叠加弹窗各自清理，仅靠 withoutHiddenClass 判断防重复加类，多层弹窗退栈顺序敏感是已知弱点。
  • Vuetify [主流实践]（Vue 生态，VueTorrent 的底层）：packages/vuetify/src/components/VOverlay/scrollStrategies.ts（https://github.com/vuetifyjs/vuetify，经 jsdelivr 核实）：scrollStrategy prop default: 'block'（另有 none / close / reposition）；block 策略对目标与内容元素的所有 scroll parents（去重）：① 把当前滚动位置存进 CSS 变量 --v-body-scroll-x/y，② 实测滚动条宽 window.innerWidth - document.documentElement.offsetWidth 设为 --v-scrollbar-offset，③ 加类 v-overlay-scroll-blocked（CSS 端 overflow hidden + padding 补偿）；关闭时 scrollBehavior='auto' 防动画、按变量恢复 scrollLeft/scrollTop、移除类与变量；含「html 仅在其 overflow 为 scroll 时才设 offset」的细节特判。
  • ant-design [主流实践]：官方文档 Modal 有 scrollLock prop（"Whether to lock body scroll when modal opens"，default true，6.5.0 引入）—— https://ant.design/components/modal（已核实）。底层 rc-dialog 的 getScrollBarSize + body padding-right 补偿是社区通行记载，本次未逐行核实实现文件 → 实现细节未证实。
  • 副作用清单 [主流实践 + 规范外共识]：① 布局抖动：滚动条消失 → 页宽跳变 → 三家都用补偿（Bootstrap padding-right / element-plus width calc / Vuetify CSS 变量）；② 滚动位置丢失：iOS Safari 上 overflow: hidden 对 body 历史上不可靠，position: fixed 补法会复位滚动位置 —— body-scroll-lock-upgrade README 原文："overflow: hidden doesn't work for all browsers"、"position: fixed causes the body scroll to reset"（https://github.com/rick-liruixin/body-scroll-lock-upgrade）；③ 多层弹窗退栈需引用计数（element-plus 无计数是前车之鉴；Vuetify 用 scroll-parent 去重 + class 判重）；④ 本项目 document 即滚动器，body overflow hidden 直接作用于滚动器本体，桌面端有效，但 3 套皮肤都要配补偿，且 Esc 退栈要接计数。

4.3 流派 D：JS 事件拦截（wheel / touchmove preventDefault）

  • [规范语义 + 版本史] passive 默认化的影响：MDN addEventListener（https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener）："If this option is not specified, it defaults to false — except that it defaults to true for wheel, mousewheel, touchstart, and touchmove events on Window, Document, Document.documentElement, and Document.body." → 元素级监听（挂在 .modal-mask 上）不受默认化影响，preventDefault 可直接生效；document 级则必须显式 {passive:false}。版本史：Chrome 73 把 root 目标（window / document / body）的 wheel / mousewheel 监听默认 passive（https://developer.chrome.com/blog/scrolling-intervention-2，https://chromestatus.com/feature/6662647093133312）；Chrome 56 对 document 级 touchstart / touchmove 默认 passive（通行记载，官方原文抓取超时 → 版本细节未逐字核实）。
  • body-scroll-lock / body-scroll-lock-upgrade [主流实践]（https://github.com/rick-liruixin/body-scroll-lock-upgrade，README 核实；原版 willmcpo/body-scroll-lock 已停维护）：策略 = 锁 document + touchmove preventDefault 混合：body overflow hidden + reserveScrollBarGap 选项补 padding-right；iOS 上 document 级 touchmove preventDefault；保留目标滚动：allowTouchMove 回调 / body-scroll-lock-ignore 属性向上遍历 DOM 判定，命中则不 preventDefault —— 即「事件拦截只拦目标以外的触摸滚动」；明确反对裸 document.body.ontouchmove = e => e.preventDefault()：会连弹窗内滚一起锁死，也警告粗暴方案破坏 iOS 惯性 / 橡皮筋。
  • react-remove-scroll [主流实践]（https://github.com/theKashey/react-remove-scroll，README 核实）：策略 = 纯事件拦截：非 passive wheel / touchmove 监听同步阻断；支持嵌套滚动容器与 shards（锁外仍可交互区域）；多层锁只有最后一个生效；不用 position:fixed，滚动条空间用配套 react-remove-scroll-bar 保持（zeroRight / fullWidth 辅助类）；noRelative 防 body 被加 position: relative；README 自述两个坑：非 passive 监听 "may affect scrolling performance"；inert 模式 "disables events the rest of page completely using pointer-events" 且 "not portals friendly"；iOS：touch 内建处理，-webkit-overflow-scrolling: touch 建议加在滚动目标上。

4.4 流派 E：<dialog> showModal 与 inert

  • [规范语义] showModal 是否原生锁背景滚动：否。MDN："Elements inside the same document as the dialog, except the dialog and its descendants, become inert (as if the inert attribute is specified)" —— 只提 inert（非交互化），全页无一句滚动相关表述（https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/showModal）。
  • [规范语义 + 实践推论] inert 能否阻止滚轮滚动：不能。MDN inert 属性列出的全部被禁行为为：click 事件、focus、find-in-page、文本选择、编辑、无障碍树暴露 —— 不包含滚动（https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inert）。社区同结论，补救即 CSS：body:has(dialog[open]) { overflow: hidden; }（https://www.amitmerchant.com/how-to-disable-scrolling-the-page-behind-a-dialog-element/）。whatwg/html 有关于 modal dialog 应否内置 scroll lock 的 issue（本次未定位到具体编号 → 未证实）。
  • [主流实践] Vue 生态组合：Teleport / Portal + 背景 inert / aria-hidden + 独立的滚动锁三件套。Radix（React 代表）的 @radix-ui/react-dialog package.json 依赖实证：react-remove-scroll: ^2.7.2 + aria-hidden: ^1.2.4（npm 核实）—— 即官方组件库也承认「inert 不锁滚动」，需另配滚动锁库。Vue 侧积木：VueUse useScrollLock（可写 ref 控制）。
  • [本项目适配] 12 个弹窗换 <dialog> 属大改（3 皮肤同构但结构各异），收益仅 focus 管理与 top layer，滚动锁仍要另做 → 不建议。

5推荐方案与备选

5.1 推荐主案（CSS 层为主，B + A 组合，可叠加）

第一层（主改动）：三皮肤共用的 .modal-mask 加一组规则（atlas/css/components.css:546、console/css/components.css:461、prism/css/components.css:235 三处各 +1 行）：

/* 三皮肤 .modal-mask 各追加: */
.modal-mask { overflow: hidden; overscroll-behavior: contain; }

理由：① 规范与 MDN 明文背书（4.1 节引文：无滚动潜力的滚动容器恒在边界上，设 contain 即阻断向祖先连锁，官方场景就是 dialog / overlay），一行 CSS 覆盖「有内滚区」与「无内滚区」两类形态 —— 遮罩覆盖整个视口，滚轮目标必然在遮罩子树内，链上最近滚动容器即遮罩；② 零布局位移、无需滚动条补偿、无需动 12 个弹窗的开关逻辑；③ 只碰 .modal-mask 类，天然不伤无遮罩浮层（.col-menu 等不含该类）；④ qB 官方 WebUI 证明问题在「document 滚动器」这一布局形态，本方案不动布局架构、改动面最小。

第二层（顺手加固，A 档）：8 类弹窗内滚区补 overscroll-behavior: contain —— .add-dialog-body（atlas/css/dialogs.css:205）、.add-pop-list（dialogs.css:248）、.db-list（atlas/css/views.css:276）、.mgr-list（atlas dialogs.css:347）、.meta-tags（dialogs.css:372）、.modal-members（atlas/css/views.css:256）、.kb-help-body（shared/console_hub.css:1109）、.hr-full-modal-bd（atlas dialogs.css:197）。即使主层已兜住，这层仍是双保险（防日后某弹窗脱离遮罩壳或遮罩规则被覆盖），且单独修复「内滚区到边界后连锁」这一半语义。

第三层（HR 全屏特例，必须单列）：12 号 HR 站点状态全屏用的是专属遮罩 .hr-full-mask（atlas dialogs.css:187-188，z-index 128，top/bottom 用 --head-h / --statusbar-h 变量），且遮罩与 .hr-full-modal 是兄弟元素、不含 .modal-mask 类名 —— 共享壳改动覆盖不到它。需在 atlas/console 的 dialogs.css 与 prism 的 components.css（dialogs.css:186 注释自证「三套 UI 成对改」）给 .hr-full-mask 补同一组 overflow: hidden; overscroll-behavior: contain;，并给 .hr-full-modal-bd 补 contain。

第四层（JS 兜底，收窄版 D，仅老 Safari / iOS < 16 生效）：

  • 激活门控：CSS.supports('overscroll-behavior', 'contain') 为 false 才启用 —— 现代浏览器（Chrome 63+ / Firefox 59+ / Safari 16+）零开销、零行为差异。
  • 挂点修正：阶段 2 提议挂在 ui_feedback.js:_openModal（ui_feedback.js:87），但阶段 1 证据显示 _openModal 只驱动 6 号通用壳（其余 11 个弹窗各有独立 Vue 标志与打开方法，且没有公共 open/close 管理器，见 §2.1）。若要 12/12 全覆盖，兜底应改为单点 document 级捕获监听：wheel + touchmove 各挂一个 {passive: false} 捕获监听（门控在监听器内部再查一次，双保险），回调里现查 document.querySelector('.modal-mask, .hr-full-mask') 是否存在 —— 存在且事件路径不在放行名单内才 preventDefault()。选 document 级而非逐遮罩挂监听的原因：① 单点覆盖全部 12 弹窗与未来新增；② 弹窗叠加（1 添加种子 → 2 选择保存位置，dialogs-mgr.html:85 → add_torrent.js:202 真实存在）无需退栈计数 —— 监听常驻、每次事件现查状态，v-if 卸载自然失效；③ 门控保证现代浏览器根本不走这条路（注意 MDN passive 默认化条款：document 级 wheel 监听在实施干预的浏览器里默认 passive，必须显式 {passive:false}，而兜底目标老 Safari 无此默认化，同样显式写、防御性兼容两侧）。
  • 放行名单（allow-list）：事件路径（composedPath() 或 target.closest 向上遍历）命中 8 类内滚区类名（见第二层清单）则不拦截 —— body-scroll-lock 的 allowTouchMove 同款思路。三皮肤内滚区类名阶段 1 结论是同构，名单一份即可。
  • 成本：约 40 行 vanilla JS，无需引库、无需 vendor。

5.2 为什么不选锁 document 派（流派 C）

  • 无滚动条位移问题可赚：C 的全部复杂度（三家生产库都要写的滚动条宽度补偿）源于「锁掉滚动器后滚动条消失、页宽跳变」。推荐主案 B+A 根本不锁 document，滚动条全程不动，补偿代码一行都不需要 —— C 在本项目里只有成本、没有增量收益。
  • iOS 老 Safari 位置丢失史：body overflow hidden 历史上不可靠、position:fixed 补法复位滚动位置（body-scroll-lock-upgrade README 原文，4.2 节）—— 恰在兜底目标人群上更不可靠。
  • 改动面与状态管理成本最高：12 弹窗 × 3 皮肤的打开点收拢（本项目没有公共 open/close 管理器，需新增一层）+ 多层弹窗引用计数（1→2 选择位置叠加真实存在；element-plus 无计数是前车之鉴）+ Esc 退栈链（lifecycle.js:56-88）要接计数恢复。
  • 全局锁的误伤面：锁 document 是全局的，弹窗开着期间连无遮罩浮层也被锁；B+A 只碰遮罩子树。

5.3 备选取舍一览

备选取舍结论
C 锁 document + 补偿不采用。见 5.2：无滚动条位移可赚，却有补偿 + 计数 + iOS 位置丢失三重成本，收益不比 B+A 多。
D 全量常开（react-remove-scroll 式，无特征检测）不采用。非 passive 监听常开的性能损耗（库 README 自述）、allow-list 误锁风险、键盘滚动不覆盖 —— 仅收窄为「特征检测门控的老浏览器兜底」才值得（即 5.1 第四层）。
E 换 <dialog> / Teleport + inert不采用。inert 不锁滚动（MDN 规范语义，4.4 节），换完仍要另做滚动锁；12 弹窗 × 3 皮肤重构不值。
仅 A（只给内滚区加 contain）不够。滚轮落在标题 / 按钮 / 遮罩空白时链不经过内滚区，无内滚区弹窗（7 / 9 / 10 / 6 号短形态）完全挡不住 —— 必须与 B 组合。
照搬 qB 官方（内部面板滚动架构）不在本轮范围。官方是「让 document 不成为滚动器」的架构性回避，等于重排整页布局模型；可作远期方向，与本修复不冲突。

5.4 需要用户拍板的分叉

分叉① JS 兜底是否本期做
推荐：做（约 40 行，document 级捕获 + CSS.supports 门控 + 8 类白名单，见 5.1 第四层）。不做的话，Safari < 16 / iOS < 16（caniuse 支持线，2026 年存量占比低但非零）上 12 个弹窗的穿透维持现状。可拆第二期：CSS 主案先上，兜底单独一轮（白名单需逐弹窗核对后另验）。
分叉② 遮罩 overflow 用 hidden 还是 auto 变体
推荐：overflow: hidden 起步（最小改动、无 flex 溢出边角）。依据：.modal-mask 是 flex + align-items: center，若改 overflow-y: auto，超高弹窗在 flex 居中下会触发「溢出起始边不可达」的经典问题，需连带改 align-items: safe center 或 flex-start + .modal { margin: auto }，复杂度上升。风险点在 6 号通用壳：.modal 本体无 max-height（atlas components.css:549），长内容确认框（如删除确认 wide+checks+details，delete_flow.js:200）在矮视口可能超出视口高，hidden 会把超出部分裁成不可达（现状靠背景滚动「救」）。可选加固子选项：给 6 号壳补 max-height（与 1 号同款 calc(100vh - 120px)）并让其 body 内滚 —— 是否纳入本期由用户定。
分叉③ 无遮罩浮层（含「列」窗口）确认不改
推荐：不改，与用户假设一致。完整裁决见 §6.3 —— 此处确认：推荐方案的全部落点（.modal-mask / .hr-full-mask / 8 类内滚区）都不含任何无遮罩浮层类名，零误伤。

6.3 无遮罩浮层判定与用户假设裁决

用户原话：「添加种子弹窗需要改，但"列"窗口应该不需要改」。

裁决：假设成立 —— 遮罩 / 无遮罩这条分界线可以作为「要改 / 不改」的判据
  • 事实核对无误：添加种子弹窗（1 号）确是遮罩模态且有内滚区（.add-dialog-body，滚到边界后连锁，dialogs-mgr.html:5-7 + atlas/css/dialogs.css:205-207）；「列」窗口确是无遮罩的 .col-menu 弹层（topbar.html:73；CSS max-height: 70vh; overflow-y: auto，atlas views.css:107 · console views.css:80 · prism components.css:404；右键路径 JS 动态 fixed + maxHeight + overflowY:auto，columns.js:33-37）。
  • 判据的机制依据（为什么分界线成立）：违和感的本质是「视觉隔绝」与「背景滚动」的矛盾 —— 遮罩弹窗在视觉上宣告背景不可交互，背景跟着滚才是缺陷；无遮罩浮层不隔绝背景、页面本可交互，其滚动链传到 document 的观感 ≈ 「页面继续往下滚」的正常语义（与抽屉 drawer 同判，§2.3；限速浮层同判，§3.3）。「列」窗口自身滚到边界后确实也会连锁滚背景，但这与用户直接滚动页面滚到底后「停下来」还是「背景（其实就是页面本身）继续」是同一件事，不构成缺陷。
  • 判据同时是改动面的自然边界（为什么可执行）：推荐方案只触碰 .modal-mask、.hr-full-mask 与遮罩模态的内滚区类 —— .col-menu 等无遮罩浮层不含任何这些类，零改动、零误伤。判据不需要人为维护，CSS 类名天然把两边切开。
  • 边界线内部的一层细化（不影响判定）：遮罩侧内部还有「有 / 无内滚区」第二层划分 —— 连锁时机不同（边界后连锁 vs 立即连锁），但 12 个都要改且都由共享壳一处覆盖（§6.1）；无遮罩侧的「列选择器 / 筛选器弹层」自身是滚动容器，同样滚到边界后连锁，但维持不改。
  • 唯一注意点：12 号 HR 全屏是遮罩侧的类名特例（.hr-full-mask），若实施时只改 .modal-mask 会漏掉它 —— 已在判定表单列。
无遮罩浮层判定理由
列选择器（「列」窗口）不改无遮罩，连锁观感 ≈ 正常页面滚动；修复面不含 .col-menu，零误伤

详情抽屉（drawer）不改文档流的一部分，非浮层（§2.3）

7.2 残留风险

  1. caniuse 全线 "partial support"：overflow: hidden + contain 在真实 Chromium / Safari 的边界行为需真机验证 —— 本次未检索到权威反例 bug 单，标注「未证实」而非不存在；用 dev.run --dry-run 真机 + DevTools 触屏模拟双验。
  2. 兜底白名单误锁内滚：JS 兜底的 allow-list 若漏登记某内滚区类，后果是弹窗内滚被误锁（比穿透更糟）。阶段 1 结论是三皮肤内滚区类名同构，名单一份即可，但落地前需按 §6.1 的 8 类逐一核对。
  3. 超高弹窗裁切（分叉②）：overflow: hidden 遮罩会让高于视口的弹窗盒无法触及（现状靠背景滚动补救）；6 号通用壳 .modal 无 max-height 是已知风险面，加固子选项见 §7.1 末行。
  4. 键盘滚动不在覆盖内：Space / PgDn / 方向键在焦点未入弹窗时仍可滚背景 —— 本修复只针对滚轮 / 触摸穿透，与本次目标一致，但需如实声明。
  5. contain 会同时关掉弹窗打开期间的浏览器下拉刷新 / 横滑导航手势—— 遮罩场景下属预期行为，非缺陷。
  6. JS 兜底的性能面：document 级非 passive wheel 监听若在现代浏览器常开会损耗滚动性能（react-remove-scroll README 自述同类坑）—— CSS.supports 门控保证现代浏览器根本不注册 / 不生效，实现时建议连监听注册一起门控（supports 通过则不注册）。
