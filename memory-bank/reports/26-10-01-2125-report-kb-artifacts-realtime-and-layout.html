0结论

两个命题分开裁定：生成物（各目录 _index.md）是否改为脚本实时生成；四工位（issues / plans / reports / tasks）是否改 pitfalls 式按专题分目录。

维持 · 生成物落盘
_index.md 不改全量实时生成

索引是「每次路由都读、每轮收尾才写一次」的高读低写件。落盘 + 生成器 + 三层守卫的现架构在 token 上不比现算贵（输出相同），却保住了零依赖直读、diff 审阅面、守卫载体。库内已有现算先例（kb.docmap / kb.active / kb.baseline），分界线已经画对。

不做 · 专题目录化
四工位维持平铺 + doc-topic 逻辑归组

pitfalls 模型成立的三条前提（封闭小分类学、扫读式访问、单件自足）在四工位全部不成立：doc-topic 是开放集（实测 162 个，69% 为单件），访问是点查，件有状态与跨件链。物理按专题归堆等于把已退役的物化路线换个更重的形态再来一遍。

可选 · 低风险增强
摘要截断 + 状态归档预案

真要对症做点什么：① issues 索引生成端补 SUMMARY_MAX 式截断（现无截断，20.2KB）；② tasks 索引已到 cap 的 95%，触顶时按状态归档 Done/Superseded 冻结件（冷占 71%），不是按专题分目录。

2命题一：生成物能否脚本实时生成（不落盘）

先把「生成物」分对类

「实时生成」只对可从库内其它数据推导的东西成立。逐类盘点后，命题实际收敛为 20 份 _index.md：

类别成员可否实时生成判据
纯派生20 份 _index.md可数据源是各件的三行头 / doc-* / issue-* meta / Status·Summary，生成器已在维护
已现算docmap / active / baseline 查询已是实时2026-09-29 起查询现算不落盘，库已完成这一步
点时快照plans / issues / reports HTML、tasks 档案、activeContext 切片不可制品是当时的现场与决策（拍板后冻结），切片是 agent 写的状态，无源可推
需真跑才有testing/baselines/ 基线切片不可数字来自真跑 test.full（35s 级）且历史数字不可重算，本就是一次性快照

三个方案的对比（对象：20 份 _index.md）

维度A · 落盘 + 生成器 + 守卫（现状）B · 全实时生成（不落盘）C · 混合：骨干落盘 + 过滤查询
单次读 token索引全文直读（1.2–24KB/次）全量输出同 A；加过滤参数后点查 0.3–2KB路由扫读 = A；点查 = B 的过滤输出
读路径依赖零依赖：Read 即得。IDE 注入上下文、未装 wrapper 的 agent、fresh clone、只读会话全部可达每次读取经 commands 引擎（子进程 0.3–1s）；wrapper 未装即断；路由可达性被绑死在工具链上扫读走 A，点查走 B
写路径成本每轮 KB 回写后跑一次 kb.index（约 1s）；索引合并冲突靠「重跑即解」零写、零冲突同 A
新鲜度与守卫三层守卫兜住：陈旧索引带着提交会红。红灯防的不只是过期，更是生成器漏跑、集合漂移、生成器本身坏掉（26-09-24 集合漏项事故、26-10-01 收编 issues 生成器都是这条线的维护记录）天然不过期，但「索引 == 生成结果」红灯失去比较对象，提交闸门对 memory-bank/ 的检查集合变空，生成器质量回归（test_index_is_regenerated）失去真实载体同 A
审阅与回溯索引进 git：diff 可审、历史可查输出不留痕，PR 里看不到索引变化同 A
实现面已有，零改动需统一查询入口覆盖 4 生成器 × 过滤参数；每加一个查询面都是新的脚本面积（生成器集合是事故易发区）给 4 个落盘生成器补 --topic/--status 过滤参数，闸门 note 同步
裁定：A 为主，选择性吸收 B 的一个局部优点 → C 的增量可选项

关键账是读写比与收益倒挂：索引每次会话都要读、每轮收尾才写一次；B 省下的只有「收尾跑 1 次 kb.index（约 1s）」和「偶发索引冲突（重跑即解，零思考动作）」，付出的却是每次读取子进程化、非命令上下文不可达、审阅面丢失、闸门收窄。而 B 唯一的 token 优势（过滤后点查省 80–98%）不需要放弃落盘就能拿到——C 在 A 之上加过滤参数即可。

更重要的视角校准：索引层全量 135KB 只占库的 1.7%。组织层优化的收益上限就是这 1.7% 里的路由差额；token 大头在制品层（plans+tasks+issues+reports ≈ 5.7MB，占 71%），而制品成本已经被「三行头 + 摘要 + 索引路由、禁止整读」压到「读一两个件」的水平。为路由层做架构手术，天花板很低。

库内先例（本分析最强的经验证据）

这个库不是没试过实时化，而是已经画对了一条分界线：路由骨干（低频写、高频读）落盘；点查视图与易变聚合（高频写或写热点）现算。2026-09-29 _doc-map.md 物化退役（写热点 + index-auto cap 反复触顶）改 kb.docmap 查询；kb-structure.md 把「生成 _recent.md 之类摘要缓存」列为反模式——「一个看着可读、实际是上次运行快照的文件比没跑脚本更危险」。本报告的裁定就是把这条已被实践校准过的分界线维持住。

3命题二：四工位改 pitfalls 式专题目录

pitfalls 模型为什么成立（三条前提）

2026-09-22 目录化重构（本专题的上一轮工作）把 pitfalls 做成 7 类目录 + 两级索引，它有效靠的是三条同时成立：

  1. 分类学小而封闭：7 类按动作域划分（backend / git / web-ui / testing / ops / kb / docs），枚举单点 PITFALL_CLASSES，「没有合适的类先扩枚举」——类是封闭集，不随项目功能线增长。
  2. 访问方式是扫读：每次改代码前「按动作选类 → 进类索引 → 选主题文件」，类级 cap（条目集 12,000）把单次扫读压在 4–10KB。
  3. 单件自足：一条陷阱一个文件，无状态机、无跨件链，文件即全部事实。

四工位逐条对照（前提全部不成立）

裁定：不做专题目录化

决定性数据是专题基数：162 个专题键、69% 单件——「不同的专题放入不同的文件夹」在四工位得到的不是归组而是碎片化。pitfalls 的类是「动作域」（改代码、跑 git、写测试），天然少而稳；四工位的专题是「项目功能线」（hr-verify、docker-deploy、webui-keyboard-shortcuts…），天然多而散。两者访问模式也不同：陷阱要扫，事件要点查。物理布局改变不了任何一次真实检索的 token 账。

那索引触 cap 了怎么办（真问题的真解法）

tasks/_index.md 已达 cap 的 95%，这是本分析里唯一真实迫近的结构压力。对症的顺手顺序：

  1. 生成端摘要截断（token 立减）：tasks 已有 SUMMARY_MAX=80，issues 生成器无截断——20.2KB / 62 条、均行 ~325B，长摘要是大头。对齐补一个截断策略，预计索引 -30~50%，一处生成器常量，无结构改动。
  2. 按状态归档，不是按专题：实测冷数据（Done + Superseded）占各索引 63–77%。Done/Superseded 是冻结终态（协议本身规定「终态即冻结」「拍板后冻结」），几乎只做考古。预案：冻结件移 */archive/（或按年分），索引只保活跃分区 + 归档汇总一行。判冷数据的字段是 status，不是 topic——状态会终结，专题不会，这就是状态归档对症而专题目录不对症的根本原因。
  3. 领域子目录留作远期预案：仅当单目录件数失控（如 plans > 200 件）或归档后索引二次触顶再议；届时 tasks 的 slug 领域枚举（8 类）是现成的分类学，pitfalls 的「扩类三处同步」配方也是现成的。
