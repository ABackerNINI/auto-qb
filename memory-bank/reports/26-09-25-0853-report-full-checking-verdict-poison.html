full-checking 误报「校验未通过」与批量不触发
故障取证分析

两个现象同源, 是一条因果链的两段: 校验结果轮询的首样本竞态误判产生假「校验失败」记录 → 该记录进入当日失败冷却并被即时落盘 → 同组其它成员被决策链 1.6「失败推断」静默拦截。误报的 WARNING 是链头, 批量不触发且无日志是链尾。

0 · 结论速览

核心结论

问题一(误报 WARNING): 校验结果轮询子任务(check-checking-result)的失败判定分支把「recheck 尚未被 qB 应用/尚未进同步快照」误读成「校验已跑完但未通过」。提交 recheck 后约 2s 的第一个任务线 tick 采样时, 种子状态还不是 checking 且 progress=0.0(跨种刚添加的典型初值), 三个条件恰好落进失败分支 —— 而此时 qB 侧的校验要么马上开始、要么已在进行, 最终正常完成。这是判定语义缺陷, 不是偶发抖动: 代码没有「本轮曾观察到 checking 态」或「启动宽限」的前提, 首个满足条件的样本立即定罪。

问题二(批量概率性不触发): 误判会调用 _bump_recheck_fail 写入 state["recheck_fails"][hash] 当日失败计数并即时落盘。此后同组、文件映射一致(同一物理数据)的其它成员在决策链 1.6 被直接跳过; 该 skip 日志是 DEBUG 级, 生产 INFO 日志下完全不可见 —— 即「无相关 log」。重启不解(state.json 当日记录仍在), 次日按日期口径自动归零恢复; 手动强校验当然成功, 因为数据本来就是好的。

用户假设验证: 成立。full_checking.py:208-228 的 _skip_on_group_check_failed 就是「同组校验失败(误判) + 文件映射一致 → 不再校验」的实现, 冷却即 recheck_fails 当日计数。「误判」的来源正是问题一 —— 两个问题是一个 bug 的两段表现, 掐断问题一的判定, 问题二的毒源随之消失。

2.3 决策链 1.6: 组内失败推断 full_checking.py:208-228

# _skip_on_group_check_failed: 组内其它成员校验失败且文件映射一致 -> 结果必然相同, 直接跳过
for h in members:
    if h == hash or _recheck_fail_count(manager, h) <= 0:   # 只要有失败记录(≥1 次)即命中, 不要求达上限
        continue
    if sizes.get(h) == mine:                                # 文件映射(相对路径->大小)完全一致
        return ActionResult.skip(f"同组种子 {h[:8]} 校验失败且文件映射一致(同一物理数据), 不再校验")

关键点: 触发条件是同组任一成员当日失败计数 ≥ 1 —— 1 次假失败就足以毒化全组; 文件映射一致性判据(group_sizes 相对路径→大小映射相等)对真实辅种恒成立。

  • 同步线(sync_interval 1.5s): 拉 qB /sync/torrents 增量, store 记录原地更新 —— 轮询读到的永远是「最近一次同步完成时」的快照。
  • 任务线(main_tick 2.0s): run_due 执行到期任务。轮询子任务 add_task 时 next_run=now, 但因 run_due 先快照后执行, 首样本必然落在下一个任务线 tick(≈提交后 2s)。

3.2 三个叠加因素

  1. qB 应用延迟: recheck 是透传请求, qB 收到到种子状态翻转存在异步间隙; 批量加入、qB 繁忙(校验队列串行)时间隙拉长。
  2. 同步快照滞后: 同步线 1.5s 节拍 + 增量轮只含有变化的种子 —— recheck 应用后总要等下一轮同步才进快照; 首样本读到的快照可能比判定时刻旧最多 ~1.5s。
  3. 判定无前提(决定性): 失败分支不要求「本轮曾观察到 checking 态」, 也没有启动宽限 —— 只要某个样本恰好落在「未开检」窗口内就定罪。taskqueue.py:169-171 注释显示同 tick 重入导致的同类误判已被防住(「避免同批重入导致未校验即误判失败」), 但跨 tick 的快照陈旧这层没防。

3.3 误判之后的分叉 —— 这正是问题二的入口

失败分支把 origin(规则任务)重置重入队, 下一个 tick 重走完整决策链。此时种子的 qB 状态决定走向:

分支重跑时种子状态走向失败计数后果
b·自愈仍是 stoppedDL(recheck 未应用)再次到达 full-checking → 重发 recheck + 新轮询 → 新轮询等到 checking → 成功成功时被 pop 清除仅留下一条噪音 WARNING
a·毒化已翻转(checkingResumeData / 已完成)决策链 0 拦截(checking.py:83-84 仅放行「暂停中未完成」) → 规则终了无人清除假失败记录常驻当日; progress=1 后决策链 0 永远 skip, 记录再无清除机会
c·三连击长时间未应用(qB 极忙)每次重跑都重发 recheck 又都误判 → 3 次后「今日不再重试」skip(DEBUG)=3, 常驻毒化更深, 且与分支 a 同样无人清除

概率来源: 分支 a 需要状态翻转恰好落在「首样本之后、origin 重跑之前」的窄窗内 —— 单发时是小概率; 而批量加入时任务积压把 origin 重跑推迟数个 tick, 几乎必然落在翻转之后, 毒化概率被显著放大。这与「一批辅种同时加入时」的现象高度吻合。

4.3 为什么「部分成功触发、部分不触发」

  • 组间差异: 每个组第一只被扫到的成员决定全组命运 —— 它若干净走完(首样本采到 checking 或落在分支 b), 全组随后逐个提交(配置两段均 full-checking, 组内 1.5 串行); 它若落进分支 a/c, 全组被 1.6 拦截。一批辅种跨多个组 → 现象呈「部分成功、部分哑火」。
  • 组内时间序: 同组内排在 A 之前/并发窗口内被处理的成员不受毒化, 排在其后的全部被拦。

6 · 修复方向建议(供拍板, 本报告未实现)

6.1 P1: 失败判定加「已见 checking」前提(掐断毒源)

  • 核心判据: 只有在本轮询周期内曾观察到 is_checking 之后出现的「非 checking 且 progress<1」才允许判败 —— 真实的校验失败必然经过 checking 态, 该判据不损失对真损坏数据的保护, RECHECK_FAIL_LIMIT 的防死循环语义原样保留。
  • 启动宽限兜底: 未见过 checking 时进入宽限(如 60s, 建议可配), 宽限内一律 REQUEUE; 宽限到期仍未开检 → 重发一次 recheck 而非计败(防 API 请求被 qB 静默丢弃的极端情形)。宽限值定多大可依 §7 未定案点的真机观察校准。
  • 不改: 「先登记在途、再发 recheck」的顺序(pitfalls/backend/concurrency.md:27-32 已有硬约束)与冷却计数即时落盘(behavior-core.md:77)。

6.2 P2: 假失败记录自愈 + 1.6 推断前置校验(解毒)

  • 自愈: _recheck_fail_count 命中时若该 hash 当前 progress≥1(检查实际已完成 = 记录必为假), 顺手清除记录(均在主循环线程, 无并发风险)。即使未来再出现新型假记录, 也会在下一轮扫描时自动消解。
  • 1.6 前置校验: 推断前校验「失败者仍是未完成的暂停态」; 已完成/已删除的失败记录视为陈旧, 不参与推断。与自愈二选一即可, 同时做更稳。

6.3 可观测性: 关键 skip 提级

  • 决策链 1.6 的「同组失败推断」skip 提到 INFO(本次故障中它就是唯一的哑火原因, 却不可见); 决策链 0 / 1.5 / 「今日不再重试」可保持 DEBUG 或同样提级 —— 以「用户排障时需要看到的最低集合」为准。
  • 误判发生时可在 WARNING 里带上「本轮是否曾观察到 checking」字段, 为后续定位留指纹。

6.4 测试影响

  • tests/test_checking.py:1280-1304 (test_checking_full_checking_fail_retry) 现把「非 checking + progress=0.5 → 判败」语义固化 —— 修判定需同步改造该用例(fail 模拟应改为「曾见 checking 后落回」)。
  • 建议新增回归: ① 首样本未见 checking → REQUEUE 而非判败; ② 宽限到期仍未开检 → 重发 recheck 不计败; ③ 假失败记录 + 同组成员 → 1.6 拦截 → 记录自愈后恢复触发的 e2e。

7 · 影响面与未定案点

7.1 影响面

  • 受影响: full-checking 轮询判定(poll 失败分支)与决策链 1.6 失败推断; 波及所有用 full-checking 的规则(r_rule / i_rule / h_rule 的无参考段 / hhan_checking_rules)。
  • 不受影响: skip-checking 四阶段流程; 决策链 1(组内有活跃下载); 「先登记后 recheck」顺序; 冷却即时落盘设计本身(它只是把假记录放大成了跨重启问题)。
  • 假阴性评估: 真实损坏数据的校验失败必然经过 checking 态, §6.1 判据不会放过它; 1.6 对「真失败」的推断语义(同组同数据 → 必然同结果)保持有效。

7.2 未定案点(不影响结论, 影响参数标定)

  • qB 对「已受理但排队未开检」的 recheck 报告何种状态(checkingResumeData 与否)未真机验证 —— 本结论不依赖它(日志已证明存在「非 checking 且 progress=0.0」的采样点), 但它决定 §6.1 启动宽限该定多大。
  • recheck_fails 条目仅在成功/种子删除时清除, 陈旧条目(过去日期)会常驻 state.json —— 轻微足迹问题, 与本故障独立, 修复时可顺带按日期清理。
