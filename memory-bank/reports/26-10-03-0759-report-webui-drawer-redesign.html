02成熟方案调研摘要

产品详情面板形态键盘行为可借鉴点
qBittorrent 桌面版 属性面板 (PropertiesWidget) 是可停靠面板, 默认停靠在传输列表下方, 可拖拽改靠右/隐藏; 选中行一变, 面板内容立即跟随 Alt+1~6 切属性页签; 列表上下键移动选中, 详情实时跟随; 无遮罩 方案 A 的布局先例; Alt+数字切详情页签的习惯与本站现状 (Alt+1-4) 一致
qBittorrent WebUI 选中种子后从工具栏唤出的右侧滑出属性面板 (浮层, 轻遮罩), 不清空列表 WebUI 键盘支持弱 (点击驱动) 「右缘滑出 + 列表仍可见」是已被验证的 Web 形态, 对应方案 C
Deluge (GTK 与官方 WebUI) 列表下方详情面板, 页签 Status / Details / Files / Peers / Trackers / Options; 选中即切换 点击驱动为主 方案 A 的直接先例 (WebUI 与桌面同构)
Transmission 桌面版 Inspector 独立窗口 (Ctrl/Cmd+I), Info / Activity / Trackers / Peers / Files, 跟随选中 独立窗口路线, 详情与列表彻底解耦 对 Web 端不适用 (无窗口概念), 仅作形态参考
Transmission WebUI 及社区前端 (TrguiNG / Flood) stock 版详情 = 浮层 inspector; TrguiNG / Flood = 主从分栏: 列表与详情常驻两栏 点击驱动为主, 光标键弱 方案 B 的先例; 也证明分栏在种子列表这种宽表场景会压缩列表列
ruTorrent 详情为可拖动的非模态浮窗, 列表仍可见可操作 点击驱动 「非模态浮层」先例: 浮层不必重遮罩
Gmail / Outlook 预览窗格 列表 + 阅读窗格常驻 j/k 或方向键移动高亮行, 阅读窗格实时跟随; 高亮行自动滚动进视口; 光标与选中分离 键盘跟随模型的黄金标准; 「光标行高亮 + 自动滚动」正是用户约束的解法骨架
Linear / Slack / GitHub 列表 列表页, Enter 进详情页 (Linear) 或右栏 (Slack) 方向键移动「活动行」, 活动行视觉强烈 (底色/描边); 边界夹取或循环; Enter 打开, Esc 退回 活动行视觉强度; 键盘流状态机 (列表 ⇄ 详情)
VS Code 资源管理器 / QuickOpen: 列表 + 单行 detail 区 上下键 + 右侧/底部 detail 跟随; 连发 (repeat) 时 detail 刷新节流 连发节流的必要性 (Web 端详情是 API 拉取, 不是桌面内存读取)

共识做法归纳

  1. 列表永远在场: 详情面板要么停靠 (下/右), 要么非模态浮层; 重遮罩 + 模糊列表几乎只出现在移动端小屏抽屉 (屏幕小才需要遮罩聚焦)。桌面级 Web 产品普遍不模糊列表。
  2. 光标与选择分离: 方向键移动光标, 详情跟随光标; 光标行视觉醒目 (描边或底色) 并自动滚动进视口。本站的 kbCursor + .kb-cursor 双语义模型与这一共识完全对齐, 可直接复用。
  3. 连动节流: 键盘连发时详情刷新必须防抖/取消在途请求 (桌面端读内存可以即时, Web 端每个 hash 一次 API)。
  4. 键位习惯: Alt+数字切详情页签 (qBt 系), Enter 开 / Esc 关 (通用), 上下键永远属于列表 (Gmail/Linear/VS Code 一致)。

03三个候选方案

每个方案都完整回答三个 issue 的功能缺口与「blur 下看不清列表当前行」约束。配对的交互原型见 memory-bank/reports/26-10-03-drawer-redesign-templates/ (plan-a / plan-b / plan-c 各一份, 静态假数据 + 原生 JS, 双击可开, 键盘可实际操作)。

方案 A底部停靠属性面板 (qBittorrent / Deluge 式)

┌──────────────────────────────────────────────────────┐ │ 顶栏 / 筛选 / 搜索 │ ├──────────────────────────────────────────────────────┤ │ 种子列表 (flex: 1, 光标行高亮 + 滚动跟随) │ │ row 3 │ │ ▶ row 4 <-- .kb-cursor, 详情面板跟随此行 --> │ │ row 5 │ ├────────────────── 拖拽调高 · 可收起 ──────────────────┤ │ 详情面板 (默认约 42vh, 全宽, 无任何遮罩) │ │ [常规] [Tracker] [用户] [内容] [×] │ │ 名称 / 哈希 / 大小 / 状态 / 进度 / HR … │ │ tracker 表 / peers 表获得全宽 (本站宽表受益) │ └──────────────────────────────────────────────────────┘

键盘交互: 上下键保持列表 scope 的光标语义 (现 _kbMove 不动), 光标变化 → 详情面板防抖跟随 (~200ms, 取消在途请求); Alt+1~4 提升为跨 scope —— 列表侧 = 开面板并定位页签 (顺带解决 drawer-open), 面板内 = 现切页行为; Enter 开/关面板, Esc 关面板回列表。

对 blur 问题的回答: 结构性消除 —— 不存在全屏遮罩, 列表整幅永久可见, 不需要任何补偿手段。

改造面与代价 (M-L): drawer.html 结构重排 (浮层 → 内嵌停靠面板); 种子视图容器改 flex column; 三皮肤 .drawer-mask/.drawer 族整体重写 (每皮肤 dialogs.css/views.css 头段); openTorrentDrawer/closeDrawer 语义调整 (开面板不再遮罩, 轮询逻辑不变); 注册表加 2-3 条目 + scope 调整。风险: 面板占高压缩列表可视行数; 追剧视图 / 组视图的兼容回归; 三皮肤视觉回归面大。

  • 优: 行业心智 (qBt/Deluge 同构); 键盘流最顺 (上下键天然属列表); tracker/peers 宽表获得全宽。
  • 缺: 竖向空间挤压 (小屏更明显); 模板与三皮肤大改; 既有「右缘抽屉」交互习惯重学。

方案 B主从分栏 (列表左 · 详情右常驻)

┌──────────────────────────────────────────────────────┐ │ 顶栏 / 筛选 / 搜索 │ ├───────────────────────────┬──────────────────────────┤ │ 种子列表 (约 58%, 常驻) │ 详情栏 (约 42%, 常驻) │ │ row 3 │ [常规] [Tracker] [用户]… │ │ ▶ row 4 (光标行, 跟随) │ 名称 / 哈希 / 大小 … │ │ row 5 │ │ └───────────────────────────┴──────────────────────────┘

键盘交互: 与 A 相同的跟随模型; Alt+1~4 同 A; 可选 ←/→ 在列表域与详情域间移焦点; Esc 收起详情栏回纯列表。

对 blur 问题的回答: 结构性消除 (无遮罩), 列表左栏永久可见。

改造面与代价 (L): 视图骨架 grid 重排; 本站列表 20+ 列 (columns.js), 分栏后水平挤压是最大痛点 —— 列宽偏好、列拖拽、行窗口化几何 (_rowPre 前缀和 / _kbViewportRow 视口判定按几何换算) 全部受列宽变化影响, 需逐一回归; 三皮肤 views/dialogs CSS 重排。风险: 三方案中回归面最大, 表头吸顶/列拖拽/搜索高亮等长尾联动多。

  • 优: 信息密度最高; 详情与列表完全同屏; 宽屏利用率好 (Flood/TrguiNG/Gmail 已验证)。
  • 缺: 宽表挤压最痛; 几何相关代码回归面大; 小屏退化需要另设计 (再套一层响应式)。

方案 C非模态浮层抽屉 (保留右缘抽屉 · 去 blur · 降遮罩 · 行高亮跟随)

┌──────────────────────────────────┬───────────────┐ │ 种子列表 (可见! 不再被模糊) │ 详情抽屉 │ │ │ 收窄约 560px │ │ ▶ row 4 <-- .kb-cursor 增强 + -->│ [常规][Trk]… │ │ <-- 自动滚动跟随 --> │ 字段… │ │ │ │ └──────────────────────────────────┴───────────────┘ 遮罩: 摘掉 backdrop-filter, 透明度 .5/.38 → 约 .15 (或无遮罩: 抽屉外点击 = 关闭, 列表 hover 不被拦截)

键盘交互: 抽屉 scope 新增 drawer-cursor-up / drawer-cursor-down 两个动作 (repeat 放行连发): 移动既有 kbCursor → _kbScrollRowIntoView → 换 drawer.hash 重拉详情 (防抖 + 取消在途); Esc 关抽屉回列表 (退栈链已有); Alt+1~4 双态 —— 列表侧 = 直接打开光标/选中种子的抽屉并定位页签 (解决 drawer-open), 抽屉内 = 维持现切页。

对 blur 问题的回答: 直接摘掉 backdrop-filter (全站归零, 给 PERF-01 收尾) + 遮罩透明度大幅下调; 光标行描边/底色对比度增强 + 自动滚动跟随; 抽屉收窄给列表让出可见区。模板里做了一个「旧遮罩 blur(2px) ⇄ 新轻遮罩」对比开关, 可直观看差异。

改造面与代价 (S-M): shortcuts.js +2 动作 + 派发规则小调; drawer.js 加一个 drawerNav(delta) (约 20 行, 复用 _kbRows/_kbScrollRowIntoView); 三皮肤遮罩各改 1-2 行 + shared/console_hub.css .kb-cursor 增强一处 (共用层单点); 模板基本不动, 页签记忆 / 长文本截断 / FX-22 全部保留。风险: 三方案最低。残留: 抽屉仍盖住列表右缘 (宽列表右侧列被挡); 重设计幅度有限, 信息密度问题只是缓解。

  • 优: 代价最小, 三个 issue 一波全解; 与既有交互连续 (无重学); 三皮肤并行维护代价小 (每皮肤两行)。
  • 缺: 浮层形态上限低 —— 布局/信息密度只能局部优化; 连发节流要做, 否则详情 API 风暴。

理由: C 用最小的改造面 (不动模板、三皮肤各两行) 一次性解决三个 issue 与 blur 硬约束, 不回退任何既有局部改进, 完全符合分波提交与范围守恒纪律; 而抽屉「整体重设计」(issue 2119 的完整答案) 更符合行业心智的终态是 A —— 建议在 C 落地、键盘流跑通后, 把 A 单独立计划推进。B 在本站 20+ 列宽表场景下挤压最痛、几何回归面最大, 不推荐为首选。

关联提示 (不纳入方案范围): 池内相邻条目 26-10-01-2108-feat-webui-selection-follow-mouse.html (选中跟随鼠标) 与本报告的「光标行视觉」是同一行状态的两套输入 (鼠标 / 键盘), 无论最终选哪个方案, 落地时给鼠标路径预留同一个行状态挂点即可, 将来可以零成本合流。
