双计划联合偏差审计报告

联合审计两份计划——前计划 26-10-11-1722(WEBUI 表格公共组件, P0–P5 已落地)与后计划 26-10-11-2106(WEBUI 抽屉重构, 执行至 W7)——以用户真实目标函数「所有表格统一、提供类似的交互逻辑、减少维护点」为基准, 给出偏差清单、量化账本与整改方向。本文是重审计划的输入, 不是整改实施。

1结论摘要

计划与目标在前提上分岔了。用户的目标函数是「表格能力统一 × 交互逻辑同源 × 维护点下降」; 计划 26-10-11-2106 的终态判据却是「抽屉只剩一套渲染技术」——它优化的度量是渲染技术份数, 不是表格能力覆盖和维护点数量。由此产生根本分岔: 面对变体表格与主表能力不统一的病灶, 计划开的药方是「删掉变体」(W5/W6), 而不是「统一变体表格」。前者已被用户裁定越权并经 W7 回收; 回收之后, 目标本身的缺口原封不动:

当前缺口 (W7 后实测)

抽屉 15 个数据表表面中, 只有 3 个(经典链 tracker/peer/file)吃到主表引擎能力; 8 个列表变体(tracker 04/05/06、用户 07/08/09、内容 10/11)仍是各自手搓的表格——0/8 拖宽、0/8 右键隐藏列、0/8 列偏好持久化, 其中 4 个变体(04/07/08/09)各带一套独立手搓的排序状态机与比较器。「表格统一」目标达成率: 7/15 表面, 变体侧 0%。

8 个波次中, 与目标直接相关的只有 W2(且只做一半——范围圈定在经典页); W5、W6、W7 三波(37.5%)耗在「错误前提的执行与回收」上。测试面同样偏差: 现有守阵与 e2e 钉的全是「经典接壳能力」和「变体原样行为」, 没有任何一条守阵钉「变体表格与主表交互逻辑一致」——目标从来没有进入过验收函数。

联合判定: 偏差是一条两计划链条, 不是单计划失误

把前计划 26-10-11-1722 一起审, 链条完整显形: ① 1722 是目标在 A+C 系统的正主且已完成(主视图 4 表 + 设置页 HR 3 表进引擎, A/B DOM 逐字节等价验收)——用户当日原始诉求里甚至点名了抽屉(「方便后续重构种子详情页用户列表/文件列表」), 因用户定调「抽屉完全重构、不考虑兼容」而合法移出范围, 遗留 P6 前向契约(至今未写)与条件性 DOM 适配。② 2106 正是从该 P6「另立专题」承接抽屉重构的——偏差不在 1722 的遗留定义里, 而在 2106 对它的翻译里: 目标函数从「表格统一」被换成「一套渲染技术」; 且「不考虑兼容 ≠ 可退役」, 1722 明确写的是「为重构后的面板预留接入面」(资产保留、能力接入), W5/W6 把它执行成了「删掉宿主」。③ 2106 W2 对经典 3 表的接壳(DRAWER_TABLE_DEFS, 与 HR_TABLE_DEFS 同法)是 P6 契约精神在代码侧的唯一兑现——即上表的 3/15。

全局达成率重算(含 1722 成果): 全 WebUI 数据表表面 18 个(主视图 4 + HR 3 + 抽屉经典 3 + 变体 8), 已统一 10/18(56%), 缺口 100% 集中在变体侧; 抽屉内部口径 3/11。1722 预留的条件性 DOM 适配(「仅当重构后的面板仍走字符串 DOM」)经 W7 恢复变体后条件已成立, 但无人认领——两计划交接处悬置着三件事: P6 契约文档、DOM 适配决策、变体表格接入。

2目标重述与判据

把用户在三次表态中的原话串起来, 目标函数有三条判据, 且彼此独立、缺一不可:

① 「本轮目标是更改详情模板中的表格, 将其与主表能力统一, 减少维护点, 从来没说过要动模板」(26-10-12 裁定);

② 「我需要的是所有表格统一, 提供类似的交互逻辑, 减少维护点」(26-10-12 重审指令);

③ 前置约束: 「全部模板原样找回」(26-10-12, 已由 W7 兑现)——模板是资产, 不是可弃物。

④ 目标源头: 「将种子页列表辅种表和追剧表提取为一个公共模板组件, 支持拖拽换位/拖拽调整宽度/点击排序/右键隐藏, 方便后续重构种子详情页用户列表/文件列表/设置中的各种表」(26-10-11, 1722 计划的用户原始诉求)——抽屉表格与设置页表格从第一份计划起就点名在案, 目标面从来不是只有主视图。

#判据可检验口径
G1所有表格统一抽屉内每一个数据列表表面(经典 + 全部变体)都具备主表四件套: 拖宽 / 排序 / 右键隐藏列 / 列偏好持久化
G2交互逻辑类似同一套手势语言与实现单点: 表头点击排序、边缘拖宽、右键菜单隐藏、偏好按表落 localStorage——不要求观感相同, 要求行为同源
G3维护点减少排序/拖宽/隐藏/持久化的逻辑实现份数下降且可数; 新增一个表格表面 = 声明一份列模型配置, 不再新写渲染与交互代码

注意 G1–G3 与「渲染技术份数」无直接关系: 经典是 Vue 组件、变体是字符串 DOM, 两套技术并存(用户已接受)不妨碍表格能力同源——能力在引擎里, 不在渲染技术里。

5偏差清单

P-1 · 交接偏差 (跨计划): 1722 的三件遗留悬置, 条件项被 W7 静默激活

1722 对抽屉的排除有用户定调背书, 范围决策本身无偏差; 偏差发生在交接处。1722 留给「重构后的面板」三件东西: ① P6 前向契约文档(描述符字段/行为开关/渲染器接口, 任务档案至今标「待做」); ② 条件性 DOM 适配 table-dom.js(触发条件: 重构后的面板仍走字符串 DOM——W7 恢复变体后该条件已成立, 但没有任何一方知晓或认领); ③ 抽屉表格的最终接入承诺(「用户列表/文件列表各注册一行 + 一个行渲染器」)。2106 作为承接者, 把目标函数从「表格统一」翻译成「一套渲染技术」, 三件遗留一件都没接住。

结构性根因: 两份计划之间没有共同的量化目标函数作交接物——1722 的终态判据是「新增一张表 = 注册一行」(可数), 2106 的终态判据是「一套渲染技术」(不可数、且与表格无关)。交接丢的不是需求, 是度量衡。

P0 · 前提偏差: 计划优化了错误的度量

偏差: 计划的终态判据写成「抽屉只剩一套渲染技术」, 由此把「变体」整体定义为待清除物(W5 变体退役 → 声明式密度档; W6 选择层退役)。但用户目标里的「减少维护点」指的是表格交互逻辑的实现份数, 不是渲染技术份数; 且用户对变体的态度始终是「保留模板能力」(W7 已裁定量)。对同一病灶(变体表格能力缺失), 计划选择了消灭宿主, 而非统一能力。

后果: 即便 W5/W6 没有越权、顺利落地, 密度档也只统一「密度与结构开关」——变体表格照样没有拖宽/隐藏/偏好, G1–G3 一条都不满足。这个计划即使完全按计划成功, 也是一次与目标无关的成功。对照前计划: 1722 的终态判据(「新增一张表 = 注册一行描述符 + 一个渲染器」)恰好就是 G3 的可检验形态——同一用户、同一天, 一份计划把目标写对了, 另一份写错了。

P1 · 范围偏差: W2 只圈了经典页, 「所有表格」只覆盖 3/15

W2 的接壳(列模型注册 DRAWER_TABLE_DEFS 并入 ALL_TABLE_DEFS + 三个行渲染器)是目标正主, 但范围被写成「经典页三列表」。变体的 8 份手搓表当时就在同一面板里、消费同一批数据(drawer.trackers/peers/files), 却从未被列入接壳清单——「所有表格统一」在第 2 波就变成了「经典三表统一」。引擎侧本来已具备多表消费结构(tableDefs 按表 id 遍历、偏好按 table-id 隔离), 变体接壳不存在引擎障碍, 纯属范围划定遗漏。

P2 · 验收偏差: 目标从未进入验收函数

八波验收全部是「测试数字 + 红验 + 基线切片」, 没有任何一波验收过: ① 能力矩阵缺口收敛了多少; ② 交互逻辑实现份数下降了多少; ③ 新旧表格手势是否同源。没有量化指标的目标等于没有目标——这也是 W5/W6 偏离后三波才被发现的结构性原因: 验收函数探测不到「离目标更远了」这种事。

P3 · 测试偏差: 守阵钉的是实现, 不是目标

现状守阵分布: drawer-tables.spec.mjs 钉经典接壳能力(拖宽/排序/右键隐藏/偏好), 4 条变体 spec 钉变体自身行为(dt11 吸顶 / peers 列 / sticky / reannounce), panel 守阵钉接线与结构。零守阵钉「变体表格行为与主表一致」或「排序实现单点」——假如明天有人再往某个变体里加一套手搓排序, 全部绿灯。测试保护的是 W2/W7 的既成事实, 不保护 G1–G3。

P4 · 文档偏差: 债务没有入账

模块文档 webui-static-contract.md、坑档、任务档案的全部记录围绕「退役/恢复」叙事展开; 「变体表格与主表能力不统一」这个最大的已知债务, 只在 W2 条以「经典侧完成」的口吻出现过, 从未作为未清项登记。26-10-07-0542 的 15 变体摸排报告其实已盘点过变体问题, 但其结论被 W5 的「退役」路线吸收后随退役一起消失, 没有转化为接壳需求。

7整改方向与建议

方向 A · 变体表格体接引擎 (全量统一, 推荐)

变体保留版式外壳与专属交互(卡片/分组/树/批量条), 列表体接 aq-table 引擎: 每变体声明一份列模型(可复用/裁剪 DRAWER_*_COLUMNS, 允许列子集与默认排序), 注册进 DRAWER_TABLE_DEFS——引擎按 table-id 遍历、偏好按 table-id 隔离, 已天然支持多表。需要先做的引擎扩展(spike): ① 列子集/默认列可见性声明; ② 排序字段泛化(现 state.js 六字段按经典三表硬编码, 需改 per-table-id 通用); ③ 引擎在变体宿主 DOM 内的挂载验证(aq-table 是全局组件, 变体宿主在其内可用, 但 headRef/tableRef 的 DOM 兜底路径需实测)。

代价: 引擎 spike + 8 个变体的表格体改造(tracker 3 / 用户 3 / 内容 2); 收益: G1–G3 全达成, 逻辑实现 9→1 份, 排序 5→1 份, 注入 CSS −约 500 条。

技术路线 fork(1722 已预留, 重审计划必须拍板): 变体是字符串 DOM, 引擎行为是 Vue 根实例单点——变体接壳有两条已铺好的路: ① DOM 适配 table-dom.js(1722 §03 ③b 条件项, 触发条件经 W7 已成立): 变体表格体产出与 aq-table 同类名的 DOM, 手势与状态经引擎单点(1722 已写明复用 dtHtml 转义单点 + H.wireEvents 委托); ② 变体表格体 Vue 组件化: dtVueTab 双分支已存在, 增加「变体外壳 + 引擎表体」混合分支, 表格体不再走字符串 DOM。①保变体技术形态(贴合「模板原样找回」精神), ②少一层适配但动变体表格体渲染技术。另注意 1722 D3=B 先例: 排序语义特殊的表(HR、可能的树表 10/11)可以只借壳不并排序——「行为同源 ≠ 实现合并」。

方向 B · 变体原地补能力 (不接壳)

给 8 份手搓表逐个补拖宽/隐藏/偏好。反对理由: 等于重造 8 份引擎, G3 直接反向——列为对照项, 不推荐。

方向 C · 用户表三变体先行 (A 的起步节奏)

07/08/09 三个 peers 变体先行接壳(用户点名的表), 验证引擎扩展与变体宿主挂载架构, 再推广到 tracker/内容组。风险最小, 每步可独立验收。
