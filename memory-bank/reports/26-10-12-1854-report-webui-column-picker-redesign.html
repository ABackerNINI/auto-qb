Research Report · Column Picker IA

WEBUI「列」选择器
信息架构重设计 · 方案调研与对比

用户报「表格太多，统一到『列』按钮里显得杂乱难寻」。本报告先量化取证这一体感的成因（实测：一个 300px 弹层里平铺 7 个分组 / 107 个勾选项），再横向调研业界 6 类成熟方案（AG Grid / MUI X / DevExtreme / Syncfusion / TanStack+shadcn / Airtable·Notion 等），最后对用户提出的两个初步方案做逐项评估，给出推荐形态与落地拆解。本文是调研与设计输入，不改任何代码。

状态 Done（快照） 取证范围 src/auto_qb/webui/static/shared/ 列模型 · 列交互引擎 · 顶栏与表头模板 结论 作用域收敛 + 双入口 + 分类折叠 + 检索

1结论摘要

「杂乱难寻」不是一个视觉问题，是一个信息架构问题：当前选择器的作用域是「整个应用的全部表」，而用户此刻面对的只是「一张表」。实测用户在辅种页点「列」，会看到一个 300px 宽、max-height:70vh 的弹层，里面线性平铺 7 个分组标题 + 107 个勾选项，其中约 86 项属于屏幕上根本看不见的表（明细表 / 种子页 / 追剧视图 / 抽屉三表）。

现状一句话

一个入口、一个弹层、一张 107 行的线性清单：无检索、分组不可折叠、跨表混列、无状态提示。要勾「种子页 · 保存路径」必须从顶滚到底。

调研结论（详见 §4–§5）：业界没有任何一款成熟数据表格把「所有表的全部列」平铺进一个弹层。跨表/多列场景的成熟做法只有两条路——要么在弹层内加「分组折叠 + 检索 + 全选」（AG Grid / MUI X / DevExtreme / DataTables colvis），要么干脆把作用域收敛到当前表/当前视图（AG Grid 表头菜单、原生 Finder 右键列头、Airtable/Notion 视图级字段配置）。

对用户提出的两个初步方案：

初步方案判断理由
① 保留「列」按钮，分类 + 折叠 必要但不充分 默认展开项可从 107 降到 21（辅种页），首屏噪音显著下降；但作用域仍是「全应用」，其它 6 组只是被折起，错配没解，且仍无检索。
② 右键 + 弹窗，各表分开 方向正确 作用域 = 被操作的那张表，语义最贴；且代码地基已有 70%——openColMenuAt(ev, page) 的 page 参数已预留但闲置，表头右键菜单 openHeadMenu 已在线上。唯一短板是右键的可发现性。
推荐形态（§7）

以方案 ② 为骨、方案 ① 为肉：弹层数据源从「全表」收敛为「当前表」（复用已闲置的 page 参数，零新增 API 面）→ 表头右键为主入口、顶栏「列」按钮为当前表的备选入口（按钮上标注当前表名）→ 弹层内做检索框 + 分类折叠（按列语义族）+ 组内可见计数 + 三态勾选 + 重置本表显隐 → 抽屉/变体表的恢复入口随作用域一起迁到「各自表头的右键菜单」。持久化层零改动（仍走 persistPage 唯一漏斗与 v5 双轨模型）。

附带发现（只取证不改）：TORRENT_COLUMNS 第 158 行注释称扩展字段「默认隐藏」，但这 13 个列定义里没有 hide: true 标志，而 loadColState 的播种判据是 filter(c => c.hide) —— 即种子页实际默认渲染全部 28 列。这很可能是「表格太挤」体感的一部分成因。属注释与代码漂移，本报告只记录，是否修/入池需另行确认（范围守恒）。

2.2 弹层规格与入口

弹层规格（三皮肤一致）
  • 容器：.col-menu，width: 300px
  • 高度：max-height: 70vh; overflow-y: auto
  • 结构：v-for def in tableDefs → 每表一个 .col-menu-title + N 个 .col-menu-item
  • 底部动作：恢复默认列宽 / 适应窗口宽度（全表，遍历 ALL_TABLE_PAGES）
入口（两条，同一弹层）
  • 顶栏「列」按钮：topbar.html，仅 page === 'groups' 时渲染 → toggleColMenu
  • 表头右键：openHeadMenu → 「显示/隐藏列…」→ headMenuPicker() → openColMenuAt(ev, page)
  • 右键菜单已含：隐藏本列 / 按本列排序 / 时间口径切换 / 显示隐藏列…
关键事实：方案 ② 的扩展点已经存在

columns.js::openColMenuAt(ev, page) 已经接收 page 参数，但源码注释明说「page 参数当前仅区分语义（弹层四段全量展示），留作按视图段落定位的扩展点」——它被调用时确实带着表 id（headMenuPicker 传 m.page），只是数据源没用它。也就是说「各表分开」不需要新增 API 面，只需要让 tableDefs 按 page 过滤。

2.4 持久化层（重设计不触碰）

列状态走双轨模型：意图态（colHidden / colOrder / colW）是唯一持久化对象，经唯一漏斗 persistPage 按 v5 页子树 RMW 落盘；生效态（colWidths）永不落盘。重设计只改「UI 呈现 + 数据源过滤」，不动存储结构，因此不升版本（符合 pitfalls/web-ui/columns-persist.md 的判据）。

3根因分析

「杂乱」是三条结构性成因叠加的结果，缺一条都不至于如此：

成因一 · 作用域错配（主因）

选择器的数据源是 tableDefs（ALL_TABLE_PAGES 全量），作用域 = 「整个应用的全部表」。但用户此刻面对的是「一张表」。在辅种页点「列」，看到的是 107 项，其中 86 项（明细表 28 + 种子页 28 + 追剧视图 11 + 抽屉 19）与屏幕上的任何东西都无关 —— 用户必须先在脑子里做一次「这些跟我现在看的东西有什么关系」的映射，这本身就是负担。

成因二 · 无检索 / 分组不可折叠

107 项线性平铺，只有 7 个不可折叠的标题分隔（.col-menu-title 只是视觉分隔，无交互）。要勾「种子页 · 保存路径」，需从弹层顶部滚动到中部再逐行找。业界在超过约 10–15 项时普遍提供检索框，这里没有。

成因三 · 无状态提示

勾选项不区分「默认隐藏 / 用户隐藏 / 必显（locked）」，也不显示「当前可见 N / 共 M」。用户无法一眼看出「我改了哪些」和「这张表一共几列」，进一步放大了「找不到」的感觉。

补充 · 「表格太多」的另一半来自列本身

用户原话是「表格太多了」——除了表多，列也多：种子页 28 列默认全可见（§1 附带发现）。即使选择器改得再好，表体本身拥挤的体感也需要单独处理（本报告不改）。

4业界成熟方案调研

把主流数据表格/表格型产品的「列管理」抽象，可归为 6 类模式。每类给出代表产品、特性清单与对本项目的适配判断。

模式 A · 工具侧栏（Tool Panel）

代表：AG Grid Columns Tool Panel、Grafana 表格面板 Fields 页、Notion 视图属性面板。

  • 常驻或可开关的侧栏，按用途分节（AG Grid：Columns / Row Groups / Values / Pivot / Column Labels），每节可展开折叠；
  • 顶部检索框（对列名与分组名过滤）；
  • 支持拖拽重排、全选/清空、列分组树（父级三态勾选）；
  • 与「表格是页面主体」不抢焦点，可常驻。

优点：空间充足，能同时容纳检索/分组/拖序/全选，是「大列表」场景的最强形态。
缺点：占宽（AG Grid 默认约 250px）；本项目主内容区已有 .layout 两栏语义 + 吸底抽屉（见 pitfalls/web-ui/dock-panel.md），再插一个侧栏会挤压布局，且三皮肤需成对改，窄屏退化成本高。
适配：中——适合作为「完整模式」的远期选项，不适合本期。

模式 B · 弹层复选（Dropdown + Checkbox）

代表：TanStack Table（headless）+ shadcn/ui Data Table with column visibility、MUI X Data Grid Column visibility panel、Ant Design 生态的「列设置」、DataTables colvis。

  • 工具栏按钮 → 弹层，内含复选列表（TanStack/shadcn 即 DropdownMenu + CheckboxItem）；
  • MUI X 面板含：检索框、勾选列表、hideable:false 的禁改项、重置按钮、toggleAllMode: 'filteredOnly'（检索态下「全选」只作用于过滤结果）；
  • DataTables 的 colvis：下拉 + 复选 + colvisGroup（按分组批量显隐）+ Show all / Show none；
  • AntD 生态的「列设置」普遍是 Popover + 复选 +（第三方）拖拽排序 + 分组树。

优点：与现状形态最接近，改造成本最低；可在原位加检索/分组/折叠/全选；不占布局。
缺点：300px 宽弹层塞「检索 + 7 组折叠 + 107 项」仍偏挤；高度受视口限制。
适配：高——这就是「方案 ①」的正确实现形态。

模式 C · 模态列选器（Modal Column Chooser）

代表：AG Grid Column Chooser（dialog 版）、DevExtreme columnChooser、Syncfusion Column Chooser。

  • 独立弹窗/覆盖层，含标题与列检索 UI（DevExtreme allowSearch，官方在「隐藏列较多」时推荐开启）；
  • DevExtreme 两种模式：mode: 'dragAndDrop'（拖列头进出）与 'select'（勾选，面向触屏）；
  • 两个独立开关：allowHiding:false（永不可隐藏）与 showInColumnChooser:false（隐藏后不出现在列选器里）；
  • 程序化 API：showColumnChooser() / hideColumnChooser()。

优点：空间充足，可放检索 + 分组 + 拖序 + 全选 + 重置，与主布局解耦。
缺点：模态遮罩打断「边看表边调列」的即时反馈；本项目已有大量浮层（ctx-menu / pop-menu / col-menu），再加模态要处理层级与 Esc 栈（见 overlays / dock-panel 坑档）。
适配：中——不推荐（与既有浮层体系冲突）。

模式 D · 表头右键（Header Context Menu）

代表：原生 OS 惯例（macOS Finder / Windows 资源管理器：右键列头 → 列清单勾选）、AG Grid 表头菜单（Pin / Autosize / Hide / Reset）、MUI X 列菜单的「Manage columns」。

  • 在列头上右键 → 菜单里给出「隐藏本列 / 列选择器」等入口；
  • 语义最贴：「我就在这一列上，我要动这一列」；
  • 本项目已实现：openHeadMenu → 隐藏本列 / 按本列排序 / 时间口径 / 显示隐藏列…

优点：零占位、语义最贴、代码已在线上。
缺点：可发现性最差（无视觉提示，新用户不知道能右键）；不适合「一次性配置多列」的长任务。
适配：高——作为主入口，但必须配可发现性兜底（顶栏按钮）。

模式 E · 按视图保存（Saved Views / Presets）

代表：Airtable / Notion（字段显隐是视图级配置，可保存多个视图）、Grafana panel field overrides、Excel「自定义视图」（列宽/显隐/筛选的命名快照）、Linear / Jira 的「保存视图」。

  • 一次配置复用；多场景（如「下载视图」「保种视图」）切换；
  • 列配置随「视图」这一对象走，而不是随「表」走。

优点：复用性强，多场景友好。
缺点：引入「视图」这一新维度（当前是「每张表一份偏好」，见 v5 存储）；实现与心智成本最高。
适配：低-中——可作为远期演进，本期不做。

模式 F · 命令面板 / 模糊检索（Command Palette）

代表：VS Code / Linear 的 ⌘K、各类「快速切换列」实现。

  • 输入列名即过滤并可直接切换；
  • 107 项时检索最快，键盘流友好。

优点：检索效率最高。
缺点：纯键盘交互，与「鼠标勾选」的表格用户习惯有距离，仍需一个可视化列表兜底。
适配：中——作为增强：在弹层顶部加一个检索框即可拿到约 80% 的收益，无需另做面板。

矩阵读出的三条结论
  1. 没有任何单一模式在「可发现性 + 作用域契合 + 低成本」三项同时满分。D 的「作用域契合」与「已有实现」是独一档优势，短板恰好是 B 的强项（可发现性）；B 的短板是 D 的强项。→ 组合，而非二选一。
  2. 「作用域契合」这一列才是本题的胜负手（§3 成因一）。B/C 都在「作用域契合」上要么靠实现（B 可收敛）要么偏弱（C 偏全局），只有 D 天然正确。
  3. 检索与分组折叠是「承载 107 项」的必需品，无论选哪种容器：AG Grid / MUI X / DevExtreme / DataTables 全部内置其中之一或全部。

6两个初步方案评估

6.1 方案 ①：保留「列」按钮 + 分类 + 折叠

维度评估
做法把 7 个 .col-menu-title 从「视觉分隔」升级为「可折叠分组头」，默认只展开当前视图对应的那一组。
收益默认展开项从 107 → 21（辅种页），首屏噪音显著下降；改动面小（模板 + CSS + 一条 colGroupOpen 状态）。
局限 ① 作用域仍是全应用（其它 6 组仍在，只是收起）；
② 仍无检索；
③ 「我在这张表，为什么要看别的表」这层错配没解；
④ page 参数继续闲置。
结论必要但不充分——是最终方案的组成部分（「肉」），不是完整方案。

6.2 方案 ②：右键 + 弹窗，各表分开

维度评估
做法表头右键 → 弹层只列本表的列（作用域 = 被右键的表）。
收益作用域正确（21 项而非 107）；语义最贴；代码地基已有 70%（page 参数 + openHeadMenu 已在线）。
局限 ① 可发现性差（右键无提示，新用户不知道）；
② 顶栏「列」按钮若仍是「全表」，两条入口语义不一致；
③ 抽屉表/变体表的「恢复入口」不变式必须保住（见 §7.4）。
结论方向正确——作为骨架（「骨」）。
为什么不是「二选一」

方案 ① 解「弹层内怎么摆」，方案 ② 解「弹层该装什么」。两者是正交的两个决策：先定作用域（②），再定弹层内信息架构（①）。把它们合成一个方案，才能同时拿下「作用域正确」与「大列表可导航」。

7推荐方案

一句话：作用域收敛到当前表 + 双入口同语义 + 弹层内检索与分类折叠 + 抽屉/变体表的恢复入口随作用域一起迁移。持久化层零改动。

7.1 作用域单点：让闲置的 page 参数上岗

弹层数据源从 tableDefs（全表）改为按 page 过滤：新增 tableDefFor(page)（或 tableDefsFor(page)），返回该表一项。openColMenuAt(ev, page) 的 page 从「仅区分语义」变为「数据源过滤键」。零新增 API 面——调用方本就已传 page。

7.2 双入口同语义

入口作用域可发现性角色
表头右键（主）被右键的那张表快捷、语义最贴；现有 openHeadMenu → 「显示/隐藏列…」
顶栏「列」按钮（备选）当前视图的表（VIEW_TABLE[viewMode]）消除「不知道能右键」的盲区；建议按钮文案标注当前表名，如「列 · 辅种表」

两条入口打开的是同一个弹层、同一份数据源 —— 不会出现两套语义。注意顶栏按钮当前只在 page === 'groups' 渲染；若希望种子页/追剧页也有可发现入口，需同步放开渲染条件（属可选增强）。

7.3 弹层内信息架构（方案 ① 的正确实现）

  • 顶部检索框：按列 label 过滤，命中即展开所在分组；「全选」只作用于过滤结果（MUI X 的 toggleAllMode:'filteredOnly' 语义）。
  • 分类折叠分组：分组维度建议取列语义族（标识 / 速度 / 体量 / 时间 / 站点与标签 / 计数与诊断 / 操作），而不是「按表」——作用域已收敛到单表，再按表分组就退化成「一组」，折叠失去意义。
  • 组头三态：显示「可见 / 共」计数（如 3/6）+ 三态勾选（组内全显 / 全隐 / 混合）。
  • 每项状态提示：区分「必显（locked，置灰不可点）/ 用户隐藏 / 默认隐藏」。
  • 底部动作：保留「恢复默认列宽 / 适应窗口宽度」（现有），新增「重置本表列显隐」（语义 = 清空本表 colHidden[page]）。

7.4 「全表」恢复入口（保住既有不变式）

必须保住的一条不变式

现行「全表弹层」是 2026-10-11 W2 的有意决策（计划 26-10-11-2106）：抽屉三表头右键的「隐藏本列」是不可逆操作，把抽屉表列进主选择器，是为了给它们留一条恢复入口（否则只剩改 localStorage）。任何作用域收敛都必须重新提供这条恢复路径。

解法：把恢复入口随作用域一起迁到各自表头的右键菜单——抽屉表头本就已走同一条 openHeadMenu（见 app.js 中 DRAWER_TABLE_DEFS 的 headRef:null + columns.js::_headEl 的 DOM 兜底），所以「在谁的头上右键，就在谁的菜单里恢复」天然成立，且比现在更贴。对无表头的变体（如 Tracker 04/05、内容 10，列头被 CSS 隐藏，源码已记「拖宽/右键隐藏/列偏好不适用」），本来就没有右键隐藏能力，也就无需恢复入口 —— 口径自洽。

7.5 不动的部分

列宽拖拽、拖序重排、双击自适应、列对齐注入（colAlignCss）、行窗口化、persistPage 唯一漏斗与 v5 双轨存储 —— 全部不动。

波次内容触碰点验收

9风险与边界

风险说明对策
可发现性右键入口无视觉提示，功能可能被埋保留顶栏「列」按钮作为备选入口（作用域 = 当前表）
抽屉/变体表恢复入口作用域收敛会移走它们的列恢复入口（W2 不变式）迁到各自表头右键菜单；无表头的变体本无此能力，口径自洽
测试面脆弱e2e/column-prefs.spec.mjs 依赖 .col-menu-item 全局下标W4 统一改为「分组 + 标签」定位；避免新增下标型断言
分组维度选择按「列语义族」分组需为 107 个列定义归族用单点映射表；归族口径需一次拍板（可先按现有注释里的语义段落归）
顶栏按钮渲染条件当前仅 page === 'groups' 渲染，种子页/追剧页无按钮入口若要全面可发现，需放开渲染条件（可选增强，单独拍板）
明确不做（本期）
  • 模式 E「保存视图」：引入「视图」新维度，实现与心智成本最高，列为远期演进。
  • 模式 C 模态列选器：与既有浮层体系（ctx-menu/pop-menu/col-menu）的层级与 Esc 栈冲突。
  • 种子页默认隐藏漂移的修复：属范围外，本报告只取证；是否修/入池需另行确认。
