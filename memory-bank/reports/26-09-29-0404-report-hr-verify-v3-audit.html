2 · 安全边界核验(PT 站访问面)

这是本功能最要紧的面, 逐项验证如下 —— 全部成立:

2.1 零 cookie 边界(后端不持凭据、不直连站点)

  • 协议层无凭据字段: HrTask / HrResult 只有 URL 与内容字节(channel.py:213-270); 登录态只存在于浏览器扩展上下文。
  • 无通道时回落不是偷偷直连: NullFetcher 调用即抛 HrChannelUnavailable, 由 service 转「未核实 + 本地兜底」(fetcher.py:77-87) —— 「零 cookie」在故障路径也不破。
  • 下载 URL 单点来自内置档案 /download.php?id={id}(site_presets.py), 不含 passkey; 密钥文件 hr.token 内容不进日志(channel.py:105-107, 有注释钉死原因)。

2.2 本地端点四道防线(server.py + channel.py)

  • token: secrets.compare_digest 常数时间比较(server.py:270-272); 401 前不写任何状态(server.py:204-207); 随机生成持久化 0600。
  • origin 白名单: 非扩展 origin 一律 403 且不给 CORS 头; 配了 extension_id 再钉死到单一扩展(校验器强制 32 位 a~p 形态, sections.py:201-206)。runtime 在 extension_id 留空时每次启动 WARNING 提醒(runtime.py:126-141) —— 纵深提示到位。
  • URL 白名单(SSRF): 任务 URL 只由后端按配置拼出, 下发前必过 UrlPolicy.require(域名 + 路径 + scheme 三重), 端点本身不接受任何 URL 入参 —— 不可能被诱导成「带登录态的任意站代理」。手工 URL 解析的怪形态(userinfo/尾点)均「不匹配即拒」, 失败方向安全。
  • 回传防伪: 只接受「确实派发过且未回过」的任务 id + 域名必须与派发一致 + 未派发即收到也拒(queue.py:137-156); 过期任务 240s TTL 作废, 晚到回传不堆积。
  • 网络面收窄: 只听 127.0.0.1; allow_reuse_address=False 防 Windows 抢绑(端口独占守卫有效); 请求体 12MB 上限在 dispatch 与 route 双卡; 每请求 Connection: close; 端点线程只入队, 异常不外泄(500 兜底)。

2.3 对站点的访问节奏(双保险)

  • 后端单模型频控: min_interval(下限 5s 配置强制, 默认 90s)+ 只向上抖动(实测间隔恒 ≥ 配置) + 日额 240 + allow_window + 复用窗(多实例不重复取数)。
  • 扩展侧独立第二道闸(60/时·600/天): 触发即 HrChannelQuota → 计「让位」不计失败 —— 不会把后端频控失效伪装成站点故障推进任何错误状态, 且只报一次告警。
  • 「取数失败 = 档位截断 + 周期自然重试」的 v3 口径本身保守; 但失败路径的持久化存在盲区 → 见 H1/M1。

2.4 数据面(不可信内容处理)

  • 扩展回传的 HTML: 标准库 html.parser 栈式抽取, 表头锚定 + 必填字段零容忍(S2) + 排序单调校验(方向自适应、证据不足不误报)。
  • 扩展回传的 .torrent: 自写 bencode, 深度上限 64 防递归炸栈, 整数前导零/超长字节串拒收, infohash 取原始字节切片(正确性关键, 有独立向量测试)。
  • WebUI 呈现: 全部 Vue {{ }} 插值(自动转义), HR 模板无一处 v-html —— 站点页面内容经「站点 → 扩展 → JSON → 界面」的存储型 XSS 链不成立。

3 · 稳定性核验

  • 存储层(store.py): 每站点一把 filelock(拿不到即让位, 不排队轰炸); 写者心跳自检(revision 回退 / 心跳被覆盖 ⇒ 判锁不生效, 退化只读防双写); 坏文件先隔离(.bad-ts 留证)再试 .bak 兜底, 且「坏文件被换下后写盘不再复制 .bak」防止好备份被盖 —— 顺序正确; 原子替换写保证无锁读完整。
  • 线程边界: 端点线程只入队 / 取数线程持锁干全部重活 / 主循环只读原子发布的不可变视图(publisher 单元组防撕裂); 锚点交接用 frozen dataclass 只读快照(qbmanager.py:716-738) —— 单一写线程法则守住。
  • 关停安全: stop() 先 cancel_all 叫停队列再 join; 频控睡眠可中断(1s 切片查停止位, 抛 HrChannelStopped 让位) —— 关停不会白等 180s 或持锁睡完间隔。
  • 崩溃安全: 每页解析完 + 每个下载完成即增量 commit(分钟级波内 Ctrl+C 不丢已抓数据); 取数线程单轮异常被兜住不打死线程; 单站点失败不外抛。
  • 告警防轰炸: 节流状态按根因归一(pacing_class)而非 action; 持续状态 6h 周期提醒; 产生处已告警的 worker 只记 INFO —— 三层设计在 2026-09-24 实报场景上都闭环。
  • 配置 fail-fast: hr_check 三层未知键拦截(全局/channel/sites 条目) + 全部键有类型与范围校验(min_interval ≥5s / request_timeout 5s–1h / port 1–65535 / refresh_interval 60s–30d) + 站点档案登记制 + 绑定校验(显式 tracker 存在 / 默认映射命中 / 唯一性 / 绑定站点 hr 段必填否则整站保护静默失效 —— 已在配置期拦下)。

4 · 判定正确性核验

  • 四行判定表: A 命中即管束(本地达标也管) → 终态 B/C/D 放行(永续) → 放行记录(锚点漂移作废回行 4) → NO_EVIDENCE 交调用方本地兜底。双 infohash 合并取保守序(管束 > 放行 > 无证据), 方向正确。
  • RecursionError 修复复核(05a8415): 行 4 回落改直调 _local_hr_triggered()。两条进入路径(judged is None / NO_EVIDENCE)下 check_hr_condition 的站点侧分支均已先行返回, 逐一走查确认无环、语义等价; 补的回归测试(test_record_hr_no_evidence_row4_no_recursion)覆盖了此前漏掉的 NO_EVIDENCE 路径。修复质量高。
  • 防伪三件套: A 档流转守恒(留存率 ≥0.7 否则冻结批量签发)、总行数骤降(<基线 30% 冻结)、零行需人工确认戳(再现非零行自动失效) —— 加上放行前置「各档全部有效 + 新鲜度闸门(added_on ≤ 该档取数时刻)」, 把「改版吞行被误判未列出」这条最危险的误放行路径层层锁死。放行永续 + 锚点漂移作废(本机重下)的残余风险(其它客户端下载看不见)已在文档如实声明。(26-09-29 裁决: 骤降保护移除, 防伪收敛为守恒 + 零行戳两道 —— 见 §13.3)
  • 覆盖证明: 三停翻条件(完成时间 +1D 余量 / 到期段强信号 / 本地全集)与缺席证明(全深度位置无关 / 有界档按可信完成时刻)方向推演无误; 失踪观察期(2 波 + 位置覆盖)「没看到不终结考察中」保守正确。

5 · 缺陷清单(附证据与修复建议)

H1 · 站点 Retry-After 指令不跨波生效 HIGH

后果: 站点明确要求「等待 N 秒后再来」时, 取数线程仍按 worker 轮询节奏(60s)每波重发请求, 直到日额(默认 240)烧尽 —— 恰好在站点开始限流、最不该加压的时刻持续加压; 同时烧掉的配额让当天正常核实能力受损。v3 设计明确「Retry-After 是站点明确指令, 单存 retry_after_until 并参与下次可取时刻」(ratelimit.py:103-122 已实现读取侧), 但写入侧从未持久化。

# hr/service.py:485-493 —— _do_wave 的 HrFetchError 分支
except HrFetchError as e:
    retry_after = float(getattr(e, "retry_after", 0.0) or 0.0)
    if retry_after > 0:
        data.retry_after_until = self._now() + min(retry_after, 24 * 3600.0)
        result.action = ACTION_WAITING
        result.reason = f"站点要求等待(Retry-After {retry_after:.0f}s): {e}"
        return   ← 直接返回, 不走 _finish_wave ⇒ session.commit 永不发生
  • 根因链: hold() 每次进入都从磁盘重读 HrLockSession(store.py:258-269), 写在 session.data 上的 retry_after_until 随会话关闭丢弃 → 下一波 next_allowed_at 读到 0 → 间隔门槛也不成立(该路径 budget.mark() 在 get_text 成功后才调用, service.py:549, 失败时 last_fetch_ts 不前进) → 下一波立即重试。两道闸同时失效, 唯一剩下的限流是日额本身。
  • 连带问题: .torrent 下载路径的 Retry-After 被当作普通种子失败计入 data.fails(service.py:821-826), 站点指令再次被降级处理。
  • 测试缺口(同一根因的两处都无覆盖): test_hr_service.py:773 注释明确把 Retry-After 语义「外包」给 ratelimit 单测 —— 而单测是注入值测读取侧, service 收到 Retry-After 后的持久化行为零覆盖。
修复建议: 该分支 return 前若 session.writable 则 session.commit()(一行); 顺带 budget.mark() 让间隔基准前进; 下载路径对带 retry_after 的 HrFetchError 改为上抛走波级让位。补 service 级单测: 波 A 收到 Retry-After → 断言波 B 的 next_allowed_at ≥ retry_after_until。

M1 · 登录失效路径不记间隔基准, 烧日额且拖慢恢复 MED

后果: 扩展取到登录页(KIND_LOGIN_PAGE → HrLoginExpired, fetcher.py:142-145)时 get_text 直接抛出, mark() 未执行。登录态失效期间每波(60s)都立即重试: take() 先扣日额 → 取数失败 → 无间隔记录 → 下一波照旧。日额以每分钟 1 次的速度烧(4 小时烧完 240), 且用户去浏览器登录回来后, 当日配额可能已耗尽, 在线核实停摆到零点。v3 有意「登录失效不推进熔断」(重试无法解决, 正确), 但没有配套「至少拉开重试间隔」。

修复建议: HrLoginExpired 抛出路径同样执行 budget.mark()(或 take() 时预记), 让 min_interval 挡住轮询节奏; 更优: service 对该站记一个「登录失效静默期」(如 30min)再重试。属 H1 同根(失败路径无持久化), 可一并修。

M2 · 站点文件 schema 比程序新时, 空数据覆写新版文件 MED

后果: 版本回退场景(新版写过站点文件后跑回旧版程序)下, _parse 对 SchemaVersionError 返回 recoverable=False(store.py:136-137), HrLockSession 据此用空数据继续(store.py:265-266) —— 但 _refresh_locked 不检查 read_error, 波次照常取数并在结束时 commit,新版文件的索引/放行记录/已取记录被空波覆写(.bak 只保住一份, 随下一次写被盖)。读侧「不符即拒、不猜未来版本」的设计正确, 但写侧没跟上同一防线。

修复建议: read_error 且非「坏文件」类(schema 不符)时, _refresh_locked 直接返回 ACTION_ERROR 且不 commit(一个 if); 或 HrLockSession 对该情形置 writable=False。低概率高损失, 值得堵上。

L1 · judge_record 的并列 tie-break 文档承诺未实现 LOW

docstring(resolve.py:253-255)承诺「同为放行取依据更强者(D 免罪 > B > 缺席); 同为管束取剩余时间更少的行展示」, 实现(resolve.py:265-269)是严格大于才替换 —— 并列时 first-wins(v1 先到先得)。判定身份不受影响(都已是 RELEASED/HR), 仅展示口径与文档漂移。

L2 · 完整 URL 进日志与系统通知, 无脱敏钩子 LOW

queue.py:149 / fetcher.py:138,145,147-148 把完整 URL 拼进异常消息, 一路进 service 的 WARNING(service.py:825) → notify 推系统通知。当前 preset 的 hr_page_url / download_path 都不含 passkey(已核对 site_presets.py), 但本仓库对 qB tracker URL 已有「拉取即脱敏」的既有口径(tracker-url-source-sanitize 专题), HR 侧 URL 是同一类敏感面 —— 机制上建议日志出口对 query 做统一遮蔽, 防未来档案变更引入参数后裸奔。

L3 · skip_local_verify=true 时 confirm-empty 可被 CSRF LOW

/api/hr/confirm-empty 是写端点, 默认配置下走 web.token 鉴权(skip_local_verify 默认 false, models.py:217, 已核实), 安全。但用户开启 web.skip_local_verify 后, FastAPI 对 dict body 不校验 Content-Type —— 任意网页可用 text/plain 简单请求(无预检)携带 JSON 体成功调用, 写入人工对账戳(条件性危害: 仅在真实零行波时放大签发)。这是 WebUI 全局口径问题, HR 端点只是继承者; 若要收口, 对写端点要求自定义头(预检必触发)即可。

L4 · 排序方向只做波内校验 LOW

order_directions 每波重置(service.py:266), 站点改升降序(或首波即升序)时单波内自洽可通过校验: 升序页 1 的最深行即全站最老行, 停翻条件①立即满足 → cutoff 极小 → 对「完成时间较新」的未对账对象缺席证明成立 → 理论上可批量误签「未列出」。实际被纵深防御兜住: 上波 A 档行存在时流转守恒必然不达标冻结签发; 误放的行若真在考察中, 下波命中即撤销放行并管束。残余面是「无 A 历史 + 首波即升序」的组合, 建议把方向记入 HrLaneState 跨波比对(翻转视同违反), 成本一行。

  • I3 嵌套表递归无深度上限: parse.py walk 递归展开, 理论上 12MB 恶意 HTML 可致 RecursionError; 解析在波次异常边界内不会打死线程, 且站点是可信方 —— 仅记录。
  • I4 CLI confirm-empty 不校验站点名: 任意名字符串(含 ../ 逃逸)都会创建站点 JSON/lock 文件(WebUI 侧已校验白名单, routes/hr.py:39-44); 本机用户自身操作, 风险极低。
  • I5 0600 权限在 Windows 不生效: hr.token / web.token 的 os.open mode 仅 POSIX 有意义; 目录在用户 profile 下, 可接受。

9.1 启动装配(qbmanager → HrRuntime)

  • 主程序启动时 qbmanager 构造 HrRuntime 并把门面挂为全库记录的 hr_link(qbmanager.py:227-230); 仅在非 dry-run 时 hr.start()(qbmanager.py:369-370) —— --dry-run 下 HR 运行时完全不启动(不是「只读运行」, 是没有)。
  • start()(runtime.py:105-124): 先幂等 stop → 判 enabled(总开关开 且 ≥1 站点接入, runtime.py:94-96) → 建 HrTaskQueue / HrRefreshService(persist=True, allow_fetch=有通道, sleeper=可中断睡眠) → channel.enabled 才 resolve_token(显式配置优先, 否则随机 32 字节落 <data_dir>/hr.token 0600) 并起端点 → 端口被占抛 HrChannelBindError 穿透到 CLI 退出码 1(fail-fast) → 起取数线程。
  • 取数线程节奏: POLL_INTERVAL = 60.0 是代码常量(service.py:129, v3 删了配置键); 线程循环先跑一轮再等(runtime.py _loop → worker._loop, worker.py:236-250)。hr.wake() 当前无任何调用点(qbmanager.py:225 注释明确「留给主循环的可选叫醒口」) —— 主循环与取数线程零握手, 60s 纯自唤醒。
  • 配置热重载(runtime.py:160-189): channel 的 enabled/port/extension_id/token 或 shared_dir 变 → 整体重挂(先停线程与端点再启); 其余字段变 → 重建 service 与线程、端点不重绑; 总开关关 → 收掉线程与端点。

9.2 一次「波」的全生命周期(service.py 主流程)

取数线程每 60s 一轮, 对每个启用站点依次 refresh_site(站点之间互不阻塞); 单站点流程如下:

  1. 抢锁(service.py:364): hold() 抢站点文件锁, timeout=0 拿不到即 skipped-locked 让位(不排队); 锁内完成「读 → 判 → 抓 → 写 → 释放」全程。
  2. 复用窗(service.py:395-403): fetched_at>0 且 expires_at>now → 直接复用已有数据(零请求), expires_at 在健康波结束时设为 now + refresh_interval(默认 12h, service.py:927)。多实例同账号靠它保证同站点只被一个实例抓。
  3. 频控闸(service.py:410-414 → ratelimit.py:97-122): next_allowed_at 取四者最晚 —— ①上次请求 + 抖动间隔(90s × (1+0~25%) = 90~112.5s, 抖动只向上) ②Retry-After 时刻 ③日额耗尽则次日零点 ④时间窗起点。未到 → waiting(INFO 节流)。
  4. 对象集现算(service.py:1079-1117): 本地种子锚点(主循环 store 快照只读交接, qbmanager.py:716-738)中 —— 已有放行记录且未漂移的跳过; 绑定了终态档(B/C/D)条目的跳过; 做种时长 ≥ 3× 要求时长的跳过(超额线, 常量 SEED_EXEMPT_RATIO, service.py:100); 锚点漂移(本机重下/删种重加/进度回退, 判据 resolve.py:61-73)则作废旧放行回炉。剩下 = 覆盖对象集(未对账 ∪ 考察中)。
  5. A/B/C 轮流翻页(service.py:501-617): 三档(考察中 A / 已达标 B / 未达标 C; D 档不抓 —— model.py:34 注释「命中 D 与未列出同为放行, D 档没有增量信息」, FETCH_LANES 只含 A/B/C, 两 adapter 也只传 FETCH_LANES, adapters/__init__.py:30-48)每轮各推一页、每页都过预算:
    • budget.take()(service.py:235-249): 先按第 3 步的四闸等(锁内睡, 单次上限 300s / 本波累计 900s, 超限放弃剩余请求下波继续), 通过即先扣日额再发请求。
    • 发任务给扩展(queue.put → wait ≤ request_timeout 180s): URL 先过白名单; 扩展超时/被叫停/配额/登录页/Challenge 的分流见第 10 章。
    • 页面有效才计进度(表头缺失或必填字段缺失率 >0 → 该档结构性截断 _LaneAbort; 排序违反 → 强制早停; service.py:562-573)。
    • 每页解析完 → 行处理(命中即定论: infohash 与本地对上按档位落身份、撤销既有放行; 无身份行进入下载队列 —— A 档行无条件下载, B/C 行需宽泛名称粗配 ≥12 连续重合段才下, service.py:729-763) → 下载回填(每 tid 永不重下; 3 次失败冷却 1h; 下载也过同一预算; service.py:777-852) → 增量落盘(每页 + 每下载各 commit 一次, Ctrl+C 只丢当前请求)。
  6. 每档停翻三条件(service.py:665-701, 任一成立该档退出轮转): ①最深已见行早于「最老未定论对象完成时间 − 1D 余量」(位置覆盖) ②页尾跨页连续 ≥5 行剩余考察时间为 0(到期段强信号, 判全深度) ③未对账对象全部与已见行对上且无待回填(本地全集)。翻到末页(下一页链接不存在且页脚脚本 maxpage 不大于当前页, parse.py:225-253)也判全深度。
  7. 波后收尾(service.py:867-966): ①失踪观察期 —— 上波考察中、本波未重见且位置被各档覆盖的, 连续 2 波判「移出」放行; 位置没覆盖就冻结局( 位置判据 service.py:1233-1247) ②防伪: A 档流转守恒(上波 A 行本波留存率 <0.7 → 冻结批量签发)、总行数 < 基线高水位 30% → 冻结、结构完好零行 → 不签发需人工确认戳 ③批量「未列出」放行: 仅各档全部有效 + 无骤降 + (非零行或已确认)时, 对缺席证明成立(全深度或位置覆盖, service.py:1250-1271)且 added_on 不晚于该档取数时刻的对象签发 —— 放行永续 ④终态条目未重见且位置被证明 → 退役 + 落放行记录 ⑤非活跃 30 天淘汰 ⑥写波次元数据、fetched_at、复用窗。
  8. 发布视图(worker.py:284-290 + 99-130): 用内容指纹(revision/档位规模/健康波时刻等)判断实质变化才抬版本号, 主循环读到的永远是完整一份。

9.3 判定消费链(主循环 / Web 线程, 只读现算)

12 · 默认口径下的具体运行画像(全部按默认值推演)

12.1 默认(不动配置): 绝对零行为

hr_check.enabled 缺省 false → 运行时不建、无线程、无端点、无文件读写; 判定全走既有本地字段逻辑。channel.enabled 也默认 false —— 即使总开关开了, 没显式开 channel 的实例也只读共享数据、零请求。

12.2 启用一个站点后(其余全部默认)

  1. t=0 启动: 端点起在 127.0.0.1:8788(若 channel.enabled); 取数线程立即跑第一轮(worker._loop 先 run_once 再等)。扩展侧每 1 分钟来拉一次任务。
  2. 首波(站点文件为空, 无复用): 对象集 ≈ 该站全部本地种子(超额 ≥3× 的除外) → A/B/C 各从第 1 页轮转。第 1 个请求立即发出(last_fetch_ts=0 无间隔门槛); 此后每个请求(页或下载)间隔 90~112.5s。设首波需要 P 页 + D 个下载, 波耗时 ≈ (P+D−1)×100s; 但锁内累计等待 900s 封顶 —— 超出部分放弃、下波从第 1 页重来(对象集已变浅), 大账号的首次全量对账天然分摊到多波。单波页数上限 30。
  3. 请求记账: 每个请求先扣日额(240)再发; 页面与 .torrent 同一本账。一小时硬顶 = 3600/90≈40 个、3600/112.5≈32 个(抖动随机)。扩展侧独立余量: 页 60/时·600/天, 种 50/时·200/天 —— 按设计「≥ 后端 ×1.5」只在后端失效时拦截。
  4. 首波结束: 健康波(任一档有效)→ expires_at = now+12h → 之后 12h 内取数线程的每轮(60s 一次)与其它实例全部复用, 零请求。
  5. 稳态(对象集只剩增量): 每 12h 一波; 未对账/新考察中对象很少, 通常每档 1 页即触发停翻(①完成时间覆盖或③本地全集), 典型 1~3 页 + 0~几个下载 ≈ 2~6 请求/波 → 约 4~12 请求/天/站, 距 240 日额余量极大。
  6. 极端上界: 页数失控被 30 页/波 + 240/天双闸兜住; 即使处于失败重试循环(第 5 章 H1/M1 场景), 实际站点访问也被日额压在 ≤240/天/站(这就是两个缺陷的完整爆炸半径 —— 有节流下限但无节流是设计初衷)。

12.3 判定侧默认行为

站点接入但尚未抓到数据时(首波完成前), 所有种子落行 4 → 本地兜底(达标放行/未达标管束, 硬编码): 本地触发条件(dlratio/dlsize/下满)∧(做种 ≥ required+extra 或 分享率达标)。首批数据落盘后切换为站点侧权威判定; 放行一经签发永续, 不因数据变旧失效(「证据无时效, 只有真伪」), 只有锚点漂移或重新命中清单才作废。

12.4 多实例默认分工

同一账号多实例: 有浏览器有扩展的实例抓数(各用不同 port), 其它实例(channel.enabled=false)只读共享目录(shared_dir 需显式配置, 未配则各抓各的、访问翻倍 —— 启动 INFO 引导)。同站点由「文件锁 + 12h 复用窗」保证只被访问一次; 锁在该目录不生效时自检退化只读, 宁可单实例化也不双写。

13.4 观察期设计依据确认: 「缺席 ≠ 没证据」, 行 4 特例不可塌缩(26-09-29 用户确认)

问答中确认了失踪观察期的完整设计依据, 用户认可并要求存档 —— 它回答「缺席结论进观察期, 不就是没证据吗」的疑问: 观察期的本质恰恰是拒绝在单次缺席上得出结论, 不是「得出缺席结论再进观察期」。

  • 两种证据状态不可混同: 行 4(没证据 → 本地兜底)适用于站点没表过态的种子; 失踪 A 行的最后已知结论是站点权威的「考察中」, 本波未见有四种解释 —— 移出 / 转 D 免罪(放行正确)与扫描漏看 / 吞行(放行即漏 HR), 行 4 塌缩无法区分, 而区分失败的方向是灾难性的。
  • 行 4 兜底的具体漏洞: 行 4 含「达标放行」。若缺席即落行 4: 种子考察中 + 本地做种早已达标(越努力的用户越先中招)→ 一次扫漏 → 放行 → 站点实际仍在考 → H&R。20:58「本地达标 × 网站考察中 → 管束」必须由观察期载体执行 —— 条目保持 active 留在 lane_a, 判定恒走行 1, 根本到不了行 4。
  • 出口参数的取舍: 缺席即放行 = 单次抖动错放(灾难方向); 缺席即永管 = 真移出后永远管着(反向浪费 + 22:38 死锁)。2 波 + 位置覆盖(MISSING_GRACE_WAVES=2 + _position_covered)= 两次独立采样在「已证明扫过其位置」的前提下都未见, 「站点移出」才成为主导解释 —— 单次抖动被过滤。
  • 与批量签发的不对称(同源原则的两个落点): 未对账对象无站点旧结论可持, 一次可信扫描(守恒闸担保扫描完整性)即可签; 失踪 A 行持站点新鲜权威结论, 缺席需加倍确认。守恒的波级冻结只作用于前者(批量缺席签发, 22:38 解耦), 不作用于观察期。两个方向都是「宁多管不漏」。
  • 成本为零: 纯状态机(missing_streak 计数 + 位置判定, 重见清零), 不发任何请求。

一句话口径: 「没看到 ≠ 没证据」—— 行 4 只属于站点没表过态的种子; 站点表过态(考察中)的种子, 缺席需双波 + 位置证明才能转放行。
