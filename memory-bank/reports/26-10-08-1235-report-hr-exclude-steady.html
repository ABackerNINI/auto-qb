HR 排除未落到取数侧 — 稳态降频失效取证

用户报「通过标签/分类排除 HR 管理的种子似乎打破了稳态触发拉取」。取证结论: 排除表只在「判定侧」生效 (TorrentRecord 的 hr_managed / hr_judgement / check_hr_condition 三入口), 「取数/对账侧」从不读它 —— HrRuntime._anchors 把所有接入站点的本地种子无差别交给取数线程, HrRefreshService._build_objects 的排除链里也没有「HR 排除」这一档。后果: 被排除的种子仍进「对账对象集」⇒ 稳态条件 (对象集为空) 恒不成立 ⇒ 拉取间隔闸永远取 refresh_interval (用户 5H), 稳态降频 idle_refresh_interval (24H) 永不生效。日志侧证: 相邻两波间隔 16h55m < 24H, 与「稳态 24H」直接矛盾。

01结论速览

项结论判据
根因 HR 排除 (hr.exclude_tags / hr.exclude_categories) 在取数/对账侧未实现 —— 判据单点 TorrentRecord.hr_excluded() 只有判定侧与 WebUI 展示侧消费, 取数侧 (锚点采集 → 对象集现算) 完全没读它。 见 §04 两条代码证据 + 对照表
表现 被排除的种子仍算「需对账的对象」⇒ steady = anchors_known and not objects 恒为假 ⇒ 间隔闸恒取 refresh_interval, 24H 稳态降频永不生效。 service.py:497-498 / 522-531
「加了 IYUU 种子」的角色 是「破稳态的充分条件」而非「排除动作导致」。新种子进 anchors ⇒ 对象集非空, 这本就是设计要的「新下载即回常态」; 缺陷在于排除本应把它们移出对象集, 却没有路径。 报告 26-10-03-1505 §13.2
日志能证什么 两波间隔 16h55m 小于 配置的 24H 稳态间隔 ⇒ 稳态降频当时未在生效。日志不能直接读出「引擎用的是 5H 还是别的」, 那要看站点文件的 wave.idle_mode。 见 §05
自愈窗口 即使不修, 种子做种满 3 × required_seeding_time (CarPT = 3 × 36H = 108H ≈ 4.5 天) 后走「超额线」自动出对象集。但 IYUU 持续新增辅种时总有 <108H 的种子在线, 稳态仍然长期打不上 —— 这正是排除本该解决而没解决的问题。 service.py:1406-1407
一句话: 排除是「用户显式声明这类种子对本站无 HR 义务」。判定侧认这条声明 (不打标 / 不管束), 取数侧不认 —— 于是它一边被当「无义务」(判定侧不展示、不管束), 一边又被当「有义务」(取数侧持续为它翻页), 两个消费侧口径分裂。

03机制背景: 稳态降频怎么判

稳态降频 (计划 26-10-05-0555 / 报告 26-10-03-1505 §13) 的判据只有一条: 对账对象集是否为空。整条链路是:

本地种子 (store.all)
  └─ HrRuntime._anchors()            过滤: tracker_conf.hr_check 已接入且 enabled
       └─ {站点: {infohash: HrAnchor}}
            └─ (取数线程) worker.run_once → service.refresh_site(site, anchors)
                 └─ HrRefreshService._build_objects(data, anchors, required_seeding_time)
                      排除链: ① index 活跃终态行(B/C) → 出
                              ② 已有放行记录 verified → 出
                              ③ 超额线: seeding_time ≥ 3×required → 出
                      剩余 → objects (对象集)
                 └─ steady  = anchors_known and not objects       # service.py:497
                    interval = idle_refresh_interval if steady else refresh_interval  # :498
                 └─ 间隔闸: now < healthy_ts + interval ⇒ WAITING   # :522-531

所以「稳态生效」的等价条件是: 该站点所有本地种子都已被三条排除链清掉。只要还有一个 `objects` 成员, 引擎就一直按常态 5H 跑。

另有一条与本题相关的既有事实 (报告 §13.2, 已复读确认): 「对象集为空也不跳波」, 稳态期每波仍 A/B/C 各至少翻 1 页 = 3 个页面请求 —— 这解释了日志里为什么总是「3 行一簇」。

04根因定位

「HR 排除」的概念有唯一判据单点, 位于 TorrentRecord:

# src/auto_qb/torrents/record.py:297-337
def _hr_exclusion_hits(self):
    hr = self.tracker_conf.hr
    ...
    tag_hit = ... match_tag_patterns(t, hr.exclude_tags) ...
    cat_hit = ... match_tag_patterns(self.category, hr.exclude_categories) ...
    return (tag_hit, cat_hit)

def hr_excluded(self) -> bool:      # 单一判据
    tag_hit, cat_hit = self._hr_exclusion_hits()
    return tag_hit or cat_hit

证据二: 两处「取数侧」代码逐行核对

锚点采集只按「站点是否接入」过滤, 完全没有排除表的概念 (hr/runtime.py:358-383):

def _anchors(self):
    out = {}
    for rec in self._manager.store.all():
        conf = rec.tracker_conf
        if conf is None:
            continue
        site_conf = conf.hr_check
        if site_conf is None or not site_conf.enabled:   # ← 只判「站点接入」
            continue                                     #   (无 rec.hr_excluded() 这一档)
        anchor = rec.hr_anchor()
        site = out.setdefault(conf.name, {})
        for h in (rec.infohash_v1, rec.infohash_v2):
            if h:
                site[h] = anchor
    return out

对象集现算的排除链有三档, 也没有 HR 排除 (hr/service.py:1402-1412):

entry = bound_entries.get(h)
if entry is not None and lane_is_terminal(entry.lane):
    continue                                  # ① 终态 (B/C 档)
if ver is not None:
    continue                                  # ② 已有放行记录
if required_seeding_time > 0 and anchor.seeding_time >= SEED_EXEMPT_RATIO * required_seeding_time:
    continue                                  # ③ 超额线 (3×)
objects[h] = anchor                           # ← 排除的种子在这里照样进对象集
if entry is not None and entry.lane == LANE_SCOPE:
    observing[h] = entry
else:
    unmatched[h] = anchor
双向核对结论: HrAnchor 结构里也没有承载排除态 (resolve.py:44-58 只有 added_on / downloaded / completion_on / progress / seeding_time / name)。即: 从本地快照 → 锚点 → 对象集的这条路上, 排除信息在第一个环节就丢了, 后面任何环节都不可能再补判。

旁证: 计划 26-10-05-0555 §02 复述对象集判据时, 枚举的是「①终态 ②放行 ③超额」三条 —— 设计文档本身就没把 HR 排除列入取数侧的排除链, 说明这是一处未覆盖的设计缺口, 不是实现写漏了一行。

能确定的对账

  • 每簇 3 个请求、间隔约 120s —— 与「稳态/常态每波 A/B/C 各翻 1 页 = 3 请求」(报告 §13.2) 及 min_interval=90s + 抖动 + 请求耗时的量级一致。即一簇 = 一波, 日志里是两波。
  • 两波起点间隔 = 16h55m (10-07 07:02:52 → 10-08 00:02:05)。若稳态 24H 真在生效, 后一波不可能在 24H 之前发生 ⇒ 当时稳态降频未生效。这是日志能给出的最强结论。

日志不能直接证明的 (别过度解读)

  • 间隔 16h55m 既不等于 24H 也不等于 5H —— 这说明「取数页请求的落时刻」并不单纯由间隔闸决定: 取数通道必须可用 (浏览器扩展在线) 才会真正发出请求; 通道不可用时波会以「无可用通道/让位」收尾而不产生页面请求, 于是落时刻被「浏览器在线的时刻」过滤过。所以光看这份日志反推不出引擎实际用的是哪个 interval。
  • 要读引擎的真实取值, 看站点文件: <data_dir>/hr/carpt.json 里的 wave.idle_mode (True = 本实例最近一次现算判为稳态) 与 wave.healthy_ts。
判据 (可直接自查): 稳态生效时, 日志/状态里应出现带「稳态降频」字样的等待理由 —— 未到拉取时刻(拉取间隔·稳态降频, 还差 Ns) (service.py:528)。若一直是 未到拉取时刻(拉取间隔, 还差 Ns) (不带「稳态降频」), 就是常态间隔在跑, 即稳态未生效。

06为什么「排除」救不了场

把用户的动作串起来看, 逻辑是闭合的:

  1. 10-07→10-08 之间新增了 IYUU自动辅种 种子。这些种子属于已接入站点 (CarPT), 于是进入 anchors。
  2. 它们既无放行记录、又非终态, 做种时长也还没到 3×36H=108H 的超额线 ⇒ 落入 objects (对象集) ⇒ steady=False ⇒ 间隔闸退回 5H。这一步是设计本意 (新下载自动破稳态, 报告 §13.2), 不是缺陷。
  3. 用户随即在设置里把它们「排除 HR」, 期望恢复稳态。但排除的唯一判据 hr_excluded() 在取数侧没有任何调用点 (§04) ⇒ 这些种子照样进对象集 ⇒ 稳态照样打不上。
  4. 于是用户观察到: 明明排除了, 拉取频率却没降回来 —— 就是这个「排除不生效」。
自愈窗口为何救不了长期使用: 就算不修, 单颗种子做种满 108H 后会走超额线出对象集。但 IYUU 辅种是持续新增的, 任意时刻几乎总有若干颗 seeding_time < 108H 的在线 ⇒ 对象集长期非空 ⇒ 稳态长期打不上 (请求量、站点访问频率一直停在高位)。而对没有配 HR 规则的站点, required_seeding_time=0, 超额线整条判据失效 (required_seeding_time > 0 前置) ⇒ 这些站的排除种子永远出不了对象集。用户本次排除的正是「本该无需 HR 关注」的那一类种子 —— 排除无效使这个诉求完全落空。

07影响面评估

面是否有影响说明
HR 判定正确性无判定侧本来就认排除 (record.py 三入口 + 展示侧), 被排除种子不会被误打标/误管束; 本缺陷不改变任何判定结论。
防御强度 (漏 HR)无削弱缺陷是「跑得比该跑的更勤」, 不是「跑得不够」。方向安全。
取数频率 / 站点访问量有 (偏高)本应 24H 一波, 实际停在 5H 一波 (约 4.8×)；请求量与站点风控暴露同步偏高。
日额 / 频控余量被消耗每波 3 请求 × 更密的波次, 吃掉站点级日额 (max_requests_per_day), 挤占真正需要的取数。
稳态降频特性 (整条)对有排除种子的站点形同未启用计划 26-10-05-0555 声称的「请求量 −57%~−79%」在这类站点上拿不到。
展示一致性口径分裂界面显示「已排除 / 不管束」, 引擎却仍在为它翻页 —— 用户看到的与系统在做的相反。

08修复方向 (候选, 未拍板)

修复的实质是: 把「HR 排除」这条判据补齐到取数/对账侧, 使排除种子的语义在两侧一致。三档方案, 由轻到重:

方案做法优点代价 / 风险
A. 锚点采集即剔除 在 HrRuntime._anchors 里对 rec.hr_excluded() 为真的记录 continue。 改动最小、语义最直白; 对象集自然为空 ⇒ 稳态可生效。 被排除种子同时从 wave.local_hashes / local_names 消失 ⇒ 站点清单里对应的 A 档行不再被识别为本地命中, 反而会触发一次 .torrent 下载去登记身份 (_process_rows → pending_downloads) —— 多花配额。
B. 锚点带排除位, 只出对象集 给 HrAnchor 加 excluded: bool (或另传一个 excluded-hash 集合); _build_objects 里把 excluded 的 anchor 跳过, 但仍留在 local_hashes。 稳态能生效, 且保留「命中识别」能力, 不多下 .torrent; 语义精确。 要动 HrAnchor 结构 (注意它在放行记录快照/漂移判定链路里被引用, resolve.py:60-74); 需核对快照序列化不受影响。
C. 站点级开关 新增配置「本站是否让排除种子参与取数对账」。 把口径分歧显式化、可回退。 新增一个大概率永远为默认值的旋钮, 违反「程序能定的绝不配置」; 不推荐。

倾向: 方案 B —— 它在不削弱命中识别的前提下让稳态可生效, 与「排除 = 不纳入 HR 体系 (不打标 / 不在线核实 / 规则按未触发)」的既有文档口径 (models.py:49-51) 吻合。方案 A 的 .torrent 重复下载副作用需要评估后再定。

另需一并定的口径: 种子「中途被排除」(原本有放行记录 / index 行) 时, 是否要清理其既有的 verified / index 行? 本文倾向不清理 (排除是判定侧叠加态, 撤销排除后应能恢复原判定), 但需在实施计划里明确写死。

09未决问题 / 待确认

  • 引擎实际用的 interval: 请以 <data_dir>/hr/carpt.json 的 wave.idle_mode 为准 (True/False + healthy_ts), 本文对日志的解读 (§05) 只能证「稳态未生效」, 不能证「正在用 5H」。
  • 被排除种子的站点侧身份: 这批 IYUU 种子是否确实被 CarPT 列在「考察中(A 档)」? 若被列, 它们会长期留在对象集 (本文 §06 的长期化路径成立); 若没被列, 它们会在下一波被批量「未列出」放行而自行出对象集 —— 这两种情况的自愈速度不同, 需以站点文件 index / verified 佐证。
  • 是否要把本缺陷入池: 本文只做出报告 (证据快照); 「要修 / 排期」应在 issue 工位裁决 —— 未拍板前不入池。
  • 是否有第二处同类缺口: 「超额线」以外, 是否还有别的「判定侧认、取数侧不认」的种子属性 (如某些规则标签)? 值得在设计阶段一并列举。

  • 缺 infohash 的 A 档行走 elif lane == LANE_SCOPE or _row_looks_local(...) ⇒ 无论 A/B 都会下载 (A 档硬规则), 与是否在 local_hashes 无关。
  • 带 infohash 的行走 if h: 分支, 其「命中登记」并不以 local_hashes 为唯一入口 (dl_by_hash 亦可使它命中); 该分支不下载。
  • ⇒ A 与 B 对「对象集是否为空 / 稳态能否生效」的结果等价; 实质差别只是「被排除种子是否继续参与行匹配与身份登记」。

因此选 B 的理由修正为「爆炸半径最小」: 除对象集少一类成员外, 取数侧的命中识别 / 身份登记 / 下载触发 / 防伪全部与现状逐字相同, 改动可被单条守阵钉死 (见计划 §03.3 / §04 S3-2)。§08 的 A/B 选型结论 (选 B) 不变。
