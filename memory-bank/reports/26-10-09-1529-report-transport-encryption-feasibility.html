本地通道传输安全: WebUI 与 HR 取数通道的加密方案对比

现状两条本机通道(浏览器 WebUI ⇄ auto-qb 后端、浏览器扩展 ⇄ auto-qb 取数端点)全部是明文 HTTP + 共享令牌。本报告把成熟方案(TLS/本地受信 CA、反向代理、应用层 AEAD、网络层 VPN)逐个摆出来比对。核心结论有两层: 在「本机回环」这一默认形态下, 明文 HTTP 的残余风险有限, 加密的边际收益小; 而一旦把通道暴露到局域网或跨机, 唯一「正确且省事」的答案是 TLS。用户设想的「令牌加密载荷」在回环下技术上成立, 但在最需要它的跨机场景恰恰行不通 —— 浏览器只在安全上下文(HTTPS 或回环)才提供 Web Crypto。

01问题、口径与调研方法

要回答的问题

  1. 两条本机通道现在到底传输什么、暴露面在哪、已有的防护是什么。
  2. 「用 token 对数据加密, 两端解密」这个设想(方案 D)在技术上成不成立、成本多大。
  3. 相比成熟方案(TLS 本地受信 CA / 反代 / VPN), 各方案的优劣与适用面 —— 给出可拍板的分阶段路径。

方法

  • 外部调研: 以浏览器/规范官方来源为准(MDN 安全上下文、Chrome for Developers 的本地网络访问、mkcert/Caddy 官方文档), 博客类仅作旁证。
  • 本仓核实: 逐行核对两条通道的实现(鉴权/载荷/监听), 锚点见 §14; 结论里所有「现状」断言均可回代码验证。
  • 口径: 本报告只做方案对比与可行性, 不含实现。落地方案另行立项(专题 hr-channel-remote 已就跨机形态入池, 见 issues/26-10-09-0855)。
本报告里带版本号的外部事实(如 Chrome 142 的 LNA 推出时间)是 2026-10-09 这一刻的快照; 浏览器安全策略迭代很快, 落地时须以当时的官方文档复核。方案层面的取舍判断不随版本变化。

02结论速览

部署形态现状风险建议
同机回环(默认: web.host=127.0.0.1 / HR 端点恒 127.0.0.1) 低。载荷与令牌仅在本机回环上走, 嗅探回环需本机特权; 能嗅探的同用户进程本就能直接读 token 文件。 维持明文 + 令牌, 在文档里把残余风险写清。加 TLS 的边际收益小、成本不低。
WebUI 暴露到局域网(用户把 web.host 改成 0.0.0.0 或 LAN IP) 高。Bearer 令牌与全部载荷在 LAN 上明文可嗅; 拿到令牌 = 可删除种子 / 改配置。 必须上 TLS(本地受信 CA 或反代), 或改走 VPN/隧道。见 §06/§07/§09。
HR 通道跨机(NAS 后端 + 外部 PC 扩展, 见 issue 26-10-09-0855) 高。当前两端写死回环、形态不成立; 一旦放开, 明文 token 在 LAN 可嗅。 优先 TLS + 本地受信 CA; 若不愿在客户端装 CA, 可退而用共享密钥 AEAD 信封(§08)作受限兜底 —— 扩展侧可行, 因为它自身是安全上下文。
远程访问(不在同一 LAN) 不适用(现状不支持)。 引导走 VPN / 隧道(Tailscale/WireGuard/SSH), 让通道在网络层就已加密, 应用层零改动。

三条核心判断

判断一: 用户设想的「token 加密载荷」不是主方案, 也不该是。它能在回环下工作(回环算安全上下文, crypto.subtle 可用), 但在跨机 LAN 的 http://<私网IP> 页面里 Web Crypto 根本不存在 —— 恰恰在最需要加密的场景失效。见 §08、§10。
判断二: 加密要么在网络层(TLS/VPN), 要么别做。TLS 同时解决三件应用层方案难同时做好的事: 机密性(含头部令牌)、服务器身份认证、前向保密。自研 AEAD 信封要么缺后两者, 要么引入大量自定义协议风险。
判断三: 最该先做的不是加密, 而是「暴露即提醒/收口」。默认回环已经安全; 真正的高风险来自用户把 web.host 改成非回环却没意识到后果。在配置层给一道「暴露即加密」的提示或闸门, 收益远大于默认给回环上加密。

通道二: 浏览器扩展 ⇄ HR 取数端点

纵深防御Origin 白名单(仅 chrome-extension://, 可锁单扩展 id) + 任务 URL 白名单(SSRF 在下发任务时卡死) + 任务绑定(只收回派发过的任务、域名须一致)
端点4 个: GET /api/hr/tasks(领清单)、POST /api/hr/result(回传)、GET /api/hr/sites、POST /api/hr/refresh
载荷任务清单(URL/kind/id)、回传的页面 HTML 与 .torrent 字节(base64)
轮询扩展每 1 分钟拉一次清单; 站点侧节奏由后端把守

明文到底暴露了什么

  • 令牌本身在头部明文 —— 这是比载荷更值钱的目标。嗅到 web.token 即可冒充前端下发删除/暂停/改配置命令; 嗅到 hr.token 即可冒充扩展领任务、回传伪造数据。
  • 载荷明文 —— 种子名/哈希/路径、站点 URL、页面 HTML(含站点内容)、配置内容。
  • 元数据明文 —— 请求路径、方法、时序、大小(即便只加密 body 也挡不住)。
注意: 两条通道现状都只听回环。这意味着「明文」的实际暴露面 = 本机; 是否升级为「网络可嗅」取决于用户是否把 web.host 改出回环, 以及未来是否放开 HR 端点的跨机。

04威胁模型分层

「有安全风险」必须先落到具体威胁, 否则方案无从取舍。按攻击者位置分五层:

#攻击者位置能做什么传输加密能挡吗
T0 同机、同用户的进程(恶意软件/脚本) 直接读 web.token/hr.token 文件, 甚至读进程内存 否 —— 令牌文件对同用户可读, 加密通道也拦不住「有钥匙的人」
T1 同机、不同用户的低权限进程 理论上嗅探回环, 但抓回环流量通常需要管理员/驱动级权限 部分 —— 有价值但门槛高; 且同机场景通常已有更简单的攻击面
T2 局域网内的被动嗅探者(同 WiFi/交换机镜像端口) 嗅到明文令牌与全部载荷 是 —— 这是加密的主要正当理由; 前提是 web.host 已暴露到非回环
T3 局域网内的主动中间人(ARP 欺骗/伪造服务器) 除嗅探外, 还能冒充后端给扩展下发任意 URL(拿登录态打站点)、给前端返回伪造数据 部分 —— 只有带服务器身份认证的方案(TLS 证书校验)能挡; 纯共享密钥 AEAD 可挡「无密钥的伪造」但无前向保密
T4 恶意网页(跨站请求/DNS rebinding) 用浏览器自动带上/伪造的请求打本机端点 已有防护 —— token + Origin/Host 白名单 + 任务绑定已覆盖, 与传输加密无关
读法: T0 加密挡不住(T1 门槛高), 而默认回环形态下 T2/T3 不成立 —— 所以「默认给回环上加密」的收益很小。真正要解的是 T2/T3 在通道暴露后的场景, 以及为未来跨机形态备好答案。

05候选方案总览

方案一句话解决的威胁
A 现状加固保持明文回环 + 令牌, 补文档与暴露提示T4; 对 T2/T3 无解(故仅适用回环)
B HTTPS + 本地受信 CA程序自建本地 CA、签发本地证书, 让浏览器/系统信任T2 + T3, 机密性/身份/前向保密俱全
C 反向代理 / Caddy用 Caddy(内部 CA)或 nginx 在前置终止 TLS同 B, 但多一层部署依赖
D 应用层 AEAD(用户设想)token 派生密钥, 对载荷做 AES-GCM 加解密回环下可用; 跨机 LAN 失效(见 §08)
E 网络层 VPN / 隧道Tailscale / WireGuard / SSH 把通道裹进加密网络T2 + T3, 且对远程访问一并解决; 应用层零改动

另有一类「mTLS(双向证书)」用于强身份绑定, 但扩展的 fetch 不便携带客户端证书, 落地成本高, 本报告不作为候选。

06方案 B: HTTPS + 本地受信 CA(mkcert 式)

原理

自签证书的痛点不是「不能加密」, 而是「浏览器不信任」—— 未受信的证书在浏览器里会弹拦截页, 而扩展的 fetch 连拦截页都没有, 直接网络层失败。成熟做法是 mkcert 引入的「本地 CA」: 程序(或用户)一次性生成一个根 CA, 把它装进操作系统/浏览器的信任库, 之后用它签发 localhost/127.0.0.1 的叶子证书 —— 浏览器就绿灯信任, 无需每次点「继续访问」。

优点

  • 真 TLS: 机密性(含头部令牌)、服务器身份认证(证书校验)、前向保密(ECDHE), 三件一次到位。
  • 零协议自研: 用久经考验的实现(uvicorn 的 ssl 支持 + 标准证书校验), 不碰密码学细节。
  • 同时喂两条通道: WebUI(uvicorn)与 HR 端点都可以套同一套证书; 扩展只需信任同一个 CA。

成本与坑

  • 信任安装是最大的 UX 成本: 需要往 OS 信任库写根 CA(Windows certutil/证书存储、macOS 钥匙串、Linux update-ca-certificates + Chrome 走 NSS 库)。装 CA 需要用户授权, 且不同浏览器/系统路径不一 —— 这正是 mkcert 存在的理由, 但它也把复杂度留给了「首次安装」。
  • Python 侧需新增依赖: 当前 pyproject.toml 没有 cryptography/pycryptodome。生成 CA/证书要么引入 cryptography(或更省事的 trustme, 它内部依赖 cryptography), 要么 shell 调用 openssl(跨平台脆弱)。这是一次实打实的依赖增量。
  • 证书轮换/有效期: 叶子证书有有效期, 需自动续期, 否则某天突然失效(且扩展侧表现为难查的 Failed to fetch)。
  • 回环下是「过度工程」: 默认形态根本不需要它 —— 收益只体现在通道暴露之后。
适用: 通道需要暴露到 LAN(或跨机扩展)时的首选。建议做成「一键本地 CA」: 显式开启(保守默认关闭)、幂等、证书与 CA 落 <data_dir>、把信任安装步骤清晰引导给用户(或提供半自动脚本)。

07方案 C: 反向代理 / Caddy 内部 CA

把 TLS 终止交给一个成熟的反代, 后端继续只说明文回环:

  • Caddy: 对 localhost/内部主机名会自动用其内部 CA 签发证书(automatic HTTPS), 配置量极小; 代价是引入一个外部二进制依赖, 且其内部 CA 同样需要被客户端信任(或用户在浏览器里手动信任)。
  • nginx: 更通用, 但证书与配置全手写, 对「只想本地加密」的场景偏重。
与本仓的契合度: 项目定位是「单机长驻 Python 程序, 零第三方运行时依赖」的风格。引入反代等于把「部署形态」复杂化(多一个进程要管生命周期)。因此反代更像用户侧的可选方案(文档里给指引), 而不是程序内置路径; 程序内置首选方案 B。

08方案 D: 应用层 AEAD —— 对用户设想的深入评估

用户设想: 「auto-qb 用 token 对数据加密, WebUI 收到后解密, 扩展同理」。把它具体化为一个可评估的设计:

key = HKDF-SHA256(ikm = token, salt = 固定串, info = "auto-qb/transport/v1")  // 32 字节
nonce = 随机 96 bit(每条消息)
ciphertext = AES-256-GCM(key, nonce, plaintext, aad = 路径 + 时间戳)
wire = base64(nonce || ciphertext || tag)

它在哪儿成立

  • 回环下成立: http://127.0.0.1 与 http://localhost 是安全上下文, 所以前端页面与扩展 service worker 都能用 crypto.subtle 做 AES-GCM / HKDF(MDN 明确: 回环与 localhost 属 potentially trustworthy origin)。
  • 扩展侧更宽松: 扩展自身的 origin(chrome-extension://)本身就是安全上下文, 所以即便端点是明文 HTTP, 扩展仍能用 Web Crypto —— 这让方案 D 在「跨机扩展」场景里技术上可行。

它的致命约束(为什么不能当主方案)

约束一: 跨机 LAN 的 WebUI 页面用不了 Web Crypto。安全上下文只认 https/wss/file/127.0.0.0/8/::1/localhost/*.localhost。http://192.168.x.x:8080 不是安全上下文 ⇒ window.crypto.subtle 直接是 undefined。也就是说, 在「WebUI 暴露到 LAN」这个最需要加密的场景里, 前端侧的应用层加密根本跑不起来。
  • 想绕开就得引入不依赖 Web Crypto 的密码库(libsodium.js / TweetNaCl.js 这类 WASM/纯 JS 实现), 但那等于把「自研传输协议 + 前端密码库」两件高风险的事一起揽下 —— 相比直接用 TLS, 性价比极低。
  • 保护不到头部令牌: 若只加密 body, Authorization/X-Hr-Token 仍明文可嗅 —— 而令牌正是最值钱的目标。要连头部一起保护, 就得把「令牌+请求」整体塞进加密信封, 于是鉴权与传输彻底耦合, 复杂度陡增。
  • 无服务器身份 / 无前向保密: 共享密钥能挡「不知道密钥的伪造」, 但挡不住「持有密钥者的历史解密」(无前向保密), 也不提供证书式的身份语义。密钥一旦泄漏, 全部历史与未来都失守。
  • 自管 nonce / 重放 / 时钟: AES-GCM 的 nonce 复用是致命错误; 还要加时间戳/序号防重放 —— 这些都是 TLS 已经替你做好、而手写极易出错的细节。
  • Python 侧新增依赖: 服务端要 AES-GCM + HKDF, 同样要引入 cryptography 或 pycryptodome(当前两者都没有)。
  • 测试成本: 一套自研协议要配「两端对拍 + 篡改/重放/降级」的守阵, 而 TLS 的正确性由生态背书。
定位结论: 方案 D 不作为主方案。它唯一有意义的落点是: 「HR 通道跨机 + 用户拒绝在客户端装 CA」时的受限兜底 —— 且必须限定「扩展侧」(因为扩展是安全上下文), 明确接受「无前向保密、无证书身份」的降级, 并把 nonce/重放防护做扎实。即便如此, 也应优先推 TLS。

09方案 E: 网络层 VPN / 隧道

把「加密」交给网络层, 应用层一行不改 —— 这是最省心的路线, 尤其适合「不在同一 LAN 的远程访问」:

  • Tailscale: 基于 WireGuard 的零配置私有网, 设备间自动组网、加密与身份由平台管理; 适合「在家用 NAS、出门用笔记本」的形态。免费档够个人用。
  • WireGuard: 自建、极简、快; 需要一点网络配置(密钥、端点、路由)。
  • SSH 隧道: 最轻, ssh -L 8080:127.0.0.1:8080 nas 即可把远端 WebUI 映射到本地回环, 于是本地页面仍是 http://127.0.0.1(安全上下文), 链路由 SSH 加密。零应用改动。
与本仓的契合: 项目本身是「单机长驻」形态, 远程访问不是核心场景。因此 VPN/隧道更适合作为文档指引推荐给有远程需求的用户, 而不是程序内置能力。SSH 隧道尤其值得在文档里点名 —— 它用最小的代价同时解决了「远程」与「加密」。

10决定性前提: 浏览器安全上下文与 Chrome 142 LNA

上面的取舍都指向同一条底层规则: 浏览器只在「安全上下文」里给你现代加密与权限能力。这条规则决定了「加密必须在 TLS 层做」。

http://192.168.x.x / 其它私网 IP / 公网域名否否
浏览器扩展页 / 扩展 service worker(chrome-extension://)是是
这张表就是方案 D 的死穴: 「WebUI 暴露到 LAN」时页面是 http://<私网IP>, 非安全上下文 ⇒ 前端做不了应用层加密。要在 LAN 上让 WebUI 能加密, 唯一出路是先给它 HTTPS —— 而一旦有了 HTTPS, 加密本身就已经完成了。

Chrome 142 的本地网络访问(LNA): 一个新变量

  • Chrome 从 142 起(官方 2025-09-29 公告)推出「本地网络访问」权限: 限制公共网络来源 → 本地网络/回环目的地的请求, 需要用户先授权, 且仅安全上下文能请求该权限。
  • 对 WebUI 自身无影响: WebUI 页面来自 http://127.0.0.1, 它访问的是同源后端, 不是「公网→本地」, 不触发 LNA。
  • 对「用公网域名/隧道访问 WebUI」有影响: 若用户用外网域名反代到本机 WebUI, 该页面发往本机的请求可能被判为本地网络请求而需授权 —— 这也是「远程访问更该走 VPN/隧道(SSH 隧道后页面仍是回环)」的又一理由。
  • 扩展侧待观察: 官方博客点名了 Service Worker 的本地网络请求规则, 但未明确扩展(chrome-extension://)是否豁免; 扩展本就用 host_permissions 授权, 且现状已在拉回环。这是一条需要跟踪的变量(见 §14 复核清单), 落地时须实测。

12建议落地路径

按「先收口、后加密」排序, 每一阶段独立可用:

阶段 0 —— 默认形态: 维持明文回环 + 把风险写清(几乎零成本)

  • 保持现状(回环 + 令牌), 不引入加密。在配置 UI 与文档里明确: 回环下残余风险 = 同用户恶意进程可读 token 文件, 传输加密对此无解。
  • 把「同用户进程可读 token 文件」这条事实写进安全边界说明(扩展 README 的「安全边界」表已有雏形, 可补一行)。

阶段 1 —— 「暴露即加密」闸门(高性价比, 建议优先)

  • 在配置层检测 web.host 非回环(即 0.0.0.0/LAN IP)时, 给出显式风险提示, 并引导开启 HTTPS(方案 B)。保守默认不改变监听身份。
  • 这是「用最小改动换取最大安全收益」的一步 —— 因为它把用户从「不知情地明文暴露」推到「知情并可选加密」。

阶段 2 —— 内置「一键本地 CA」(方案 B 的工程化)

  • 新增配置键(如 web.tls.enabled / 证书路径), 必须同步进 validate_config 与 config/schema(黄金法则 4)。
  • 实现: 生成/复用本地 CA 与叶子证书(落 <data_dir>, 幂等), uvicorn 走 ssl; 给用户清晰的「信任根 CA」引导(或半自动脚本)。
  • HR 端点同理复用同一 CA; 扩展只需信任该 CA。跨机场景与 issue hr-channel-remote 一并推进。

阶段 3 —— 兜底与远程

  • 若「跨机扩展 + 拒绝装 CA」无法回避, 再评估方案 D 的受限版(仅扩展侧、共享密钥 AEAD、明确降级说明); 但要先证明方案 B 不可行。
  • 远程访问场景: 文档引导 VPN / SSH 隧道(方案 E), 应用层零改动, 顺带规避 Chrome 142 LNA。
一句话路径: 回环照旧 → 暴露就提示 → 一键本地 CA → 跨机复用同一 CA → 远程走 VPN。加密只在「通道真的离开本机」时才上, 且用 TLS 而不是自研。
