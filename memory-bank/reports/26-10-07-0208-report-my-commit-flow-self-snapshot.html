my-commit-flow 自我改写版本撕裂 · 临时目录快照自举

本包脚本与配置住在它自己中途改写的仓库里: 一次 ship.commit 内部的同步 rebase 会把远端新版包脚本 / 配置换进工作区, 于是同一次调用里"提交前"与"提交后"跑的可能不是同一版代码 / 同一份规则。既有修复(reload_config + refresh_package_modules)是逐点打补丁, 治标不治本 —— 本报告用原型实测确认「把整包复制到仓库外临时目录再运行」彻底可行, 并给出更完整的方案空间与实施计划。

01任务与验证方式

用户报告: my-commit-flow 在 pull 时会自我更新; 若它本身也被更新, 一次运行可能"一部分按更新前、一部分按更新后"跑 —— 之前的修复只是治标。提出的候选方案是「my-commit-flow 把自己复制到临时目录运行」, 要求验证可行性、或给出更好的方案, 并出报告。

验证方式分两步: ①代码事实核对 —— 通读 .commands/my-commit-flow/scripts/ 全部脚本与 references/, 逐点确认"启动时快照、之后一直用"的位置, 并核对既有修复的覆盖边界; ②原型实测 —— 在真 git 仓里对真实包注入快照机制, 端到端跑 commit.py --no-push, 并用"改写原包后跑旧副本"证明快照语义成立(§07)。原型脚本在 tmp-analysis/mcf-snapshot-proto/(临时区, 不入库), 核心模块全文见 §06 附录。

本报告只做分析与验证, 不改动生产脚本 —— 实施授权与批次由用户拍板。

02结论速览

问题判定依据
临时目录快照自举是否可行? 可行 · 原型 10/10 通过 真仓真包端到端提交成功; 副本在仓库外、含包脚本; 改写原包后旧副本输出不变(免疫), 新调用则采用新版本; import 不触发重入; 退出码 / argv 透传。代价: 16 文件复制 ~26ms。
是否有更好的方案? 无 —— 快照自举即最优解 「移出仓库」「git worktree」「两段进程」「继续打补丁」均有结构性缺陷(§05); 快照自举是唯一同时满足「不改复用模型 / 免疫一切自我改写 / 一次调用一个版本」的方案。
现有修复的性质 治标 · 有 5 处已知漏洞 入口脚本无法热刷新; importlib.reload 不重绑调用方已导入的名字; 配置重取只两个点; 逐点接线无不变量; 门控 / 依赖序本身脆弱(§04)。
核心结论: 采纳「快照语义」—— 一次调用只认一个版本。用临时目录复制 + 重入实现: 副本在仓库之外, git rebase 永远碰不到它, 中途的一切自我改写对本进程不可见。这同时把 §04 的五处漏洞一次性关掉(它们全部是"进程手里的快照过期"这一根因的表现)。

03问题定性: 自我改写 → 版本撕裂

这是一类自指(self-reference)缺陷: 工具的源码与配置就住在被它自己操作的仓库里, 而工具在运行中途会改写这棵树。

机制链

commands run ship.commit
  └─ 引擎调 /.commands/my-commit-flow/scripts/commit.py   (COMMAND_FLOW_PACK_DIR=<原包>)
       ├─ ① 启动时 load_config() 读 .my-commit-flow.toml         ← 快照 A(规则)
       ├─ ② import _pipeline / sync / push / _ship_config          ← 快照 B(代码)
       ├─ ③ 闸门 → 暂存 → commit → 核 ref
       ├─ ④ 内部同步 run_sync: fetch + merge --ff-only / git rebase
       │       ★ 远端若改过 .commands/my-commit-flow/**, rebase 会把新脚本 / 新配置
       │         写进工作区 —— 而进程手里的 A / B 还是启动时那份
       ├─ ⑤ rebase 后复跑闸门 / 收尾 amend
       └─ ⑥ 内联推送 run_push(内部还可能再同步一次)

撕裂发生在 ④ 之后: 进程继续用旧代码 + 旧规则处理已被换成新版的工作树。危害分两族(既有坑档已记):

族症状可见性
模块缓存族(self-rewrite-imports.md)延迟 import 的新脚本撞上进程缓存的旧依赖 ⇒ ImportError, 退出码被误置 1报出来
配置快照族(self-rewrite-config.md)闸门照跑, 只是规则不对(旧闸门集 / 旧 each_limit / 旧红线 / 旧生成物白名单); 输出与"全过"一字不差静默
用户说的"一部分按更新前、一部分按更新后"正是这个撕裂: ③ 之前是旧版, ⑤/⑥ 因为打了补丁而部分跟随新版 —— 同一次调用里混了两个版本, 且混合边界取决于补丁打在哪几个点, 不可预测。

04为什么现有修复只是治标

既有修复(commit 58f7bb0a)加了两件机制: _pipeline.refresh_package_modules()(热刷新包模块)与 _pipeline.reload_config() / sync._reload_cfg()(自我改写后重取配置)。它们各自解决了被发现的那一处, 但没有、也无法建立"一次调用一个版本"的不变量。逐点核对如下:

#漏洞代码事实后果
1 入口脚本自身永远无法热刷新 _pipeline._PACKAGE_MODULES = ("_ship_config", "_pipeline", "sync", "push") —— 不含 commit.py / verify_ref.py; 它们作为 __main__ 运行, 字节码在进程启动即固定 远端若改了编排逻辑(步骤顺序 / 输出契约 / 暂存分流), 本进程仍按旧编排跑新树
2 importlib.reload 只换模块对象, 不重绑调用方已导入的名字 commit.py:52 from _pipeline import (changed_files, run_gates, reload_config, …) 是 import 期绑定; reload 后这些名字仍指向旧函数对象 ⇒ 第 6 步复跑(commit.py:267 run_gates(...))调的还是旧闸门引擎 真正受益的只有 reload 之后才 import 的 sync / push; commit.py 自己的调用全部停在旧版
3 配置重取只覆盖两个点 仅 commit.py:255(复跑前)与 sync._reload_cfg(sync.py:178); verify_ref.py:27 的 REPO / BRANCH 是 import 期定死; commit.py 手里的 cfg dict 之后仍被用于红线 / warn / each_limit 其它读配置的路径照旧吃启动快照; 覆盖是"点"不是"面"
4 逐点接线, 没有全局不变量 同类缺陷已修两轮(模块缓存 → 配置快照), 每发现一处新组合就补一处 "旧代码 × 新树"的组合空间无法穷举 ⇒ 这类 bug 靠打补丁无法闭环, 只会不断复发
5 门控与依赖序本身脆弱 refresh_package_modules 按"源码变了"的内容摘要门控, 且注释自承 _pipeline reload 会重算 _PACKAGE_DIGESTS 的排序陷阱; 它看不见 commit.py / verify_ref.py 机制越修越复杂, 而覆盖仍不完整
定性: 现有修复把"混合两个版本"的边界从"随机"收窄到"补丁点", 但没有消除混合本身。用户的判断成立 —— 需要一个治本方案。

05方案空间与选型

方案机制优点缺点判定
A. 临时目录快照 + 重入
(用户提议)		 入口启动时把整包复制到仓库之外的临时目录, 从副本重入 一次调用 = 一个版本; 免疫一切自我改写; 心智模型简单; 副本含工作区未提交改动(所见即所跑) 需重入管道 + 真根注入; 失去"复跑用新规则"(见 §06 语义); 会留临时目录 推荐
B. 把包移出仓库
(独立安装 / 子模块)		 包不再住在 .commands/ 里 从根上无自我改写 破坏"整包复制即可带走"的设计; 引擎要求包在 .commands/ 下; 包与仓库版本同步变手工 否
C. git worktree 快照 在临时 worktree 里跑 HEAD 版 用 git 原生快照 只含已提交版(丢工作区改动 —— 正在改流水线自己时反而跑旧版); worktree 的 .git 文件让"根"歧义更复杂; 重 否
D. 拒绝自我改写
(检测到本包被改 → 停下要求重跑)		 rebase 后检测本包是否被换, 若是则停 无需复制; 显式 不能自动续推, 要人重跑; 仍是"半程" 可作补充
E. 两段进程
(提交 / 同步+推送 拆两次调用)		 每阶段独立进程 每段内部一致 段间仍撕裂(旧提交 + 新推送); 输出契约跨进程拼接复杂 否
F. 维持现状继续打补丁 逐点 reload 无迁移成本 治标; 已知 5 处漏洞; 无法闭环(§04) 否

选型结论: 采纳 A, 并把 D 降级为"提示"并入 A —— 快照让本进程免疫, 但"上游改动了本包"这件事对用户是有价值的信号, 应登记一行步骤行提示"重跑以采用新版本", 而不是静默。

06推荐方案: 快照自举(临时目录 + 重入)

6.1 语义: 一次调用 = 一个版本(快照语义)

启动时复制、从副本重入, 于是整个调用跑的是同一份代码与同一份配置。中途 rebase 把新版本写进工作区, 对本进程不可见 —— 新版本从下一次调用生效。这与"引擎不能中途换零件"同构, 简单、可预测, 一次性消灭整类撕裂。

关键取舍: 放弃"复跑用新规则"。既有补丁试图让复跑采纳合并后的新配置, 但那正是撕裂的来源, 且永远补不全(§04)。快照语义下改为: rebase 后若发现本包被上游改动 → 登记一行提示「本次仍按启动版本运行, 重跑以采用新版本」, 不静默。

6.2 契约(由 _snapshot.py 注入)

环境变量值作用
COMMAND_FLOW_SNAPSHOT1标记"已在快照里" —— 防止无限重入
COMMAND_FLOW_PACK_DIR<副本>覆盖引擎注入的原包路径 ⇒ 配置 / 模块一律从副本读
COMMAND_FLOW_REPO_ROOT<真根>副本在仓库外, 向上找不到 .git ⇒ 显式告知真根
COMMAND_FLOW_ORIGINAL_PACK<原包>诊断 / 排障
COMMAND_FLOW_SNAPSHOT_KEEP1保留临时目录(排障 / 测试)

6.3 入口用法(每个入口脚本 __main__ 分支, 3 行)

if __name__ == "__main__":
    sys.path.insert(0, str(Path(__file__).resolve().parent))
    from _snapshot import maybe_respawn
    _rc = maybe_respawn(__file__)      # 未在快照里 → 复制 + 重入, 返回子进程退出码
    if _rc is not None:
        raise SystemExit(_rc)          # 已由子进程接管
  • 放在 if __name__ == "__main__" 下 ⇒ 测试 import commit 不受影响(__name__ 非 __main__)。
  • 重入用 subprocess.call(非 os.execv) —— Windows 上 exec 语义不可靠, 多一层进程换稳定。
  • 纯信息入口(--help / -h / --safety / --show-config / --init)不复制, 直接作用于原包 —— 尤其 --init 要把配置写进真包, 不能写进临时副本。

6.4 需要同步改的两处

  • _ship_config.find_root(): 顶部加一行 —— 有 COMMAND_FLOW_REPO_ROOT 就用它(副本在仓库外, 原有的"向上找 .git"会落到错误位置)。
  • 退役 refresh_package_modules / reload_config 及其调用点 —— 快照语义下它们不再有意义, 留着是死代码。

6.5 附录: 原型模块全文(已验证)

"""包快照自举: 把本包复制到仓库之外的临时目录后再运行 —— 让一次调用只认一个版本。"""
from __future__ import annotations
import os, shutil, subprocess, sys, tempfile, time
from pathlib import Path

SNAPSHOT_ENV = "COMMAND_FLOW_SNAPSHOT"
REPO_ROOT_ENV = "COMMAND_FLOW_REPO_ROOT"
ORIG_PACK_ENV = "COMMAND_FLOW_ORIGINAL_PACK"
PACK_DIR_ENV = "COMMAND_FLOW_PACK_DIR"
KEEP_ENV = "COMMAND_FLOW_SNAPSHOT_KEEP"
SNAPSHOT_PREFIX = "my-commit-flow-"
SWEEP_AGE = 24 * 3600                      # 超过一天的旧快照清掉(强杀时 atexit 不跑)
INFO_FLAGS = ("--help", "-h", "--safety", "--show-config", "--init")

def _pack_dir(entry_file):
    return Path(entry_file).resolve().parent.parent

def _find_repo_root(start):
    for parent in (start, *start.parents):
        if (parent / ".git").exists():
            return parent
    return None

def _sweep_old():
    base, now = Path(tempfile.gettempdir()), time.time()
    for entry in base.glob(SNAPSHOT_PREFIX + "*"):
        try:
            if entry.is_dir() and now - entry.stat().st_mtime > SWEEP_AGE:
                shutil.rmtree(entry, ignore_errors=True)
        except OSError:
            pass

def make_snapshot(src_pack):
    _sweep_old()
    dest = Path(tempfile.mkdtemp(prefix=SNAPSHOT_PREFIX))
    shutil.copytree(src_pack, dest / "pack",
                    ignore=shutil.ignore_patterns("__pycache__", "*.pyc"))
    return dest / "pack"

def maybe_respawn(entry_file, argv=None):
    if os.environ.get(SNAPSHOT_ENV) == "1":
        return None
    args = list(sys.argv[1:] if argv is None else argv)
    if any(f in args for f in INFO_FLAGS):
        return None
    src_pack = _pack_dir(entry_file)
    repo_root = _find_repo_root(src_pack)
    snap_pack = make_snapshot(src_pack)
    child = snap_pack / "scripts" / Path(entry_file).name
    env = {**os.environ, SNAPSHOT_ENV: "1", PACK_DIR_ENV: str(snap_pack),
           ORIG_PACK_ENV: str(src_pack)}
    if repo_root is not None:
        env[REPO_ROOT_ENV] = str(repo_root)
    try:
        rc = subprocess.call([sys.executable, str(child), *args], env=env, cwd=os.getcwd())
    finally:
        if os.environ.get(KEEP_ENV) != "1":
            shutil.rmtree(snap_pack.parent, ignore_errors=True)
    return rc

07可行性验证(原型实测)

原型对真实包注入快照机制: 建真 git 仓 → 把真包复制进 <repo>/.commands/my-commit-flow/ → 注入 _snapshot.py + 入口守卫 + find_root 的 env 覆盖 + 最小配置(无闸门, 隔离快照机制本身) → 跑真 commit.py。全部 10 项断言通过(可重复):

#用例断言实测
T1端到端提交commit.py --no-push 经快照重入后提交成功PASS 提交成功 <hash>(未推送 —— 补推: …)
T2副本位置生成仓库之外的临时副本, 且含包脚本PASS H:/Temp/my-commit-flow-xxxxxxxx
T3a免疫(核心)改写原包后, 跑旧副本 → 无新版哨兵PASS 输出不含 SENTINEL_V2
T3b采纳改写原包后, 新调用 → 采用新版(有哨兵)PASS 输出含 SENTINEL_V2
T4测试不受影响import commit 不触发重入(副本数不变)PASS
T5信息入口_pipeline.py --show-config 不复制且读原包配置PASS
T6根解析find_root() 经 env 指向真仓库根PASS
T7退出码透传失败场景 rc=1 透传给调用方PASS rc=1

开销: 包共 16 个文件; make_snapshot 实测 min 22.5ms / max 38.2ms / avg 26.2ms(5 次)。加上一次额外 Python 启动, 单次调用总开销约百毫秒级 —— 对提交流水线可忽略。

T3a / T3b 是快照语义的直接证据: 同一个副本在"原包已被改写"之后仍产出旧行为(免疫), 而原包的新调用产出新行为(采纳)。这正是"一次调用 = 一个版本"的定义。

09风险与边界

项风险处置
Windows 进程os.execv 不真正替换进程 / stdio 继承有坑用 subprocess.call + sys.exit(rc)(原型已验证)
临时目录泄漏强杀 / 崩溃时 finally 不跑启动时清扫 >1 天的旧快照; 正常路径 finally 删除
--init 写错位置从副本跑会把配置写进临时目录而丢失INFO_FLAGS 让纯信息入口不复制, 作用于原包
不在 git 仓里找不到 .git, 注入错误根找不到就不注入, 让脚本走自己的兜底
调试栈指向临时路径报错里 __file__ 是副本路径, 排障时困惑注入 COMMAND_FLOW_ORIGINAL_PACK; 可选: 失败时保留副本并打印其路径
冒烟闸门扫到新脚本<each:.commands/**/scripts/*.py> --help 会带上 _snapshot.py无 main ⇒ 跑 --help 无副作用, rc=0, 无害
闸门(外部工具)仍跟仓库走<skill-dir:commands> 等被 rebase 换掉这是对的: 闸门要测被测的树, 每次都是新进程、内部一致; 必须固定的只有流水线自身
语义变化失去"复跑用新规则"用「本包被上游改动」步骤行提示重跑; 这是刻意的取舍(§06.1)
