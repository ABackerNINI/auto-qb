00结论摘要

一句话根因

qB 的 all-time 计数器在瞬时速率字段恒读 0 的情况下持续增长（已实锤：当前 ~550 B/s 双向，且不落在任何现存种子的 payload 上）；采样器以速率字段 (0,0) 为判据开启 z 游程，而 z 游程的 totals 快照冻结在开启时刻 —— 于是 10-15 凌晨 6.6 小时的计数器增长（+15.3 MB 下行 / +16.5 MB 上行）在磁盘上零痕迹；进程重启后新实例首个采样读入新鲜 totals，读侧 rate = delta/w 口径把整个陈旧差打进接缝处的单个桶，形成 6.9 MB/s 的幻影尖峰；同一接缝（末样 06:36:00.5 → 首样 ~06:36:10，约 10s）在 raw 视图呈现为 null 桶游程（无采样区斜纹），叠加旧 WEBUI 死亡到新活尾落袋的投递黑障，用户看到无采样区「延伸到观察时刻」。

02现象一定位：异常峰值

2.1 机理链（四环相扣）

环 1 · qB 侧速率字段恒 0alltime 计数器在涨，但 dl_info_speed / up_info_speed 读 0。本版修正语义：该字段是 payloadDownloadRate（payload 口径），读 0 只表示「没有载荷」，不是「qB 算不出总速率」—— session 级总速率 m_status.downloadRate（= alltime 差分）存在，但 WebUI 不暴露它
环 2 · 采样器z 游程 + 快照冻结_sample_global 以速率 (0,0) 为判据开 z 游程；z 游程 totals 快照冻结在开启时刻（00:00:01.5），此后每轮读到的 totals 被丢弃
环 3 · 落盘磁盘链陈旧stop() 封口的 z 行只带 (0,0) 与开启快照；6.6 小时增长在 2026-10-15.dat 上零痕迹
环 4 · 读侧delta/w 单桶归因新实例首样新鲜 totals 与磁盘链末点的差，被 v4_rate_from_totals（rate = delta/w）整个打进接缝桶

2.3 前作口径的边界缺口

26-10-07-2031-report-qb-traffic-rate-basis（delta/w 口径立项）对边界语义的判研是「qB 重启 = all-time 计数器经 fastresume 持久，通常无缝」——那覆盖的是 qB 进程重启（计数器不丢）。本次事故是 auto-qb 进程重启：磁盘链末点是 z 游程的陈旧快照，而 qB 计数器在 auto-qb 停机期间照常增长 —— 两类重启的接缝语义不同，前作未覆盖此情形。

4.5.1 计数器链：alltime 到底由什么合成

环节事实出处
qB 的 alltime 合成式 allTimeDownload = 历史持久值 + m_status.totalDownload，而 totalDownload = stats[net.recv_bytes] + stats[net.recv_ip_overhead_bytes]；totalUpload 对称用 sent_*。 sessionimpl.cpp:6569-6572
sessionimpl.cpp:6625-6626
WebUI 的 payload 字段 dl_info_speed = payloadDownloadRate、dl_info_data = totalPayloadDownload（= net.recv_payload_bytes）。与 alltime 是两套口径，所以「payload 全 0」与「alltime 在涨」可以同时成立。 synccontroller.cpp:164-167
sessionstatus.h:39-71
net.recv_bytes 的自增点 唯一入口 session_impl::received_bytes(payload, protocol)：recv_bytes += payload + protocol，recv_payload_bytes += payload。BT 协议里只有 piece 块数据走 payload 分支（received_bytes(received, 0)），其余 43 处全部是 received_bytes(0, received) —— 握手、keep-alive、bitfield/have、choke/interested、request/reject、扩展握手（ut_metadata/ut_pex）、DHT-port 等一律以 payload=0 记入 recv_bytes。 session_impl.cpp:3454-3464
bt_peer_connection.cpp:1078/1087（仅此两处带 payload）
其余 43 处 payload=0
net.recv_ip_overhead_bytes 是模型量 trancieve_ip_packet(bytes)：overhead = max(1, ceil(bytes/1460)) * 40，同一次调用同时加到 sent 与 recv 两侧（TCP 假定每个数据包都带回一个 ACK）；出站建链另有 sent_syn() +40（仅 sent 侧）与 received_synack() +40/+40（双向）。宿主私有种子下 DHT 关闭，故 DHT 的 +28/48 项为 0。 session_impl.cpp:3466-3483
session_impl.cpp:3485-3503
peer_connection.cpp:451 / 6384
dht_tracker.cpp:493/718
「双向近似对称」由此而来 IP 开销对每个收发动作双向各记一次，握手数据本身也近似对称 → dl≈ul；每连接多一次「SYN 只记 sent」的 +40，故 dl 恒略小于 ul。与四次实测的 dl/ul = 0.92–1.00 完全吻合。 同上；实测见 §4.5.4

4.5.2 被排除的既有猜测（本版实测 + 源码双向否证）

原猜测否证依据
DHT / PeerExchange 实测 prefs：dht=false、pex=false、lsd=false；且 180 个种子全是私有种子，tracker 列表里 DHT/PeX/LSD 三条均显示「这是私有 torrent」（per-torrent 亦禁用）。另注：即使开启，DHT 也只有 IP 开销（+28/48 per datagram）会进 alltime，报文本体走 dht.bytes_in/out。
tracker 开销 tracker 字节走独立计数器 net.recv_tracker_bytes / sent_tracker_bytes，不参与 alltime 合成（qB 只取 recv_bytes + recv_ip_overhead）。实测实例确实在正常 announce（4 个 PT tracker 状态均 = 2「Working」，其中一个返回 4 个 peer），但它对 alltime 零贡献。修正 §04.4 原表述。
uTP 报文开销 uTP 虽在启用（bittorrent_protocol=0 = TCP+uTP，日志可见 端口:UTP/61323），但入站 UDP 包在 session_impl::on_udp_packet 里直接交给 uTP 管理器，不做 net.* 记账；uTP 的包计数落在 utp.* 独立计数器，纯 ACK 包不会变成 alltime 的字节。
「被丢弃的载荷」 redundant/failed 字节是 payload 的子集（net.recv_redundant_bytes + recv_failed_bytes → total_wasted）；payload 全平即证明细流里没有这类字节。

4.5.3 机制：为什么「有字节、无 payload、无 peer」能同时成立

前提全部完成、纯做种180 个种子：120 stalledUP / 36 stoppedDL / 24 missingFiles，is_finished() 为真；announce 正常、swarm 里有 peer（tracker 返回 0–4 个）
建链出站连接尝试libtorrent 对被 announce 回来的 peer 持续发起连接；sent_syn() 记账（+40 sent），建链成功再 received_synack()（+40/+40）
握手非载荷字节MSE 加密握手（encryption 非关闭）+ BT 握手 68B + 扩展握手/bitfield —— 全部 payload=0 → 进 recv_bytes；每笔 socket 收发再按模型加 IP 开销
立刻断开seed↔seed 冗余两端都是 seed 时 libtorrent 主动断开：errors::upload_upload_connection（close_redundant_connections 默认 true）→ 连接存活 <1s、从不进 peer 表，故 total_peer_connections 恒 0、payload 恒 0，只剩握手字节

断开判据出处：bt_peer_connection.cpp:2123-2129（t->is_finished() && upload_only() && close_redundant_connections → disconnect(upload_upload_connection)）与 peer_connection.cpp:2344-2350；开关默认值见 settings_pack.cpp:150（SET(close_redundant_connections, true, nullptr)），qB 未覆盖它。

09未决与待确认

  • 细流的 qB 侧精确来源 —— 本版已定位：计数器链、自增点、被排除项与量级闭环见 §04.5。剩余未拆分项只有一处：单连接约 2.2 KB 里「MSE 握手 / BT 握手 / 扩展握手 / bitfield」各占多少无法从 WebUI 观测面拆分（qB 不暴露 libtorrent session_stats 原始计数器）；要拆到字节级需受控环境抓 net.* 计数器或抓包，属可选深挖，不影响本事故的修复结论。
  • 用户观察时刻的精确对应：浏览器渲染时序无日志；「延伸到观察时刻」已由投递黑障机理解释，但用户实际观察窗与黑障窗的秒级对应无法复盘。
  • 拍点跳过 ~2%（15,518 vs 15,839 槽）：任务线竞争的次要注记，读侧等距重建自洽，建议另案评估是否需要在槽位密度上显式化。
