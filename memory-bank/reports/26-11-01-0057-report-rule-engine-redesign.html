§01 · 结论先行核心矛盾与决策建议

根因一句话:执行模型已经从「同一 Tracker 引用下的规则顺序链」演进为「每规则每种子独立任务 + 事件即时分派」,但控制流语义(stop_following_rules_if)、容错语义(ignore_next_action_error)和调用契约(process 返回的 handled/stop)还停留在旧链式模型上,且返回值在生产路径被整体丢弃——「规则」这一个抽象同时承担了触发、条件、动作序列、去重、链间控制流五种职责,后两种在现行架构里已无承载点。

三条判断

  • 死配置要删,不要做实。stop_following_rules_if 六档全部无消费者(§02 G1),条件出错日志宣称「停止后续规则」与实际行为不符。修复方向取 issue 1304 报告的②:承认无链、降级配置;确需「首中即停」时以引擎级一等参数(easy-rules 的 skipOnFirst* 模式)表达,而非规则字段。
  • 控制流不要藏进数据字段。{"ignore_next_action_error": true} 是一条「没有动作语义的动作」;成熟系统(HA / Zapier / easy-rules)无一例外把错误策略做成 per-step options 对象或引擎级参数——步骤元数据与动作内容分离。
  • 规则间不级联是特性不是缺陷。ECA 学术共识:级联触发是 termination 问题的根源,必须显式收口;跨规则协作的正确答案是把状态做成可引用的具名共享状态(HA helper entity 模式),让规则通过读写状态间接通信。

建议形态(8 个最小原语,详见 §06)

trigger(已有)→ 条件组合树 all/any/not → 动作序列 + 每步 on_error → choose 分支块 → 引擎参数 mode/evaluation → 具名状态 → per-run trace → 单一 registry。明确不做:Rete/增量匹配、规则间级联、规则依赖图、通用循环、图灵完备表达式语言。选型蓝本是 Home Assistant automation——与本项目「事件 + 定时 + 实体状态 + 动作序列」场景同构度最高,其 mode / continue_on_error / try-except / trace 四件套可直接对照;Drools 只学语义词汇不学匹配算法,Rete 对「每种子 × 十来条规则的一次性快照求值」属过度设计。

§03 · 成熟系统逐个拆七类系统的执行模型与错误策略

「触发→条件→动作」三段式是所有成熟系统的最大公约数;分歧只出现在编排(谁先谁后)、错误策略(每步怎么失败)、执行语义(全执行/首中即停/agenda)三个维度。逐个展开(默认收起,点开细读)。

Drools(Rete/PHREAK)只学词汇,不学算法

核心抽象:事实(working memory)+ 规则(when-then)+ 匹配网络 + agenda。插入事实 → Rete/PHREAK 增量算出所有匹配(activation)→ 放入 agenda → 按 salience 逐条 fire,fire 中的动作可再插入事实触发新一轮匹配。条件用 DSL(when 子句)模式匹配 + join 编译进网络节点;错误处理引擎层不管,consequence 是任意 Java 代码。编排词汇:salience(数值优先级)、agenda-group(分组+setFocus)、activation-group(组内首条 fire 后取消其余,XOR)、ruleflow(显式流程图)。

为何对本项目过度设计:Rete 解决「N 条规则 × M 个事实,事实频繁增量变化时避免全量重匹配」;本项目事实 = 单个种子的字段快照、规则十来条、每次事件都是一次性「拿快照→顺序求值」,网络节点缓存毫无收益。该学的是语义词汇(salience / activation-group =「首中即停」的组化表达),不是匹配算法。

OPA/Rego 与 Google CEL表达式策略引擎路线

OPA:策略即代码,PDP/PEP 分离——引擎只做「给输入,回决策」,执行完全归应用,带 decision log 审计;Rego 是 Datalog 血统。OPA 只回答「是否允许/给什么结论」,不执行副作用动作。CEL:设计目标就是「不做成规则引擎」——非图灵完备(保证终止)、纯表达式无副作用、纳秒-微秒级可预期开销、compile-once-eval-many;Kubernetes admission / IAM Conditions 用它做条件求值层,编排/动作/状态全留宿主。

边界结论:表达式引擎路线 = 条件表达力↑、编排能力 = 0,把 G6(动作编排)完全排除在语言之外——条件用表达式、动作仍用结构化列表恰是最优切分,而不是全盘 Rego 化。Go 的 expr / Grafana alerting 走同款路线。

json-rules-engine(JS)条件组合代数

规则 = {conditions, event};conditions 是递归组合树:组合节点 all/any/not 任意嵌套,叶节点 {fact, operator, value},fact 可为计算型(async)或 JSONPath 深挖。engine.run(facts) 默认全部规则独立求值互不影响,无内置顺序/优先级——复杂分支一律用嵌套条件表达;每条规则求值结果(成功/失败及失败事实)可回收,天然支持「哪个条件没过」的可观测性。错误处理:动作 = 声明 event 由外层消费,fact 求值异常有 on('failure') 钩子。

最有价值的点:组合树是 13 种硬编码条件算子的替代方案——新增条件只需新增 operator,NOT/OR 组合逻辑零成本获得。

easy-rules(Java,维护模式)停止语义的一等参数化

Rule = name, description, priority, condition(facts), action(facts);priority 小者先执行,顺序执行全部规则(没有 Rete)。RulesEngineParameters 就是「停止语义的一等参数化」,是对本项目 G1 最直接的对照:

参数默认语义
skipOnFirstAppliedRulefalse首条命中即停
skipOnFirstNonTriggeredRulefalse首条条件不满足即停(顺序链场景)
skipOnFirstFailedRulefalse首条失败即停
rulePriorityThresholdMAX_INT超过优先级阈值即停

四个布尔开关在引擎层消费 fire 的返回信号,而不是让用户在 condition/action 里塞哨兵字段;默认全 false = 全执行。失败定义:action 抛异常 = 该规则 failed;不设 skip 时默认继续下一条,失败详情经 rule listener 回调暴露。CompositeRule 把多条规则打包成一条(组内按 priority 顺序)。

IFTTT / Zapier 管道per-step error policy

Zapier 每步结果是一个枚举状态机:success / errored / halted / filtered,而非布尔。关键区分:errored(平台/瞬时故障,可 autoreplay 重试)vs halted(该次数据问题,重试无意义,只停本次 run)。per-step 策略组合:①Filter step(前置校验,失败 = 正常结束而非错误——把可预料的失败转化为条件)②Paths(显式分支,每分支自带条件)③Autoreplay(run 级重试)④错误通知。没有 per-step try/catch——答案是「预料到的失败用 Filter 前置消化」。IFTTT 更简单(trigger→filter code→action,基本无错误策略),反面印证「策略要给足而不是做多」。

ECA(active database 学术经典)级联必须收口

经典语义 ON event IF condition DO action 之外的两个关键设计点:Coupling mode(规则与触发事务的耦合:immediate / deferred / detached——对应本项目「事件即时分派 vs interval 轮询」,其实已隐式拥有两种 mode);Cascading 与 termination(规则动作触发新事件→级联激活其他规则;学术结论:级联必须显式收口——或禁止、或最大迭代数、或优先级选择,否则 non-termination 是必然事故)。

对本项目:G3 的正确答案不是做级联,而是 ECA 文献的反面教训——明确「规则间不级联」是特性不是缺陷;跨规则协作用共享状态间接通信,不直接触发。

Home Assistant automation与本项目最同构,设计蓝本

HA automation = trigger + condition + action,与本项目几乎一一对应,但把本项目缺失的承载点全部做成了一等公民:

本项目缺口HA 对应设计
触发模型trigger 列表(事件/状态变化/时间/区间/模板);明确「对变化反应,不对持续状态反应」——状态类判断放 condition,触发只认 change
条件组合(G4)默认全部 AND;OR/NOT 用 and/or/not 组合块显式包裹(= json-rules-engine 组合树思路)
动作编排(G6)action 是脚本化序列,内建 building block:choose(if/elif 分支+default)、if/then/else、repeat(count/while/until/for_each)、wait、parallel——分支是动作域内的显式语法块,不是伪动作项
单步错误策略(G5)每步可写 continue_on_error: true(失败继续)与 enabled: false(按模板条件跳过)——per-step options 对象,与动作类型无关的横切属性;默认失败 = 中止本次 run
结构化失败处理2024.10 起内建 try / except(error filter + error_variables) / finally 块
重试不在每步内建 retry,重试由用户用 repeat/wait 表达,保持原语少
并发重叠语义mode: single(默认,重触发忽略)/ restart(杀旧起新)/ queued / parallel,配套 max、max_exceeded——本项目「每规则×每种子独立任务」缺的并发重叠策略一等表达
去重/状态(G7/G3)无内建去重;状态一律外置(helper entity/timer),规则间通信 = 读同一 helper——可引用共享状态,而非引擎内建黑盒
可观测性trace 系统:每次 run 记录每步 verdict(命中/跳过/错误、各条件求值结果),保留最近 N 条——「为什么这条自动化没跑」有确定性答案
优先级没有规则间优先级——规则独立,顺序问题在单条规则的 action 序列内解决

§04 · 横切设计原语一个「完备」规则引擎的正交维度

  1. 触发模型:事件即时 / 轮询 / 混合。要点:触发只认「变化」,持续状态判断归条件(ECA coupling mode;HA 的 react-to-changes 原则)。
  2. 条件组合代数:两选一——①结构化递归树 all/any/not(json-rules-engine、HA)②受限表达式(CEL/expr)。比「13 种枚举算子」可演进:新增只是新增 operator/函数,组合零成本。
  3. 规则间编排:谱系「无编排(独立执行)→ priority 排序 → 首中即停组(activation-group/CompositeRule)→ 显式流程图(ruleflow)」。成熟共识:默认无编排,需要时给 priority + skipOnFirstApplied 两三个参数即可覆盖 90% 场景;链式依赖(下条规则依赖上条副作用)是公认反模式。
  4. 执行语义:全执行 / 首中即停 / agenda。小系统取前二;easy-rules 证明「全执行为默认 + 3 个 skip 开关」即可参数化全部语义。
  5. 错误处理(per-step policy):每步独立 options:continue_on_error、结构化 try/except/finally、失败分类(errored=可重试瞬时 / halted=数据性,Zapier)、run 级 autoreplay。错误策略是横切属性,挂在步骤上,不是动作类型的一部分。
  6. 状态与去重:内建黑盒去重 vs 可引用共享状态。成熟系统(HA)选外置共享状态:去重、跨规则通信(G3)、跨轮次记忆(G7)统一为同一原语「规则可读写的具名状态」。
  7. 并发/重叠语义:同规则同主体再次触发怎么办——single/restart/queued/parallel(HA mode);事件+定时混合系统的必备维度。
  8. 可观测性:per-run trace——每步 verdict(通过/跳过/错误+原因、条件求值细节)持久化最近 N 条(HA trace / OPA decision log 同款)。
  9. 可演进性(插件注册):条件/动作 = 向单一注册表注册的 (类型名, 求值/执行函数, schema 声明) 三元组;schema 从注册表生成(json-rules-engine operator 注册、CEL 函数库注册模式),杜绝「加一个动作改 4 处」(G9)。

6.2 最小完备原语集候选(8 项)

完备判据:能表达「触发→条件→动作序列→单步错误策略→去重」且无伪语法;不复杂判据:无 Rete/规则链/级联。

  1. trigger(已有):on_torrent_added / on_field_changed / interval,保留事件+轮询混合;补 HA 原则进文档——持续状态判断写条件,不写轮询。
  2. conditions 组合树:叶子 {field, operator, value} + 组合 all/any/not(递归),替代 13 枚举;条件求值异常 = verdict:error,规则不命中,不影响他规则(修 G2/G4)。
  3. actions 有序序列 + 每步 options:{type, params, on_error: {policy: stop|continue|retry, retries, backoff}, enabled};policy 替代 ignore_error 与伪动作项(修 G5);stop 仅中止本规则本次 run。
  4. choose 块(唯一新增编排块):{choose: [{when: <cond树>, then: [...]}], default: [...]}——动作域内分支,G6 的最小子集。
  5. 执行语义引擎参数(每规则可选):mode(single/restart/queued,借 HA)+ 可选 evaluation: all|first_match(借 easy-rules skipOnFirstAppliedRule)——以引擎层一等参数替代 stop_following_rules_if(修 G1)。
  6. 具名状态:规则可读写的键值状态(去重 = 预置模式,跨规则通信 = 读写共享键),落 state_file(修 G3/G7)。
  7. per-run trace:每种子×每规则每次求值记录每步 verdict(条件树结果、动作结果、错误类别),保留最近 N 条(修可观测性,支撑排障)。
  8. 单一 registry:条件/动作/块统一注册(类型→函数+schema+文档),schema 与校验从注册表生成(修 G9,顺带收编 G13/G10/G11)。
# 6.3 目标形态示例(YAML 示意, 非本次实现; 中文注释)
# 规则 spec: 组合树条件 + 每步 on_error + choose 分支
rule:
  trigger: on_torrent_added          # 事件即时分派 (已有)
  mode: single                        # 引擎参数: 同种子重触发忽略 (借 HA)
  conditions:
    any:                              # 组合树: OR (替代「逗号分组」约定)
      - { field: path,  operator: contains, value: "/movies/" }
      - all:                            # 嵌套 AND
          - { field: size, operator: ">=", value: "10GiB" }
          - not: { field: tags, operator: contains_any, value: [archived] }
  actions:
    - type: add_tags
      params: { tags: [auto] }
      on_error: { policy: retry, retries: 3, backoff: 60s }   # 每步选项, 不再是伪动作项
    - choose:                          # 动作域内显式分支 (G6 最小子集)
        - when: { field: category, operator: exists }
          then: [ { type: add_tags, params: { tags: [has-cat] } } ]
      default: [ { type: add_category, params: { category: uncategorized } } ]

6.4 明确不做(不复杂边界)

  • Rete / 增量匹配——事实非持续增量变化,一次性快照求值用顺序循环即可。
  • 规则间直接级联触发——ECA 学术共识的反面教训;跨规则协作走具名状态。
  • 规则依赖图 / 显式流程图——90% 场景「默认无编排 + 两三个引擎参数」已覆盖。
  • 通用循环(repeat/while)——choose 先行,循环按需再加,不做图灵化。
  • 图灵完备表达式语言——如需更强条件表达,届时再评估内嵌 CEL 类表达式作叶子求值器。
