01 / 结论速览

路线 A 适配且互相增强; 路线 B 不适配跨机目标

两份文档在解两个不同轴的问题: 跨机计划解空间轴(端点绑哪个地址、扩展认不认非回环、传输与鉴权); 去端口报告解配置轴(用户零配置、端口随机化、token 自动分发、轮询还是推送)。两者的交集是连接模型——而跨机计划的数据流图本来就是「扩展拨后端」, 与去端口报告唯一的硬事实(只有扩展能发起连接)方向一致, 不构成冲突。

路线对跨机计划一句话理由
A · 发现端口 + 随机数据端口 + token 分发 适配 · 推荐 保留计划全部不变项(轮询/token 文件/origin 白名单), 还把跨机配置面从「端点 URL + token」缩到「NAS 地址」一项。
B · native messaging 桥 + 命名管道 不适配 原生消息宿主只能由本机浏览器拉起, 结构上到不了 NAS; 对跨机配置面零缩减, 还多付桥组件 + 注册表注册, 并打破计划 §7.2「协议不变」不变项。
C · 发现 + WebSocket 长连接(报告 §06) 同 A 的子问题 寻址与配置面同 A; 是否上推送是独立决策, 不改变「选 A 不选 B」的结论。
联合结论: 跨机计划的落地路线 = 计划自身的路径 C(端点直绑)作为产品化主体, 叠加去端口报告的路线 A 作为配置层; 传输拍板(D1)从「覆盖 1 个端点」扩为「覆盖发现 + 数据 2 个端点」; 路线 B 缓行, 不并入本计划。

03 / 路线 B 为什么不入围

原生消息桥结构上到不了 NAS

  • 宿主只能由本机浏览器拉起: native messaging 的桥进程由外部 PC 的 Chrome 按清单启动、走 stdio。NAS 上的后端无法被 PC 的浏览器拉起, PC 上的桥也替换不掉「经网络拨 NAS」这一跳 —— NAS 地址、token、传输信任, 一项配置都少不了, 却多付一个桥组件 + 一次性注册表主机注册。
  • 打破计划 §7.2 不变项: 路线 B 把「60s 短轮询」换成「离屏文档持长连接 + 后端主动推送」。计划的协议不变项是明文写着的; 换协议意味着 §03.5 的安全重评要重做(PC 侧的准入从 origin 白名单变成管道 ACL + 清单 origins), 而计划明确「不动三道安全资产」。
  • 独特收益只在同机内成立: 零端口、亚秒派发、request_timeout 约束消失 —— 这些都发生在「同一台机器」内部。跨机那一跳照旧是端口 + HTTP, B 相对 A 没有任何增量。
结论: 路线 B 与跨机计划正交——它回答的是计划没问的问题(同机端口清零), 对计划真正的问题(绑哪、怎么传、怎么鉴权)零贡献。不并入本计划; 若未来为同机推送时延重拾, 应另立计划, 并重新评估轮询不变项。
04 / 路线 A 为什么适配

零冲突, 且把跨机配置面砍掉一半

4.1 对同机形态(默认)

  • 发现端口固定 18788(免配置、可覆盖) + 数据端口交 OS 随机 + token 由发现响应携带 ⇒ 「抄端口 + 粘 token」两道手工配置归零。
  • 发现端口默认绑回环 ⇒ 与计划「默认仍回环, 同机零感知」同一气质; 顺带消灭同机多实例端口撞车(注册表按心跳聚合)。

4.2 对跨机形态(计划目标)

  • 发现端点继承计划的 host 可配性(这是 S1/S2 的直接产物): 扩展填 http://<nas-ip>:18788 一次, 发现响应带回 {随机数据端口, token, 实例清单}。NAS 地址是唯一不可消除的配置项——扩展必须知道 NAS 在哪, 没有任何机制能去掉它。
  • 跨机配置面从「端点 URL + token」收缩为「NAS 地址」; token 不再经聊天/邮件在两台机器之间搬运(可用性 + 机密性双赢)。
  • 附带安全增益: 数据端口每次启动随机 ⇒ LAN 端口扫描对数据端点失效, 可寻址的只剩发现端口(且 Origin 钉死)。相对计划路径 C 的固定端口暴露, 这是净改善。

4.3 计划 §7.2 不变项逐条核对

计划不变项路线 A说明
默认仍回环(host 缺省 127.0.0.1)保持发现与数据两个端口都随 host 走, 缺省同绑回环。
URL 白名单 / 任务绑定 / origin 白名单逐字不变保持发现端点同样只认 chrome-extension:// origin; 普通网页 JS 打进来 403。
协议不变: 60s 短轮询 + token 鉴权保持路线 A 本来就是轮询; 「轮询周期 < request_timeout」硬约束不动。
allow_reuse_address=False 独占端口守卫保持两个端口都沿用; 发现端口被占 ⇒ 明确日志 + 退手动配置。
hr_check.shared_dir 只读路径保留保持与配置轴无关, 并列关系不变。
05 / 安全联动

必须和计划一起拍板的三处

5.1 发现端点免 token ⇒ 非回环时配对码从「可选」升「强制」

发现端口本身就是发 token 的, 不可能再要求 token(先有鸡还是先有蛋)。计划已立「非回环 + 空 token ⇒ 报错」的安全默认范式; 路线 A 按同一范式延伸: 发现端点绑非回环 ⇒ 一次性配对码强制开启(daemon 在日志/WebUI 亮码, 选项页输入一次, 之后发现响应须带配对密钥 HMAC 才被采信)。今早报告里配对码默认关——联合分析建议把默认语义反转为「同机可选、非回环强制」。

精度说明: 配对码只解决「谁可以拉取 token」(未授权发现), 不解决链路嗅探——T1 明文 LAN 下嗅探者仍能直接读到 token 字节。链路机密性仍归计划的 D1 拍板, 两件事不能互相替代。

5.2 D1 传输决策的覆盖面从 1 个端点扩为 2 个

D1 选项对数据端点(同计划)对发现端点(新增)
T3 反代 TLS后端仍回环, 零攻击面反代需同时暴露 18788; 或数据端口显式固定、只让发现走反代(token 自动分发仍可得)。
T1 受信 LAN明文, token 可嗅探(文档警示)同上也明文 ⇒ 配对码成为必选项而非可选项, 且文档须明示「token 可被同网段获取」。
T2 端点 TLS自签 + MV3 证书信任难题两张证书管理, 复杂度 ×2; 更不推荐。

5.3 401 节流(S4)对两个端口都做; origin 钉死建议配 extension_id

计划 S4 的 401 节流(状态变化报一次 + gap 提醒)天然覆盖两个端口, 一次改动两处受益。另: 发现端点在 extension_id 未配时只认「任意 chrome-extension:// origin」——跨机场景强烈建议配 extension_id, 它是发现端点唯一的准入门槛。

5.4 一处真实冲突(开放设计点, 不在本报告定案)

随机数据端口与计划的路径 A(SSH 静态转发)/ 路径 B(反代静态上游)天然冲突: 转发规则写不死一个每次启动都变的端口。结论性口径: 隧道/反代用户保持显式端口(路线 A 定义的完全旧行为, 存量零感知), 不受随机化影响; 若也想让这类用户获得 token 自动分发, 需给发现响应一个「对外声明端点」覆盖键(如 advertise, 默认 = bind 地址, 隧道/反代场景显式覆盖)——列为开放设计点, 见 §09。

07 / 实施次序

先 host 键, 再发现层, 传输一次拍板覆盖两端

  1. 先落跨机计划 S1/S2(host 配置键 + 接线): 这是路线 A 的前置——发现端口必须同样可配 host, 否则跨机发现无从谈起。
  2. 路线 A 作为同一计划的快跟层: 发现端点 + port: 0 语义 + 实例注册表; 复用 S4 的 401 节流与 origin 白名单机制, 不新增安全件。
  3. D1 拍板时一并覆盖两个端点(§05.2), 避免传输方案落地后又为发现端点返工。
  4. 路线 B 在去端口报告中标注「缓行/远期」, 不并入跨机计划; 若未来重拾, 另立计划并重评轮询不变项。
  5. 旧兼容不变: 显式 port = 完全旧行为(存量零感知); 旧扩展遇新后端退手动配置; 新扩展遇旧后端同样退手动——不做断崖切换。

09 / 仍然开放

联合之后仍未定案的问题

  1. advertise 覆盖键(隧道/反代 + token 自动分发)要不要做? 不做则这类用户停留在显式端口 + 手工 token。
  2. 配对码多次使用 vs 按实例/按 PC 签发(多 PC 场景的撤销与轮换)。
  3. 发现响应是否带实例名/备注(NAS 上多 data_dir 实例时供人选择)?
  4. 多 PC 部署是否把「打包扩展(固定 key)」写成推荐安装方式?
  5. 数据端口每次启动随机 ⇒ 扩展侧缓存端点失效的重发现逻辑(报告 §04 已有「全部实例连不上时探测」, 确认覆盖重启场景即可)。
