01问题、口径与调研方法

要回答的三件事

  1. Python 与 WEB UI 涉及语言（JS）各自有哪些变异测试框架, 现状如何（是不是活的、支持什么、要什么前提)。
  2. 它们能不能落在本项目: 本机 Windows 为主、测试全 Fake 无外部依赖、提交闸门已挂 98% 分支覆盖。
  3. 成本与收益的量级 —— 不止给结论, 给本机实测数字外推。

方法

  • 外部调研: 框架官网 / PyPI / README / 第三方对比表交叉核对（单一来源的数字一律不采信)。
  • 本机实测: 全部在本机 Windows 上真跑。为避免污染主仓库与环境, 另建沙箱副本 R:/Temp/auto-qb/mut-exp（uv sync 独立 venv, 主仓库 .venv、pyproject.toml、uv.lock 一律未改动)。
  • 工具选择: 实测对象为 pytest-gremlins（唯一在本机原生可跑的 pytest 插件型)。mutmut 也装了并试跑, 结论是本机被明确拒绝（见 §09)。
本报告里的被测框架版本与存活数是 2026-10-08 这一刻的快照: pytest-gremlins 迭代很快（几个月内 1.8 → 1.11), 换版本重跑数字会变, 特别是变异算子覆盖面与存活数。结论层面的判断（量级、节奏、值不值得做)不随之变化。

为什么排除了 mutmut（本机实证, 不是推断)

装完后在本机直接试跑, 工具第一句就拒绝:

$ uv run mutmut run --paths-to-mutate=src/auto_qb/infra/versioning.py --tests-dir=tests/test_versioning.py
To run mutmut on Windows, please use the WSL. Native windows support is tracked in issue .../issues/397

本项目开发主平台是 Windows（Linux 只在 CI 与 commands run test.linux 的容器里), 所以「要跑 mutmut」等价于「所有本地迭代都要跳进 Linux 容器」。成本不是不能付, 而是没必要付 —— pytest-gremlins 在同样机器上是原生的。若日后需要 mutmut 的算子面, 第二条可用路径是 cosmic-ray。

三者成本/性能的机制差异（决定第一眼的时间量级)

  • 重写源码 vs 不改源码: cosmic-ray 用 import hook、gremlins 用一次性插桩 + 环境变量切换 —— 都不落盘改文件。mutmut v3 只变异函数体内的代码（模块级常量、装饰器不在范围内)。
  • 覆盖引导: 三者都有; 实测是最大的时间杠杆（见 §07)。
  • 增量: gremlins 按内容 hash 缓存; cosmic-ray 靠会话库; mutmut 的缓存在同期评为「有限」。
  • 集成形式: gremlins 是 pytest 插件（一条命令、吃现有 fixtures/markers); 另两个是独立 CLI, 要单独配测试命令。

两个决定「变异测试能见到的东西」的现状事实

事实一: Python 端已经贴着变异测试在做事了, 只是手工。 Memory Bank 的基线切片里反复出现「变异红验 N 条」「临时还原旧行为 → 当场变红 → 逐条精确还原」。这就是手工变异测试: 人自己造一个变异、跑测试、看红不红。它的问题是覆盖率低且无系统性 —— 人只会改自己刚碰的那几行, 而且天然挑「自己觉得会被抓到」的变异。

事实二: 前端没有「可执行单元层」, 只有「文本阅读层」与「浏览器层」。 前端 JS 是 window.AQB_* 全局对象 + Vue 3 CDN 全局版本 + 严格依赖 <script> 顺序, 无模块、无构建（这是刻意选择, 见 app.js 头注释)。因此它的验证手段是: tests/test_web.py 等读源码文本的静态守阵 + e2e/ 的真浏览器断言（单 instance、workers: 1、fullyParallel: false, @fast 子集分钟级、全矩阵单次约 164–219s)。而 memory-bank/pitfalls/testing/static-guard-mutation.md 已经记了这个形态的固有盲区: 「字符串包含」式守阵拦不住短路禁用/语句删改 —— 而这个盲区正好是变异测试唯一补不上的那类: 变异测试要执行代码, 静态守阵永远只对着文本。

07成本模型与全项目外推

第一步: 变异总数

实测密度带宽 0.135 – 0.300 变异/行（差异来自「逻辑密度」: 格式化/决策型代码高, 声明/dataclass/CLI 型低)。取中值 0.20 做点估, 取两端做区间:

上界（全仓库都像 utils)0.30≈ 10,400

第二步: 单轮时长

口径每变异 CPU总 CPU8 worker 墙时32 worker 墙时
乐观（都像窄池)2.6s≈ 5 CPU-h≈ 37 min≈ 9 min
现实（混宽调用面, 5.0s)5.0s≈ 9.6 CPU-h≈ 72 min≈ 18 min

对照: 当前全量测试 56.24s。一轮全项目变异 ≈ 全量测试的 20–150 倍 —— 与业界常说「10–30×」同数量级但偏上限, 因为本机单个 pytest 子进程起步成本高（~2.5s), 而每个测试用例本身极快（Fake 数据、无 IO), 摊不掉。

这条数字是本报告的正面结论: 业界对变异测试的普遍恐惧（「小时级、烧 CI」)在本仓库不成立 —— 测试套件无 IO 等待、本机 32 核, 全项目一轮只是「一顿饭」量级。按包切开后是「一杯咖啡」量级（单个包约 5–20 分钟)。

第三步: 不同节奏下的成本

节奏单次成本评价

08收益: 找到了什么

收益一: 它把这个阶段「覆盖率看不出」的洞具体标出来了

在 99% 分支覆盖、--cov-fail-under=98 的前提下, 单次抽样命中:

  • utils.py:48 —— parse_hm 的取值区间判别。窄池下 10 个存活（<= to <、<= to >、边界位移); 加入 test_conditions.py 后比较类都被杀（那几条 parse_hm("23:59") / ("00:00") 立功), 但仍有 4 个边界位移变异存活 ⇒ 这条给规则引擎与通知免打扰共用的校验, 两侧边界的邻值从未被探过。
  • file_access.py 的 10 个存活集中在容器/抽象实现的 NotImplementedError / NotSupported 分支与 open_path 默认参数 —— 这一类偏「覆盖没到」而非「断言太弱」, 价值中等。
  • utils.py 里 501 用例都没杀掉的高调用面变异 —— 详见下一节, 这一类不一定是真洞。

收益二（必须说的反面): 存活数是「测试池」的函数, 别直接当缺口单

实测: 同一目标 utils.py、同一套变异, 只把选择池从 1 个测试文件换到 5 个测试文件, 存活数 97 → 70（−27%)。把它推到极限验了一次:

# 手工把 utils.py:485 的 return re.compile(...) 改成 return None, 再跑全套件
8 failed, 2761 passed, 4 skipped   # 其中 3 条新红 ⇒ 全套件会杀死它
# 但它在「5 文件池」下被报成 SURVIVED（且选中了 501 个用例)
方法论结论（本报告最该被记住的一条): 窄池跑出来的存活清单, 相当一部分是「相关测试不在池里」的假存活。判断一个存活变异是不是真洞, 唯一标准是拿全套件手工改一次验证 —— 也就是本项目已经在做的「变异红验」, 只是现在由机器批量提名研究对象。机器提名 + 手工确认才是这里的正确组合。

收益三: 与现有手工红验是替换关系吗

不是, 是分工: 手工红验回答「我刚写的这个守阵是不是空转」(成本极低、与行为同构, 是必要的收尾动作); 机器变异回答「哪些地方我从没想过要写守阵」(这件事人做不了 —— 人不会去改自己没动过的那 34,000 行)。

09坑与流程摩擦（本机实证)

#现象后果处置
1 mutmut 本机直接拒绝: To run mutmut on Windows, please use the WSL 本机用不了最主流的那个 改选 pytest-gremlins; 需要它算子面时走 Linux 容器
2 全测试池下预扫崩溃: 覆盖预扫子进程 FileNotFoundError: [WinError 206] 文件名或扩展名太长 「全 src × 全 tests」一把跑在本机当前不可行 按包/按文件切目标 + 限制选择池（也正是推荐节奏); 或 --gremlin-no-coverage-filter（贵)
3 与 xdist 互斥: -n 一起用会报错/零变异 pytest.ini 的 addopts 里写了 -n 4 每次显式 -n 0; 并行交给 --gremlin-workers
4 基线不绿直接不开跑: skipping mutation testing because 75 baseline test(s) failed 树已经红着的时候没法拿它定位问题 必须先全绿 —— 与本项目闸门纪律一致, 无额外成本
5 覆盖率闸门误伤: 带 --cov-fail-under=98 跑子集必然不达标 「用例全绿」被判红 必带 --no-cov（与 test.one 那条发现同形)
6 TMPDIR 老坑继续适用: 工具 shell 默认 H:\Temp 会在收尾崩（退出码非 0 但测试全过) 假红 自带 set "TMPDIR=R:/Temp/auto-qb/tests"（cmd.exe 写法, 引号不能省)
7 报告默认落 coverage/gremlins/（仓内) 踩删除拦截层的同一类历史坑 报告目录指到 R:/Temp/auto-qb/
8 成熟度风险: 单作者; PyPI 仍标 Alpha; 半年内大版本跳动快 结果随时会变 按本项目惯例 == 精确钉 + uv lock; 每轮在切片里记下版本号

10建议落地方案

建议一: 定 pytest-gremlins, 但只做「定期审计」, 不进闸门

  • 对象优先级（按「判据密度 × 出错代价」而不是按行数): ①rules/（规则引擎判据) ②hr/（HR 判定与做种要求链路) ③config/（fail-fast 校验) ④core/（主循环/限速) —— infra/ 与 webui/server/ 估值最低（IO 胶水层, 变异多为等价或平凡杀死)。
  • 入场练手: 先用已实测的 infra/utils.py（349 变异 / 约 5–10 min)把整条流程跑通一轮, 先建立「真洞 / 等价变异 / 假存活」三分类的习惯。
  • 记录: 每轮一个基线切片 testing/baselines/YY-MM-DD-HHMM-mutants-<包>.md, 内容 = 目标/变异数/杀死率/耗时/工具版本/手工确认后的真洞数。目标不是「分数增长」, 是「包内不再有不知道为什么活着的变异」。
  • 不做: 不设 break 阈值挂 CI、不给 thresholds、不做「必须杀死 100%」的追逐 —— 等价变异（@dataclass(frozen=True) → False 这类)杀不掉是数学事实。

建议二: 命令接入 —— 新增 test.mutants（建议写法, 本次未改动任何命令包)

四条必带的要素缺一不可（每一条都对应 §09 一个坑):

[tasks."test.mutants"]

       'uv run pytest <args> --gremlins -n 0 --no-cov --gremlin-workers=16 '

建议三: 沉淀一条 pitfall（本轮未落, 待你点头)

「变异分数与存活数是选择池的函数: 窄池下 utils.py 存活 97, 换 5 文件池降到 70; 一个被判成存活的变异, 拿全套件手工验证后其实是被杀死的」。建议入 memory-bank/pitfalls/testing/mutation-pool-artifact.md —— 不先定这条规矩就投产, 第一份存活清单会被当成缺口单来处理, 从而把人力浪费在伪洞上。

11前端专项结论

结论: 现在不具备做变异测试的结构前提, 建议不做。不是「Stryker 不适合这个项目」, 是「变异测试需要一个能快速执行被测代码的单元层, 而本项目前端没有」。

三个逐层卡点

  1. 没有单元层: JS 是 window.AQB_* 全局 script + Vue 3 CDN, 无模块、无构建。要跑 Stryker 的 jest/vitest runner, 得先有一层能吃这些全局脚本的执行环境（jsdom + 手工拼接 <script> 顺序), 这本身就是一笔独立投资。
  2. 唯一执行面是浏览器 e2e: Stryker 官方 runner 矩阵无 Playwright; 且 @fast 子集已是分钟级。按同一密度带估 ~3,000 个前端变异 → 即使按每变异 10s 乐观估, 也是 数个小时 CPU/轮; 叠加风险（突变引入死循环 / 状态机卡死)时更长。
  3. 变异测试补不了当前的真盲区: pitfalls/testing/static-guard-mutation.md 记的「静态守阵拦不住短路禁用/语句删改」, 是文本层的缺陷。变异测试是执行层的手段 —— 它评估的是测试, 而这里缺的不是测试强弱评估, 而是「这些守卫压根没在执行这条路」。

如果将来真想要: 路径与前置

  1. 先决动作（独立决策, 不要和变异测试打包): 从 20,771 行 JS 里挑出纯决策函数（格式化/比较/排序/解析类, 如 shared/format.js、columns.js、sort.js), 抽成可被 Node 直接引入的模块 + 配 Vitest 单元层。按规模估这是「一个专题」的工作量, 不是「顺手」。这一步的价值本身不依赖变异测试 —— 它同时解决 e2e 反馈太慢、静态守阵只能读文本两个问题。
  2. 在这层之上再叠 @stryker-mutator/vitest-runner（注: 官方注明 Vitest browser mode 不在支持范围, 所以必须是 Node 侧执行的那一层)。
  3. 在此之前维持现状并加强: 继续用手工变异（改造 JS → 看 e2e 是否红)做抽验, 并把静态守阵从「字符串包含」升级为报告里已给出的两档写法（整行活性锚定 + 逐分支语句清单)。这是当前性价比最高的前端投入。
