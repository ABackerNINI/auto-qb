变异测试框架调研与适配性: Python 与 WEB UI 语言面

把 Python 端的四个活跃/半活跃变异框架与 JS 端的 StrykerJS 逐个摆出来比对后, 在本仓库真跑了两轮: 第一轮在 Windows 上跑 pytest-gremlins（三个样本模块、两轮换池); 第二轮（本次追加)在 WSL 里把 mutmut 与 gremlins 同环境对着跑, 并跑完了整个 rules/ 包。结论修正: Python 端值得做、且便宜; 框架选型由 gremlins 改为 mutmut（WSL 下 58% 的墙时打 3.8 倍的变异, 且打得到字符串/语句类); 全项目变异总数实测 34,702（初版外推低估 3–7 倍), 但一把跑会把 WSL 打挂, 按包跑是硬要求。前端结论不变: 现在不具备做变异测试的结构前提。

01问题、口径与调研方法

要回答的三件事

  1. Python 与 WEB UI 涉及语言（JS）各自有哪些变异测试框架, 现状如何（是不是活的、支持什么、要什么前提)。
  2. 它们能不能落在本项目: 本机 Windows 为主、测试全 Fake 无外部依赖、提交闸门已挂 98% 分支覆盖。
  3. 成本与收益的量级 —— 不止给结论, 给本机实测数字外推。

方法

  • 外部调研: 框架官网 / PyPI / README / 第三方对比表交叉核对（单一来源的数字一律不采信)。
  • 本机实测（第一轮): 在本机 Windows 上真跑。为避免污染主仓库与环境, 另建沙箱副本 R:/Temp/auto-qb/mut-exp（uv sync 独立 venv, 主仓库 .venv、pyproject.toml、uv.lock 一律未改动)。
  • 本机实测（第二轮, 本次追加): 本机已装 WSL（Ubuntu-26.04), 且变异测试定位是定期审计而非每 PR 闸门 —— 两条前提变化后, mutmut 的「WSL-only」不再是排除理由。故把仓库副本搬进 WSL 原生文件系统, 在同一环境里把 mutmut 与 pytest-gremlins 对着跑（§07)。
  • 工具选择: 第一轮实测对象是 pytest-gremlins（唯一在 Windows 原生可跑的 pytest 插件型); mutmut 在 Windows 上被明确拒绝（见 §10)。第二轮两者都在 WSL 下实测并直接对比。
本报告里的被测框架版本与存活数是 2026-10-08 这一刻的快照: pytest-gremlins 迭代很快（几个月内 1.8 → 1.11), 换版本重跑数字会变, 特别是变异算子覆盖面与存活数。结论层面的判断（量级、节奏、值不值得做)不随之变化。

mutmut 的平台门槛: 只认 WSL（本机实证, 不是推断)

装完后在 Windows 上直接试跑, 工具第一句就拒绝（3.8.0 里这句仍在, 源码 mutmut/__main__.py:16):

$ uv run mutmut run --paths-to-mutate=src/auto_qb/infra/versioning.py --tests-dir=tests/test_versioning.py
To run mutmut on Windows, please use the WSL. Native windows support is tracked in issue .../issues/397

初版据此把 mutmut 排除了, 理由是「开发主平台是 Windows, 要跑 mutmut 等价于所有本地迭代都跳进 Linux」。本次重估推翻了这个理由: 前提有两条变化 —— ①本机已装 WSL（Ubuntu-26.04); ②变异测试的定位是定期审计, 不是每 PR 闸门, 所以「跳进 Linux」的成本是每月一次而不是「每次迭代」。门槛是真的, 但代价被高估了一个数量级。

代价里唯一残留的一条是算力: C:\Users\11059\.wslconfig 把 WSL 限成 processors=8 / memory=8GB, 而 Windows 侧是 32 逻辑核 —— 也就是说 mutmut 只能用 1/4 的核。即便如此, 实测它仍比 Windows 侧满核跑的 gremlins 快（§07)。若愿意改 .wslconfig, 还有一倍以上的余地。

三者成本/性能的机制差异（决定第一眼的时间量级)

  • 重写源码 vs 不改源码: cosmic-ray 用 import hook、gremlins 用一次性插桩 + 环境变量切换 —— 都不落盘改文件。mutmut v3 只变异函数体内的代码（模块级常量、装饰器不在范围内)。
  • 覆盖引导: 三者都有; 实测是最大的时间杠杆（见 §08)。
  • 增量: gremlins 按内容 hash 缓存; cosmic-ray 靠会话库; mutmut 的缓存在同期评为「有限」。
  • 集成形式: gremlins 是 pytest 插件（一条命令、吃现有 fixtures/markers); 另两个是独立 CLI, 要单独配测试命令。

两个决定「变异测试能见到的东西」的现状事实

事实一: Python 端已经贴着变异测试在做事了, 只是手工。 Memory Bank 的基线切片里反复出现「变异红验 N 条」「临时还原旧行为 → 当场变红 → 逐条精确还原」。这就是手工变异测试: 人自己造一个变异、跑测试、看红不红。它的问题是覆盖率低且无系统性 —— 人只会改自己刚碰的那几行, 而且天然挑「自己觉得会被抓到」的变异。

事实二: 前端没有「可执行单元层」, 只有「文本阅读层」与「浏览器层」。 前端 JS 是 window.AQB_* 全局对象 + Vue 3 CDN 全局版本 + 严格依赖 <script> 顺序, 无模块、无构建（这是刻意选择, 见 app.js 头注释)。因此它的验证手段是: tests/test_web.py 等读源码文本的静态守阵 + e2e/ 的真浏览器断言（单 instance、workers: 1、fullyParallel: false, @fast 子集分钟级、全矩阵单次约 164–219s)。而 memory-bank/pitfalls/testing/static-guard-mutation.md 已经记了这个形态的固有盲区: 「字符串包含」式守阵拦不住短路禁用/语句删改 —— 而这个盲区正好是变异测试唯一补不上的那类: 变异测试要执行代码, 静态守阵永远只对着文本。

07追加实测: mutmut 在 WSL 下重测

触发: 用户指出本机已装 WSL, 且变异测试只做定期审计、不占开发主线的迭代节奏 —— 初版排除 mutmut 的那条理由因此不成立。本轮把仓库副本搬进 WSL 原生文件系统, 在同一个环境、同一个目标、同一个测试池下把两个工具对着跑。

环境

  • WSL2 Ubuntu-26.04; .wslconfig 限 processors=8 / memory=8GB / swap=0（Windows 侧 32 逻辑核)。
  • mutmut 3.8.0 与 pytest-gremlins 1.11.2 装在同一个 venv（uv sync + uv pip install), 排除环境差。
  • mutmut 配置: process_isolation="forkserver"、--max-children 默认 8（全项目那轮调到 6)、必带 -n 0 --no-cov、两条文本层守阵 --deselect（§10 #9/#10)。
  • 仓库副本放 WSL 原生 ext4（/home/abacker/mut-wsl), 不经 /mnt/* —— 实测从 Windows 盘拷 116MB 进来要 52s, 真要做建议直接 git clone。

对照四: 全项目一轮（mutmut, 实测打到 37% 中断)

12,957/34,702  🎉 8,550  🫥 613  ⏰ 14  🙁 3,780
  • 生成: 128 文件全部插桩, 18.9s 完成 → 34,702 变异。
  • 跑到 37% 时 WSL 整体失去响应（需 wsl --shutdown 才恢复)。已跑完的部分: 杀死 8,550 / 存活 3,780 / 超时 14 ⇒ 已判定 12,344 个里杀掉 69.3%; 另有 613 个判为 no tests。
  • 吞吐不是常数: 起步 38 变异/秒, 中段降到 6–10 变异/秒 —— 前期是那些「一个测试文件就能打死」的小目标, 后期轮到宽调用面模块（与 gremlins 那条成本尾巴同源)。按实测区间外推 40–90 分钟; §08 用下面这个跑完的包做锚点, 把全项目收敛到 ≈ 77 分钟。
结论: 全项目一把跑不可行, 按包切是硬要求。在 8GB + swap=0 的 WSL 里, mutmut 的 forkserver + N 个子进程会把整个 WSL 拖死（同一现象复现两次: 全 src 那轮 37% 处、rules/ 单包那轮 74% 处), 而且它是硬崩 —— 不报错、不退出, 整个 WSL 失去响应, 要 wsl --shutdown 才救回来。按包跑既避开这条, 也是 §08 推荐节奏本来就有的粒度。

  • 杀死率 55.5%（1,813 / 3,269 已判定) —— 比 infra/utils.py 的 72.5% 低 17 个点。优先级最高的包, 分数反而最差: 规则引擎的判据密度最高、出错代价最大, 而它的测试更偏「跑通」而不是「钉死边界」。这一条本身就是本报告最实在的产出: 覆盖率的 98% 在这两处是同样的 98%, 变异分数却差了 17 个点。
  • 池的影响没想象中大: 同一包用全 tests 作池时, 跑到同一进度点（2,42x)的杀死率是 53.6%, 定向池是 52.4% —— 差 1 个点。宽池的代价落在内存（打挂 WSL)而不是结论上。
  • 存活 1,446 个不等于 1,446 个洞: 其中相当比例是等价变异与「判据换种写法仍然成立」的变异。这正是 §09 那条方法论的用武之地 —— 机器提名, 手工确认。

那 gremlins 还有没有位置

有, 两条: ①Windows 侧兜底 —— mutmut 在 Windows 上仍然被硬拒, 不想开 WSL 的那天就用 gremlins; ②交叉验证 —— 两个工具在 utils.py 上给出同一个杀死率（72% / 72.5%), 这个一致性本身就是「数字可信」的证据; 哪天两者分歧变大, 说明其中一个的算子/选池出了偏差。反过来, mutmut 有一条 gremlins 补不上的:字符串变异 —— mutants/ 树里能直接看到 XXbuild_search_indexXX 这类变异体, 而 gremlins 的算子面明确不含字符串。

09收益: 找到了什么

收益一: 它把这个阶段「覆盖率看不出」的洞具体标出来了

在 99% 分支覆盖、--cov-fail-under=98 的前提下, 单次抽样命中:

  • utils.py:48 —— parse_hm 的取值区间判别。窄池下 10 个存活（<= to <、<= to >、边界位移); 加入 test_conditions.py 后比较类都被杀（那几条 parse_hm("23:59") / ("00:00") 立功), 但仍有 4 个边界位移变异存活 ⇒ 这条给规则引擎与通知免打扰共用的校验, 两侧边界的邻值从未被探过。
  • file_access.py 的 10 个存活集中在容器/抽象实现的 NotImplementedError / NotSupported 分支与 open_path 默认参数 —— 这一类偏「覆盖没到」而非「断言太弱」, 价值中等。
  • utils.py 里 501 用例都没杀掉的高调用面变异 —— 详见下一节, 这一类不一定是真洞。

收益二（必须说的反面): 存活数是「测试池」的函数, 别直接当缺口单

实测: 同一目标 utils.py、同一套变异, 只把选择池从 1 个测试文件换到 5 个测试文件, 存活数 97 → 70（−27%)。把它推到极限验了一次:

# 手工把 utils.py:485 的 return re.compile(...) 改成 return None, 再跑全套件
8 failed, 2761 passed, 4 skipped   # 其中 3 条新红 ⇒ 全套件会杀死它
# 但它在「5 文件池」下被报成 SURVIVED（且选中了 501 个用例)
方法论结论（本报告最该被记住的一条): 窄池跑出来的存活清单, 相当一部分是「相关测试不在池里」的假存活。判断一个存活变异是不是真洞, 唯一标准是拿全套件手工改一次验证 —— 也就是本项目已经在做的「变异红验」, 只是现在由机器批量提名研究对象。机器提名 + 手工确认才是这里的正确组合。

收益三: 与现有手工红验是替换关系吗

不是, 是分工: 手工红验回答「我刚写的这个守阵是不是空转」(成本极低、与行为同构, 是必要的收尾动作); 机器变异回答「哪些地方我从没想过要写守阵」(这件事人做不了 —— 人不会去改自己没动过的那 34,000 行)。

收益四（本次追加): 它给「哪块最该补」提供了一个覆盖率给不出的刻度

rules/ 与 infra/utils.py 在覆盖率上是同一个 98%, 变异分数却差 17 个点（55.5% vs 72.5%)。方向也值得注意: rules/ 是按「判据密度 × 出错代价」排在第一位的包, 恰恰是分数最低的那个 —— 判据多的地方, 测试更容易只写「跑通」而不写「边界」。「先跑哪个包」因此可以不再靠直觉排: 先各跑一轮拿分数, 分数最低的先补。

附带一个读法提醒: mutmut 把「no tests（没有任何测试覆盖)」与「survived（有测试覆盖但没杀掉)」分成两类, gremlins 因为做覆盖率过滤, 前者根本不生成变异。所以两个工具的分母不同, 分数只能各自纵向比, 不要横向混着看。

10坑与流程摩擦（本机实证)

#现象后果处置
1 mutmut 拒绝 Windows 原生: To run mutmut on Windows, please use the WSL 只能在 WSL 里跑（本机已装, 门槛成立但可付) WSL 里另备一份仓库副本（git clone 优于从 /mnt 拷, 实测拷 116MB 要 52s); Windows 侧的兜底选项仍是 pytest-gremlins

5 覆盖率闸门误伤: 带 --cov-fail-under=98 跑子集必然不达标 「用例全绿」被判红 必带 --no-cov（与 test.one 那条发现同形)
6 TMPDIR 老坑继续适用: 工具 shell 默认 H:\Temp 会在收尾崩（退出码非 0 但测试全过) 假红 自带 set "TMPDIR=R:/Temp/auto-qb/tests"（cmd.exe 写法, 引号不能省)
7 报告默认落 coverage/gremlins/（仓内) 踩删除拦截层的同一类历史坑 报告目录指到 R:/Temp/auto-qb/

9 mutmut 把变异体写进同一份文件, 文本层守阵在基线就红: mutants/ 里 versioning.py 由 185 行 / 9.4KB 变成 4,890 行 / 254KB, 正文里出现 XXbuild_search_indexXX 这类字符串变异体 凡「读源码文本做断言」的守阵会误报, 而 mutmut 与 gremlins 一样要求基线全绿才开跑 ⇒ 整轮直接中断。实测命中 test_web.py::test_api_enqueue_wakes_main_loop（自投递命令登记)与 test_sim_corpus.py::test_fs_mock_coverage_static_guard（FS 探测点计数) 这类守阵必须显式 --deselect; 代价是它们覆盖的那部分代码变成 no-tests。这是 mutmut 相对 gremlins 的结构性劣势 —— gremlins 不落盘改文件, 文本层守阵不受影响
10 fork 隔离下注册表类守阵假红: 默认 process_isolation=fork 时, test_actions_registry_complete(多出 noop)、test_condition_plugins_cover_registry 在 mutmut 的 clean test 里红; 但同一份 mutants/ 树手跑全套件是绿的 同一条基线, 手跑绿、工具跑红 —— 极难归因, 每发现一条要付一轮 3 分钟 配 process_isolation = "forkserver"(实测改用后基线立刻变绿)。根因未定位, 只确认与 fork 继承的调用形态相关
11 mutmut 的配置面在 pyproject.toml 且键名已换: 老键 paths_to_mutate / tests_dir 已废弃 → 现为 source_paths / pytest_add_cli_args_test_selection; 跑测试的命令靠 pytest_add_cli_args 追加 照网上教程写会告警甚至跑空 ①source_paths 必须写整个 src(写单文件会因包内相对 import 失败), 目标用 only_mutate = ["**/infra/utils.py"] 收窄; ②必带 -n 0 --no-cov 抵消 pytest.ini 的 addopts; ③别忘 use_git_change_detection
12 mutants/ 是一整份仓库副本, 且要自己补料: mutmut 只自动带 tests/ + 锁文件, 其余靠 also_copy 漏一个就基线红。本项目实测补了 .agents(gen_doc_map.py 在那儿)、docker/config.example.yml、AGENTS.md、memory-bank、.commands、.github 等十来项才绿 补齐全后 mutants/ 实测 227MB; 别落在主仓库里（同类于 gremlins 报告落仓内那条), 也别放在 /mnt/* 上
13 WSL 里没有 python 只有 python3: tests/test_commands_engine.py 的 wrapper 端到端用例 exec python 直接 127 WSL 侧基线红, 与变异无关 ln -s $(which python3) ~/.local/bin/python 补一个; 这类「平台差异导致的既有用例红」是 WSL 路线的固定税
14 WSL 只有 8 核: .wslconfig 里 processors=8(Windows 侧 32 逻辑核); mutmut 的 --max-children 默认取 os.cpu_count() mutmut 只能用 1/4 的核 —— 即便如此仍比 Windows 侧满核的 gremlins 快 想再快一倍以上就改 .wslconfig; 不建议为了变异测试去动它（会影响 WSL 其它用途)

11建议落地方案

建议一（本次修正): 定 mutmut, 在 WSL 里按包做「定期审计」, 不进闸门

  • 为什么改: 本机已装 WSL + 只做定期审计 ⇒ 「WSL-only」这条门槛从每迭代付一次降为每月付一次; 而 mutmut 用 58% 的墙时打了 3.8 倍的变异, 且打得到 gremlins 打不到的字符串/语句类（§07)。
  • 对象优先级（按「判据密度 × 出错代价」而不是按行数): ①rules/（规则引擎判据, 实测 3,270 变异) ②hr/（HR 判定与做种要求链路) ③config/（fail-fast 校验) ④core/（主循环/限速) —— infra/ 与 webui/server/ 估值最低（IO 胶水层, 变异多为等价或平凡杀死)。
  • 入场练手: 先用已实测的 infra/utils.py（1,314 变异 / 19.5s)把整条流程跑通一轮, 先建立「真洞 / 等价变异 / 假存活」三分类的习惯 —— 这一轮的成本已经低到「跑错了再跑一次」无所谓。
  • 硬性约束: ①按包跑, 别按全 src; ②选择池用定向的几个测试文件, 别用全 tests（实测把 WSL 打挂两次); ③process_isolation = "forkserver"; ④文本层守阵要 --deselect。
  • 记录: 每轮一个基线切片 testing/baselines/YY-MM-DD-HHMM-mutants-<包>.md, 内容 = 目标/变异数/杀死率/耗时/工具版本/选择池/手工确认后的真洞数。目标不是「分数增长」, 是「包内不再有不知道为什么活着的变异」。选择池必须写进切片 —— 同一个 utils.py, 换池能让存活数从 97 掉到 70（§09); 不记池的数字无法跨轮比较。包级反而是例外: rules/ 用「6 个定向文件」与「全 tests」两池跑到同一进度点时杀死率只差 1 个点（52.4% vs 53.6%) —— 覆盖引导已经把相关用例挑出来了, 池宽的代价只体现在内存（打挂 WSL)上, 不体现在结论上。
  • 不做: 不设 break 阈值挂 CI、不给 thresholds、不做「必须杀死 100%」的追逐 —— 等价变异（@dataclass(frozen=True) → False 这类)杀不掉是数学事实。

建议二: 命令接入 —— 两条路线（建议写法, 本次未改动任何命令包)

A. mutmut（推荐, 走 WSL) —— 三条必带要素各对应 §10 一个坑:

# 1) 仓库镜像: 在 WSL 原生文件系统里放一份（git clone, 不要 cp, 更不要放 /mnt/*）
wsl -d Ubuntu-26.04 -- bash -lc 'cd ~/auto-qb-mut && git pull && uv sync'

# 2) pyproject.toml 的 [tool.mutmut]（source_paths 必须是整个 src, 目标用 only_mutate 收窄）
source_paths = ["src"]
only_mutate = ["**/rules/*.py"]
pytest_add_cli_args = ["-x", "-q", "-n", "0", "--no-cov",
                       "--deselect", "tests/test_sim_corpus.py::test_fs_mock_coverage_static_guard",
                       "--deselect", "tests/test_web.py::test_api_enqueue_wakes_main_loop"]
pytest_add_cli_args_test_selection = ["tests/test_conditions.py", "tests/test_actions.py"]
process_isolation = "forkserver"          # fork 会让注册表类守阵假红
also_copy = ["pytest.ini", ".agents", "docker", "memory-bank", "AGENTS.md", ...]  # 漏一个基线就红

# 3) 跑（--max-children 别拉满; 池必须是定向的几个文件, 不是 tests）
wsl -d Ubuntu-26.04 -- bash -lc 'cd ~/auto-qb-mut && uv run mutmut run --max-children 4'

B. pytest-gremlins（Windows 侧兜底) —— 四条必带要素缺一不可（每一条都对应 §10 一个坑):

[tasks."test.mutants"]
run = ['set "TMPDIR=R:/Temp/auto-qb/tests" && set "COVERAGE_FILE=R:/Temp/auto-qb/gremlins.cov" && '
       'uv run pytest <args> --gremlins -n 0 --no-cov --gremlin-workers=16 '
       '--gremlin-targets=<args> --gremlin-report=json --gremlins-html-dir=R:/Temp/auto-qb/mut-report']
when = "定期审计: 对某个包跑一轮变异测试（不要放进提交闸门）"
note = "cmd.exe 写法 + 引号不能省（见本文件顶部）; -n 0 必带（与 xdist 互斥, addopts 里有 -n 4）; "
       "--no-cov 必带（子集跑必然不满足 98% 闸）; 报告落 R 盘（仓内写入会撞删除拦截层）"

依赖按项目惯例加: uv add --dev pytest-gremlins==<精确版本> / mutmut==<精确版本>（本项目直接依赖一律 == 钉死, 见 techContext.md), 随后 commands run env.sync。两个工具可以并存: mutmut 做主力审计, gremlins 做 Windows 侧抽查与交叉验证。

建议三: 沉淀一条 pitfall（本轮未落, 待你点头)

「变异分数与存活数是选择池的函数: 窄池下 utils.py 存活 97, 换 5 文件池降到 70; 一个被判成存活的变异, 拿全套件手工验证后其实是被杀死的」。建议入 memory-bank/pitfalls/testing/mutation-pool-artifact.md —— 不先定这条规矩就投产, 第一份存活清单会被当成缺口单来处理, 从而把人力浪费在伪洞上。

12前端专项结论

结论: 现在不具备做变异测试的结构前提, 建议不做。不是「Stryker 不适合这个项目」, 是「变异测试需要一个能快速执行被测代码的单元层, 而本项目前端没有」。

三个逐层卡点

  1. 没有单元层: JS 是 window.AQB_* 全局 script + Vue 3 CDN, 无模块、无构建。要跑 Stryker 的 jest/vitest runner, 得先有一层能吃这些全局脚本的执行环境（jsdom + 手工拼接 <script> 顺序), 这本身就是一笔独立投资。
  2. 唯一执行面是浏览器 e2e: Stryker 官方 runner 矩阵无 Playwright; 且 @fast 子集已是分钟级。按同一密度带估 ~3,000 个前端变异 → 即使按每变异 10s 乐观估, 也是 数个小时 CPU/轮; 叠加风险（突变引入死循环 / 状态机卡死)时更长。
  3. 变异测试补不了当前的真盲区: pitfalls/testing/static-guard-mutation.md 记的「静态守阵拦不住短路禁用/语句删改」, 是文本层的缺陷。变异测试是执行层的手段 —— 它评估的是测试, 而这里缺的不是测试强弱评估, 而是「这些守卫压根没在执行这条路」。

如果将来真想要: 路径与前置

  1. 先决动作（独立决策, 不要和变异测试打包): 从 20,771 行 JS 里挑出纯决策函数（格式化/比较/排序/解析类, 如 shared/format.js、columns.js、sort.js), 抽成可被 Node 直接引入的模块 + 配 Vitest 单元层。按规模估这是「一个专题」的工作量, 不是「顺手」。这一步的价值本身不依赖变异测试 —— 它同时解决 e2e 反馈太慢、静态守阵只能读文本两个问题。
  2. 在这层之上再叠 @stryker-mutator/vitest-runner（注: 官方注明 Vitest browser mode 不在支持范围, 所以必须是 Node 侧执行的那一层)。
  3. 在此之前维持现状并加强: 继续用手工变异（改造 JS → 看 e2e 是否红)做抽验, 并把静态守阵从「字符串包含」升级为报告里已给出的两档写法（整行活性锚定 + 逐分支语句清单)。这是当前性价比最高的前端投入。

这轮与后续轮次给流程的五条修正

  • 「全套件确认」是最大成本项(≈15s/条) —— 已收进命令包 mutants.verify(apply → 全套件 → 还原, 可续跑); 候选要先按「判据密度 × 出错代价」收窄, 别对全部存活无差别开跑。
  • 池太窄会成片产生 no tests —— 55 条全部集中在两个规则条件校验器上(池内 6 个文件不覆盖规则条件), 那批变异连三分类都做不了。定池先核「覆盖目标包的函数面」。
  • 复跑要带新守阵必须 --no-refresh —— mutants.run 默认 git checkout -f 会把镜像里未提交的测试改动冲掉, 存活数纹丝不动还以为是真洞。
  • 每轮实施后要同步常驻锚的覆盖进度总表 —— 增加第四个记录工位: 常驻排期锚 issues/26-10-08-0642-…html 的 §07 覆盖进度总表(包 / 上次测试日期 / 变异数 / 杀死率 / 轮次 / 状态 / 切片链接), 一轮跑完必更; 否则「覆盖到哪几个包了」没有单点, 下轮得翻遍切片。该表只放汇总刻度与指针, 不是流水(规程见 mutation-testing skill 的「覆盖进度总表(收尾必更)」节与硬约束 12)。
  • 只有「变异形态」没有 id 时, 走形态级手搓复验(2026-10-10, config loader-defaults 轮) —— 真洞 issue 常只写形态(_get(spec, KEY, d.<field>) 默认值换成 None / 删掉关键字实参)给不出 id, 而 mutants.verify 是按 id 工作的, 这时用不上。做法: 临时脚本按形态造同构变异 → 跑定向池 (实测 ≈3s/条)而非全套件(≈15s/条), 同一份脚本跑两遍 = 形态复验(补测前存活几条) + 红验(补测后是否全红)。 边界: 手搓变异不是 mutmut 编号, 不进存活计数, 量化仍走 mutants.run 同目标同池复跑; 锚点 count != 1 必须报错停手(否则「变异没生效」会被当成「守阵挡不住」)。同源发现: 派生值恰等于字段默认时, 删实参是等价变异 —— 判等价前先造能区分的输入(合成非默认档案), 别把可观测的真洞误判成等价变异。已写进 skill 硬约束 13 与「形态级手搓复验」节。
方法论读数: 274 条候选里 54 条(19.7%)是假存活 —— 与 §09 结论同向, 但比例比调研轮(1 个文件池 → 5 个文件池, 存活降 27%)温和得多: config 的池已经是「定向 6 文件」, 漏掉的主要是与 config 交叉的规则 / 事件域测试文件。另记一条本机环境坑: WSL 登录壳是 zsh, $() 取错 cwd 会让 mutants.status 恒报 mutmut=no(不影响 mutants.run)。
