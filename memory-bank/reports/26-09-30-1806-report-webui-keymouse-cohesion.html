WEBUI 列表键鼠交互割裂
业界成熟方案调研与推荐

01 · 结论 TL;DR

割裂的根因不是滚动实现，而是两套互不知晓的状态机：键盘光标 kbCursor（shortcuts.js）与鼠标操作锚点 selAnchor*（selection.js）各自为政——鼠标路径从不回写键盘光标，且光标为空/失效时引擎的回落口径是「↓ 落首行、↑ 落末行」，在几千行的种子列表上，一次按键就把视口滚到底。

业界对「列表里键盘与鼠标不打架」有稳定共识，可归纳为三条法则：

  1. 单一事实源：焦点/光标（focus）、选中（selection）、悬停（hover）三者独立建模。hover 只是纯视觉临时态，永不回写任何事实源。
  2. 点击是键鼠的衔接点：点击某行即设置键盘光标/焦点——鼠标操作的终点就是键盘导航的起点，键盘绝不清零重置、绝不经由 hover 移动。
  3. 视口最小跟随：目标行已在视口内就不滚动，出视口才滚到「刚好可见」（nearest 语义）；数据轮询/重渲染路径绝不触发滚动。

推荐

方案 B：① 把无光标回落口径从「极值行」改为「视口就近行」；② 四个鼠标点击入口回写 kbCursor（落光标 ≠ 选中，不违反 2026-09-17「普通点击不选中」的既定口径，恰是 VS Code / Gmail 的 focus 语义）。两处小改，不碰滚动实现，视觉双轨（kb-cursor 与 selected）已经就位。详见 §06。

02 · 问题现场（代码取证）

2.1 三个触发场景

场景用户操作实际行为
S1 页面刚打开（或光标已被清空），鼠标在列表顶部浏览，按一下 ↑ _kbMove 发现 kbCursor 为空（cur = -1），按 delta < 0 回落到 rows.length - 1 —— 光标落到列表末行，_kbScrollRowIntoView 随即把整页滚到底部。几千行的大库上就是「一按键跳到最下面」。
S2 用鼠标点选 / 展开某一行，然后按 ↑↓ 鼠标点击路径（onGroupClick / onMemberClick / onTorrentClick / onShowClick 等）从不写 kbCursor——全仓写点只有 state.js:176 的初始 null 与 shortcuts.js 的键盘路径。键盘从「上次键盘停留处」出发，与刚点击的位置毫无关系。
S3 早先用键盘走过一遍（光标停在列表中部/底部），之后一直用鼠标+滚轮在顶部操作，按一下 ↑↓ 光标仍在旧位置（身份重定位让它在轮询下一直存活），按键后视口跳回旧光标行——同样表现为「视图自己跑了」。

2.2 机制：两套互不知晓的状态机

状态权威文件语义
kbCursor（kind + id）shared/shortcuts.js键盘光标：↑↓ 移动的对象，Enter/Space/动作键的目标兜底；带 kb-cursor 视觉类。
selGroups / selMembers + selAnchorGroup / selAnchorMember / selAnchorUnitshared/selection.js鼠标选择与 Shift 区间锚点；Ctrl/Shift+点击维护；不与 kbCursor 联动。

证据位置（本轮实测）：

                       （注释自称「就近回落口径」，实际是极值回落 —— S1 直接来源）
shortcuts.js:455-458   _kbApplyCursor: 设光标 + 滚动跟随（只在键盘路径调用）

                       （渲染行）+ 窗口化前缀和换算（未渲染行，长度不符则放弃）

另外值得记录：_kbHint 的提示文案是「先用 ↑↓ 移到一行，或点选/框选目标」——产品语义上已经承认光标与点选是两条独立通道，但用户心智模型里它们应该是同一个位置感。

03 · 已有底子（做对了什么）

对照业界共识（§05），本项目的底子比预期好——六个差距点里四个已经达标，要补的只有「点击衔接」与「回落口径」两处：

  • 光标按身份而非下标定位（{kind, id}）：轮询整表替换 / 排序 / 筛选后按身份重定位，刷新不丢光标、不跳行——与 VS Code「focus 持有身份，刷新只 diff 数据」同款（§4.2）。
  • 滚动跟随已是「最小滚动」手工实现：行可见则不动（rect 差值只补出界部分），窗口化未渲染行用前缀和换算、口径不符宁可放弃本次滚动（P1-2 退避口径）。业界推荐的手工 getBoundingClientRect 差值路线（§4.5），且禁用 scrollIntoView 有坑档背书（pitfalls/web-ui/hover-keynav-fight.md：它逐层滚动可滚祖先会连带滚整页）。
  • hover 不回写状态：主列表行的悬停是纯 CSS :hover 视觉，不写任何 Vue 状态（模板里的 @mouseenter 都属于 HR 浮层 / 图表 / 右键子菜单 / 下拉组合框等既有协议，与列表高亮无关）——天然符合法则 1。
  • 视觉双轨已分立：四个视图模板的行类都同时挂 selected（选中）与 kb-cursor（键盘光标）两套类名——「焦点 ≠ 选中」的视觉语言已就位，衔接后不需要新视觉。
  • 同族问题在下拉面板已修过一轮：站点搜索命中面板与弹窗三下拉的「hover 与键盘活动项打架」（issue 26-09-29-2142）已按坑档处置（mousemove + 3px 位移门限 + CSS 单路高亮 + 手工滚动跟随），参考实现都在（config_hub.js hubTrackerHoverIdx / hubTrackerScrollActIntoView、add_torrent.js comboHoverIdx）——主列表的问题不是打架，是锚定，但工程先例与红线都齐了。
  • 目标解析已双轨：动作键（暂停/删除等）目标解析「有选中走选中集合，无选中用光标行」（_kbTargets）——点击落光标后，这套语义无需改动即自然成立。

04 · 业界方案调研

4.1 WAI-ARIA APG 官方模式（规范层）

APG Listbox Pattern 规定 ↑↓「把焦点移到下/上一个 option」；单选时 selection 可跟随 focus，多选时二者明确分离（Space 改选中、Ctrl+Arrow 只移焦点、Shift+Space 选连续区）。对初始状态有一条直接对口的规则：「若已有选中项，初始焦点落在选中项上」——键盘从既有状态出发，而非重置到极值。规范原文明确「DOM focus（active element）与 selected state 是功能上不同的两件事」。焦点管理两种做法：roving tabindex（组内仅一项 tabindex="0"，箭头键调 element.focus() 移动）或容器统一接管 + aria-activedescendant（DOM focus 恒在容器，属性指向当前项——适合虚拟列表，被滚走的行可以没有 DOM focus）。

来源：APG Listbox Pattern · APG Patterns

4.2 VS Code（工程标杆）

列表/树把 focus、selection、anchor 建为三个独立 trait（源码自述）：focus 是唯一键盘光标（画 focus 边框、接收按键），selection 可多选可清空，Enter/Space 作用于 selection 而箭头键只动 focus；hover 纯视觉永不改 selection；键盘导航永远从当前 focus 出发，不重置。滚动跟随 List.reveal(index) 是最小滚动语义——源码里对已在视口内的元素直接 no-op；惯用法是 getRelativeTop(index) 返回 null（不可见）才调 reveal。focus 持有身份，轮询刷新只 diff 数据、不动 focus。

来源：VS Code Wiki: Lists And Trees · listWidget.ts

4.3 Gmail / Superhuman / Linear（键盘光标叠加）

Gmail 的 j/k 在会话列表上维护一个独立键盘光标（Vim 传统）：叠加高亮一行但不算「选中」，x 选中、o/Enter 打开、动作键对光标行生效；鼠标 hover 只是临时高亮，不移动光标；点击某行则把光标设到该行——这就是键鼠衔接点。实现上就是与列表同构的 cursorIndex 状态：onClick 写 cursorIndex = i，j/k 时 ±1 并触发最小滚动，渲染为叠加样式类（非 hover 类）。Superhuman / Linear 同把键盘导航当一等公民（鼠标 optional）。

来源：Gmail 快捷键官方文档 · Superhuman: built for speed · Linear docs

4.4 桌面文件管理器（对照系）

Windows Explorer 与 macOS Finder 行为一致：点击 = 该项获得焦点（focus rect）并设置 selection mark / anchor；此后方向键从焦点项（你刚点的那行）出发，Shift+箭头在 anchor 与焦点之间扩展选区。Windows 把 anchor 做成了显式 API（LVM_SETSELECTIONMARK——多选起点的 item index，独立于选中态本身）；「焦点项」与「选中项」在 Win32 / NSTableView 里本就是两个字段。三十年 GUI 桌面的同一答案，值得当作默认口径。

来源：LVM_SETSELECTIONMARK · Windows UX Guide: Keyboard · Apple 键盘快捷键

4.5 通用实现原语

  • 最小滚动：scrollIntoView({block:'nearest'}) 的契约是「已可见则不滚，否则尽量少滚」——视口跟随应只用 nearest（裸调默认 block:'start' 会把行顶到头上造成跳动）。需要给 sticky 表头留边时用 CSS scroll-margin（目标侧）/ scroll-padding（容器侧）。
  • 手工最小滚动：getBoundingClientRect() 比较行与容器矩形，只在出界时补差价——比 scrollIntoView 可控（不受多级嵌套滚动祖先影响），正是本项目 _kbScrollRowIntoView 的既有路线。
  • 重渲染禁止无条件滚动：轮询刷新若触发 scrollIntoView 会与用户正在进行的滚动打架（Downshift 官方 issue 结论：检测到用户在滚动就不调）。规则：滚动只允许由「键盘移动光标」与「显式定位指令」两类事件触发。
  • 虚拟列表：react-window scrollToItem(i,'auto') / TanStack Virtual scrollToIndex(i,{align:'auto'}) 的 auto 即最小滚动；键盘导航应在数据层维护 index 调 scrollToIndex，不依赖离屏行的 DOM focus——这也是 aria-activedescendant 适合虚拟化的原因。

来源：MDN scrollIntoView · MDN scroll-padding · TanStack Virtual API · Downshift issue #281

4.6 成熟组件库的默认行为

库与本议题对口的默认行为
react-aria箭头键移动 focus（keyboardDelegate 可覆写）；selectionBehavior:'replace' 下 selection 跟随 focus，'toggle' 下二者独立、Space/Ctrl 切换；Shift 区间不受 behavior 影响；虚拟化走 isVirtualized + scrollToItem。
DownshifthighlightedIndex（键盘高亮）与 selectedItem（真选中）天然分离；高亮项变化时自动最小滚动，可替换或禁用。
AG Grid键盘模型以 focused cell 为中心：方向键移焦点、网格自动把焦点滚入视口；提供 navigateToNextCell / setFocusedCell / ensureIndexVisible——与「键盘从当前焦点出发 + 视口跟随」完全同构。

来源：react-aria useListBox · Downshift useSelect · AG Grid Keyboard Interaction

05 · 共识提炼与差距对照

所有成熟实现收敛为同一条心智模型：focus / selection / hover 三分，点击落焦点，滚动最小跟随，刷新不动焦点。逐条对照本项目：

法则业界做法本项目现状判定
光标独立建模focus/cursor 是独立字段，与 selection 分离kbCursor（kind+id）已独立存在，kb-cursor 视觉类已分立达标
点击衔接（核心差距）点击行 → 写 focus/cursor（Win32 selection mark、Gmail、VS Code 全体一致）五个鼠标点击入口均不写 kbCursor，键盘从旧位置出发缺失
无焦点回落口径（跳底直接来源）初始焦点 = 已选中项（APG）；至少是「就近」而非极值cur<0 时 ↓→首行 / ↑→末行（极值回落）偏差
视口最小跟随nearest / no-op 语义；手工 rect 差值_kbScrollRowIntoView 已是差值补差价，行可见不动达标
刷新不动光标刷新只 diff 数据，focus 持身份身份重定位（kind+id），轮询天然安全达标
hover 不回写hover 纯视觉主列表 hover 为 CSS :hover，不写状态达标
数据刷新不触发滚动滚动只由键盘移动/显式定位触发滚动只在键盘路径（_kbApplyCursor）内发生达标

结论：本项目差的是两处状态口径（点击衔接、回落口径），不是架构——不需要引入 roving tabindex 式的重构才能解决割裂感。

06 · 方案比选与推荐

方案 A 仅改回落口径

cur < 0 时不再落极值行：↓ → 视口内第一行，↑ → 视口内最后一行（实现可借 _rowWindow 窗口信息或对 _kbRows 做一次可见性扫描；无窗口信息时退化为「↓ 首行 / ↑ 末可见行」的保守版）。

能消掉 S1（跳底）；不能消 S2/S3（点击后键盘仍从旧位置出发）——割裂感只解决一半。改动最小（一处分支），可作为方案 B 的子集先行。

方案 B（推荐） A + 点击落光标

在 A 之上，把「点击行」作为键鼠衔接点：五个鼠标点击入口（onGroupClick / onMemberClick / onTorrentClick / onShowClick / onShowEpClick）按所在行回写 kbCursor，与既有 selAnchor* 维护并存。要点：

  • 落光标 ≠ 选中：写的是 focus 语义（kbCursor），不动 selGroups/selMembers——与 2026-09-17「普通点击不触发选择」的既定口径不冲突，恰是 VS Code / Gmail 的 focus 模型。Ctrl/Shift+点击在原有选中语义之外同样落光标。
  • 普通点击获得轻量视觉反馈：行上出现 kb-cursor 光标环——这正是「键盘起点在这里」的可见承诺，也是衔接感的来源（Gmail/VS Code 同款）。是否接受这一视觉变化是本方案唯一的口径决策点。
  • S3（残留光标）在业界属「焦点持久」的正常语义：VS Code 同样保留焦点、按键跳回。B 落地后点击高频重锚，残留窗口大幅缩短；如仍有体感问题，可加可选加固「光标出视口且用户滚动超过一屏后，首次按键回落到可见行」——默认不建议做，避免过度工程。

方案 C 完整 roving tabindex / aria-activedescendant 改造

把列表纳入 WAI-ARIA 官方焦点管理（Tab 可进入列表、读屏可感知、DOM focus 随箭头移动）。可访问性收益真实，但需改四份模板的 tabindex/DOM focus 管理并处理窗口化离屏行，改动面大；当前无读屏诉求，缓议——B 的状态模型与 C 完全兼容，将来要补 a11y 时不需要推翻 B。

推荐理由（B）

① 三个触发场景全部消除（S1 靠回落口径、S2 靠点击落光标、S3 因高频重锚自然缓解）；② 改动集中在 _kbMove 回落分支 + 五个点击入口各一行回写，不碰滚动实现、不碰模板视觉；③ 六条业界法则全数达标；④ 与既有双轨目标解析（_kbTargets）无缝：点击 → 光标 → Space/Enter/动作键一气呵成。

07 · 实施风险与坑（实施时注意）

  • 禁用 scrollIntoView 是既有红线（pitfalls/web-ui/hover-keynav-fight.md：逐层滚动可滚祖先连带滚整页）——落光标若伴随滚动跟随，必须继续走 _kbScrollRowIntoView 的差值路线，并在 $nextTick 里量（等 Vue 把 kb-cursor 类挪到新行）。
  • 点击落光标的滚动天然安全：被点的行本来就在视口内，最小滚动语义下 no-op——不会出现「点一下滚一下」。
  • 长按连发交互（26-09-30 刚落地）：回落口径改后，连发首拍落视口就近行、后续正常步进，无额外处理；注意 repeat 放行条目仍限于上下键族。
  • 窗口化未渲染行：回落口径若基于「可见行」，注意与 _rowPre 前缀和同源校验（长度不符放弃，沿用 P1-2 退避口径）。
  • 注释与实际口径不符：现注释自称「就近回落口径」但行为是极值回落——实施时一并修正注释与 _kbHint 文案（提示语无需再教「先 ↑↓ 移到一行」，点过就行）。
  • 守阵联动：点击回写 kbCursor 涉及 selection.js，建议随实施补静态守阵（grep 式断言五入口都有回写），避免后续改鼠标路径时悄悄丢掉衔接。
