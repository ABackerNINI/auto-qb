qB/libtorrent 跳检机制源码核查 — seed_mode 语义、惰性哈希校验与标记可替代性

跳检种子的特殊标记就是 libtorrent 的 torrent_flags::seed_mode；上传时它不是"顺便"校验，而是发块前强制整片哈希，失败即强制全量重校验——因此坏数据一个字节都发不出去。但该标记不能替代 zSkipChecked 标签：它没有 Web API 读面、落盘可滞后一小时、且全部验完后会自毁。

§01结论

三问三答

问题结论证据锚点
跳检的种子有特殊标记吗 有。lt::torrent_flags::seed_mode，由 qB 的 AddTorrentParams::seedMode 置位，写入 resume 数据持久化。 sessionimpl.cpp:3086-3089 · write_resume_data.cpp:84
上传时会顺便检查块 hash 吗 会，且比"顺便"更强：该片首次被请求时先算整片哈希（v1 全片 sha1；v2 全片所有 block 的 sha256），请求被 hold 而非 reject，验完才发块。每片只验一次。 peer_connection.cpp:5331-5367 · 5431-5530
块 hash 不对会触发全文件校验吗 会，且是强制全量：hash_failed_alert + leave_seed_mode(check_files) → set_have_all(false) + force_recheck()，整种回退重校验、缺片重新下载。 torrent.cpp:542-580
数据完整性这条腿是硬的

跳检的安全模型不是"信任文件存在"，而是信任首次使用（trust on first use）：未验过的片不对外发送，任何一次校验失败都会把整种拉回全量校验。所以"跳检会往群里传垃圾数据"这个担心，在 libtorrent 这一层是不成立的。

收益与成本都严格取决于数据是否完整

完整数据下，哈希读与该片的服务读紧邻发生、命中页缓存，物理上只落一次盘——相对全量校验（校验读一次 + 之后冷读一次），相当于省掉一次全量读盘，且不必等校验跑完即可做种。

残缺数据下则相反：一次 force_recheck 把省下的全部收走还倒贴，而且补齐缺口要计入站点下载量——全量校验本身不花一个字节流量，跳检却把"发现缺口"推迟到最坏的时点。详见 §2.10。

能否替代 zSkipChecked 标签

不能替代。它是引擎侧的事实，但不是一个可用的对外判据。三条决定性障碍见 §2.8，一句话版本：

  • 没有 API —— torrents/info / sync/maindata / torrents/properties 全都没有该字段，只能读 qB 配置目录里的 .fastresume 文件，Docker 只挂下载目录、seedbox 远程部署直接失效。
  • 不实时 —— resume 落盘由默认 60 分钟定时器驱动，跳检是删种重加且不触发校验，重加后既无校验完成事件也无状态跳变，文件可能一小时不更新甚至还不存在。用它确认"这次跳检成功了"必然误判。
  • 会自毁 —— 全部片惰性验完后 leave_seed_mode(skip_checking) 立即 m_verified.clear()，seed_mode 同时归 0。所以"位图全满"这个状态永远观察不到，seed_mode=0 是个歧义值。

但它有两个标签补不了的价值，前提是只当旁证用、且 fail-open：

  • 崩溃对账：现有 _skip_step_finish 打标失败只记 warning（"不影响跳检结果"），崩在打标之前安全性判据就静默破了。此时 seed_mode=1 是引擎侧铁证。
  • 自动摘标：对一个带 zSkipChecked 的种子，seed_mode=0 且 progress==1 ⇒ 数据已完整校验（单向推断，论证见 §2.8）。这正好补上现在"程序只打不摘"（infra/utils.py:638）的缺口。

预分配文件能过闸

稀疏预分配使文件尺寸等于完整尺寸，这条"只查不小于"的检查会放行——内容却是零块。于是 progress 落在 (0,1) 的种子跳检会成功进入 seed mode，但产出的不是"垃圾数据外传"，而是"宣告 seeder 却供不出数据"：坏片在发块前被整片哈希拦下（§2.5），一个字节都出不去；代价是对端请求被扣住白等，以及必然触发的全量重校验（§2.6）。这不是 libtorrent 的缺陷，而是"信任首次使用"模型的前置条件。本项目 ops_mod.py 的 partial 闸门（仅 progress==0 可跳检）由此得到引擎层佐证，必须保留——但理由是收益分档（§2.10），不是"防外传"。

2.5 上传路径：发块前强制整片哈希

// src/peer_connection.cpp:5331-5367
bool const seed_mode = t->seed_mode();
if (seed_mode && !t->verified_piece(r.piece)
    && !m_settings.get_bool(settings_pack::disable_hash_checks))
{
    if (t->verifying_piece(r.piece)) continue;            // 同片去重
    if (m_outstanding_piece_verification >= 3) continue;  // 每 peer 最多 3 个在途
    ++m_outstanding_piece_verification;
    disk_job_flags_t flags;
    if (t->info_hash().has_v1() && !t->disable_v1_hashes()) flags |= disk_interface::v1_hash;
    aux::vector<sha256_hash> hashes;
    if (t->info_hash().has_v2()) hashes.resize(t->torrent_file().layout().blocks_in_piece2(r.piece));
    m_disk_thread.async_hash(t->storage(), r.piece, v2_hashes, flags, ...);
    t->verifying(r.piece);
    continue;                                             // 请求被 hold, 不是 reject
}

三个要点：

  • 粒度是整片，不是块。请求一个 16 KiB 块，代价是读并哈希整个片（v1 全片 sha1；v2 全片所有 block 的 sha256）。
  • 请求被扣住而非拒绝：continue 保留 m_requests[i]，验完由 on_seed_mode_hashed 末尾再 fill_send_buffer() 续发。对端只感受到延迟，不感受到错误。
  • 每片只验一次：结果落 m_verified（torrent.cpp:1321 起 verified()），并随 resume 落盘。

配套：is_seed() 在 seed mode 下恒真、bytes_left() 恒 0（torrent.cpp:9252-9263、:4365），即对 tracker 立刻宣告 left=0、立刻做种。disable_hash_checks 默认 false（settings_pack.cpp:158），qBittorrent 全仓从不设置它（grep 无命中）——这道闸不可被 qB 侧关闭。

2.9 能否替代 zSkipChecked：语义对照与判据

维度zSkipChecked 标签.fastresume 的 seed_mode / verified
读取通道Web API torrents/info.tags（现有）只能读 qB 配置目录
时效打标即时（_skip_step_finish）默认 60 分钟级滞后；新加种可能尚无文件
存活期永久，直到人工摘自毁：全验完即清（§2.7）
表达的信息"我们跳检过它""它跳检过且还有片没验"
用户可见qB 界面可见、可手动摘完全不可见
依赖仅 API文件系统 + 部署形态 + 存储后端

单向推断（成立，且有实用价值）

对一个带 zSkipChecked 的种子：seed_mode=0 且 progress==1 ⇒ 数据已经过完整哈希校验。论证是穷举离开 seed mode 的全部路径：

路径结果
leave_seed_mode(skip_checking)（全部片已验）已校验 ✓
leave_seed_mode(check_files)（校验失败/磁盘错误）force_recheck() → 全量校验后仍为"已校验或待下载"；progress==1 即已校验 ✓
加种时因 file/piece priority 或 have_pieces 被忽略（§2.3）走正常校验 ✓
resume 被拒（文件尺寸不符等，§2.4）走正常校验 ✓
删种后以普通方式重加走正常校验 ✓

失效方向是安全的：文件缺失 / 读不到 ⇒ 视为未知 ⇒ 维持标签（fail-open）；文件滞后仍写 seed_mode=1 ⇒ 维持"未验证"判断（fail-closed 方向正确）。反向滞后不可能——删种会连带删除该文件（sessionimpl.cpp:2700）。

建议：保留标签为唯一权威，旁证只做增益

① zSkipChecked 继续作为参考种子排除（checking.py:_find_reference）的唯一来源——该判据必须 fail-closed，而文件读取天然会失败。
② 若将来引入"读 qB 配置目录"能力，仅用于两件事：崩溃在打标之前时的对账（seed_mode=1 作证）、以及 §2.9 单向推断触发的自动摘标。
③ 更便宜的等价路径已存在：verified_references 内存并集（历史 full-checking 通过即入池），只是要花一次全量校验。

2.10 跳检的 I/O 账与对口径的影响

校验读与服务读会合并

这是跳检收益的机制来源，也是它最容易被低估的地方。全量校验把"哈希读"提前到加种那一刻，等服务请求到来时缓存早已冷掉，同一批数据要再读一遍；跳检把哈希读推迟到该片首次被请求的瞬间，async_hash 读进页缓存后紧接着的 async_read 直接命中，物理上只落一次盘。

场景校验读服务读合计
直接全量校验T（冷）U（冷）T + U
完整数据 + 跳检合并——哈希后立即服务，命中页缓存≈ T
残缺数据 + 跳检失败前已读 Σ + 强制全量重校验T + U + Σ

T = 种子总大小；U = 实际上传字节数（被完整下载一遍时 U ≈ T）；Σ = 撞上坏片之前已读的片。

严格说不是"少一个读任务"：async_hash（peer_connection.cpp:5363）与随后的 async_read 仍是两个独立磁盘任务，只是第二次命中缓存。libtorrent 并未刻意做"读一次算两用"的优化，这是"哈希必须在发块前、且紧邻发块"这一顺序的必然结果。另外 pread_disk_io::async_hash 会先试 m_cache.try_hash_piece()，该片已在读缓存时连读盘都省掉。

收益按数据完整性分档

数据状态收益代价结论
完整（progress==1） 省掉一次全量读盘（U ≈ T）+ 不必等校验跑完即可做种 每片首次请求多一次哈希延迟；未被请求的片不验 净正收益
残缺（0 < progress < 1） 失败前的短暂供种 多读 Σ + 必然触发 force_recheck（已验片一个不留）+ 位图全 1 翻全 0 的公开翻转 + 做种进度清零 + 补齐缺口计入站点下载量 净负收益

残缺档的关键是必然性：force_recheck() 里 set_have_all(false) 加 ++m_picker_generation（源码注释 "forget that we have any pieces"），已验结果一律不保留。所以只要有一片坏且被请求到，省下的校验时间就要连本带利还回去，还多一次删种重加。跳检省下的读盘，是在赌没人请求到坏片——赌赢了省一点，赌输了倒贴。

残缺档还有一笔硬成本：下载量

上面的账只算了 I/O 与时间。残缺档真正的成本大头在 PT 站点侧——补齐缺口要重新下载，每一个字节都计入你的下载量，而下载量是不可逆的硬通货（分享率、HR 判定、下载配额），花掉就没了。这笔账有三个特点：

  • 全量校验本身不花下载量。校验只是读盘，零流量。所以残缺档的跳检，本质是用下载量去买一个本来免费的东西（少等一次校验）——这个交易在结构上就是亏的，而完整档根本不会触发下载。
  • 发现时点被推迟，且不可控。全量校验在加种后几分钟就把缺口摆在你面前，你可以先看清"要重下多少"再决定删不删；跳检则要等到第一次有人请求坏片才引爆——此时你已经投入做种（HR 计时、站点记为 seeder、可能已有 peer 连上来），删种有沉没成本，留着要付下载量。引爆的时点可能是凌晨、可能是配额快用完的时候。
  • 按整片放大。piece 是原子单位，一个片里坏一个块就要重下整片（4–16 MiB），坏片集中在大文件时放大更明显。
这才是 partial 闸门真正的价值

不是"防垃圾外传"（不会外传），也不只是"防 I/O 倒贴"（那只是时间）。是防止把下载量这种不可逆的硬通货，花在本来可以免费避免的地方。反过来说，"有可信参考种子"这道闸的经济含义也随之清晰：它降低的是触发重下的概率，也就是保护下载量——而不是"防止坏数据扩散"。

待实测项：跳检是删种重加，客户端侧的 downloaded 计数器会归零重新累计，站点如何处理这次回退取决于其记账实现（取最大值 / 按增量 / 按会话）。成熟站点按增量记账一般不会重复计费，但这一点无法从客户端源码判定，建议跳检前后各记一次站点面板数字做核对，别把它当成异常增长。

一处需要纠正的常见说法

残缺档的危害不是"零块被上传成垃圾数据"。发块前的整片哈希（§2.5）保证坏片一个字节都出不去；真正的危害是对端请求被扣住白等、以及位图全 1 翻全 0 的公开翻转与随之而来的全量重校验。

因此该守什么

既然坏数据发不出去、且必自愈，"有没有可信参考种子"其实不是数据完整性要件——libtorrent 已经兜底。真正该守的是另外三条：

  1. 数据必须完整：progress 为 0 或 1。这不是"防外传垃圾"（不会外传），而是防上表第二行的净负收益，尤其是不可逆的下载量损失（§2.4）。partial 闸门不可动。
  2. 共享物理文件不能有并发写方：片验完之后被别的种子写坏，再上传就真漏了（TOCTOU）。组内有活跃下载成员、组内校验在途这两类闸门防的是这个，不属于可放开范围。
  3. 未校验窗口：没人请求的片永远不验。死种场景下这没有危害（无人取数据），但该种若日后复活，校验债会在那一刻一次性兑现。跳检后主动促验（或隔期补一次 recheck）可把窗口压短，使"跳检"退化为"把全量校验摊到做种过程中"。

据此，可考虑的放宽方向是把"参考种子"从硬闸降级为优先级/顺序因素，而不是取消数据完整性与并发写方这两道闸。完整数据档的跳检是实打实省掉一次全量读盘、且不涉及任何下载量，不是"用风险换时间"——这为放宽口径提供了正面依据；而残缺档恰好相反，省的是时间、赔的是下载量。

§03方法与局限

方法

  • 静态源码走查，不做运行时抓包。以 grep 定位符号（seed_mode / seedMode / verified_pieces / hash_failed_alert / save_resume_data），再逐段读上下文与调用链，全部结论均带文件名与行号。
  • 覆盖链路：qB AddTorrentParams → lt::add_torrent_params.flags → torrent::init → 启动 async_check_files → 上传 fill_send_buffer → on_seed_mode_hashed → leave_seed_mode → resume 写读。
  • 本项目侧核对：ops_mod.py 跳检相位机与打标、rules/actions/checking.py 参考种子排除、infra/utils.py 标签口径、qbittorrentapi 实装参数表。

局限

  • 未做运行时验证：没有构造坏片实测"上传被 hold → 全量重校验"的时序，结论来自代码路径，非观测。
  • 版本绑定：结论对应 libtorrent 2.1.2.0 与 qB v5.3.0 分支。qB 4.x 的 WebUI 参数仍是 skip_checking，行为等价但参数名不同。
  • ABI 1 差异：torrent_status::seed_mode 字段在 TORRENT_ABI_VERSION == 1 下才存在（torrent_status.hpp:517-521），ABI 2 走 status.flags。不影响 WebUI（本来就不暴露）。
  • 纯 v2 种子未实测：.fastresume 文件名正则只认 40 位 v1 hash，纯 v2 种子在该目录的落盘/加载行为未进一步验证。
  • SQLite 后端未验证：若用户把 resume 存储切到 torrents.db，文件面结论整体失效。
