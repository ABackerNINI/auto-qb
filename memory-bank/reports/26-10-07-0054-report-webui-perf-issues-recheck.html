04Issue 1 新变量: SSE 推送改写消费动态

issue 入池两天后（2026-09-21, 0c18fcda）, _publish_locked 增加了事件推送: 重建完成后 notify("ver", {ver})（runtime.py:793-795）; 前端收到 ver 事件后 60ms 去抖即拉 /api/state（static/shared/polling.js:50-55）, 轮询保留为兜底（polling.js:106-111, 分档 1.5/2/3s）。notify 是 per-subscriber put_nowait（runtime.py:264-279）, 事件毫秒级可达。这改写了 issue 的两个组成部分:

① 「总账不省」的论断仍真, 但机理变了

SSE 在线 + 活跃库时: 每个 sync tick（默认 1.5s）置脏 → 无欠账 → 主循环重建 → 推 ver → 客户端 ~100ms 内拉走清账 → 下一 tick 再重建。总重建次数 ≈ 服务端 tick 数（60s 约 40 次）, 与无门控基线（41 次）相比依旧 ≈0% 净省——issue 的标题论断在 SSE 世界同样成立。但机理不同: 入池时是「主循环省下的版本被请求路径补回来」（20/20 分摊）; SSE 下客户端每版必拉, unconsumed 在下一拍几乎恒为假, 门控在主路径上等效失效, 主循环承担几乎全部重建。

② 「每次 /api/state +48.7ms」的伤害在主路径基本消失

入池时的实测伤害是「一半重建搬到请求线程, 每次请求可能撞上脏视图多付 ~49ms」。SSE 下请求到达时视图通常是净的（ver 推送紧随发布之后）, 请求路径重建频次趋近于零。该伤害只在轮询兜底路径回归: SSE 断线 / 浏览器不支持 / 反代缓冲时, 客户端退回 3s 定档轮询, 原动态（20/20 分摊 + 请求侧延迟双峰）原样复现。

③ 方案 A 的 -51% 收益蒸发, 降级为「线程归属」交易

方案 A（全惰性, 主循环不再重建）的卖点是把总账从 41 压到 20（-51%, 按 3s 消费档）。SSE 下消费率 = 生产率（客户端每版必拉）, 每个被消费的版本都需要恰好一次重建, 40 次/60s 是任何方案都降不破的下界——方案 A 只能把这 40 次从主循环挪到请求线程, 省不了总量。它对「主循环解耦」（P0-5 命令响应）仍有交易价值, 但不再是「省 CPU」的优化。

④ 方案 B 与顺带小修仍有效

  • 方案 B（修正口径）: 门控注释/提交结论里的「省 50%」仍是主循环单列口径, 且门控在 SSE 主路径上等效失效这一点（flush_views docstring 与「节拍对齐」注释, runtime.py:504-507）没有写明——文档修正的范围比入池时更大了, 仍建议做。
  • 顺带小修（ensure_view 清账）: 原样有效。且入池时说「当前 UI 只走 /api/state」, 现在可以加一句: 前端 shared/ 下对 /api/groups 的调用已清零（grep 取证 2026-10-07）, 影响面仍限「只打 /api/groups 的外部脚本」。
  • 方案 C（请求侧最短间隔）: 在 SSE 世界基本失去意义（请求侧已很少重建）, 仅轮询兜底路径还沾边, 优先级进一步下调。
