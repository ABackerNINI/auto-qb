§01结论

矩阵(S0①, 现行实现, R 盘, 全部实测): 5000 系列恢复耗时 fresh/stale/fallback = mixed 297.5 / 666.1 / 1435.5s, zheavy 253.0 / 528.7 / 1236.2s, rheavy 412.0 / 914.1 / 1944.1s。计划 §02.3 的 ~250s 外推与实测同量级(fresh 实测 253-412s)。

236 生产形态对照(S0① 对账面): 按快照实测构成(1.5s 档 / 相位 8.23h / 读集 465.97 万槽)合成 236 系列, fresh 实测 10.222s, 对照生产 before 11.72s(读集 466 万槽): 槽位差 ≈0.01%, 耗时差 12.8% —— 同量级吻合, 每槽成本 2.19µs vs 生产 2.52µs(残差 = 语料构成/机器状态差异, 见 §02.3)。

尺寸预算(S0②, 全部实测): 生产快照构成(48 系列, z 游程主导, 全库 1.5s 档, r 行槽位占比 1.77%)折算 5000 系列 × 4 天文件 ≈ 0.22-0.38GiB, 达标; r-heavy 极端(4s 档全天全活跃, 实测 777.6KB/天文件)≈ 14.48GiB, 达标; 超限边界只在 1.5s 档全天全活跃兑现(实测 2.13MB/天文件 → 39.75GiB) —— 与计划 R8 处置一致(配置面 sample_interval_multiplier), 不需要新机制。已回填计划 §03.2 预算表(新列「S0 实测」+ kb.bump R1 行)。

快照规模与计划正文的差异如实披露: 快照实测 48 系列(1 global + 47 torrents)/25.09MB/42 天, 与计划正文「236 系列/466 万槽」对不上 —— 按任务口径如实记录, 不解读为计划错误(快照时点/生产库清理状态不明), 见 §02.5。

真机轨 before(S0③, 追加于 R1): 环境1/R 盘 5001 系列真实主程序受控复测 —— 优雅重启中位 243.8s(g2/g3), 崩溃重启中位 243.0s(c2/c3, 与优雅同路同槽位), 补算变体 282.2s, 冷启 274.2s; flush stall = 稳态零 IO + 停机封口 5001 文件跨度 5.18-5.35s; 对照计划 §02.3 外推 ~250s 同量级吻合。全文见 §04。

02.6 48-vs-236 规模差异披露

任务口径指出已知事实「47 系列/42 天/共 27MB」与计划正文「236 系列/466 万槽」对不上。本次实测: 48 系列(global 1 + torrents 47; 任务口径的 47 应为 torrents 目录数, 加 global 为 48)/42 天/25.09MB, 与任务口径一致。计划正文的 236 系列/466 万槽出自 2026-11-21 生产日志的恢复读集(系列键数 × 读集槽位), 两者是不同时点/不同口径的事实: 快照可能是生产库某个更早/更晚时点的拷贝(期间发生过种子淘汰、清理或数据目录迁移, 均不可从快照本身考证)。按任务纪律: 如实测如实写, 不擅自解读为计划错误; 236 规模的对照改由 prod236 合成语料承担(§02.3, 语料参数照快照实测构成放大), 对账成立。

02.7 线性规律与 D5 全窗最坏值(拟合外推, 非实测)

同形态三场景耗时比(1 : 2.24 : 4.82)与槽数比(1 : 2.215 : 4.646)线性吻合; mixed30 的 30 天全窗 cell(500 系列 × 30 天)与 mixed 5000 × 4 在「系列×天」总量上交叉验证: 1028.9s / 1435.5s = 0.717 vs 总量比 15000/20000 = 0.75(±4.5%)。每槽成本按形态族稳定: rheavy 4.635-4.709µs(极差 ±1%), zheavy 2.686-2.994µs(±5%), mixed 族 2.799-3.477µs(±10%, 500 与 5000 系列两档的逐系列固定开销占比不同所致)。

D5 真最坏值外推(现行无清理, 淘汰龄 30d → 单系列至多 ~31 个天文件; 5000 系列 × 30 天 ≈ 3.24G 槽): 按各形态实测每槽成本区间 —— mixed 3.19-3.48µs → ≈ 10,340-11,270s(≈ 2.9-3.1h), zheavy 2.69-2.99µs → ≈ 8,700-9,700s, rheavy 4.64-4.71µs → ≈ 15,000-15,260s。此为拟合外推值(30 天 × 5000 系列的语料 20GB+ 未直接实测), 但线性基础有 1/2/4/30 天四点实测支撑; 计划 §02.3 fallback 行的「250-500s」量级在此被实测显著上修 —— 5000 规模下现行实现的 fallback(升级首启自举、账本损坏等场景)是真锅盖, 印证 D1 改判(快照一步到位)。

§03方法与局限

方法

  • 真实入口: 计时体 = TrafficSampleModule(ctx).start(ctx, dry_run=False)(生产 start() 钩子路径), 内部 _recover_aggregates → _recover_series → _agg_credit_day_file → _agg_append/_agg_trim 全部生产原码; ctx/config 为最小装配(SimpleNamespace + 真实 QbTraffic 缺省: rollup_window 30D / raw_window 24H), 恢复代码零改动、src/ 零触碰。
  • 真实格式语料: 全部天文件经 format_v4_day_text(项目 codec 单点)序列化; 活跃日 = 600s 块(B 行 + 块内 r 行按 interval 铺满, totals 单调, 块基线语义与写侧状态机同构); 空闲日 = 单块单 z 游程(显式退化末端对); prod236 混合日 = [z 前缀 | r 行窗 | z 后缀] 三段式, 槽位守恒。
  • 场景实现: 场景差异只在 agg.dat 水位形态(fresh = 30d hour 历史 + 当日 0-18h 整点行; stale = 止于昨日 23h; fallback = 仅头行+key 行), 每 cell 前重写 agg.dat(幂等可重入); 天文件不被恢复路径改写, 多场景安全复用。
  • 计时与记录: time.perf_counter 包住 module.start; 恢复 INFO 日志按生产同成本落文件(计入计时); 结果 JSON 按 cell@impl_tag 键实时落盘(同键覆盖、换 tag 追加), 每 cell 打进度行。

局限(如实列)

  • 矩阵语料间隔 4.0s(对齐计划 §02.2 的 ~2 万槽/文件口径, 21600 槽/日 +9%); 生产现档 1.5s 的绝对对账由 prod236 cell 承担。每槽成本与间隔值无关(成本 ∝ 槽数, 已由 prod236 1.5s 点旁证)。
  • fallback 读集受语料天数限制(4 天); 30 天全窗最坏值 = mixed30(500×30)实测 + 每槽稳定性的拟合外推(§02.7), 不是 5000×30 直接实测。
  • 每 cell 单次计时, 无重复方差; 挂钟只影响「幸存小时的完结判定与 catch-up append 行数」(stale 补算小时 85,000 vs rheavy 90,000 即不同运行时刻的差), 主成本段(解析+展开+入账)不受影响。
  • 合成语料不含 n 游程(断连)与 dt_ms 漂移行(生产有, 两者均为低成本路径, 不改变量级); 语料行宽 34-37B vs 生产 23.8B 均值。
  • 基准环境: 95G 内存 / R 盘内存盘 / Windows 独占(生产为系统盘 SSD + 常驻负载)。

04.4 ③flush stall 基线(空闲库, 如实口径)

量法: 稳态窗内每 2s 全库 5001 个 agg.dat mtime 扫描(burst 命中后 0.3s 粒度追扫, 写窗 = mtime 跨度) + 每 ~6s WEB /api/state rid 探针 + state.json mtime; 稳态后解析活跑天文件的 dt_ms 行(累积漂移判据 DRIFT_TOL_MS = 250ms)。覆盖: g1 稳态 1300s = 2 个 flush 窗(任务要求 ≥600s), g2/g3/c2/c3 各 180s。

观测面实测解读
稳态 agg 写面全部扫描行 agg_changed = 0(g1 650 行 + 各轮 90 行, 零 burst)空闲采样产生开放 z 游程, 跨 flush 滞留内存(机制: 随封口或 stop 落盘) → flush tick 对 5001 系列做纯内存迭代, 零 IO, 文件面不可观测。flush #1(恢复后首个 600s tick, ≈22:26:45)同样零写 —— hour8 的 5001 个 catch-up append 已在恢复内完成(补算小时 5001)
可观测的 5000 系列批量写优雅停机封口: 5001 个当日天文件追加, mtime 跨度 5.18 / 5.28 / 5.35 s(g2/g3/g1 三次实测 ≈ 1.05ms/文件)现行实现「5000 系列批量追加」的直接实测; S2 的 acc 账本 flush 随批追加是同形状 per-series 批量, 此跨度即其量级先例
主循环节律(dt_ms 漂移)活跑窗有效采样间隔被拉长: g1 窗 775 槽/1301.6s(标称 867 槽, 缺 ~92 拍 ≈ 138s), g2 窗 69 槽/179.0s(标称 119 拍, 缺 50 拍), g3 窗 67 槽/180.5s; 天文件 dt_ms 行实测值 1,301,558 / 179,028 / 180,521 ms拉长归因 = 5000 种子首轮任务排空(5000 任务 / 20 每拍 ≈ 250 拍, 归组管线串发为 0259 已入池面), 非流量 flush —— g1 窗前段(任务排空期)拉伸 ~2.6s/拍, 排空完成后向 1.5s 回收(全窗均值 1.68s); g2/g3 的 180s 窗整体落在排空期
rid 探针稳态期 366 次探针(g1 216 + g2/g3/c1/c2/c3 各 30)全部非 None, 每轮单一 rid, 零推进空闲库无状态变化 → 无重发布, rid 不构成节律信号(如实记录, 弃用)
state.json 周期落盘120s 节律保持(g1 窗 740s 内 6 次), 文件 90B主循环线程存活 + 周期落盘不受稳态扰动

flush stall 判据(≤50ms/600s)在本环境的口径: 空闲库下 flush tick 零 IO、无可观测 stall(未观测到任何 ≥250ms 累积漂移可归因 flush 的独立事件 —— 观测到的漂移全部由首轮任务线承担); S2 引入的账本追加在空闲库为 0 行(空闲系列零追加), 故「无恶化」是本环境能给出的诚实结论。生产形状(60% 活跃 × 400 r 行/flush)的 flush 写量未复现 —— 需要 L2 活跃流量面, 本轮范围外; S5 真机验收若沿用本环境, 同口径复测即可对齐, 若要真活跃写面须先解决 L2 规模化。

04.5 方法、局限与复跑

  • 量法与分辨率: 恢复耗时 = 产品日志「启动恢复完成 … 耗时 X s」(模块时钟, 生产 11.72s 取证同口径; 墙钟差与模块时钟差 ≤0.03s, 分辨率 = 日志毫秒); 首拍 = /api/state 轮询时间线(0.3s 粒度, measure_boot_first_data 同款); 稳态写面 = mtime 扫描(2s 粒度 + 0.3s 追扫, mtime 分辨率毫秒); 漂移 = dt_ms(250ms 累积判据, 值为毫秒)。
  • 局限: 元数据-only 种子 → 活跃流量面缺失(flush r 行写、真实速率分布未复现); R 盘内存盘 + 独占机(与生产 SSD + 常驻负载不同); 夜间单会话单次测量; 首轮任务线拉长节律为 0259 已入池面, 不计入本计划判据。
  • 复跑(语料/种子留存, 见 §04.1; 若跨日须按当日相位重新 gen 语料并对齐新种子): uv run python tests-real/.work/s0traffic/tools/s0r.py cycle --tag X --mode graceful|crash --steady 1300 --measure-timeout 900(前置: real.up 双实例 + real.guard + 36596 已含 5000 real-fake 种子; 恢复耗时另见 R:\aqb-traffic-bench\20261121-2145\live\logs\auto-qb.log 的「启动恢复完成」行)。
