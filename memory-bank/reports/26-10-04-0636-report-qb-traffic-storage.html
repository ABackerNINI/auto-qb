01摘要（结论先行）

结论一 · 问题一根因

「速度 0 → 断线无数据」不是写错值，而是语义倒挂：单种系列采样有活跃过滤（dlspeed>0 or upspeed>0 才产点，traffic_sample_mod.py:243），空闲期不写任何行；读侧把「无行桶」一律当断线（traffic_grid.py:158），前端悬停 null 桶显示「断线 · 无数据」（drawer.html:115）。于是最大量的常态观测（速度 0）被落进了本该表示「采集异常」的缺口编码。工业界与 qB 生态全部先例相反：测得 0 就画 0 平线，缺口只留给「无观测」（qB 桌面端、VueTorrent、Flood、Deluge 均定频推 0 样本；Prometheus staleness / RRD heartbeat 都把「没数据」当一等状态与 0 严格区分）。

结论二 · 存储方案

推荐 v2 零值行程行（z 行）方案：连续零速采样段压缩为一行 z,<start>,<end>,<dl_total>,<up_total>（行程行自身携带时间边界，不依赖间隔推算，天然免疫采样间隔配置变更）；数据行保持显式时间戳不变。文本格式内预期压缩 5–10x（205KB 上界 → 约 25–40KB），且空闲段行数与空闲时长解耦 ——「提高保存间隔」的诉求被更优地满足：不需要牺牲图表分辨率。这是工业界同构先例最密集的一条路（Gorilla XOR 对恒值只写 1 bit、VictoriaMetrics constant 段编码、InfluxDB 时间戳 RLE、Prometheus head chunk 120 样本封口纪律）。

结论三 · 明确不做（本轮）

「段头 start + 隐含间隔、段内省略时间戳」先例成立（Netdata 页元数据 / InfluxDB RLE / Gorilla 块头）但在文本格式下收益仅约 −20%，且与「抖动是事实、坏行跳过、间隔可改」三条现状纪律相抵，列为 v3 备选不实施；整文件 gzip/zstd 透明压缩与追加写冲突，仅适合轮转归档层，不采用；JSONL 比 CSV 行式大 1.5–3x，全面劣势；二进制格式（SQLite / Gorilla 式分块 / Parquet / RRD-Whisper）完成调研留档 §04.5，供以后演进，本轮不动。

问题一的修法在 v2 之上自然落定（§07）：单种空闲段出现 z 行 → 图上画 0 平线；tooltip 三态文案（0 值 / 无采样 / 采集中断）；空闲段不再断累计增量链。组图已借 global.dat 区分真空闲与停机（traffic_grid.py:204），语义保持。本报告为调研快照，未动任何代码；实施需另行计划并拍板（请求边界）。

2.2 体量模型（压缩空间的量化）

  • 行字节数：空闲行 raw,1770000000,0,0,4500000000,900000000\n ≈ 40B；活跃行 ≈ 52B（时间戳 11B + 逗号占每行 ~23%）。
  • global.dat 上界 = raw 24h@30s = 2,880 行（≈150KB）+ hour 30d = 720 行（≈55KB）≈ 205KB/文件（方案C §02.3 设计上界）。
  • 闲时占比：qB 长期在线但无传输是常态 —— 全局系列空闲期 每 30s 一行全 0 行，典型场景 90%+ 的行是冗余零行（每行的速率对全 0、累计对与前一行完全相同、唯一变化的时间戳也只是等差递增）。
  • 单种系列反向问题：空闲期一行没有 → 图上该时段全是缺口（§03），存储省了但语义丢了。
关键观察

两个问题在存储层是同一件事的两面：v1 格式里「有观测」只能表达成「有一行」，于是单种图为了省磁盘选择不观测空闲，全局图为了语义完整为空闲付出 90% 冗余行。缺一个「廉价表达连续零速观测」的行型，两个问题互为代价。z 行（§06）就是补上这个缺失的行型。

03问题一取证：「速度 0 → 断线无数据」的成因链

3.1 主因（系统性）：单种系列的活跃过滤

种子从有速度降到 0（下载完成转做种、暂停、做种无上传）后，采样器跳过它（traffic_sample_mod.py:243）→ 空闲期零行 → 读侧空桶 = null（traffic_grid.py:158–163）→ uPlot spanGaps:false 断线 + 悬停「断线 · 无数据」（drawer.html:115）。用户在单种「流量」页签悬停任何空闲段都稳定复现。这是方案C的刻意拍板（「单种空闲与停机同为无行，停机洞由全局系列表达」），但把「空闲」这个最大量的常态放进了「断线」这个异常编码里 —— 用户误读是必然结果（§04.3 生态先例全是反面）。

3.2 次因一：tooltip 文案二义

「断线 · 无数据」把三种完全不同的状态说成一句话：①qB 断连（有显式 null 行，真实断线）；②程序停机/未启用（无行）；③（经 3.1 放大后的）速度 0 空闲。三态在业界是三种颜色/三种措辞（§04.2）。

3.3 次因二：配置间隔变更让旧数据「变稀」

读侧桶宽 = 当前 sample_interval（traffic_qb.py:65–70）。若间隔从 300s 改成 30s，旧 raw 行仍按 300s 节奏分布 → 旧段 90% 桶无行 → 整段渲染成断线（伪断线）。跟进轮修过一处同类问题（小数间隔下 floor 桶宽伪断线，改 ceil，traffic_grid.py:85–87），但「当前桶宽 × 历史行距」的错配没有解 —— 这正是用户「注意配置可能更改」担心的场景，z 行自带时间边界所以免疫（§06.4）。

3.4 次因三：全局系列的抖动缺口（罕见但存在）

全局系列逐点落盘，桶宽 = ceil(间隔)：均匀漂移（每拍晚 < 1 间隔）不漏桶；但主循环单拍迟滞超过一个间隔（高负载轮）会漏出一个孤桶 → 空闲段中间插一个「断线」缺口。z 行方案下空闲段没有逐点行可漏（行程在内存连续延伸），此问题免费消失；活跃段的偶发缺口可选用 UI 阈值吸收（§07 拍板点，默认不做）。

边界澄清

以下不是问题：①全局图空闲段画 0 平线 —— 全局恒采，0 行本来就写盘；②组图空闲 0 线/停机断线 —— 已借 global.dat 区分（traffic_grid.py:204–221），设计正确；③断连退避期的真缺口 —— null 行如实表达，应当保留。问题收敛在单种（及 hour 段单种 30d）的空闲语义。

4.2 「测得 0 vs 没数据」的渲染惯例

  • Prometheus：无样本 ≠ 0 —— 序列标 stale 后查询不返回值，图上从最后采样时刻起消失；官方明文「no value is returned for that time series」。
  • Grafana：null 处理三选项 Never（缺口，默认）/ Always（连线）/ Threshold（缺口超过阈值才断开）；空值渲染「-」不渲染 0；旧面板选项名就叫 null as zero / as gap。
  • 状态页工具（UptimeRobot / Gatus / Statuspage）：事实上的三态图形语言 —— 颜色只编码「观测结果好坏」，「无观测」永远用灰/空缺表达，不与故障色混用。
  • uPlot（本项目在用）：系列级 spanGaps 默认 false（null 即断线），可设秒数实现「短缺口连线」—— 与 Grafana Threshold 同构。

4.4 文本行内压缩技术（对零值冗余的收益排序）

  1. 零值行程行（RLE 特例）：连续 N 个全 0 采样合并为一行。估算（按本系统行字节数显式推算）：空闲段平均 1 小时 → 约 7.4x；平均 10 分钟 → 约 5.7x。单项收益最大，且与追加/归并语义零冲突。「行程进行中如何落盘」的工业先例 = Prometheus head chunk（开放块，写满 120 样本或 2h 才封口）+ logrotate delaycompress（只封上一周期）—— 对应到本系统：开放行程在内存延伸，每小时封口扫描强制落盘，崩溃丢失上界 = 1 个行程（纯零信息，无信息价值）。
  2. 段头 start + 显式步长快照、段内省略时间戳：先例 = Gorilla 块头（96% 时间戳压成 1 bit）、InfluxDB「delta 全同即 RLE」、Netdata 页头。文本下估算每行省 11B（−20%）。坑：坏行跳过后段内计数不可信（需补序号字段）；跨段重建时间轴；间隔变更必须「变更即新段」写进写侧不变式。
  3. 数值列定点化 / totals 降频：速率缩 KiB/s、totals 只进 hour 行 —— 再省 15–20%，但破坏「逗号计数判坏行」的简单性，需以行型前缀表达，列为激进项。
  4. 小时封口块 gzip/zstd：数字型文本典型 3:1 起；gzip 多成员拼接（RFC 1952）Python 原生可读、可在每小时封口时 append。代价：文件不再是可 grep 的纯文本 —— 与「dat 是行式文本」的现有纪律相抵，不推荐本轮做。
  5. JSON/JSONL：比 CSV 行式大 1.5–3x（本数据形态估算 ~2.6x），全面劣势，排除。

4.5 二进制格式备选（供以后，本轮不实施）

对用户提案「保存开始时间 + 间隔、之后推算」的正面回答

方向正确且有工业先例（Gorilla 块头 / InfluxDB RLE / Netdata 页头），但存在一个次序判断：文本格式下主要冗余是零值行而不是时间戳列——时间戳列只占每行 ~23%，而零值行占行数的 90%+。z 行（B）把行程的时间边界显式写进行内，同样实现了「一次写时间、后续推算」，却不依赖间隔恒定：采样抖动、坏行跳过、间隔改配置都伤不到它。等 v2 落地后若还需再压，段头隐含时间戳（C）是现成的下一级，且两者的版本门闩机制相同。

06推荐设计：dat 格式 v2（零值行程行）

6.1 格式定义

# auto-qb qb-traffic v2                      <- 头行版本号 = 双读门闩
key,<系列标识>
raw,<epoch_s>,<dl_rate>,<up_rate>,<dl_total>,<up_total>    <- 不变：非零速率采样行（语义收窄为「非零观测」）
z,<start_s>,<end_s>,<dl_total>,<up_total>                  <- 新增：零值行程行
                                              [start,end] 区间按采样节奏观测，速率恒 (0,0)；
                                              all-time 累计快照行程内恒定（无传输则不增长）
raw,<epoch_s>,,,,                            <- 不变：null 行（断连/缺字段），v1 v2 同形
hour,<hour_epoch>,<dl_avg>,<dl_max>,<up_avg>,<up_max>,<dl_total>,<up_total>   <- 列不变；聚合口径扩展（6.4）
  • 逐列冻结纪律对 v1 行型继续成立；v2 = v1 解析器 + z 行型，读侧按头行版本分发（双读单写）。
  • z 行自带 start/end 时间边界 —— 不依赖采样间隔推算，间隔配置变更后新旧数据各自如实（§05 候选 B 的核心优势）。

6.2 采样器：开放行程（open run）纪律

  • 每系列内存至多一个开放行程 {start, last_seen, dl_total, up_total}；速率 (0,0) 的采样只推进内存行程（不落盘），非零采样先封口写出 z 行再写 raw 行。
  • 封口三触发（崩溃丢失上界 = 1 个行程，且行程内容是纯零信息）：①非零样本到达；②小时封口扫描强制封口（与现有 catch-up 语义同款，顺带保证 hour 聚合能看到行程）；③行程长度上限 120 样本（Prometheus head chunk 120 样本封口先例；@30s = 1h）。
  • 程序崩溃/重启：内存行程随进程消失 —— 丢一段「零性」，与丢一行零行等价，无信息损失。
拍板点 · 单种系列的行程开启条件（防文件数失控）

若单种系列无条件恒采，则每个种子（含从未传输的）都会在首个小时封口时建文件 —— 击穿方案C「文件数 = 1 + 有过流量的种子数」的三闸收敛。建议规则：零样本仅在「该系列已有数据文件或已开行程」时才延长/开启行程 —— 语义即「动过的种子停下 = 0 线；从没动过的种子 = 无数据（空态）」。既保住惰性建文件，又恰好符合用户直觉（用户抱怨的是「动过然后停下」被画成断线，不是「从没动过」没有图）。

6.3 读侧：行程展开语义

  • 栅格离散：z 行使其覆盖区间 [start,end] 内的所有桶获得速率 (0,0) 观测（桶与区间相交即覆盖）——空闲段在图上是连续 0 平线，中间没有可漏的逐点行（§03.4 抖动缺口免费消失）。
  • 累计增量：z 行携带的 totals 快照作为行程末快照进入差分链 —— 空闲段不再断链，其后首个活跃桶有基线，「窗口累计」不再漏计。
  • hour 聚合：行程对桶贡献 0 速率样本（样本数按 (end−start)/interval 估算，仅用于均值权重）；单种空闲小时由此产出 hour 行（avg=0）—— 30d 单种图从「整幅空白」变为带 0 线（P5 已做孤点渲染，此前是 hour 行缺失）。
  • 坏行校验：z 行 end ≥ start 且差值与本文件见过的节奏相容（宽松校验防手编损坏放大影响面），失败按坏行跳过计数（走既有 5% 阈值隔离）。

6.4 体量与配置影响

  • global.dat 空闲 24h：今天 2,880 行 ×40B ≈ 115KB → v2 约 24 条行程 ≈ 1.2KB（−99%）；活跃段行数不变。单文件 205KB 上界估算降到 25–40KB（5–10x，活跃占比越高越接近低值 —— 必须实测复核）。
  • 单种 .dat：空闲期从 0 行变为每小时 1 条 z 行（≈48B/小时）—— 这是用户想要的增量（0 线可见性），且 rollup 窗口裁剪纪律不变。
  • 零新配置键（黄金法则 2/4 免事务）：sample_interval / raw_window / rollup_window 口径全部不变；「提高保存间隔」的诉求由「空闲不再逐行」满足，分辨率零损失。若未来还要压活跃段，调大 sample_interval 即可，两个杠杆解耦。
  • 迁移：双读单写，头行版本分发；本 clone 生产 config.yml 未启用 qb_traffic，预计零存量数据；他 clone 若已启用，v1 文件保持原样直到自然滑出保留窗（旧空闲段显示为缺口，属历史数据如实呈现）。

08风险、取舍与验收要点

8.1 风险与缓解

  • 一行坏 = 一段空闲异常：z 行影响面比 raw 行大（一行错 = N 个点错）。缓解：end−start 整除/单调校验 + 既有 5%/≥2 坏行隔离阈值 + 行程上限 120 样本天然封顶影响面。
  • 单种恒采的内存与遍历开销：每轮遍历 by_hash 本就发生（活跃过滤只是 skip）；内存行程 = 每种子一条小 dict（几百种子量级，主循环线程无锁）——可忽略。
  • 双读复杂度：v1/v2 两个解析器并存一个版本周期。缓解：v2 = v1 + z 行型（增量解析，非平行实现）；本 clone 预计零存量。
  • 压缩比是估算：5–10x 基于行字节数显式推算，实际取决于活跃占比 —— 实施时以真实采样数据实测复核（验收数字必须实测，见基线口径）。

8.2 测试面（改动波及）

现有钉住 v1 行为的测试：test_traffic_store.py（42 用例）/ test_traffic_sample.py（18）/ test_traffic_grid.py（12）+ test_web / test_module_host 引用。需同步口径的既有用例族：「空闲零采样行」「每轮每系列恰一行 raw」；需新增的用例族：z 行格式化/解析/坏行校验、开放行程三触发封口、单种首零不建文件（§06.2 拍板点）、覆盖展开（含桶跨行程边界）、间隔变更混排数据、30d 行程聚合、v1 文件双读回归。

8.3 验收判据（建议）

  1. 单种「流量」页签：活跃→停止后，空闲段渲染为 0 平线，悬停显示 0 值文案；删种冻结/重加/计数器回落既有语义不回归。
  2. qB 断连段仍为缺口（null 行语义不变）；程序停机段仍为缺口；两者文案与 0 值可区分。
  3. 同等采样数据下 dat 文件体积实测下降（目标 ≥5x，以真实工况记录实测数字入基线切片）。
  4. 改 sample_interval（如 300s→30s）后，旧段空闲仍为 0 线（z 行覆盖语义）、旧活跃段呈稀疏点（如实），无成段伪断线。
  5. 崩溃丢失上界复验：kill 进程后重启，最多丢 1 个未封口行程。
