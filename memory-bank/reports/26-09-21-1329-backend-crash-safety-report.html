总评：架构对崩溃的「自愈面」做得很足，真正的暴露面集中在 state_file 的「仅优雅退出时落盘」策略，以及它的两个放大器。任务队列、种子快照、分组索引、校验参考全部是纯内存态且启动时从 qB 全量重建 —— 这些崩了会自己长回来。不会长回来的是 state.json 里那 9 类去重/冷却/基线状态：它只在优雅退出那一刻写盘，强杀、断电、关机、控制台窗口直接关闭都会丢掉整个运行期累计；而配置热重载的 L2 分支甚至不需要崩溃，一次普通的「保存设置」就会把同一批状态回滚到磁盘旧版。最尖锐的单点是跳检动作「删除 → 重加」之间约 0.5–5.5 秒的无备份窗口 —— 崩在这条缝里，种子从 qB 消失且没有任何恢复凭据。

共确认 5 项发现（2 高 / 1 中高 / 1 中 / 1 低），全部有明确代码证据与低代价修法；另核实了 10 项已经做对的防护。除 F2 是确定性触发外，其余均需要「非优雅终止 + 恰逢窗口」两个条件叠加。

01

调查范围与方法

本次调查回答一个问题：auto-qb 后端进程在任意时刻被终止（无论优雅与否），会留下什么烂摊子，重启后能不能自己收拾好。核查面包括：持久化写入的时机与原子性、单实例锁的陈旧语义、对 qB 的外部副作用在中途被打断后的收敛性、信号与退出路径覆盖、以及崩溃后重启的自愈行为。

  • 静态读码：全量通读核心链路 20 个文件（主循环 / 状态持久化 / 任务队列 / 数据层 / 规则框架 / 跳检与校验动作 / Web 命令层 / 配置写盘 / 托盘 / 锁 / 入口）。
  • 落盘点枚举：全库递归 grep save_state / _load_state / atomic_write / 直接 open(..., "w")，确认每一处磁盘写入的原子性与调用时机。
  • 退出路径枚举：递归 grep atexit / signal / SIGTERM / SetConsoleCtrlHandler —— 结果为零，进程没有任何 OS 信号处理器。
  • 边界：未做动态故障注入（kill -9 / 断电实测）；结论基于代码语义推演 + 既有单测与知识库（systemPatterns / pitfalls）交叉验证。基线 239082c，落后 origin/develop 1 个提交（仅知识库文档改动，不影响后端代码事实）。
02

数据资产与落盘点

后端真正持久化的自有数据只有三样：state.json（状态）、config.yml（配置，含 Web UI 写回）、以及跳检失败时的 skip-check-backup/*.torrent 备份。其余一切（任务队列、种子快照、分组、校验参考、Web 回执）都是内存态，靠「启动首轮全量同步」从 qB 重建 —— 这是整个安全模型的根基。

03

崩溃场景推演

把「任意时刻终止」拆成十类具体场景，逐类核对最终状态。关键分野：Python 在 Windows 上只有 Ctrl+C（CTRL_C_EVENT）会被转成 KeyboardInterrupt 走优雅路径；控制台窗口直接关闭（CTRL_CLOSE_EVENT）、注销、关机、taskkill /F、断电、原生崩溃都不经过任何 Python 异常 —— finally 不执行，save_state 不发生。

1Ctrl+C（控制台）优雅落盘finally：停 Web → save_state → 释放锁—
2托盘「退出」优雅落盘stop_event 唤醒主循环，≤0.5s 退出；join(5s) 超时则放弃（F6）低
3taskkill /F / 原生崩溃 / OOM不落盘重启全量重建内存态F1：运行期去重/基线全丢

04

发现 F1–F5

F1

状态仅优雅退出时落盘，非优雅终止丢失整个运行期状态

高

save_state() 全库只有两个调用点：主循环 finally（仅优雅退出可达）与跳检备份路径。进程没有注册任何信号处理器，因此「强杀 / 断电 / 关机 / 关闭控制台窗口」这一整类终止都拿不到落盘机会 —— 丢的不是几秒增量，而是本次进程启动以来的全部去重记录、冷却计数与上传基线（02 节后果表）。

# 零命中 —— 无任何 OS 级退出兜底

重放的实际代价有多大：动作插件普遍先查状态再写（加标签先过滤已有、设限速先比对现值、启停先看状态），所以 exec_history 丢失引发的重放大多只是多几次幂等 API 调用。已知有真实代价的重放只有两类：skip_check_day 丢失 → 同日重复跳检（本地统计再丢一次）；reannounce_ts 丢失 → 向站点多发一次 announce。「仅退出落盘」是注释里写明的写入放大规避（减少磁盘写入），属于知情取舍而非疏忽 —— 但以本项目状态变更的真实频率（规则命中/跳检/校验失败，小时级到天级），周期性落盘的写放大代价几乎为零。

F2

热重载 L2 分支重读磁盘 state，把运行期内存态整份回滚 —— 确定性触发，无需崩溃

高

L2 级配置变更（rules_config / interval / delete_tags* / global_speed_limit_curve / tracker 的 domains|rules|groups，且未列出的新配置项默认 L2）会重建任务队列与规则。这一分支在重建前执行了 self.state = self._load_state()：由于 state 平时根本不落盘，磁盘上永远是「上次退出时」的旧版本 —— 这一行等于把本次运行累计的全部状态主动丢弃，与 F1 同量级，但由一次普通的「在 Web UI 改规则并保存」确定性地触发。而 state_file 本身是 R 级（改动需重启进程），运行期磁盘 state 不可能因合法途径变新，这次重读没有任何正向价值。

F3

跳检「删除 → 重加」之间存在无备份崩溃窗口，重启后无任何恢复凭据

中高

跳检流程是四阶段：导出 .torrent（仅进内存）→ 删除种子（保留文件）→ 轮询确认消失（10 × 0.5s）→ 以跳过校验方式重加。备份机制存在且设计得很好（落盘 + 元数据 + 立即 save_state），但它只在「重加失败」的两条路径上触发 —— 删除已生效、重加还没被 qB 接受的缝隙内崩溃，.torrent 字节随进程消失，种子不在 qB 里，文件还在磁盘上，重启后程序对此毫无记忆。用户只能回站点重新下载种子文件。

窗口宽度：从 torrents_delete 发出到 torrents_add 被 qB 接受约 0.5–5.5 秒（被确认轮询主导）。单次跳检崩在缝里的概率小，但跳检是周期性批量行为，长期运行下不可忽略。修复方向明确：把「失败才备份」改成「删除前就备份」，重加确认成功后再清理 —— 备份管线（含立即落盘）现成，只是挪一个调用时机。

F4

state.json 损坏时静默清空；.bak 备份写了却从不用于恢复

中

_load_state 对 JSONDecodeError 静默返回空字典，连一条 WARNING 都没有。原子写已经挡住了「写一半」这个主因（崩溃中的写入只会留下完整的旧文件），但磁盘级损坏、外部工具改写、或旧版本遗留的半截文件仍会走到这条路 —— 后果与 F1 相同（去重全丢、规则重放），却连排查线索都没有。更可惜的是 atomic_write(keep_backup=True) 每次都维护 state.json.bak（上一代内容），而全库没有任何代码读它 —— 恢复凭据一直在盘上，只是没人捡。附带一个小瑕疵：崩溃若发生在 mkstemp 与 os.replace 之间，会残留 state.json.*.tmp 孤儿文件，启动时没有清理。

F5

web.token 生成是非原子写

低

ensure_web_token 用 os.open(O_TRUNC) 直写密钥文件。写到一半被杀会留下半截 token：空文件可自愈（下次启动重新生成），但非空半截会被当作有效密钥持久化，导致鉴权静默漂移（浏览器已存密钥失效，用户需打开 web.token 手工对账）。项目里已有 atomic_write，换成它是一行改动。其余辅助文件（锁 meta、ui.port）损坏无实害，不另立条目。

src/auto_qb/web.py:73-75
fd = os.open(token_file, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)
with os.fdopen(fd, "w", encoding="ascii") as f: f.write(token)
F6

托盘模式：优雅退出超 5 秒即放弃落盘（并入 F1 的崩溃类清单）

低

托盘模式把主循环放进 daemon=True 线程，退出时 join(timeout=5)：若主循环正卡在一次长 qB 调用或长 tick，5 秒内没能走到 finally，线程被放弃，本次运行状态不落盘（原子写保证文件完整性不受损，损失等同于 F1 的单次运行期丢失）。另外 Windows 注销/关机对托盘进程同样不给优雅机会 —— 与 F1 同类，单列仅作提醒。正常路径（托盘菜单退出）实测 ≤0.5s 内退出，风险很低。

07

测试覆盖缺口

现有守阵已覆盖：原子写基础行为与空路径拒绝、run 退出必存状态且为合法 JSON、CLI 捕获 KeyboardInterrupt、配置 .bak 生成与「项目根不散落备份」、save_state 异常吞掉。本次发现的五个点上，以下场景没有守阵，修复时应同步补齐：

  • L2 热重载保态：热重载后断言 exec_history / skip_check_day 保留 —— 对现行为做红验必然变红，是 F2 修复的验收凭据。
  • state 损坏恢复：写入半截 JSON 后启动，断言 WARNING + .bak 回退（F4）。
  • 跳检备份顺序：静态或行为断言「备份文件先于 torrents_delete 存在」（F3；真实崩溃窗口无法在单测模拟，锁顺序即可）。
  • token 写入原子性：改走 atomic_write 后断言无 O_TRUNC 直写残留（F5，可并入静态扫描）。
