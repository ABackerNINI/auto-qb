一句话结论：auto-qb 从来没把「下载器」设计成可替换插槽（全仓 src/ 搜 downloader / client_type / backend_type 零命中），但它恰好在下载器写入点上有一个足够干净的单例收口（core/qbapi.py，49 个端点全在一个文件里）。所以「换一个 HTTP 客户端」这一步便宜得惊人；真正的代价在类型面——TorrentRecord 的 70 个槽名逐字等于 qB 字段名，向上穿透前端、向外穿透用户 YAML 的规则 DSL、向下穿透磁盘持久化键。

值不值得，取决于跳检这一条：它是辅种工具的立身之本，而它在 tr 上从「我说了算」变成「看条件」。

04耦合的形状：集中，还是渗透

两者都是，但在不同层上。这是判断成本的关键。

调用面：高度集中（好消息）

49 个 qB 端点全部收在 src/auto_qb/core/qbapi.py（413 LOC）一个文件的 self._client.* 上。全仓 84 处 api.<method>( 调用分布在 19 个文件，但一律流经这个唯一门面。单看「换一个 HTTP 客户端」，工作量小得惊人。

类型面：全栈渗透（坏消息）

src/auto_qb/torrents/record.py 的 docstring 把设计意图写得毫无歧义：

种子快照记录: 字段名与 TorrentDictionary 一致, 鸭子类型兼容
种子数据的**唯一所有者**(无需中间投影视图) ...
  • 没有翻译层 —— src/ 内不存在任何 torrent 字段的 from_qb / normalize / 投影（同名命中全部与 torrent 无关）。
  • 70 个槽名逐字等于 qB 字段名，哨兵值也是 qB 的（-1=未设、-2=跟随全局、eta=8640000=无 ETA）。
  • 向外穿透到用户契约：rules/expr/env.py:286-292 把 TorrentRecord 的注解自动注册成规则表达式里的 tor.* —— 用户可以在 config.yml 里写 tor.num_seeds > 5。这不是内部耦合，是已发布的对外契约，改字段名即等于破坏存量配置。
  • 向下穿透到持久化：hash 被当稳定全局 ID 用在内存索引、state 的 auto_categories[hash] / skip_check_day[hash]、以及备份文件名 skip-check-backup/<hash>.torrent 三处。

对照组：项目在别的领域其实很会用抽象 —— core/module.py 的 Module(Protocol)、hr/adapters/base.py 的 HrAdapter(ABC)、rules/base.py 的 BaseCondition/BaseAction。唯独下载器没被当成可替换插槽设计过。

08跳检专项：唯一真正需要拍板的一条

辅种工具的立身之本是「同一份数据，换个站的种子文件加进去，不要重新校验几十 GB」。当前实现是 ops_mod.py:401-418 的一次 torrents_add(...)，其中 is_skip_checking=True 是强制的：qB 会把所有 piece 标为有效，立刻开始做种。

tr 4.0+ 的 torrent-added-verify-mode: fast

2023-02 发布的 Transmission 4.0.0 引入该设置（默认 fast）。官方描述的跳过完整校验条件是：

种子有元数据（不是磁力链接）
所有文件都存在
所有文件都不是未完成（.part）文件
所有文件的大小都与 .torrent 中列出的大小相匹配
所有文件的 mtime 都早于添加 torrent 的时刻
第一段通过校验和测试

一个值得注意的对齐：上面第 2、4 条，恰好就是 auto-qb 自己在跳检前做的 filelist 前置检查（ops_mod.py 的「文件存在 + 大小对比」）。也就是说 auto-qb 的跳检闸门与 tr 的跳过条件是同向的——正常情况下条件会满足。

但语义变了：从「我说了算」到「看条件」

维度qB is_skip_checking=Truetr fast 模式
控制点per-add，调用方强制daemon 全局设置（per-add 无覆盖参数）
可控性确定性依赖 3 个前置条件 + 首片校验通过
条件不满足时（不会发生）退化为完整校验 —— 几十 GB 的种子代价极高
坏数据行为全部标有效 → 可能上传垃圾
（auto-qb 用 zSkipChecked 标签排除它作参考种子来兜底）		按片惰性校验 → 坏片在被请求时才暴露，随后重下
更安全，但原种子可能被覆写（cross-seed 社区已报此案例）
用户配置反向干预无用户把 torrent-added-verify-mode 设为 full 即全局失效

这是本报告最实质的一条发现，也修正了「tr 完全不支持跳检」的直觉。tr 4.0+ 不是能力缺失，而是能力不可控：auto-qb 无法在 per-add 层面保证「这次一定跳过」，只能依赖 daemon 全局配置与运行时条件。

对一个以「确定性」为卖点的自动化工具，把核心流程从保证降级为大概率，且失败模式是静默的完整校验（用户体感：辅种完卡住几十分钟到几小时），这是产品层面的风险，不只是工程量。

另注：社区存在 torrent-skip-verify 的第三方 fork（基于 tr 3.0 的补丁，未合流上游）。依赖它等于要求用户换非官方二进制，不在可行范围内。

10建议与重开条件

本轮建议：不做（Dropped 候选）

  1. 核心能力降级不可接受 —— 跳检从确定性变启发式（§08），而跳检正是本项目的价值所在。
  2. 投入产出比最差的一档 —— 38–58 人日换来一个「功能集更弱、可靠性更低」的后端，且永久增加双后端维护税。
  3. 目标用户重叠度低 —— 本项目的使用场景（PT 站辅种 + 规则自动化）在 tr 用户群里需求稀薄；tr 主打轻量与低占用，与「常驻主循环 + 规则引擎 + WebUI」的用法画像本就不重合。

如果一定要做，唯一划算的形态是「最小只读子集」（8–12 人日）：连接 tr、读状态、启停、限速、移动、标签管理，明确不支持跳检与辅种，作为监控/轻量管理入口。这样既不碰 C1/C4/C5 三条硬骨头，也不用付全量维护税。

重开条件（满足任一即重新评估，不必从头调研）

  • tr 上游提供 per-add 的校验控制（RPC 参数或 torrent-skip-verify 合流）—— 直接消除 C1。
  • 出现具体的、可点名的真实用户需求（不是「支持一下更好」），≥1 个愿意参与验收的 tr 用户。
  • 因其它原因要建下载器抽象层（例如未来接 Deluge / libtorrent 直连），届时 tr 的边际成本会大幅下降 —— 这是最值得等的时机。

本报告是快照（report 恒 Done，出厂即冻结）。若上述条件触发，重开时应新建计划文档（plans/）并引用本报告，而不是修改本报告。
