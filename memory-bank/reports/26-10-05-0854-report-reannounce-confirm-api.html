强制汇报确认机制调研: qB / qbittorrent-api 的汇报状态接口

2026-10-05 · 基线 911af7ef (develop) · 目标 qB 5.2.3 (用户实测) · 依赖 qbittorrent-api 2026.8.1 · 档案: memory-bank/tasks/26-10-05-backend-reannounce-confirm.md

§1 结论先行

有 —— 而且 qB 5.2 起就有"准直接"接口。 GET /api/v2/torrents/trackers 自 WebAPI 2.13.0 (qB 5.2.0, PR #23045) 起, 每个 tracker 返回 next_announce / min_announce (单位: Unix epoch 秒) 与 endpoints 明细数组, 外加既有 updating (bool) / status / msg。配合 libtorrent 源码级状态机, 可以把"强制汇报是否真的发生了"做成 持久、2 秒轮询粒度即可判定的证据门控, 不再依赖捕捉半秒抖动。

现判定失准的根因不是"接口缺信号", 而是把 epoch 绝对时间当倒计时用: _confirm_reannounce_result 的核心判据 next_announce < 基线 - 60 在 epoch 语义下方向相反 —— 汇报成功时 next_announce 是前跳(变大)而不是变小, 该判据在成功路径上恒不触发, 于是 30 秒窗口走完只能误报"确认超时"。用户观察到的「下一个 announce 8分钟 → 0 → 回到 8分钟」 恰好是这个机制的直接证据(§2 解码)。

本报告只做调研与可行性结论, 不动代码; 修复方案如需落地, 走后续计划文档。

§2 用户观察解码 (对照 libtorrent 源码)

用户实测(qB 5.2.3 GUI, 中文界面): 投递(下发强制汇报指令)前显示「下一个announce 8分钟, 最小announce 8分钟」, 投递后瞬间显示「0分钟, 0分钟」约半秒, 随后回到「8分钟, 8分钟」。

时刻qB 显示libtorrent 层实际状态 (RC_2_0 源码)
投递前8分钟 / 8分钟 上次 announce 响应以来: next_announce = P + interval, min_announce = P + min_interval (P = 上次响应时刻; 该站 interval ≈ min_interval ≈ 8min)。倒计时显示 = epoch − now。
投递后 ~0.5s0分钟 / 0分钟 announce 请求在途: 发送瞬间 libtorrent 置 updating=true; next_announce = min_announce = now (torrent.cpp L3387-3390) → 倒计时归 0。能走"立即路径"说明此刻 min_interval 已过期 (否则会被推迟到 min_announce 才发, 见 §5)。
之后8分钟 / 8分钟 tracker 响应: next_announce = now + interval, min_announce = now + min_interval, fails = 0, last_error 清空 (torrent.cpp L3621-3627)。

要点: 投递前后的「8分钟」数值相同但含义不同 —— 前者是旧周期计划的剩余量, 后者是本次汇报完成后 重新排期的新计划。GUI 的倒计时显示把两者折叠成同一个数, 这正是"汇报发生了却看不出差别"的观感根源; 而 API 暴露的是 epoch 绝对时间, 前后两个值相差恰好"上次汇报至今的时长", 可拆可测(§7 判据 A)。

§3 现状实现与失效分析

3.1 现状链路 (代码锚点)

  • webui/commands.py:24 — REANNOUNCE_CONFIRM_TIMEOUT = 30.0 (确认窗口, 主循环 main_tick=2s → 约 15 轮确认机会)。
  • commands.py:209 _trackers_baseline — 汇报前逐种子读 torrents/trackers, 排除 ** [DHT] ** / [PeX] / [LSD] 虚拟行, 记 {url: (status, next_announce)}。
  • commands.py:227 _confirm_reannounce_result — 四判据 (下表)。
  • runtime.py:301 check_pending — 每 tick 轮询 torrents_trackers, 全部种子出结论或 30s 超时后聚合写回执。

3.2 四判据 vs 实际机制

判据 (现码)设计假设qB 5.2 epoch 语义下的实际结果
status == 3 → 成功轮询能撞见 updating 态 updating 窗口 ≈ 0.5s (用户实测), 轮询周期 2s → 命中概率 ≈ 0.5/2 = 25% 多数错过
na < b_na − 60 → 成功na 是"秒数倒计时", 汇报后被重置变小 na 是 epoch 绝对时间: 汇报成功时 na 前跳(变大), 本式恒假; 仅当 tracker 返回更短 interval 时才可能为真 成功路径恒不触发 (语义错位)
status==2 ∧ b_status≠2 → 成功tracker 从未联系变 working 对"已在做种(working)"的种子 2→2 无变化 —— 恰是辅种/投递场景的常态 常态场景不触发
status==4 ∧ msg → 失败tracker 拒绝可见 成立: libtorrent 把 tracker 文本放进 message, 状态转 not working, 持久可读 有效 (否定信号)
30s 未出结论 → 失败私站响应 1~10s 若 min_interval 未过期, libtorrent 把强制汇报推迟到 min_announce(可能数分钟后)才发(§5) —— 30s 必超时 "推迟"被误报成"失败"

用户场景(已 working + 立即成功)下, 三条正向判据全部落空 → 恒走 30s 超时 → 误报失败。 这与"经常无法识别"的现象完全吻合。

附注 — 停止种子盲区: libtorrent torrent::force_tracker_request 开头就是 if (is_paused()) return; (torrent.cpp L3900) —— 对停止的种子, torrents/reannounce 返回 HTTP 200 但静默不执行任何汇报。现实现同样要白等 30s 才超时。

G指令受理 torrents/reannounce HTTP 200 全版本正向(弱)— 仅"指令已受理", 无回执语义; 支持可选 urls 参数按 tracker 定向; 停止种子静默 no-op
HqB 主日志 log/main 全版本无— 成功 announce 不产生主日志条目 (libtorrent 的 announce 日志在 debug 级, 不进 log/main; qB 只聚合 warning/error 为 has_*_error 位) —— 无正向信号

§5 libtorrent 机制 (源码级, RC_2_0 = qB 5.2.3 实配)

调用链: WebAPI torrents/reannounce → qB reannounceAction → TorrentImpl::forceReannounce() → lt::force_reannounce(0, index) → torrent::force_tracker_request(now, idx, flags)。

# qB 5.2.3 torrentimpl.cpp L1655 —— 关键: 不带 ignore_min_interval 旗标
void TorrentImpl::forceReannounce(const int index)
{
    m_nativeHandle.force_reannounce(0, index);
}

# libtorrent torrent.cpp L3893 (force_tracker_request)
if (is_paused()) return;                       // 停止种子: 静默 no-op
a.next_announce = (flags & ignore_min_interval)
    ? t + 1s
    : std::max(t, a.min_announce) + 1s;        // qB 无旗标 ⇒ 尊重 min_interval,
                                               // 未过期时推迟到 min_announce 才发
a.min_announce = a.next_announce;              // 两者被拉成同一时刻
a.triggered_manually = true;

# 发送瞬间 (torrent.cpp L3387) —— 用户看到的 0/0 抖动
a.updating = true; a.next_announce = now; a.min_announce = now;

# tracker 响应 (torrent.cpp L3621)
a.next_announce = now + interval;
a.min_announce = now + resp.min_interval;
a.updating = false; a.fails = 0; a.last_error.clear();
a.message = resp.warning_message 或 空串;      // 成功时 msg 干净
  • 两种路径: min_interval 已过期 → 立即发送(0 抖动可见); 未过期 → 推迟到 min_announce + 1s 才发(HTTP 200 已返回, 无任何报错) —— 任何确认机制都必须覆盖推迟路径。
  • 成功响应的可观测变化: next_announce/min_announce 前跳(epoch 持久可读)、 fails 清零、msg 清空、状态回 working —— 但对"本就 working 且 msg 本就为空"的种子, 后两项与汇报前无差别, 唯一持久的正向证据就是 epoch 前跳。
  • 另一个盲区: qB 自身的周期性 announce 到期同样会前跳 next_announce —— 若语义要求"强制触发的汇报", 需结合前跳时刻 ≈ 指令时刻收窄; 若语义是"tracker 侧收到了新鲜汇报" (辅种场景的真实目的), 两者等价(§7 讨论)。

§7 候选判定设计 (供后续拍板, 本轮不实施)

基线 (指令时刻 t0, 逐 real tracker):  status, updating, next_e, min_e

每 tick 轮询 (复用 check_pending 的 30s 级窗口):
  ① 种子 stopped                    → 未发送   (直接出结论, 免白等 30s)
  ② 任一 tracker updating / status 3 → 成功(在途)  — 直接证据, 撞见即收
  ③ 任一 tracker next_e > b.next_e + TOL   → 成功      — 主判据 (epoch 前跳)
     (min_e > b.min_e + TOL 同向佐证)
  ④ 任一 tracker status 4 且 msg 非空      → 失败      — tracker 拒绝, 持久可靠
  ⑤ 窗口走完仍无 ①-④                      → 未确认    — 单列, 不与"失败"混淆

TOL 建议 3~5s: epoch 在两次 announce 之间恒定, 噪声只剩秒级取整;
立即路径的前跳幅度 = 响应时刻 − 上次响应时刻(恒 > 0), 上次汇报越"新鲜"跳幅越小,
故 TOL 不能大 —— 用户"投递后立刻汇报"场景的跳幅可能只有几秒。

窗口建议 max(30s, min_e − t0 + 余量, 上限如 10min):
推迟路径的 announce 在 min_announce 才发, min_e 是 API 直出的预计发送时刻 ——
也可选择直接回"推迟, 预计 HH:MM"回执, 不必干等。

旧 qB (< 5.2.0, 无 epoch 字段): 回退 status/msg/updating + 种子级 reannounce 的
证据门控 —— 成功难证、失败可证, 与 pitfalls/backend/effect-confirmation.md 的
"证据门控"口径一致; 该场景下回执语义建议只承诺"未观测到拒绝"。
  • 语义边界需拍板: qB 周期 announce 到期同样前跳 next_e。"成功"指 (a) 强制指令触发的汇报, 还是 (b) 窗口内 tracker 收到了新鲜汇报? 辅种场景目的上是 (b), 两者在效果上等价; 若取 (a), 用"前跳时刻距指令时刻 < 一个 tick"收窄即可。
  • 规则侧缺口顺带记录: 规则动作 rules/actions/transfer.py 的 ReannounceAction 只有 600s 限频, 没有任何结果确认 —— 若确认器重构, 可复用同一判定函数。
