1摘要

问题（用户命题）
项目里「全局流量」（今日/本月上传下载、历史流量图、按流量分档的自动限速）都来自外部程序 TrafficMonitor 的 history_traffic.dat。用户反馈这份来源信息滞后，希望：① 调研成熟解决方案；② 分析「自写一个独立监视全局流量的小工具」是否可行。
核心结论（一句话）
真正的滞后不在 TrafficMonitor（它 ~30s 落一次盘），而在本项目自己的读侧节拍：全项目只有一处读这个文件 —— 限速曲线任务，它的执行间隔 global_speed_limit_curve.interval 缺省回退主 interval（默认 60s，文档示例给的是 10M=600s），而且「读文件 + 发布 WebUI 快照 + 应用限速」共用同一个节拍。所以「今日流量」在 WebUI 上最多可旧 60s~600s。最高性价比的一步不是另写工具，而是把这个「发布节拍」从「限速应用节拍」里拆出来（方案 1，零依赖、零新进程）。若仍要脱离 TrafficMonitor，则项目里已有 80% 的现成基建（traffic_sample_mod 的 30s 采样 + 活尾 + 聚合分层 + 崩溃恢复），把它升级成「全局流量 provider」远优于另起一个游离进程。
议题结论
滞后到底在哪一层 三层（§3）：L1 TrafficMonitor 落盘 ≤ ~30s；L2 本项目读侧/发布节拍 60s ~ 600s（主因）；L3 WebUI 前端按需拉快照 非瓶颈。前端再快也追不上 L2。
实测复核（本机） 生产 config.yml:90-91 的 global_speed_limit_curve.interval: 10M（config.yml:17 的 interval: 60S 是主循环间隔、不适用）⇒ 顶栏「今日流量」最坏滞后 ≈ 10.5 分钟。用户观测 TM 40GB vs 顶栏 ↓ 31GB（差 9GB）÷ 630s ≈ 15 MB/s，滞后全额解释，无需其他故障（§3.2 实测复核）。
成熟方案有几条路 三条（§4）：A. 复用 qB 自身计数器（项目已实现，30s 采样）；B. 操作系统网卡计数器（Windows IP Helper / PDH / psutil，机器全局含非 qB 流量）；C. 第三方/路由器 SNMP（最准的「整机」，非本机粒度）。
自写独立小工具可行吗 技术可行（高），但「独立进程」不是最优形态（§5）。四种形态里：方案 1（解耦发布节拍，改现有代码）性价比最高；方案 3（复用 qb_traffic 采样器 + provider 抽象）最一致；方案 2（游离小脚本写 TM 兼容文件）能跑但会重造日界/重置/恢复/单实例一整套已解难题。
口径陷阱 「全局流量」有三个互不等价的口径：①整机总量（含所有应用） / ②qB 进程流量 / ③指定网卡流量。TrafficMonitor = ①③ 且按当前选中网卡分账；qB 计数器 = ②。限速曲线的目的决定了该选哪个（§4.4）——这是比「换不换工具」更关键的一步拍板。

2现状界定：项目里的「全局流量」是什么、谁在消费

先把「来源」和「消费方」钉死，后面的滞后链才有落点。

2.1 数据源：一个外部程序拥有的只读文本文件

「全局流量」在本项目里不是一个自有模块，而是一份外部文件：TrafficMonitor（zhongyang219，Windows 任务栏网速/流量悬浮窗）写出的 history_traffic.dat。本程序对它只读，不做任何写入。

  • 路径配置：config.models.GlobalSpeedLimitCurve.dat_path（config/models.py:279-291）—— 注释原样写明「history_traffic.dat 路径(每行 "YYYY/MM/DD <上传KB>/<下载KB>", 单位 KB=1024B)」。
  • 格式与解析：core/curves.py:1-73（首行 lines: "N" 跳过；每行「日期 上传KB/下载KB」；坏行跳过计数；单位 ×1024 转字节）。
  • 用户文档：docs/configuration.md:355-412（明确「目前本软件不支持监控设备全局流量，所以需配置外部流量数据来源」，并给出 TrafficMonitor 的 Gitee/GitHub 链接与取文件路径的操作步骤）。
上游程序写的是什么
TrafficMonitor 的 history_traffic.dat 是「某日已累计上传/下载量」的按日行（当天行随流量增长，跨天重置）——见 curves.py:8 原文。它是日粒度累计，不是时序采样；TrafficMonitor 另有 history_traffic.dat.bak（退出/关机时自动备份）。

3滞后链取证：三层，主因在中间那层

L1 上游 TrafficMonitor（NIC 采样 → 内存聚合 → 落盘 history_traffic.dat）
    ↓ 文件（外部只读）

3.1 L1 — TrafficMonitor 侧：~30s，不是主因

TrafficMonitor 是「内存为主、落盘为界」的设计：实时显示每秒刷新，历史按策略批量落盘。核对 master 源码（TrafficMonitor/TrafficMonitorDlg.cpp，经 grep.app 命中）：

  • 采样节拍：默认 1000ms（选项设置「监控时间间隔」，wiki 原文「默认为1000毫秒」）。
  • 落盘节拍：每 30 秒一次，且仅当「今日累计 KB 变化」才写；写的是增量（SaveTodayOnly：只改首行行数 + 今日行），退出时才 SaveHistoryTrafficFull() 全量。
  • ⇒ 文件本身的滞后 ≤ ~30s，且是日累计（不是时序），对「今日/本月总量」这类消费而言 30s 完全够用。
历史包袱（老版本）
旧版本（如 issue #2269 报告的 v1.85.1）每次保存是整文件逐行重写，行数越多年份越久写放大越严重（用户实测 6 年 ~2000 行「一次保存要刷 2000 次」）。当前 master 已改为增量保存。这不是滞后，但如果你在用的版本较老，文件写入本身会拖慢，值得顺手升级。

自查三步（下次再遇到「对不上」）
  1. 先看对的那个 interval：config.yml 的 global_speed_limit_curve.interval（曲线/发布节拍），不是顶层 interval（主任务节拍）。
  2. 算滞后秒数：(TM 今日下载 − 顶栏 ↓) ÷ 你的实时下载速度；≈ 10.5 分钟即命中本报告的 L2 根因，≈ 30s 量级才需要考虑 L1/口径问题。
  3. 排除口径/字段混淆：TM 的 dat 字段序是 <上传>/<下载>（TM 源码 HistoryTrafficFile.cpp:38-39），与项目解析一致（curves.py:62-72）—— 若顶栏 ↓ 与 TM 的下载对不上、却与 TM 的上传对得上，那才是读数混淆（本轮已排除：用户确认看的是 ↓）。
根因：三个职责被耦合在同一个节拍上
handle_speed_limit_curve 一轮里同时做：①读文件（:140-156）→ ②聚合查档（:158-181）→ ③写 qB 限速（:189-238）→ ④发布快照（_publish_traffic）。
写限速应该慢（10 分钟一次足够、且限速是低频动作）；但发布「今日流量」到 WebUI 完全不需要跟它同频。现在二者共用节拍 ⇒ 用户看到的「今日流量」被限速任务的节奏拖住。

3.3 L3 — WebUI 前端：非瓶颈

历史流量弹层在打开时按需拉 /api/traffic/history（dialogs.js:606），顶栏走主状态轮询；两者拿到的都是 L2 的快照。前端无论多快，快照不更新它就看不到新值 —— 所以调前端轮询没有意义。

4成熟解决方案调研：三条技术路线

「监控全局流量」在 Windows 上有三层可选的数据获取面，粒度、延迟、依赖、口径各不相同。

4.1 路线 A — 复用 qB 自身的计数器 项目已实现

qBittorrent WebAPI 本身就提供累计流量：/api/v2/sync/maindata 的 server_state（alltime_dl / alltime_ul / dl_info_data / up_info_data / dl_info_speed / up_info_speed），以及 /api/v2/transfer/info。

项目里已经有一台「qB 口径全局流量采样器」
core/modules/traffic_sample_mod.py（v4）已经在做这件事，而且做得相当完整：30s 采样（sample_interval 默认 30s）、零新增 qB 请求（读 1.5s 增量同步的 server_state 内存快照）、活尾快照（未落盘数据也能立刻上图）、小时/日/月聚合分层 + 崩溃恢复 + 按龄淘汰，落盘在 qb-traffic-v4/global/，供 /api/traffic/qb/global 十三档窗口消费。
唯一「拦路虎」：QbTraffic.enabled 默认 False（models.py:314，保守默认）—— 要显式打开才有数据。

口径 = qB 进程流量（不含其它应用）；粒度 = 时序（比 TM 的「日累计」信息量大得多）；延迟 = 30s（可配到 1s）。

4.2 路线 B — 操作系统网卡计数器（机器全局）

方案口径/粒度依赖说明
Windows IP Helper API
GetIfTable2 / GetIfEntry2		 逐网卡 64 位累计字节（InOctets/OutOctets） 纯 stdlib（ctypes 调 iphlpapi.dll） 最「零依赖」的整机口径；项目已有 _win_user32 惰性绑定 ctypes 模式可照抄（见 §5 风险）。
性能计数器 PDH
Network Interface\Bytes Received/sec 等		 逐网卡速率/累计 Windows PDH（ctypes） 与任务管理器同源；TrafficMonitor 自身也走类似路径。
psutil.net_io_counters(pernic=True) 逐网卡累计字节 第三方库 psutil 跨平台、API 最省事；nowrap 可处理 32 位回绕。缺点是新增一个依赖。
ETW Microsoft-Windows-Kernel-Network 进程/连接级实时 ETW 消费端（较重） 能做到「哪个进程用了多少」；对「整机总量」是杀鸡用牛刀，实现成本最高。

口径 = 整机（含所有应用），与 TrafficMonitor 同口径；粒度 = 逐网卡累计（需自己差分）；延迟 = 取决于轮询频率（可做到 1s）。

4.3 路线 C — 第三方工具 / 路由器 SNMP

  • 同类替代：NetSpeedMonitor、NetWorx、GlassWire、DU Meter、Sniffnet、ntopng。大多也是「读网卡计数器 + 落一份历史」，换汤不换药 —— 除非它提供更友好的机器可读输出，否则换工具不解决本项目 L2 的滞后。
  • 路由器 / SNMP 侧统计：最准的「全屋/整机」口径（运营商级），但无法区分是哪台机器，对单机自动限速场景不适用；仅当目标是「家庭总带宽」时才考虑。

4.4 三条路线对比（以及一个比选型更重要的拍板）

维度A · qB 计数器B · 网卡计数器C · 第三方/SNMP
覆盖口径仅 qB 进程整机（含所有应用）整机 / 全屋
粒度时序（可出曲线）逐网卡累计日/小时汇总
可达延迟30s（可到 1s）1s（自定轮询）分钟级
新增依赖零（已内建）零（ctypes）或 psutil需装/维护外部程序
跨平台是（qB 在哪它就在哪）需分平台实现是

适合的用途「按 qB 自己的用量自动限速」「按整机用量限速 / 观察非 qB 流量」「看家庭总用量」
必须先拍板：你要的「全局流量」是哪一个口径？
  • 口径①整机总量（TrafficMonitor 现在给的）：含浏览器/视频/系统更新等一切流量。用它驱动「qB 限速」，会出现「别的应用把额度吃光 → qB 被误限速」。
  • 口径②qB 进程流量（qB 计数器给的）：限速的对象就是 qB，用它驱动「qB 限速」语义最自洽 —— 也更符合限速曲线「按已用流量收紧 qB」的初衷。
  • 口径③指定网卡：只在多网卡/分流/VPN 场景才有意义，且要处理「换网卡」的分账问题。
这个口径选择直接决定选哪条路线，比「用不用自写工具」重要得多。

5「自写独立监视全局流量小工具」可行性分析

总判：技术可行（高），但「独立进程」未必是最优形态
自写监视器要解决的「读计数器 → 差分 → 日界聚合 → 落盘 → 崩溃恢复 → 单实例」这一整套，项目里的 traffic_sample_mod 已经全部解决过一遍（v4 采样器）。所以真正的问题不是「能不能写」，而是「写在哪、复用谁」。

5.1 四种落地形态

方案 1 — 解耦「发布节拍」与「限速应用节拍」推荐先行

  • 做法：把 handle_speed_limit_curve 里的「读文件 + 发布快照」拆成独立更快的节拍（如主 tick / 30s），「聚合查档 + 写限速」仍按原 interval 走。
  • 改动面：speed_curve_mod.py 单模块；_publish_traffic 的调用点重排。
  • 收益：直接把「今日流量」滞后从 60s~600s 压到 30s；零新依赖、零新进程、零新配置键。
  • 风险：极低。注意读文件是 I/O，节拍别压到主 tick（2s）级别——30s 已足够且与 TM 的落盘节拍同量级。
  • 代价：不解决「脱离 TrafficMonitor」；仍受 TM 的 30s + 按网卡分账约束。

方案 2 — 独立小脚本，写 TrafficMonitor 兼容文件 能跑但不划算

  • 做法：一个独立进程轮询 qB transfer/info（或网卡计数器），按 TM 格式写 history_traffic.dat（或另写自有文件 + 配 dat_path 指过去）。对项目是零改动（消费者只认路径）。
  • 要自己造的轮子：单实例锁、原子写、日界/时区/时钟回拨、计数器重置与回绕（32 位溢出、网卡重连清零、qB 重启 session 归零）、崩溃窗口与重启恢复。这些 traffic_sample_mod 都已解决（delta/reset 单点、v4 块化批量落盘、_recover_aggregates catch-up）。
  • 结论：作为「脱离主程序」的权宜可以，但会把项目里已收敛的健壮性难题复制到程序外再解一遍，且多一个需要守护的进程。

方案 3 — 把 qb_traffic 采样器升级为「全局流量 provider」 最一致

  • 做法：打开 qb_traffic.enabled，把 qb-traffic-v4/global/ 的日累计导出/暴露成「全局流量源」，让限速曲线与 sys.* 表达式改从这里取数。
  • 改动面：新增一个「从 qb 采样器取当日/当月累计」的读取函数（等价于 curves.aggregate 的口径），改 speed_curve_mod 与 env._traffic 的数据来源。
  • 收益：复用全部既有健壮性基建（30s 采样、活尾、聚合分层、崩溃恢复、按龄淘汰）；口径改为「qB 进程流量」，与限速对象自洽；可彻底不用 TrafficMonitor。
  • 风险：口径变更属语义变更（整机 → qB），需用户明确认可；enabled 默认关，需改默认或在文档里引导开启。

方案 4 — 数据源抽象成多 provider 最贴合既有设计

  • 做法：把配置里的 traffic_source: [traffic_monitor: ...] 抽象成 provider 列表（traffic_monitor / qb / nic / 自写文件），按配置选择与回退。
  • 证据：配置注释已预留演进意图 ——「# 后续可能支持接入其它软件来源」（docs/configuration.md:370）。
  • 收益：一劳永逸，未来接任何源都不用再动消费方。
  • 风险：新配置键必须同步进 validate_config 与 config/schema（黄金法则 4，守卫测试会查），改动面最大。

5.2 可行性的硬约束清单（无论选哪个方案都要面对）

约束说明项目里已有的对策
口径必须显式定义qB / 整机 / 网卡三者不等价（§4.4）。需新增文档口径段；config-reference/keys.md 补注。
计数器重置/回绕32 位溢出、网卡重连清零、qB 重启 session 归零（alltime 不归零）。traffic_sample_mod._delta（判重置记 null）+ v4 块内负 delta 校验。
日界 / 时区 / 时钟回拨按本地日 00:00 重置累计。v4_day_epoch / v4_epoch_date_str + 跨天硬切块。
崩溃窗口与持久化TM 是内存先聚合；自写必须落盘 + 重启恢复。flush_interval 批量落盘 + _recover_aggregates catch-up。
单实例 / 单写线程不引入并发写（黄金法则 5）。采样 handler 在主循环线程执行，单引用快照发布给 Web 线程只读。
幂等 / 去重重复执行无副作用（黄金法则 1）。活尾与 flush 按 ts 精确去重、解析按同 epoch 取末行。
新配置键的校验缺 validate_config/schema 即守卫红（黄金法则 4）。照现有 QbTraffic 的注册路径补。
Windows 专属实现IP Helper / PDH 是 Windows-only。项目已有 _win_user32 惰性绑定 + is_windows() 早退模式可照抄。

6结论与建议路线

6.1 一句话结论

滞后主因是「本项目读侧节拍」，不是 TrafficMonitor
TrafficMonitor 的文件 ~30s 就刷新一次，够快；真正拖住「今日流量/历史流量」的是本项目把「读文件 + 发布快照」和「写限速」绑在了同一个 60s~600s 的任务节拍上。所以先做方案 1（解耦发布节拍）——改一个模块、零新依赖，就能把滞后压到 ~30s。若还想要「脱离 TrafficMonitor + 更细粒度」，再做方案 3/4（复用 qb_traffic 采样器 + provider 抽象），而不是另起一个游离进程。

6.2 建议路线（按性价比排序）

  1. 第 0 步（先拍板口径）：确认「全局流量」要的是整机总量还是 qB 进程流量。这一步决定后面选 A 还是 B。
  2. 第 1 步（立竿见影）：方案 1 —— 解耦 speed_curve_mod 的发布节拍。预期：今日流量滞后 600s → ~30s。
  3. 第 2 步（若仍要脱离 TM）：方案 3/4 —— 打开 qb_traffic，加 provider 抽象，让限速曲线/表达式改从 qB 采样器取数；traffic_monitor 降为可选 provider。
  4. 第 3 步（仅当必须整机口径且不要 TM）：在 traffic_sample_mod 同构地加一个「网卡计数器系列」（走 §4.2 的 IP Helper / psutil），复用其日界/重置/恢复基建。
  5. 顺带：若在用的 TrafficMonitor 是旧版（整文件重写），升级到最新版（增量保存）以减轻写放大；并核对「当前选中网卡」是否就是你希望统计的那张（§3.4）。

6.3 验收要点（若拍板实施）

  • 「今日流量」在 WebUI 顶栏的刷新滞后实测 ≤ ~30s（可用 TrafficMonitor 的今日行做对照）。
  • 限速「应用」节拍保持不变（不因拆节拍而提高写 qB 的频率 —— 黄金法则 2 保守默认）。
  • 口径变更（若走方案 3）需在 docs/configuration.md 与 config-reference/keys.md 显式写明「全局流量 = qB 进程口径」，并同步 validate_config/schema。
  • 新配置键（若走方案 4）必须过守卫测试；不新增绕开单写线程的并发路径。
