文件丢失+设定位置恢复机制验证

「文件丢失」状态 +「设定位置」可以零哈希、零代码改动地恢复辅种组整组迁移后的进度 —— 该路径是 qBittorrent 源码里设计好的恢复机制(注释原文 // it can be moved to the proper location)，唯一限制是必须先经一次重启让种子进入「文件丢失」；免重启的等价方案另见专题报告。

来源 用户提问「分析 qb/libtorrent 源码: 什么情况下种子会进入"文件丢失"状态」及其延伸需求「用文件丢失+设定位置实现无痛整组移动」; 对象 = D:\Projects\Else\qBittorrent(master) + D:\Projects\Else\libtorrent(2.x)

§01结论

问题定义

辅种组内多个种子共享同一份文件树(同内容、不同 tracker)。整组从盘 A 迁到盘 B 时, 用 qBittorrent「设定位置」逐个迁移: move_storage 以 dont_replace 执行, 组内第一个种子真正搬文件并保留进度, 其余种子发现目标已有同名文件 → libtorrent 返回 need_full_check → force_recheck() → 进度瞬间清零, 靠重新校验才能找回。现有两条恢复路径都有代价: 强制检查(全量重算 hash, TB 级组小时级耗时且挤占 hashing 线程)与跳检(不校验直接信任, 错内容会长期以讹传讹)。

结论(TL;DR)

维度结论
机制是否成立成立。这正是 qBittorrent 源码里"设计好的"恢复路径, 不是 hack
是否需改代码不需要。现有 GUI(多选右键 Set location...)与 WebAPI(/api/v2/torrents/setLocation, hashes=a|b|c 批量)即可完成
恢复代价接近零: libtorrent 只做 stat + 文件大小比对, 通过后直接把旧进度位图逐块 we_have(), 不重算任何 hash; 本质是"带校验的跳检"
主要限制① 必须先让种子进入「文件丢失」, 该状态只能通过"重启 qBittorrent 且文件不在原路径"产生(运行中删文件只进 Error 状态, 不置该标志); ② 未完成且启用了「未完整文件目录」的种子不吃这条路径
主要风险resume data 时效(完成态辅种无此问题)、reload 期间断连重连、旧 handle 上有竞争的冗余 force_recheck、内容 hash 仍不被校验(同跳检, 但多一层大小/存在性护栏)

一句话: 按"暂停整组 → 退出 → 一次 mv 整组目录 → 启动 → 批量设定位置 → 启动"的 SOP 使用, 立刻获得比强制检查省掉全量 re-hash、比跳检多一层文件校验的恢复效果; 若要免重启, 需自写工具或给 qBittorrent 打补丁(见下文产品化方向与专题报告)。

推荐操作流(零代码改动)

以"辅种组共享同一目录"为例; 各成员独立目录的组同理, 按种子逐个设定各自的新路径。

步骤操作源码依据 / 说明
1多选整组 → 暂停stop() → deferredRequestResumeData() 立即刷新进度位图落盘(torrentimpl.cpp:2014-2020)
2退出 qBittorrent(托盘完全退出)~SessionImpl flush 全部 resume data(sessionimpl.cpp:777、3369-3380)
3操作系统层面一次 mv 整组共享目录到新位置只搬一次; 组内种子的相对路径不变
4启动 qBittorrent组内种子 resume data 校验失败 → 全部进入「文件丢失」并自动暂停; 全量校验快速失败(成本≈0, 见 §02)
5多选整组 → 右键 Set location... → 新路径(目录须已存在, GUI 有此检查; WebAPI 会自动创建)transferlistwidget.cpp:360-361; 批次内串行处理
6每个种子串行 reload: 旧位置无文件可搬 → 新位置校验通过 → 进度恢复见 §02.4/§02.5
7多选整组 → 开始恢复正常做种; 断开的 peer/tracker 自动重连

验收标准: 步骤 6 后列表中种子直接显示原进度(如 100% / Seeding), 无 Checking 状态; 日志无 fastresume data rejected 复现; qBittorrent 日志出现 Failed to restore torrent...(WARNING, 步骤 4 的预期日志, sessionimpl.cpp:6905-6906)。建议先拿 2–3 个小体积(<1GB)辅种走一遍再推广。

三种方案量化对比(1 TB 辅种组参照)

维度强制检查跳检(no verify)文件丢失 + 设定位置
磁盘读全量 1 TB00(仅 stat 元数据)
CPU全量 SHA1/v2 hash(数十分钟~小时级)00(仅比对文件大小)
恢复耗时小时级, 取决于盘速/CPU/队列位置秒级秒级~分钟级(N 个种子串行 reload; 小 group 通常 <1 min)
数据可信度校验后完全可信完全信任, 错内容不自知存在性 + 大小校验; 内容不校验
额外成本挤占 hashing 线程无需重启 qBittorrent; reload 断连重连
失败模式耗时而已静默错误(最危险)安全失败: 校验不过则保持「文件丢失」, 进度位图不丢, 可重试

结论: 本方案耗时对齐跳检、安全性介于两者之间且失败模式安全, 唯一实质代价是重启窗口。辅种组"文件必为字节级副本"的前提由辅种机制本身保证, 因此该方案实际风险≈0。

产品化 / 自动化方向

  1. 免重启的脚本化方案: 基于 libtorrent API 直连完成 reload 语义(save_resume_data → mv → remove+add), 绕过「文件丢失」状态与重启, 适合 auto-qb 这类自动化工具编排 —— 完整研究见 memory-bank/reports/26-10-18-0818-report-group-relocate-restart-free.html。
  2. qBittorrent 补丁候选(按收益排序): setSavePath 的 else 分支也接 reload(覆盖 §02.6 场景); 「文件丢失」状态下 set-location 跳过 move_storage; 新增"批量 relocate(保留进度)"RPC。
  3. 可观测性: 为批量 setLocation 增加进度/失败反馈(当前 WebAPI 静默执行、move 队列串行无进度上报)。

§02证据快照

2.1 背景: 普通整组移动为什么清零

aux::move_storage(libtorrent/src/storage_utils.cpp):

// :123-127
if (flags == move_flags_t::dont_replace && exists(new_path, ignore, dont_follow_links))
{
    ret |= disk_status::need_full_check;   // 目标已有文件 → 不搬, 要求全量校验
    continue;
}

torrent::on_storage_moved(libtorrent/src/torrent.cpp:9365-9390):

if (status & disk_status::need_full_check)
    force_recheck();   // → set_have_all(false) + start_checking() 全量校验

qBittorrent「设定位置」= ChangeSavePath → KeepExistingFiles → dont_replace(sessionimpl.cpp:342-356、torrentimpl.cpp:2085-2087)。因此组内第 2..N 个种子全部触发全量校验 —— 与观察到的"大部分进度被重置为 0"完全吻合。

2.2 「文件丢失」状态如何进入

唯一入口: torrent::on_resume_data_checked(torrent.cpp:2301-2317)判定

(error || status & (fatal_disk_error | need_full_check | file_exist))
    && contains_resume_data(*m_add_torrent_params)   // have_pieces 非空或 seed_mode

→ 发 fastresume_rejected_alert → SessionImpl::handleFastResumeRejectedAlert(sessionimpl.cpp:6898-6906)→ TorrentImpl::handleFastResumeRejected()(torrentimpl.cpp:2353-2357)置 m_hasMissingFiles = true。updateState() 中「文件丢失」优先于 Error 展示(torrentimpl.cpp:1299-1306)。

关键推论: 该 alert 只在种子带着 resume data 被(重新)添加时才会发。运行中删文件只产生 file_error_alert(Error 状态), 不置该标志。因此进入「文件丢失」的现实路径只有: 退出 qBittorrent → 文件被移走 → 重启(重启时每个种子都从 .fastresume 读入 have_pieces 再添加: bencoderesumedatastorage.cpp:309 lt::read_resume_data() → m_ltAddTorrentParams, torrentimpl.cpp:329)。

2.3 关键一: 进度位图在「文件丢失」期间被强制保留

libtorrent 拒绝 resume data 后会做一次全量校验(找不回任何块, 因为文件没了), 并向 qBittorrent 上报空进度。若直接落盘, 旧进度就丢了。qBittorrent 用 needPreserveProgress 专门防这个(torrentimpl.cpp:2296-2320, prepareResumeData):

const bool needPreserveProgress = m_hasMissingFiles
        || (!m_ltAddTorrentParams.have_pieces.empty() && params.have_pieces.empty());
...
m_ltAddTorrentParams = std::move(params);
if (needPreserveProgress)      // 用旧位图覆盖 libtorrent 上报的空/低进度
    m_ltAddTorrentParams.have_pieces = std::move(havePieces);

即: 只要处于「文件丢失」状态, 内存和磁盘上的 resume data 永远保留迁移前的进度位图, 可反复重试。这是整个方案成立的核心一环。

2.5 附: 「文件丢失」窗口期的行为(安全性)

  • 重启后全量校验面对的是"不存在的文件": initialize_storage 只会创建"本就应为 0 字节"的目标文件(storage_utils.cpp:712-745), 非零大小的缺失文件不会被创建; checking 读失败很快。
  • 首个失败块即触发 handle_disk_error → set_error + pause()(torrent.cpp:4517-4543、1204-1207): 种子的 libtorrent 句柄自动暂停, 不会在旧路径重新下载垃圾。qBittorrent 侧 UI 仍显示「文件丢失」(优先于 Error)。
  • 因此窗口期即使不手动暂停也基本安全; 但暂停整组仍是推荐动作, 原因见 §02.6.1(resume data 时效)。正常退出时 ~SessionImpl() 会 saveResumeData()(only_if_modified)flush(sessionimpl.cpp:777、3369-3380)。

2.6 风险与边界条件(逐条, 均已对照源码确认)

2.6.1 resume data 时效(仅影响未完成种子)

  • 周期保存间隔默认 60 分钟(sessionimpl.cpp:589、1773-1780)。
  • 完成态辅种(have_pieces 全置位)不受影响 —— 位图不会变。
  • 未完成种子: 上次保存后新完成的块会被遗忘 → 那几个块重下。缓解: 步骤 1 暂停会立即落盘(stop() → deferredRequestResumeData), 正常退出也会 flush。

2.6.2 内容可信度

  • 恢复过程不校验内容 hash(与跳检同等风险)。但比裸跳检多两层护栏: seed 情形校验每个文件大小、非 seed 情形校验已完成块覆盖文件的存在性。
  • 辅种场景(同内容字节级相同)可接受; "假辅种"(不同 release)会在 seed 情形被大小校验安全拦下, 保持「文件丢失」而不假恢复。

2.6.3 未完成 + 启用「未完整文件目录」的种子不吃此路径

TorrentImpl::setSavePath 分支(torrentimpl.cpp:523-532):

if (isFinished() || m_hasFinishedStatus || downloadPath().isEmpty())
    moveStorage(...);      // ← 才有 reload 恢复
else { m_savePath = resolvedPath; ... }   // 只改内存路径, 不 reload!

未完成且配置了独立下载目录的种子走 else 分支, 不会触发恢复。处理: 这类种子要么不放进整组迁移, 要么迁后单独 forceRecheck / 重启。

2.6.4 reload 的固有副作用

  • remove_torrent + add_torrent → 断连重连、tracker 重新 announce、DHT/PeX 重新发现。大批量时有短暂 swarm 扰动, 远小于全量校验。
  • 保留项: 队列位置(reload 内 queue_position_set, torrentimpl.cpp:1991-1993)、暂停/强制状态(1972-1984)、分类/标签/共享限制(TorrentImpl 对象本身不重建, 只换 native handle)。
  • reloadTorrent 用 delete_partfile: 使用 partfile(优先级 0 文件)的种子会丢未完成块记录; 完成态辅种无 partfile, 无影响。

2.6.5 旧 handle 上冗余的 force_recheck(有界损耗)

「设定位置」时 move_storage 因"目标已有文件"返回 need_full_check → on_storage_moved → force_recheck() 在旧 handle 上启动(torrent.cpp:9381)。紧接着 reload 的 remove_torrent 会置 m_abort, 使 on_force_recheck 早退(torrent.cpp:2544)。libtorrent 与 Qt 事件循环在同一线程(qBittorrent 无独立 session 线程), 正常情况下 reload 胜出、不会真的全量校验; 极端磁盘繁忙下可能有少量 in-flight 校验作业后被取消。属有界损耗, 非全量 re-hash。

2.6.6 其他

  • 组内成员 save_path 不一致: 逐个人工/脚本设置各自新路径即可, 机制相同。
  • AutoTMM 种子: GUI/WebAPI 会先 setAutoTMMEnabled(false), 无需手工处理。
  • 硬链接/类似种子(mutable torrent): verify_resume_data 重建链接且强制全量校验(storage_utils.cpp:506-548、590), 本方案不适用。
  • 迁移必须一次搬净: 旧位置残留文件会让启动全量校验把"残留部分"计为真实进度; m_hasMissingFiles 期间 prepareResumeData 仍强制保留旧位图(needPreserveProgress 恒真), 不会被冲掉, 但为干净起见建议搬净。
