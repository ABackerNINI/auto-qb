04失败原因 A：落盘时机错位（与多标签无关，单标签也会丢）

这是本轮实证最有价值的发现。materializeColumns() 只改内存、从不写存储；而 6 个 saveColState() 调用点里有 3 个是"先存、再算" —— 落盘的是实体化之前的内存值。

实测 V1：隐藏一列之后，内存 colWidths.group 有 12 个键，而 localStorage 里 widths.group 是 undefined。存储与内存长期漂移，谁下一次落盘，谁就把自己那份（可能是空值/旧值）写进去。

// columns.js —— 顺序不一致的 6 个调用点
373  toggleColumn          : saveColState(page)  → $nextTick(materializeColumns)   ❌ 先存后算
382  resetAllColumnWidths  : saveColState(page)  → $nextTick(materializeColumns)   ❌ 先存后算
495  applyColOrder         : saveColState(page)  → $nextTick(materializeColumns)   ❌ 先存后算

392  fitColumnsToWindow    : materializeColumns → manual=true → saveColState(page)  ✅ 先算后存
433  startResize (up)      : 拖拽中已改 colWidths → manual=true → saveColState(page) ✅ 先算后存
464  autoFitColumn         : 改 colWidths → manual=true → saveColState(page)         ✅ 先算后存

用户侧表现：只调过显隐 / 拖过列序、没拖过宽度的页，colManual 一直为 false ⇒ 存储里的 widths 段长期是空或旧值 ⇒ 任何一次刷新都重新自适应 ⇒ 用户感觉"宽度时不时就回到默认"。这条通道单标签也会发生，第四轮修复完全没碰它。

次生：隐藏列的宽度记录被抹除。_renderedWidths() 只记录可见列的渲染宽度 ⇒ 隐藏列的 px 从内存、进而从存储中消失（S4 实测 11→10）⇒ 再显示时该列只能拿 templateMinPx 兜底。用户看到的就是"这列宽度被重置了"。

05失败原因 B：修复把成败全押在 F2 上，而真机的关键变量没被覆盖

F1 是 page 级整段替换，不是逐项合并 —— 这一点代码注释自己承认了：

// columns.js:322-324（原注释）
 *   (单独靠这招不够: 两个标签改**同一个表**时仍然后写赢 —— 真正的解法是 F2 的 storage 同步,
 *    让每个标签的内存保持新鲜; 这里挡的是"同一毫秒两边都写"的竞态。)

也就是说：F2 一旦不生效，F1 就退化成"同 page 后写赢"，等于没修。而 F2 只在"同浏览器进程 + 同 origin + 事件未被节流"三个条件同时成立时才可靠。

B1 · origin 隔离 已实测确认

用户说过"平时用固定地址打开"。但"固定地址"不等于"同一个 origin"。实测（同一 context、同一服务，仅主机名不同）：
对照组（两 page 均为 127.0.0.1:8099）→ p2 读到 hidden.group = ["size"] 共享，证明实验方法有效；
实验组（127.0.0.1 vs localhost）→ q2 读到 (空) 完全隔离，且 q2 自己改列也不影响 q1。

即：127.0.0.1 / localhost / 换过端口的地址，在 localStorage 眼里是互不相通的站点，各存各的、永不同步。用户在 A 地址调好的列，从 B 地址打开时看到的是"B 自己的旧偏好" —— 主观感受就是"又被重置了"，而且F1/F2/F3 全都够不着（不是时序问题，是两个世界）。

项目自己的知识库早就记了这条限制（activeContext.md「第十轮两处已知限制 ①」）。第四轮修复既没有处理它，也没有实测排除它 —— issue 报告里只写了一句"基本排除"。本轮把它从"待取证"变成了已确认的机制。

⚠ 过程中先跑了一版无效实验：给两个标签各建一个 browser.newContext()，而 Playwright 的 context 本身就隔离 localStorage —— 那样验出来的是"context 隔离"，与主机名无关。加对照组后重做才得到有效结论。没有对照组的隔离实验不能采信。

B2 · F3 补漏有盲区

visibilitychange 的 adopt 只在"隐藏 → 可见"时触发。用户把两个窗口并排摆放时两个都可见 ⇒ F3 永不触发，防线只剩 F2 一条。后台标签被浏览器冻结/丢弃时同理。

B3 · 冒烟守阵验不出这些

scripts/ui_smoke.cjs:843-868 的断言是：标签 1 内存的 colHidden.group ≥ 2 项，两个标签固定 waitForTimeout(600)。它在本机可靠环境下必然绿，但验不出：origin 隔离、后台节流、异宽窗口、以及 04 节的落盘漂移。守阵绿 ≠ 通道封住。

只有宽度跳变，显隐与列序不丢 —— 与用户"栏的顺序、显示、宽度经常被重置"的描述吻合：宽度是唯一受伤的那一项。

修法（写侧 + 读侧，各 1 行）

// ① shared/columns.js :: saveColState(page) —— 写侧: 非手动页不落 px
if (!this.colManual[page]) payload.widths = { ...payload.widths, [page]: {} };

// ② shared/app.js :: loadColState() —— 读侧: 非手动页不读 px(与 ① 成对)
if (!out.manual[page]) out.widths[page] = {};
② 不是可选项。只改写侧的话，浏览器里已经存在的污染 px（修复前被别的窗口写进去的）仍会被读出来，刷新后看到的还是旧值 —— 修复会"看起来没生效"。读侧一并清空，改完刷新即见效。

manual=false 时 colWidths[page] 是 materializeColumns 按当前窗口算出的自适应快照，不是用户偏好。落盘会 ① 把弹性模板固化成固定 px，该页不再随窗口自适应；② 被别的窗口算出的值整段覆盖。不落盘 ⇒ 保持弹性、各窗口各算各的；想固定宽度就拖一下（拖即置 manual=true，此后受保护）。

⚠ 光把"先存后算"改成"先算后存"是不够的 —— 顺序改了，存储拿到的仍是"最后操作的那个窗口算出的值"，照样换主人。真正的根治点是不落不该落的 px。

09下一步建议（按性价比排序）

  1. 先做一个 10 秒自查，别先改码：B1 的机制已实测确认存在（同 context 下 127.0.0.1 与 localhost 完全隔离），剩下只需确认你是否踩到它 —— 在"又重置了"的那一刻，比对两次打开的地址栏字符串（主机名 + 端口）是否完全一致。不一致则一切跨标签同步都是徒劳，先统一入口地址；一致则问题落在 04 节的落盘错位上。
  2. 统一 save / materialize 顺序（本轮证据最硬，优先做）：把 3 处"先存后算"（columns.js:373 / 382 / 495）收敛为"先 materialize 后 save"，或让 materializeColumns() 在 colManual 为假时也落盘。直接关掉 04 节那条通道 —— M1 的"内存 12 键 / 存储 0 键"就是它造成的。
  3. 隐藏列宽度保留：_renderedWidths() 只取可见列是抹除的根因，改为"以已有 colWidths[page] 为底、只覆盖可见列"，隐藏列的 px 就不会丢。
  4. F1 升级：从 page 级整段替换改为逐列/逐段时间戳合并，让 F2 失效时也不至于整段吞掉 —— 代价是要给存储结构加"谁更新"的语义，需权衡是否值得。
  5. 守阵补档：冒烟加两档 —— ① 两个标签用不同视口；② 一个标签走 page.evaluate 模拟后台冻结后恢复。现有的 600ms 固定等待不足以钉住真机时序。
  6. origin 自诊断（可选）：把当前 origin 一并写进存储，加载时比对不一致则在界面上提示一次，把"看不见的隔离"变成可见。
