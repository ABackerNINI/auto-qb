01结论速览

Verdict

用户方案成立, 且是当前性价比最高的第一步 —— 建议按它落地。「有未保存改动就弹确认框」= 业界方案 S1(原生 beforeunload 条件守卫), 是 MDN 与 Chrome 官方点名的 beforeunload 唯一合法用法; 「刷新后清零」= 明确不做草稿恢复, 这一取舍在本项目是对的选择(见 §6: 自动落盘会触发热重载, 整树存 Web Storage 会把 qbittorrent.password 摆上 XSS 面)。

它把「静默丢」变成「知情丢」, 但不减少重做量 —— 这是它唯一、也是被明确接受的代价。

草稿恢复(S3)是唯一能覆盖「崩溃 / 标签被系统回收」的机制, 但会引入三类新问题(分叉语义 · 敏感字段 · 幽灵草稿), 建议先不排, 等真的丢过一次再升级。

一个必须先说清的技术边界: 「弹确认框」若要求覆盖全部重载路径, 那就只能是浏览器原生框 —— 文案不可控、只有「留下 / 离开」两个选项。想弹自绘框(可写中文、可加「保存并刷新」), 只能拦住键盘 F5 / Ctrl+R, 拦不住地址栏回车 / 关标签 / 后退 —— 那几条还得靠原生框兜底, 于是两套框并存。详见 §4。

03成熟方案谱系

业界对「未保存改动」的解法按机制分只有五类, 差别全在「能看见哪些离开方式」与「改动是保住还是只提醒」。

S1 · 原生 beforeunload 条件守卫(文档级离开)

官方定义的标准用法: 只在 dirty 时挂监听, 保存后立刻摘掉。Chrome 与 MDN 都明确「不要无条件挂」—— 文案只显示浏览器通用串(防钓鱼), 且需要 sticky activation(页面有过用户交互才弹)。
覆盖: 刷新 / 关标签 / 地址栏 / 后退(真实导航) · 不覆盖: 崩溃、后台标签被系统回收、移动端不可靠

const h = (e) => { e.preventDefault(); e.returnValue = ""; };
// dirty 变 true: addEventListener("beforeunload", h)
// 保存成功 / 放弃后: removeEventListener("beforeunload", h)

S2 · 页内路由 / 导航守卫(SPA 内部离开)

Angular CanDeactivate · Vue onBeforeRouteLeave · React Router useBlocker: 客户端路由跳转时弹自绘框, 可写具体文案、可给「保存并继续 / 放弃 / 留下」三选项。
本项目不适用 —— 无客户端路由, 页面切换不产生导航(见 §2)。业界共识是「S1 + S2 都要」, 但前提是真有路由; 这里第二条不存在, 反而省了一层。

S3 · 浏览器侧草稿自动保存 + 恢复提示条

debounce 写入 Web Storage, 加载时若有草稿则显式询问「恢复 / 丢弃」。业界唯一能覆盖「崩溃 / 标签被回收」的机制 —— 那两类场景任何弹框都救不了。 载体选取有明确共识: sessionStorage 优于 localStorage —— 按标签隔离, 天然避免多标签互相覆盖陈旧草稿; 保存成功后必须立即删键, 否则会出现「一小时前的旧草稿提示恢复」的幽灵。
代价: 引入「内存版 vs 磁盘版」分叉语义 · 需 schema 指纹 / TTL / 形状校验 · 敏感字段暴露面 · 恢复 UI 与判据

S4 · 服务端草稿 / 自动落盘(autosave to server)

本项目不适用, 且危险。 PUT /api/config 会立即落盘并触发后端热重载 —— 编辑器里的「半截值」(端口改了一半、密码填了三个字符)会被当成真配置应用。文本编辑器那套 autosave 语义在配置页上是反的: 文档的中间态无害, 配置的中间态会改变程序行为。

S5 · 字段级即时生效(「无保存按钮」范式)

VS Code 设置 / macOS 系统设置式: 改一个字段立刻写一个字段。彻底消灭「未保存」这个概念, 但要求后端有单字段 PATCH + 单字段校验; 本项目是整树 PUT + 保存后热重载, 逐字段改写会变成逐字段热重载, 成本与风险都高。

S6 · 版本 / 冲突检测(正交)

ETag / If-Match / revision: 保存时校验服务端配置是否被别处改过。它防的是另一件事(磁盘被手工编辑 / 另一标签改过导致覆盖), 与本案不冲突但也不替代本案, 可作为后续独立议题。

04用户方案拆解

「有设置未保存刷新时弹出确认框, 刷新后设置重置改动清零」其实是两个独立的决定, 前半句有两条互斥的实现路线, 必须分开选:

决定一: 框用哪一种

路线能拦住的拦不住的代价
U1-a 原生 beforeunloadF5 / Ctrl+R / 地址栏回车 / 关标签 / 后退 —— 全部真实导航崩溃 · 后台标签被回收 · 部分移动端(根本不触发)文案是浏览器通用串, 不可定制; 只有「留下 / 离开」两选项; 需页面有过交互才弹
U1-b 自绘框(拦 F5 / Ctrl+R 键)键盘触发的刷新(keydown 里 preventDefault)地址栏回车 · 关标签 · 后退 · 崩溃可写中文、可给「保存并刷新」; 但其余路径仍需原生框兜底 ⇒ 两套框并存、文案与体验不一致
关键事实: JS 无法用自绘 modal 取消真实导航 —— 唯一能取消导航的钩子就是 beforeunload 原生框。所以「全覆盖」与「自定义文案」在这个场景里不可兼得, 只能二选一或双框并存。

决定二: 刷新后改动清零(不做草稿恢复)

这就是现状行为(cfgLoad() 用服务端树整体替换, 并重置 baseline), 只是把它从「静默发生」变成「用户点了离开之后发生」。语义极简: 要么你保存了, 要么它没存在过 —— 没有第三种「半存在」的状态。

  • 得到的: 无分叉语义(不需要定义"内存版 vs 磁盘版"谁赢) · 无陈旧草稿幽灵 · 不把密码等敏感字段写进 Web Storage · 与现成判据 cfgDirty 完全一致(单一判据, 零新增状态机)。
  • 失去的: 崩溃 / 标签被回收 / 误点「离开」这三类仍要重做。前两类本来就超出弹框能力, 第三类是用户自己做的决定 —— 从「被偷走」变成「知情放弃」, 这正是本方案要买的东西。

06代价与风险清单

  • 敏感字段(只针对 S3): 配置树含 qbittorrent.password 与 web 凭据。业界对 Web Storage 的硬性纪律是「不存密码 / token / 支付信息」—— XSS 可读。若将来做草稿, 必须只存相对 baseline 的字段级 diff 并剔除敏感路径, 不能整树 JSON.stringify 丢进去。(U1-a 不写任何存储, 天然免疫。)
  • 弹框疲劳(只针对弹框类): 长期被无意义确认框训练过的用户会闭眼点「离开」。缓解: 严格只在 cfgDirty 为真时挂载(而不是常驻), 且只在设置页 —— 脏标记本身已经是全树精确对比, 不会误触发。
  • bfcache 与移动端: Firefox 不会把带 beforeunload 监听的页面放进 bfcache; Chrome 移动端在标签被回收时不触发。本项目是单页 SPA, 前后退基本是离开站点, bfcache 影响可忽略; 移动端不可靠属于浏览器策略, 无法绕开 —— 接受即可。
  • 双框不一致(只针对 U1-b): 键盘刷新走自绘、其余路径走原生, 同一动作两种观感, 且自绘框里的「保存并刷新」在原生路径上不存在。这是 U1-b 最实的代价。
  • 幽灵草稿(只针对 S3): 保存成功后不删键, 下次刷新会提示恢复一个早就写进磁盘的旧版本; 多标签下 localStorage 还会互相覆盖(sessionStorage 按标签隔离可规避)。

07推荐落地路径

  1. 第一步(本次拍板后即做): U1-a + 清零。 在设置页且 cfgDirty 为真时挂 beforeunload(preventDefault() + returnValue = ""), cfgSave() 成功与 cfgDiscard() 之后摘除; 退出 / 登出(cfgReset())一并摘除。退出码零副作用, 可独立验证。
  2. 同步补一条现状说明: 原生框文案不可定制是浏览器策略, 中文说明放在页面上(现有的「有改动还没保存」指示已经在做), 而不是指望弹框里写字。
  3. 第二步(有条件才做): S3-lite。 触发条件 = 真的丢过一次改动(用户或日志可证)。三条硬约束: ① 只存 diff, 剔除敏感路径; ② 带 schema 指纹 + TTL, 形状不符即丢弃; ③ 恢复必须显式确认, 保存成功后立即删键。
  4. 不做的: S4(半截配置落盘 + 热重载)、S5(后端不支持且会逐字段热重载)。S6 若要做, 单开议题。

守阵建议: 前端守卫测试沿用既有 tests/ 前端守阵的写法(静态断言为主) —— 断言「存在 beforeunload 挂载点」与「dirty 假时不挂」, 不必起真浏览器。

09参考来源

取证 2026-10-02, 均为厂商 / 规范一手或权威二手:

  • MDN — Window: beforeunload event: 只显示浏览器通用串; 需 sticky activation; 移动端不可靠; Firefox 下与 bfcache 不兼容; 建议只在有未保存改动时挂、保存后摘。
  • Chrome — Page Lifecycle API: 明确「不要无条件加 beforeunload 监听, 也不要把它当会话结束信号」; visibilitychange 才是可靠的最后保存时机。
  • Chrome — Deprecating the unload event: beforeunload 在后台标签被杀时不触发; 推荐 visibilitychange / pagehide 做状态保存。
  • MDN — Window: unload event: 移动端切后台后杀进程不触发; 建议改用 visibilitychange。
  • Angular CanDeactivate / Vue onBeforeRouteLeave / React Router useBlocker: 页内导航守卫三件套, 与 beforeunload 互补而非替代。
  • 表单状态持久化实践(OpenReplay / Flavio Copes): sessionStorage 用于单标签草稿、localStorage 用于长期草稿; debounce 写入; 保存成功后立即删键; 不把密码 / token 放 Web Storage。
  • 表单守卫实践(client-side-form): 「离开文档」与「离开路由」是两套机制, 只做一套必漏; 草稿是唯一覆盖崩溃与标签回收的机制。
