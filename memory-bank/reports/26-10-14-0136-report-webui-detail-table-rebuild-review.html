03 / 诊断结论与实证

修法映射错误 + 制度失效

3.1 四个修法映射错误(均有实证)

症状上轮做法错在哪(实证)
表头异色W6 统一到 --bg基准锚错:抽屉容器底是 --bg-card。探针实测(prism/frost):面板 253,254,255 / 表头 242,246,251 / 行板 247,250,253,三样各算;修完后表区比周围暗一档。W6 自己的像素采样输出就含此证据,被判读为「色带消失」
按钮独立成列W5 locked:true命题偷换:修的是「列不可隐藏」(能力),用户报的是「按钮占一列」(呈现)。classic 与变体至今按钮仍各占一列
点击跳动W5 反应式化 + _dtMergeRows覆盖缺口:只管住纯前端状态(勾选/折叠,量具 #8 也只测勾选)。优先级点击走数据回路(POST→重拉→rowsFn 整表重建行对象)——atlas 实测点一次行位移 85px
无点击排序继承 26-10-12-0527 Q3「原口径无排序」单方裁剪:用户期望从未被收集。另探针证实 classic 内容表排序其实是通的(点「大小」→ aria-sort 变化、行序按值重排),变体面(10/11)则全列 sortable:false

3.2 制度失效(为什么全绿了还有问题)

  • 判据全部自设:量具/守阵/判据由实施者自写,测「自以为该对的」。W6 量具判据就是「表头 == --bg」——精准地做错了目标,照样 8/8 绿。
  • 零视觉回归:无截图 diff 门。W3/W4 的「实测自洽」只量几何数字不看视觉——04 卡片异色就是当时放行的。
  • 零真实交互:e2e 用 force:true 合成点击、直改内部状态;命中测试、焦点链、滚动条在场的用户路径一条没测。「点击乱选」「合并态丢内容」这类缺陷全在此盲区。
  • 零用户验收:关单依据 = 测试全绿,「默认配置下用户过目」这一环不存在。
一句话根因:方案把每个症状翻译成一个技术机制,修机制→自设判据验证→全绿关单;四个翻译里有四个是错的,而验证闭环里没有一环是用户看到的界面。测试全绿与用户有问题并存,是因为量具测的是自设判据,不是观感。

3.3 分层事实(重订计划可用)

  • 无一例用户报告出自引擎/数据层(dt_table.js 几何单点、列声明、drawer_store 合并通路)——该层有静态守阵钉住。
  • 缺陷集中在面层:交互模型(选中/命中/事件传播)、状态机(合并切换/锚换代)、呈现(背景/层级/重叠)。
  • classic 与变体是两条平行实现:classic 各页签走 drawer.js 自己的数据通路与模板(drawerFile 等),变体面走引擎桥 + drawer_store。修一条不等于修另一条。
  • 已知关键文件落点(供重订参考):引擎 shared/dt_table.js / 背景族 shared/dt_table.css(W6 产物,基准待重锚)/ 变体 shared/drawer_tpl/ / classic 内容页 drawer.js drawerFileRows() + tpl/drawer-tabs.html + tpl/xtpl-cells.html(tpl-aq-file-cells)/ 列声明 app.js DRAWER_TABLE_DEFS。
