整组迁移同机证明：推翻与最小改的可行性对比

该推翻的是判据，不是 mover 架构：剩余空间相等只是代理信号，且比的是 qB 默认保存路径那块卷；改成让 qB 用自己的目录 API 回答「我看不看得见目标路径」即可，改动量与「最小改」同一量级。主方案 D（qB 侧目录探测 + 元数据比对），兜底 A（用户显式声明）。

§01结论

一句话：判据该换，架构不该换。现行闸门用「qB 上报的剩余空间 ≈ 本机某卷剩余空间」来证明共享文件系统，这是一条错误的代理判据；而且取数取错了盘（server_state.free_space_on_disk 是 qB 默认保存路径那块卷，不是本次迁移的 src/dst）。这两点叠加，导致既误拒（qB 默认路径在本机不可读时上报 -1，必败）又可能误放（不同盘剩余空间接近时落进容差带）。

但搬移架构本身（qB 搬字节 → auto-qb 在原位建链接 → 穿透校验 → 守护收尾）不该推翻。多成员组在数据已搬走之后没有廉价回退：把数据再复制回去等于二次全量写盘，正是现有实现选择「建链失败保留现场、标记 failed」的原因（_build_links 注释与实现）。所以「后验证明 + 失败即回退」在成本上不成立；正确做法是把「预证明」换成真证据，而不是取消预证明。

推荐：主方案 D —— 预检时让 qB 用 app/getDirectoryContent 列 src 与 dst（或其最近存在祖先），把返回的 name/size/last_modification_date 与本机 stat 比对，同一文件元数据完全一致即证明 qB 与本进程看到同一份物理文件；再复用现有建链后阶段做一次 qB 侧自检（F）。兜底 A —— qB 过旧/远程/容器场景由用户显式声明 assume_shared 或盘映射，并明确告知「auto-qb 无法验证」。

成本差距的诚实结论：「推翻判据」≈ 最小改的成本量级，收益是决定性证据；「推翻架构」成本高且没有必要。最小改（G）只修「比哪块盘」，仍然留着代理判据的假阳/假阴；按路径查空间（C）要 qB ≥5.3，而项目当前支持下限是 5.2.3，今天用不上。

§02为什么现行判据事实上不可靠

2.1 判据本身错：剩余空间相等不是「同一文件系统」的证明

代码事实：same_volume_proof(qb_free, local_free) 的判据是 abs(qb_free - local_free) <= max(1GiB, local_free*2%)（relocate_units.py L702-L714）。

  • 假阳：两块 4TB 盘剩余空间恰好接近（1GiB 绝对容差或 2% 相对容差很容易覆盖）→ 判为同盘。数值相等只说明「两个卷的剩余量接近」，与「是不是同一块盘」没有逻辑蕴含。
  • 误放的真实后果（按场景分层，代价差一个数量级）：判据通过后，多成员组会在本机 src 建链接指向 dst，但破坏面分三层。①完全异机 qB：数据被 qB 搬进它自己命名空间的 dst，本机 dst 无文件，执行链的 verify 阶段（_dst_ready 本机逐文件 stat+比大小，relocate_exec.py L135-L148）先失败——链接一条不建，qB 侧做种无损，代价只是 job 账目与重归组不一致（安全侧，被现有后置防线兜住）；②容器/映射错位（最贵的一类）：qB 的 setLocation 已成功把数据搬进容器内部未挂载路径（overlay 层），本机 verify 同样失败，但数据已脱离宿主管理、占双份空间、容器重建即丢，恢复要再整搬一次；③半对齐（src 可见 dst 不可见）与巧合副本：全链本机校验都能过，破坏延迟到未来成员经 src 链接写入时爆发（qB 看不到、recheck 失败、孤儿文件）。现行代理判据对 ②③ 无任何拦截能力——这正是闸门想防的事故。
  • 假阴：qB 的 free_space_on_disk 来自 sync/maindata 快照，与本机读取之间存在同步周期和写盘漂移；虽然 2% 容差能吸收日常抖动，但大文件写入/删除会直接跨出容差带，产生间歇性误拒（设计文档 §2.4 已承认「完全相等必然间歇性误拒」）。

2.2 参数取错：比的是 qB 默认保存路径那块盘

代码事实：qb_free = store.server_state["free_space_on_disk"]（relocate_plan.py L255-L260）。qB 这个字段报的是默认保存路径所在卷，不是本次迁移的 src 或 dst。于是：

  • 正向迁移（S→T）碰巧可用：默认路径通常在 S，源侧比对能过——这也是历史真机「完全相等」证据的来源（设计计划 26-10-18-1604 §2.4 L129）。
  • 反向迁移/回滚（T→S）必然误判：qB 报 S，而这次源是 T；P7 因此放宽为「任一侧吻合」（L256-L260 注释）。注意：放宽只缓解了方向问题，没有修正「比的是默认路径」这个根本参数错位。
  • 默认路径在本机不可读 → 证明必败：本轮实测 56590 的默认保存路径是 R:\Download\PTing，本机没有 R: 盘，于是 free_space_on_disk = -1，same_volume_proof 直接返回 False。RM04 真机基线（L49）记录了这个现象，当时的绕法是「临时改 save_path 再逐字还原」——产物没有修。
  • 比 src/dst 都对的场景反而可能不成立：qB 默认路径在第三块盘（既不是 src 也不是 dst）时，两侧都对不上，即便 qB 与本机明明共享同一套盘，也会被硬拦。

2.3 归因错位：这是「共享文件系统」闸门，不是「同卷」闸门

闸门的原始动机是 (a) 证明 qB 与本机看到同一套文件系统（为了多成员组的链接可解析），实现手段才是 (c) 用剩余空间当代理；它不是为了证明 src/dst 同卷。src/dst 同卷是另一条独立事实 same_volume（relocate_plan.py L252-L254），用于空间闸门与「硬链接 vs symlink」的形态选择（alias_fs.py L131-L148）。因此修闸门时不要把它和「跨卷」混为一谈：跨卷对多成员组不是错误，只是不能硬链接、要退 symlink。

§03「不需要预证明」的设计成立吗

先把因果讲清：单成员组走 FORM_DIRECT（relocate_units.py L454），qB 自己搬完 save_path 就是目标，不需要在原地留链接，所以不需要「qB 能读本机链接」——闸门只记 note 不拦。多成员组 multi = len(facts.hashes) > 1（L420-L424）必须留链接，闸门才硬拦。

现有执行链（relocate_exec.py L158-L190）：verify（目标文件数/大小）→ link（建链接）→ penetrate（经原路径本机 stat）→ arm（重归组、守护）。两个关键缺口：

  • _dst_ready 与 _penetration_ok 都只用本进程的文件访问层做 stat（L135-L148、L245-L255），没有一个校验是从 qB 视角做的。所以「本机建链成功」并不等于「qB 能读」。
  • 建链失败时不做数据搬回（L192-L197 注释）：注释明确「搬回要再复制一遍全部数据」，所以选择保留现场 + failed。

判断：「后验证明 + 失败即回退」作为唯一机制不可行，因为失败发生在 mover 已把数据搬到 dst 之后，回退成本 = 第二次全量写盘，且多成员组没有「qB 自己搬回去」这种免链接路径。可行的组合是：预检用真证据（D）挡住绝大多数错误配置 + 建链后做 qB 侧自检（F）兜住运行时异常；失败时保留现场、给出可操作报错（现状），而不是承诺自动搬回。若未来要实现「自动搬回」，必须先接受二次写盘与做种中断的成本，这是用户要拍板的事。

§06推荐与「推翻 vs 最小改」的真实差距

6.1 主方案：D + F（判据替换，不推翻架构）

  1. 预检阶段：把 proved 的来源从 free-space 比值改为「qB 侧目录证据」：
    • 对 src：qB 列本组 content_root（组自己的内容目录）的条目，与本机 os.scandir 的 name→(size, mtime) 映射做集合比对（条目多时抽 k 个代表文件），比对 size 与 last_modification_date（本轮实测同一文件可完全相等，见 §08）。不下沉到 save_path 下载根列目录——多组共存时那会列回数千条目，§8.3 的「超大目录未压测」风险应在设计上消掉而不是留作实测项；组内文件已不齐（二次发起/断点续跑）时按「至少一个代表文件全等」判定，全空目录只走 dst 侧判定。
    • 对 dst：qB 列目标或其最近存在祖先（与现有 _volume_free_resolved 同一上溯机制），只要求「qB 看得见该目录」；dst 叶子尚未创建是正常输入。
    • 两者都成立 ⇒ 证明 qB 与本进程共享同一命名空间；链接 src→dst 才可能被 qB 解析。任一侧不成立 ⇒ 保留 GATE_SAME_FS 硬拦，但报错改成「qB 列目录失败/404（附 qB 视角路径）」。
  2. 路径翻译：请求前用现有 fs.path_map 把本机路径译成 qB 视角路径；容器场景下这正好暴露「映射缺失」而不是误判。
  3. 运行时兜底（F）：建链后的 penetrate 阶段增加一次 qB 侧列目录校验；失败按现状保留现场 + failed + 明确原因，不承诺搬回。
  4. 旧证据降级：free-space 比值不再单独构成硬拦（仅用户显式选择 legacy 模式时保留）；D 不可用时的降级路径用 B′（torrents/files 元数据比对）而非 free-space——用既有成员种子的 torrents/files（全版本可用）+ 本机同路径 stat 比 size。它证不了「qB 现在读得到」（size 来自种子元数据而非实时 FS），但作为兜底严格优于 free-space 代理：至少修掉「比错盘」（默认路径不可读 → -1 必败）与「不同盘剩余空间巧合」两类病，且不碰未文档化端点。

6.2 兜底：A 显式声明

面向 qB <5.0、远程 qB、NFS/SMB 跨机共享、或 D 端点被未来版本移除的场景。配置层允许用户声明「已确认共享文件系统」，预检回执必须显著标注「未经 auto-qb 验证，由用户承担」。这是逃生通道，不是默认路径。

6.3 成本与风险的真实差距

路线改动面风险收益结论
最小改 G（只修参数）1 个取数点 + 文案假阳/假阴仍在；远端误放仍可能发生消除「R: 不存在 → -1 必败」这一种误拒不够
C（5.3 按路径查空间）1 个 API 调用 + 判据仍是指标代理；5.3 以下不可用把「比哪块盘」修正到 path 级方向对但判据仍弱、版本受限
D+F（推荐）1 个 API 封装 + 证明函数替换 proved + 1 个阶段校验端点未在官方 wiki 文档化（有变更风险）；容器需 path_map决定性证据，假阳/假阴显著收敛；5.2.3+ 全覆盖推荐
推翻架构（放弃预证明，纯后验 + 自动搬回）执行层重构 + 回滚子系统二次全量写盘、做种中断、回滚失败态更复杂少一次预检不值得

直说：如果目标是「少写代码」，G 最便宜；但它买到的是「少一种误拒」，不是「判据正确」。如果目标是「让闸门真的证明它声称的东西」，D 的增量成本（一个只读 API + 一个证明函数）与 G 是同一量级，没有理由退而求其次。推翻架构则是把风险从「误判」搬到「数据二次搬移」，不划算。

6.4 两个新方案怎样改变结论

方案 1（地址放行）：不改变结论，而且证据方向是错的。地址只能证明「端口从本机网络栈可达」，与「qB 与 auto-qb 看到同一文件系统」无关。典型反例：Docker 端口映射下地址是本机、FS 是容器；SSH 反向隧道下地址是本机、FS 是远端。本机没有任何 Docker/WSL 可实测，但这两个反例在逻辑上已经足够判死「正向放行」。它最多能做负向早期过滤（主机明显是远端 IP → 提前拒绝）和报错提示，不能作为放行依据，也不能与 F 组合成廉价近似——F 需要的是 qB 侧文件系统证据，地址给不了。

方案 2（假种探测）：比 D 更强，但不更适合当默认。实测一轮完整探测约 1.3 秒（详见 §11），能同时证明「qB 读得到本机 src」与「qB 写得到本机 dst」，这是 D 做不到的；但它要往 qB 里加一个种子、再删掉，涉及 qB 队列/日志/规则与崩溃残留清理，侵入性明显高于 D。结论是主方案仍是 D+F，E1 作为可选「严格模式」：在 D 无法判定（权限不足、端点不可用）或用户要求一次性强证明时启用，并缓存结果；不建议每次移动都跑。

§07迁移与兼容（若采纳 D+F）

7.1 配置

  • 新增可选键（非必填）：relocate.same_fs_probe = auto | off（默认 auto：D 可用则用 D；off 走 legacy/声明）、relocate.assume_shared = false（默认关闭，保守默认）。
  • 必须同步 config.validate_config 与 config/schema.py（黄金法则 4 的守卫测试会查）。
  • 不修改 fs.path_map 语义；D 只是消费它。

7.2 报错文案与闸门 id

  • 保留 GATE_SAME_FS id（测试与前端按 id 断言）；改文案为可操作版，例如「qB 看不到目标路径（qB 侧列目录 404）—— 请检查 qB 是否与 auto-qb 同机/共享卷，或配置 fs.path_map / relocate.assume_shared」。
  • 区分两种失败：「qB 列目录 404（看不见）」与「端点不可用（旧版本/被移除）」，前者拒绝、后者降级。

7.3 既有测试与真机基线

  • same_volume_proof 的单测保留（仅 legacy 模式判据）；新增 B′（torrents/files 比对）与 D 的证明函数单测：元数据一致 / 不一致 / 纯列表（无 metadata）/ 404 / 400 / 400 缺参。

  • RM04 的「临时改 save_path 再逐字还原」绕法可以退役——D 不再依赖默认路径；基线里该段作为历史快照保留。

7.4 老用户行为会不会变

  • 会变宽（待实测闭合，验证前只是推断）：默认保存路径不可读（本机无 R:）的场景——本轮只实测了 free_space_on_disk = -1 与 C:\ 列目录，未实测 qB 能否列出 R:\Download\PTing。若 qB 自己也读不到 R:，D 会 404 照拒（出路是 assume_shared 或修盘符可见性，但报错从「必败的 -1 比对」变成可操作的 404）；若 qB 能列出而只是取不到剩余空间，D 才真正放行。落地前应在 56590 补一发 getDirectoryContent?dirPath=R:\... 验证，发版说明不要预写「必败 → 通过」。
  • 会变严：远端 qB 恰好有相同路径与相近剩余空间的用户，从「可能误放」变为「正确拒绝」——这是修 bug，但需要在发版说明里写清。
  • 真正跨机的用户需要 fs.path_map 或显式 assume_shared，否则被拒；文案必须给出这两条出路。

§10追加方案 1：直接放行本机地址

结论：不能覆盖全部本机情况，也不能排除异机。网络地址只证明「端口从本机网络栈可达」，与「文件系统同一」没有逻辑关系。最典型的两个反例是 Docker 端口映射（地址是本机、文件系统是容器）与 SSH 反向隧道（地址是本机、文件系统是远端）。地址判据最多能做负向早期过滤（明显是远端主机 → 提前拒绝）与报错提示，不能作为放行依据。

10.1 逐候选判据

候选判据会判成判错方向为什么
127.0.0.1 / ::1 / localhost 本机 假阳（异机被放行） 回环只说明本机进程栈能到达该端口。Docker -p、SSH 反向隧道、同机反向代理都会让「地址是本机、文件系统在对端命名空间」。localhost 还受 hosts/DNS 与双栈解析影响，可能指向别处或解析到 qB 未监听的家庭地址（假阴）。本轮实测：127.0.0.1 200、localhost 200、[::1] 000（qB 只绑 IPv4）。
宿主机局域网 IP（192.168 / 10. / 172.16-31）、多 NIC 本机 假阳 绑定到主机接口只说明「这台机器的这个网卡能收包」，与进程的文件系统无关。端口转发（netsh portproxy、容器映射、反向代理）同样落在本机 IP 上。本轮实测：192.168.110.130:56590 200（因 qB 绑 0.0.0.0），单网卡、无 IPv6。
绑定 0.0.0.0 或 [::] 时的可达性判断 无法判定 双向都可能 0.0.0.0 表示监听所有接口，无法区分「本机回环访问」与「远端访问」；同一个监听地址既可能对应本机进程，也可能对应映射到容器/远端的代理。实测 56590 的 web_ui_address=0.0.0.0，因此从 LAN IP 访问同样 200——这恰好说明「能连上」不构成同机证据。
Docker 桥接 / -p 8080:8080 本机 假阳（典型反例） 宿主地址 + 容器文件系统。qB 在容器里看到的 /downloads 与宿主 D:\Downloads 是两套命名空间，除非卷映射恰好把两者对齐。地址判据对这一类完全失明。
host 网络模式 本机 真阳，但不可区分 host 模式下容器与宿主共享网络与文件系统命名空间，地址判「本机」是对的；但它与 -p 桥接在地址上完全一样——两个相反结论对应同一个判据结果，说明判据不可用。
WSL2 端口转发 本机（Windows 侧） 假阳 Windows 的 localhost 可转发到 WSL2 VM；qB 在 VM 里，路径是 /mnt/... 或 VM 内卷，与 Windows 的盘符不是同一命名空间（\\wsl$ 也只是另一种映射）。
SSH 反向隧道 本机 假阳（典型反例） 本机监听一个端口，转发到远端 qB。地址是本机、文件系统是远端，链接在本机建了 qB 也读不到。
同机反向代理（nginx / Caddy 等） 本机 假阳 代理监听在本机，上游可以是远端或容器；地址证据只覆盖到代理这一跳。
同机不同命名空间 / 容器卷映射错位 本机 假阳 网络共享、文件系统不共享。卷映射只覆盖部分路径时，src 可能对齐、dst 没对齐，或反过来；地址判据看不出这种半对齐。
局域网另一台机器的 qB 异机 真阴（正确拒绝） 直接用对方 LAN IP 时会被判成异机，方向正确。但若通过本机隧道/代理再访问，就退回上一条的假阳。
VPN 内同网段机器 异机 真阴（正确拒绝） 同上；而且跨机共享存储（NFS/SMB）本来就不满足「本机建链、qB 读」的语义，拒绝是对的。
IPv6 link-local / 多网卡 / 双栈选择 本机或异机（取决于解析） 假阳 / 假阴混合 fe80:: 是接口本地地址，本机与同链路的机器都能用；localhost 可能先解析到 ::1 而 qB 只监听 IPv4，造成本机被误拒（假阴）。本轮 [::1] 实测 000 就是这一类的现实版本。

10.2 实测与环境

  • web_ui_address = 0.0.0.0、web_ui_port = 56590；本机单网卡 192.168.110.130/24，无 IPv6 地址。
  • 可达性实测：127.0.0.1 → 200、localhost → 200、[::1] → 000、192.168.110.130 → 200。
  • 本机没有 Docker、没有 WSL（docker 命令不存在；wsl 未安装内核），因此 Docker 端口映射、WSL2 转发、SSH 隧道这三类反例无法在本轮实测，只能给逻辑反例（标注「未实测」）。

10.3 结论性判据

地址 ⇏ 同一文件系统。可达性判据的语义上界是「TCP 能到」，而下层要回答的是「qB 进程能否读到本机这块盘上的文件」。两者之间可以插入任意数量的命名空间转换（容器、VM、隧道、代理、端口转发）。因此：

  • 不能作为正向放行依据；
  • 可以作为负向过滤：如果配置的 qB 主机明显不是本机地址（且没有声明这是本机隧道），提前给出「这看起来是远端 qB，多成员组需要共享文件系统」的拒绝文案；
  • 不能与 F 组合成「廉价近似」：F 需要的是 qB 侧文件系统证据，地址给不了任何增量信息。

§11追加方案 2：假种一次性探测（E1）

结论：证明力最高，实测也很快，但不适合当默认。它用 qB 自己的搬运路径（setLocation）真写一次目标盘，能同时证明「qB 读得到本机 src」与「qB 写得到本机 dst」；代价是往 qB 加删一个临时种子，需要残留清理与规则隔离。建议作为可选「严格模式」，而不是每次移动都跑。

11.1 探测设计（可执行版）

  1. 造种：单文件 4KiB，piece length 16KiB（1 个 piece），手工 bencode 生成 .torrent（本轮实测 102 字节），info.name 用唯一前缀（如 aqb-probe-<random>.bin），并打 tag aqb-probe。
  2. 落源：把内容文件写到本次的 src（或一个临时子目录），add 时 save_path=src、paused=true、autoTMM=false、category 留空——避免被分类规则搬走。
  3. 证明读：显式 recheck，轮询 progress == 1.0。qB 能把我们刚写的文件校验完成，说明它读到的就是本机这份内容。
  4. 证明写：setLocation(dst)，轮询本机 dst 出现文件；比对 size 与 SHA-1，并确认 src 消失、save_path 已更新。
  5. 清理：deleteFiles=true 删除种子与文件 → 轮询种子消失 → rmdir 清空目录（qB 不删空目录）→ 校验无残留。tag + 启动扫描兜底崩溃残留。

11.4 版本兼容与清理可靠性

  • torrents/add、recheck、setLocation、deleteFiles 在 qB 4.x 与 5.x 均存在；paused 在 5.x 有 stopped 的新写法，实现时要按版本/库别名兼容。本轮在 5.2.3 实测通过。
  • 崩溃残留：进程在 add 之后、delete 之前被杀，会留下一个探测种子与文件。必须用固定 tag + 启动扫描（按 tag 删除）兜底；否则每次崩溃都在用户 qB 里留垃圾。
  • 污染面：qB 日志会记录 add/remove；若用户开了通知/自动分类/队列上限，可能被触发。探测种子应尽量小、暂停、无 tracker、无分类。
  • 缓存：同一 qB 实例 + 同一对卷（src/dst）的探测结果可在会话内缓存；qB 重启、路径映射变更、挂载变化时应失效。一次性探测的成本才真正接近零。

§12需要用户拍板

  1. 判据替换：是否接受「以 qB 侧目录/元数据证据为准」，把剩余空间比值降级为 legacy 提示？
  2. 旧版本与远程：qB <5.0 / 远程 / 容器用户，默认拒绝还是默认允许用 assume_shared 显式越权？
  3. 写入探针：是否允许在用户目标目录短暂写一个临时文件（E）以换取更强的唯一性证明？若不接受，D 是上限。
  4. 失败语义：建链后 qB 侧自检失败时，维持「保留现场 + failed」（现状），还是要投入成本做「自动搬回」？
  5. 文案变更：是否允许改写 GATE_SAME_FS 的报错（会影响既有测试断言与用户习惯）？
  6. 5.3 补充证据：是否值得为 C 引入「5.3 按路径查空间」作为 D 的辅助证据（需先有 5.3 实例验证）。
  7. 地址判据的定位：是否接受「本机地址只作负向过滤与报错提示，不作为放行依据」？若坚持用地址放行，需要明确由谁承担 Docker 端口映射 / SSH 反向隧道的假阳后果。
  8. 假种探测（E1）是否可选：是否允许实现往 qB 加删临时种子（tag 隔离 + 启动扫描兜底 + 会话缓存）？默认关闭、仅在 D 无法判定或用户显式要求「一次性强证明」时启用，还是完全不引入。
