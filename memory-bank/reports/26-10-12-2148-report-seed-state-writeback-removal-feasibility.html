1摘要

问题（用户命题）
种子状态有两条回写通道：① qB 全量/增量同步（sync/maindata rid 增量 / 降级 torrents_info 全量，权威）；② auto-qb 自有动作（停/起/暂停/恢复）经 QbApi._sync_paused_state 直接把合成状态写进快照。后者可能与 qB 实际状态不一致。需分析移除后者的可行性与影响。
核心结论（一句话）
直接回写只有一个单点（qbapi.py:96-126 → store.py:480-544 的 state= 参数），且系统是单写线程 —— 「移除」在工程上完全可行。当前它同时服务两个目标：同 tick 值新鲜（幂等/视图脏/组脏，正当需求）与自写变更静默吸收（防自触发，是策略而非正确性需求）。26-10-12-2229 重审后者：按「源无关语义」（暂停的磁盘风险与谁按下暂停键无关），吸收实为信号压制——自家停种后该做的缺文件扫描被吞（经 auto-qb WebUI 暂停的做种恰恰跳过该功能的核心场景）。因此正解不是「移除机制」，而是把合成值换成真值、把隐式吸收换成显式发射（方案 B′，§5）：写后立即查 torrents_info 写真值 + 登记动作前基线使下一轮照常发射状态变化 —— 不一致结构性消失，新鲜度保留，信号不再被吞。
议题结论
移除可行性高。单点收口 + 单写线程，无并发竞态；state 不落盘，无迁移面。纯移除的真实代价收敛为：同 tick 幂等门失效（低）+ 冲突判定延迟一轮（低）+ 缺文件停种路径每次事件多一次冗余扫描（低，有界）。§4.2/§4.3 两项经重审不是回归而是收益/语义正确。
不一致是否真实存在是，6 类风险面（§3）：值域压平（4 值 vs qB 全枚举）、完成位推断陈旧、隐式吸收无登记、异步应用竞态、全量停种形态零覆盖、失配静默变「外部变化」。
推荐路径用户意向方案 A；A 系推荐形态 = A + 局部 deferral（§4.9）：删回写与合成值（R1-R6 全消），源无关发射天然获得；只对校验类决策（G4/G6 等，消费点可枚举）做局部延迟，收回 A 唯一实质安全缺口；幂等可选 pending_writes 意图标记。B′（真值回写 + 显式发射）是「同 tick 全决策新鲜」优先时的替代路径。（26-10-13-0441 补证：这条替代路径的「新鲜度优先」理由已被削弱 —— qB 服务端状态按 RefreshInterval 默认 1500ms 节流，真值回写在写后 ≤1.5s 内读到的常是写前值、退化为 no-op，见 §3 R4。）B 单独不完整：只修值失真，吸收盲点原样保留。
影响面（若执意 A）规则 on_torrent_state_enum_changed 对自有停/起发射（语义正确：自家停种也是真实状态变化，用户规则应可感知；反馈环需显式 external-only 过滤而非静默隐藏）；分组「上传转暂停」检测对自家停种发射（收益：源无关检查；缺文件停种路径仅多一次冗余扫描，有界）；同 tick 幂等门失效（低）；冲突判定延迟一轮（低）；G4/G6 校验闸门陈旧-放行窗口（A 的唯一实质缺口，局部 deferral 收口，§4.9.3）；WebUI 显示延迟 ≤1 tick（低，P0-5 兜底且同 tick 补刷新）。
测试守阵3 条直接守阵钉在「写后同步」契约上（tests/test_actions.py:157/179/210），任何方案都需按新契约重写；其余为权威通道仿真，不受影响。

2现状取证：两条回写通道

2.1 权威通道 —— qB 全量/增量同步

唯一以 qB 为真相的数据入口，全部经 TorrentStore：

  • 增量：apply_sync(api)（store.py:118）走 sync/maindata?rid= —— rid 一致只回变化种子的变化字段，删除走 torrents_removed；full_update=true（首轮/rid 失效）为全量。
  • 降级全量：旧版 qB / 替身缺方法时（_SYNC_UNAVAILABLE，store.py:18/128-140）降级 torrents_info() 一次性告警。
  • 应用：_apply(patches, removed, full)（store.py:193）对每个变化种子 rec.apply_delta(src)（record.py:157）拿变化字段集；其中 state 入 state_changed（store.py:239-240）；state/amount_left/tags（_CONFLICT_FIELDS，store.py:191）变化登记 dirty_groups（store.py:241-244）。
  • 轮末固化：update_state_snapshot()（store.py:301-307）把本轮 by_hash 的 state_enum 固化为「上一轮快照」，供下一轮对比。调用点在主循环 _refresh_torrents 收尾（qbmanager.py:881-885）。
  • 节拍：sync_interval 被钳制 ≤ main_tick（qbmanager.py:505-511，默认 1.5s）；WEB 命令改了状态的那轮强制补刷新一次（P0-5，qbmanager.py:525-528），即用户点击后真值在同 tick 落地。

关键性质：权威通道是唯一产生 state_changed（本轮 state 变化集）的入口，而 state_changed 是规则状态事件与分组转移检测的唯一依据（§4.2/§4.3）。

2.2 直接回写通道 —— _sync_paused_state（单点）

全部 direct-write 收口在一个方法，全仓无第二处 update_torrent_fields(state=...)：

  1. 值覆写：torrent.state = state + _state_enum 缓存失效（store.py:535-536/543-544）—— 同 tick 读 state_enum 立即是新值；
  2. 视图脏：state ∈ _VIEW_FIELDS（view.py:13）→ view_changed=True（store.py:506）→ WebUI 视图重建；
  3. 组脏：登记 dirty_groups（store.py:512-516）→ 同 tick post 相位重算该组下载冲突（增量判据，grouping_mod.py:406-408）。
隐式的第四用途：吸收下一轮 qB 上报
合成值与 qB 下一轮增量上报的值逐字相同时，apply_delta 检不出 delta ⇒ 该 hash 不进 state_changed ⇒ ① 规则 on_torrent_state_enum_changed 不对自家动作触发；② 分组「上传转暂停」检测不误判。主循环注释把这层设计写死了：「新增归组的大小一致性停种经快照同步会当场改写 by_hash 状态，放在后面会把自家停种误判为外部『上传转暂停』」（qbmanager.py:810-812）。注意这是隐式吸收（值相等即吸收），与 tags/category 的显式 self_caused_fields 期望值登记（store.py:346-387）是两套机制。（26-10-12-2229 改判：在「源无关语义」下，该吸收从「免误触发保护」重新定性为「信号压制」——自家停种同样应触发检查与事件，隐式吸收使这条信号对自有动作静默消亡，见 §4.2/§4.3/§5。）

3不一致风险面：直接回写凭什么会与 qB 实际状态脱节

直接回写是「照快照推一个值写进快照」—— 推错的每一分，都会成为快照与 qB 真值之间的差。逐条列机理与严重度：

编号风险机理（证据）严重度
R1值域压平（4 值 vs qB 全枚举） 回写只会写 pausedUP/pausedDL/stalledUP/stalledDL 四值（qbapi.py:120-123），qB 真实状态空间还含 queuedUP/queuedDL、forcedUP/forcedDL、checkingUP/checkingDL/checkingResumeData、moving、missingFiles、error 等。已知实例：ops 校验成功 auto_start 后回写 stalledUP（ops_mod.py:274），而 qB 实际是 checkingUP（recheck 恢复）—— 到下一轮 sync 才被真值纠正。源码自认该取舍：「stalled/queued/forced/检查中等细分由下轮 sync 校准（瞬态，不影响判定）」（qbapi.py:103-104）—— 但「不影响判定」只对暂停轴成立，is_checking 恰是 ops/skip-gates/代表种判据（ops_mod.py 轮询、grouping_mod.py:298）的输入。 中
R2完成位推断的陈旧性 「完成位」不是 qB 告知，而是照快照自推：enum.is_complete or progress>=1.0（qbapi.py:115-119）。快照陈旧（刚下完未上报、.!qB 改名窗口、缺文件 scanned 前）时，暂停一个即将完成的种子会写成 pausedDL（实为 pausedUP）—— 同 tick 的冲突重算按 is_complete 计 n_done（grouping_mod.py:438）、缺文件分组分支按完成位分流，全部按错位分类跑一格。这不是假想：该判据本身就加固过一次（report 26-10-11-2017 §4.2/§6.4 的「完成位联合判据」，见 qbapi.py:111-114 注释），说明此面反复出过问题。 中
R3隐式吸收，无登记、无告警 tags/category 的自写有显式 self_caused_fields 期望值登记：上报值与期望一致 ⇒ 按自写处理并消费登记；不一致 ⇒ 按外部变化放行（store.py:346-370）。state 没有任何登记与告警 —— 吸收只靠「下一轮 qB 上报值 == 写入值」的偶然相等。失配时静默降级为「外部变化」，无任何日志线索。 中
R4异步应用竞态（意图当成事实） pause/start 下发后 qB 会话状态并非即时翻转（resume 尤其明显，WebUI 侧专为此建了 truth_pending/TRUTH_RETRY_S 重试机制，qbmanager.py:536-538/568-572；flush 注释原话：「resume 后 qB 要过一会儿才翻状态」）。直接回写在 API 返回后立刻把「意图」当「事实」落进快照，与真值机制并行双轨。同仓库的跳检重加流程刻意不采用回写，而是「决定性时刻直查真值」（ops_mod.py:791-806：用 torrents_info 刚确认的结果 apply_delta）—— 即项目内部已有相反方向的最佳实践。

风险面小结
R1/R2/R4 的直接受害面是同 tick 的判定链（下载冲突 n_done、transfer 检测、checking 门、跳检参考种），不是显示层；窗口宽度 ≈ 到一个 sync 间隔（默认 ≤1.5s，钳制于 main_tick，qbmanager.py:511）。R3/R5/R6 是可观测性与一致性问题。全部六类在方案 B / B′（§5）下结构性消失。

4移除影响分析：按消费方逐条对账

直接回写不是「只喂显示层」，它是四个同 tick 契约的承重墙。逐consumer 分析纯移除（方案 A）后的行为变化：

4.1 同 tick 动作幂等 低

  • 契约：写后同步让同 tick 内二次停/起被 is_stopped/is_paused 门拦下（qbapi.py:103-105 自述：「不写回的话，同一 tick 内第二个 stop 会因 is_paused 仍为假而再发一次请求」；规则侧门在 basic.py:113/126）。
  • 移除后：第二个 stop/start 在同 tick 再发一次 HTTP。qB 的 stop/start 本身幂等 ⇒ 无功能错误，代价是重复请求与日志噪声；规则组合（多规则同 tick 作用于同种）从 skip 变 ok。
  • 守阵：test_actions.py:157 test_start_stop_idempotent 直接钉这条（其注释明写依赖「经 QbApi 同步后 state 已为 stalledUP」）。

4.2 规则状态事件的自写发射 语义改判（26-10-12-2229）

  • 现状：合成值 == qB 上报值 ⇒ apply_delta 无 delta ⇒ 自有动作不进 state_changed ⇒ on_torrent_state_enum_changed 规则不对自家动作触发（rules_mod.py:330-338 只消费 state_changed）。
  • 改判：「自家停种也是真实发生的状态变化」—— 用户完全可能写「auto-qb 暂停时通知我 / 打标 / 走后续流程」这类规则。静默吸收使这类规则永远看不到 auto-qb 自己的停/起，这是能力缺失，不是保护。发射的触发面（冲突暂停、缺文件暂停、大小不一致停组、规则自己的 stop、WebUI 用户暂停）按源无关语义应当全量可见。
  • 残留的真实风险是反馈环，且应显式治理而非隐藏：规则 R1「满足 X → stop」+ R2「on paused → 做 Y」，若 Y 使 X 重新成立则跨轮振荡（节拍 = sync 间隔）。正解是给事件规则提供显式的 external-only 过滤选项（或引擎级成环守卫），让用户自己选「只关心外部变化」—— 而不是把全部自有变更对全部用户静默吞掉。
  • 机制张力（实施时必须正视）：新鲜度与发射共用同一机制。回写让 tick N 快照新鲜 ⇒ 轮末固化后 tick N+1 的 prev[h] == cur 静默跳过（rules_mod.py:333）⇒ 即使强制把 hash 塞进 state_changed 也发不出。纯移除天然获得发射（不新鲜所以 prev≠cur）；真值回写方案必须配 显式自写变更通道（B′，§5/§6）—— 动作前登记基线，下一轮用动作前值强制发射后消费登记。

4.3 分组「上传转暂停」检测的源无关性 改判为收益（26-10-12-2229）

  • 判据的理据是源无关的：cur.is_complete and cur.is_stopped and prev.is_uploading（grouping_mod.py:206）命中即对该组跑缺文件扫描（grouping_mod.py:180-212）。其存在理由（grouping_mod.py:184-185 注释）：「做种中文件可能被外部删除，转暂停后不再主动读盘，需扫描确认」 —— 这是磁盘风险信号而非意图信号：文件在不在盘上，与谁按下暂停键无关。自家停种后同样该查。
  • 今天存在难以辩护的不对称：用户在 qB 自身 WebUI 暂停一颗做种 → 下一轮 sync 检出 pausedUP ≠ stalledUP → 扫描发生 ✅；用户在 auto-qb 的 WebUI 暂停同一颗（commands.py:525 → torrents_pause → 回写）→ 值逐字匹配被吸收 → 扫描被吞 ❌。被吞掉的恰是该功能的核心场景：做种中文件被外部删除、尚无 peer 点过那些片所以 qB 未报 missingFiles —— 暂停那一刻是唯一的廉价校验窗口。
  • 按来源对账「下一轮检查」的性质：缺文件停组（388）= 冗余但无害（本 tick 刚扫过，重扫一次再确认，MISSING 标签已在）；大小不一致停组（248）/ 下载冲突停组（461 的完成成员）/ WebUI 暂停 / 规则 stop = 正当的首次磁盘校验（size mismatch 是声明层分歧，磁盘真相此前从未验证过）；跨组交叉停（591）= 只停 amount_left>0 的下载侧 → pausedDL，is_complete=False，不命中判据，无成本。没有任何来源会产生错误动作 —— 扫描结论只取决于磁盘真相与代表种选择。
  • 真实代价的诚实量化：① 缺文件停种路径每次事件多一次全文件 stat 扫描 + N 个幂等 torrents_stop 请求（add_tags 对已有 MISSING 标签零 API 调用，maintenance_mod.py:169-170）；_missing_scanned_keys 只做轮内去重（grouping_mod.py:92 每轮清零），跨轮不抑制；② .!qB 改名窗口内被其它来源停种会使 transitional 计数器 +1，连续 3 次（TRANSITIONAL_SKIP_LIMIT，grouping_mod.py:38）才升级为真缺失 —— 既有设计已容忍此边界；③ 扫描只在转换拍触发一次，不随暂停持续重复。
  • 对纯移除的净影响：收益。移除后转移检测变成均匀的源无关检查；WEB 暂停场景还因 P0-5 命令驱动补刷新（qbmanager.py:525-528）在同一 tick 内完成「qB 真值落地 + 转移扫描」，比外部暂停路径（下一轮）还快。

4.4 下载冲突判定延迟一轮 低-中

4.9 变体评估：A + 延迟访问（自写后同 tick 访问延至下一 tick） 26-10-12-2315 追加

命题：A 之下，同 tick 内除第一次访问（qB API 调用本身，直接对 qB 生效）算新鲜外，后续经 store 的状态访问都可能是脏的（读到动作前旧值）；提议把后续状态访问统一延迟到下一 tick。以下评估其可行性与问题覆盖度。

4.9.1 结构性事实：deferral 的真实对象比想象小

主循环一拍内的顺序是 command line →（P0-5 条件强制）sync 线 → task 线，且 apply_sync 只在一拍开头跑一次（_tick = sync 线 + task 线，qbmanager.py:729-736）。按自写发生的位置，A 之下的「脏窗口」分三类：

自写来源位置A 之下后续访问状态
WEB 暂停/开始/批量（最高频）command line，sync 之前本来就新鲜：P0-5 在该轮强制补刷新（qbmanager.py:525-528），真值同迭代进快照，后续相位与 task 线看到的都是真值 ⇒ 无 deferral 对象
分组停种（248/388/461/591）、事件规则动作sync 线中段（torrents_added / post / events 相位）脏：污染同 tick 的 post 相位 + 整条 task 线

即 deferral 只需覆盖后两类；第一类（频率最高、用户最可感的来源）在 A 下已被 P0-5 解决——这是初判低估 A 的一点。

4.9.2 可行性：分层可行，且有现成机制可复用

  • task 线（主战场）有单入口：TaskQueue.run_due(..., max_tasks)（qbmanager.py:725）。执行每个任务前判「目标 hash ∈ 本轮自写集」⇒ 重排下一 tick，一处覆盖全部 task 线消费（interval 规则、ops 跳检/校验、维护、限速曲线）。重排机制已有先例：事件规则的 add_task(origin, keep_progress=True) 断点续跑（rules_mod.py:312-315）、ops 轮询的 REQUEUE（ops_mod.py:266）。
  • sync 线 post 相位：判「组 ∩ 自写集 ≠ ∅」即跳过本轮冲突/跨组检查；下一轮 _apply 经 _CONFLICT_FIELDS 自动补登记重算（store.py:241-244），自愈路径现成。
  • 事件同步分派：_dispatch_trigger_rules 加同一判据即可，但与「事件即时分派、不排队」的文档口径冲突（窄面，需改口径）。
  • 自写集生命周期：own_writes: {hash}，apply_sync 应用该 hash 新值时逐出；失败轮保留（与 rid 归零后下轮全量的时序对齐）；单写线程 ⇒ 无并发问题。不落盘（与 state 快照一致，纯内存）。

4.9.4 deferral 自身的成本与新风险（决策必须计入）

  • 核心取舍——构造性安全 vs 纪律性安全：写回是构造性安全（值恒新，消费方无需守任何规矩）；deferral 是纪律性安全——「任何状态依赖消费方不得对自写 hash 出决策」是一条跨切面不变量：漏掉任一条现存消费方 = 静默的陈旧决策；未来新增消费方天然裸奔，只能靠守阵盯（新消费方未接判据即红）。
  • 重排任务的活锁边界（有界、带原因码）、与失败轮/全量轮的交互、事件即时语义的口径修订、每个闸门的红验面。
  • update_state_snapshot 的 docstring（「自有动作经 QbApi 同步过的状态同样计入，故下轮不会被误判为外部状态变化」，store.py:303-305）在 A 下前提消失；且源无关语义要求它对自写 hash 保持旧值以保发射——要跟着改。
变体结论（26-10-12-2315）
可行，且能完整解决问题（含 G4/G6 安全面）——但它的必要性几乎全部压在 G4/G6 这一类安全闸门上。因此不建议一上来就做全系统 deferral；推荐的落地形态是 A + 局部 deferral：只延迟校验类决策——G4/G5/G6/G7-8 与决策链 0/1/1.5 的消费点可枚举收敛（ops_mod 两处 + checking.py 两处 + 各自守阵），其余全部接受 ≤1 tick 滞后（与外部变更完全对称，本就是系统既有工作模式）。幂等层面要么接受重复 HTTP（qB 幂等、无害），要么加一个诚实的小标记集 pending_writes: {hash: 意图}——只带「本 tick 发过停/起」的意图、不带假值，不犯 R1-R6 任何一条，仅供动作守卫查询。若把「同 tick 全决策新鲜」列为硬需求，才升级全系统 deferral，并把该不变量写成守阵。

什么情况下仍选 A / 何时升级（26-10-12-2315 修订）
A + 局部 deferral 是语义最干净的形态：快照严格 = 最近一次 sync 的应用结果，转移检测与状态事件天然源无关，无合成值、无跨切面新鲜度不变量。升级到 B′ 的理由是「同 tick 全决策新鲜」成为硬需求（规则密集、校验与动作高频同批交错的场景）—— 但 26-10-13-0441 补证指出该理由在暂停轴上已不可兑现（qB 服务端按 1500ms 节流，真值回写在写后 ≤1.5s 内退化为 no-op），故 B′ 的现实必要性只剩其发射通道（该通道亦可叠加在 A 系之上）；升级到全系统 deferral 的唯一理由是「同 tick 新鲜」且「不接受每动作一次 info 调用」——此时必须把「状态依赖消费方不得对自写 hash 出决策」写成守阵（新消费方未接判据即红），并把该不变量当作长期契约维护。若未来把「快照严格 = sync 应用结果」定为架构不变量（多写线程、快照外供审计），A 系是唯一形态。
