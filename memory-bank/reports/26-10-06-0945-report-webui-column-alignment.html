§1结论先讲

两个互相独立的机制, 都让「表头文字」与「值文字」的右缘差一截。三套主题同源(共用同一份列模型与同一套盒子规格), 所以三套一起错、错得一样多。

P1 · 主视图 4 表 · 全站可见

表头多 10px 右内边距

.h-cell 为给「拖拽调宽把手」留命中区写了 padding-right: 10px, 值单元格没有。表头右对齐文字于是落在「列右缘 − 10px」, 值落在「列右缘」。实测 11px(多出的 1px 来自数据行有 1px 边框、表头行没有; 明细行无侧边框 ⇒ 恰好 10px)。

P2 · 设置页 HR 表① · 4 列

隐形排序箭头仍占位

HR 明细表①的 th 里排序箭头没有 v-if, 只用 opacity: 0 隐藏 ⇒ 布局上仍占 11px + margin-left: 3px。右对齐的 num 列文字被它往左顶。实测 14px。

P3 · 排序中的列 · +11px

箭头一出现, 右对齐表头再左移

主表箭头是文字标签的同行内联兄弟。左对齐列箭头长在文字右侧(不影响起读位置), 右对齐列则把文字整块往左顶。实测: 种子页「大小」未排序偏移 11px, 点一次排序后变成 22px。

不受影响 · 无需动作

抽屉 Tracker / 用户 / 内容三表与 HR 波次表②、拉取历史表③: th/td 内边距同值、表头无箭头 ⇒ 右对齐实测偏移 0。左对齐列全站 ≤1px。

§3根因

两处都是「为另一个功能预留的空间」泄漏进了文字排版 —— 不是对齐口径(哪列该左/该右)错, 口径是健康的、单点的。

根因 ①: 拖拽把手需要 10px 命中区, 于是整个表头格子被加了 10px 右内边距

表头把手 .h-cell .resizer 必须完全落在 .h-cell 之内 —— 因为 .h-cell 有 overflow: hidden(给列名省略号用), 把手伸到格子外会被裁掉、点不到(星图主题里有一条注释专门记着这个坑)。于是三条规则串成了一个必然结果:

  • .group-head { padding: 7px 14px } 与 .group-row { padding: 10px 14px } 同值 ⇒ 表头与数据行的「列盒子」位置一致(这一层是对的);
  • .h-cell { padding-right: 10px } 只有表头有 ⇒ 表头格子的内容盒右缘比列右缘缩进 10px;
  • 值格子(.g-stat / .m-stat)的 padding-right 是 0 ⇒ 值文字正好落在列右缘。

右对齐时两者都贴着「各自内容盒的右缘」, 于是差出 10px。左对齐时都贴着左缘(表头左内边距为 0) ⇒ 看不出来。这就是为什么只有右对齐列被反馈。

根因 ②: 排序箭头用 opacity: 0 藏, 而不是从布局里移除

主表的箭头写法是 <span v-if="col.sortable" class="arrow"><svg v-if="已排序"…> —— 未排序时 <span> 为空、宽度 0, 只在真正排到该列时才占 11px。HR 表①少写了内层 v-if(箭头 SVG 恒在 DOM), 靠 CSS opacity: 0 隐藏; 透明度不影响布局 ⇒ 表头标签右缘恒被左顶 11px + 3px。

同一机制在主表上表现为 P3: 右对齐列一旦成为当前排序列, 箭头现身, 标签再左移 11px —— 用户会看到「点一下排序, 标题跳一下」。

§5修改范围

按「改哪几个文件、各几处」给两套方案。P1/P3 与 P2 是两件独立的事, 可以分开做。

P1 + P3(主视图 4 表 × 3 主题)

A1最小方案 —— 只改 1 个文件。shared/columns.js 的 colAlignCss()(约 :652-663) 已经按列生成 :where([data-table="X"]) > :nth-child(N) 规则、且同时命中表头与值格。对 align==="right" 的列追加 padding-right: 10px 即可 —— 表头格子本来就有 10px(无变化), 值格子由此获得同一右槽, 两边文字同缘。残余 ≤1px(数据行的 1px 侧边框)。三主题共用一份列模型 ⇒ 一处改、三套全好。
A2代价与取舍(必须知情)。右对齐列的内容宽各少 10px; 数值与右邻列文字的间距 +10px。换来的是把手命中区依旧不压文字(若反过来把表头 padding-right 归 0, 右对齐表头最后 10px 会变成拖拽区 —— 点标题会被判成拖宽)。
A3P3 单独修: 右对齐列的箭头排到文字左侧。同一处生成逻辑追加「右对齐列的 .arrow 取 order:-1」, 并把 .h-cell 变成 flex 容器(三主题各 1 行)。这样排序时标题不再左右跳。

P2(设置页 HR 表①)

B1模板 + 主题 CSS 各 1 处。tpl/settings-detail.html:321-324 给箭头补 v-if(仅当前排序列渲染)—— 最省事, 但排序列切换时标题会左右跳(与主表 P3 同形); 更稳的做法是让箭头绝对定位不占流(th 补 position:relative), 触点是三主题 .hr-detail-table th .arrow 各 1 条: atlas/css/dialogs.css:172 · console/css/dialogs.css:165 · prism/css/views.css:664。

P0(可选 · 彻底方案, 建议单独立计划)

C1把「把手槽」与「文字排版」解耦。让 10px 只存在于把手需要的地方: .h-cell 的省略号下移到内层标签 <span>, .h-cell 自身 overflow: visible; padding-right: 0, 把手挪进 grid 的 10px 列间距里(半进半出)。需动 5 个表头块 / 3 个模板 + 3 主题 CSS + columns.js 的箭头顺序; 好处是数值列不再损失 10px 宽、语义上也更正确。风险与工作量都明显更高, 不建议与本次混做。

§7附带发现与边界

  • 与上一份审计的关系: 26-09-28-2345 列对齐审计 判定主表「机制健康」指的是对齐口径单点化(哪列该左/右只写在列模型里, 表头与值同源注入)—— 那一层确实健康。本件补的是它没验的那一层: 口径一致 ≠ 几何对齐。该报告结论不推翻, 但「表头与值同源 ⇒ 不会错位」的推论需要修正。
  • 0 值居中(既有口径): .g-stat.zero { text-align:center } 让「值为 0」的格子居中, 而表头仍是右对齐 —— 用户截图里的「可用性 0.00」正是这一条。这是 2026-09-17 拍板的既有口径(0 值只留极淡占位、居中避免满屏噪声), 但它与「右对齐列标题要对齐」的诉求直接冲突, 需要一次明确的取舍(要么 0 值也右对齐, 要么接受 0 值列看起来没对齐)。本件不擅自改。
  • 中心列的量法: H&R / 站数 / 版本 三个居中列用「左缘差」量会得到 −7 ~ −14px 的假错位(居中时左缘随内容宽度变化), 正确量法是比中线。本轮未发现居中列的真实缺陷。
  • 数值溢出是另一回事: 个别值(如 299.00 KiB/s)宽于列宽时会被省略号截断, 墨迹右缘量值会偏出 10px —— 那是列宽/省略号问题, 与本次对齐缺陷无关, 本件不并入。
  • 未做: 未改任何代码、未入池 issue、未提交。修法需要先拍板 A2 的代价与 0 值口径。
