一句话结论：这不是一次「数据获取」工程，而是一次「时序记录」工程——主循环每 1.5s 的增量同步早已把三张图需要的每一个实时数字搬进了内存，本报告核对的全部工作都在「把它们按时间存下来、按曲线吐出去」。真正的三个决策点是：时序落点（state v4 vs 独立文件，推荐 state v4）、停机空洞表达（null 断线，不补 0）、分组换 key 后旧历史（推荐不保留）。

口径先行：本报告的「qB 流量」与既有「Traffic Monitor 全局流量」是两套数据源、两种口径（§02 划界）。相关 issue 26-10-01-2138 正是因混淆两者被静态核验结案（Dropped）——该 issue 提出的问题实为真需求，本报告即为它的正式可行性回答。

02需求口径与划界

2.1 三图定义（仅展示，不入规则）

#图口径数据来源挂点
①qB 全局实时流量图 qB 进程整体的上/下行速率与累计（会话 + 终身），近 24h 高分辨率 + 30 天小时均值 qB server_state（dl_info_speed/up_info_speed 瞬时；dl_info_data/up_info_data 会话累计；alltime_dl/alltime_ul 终身累计），每轮 sync 已在内存 今日流量面板弹层（与既有历史流量弹层同族）
②单种子流量图 单个 torrent 的速率曲线与累计增量，仅对该种子处于活跃期采样 TorrentRecord 已有 dlspeed/upspeed（瞬时）+ downloaded/uploaded（all-time）+ downloaded_session/uploaded_session（会话） 种子详情抽屉新增「流量」页签
③辅种分组流量图 组级聚合速率/累计曲线；分组键 = 内容指纹，跨重启稳定 组级流量聚合已存在（_build_group_view 每 tick 已 sum dlspeed/upspeed/uploaded/downloaded），以组 key 为键做时间序列 分组弹层

三图精度要求低、采样率低（30–60s 档），不做实时仪表盘；仅展示，不喂给规则引擎。

2.2 划界：Traffic Monitor 全局流量 ≠ qB 流量

既有：Traffic Monitor 全局流量（不动）

  • 数据源 = 外部程序 Traffic Monitor 拥有的 history_traffic.dat，本程序只读（src/auto_qb/config/models.py:270-274，src/auto_qb/core/curves.py:3-8）
  • 口径 = TM 自采的机器级每日累计（每行「某日已累计上传/下载量」），按天/月/年聚合
  • 链路：speed_curve 每轮整文件读入（speed_curve_mod.py:142-157）→ 快照经 ctx.web.set_traffic_view() 整体替换（runtime.py:233-240）→ 端点 GET /api/traffic/history（routes/state.py:108-117）→ 前端自绘 SVG 柱状图（shared/dialogs.js:549-858）
  • 聚合语义：窗口内缺失日视为 0、不补点（curves.py:76-92）——这是「聚合」口径

本报告新增：qB 口径三图

  • 数据源 = qB WebUI API（本程序已有的同步链路），不依赖外部程序
  • 口径 = qB 进程视角：瞬时速率（秒级语义）+ 会话累计 + 终身累计；单位与采样时刻以 qB 为准
  • 时间语义 = 连续时序曲线（速率），不是「按日聚合柱」；停机期是空洞不是 0（§10-①）
  • 与 TM 图并存不替代：TM 图继续服务「限速曲线的数据源展示」，qB 图服务「qB 到底在跑多快」

2.3 相关 issue 的来龙去脉

26-10-01-2138（question · webui-traffic-history-chart，Dropped）问的是「WEBUI 流量历史图做不做」。静态核验时，既有「历史流量图」（/api/traffic/history，TM 数据源）被误当成「qB 流量图已存在」，该 issue 遂被判定为已覆盖而 Dropped。实际上 TM 图是外部数据源的每日累计柱状图，与该 issue 想要的 qB 口径实时/时序流量图不是一回事（§2.2）。本报告在口径上把两者划清，并作为该问题真需求面的正式可行性结论。

2.4 非目标与边界

  • 不恢复「以种子流量统计作为规则条件」功能：upload_size 四条件 + begin_round 统计底座已随计划 26-09-27-1232 移除，其重设计归主 issue 26-09-27-1248（Open）。本报告三图是纯展示层，不向规则表达式暴露任何新变量。
  • 与统计重设计互不阻塞：主 issue 若落地自己的统计口径，三图的采样管线可复用其产出；三图先行不预判其结论。两者共享的唯一假设是「TorrentRecord 的流量字段可信」——这已是现状事实。
  • 不做数据导出 / 长期归档 / 跨设备汇总：30 天窗口是产品决策上限（拍板点③）。

04外部调研

标记约定：【官方】= 官方文档/源码证实；【社区】= 社区/第三方经验。

4.1 qB API 字段语义

  • 种子级累计的两种口径【官方】：/torrents/info 的 uploaded/downloaded = all-time 口径（无 session 后缀）；uploaded_session/downloaded_session = 本会话。（WebUI-API (qBittorrent 5.0) wiki）
  • 单种 all-time 疑似跨 qB 重启持久：libtorrent add_torrent_params::total_uploaded/total_downloaded 随 write_resume_data 序列化【官方】（libtorrent reference-Add_Torrent）+ 社区实测 fastresume bencode 含 total_uploaded ⇒ 单种累计跨 qB 重启持久（源码级证据强，无一句话官方文档，列待真机验证，§11-①）；删种重加归零。
  • 全局量【官方·源码】：/transfer/info 的 dl_info_speed/up_info_speed = 瞬时速率，dl_info_data/up_info_data = 会话累计（重启归零）；server_state 与 /transfer/info 是同一对象，另含 alltime_dl/alltime_ul 终身累计（qB 源码 sessionstatus.h + 前端 statistics.js）。alltime 持久化在 qBittorrent-data.ini 周期落盘，非优雅退出可能回退【社区】⇒ 全局长段累计曲线不能依赖 alltime 差分做唯一口径，须自采样基线 + max(0,·)。
  • qB WebUI 无任何历史/统计端点、无单种速度历史 API，必须自采【官方·源码】（src/webui/www/private/scripts 无图表脚本；对照 qB 桌面端有速度图而 WebUI 没有）。
  • rid 增量语义【官方】：rid 变化 full_update；断线重置 rid=0 拉全量——与本项目 store 的 reset_sync 行为一致（store.py:168-176）。

4.4 采样与存储的业界口径

  • Prometheus 标准口径【官方】（querying/functions）：存累计快照、展示前差分，计数器回落按重置处理。本项目落地：存储累计快照 + max(0,·) 差分 + last 只在进程内推进；组键换手（删重加/换指纹）必须重置该组基线。
  • 两条都存：速率优先（dlspeed/upspeed 瞬时值）做高频段 + 累计差分做长段。
  • 存储取舍：内存环 + 周期 flush 进 state.json 零新增机制（崩溃丢 ≤2min）——推荐；追加式 dat 每组一文件管理成本涨（方案 C）；SQLite 干净但第二套存储心智。
  • 数据量估算：30s 采样 30 天 = 86,400 点/系列 ≈2.2MB/组，不可全量存原始；分层后：近 24h 内存环 @30s = 2,880 点（可丢）+ 30 天小时 rollup（avg+max）720 点 ≈32KB/组/30天；100 组 ≈3-4MB JSON 单文件原子写可行。

4.5 停机空洞表达

惯例：停机/断档写 null 不写 0——0 会把「没运行」画成「没流量」，是反模式【社区/业界共识】。默认断线；spanGaps/connectNulls 可设最大跨越（Chart.js/uPlot/ECharts 均支持）。注意与 TM 图「缺失日=0」划清：那是聚合语义（窗口内缺失日不贡献流量），不适用于时序曲线。

06方案对比

6.2 前端选型小节（两个子选项）

子选项 1：vendor uPlot 单文件

  • 21.9KB gzip，IIFE 单文件进 static/shared/vendor/，与 Vue3 vendor 同模式，无构建链兼容
  • 3600 点 60fps ≈10% CPU；原生 null 缺口（停机空洞表达免费拿）
  • 无内建 LTTB ⇒ 数据侧自降采样（参考实现 ~90 行）；options 样板多（一次性封装成双系列组件后三图复用）
  • 适合：要时间窗缩放 / 十字线联动 / 后续加系列

子选项 2：继续自绘 SVG

  • 0 体积、完全可控；dialogs.js:549-858 既有历史流量弹层就是可仿写先例（含 hover 取值、天/月/年切换）
  • 三图都是双系列（上/下）数百~数千点，自绘绰绰有余
  • null 断线渲染需自己处理（跳段路径），hover 取值/缩放自造
  • 适合：只要「静态浏览 + hover 取值」——与既有弹层交互水平对齐

判据：两者在数据量上都无压力，差异在体积与交互开发成本。若产品预期只是「看一眼趋势」（与既有弹层同级），自绘与现库一致且零依赖；若预期要缩放/细看某小时，uPlot 一次封装长期受益。→ 拍板点②。

07推荐方案：A

推荐：方案 A（后端统一采样管线 + 内存环 + 小时 rollup + state v4）。理由：

1. 唯一同时满足「30 天历史」与「单一写线程」约束的方案——采样挂 internal 全局任务在主循环线程执行，state.json 是既有落盘单点（原子写 + .bak + 版本链），黄金法则 3/5 全部沿用既有机制，零新增并发模型。

2. 数据量在单文件原子写的舒适区：100 组 30 天 rollup ≈3-4MB，对照 state.json 现有载荷量级可控；内存环把高频段挡在落盘之外，崩溃丢窗口 ≤ state_save_interval（默认 120s）。

3. B 不满足需求（历史丢失），C 买错了先例（TM 的 dat 是外部只读文件，自产追加式 dat 引入线性文件数 + 半行容错 + 独立清理三个维护面，违背「状态持久化统一进 state_file」的黄金法则 3）。

4. 成本可控且可分期：4-6 人日可拆成 5 个独立可提交单元（§12），每段都有独立验收判据，随时可停在任意阶段不烂尾。

同时明确：方案 A 的实施以 §08 拍板为前提——5 个决策点中任何一个换向（尤其 ②④⑤）都不改变「可行性成立」的结论，只改变设计草案的对应段落。

09设计草案（按方案 A 展开）

9.1 采样器挂点与采样内容

  • 挂点：internal 全局任务，仿 speed_limit_curve 经 subscribe("queue_rebuilt") 自注册，REQUEUE 按 interval 周期重入队（taskqueue.py:27, 59-75, 156）。interval = 拍板点③（建议 30s）。在主循环线程执行——state 写点天然单线程（state.py:8-9），无锁。
  • 全局系列：读 store.server_state —— dl_info_speed/up_info_speed 瞬时值入环；alltime_dl/alltime_ul + dl_info_data/up_info_data 存累计快照（Prometheus 口径：存快照、展示前差分）。
  • 单种系列：只对活跃种子（dlspeed>0 or upspeed>0 或状态 active）采样，避免全库 86,400 点 × N 的爆炸；非活跃期不产生采样点（展示层为断线）。
  • 分组系列：复用 _build_group_view 的组级 sum 结果（views.py:404-485），以组 key（grouping_mod.py:41-49）为序列键，不重算。

9.2 差分与基线重置规则

  • 速率 = last 只在进程内推进：rate = max(0, cur - last)；cur < last（qB 重启会话归零 / alltime 回退 / 删重加）⇒ 判定为计数器重置：基线重置为 cur，该窗口记 null（不产伪速率）。
  • 基线重置显式触发（与隐式回落判定双保险）：组键换手（删重加/移动目录/增删文件 ⇒ key 变化）⇒ 新 key 从零起；种子删除 ⇒ 该 hash 系列清除（对齐 field_snapshots 删种即清先例，store.py:291-307）。
  • 高频段（24h 环）直接存 dlspeed/upspeed 瞬时值，不经差分——瞬时值对重启归零免疫，两条腿互为校验。

9.3 内存环 + rollup 结构

内存（每系列）：
  ring_24h   @30s   上限 2,880 点/系列   纯内存，崩溃可丢（口径声明）
  采样点 = { t, dl_rate, up_rate, dl_total, up_total }   # 速率直存 + 累计快照并存

落盘（state["qb_traffic"]，state v4 新增顶层键）：
  rollups:  key → [ { hour, dl_avg, dl_max, up_avg, up_max }, ... ]   # 720 点/30天 ≈32KB/组
  baselines: key → { dl_total, up_total, updated_at }                 # 差分基线（进程内推进，落盘仅供重启后接续）
  meta:     { sampled_at, interval_s, window_days }                   # 自描述，服务迁移与排障

体量：100 组 ≈ 3-4MB JSON；随 maybe_flush 周期落盘（默认 120s ⇒ 崩溃丢 ≤2min rollup 增量）
  • rollup 在内存环滚动过期时归并产生（每小时封口一条 avg+max），环本身不落盘——写放大最小。

9.4 state v4 迁移草案

  • CURRENT_VERSIONS["state"] 3→4（infra/versioning.py:29-34），迁移函数落 config/migrations.py 同级机制；纯加法迁移：旧 state 无 qb_traffic 键则补默认结构，无存量数据转换，风险低。
  • 清理策略与键位纪律（吸取既有教训）：speed_limit_curve[date] 无界增长（speed_curve_mod.py:272-278）是前车之鉴——qb_traffic.rollups 按 30 天滚动窗口清理（按日清理先例 ops_mod.py:365-367）；单种系列不落盘（24h 环纯内存即满足观察需求）或按 hash 清理（先例 store.py:291-307），杜绝新键复刻无界增长。
  • 纳入版本链判据自查（versioning.py:5-9）：state v4 是「程序读回且结构演化」——成立。
