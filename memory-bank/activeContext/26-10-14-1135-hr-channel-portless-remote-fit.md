## 本轮结论(报告 §01 速览)

- 两份文档解两个轴: 跨机计划 = 空间轴(端点绑哪/传输/鉴权); 去端口报告 = 配置轴(零配置/端口随机/token 分发)。交集 = 连接模型, 而计划数据流本就是「扩展拨后端」, 与「只有扩展能发起」的硬事实不冲突。
- 路线 A: 跨机配置面从「端点 URL + token」缩为「NAS 地址」(唯一不可消除项); token 不再跨机器搬运; §7.2 五条不变项逐条保持; 数据端口随机 = LAN 端口扫描净改善。
- 路线 B: 桥进程只能跑在外部 PC, 仍要经网络拨 NAS ⇒ NAS 地址/token/传输信任一项少不了, 却多付桥组件 + 注册表注册; 打破轮询不变项、新增离屏文档面。缓行, 不并入计划。

## 关键新发现(本轮取证)

- **扩展 manifest 无 `key` 字段** ⇒ 未打包安装的扩展 id 随安装路径变化 ⇒ 跨机多 PC 时两台机器扩展 id 不同, 钉单 `extension_id` 会挡住第二台 PC(计划 D4「同一扩展装多台同 id」的假设对未打包安装不成立)。缓解: 打包固定 key, 或留空 extension_id + 配对码把关。
- 发现端点免 token(它发 token) ⇒ 非回环可达时是 LAN 上的 token 分发器 ⇒ 配对码语义应从「默认关」反转为「同机可选、非回环强制」(镜像计划「非回环+空 token ⇒ 报错」的安全默认范式)。
- 随机数据端口与 SSH 隧道/反代静态转发天然冲突 ⇒ 隧道/反代用户保持显式端口(= 完全旧行为, 不受影响); 若要他们也拿到 token 自动分发, 需 `advertise` 覆盖键(开放设计点)。
