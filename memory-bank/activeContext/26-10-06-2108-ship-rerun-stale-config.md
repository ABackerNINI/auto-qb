# 自我改写后仍用启动时那份配置 — commit 的闸门复跑 + sync 的生成物自动化解

> 摘要: 另一会话报出的**计划外引擎缺陷**(撞迁移窗口必现, 平时不可见): 流水线自己会把远端新版
> `.my-commit-flow.toml` rebase 进工作区(本包目录就在仓库里), 而进程手里那份 `cfg` 还是**启动时**读的。
> 两处受害 —— ①`ship.commit` 的闸门**复跑**照跑, 只是规则不对(旧闸门集 / 旧 `each_limit` / 旧红线),
> 输出与"全过"**一字不差**; ②`sync.py` 的生成物自动化解用旧白名单 / 旧重跑命令**丢本地内容**。
> 修法 = 树被改写后按**磁盘现版本**重取配置(`_pipeline.reload_config`, 含 STOP 级复检)。
> 最后活动: 2026-10-07 01:38

**Refs:** memory-bank/tasks/26-10-06-ship-rerun-stale-config.md

## 现状

- **机制单点**: `_pipeline.reload_config(cfg) -> (配置, 停止原因)` —— 交出**磁盘现版本**, 并**复检 STOP
  级问题**; 读不到 / 新配置有错 → 返回原因且调用方**必须停下**(返回值是旧 cfg, 仅占位不可用)。
- **commit 侧**(第一轮): `commit.py` 第 6 步(内部同步真改写 HEAD)复跑闸门**之前**; 顺序不可反 ——
  ① `refresh_package_modules()`(让 `_ship_config.KEY_DEFAULTS` 跟着现版本, 否则远端新加的键撞旧白名单
  被按「顶层未知键」误判 STOP) → ② `reload_config(cfg)`。配置变了登记
  `闸门复跑: 合流后 .my-commit-flow.toml 已更新 → 按新配置复跑`(没变静默); 复跑仍按**同一份改动清单**
  (`present`, 设计如此), 但 `ctx.each_limit` 跟着新配置走。
- **sync 侧**(第二轮): `sync._reload_cfg(cfg)` = `reload_config` + "新配置仍允许自动化解" 两档判据;
  **三个取用点** —— 快进路径 `merge --ff-only` **之后**(并**按新白名单复核"已丢弃的那几处"**)、
  分叉路径**每轮 rebase 循环开头**、分叉路径**收尾**(白名单随之换新, `dirty` 用新白名单)。
  任一档不成立 → **放弃自动化解、回滚**, 退回**现状失败行**(自动化解是优化, 不新增失败模板)。
- **两个不变**: `--no-push` 不同步 ⇒ 无复跑、无重取; 复跑的清单不重算成"合流后全部 diff"。
- **守阵 10 条**: `test_pipeline.py::ReloadConfigTest` 3(机制) + `test_commit.py` 3(接线) +
  `test_sync.py` 4(机制 1 + 快进 2 + 分叉 1)。**红验五处**均已还原。
  ⚠ sync 侧夹具必须把配置放进**仓库里**(`<repo>/pack/.my-commit-flow.toml`) —— 临时包目录在仓库外,
  rebase 换不掉它, 那样的用例测不到本缺陷。
- **验证**: `test.pkg` **141 passed**(第二轮基线 137, +4); `test.full` 见基线切片(零 `src/` 改动)。

## 关键决策

- **不把 `load_config()` 挪一行了事**: 远端新配置若同时**加了新键**, 进程里的旧 `KEY_DEFAULTS` 会把新键
  静默丢掉, 又被 `config_problems` 判「顶层未知键」STOP ⇒ 假红。所以必须**先刷新模块再重取**。
- **两侧的"停"不同**: commit 侧按「推送未完成」(提交已落稳, 退出码 0); sync 侧**放弃自动化解、回滚**后
  退回现状失败行 —— 自动化解是优化, 不为它新增失败模板(所以这一步对调用方是静默的, 只能靠守阵发现)。
- **sync 侧分叉路径**要"每轮"重取, 不只一次: 每轮 `rebase --continue` 都把树往上推了一笔, 配置可能再变;
  收尾那次针对的是"最后一笔重放的是本地提交, 它也可能改了配置"。
- **不加开关**: "复跑前重读配置"没有可关的正当场景(拿旧规则验新树无意义), 加开关只会多一个能被关掉的旋钮。
- **放 `_pipeline` 不放调用方**: `config_stops`(配置体检)本就在 `_pipeline`, 且与
  `refresh_package_modules` 同族同家 —— `_pipeline` 的定位正是"内部共享件"。

## 未闭环

- **`commit.py` 自己的旧绑定仍是老问题**: 刷新发生在 commit 进程内, 它已导入的
  `run_gates` / `git_run` 在整个进程内保持启动那版 —— 当前安全(`_pipeline` 两版函数对 commit 的用法等价),
  但同步改签名与改包脚本加载逻辑别同批。
- **`_reload_cfg` 的"停"对调用方是静默的**: 新配置关掉自动化解 / 有 STOP 级问题时, 用户只看到
  `需解决冲突 …` 或 `树脏挡路 …`, 不知道自动化解为什么没生效 —— 按现状失败行逐字不变的契约,
  本轮**没往失败行里加原因**; 若将来觉得这条解释值得, 得先改 v3 的行模板契约。
- **`activeContext/` 切片数债务**(上限 70): 本轮沿用同一张切片(未新增), 计数不变 —— 机检判为**债务**
  (不拦提交)。按治理纪律(单点 `pitfalls/kb/cap-counting.md`)不在本会话清理, 转告用户另开会话处置。
  `doc.caps` 本身无债务。
