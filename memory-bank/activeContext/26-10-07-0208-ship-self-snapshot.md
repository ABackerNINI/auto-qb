# my-commit-flow 自我改写版本撕裂 — 快照自举可行性验证与治本方案

> 摘要: 本包脚本与配置住在它自己中途改写的仓库里 —— `ship.commit` 内部同步的 rebase 会把远端新版**包脚本 / 配置**
> 换进工作区, 于是同一次调用里"提交前"与"提交后"跑的可能不是同一版代码 / 同一份规则。既有修复
> (`reload_config` + `refresh_package_modules`)逐点打补丁, **治标**(5 处漏洞: 入口脚本无法热刷新 /
> `importlib.reload` 不重绑已导入名 / 配置重取只两点 / 无全局不变量 / 门控脆弱)。用户提议「整包复制到临时目录运行」,
> 本轮**只做可行性验证 + 出报告, 未改生产脚本**: 对真实包注入快照机制原型, 真仓端到端 **10/10 通过**
> (核心 = 改写原包后旧副本免疫、新调用采纳新版), 复制开销 avg 26.2ms。结论: **快照自举可行且为最优解**,
> 采纳「快照语义」= 一次调用只认一个版本。

## 现状

- **缺陷定性**: 自指(self-reference) —— 工具的源码/配置住在被它自己操作的仓库里, 而工具运行中途会改写这棵树。
  危害两族: **模块缓存族**(`ImportError`, 报出来) / **配置快照族**(闸门照跑但规则不对, 静默)。
  用户说的"一部分按更新前、一部分按更新后"正是撕裂本身。
- **既有修复覆盖边界(5 处漏洞)**: ①入口脚本(`commit.py`/`verify_ref.py`)作为 `__main__` **无法热刷新**;
  ②`importlib.reload` 只换模块对象, `commit.py:52` 的 `from _pipeline import …` 旧绑定不变 ⇒ 复跑仍调旧闸门引擎;
  ③配置重取只 `commit.py:255` + `sync._reload_cfg` 两点; ④逐点接线无全局不变量(已修两轮, 无法闭环);
  ⑤`refresh_package_modules` 的门控 / 依赖序本身脆弱。
- **方案选型**: A 临时目录快照 + 重入(**采纳**) · B 移出仓库(否) · C git worktree(否) ·
  D 拒绝自我改写(降为**提示**, 并入 A) · E 两段进程(否) · F 继续打补丁(否)。
- **可行性证据**: 原型 `tmp-analysis/mcf-snapshot-proto/`(临时区, 不入库)对真实包注入快照机制, 真 git 仓实测
  **10/10 通过** —— T1 端到端提交 / T2 副本在仓库外 / **T3a 免疫** / **T3b 采纳** / T4 `import` 不重入 /
  T5 信息入口作用原包 / T6 根解析 / T7 退出码透传。复制 16 文件 avg 26.2ms。
- **产物**: 报告 `memory-bank/reports/26-10-07-0208-report-my-commit-flow-self-snapshot.html`(含 `_snapshot.py` 全文)。

## 关键决策

- **快照语义(一次调用 = 一个版本)**: 启动时复制、从副本重入 ⇒ 中途 rebase 写进工作区的新版本对**本进程不可见**,
  从**下一次调用**生效。与"引擎不能中途换零件"同构, 简单可预测, 一次性消灭整类撕裂。
- **放弃"复跑用新规则"**: 那正是撕裂来源且永远补不全; 改为 rebase 后若发现本包被上游改动 → 登记一行步骤行
  提示重跑(**不静默**) —— 这是 D 方案降级为提示后的形态。
- **重入用 `subprocess.call` 而非 `os.execv`**: Windows 上 exec 语义不可靠(不真正替换进程 / stdio 继承有坑)。
- **纯信息入口不复制**: `--help` / `-h` / `--safety` / `--show-config` / `--init` 直接作用原包 ——
  尤其 `--init` 要把配置写进真包, 不能写进临时副本。
- **必须同步改 `_ship_config.find_root()`**: 副本在仓库外, 向上找不到 `.git`, 得认 `COMMAND_FLOW_REPO_ROOT` 注入。
- **闸门(外部工具)仍跟仓库走是对的**: 闸门要测**被测的树**, 每次都是新进程、内部一致; 必须固定的只有流水线自身。
