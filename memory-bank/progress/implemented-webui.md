- **WEBUI 强制汇报混选投递收敛**(2026-10-10; 档案同上 [26-10-10-webui-reannounce-inactive-gate](../tasks/26-10-10-webui-reannounce-inactive-gate.md)): 用户追问「多选时"任一可汇报即可用", 目前的方案会不会导致混选时汇报非活跃种子?」—— 成立, 但**危害判断修正**: 请求层确实全量投递(闸门是集合级全有全无), 真正的代价不在"汇报"(qB 引擎 `force_tracker_request` 对暂停/排队种子本就空转, qB 自己也是照发全选)而在**我们自己的确认层** —— 非活跃目标进 `_register_reannounce_pending` 后 tracker 永不前跳, 白等到 item deadline(上限 600s)落「未确认」, 前端三桶聚合把一次干净的成功渲染成 `成功 1, 未确认 3`(qB 的 GUI 无 per-target 回执, 故不显此症)。用户三项拍板(收敛为活跃子集 / 前后端双保险 / 回执体现跳过数)后补**第二层**: 前端单点 `decorate.js::reannouncePlan`(判"发给谁"; 解析面与闸门同源 `_findGroup`/`memberByHash`, 组目标展开为活跃成员 hash, 解析不出的原样交回不静默丢)+ `_actCore` 按计划投递(目标计数改用实际投递数, 跳过数非零时在**等待态就缀「跳过 N 个非活跃」**, 空投递显式收口不再报「成功 0 个目标」)+ 后端 `commands.py` 模块级 `REANNOUNCE_BLOCKED_STATES`/`reannounce_blocked()`/`_reannounce_active()` 与两个 `_cmd_reannounce_*` 过滤(**第二道闸**: 防竞态与直连端点; 全非活跃给显式 warn 回执)。⚠ 后端判据**不得**用 `state_enum` 谓词(实测 `queuedDL`/`queuedUP` 命中 `is_downloading`/`is_uploading`, `paused*/stopped*` 才是 `is_stopped`), 必须判 `rec.state` 原文 —— 守阵钉前后端两表逐项同表。测试桩 `helpers.py` 补 `reannounce_hashes_calls`(同 `recheck_hashes_calls` 模式); 新单测 `test_reannounce_skips_inactive_targets` + 注册直判用例改造(其 (a) 支降级为竞态兜底)+ 守阵扩段 + e2e 混选双皮肤(**按 hash 断言不数条数** —— 桩 300 种子/150 组, 两行必同组)。三轮红验全过。机理 → [pitfalls/web-ui/reannounce-inactive-gate.md](../pitfalls/web-ui/reannounce-inactive-gate.md) 末节「闸门 ≠ 投递集合」。基线见 kb.baseline 最新一条。
