## 原始请求

> 设计一个独立测试, 仿真客户端, 5000种子, 每1.5秒活跃10%, 主要用于测试安全/性能, 分析可行性, 列计划

评审中确认的四项口径: ①「活跃 10%」两种语义**都做可切换**(`churn` 滚动换批默认 / `steady` 固定活跃池); ②仿真形态**分析利弊**后定(结论: 独立 HTTP 服务); ③**不进 CI**, 手动跑; ④**先纯外部观测**, 不动 `src`。

## 思考过程与决策

- **先探针后计划**, 不凭直觉排期: 5000 种子规模的性能瓶颈位置无法靠推理确定(可能在网络、可能在序列化、可能在任务队列)。临时探针(`.workbuddy-ai/tmp/sim_probe*.py`, 一次性不入库)用真实 `qbittorrent-api` 走回环 HTTP 实测, 拿到四个决定性数字 —— ①全量载荷 8.77 MB / 端到端 205–240 ms; ②增量(500×8 字段)107 KB / 端到端 3.3 ms, **差 62 倍**; ③朴素全量 diff 22.6 ms vs 脏集合 0.34 ms(**67 倍**); ④单次回环请求 2.27 ms。
- **结论一: 同步层完全不是瓶颈**, 稳态每轮≈4 ms 占 2 s tick 的 0.2%。计划里因此把观测重心从 sync 挪走。
- **结论二: 真正的压力在首轮与任务吞吐**。`grouping.py:143` 的 `_assign_new_torrent` 对每个新种子发一次 `torrents/files`(5000 次 ≈ 11.4 s), 新种子的内置 maintenance 是**立即执行**而非入队(≈1 万次写 ≈ 22.7 s)⇒ 首轮约 34 s 主循环停摆。这不是测试假象: 真实 qB 装 5000 种子启动时行为一致, 且真实 qB 更慢。安全侧同样是「批量写风暴」, 正是"保守默认"要防的情形。
- **结论三(产品级)**: `max_tasks_per_tick=20` 下, 5000 种子 ×(1 maintenance + R 规则) 使规则实际执行周期被稀释到 8 min(R=0)/ 25 min(R=2)/ 50 min(R=5), 而用户配置写的是 60 s。本阶段只测出并记录, 不动代码。
- **探针踩到的坑即是设计约束**: `sync/maindata` 的 `rid` 在 **POST body** 里, 只解析 query 会恒得 `rid=0` ⇒ 服务端永远回全量。故仿真端必须 body+query 合并解析(与既有 `FakeQbServer` 同口径)并用单测锁死。
- **形态取舍的本质是"要不要保留真实协议栈成本"**: 恰恰是这段成本构成 62 倍差异, 所以"跑得快的进程内 Fake"不能用来出性能数字。定案: **独立 HTTP 为主**(auto-qb 子进程接入、源码零改动、安全断言有服务端写台账作硬证据); **进程内版不作为交付物**, 只在 W5 需要 tick 内部剖面时临时用。
- **安全断言的证据源放在被测进程之外**: 全部 S 场景判据归结到服务端 JSONL 写台账的查询, 不读 auto-qb 日志自检。dry-run 场景配 `--read-only`(写端点回 403 但仍记账), 既拿到"确实发了"的证据又不污染服务端状态 —— 与既有 `tests/sidefx.py`「测试期禁止真实系统副作用」同一思路, 搬到进程外。
- **不复用 `test_yamls/`**: 测试配置由驱动器在临时目录动态生成, 避免又多一份要维护的配置。
- **1.5 s 节拍与 2 s tick 不刻意对齐**: 作为默认场景(客户端比我们快, 更接近真实), 每轮实际看到≈667 个变化种子; 另给 1.5 s 对齐档做 1:1 对照。

### 2026-09-19（第三轮 · 指定目录 + R 盘边界）

- 用户追加: 仿真加**指定目录**功能, 所有测试文件放到该目录, **平时在 R 盘跑**。
- **`--root` 工作根**(默认 `R:\auto-qb-sim`, 环境变量 `AUTOQB_SIM_ROOT` 覆盖): 虚拟文件树 / 本次配置 / auto-qb 的 `data_dir`(state.json·锁·程序日志) / 两层日志 / 报告, 全部落在 `<root>/runs/<时间戳-场景ID>/` 下, 不再散落到系统临时目录。R 盘不存在(换机器/Linux/CI)时自动回退临时目录并记 `ROOT_FALLBACK` WARN, **不硬崩**。`--fs-reuse` 可复用文件树省建树时间, 但 **D 系列强制重建**(复用被删过文件的树 = 脏现场)。
- **R 盘即真实下载盘 ⇒ 删除必须硬边界**(B1–B4, 任一不过即拒绝): B1 `--root` 不得是盘根目录或真实下载目录, 必须是新建空目录或含哨兵 `.auto-qb-sim-root` 的目录; B2 每次删除前 `os.path.realpath` 归一并断言在 `<run>/fs/` 之下(防 `..` 与符号链接; Windows 需同时处理 `\\?\` 长路径前缀与大小写); B3 单次删除数量上限(≤ 场景声明 × 2); B4 收尾核对 `fs-after.txt`, 预期外缺失进 `unexpected_removals` ⇒ `verdict=FAIL`。**W1 就要带单测**, 不是等出事再补。种子 `save_path` 一律指向树内, 绝不指向 `R:\Downloads`。
- **修正初稿一处错误**: 原定"只物化 300 个种子"是错的 —— 未物化种子的 `save_path` 在磁盘上不存在, 缺文件扫描会把它们**全判成文件丢失** ⇒ 约 4700 个种子被误打 MISSING 并整组暂停, D4 的"组内停止率 100%"彻底失去意义, 首轮还多出几千次多余 stop 写。改为**默认全量物化**(每种子 1 个 4 KiB 占位文件, 辅种群共享; 约 4300 文件 / 17 MB, 建树数秒); `--fs-materialize 0` 保留为降级开关但仅限不开分组的场景。
- 风险表补 R12(未物化误判缺文件) 与 R13(运行目录累积占满 R 盘 ⇒ `--keep-last N` 默认保留最近 10 次); 验收补 B1–B4 单测与"R 盘不可用时可回退"两条; 红线改为"R 盘是真实下载盘, 删除只在仿真专用根内"。

- **判据设计修正**: 首轮与稳态必须分开判 —— 混算平均漂移(2.438 s)会让每次跑都假红, 掩盖真问题。新增 `P1.first_round_s`(BASELINE), `SYNC.drift_max_s` 改为排除首轮。
- **踩到的四个坑**(均已修, 见 pitfalls.md):
  1. **`"errored"` 不是合法 qB 状态** —— `TorrentState` 解析成 UNKNOWN ⇒ `is_errored` 为假 ⇒ 缺文件扫描**完全不触发**。合法名是 **`"error"`**。
  2. **辅种组内成员必须共享完全相同的文件相对路径** —— 初版按种子序号算 ep, 同组 4 个种子文件名各不相同 ⇒ **根本没归成组**(sim 侧自以为 11 个组, 实际每组 1 人)。改为按组号算 ep + 组专用目录。
  3. **未配置站点的种子会被跳过且不归组** ⇒ sim 侧"组内成员数"与 auto-qb 侧不一致, D4 停止率算出 **0.75** 而非 1.0(auto-qb 视角其实是 100%)。改为辅种组成员一律用已配置站点, 未配置站点的覆盖交给非辅种种子。
  4. **`qbittorrent-api` 每次写请求前额外查一次 `app/webapiVersion`**(`request.py:750` 版本检查, **库内无缓存**) ⇒ 写请求量翻倍, 真实 qB 同样发生。叠加"auto-qb 逐种子打标签"(5000 种子 = 5000 次 addTags, 而 qB 支持一次多 hash) ⇒ 归为 W5 归因候选, 本阶段不动代码。
