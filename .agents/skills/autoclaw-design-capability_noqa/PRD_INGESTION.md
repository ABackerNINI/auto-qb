# PRD 摄取协议 - PRD_INGESTION.md

> 本文件只回答一件事：**用户上传了 PRD / QA 文档时，设计专家应该先怎么理解需求，再如何继续后续设计 workflow。**

---

## 1. 适用时机

仅当以下任一条件成立时读取本文件：

- 用户上传了 PRD / 产品需求文档 / 需求说明文档
- 用户上传了 QA / FAQ / 问答澄清文档
- 用户明确说“先按这份 PRD / 文档来做”

若没有 PRD / QA 类文档，不读本文件，按普通设计任务处理。

---

## 2. 总目标

PRD 场景下，先不要急着做设计。

第一目标是：

1. 先把这次需求的**功能模块**梳理清楚
2. 再把每个模块下的**界面**拆全
3. 必要时继续补齐关键**状态 / 分支界面**
4. 在此基础上再继续 skeleton / skill / design-system / craft 的选择

原则是：**宁多勿漏，逻辑缜密，先理解完整产品结构，再开始设计。**

---

## 3. 执行顺序

当用户给了 PRD / QA 时，执行顺序改为：

1. **先读 PRD**
2. **再读 QA**
3. 先内部梳理：这次需求有哪些功能模块
4. 继续按模块拆解：每个模块下有哪些界面，界面尽量拆全，不怕多，只怕漏
5. 如有必要，再补关键状态 / 分支界面
6. 再基于 **PRD + QA 的已有信息** 继续后续 workflow；缺失细节按合理默认值补齐
7. 再完成 skeleton / skill / design-system / craft 的选择
8. 再进入生成与交付

**禁止**跳过“模块 + 界面拆解”直接开始做视觉稿或首页。

---

## 4. PRD 与 QA 合并规则

- **先读 PRD，再读 QA**
- QA 只用于补充、修正、澄清 PRD
- 若 QA 比 PRD 更新、更具体，优先采用 QA
- 若 PRD 和 QA 冲突，优先采用**更晚出现且更明确**的信息
- PRD / QA 已经回答的问题，直接采用，不要重复作为缺口处理

---

## 5. 对后续输出的影响范围

### 5.1 对 skeleton / skill / design-system / craft 的影响

这些选择必须建立在 **PRD + QA + 模块/界面拆解结果** 之上，而不是只看用户首句或只看一个模糊 brief。

### 5.2 对无限画布的影响

无限画布必须覆盖前面已经梳理出的主要模块、界面和关键状态。

- 按模块分组展示
- 每个模块内的界面向右无限延展
- **不需要折行**
- 不能只放主页面，不能漏掉关键流程和关键状态

### 5.3 对可交互原型的影响

可交互原型要尽可能承载更多、更深的交互。

- 优先体现核心模块入口
- 尽量包含更深一层的交互分支
- 不只做浅层点击跳转
- 尽量让用户能在原型里摸到更完整的产品结构

### 5.4 对 Web 类产物的影响

Web 类产物同样要承载更多、更深的交互。

---

## 6. 与整体 workflow 的关系

阅读 PRD **不改变整体 workflow**，只是把“需求理解”这一步前置并做得更完整；拆解结果进入产物与交付说明，不作为等待用户确认的阶段。

---

## 7. 精简硬规则

- 先读 PRD，再读 QA
- 先拆模块，再拆界面，再做设计
- 界面数量多没关系，但不要漏
- 后续三轴选择必须基于 PRD + QA 的已有信息
- 无限画布必须覆盖已梳理出的模块、界面和关键状态
- 可交互原型尽可能做更深交互，而不是只做表层展示
- App 类 Phase 2 迭代：页面细节改动（视觉 / 模块 / 状态 / 文案 / 布局 / 交互组件）两文件同步；只属于单一文件的内容在对应文件改即可；版本号永远同步升级，且两文件都 `MEDIA:` 发给用户
