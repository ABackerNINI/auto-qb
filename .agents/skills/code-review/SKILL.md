# 收口评审 (Code Review)

设计主轴是**判断与机械分离**: 收口判定、相关性裁决、severity 定级是 agent 的判断; 引文校验、规模分档、基线自检是脚本的机械。机械面命令: `commands run review.pack`(评审包生成)与 `commands run review.check`(引文校验)。

## 铁律

> **完整任务收口, 收尾 DoD 之前, blocker 清零, 才算收完。**

## ① 触发与豁免

| 触发 (必须评审) | 不触发 (跳过) |
|---|---|
| 命中立档阈值 4 条的任务, 本次收尾 = 该任务**最后一次**(收口) | 小修/错字/单轮问答(阈值不命中, 本就无档案) |
| 修复 diff > 100 行的复查轮 | 中途"提交"(任务未完, 照常走 DoD 但不评审) |
| — | 纯文档/纯 HTML 交付任务(归既有闸门管) |

- **收口判定**: agent 判"本次收尾是否该任务最后一次"; 拿不准 → 问用户一句"这次是收口吗", 不自行猜。
- **豁免优先于阈值**: 同一任务同时命中「立档阈值」与「纯文档豁免」时, **豁免优先** —— 纯文档/纯 HTML 任务一律不评审。
- 评审固定发生在收尾 DoD **全部步骤之前**(第 3 步"事实回写"假设代码已定稿; 评审若改代码, 回写件返工)。
- 评审发现的修复随**最后一次提交**入库; 已推送的历史提交不回头。

## ② 评审包

`commands run review.pack --base <hash>` 生成机械四件: 基线 hash / diff 统计(**含 400 行分档提示**)/ 改动文件清单 / 红线命中预警。

- **diff 范围**: 任务起点 → 当前工作树(含未提交改动)。基线 = 任务第一个 commit 的 parent; 多会话任务 = 上次收口 commit; 拿不准问用户。
- **指路四件**(主 agent 随评审包给出): 档案/计划路径(验收标准 = 档案「原始请求」)、涉及模块清单、安全敏感面(凭据/网络/state 写入/红线文件)、基线 hash。
- **禁整库扫描**; reviewer 可读周边代码判调用面, 但发现只收评审包范围内的改动。

## ③ 派遣协议

**两档拓扑**(以 `review.pack` 的分档输出为准, 不手工数行数):

| 档 | 条件 | 拓扑 |
|---|---|---|
| 全能 | diff ≤ 400 行 | 1 个子代理全量评审 |
| 分面 | diff > 400 行, 或触安全敏感面 | 2–3 个子代理按面拆(正确性 / 安全 / 测试缺口), 主 agent 合并去重 |

> 分面代理**逐个串行派遣**: 宿主并发上限会拒收并发派遣(失败串 `user concurrency limit exceeded`, 与 prompt 无关), 逐个重派即恢复 —— 见 `pitfalls/kb/kb-subagent-concurrency.md`。

**reviewer 只读** —— 修复一律主 agent 执行。派遣提示**照抄三件套**, 不临场发挥:

> 1. **只读契约**: 禁止**一切写操作** —— git 状态变更(sync/rebase/merge/stash/checkout/commit/push)、写任何文件、跑 kb 等写类 task id 一律禁止, 只允许读命令; AGENTS.md 的开工同步对本任务豁免, 主会话已完成同步。
> 2. **双 hash 钉死**: diff 范围 = 任务起点 `<base>`(评审包的基线); 自检锚 = 派遣时 HEAD `<head>`(`git rev-parse HEAD` 现取)。
> 3. **开工自检**: `git rev-parse HEAD` ≠ 自检锚 `<head>` → **停手报告, 不评审**(基线 ≠ HEAD 是常态, 有中途提交的任务本就如此, 自检只对锚); 工作树出现评审包未声明的改动同样停手。

评审交回后主会话**收尾复核**: `git rev-parse HEAD` 仍 == 自检锚, 否则评审期间树被动过 —— 发现作废, 重新锚定后重评。

(三件套 + 收尾复核是对子代理继承 AGENTS.md「开工同步硬性」规则的完整对冲层; AGENTS.md 的子代理豁免句是治本层, 自检与复核是兜底层。)

## ④ 产出与裁决

**产出 schema**(reviewer 输出 JSON 数组, 逐条):

```json
{"file": "相对路径", "line": 42, "quote": "单行内连续引文", "severity": "blocker|major|minor|nit", "claim": "问题一句话", "relevance": "相关|不相关", "fix": "修法一句话"}
```

- `quote` 必须是**单行内连续片段**; `commands run review.check --findings <json>` 逐条校验: 引文与源码逐字比对(行号允许 ±3 邻近)、字段齐、severity 枚举合法。**refute 的条目直接弃, 不复核** —— 幻觉引文是 LLM 评审的头号失效模式。
- reviewer 指令里显式写"**不报清单**": 理论风险(说不出具体失败场景)/ 未改动代码 / 风格偏好 / 库推荐, 一律不报。
- **相关性裁决**(主 agent, reviewer 初判仅参考): 相关 = 属于本任务计划目标之内, **或**由本任务改动直接引入/直接暴露; 其余一律按 create-issue skill 入池。拿不准 → 默认入池(与 scope-guard 同口径)。
- **分级处置**: blocker(真缺陷/违反黄金法则/碰红线风险)**必修完才可收口**(硬门槛); major/minor 裁量当场修或入池; nit 通常忽略。test.full 照常兜底(DoD 第 4 步), 修复不设额外闸门。
- 修复后**不强制二轮**; 修复 diff > 100 行 → 追加一轮评审, 该轮 `--base` 取**上一轮评审基线**(只评修复增量, 不重跑全量 diff)。

## ⑤ checklist(16 条, 评审与降级自查共用)

**通用面**(源自调研: Google Engineering Practices / Mozilla goal review / OWASP 子集):

1. **Goal**: 改动对准任务目标, 修根因而非症状。
2. **Design**: 与周边架构一致, 未引入平行机制。
3. **正确性**: 边界条件、错误路径、对用户与调用方都正确。
4. **Tests**: 新行为有测试、测试有意义且会真失败。
5. **可读性**: 有无更简单的等价实现; 命名传达意图; 注释解释 why 而非 what。
6. **安全面**: 硬编码凭据、日志泄敏、输入未校验。

**本仓库面**(条条挂锚点, 锚点失效 = 文档修正任务):

7. 幂等性: 重复执行无副作用; 窗口语义走 state_file 去重(`record_execution`), 不靠循环频率 → AGENTS.md 法则 1。
8. 单一写线程: 队列结构与 state_file 只由主循环线程写; 查 TOCTOU → 法则 5。
9. 状态持久化: 跨轮状态进 state_file; 优雅退出立即落盘 + 周期落盘 → 法则 3。
10. fail-fast: 新配置键进了 `validate_config` 且同步 `src/auto_qb/config/schema/` → 法则 4(键面守卫 `test_config_key_surface` 已兜底, 查守卫外侧面)。
11. 保守默认: 高风险动作默认关, 只对显式配置范围生效 → 法则 2。
12. 红线: diff 未触碰 `config.yml` / `auto-qb-data/` → AGENTS.md 红线节 + `pitfalls/ops/prod-files.md`(提交闸门已兜底, pack 预警双保险)。
13. 范围守恒: diff 无计划外文件与"顺手改" → 法则 6 + scope-guard skill。
14. 非ASCII图形符号: 代码/配置无 emoji 与图形符号 → `conventions/code-style.md`(**需评审真查**: 提交闸门未覆盖源码符号)。
15. 测试基建: 新增测试同步 docstring"测试计划"清单; TMPDIR 约束未破坏 → AGENTS.md 测试节 + `pitfalls/testing/tmpdir.md`。
16. 真机准入: 完工功能落入真机轨两类准入 → 真机验收已做或理由已明示 → `testing/real-machine.md` §00/§06。

## ⑥ 留痕

结论写进档案进度日志一行 + 切片 R 行(`kb.wrap --did` 自然承载): `review: blocker 清零, 修 N, 入池 M(<slug>…)`, 评审包档位(全能/分面)随记。**暂不加机械守卫** —— 评审是判断性动作, 硬守卫逼出走过场; 跳过/走过场的复发数据攒够再议。

## ⑦ 降级自查

无子代理能力的工具环境: 主 agent 按 ⑤ checklist **逐条**自查, 产出同 schema 的发现列表, `review.check` 照跑; 自我裁决时**从严**(相关性与严重度都取保守侧)。其余流程(评审包/校验/裁决/留痕)不变。

## 反模式

- ❌ 跳过评审直接收尾 —— 收口任务的评审是 DoD 第 0 步, 缺一不可。
- ❌ reviewer 顺手修 —— 它只读; 修复一律主 agent 执行, 否则评审与实现混在同一双眼睛里。
- ❌ 引文没过 `review.check` 就采信 —— 对不上即弃, 不复核。
- ❌ 拿"这次改动小"豁免派遣 —— 分档只看 400 行与安全敏感面, 豁免口子一开就永远豁免。
- ❌ 把"我觉得相关"当裁决 —— 相关性的定义写死在 ④, 扩架即违反范围守恒。
