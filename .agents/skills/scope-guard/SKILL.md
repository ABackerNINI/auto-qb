# 范围守卫 (Scope Guard)

多个 AI agent / 多个 worktree / 多个计划并行时, **"顺手修一下"是最贵的动作**: 它让同一次提交里混进两条互不相关的意图, 另一个计划的编辑会与之撞车, 出事后无法判定是哪条改动引入的。

本 skill 只做一件事: **决定现在该不该动它**。该记不修的, 交给 [create-issue skill](../create-issue/SKILL.md) 入池。

## 铁律

> **不在本次计划内的一行代码、一个字都不改 —— 无论是代码还是文档。**

判据(用它做决定, 不要凭感觉):

| 属于本次计划 (直接修) | 不属于本次计划 (入池) |
|---|---|
| 本次要交付的功能/修复本身 | 相邻模块的既有 bug |
| 不修则本次交付跑不起来 / 测试红 | 文档与代码漂移(且不是本次改动造成的) |
| 本次改动引入的回归 | 历史遗留 TODO / 债务 |
| 用户当场说"这个也一起改" | 命名、格式、缩进、导入顺序不一致 |
| — | 别的计划正在摸的同一批文件 |

**三个例外**(不算越界, 但要在回复里明说):

1. **阻塞**: 不改本次交付无法完成 → 修, 并在收尾时向用户点名。
2. **安全 / 数据丢失风险**(凭据泄露、误删种子、破坏性默认值) → 立刻告知用户并修。
3. **用户当场扩范围**: 用户明确要求纳入 → 修, 并说明计划已扩大。

**拿不准 → 默认入池。** 入池是可逆的(修就是了), 越界改动不可逆(已混进提交)。

## 判定之后

- **要修** → 照常实施, 无需本 skill 其余内容。
- **不修** → 按 [create-issue skill](../create-issue/SKILL.md) 入池: 取时间(`date +"%y-%m-%d-%H%M"`)→ `new_issue.py --type <8 类之一>` 建报告 → **按档位填正文**(便签档 L1 ≤ 2 分钟: 现象一句话 + 位置; 标准档 L2 ≤ 10 分钟: 现象 / 证据 / 影响面 / 定位锚点; 根因与修法一律可选, 默认"待查")→ 索引自动重建 → **回到主线**。不为填单做代码分析(结论会过期)。
- 收尾时向用户一句话点名: "发现 N 个计划外问题, 已入池: <slug>(未修)。"

## 反模式

- ❌ "就改一行, 顺手" —— 一行也混进提交; 协作时对方 `git blame` 到的正是这一行。
- ❌ 用"这个反正很小"绕开判据 —— 大小与是否越界无关, 只与是否属于本次计划有关。
- ❌ 入池后自己接着修 —— 那等于没入池; 修之前先让它成为某个计划的一部分。
- ❌ 用 issue 池当待办清单堆着不管 —— 入池后应在回复里点名, 让用户决定排期。
