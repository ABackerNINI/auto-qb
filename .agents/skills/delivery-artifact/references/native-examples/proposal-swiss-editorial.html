真正的正交分解

CANON Explore subagent 跨 open-design(200+ 份)/ html-effectiveness(20 份)/ huashu-design(10 份)逐份抽 grid-template-columns + 视口绑定方式 + 内容打包方式,归纳出三根真正独立可变的轴:

Axis 1 · Viewport

ScrollStage
标准文档流(body 滚) vs 固定全屏舞台(position:fixed; inset:0)

Axis 2 · Navigation

LinearBranching
顺读 vs 侧栏 nav + 随机访问

Axis 3 · Content

ProseDataVisual
叙述文本 / 表格-指标-列表 / 画布-SVG-图像

CANON 为什么这三根真正交:

Stage × Linear × Visual(huashu c1)和 Scroll × Branching × Prose(docs-page)同时存在 → 证明 Viewport 跟 Navigation 独立。Scroll × Linear × Prose(kami)和 Scroll × Branching × Data(dashboard)证明 Navigation 跟 Content 独立。Stage × Linear × Visual(c1)和 Scroll × Linear × Prose(kami)证明 Viewport 跟 Content 独立。

CANON 「调性」(暖/冷/瑞士/学术)不是独立轴,是前三轴选定后由排版纪律派生的高层风格 — 不入决策树,不该当矩阵维度。

9 格有效空间 · 我们目前 1 格

CANON 2 × 2 × 3 = 12 格,其中 Stage × Branching = 反模式(舞台空间被侧栏吃掉)→ 实际 9 格有效。

逐格判断

  • OBS Scroll × Linear × Prose — kami-parchment(暖)+ eng-runbook(冷)已占,双范型够。
  • OP Scroll × Linear × Data — 选 clinical-case-report(open-design,Apache)。subagent 比对 invoice / clinical / resume-modern / finance-report 后判定:clinical 是唯一同时满足「无 shadow / 1px hairline / serif print-journal feel / 无 KPI 卡」的;invoice 有阴影,finance-report 堆 KPI 卡(违反 SKILL.md 硬约束),resume-modern 用 Tailwind(违反单文件自包含)。
  • OP Scroll × Branching × Prose — 选 docs-page(open-design,Apache)。三栏(240px nav / 1fr main / 220px mini-TOC),GitBook 经典,最像用户截图那份 worktree-investigation。
  • OP Scroll × Branching × Data 留空 — 三库里这格最佳样本是 dashboard/example.html,但 SKILL.md 硬约束「不堆 KPI 卡墙」、Native checklist P0 写「不是 dashboard」。subagent 机械填格推荐了它,被我拒。承认 native 语义下这格罕见(报告 + 侧栏 nav + 不堆卡 = 非常窄的子集,等遇到需求再补)。
  • SYN 整个 Stage 半边路由出去 — Stage 形态(position:fixed + absolute 排版)是 kiosk / 原型 / 海报的工程模式,不是「文档」。把 c1 / c5 vendor 进 Native 库,LLM 会学到「写报告也能 fixed 全屏定位」,误用风险高。Stage 形态在「第一步:选介质」里跟 PDF 平行路由出去,Native 库内只管 Scroll 这半边 6 格。

OP 结论:本轮 Native 库从 2 份扩到 4 份,覆盖 4/6 Scroll 半边格;Stage 半边 3 格全路由 huashu;留 2 格(2 个 Visual + dashboard 那格)有意识不补。

## 何时加侧栏 nav(Navigation 决策树)

[CANONICAL · Explore subagent 跨 200+ HTML 样本归纳]
触发任一条件 → 走 Branching(sticky left TOC + main):

- 章节 ≥ 4(用户能数得过来 = 不需要 nav;数不过来 = 需要)
- 用户提到「目录 / TOC / 章节导航 / 索引」
- 内容是技术文档 / API / 多层级手册 / 长 explainer
- 同一文档需要被反复访问(reference doc),不是一次性读完

否则走 Linear(单列顺读)。

参考范型:
- Scroll × Branching × Prose: references/native-examples/docs-page.html
- 反例(不走 Branching): references/native-examples/eng-runbook.html
  (技术内容,但章节 ≤ 3,顺读即可,加 nav = overkill)

侧栏 CSS 约定(放进 :root 一起 token 化):
  --nav-width: clamp(200px, 18vw, 260px);
  --main-width: minmax(0, 1fr);
  --rail-width: clamp(180px, 16vw, 220px);  /* 可选第三栏 mini-TOC */
