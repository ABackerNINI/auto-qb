# 变异测试定期审计

把「测试够不够硬」从直觉变成可测量的审计: **机器批量提名「活着的变异」, 人手工确认哪些是真洞**。

- **证据与全部实测数字**在报告 [26-10-08-0231-report-mutation-testing-feasibility.html](../../../memory-bank/reports/26-10-08-0231-report-mutation-testing-feasibility.html)
  —— 本 skill 只留「怎么做」; 框架比对 / 成本模型 / 实测表一律引报告, **不复述**(复述必然漂移)。
- **命令**一律走 `.commands/mutants/` 包的 task id, **本 skill 不抄命令本体**(手抄会被 `commands run doc.drift` 判红)。
- 本 skill 是**排期锚**（常驻 issue）与**执行**之间的那层「怎么做」; 「要不要做 / 什么时候做」在 issue 侧, 「做到哪了」在任务档案侧。

## 这套流程怎么运转 (优化后的四段)

初步设想是「开一个永远 open 的 issue, 人工定期跑」。这里把它拆成**职责互不重叠的四段** —— 每段只在一个工位有权威(见 [doc-forms 约定](../../../memory-bank/conventions/doc-forms.md)):

| 段 | 是什么 | 谁做 | 落在哪 |
|---|---|---|---|
| **1 排期锚** | 常驻 issue, 状态恒 `Open`; 只管「要不要做 / 什么时候做 / 覆盖到哪几个包了」 | 用户拍板 | `memory-bank/issues/<stamp>-test-mutation-audit-standing.html` |
| **2 派生计划** | 针对**某个包 / 模块**的分步执行计划(一次一件事) | agent(按本 skill 的「派生计划」节) | `memory-bank/plans/<stamp>-plan-<topic>.html` |
| **3 执行一轮** | 按包跑一轮 mutmut → 手工确认存活变异 → 补测 → 复跑 | 人工(定期, 全量或部分) | 命令走 `.commands/mutants/` 包 |
| **4 记录** | 每轮一条**基线切片**; 确认的真洞**各自**入池或当场补测; **同步更新锚的 §07 覆盖进度总表** | agent | `testing/baselines/` + `issues/` + 锚 §07 |

**为什么这么拆**(这是对初步设想的优化):

- **issue 只做锚, 不记流水**: 常驻 issue 若同时当「轮次台账」, 就会和任务档案抢同一份事实(重复必漂移)。轮次记录进任务档案 + 基线切片, issue 只留一行指针。**例外**: issue §07「覆盖进度总表」是**每轮实施后必更**的一张汇总表(见下节)——它只放「一行一个包」的刻度与指针, 不是流水。
- **一次计划只对一个包**: 计划是「怎么修、为什么这么修」的冻结件; 一次盯一个包, 拍板后冻结。跨包推进是**多份计划**的事, 不是一份计划越写越长。
- **真洞不是「issue 的一条」, 是「各自的 issue」**: 一个存活变异确认成真洞后, 它是一条独立的 `bug` / `test` 缺口(有位置、有复现), 按 create-issue 入池; 常驻 issue 只做它们的**共同上游**。
- **每轮都要有基线切片**: 没有切片的轮次等于没跑 —— 下一轮无法比较「存活数降了没有」。
- **人工执行 = 人工确认, 不是人工跑命令**: 命令由 agent 跑; 人的不可替代动作是**判断一个存活变异是不是真洞**(唯一判据: 拿全套件手工改一次, 看红不红)。

## 关键取舍 (照抄自报告的结论, 不再重开)

| 取舍 | 定论 | 理由(引报告) |
|---|---|---|
| 做不做 | **做, 但只在定期审计** | 便宜(每变异 0.015–0.16s), 但仍是全量测试的几十倍(§02 / §08) |
| 框架 | **mutmut(WSL)主力 + pytest-gremlins(Windows)兜底** | 同环境同池: mutmut 用 58% 墙时打 3.8 倍变异, 且打得到字符串/语句类(§07) |
| 进不进闸门 | **不进** | 反馈太慢; 工具硬要求基线全绿才开跑; 覆盖闸门已挂 98%(§02) |
| 一把跑全项目 | **不行, 按包是硬要求** | 实测 37% / 74% 两处把 WSL 打挂(§07 对照四) |
| 前端(JS) | **暂不做** | 无单元层, 唯一执行面是真浏览器 e2e, 前提不成立(§12) |
| 目标 | **不是「分数涨」** | 是「包内不再有不知道为什么活着的变异」; 等价变异杀不掉是数学事实(§11) |

## 硬约束 (缺一条就会白跑、假绿或把 WSL 打挂)

1. **按包 / 按模块切目标**, 永不一把跑全 `src` —— 全量会把 WSL 打挂(硬崩, 要 `wsl --shutdown` 才救回)。
2. **选择池必须是「定向的几个测试文件」**, 别用全 `tests/` —— 宽池的代价落在内存(打挂 WSL), 不在结论上(§07 对照五)。
3. **`process_isolation = "forkserver"`** —— 默认 `fork` 会让注册表类守阵假红(同一份 `mutants/` 树手跑却是绿的, 极难归因)。
4. **文本层守阵必须 `--deselect`** —— mutmut 把变异体写进同一份文件, 「读源码文本做断言」的守阵在基线就红, 整轮直接中断(结构性劣势, gremlins 没有)。当前需 deselect 的两条见包的 `set_conf.py` 默认值。
5. **必带 `-n 0 --no-cov`** —— 抵消 `pytest.ini` 的 addxdist `-n 4` 与覆盖率闸; 否则报错 / 零变异 / 子集跑必不达标。
6. **`--max-children` 别拉满** —— WSL 只有 8 核(`.wslconfig` 限), 默认取 `os.cpu_count()` 会打挂; 包级轮用 4。
7. **基线不绿不开跑** —— 工具会直接跳过(实测 `skipping mutation testing because N baseline test(s) failed`); 先修基线。
8. **镜像放 WSL 原生 ext4, 不放 `/mnt/*`** —— 经 `/mnt` 的 IO 慢到不可用(实测拷 116MB 要 52s); 用 `git clone` 而不是从 `/mnt` 拷。

> 这 8 条全部由 `.commands/mutants/` 包的脚本内建(它们是「看着正常但不生效」的写法), 正常路径**不需要手工拼**。
> 逐条取证与 14 条坑的完整表在报告 §10。

**另有 4 条是流程约束(脚本没法内建, 靠执行时守)**:

9. **池要覆盖被测包的「函数面」** —— 池窄到只剩几个文件时, 被测包里**没有任何池内测试碰过**的函数会整片落进
   `no tests`(config 首轮: 55 条全集中在两个规则条件校验器上), 那批变异连三分类都做不了。定池时先核
   「目标包的公开函数有没有对应的池内用例」, 缺的先补进池再跑。
10. **S4 的规模要主动收窄** —— 逐条跑**全套件**是整轮的时间大头(实测 ~15s/条: 274 条 ≈ 68min)。
    别对「全部存活」无差别开跑: 先用 `mutants.report` 的汇总挑优先文件(判据密度 × 出错代价高的档),
    或按变异形态(`continue→break` / 边界 / `and-or` / 语句删除)筛, 再 `mutants.verify`。
11. **复跑要带「新守阵」时用 `--no-refresh`** —— `mutants.run` 默认会 `git checkout -f` 把镜像刷成 develop,
    **未提交的测试改动会被冲掉**; 补测后的 S6 复跑要先把新测试 `cp` 进镜像 `tests/`, 再 `--no-refresh`。
    反之, S4 要的是「develop 的全套件」, 用默认(刷新)即可。
12. **每轮实施完成后同步更新常驻锚 §07 覆盖进度总表** —— 跑完一轮(出基线切片)就改该包那一行
    (日期 / 变异数 / 杀死率 / 轮次 / 状态 / 切片链接), 新包先插行; **不更视为该轮未收尾**。规程与列口径见
    下节「覆盖进度总表(收尾必更)」。

## 命令 (一律走 task id)

| task id | 干什么 | 什么时候用 |
|---|---|---|
| `commands run mutants.setup` | 建 / 刷新 WSL 镜像仓 + 装工具 | 首次, 或镜像落后时(其余命令会自动确保) |
| `commands run mutants.run -- <目标glob> <池文件...>` | 对某包/模块跑一轮 mutmut | **主力**: 每轮审计 |
| `commands run mutants.report -- <目标glob>` | 把上一轮的存活/未覆盖变异导出成**带 diff 的清单** + 按状态/按模块汇总 | 首轮跑完, **三分类之前**(`mutmut results` 只有 id, 没有文件:行与变异内容) |
| `commands run mutants.verify -- --from-report <清单>` | 对候选逐条 `apply` → 跑**全套件** → 还原, 记 KILLED / SURVIVED | **S4 手工确认的机械化**(整轮时间大头, 先缩小候选) |
| `commands run mutants.gremlins -- <目标文件> <池文件...>` | Windows 侧兜底 / 交叉验证 | 不想开 WSL, 或想用第二工具核对数字 |
| `commands run mutants.status` | 看镜像状态 + 上一轮结果摘要 | 轮次之间回看 |

- 细节(`<args>` 形态 / 缺省池 / 退出码语义)用 `commands run show mutants.run` 取, **不要翻文档**。
- 包内深读(为什么这么写 / 排障 / 结果怎么读)在 `.commands/mutants/references/` —— 按 `doc` 指针读, 别整读。

## 一轮的标准步骤 (round protocol)

**入场条件**: 基线全绿(`commands run test.quick` 过)。不绿先修, 别跑变异。

1. **定目标与池** —— 一个包或一个模块; 池 = 直接相关的那几个测试文件(先核「覆盖函数面」, 见硬约束 9)。
2. **跑一轮** —— `commands run mutants.run -- --target '<glob>' --pool <池...>`; 记下变异数 / 杀死率 / 耗时 / **工具版本** / **选择池**。
3. **导出清单** —— `commands run mutants.report -- --target '<glob>'`; 拿到**带 diff 的清单** + 按状态/按模块汇总。
   (别拿 `mutmut results` 的纯 id 清单去分类 —— 没有变异内容判不了真洞/等价。)
4. **三分类** —— 逐条判「真洞 / 等价变异 / 假存活」(见下节)。分类是**人**的动作, 不是工具输出。
5. **手工确认(S4)** —— `commands run mutants.verify -- --from-report <清单> [--only-status survived]`:
   对每条候选在**全套件**下 `apply` → 跑 → 还原。**只认这个判据**。先按硬约束 10 把候选收窄。
   KILLED = 假存活(全套件能杀, 只是池没选到); SURVIVED = 真洞候选(夹着少量等价变异, 逐个判)。
6. **处置** ——
   - 真洞 → **各自入池**(`test` 缺口 / `bug`)或当场补断言(走正常测试流程, 补完 `commands run test.full`);
     补的守阵必须**红验**(套上同构变异 → 目标用例变红 → 还原复绿, 源码零残留)。
   - 等价变异 → 记一笔「为什么等价」, **不追**。
   - 假存活 → 记一笔「相关测试不在池里」, 必要时**加进池**下一轮复跑。
7. **复跑** —— 同一目标 **同一池** 再跑一轮(带新守阵时见硬约束 11), 看存活数是否下降(换池的数字不可比)。
8. **记录** —— 新建一条基线切片(字段见下), 在任务档案追加一行轮次。
9. **更新常驻锚的覆盖进度表(必做, 不是可选)** —— 改 issue §07「覆盖进度总表」里该包那一行: 上次测试日期 / 变异数 / 杀死率 / 轮次 / 状态 / 基线切片链接。规程见下节「覆盖进度总表(收尾必更)」。**这步没做完, 一轮不算收尾**。

## 三分类: 真洞 / 等价变异 / 假存活

| 类 | 判据 | 处置 |
|---|---|---|
| **真洞** | 全套件手工造同构变异 → **变红**(说明有测试能抓, 只是池没选到)或**不变红**(说明真的没测试抓得住)且行为确实错了 | 入池 / 补测。**注意**: 变红 = 假存活(测试存在但没进池); 不变红且行为错 = 真缺口 |
| **等价变异** | 变异后行为与原代码**在所有输入上等价**(如 `@dataclass(frozen=True)` → `False`、`a <= b` 与 `a < b` 在离散域上的某些形态) | 记一笔理由, 不追 |
| **假存活** | 相关测试**不在选择池里** —— 换宽池就死了 | 记一笔; 需要时加进池复跑 |

> **存活数是「选择池」的函数** —— 实测同一 `utils.py` 只换池, 存活 97 → 70(−27%); 一个被判存活的变异, 拿全套件手工验证其实是被杀死的。
> 这条不先立规矩就投产, 第一份存活清单会被当成缺口单, 人力全浪费在伪洞上。完整判据见坑档
> [mutation-pool-artifact.md](../../../memory-bank/pitfalls/testing/mutation-pool-artifact.md)。

**为什么机器提名 + 手工确认**: 手工红验回答「我刚写的守阵是不是空转」(与行为同构, 是收尾动作); 机器变异回答「哪些地方我**从没想过要写守阵**」—— 后者人做不了(没人会去改自己没动过的那几万行)。两者是分工, 不是替换。

## 记录口径 (每轮一条基线切片)

命名与体例照 [testing/baseline.md](../../../memory-bank/testing/baseline.md): `testing/baselines/YY-MM-DD-HHMM-mutants-<包>.md`。
**必填字段**(缺了跨轮不可比):

- 目标(glob) · **选择池(逐个文件)** · 变异总数 · 杀死 / 存活 / `no tests` / 超时 计数 · 杀死率
- 耗时(墙时 + CPU) · **工具名 + 版本** · `--max-children` · 机器(WSL 核数)
- **首轮与复跑各一行**(复跑要写「同目标同池 + 补测」并给存活数增减; 有新增存活要单独点出)
- **手工确认后的真洞数** + 指向各自 issue 的链接 · S4 覆盖了多少条 / 其中假存活多少
- 切片自带一行 `**Refs:** <任务档案路径>`(认领链反向声明)

> `no tests`(没有任何测试覆盖)与 `survived`(有覆盖但没杀掉)是**两类**, 分开记 —— 两个工具的分母不同, 分数只能各自纵向比, 别横向混。

**两个会判红的记录纪律**(都是机械守卫, 不是建议):

- **切片之外不手抄 `N passed`** —— 回写守卫(判据族 B)只允许测试数字出现在 `testing/baselines/` 切片里;
  任务档案 / activeContext / 主题文档一律写「见 `kb.baseline`」或指向切片, 否则 `test.quick` 判红。
- **新建的 issue 要填 `doc-refs`** —— 被任务档案的 `Refs` 列出时必须反向声明认领方路径, 否则 `kb.check` 报「认领链单向」。

## 覆盖进度总表(收尾必更)

常驻排期锚 issue `memory-bank/issues/<stamp>-test-mutation-audit-standing.html` 的 **§07 覆盖进度总表** 是**「覆盖到哪几个包了」的唯一事实源** —— 该表一行一个包 / 模块, 列为:

| 列 | 填什么 |
|---|---|
| 包 / 模块 | 目标名(`config/` · `infra/versioning.py` …) |
| 上次测试日期 | 该包最近一轮的日期(`YYYY-MM-DD`) |
| 变异数 | 该轮实测总数(复跑不叠加, 取当轮) |
| 杀死率 | 首轮 → 复跑(无复跑则单值) |
| 编号 / 轮次 | 任务档案里的轮次号(R0 / R2 …) |
| 状态 | 三档: `待做` / `已做(余量在池)` / `已做(已清)` |
| 基线切片 / 计划 / 任务档案 | 链接(切片取最近一次) |

**更新时机(硬约束 12)**: **每次变异测试实施完成后** —— 即某包跑完一轮(`mutants.run`)并产出基线切片 —— **必须同步更新该表**, 再走收尾回写。**更新内容**:

1. 该包那一行的日期 / 变异数 / 杀死率 / 轮次 / 状态 / 切片链接;
2. 若该包状态从 `待做` 变 `已做`, 同时把该行状态改掉;
3. 新开一个包前**先插一行**(状态 `待做`), 跑完再填数字 —— 不允许出现「只有数字没有切片」的行。

**为什么不违反「issue 不记流水」**: 这张表只放**汇总刻度 + 指针**(一行一个包), 轮次明细仍在基线切片与任务档案里。它替代的是「翻遍所有切片才知道哪个包做过了」的成本, 不是**再记一遍**流水。

**口径自查**(收尾时对着看, 与 `kb.check` / 回写守卫并行的自律项): 表中每个「已做」行都有基线切片链接 · 日期与切片一致 · 变异数/杀死率与切片逐位一致 · 无一包只填数字不挂链接。**表里不放 `N passed`**(那是切片的事, 手抄会被回写守卫判红)。

> 派生计划执行到 S9 时, 这一条是**验收项之一**(见「派生计划」§4 验收)。

## 派生「针对 X 的分步执行计划」

用户说「**根据变异测试指导写一份针对 <X> 的分步执行计划**」(X 如 `config`)时, 按本节的骨架写。
产出走 [delivery-artifact skill](../delivery-artifact/SKILL.md), 放 `memory-bank/plans/<stamp>-plan-<topic>.html`(**单文件 HTML, dark 主题**)。

**骨架**(每一节都必须落到 X 上, 不许留泛泛的模板话):

1. **范围与目标**
   - 目标: `src/auto_qb/<X>/` (glob 写全, 例 `**/config/*.py`); 目标函数/类清单(按「判据密度 × 出错代价」排)。
   - 为什么先它: 引报告 §11 的对象优先级, 或引 §09 的实测刻度(分数最低的先补)。
   - **显式排除**: 不在范围内的文件/行为。
2. **测算基数**(用报告实测密度与单价外推, 别拍脑袋)
   - 变异数 ≈ 行数 × 1.0(实测 0.84–1.23/行); 单轮时长 ≈ 变异数 × 0.134s(包级锚点, WSL 8 核 `--max-children 4`)。
     口径按**目标 glob 命中的全行**算就行 —— **别**自作聪明剔除「纯数据声明」行: config 首轮这么精化后估 ≈3,800,
     实测 **4,799**(+26%), 估算只用于排期, **首轮一律以实测为准**并原样记进切片。
   - 池: 列出 X 的直接测试文件; 说明为何不用全 `tests/`; 并核「池是否覆盖目标包的函数面」(见硬约束 9 ——
     池太窄时, 没被池碰过的函数会整片落进 `no tests`, 那批变异连三分类都做不了)。
3. **执行步骤**(每步一条 `commands run <task>`, **不写裸命令**)
   - S1 环境: `mutants.setup`
   - S2 首轮: `mutants.run -- <X glob> <池...>`
   - S3 导出 + 三分类: `mutants.report -- <X glob>` 拿**带 diff 的清单** → 分类表(真洞 / 等价 / 假存活)
   - S4 手工确认: `mutants.verify -- --from-report <清单>`(全套件 `apply` → 跑 → 还原); 先按硬约束 10 收窄候选
   - S5 补测: 对确认的真洞加断言(正常测试流程 + **红验**), 补完 `test.full`
   - S6 复跑: 同目标同池(带新守阵时 `--no-refresh` + 先 cp 测试进镜像), 看存活数
   - S7 记录: 基线切片 + 真洞各自入池(issue 记得填 `doc-refs`)
   - S8 更新常驻锚: 改 issue §07 覆盖进度总表该包那一行(日期 / 变异数 / 杀死率 / 轮次 / 状态 / 切片链接)
4. **验收**(可判定)
   - 每轮基线切片字段齐(见上节); 真洞**全部**已入池或已补测; 复跑存活数 ≤ 首轮(同池)。
   - **常驻锚 §07 覆盖进度总表已同步该包行**(硬约束 12) —— 日期/变异数/杀死率与切片逐位一致, 且挂了切片链接。
5. **风险与停手点**
   - 基线不绿 → 停, 先修; WSL 无响应 → `wsl --shutdown` 后降 `--max-children` 重来; 池越宽内存越紧 → 回定向池。

**计划的边界**: 计划只写「怎么修 / 为什么这么修」; **不在计划里实施**。执行时按 [memory-bank skill](../memory-bank/SKILL.md) 立任务档案, 轮次进档案。

- 全部 14 条实测坑与处置在报告 §10(镜像 / 池 / 隔离 / 配置键名 / `mutants/` 补料 227MB / WSL 无 `python` / 8 核 …)。
- **方法论坑**单点在 [pitfalls/testing/mutation-pool-artifact.md](../../../memory-bank/pitfalls/testing/mutation-pool-artifact.md)。
- **静态守阵盲区**(与本流程互补的那类)在 [pitfalls/testing/static-guard-mutation.md](../../../memory-bank/pitfalls/testing/static-guard-mutation.md) —— 变异测试补不了文本层守阵的缺陷, 两者各管一层。
- **结果怎么读 / 状态存在哪**(`mutmut results` 只有 id; 状态在 `mutants/<路径>.meta`, `mutmut-cache.db` 是 0 字节的幌子)
  在包内 [references/why.md](../../../.commands/mutants/references/why.md) —— 排障时才读。
- **本机 WSL 登录壳是 zsh**: `cd` 改了真实 cwd, 但 `$PWD` / `$()` 仍报启动目录 —— 写 WSL 脚本别用 `$()` 取相对路径。
  工具侧 `mutants.status` 的这处失真**已修(2026-10-08, `cd X && cmd` 直连形态)**;
  `mutants.run` 本来就不受影响。若再见到 `mutmut=no`, 见
  [pitfalls/testing/mutants-wsl-shell.md](../../../memory-bank/pitfalls/testing/mutants-wsl-shell.md)。

## 反模式

- ❌ 一把跑全 `src` / 用全 `tests/` 当池 —— 会打挂 WSL, 且不是「更全」, 是「跑不完」。
- ❌ 把存活清单直接当缺口单 —— 先手工确认, 假存活比例不小。
- ❌ 追「杀死率 100%」/ 设 `break` 阈值挂 CI —— 等价变异杀不掉, 追它等于自欺。
- ❌ 换池后跨轮比存活数 —— 池是变量, 数字不可比; 选择池必须写进切片。
- ❌ 拿 mutmut 的分数和 gremlins 的分数横向比 —— 分母不同(前者含 `no tests`)。
- ❌ 在计划 / 文档里手抄命令 —— 只写 task id(`doc.drift` 判红)。
- ❌ 为了跑变异去动主仓库的 `pyproject.toml` / `.venv` —— 镜像与工具在 WSL 侧独立, 主仓库环境不动(报告 §01 的沙箱纪律)。
- ❌ 拿 `mutmut results` 的**纯 id 清单**直接分类 —— 没有文件:行与变异内容, 判不出真洞/等价; 先 `mutants.report`。
- ❌ 对「全部存活」无差别开 `mutants.verify` —— 每条要跑一遍全套件(实测 ~15s/条), 先把候选收窄。
- ❌ 复跑忘了 `--no-refresh` —— 新加的守阵会被镜像刷新 `git checkout -f` 冲掉, 存活数纹丝不动, 还以为是真洞。
- ❌ 在基线切片**之外**手抄 `N passed` —— 回写守卫判据族 B 判红(数字只写 `testing/baselines/` 切片)。
- ❌ 跑完一轮**不更常驻锚 §07 覆盖进度总表** —— 「覆盖到哪几个包了」就散了, 下轮得翻遍切片才知道谁做过了(硬约束 12; 该表只放汇总刻度与指针, 不是流水)。
