# Issue 报告 (issues 池)

把"暂时不修的问题"变成一份**别人不用重新调查就能开工**的记录, 并在索引里留一条 `类型 · 简述 · 链接`。

- 什么该入池、什么该当场修 → 见 [scope-guard skill](../scope-guard/SKILL.md)。
- 本 skill 只负责**记录与状态流转**, 不负责判断修不修。
- **核心原则: 入池成本与问题重量成正比** —— 文档漂移写三行就够, 复杂缺陷才值得停下来取证。

## 类型(8 类, 进文件名第二段)

类型 token 直接进文件名, 是**唯一**的强制分类维度(不加优先级 / 模块 —— 加了就又变成大单)。
枚举单点定义在 `scripts/_common.py` 的 `TYPES`, 增删类型只改那一处。

| token | 含义 | 什么时候用它 | 默认档位 |
|---|---|---|---|
| `bug` | 缺陷 | 行为不符预期、报错、回归、平台兼容 | standard |
| `perf` | 性能 | 慢、卡顿、无谓重建、内存 / CPU | standard |
| `docs` | 文档 | 文档漂移 / 缺失 / 写错 / 与代码不一致 | light |
| `test` | 测试 | 用例缺失、失败、守卫缺口 | light(失败用例用 `--tier standard`) |
| `refactor` | 技术债 | 重构、耦合、命名 / 格式不一致、历史 TODO | light |
| `feat` | 功能 | 新增能力或增强(未排期) | standard |
| `chore` | 杂项 | 依赖升级、CI、配置、脚本维护 | light |
| `question` | 待拍板 | 缺决策就动不了手(方向二选一、等用户定调) | light |

**不单列的类型归到哪儿**:

- `security` —— **不入池**。与 scope-guard 的例外 2 一致: 当场告知用户并修; 确需留痕时用 `bug` + 严重度"高"。
- `regression` / `compatibility` —— 归 `bug`, 正文首行标注即可。
- `epic` / `RFC` / 大改造 —— 不进 issues, 走 `memory-bank/tasks/` 档案或 `docs/plans/` 计划。

## 档位(类型决定, `--tier` 可覆盖)

| 档位 | 适用类型 | 必填段 | 可选段 | 时间预算 |
|---|---|---|---|---|
| **L1 便签** `light` | docs / refactor / chore / question / test 缺口 | 现象一句话 · 位置 · 状态日志 | 建议一句 | **≤ 2 分钟** |
| **L2 标准** `standard` | bug / perf / feat / test 失败 | 现象与场景 · 证据(贴原文) · 影响面(3 行) · 定位锚点 · 状态日志 | 根因(默认"待查") · 建议修法 | **≤ 10 分钟** |

超时就只写事实 + 待查, **立刻回主线** —— 入池是"顺手记一笔", 不是"先调查清楚"。

## 新建一条 issue (3 步)

### 1. 取当前时间(必须命令取, 禁止凭记忆)

```bash
date +"%y-%m-%d-%H%M"                 # git bash / Linux / macOS → 26-09-19-1808
Get-Date -Format "yy-MM-dd-HHmm"      # PowerShell
```

下面第 2 步的脚本会自己取时间, 但仍要**先跑一次**确认取值合理(系统时间明显不对时人工纠正)。

### 2. 生成报告

```bash
python .agents/skills/create-issue/scripts/new_issue.py <slug> \
  --type docs --title "中文标题" --summary "一句话简述(进索引)" \
  [--module webui] [--tier light] [--dir memory-bank/issues] [--project 项目名]
```

- `<slug>`: 小写英文短横线, 建议 `<领域>-<专题>`(只是建议, 分类职责已交给 type)。
- `--type`: **必填**, 不在 8 类枚举里直接报错。
- 产出 `<issues dir>/<时间>-<类型>-<slug>.html`, 例 `26-09-19-2359-docs-memory-bank-push-rule-drift.html`。
- 脚本随后**自动重建 `_index.md`** 并打印路径; 文件已存在则报错退出, 不覆盖。
- `--dir` 不传时按 `memory-bank/issues` → `issues` → `docs/issues` 探测已存在的那个; 都不存在则要求显式指定。

### 3. 填正文(按档位, 这是入池的价值所在)

脚本只填封面。接着按档位补齐 —— **只为"别人能直接开工"而写, 不为填满字段而写**:

- **L1**: 一句话现象 + 位置(grep 锚点) + 可选一句建议。
- **L2**: 现象与场景 · 证据原文 · 影响面三行 · 定位锚点(符号名 + grep 词 + 当时行号)。

## 防过期原则(5 条)

问题会等很久才被认领, 而代码一直在动。这五条比"填什么字段"更重要:

1. **只记事实, 不记结论。** 根因与修法默认"待查"; 有结论才写, 不确定就写"已排除：X、Y"。不要把猜测写成结论。
2. **行号要标"当时"。** 定位锚点 = 符号名 + grep 关键词 + 当时的行号(注明取证时间)。代码漂移后靠符号与 grep 重新定位, 行号只是加速项。
3. **不为填单做分析。** 入池的时间预算写死在上面: L1 ≤ 2 分钟、L2 ≤ 10 分钟。
4. **证据贴原文并标时间。** 日志 / 报错 / 命令输出原样贴, 附取证时间, 让读者自己判断新鲜度。
5. **开工时先复验。** 认领后第一件事是重跑锚点、确认现象仍在; 报告里补一行"复验：`<时间>` 仍复现 / 已消失"。

## 状态机

状态写在报告 HTML 的**封面状态徽标**(`<span class="badge">`)与 `<head>` 的 `<meta name="issue-status">`(**两处一起改**, 索引只读 meta), 取值仅五种:

| 状态 | 含义 |
|---|---|
| `Open` | 未修, 待排期(新建默认) |
| `In Progress` | 已被某个计划认领, 正在修 —— **认领人只能是"用户指派"或"用户已批准的计划"** |
| `Fixed` | 已修并验证(写清验证方式与测试数字) |
| `WontFix` | 决定不修(必须写明理由) |
| `Duplicate` | 与既有 issue 重复(写明指向哪一条) |

改状态的唯一流程: **改 HTML 的两处状态 → 追加一行状态变更日志 → 重建索引**:

```bash
python .agents/skills/create-issue/scripts/gen_issues_index.py         # 重建
python .agents/skills/create-issue/scripts/gen_issues_index.py --check # 只比对(供守卫/CI 用)
```

`_index.md` 是**生成物**(与 `tasks/_index.md` 同款): 按状态分区, 每行 = `类型 · 简述 · 报告链接`, 顶部有 Open 状态的按类型计数表。**不要手改它** —— 多个 worktree 并行时手改必然冲突, 冲突的解法是重跑脚本, 不是人工合并两版文本。
文件名合规(含合法 type)与状态取值由生成器守卫, 不合规直接报错退出。

## 修一条 issue 时

1. 确认它已成为某次计划的一部分(**用户指派**, 或用户已批准的计划认领)。❗**Agent 不得自行认领**
   "我提议认领 → 用户说继续"不算指派, 那样入池和认领都是越界;
   没认领就改代码 = 越界, 没认领就置 `In Progress` 同样是越界。用户没指派时, 正确动作是把
   issue 留在 `Open`, 在回复里说明"要不要认领 / 什么时候修", 等一句明确的话。
2. 开工置 `In Progress`, 先**复验**(防过期原则第 5 条), 再重建索引。
3. 修完置 `Fixed`, 在报告里补"实际修法 / 验证方式 / 测试数字"; 与"建议修法"不同则保留建议原文并说明改道原因。
4. 按 `memory-bank` skill 的收尾 DoD 跑测试、回写 `memory-bank/` 主题文档; 需要时同步更新报告正文。
5. 重建索引, 让 `_index.md` 反映新状态。

## 可移植性(换项目怎么用)

本 skill 不含项目绑定, 装到别的项目直接可用; 需要调的只有这几处:

| 项 | 默认行为 | 怎么调 |
|---|---|---|
| issues 目录 | 探测 `memory-bank/issues` → `issues` → `docs/issues` | `--dir <相对仓库根的路径>` |
| 仓库根 | 向上探测 `.git`(目录或 worktree 的 `.git` 文件) | `--root <路径>` |
| 项目名 | 模板里不出现项目名 | `--project <名>` 注入封面 kicker |
| meta 名 | `issue-slug / -stamp / -type / -tier / -status / -title / -summary`(无项目前缀) | 不用改 |
| 语言 | 中文模板 | 替换 `assets/*.html` |
| 类型枚举 | `scripts/_common.py` 的 `TYPES` | 改这一处即可 |

不按 skill 安装深度反推仓库根(旧实现的 `parents[4]` 只在一种布局下成立), 所以换目录结构不会失效。

## 反模式

- ❌ 报告只写"XX 有问题" —— 没有证据和位置等于没记, 下次还得重查。
- ❌ 把猜测当根因写死 —— 后续会沿着错误结论修。
- ❌ 为填满字段去读代码 —— 分析会过期(见防过期原则), 且违背"入池不改码"的初衷。
- ❌ 轻问题走标准档 —— 文档漂移写 7 段是纯浪费。
- ❌ 文件名 / 时间戳凭记忆编 —— 必然与真实时间不符, 且与别的文件撞序。
- ❌ 手改 `_index.md` —— 生成物, 重跑脚本即可。
- ❌ 只改 meta 不改封面徽标(或反之) —— 两处漂移, 人读的和脚本读的不一致。
- ❌ 把大改造塞进 issues —— 那该是 `tasks/` 档案或 `docs/plans/` 计划。
