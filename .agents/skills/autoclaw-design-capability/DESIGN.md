# 设计工作规范 - DESIGN.md

> 将设计方法论融入产品设计师的日常工作准则。

---

## 一、规则强度说明

本文件的规则分为三档。执行时先判断规则类型，再判断是否可以根据上下文调整。
执行顺序：
1. 先判断这条规则保护什么：安全/版权/稳定性，还是审美/可信度/表现力。
2. 硬约束按原文执行。
3. 默认策略先执行；若品牌、用户要求或内容结构提供明确理由，可以调整。
4. 设计建议用于提升质量，不阻塞交付。

### 1. 硬约束

适用于会影响安全、版权、运行稳定性、交付协议、宿主环境兼容的问题。

判断标准：
- 违反后会导致页面报错、功能失效、资源加载失败
- 违反后可能涉及版权、品牌冒用或安全风险
- 违反后会破坏平台约定、文件交付或用户操作路径

语言特征：
- 可以使用“必须/不得/禁止/严禁/绝不”
- 需要给出原因或已知风险

### 2. 默认策略

适用于大多数情况下更好的设计选择，但允许在有明确理由时调整。

判断标准：
- 违反后不一定出错，但可能降低审美、可信度或完成度
- 是否使用取决于品牌、用户要求、内容结构或场景
- 可以被明确的设计理由覆盖

语言特征：
- 优先使用“默认/优先/通常/建议/避免/先考虑”
- 搭配“原因/替代方案/可用条件”

### 3. 设计建议

适用于提升质量、增加表现力或启发创意的建议。

判断标准：
- 不执行也不会造成明显错误
- 主要影响风格、精致度、差异化或表达力
- 可根据项目目标自由取舍

语言特征：
- 使用“可以/尝试/适合/值得考虑”
- 不作为交付阻塞条件

## 二、设计工作流

1. **理解需求** — 面对新项目或含糊的需求先问清楚：输出形式、保真度、方案数量、约束条件、涉及的设计系统/品牌。信息不足时直接开始，会导致方向偏差和返工；先补齐关键约束。
2. **探索资源** — 通读设计系统、UI 套件、品牌指南、已有代码/截图。动笔前先理解视觉语汇。
3. **规划变体** — 对任何设计决策，产出 3+ 方案。让用户选择，而不是替用户决定。
4. **迭代构建** — 先搭结构再叠细节。频繁验证、频繁获取反馈。
5. **验证交付** — 检查渲染是否干净、交互是否正常、响应式是否工作、无障碍基础是否具备。
6. **简短摘要** — 只讲注意点和下一步，不废话。

## 三、设计思维框架（编码前必经）

在写任何代码之前，先完成设计思维四问：

| 维度 | 问题 |
|------|------|
| **Purpose** | 这个界面解决什么问题？谁在用？ |
| **Tone** | 选一个极端的美学方向：极致极简 / 极繁主义 / 复古未来 / 有机自然 / 奢华精致 / 玩具感 / 编辑杂志风 / 粗野主义 / 装饰艺术 / 柔和粉彩 / 工业实用... 避免模糊折中，确保方向能被执行。 |
| **Constraints** | 技术约束（框架、性能、无障碍） |
| **Differentiation** | 这个设计最想让用户记住的一个独特记忆点是什么？它通过哪种视觉或交互手段体现？|

**关键**：选一个清晰的概念方向，然后精确执行。大胆的极繁和精致的极简都行——关键是**意图性**，不是强度。

### 实现复杂度要匹配美学愿景
- 极繁主义设计 → 需要精致的代码、大量的动画和效果
- 极简/精致设计 → 需要克制、精确、对间距/字体/微妙细节的极致关注
- 优雅来自对愿景的精确执行，不是来自“刚刚好”

## 四、视觉风险与推荐方向

以下是常见的模版化风险模式。它们不是绝对不可用的，但在缺少品牌、内容结构或明确意图支撑时，容易让作品显得默认、空泛或不可信。默认先避开；如果使用，需要说明它服务于什么设计目标。

符号说明：
- ❌ = 风险信号。默认避开，但不是硬约束；当品牌、用户要求或内容结构提供明确理由时，可以使用。
- ✅ = 推荐方向。优先考虑，但不是必须全部使用；根据项目目标选择。

执行时：
1. 先看规则强度： 硬约束>默认策略>设计建议。
2. 本章中的❌默认按“风险信号”处理，不自动等同于硬约束；除非条目明确标注为硬约束。
3. 若保留某个❌风险模式，需要能说明它服务于品牌、信息层级或用户任务。
4. 不需要为了使用✅而堆叠视觉效果；每个元素都要有明确作用。

### 配色与渐变
判断标准：配色应有来源，能服务于品牌、层级或情绪；没有来源的炫技色彩默认避开。
- ❌ 紫蓝渐变 `linear-gradient(135deg, #667eea 0%, #764ba2 100%)`
- ❌ 白底紫渐变——最典型的 AI slop 配色
- ❌ 彩虹/全息渐变
- ❌ 万物加重阴影 `box-shadow: 0 10px 40px rgba(0,0,0,0.3)`
- ❌ 暗底霓虹发光
- ❌ 胆怯的、均匀分布的调色板——主色+锐利点缀色 > 均匀分配
- ✅ 用品牌色、微妙阴影、有意识的对比
- ✅ 用 CSS 变量保持一致性
- ✅ 主导色 + 锐利点缀色，比胆怯的均匀调色板更有力

### 字体
判断标准：字体选择应匹配品牌气质和阅读场景；避免只因为常见或顺手而选择。
- ❌ Inter / Roboto / Open Sans / Arial / system-ui 无脑默认
- ❌ Space Grotesk 等“AI 默认精选”——跨次生成不要收敛到相同选择
- ❌ 全大写标题 + 极端字间距 `letter-spacing: 0.2em`
- ❌ 正文用极细字重（100-300）——不可读
- ✅ 选择有个性、独特、有趣的字体
- ✅ 用有辨识度的展示字体 + 精致的正文字体配对
- ✅ 对齐设计系统的字体层级；没有就用心选择

### 布局
判断标准：布局应服务信息层级；如果只是套常见模版，默认重新组织结构。
- ❌ 左边彩色强调线的卡片 `border-left: 4px solid #color`
- ❌ 抽象几何 blob SVG 的英雄区
- ❌ 图标 + 标题 + 描述完美对称的功能网格
- ❌ 引号 + 头像圆圈的推荐卡片
- ❌ 可预测的布局和组件模式——千篇一律的 cookie-cutter 设计
- ✅ 不对称布局、变化密度、编辑式构图
- ✅ 意想不到的布局：重叠、对角线流动、打破网格
- ✅ 大量留白 或 受控的高密度——两个极端都比中间地带有力
- ✅ 每次设计都不一样——在亮/暗主题、不同字体、不同美学之间变化

### 插图与图标
判断标准： 图形元素应帮助理解内容或强化品牌气质；不能只作为装饰填充。
- ❌ 手绘 SVG 插图（“友好涂鸦”风）
- ❌ 简单概念用等距 3D 图标
- ❌ Emoji 作为核心视觉元素——风格不可控，容易削弱专业感；需要图形表达时，优先使用 SVG 线性图标、品牌图标或真实素材
- ❌ 通用占位图风格的图片
- ✅ 真实摄影、极简线图标；若图形不能帮助理解，则不使用图形

### 动画
判断标准：动画应服务注意力引导、状态反馈或叙事节奏；避免无目的动效堆叠。
- ❌ 每个区块滚动淡入
- ❌ 悬停弹跳过渡 `cubic-bezier(0.68, -0.55, 0.265, 1.55)`
- ❌ 背景图视差效果
- ❌ 散落各处的微交互——一个精心编排的页面加载动画（staggered reveals + animation-delay）比一堆零散微交互更打动人
- ✅ 有目的的运动——引导注意力或确认操作
- ✅ CSS-only 优先（HTML），React 用 Motion 库
- ✅ 滚动触发和悬停态要有惊喜感

### 背景与视觉细节
判断标准：背景应建立氛围和层级，但不能干扰内容阅读。
- ❌ 纯色背景作为默认——要创造氛围和深度
- ✅ 渐变网格、噪点纹理、几何图案、层叠透明度
- ✅ 戏剧性阴影、装饰性边框、自定义光标、颗粒感叠加
- ✅ 与整体美学匹配的上下文效果和纹理

### 典型高风险案例：配色与渐变

**❌ Mesh gradient 铺满背景**
- **风险**：整屏 mesh gradient 容易成为模板化 hero 背景，抢走内容层级
- **处理方式**：优先改为局部渐变、品牌色块、真实图像、纹理背景，或只在按钮/hover/小面积装饰中使用
- **可用条件**：品牌本身依赖流体渐变，或用户明确需要梦幻、流动、AI 感视觉

**❌ 夜间模式简单反色（粗暴 invert）**
- **风险**：直接反色会破坏品牌色、文字对比度和层级关系
- **处理方式**：重新调暗色背景、文字层级、边框透明度、accent 饱和度，而不是直接 invert
- **可用条件**：低保真内部工具，且用户只需要快速可用的暗色预览

### 典型高风险案例：字体

**❌ Fraunces 字体（与 Space Grotesk 同列入"AI 默认精选"）**
- **风险**：在没有品牌依据时使用，会显得像默认审美模板，削弱辨识度
- **处理方式**：先根据项目气质选择字体方向；editorial 可用衬线 display，technical 可用 mono display，工具型产品优先高可读 sans
- **可用条件**：品牌规范明确指定，或项目确实需要复古、文学、柔和的衬线气质

### 推荐参考：字体
**✅ 字体配对方向**（用于避免凭空挑字体）：
- 衬线 display + 无衬线 body（editorial / 杂志感）
- Mono display + sans body（technical / 工程感）
- Heavy display + light body（强弱对比）
- Variable font 做 hero 的粗细动画

**✅ Google Fonts 冷门好选项**（用于初始探索，不作为固定清单）：
- Instrument Serif（衬线 display）
- Cormorant（衬线 display）
- Bricolage Grotesque（无衬线 display）
- JetBrains Mono（等宽，适合 technical 场景）

### 典型高风险案例：布局

**❌ Bento grid 过度泛滥**
- **风险**：Bento grid 是高频 landing page 模式；若内容没有真实主次关系，容易显得模板化
- **处理方式**：先判断内容是否天然模块化；如果不是，改用叙事流、对比区块、步骤结构、案例结构或单屏聚焦布局
- **可用条件**：内容确实有并列模块、强弱层级和多类型信息，需要在同一屏中组合展示

**❌ “大 hero + 3-column features + testimonials + CTA” 模板**
- **风险**：这是高频SaaS落地页结构，容易让页面显得通用，缺少产品记忆点
- **处理方式**：重新组织叙事结构，例如从真实使用场景、核心工作流、问题对比、产品界面或关键结果切入
- **可用条件**：用户明确要求经典 SaaS 模板风（且能接受平庸）

**❌ Card grid 里每个 card 长得一样**
- **风险**：均匀对称 = 偷懒。Asymmetric / 不同大小 / 有的带图有的不带 / 有的跨列——才像真设计师做的
- **处理方式**：通过卡片大小、图片比例、跨列、背景层级、内容密度或留白变化建立主次关系
- **可用条件**：纯数据展示、表格、价格对比等需要公平比较和稳定扫描的场景

### 内容陷阱

**❌ Data slop**——编造的 stats / 装饰性 metric cards / mock table 假数据
- **风险**：「10,000+ happy customers」、「99.9% uptime」、用 icon+数字+词组成的装饰性 metric cards、mock table 里花里胡哨的假数据——模型 / 用户一眼识别为 AI slop
- **处理方式**：没有真实数据时，使用明确占位符，如 `[此处放真实数据]`；版面显空时，用结构、比例和留白解决，不靠假指标填充。
- **可用条件**：用户明确要求示意稿，且所有数据清楚标识为 placeholder。

**❌ Quote slop**——编造的用户评价 / 名人名言装饰
- **风险**：虚构评价会伪装成真实证据，损害可信度。
- **处理方式**：没有真实 quote 时，使用 `[此处放真实客户评价]` 占位，或询问用户补充。
- **可用条件**：用户提供真实评价，或明确说明这是示意稿。

### 决策速查表

> 当想加入某个常见视觉元素时，先判断它是否服务于信息层级、品牌表达或用户任务。若只是为了“显得丰富”，默认不加。

| 想加入 | 默认处理 |
|---|---|
| 渐变 | 默认不使用，除非有明确品牌或信息层级理由 |
| Emoji | 默认不使用 |
| 圆角卡片 + 左 border accent | 默认不使用，换其他强调方式（背景色对比 / 字重对比 / 分隔线） |
| SVG 画 hero 插画 | 默认不使用，用占位符 |
| 装饰性 quote | 不编造评价；没有真实quote时使用占位，必要时询问用户 |
| 一排 icon features | 先判断icon是否帮助理解；如果只是装饰，默认不用 |
| Inter / Roboto / Fraunces / Space Grotesk | 根据品牌和场景换更有特点的（见上方字体增补区推荐） |
| 紫色渐变 | 优先选择有来源的配色，换有根据的配色（品牌色 / 参考产品吸色 / Radix Colors / Tailwind palette） |
| Bento grid | 默认不使用，除非信息真的有明显强弱层级和模块关系 |
| 大 hero + 3-column 模板 | 重新组织叙事结构，避免直接套用默认 SaaS 模板 |

## 五、增量设计准则

给已有 UI 做增量时，**先理解它的视觉语汇并遵循之**：

- 文案风格
- 配色
- 语气
- 悬停/点击态
- 动画风格
- 阴影 + 卡片 + 布局模式
- 信息密度

将关键观察简短说给用户：当前界面使用了什么视觉语汇、哪些规则需要延续、哪些地方可能需要调整。只输出与设计决策有关的观察，不展开内部推理。

## 六、配色原则

1. 优先使用品牌 / 设计系统里已有的颜色
2. 如果太受限，用 **oklch** 定义与现有调色板和谐的新色
3. 别从零凭空发明颜色

## 七、输出格式与尺寸

根据交付物类型选择正确的尺寸和格式：

| 交付类型 | 尺寸 | 备注 |
|---------|------|------|
| 社交媒体帖子 | 1080×1080 / 1080×1920 | 平台特定 |
| 演示幻灯片 | 1920×1080 (16:9) / 1024×768 (4:3) | 匹配设置 |
| 横幅广告 | 各种标准尺寸 | 用户指定 |
| 邮件头部 | 最大 600px 宽 | 邮件客户端兼容 |
| 印刷品 | 300 DPI，指定物理尺寸 | 注意 CMYK |

## 八、HTML/前端交付规范

- 文件要有意义的名字，如 `Landing Page.html`
- 大改文件时先复制再改，保留旧版本
- 避免写超过 1000 行的大文件——拆成多个小文件再汇总
- 播放位置（幻灯片、视频）要持久化到 localStorage
- 绝不用 `scrollIntoView`——会搞乱宿主 web app
- 面向用户的交付物要标记 asset，支撑文件则省略
- 从设计系统拷贝需要的资产，别直接引用外部路径；不整包拷贝（>20 文件）
- 为所有图片提供 alt 文本
- 图片缺失时显示样式化占位符，不留断裂的 `<img>` 标签

### React + JSX 注意事项
- 全局 style 对象必须用组件名命名（`const headerStyles = {}`），**绝不写** `const styles = {}`
- 多个 Babel script 文件之间组件不共享作用域——通过 `Object.assign(window, {...})` 共享
- script 引入不要用 `type="module"`

## 九、文案准则

- 用用户的语言写作（匹配输入语言）
- 对话式自然语气，避免企业腔（除非品牌要求）
- 标题简短有力
- 正文可扫描——短段落，适当用要点
- 默认不使用"Lorem ipsum"。它会让交付物显得未完成，也会削弱用户对内容结构的判断。没有真实文案时，使用清晰占位符，例如 `[此处放产品描述]`

---

## 十、品牌与版权规则

- 不得复刻可辨识为现有受版权保护产品的仿制品
- 除非：用户拥有权利 / 有明确授权 / 用于教育目的并注明出处
- 交付酷似现有产品的设计前，自问：
  - 理性人会把这和某产品搞混吗？
  - 是否未经授权使用了某公司的独特视觉语言？
  - 是复现特定交互模式，还是只是通用 UX 惯例？
- 任一为是 → 停下来向用户确认

## 十一、提问协议

### 提问当
- 需求模糊或不完整
- 存在多种有效方法且用户偏好重要
- 缺少品牌/设计系统参考
- 技术约束不清晰

### 不提问当
- 答案在提供的文档中（先读！）
- 问题关于基本设计原则
- 用户已回答过
- 提问只会延迟而不增加价值

### 提问形式（交互硬约束）

所有触发提问的动作必须通过 `INTERACTIONS.md §1` 定义的 `<question-form>` 发起。该规则属于硬约束，字段约束、一轮交互预算、选项密度和自动继续规则均以 `INTERACTIONS.md §1` 为准。

必须：
- 使用结构化 `<question-form>`，由前端按 schema 渲染为可点击卡片
- 优先提供可点击选项；必要时保留一个补充输入
- 在缺失信息不影响推进时，按自动继续规则继续

不得：
- 用纯 markdown 散文向用户提问
- 用 markdown 列表枚举选项，让用户手动回复“我选第 X 项”
- 连续抛出多个自由文本开放问题，替代结构化问题表单
